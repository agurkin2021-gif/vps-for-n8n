הרחבת משאבים

מצב תור (Queue Mode) ב-n8n

מצב תור מפריד בין הרצת תהליכי עבודה לבין התהליך הראשי של n8n. המופע הראשי מקבל טריגרים ויוצר משימות הרצה; ‏Redis מנהל את התור, ה-Workers מבצעים את המשימות ו-PostgreSQL שומר את נתוני תהליכי העבודה וההרצות המשותפים.

החלטה מהירה

האם אתם באמת צריכים מצב תור?

הישארו במצב רגיל כאשר

מופע יחיד מטפל בנוחות גם בהרצות בשעות השיא, וצריכת ה-CPU, ה-RAM וזמני ההרצה נשארים יציבים. מצב תור יוסיף רכיבים שעדיין אינכם זקוקים להם.

שקלו מצב תור כאשר

הרצות מקבילות מתמשכות יוצרות תחרות על המשאבים, זמן ההרצה מתארך בעומס, או שנדרשת הגדלת קיבולת באמצעות הפעלת כמה Workers.

הגדילו תחילה את משאבי השרת כאשר

צוואר הבקבוק הוא פשוט מחסור ב-CPU או ב-RAM, ומופע גדול יותר עדיין יכול לטפל בעומס העבודה ללא קושי.

מדדו לפני שינוי הארכיטקטורה

השתמשו במדדים של שיא ההרצות המקבילות, CPU, ‏RAM, משך ההרצות, עומק התור והעומס על מסד הנתונים כדי להצדיק את המעבר.

ארכיטקטורה

כיצד פועל מצב תור ב-n8n

1 · תהליך ראשימקבל טריגרים מתוזמנים, Webhooks ובקשות לתהליכי עבודה, ויוצר משימת הרצה במקום לבצע בעצמו את ההרצה בסביבת הייצור.
2 · Redisמשמש כמתווך הודעות. הוא מחזיק הודעות על הרצות ממתינות, כדי שה-Worker הפנוי הבא יוכל לקבל משימה.
3 · Workerמקבל את מזהה ההרצה, טוען את נתוני תהליך העבודה ממסד הנתונים המשותף, מבצע את התהליך וכותב בחזרה את התוצאה.
4 · PostgreSQLמספק נתונים משותפים ומתמשכים של תהליכי עבודה והרצות. מצב תור מבוזר אינו נתמך עם SQLite.

דרישות יסוד

מה נדרש בכל התקנה של מצב תור

Redis

התהליך הראשי וכל ה-Workers זקוקים לגישה אמינה לשירות Redis המנהל את התור.

PostgreSQL

התהליך הראשי וה-Workers חייבים להשתמש באותו מסד נתונים. מצב תור הוא ארכיטקטורה מבוזרת, ואין לבסס אותו על SQLite.

הגדרות n8n תואמות

התהליך הראשי וה-Workers צריכים לפעול במצב תור ולהשתמש בהגדרות משותפות לגישה ל-Redis, ל-PostgreSQL ולפרטי גישה מוצפנים.

קיבולת Workers

ה-Workers זקוקים לדי CPU ו-RAM עבור תהליכי העבודה שהם מריצים. הוספת תהליכים אינה מבטלת את עלות המשאבים של כל הרצה.

הפעלת מצב תור במערכת קיימת באירוח עצמי. תחילה ודאו שהשירות הראשי של n8n וכל Worker יכולים להגיע לאותו מסד PostgreSQL ולאותו Redis ברשת פרטית. הגדירו את EXECUTIONS_MODE=queue גם בתהליך הראשי וגם ב-Workers, וספקו את QUEUE_BULL_REDIS_HOST=redis ו- QUEUE_BULL_REDIS_PORT=6379 כאשר redis הוא השם האמיתי של השירות בקובץ Compose שלכם. השתמשו ב- DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres ובערכים תואמים של DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER ו- DB_POSTGRESDB_PASSWORD בכל התהליכים; החליפו את שמות השירותים שבדוגמה בשמות אצלכם. ספקו לכל התהליכים את N8N_ENCRYPTION_KEY הקיים והמדויק. לעולם אל תפרסמו פורטי מארח של Redis או PostgreSQL רק לצורך חיבור בין קונטיינרים באותה רשת Compose.

הפעילו תהליך ביצוע, ולא עורך נוסף. הוסיפו שירות Worker של n8n עם אותה גרסת תמונה מקובעת ועם ההגדרות המשותפות של התהליך הראשי, אך הפעילו אותו באמצעות הפקודה worker אם נתתם לשירות את השם n8n-worker, הפעילו אותו באמצעות docker compose up -d n8n-worker. לאחר שווידאתם שהרצות מתבצעות בפועל ב-Worker יחיד, תוכלו להשתמש בפקודה docker compose up -d --scale n8n-worker=2 כדי להפעיל Worker שני מאותו שירות. אלה תוספות למערכת קיימת שהוגדרה כראוי של Compose, ולא קובץ התקנה עצמאי. שמרו על נפחי האחסון המתמשכים, פרוקסי ה-HTTPS, הסודות והגיבויים הקיימים.

קטע מקובץ Compose עבור מצב תור במערכת קיימת. שלבו את הדוגמה שלהלן בתוך הקובץ הקיים compose.yaml; היא אינו אינה התקנה עצמאית מלאה. ההנחה היא שכבר פועלים אצלכם שירותים פרטיים ומתמשכים של postgres ו- n8n וכן קיים N8N_VERSION המוגדר בסביבה, לצד סוד שמור ומוגן של POSTGRES_PASSWORD ומפתח הצפנה מקורי N8N_ENCRYPTION_KEYהתאימו את שמות השירותים, נפחי האחסון, מסד הנתונים וגרסת n8n לפרויקט הקיים. הוסיפו גם את הגדרות Redis למצב תור ואת EXECUTIONS_MODE=queue לשירות הראשי הקיים, כפי שהוסבר למעלה.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

בקטע הזה אין פרסום של פורט מארח עבור Redis או ה-Worker. שמירה מתמשכת של Redis במצב Append-Only היא שכבת התאוששות נוספת, אינו ולא תחליף לגיבויים מחוץ לשרת. השאירו את הגדרות ה-HTTPS והאימות הקיימות ללא שינוי. עבור צומתי Code הזקוקים למנגנוני הרצת משימות חיצוניים, הגדירו את תהליכי ה-Runner בנפרד עבור ה-Workers; מצב תור עצמו אינו מחליף מנגנוני הרצת משימות.

מעבירים מופע SQLite קיים? אל תשנו רק את DB_TYPE ותפעילו את המערכת מול מסד PostgreSQL ריק: פעולה כזו אינה מעבירה את תהליכי העבודה ופרטי הגישה הישנים. לפני המעבר גבו את מסד הנתונים המקורי ואת תיקיית הנתונים המתמשכת .n8n ואת מפתח ההצפנה המקורי. השתמשו בתהליך ייצוא/ייבוא או העברה שנתמך על ידי n8n, ולאחר מכן ודאו שתהליכי העבודה ופרטי הגישה המוצפנים תקינים בשרת יעד נפרד. שמרו את הקבצים המקוריים כדי שתוכלו לחזור לאחור, והיעזרו במדריך הגיבוי והשחזור המקושר להלן להכנת ההתאוששות. לעולם אל תמחקו את database.sqlite כקיצור דרך.

הרצות מקבילות ב-Workers

הרחבת Workers תלויה במספרם ובמספר המשימות לכל Worker

כל Worker יכול לעבד כמה משימות במקביל. ברירת המחדל הנוכחית של n8n היא 10 הרצות מקבילות לכל Worker, ובתיעוד מומלץ ערך של 5 ומעלה. מספר גדול של Workers עם קיבולת מקבילה נמוכה מאוד עלול ליצור חיבורים מיותרים למסד הנתונים ולמצות את מאגר החיבורים שלו.

להגדיל את מספר ההרצות המקבילות כאשר

ל-Worker יש משאבי CPU ו-RAM פנויים, ותהליכי העבודה בעיקר ממתינים לשירותים חיצוניים במקום למצות את כוח העיבוד או את הזיכרון.

הוסיפו Workers כאשר

תהליך Worker יחיד הופך לצוואר בקבוק, ולמסד הנתונים, ל-Redis ולתשתית יש יכולת לתמוך בהרצות מקבילות נוספות.

צמצמו את ההרצות המקבילות כאשר

תהליכי העבודה צורכים הרבה זיכרון או CPU, ומשימות מקבילות גורמות לתחרות על משאבים, ללחץ זיכרון (OOM) או לזמני הרצה לא יציבים.

עקבו אחר PostgreSQL

הוספת Workers והגדלת מספר ההרצות המקבילות מגבירות את הפעילות במסד הנתונים. הגדלת קיבולת ההרצה ללא הגדלת קיבולת מסד הנתונים עלולה רק להעביר את צוואר הבקבוק למקום אחר.

בדקו איזו מגבלת הרצות מקבילות חלה בפועל. אפשר להפעיל Worker באמצעות n8n worker --concurrency=5, או באמצעות פקודת Worker מקבילה בשירות Compose שלכם. אם N8N_CONCURRENCY_PRODUCTION_LIMIT מוגדר במפורש לערך שאינו -1, הגדרה זו מקבלת עדיפות במצב תור; אחרת n8n משתמש בערך של ה-Worker עבור --concurrency או בברירת המחדל שלו, 10. אל תכפילו את מספר ה-Workers בברירת המחדל ותקראו לתוצאה תפוקה מובטחת: הקיבולת בפועל תלויה במשך המשימות, ב-CPU, בזיכרון, בממשקי API חיצוניים ובחיבורים ל-PostgreSQL.

Webhooks

מצב תור עשוי להוסיף השהיה בהעברת משימות לביצוע

התהליך הראשי או תהליך ה-Webhook מקבלים את בקשת ה-HTTP, אך Worker מבצע את תהליך העבודה. ההעברה דרך Redis מוסיפה תקורה מסוימת. עבור Webhooks הרגישים להשהיה, מדדו את זמן התגובה מקצה לקצה במקום להניח שיותר Workers יאיצו אוטומטית כל בקשה.

קבלההתהליך הראשי או תהליך ה-Webhook מקבל את הבקשה.
תורההרצה מועברת ל-Redis.
ביצועWorker פנוי מריץ את תהליך העבודה.
מועד התגובההתוצאה מועברת בחזרה דרך מסלול התור כאשר הדבר נדרש.

נתבו תעבורת Webhook לתהליך המתאים. כאשר משתמשים בתהליכי n8n webhook ייעודיים מאחורי פרוקסי הפוך או מאזן עומסים, נתבו את נתיבי הייצור /webhook/* ו- /webhook-waiting/* אל מעבדי ה-Webhook, והשאירו את /webhook-test/*, את העורך ואת בקשות ה-API בתהליך הראשי. אל תוסיפו את התהליך הראשי למאגר איזון העומסים של Webhooks בסביבת ייצור, אלא אם בחרתם במודע לקבל עליו את העומס הנוסף. תהליך עבודה עם תגובה ל-Webhook עשוי להשאיר את הלקוח בהמתנה עד שה-Worker יסיים וישיב. לכן מצב תור אינו מבטיח תגובות HTTP מיידיות או היעדר פקיעות זמן. בדקו את הבקשה החיצונית ואת התגובה בפועל לפני העברת התעבורה.

נתונים בינריים

אל תזניחו את האחסון המשותף

מגבלה של אחסון במערכת הקבצים

מצב תור אינו תומך באחסון נתונים בינריים במערכת הקבצים כמודל אחסון מתמשך משותף ל-Workers מבוזרים.

אחסון בינרי חיצוני

כאשר תהליכי עבודה חייבים לשמור נתונים בינריים בין Workers מבוזרים, השתמשו בפתרון אחסון הנגיש לכל המופעים הנדרשים, למשל אחסון אובייקטים חיצוני נתמך.

תגובות Webhook גדולות

תגובות Webhook שמופקות על ידי Workers מועברות בחזרה לתהליך שקיבל את הבקשה. גופי תגובה גדולים עלולים להגביר את לחץ הזיכרון על Redis ומחייבים תכנון מתאים של אחסון התגובות.

תכננו לפני פיזור Workers בין שרתים

תהליכי עבודה שתלויים במידה רבה בקבצים מקומיים מחייבים תכנון מחדש של אחסון משותף לפני פיזור ה-Workers בין מכונות.

מגבלות על תגובות Webhook גדולות. בתיעוד הנוכחי של n8n מצוין N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX ערך ברירת מחדל של 64 MiB לתגובה של Worker הנשלחת בחזרה דרך התור. Redis עשוי להחזיק כמה עותקים של נתונים בזמן העברה, ולכן יש להקצות בקירוב פי 1.5 מגודל התגובה בזיכרון Redis לכל תגובה גדולה במקביל. ללא העברת האחסון למקום אחר, תגובה שגודלה חורג מהמגבלה תיכשל; הוספת Workers לא תהפוך אותה למהירה יותר.

מגבלות גרסה ורישוי. החל מגרסת n8n 2.34.0, ‏Workers יכולים להשתמש ב- N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true כדי להעביר גופי תגובת Webhook גדולים מדי לאחסון בינרי משותף שניתן לקריאה, אך תחילה יש לשדרג את כל התהליכים הראשיים ומעבדי ה-Webhooks לגרסה 2.34.0 ומעלה. הגדרת N8N_DEFAULT_BINARY_DATA_MODE חייבת לאחסן נתונים בפועל ולהיות נגישה לקריאה לכל תהליך משתתף. אחסון בינרי חיצוני ב-S3 וב-Azure דורש רישיון תקף לאירוח עצמי מסוג Business או Enterprise ; אל תניחו שמהדורת Community מאפשרת להפעיל אותם. מצב database של אחסון בינרי יכול להעביר תגובה גדולה מדי ללא אחסון חיצוני בתשלום, אך המופע הראשי טוען את כל גוף התגובה השמור לזיכרון, ולאחסון במסד הנתונים יש מגבלת גודל קובץ משלו. עבור העברה של אחסון גופי תגובות בלבדמתאר n8n גם אפשרות לאחסון filesystem משותף כאשר כל המופעים מחברים את אותו דיסק, אך מציין במפורש שהסידור הזה אינו מומלץ. אל תבלבלו בין אפשרות מיוחדת זו להעברת גופי תגובה לבין תמיכה באחסון בינרי מתמשך המבוסס על מערכת קבצים בהתקנת מצב תור מבוזרת. לפני הפעלת ההעברה בדקו את המהדורה, הגרסה ותצורת האחסון שלכם.

ניטור

בדקו אם התור אכן משפר את הביצועים

עומק התור

תור שגדל מהר יותר מהקצב שבו Workers מסיימים משימות מעיד על קיבולת הרצה לא מספקת או על צוואר בקבוק בהמשך תהליך העיבוד.

CPU ו-RAM של Workers

מדדו את ניצול המשאבים ואת שיאי צריכת הזיכרון לכל Worker. ‏Workers פנויים לצד תור הולך וגדל מעידים על מגבלה אחרת.

השהיית תחילת הרצה

עקבו אחר ההשהיה בין יצירת משימת הרצה לבין תחילת ביצועה בפועל, ולא רק אחר זמן הריצה של תהליך העבודה.

בדיקות תקינות

נקודות קצה לבדיקת תקינות של Worker יכולות לדווח אם התהליך פועל ואם החיבורים שלו למסד הנתונים ול-Redis מוכנים.

ודאו שה-Worker מבצע הרצות בפועל, ולא רק שהקונטיינר מסומן כתקין. במערכת Compose שהוגדרה כראוי, בדקו את docker compose ps ו- docker compose logs --tail=100 n8n-worker (החליפו את שם השירות אם הוא שונה). הריצו תהליך עבודה לא מזיק שפורסם בסביבת הייצור באמצעות טריגר מתוזמן או Webhook לבדיקה; לאחר מכן התאימו את ההרצה בתצוגת Executions של n8n לעיבוד בפועל ביומני ה-Worker. עורך שנפתח בהצלחה, קונטיינר Redis שפועל או משימה שממתינה בתור לבדם אינו אינם מוכיחים ש-Worker ביצע את המשימה.

בדקו את התלויות ואת מוכנות השירותים. כאשר משתמשים בשמות השירותים המוגדרים כברירת המחדל בדוגמה, הפקודה docker compose exec -T redis redis-cli ping אמורה לקבל PONG כאשר אימות Redis מאפשר זאת, והפקודה docker compose exec -T postgres pg_isready -U n8n -d n8n בודקת את מוכנות PostgreSQL (התאימו את פרטי הגישה ואת שמות השירותים). הפעילו את QUEUE_HEALTH_CHECK_ACTIVE=true ב-Worker כאשר אתם זקוקים לנקודות הקצה הפרטיות שלו עבור /healthz ו- /healthz/readiness ; נקודת הקצה לבדיקת מוכנות בודקת את החיבור ל-Redis ולמסד הנתונים. אל תחשפו את נקודות הקצה של ה-Worker לציבור רק כדי לנטר אותן.

הרצות ידניות הן בדיקה נפרדת. כברירת מחדל OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, ולכן הפעלה ידנית של תהליך עבודה מהעורך עשויה להתבצע בתהליך הראשי גם כאשר מצב תור הוגדר נכון. הגדירו ערך true רק אם אתם מתכוונים לשלוח הרצות ידניות ל-Workers ובדקתם את השינוי בסביבת בדיקה. ‏Workers של מצב תור שונים גם ממנגנוני הרצת המשימות החיצוניים של n8n, שדורשים הגדרות נפרדות להפעלת צומתי Code.

טפלו בכל פעם בצוואר בקבוק אחד

שלב 1מופע n8n יחיד עם PostgreSQL; מדדו CPU, ‏RAM ומספר הרצות מקבילות בשיא.
שלב 2הגדילו את משאבי ה-VPS כאשר הרחבה אנכית עדיין פותרת את צוואר הבקבוק שנמדד.
שלב 3הוסיפו Redis ו-Workers כאשר עומס מקביל מתמשך מצדיק הרצה מבוזרת.
שלב 4הוסיפו Workers או כווננו את מספר המשימות המקבילות לכל Worker תוך ניטור PostgreSQL, ‏Redis והשהיית ההרצות.
שלב 5פזרו רכיבים בין שרתים רק כאשר דרישות הקיבולת, הזמינות או התפעול מצדיקות את המורכבות הנוספת.

גבולות הזמינות הגבוהה

מצב תור מרחיב את יכולת ההרצה, אך אינו מבטיח אוטומטית זמינות גבוהה לתהליך הראשי

שתפו את מפתח ההצפנה

כל Worker חייב להשתמש באותו N8N_ENCRYPTION_KEY שבו משתמש המופע הראשי, כדי שה-Workers יוכלו לפענח את פרטי הגישה הנדרשים להרצות תהליכי עבודה.

שמרו על התאמה בין הגרסאות

התהליך הראשי, מעבדי ה-Webhooks וה-Workers צריכים לפעול באותה גרסת n8n. שילוב גרסאות שונות עלול ליצור התנהגות לא תואמת בזמן עדכונים מדורגים.

מעבדי Webhooks הם שכבת הרחבה נפרדת

כאשר כמות בקשות ה-Webhook הנכנסות הופכת לצוואר בקבוק, אפשר למקם מעבדי Webhooks ייעודיים מאחורי מאזן עומסים בעוד שה-Workers מבצעים את תהליכי העבודה. אל תוסיפו שכבה זו ללא נתוני עומס שמצדיקים אותה.

Multi-main היא יכולת נפרדת

הפעלת כמה תהליכים ראשיים להשגת זמינות גבוהה אינה זהה למצב תור רגיל. לפי התיעוד הנוכחי של n8n, ‏multi-main היא תכונה של מהדורת Enterprise באירוח עצמי, הדורשת גם מאזן עומסים והגדרות נוספות לניהול סשנים.

הארכיטקטורה וההגדרות הרשמיות של מצב תור

שאלות נפוצות

שאלות נפוצות על מצב תור ב-n8n

האם מצב תור ב-n8n מחייב Redis?

כן. Redis הוא מתווך ההודעות שמתאם את ההרצות הממתינות בין המופע הראשי ל-Workers.

האם מצב תור יכול להשתמש ב-SQLite?

לא בארכיטקטורת מצב תור מבוזרת. התהליך הראשי וה-Workers זקוקים לגישה משותפת למסד נתונים, ו-n8n מתעד את PostgreSQL כמסד הנתונים למבנה הזה.

כמה Workers כדאי להפעיל?

אין מספר שמתאים לכולם. התחילו לפי מספר ההרצות המקבילות וניצול ה-Workers שנמדדו בפועל, והוסיפו קיבולת תוך ניטור PostgreSQL, ‏Redis, ‏CPU, ‏RAM ועומק התור.

מה פירוש מספר הרצות מקבילות ל-Worker ב-n8n?

זהו מספר המשימות ש-Worker יכול לעבד במקביל. ברירת המחדל הנוכחית היא 10, ו-n8n ממליץ על 5 הרצות מקבילות ומעלה לכל Worker במקום ליצור Workers רבים בעלי מקביליות נמוכה.

האם כדאי להפעיל מצב תור על VPS קטן?

רק כאשר עומס העבודה מצדיק זאת. התקנה קטנה שפועלת היטב במופע יחיד תהיה בדרך כלל פשוטה יותר לתפעול ללא Redis וללא Workers נפרדים.
