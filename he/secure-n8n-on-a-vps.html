אבטחת סביבת ייצור

אבטחת n8n על שרת VPS

כדי לאבטח n8n על VPS, אל תחשפו לאינטרנט את n8n (5678), ‏PostgreSQL (5432) ואת Redis האופציונלי (6379). השתמשו בפרוקסי הפוך עם HTTPS, במפתחות SSH ובאימות רב-שלבי (MFA); שמרו על מפתח ההצפנה, אמתו בקשות Webhook, הגבילו יכולות מסוכנות של תהליכי עבודה ובצעו ביקורת אבטחה למופע שהותקן. אבטחו את העורך בנפרד מנתיבי ה-Webhooks הציבוריים. ‏HTTPS לבדו אינו מאבטח את השירותים המחוברים.

בחירת VPS עבור n8n

קישור שותפים: ייתכן שנקבל עמלה על רכישות.

רשימת בדיקה מהירה

אמצעי האבטחה המינימליים לפני חשיפה לאינטרנט

התחילו בבדיקת הפורטים הנגישים מבחוץ, הגדרת HTTPS, אימות הגישה למנהלי המערכת, הפעלת MFA והגנה על פרטי הגישה השמורים. אמתו כל בקשת Webhook נכנסת לפני שתוכל להפעיל פעולות רגישות. לאחר שינוי הרשאות הגישה, ודאו שהמשתמשים המורשים והאינטגרציות החיצוניות עדיין פועלים, ואז הריצו את ביקורת האבטחה של n8n.

HTTPS בלבד

הציבו את n8n מאחורי פרוקסי הפוך עם TLS שהוגדר כראוי, והשתמשו באופן עקבי בכתובת HTTPS הציבורית עבור העורך וה-Webhooks.

פתיחת פורטים מינימלית

חשפו רק את הפורטים הנדרשים לתעבורה ציבורית. השאירו את PostgreSQL, ‏Redis ופורטי היישום הפנימיים מחוץ להישג האינטרנט הציבורי.

הקשחת SSH

השתמשו במפתחות לצורך גישה מנהלית, הגבילו את המשתמשים שיכולים להתחבר והתקינו עדכוני אבטחה למערכת ההפעלה.

הגנה על פרטי גישה

שמרו את מפתח ההצפנה של n8n קבוע וסודי. התייחסו לקובצי סביבה, להרשאות גישה למסד הנתונים ולעותקי גיבוי כאל נכסים רגישים.

הגנה בגבול הרשת

פרוקסי הפוך, HTTPS וכותרות מהימנות

סיום חיבור TLS

השתמשו בפרוקסי הפוך כגון Nginx, ‏Caddy או Traefik לטיפול בחיבורי HTTPS. הפנו בקשות HTTP לא מאובטחות ל-HTTPS, ואל תחשפו ישירות את פורט היישום של n8n כאשר הפרוקסי הוא נקודת הכניסה המתוכננת.

הגדרת הפרוקסי

כאשר n8n פועל מאחורי פרוקסי הפוך, הגדירו נכון את מספר מעברי הפרוקסי והעבירו את כותרות הבקשה ש-n8n צריך כדי לזהות את פרטי הבקשה המקורית של הלקוח.

קובצי Cookie מאובטחים

הגישו את העורך באמצעות HTTPS כדי שקובצי ה-Cookie של האימות יהיו מאובטחים. אל תעקפו תצורת TLS לא תקינה באמצעות החלשת אבטחת קובצי ה-Cookie.

כתובת Webhook

הגדירו את כתובת ה-Webhook הציבורית לפי שם מארח HTTPS שניתן לגשת אליו מבחוץ, כדי שנקודות הקצה שייווצרו לא יפנו לקונטיינר פנימי או לכתובת HTTP.

הגבילו את הגישה לעורך בלי לשבש את ה-Webhooks. ככל שניתן, הגבילו את הגישה לניהול באמצעות VPN, מדיניות כתובות IP מהימנות או פרוקסי שדורש אימות. ייתכן שנקודות קצה של Webhooks ציבוריים וכתובות חזרה של OAuth חייבות להישאר נגישות. לפני אכיפת כלל בפרוקסי בדקו גם כניסה מורשית לעורך וגם בקשת חזרה חיצונית אמיתית. קבלו כותרות של כתובת הלקוח רק מפרוקסי מהימן, ולא מכותרות שרירותיות של בקשות.

אמתו את שולחי בקשות ה-Webhook: בצומת Webhook בחרו אימות Basic, ‏Header או JWT במקום None, כאשר השירות השולח תומך בכך. השתמשו בהגדרת רשימת כתובות IP מורשות לפי הצורך, ואמתו חתימות של הספק כאשר האינטגרציה תומכת בבקשות חתומות. כתובת שקשה לנחש אינה תחליף לאימות. הגדירו מגבלות קצב בפרוקסי כאשר הדבר מתאים, וודאו שהן אינן חוסמות עומסים לגיטימיים. ראו את אפשרויות האימות הרשמיות של Webhook.

הקשחת VPS

צמצום שטח התקיפה של השרת

חומת אש

חסמו כברירת מחדל תעבורה נכנסת שלא נתבקשה ואפשרו רק שירותים שחייבים להיות נגישים. פורטים של מסד הנתונים ו-Redis אמורים בדרך כלל להישאר ברשתות פרטיות או מקומיות.

SSH

העדיפו מפתחות SSH על פני סיסמאות, השביתו דרכי כניסה מיותרות והגבילו גישת מנהלים. יש לפקח בקפידה על הרשאות השקולות ל-root.

עדכוני מערכת ההפעלה

התקינו עדכוני אבטחה לשרת Linux ולסביבת הרצת הקונטיינרים. הקשחת היישום אינה מפצה על מערכת הפעלה חשופה או מיושנת.

חשיפת קונטיינרים

פרסמו רק פורטים שחייבים להיות נגישים מהמארח. שירותים פנימיים צריכים לתקשר ברשתות Docker פרטיות, ולא דרך ממשקים ציבוריים.

בדקו לפני שינוי חומת האש או הגדרות SSH: בדקו פורטים שמאזינים לחיבורים באמצעות sudo ss -lntp, פורטים שפורסמו על ידי Docker באמצעות docker compose ps מתיקיית הפרויקט, ואת מדיניות חומת האש של השרת באמצעות sudo ufw status verbose אם אתם משתמשים ב-UFW. לפני השבתת כניסה בסיסמה, ודאו את פורט ה-SSH בפועל והתחברו בהצלחה באמצעות מפתח בחיבור נפרד. פורטים ש-Docker מפרסם עשויים לעקוף כללי UFW; הצגת מצב חומת האש לבדה אינה מוכיחה שפורט 5678 פרטי. בדקו את הנגישות בפועל מבחוץ. ראו את ההסתייגות לגבי Docker ו-UFW.

בדקו שעדכוני האבטחה האוטומטיים של Ubuntu פועלים במקום להניח זאת: בדקו את apt-config dump APT::Periodic::Unattended-Upgrade ואת קובץ היומן /var/log/unattended-upgrades/unattended-upgrades.log. אם שדרוגי האבטחה האוטומטיים מושבתים, הפקודה sudo dpkg-reconfigure unattended-upgrades מציגה חלון הגדרות נתמך. בדקו כיצד יתבצעו הפעלות מחדש של השרת והשירותים לפני הפעלת האפשרות ב-VPS פעיל. עדכוני Ubuntu באמצעות APT אינו אינם מעדכנים אוטומטית את תמונת Docker של n8n או כל מאגר תוכנה חיצוני. ראו תיעוד העדכונים האוטומטיים של Ubuntu.

ניטור אופציונלי של ניסיונות כניסה חוזרים ל-SSH: Fail2Ban יכול לזהות ניסיונות כניסה חוזרים שנכשלו ב-SSH. אם הוא מותקן ומוגדר ל-SSH, בדקו את הגדרת ה-jail באמצעות sudo fail2ban-client status sshd וודאו שהוא קורא את יומן האימות האמיתי של SSH ומתאים לפורט שהוגדר. זהו אמצעי משלים למפתחות SSH ולהגבלות רשת, ולא תחליף להם. אל תעתיקו פורט SSH קבוע או כלל חסימה לפני בדיקת הגישה הקיימת. ראו את הנחיות Ubuntu להקשחת SSH.

מסד נתונים ו-Redis

השאירו שירותי צד שרת ברשת פרטית

בהתקנת Docker Compose טיפוסית, PostgreSQL ו-Redis של מצב התור צריכים להיות נגישים לקונטיינרים המתאימים דרך רשת פרטית, ולא דרך פורטים שמפורסמים במארח. ודאו באמצעות docker compose ps שהפורטים 5432 ו-6379 אינם מפורסמים לציבור. בדקו בנפרד גם את חשיפת חומת האש של ה-VPS או הענן. מדיניות רשת אינה תחליף לפרטי גישה למסד הנתונים עם ההרשאות המינימליות הדרושות.

PostgreSQLקשרו אותו לממשק פרטי או לרשת קונטיינרים, אלא אם נדרשת במפורש גישה מרחוק והיא מאובטחת בנפרד.
RedisRedis המשמש במצב תור הוא רכיב תשתית, ולא נקודת קצה ציבורית. הגבילו את הגישה אליו ברשת לרכיבי n8n שזקוקים לו.
פרטי גישההשתמשו בפרטי גישה ייעודיים למסד הנתונים, עם ההרשאות הנחוצות ליישום בלבד, ושמרו עליהם מחוץ למערכת בקרת הגרסאות.
תעבורהכאשר תעבורת מסד הנתונים עוברת ברשתות לא מהימנות, השתמשו בהצפנת תקשורת מתאימה ואל תסתמכו רק על הצפנת פרטי הגישה ברמת היישום.

סודות הגישה של n8n

הגנה על מפתח ההצפנה ועל פרטי הגישה

מפתח הצפנה

n8n מצפין את פרטי הגישה השמורים באמצעות מפתח ההצפנה של המופע. שמרו על אותו מפתח בכל הפעלה מחדש ובכל ה-Workers, והגנו עליו בנפרד מתוכן היישום הרגיל.

סודות בסביבת ההרצה

אל תעלו סיסמאות, אסימוני גישה או את מפתח ההצפנה למאגר ציבורי. הגבילו את הגישה לקובצי הסביבה ולסודות ההתקנה.

גישת משתמשים

אפשרו גישה לעורך רק למשתמשים מהימנים. תהליכי עבודה יכולים להתחבר למערכות רגישות, לעבד סודות ולהפעיל צמתים בעלי יכולות נרחבות.

היקף הרשאות הגישה

כאשר אפשר, השתמשו בחשבונות שירות ובאסימוני API בעלי הרשאות מצומצמות. תהליך עבודה שנפרץ לא אמור לקבל אוטומטית גישה רחבה למערכות שאינן קשורות אליו.

הגדרות n8n שכדאי לבדוק: N8N_BLOCK_ENV_ACCESS_IN_NODE=true מונע מצומתי Code ומביטויים גישה לערכי משתני הסביבה; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true מבקש הרשאות לקובץ ההגדרות המוגבלות לבעלים בלבד. שמרו את N8N_ENCRYPTION_KEY קבוע ומגובה באופן מאובטח: ‏n8n יכול ליצור מפתח אקראי בהפעלה הראשונה, אך אובדנו עלול להפוך פרטי גישה מוצפנים קיימים לבלתי שמישים. אל תחליפו מפתח הצפנה של סביבת ייצור ללא הליך מוסדר; השתמשו בתהליך החלפת מפתחות שנתמך רשמית. חסימת גישה למשתני סביבה עלולה לשבש אינטגרציות קיימות, לכן בדקו אותה לפני שינוי בסביבת הייצור. ראו את הגדרות משתני האבטחה של n8n.

סיכונים בתהליכי עבודה

צמתים יכולים להרחיב את גבולות הגישה

באירוח עצמי תהליכי העבודה מקבלים יכולות נרחבות. הרצת קוד, גישה למעטפת המערכת, בקשות HTTP לכתובות שרירותיות וצומתי קהילה של צד שלישי עלולים להגדיל את הסיכון. השביתו יכולות מיותרות ובדקו תהליכי עבודה שיובאו ממקורות לא מהימנים לפני הפעלתם.

השתמשו באמצעי בקרה נתמכים ומדויקים: הגדירו את NODES_EXCLUDE כמערך JSON של צמתים שיש להשבית, כגון n8n-nodes-base.executeCommand ו- n8n-nodes-base.readWriteFile, אם אין בהם צורך. בגרסאות חדשות חלק מהצמתים המסוכנים כבר חסומים כברירת מחדל; בדקו את הרשימה בפועל לפני שינוי. ראו את תיעוד החרגת הצמתים הרשמי.

החל מגרסת n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true מאפשר בדיקות של בקשות HTTP יוצאות לכתובות פנימיות, לכתובות Loopback ולטווחי כתובות מטא-נתונים. ייתכן שתהליכי עבודה תקינים המשתמשים ב-API פנימי יפסיקו לפעול; בעת הצורך התירו באופן מצומצם רק יעדים שבשליטתכם. השאירו הפרדת רשתות כאמצעי ההגנה העיקרי. לבידוד צומתי Code בדקו מנגנוני הרצת משימות חיצוניים. הגנת SSRF · בידוד מנגנוני הרצת משימות.

צומתי קהילההתקינו רק חבילות שאתם סומכים עליהן; הן מריצות קוד בתוך סביבת n8n שלכם.
צמתים מסוכניםהחריגו צמתים שאין בהם צורך כאשר יכולותיהם חורגות מגבולות הגישה שהתכוונתם לאפשר לתהליכי העבודה.
SSRFהפעילו את הגנות SSRF של n8n ואת בקרות הרשת כאשר אסור לתהליכי עבודה להגיע לנקודות קצה פנימיות או לכתובות מטא-נתונים.
ייבוא תהליכי עבודהלפני הפעלה בדקו את תהליכי העבודה שיובאו, את פרטי הגישה, את הביטויים ואת השלבים שמריצים קוד.

ביקורת אבטחה ועדכונים

אבטחה היא תהליך תפעולי מתמשך

הרצת ביקורת האבטחה של n8n

פקודת ה-CLI הרשמית היא n8n audit. אם שירות Docker Compose שלכם נקרא n8n, הריצו docker compose exec -T n8n n8n audit בתיקיית ההתקנה. בדקו את חמש הקטגוריות: פרטי גישה שאינם בשימוש, דפוסי שאילתות SQL מסוכנים, גישה למערכת הקבצים, צמתים מסוכנים או צומתי קהילה, וסיכונים במופע כגון Webhooks שאינם מוגנים וגרסאות מיושנות. תקנו ממצאים רלוונטיים והריצו שוב. זו אינה בדיקת חדירה. ראו את מדריך ביקורת האבטחה הרשמי.

עדכון מבוקר

עדכנו את n8n בתדירות המאפשרת לקבל תיקוני אבטחה. קראו הערות גרסה ובדקו שדרוגים חשובים, במקום להשאיר מופע החשוף לאינטרנט עם גרסה מיושנת לאורך זמן.

ניטור גישה ואימות

עקבו אחר דפוסי גישה בלתי צפויים, שינויים בתהליכי עבודה וכשלים. הגבילו עוד את הגישה לממשק העורך כאשר המודל התפעולי שלכם אינו מחייב נגישות ציבורית רחבה.

הכנה לחזרה לאחור ולשחזור

צרו גיבויים שניתן לשחזר לפני שדרוגים משמעותיים. היקף הגיבוי ושלבי השחזור מפורטים במדריך ההתאוששות הנפרד.

צמצמו שמירה של היסטוריית הרצות רגישה: הרצות שהושלמו בהצלחה עלולות לשמור נתוני לקוחות ואסימוני גישה. בעת הצורך הגדירו את EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, השאירו את EXECUTIONS_DATA_PRUNE=true, ובחרו ערך עבור EXECUTIONS_DATA_MAX_AGE בשעות, למשל 168 (שבעה ימים). אלה דוגמאות להגדרות הניתנות לשינוי, ולא דרישות שמירה חוקיות. שמירת פחות היסטוריה פירושה גם פחות נתונים לאבחון תקלות ולחקירת אירועים; ייתכן שהרצות פעילות, ממתינות או מסומנות אינן נמחקות באותה דרך. ראו את תיעוד שמירת נתוני ההרצות הרשמי.

חשד לפריצה: הגבילו גישה זדונית בלי להשמיד ראיות, בדקו את פעילות הפרוקסי, השרת ו-n8n ואת תהליכי העבודה ששונו, בטלו או החליפו פרטי גישה של שירותים חיצוניים שאולי נחשפו, תקנו את גורם הפריצה ושחזרו בעת הצורך רק מגיבויים שנבדקו. בדקו כתובות Webhook שנפגעו, חשבונות עורך ושירותים מחוברים; אל תניחו ש-HTTPS, ‏Snapshots או רכישת VPS כוללים שירותי תגובה לאירועי אבטחה.

חיזוק ההגנה על כניסה לחשבון

הפעילו אימות דו-שלבי לחשבונות העורך ואכפו MFA באמצעות מדיניות האבטחה של n8n כאשר המהדורה שלכם תומכת באכיפת מדיניות מרכזית.

הגבלת הרשאות עריכה של תהליכי עבודה

גישה לעורך היא גישה בעלת הרשאות גבוהות: תהליכי עבודה יכולים לקרוא פרטי גישה, לפנות למערכות פנימיות ולהפעיל צמתים רבי-עוצמה. הגבילו גישת משתמשים והסירו חשבונות שאינם זקוקים לה עוד.

השבתת יכולות שאינן בשימוש

צמצמו את שטח התקיפה של היישום באמצעות השבתת ה-API הציבורי כאשר אינו נחוץ וחסימת צמתים או תכונות מסוכנים שהמערכת אינה צריכה.

שימוש מבוקר בהגנות SSRF ובקרות סודות

כאשר תהליכי עבודה מסוגלים לשלוח בקשות HTTP לכתובות שרירותיות, בדקו את הגנת SSRF של n8n ושמרו סודות מחוץ לקוד התהליכים, למאגרים ציבוריים ולקובצי סביבה הנגישים לקריאה רחבה.

הגבילו נקודות קצה ניהוליות שאינן בשימוש: N8N_PUBLIC_API_DISABLED=true משבית את ה-REST API הציבורי של n8n, ואילו N8N_PUBLIC_API_SWAGGERUI_DISABLED=true משבית בנפרד את סביבת הבדיקה של ה-API. עשו זאת רק כאשר האינטגרציות שלכם אינן זקוקות לתכונות האלה. השבתת REST API אינה מאמתת אוטומטית בקשות ל-Webhooks של תהליכי עבודה. השתמשו ב-MFA עבור משתמשי העורך ובמדיניות מרכזית רק כאשר מהדורת n8n שלכם תומכת בכך.

שאלות נפוצות על אבטחת n8n ב-VPS

האם צריך לחשוף ישירות את הפורט של n8n?

כאשר פרוקסי הפוך משמש נקודת כניסה ציבורית, חשפו את הפרוקסי והשאירו את פורט היישום מאחוריו, במקום לפרסם שירותים שאינם נחוצים.

האם PostgreSQL או Redis צריכים להיות נגישים לציבור?

בדרך כלל לא. הם צריכים להיות נגישים רק למערכות שזקוקות להם. חשיפה לציבור מגדילה את שטח התקיפה ואינה מסייעת להפעלה רגילה של n8n.

למה מפתח ההצפנה של n8n חשוב?

הוא מגן על פרטי הגישה ש-n8n שומר, וחייב להישאר זהה בכל רכיבי ההתקנה. אובדנו עלול למנוע שימוש בפרטי הגישה המוצפנים לאחר שחזור הנתונים.

האם צומתי קהילה בטוחים לשימוש?

הם מרחיבים את n8n באמצעות קוד של צד שלישי, ולכן יש להתייחס אליהם כתלויות תוכנה הכוללות סיכוני שרשרת אספקה והרשאות משלהן. התקינו רק צמתים נחוצים ממקורות מהימנים.

האם HTTPS לבדו מאבטח מופע n8n באירוח עצמי?

לא. HTTPS מגן על התקשורת. אבטחת סביבת ייצור מחייבת גם הקשחת השרת, בקרת גישה, שירותי צד שרת פרטיים, הגנה על סודות, הגבלת יכולות מסוכנות של תהליכי עבודה, ניטור ועדכונים.

האם אפשר להגביל את העורך ובו בזמן להשאיר Webhooks של ייצור פעילים?

כן. פרוקסי הפוך מהימן או VPN יכולים להגביל גישה לעורך ולממשק הניהול בנפרד מנתיבי Webhook ציבוריים ומכתובות חזרה של OAuth. לאחר כל שינוי בכללי הגישה בדקו כניסה מורשית וקבלת Webhook חיצוני, כדי שלא תחסמו בטעות אינטגרציות תקינות.

איך מאמתים בקשות Webhook נכנסות ל-n8n?

הגדירו אימות Basic, ‏Header או JWT בצומת Webhook כאשר השולח תומך בכך. אפשר להשתמש גם ברשימת IP מורשות ולאמת חתימות של הספק כאשר הן זמינות. אל תסתמכו רק על נתיב שנראה סודי, ואמתו בקשות לפני שהן מפעילות פעולות API רגישות.
