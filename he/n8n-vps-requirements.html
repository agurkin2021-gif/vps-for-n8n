מינימום לעומת קיבולת מעשית

האם ל-n8n יש גודל VPS מינימלי רשמי אחד?

לא עבור כל עומס עבודה. הדוגמאות הרשמיות לדרישות המקדימות של n8n מתארות התקנת OEM להמחשה ומזהירות במפורש שהדרישות משתנות בהתאם לעומס העבודה. התיעוד אינו מבטיח באופן גורף שהקצאה מסוימת של CPU, ‏RAM או דיסק תספיק לאוטומציות בסביבת ייצור.

לפי n8n, מופע שאינו פעיל עשוי לצרוך מעט זיכרון יחסית, אך צומת Code, נתונים בינריים גדולים או הרצות בו-זמניות עלולים להגדיל בחדות את צריכת הזיכרון. הקצו משאבים גם למערכת ההפעלה, ל-Docker, ל-PostgreSQL ולכלי גיבוי וניטור.

מקורות טכניים: דרישות מקדימות להמחשה של n8n ומדריך הזיכרון הרשמי. ארבע השורות שלמעלה מייצגות חבילות משאבים אמיתיות שניתן לרכוש, ולא דרישות רשמיות מחייבות של n8n.

RAM ו-CPU

מה באמת צורך את משאבי השרת

הרצות מקבילות

כמה תהליכי עבודה שפועלים באותו זמן עשויים להשפיע יותר ממספר התהליכים הכולל השמור ב-n8n. עקבו אחר שיאי צריכת הזיכרון וזמני ההרצה בעת חפיפה.

גודל הנתונים

אובייקטי JSON גדולים, קבצים ונתונים בינריים מגדילים את הלחץ על הזיכרון. כמה הרצות עתירות נתונים עשויות לדרוש יותר RAM מאוטומציות API קלות רבות.

צמתים עתירי CPU

צומתי Code, המרות נתונים ושלבים נוספים עתירי חישוב עשויים ליצור עומס CPU מתמשך. ליבות נוספות עוזרות כאשר הרצות אמיתיות מתחרות על כוח העיבוד.

שירותים תומכים

גם מערכת ההפעלה, PostgreSQL, הפרוקסי ההפוך, כלי הניטור ו-Docker זקוקים למשאבים. התאימו את הגודל למערכת כולה, לא רק לתהליך של n8n.

מדדו לפני שדרוג

איך לדעת אם n8n זקוק ליותר RAM, ‏CPU או דיסק

הריצו את תהליך העבודה הגדול ביותר שצפוי לכם, לצד עומס מציאותי של משימות חופפות, ובדקו את השרת ואת יומני ההרצות של n8n. מספר תהליכי העבודה השמורים בעורך אינו מדד מועיל לקיבולת בפני עצמו.

זיכרון / OOM

בדקו docker stats --no-stream ו- free -h. אם הזיכרון נגמר, תחילה צמצמו נתוני JSON או נתונים בינריים, חלקו ייבוא גדול למנות והימנעו משלבי Code עתירי זיכרון. הוספת vCPUs אינה בהכרח פותרת שגיאת זיכרון Heap של JavaScript.

CPU / הרצות מקבילות

בדקו אם ה-CPU נשאר עמוס בזמן עיבוד נתונים או שהמשימות רק ממתינות לתגובות מממשקי API חיצוניים. במצב רגיל שקלו להגדיר מגבלה נתמכת להרצות מקבילות בסביבת ייצור לפני הרחבה ל-Workers. הגדלת CPU אינה מאיצה API חיצוני שמגביל את קצב הבקשות.

אחסון / מסד נתונים

בדקו df -h, את גודל מסד הנתונים ואת היסטוריית ההרצות שנשמרת. עקבו אחר גידול הדיסק ופעולות איטיות של מסד הנתונים. הגדירו במכוון תקופת שמירה לפני שתשלמו על דיסק גדול יותר; שמרו עותקי שחזור מחוץ לשרת.

היעזרו בהנחיות n8n להרצות מקבילות ובהסבר הרשמי על מבחני ביצועים. כל מספר מפורסם של תהליכי עבודה מקבילים, ללא ידיעת גודל הנתונים וזמן ההשהיה של ה-API, הוא אומדן בלבד.

מסד נתונים ואחסון

SQLite, ‏PostgreSQL ונתונים מתמשכים

SQLite

SQLite יכול להתאים להתקנות קטנות עם מופע יחיד ולסביבות בדיקה. ככל שהשימוש בסביבת ייצור והצורך בהרצות מקבילות גדלים, בחירת מסד הנתונים הופכת לשיקול תפעולי ולא רק לפרט בהתקנה.

PostgreSQL

לסביבת VPS המיועדת לייצור, PostgreSQL מספק בסיס חזק יותר למסד הנתונים. הקצו RAM, ‏CPU ונפח דיסק גם למסד הנתונים עצמו, ועקבו אחר הגידול שלו.

נתונים מתמשכים בתיקיית ‎.n8n

אל תראו ב-PostgreSQL את הרכיב המתמשך היחיד. שמרו גם את תיקיית הנתונים של n8n והגנו על מפתח ההצפנה הדרוש לשחזור פרטי גישה מוצפנים.

גידול בנפח הדיסק

היסטוריית הרצות, נתונים בינריים, קובצי מסד נתונים ויומנים עשויים לגדול עם הזמן. הגדרות השמירה והגיבויים מחוץ לשרת משפיעים ישירות על הנפח הדרוש.

קיבולת הדיסק

העריכו את נפח היסטוריית ההרצות של n8n לפני ההזמנה

התחילו בנוסחה מספר הרצות שמורות ביום × מספר בתים ממוצע שנשמר לכל הרצה × מספר ימי שמירה. לדוגמה, 500 הרצות שמורות ביום × 200 KB לכל הרצה × 14 ימים = 1.4 GB של נתוני הרצות בדוגמה, לפני התקורה של מסד הנתונים. ההנחה של 200 KB היא להמחשה בלבד, ולא נתון ממבחן ביצועים של n8n.

הקצו נפח דיסק גם למערכת ההפעלה, לשכבות תמונות Docker, לאינדקסים של מסד הנתונים, לקבצים בינריים, ליומני היישום, לשדרוגים ולקבצים זמניים. גם גיבויים מחוץ לשרת דורשים נפח משלהם. דיסק של 10 GB עשוי להספיק לסביבה מצומצמת, אך יישאר בו הרבה פחות מקום לקבצים שמורים מאשר בדיסק של 40 או 80 GB.

בתיעוד n8n מתואר מחיקת נתוני הרצות כברירת מחדל לפי גיל (336 שעות / 14 ימים) או לפי מספר (10,000 הרצות), בכפוף לחריגים. בדקו את ההגדרות בפועל ואת הנתונים שנשמרים לפני שינוי. SQLite עשוי להשתמש מחדש במקום שהתפנה במקום להקטין אוטומטית את הקובץ.

מקור: התיעוד של n8n לניהול נתוני הרצות ולמחיקתם. דרישות הדיסק תלויות בגדלים שנמדדו עבור הנתונים השמורים, ולא רק במספר הצמתים.

הרצות מקבילות

מתי הגדלת ה-VPS כבר אינה הפתרון המלא

הגדלת משאבים אנכית מתאימה כל עוד מופע יחיד יכול לטפל בעומס העבודה היטב. כאשר דרישה מתמשכת להרצות מקבילות יוצרת עומס משותף על המשאבים, בחנו מצב תור ו-Workers. מצב תור מוסיף Redis, ‏PostgreSQL ותהליך Worker אחד או יותר; הקצו RAM ו-CPU לכל רכיב, לא רק ל-n8n. ‏n8n מתעד גם מגבלות על אחסון נתונים בינריים במערכת הקבצים במצב תור, ולכן בדקו התאמה של פתרון האחסון לפני המעבר.

קראו את המדריך למצב תור ול-Workers

להישאר עם מופע יחידכאשר ה-CPU, ה-RAM וזמני ההרצה נשארים בטווח תקין גם בשיא העומס המקביל.

לבחון מצב תורכאשר הביקוש המקביל שנמדד מצדיק Redis ו-Workers נפרדים.
לבדוק שוב את האחסוןכאשר הגידול בהיסטוריית ההרצות, בנתונים הבינריים או ב-PostgreSQL הופך למגבלה העיקרית.

SSD רגיל מספיק לאוטומציות קלות. NVMe מועיל יותר כאשר PostgreSQL והיסטוריית ההרצות יוצרים פעולות קריאה וכתיבה תכופות או כאשר זמני ההשהיה של הדיסק משפיעים על ביצועי תהליכי העבודה שנמדדו.

שאלות נפוצות על דרישות VPS ל-n8n

כמה RAM צריך n8n?

אין מספר אחיד לכולם. הדרישה ל-RAM משתנה בהתאם להרצות המקבילות, לגודל הנתונים, לאופי ההרצה ולשירותים התומכים על ה-VPS. שרת עם 4 GB הוא נקודת פתיחה מעשית לסביבת ייצור קטנה, ולא דרישה מובטחת לכל עומס עבודה.

כמה ליבות CPU כדאי להקצות?

עומסי עבודה קלים יכולים להתחיל בהקצאת CPU קטנה. הוסיפו ליבות כאשר הניטור מראה עומס CPU מתמשך או האטה בהרצות מקבילות, ולא רק לפי מספר תהליכי העבודה.

האם n8n מחייב PostgreSQL?

התקנות קטנות יכולות להשתמש ב-SQLite, אך PostgreSQL הוא פתרון מתאים יותר לסביבת ייצור ככל שדרישות התפעול וההרצות המקבילות גדלות.

מתי נדרש Redis?

Redis משמש במצב תור. התקנה רגילה עם מופע יחיד אינה מחייבת Redis רק משום שהיא פועלת על VPS.

כמה נפח דיסק כדאי להקצות?

צריכת הדיסק תלויה בגידול של PostgreSQL, בהיסטוריית ההרצות השמורה, בנתונים בינריים, ביומנים, בשכבות הקונטיינרים ובגיבויים. נטרו את הגידול והשאירו מרווח, במקום להסתמך על מספר קבוע ואחיד.

האם אפשר להפעיל n8n ברציפות על VPS עם 1 GB?

כן, כאשר עומס העבודה בפועל מתאים למשאבים. VPS עם 1 GB הוא שרת אמיתי שיכול לתמוך באוטומציות קטנות, בעיקר רציפות, אך מרווח הזיכרון מוגבל. אל תניחו שסביבה עם PostgreSQL על אותו שרת, משימות עתירות נתונים בינריים או כמה הרצות גדולות במקביל יתאימו למשאבים האלה. נטרו את הצריכה ושדרגו בהתאם ללחץ המשאבים שנמדד.

מה מתאים יותר לסביבת ייצור של n8n על VPS: ‏2 GB או 4 GB RAM?

תצורת 2 GB משאירה יותר מקום ממופע מצומצם עם 1 GB, בעוד ש-4 GB היא נקודת פתיחה מעשית לבחינת n8n יחד עם PostgreSQL ו-HTTPS. אין מינימום מובטח ואחיד לסביבת ייצור: מורכבות התהליכים, שיא העומס המקביל, הגדרות הקונטיינרים והנתונים שנשמרים קובעים את הדרישה האמיתית.

האם תהליכי AI ב-n8n מחייבים GPU?

לא כאשר n8n רק קורא ל-API חיצוני של מודל: ספק המודל מבצע את ההסקה, בעוד שה-VPS אחראי לתיאום התהליכים, לנתונים ולהרצות מקבילות. הפעלת מודלי הסקה באופן מקומי היא החלטת חומרה נפרדת, שעשויה לדרוש הרבה יותר RAM ומשאבי GPU מתאימים.

מה גורם לשגיאות חוסר זיכרון ב-n8n?

נתוני JSON גדולים או נתונים בינריים, פעולות Code עתירות זיכרון והרצות חופפות הם גורמים נפוצים. בדקו את יומני ההרצה ואת צריכת הזיכרון בשיא, ואז צמצמו את כמות הנתונים שמוחזקת בהרצה אחת או הקצו RAM נוסף בהתאם לבעיה שנמדדה.
