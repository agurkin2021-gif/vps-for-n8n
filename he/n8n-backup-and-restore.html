גיבוי והתאוששות

גיבוי ושחזור של n8n

כדי לגבות ולשחזר n8n באירוח עצמי, שמרו על מסד הנתונים SQLite או על גיבוי עקבי של PostgreSQL, על תיקיית ‎.n8n המתמשכת ועל מפתח ההצפנה המקורי, על קובצי התצורה ועל כל קובץ חיצוני, נתון בינרי או תיקייה מחוברת שהמערכת תלויה בהם. שמרו עותק מוצפן מחוץ ל-VPS ובדקו את השחזור במופע נפרד. ייצוא תהליכי עבודה ופרטי גישה באמצעות CLI מתאים לשחזור ממוקד, אך קובצי JSON לבדם אינם גיבוי מלא של השרת.

בחירת VPS עבור n8n

רשימת בדיקה מהירה

מה חייב להיכלל בגיבוי של n8n

מסד נתונים

גבו את מסד הנתונים PostgreSQL או את קובץ SQLite שבו משתמש המופע. מסד הנתונים מכיל מידע מרכזי של n8n, ובהם תהליכי עבודה, פרטי גישה ונתוני הרצות.

מפתח הצפנה

שמרו בנפרד ובאופן מאובטח עותק מדויק של מפתח ההצפנה של n8n. שחזור פרטי גישה מוצפנים מחייב שימוש באותו מפתח.

קבצים באחסון מתמשך

כללו את תיקיית הנתונים המתמשכת של n8n, וכן קבצים מחוברים, אחסון נתונים בינריים וקובצי עזר לתהליכי העבודה שבהם ההתקנה תלויה.

תצורת ההתקנה

שמרו את קובצי Compose והגדרות ההתקנה שאינם סודיים, הנדרשים לבניית הסביבה מחדש. על סודות הגישה יש להגן באמצעות הרשאות מתאימות.

שתי רמות של גיבוי

ייצוא לוגי לעומת התאוששות מלאה מאסון

ייצוא תהליכי עבודה ופרטי גישה

ייצוא באמצעות CLI של n8n שימושי להעברה בין שרתים, לשמירת גרסאות של תהליכי עבודה ולשחזור ממוקד. אפשר לייצא פרטי גישה בצורה מוצפנת ולייבא אותם בהמשך בעזרת מפתח ההצפנה התואם. לשחזור של תהליך עבודה יחיד, פתחו את תפריט שלוש הנקודות בעורך, הורידו את קובץ ה-JSON שלו וייבאו אותו באמצעות Import from File לתהליך חדש לבדיקה או למופע מבודד. לפני החלפת תהליך פעיל בדקו את פרטי הגישה, מזהי התהליכים והפרמטרים של הצמתים: שחזור JSON של תהליך עבודה אינו משחזר את השרת כולו.

ייצוא ישויות

כלי CLI יכול לייצא ישויות של מסד הנתונים לצורך העברת מידע בין סוגי מסדי נתונים נתמכים. טבלאות היסטוריית הרצות הן אופציונליות, משום שהן עשויות להיות גדולות מאוד.

שחזור המופע במלואו

בתרחיש של אובדן שרת, יש לשמור על מסד הנתונים עצמו, מפתח ההצפנה, הנתונים המתמשכים והתלויות של ההתקנה. אל תניחו שייצוא JSON של תהליכי עבודה מסוגל לשחזר את המופע כולו.

תמונת מצב (Snapshot) של הספק

Snapshot של VPS יכול לשמש שכבת התאוששות נוספת, אך לא להיות העותק היחיד או להחליף גיבוי של היישום ומסד הנתונים שנבדק באופן עצמאי.

מסד הנתונים

יצירת גיבוי עקבי של מסד הנתונים

PostgreSQL

השתמשו בשיטה שמבטיחה גיבוי עקבי של PostgreSQL ושמרו את העותק מחוץ ל-VPS. עותק של מסד הנתונים על אותו דיסק שנכשל אינו מאפשר התאוששות מאסון.

SQLite

אם ההתקנה משתמשת ב-SQLite, גבו את קובץ מסד הנתונים מתוך תיקיית הנתונים המתמשכת של n8n. הימנעו מהעתקת מסד נתונים בזמן שמתבצעות בו כתיבות, ללא שיטת גיבוי בטוחה.

היסטוריית הרצות

החליטו אם היסטוריית ההרצות חייבת להיכלל בשחזור. היא עלולה להגדיל משמעותית את נפח הגיבוי, ולכן יש לבחור בהתאם לדרישות השמירה והציות שלכם.

גרסת מסד הנתונים

תעדו את סוג מנוע מסד הנתונים ואת גרסתו בהתקנה המקורית, כדי להכין סביבת שחזור תואמת.

PostgreSQL על VPS עם Docker Compose. אם שירות PostgreSQL נקרא postgres וגם מסד הנתונים והמשתמש נקראים n8n, הפקודה הבאה יוצרת במחשב המארח קובץ גיבוי עקבי של PostgreSQL בפורמט מותאם. לפני ההרצה בדקו את קובץ ה-Compose שלכם והתאימו את שמות השירותים ואת פרטי הגישה למסד הנתונים. pg_dump מסוגל ליצור גיבוי לוגי עקבי בזמן ש-PostgreSQL פועל; הוא אינו מגבה את תיקיית המשתמש הנפרדת .n8n או נתונים בינריים המאוחסנים מחוץ למסד הנתונים.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

בדיקת רשימת האובייקטים בארכיון יכולה לחשוף בעיות פורמט ברורות, אך אינה מוכיחה שניתן לשחזר את המידע. שמרו עותק מוצפן מחוץ לשרת ותרגלו שחזור. לפרמטרים הספציפיים למסד הנתונים היעזרו בתיעוד הרשמי של pg_dump ב-PostgreSQL.

SQLite בסביבת Docker. בהתקנת SQLite ברירת המחדל, הקובץ database.sqlite וההגדרות המכילות את מפתח ההצפנה שנוצר נמצאים בתיקייה המתמשכת .n8n (שמחוברת בדרך כלל לנתיב /home/node/.n8n). אל תחשיבו העתקה רגילה של SQLite בזמן פעילות לגיבוי עקבי. עצרו את n8n ואת כל התהליכים שכותבים למסד הנתונים לפני העתקת התיקייה, או השתמשו במנגנון הגיבוי המקוון הנתמך של SQLite אם אי אפשר לעצור את המערכת:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

הפקודות הן דוגמאות לשירות ולנתיב המוצגים, ואינן מתאימות בהכרח לכל מבנה אחסון. בתחילה התיקייה המועתקת עדיין נמצאת על אותו VPS, ולכן יש להעביר אותה לאחסון חיצוני מאובטח. אם קיימים Workers של תור או תהליכי כתיבה אחרים, עצרו גם את הכתיבה שלהם ופעלו לפי ארכיטקטורת ההתקנה בפועל. מדריך הגיבוי המלא העדכני של n8n מתאר את דרישת העקביות של SQLite.

שחזור תיקיית SQLite של ברירת המחדל לסביבה נקייה: תחילה עצרו את שירות n8n ואת כל התהליכים שכותבים למסד הנתונים. לאחר שקיימים קונטיינר n8n תואם ונפח אחסון יעד, העתיקו מתוך הגיבוי את .n8n התוכן בחזרה לאותה תיקייה מתמשכת. הפעולה דורסת קבצי יעד, ולכן אין לבצע אותה במופע שמכיל נתונים שחשוב לשמור:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker מסוגל להעתיק קבצים גם לקונטיינרים שעצרו, אך הבעלות על הקבצים ביעד עשויה להיות שונה. ודאו שלתהליך n8n יש הרשאות קריאה וכתיבה לקובצי התצורה ומסד הנתונים המשוחזרים לפני הפעלתו. אם הגדרות ה-Compose שלכם משתמשות בנתיב או ב-bind mount אחרים, התאימו את פקודות ההעתקה. ראו את תיעוד פעולת ההעתקה של Docker Compose. שחזור תיקיית n8n בלבד אינו מספיק כאשר מסד הנתונים PostgreSQL נמצא בנפרד.

סוד אבטחה חיוני

מפתח ההצפנה חיוני לשחזור

n8n מצפין פרטי גישה שמורים באמצעות מפתח הצפנה של המופע. אם תשחזרו מסד נתונים או ייצוא מוצפן ללא המפתח המתאים, ייתכן שתהליכי העבודה לא יוכלו להשתמש בפרטי הגישה השמורים.

אם הגדרתם N8N_ENCRYPTION_KEY, שחזרו את ערך הסוד המקורי במדויק. אחרת המפתח שנוצר שמור בקובץ המתמשך ‎.n8n/config, ויש לשמור על הקובץ בזמן גיבוי או בנייה מחדש. אחסנו מפתחות שחזור באופן מאובטח מחוץ ל-VPS. במצב תור, התהליך הראשי וכל תהליכי ה-Worker חייבים להשתמש באותו מפתח.

מה לעשותשמרו עותק מוגן ומדויק של המפתח שבו משתמשת סביבת הייצור.
מה לעשותלפני בדיקת פרטי הגישה, ודאו שסביבת השחזור משתמשת באותו מפתח.
ממה להימנעלהסתמך על מפתח חדש שנוצר לאחר בנייה מחדש של השרת.
ממה להימנעלהעלות את המפתח למאגר קוד ציבורי או לשמור אותו ליד גיבוי שאינו מוגן.

קבצים ונתונים בינריים

גיבוי מסד הנתונים אינו מכסה בהכרח את כל התלויות

נתונים מתמשכים בתיקיית ‎.n8n

אתרו ושמרו את תיקיית המשתמש האמיתית ‎.n8n, ולא רק את תמונת הקונטיינר. בהתקנת Docker טיפוסית היא מחוברת לנתיב ‎/home/node/.n8n, ומחוץ ל-Docker נתיב ברירת המחדל הוא ‎~/.n8n. אם הוגדר N8N_USER_FOLDER, ‏n8n יוצר תיקיית ‎.n8n בתיקיית האב שצוינה. כללו את מפתח ההצפנה שבקובץ התצורה ואת נתוני SQLite, הנתונים הבינריים וקובצי ההרצות המקומיים שבהם ההתקנה שלכם משתמשת.

קבצים המחוברים לתהליכי העבודה

אם תהליכי העבודה קוראים או כותבים לתיקיות של המארח שמחוברות לקונטיינר, גבו גם אותן בנפרד. שחזור n8n בלעדיהן עלול להשאיר תהליכי עבודה תקינים לכאורה שאינם מסוגלים לפעול.

נתונים בינריים

בדקו באיזו שיטת אחסון אתם משתמשים ושחזרו כל תלות חיצונית. נתונים בינריים או נתוני הרצות הנשמרים במערכת הקבצים עשויים להימצא ב-‎.n8n או בתיקייה מותאמת; אחסון חיצוני כגון S3 או Azure Blob דורש עותק שניתן לשחזור והגדרות גישה משלו. גיבוי מסד הנתונים לבדו אינו יכול להחליף את הקבצים האלה.

צומתי קהילה

תעדו חבילות של צומתי קהילה ואת גרסאותיהן, וגבו תיקיות נוספות של צמתים מותאמים אישית שהוגדרו באמצעות N8N_CUSTOM_EXTENSIONS. תיקיות אלו עשויות להיות מחוץ ל-‎.n8n, ולכן שחזור מסד הנתונים ותיקיית המשתמש בלבד עלול להשאיר תהליכים שמסתמכים על צמתים מותאמים לא שמישים.

אסטרטגיית גיבוי מחוץ לשרת

גיבוי על אותו VPS הוא עותק מקומי בלבד

עותק מקומישימושי לחזרה מהירה למצב קודם, אך חשוף לאובדן השרת, לכשל בדיסק ולטעויות הרסניות.
עותק מחוץ לשרתשמרו לפחות גיבוי אחד באחסון שאינו תלוי ב-VPS של סביבת הייצור.
עותקים עם היסטוריית גרסאותשמרו כמה נקודות שחזור, כדי ששחיתת נתונים או שינוי שגוי לא ידרסו את הגיבוי התקין היחיד.
בקרת גישהגיבויים עשויים להכיל פרטי גישה, לוגיקה של תהליכי עבודה ומידע עסקי רגיש. הצפינו אותם והגבילו את הגישה אליהם בהתאם.
ניטורהגדירו התראות כאשר גיבויים מתוזמנים נכשלים או מפסיקים לייצר נקודות שחזור חדשות.

הגדירו לוח זמנים שניתן למדוד ולאמת. תעדו לכל גיבוי שהצליח את שעת היצירה, סיום ההעברה, גודל הקובץ, גרסת מסד הנתונים המקורי, מיקום מפתח ההצפנה לשחזור ואת תאריך בדיקת השחזור המוצלחת האחרונה. הגדירו התראות לקבצים חסרים, לגיבויים שנכשלו ולקבצים ריקים באופן בלתי צפוי. הצפינו ארכיוני גיבוי לפני העברתם מחוץ ל-VPS והגבילו את הגישה לסודות השחזור. שמירת כמה נקודות שחזור עם תאריכים מגינה מפני מצב שבו שחיתות נתונים מתגלה רק לאחר שהעותק החדש דרס את העותק התקין האחרון.

לדוגמה, אם אתם מסוגלים לספוג אובדן של עד שש שעות שינויים, גיבוי מוצלח מדי שש שעות הוא נקודת התחלה בלבד, לא הבטחה. משימות גיבוי שנכשלו ועיכובים בהעתקת הגיבוי מחוץ לשרת עשויים להגדיל את האובדן בפועל. התאימו את משך השמירה ואת תדירות בדיקות השחזור ליעדי RPO/RTO ולדרישות המידע שלכם, במקום להניח שמדיניות אחידה של 7 או 30 ימים מתאימה לכולם.

סדר השחזור

שחזור לפי סדר פעולות מבוקר

1 · הכנההכינו שרת תואם, מסד נתונים תואם וסביבת הרצה או קונטיינרים מתאימה.
2 · שחזור סודות גישההגדירו באופן מאובטח את מפתח ההצפנה המקורי של n8n ואת יתר הסודות הנדרשים להפעלת הסביבה.
3 · שחזור מסד הנתוניםשחזרו את PostgreSQL או SQLite וודאו ש-n8n מסוגל להתחבר לנתונים הצפויים.
4 · שחזור קבציםשחזרו תיקיות באחסון מתמשך, נתונים בינריים וקבצים המחוברים לתהליכי העבודה.
5 · הפעלת n8nהפעילו את היישום עם שם המארח, מסד הנתונים והגדרות הסביבה המתאימים.
6 · בדיקת תקינותודאו שמשתמשים, תהליכי עבודה ופרטי גישה נטענים, ולאחר מכן הפעילו תהליכים מייצגים ובדקו נתיבי Webhook.

דוגמה להתאוששות מאסון באמצעות PostgreSQL: על יעד שחזור נפרד ונקי שבו כבר קיים תפקיד מסד הנתונים המתאים ומסד נתונים n8n ריק, הפעילו רק את PostgreSQL. המתינו עד שהשירות יהיה תקין ומוכן לפני הייבוא: docker compose up -d עשויה להסתיים בזמן ש-PostgreSQL עדיין מאותחל, ולכן פקודת pg_restore עלולה להיכשל. הדוגמה משתמשת בפרמטר --wait בהתקנת Compose עדכנית ובודקת בנפרד את מוכנות השירות באמצעות pg_isreadyהגדירו בדיקת בריאות מתאימה ל-PostgreSQL כדי להמתין בצורה אמינה, או ודאו במפורש שהמסד מוכן לפני המשך הפעולות. אל תריצו את הפקודה מול מסד נתונים פעיל שמכיל מידע, ואל תפעילו n8n לפני ששוחזרו מסד הנתונים וגם מפתח ההצפנה והנתונים .n8n התואמים לו.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

סביבת היעד חייבת להכיל גרסת PostgreSQL תואמת, הרשאות תפקיד מתאימות, הרחבות נדרשות ואת תצורת n8n המקורית. שחזרו את .n8n לנפח האחסון המתמשך או ל-bind mount המתאים באמצעות שיטת הגיבוי שלכם, תוך שמירה על בעלות והרשאות הקבצים. שחזרו גם נתונים בינריים חיצוניים, הרחבות מותאמות, קובצי Compose וסודות הגישה; לאחר מכן הפעילו גרסת n8n תואמת ובדקו את היומנים. שחזור מסד הנתונים בלבד אינו משחזר את המפתח: בהתקנת PostgreSQL, ‏n8n שומר את המפתח בקובץ .n8n/config אלא אם הגדרתם במפורש N8N_ENCRYPTION_KEY· תיעוד pg_restore · סדר שחזור המופע המלא של n8n.

תרגול שחזור מאומת: SQLite ו-PostgreSQL

סביבת הבדיקה: n8n 2.42.5 בקונטיינרים מבודדים של Docker על סביבת GitHub Actions זמנית, באמצעות תהליך עבודה סינתטי עם שני צמתים. הבדיקות בוצעו בתאריך 8 באוקטובר 2026, ולא על שרת לקוח או על שרת n8n של סביבת ייצור.

SQLite: עבר בהצלחהתהליך העבודה לבדיקה יובא ויוצא, כל תהליכי הכתיבה נעצרו, ותיקיית הנתונים המתמשכת המבוססת על SQLite .n8n יחד עם מפתח ההצפנה שנוצר גובתה לארכיון ושוחזרה בנפח אחסון נקי. לאחר מכן הופעל n8n, ותהליך העבודה המשוחזר יוצא מחדש והורץ.
PostgreSQL: עבר בהצלחהאותו תהליך עבודה לבדיקה יובא, נוצר ונבדק קובץ גיבוי בפורמט מותאם pg_dumpוהוא שוחזר באמצעות pg_restore לתוך מסד PostgreSQL חדש וריק. לאחר מכן שוחזרה התיקייה הנפרדת .n8n ותהליך העבודה המשוחזר יוצא מחדש והורץ.
מה מוכיחה תוצאת PASSשיטות הגיבוי שנבדקו שמרו על תהליך העבודה, על שני הצמתים שבו ועל הקשרים ביניהם, ואפשרו להפעילו לאחר השחזור. אלה בדיקות תפקוד בסיסיות שניתן לשחזר, ולא מבחני ביצועים תחת עומס.
מה לא נבדקלא נבדקו פענוח ואימות של פרטי גישה אמיתיים, Webhooks של סביבת ייצור, Workers של מצב תור ו-Redis, אחסון בינרי ב-S3 או Azure, צמתים מותאמים, הרשאות משתמשים ופרויקטים או התאוששות של מופע ייצור פעיל. תרגלו בנפרד כל תלות שבה אתם משתמשים בפועל.

כיצד לשחזר את הבדיקה: השתמשו בהתקנת n8n זמנית, צרו תהליך עבודה לא מזיק עם שני צמתים, בצעו גיבוי של מסד הנתונים ושל התיקייה המתמשכת, שחזרו לנפח אחסון או למסד נתונים נקי, ובדקו את הצמתים, הקשרים וההרצה בפועל של התהליך המשוחזר. בסביבת הייצור בדקו גם פרטי גישה מוצפנים, Webhooks וקבצים חיצוניים לפני הכרזה על הצלחת התאוששות מאסון.

רשימת בדיקות לקבלת תוצאות תרגול השחזור: השתמשו בדומיין ובסביבה מבודדים; ודאו שהמשתמשים ותהליכי העבודה קיימים, שלפחות פרט גישה מוצפן אחד מאפשר אימות ללא הזנה מחדש, ש-Webhook של סביבת הייצור מפעיל את התהליך המשוחזר הנכון, שקבצים מחוברים ונתונים בינריים נשארים קריאים ושהאינטגרציות עם צומתי הקהילה הנדרשים נטענות. בדקו את גיל הגיבוי, משך ההשבתה שנמדד ואת זמינות העותק מחוץ לשרת. אם בדיקה חיונית כלשהי נכשלת, סמנו את נקודת השחזור כ- לא מאומתת במקום לדווח שהגיבוי מלא.

מגבלות גיבוי דרך CLI

מה ייצוא תהליכי עבודה ופרטי גישה אינו משחזר

ייצוא דרך CLI אינו גיבוי מלא של המופע

שחזור במופע חדש מחייב הגדרת בעלים

במופע חדש ונקי יש להשלים את הגדרת המשתמש הראשי לפני ייבוא פרטי הגישה. בשחזור של כמה משתמשים או פרויקטים ייתכן שיהיה צורך גם בשיוך נכון של משתמשים ופרויקטים.

מזהים מיובאים עלולים לדרוס פריטים קיימים

ייצוא תהליכי עבודה ופרטי גישה משמר את המזהים המקוריים שלהם. ייבוא למופע שכבר מכיל את אותם מזהים עלול להחליף פריטים קיימים.

פרסמו תהליכי עבודה מיובאים באופן מבוקר

ייבוא באמצעות CLI משאיר בדרך כלל את תהליכי העבודה לא פעילים. ב-n8n 2.x בדקו אם כל תהליך מיובא פורסם, ופרסמו רק את התהליכים שברצונכם להפעיל. ‏Server CLI באירוח עצמי תומך גם בפקודה n8n publish:workflow --id=YOUR_WORKFLOW_ID. כאשר n8n פועל, שינויי מצב פרסום או ביטול פרסום באמצעות Server CLI נכנסים לתוקף רק לאחר הפעלה מחדש של n8n. הפעילו מחדש לפני בדיקת טריגרים מתוזמנים ו-Webhooks של סביבת הייצור, או לפני העברת התעבורה.

דוגמה לייצוא מרוכז באמצעות Docker Compose: אם שירות n8n שלכם נקרא n8nתוכלו להריץ את פקודות הגיבוי הרשמיות של CLI שלהלן. נתיב הפלט נמצא במכוון בתוך תיקיית הנתונים המתמשכת .n8n שמחוברת לקונטיינר, מכיוון שתיקיות אחרות בתוך הקונטיינר עלולות להיעלם בעת יצירתו מחדש. ודאו שלמשתמש בקונטיינר של n8n יש הרשאת כתיבה לתיקייה. שמרו את קובצי ה-JSON של תהליכי העבודה ופרטי הגישה ב- תיקיות נפרדות—בתיעוד n8n מצוינת בעיית ייבוא כאשר שני סוגי הקבצים נמצאים באותה תיקייה.

גיבוי טיוטה לעומת גרסה מפורסמת ב-n8n 2.x: ייצוא רגיל באמצעות --backup שומר את הטיוטות הנוכחיות של תהליכי העבודה; הן עשויות להיות שונות מהגרסאות שפורסמו בסביבת הייצור. כדי לשמר את הגרסה שפורסמה בפועל של תהליך מסוים, ייצאו אותה בנפרד באמצעות docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, לאחר שווידאתם שתיקיית הפלט קיימת וניתן לכתוב אליה. ‏CLI יכול לייצא גם גרסה היסטורית באמצעות --version=VERSION_ID. שמרו את העותקים מחוץ לשרת לצד הגיבוי המלא; אל תניחו שקובץ JSON של טיוטה משקף את הגרסה הפעילה שפורסמה.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

התיקייה שהועתקה ~/n8n-recovery/cli עדיין נמצאת על ה-VPS עד שתעבירו אותה למקום גיבוי עצמאי ומאובטח. ייצוא פרטי גישה מוצפן כברירת מחדל, ובייבוא נדרש מפתח ההצפנה התואם. הימנעו משימוש בפרמטר --decrypted אלא בהעברה מבוקרת בקפידה, משום שהוא שומר סודות בטקסט גלוי. לעולם אל תעלו למאגר GitHub ציבורי קובצי ייצוא שמכילים לוגיקה רגישה של תהליכי עבודה או פרטי גישה. חלק מתבניות הגיבוי ל-GitHub של צדדים שלישיים מייצאות במכוון סודות ללא הצפנה; מאגר פרטי מגביל גישה, אך אינו מצפין את התוכן. בדקו את הגדרות הייצוא והרשאות האחסון של כל תבנית, הצפינו סודות לפני העברה מחוץ לשרת והחליפו פרטי גישה שנחשפו בעקבות העלאה בלתי מכוונת של טקסט גלוי.

דוגמה לייבוא מרוכז: בשרת יעד נקי, השלימו את הגדרת המשתמש הראשי, הזינו את מפתח ההצפנה המקורי וודאו שקובצי הגיבוי זמינים על VPS השחזור. הפעולות הבאות יוצרות את תיקיית היעד ומעתיקות את תיקיות המשנה workflows/ ו- credentials/ מהמחשב המארח אל הקונטיינר של n8n. התאימו את הנתיבים אם מבנה נפחי האחסון של Docker אצלכם שונה:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

בדקו את הבעלות על הקבצים ואת הרשאות הגישה של המשתמש בקונטיינר n8n. אל תייבאו למופע ייצור שמכיל מידע ללא אפשרות חזרה לאחור שנבדקה: מזהי תהליכי עבודה ופרטי גישה עלולים לדרוס רשומות קיימות. לאחר מכן הריצו:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

מזהים מיובאים עלולים להחליף תהליכי עבודה או פרטי גישה קיימים. השתמשו במופע בדיקה מבודד להרצות ניסיון, ולאחר מכן בדקו את פרטי הגישה ואת מצבי ההפעלה והפרסום. ב-n8n 2.x, שחזור טיוטת JSON אינו מוכיח בפני עצמו שהתהליך פורסם ויכול להפעיל טריגרים מתוזמנים. בטיחות הייבוא: במופע n8n שאינו משתמש בארכיטקטורת multi-main, טריגרים מתוזמנים של cron שהיו פעילים עשויים להמשיך לפעול לאחר ייבוא CLI עד להפעלה מחדש של המופע. עצרו או בודדו טריגרים של סביבת הייצור והפעילו מחדש את n8n לפני הפעלת משימות משוחזרות; ודאו שאין הרצות כפולות. ייצוא CLI אינו אינו כולל משתמשים מקוריים, יומני הרצות, משתני מופע או את מפתח ההצפנה. --backup מפעיל את האפשרויות --all --pretty --separate, ולא מבצע גיבוי של המופע המלא. מקורות: מדריך הגיבוי והשחזור הרשמי העדכני של n8n ותיעוד פקודות CLI.

שחזור מרוכז מתבניות GitHub או Google Drive: זו אפשרות חלופית לקובצי JSON של תהליכי עבודה בלבד, ולא לגיבוי מסד הנתונים של המופע, המשתמשים, הערכים המוצפנים של פרטי הגישה או מפתח ההצפנה. לפני הפעלת תבנית המבוססת על API, בדקו את הרשאות ה-API של n8n ושל האחסון, את גרסת הגיבוי ואת מופע היעד, אם התבנית מעדכנת מזהים תואמים ויוצרת מחדש תהליכים שנמחקו, וכיצד היא מטפלת בפרסום תהליכי העבודה. לא כל התבניות יוצרות מחדש תהליך שמזההו חסר ביעד; בדקו את התרחיש הזה בנפרד לפני הסתמכות על שחזור אוטומטי.

שאלות נפוצות

שאלות נפוצות על גיבוי ושחזור n8n

האם ייצוא תהליכי עבודה מספיק לגיבוי של n8n?

לא. ייצוא תהליכי עבודה מספק עותקים לוגיים שימושיים, אך לשחזור מלא ייתכן שיידרשו גם פרטי גישה, מפתח ההצפנה המתאים, מצב מסד הנתונים, קבצים מתמשכים ואחסון נתונים בינריים.

האם צריך את מפתח ההצפנה של n8n גם אם יש לי את מסד הנתונים?

כן, אם ברצונכם להמשיך להשתמש בפרטי הגישה המוצפנים שנשמרו במסד הנתונים. שמרו את המפתח המקורי באופן מאובטח.

האם לגבות PostgreSQL או לייצא תהליכי עבודה ופרטי גישה?

לצורך התאוששות מאסון יש לגבות את מסד הנתונים ואת מפתח ההצפנה. ייצוא לוגי הוא שכבה נוספת וחשובה להעברה ולשחזור ממוקד, ולא תחליף לכל רכיבי המופע.

האם Snapshot של VPS יכול להיות הגיבוי היחיד?

עדיף להתייחס אליו כשכבת התאוששות אחת בלבד. שמרו גיבוי עצמאי מחוץ לשרת, כדי שכשל אצל הספק, בחשבון, בשרת או ב-Snapshot לא ימחק את כל נקודות השחזור.

איך אפשר לדעת שהגיבוי פועל?

שחזרו אותו לסביבת בדיקה נקייה, ודאו שפרטי הגישה המוצפנים נפתחים והריצו תהליכי עבודה מייצגים. עצם הצלחת משימת הגיבוי אינה מוכיחה שניתן לשחזר.

האם גיבוי תהליכי עבודה ל-GitHub או Google Drive כולל סודות של פרטי גישה?

גיבויי JSON של תהליכי עבודה בלבד אינם כוללים את ערכי הסודות שמנוהלים במאגר פרטי הגישה של n8n או את מפתח ההצפנה של המופע. עם זאת, קובצי JSON מיוצאים יכולים לחשוף שמות ומזהים של פרטי גישה, וכן סודות שהוזנו ישירות לפרמטרים של צמתים, כגון כותרות אימות. בדקו והגנו על קובצי ה-JSON לפני העלאה או שיתוף. לשחזור מלא גבו את מסד הנתונים והמפתח המקורי, או השתמשו בייצוא CLI מוצפן נתמך של פרטי גישה עם שחזור שנבדק. תבנית GitHub או Google Drive המגבה רק תהליכי עבודה אינה פתרון מלא להתאוששות מאסון.

יעדי ההתאוששות

הגדירו RPO ו-RTO לפני תקלה

RPO הוא פרק הזמן המרבי של שינויים שניתן לספוג את אובדנם. יש למדוד אותו לפי נקודת השחזור העדכנית ביותר שניתן להשתמש בה ושנשמרה בנפרד; משימת גיבוי מתוזמנת מדי שש שעות אינה מבטיחה RPO של שש שעות אם הייצוא או ההעברה נכשלו. RTO הוא משך ההשבתה המרבי שניתן לסבול. מדדו אותו במהלך תרגול שחזור בסביבה נקייה, כולל אחזור סודות, שחזור קבצים חיצוניים, בדיקה מחדש של פרטי גישה ופרסום תהליכי עבודה משוחזרים — ולא רק זמן הפעלת הקונטיינר.

מפתח לשחזור

אתרו את מפתח ההצפנה המקורי לפני בנייה מחדש

אם בסביבת הייצור הוגדר N8N_ENCRYPTION_KEY, שמרו את ערך סוד הסביבה המקורי במדויק. אם הוא לא הוגדר, שמרו את המפתח שנוצר בקובץ המתמשך המקורי ‎.n8n/config. לפני ייבוא פרטי גישה מוצפנים בדקו באיזה מקור מפתח משתמש המופע המשוחזר בפועל; מפתח חדש אינו מסוגל לפענח את פרטי הגישה ממסד הנתונים הישן.

משווים בין ספקים?

לבחירת ספק והשוואת התקנה בלחיצה אחת, היקף תמיכה, גיבויים, העברה, אזורי אירוח והרחבת משאבים, היעזרו ב- השוואת ספקי VPS מומלצים ל-n8n. להתאמת משאבי השרת חזרו אל המדריך הראשי לבחירת VPS ל-n8n.
