התקנת n8n על שרת VPS

התקינו n8n על VPS באמצעות Docker Compose ו-PostgreSQL. להפעלה בסביבת ייצור נדרשים גם אחסון מתמשך של היישום ומסד הנתונים, מפתח הצפנה קבוע N8N_ENCRYPTION_KEY, שם מארח ציבורי, HTTPS והגדרות נכונות של Webhooks. בדקו את כל אלה לפני הפעלת תהליכי עבודה בסביבת הייצור.

מתקינים על VPS שכבר מאחסן אתרים? אפשר להוסיף n8n לשרת שבשליטתכם אם משאבי ה-CPU, ה-RAM והאחסון מאפשרים זאת. אולם אם Nginx, Apache, Caddy או פרוקסי הפוך אחר כבר משתמש בפורטים 80/443, אל אינו תפעילו את קונטיינר Caddy שבדוגמה שלהלן ללא שינויים: תהיה התנגשות בין הפורטים. במקום זאת, נתבו תת-דומיין חדש של n8n דרך הפרוקסי הקיים תוך שימוש ברשת פרטית מתאימה, או השתמשו ב-VPS נקי עבור דוגמת Compose כפי שהיא. שמרו על האתרים האחרים ועל הגדרות ה-TLS שלהם; הדוגמה מניחה שהפורטים 80/443 פנויים.

דוגמת התקנה להעתקה ולהתאמה

התקנת n8n על ה-VPS שלכם באמצעות Docker Compose

השתמשו בדוגמה זו כדי להקים n8n על שרת Linux VPS בניהול עצמי. ההתקנה והתחזוקה של n8n באחריותכם; בחירת שרת דרך השותף שלנו אינה כוללת מופע n8n מותקן מראש. הדוגמה משלבת n8n, ‏PostgreSQL, מנגנון חיצוני להרצת משימות ו-Caddy ל-HTTPS ברשת Compose פרטית. זוהי תבנית הגדרות, ולא טענה שההתקנה נבדקה בפועל בסביבת ייצור.

מעדיפים התקנה ראשונית מהירה יותר? ל-n8n קיימת גם שיטת התקנה רשמית של Docker בפקודה אחת. ניתן להוריד ולבדוק את הסקריפט באמצעות curl -fsSL https://get.n8n.io -o get-n8n.sh לפני הרצת sh get-n8n.shאפשרות זו מפעילה מופע התחלתי עם SQLite בכתובת מקומית וכוללת את שירותי סביבת הבדיקה של n8n Assistant; היא אינה זהה להתקנת ה-VPS המתוארת כאן, המשתמשת ב-HTTPS ציבורי וב-PostgreSQL. סביבת הבדיקה הרשמית המלאה דורשת יותר RAM ו-CPU מהתקנת n8n מצומצמת (מדריך ה-Compose שלה מציין לפחות 4 GB RAM ו-2 vCPUs). עבור VPS המיועד לסביבת ייצור ונגיש מהאינטרנט, המשיכו בהגדרות הידניות שלהלן.

1. הכנת Docker, ‏DNS והרשאות גישה

התחברו באמצעות SSH עם הרשאות sudo, והפנו רשומת DNS מסוג A עבור n8n.example.com אל כתובת ה-IPv4 של ה-VPS. בשרת Ubuntu חדש בגרסה 22.04, ‏24.04 או 26.04 VPS, הפקודות הבאות מתקינות את Docker Engine ואת התוסף המודרני docker compose מתוך מאגר החבילות החתום הרשמי של Docker עבור apt מערכת ההפעלה:

# Fresh official Ubuntu 22.04 / 24.04 / 26.04 installation
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Register Docker's signed apt repository
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

זוהי שיטת ההתקנה באמצעות מאגר חבילות, המומלצת לסביבת ייצור במדריך הרשמי להתקנת Docker על Ubuntu. אל תתקינו מחדש ואל תסירו את Docker ללא בדיקה ב-VPS שכבר מריץ קונטיינרים או אתרים אחרים; בדקו תחילה את ההתקנה הקיימת ואת האפשרות להתנגשות בין חבילות. עבור Debian או הפצה אחרת השתמשו בהוראות הרשמיות המתאימות למערכת, ולא בפקודות המיועדות ל-Ubuntu.

כעת בדקו את Docker, את התוסף Compose, את הגדרות ה-DNS ואת תיקיית העבודה:

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

אם getent hosts אינה מחזירה כתובת או מחזירה כתובת שגויה, תקנו את ה-DNS לפני הפעלת Caddy; החליפו את n8n.example.com בכל המקומות במדריך בשם המארח האמיתי שלכם. Docker דורש בדרך כלל הרשאות root: אם משתמש ה-SSH שלכם אינו יכול להפעיל ישירות את docker compose הפקודות הבאות, הוסיפו בתחילתן sudoהוספת משתמש לקבוצת docker מעניקה הרשאות השקולות ל-root, ולכן אין לבצע זאת כלאחר יד בשרת משותף.

ודאו שפורט הניהול של SSH נשאר נגיש לפני הפעלת חומת האש. אפשרו תעבורת HTTP נכנסת (80) ו-HTTPS (443) להנפקת תעודות ולגישה לעורך. פורטים שקונטיינרים מפרסמים באמצעות Docker יכולים לעקוף חלק מכללי UFW, ולכן עיינו בהנחיות חומת האש של Docker ופרסמו רק את הפורטים המיועדים של Caddy. דוגמת Compose זו במכוון אינו אינה חושפת את PostgreSQL ‏(5432), את n8n ‏(5678) או את הברוקר של מנגנון הרצת המשימות (5679) לאינטרנט הציבורי.

2. יצירת ערכי סביבה ושמירת מפתח ההצפנה

מתיקיית הפרויקט צרו שלושה ערכים שונים אקראיים בפורמט הקסדצימלי באמצעות:

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

צרו קובץ בשם .env לפי התבנית שלהלן, החליפו כל מופע של REPLACE_WITH_RANDOM_HEX בערך שונה שיצרתם, ושנו את שם המארח ואת אזור הזמן. תג הגרסה 2.42.5 המוצג הוא תג גרסה יציבה שהייתה רשומה ב-8 באוקטובר 2026והוא משמש כאן דוגמת הגדרה המתייחסת לתאריך זה, לא כהבטחה שההתקנה נבדקה בפועל או שתישאר מאובטחת בעתיד. לפני ההתקנה בדקו את גרסאות n8n הרשמיות העדכניות, והשתמשו באותה גרסה מאומתת של n8n ושל תמונת מנגנון הרצת המשימות.

# .env — replace the three example secrets
# Pin a maintained n8n release; keep n8n and runner equal.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

לעולם אל תעלו את .env למאגר קוד ציבורי. שמרו את מפתח ההצפנה ואת הוראות השחזור בצורה מאובטחת מחוץ ל-VPS. המפתח חייב להישאר זהה גם לאחר יצירת הקונטיינר מחדש או העברת המערכת.

3. יצירת קובץ compose.yaml להתקנה חדשה

באותה תיקייה צרו את compose.yamlהדוגמה משתמשת במוסכמות הרשמיות של משתני הסביבה של n8n ובנתיב הנתונים של PostgreSQL 18 PGDATA המתועד בפרויקט האירוח של n8n:

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

לארבעת השירותים תפקידים שונים: PostgreSQL שומר את נתוני מסד הנתונים, ו-n8n מפעיל את תהליכי העבודה; n8n-runner שירות הרצת המשימות מבצע משימות Runner עם גרסה תואמת ואסימון אימות משותף, ו-Caddy מטפל ב-HTTPS הציבורי. מנגנון חיצוני של הרצת משימות אינו מצב תור המבוסס על Redis. רק Caddy מפרסם פורטים במארח. הדוגמה המצומצמת משתמשת בתפקיד מסד נתונים אחד לשם פשטות; להפרדת הרשאות חזקה יותר ב-PostgreSQL עיינו בדוגמה הרשמית להתקנת n8n עם PostgreSQL.

4. יצירת Caddyfile עבור HTTPS

צרו את הקובץ Caddyfile (עם האות C הגדולה וללא סיומת) לצד compose.yaml. החליפו בכל מקום את שם המארח שבדוגמה בשם ה-DNS שלכם:

n8n.example.com {
    reverse_proxy n8n:5678
}

Caddy מבקש ומחדש תעודות TLS ציבוריות כאשר הדומיין מפוענח כראוי וניתן להגיע מבחוץ לפורטים 80/443. אל תפנו את ה-DNS אל localhost. אם תחליפו את Caddy בפרוקסי הפוך אחר, העבירו את כותרות הבקשה המכילות את שם המארח המקורי, הפרוטוקול וכתובת הלקוח, והתאימו את N8N_PROXY_HOPS למספר מעברי הפרוקסי המהימנים בפועל.

5. הפעלת הקונטיינרים ובדיקה מבחוץ

הריצו את הפקודות הבאות מתיקיית הפרויקט לאחר שמירת .env, compose.yaml ו- Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

הפקודה האחרונה בודקת את נקודת הקצה של HTTPS הציבורי לבדיקת תקינות השירות. אם הנפקת התעודה עדיין ממתינה, בדקו את יומני Caddy ואת הגדרות ה-DNS והפורטים לפני שתסיקו שיש תקלה ב-n8n. פתחו את https://n8n.example.com, צרו מיד את חשבון הבעלים הראשון והפעילו אמצעי הגנה מתאימים לכניסה. ודאו שהמופע אכן מריץ תהליך עבודה, ולא רק שהעורך נטען:

  1. בעורך צרו תהליך עבודה עם טריגר מסוג Webhook והגדירו את שיטת HTTP לערך GET, בחרו את Path vps-check, והגדירו את מועד התגובה לערך מיד. שמרו את תהליך העבודה.
  2. לחצו על האזנה לאירוע בדיקהוהעתיקו את כתובת הבדיקה המלאה שמציג n8n. ממכשיר אחר הריצו curl -i 'PASTE_TEST_URL_HERE' עם ה-URL שהעתקתם. אמורה להתקבל תגובת HTTP המעידה על הצלחה, והאירוע הנכנס אמור להופיע בעורך n8n. כתובות בדיקה פועלות רק כאשר n8n מאזין לאירוע.
  3. פרסמו את תהליך העבודה, עברו בְּצומת אל כתובת סביבת הייצורוהעתיקו אותה. הריצו curl -i 'PASTE_PRODUCTION_URL_HERE' שוב. ודאו שההרצה מופיעה בלשונית הרצות של תהליך העבודה. בקשות Webhook לסביבת ייצור מחייבות שתהליך העבודה יהיה מפורסם, והנתונים שלהן אינם מוצגים בתצוגת הבדיקה של העורך.

זוהי בדיקת תקינות בסיסית ופשוטה במכוון, ללא אימות משתמשים: לעולם אל תשלחו אליה סודות. לאחר הבדיקה בטלו את פרסום התהליך או מחקו אותו; לחלופין, הגדירו אימות ל-Webhook והגבלות IP לפני שימוש בנקודת קצה ציבורית עם נתונים אמיתיים. ראו את התיעוד הרשמי של Webhooks במצב בדיקה וייצור.

6. גיבוי לפני שינוי גרסאות מקובעות

שמרו גיבוי PostgreSQL שניתן לשחזר ממנו, ו- את נפח האחסון המתמשך של n8n, .envאת מפתח ההצפנה ואת הקבצים החיצוניים הנדרשים באחסון שמחוץ לשרת זה. ודאו שהשחזור מצליח לפי מדריך הגיבוי וההתאוששות לפני עדכון סביבת הייצור. פקודות לדוגמה:

# Back up the database, encryption key, instance data,
# and files before changing the pinned versions.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# After securing the backup outside this VPS:
docker compose pull
docker compose up -d
docker compose ps

שנו את הגרסה המקובעת של N8N_VERSION רק לאחר קריאת הערות הגרסה; יש לעדכן יחד את תמונות n8n ומנגנון הרצת המשימות. אל תריצו docker compose down -v במהלך תחזוקה שוטפת, משום שהפעולה מוחקת נפחי אחסון בעלי שמות. מעבר בין גרסאות ראשיות של PostgreSQL מחייב שדרוג מסד נתונים או תוכנית גיבוי ושחזור; החלפת תמונת Postgres 18 בתג של גרסה ראשית אחרת אינה מבצעת העברה אוטומטית.

מקורות מוסמכים: מדריך Docker Compose של n8n, הגדרות הפרוקסי ההפוך וה-Webhooks של n8n, והנחיות ההתקנה הרשמיות של PostgreSQL. אין כאן הנחה שנערך מבחן ביצועים לתשתית או שקיימת אצל ספק מסוים תכונה מותקנת מראש.

כתובת Webhook

הגדירו את N8N_WEBHOOK_URL לכתובת הבסיס של HTTPS הנגישה לציבור, והגדירו את N8N_PROXY_HOPS=1 כאשר יש פרוקסי הפוך מהימן אחד. WEBHOOK_URL הוא שם חלופי שהוצא משימוש החל מ-n8n 2.35.0; אל תעתיקו אותו ממדריכים ישנים.

שאלות נפוצות

שאלות נפוצות על התקנת n8n באמצעות Docker

האם n8n חייב להשתמש ב-PostgreSQL בסביבת Docker?

Docker אינו מחייב שימוש ב-PostgreSQL, והתקנות קטנות יכולות להשתמש ב-SQLite. בהתקנת VPS המיועדת לייצור, PostgreSQL מספק בסיס חזק יותר למסד הנתונים ותומך בהרחבה עתידית באמצעות מצב תור.

למה צריך נפח אחסון מתמשך של n8n אם הנתונים נשמרים ב-PostgreSQL?

תיקיית n8n המתמשכת עשויה להכיל נתוני מצב והגדרות חשובים של המופע. שמרו אותה בהתאם לארכיטקטורת ההתקנה, ואל תניחו שמסד הנתונים הוא הרכיב היחיד הנדרש לשחזור.

למה ה-Webhook שלי מציג localhost?

כתובת הקונטיינר הפנימית שונה מכתובת הגישה הציבורית. הגדירו את שם המארח החיצוני, הפרוטוקול וכתובת ה-Webhook, וודאו שהפרוקסי ההפוך מעביר את כותרות הבקשה הדרושות.

האם צריך לחשוף את פורט 5678 לאינטרנט?

בהתקנת ייצור רגילה מאחורי פרוקסי הפוך, חשפו את HTTPS דרך הפרוקסי והשאירו את פורט היישום של n8n פנימי, אלא אם יש סיבה תפעולית מוגדרת לפעול אחרת.

האם צריך Redis?

לא בהתקנת Docker רגילה עם מופע יחיד. Redis נחוץ כאשר עוברים במכוון למצב תור ולהרצה באמצעות תהליכי Worker.

האם מנגנוני הרצת המשימות החיצוניים של n8n זהים ל-Workers של מצב תור?

לא. מנגנוני הרצת משימות חיצוניים מבצעים קוד משימות נתמך בנפרד מהתהליך הראשי של n8n ומשתמשים באסימון אימות משותף. מצב תור המבוסס על Redis מחלק את הרצות תהליכי העבודה בין Workers ודורש תשתית נפרדת. הדוגמה כאן מציגה מנגנון חיצוני להרצת משימות, ולא מצב תור של Redis. הקפידו שגרסת תמונת ה-Runner תתאים לגרסת n8n.
