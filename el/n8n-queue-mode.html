Λειτουργία ουράς του n8n

Η λειτουργία ουράς διαχωρίζει την εκτέλεση της ροής εργασίας από την κύρια διαδικασία n8n. Η κύρια παρουσία λαμβάνει ενεργοποιήσεις και δημιουργεί εκτελέσεις, η Redis συντονίζει την ουρά, οι workers εκτελούν εργασίες και η PostgreSQL αποθηκεύει την κοινή ροή εργασίας και τα δεδομένα εκτέλεσης.

ΓΡΗΓΟΡΗ ΑΠΟΦΑΣΗ

Χρειάζεστε πραγματικά λειτουργία ουράς;

Παραμείνετε σε κανονική λειτουργία όταν

Μια μεμονωμένη περίπτωση χειρίζεται άνετα τις κορυφαίες εκτελέσεις και οι CPU, RAM και η καθυστέρηση εκτέλεσης παραμένουν σταθερά. Η λειτουργία ουράς προσθέτει στοιχεία που δεν χρειάζεστε ακόμα.

Εξετάστε τη λειτουργία ουράς όταν

Οι συνεχείς παράλληλες εκτελέσεις δημιουργούν διαμάχη, η καθυστέρηση εκτέλεσης αυξάνεται υπό φορτίο ή πρέπει να προσθέσετε ικανότητα εκτέλεσης εκτελώντας πολλούς workers.

Κλίμακα κατακόρυφα πρώτα όταν

Το σημείο συμφόρησης είναι απλώς ανεπαρκές CPU ή RAM και ένα μεγαλύτερο παράδειγμα μπορεί να ανταποκριθεί πλήρως στον φόρτο εργασίας.

Μετρήστε πριν αλλάξετε αρχιτεκτονική

Χρησιμοποιήστε ταυτόχρονη αιχμή, CPU, RAM, διάρκεια εκτέλεσης, βάθος ουράς και πίεση βάσης δεδομένων για να δικαιολογήσετε τη μετακίνηση.

ΑΡΧΙΤΕΚΤΟΝΙΚΗ

Πώς λειτουργεί η λειτουργία ουράς του n8n

1 · ΚύριαΛαμβάνει χρονόμετρα, webhooks και αιτήματα ροής εργασίας και δημιουργεί μια εκτέλεση αντί να κάνει η ίδια την εκτέλεση παραγωγής.
2 · RedisΛειτουργεί ως μεσίτης μηνυμάτων. Διατηρεί εκκρεμή μηνύματα εκτέλεσης, ώστε ο επόμενος διαθέσιμος workers να μπορεί να διεκδικήσει μια θέση εργασίας.
3 · WorkerΛαμβάνει το αναγνωριστικό εκτέλεσης, φορτώνει δεδομένα ροής εργασίας από την κοινόχρηστη βάση δεδομένων, εκτελεί τη ροή εργασίας και εγγράφει το αποτέλεσμα.
4 · PostgreSQLΠαρέχει κοινόχρηστα μόνιμα δεδομένα ροής εργασίας και εκτέλεσης. Η λειτουργία κατανεμημένης ουράς δεν υποστηρίζεται μέσω της SQLite.

ΒΑΣΙΚΕΣ ΑΠΑΙΤΗΣΕΙΣ

Τι χρειάζεται κάθε εγκατάσταση σε λειτουργία ουράς

Redis

Όλες οι κύριες διαδικασίες και οι διεργασίες εργασίας χρειάζονται αξιόπιστη πρόσβαση στην υπηρεσία Redis που χρησιμοποιείται για τον συντονισμό της ουράς.

PostgreSQL

Ο κύριος και οι workers πρέπει να μοιράζονται τη βάση δεδομένων. Η λειτουργία ουράς είναι μια κατανεμημένη αρχιτεκτονική και δεν πρέπει να σχεδιάζεται γύρω από την SQLite.

Αντιστοίχιση διαμόρφωσης n8n

Το Main και οι workers πρέπει να εκτελούν τη λειτουργία ουράς και να μοιράζονται τη διαμόρφωση που απαιτείται για πρόσβαση στα Redis, PostgreSQL και στα κρυπτογραφημένα διαπιστευτήρια.

Εργατική ικανότητα

Οι workers χρειάζονται αρκετές CPU και RAM για τις ροές εργασίας που εκτελούν. Η προσθήκη διεργασιών δεν αφαιρεί το κόστος πόρων κάθε εκτέλεσης.

Ενεργοποιήστε τη λειτουργία ουράς σε μια υπάρχουσα αυτο-φιλοξενούμενη στοίβα. Πρώτα επιβεβαιώστε ότι η κύρια υπηρεσία n8n και κάθε workers μπορούν να αποκτήσουν πρόσβαση στην ίδια βάση δεδομένων PostgreSQL και Redis μέσω ενός ιδιωτικού δικτύου. Σετ EXECUTIONS_MODE=queue τόσο στον κύριο όσο και στους workers και στον εφοδιασμό QUEUE_BULL_REDIS_HOST=redis και QUEUE_BULL_REDIS_PORT=6379 όταν redis είναι το πραγματικό όνομα της υπηρεσίας Compose. Χρήση DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres και αντιστοίχιση DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER και DB_POSTGRESDB_PASSWORD σε κάθε διαδικασία? αντικαταστήστε τα παραδείγματα ονομάτων υπηρεσιών με τα δικά σας. Δώστε τα ακριβή υπάρχοντα N8N_ENCRYPTION_KEY σε όλους αυτούς. Ποτέ μην δημοσιεύετε τις θύρες κεντρικού υπολογιστή Redis ή PostgreSQL απλώς για τη σύνδεση κοντέινερ στο ίδιο δίκτυο Compose.

Εκκινήστε έναν εκτελεστή, όχι έναν δεύτερο επεξεργαστή. Προσθέστε μια υπηρεσία workersυ n8n χρησιμοποιώντας την ίδια καρφιτσωμένη έκδοση εικόνας n8n και τις κοινόχρηστες ρυθμίσεις ως κύρια, αλλά εκτελέστε την με το worker εντολή. Αν ονομάσατε αυτήν την υπηρεσία n8n-worker, ξεκινήστε με docker compose up -d n8n-worker. Αφού επιβεβαιώσετε την πραγματική εκτέλεση σε έναν workers, μπορείτε να χρησιμοποιήσετε docker compose up -d --scale n8n-worker=2 για να ξεκινήσει ένας δεύτερος workers από αυτήν την υπηρεσία. Πρόκειται για προσθήκες σε ένα υπάρχουν σωστά διαμορφωμένες Σύνθεση στοίβας, όχι μεμονωμένο αρχείο εγκατάστασης. κρατήστε τους υπάρχοντες μόνιμους τόμους, το διακομιστή μεσολάβησης HTTPS, τα μυστικά και τα αντίγραφα ασφαλείας.

Λειτουργία ουράς Σύνθεση θραύσματος για μια υπάρχουσα στοίβα. Συγχωνεύστε το παρακάτω παράδειγμα στο τρέχον σας compose.yaml; είναι όχι μια πλήρη αυτόνομη ανάπτυξη. Προϋποθέτει ότι έχετε ήδη επίμονο, ιδιωτικό postgres και n8n υπηρεσίες, ένα υπάρχον N8N_VERSION καρφίτσα στο περιβάλλον σας και το δικό σας προστατευμένο POSTGRES_PASSWORD και πρωτότυπο N8N_ENCRYPTION_KEY. Αντιστοιχίστε τα ονόματα, τους τόμους, τη βάση δεδομένων και την έκδοστο n8n με το υπάρχον έργο. Προσθέστε τις ρυθμίσεις Redis της λειτουργίας ουράς και EXECUTIONS_MODE=queue και στην υπάρχουσα κύρια υπηρεσία, όπως περιγράφεται παραπάνω.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Δεν δημοσιεύεται καμία θύρα κεντρικού υπολογιστή για την Redis ή τον workers σε αυτό το τμήμα. Redis η επιμονή μόνο για προσάρτηση είναι ένα επιπλέον επίπεδο ανάκτησης, όχι ένα υποκατάστατο για αντίγραφα ασφαλείας εκτός διακομιστή. Διατηρήστε την υπάρχουσα HTTPS και τη διαμόρφωση ελέγχου ταυτότητας αμετάβλητη. Για τους κόμβους κώδικα που απαιτούν εξωτερικούς δρομείς εργασιών, ρυθμίστε τις παραμέτρους των διεργασιών εκτέλεσης για την ανάπτυξη του workersυ σας ξεχωριστά. Η ίδια η λειτουργία ουράς δεν αντικαθιστά τους δρομείς εργασιών.

Μετατροπή μιας υπάρχουσας παρουσίας SQLite; Μην αλλάζετε απλά DB_TYPE και ξεκινήστε από μια κενή βάση δεδομένων PostgreSQL: με αυτόν τον τρόπο δεν μεταφέρονται οι παλιές ροές εργασίας και τα διαπιστευτήρια. Πριν από οποιαδήποτε αποκοπή, δημιουργήστε αντίγραφα ασφαλείας της βάσης δεδομένων πηγής, μόνιμα .n8n κατάλογο και αρχικό κλειδί κρυπτογράφησης. χρησιμοποιήστε μια υποστηριζόμενη διαδικασία εξαγωγής/εισαγωγής ή μετεγκατάστασης n8n και, στη συνέχεια, επαληθεύστε τις ροές εργασίας και τα κρυπτογραφημένα διαπιστευτήρια σε έναν ξεχωριστό στόχο. Διατηρήστε τα αρχικά αρχεία για επαναφορά και χρησιμοποιήστε τον οδηγό δημιουργίας αντιγράφων ασφαλείας και επαναφοράς που συνδέεται παρακάτω για προετοιμασία ανάκτησης. Μην διαγράψετε ποτέ database.sqlite ως συντόμευση.

ΣΥΓΧΡΟΝΟΣ ΕΡΓΑΤΩΝ

Οι workers κλιμακώνονται ανά αριθμό και ανά παράλληλες εργασίες

Κάθε workers μπορεί να επεξεργαστεί πολλές εργασίες ταυτόχρονα. Η τρέχουσα προεπιλεγμένη συγχρονισμός workers του n8n είναι η 10 και η τεκμηρίωσή της συνιστά τη συγχρονισμό 5 ή υψηλότερη. Ο πολύ χαμηλός συγχρονισμός σε συνδυασμό με πολλούς workers μπορεί να δημιουργήσει περιττές συνδέσεις βάσης δεδομένων και να εξαντλήσει τη δεξαμενή σύνδεσης της βάσης δεδομένων.

Αυξήστε τη συγχρονικότητα όταν

Ένας workers έχει επιπλέον CPU και RAM και οι ροές εργασίας περιμένουν κυρίως σε εξωτερικές υπηρεσίες αντί για κορεσμό υπολογιστών ή μνήμης.

Προσθήκη workers όταν

Μία διεργασία workers γίνεται εμπόδιο και η βάση δεδομένων, η Redis και η υποδομή έχουν ικανότητα για πιο παράλληλη εκτέλεση.

Μειώστε την ταυτόχρονη όταν

Οι μεμονωμένες ροές εργασίας είναι βαριές με μνήμη ή CPU-βαριές και οι παράλληλες εργασίες προκαλούν διαμάχη, πίεση OOM ή ασταθείς χρόνους εκτέλεσης.

Παρακολουθήστε PostgreSQL

Περισσότεροι workers και περισσότερη ταυτόχρονη αύξηση της δραστηριότητας της βάσης δεδομένων. Η κλιμάκωση της χωρητικότητας εκτέλεσης χωρίς χωρητικότητα βάσης δεδομένων μπορεί να μετακινήσει το σημείο συμφόρησης αντί να το αφαιρέσει.

Μάθετε ποιο όριο συγχρονισμού ισχύει πραγματικά. Ένας workers μπορεί να αρχίσει να χρησιμοποιεί n8n worker --concurrency=5, ή την αντίστοιχη εντολή workers στην υπηρεσία Σύνταξης. Αν N8N_CONCURRENCY_PRODUCTION_LIMIT ορίζεται ρητά σε τιμή διαφορετική από -1, αυτή η ρύθμιση έχει προτεραιότητα στη λειτουργία ουράς. διαφορετικά το n8n χρησιμοποιεί του workers --concurrency τιμή ή προεπιλογή της 10. Μην πολλαπλασιάσετε τον αριθμό των workers με μια ονομαστική προεπιλογή και καλέστε το εγγυημένη απόδοση: η πραγματική χωρητικότητα εξαρτάται από τη διάρκεια εργασίας, την CPU, τη μνήμη, τα εξωτερικά API και τις συνδέσεις PostgreSQL.

ΙΣΤΟΣΕΛΙΔΑ

Η λειτουργία ουράς μπορεί να αυξήσει την καθυστέρηση ανάθεσης εκτελέσεων

Η κύρια διαδικασία ή η διαδικασία webhook λαμβάνει το αίτημα HTTP, αλλά ένας workers εκτελεί την εκτέλεση της ροής εργασίας. Αυτή η μεταβίβαση μέσω της Redis προσθέτει κάποια γενικά έξοδα. Για webhook ευαίσθητα σε καθυστέρηση, μετρήστε τον χρόνο απόκρισης από άκρο σε άκρο αντί να υποθέσετε ότι περισσότεροι workers κάνουν αυτόματα κάθε αίτημα πιο γρήγορα.

ΛήψηΗ διαδικασία κύριας/webhook αποδέχεται το αίτημα.
ΟυράΗ εκτέλεση παραδίδεται στην Redis.
ΕκτελέστεΈνας διαθέσιμος workers εκτελεί τη ροή εργασίας.
ΑπαντήστεΤο αποτέλεσμα αναμεταδίδεται πίσω μέσω της διαδρομής ουράς όταν απαιτείται.

Δρομολογήστε την κίνηση δεδομένων του webhook στη σωστή διαδικασία. Με αφιερωμένο n8n webhook επεξεργαστές πίσω από έναν αντίστροφο διακομιστή μεσολάβησης ή έναν εξισορροπητή φορτίου, δρομολογούν διαδρομές παραγωγής /webhook/* και /webhook-waiting/* στους επεξεργαστές webhook? κρατήστε /webhook-test/*, αιτήματα επεξεργασίας και API στο κύριο. Μην τοποθετείτε main στο load-balancing pool του webhook παραγωγής, εκτός και αν αποδεχτείτε σκόπιμα αυτόν τον πρόσθετο φόρτο εργασίας. Α Απαντήστε στο Webhook Η ροή εργασίας μπορεί να κρατήσει τον πελάτη σε αναμονή έως ότου ο workers ολοκληρώσει και επιστρέψει την απάντησή του, επομένως η λειτουργία ουράς δεν αποτελεί υπόσχεση για άμεσες απαντήσεις HTTP ή μηδενικά χρονικά όρια. Ελέγξτε την πραγματική συμπεριφορά εξωτερικής επανάκλησης και απόκρισης πριν αλλάξετε την κίνηση δεδομένων.

ΔΥΔΙΚΑ ΔΕΔΟΜΕΝΑ

Μην παραβλέπετε την κοινόχρηστη αποθήκευση

Περιορισμός συστήματος αρχείων

Η λειτουργία ουράς δεν υποστηρίζει την αποθήκευση δυαδικών δεδομένων συστήματος αρχείων ως το κοινό μοντέλο επιμονής για κατανεμημένους workers.

Εξωτερική δυαδική αποθήκευση

Όταν οι ροές εργασίας πρέπει να παραμένουν δυαδικά δεδομένα σε κατανεμημένους workers, χρησιμοποιήστε μια σχεδίαση αποθήκευσης στην οποία μπορεί να έχει πρόσβαση κάθε απαιτούμενη παρουσία, όπως η υποστηριζόμενη αποθήκευση εξωτερικών αντικειμένων.

Μεγάλες απαντήσεις webhook

Οι απαντήσεις Webhook από τους workers ταξιδεύουν πίσω προς τη διαδικασία λήψης. Τα μεγάλα σώματα απόκρισης μπορούν να αυξήσουν την πίεση μνήμης Redis και απαιτούν σκόπιμη διαμόρφωση αποθήκευσης απόκρισης.

Σχεδιάστε πριν από τη διανομή των workers

Ένας φόρτος εργασίας που εξαρτάται σε μεγάλο βαθμό από τα τοπικά αρχεία πρέπει να επανασχεδιαστεί για κοινή επιμονή προτού οι workers κατανεμηθούν σε όλα τα μηχανήματα.

Μεγάλο όριο απόκρισης webhook. Η τρέχουσα τεκμηρίωστο n8n δίνει N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX μια προεπιλογή του 64 MiB για την απάντηση ενός workers που εστάλη πίσω από την ουρά. Η Redis μπορεί να κρατήσει πολλά αντίγραφα εν πτήσει, επομένως ο προϋπολογισμός είναι περίπου 1.5 φορές το μέγεθος απόκρισης στη μνήμη Redis ανά ταυτόχρονη μεγάλη απόκριση. Χωρίς εκφόρτωση, μια υπερμεγέθη απόκριση αποτυγχάνει αντί να γίνει ως δια μαγείας ταχύτερη με την προσθήκη workers.

Όρια έκδοσης και άδειας χρήσης. Από n8n 2.34.0, οι workers μπορούν να χρησιμοποιήσουν N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true για να μεταφορτώσετε υπερμεγέθη σώματα απόκρισης webhook σε αναγνώσιμο κοινόχρηστο δυαδικό χώρο αποθήκευσης, αλλά πρώτα αναβαθμίστε κάθε κύριος και webhook επεξεργαστής στην 2.34.0 ή μεταγενέστερη. Το επιλεγμένο N8N_DEFAULT_BINARY_DATA_MODE πρέπει να αποθηκεύουν πραγματικά δεδομένα και να είναι αναγνώσιμα από κάθε συμμετέχουσα διαδικασία. Ο εξωτερικός δυαδικός χώρος αποθήκευσης S3 και Azure απαιτούν έγκυρη αυτο-φιλοξενία Επιχείρηση ή Επιχείρηση άδεια? μην υποθέσετε ότι η Community Edition μπορεί να τις ενεργοποιήσει. Το database Η δυαδική λειτουργία μπορεί να εκφορτώνει μια απόκριση μεγάλου μεγέθους χωρίς εξωτερική αποθήκευση επί πληρωμή, αλλά η κύρια εμφάνιση φορτώνει ολόκληρο το αποθηκευμένο σώμα στη μνήμη και η αποθήκευση της βάσης δεδομένων έχει το δικό της όριο μεγέθους αρχείου. Για απόκριση-εκφόρτωση σώματος συγκεκριμένα, το n8n περιγράφει επίσης ένα κοινόχρηστο filesystem επιλογή όταν κάθε στιγμιότυπο προσαρτά τον ίδιο δίσκο, αλλά ρητά δεν συνιστά αυτή τη διάταξη. Μην μπερδεύετε αυτήν την ειδική διαδρομή εκφόρτωσης ως υποστήριξη μόνιμων δυαδικών δεδομένων που βασίζονται σε σύστημα αρχείων σε μια ανάπτυξη κατανεμημένης λειτουργίας ουράς. Ελέγξτε την έκδοση, την έκδοση και τη διαμόρφωση αποθήκευσης πριν ενεργοποιήσετε τη μεταφόρτωση.

ΠΑΡΑΚΟΛΟΥΘΗΣΗ

Ελέγξτε αν η ουρά βελτιώνει πραγματικά την απόδοση

Βάθος ουράς

Μια ουρά που μεγαλώνει πιο γρήγορα από ό,τι την αποστραγγίζουν οι workers υποδηλώνει ανεπαρκή ικανότητα εκτέλεσης ή συμφόρηση κατάντη.

Εργαζόμενος CPU & RAM

Μέτρηση κορεσμού και κορυφών μνήμης ανά workers. Οι αδρανείς workers με μια αυξανόμενη ουρά οδηγούν σε έναν άλλο περιορισμό.

Καθυστέρηση εκτέλεσης

Παρακολουθήστε την καθυστέρηση μεταξύ της δημιουργίας μιας εκτέλεσης και της πραγματικής έναρξης, όχι μόνο του ίδιου του χρόνου εκτέλεσης της ροής εργασίας.

Έλεγχοι υγείας

Τα τελικά σημεία υγείας των workers μπορούν να αναφέρουν εάν ένας workers είναι ζωντανός και εάν η βάση δεδομένων του και οι συνδέσεις Redis είναι έτοιμες.

Επαληθεύστε την εκτέλεση σε έναν workers, όχι μόνο σε ένα πράσινο δοχείο. Με μια σωστά διαμορφωμένη στοίβα Compose, ελέγξτε docker compose ps και docker compose logs --tail=100 n8n-worker (αντικαταστήστε το όνομα της υπηρεσίας εάν είναι διαφορετικό). Τρέξτε ένα αβλαβές δημοσιευμένη παραγωγή ροή εργασιών χρησιμοποιώντας μια προγραμματισμένη ενεργοποίηση ή δοκιμαστικό webhook και, στη συνέχεια, αντιστοιχίστε την εκτέλεσή της στην προβολή Εκτελέσεις του n8n με την πραγματική επεξεργασία του workersυ στα αρχεία καταγραφής workers. Ένα πρόγραμμα επεξεργασίας που ανοίγει με επιτυχία, ένα κοντέινερ Redis που εκτελείται ή μια εκτέλεση σε ουρά μόνο κάνει όχι αποδείξει ότι ένας workers έχει εκτελέσει τη δουλειά.

Ελέγξτε τις εξαρτήσεις και την ετοιμότητα. Με προεπιλεγμένα παραδείγματα ονομάτων υπηρεσιών, docker compose exec -T redis redis-cli ping πρέπει να λάβει PONG όταν ο έλεγχος ταυτότητας Redis το επιτρέπει, και docker compose exec -T postgres pg_isready -U n8n -d n8n ελέγχει την ετοιμότητα PostgreSQL (προσαρμόστε τα διαπιστευτήρια και τα ονόματα υπηρεσιών). Ενεργοποίηση QUEUE_HEALTH_CHECK_ACTIVE=true σε έναν workers όταν χρειάζεστε ιδιωτικό /healthz και /healthz/readiness καταληκτικά σημεία? το τελικό σημείο ετοιμότητας ελέγχει τη συνδεσιμότητα Redis/βάσης δεδομένων. Μην εκθέτετε δημόσια αυτά τα τελικά σημεία των workers μόνο και μόνο για να τα παρακολουθείτε.

Οι χειροκίνητες εκτελέσεις είναι μια διαφορετική δοκιμή. Από προεπιλογή OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, επομένως η μη αυτόματη εκτέλεση μιας ροής εργασίας στο πρόγραμμα επεξεργασίας μπορεί να εκτελεστεί στο main ακόμα και όταν η λειτουργία ουράς έχει ρυθμιστεί σωστά. Ρυθμίστε το σε true μόνο εάν σκοπεύετε να στείλετε χειροκίνητες εκτελέσεις σε workers και έχετε ελέγξει την αλλαγή σε ένα περιβάλλον σκηνής. Οι workers στη λειτουργία ουράς διακρίνονται επίσης από τους εξωτερικούς δρομείς εργασιών n8n, οι οποίοι έχουν ξεχωριστές απαιτήσεις διαμόρφωσης για την εκτέλεση κόμβου κώδικα.

Η λειτουργία ουράς κλιμακώνει τις εκτελέσεις, αλλά δεν εξασφαλίζει από μόνη της υψηλή διαθεσιμότητα

Κοινή χρήση του κλειδιού κρυπτογράφησης

Κάθε workers πρέπει να χρησιμοποιεί το ίδιο N8N_ENCRYPTION_KEY ως το κύριο παράδειγμα, ώστε οι workers να μπορούν να αποκρυπτογραφήσουν τα διαπιστευτήρια που απαιτούνται από τις εκτελέσεις ροής εργασιών.

Διατηρήστε τις εκδόσεις ευθυγραμμισμένες

Οι διεργασίες Main, webhook και worker θα πρέπει να εκτελούν την ίδια έκδοστο n8n. Οι μικτές εκδόσεις μπορούν να δημιουργήσουν ασύμβατη συμπεριφορά κατά τη διάρκεια των κυλιόμενων αλλαγών.

Οι επεξεργαστές Webhook είναι ένα ξεχωριστό επίπεδο κλιμάκωσης

Όταν ο εισερχόμενος όγκος webhook γίνεται το σημείο συμφόρησης, οι αποκλειστικοί επεξεργαστές webhook μπορούν να βρίσκονται πίσω από έναν εξισορροπητή φορτίου ενώ οι workers χειρίζονται την εκτέλεση. Μην προσθέτετε αυτό το επίπεδο εκτός εάν ο μετρημένος όγκος αιτημάτων το δικαιολογεί.

Το multi-main είναι ένα διαφορετικό χαρακτηριστικό

Η εκτέλεση πολλών κύριων διεργασιών για υψηλή διαθεσιμότητα δεν είναι ίδια με τη συνηθισμένη λειτουργία ουράς. Το n8n τεκμηριώνει επί του παρόντος το multi-main ως μια αυτο-φιλοξενούμενη δυνατότητα Enterprise με πρόσθετες απαιτήσεις εξισορρόπησης φορτίου και περιόδου λειτουργίας.

Συχνές ερωτήσεις

Λειτουργία ουράς του n8n: συχνές ερωτήσεις

Η λειτουργία ουράς n8n απαιτεί Redis;

Ναι. Η Redis είναι ο μεσίτης μηνυμάτων που συντονίζει τις εκκρεμείς εκτελέσεις μεταξύ της κύριας παρουσίας και των workers.

Μπορεί η λειτουργία ουράς να χρησιμοποιήσει SQLite;

Όχι για την αρχιτεκτονική κατανεμημένης λειτουργίας ουράς. Η κύρια και οι workers χρειάζονται πρόσβαση σε κοινόχρηστη βάση δεδομένων και έγγραφα n8n PostgreSQL ως βάση δεδομένων για αυτήν τη ρύθμιση.

Πόσους workers πρέπει να τρέξω;

Δεν υπάρχει καθολική καταμέτρηση. Ξεκινήστε από τη μετρημένη ταυτόχρονη χρήση και τη χρήση των workers και, στη συνέχεια, προσθέστε χωρητικότητα ενώ παρακολουθείτε τις PostgreSQL, Redis, CPU, RAM και το βάθος της ουράς.

Τι είναι το n8n συγχρονισμός workers;

Είναι ο αριθμός των εργασιών που ένας workers μπορεί να επεξεργαστεί παράλληλα. Η τρέχουσα προεπιλογή είναι η 10 και το n8n συνιστά τη συγχρονισμό workers της 5 ή υψηλότερης αντί της δημιουργίας πολλών workers χαμηλής συγχρονισμού.

Πρέπει να ενεργοποιήσω τη λειτουργία ουράς σε ένα μικρό VPS;

Μόνο όταν ο φόρτος εργασίας το δικαιολογεί. Μια μικρή ανάπτυξη που λειτουργεί άνετα ως μία περίπτωση είναι συνήθως πιο απλή στη λειτουργία χωρίς Redis και χωριστούς workers.
