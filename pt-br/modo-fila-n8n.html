ESCALABILIDADE

Modo fila do n8n

O modo fila separa a execução dos workflows do processo main do n8n. A instância main recebe triggers e cria execuções, o Redis coordena a fila, os workers executam tarefas e o PostgreSQL armazena os dados compartilhados de workflows e execuções.

DECISÃO RÁPIDA

Você realmente precisa do modo fila?

Permaneça no modo normal quando

uma única instância lida confortavelmente com os picos de execução e CPU, RAM e latência permanecem estáveis. O modo fila adiciona componentes dos quais você ainda não precisa.

Considere modo fila quando

execuções paralelas contínuas criam contenção, a latência aumenta sob carga ou você precisa adicionar capacidade executando vários workers.

Escale verticalmente primeiro quando

o gargalo for simplesmente CPU ou RAM insuficientes e uma instância maior ainda conseguir atender bem à carga.

Meça antes de mudar a arquitetura

Use concorrência máxima, CPU, RAM, duração das execuções, profundidade da fila e pressão sobre o banco para justificar a mudança.

ARQUITETURA

Como funciona o modo fila do n8n

1 · MainRecebe timers, webhooks e solicitações de workflows e cria uma execução em vez de realizar a execução de produção por conta própria.
2 · RedisAtua como broker de mensagens. Mantém mensagens de execuções pendentes para que o próximo worker disponível possa assumir uma tarefa.
3 · WorkerRecebe o ID da execução, carrega os dados do workflow do banco compartilhado, executa o workflow e grava o resultado.
4 · PostgreSQLFornece dados persistentes compartilhados de workflows e execuções. O modo fila distribuído não é suportado com SQLite.

REQUISITOS BÁSICOS

O que todo deploy em modo fila precisa

Redis

Todos os processos main e worker precisam de acesso confiável ao serviço Redis usado para coordenar a fila.

PostgreSQL

Main e workers devem compartilhar o banco. O modo fila é uma arquitetura distribuída e não deve ser projetado em torno do SQLite.

Configuração consistente do n8n

Main e workers devem executar em modo fila e compartilhar a configuração necessária para acessar Redis, PostgreSQL e credenciais criptografadas.

Capacidade dos workers

Os workers precisam de CPU e RAM suficientes para os workflows que executam. Adicionar processos não elimina o custo de recursos de cada execução.

Ative o modo fila em um stack self-hosted existente. Primeiro confirme que o serviço main do n8n e cada worker conseguem alcançar o mesmo banco PostgreSQL e o Redis por uma rede privada. Defina EXECUTIONS_MODE=queue tanto em main quanto nos workers e forneça QUEUE_BULL_REDIS_HOST=redis e QUEUE_BULL_REDIS_PORT=6379 quando redis for o nome real do seu serviço Compose. Use DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres e valores correspondentes DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER e DB_POSTGRESDB_PASSWORD em cada processo; substitua os nomes dos serviços de exemplo pelos seus. Forneça a chave existente exata N8N_ENCRYPTION_KEY a todos eles. Nunca publique portas de host do Redis ou PostgreSQL apenas para conectar contêineres na mesma rede Compose.

Inicie um executor, não um segundo editor. Adicione um serviço worker do n8n usando a mesma versão fixada da imagem e as mesmas configurações compartilhadas do main, mas execute-o com o comando worker Se você nomeou esse serviço n8n-worker, inicie-o com docker compose up -d n8n-worker. Depois de confirmar uma execução real em um worker, você pode usar docker compose up -d --scale n8n-worker=2 para iniciar um segundo worker a partir desse serviço. Isso são adições a um stack Compose existente e configurado corretamente não um arquivo de instalação independente; mantenha seus volumes persistentes, proxy HTTPS, secrets e backups existentes.

Fragmento Compose de modo fila para um stack existente. Integre o exemplo abaixo ao seu compose.yamlatual; ele não é um deploy completo e independente. Ele pressupõe que você já tenha serviços privados e persistentes postgres e n8n além de uma versão N8N_VERSION fixada no ambiente e sua própria chave protegida POSTGRES_PASSWORD e original N8N_ENCRYPTION_KEY. Faça nomes, volumes, banco e versão do n8n corresponderem ao projeto existente. Adicione as configurações Redis do modo fila e EXECUTIONS_MODE=queue também ao serviço main existente, como descrito acima.

# Integre aos serviços existentes; não substitua seu arquivo Compose completo.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Nenhuma porta de host é publicada para Redis ou worker neste fragmento. A persistência append-only do Redis é uma camada adicional de recuperação, não é não um substituto para backups fora do servidor. Mantenha a configuração existente de HTTPS e autenticação sem alterações. Para nodes Code que exigem task runners externos, configure os processos runner do seu deploy de workers separadamente; o modo fila não substitui task runners.

Convertendo uma instância SQLite existente? Não altere simplesmente DB_TYPE e inicie contra um banco PostgreSQL vazio: isso não migra os workflows e credenciais antigos. Antes de qualquer mudança, faça backup do banco de origem, do diretório persistente .n8n e da chave de criptografia original; use um procedimento suportado de exportação/importação ou migração do n8n e depois verifique workflows e credenciais criptografadas em um destino separado. Mantenha os arquivos originais para rollback e use o guia de Backup & restauração abaixo para preparar a recuperação. Nunca exclua database.sqlite como atalho.

CONCORRÊNCIA DOS WORKERS

Workers escalam tanto pela quantidade de processos quanto pelas tarefas por worker

Cada worker pode processar várias tarefas simultaneamente. A concorrência padrão atual de worker no n8n é 10 e a documentação recomenda 5 ou mais. Concorrência muito baixa combinada com muitos workers pode criar conexões desnecessárias com o banco e esgotar o pool de conexões.

Aumente a concorrência quando

um worker tiver CPU e RAM livres e os workflows estiverem principalmente aguardando serviços externos em vez de saturar computação ou memória.

Adicione workers quando

um processo worker virar gargalo e banco, Redis e infraestrutura tiverem capacidade para mais execução paralela.

Reduza a concorrência quando

workflows individuais forem intensivos em memória ou CPU e tarefas paralelas causarem contenção, pressão OOM ou tempos de execução instáveis.

Monitore PostgreSQL

Mais workers e maior concorrência aumentam a atividade do banco. Escalar capacidade de execução sem capacidade do banco pode apenas deslocar o gargalo.

Saiba qual limite de concorrência realmente se aplica. Um worker pode ser iniciado usando n8n worker --concurrency=5, ou o comando equivalente de worker no serviço Compose. Se N8N_CONCURRENCY_PRODUCTION_LIMIT for definido explicitamente com um valor diferente de -1, essa configuração tem prioridade no modo fila; caso contrário, o n8n usa o valor --concurrency do worker ou o padrão de 10. Não multiplique a quantidade de workers por um valor nominal e chame isso de throughput garantido: a capacidade real depende da duração das tarefas, CPU, memória, APIs externas e conexões PostgreSQL.

WEBHOOKS

O modo fila pode adicionar latência na transferência de execução

O processo main ou webhook recebe a requisição HTTP, mas um worker executa o workflow. Essa transferência pelo Redis adiciona algum overhead. Para webhooks sensíveis à latência, meça o tempo de resposta ponta a ponta em vez de presumir que mais workers tornam automaticamente todas as requisições mais rápidas.

ReceberO processo main/webhook aceita a requisição.
FilaA execução é entregue ao Redis.
ExecutarUm worker disponível executa o workflow.
ResponderO resultado retorna pelo caminho da fila quando necessário.

Direcione o tráfego de webhooks ao processo correto. Com processadores dedicados n8n webhook atrás de reverse proxy ou load balancer, direcione as rotas de produção /webhook/* e /webhook-waiting/* aos processadores de webhook; mantenha /webhook-test/*, solicitações do editor e API no main. Não coloque main no pool de balanceamento de webhooks de produção, a menos que aceite deliberadamente essa carga adicional. Um Respond to Webhook workflow pode manter o cliente esperando até o worker terminar e retornar a resposta; portanto o modo fila não promete respostas HTTP instantâneas nem zero timeouts. Teste o callback externo real e o comportamento da resposta antes de mudar o tráfego.

DADOS BINÁRIOS

Não ignore o armazenamento compartilhado

Limitação do sistema de arquivos

O modo fila não suporta armazenamento de dados binários em sistema de arquivos como modelo de persistência compartilhada para workers distribuídos.

Armazenamento binário externo

Quando workflows precisam persistir dados binários entre workers distribuídos, use um design de armazenamento acessível por todas as instâncias necessárias, como object storage externo suportado.

Respostas grandes de webhook

Respostas de webhook dos workers retornam ao processo receptor. Bodies grandes podem aumentar a pressão de memória do Redis e exigir configuração consciente do armazenamento de respostas.

Planeje antes de distribuir workers

Uma carga que depende fortemente de arquivos locais precisa ser redesenhada para persistência compartilhada antes que workers sejam distribuídos entre máquinas.

Limite para grandes respostas de webhook. A documentação atual do n8n define para N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX um padrão de 64 MiB para a resposta de um worker enviada de volta pela fila. O Redis pode manter várias cópias em trânsito, então reserve aproximadamente 1.5 vezes o tamanho da resposta em memória Redis por resposta grande simultânea. Sem offloading, uma resposta grande demais falha em vez de ficar magicamente mais rápida com mais workers.

Limites de versão e licença. A partir do n8n 2.34.0, workers podem usar N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true para fazer offload de bodies de resposta grandes demais para armazenamento binário compartilhado legível, mas primeiro atualize todos os processos main e webhook para 2.34.0 ou posterior. O N8N_DEFAULT_BINARY_DATA_MODE selecionado precisa realmente armazenar os dados e ser legível por todos os processos participantes. Armazenamento binário externo S3 e Azure exige uma licença self-hosted válida Business ou Enterprise ; não presuma que a Community Edition consiga habilitá-los. O modo binário database pode fazer offload de uma resposta grande demais sem armazenamento externo pago, mas a instância main carrega todo o body armazenado na memória e o armazenamento de banco tem seu próprio limite de tamanho. Para especificamente o offload do body de resposta, o n8n também descreve uma opção compartilhada de filesystem quando todas as instâncias montam o mesmo disco, mas explicitamente não recomenda essa configuração. Não confunda esse caminho especial de offload com suporte a dados binários persistentes baseados em sistema de arquivos em um deploy distribuído de modo fila. Confira sua edição, versão e configuração de armazenamento antes de habilitar offload.

MONITORAMENTO

Saiba se a fila está ajudando

Profundidade da fila

Uma fila que cresce mais rápido do que os workers conseguem esvaziá-la indica capacidade insuficiente de execução ou gargalo posterior.

CPU & RAM dos workers

Meça saturação e picos de memória por worker. Workers ociosos com fila crescente apontam para outra limitação.

Latência de execução

Acompanhe o atraso entre uma execução ser criada e realmente começar, não apenas o tempo de execução do workflow.

Health checks

Endpoints de health dos workers podem indicar se um worker está ativo e se suas conexões com banco e Redis estão prontas.

Verifique a execução em um worker, não apenas um contêiner verde. Com um stack Compose configurado corretamente, verifique docker compose ps e docker compose logs --tail=100 n8n-worker (substitua o nome do serviço se for diferente). Execute um workflow inofensivo publicado de produção usando um trigger agendado ou webhook de teste e relacione sua execução na visão Executions do n8n com o processamento real nos logs do worker. Um editor que abre corretamente, um contêiner Redis em execução ou uma execução na fila, sozinhos, não é não provam que um worker executou a tarefa.

Verifique dependências e prontidão. Com os nomes de serviço padrão do exemplo, docker compose exec -T redis redis-cli ping deve receber PONG quando a autenticação do Redis permitir, e docker compose exec -T postgres pg_isready -U n8n -d n8n verifica a prontidão do PostgreSQL (adapte credenciais e nomes de serviço). Habilite QUEUE_HEALTH_CHECK_ACTIVE=true em um worker quando precisar dos endpoints privados /healthz e /healthz/readiness ; o endpoint de readiness verifica a conectividade Redis/banco. Não exponha esses endpoints dos workers publicamente apenas para monitorá-los.

Execuções manuais são um teste diferente. Por padrão OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, portanto executar manualmente um workflow no editor pode rodar no main mesmo quando o modo fila está configurado corretamente. Defina como true somente se você pretende enviar execuções manuais aos workers e tiver testado a mudança em um ambiente de staging. Workers de modo fila também são diferentes dos task runners externos do n8n, que têm requisitos próprios de configuração para execução de nodes Code.

LIMITE DE ALTA DISPONIBILIDADE

O modo fila escala execuções, mas não torna automaticamente o processo main altamente disponível

Compartilhe a chave de criptografia

Todo worker deve usar a mesma N8N_ENCRYPTION_KEY da instância main para que os workers consigam descriptografar credenciais necessárias às execuções.

Mantenha as versões alinhadas

Processos main, webhook e worker devem executar a mesma versão do n8n. Misturar versões pode criar comportamentos incompatíveis durante mudanças rolling.

Processadores de webhook são uma camada separada de escalabilidade

Quando o volume de webhooks recebidos vira gargalo, processadores dedicados podem ficar atrás de load balancer enquanto os workers cuidam das execuções. Não adicione essa camada sem que o volume medido justifique.

Multi-main é um recurso diferente

Executar vários processos main para alta disponibilidade não é o mesmo que o modo fila comum. O n8n atualmente documenta multi-main como recurso Enterprise self-hosted com requisitos adicionais de load balancer e sessão.

FAQ

Modo fila do n8n: perguntas frequentes

O modo fila do n8n exige Redis?

Sim. Redis é o broker de mensagens que coordena execuções pendentes entre a instância main e os workers.

Modo fila pode usar SQLite?

Não para a arquitetura distribuída do modo fila. Main e workers precisam de acesso compartilhado ao banco, e o n8n documenta PostgreSQL como banco para essa configuração.

Quantos workers devo executar?

Não existe quantidade universal. Comece pela concorrência medida e utilização dos workers e adicione capacidade enquanto monitora PostgreSQL, Redis, CPU, RAM e profundidade da fila.

O que é concorrência de worker no n8n?

É a quantidade de tarefas que um worker pode processar em paralelo. O padrão atual é 10, e o n8n recomenda concorrência de 5 ou mais em vez de criar muitos workers com baixa concorrência.

Devo ativar modo fila em um VPS pequeno?

Somente quando a carga justificar. Um deploy pequeno que funciona confortavelmente em uma instância geralmente é mais simples de operar sem Redis e workers separados.
