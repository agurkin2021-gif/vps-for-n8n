INSTALAÇÃO COM DOCKER

Instalar n8n em um VPS

Instale o n8n em um VPS usando Docker Compose e PostgreSQL. Um deploy de produção também precisa de dados persistentes da aplicação e do banco, uma N8N_ENCRYPTION_KEY, um hostname público, HTTPS e configuração correta de webhooks. Verifique esses componentes antes de ativar workflows de produção.

PRÉ-REQUISITOS

Prepare o VPS antes de iniciar o n8n

VPS Linux

Use um servidor Linux com manutenção e recursos suficientes para n8n, PostgreSQL, Docker e reverse proxy.

DNS

Aponte um domínio ou subdomínio para o VPS antes de emitir certificados TLS e publicar URLs de webhook.

Docker Compose

Instale Docker Engine e o plugin Compose usando pacotes compatíveis com o sistema operacional.

Firewall

Exponha apenas as portas web e de administração necessárias. Mantenha PostgreSQL e serviços internos da aplicação privados.

Instalando em um VPS que já hospeda sites? Você pode adicionar o n8n a um servidor que controla quando CPU, RAM e armazenamento permitirem. Porém, se Nginx, Apache, Caddy ou outro reverse proxy já ocupa as portas 80/443, não inicie o contêiner Caddy do exemplo abaixo sem alterações: as portas entrarão em conflito. Em vez disso, roteie um novo subdomínio do n8n pelo reverse proxy existente com rede privada adequada ou use um VPS limpo para seguir exatamente o exemplo Compose. Preserve os outros sites e a configuração TLS deles; o exemplo pressupõe que as portas 80/443 estejam disponíveis.

INSTALAÇÃO PARA COPIAR E ADAPTAR

Instale n8n no seu VPS com Docker Compose

Use este exemplo para montar um deploy do n8n em um VPS Linux autogerenciado. Você instala e mantém o n8n por conta própria; escolher um servidor pelo nosso parceiro não inclui uma instância n8n pré-instalada. O exemplo combina n8n, PostgreSQL, um task runner externo e Caddy HTTPS em uma rede privada do Compose. É um template de configuração, não uma afirmação de que o deploy foi testado em produção.

Prefere a instalação nova mais rápida? O n8n também oferece um setup oficial de Docker em uma linha. Você pode baixar e revisar o script com curl -fsSL https://get.n8n.io -o get-n8n.sh antes de executar sh get-n8n.sh. Essa opção inicia uma instância inicial com SQLite em uma URL local e inclui serviços sandbox do n8n Assistant; ela não é a mesma coisa que este deploy em VPS com HTTPS público e PostgreSQL. O stack sandbox oficial completo precisa de mais RAM e CPU que uma instalação enxuta do n8n (o guia Compose especifica pelo menos 4 GB RAM / 2 vCPUs). Para um VPS de produção exposto à Internet, continue com o stack configurado manualmente abaixo.

1. Prepare Docker, DNS e acesso

Conecte-se por SSH com acesso sudo e aponte um registro DNS A para n8n.example.com para o endereço IPv4 do VPS. Em um Ubuntu 22.04, 24.04 ou 26.04 recém-instalado VPS, os comandos a seguir instalam Docker Engine e o moderno plugin docker compose do repositório oficial assinado da apt Docker:

# Instalação oficial nova do Ubuntu 22.04 / 24.04 / 26.04
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Registre o repositório apt assinado do Docker
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

Este é o método de repositório orientado à produção do guia oficial de instalação do Docker no Ubuntu. Não reinstale nem remova Docker às cegas em um VPS que já executa contêineres ou outros sites; primeiro inspecione a instalação existente e possíveis conflitos de pacotes. Para Debian ou outra distribuição, use as instruções oficiais específicas do sistema em vez dos comandos do Ubuntu.

Agora verifique o Docker, o plugin Compose, DNS e o diretório de trabalho:

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

Se getent hosts não retornar endereço ou retornar o endereço errado, corrija o DNS antes de iniciar o Caddy; substitua n8n.example.com ao longo deste guia pelo seu hostname real. O Docker normalmente exige privilégios root: se seu usuário SSH não conseguir executar diretamente os comandos docker compose seguintes, coloque sudoantes deles. Adicionar um usuário ao grupo docker concede acesso equivalente a root e não deve ser feito sem cuidado em um servidor compartilhado.

Mantenha acessível sua porta real de administração SSH antes de ativar o firewall. Permita HTTP (80) e HTTPS (443) de entrada para emissão de certificados e acesso ao editor. Portas de contêiner publicadas pelo Docker podem contornar algumas regras UFW; revise a orientação de firewall do Docker e publique apenas as portas do Caddy previstas. Este exemplo Compose deliberadamente não não publica PostgreSQL (5432), n8n (5678) nem o broker do task runner (5679) na Internet pública.

2. Crie valores de ambiente e preserve a chave

No diretório do projeto, gere três valores hexadecimais aleatórios diferentes com:

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

Crie um arquivo chamado .env usando o template abaixo, substitua cada REPLACE_WITH_RANDOM_HEX por um valor gerado diferente e altere o hostname e o fuso horário. A tag 2.42.5 mostrada corresponde à versão estável listada em 8 de outubro de 2026, usada aqui como exemplo de configuração datado, não uma garantia de deploy testado em produção nem de segurança futura. Antes de instalar, verifique as versões oficiais atuais do n8n e mantenha o n8n e a imagem do task runner na mesma versão verificada.

# .env — substitua os três secrets de exemplo
# Fixe uma versão mantida do n8n; mantenha n8n e runner na mesma versão.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

Nunca faça commit de .env em um repositório público. Guarde a chave de criptografia e as instruções de recuperação com segurança fora do VPS. A chave deve permanecer a mesma após recriação de contêineres ou migração.

3. Crie compose.yaml para uma instalação nova

No mesmo diretório, crie compose.yamlO exemplo usa as convenções oficiais de variáveis de ambiente do n8n e o caminho PGDATA do PostgreSQL 18 documentado pelo projeto de hospedagem do n8n:

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

Os quatro serviços têm funções diferentes: PostgreSQL armazena o estado do banco, n8n executa workflows, n8n-runner executa tarefas do runner com versão correspondente e token de autenticação compartilhado, e Caddy cuida do HTTPS público. Um task runner externo não é o modo fila com Redis. Apenas o Caddy publica portas do host. Este exemplo enxuto usa um único role de banco para o setup; para separar melhor os privilégios do PostgreSQL, consulte o exemplo oficial de deploy PostgreSQL do n8n.

4. Crie o Caddyfile HTTPS

Crie o arquivo Caddyfile (C maiúsculo, sem extensão) ao lado de compose.yaml. Substitua o hostname de exemplo em todos os lugares pelo seu nome DNS:

n8n.example.com {
    reverse_proxy n8n:5678
}

O Caddy solicita e renova certificados TLS públicos quando o domínio resolve corretamente e o tráfego externo consegue alcançar as portas 80/443. Não aponte o DNS para localhost. Se substituir o Caddy por outro reverse proxy, encaminhe os headers originais de host, protocolo e endereço do cliente e ajuste N8N_PROXY_HOPS para o número real de saltos de proxy confiáveis.

5. Inicie os contêineres e teste de fora

Execute estes comandos no diretório do projeto depois de salvar .env, compose.yaml e Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

O último comando verifica o endpoint de saúde HTTPS público Se a emissão do certificado ainda estiver pendente, inspecione os logs do Caddy e DNS/portas antes de concluir que o n8n está com problema. Abra https://n8n.example.com, crie imediatamente a primeira conta owner e ative proteções adequadas de login. Confirme que a instância realmente executa um workflow, não apenas que o editor carrega:

  1. No editor, crie um workflow com um trigger Webhook Defina HTTP Method como GET, escolha o Path vps-check, e defina Respond como Immediately. Salve o workflow.
  2. Clique em Listen for Test Eventcopie a URL completa de Test URL mostrada pelo n8n e, em outro dispositivo, execute curl -i 'PASTE_TEST_URL_HERE' com a URL copiada. Espere uma resposta HTTP de sucesso e o evento recebido aparecendo no editor do n8n. URLs de teste funcionam apenas enquanto o n8n estiver aguardando o evento.
  3. Publique o workflow, altere o node para sua Production URL, copie-a e execute curl -i 'PASTE_PRODUCTION_URL_HERE' novamente. Confirme a execução na aba Executions do workflow. Requisições de webhook de produção precisam do workflow publicado e não mostram o payload na visualização de teste do editor.

Este é deliberadamente um smoke test simples e sem autenticação: nunca envie secrets para ele. Despublique ou exclua após o teste, ou configure autenticação do Webhook/restrições de IP antes de usar um endpoint público com dados reais. Consulte a documentação oficial de Webhook de teste/produção.

6. Faça backup antes de alterar versões fixadas

Salve um dump recuperável do PostgreSQL e o volume persistente de dados do n8n, .env/chave de criptografia e arquivos externos necessários em armazenamento fora deste servidor. Verifique uma restauração usando o guia de backup e recuperação antes de atualizar produção. Comandos de exemplo:

# Faça backup do banco, chave de criptografia e dados da instância,
# e dos arquivos antes de alterar as versões fixadas.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# Depois de proteger o backup fora deste VPS:
docker compose pull
docker compose up -d
docker compose ps

Altere a versão fixada N8N_VERSION somente depois de ler as release notes; as imagens do n8n e do runner devem avançar juntas. Não execute docker compose down -v durante manutenção de rotina porque isso exclui volumes de dados nomeados. Mudanças de versão principal do PostgreSQL exigem upgrade do banco ou plano de dump/restauração; trocar a imagem Postgres 18 por outra major tag não é migração automática.

Referências principais: guia Docker Compose do n8n, configuração de reverse proxy/webhook do n8n e notas oficiais de deploy do PostgreSQL. Nenhum benchmark de infraestrutura ou recurso pré-instalado específico de provedor é presumido.

CONFIGURAÇÃO

Defina secrets e URLs públicas de forma consciente

Chave de criptografia

Defina e preserve uma chave de criptografia forte do n8n antes de armazenar credenciais de produção. A mesma chave será necessária após a recuperação.

Credenciais do PostgreSQL

Use credenciais dedicadas do banco e mantenha senhas fora de controle de versão público.

Hostname público

Configure o hostname externo real e a origem HTTPS em vez de um endereço interno de contêiner.

URL do webhook

Defina N8N_WEBHOOK_URL como a URL base HTTPS acessível publicamente e defina N8N_PROXY_HOPS=1 quando houver um único reverse proxy confiável. WEBHOOK_URL é um alias obsoleto no n8n 2.35.0 e posteriores; evite copiá-lo de tutoriais antigos.

PERSISTÊNCIA

Mantenha n8n e PostgreSQL persistentes separadamente

Dados do n8n

Monte armazenamento persistente para o diretório de dados do n8n para que o estado crítico sobreviva à recriação do contêiner.

Dados do PostgreSQL

Mantenha o diretório do banco persistente de forma independente do contêiner PostgreSQL.

Permissões de arquivo

Faça com que os caminhos montados possam ser gravados pelo usuário previsto do contêiner sem tornar o armazenamento do host permissivo demais.

Arquivos de workflow

Mantenha persistentes os arquivos montados ou armazenamento de dados binários de que os workflows de produção dependem.

FALHAS COMUNS

Por que uma instalação Docker do n8n funciona localmente mas falha em produção

URL de webhook errada

Callbacks apontam para localhost, HTTP ou hostname interno em vez da origem HTTPS pública.

Persistência ausente

O estado da aplicação ou do banco desaparece quando um contêiner é recriado.

Chave de criptografia perdida

Credenciais salvas ficam inutilizáveis após reconstrução porque a nova instância usa outra chave.

Porta pública do banco

O PostgreSQL fica exposto desnecessariamente mesmo que apenas o n8n precise acessá-lo.

VERIFICAÇÃO PÓS-DEPLOY

Verifique o estado antes de conectar workflows reais

Verifique o estado dos contêineres

Execute docker compose ps e confirme que os serviços da aplicação e do banco estão rodando como esperado antes de considerar o deploy saudável.

Verifique o endpoint de saúde do n8n

No exemplo Compose acima, a porta 5678 não é publicada no host. Verifique o endpoint público com curl -fsS https://n8n.example.com/healthz depois de alterar o hostname e use docker compose ps além dos logs dos serviços se HTTPS ou o banco não estiverem prontos.

Fixe as versões da aplicação

Não trate uma atualização automática não revisada de imagem flutuante como estratégia de manutenção. Registre a versão do n8n em uso, leia as release notes e faça backup antes de alterá-la.

Não aumente versões principais do PostgreSQL diretamente

Alterar apenas a tag da versão principal do Postgres pode tornar um diretório de dados existente incompatível. Faça backup e siga o procedimento de upgrade do banco em vez de presumir que recriar o contêiner faz uma migração de versão principal.

FAQ

Instalando n8n com Docker: perguntas frequentes

O n8n precisa de PostgreSQL ao usar Docker?

Docker não exige PostgreSQL e pequenos deploys podem usar SQLite. Para um VPS orientado à produção, PostgreSQL oferece uma base mais robusta e permite escalar depois com modo fila.

Por que manter um volume persistente do n8n se o PostgreSQL armazena dados?

O diretório persistente do n8n pode conter estado e configuração importantes da instância. Preserve-o de acordo com o design do deploy em vez de presumir que o banco é o único recurso de recuperação.

Por que meu webhook mostra localhost?

O endereço interno do contêiner é diferente da origem pública. Configure hostname externo, protocolo e URL do webhook e garanta que o reverse proxy encaminhe os headers necessários.

A porta 5678 deve ser pública?

Em um deploy normal de produção atrás de reverse proxy, exponha HTTPS no proxy e mantenha a porta da aplicação n8n interna, salvo motivo operacional específico.

Preciso de Redis?

Não em um deploy Docker padrão com uma única instância. Redis passa a ser relevante quando você migra deliberadamente para modo fila e workers.

Task runners externos do n8n são a mesma coisa que workers de modo fila?

Não. Task runners externos executam código de tarefas compatível separadamente do processo main do n8n e usam um token de autenticação compartilhado. O modo fila com Redis distribui execuções de workflows e tem seus próprios requisitos de infraestrutura. Este exemplo mostra um task runner externo, não o modo fila com Redis. Faça a versão da imagem do runner corresponder à versão do n8n.
