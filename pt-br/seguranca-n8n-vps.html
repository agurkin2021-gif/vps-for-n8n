SEGURANÇA EM PRODUÇÃO

Proteger n8n em um VPS

Para proteger n8n em um VPS, mantenha n8n (5678), PostgreSQL (5432) e o Redis opcional (6379) fora da Internet pública; use reverse proxy HTTPS, chaves SSH e MFA, preserve a chave de criptografia, autentique webhooks, limite recursos de risco dos workflows e audite a instância implantada. Proteja o editor separadamente das rotas públicas de webhook. HTTPS sozinho não protege os serviços conectados.

LISTA RÁPIDA

Base mínima de segurança antes da exposição pública

Comece pelas portas acessíveis, HTTPS, acesso administrativo verificado, MFA e proteção das credenciais salvas. Autentique cada webhook recebido antes que ele possa acionar operações sensíveis. Depois de alterar controles de acesso, verifique se os editores autorizados e as integrações externas continuam funcionando e execute a auditoria de segurança do n8n.

Somente HTTPS

Coloque o n8n atrás de um reverse proxy TLS configurado corretamente e use de forma consistente a URL HTTPS pública para editor e webhooks.

Mínimo de portas abertas

Exponha apenas as portas necessárias para o tráfego público. Mantenha PostgreSQL, Redis e portas internas da aplicação fora da Internet pública.

Reforce o SSH

Administre com chaves, restrinja quem pode fazer login e mantenha o sistema operacional atualizado.

Proteja as credenciais

Mantenha a chave de criptografia do n8n estável e secreta. Trate arquivos de ambiente, acesso ao banco e cópias de backup como ativos sensíveis.

BORDA DA REDE

Reverse proxy, HTTPS e headers confiáveis

Terminação TLS

Use um reverse proxy como Nginx, Caddy ou Traefik para terminar HTTPS. Redirecione HTTP simples e evite expor diretamente a porta da aplicação n8n quando o proxy for o ponto de entrada previsto.

Configuração do proxy

Quando o n8n roda atrás de reverse proxy, configure corretamente a quantidade de saltos de proxy e encaminhe os headers de que o n8n precisa para reconstruir a requisição original do cliente.

Cookies seguros

Sirva o editor por HTTPS para manter seguros os cookies de autenticação. Não contorne uma configuração TLS quebrada enfraquecendo a segurança dos cookies.

URL do webhook

Defina a URL pública do webhook como o hostname HTTPS acessível externamente para que endpoints gerados não apontem para um contêiner interno ou endereço HTTP.

Mantenha o editor privado sem quebrar os webhooks. Restrinja o acesso administrativo usando VPN, política de IPs confiáveis ou proxy autenticado quando for prático. Receptores públicos de webhooks e rotas de callback OAuth podem precisar continuar acessíveis; teste tanto o login de um editor confiável quanto um callback externo real antes de aplicar uma regra de proxy. Encaminhe headers de endereço do cliente apenas a partir de proxies confiáveis, não de headers arbitrários da requisição.

Autentique quem chama os webhooks: no node Webhook escolha autenticação Basic, Header ou JWT em vez de None quando o remetente suportar. Use a opção IP(s) Allowlist quando apropriado e verifique assinaturas do provedor quando a integração suportar requisições assinadas. Uma URL difícil de adivinhar não é autenticação suficiente. Aplique rate limits no proxy quando adequado e confirme que picos válidos não sejam bloqueados. Opções oficiais de autenticação do Webhook.

HARDENING DO VPS

Reduza a superfície de ataque do servidor

Firewall

Negue por padrão tráfego de entrada não solicitado e permita apenas serviços que realmente precisam estar acessíveis. Portas de banco e Redis normalmente devem ficar em redes privadas/locais.

SSH

Prefira chaves SSH a senhas, desative caminhos de login desnecessários e limite o acesso administrativo. Acesso equivalente a root deve ser rigidamente controlado.

Atualizações do sistema

Mantenha o host Linux e o runtime de contêineres atualizados. Hardening da aplicação não compensa um sistema operacional exposto ou obsoleto.

Exposição de contêineres

Publique apenas as portas que precisam de acesso pelo host. Serviços internos devem se comunicar por redes Docker privadas em vez de interfaces públicas.

Inspecione antes de alterar firewall ou SSH: verifique portas em escuta com sudo ss -lntp, portas publicadas pelo Docker com docker compose ps no diretório do projeto e a política do firewall do host com sudo ufw status verbose se UFW for usado. Verifique a porta SSH real e um login bem-sucedido por chave em uma sessão separada antes de desativar acesso por senha. Portas publicadas pelo Docker podem contornar regras UFW; o status do firewall sozinho não prova que a porta 5678 é privada. Verifique a acessibilidade externa real. Limitação Docker/UFW.

Verifique as atualizações automáticas de segurança do Ubuntu em vez de presumir que funcionam: inspecione apt-config dump APT::Periodic::Unattended-Upgrade e o log /var/log/unattended-upgrades/unattended-upgrades.log. Se atualizações de segurança unattended estiverem desativadas, sudo dpkg-reconfigure unattended-upgrades oferece uma caixa de configuração compatível. Revise o comportamento de reinicialização do sistema e dos serviços antes de ativar em um VPS em produção. Atualizações APT do Ubuntu não atualizam automaticamente a imagem Docker do n8n nem todos os repositórios de software de terceiros. Documentação do Ubuntu sobre atualizações automáticas.

Monitoramento opcional de brute force em SSH: Fail2Ban pode detectar tentativas repetidas e malsucedidas de login SSH. Se estiver instalado e configurado para SSH, verifique a jail com sudo fail2ban-client status sshd e confirme que ele lê o log ou journal real de autenticação SSH e corresponde à porta configurada. Isso complementa chaves SSH e restrições de rede; não as substitui. Não copie uma porta SSH fixa nem uma regra de ban sem verificar primeiro o acesso existente. Orientação do Ubuntu para hardening de SSH.

BANCO DE DADOS & REDIS

Mantenha os serviços de backend privados

Em uma configuração típica do Docker Compose, PostgreSQL e Redis de modo fila devem ser acessíveis pelos contêineres relevantes por rede privada, não por portas publicadas no host. Verifique com docker compose ps que 5432 e 6379 não estão publicadas publicamente; revise separadamente a exposição do firewall do VPS/cloud. Políticas de rede não substituem credenciais de banco com princípio de menor privilégio.

PostgreSQLVincule-o a uma interface privada ou rede de contêineres, salvo quando acesso remoto for explicitamente necessário e protegido de forma independente.
RedisRedis de modo fila é infraestrutura, não um endpoint público. Restrinja o acesso de rede aos componentes do n8n que precisam dele.
CredenciaisUse credenciais dedicadas do banco apenas com as permissões necessárias à aplicação e proteja-as fora do controle de versão.
TransporteQuando o tráfego do banco atravessar redes não confiáveis, use transporte criptografado apropriado em vez de depender da criptografia de credenciais no nível da aplicação.

SECRETS DO N8N

Proteja a chave de criptografia e o limite das credenciais

Chave de criptografia

O n8n criptografa credenciais armazenadas usando sua chave de criptografia. Preserve a mesma chave entre reinicializações e workers e proteja-a separadamente do conteúdo normal da aplicação.

Secrets de ambiente

Não faça commit de senhas, tokens ou da chave de criptografia em repositório público. Restrinja o acesso a arquivos de ambiente e secrets do deploy.

Acesso de usuários

Conceda acesso ao editor apenas a usuários confiáveis. Workflows podem se conectar a sistemas sensíveis, processar secrets ou executar nodes poderosos.

Escopo das credenciais

Use contas de serviço e tokens de API com escopo restrito sempre que possível. Um workflow comprometido não deve herdar automaticamente acesso amplo a sistemas não relacionados.

Configuração do n8n a revisar: N8N_BLOCK_ENV_ACCESS_IN_NODE=true impede que o node Code e expressões acessem valores do ambiente; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true solicita permissões apenas do owner no arquivo de configurações. Mantenha N8N_ENCRYPTION_KEY persistente e com backup seguro: o n8n pode criar uma chave aleatória na primeira inicialização, mas perdê-la pode tornar credenciais criptografadas existentes inutilizáveis. Não substitua uma chave de criptografia de produção sem cuidado; use um procedimento oficial de rotação. Bloquear o acesso ao ambiente pode quebrar integrações existentes, então teste antes de mudanças em produção. Definições das variáveis de segurança do n8n.

RISCO DOS WORKFLOWS

Nodes podem ampliar o limite de segurança

Self-hosting dá bastante poder aos workflows. Execução de código, acesso ao shell, requisições HTTP arbitrárias e community nodes de terceiros podem aumentar o risco. Desative recursos desnecessários e revise workflows importados de fontes não confiáveis antes de executá-los.

Use exatamente os controles suportados: configure NODES_EXCLUDE com um array JSON de nodes a desativar, como n8n-nodes-base.executeCommand and n8n-nodes-base.readWriteFile, se não forem usados. Alguns nodes de alto risco já são bloqueados por padrão em versões mais novas; revise a lista real antes de alterá-la. Exclusões oficiais de nodes.

A partir do n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true ativa verificações para requisições HTTP de saída destinadas a faixas internas, loopback e endereços de metadata. Workflows legítimos com APIs internas podem parar de funcionar; se necessário, adicione à allowlist apenas destinos específicos que você controla. Mantenha segmentação de rede como defesa principal. Para isolamento do node Code, revise task runners externos. Proteção SSRF · Isolamento de task runner.

Community nodesInstale apenas pacotes em que confia; eles executam dentro do ambiente do n8n.
Nodes de riscoExclua nodes que o deploy não precisa quando suas capacidades ultrapassarem o limite pretendido do workflow.
SSRFUse a proteção SSRF do n8n e controles de rede onde workflows não devem conseguir acessar endpoints internos ou de metadata.
Importações de workflowsRevise workflows importados, credenciais, expressões e etapas executáveis antes da ativação.

AUDITORIA & ATUALIZAÇÕES

Segurança é um processo operacional

Execute a auditoria de segurança do n8n

O comando oficial da CLI é n8n audit. Se seu serviço Docker Compose se chama n8n, execute docker compose exec -T n8n n8n audit no diretório do deploy. Revise as cinco categorias: credenciais não usadas, padrões arriscados de consultas SQL, acesso ao sistema de arquivos, nodes de risco/community e riscos da instância, incluindo webhooks desprotegidos e versões desatualizadas. Corrija os achados relevantes e execute novamente. Isso não é um teste de penetração. Guia oficial de auditoria.

Atualize de forma consciente

Mantenha o n8n atualizado o suficiente para receber correções de segurança. Revise release notes e teste upgrades importantes em vez de deixar uma instância exposta à Internet permanentemente desatualizada.

Monitore a autenticação

Observe padrões inesperados de acesso, mudanças em workflows e falhas. Restrinja ainda mais a interface do editor quando seu modelo operacional não exigir ampla acessibilidade pública.

Prepare rollback e recuperação

Faça backups recuperáveis antes de upgrades importantes. O escopo detalhado de backup e restauração pertence ao guia separado de recuperação.

Minimize histórico sensível de execuções: execuções bem-sucedidas podem persistir dados de clientes e tokens. Quando apropriado, defina EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, mantenha EXECUTIONS_DATA_PRUNE=true, e escolha um EXECUTIONS_DATA_MAX_AGE em horas, como 168 (sete dias). São exemplos configuráveis, não regras legais de retenção. Menos histórico significa menos dados para depuração e análise forense; execuções em andamento, aguardando ou anotadas podem não ser podadas da mesma forma. Retenção oficial de execuções.

Suspeita de comprometimento: restrinja acesso malicioso sem destruir evidências, inspecione atividade do proxy, host e n8n e workflows alterados, revogue ou rotacione credenciais externas possivelmente expostas, corrija a causa e, quando necessário, restaure apenas a partir de backups recuperáveis testados. Revise URLs de webhook afetadas, contas do editor e serviços conectados; não presuma que HTTPS, snapshots ou a compra de um VPS forneçam serviços de resposta a incidentes.

CONTROLES DE CONTA & PLATAFORMA

Proteja o editor e o VPS

Exija proteção de login mais forte

Ative autenticação de dois fatores para contas do editor e imponha MFA pelas políticas de segurança do n8n quando sua edição suportar aplicação centralizada de políticas.

Limite quem pode editar workflows

Acesso ao editor é acesso privilegiado: workflows podem ler credenciais, chamar sistemas internos e executar nodes poderosos. Mantenha o acesso dos usuários restrito e remova contas que não precisam mais dele.

Desative recursos que não usa

Reduza a superfície de ataque da aplicação desativando a API pública quando ela for desnecessária e bloqueando nodes ou recursos de alto risco que seu modelo operacional não precisa.

Use controles SSRF e de secrets de forma consciente

Para workflows capazes de fazer requisições HTTP arbitrárias, avalie a proteção SSRF do n8n e mantenha secrets fora do código dos workflows, repositórios públicos e arquivos de ambiente amplamente legíveis.

Restrinja endpoints de gerenciamento não usados: N8N_PUBLIC_API_DISABLED=true desativa a API REST pública do n8n, e N8N_PUBLIC_API_SWAGGERUI_DISABLED=true desativa separadamente o API playground. Faça isso somente quando suas integrações não exigirem esses recursos. Desativar a REST API não autentica URLs de webhook dos workflows. Use MFA para usuários do editor e políticas centralizadas apenas quando sua edição do n8n as suportar.

FAQ

Segurança do n8n em VPS: perguntas frequentes

A porta do n8n deve ser exposta diretamente?

Quando um reverse proxy for o ponto de entrada público, exponha o proxy e mantenha a porta da aplicação atrás dele em vez de publicar serviços desnecessários amplamente.

PostgreSQL ou Redis devem ser públicos?

Normalmente não. Devem ser acessíveis apenas pelos sistemas que precisam deles. Exposição pública aumenta a superfície de ataque sem ajudar o funcionamento normal do n8n.

Por que a chave de criptografia do n8n é importante?

Ela protege as credenciais armazenadas pelo n8n e deve permanecer consistente em todo o deploy. Perdê-la pode impedir que dados recuperados produzam credenciais criptografadas utilizáveis.

Community nodes são seguros?

Eles ampliam o n8n com código de terceiros e devem ser tratados como dependências de software com riscos próprios de cadeia de suprimentos e privilégios. Instale apenas o que você precisa e em que confia.

HTTPS torna uma instância n8n self-hosted segura?

Não. HTTPS protege o transporte. Segurança em produção também exige hardening do host, controle de acesso, serviços de backend privados, proteção de secrets, recursos seguros de workflow, monitoramento e atualizações.

O editor do n8n pode ser privado enquanto webhooks de produção continuam funcionando?

Sim. Um reverse proxy confiável ou VPN pode restringir acesso de editor/admin separadamente das rotas públicas de webhooks de produção e callbacks OAuth. Teste login confiável e entrega externa de webhooks após cada alteração de regra para evitar bloquear integrações acidentalmente.

Como autenticar webhooks recebidos pelo n8n?

Configure autenticação Basic, Header ou JWT no node Webhook quando o remetente suportar. Você também pode usar IP(s) Allowlist e verificar assinaturas do provedor quando disponíveis. Não dependa apenas de um caminho que pareça secreto e valide as requisições antes que acionem ações sensíveis de API.
