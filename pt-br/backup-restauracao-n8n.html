BACKUP & RECUPERAÇÃO

Backup e restauração do n8n

Para fazer backup e restaurar um n8n self-hosted, proteja o banco SQLite ou um dump consistente do PostgreSQL, a pasta persistente .n8n e a chave de criptografia original, a configuração do deploy e todas as dependências externas de dados binários ou arquivos montados. Mantenha uma cópia criptografada fora do VPS e teste a recuperação em uma instância separada. Use exportações via CLI de workflows e credenciais para recuperação seletiva; exportações JSON sozinhas não são um backup completo do servidor.

LISTA RÁPIDA

O que um backup do n8n deve proteger

Banco de dados

Faça backup do banco PostgreSQL ou do arquivo SQLite usado pela instância. O banco contém o estado essencial do n8n, como workflows, credenciais e dados de execução.

Chave de criptografia

Preserve exatamente a mesma chave de criptografia do n8n de forma separada e segura. Credenciais criptografadas restauradas dependem da mesma chave.

Arquivos persistentes

Inclua o diretório persistente de dados do n8n e todos os arquivos montados, armazenamento de dados binários ou recursos de workflow dos quais seu deploy depende.

Configuração do deploy

Guarde os arquivos de Compose/configuração e a configuração não secreta necessária para reconstruir o stack. Proteja secrets com controles de acesso adequados.

DOIS NÍVEIS DE BACKUP

Exportação lógica vs recuperação completa de desastre

Exportação de workflows & credenciais

As exportações via CLI do n8n são úteis para migração, cópias versionadas de workflows e restauração seletiva. As credenciais podem ser exportadas criptografadas e importadas depois com a chave correspondente. Para recuperar apenas um workflow, use o menu de três pontos do editor para baixar seu JSON e depois Import from File em um novo workflow de revisão ou instância isolada. Verifique credenciais, IDs de workflow e parâmetros dos nodes antes de substituir um workflow ativo: restaurar o JSON do workflow não restaura o servidor inteiro.

Exportação de entidades

A CLI pode exportar entidades de banco para mover dados entre tipos de banco compatíveis. As tabelas de histórico de execuções são opcionais porque podem ser muito grandes.

Recuperação completa da instância

Para um cenário de servidor perdido, proteja o banco real, a chave de criptografia, os dados persistentes e as dependências do deploy. Não suponha que uma exportação JSON de workflow reconstrua toda a instância.

Snapshot do provedor

Um snapshot do VPS é útil como camada adicional de recuperação, mas não deve ser a única cópia nem substituir um backup de aplicação/banco verificado de forma independente.

BANCO DE DADOS

Faça backup consistente do banco de dados

PostgreSQL

Use um método consistente de backup do PostgreSQL e armazene o resultado fora do VPS. Uma cópia do banco no mesmo disco que falhou não é recuperação de desastre.

SQLite

Se o deploy usa SQLite, proteja o arquivo de banco do diretório persistente de dados do n8n. Evite copiar o banco em um estado inseguro enquanto ele está sendo alterado ativamente.

Histórico de execuções

Decida se o histórico de execuções faz parte do objetivo de recuperação. Ele pode aumentar muito o tamanho dos backups, então retenção e requisitos de compliance devem orientar a escolha.

Versão do banco

Registre o engine e a versão do banco usados no deploy de origem para preparar um ambiente de recuperação compatível.

PostgreSQL em um VPS com Docker Compose. Se o serviço PostgreSQL se chama postgres e tanto o banco quanto o usuário são n8n, o comando a seguir cria no host um dump consistente do PostgreSQL em formato custom. Confira seu arquivo Compose real antes de executar e ajuste credenciais do banco e nomes dos serviços. pg_dump pode produzir um snapshot logicamente consistente enquanto o PostgreSQL está em execução; ele não faz backup da pasta separada .n8n do usuário nem de dados binários externos.

# No projeto Docker Compose; adapte nomes do serviço, banco e usuário
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Verifique se o arquivo tem uma lista de objetos legível
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

A verificação da lista do arquivo detecta problemas óbvios de formato, mas não prova que os dados podem ser restaurados. Guarde uma cópia criptografada fora do servidor e ensaie a restauração. Use a documentação oficial do PostgreSQL pg_dump para opções específicas do banco.

SQLite no Docker. No deploy padrão com SQLite, database.sqlite e a configuração gerada da chave de criptografia ficam dentro da pasta persistente .n8n (normalmente montada em /home/node/.n8n). Nunca considere uma cópia simples em tempo real do SQLite como consistente. Pare o n8n e outros processos que escrevem no banco antes de copiar a pasta ou use o mecanismo online de backup compatível do SQLite quando a interrupção for impossível:

# Somente para SQLite e a montagem padrão /home/node/.n8n
# Pare o n8n (e qualquer outro processo de escrita) antes de copiar um banco SQLite
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Esses comandos são exemplos para o serviço e caminho mostrados, não um layout universal de volumes. A pasta copiada inicialmente ainda está no mesmo VPS; transfira e proteja-a fora do servidor. Quando houver workers de fila ou outros processos de escrita, pare-os também e siga o design real do deploy. A orientação atual do n8n sobre backup completo documenta o requisito de consistência do SQLite.

Restaurando a pasta SQLite padrão em um destino limpo: primeiro pare o serviço n8n e todos os processos que escrevem no banco. Quando existir um contêiner compatível do serviço n8n e seu volume de destino, copie o conteúdo salvo de .n8n conteúdo de volta para o mesmo diretório persistente. Isso sobrescreve arquivos de destino, portanto não execute em uma instância com dados que precisa manter:

# Execute somente na instância LIMPA destinada à recuperação
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# ANTES do próximo comando, verifique proprietário e permissões para o usuário do contêiner n8n
# Inicie somente depois que os arquivos restaurados puderem ser lidos/gravados pelo n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

O Docker pode copiar para contêineres parados, mas a propriedade dos arquivos no destino pode ser diferente da original; antes de iniciar, garanta que a configuração restaurada e o arquivo do banco possam ser lidos e gravados pelo processo n8n. Se seu Compose real usa outro caminho ou bind mount, adapte a cópia. Referência de cópia do Docker Compose. Restaurar apenas a pasta do n8n não basta para deploys que usam um banco PostgreSQL separado.

SECRET CRÍTICO

A chave de criptografia faz parte da recuperação

O n8n criptografa credenciais armazenadas com uma chave de criptografia da instância. Um banco ou exportação de credenciais criptografadas sem a chave correspondente pode deixar os workflows restaurados incapazes de usar as credenciais salvas.

Se você definiu N8N_ENCRYPTION_KEY, restaure exatamente esse secret. Caso contrário, a chave gerada fica no arquivo persistente .n8n/config: proteja essa configuração ao fazer backup ou reconstruir. Guarde chaves de recuperação com segurança fora do VPS. No modo fila, todos os processos main e worker devem usar a mesma chave.

FaçaMantenha uma cópia protegida da chave exata usada em produção.
FaçaVerifique se o ambiente de recuperação usa essa chave antes de testar credenciais.
Não façaNão dependa de uma chave recém-gerada após reconstruir o servidor.
Não façaNão faça commit da chave em um repositório público nem a guarde ao lado de um backup desprotegido.

ARQUIVOS & DADOS BINÁRIOS

O backup do banco pode não cobrir todas as dependências dos workflows

Dados persistentes de .n8n

Localize e preserve a pasta real de usuário .n8n, não apenas a imagem do contêiner. Em um deploy Docker típico ela é montada em /home/node/.n8n; fora do Docker, o padrão é ~/.n8n. Se N8N_USER_FOLDER estiver configurado, o n8n cria .n8n dentro do diretório pai informado. Inclua sua chave de configuração e quaisquer dados locais SQLite, binários ou de execução em sistema de arquivos usados pela instalação.

Arquivos de workflow montados

Se workflows leem ou gravam diretórios montados do host, faça backup desses diretórios separadamente. Restaurar o n8n sem eles pode deixar workflows válidos quebrados.

Dados binários

Identifique o modo de armazenamento e restaure cada dependência externa. Dados binários ou de execução baseados em sistema de arquivos podem ficar em .n8n ou em um diretório personalizado; S3/Azure Blob ou outro armazenamento externo configurado precisa de sua própria cópia recuperável e configurações de acesso. Um dump do banco sozinho não substitui esses arquivos.

Community nodes

Registre pacotes community e versões e faça backup de diretórios adicionais de nodes personalizados configurados por N8N_CUSTOM_EXTENSIONS. Esses diretórios podem ficar fora de .n8n; restaurar apenas o banco e a pasta do usuário ainda pode deixar workflows com nodes personalizados inutilizáveis.

ESTRATÉGIA FORA DO SERVIDOR

Um backup no mesmo VPS é apenas uma cópia local

Cópia localÚtil para rollback rápido, mas vulnerável à perda do servidor, falha de disco e erros destrutivos.
Cópia fora do servidorMantenha pelo menos um backup em armazenamento independente do VPS de produção.
Cópias versionadasMantenha vários pontos de recuperação para que corrupção ou uma mudança ruim não sobrescreva o único backup utilizável.
Controle de acessoBackups podem conter credenciais, lógica de workflows e dados empresariais sensíveis. Criptografe-os e restrinja o acesso adequadamente.
MonitoramentoGere alertas quando backups agendados falharem ou pararem de produzir novos pontos de recuperação.

Torne o cronograma mensurável. Registre o horário de cada backup bem-sucedido, conclusão da transferência, tamanho do arquivo, versão do banco de origem, local de recuperação da chave de criptografia e o último teste de restauração bem-sucedido. Gere alertas para arquivos ausentes, com falha ou inesperadamente vazios. Criptografe os arquivos de backup antes de enviá-los para fora do VPS e restrinja o acesso aos secrets de recuperação. Vários pontos de recuperação datados protegem contra descobrir corrupção apenas depois que a cópia mais nova sobrescreveu a última saudável.

Por exemplo, se você tolera no máximo seis horas de mudanças perdidas, um backup bem-sucedido a cada seis horas é apenas um ponto de partida, não uma garantia: tarefas com falha e replicação atrasada para fora do servidor podem aumentar a perda real. Defina retenção e frequência de restauração conforme seus próprios RPO/RTO e requisitos de dados, em vez de assumir uma política universal de 7 ou 30 dias.

ORDEM DE RESTAURAÇÃO

Recupere em uma sequência controlada

1 · PrepararPrepare servidor, banco de dados e ambiente de contêiner/runtime compatíveis.
2 · Restaurar secretsConfigure com segurança a chave de criptografia original do n8n e os secrets necessários do deploy.
3 · Restaurar bancoRecupere PostgreSQL ou SQLite e verifique se o n8n consegue se conectar aos dados esperados.
4 · Restaurar arquivosRecupere diretórios persistentes, dados binários e recursos de workflow montados.
5 · Iniciar n8nInicie a aplicação com hostname, banco e configuração de ambiente esperados.
6 · ValidarConfirme que usuários, workflows e credenciais carregam e depois execute workflows representativos e rotas de webhook.

Exemplo de recuperação de desastre com PostgreSQL: em um destino de restauração separado e limpo que já possua o role correto e um banco n8n vazio, inicie somente o PostgreSQL. Espere até que esteja saudável antes de importar: docker compose up -d sozinho pode retornar enquanto o PostgreSQL ainda está inicializando, portanto um pg_restore seguinte pode falhar. O exemplo usa --wait em uma instalação moderna do Compose e verifica separadamente pg_isready. Configure um healthcheck adequado do PostgreSQL para esperar de forma confiável ou confirme explicitamente a prontidão antes de continuar. Não aponte esse comando para um banco de produção com dados nem inicie o n8n antes que o banco e a chave/dados correspondentes .n8n sejam restaurados.

# RESTAURE SOMENTE EM UM BANCO DE DESTINO NOVO E VAZIO
# Adapte nomes do serviço Postgres Compose, banco e usuário
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

O destino deve ter versão compatível do PostgreSQL, privilégios de role, extensões e a configuração original do n8n. Restaure .n8n no volume persistente ou bind mount correto usando seu mecanismo de backup, preservando propriedade e permissões. Restaure arquivos binários externos, extensões personalizadas, Compose e configuração de secrets; depois inicie o n8n em uma versão compatível e confira os logs. Restaurar apenas o banco não recupera a chave: um deploy com PostgreSQL mantém a chave em .n8n/config a menos que você tenha configurado explicitamente N8N_ENCRYPTION_KEY. TESTE DE RESTAURAÇÃO

Um backup só é comprovado quando a restauração funciona

Teste em um ambiente limpo

Um teste real deve provar que o backup consegue reconstruir a instância sem depender de arquivos não declarados deixados no servidor de produção.

Verifique as credenciais

Abrir um workflow não basta. Confirme que as credenciais criptografadas restauradas realmente são descriptografadas e autenticam com sucesso.

Execute workflows representativos

Teste workflows que dependem de webhooks, APIs externas, arquivos montados e community nodes em vez de validar apenas uma automação trivial.

Meça o tempo de recuperação

Registre quanto tempo a restauração leva e quais etapas manuais permanecem. Isso transforma um backup presumido em um procedimento operacional de recuperação.

Teste de restauração verificado: SQLite e PostgreSQL

Ambiente de teste: n8n 2.42.5 em contêineres Docker isolados em um runner descartável do GitHub Actions, usando um workflow sintético de dois nodes. Essas verificações foram executadas em 8 de outubro de 2026, não em um servidor n8n de cliente ou produção.

SQLite: PASSUm workflow de teste foi importado e exportado, todos os processos de escrita foram parados e a pasta persistente baseada em SQLite .n8n junto com sua chave de criptografia gerada foi arquivada, restaurada em um volume limpo, o n8n foi iniciado e depois o workflow recuperado foi reexportado e executado.
PostgreSQL: PASSO mesmo workflow de teste foi importado, foi criado e inspecionado um dump em formato custom pg_dump, restaurado usando pg_restore em um novo banco PostgreSQL vazio, restaurada a pasta separada .n8n e depois o workflow recuperado foi reexportado e executado.
O que PASS comprovaOs caminhos de backup testados preservaram esse workflow, seus dois nodes e conexões e permitiram a execução após a recuperação. São testes funcionais reproduzíveis, não benchmarks de carga.
O que não foi testadoNão foram testadas a descriptografia e autenticação de credenciais reais, webhooks de produção, workers de modo fila e Redis, armazenamento binário S3/Azure, nodes personalizados, acesso de usuários/projetos ou a recuperação de uma instância de produção em execução. Faça um teste separado para cada dependência realmente usada.

Como reproduzir: use uma instalação descartável do n8n, crie um workflow inofensivo de dois nodes, faça o backup aplicável do banco mais pasta persistente, restaure em um volume ou banco limpo e depois verifique os nodes, conexões e execução real do workflow restaurado. No sistema de produção, verifique também credenciais criptografadas, webhooks e arquivos externos antes de considerar a recuperação de desastre comprovada.

Lista de aceitação do teste de restauração: use um domínio/ambiente isolado; verifique se usuários e workflows estão presentes, se uma credencial criptografada existente autentica sem ser redigitada, se um webhook de produção chama o workflow restaurado correto, se arquivos montados e anexos binários continuam legíveis e se as integrações com community nodes necessários carregam. Confirme a idade do backup, downtime medido e acessibilidade fora do servidor. Se alguma verificação essencial falhar, marque esse ponto de recuperação como não verificado em vez de informar o backup como completo.

LIMITES DOS BACKUPS VIA CLI

Saiba exatamente o que as exportações de workflows e credenciais não restauram

Exportações via CLI não são backup completo da instância

As exportações de backup de workflows e credenciais não incluem usuários e roles, histórico e logs de execução, variáveis nem configurações da instância, como a chave de criptografia.

Restauração em instância nova precisa de owner

Em uma instância limpa, conclua a configuração do owner antes de importar credenciais. Restaurações multiusuário ou de projetos também podem precisar da atribuição correta de usuário ou projeto.

IDs importados podem sobrescrever itens existentes

As exportações de workflows e credenciais preservam os IDs originais. Importar em uma instância que já contenha os mesmos IDs pode substituir os itens existentes.

Publique workflows importados de forma consciente

Importações via CLI normalmente deixam workflows inativos. No n8n 2.x, verifique o estado de publicação de cada workflow importado e publique apenas os que pretende executar; a Server CLI self-hosted também suporta n8n publish:workflow --id=YOUR_WORKFLOW_ID. Quando o n8n está em execução, mudanças de publish/unpublish feitas pela Server CLI só entram em vigor após reiniciar o n8n. Reinicie antes de verificar triggers agendados e webhooks de produção ou mudar o tráfego.

Exemplo de exportação em massa com Docker Compose: se o seu serviço n8n se chama n8nvocê pode executar os backups oficiais via CLI abaixo. O caminho de saída fica deliberadamente dentro do diretório persistente montado .n8n porque diretórios arbitrários dentro de um contêiner podem desaparecer quando ele é recriado. Confirme que o diretório pode ser gravado pelo usuário do contêiner n8n. Mantenha JSON de workflows e credenciais em diretórios separados—o n8n documenta um problema de importação quando ambos os tipos compartilham o mesmo diretório.

n8n 2.x: backup de rascunho vs publicado: uma exportação normal de --backup workflow captura os rascunhos atuais; eles podem ser diferentes das versões publicadas em produção. Para preservar a versão realmente publicada de um workflow específico, exporte-a separadamente usando docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, depois de garantir que a pasta de saída existe e pode ser gravada. A CLI também pode exportar uma versão histórica usando --version=VERSION_ID. Mantenha essas capturas fora do servidor junto com o backup completo; não suponha que o JSON do rascunho registre o estado publicado em produção.

# Execute a partir do projeto Docker Compose; o serviço n8n deve existir
# Mantenha backups de workflows e credenciais em pastas DIFERENTES
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copie os diretórios exportados PARA FORA do contêiner, para o host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

O diretório copiado ~/n8n-recovery/cli continua no VPS até você movê-lo para um local de backup seguro e independente. A exportação de credenciais é criptografada por padrão e precisa da chave correspondente ao importar. Evite usar --decrypted exceto em uma migração estritamente controlada: ele grava secrets em texto simples. Nunca faça commit de exportações com lógica sensível de workflows ou credenciais em um repositório público do GitHub. Alguns templates de terceiros para backup de credenciais no GitHub exportam deliberadamente secrets descriptografados; um repositório privado é uma restrição de acesso, não criptografia. Inspecione as configurações reais de exportação e permissões de armazenamento de cada template, criptografe secrets antes da transferência para fora do servidor e faça rotação de qualquer credencial exposta por upload não intencional em texto simples.

Exemplo de importação em massa: em um destino limpo, conclua a configuração do owner, forneça a chave de criptografia original e garanta que os arquivos de backup salvos estejam disponíveis nesse VPS de recuperação. O comando a seguir cria a pasta de destino e copia as subpastas workflows/ e credentials/ do host para o contêiner n8n; adapte os caminhos se o layout de volumes Docker for diferente:

# Execute somente na instância LIMPA destinada à recuperação
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Verifique propriedade e acesso aos arquivos para o usuário do contêiner n8n. Não importe sobre uma instância de produção com dados sem um rollback verificado: IDs de workflows e credenciais podem sobrescrever entradas existentes. Depois execute:

# Após configurar o owner da nova instância E fornecer a chave correta
# Copie o conteúdo salvo de cli/ de volta para .n8n/backups/ do serviço n8n de destino
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

IDs importados podem substituir workflows ou credenciais existentes; use uma instância de teste isolada para simulações e depois verifique credenciais e estados de ativação/publicação. No n8n 2.x, restaurar o JSON do rascunho não prova por si só que um workflow foi publicado e pode executar triggers agendados. Segurança da importação: em uma instância n8n sem multi-main, triggers cron que estavam ativos podem continuar rodando após importação via CLI até a instância reiniciar. Pare ou isole os triggers de produção e reinicie o n8n antes de ativar tarefas restauradas; confirme que não há execução duplicada. As exportações via CLI não não contêm usuários originais, logs de execução, variáveis da instância nem a chave de criptografia. --backup define --all --pretty --separate, não “instância completa”. Fontes: guia oficial atual de backup/restauração do n8n e referência de comandos da CLI do n8n.

Restauração em massa por templates do GitHub ou Google Drive: isso é uma alternativa apenas para JSON de workflows, não para o banco da instância, usuários, valores criptografados das credenciais ou chave de criptografia. Antes de executar um template baseado em API, verifique permissões da API do n8n e do armazenamento, a versão do backup selecionada e a instância de destino, se IDs correspondentes são atualizados e workflows apagados são recriados e como a publicação é tratada. Nem todos os templates recriam um ID ausente no destino; teste esse cenário isoladamente antes de confiar em restauração automática.

FAQ

Backup e restauração do n8n: perguntas frequentes

Exportar workflows é suficiente para fazer backup do n8n?

Não. Exportações de workflows são cópias lógicas úteis, mas a recuperação completa também pode exigir credenciais, a chave de criptografia correspondente, estado do banco, arquivos persistentes e armazenamento de dados binários.

Preciso da chave de criptografia do n8n se tenho o banco de dados?

Sim, se precisar que as credenciais criptografadas armazenadas nesse banco continuem utilizáveis. Preserve a chave original com segurança.

Devo fazer backup do PostgreSQL ou exportar workflows e credenciais?

Para recuperação de desastre, proteja o banco e a chave de criptografia. Exportações lógicas são valiosas como camada adicional de migração e recuperação seletiva, não como substituto de todas as partes da instância.

Um snapshot do VPS pode ser meu único backup?

É melhor tratá-lo como uma camada de recuperação. Mantenha um backup independente fora do servidor para que uma falha do provedor, conta, servidor ou snapshot não elimine todos os pontos de recuperação de uma vez.

Como sei se meu backup funciona?

Restaure em um ambiente de teste limpo, verifique se as credenciais são descriptografadas e execute workflows representativos. Uma tarefa de backup bem-sucedida, sozinha, não prova recuperabilidade.

Backups de workflows no GitHub ou Google Drive incluem secrets de credenciais salvas?

Backups JSON apenas de workflows não incluem os valores secretos gerenciados pelo armazenamento de credenciais do n8n nem a chave de criptografia da instância. Porém, o JSON exportado pode expor nomes e IDs de credenciais e secrets digitados diretamente em parâmetros de nodes, como headers de autenticação. Inspecione e proteja o JSON antes de fazer upload ou compartilhar. Para recuperação completa, faça backup do banco e da chave original ou use exportações criptografadas de credenciais via CLI com restauração testada. Um template do GitHub ou Google Drive apenas para workflows não é recuperação completa de desastre.

OBJETIVOS DE RECUPERAÇÃO

Defina RPO e RTO antes de um incidente

RPO é a perda máxima tolerável de mudanças recentes. Meça a partir do ponto de recuperação utilizável mais recente armazenado de forma independente; uma tarefa agendada a cada seis horas não estabelece RPO de seis horas se exportações ou transferências falharam. RTO é a indisponibilidade máxima tolerável. Meça em um teste limpo de restauração, incluindo recuperação de secrets, restauração de arquivos externos, nova verificação de credenciais e publicação dos workflows recuperados — não apenas iniciando um contêiner.

CHAVE DE RECUPERAÇÃO

Encontre a chave de criptografia original antes de reconstruir

Se a produção definiu N8N_ENCRYPTION_KEY, preserve exatamente esse secret de ambiente. Caso contrário, preserve a chave gerada no .n8n/config persistente original. Verifique qual fonte a instância recuperada realmente usa antes de importar credenciais criptografadas; uma chave nova não pode descriptografar credenciais do banco antigo.
