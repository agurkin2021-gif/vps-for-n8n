REQUISITOS DO SERVIDOR

Requisitos de VPS para n8n

Para definir os requisitos de VPS do n8n, comece pela sua carga de trabalho, não por um mínimo universal de hardware. Um VPS de 1 vCPU / 1 GB bem dimensionado pode executar pequenas automações sempre ativas, enquanto 2 vCPU / 4 GB RAM é uma classe inicial prática para n8n com PostgreSQL e HTTPS. Payloads grandes, execuções simultâneas e processamento local exigem mais folga; meça o uso real antes de escolher.

REQUISITOS RÁPIDOS

Mínimo, produção prática e cargas mais pesadas

Instância leve sempre ativa

1 vCPU · 1–2 GB RAM

Um VPS real de 1 GB pode executar workflows contínuos e leves do n8n com limites cuidadosos quando a folga de memória e disco é verificada. A classe de 2 GB deixa mais espaço para Docker, pequenos picos e outros serviços. Nenhum dos valores garante uma quantidade específica de workflows.

Produção pequena prática

2 vCPU · 4 GB RAM

Uma classe inicial equilibrada quando o n8n compartilha o VPS com PostgreSQL, Docker e reverse proxy. Deixe folga para execuções sobrepostas e manutenção.

Carga pesada ou intensiva em dados

4+ vCPU · 8 GB+ RAM

JSON grandes, arquivos binários, nodes Code, trabalho com navegador e muitas execuções sobrepostas podem justificar bem mais CPU e memória.

Armazenamento

SSD / NVMe com folga para crescimento

A capacidade depende do crescimento do PostgreSQL, retenção das execuções, dados binários, logs, camadas Docker e estratégia de backup, não apenas do n8n.

MÍNIMO VS CAPACIDADE PRÁTICA

O n8n tem um tamanho mínimo oficial de VPS?

Não para todas as cargas. Os exemplos oficiais de pré-requisitos do n8n descrevem um deploy OEM ilustrativo e alertam explicitamente que os requisitos variam conforme a carga. Essa documentação não garante universalmente que uma alocação específica de CPU, RAM ou disco suporte automações de produção.

O n8n observa que uma instância ociosa pode usar relativamente pouca memória, mas um node Code, um grande payload binário ou execuções simultâneas podem aumentar muito a demanda. Reserve recursos separadamente para o sistema operacional, Docker, PostgreSQL e ferramentas de backup/monitoramento.

Fontes técnicas: pré-requisitos ilustrativos do n8n e guia oficial de memória. As quatro linhas acima são pacotes reais de recursos disponíveis para compra, não requisitos oficiais prescritos pelo n8n.

RAM & CPU

O que realmente consome recursos do servidor

Execuções simultâneas

Vários workflows executados ao mesmo tempo podem importar mais que a quantidade total armazenada no n8n. Observe picos de memória e latência durante a sobreposição.

Tamanho do payload

Objetos JSON grandes, arquivos e dados binários aumentam a pressão sobre a memória. Algumas execuções intensivas em dados podem exigir mais RAM que muitas automações leves de API.

Nodes intensivos em CPU

Code, transformações e outras etapas intensivas em computação podem criar pressão contínua de CPU. Mais núcleos ajudam quando execuções reais disputam capacidade de processamento.

Serviços auxiliares

Sistema operacional, PostgreSQL, reverse proxy, monitoramento e Docker também precisam de recursos. Dimensione o stack completo, não apenas o processo do n8n.

MEÇA ANTES DE FAZER UPGRADE

Como saber se o n8n precisa de mais RAM, CPU ou disco

Execute o maior workflow esperado e um pico realista de sobreposição; depois inspecione o servidor e os logs de execução do n8n. A quantidade de workflows salvos no editor, sozinha, não é um benchmark útil de capacidade.

Memória / OOM

Verifique docker stats --no-stream e free -h. Se a memória se esgotar, primeiro reduza payloads JSON ou binários, processe grandes importações em lotes e evite etapas Code intensivas em memória. Um erro de heap do JavaScript não é necessariamente resolvido adicionando vCPUs.

CPU / concorrência

Meça se a CPU fica ocupada durante transformações ou se as tarefas apenas aguardam APIs externas. No modo normal, considere um limite suportado de concorrência de produção antes de escalar para workers. Aumentar CPU não acelera uma API externa limitada por rate limit.

Armazenamento / banco

Verifique df -h, o tamanho do banco e o histórico de execuções mantido. Observe o crescimento do disco e operações lentas no banco. Defina a retenção conscientemente antes de pagar por um disco maior; mantenha cópias de recuperação fora do servidor.

Use a orientação de concorrência do n8n e a explicação oficial sobre benchmarks. Qualquer quantidade anunciada de workflows simultâneos sem conhecer payloads e latência de API é apenas uma estimativa.

BANCO DE DADOS & ARMAZENAMENTO

SQLite, PostgreSQL e dados persistentes

SQLite

SQLite pode servir para pequenos deploys de uma única instância e testes. Conforme o uso em produção e a concorrência crescem, a escolha do banco vira uma restrição operacional, não apenas um detalhe de instalação.

PostgreSQL

Para um stack VPS orientado à produção, PostgreSQL oferece uma base mais robusta. Reserve RAM, CPU e disco para o próprio banco e monitore seu crescimento.

Dados persistentes de .n8n

Não trate o PostgreSQL como o único recurso persistente. Preserve o diretório de dados do n8n e proteja a chave de criptografia necessária para recuperar credenciais criptografadas.

Crescimento do disco

Histórico de execuções, dados binários, arquivos do banco e logs podem crescer com o tempo. Configurações de retenção e backups fora do servidor afetam diretamente a capacidade necessária.

CAPACIDADE DE DISCO

Estime o armazenamento do histórico de execuções do n8n antes de comprar

Comece com execuções salvas por dia × bytes médios armazenados por execução × dias de retenção. Por exemplo, 500 execuções salvas por dia × 200 KB cada × 14 dias = 1.4 GB de dados de execução de exemplo antes do overhead do banco. A suposição de 200 KB é ilustrativa, não um benchmark do n8n.

Reserve disco também para o sistema operacional, camadas de imagens Docker, índices do banco, arquivos binários, logs da aplicação, upgrades e arquivos temporários. Backups fora do servidor precisam de capacidade própria. Um disco de 10 GB pode funcionar para um stack enxuto, mas deixa muito menos espaço para arquivos mantidos que um disco de 40 ou 80 GB.

O n8n documenta pruning padrão de execuções por idade (336 horas / 14 dias) ou quantidade (10,000 execuções), com exceções. Confira suas configurações reais e o que é mantido antes de alterá-las. O SQLite pode reutilizar espaço liberado em vez de reduzir automaticamente o arquivo.

Fonte: n8n: gerenciamento de dados de execução e pruning. Os requisitos de disco dependem dos tamanhos observados dos payloads salvos, não apenas da quantidade de nodes.

REQUISITOS DO SISTEMA

Docker e overhead de produção

VPS Linux

Use uma distribuição Linux com manutenção e recursos suficientes para o sistema operacional e atualizações de segurança, além do stack da aplicação.

Docker & Compose

Deploy em contêineres simplifica repetibilidade, mas não elimina overhead de recursos. Mantenha dados do n8n e do banco persistentes fora de contêineres descartáveis.

HTTPS & reverse proxy

Webhooks públicos exigem hostname estável e HTTPS configurado corretamente. Inclua reverse proxy e camada TLS no design de produção.

Monitoramento & backups

Monitore RAM, CPU, disco e crescimento do banco. Mantenha backups recuperáveis fora do VPS e teste restauração em vez de presumir que um snapshot é suficiente.

CONCORRÊNCIA

Quando um VPS maior deixa de ser toda a solução

Escalabilidade vertical é adequada enquanto uma instância consegue lidar bem com a carga. Quando demanda paralela contínua cria contenção, avalie modo fila e workers. O modo fila introduz Redis, PostgreSQL e um ou mais processos worker; reserve RAM e CPU para todos os componentes, não apenas n8n. O n8n também documenta restrições ao armazenamento de dados binários em sistema de arquivos no modo fila, então valide um design de armazenamento compatível antes de mudar.

NÍVEL DE ENTRADA & I/O DE ARMAZENAMENTO

Como usar um VPS de entrada de 1 GB

1 GB RAM

É um nível real de VPS, não um produto apenas de teste. Pode servir para pequenas automações sempre ativas e trabalho de API principalmente sequencial quando memória, uso de disco e tarefas simultâneas permanecem dentro de limites medidos. Oferece pouca folga para PostgreSQL no mesmo servidor, payloads grandes ou execuções paralelas pesadas.

2 GB RAM

Use 2 GB como base mais segura para uma instância leve quando quiser mais espaço para o sistema operacional, Docker e pequenos picos sem migrar imediatamente para um stack de tamanho de produção.

SSD vs NVMe

SSD padrão é suficiente para automação leve. NVMe se torna mais útil quando PostgreSQL e histórico de execuções geram leituras e gravações frequentes ou quando a latência do disco aparece no desempenho medido dos workflows.

Meça antes de fazer upgrade

Use CPU, memória, crescimento do disco e duração das execuções na sobreposição máxima para decidir se o gargalo é computação, memória ou armazenamento, em vez de presumir que um VPS maior resolve toda lentidão.

FAQ

Requisitos de VPS do n8n: perguntas frequentes

Quanta RAM o n8n precisa?

Não existe um valor universal. A demanda de RAM muda conforme concorrência, tamanho do payload, comportamento das execuções e serviços auxiliares no VPS. Um servidor de 4 GB é uma classe inicial prática para pequena produção, não um requisito garantido para todas as cargas.

Quantos núcleos de CPU devo usar?

Cargas leves podem começar com pequena alocação de CPU. Adicione núcleos quando o monitoramento mostrar pressão contínua de CPU ou execuções mais lentas sob concorrência, em vez de dimensionar apenas pela quantidade de workflows.

O n8n exige PostgreSQL?

Pequenos deploys podem usar SQLite, mas PostgreSQL é a opção mais robusta para produção conforme os requisitos operacionais e a concorrência aumentam.

Quando Redis é necessário?

Redis está associado ao modo fila. Um deploy normal de uma única instância não precisa de Redis apenas porque roda em um VPS.

Quanto espaço em disco devo reservar?

A necessidade de disco depende do crescimento do PostgreSQL, histórico de execuções mantido, dados binários, logs, camadas dos contêineres e backups. Monitore o crescimento e deixe folga em vez de depender de um valor universal fixo.

Posso executar n8n continuamente em um VPS de 1 GB?

Sim, quando a carga real couber. Um VPS de 1 GB é um servidor real e pode suportar pequenas automações principalmente sequenciais, mas a folga de memória é limitada. Não presuma que PostgreSQL no mesmo servidor, tarefas intensivas em dados binários ou várias execuções grandes simultâneas caberão. Monitore o consumo e faça upgrade conforme a pressão de recursos observada.

2 GB ou 4 GB RAM é melhor para um VPS de produção com n8n?

Dois gigabytes dão mais espaço que uma instância enxuta de 1 GB, enquanto 4 GB é uma classe inicial prática para avaliar n8n junto com PostgreSQL e HTTPS. Não existe mínimo universal garantido para produção: complexidade da carga, sobreposição máxima, configuração dos contêineres e dados mantidos determinam a demanda real.

Workflows de IA do n8n exigem GPU?

Não quando o n8n apenas chama uma API externa de modelo: o provedor do modelo cuida da inferência, enquanto o VPS cuida de orquestração, payloads e concorrência. Executar modelos de inferência localmente é outra decisão de hardware e pode exigir muito mais RAM e recursos adequados de GPU.

O que causa erros de falta de memória no n8n?

Payloads JSON ou binários grandes, operações Code intensivas em memória e execuções sobrepostas são causas comuns. Confira logs de runtime e pico de uso de memória; depois reduza os dados mantidos em uma execução ou aloque mais RAM conforme o problema medido.
