BEZPEČNOSŤ V PRODUKCII

Zabezpečenie n8n na VPS

Ak chcete zabezpečiť n8n na VPS, nesprístupňujte porty n8n (5678), PostgreSQL (5432) ani voliteľného Redis (6379) verejnému internetu. Používajte reverzný proxy server s HTTPS, kľúče SSH a viacfaktorové overovanie (MFA), uchovajte šifrovací kľúč, overujte volania webhookov, obmedzte rizikové možnosti pracovných postupov a vykonajte audit nasadenej inštancie. Prístup k editoru chráňte oddelene od verejných trás webhookov. Samotné HTTPS nezabezpečí pripojené služby.

STRUČNÝ KONTROLNÝ ZOZNAM

Minimálne bezpečnostné opatrenia pred sprístupnením internetu

Začnite kontrolou dostupných portov, HTTPS, overeného prístupu správcu, MFA a ochrany uložených prístupových údajov. Každý prichádzajúci webhook autentifikujte skôr, než môže spustiť citlivú operáciu. Po zmene pravidiel prístupu overte, že oprávnení používatelia editora a externé integrácie stále fungujú, a potom spustite bezpečnostný audit n8n.

Iba HTTPS

Umiestnite n8n za správne nakonfigurovaný reverzný proxy server s TLS a používajte verejnú URL adresu HTTPS konzistentne pre editor aj webhooky.

Minimum otvorených portov

Sprístupnite iba porty potrebné na verejnú prevádzku. PostgreSQL, Redis a interné porty aplikácie ponechajte neprístupné z verejného internetu.

Zabezpečenie SSH

Na správu používajte kľúče SSH, obmedzte oprávnených používateľov a pravidelne aktualizujte operačný systém.

Ochrana prístupových údajov

Šifrovací kľúč n8n musí zostať nemenný a tajný. So súbormi prostredia, prístupom k databáze a zálohami zaobchádzajte ako s citlivými údajmi.

SIEŤOVÉ ROZHRANIE

Reverzný proxy server, HTTPS a dôveryhodné hlavičky

Ukončenie TLS

Na ukončenie spojení HTTPS používajte reverzný proxy server, napríklad Nginx, Caddy alebo Traefik. Presmerujte nešifrované HTTP a nesprístupňujte priamo port aplikácie n8n, ak je určeným vstupným bodom proxy server.

Konfigurácia proxy servera

Ak n8n beží za reverzným proxy serverom, správne nastavte počet proxy uzlov na ceste a preposielajte hlavičky, ktoré n8n potrebuje na zistenie pôvodnej požiadavky klienta.

Bezpečné súbory cookie

Editor sprístupňujte cez HTTPS, aby autentifikačné súbory cookie zostali zabezpečené. Nefunkčné TLS neobchádzajte oslabením zabezpečenia súborov cookie.

URL adresa webhookov

Nastavte verejnú URL adresu webhookov na názov hostiteľa dostupný zvonka cez HTTPS, aby vygenerované koncové body webhookov nesmerovali na interný kontajner ani na HTTP.

Chráňte editor bez narušenia webhookov. Ak je to možné, obmedzte prístup na správu pomocou VPN, pravidiel pre dôveryhodné IP adresy alebo autentifikovaného proxy servera. Verejné prijímače webhookov a spätné adresy OAuth môžu musieť zostať dostupné; pred vynútením pravidla proxy servera otestujte prihlásenie dôveryhodného používateľa editora aj skutočné externé spätné volanie. Hlavičky s adresou klienta prijímajte len od dôveryhodných proxy serverov, nie z ľubovoľných požiadaviek.

Overujte volajúcich webhookov: v uzle Webhook zvoľte namiesto None autentifikáciu Basic, Header alebo JWT, ak ju odosielateľ podporuje. Podľa potreby využite možnosť IP(s) Allowlist a pri integráciách s podpisovanými požiadavkami overujte podpisy poskytovateľa. Ťažko uhádnuteľná URL adresa nie je dostatočnou autentifikáciou. Podľa potreby nastavte na proxy serveri limity frekvencie požiadaviek a overte, že neblokujú legitímne krátkodobé špičky. Pozrite si oficiálne možnosti autentifikácie webhookov.

ZABEZPEČENIE VPS

Zmenšite plochu útoku na server

Firewall

Predvolene odmietajte nevyžiadanú prichádzajúcu prevádzku a povoľte len služby, ktoré musia byť dostupné. Porty databázy a Redis majú byť spravidla v súkromnej alebo lokálnej sieti.

SSH

Uprednostnite kľúče SSH pred heslami, vypnite nepotrebné spôsoby prihlasovania a obmedzte správcovský prístup. Prístup s oprávneniami root musí byť prísne kontrolovaný.

Aktualizácie OS

Aktualizujte linuxového hostiteľa aj prostredie kontajnerov. Zabezpečenie aplikácie nenahradí ochranu odkrytého alebo zastaraného operačného systému.

Vystavenie kontajnerov sieti

Publikujte iba porty, ku ktorým musí mať prístup hostiteľ. Interné služby majú komunikovať v súkromných sieťach Docker, nie cez verejné rozhrania.

Pred zmenou firewallu alebo nastavení SSH najprv skontrolujte stav: otvorené porty zobrazíte príkazom sudo ss -lntp, publikované porty Dockera príkazom docker compose ps z adresára projektu a pravidlá firewallu hostiteľa príkazom sudo ufw status verbose , ak používate UFW. Pred vypnutím prihlasovania heslom overte skutočný port SSH a úspešné prihlásenie kľúčom v samostatnej relácii. Porty publikované Dockerom môžu obísť pravidlá UFW; samotná stavová stránka firewallu nedokazuje, že port 5678 je súkromný. Skontrolujte skutočnú dostupnosť zvonka. Upozornenie na Docker/UFW.

Skontrolujte automatické bezpečnostné aktualizácie Ubuntu, nepredpokladajte, že fungujú: preskúmajte apt-config dump APT::Periodic::Unattended-Upgrade a protokol /var/log/unattended-upgrades/unattended-upgrades.log. Ak sú automatické bezpečnostné aktualizácie vypnuté, príkaz sudo dpkg-reconfigure unattended-upgrades otvorí podporovaný dialóg nastavenia. Pred jeho zapnutím na používanom VPS zvážte reštarty a opätovné spustenie služieb. Aktualizácie Ubuntu cez APT neaktualizujú automaticky obraz n8n v Dockeri ani všetky repozitáre softvéru tretích strán. Pozrite si dokumentáciu automatických aktualizácií Ubuntu.

Voliteľné monitorovanie pokusov o prelomenie SSH: Fail2Ban dokáže zisťovať opakované neúspešné prihlásenia cez SSH. Ak je nainštalovaný a nakonfigurovaný pre SSH, overte jeho pravidlo príkazom sudo fail2ban-client status sshd a skontrolujte, či číta skutočný autentifikačný protokol SSH alebo systémový žurnál a zodpovedá nastavenému portu. Dopĺňa kľúče SSH a sieťové obmedzenia, ale nenahrádza ich. Nekopírujte pevne určený port SSH ani pravidlo blokovania bez kontroly existujúceho prístupu. Pozrite si odporúčania Ubuntu na zabezpečenie SSH.

DATABÁZA A REDIS

Uchovajte podporné služby v súkromnej sieti

V bežnom nastavení Docker Compose majú byť PostgreSQL a Redis pre režim frontu dostupné príslušným kontajnerom cez súkromnú sieť, nie cez porty publikované na hostiteľovi. Príkazom docker compose ps overte, že porty 5432 a 6379 nie sú verejne publikované; samostatne skontrolujte pravidlá firewallu VPS alebo cloudovej platformy. Sieťové pravidlá nenahrádzajú databázové oprávnenia podľa zásady najmenších privilégií.

PostgreSQLPripojte ho k súkromnému rozhraniu alebo sieti kontajnerov, ak vzdialený prístup nie je výslovne potrebný a samostatne zabezpečený.
RedisRedis v režime frontu je súčasť infraštruktúry, nie verejný koncový bod. Obmedzte sieťový prístup na komponenty n8n, ktoré ho potrebujú.
Prístupové údajePoužívajte vyhradené databázové prihlasovacie údaje iba s oprávneniami potrebnými pre aplikáciu a neskladujte ich v zdrojovom kóde.
Prenos údajovAk databázová prevádzka prechádza nedôveryhodnými sieťami, používajte vhodné šifrovanie prenosu a nespoliehajte sa len na šifrovanie prístupových údajov aplikáciou.

TAJNÉ ÚDAJE N8N

Chráňte šifrovací kľúč a prístupové údaje

Šifrovací kľúč

n8n šifruje uložené prístupové údaje pomocou svojho šifrovacieho kľúča. Zachovajte rovnaký kľúč pri reštartoch aj vo všetkých pracovníkoch a chráňte ho oddelene od bežného obsahu aplikácie.

Tajné údaje prostredia

Neukladajte heslá, tokeny ani šifrovací kľúč do verejného repozitára. Obmedzte prístup k súborom prostredia a tajným údajom nasadenia.

Prístup používateľov

Editor sprístupnite iba dôveryhodným používateľom. Pracovné postupy sa môžu pripájať k citlivým systémom, spracúvať tajné údaje alebo spúšťať výkonné uzly.

Rozsah oprávnení prístupových údajov

Ak je to možné, používajte účty služieb a API tokeny s úzko vymedzenými oprávneniami. Kompromitovaný pracovný postup nemá automaticky získať široký prístup k nesúvisiacim systémom.

Nastavenia n8n, ktoré treba skontrolovať: N8N_BLOCK_ENV_ACCESS_IN_NODE=true zabraňuje uzlom Code a výrazom v prístupe k hodnotám prostredia; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true vyžaduje oprávnenia k súboru nastavení iba pre jeho vlastníka. Premennú N8N_ENCRYPTION_KEY uchovávajte trvalo a bezpečne zálohujte: n8n môže pri prvom spustení vytvoriť náhodný kľúč, ale jeho strata môže spôsobiť nepoužiteľnosť existujúcich šifrovaných prístupových údajov. Produkčný šifrovací kľúč nemeňte bez riadneho postupu; použite oficiálne podporovanú rotáciu. Blokovanie prístupu k prostrediu môže narušiť existujúce integrácie, preto zmeny pred nasadením do produkcie otestujte. Pozrite si definície bezpečnostných premenných n8n.

RIZIKÁ PRACOVNÝCH POSTUPOV

Uzly môžu rozšíriť bezpečnostné hranice

Vlastný hosting dáva pracovným postupom značné možnosti. Spúšťanie kódu, prístup k shellu, ľubovoľné HTTP požiadavky a komunitné uzly tretích strán môžu zvýšiť riziko. Vypnite nepotrebné funkcie a pred spustením skontrolujte importované pracovné postupy z nedôveryhodných zdrojov.

Používajte presné podporované nastavenia: nastavte NODES_EXCLUDE pomocou poľa JSON s uzlami, ktoré chcete vypnúť, napríklad n8n-nodes-base.executeCommand a n8n-nodes-base.readWriteFile, ak ich nepoužívate. Niektoré rizikové uzly sú v novších verziách už predvolene zablokované; pred zmenou skontrolujte skutočný zoznam. Pozrite si oficiálne vylučovanie uzlov.

Od verzie n8n 2.12.0premenná N8N_SSRF_PROTECTION_ENABLED=true umožňuje kontrolu odchádzajúcich HTTP požiadaviek na interné adresy, loopback a rozsahy metadátových adries. Legitímne pracovné postupy s internými API môžu prestať fungovať; ak je to potrebné, povoľte iba úzko vymedzené ciele, ktoré spravujete. Primárnou ochranou má zostať segmentácia siete. Pri izolácii uzlov Code zvážte externé procesy na vykonávanie úloh. Ochrana pred SSRF · Izolácia procesov na vykonávanie úloh.

Komunitné uzlyInštalujte len balíky, ktorým dôverujete; ich kód sa vykonáva v prostredí n8n.
Rizikové uzlyVylúčte uzly, ktoré nasadenie nepotrebuje, ak ich možnosti presahujú zamýšľané hranice pracovných postupov.
SSRFPoužívajte ochranu n8n pred SSRF a sieťové pravidlá tam, kde sa pracovné postupy nemajú dostať k interným koncovým bodom alebo adresám metadát.
Importy pracovných postupovPred aktiváciou skontrolujte importované pracovné postupy, prístupové údaje, výrazy aj spustiteľné kroky.

AUDIT A AKTUALIZÁCIE

Bezpečnosť je sústavný prevádzkový proces

Spustite bezpečnostný audit n8n

Oficiálny príkaz CLI je n8n audit. Ak má vaša služba Docker Compose názov n8n, v adresári daného nasadenia spustite docker compose exec -T n8n n8n audit . Skontrolujte päť kategórií: nepoužívané prístupové údaje, rizikové vzory SQL dopytov, prístup k súborovému systému, rizikové a komunitné uzly a riziká inštancie vrátane nechránených webhookov a zastaraných vydaní. Opravte relevantné nálezy a audit zopakujte. Nie je to penetračný test. Pozrite si oficiálny návod na audit.

Aktualizujte cielene

Udržiavajte n8n dostatočne aktuálny, aby dostával bezpečnostné opravy. Pred dôležitými aktualizáciami čítajte poznámky k vydaniam a testujte ich, namiesto dlhodobého ponechania zastaranej inštancie dostupnej z internetu.

Monitorujte autentifikáciu

Sledujte neobvyklé vzory prístupu, zmeny pracovných postupov a zlyhania. Ak váš model prevádzky nevyžaduje širokú verejnú dostupnosť, ďalej obmedzte prístup k editoru.

Pripravte návrat a obnovu

Pred významnými aktualizáciami vytvorte obnoviteľné zálohy. Podrobný rozsah zálohovania a obnova patria do samostatného návodu.

Obmedzte citlivé údaje v histórii vykonaní: Úspešné vykonania môžu uchovávať údaje zákazníkov a tokeny. Vhodným nastavením môže byť EXECUTIONS_DATA_SAVE_ON_SUCCESS=none; ponechajte zapnuté EXECUTIONS_DATA_PRUNE=truea zvoľte hodnotu EXECUTIONS_DATA_MAX_AGE v hodinách, napríklad 168 (sedem dní). Ide o nastaviteľné príklady, nie o právne pravidlá uchovávania údajov. Menej histórie znamená aj menej dát na ladenie a forenznú analýzu; prebiehajúce, čakajúce alebo označené vykonania nemusia podliehať rovnakému odstraňovaniu. Pozrite si oficiálne uchovávanie údajov o vykonaniach.

Podozrenie na narušenie bezpečnosti: Zabráňte škodlivému prístupu bez zničenia dôkazov, preskúmajte aktivitu proxy servera, hostiteľa, n8n a zmenené pracovné postupy, zrušte alebo vymeňte potenciálne odhalené prístupové údaje k externým službám, opravte príčinu a podľa potreby obnovujte len z overených obnoviteľných záloh. Skontrolujte dotknuté URL webhookov, účty editora a pripojené služby; nepredpokladajte, že HTTPS, snímky alebo kúpa VPS zahŕňajú služby riešenia bezpečnostných incidentov.

OCHRANA ÚČTOV A PLATFORMY

Chráňte editor aj VPS

Vyžadujte silnejšie zabezpečenie prihlasovania

Zapnite dvojfaktorové overovanie pre účty editora a vynucujte MFA cez bezpečnostné pravidlá n8n, ak vaša edícia podporuje centrálne presadzovanie takých pravidiel.

Obmedzte oprávnenia na úpravu pracovných postupov

Prístup k editoru je privilegovaným prístupom: pracovné postupy môžu čítať prístupové údaje, volať interné systémy a spúšťať výkonné uzly. Oprávnenia používateľov ponechajte úzke a odstráňte účty, ktoré už prístup nepotrebujú.

Vypnite nepoužívané možnosti

Zmenšite plochu útoku aplikácie vypnutím verejného API, ak nie je potrebné, a zablokovaním rizikových uzlov alebo funkcií, ktoré váš model prevádzky nepotrebuje.

Ochranu pred SSRF a ochranu tajných údajov používajte cielene

Pri pracovných postupoch, ktoré môžu vytvárať ľubovoľné HTTP požiadavky, zvážte ochranu n8n pred SSRF a tajné údaje neukladajte do kódu pracovných postupov, verejných repozitárov ani všeobecne čitateľných súborov prostredia.

Obmedzte nepoužívané koncové body správy: N8N_PUBLIC_API_DISABLED=true vypína verejné REST API n8n a N8N_PUBLIC_API_SWAGGERUI_DISABLED=true samostatne vypína jeho interaktívne rozhranie API. Urobte to iba vtedy, ak vaše integrácie tieto funkcie nepotrebujú. Vypnutie REST API nezabezpečí autentifikáciu URL adries webhookov pracovných postupov. Pre používateľov editora zapnite MFA; centrálne pravidlá používajte len v edíciách n8n, ktoré ich podporujú.

ČASTÉ OTÁZKY

Bezpečnosť n8n na VPS: časté otázky

Má byť port n8n priamo sprístupnený?

Ak je verejným vstupným bodom reverzný proxy server, sprístupnite proxy server a port aplikácie ponechajte za ním, namiesto zbytočného vystavovania služieb internetu.

Majú byť PostgreSQL alebo Redis verejne dostupné?

Spravidla nie. Majú byť dostupné iba systémom, ktoré ich potrebujú. Verejné sprístupnenie zväčšuje plochu útoku bez prínosu pre bežnú prevádzku n8n.

Prečo je šifrovací kľúč n8n dôležitý?

Chráni prístupové údaje uložené v n8n a musí zostať rovnaký v celom nasadení. Jeho strata môže spôsobiť, že obnovené údaje nebudú obsahovať použiteľné šifrované prístupové údaje.

Sú komunitné uzly bezpečné?

Rozširujú n8n o kód tretích strán, preto ich treba považovať za softvérové závislosti s rizikami dodávateľského reťazca a oprávnení. Inštalujte iba to, čomu dôverujete a čo potrebujete.

Stačí HTTPS na zabezpečenie n8n na vlastnom serveri?

Nie. HTTPS chráni prenos údajov. Produkčná bezpečnosť vyžaduje aj zabezpečenie hostiteľa, riadenie prístupu, súkromné podporné služby, ochranu tajných údajov, bezpečné možnosti pracovných postupov, monitorovanie a aktualizácie.

Môže byť editor n8n súkromný, kým produkčné webhooky fungujú?

Áno. Dôveryhodný reverzný proxy server alebo VPN môže obmedziť prístup k editoru a správe oddelene od verejných trás produkčných webhookov a spätných volaní OAuth. Po každej zmene prístupových pravidiel otestujte prihlásenie oprávneného používateľa a doručenie externého webhooku, aby sa integrácie omylom nezablokovali.

Ako autentifikovať prichádzajúce webhooky n8n?

V uzle Webhook nastavte autentifikáciu Basic, Header alebo JWT, ak ju odosielateľ podporuje. Môžete použiť aj IP(s) Allowlist a podľa dostupnosti kontrolovať podpisy poskytovateľa. Nespoliehajte sa len na tajne vyzerajúcu cestu a požiadavky overte skôr, než spustia citlivé akcie API.
