TELEPÍTÉS DOCKERREL

Az n8n telepítése VPS-re

Telepítsd az n8n-t VPS-re Docker Compose és PostgreSQL használatával. Az éles üzemhez az alkalmazás és az adatbázis tartós tárolása, valamint egy állandó N8N_ENCRYPTION_KEY, nyilvános hosztnév, HTTPS és megfelelő webhook-beállítások is szükségesek. Az éles munkafolyamatok aktiválása előtt mindezt ellenőrizd.

ELŐFELTÉTELEK

Készítsd elő a VPS-t az n8n indítása előtt

Linux VPS

Használj karbantartott Linux-szervert, amelynek erőforrásai elegendők az n8n, a PostgreSQL, a Docker és a fordított proxy működtetéséhez.

DNS

A TLS-tanúsítványok igénylése és a webhook-URL-ek közzététele előtt irányíts egy domaint vagy aldomaint a VPS-re.

Docker Compose

A Docker Engine-t és a Compose-bővítményt az operációs rendszerhez támogatott csomagokból telepítsd.

Tűzfal

Csak a szükséges adminisztrációs és webes portokat tedd elérhetővé. A PostgreSQL és a belső alkalmazásszolgáltatások maradjanak privát hálózaton.

Olyan VPS-re telepítenél, amelyen már működnek weboldalak? Ha a CPU, RAM és tárhely elegendő, a saját szerveredre n8n-t is telepíthetsz. Ha viszont az Nginx, Apache, Caddy vagy más fordított proxy már használja a 80/443-as portokat, semmiképp ne indítsd el változtatás nélkül az alábbi Caddy-konténert: a portok ütközni fognak. Ehelyett a meglévő fordított proxyn keresztül, megfelelő privát hálózattal irányíts egy új n8n-aldomaint a szolgáltatásra, vagy a pontos Compose-példához használj tiszta VPS-t. Őrizd meg a többi webhelyet és azok TLS-beállításait; a példa feltételezi, hogy a 80/443-as portok szabadok.

MÁSOLHATÓ ÉS TESTRESZABHATÓ TELEPÍTÉS

Az n8n telepítése VPS-re Docker Compose segítségével

Ezzel a példával egy saját kezelésű Linux VPS-enépíthetsz n8n-környezetet. Az n8n telepítése és karbantartása a te feladatod; a partnerünkön keresztül választott szerver nem tartalmaz előre telepített n8n-példányt. A példa egy privát Compose-hálózaton egyesíti az n8n-t, a PostgreSQL-t, egy külső task runnert és a Caddy által kezelt HTTPS-t. Ez konfigurációs sablon, nem annak állítása, hogy a telepítést éles környezetben teszteltük.

Inkább a lehető leggyorsabb új telepítést szeretnéd? Az n8n hivatalos, egysoros Docker-telepítést is kínál. A szkriptet a curl -fsSL https://get.n8n.io -o get-n8n.sh paranccsal letöltheted és ellenőrizheted, mielőtt futtatnád a sh get-n8n.shparancsot. Ez a lehetőség helyi URL-en, SQLite-adatbázissal indít kezdeti példányt, és n8n Assistant-sandboxszolgáltatásokat is tartalmaz; ez nem ugyanaz a környezet, mint az itt ismertetett, nyilvános HTTPS-t és PostgreSQL-t használó VPS-telepítés. A hivatalos teljes sandboxcsomag több RAM-ot és CPU-t igényel, mint egy egyszerű n8n-telepítés (a Compose-útmutató legalább 4 GB RAM-ot és 2 vCPU-t ír elő). Internet felől elérhető éles VPS-hez folytasd az alábbi, kézzel konfigurálható összeállítással.

1. Docker, DNS és hozzáférés előkészítése

Csatlakozz SSH-n sudo-jogosultsággal, és állíts be egy DNS A rekordot a n8n.example.com hosztnévhez úgy, hogy a VPS IPv4-címére mutasson. Egy friss Ubuntu 22.04, 24.04 vagy 26.04 rendszerű VPS-en az alábbi parancsok telepítik a Docker Engine-t és a modern docker compose bővítményt a Docker hivatalos, aláírt apt csomagtárolójából:

# Fresh official Ubuntu 22.04 / 24.04 / 26.04 installation
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Register Docker's signed apt repository
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

Ez a Docker hivatalos Ubuntu-telepítési útmutatójában leírt, éles üzemhez ajánlott csomagtárolós módszer. Ne telepítsd újra vagy távolítsd el meggondolatlanul a Dockert olyan VPS-en, ahol már konténerek vagy más weboldalak működnek; előbb vizsgáld meg a jelenlegi telepítést és az esetleges csomagütközéseket. Debian vagy más disztribúció esetén az Ubuntu-parancsok helyett a megfelelő operációs rendszer hivatalos útmutatóját használd.

Ezután ellenőrizd a Dockert, a Compose-bővítményt, a DNS-t és a munkakönyvtárat:

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

Ha a getent hosts parancs nem ad vissza címet, vagy hibás címet ad, a Caddy indítása előtt javítsd a DNS-beállítást. A n8n.example.com példanevet az útmutató egészében cseréld a saját hosztnevedre. A Docker általában rendszergazdai jogosultságot igényel; ha az SSH-felhasználó nem tudja közvetlenül futtatni a későbbi docker compose parancsokat, írd eléjük a sudoparancsot. Ha egy felhasználót hozzáadsz a docker csoporthoz, lényegében root-jogosultságot adsz neki; megosztott szerveren ezt ne tedd meg kellő mérlegelés nélkül.

A tűzfal bekapcsolása előtt gondoskodj arról, hogy a tényleges SSH-adminisztrációs port továbbra is elérhető legyen. Engedélyezd a bejövő HTTP (80) és HTTPS (443) forgalmat a tanúsítványkiállításhoz és a szerkesztőhöz. A Docker által közzétett konténerportok megkerülhetnek bizonyos UFW-szabályokat, ezért ellenőrizd a Docker tűzfal-dokumentációját, és csak a szándékosan használt Caddy-portokat tedd nyilvánossá. Ez a Compose-példa szándékosan nem teszi elérhetővé a nyilvános interneten a PostgreSQL (5432), az n8n (5678) vagy a task-runner broker (5679) portját.

2. Környezeti változók létrehozása és a kulcs megőrzése

A projektkönyvtárból készíts három különböző véletlenszerű hexadecimális értéket az alábbi paranccsal:

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

Hozz létre egy .env nevű fájlt az alábbi sablon szerint, és minden REPLACE_WITH_RANDOM_HEX helyére különböző generált értéket írj. Módosítsd a hosztnevet és az időzónát is. A bemutatott 2.42.5 verziócímke a 2026. október 8-án nyilvántartott stabil kiadás, amelyet itt dátumhoz kötött konfigurációs példaként használunk; nem jelenti azt, hogy a telepítést éles rendszerben teszteltük, és nem garantálja a későbbi biztonságot. Telepítés előtt ellenőrizd az n8n aktuális hivatalos kiadásait, majd az n8n és a task-runner lemezképét ugyanahhoz az ellenőrzött verzióhoz rögzítsd.

# .env — replace the three example secrets
# Pin a maintained n8n release; keep n8n and runner equal.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

Soha ne töltsd fel a .env fájlt nyilvános repóba. A titkosítási kulcsot és a helyreállítási utasításokat biztonságosan, a VPS-en kívül tárold. A kulcsnak konténer-újralétrehozás vagy migráció után is változatlannak kell maradnia.

3. A compose.yaml elkészítése új telepítéshez

Ugyanabban a könyvtárban hozd létre a compose.yamlfájlt. A példa az n8n hivatalos környezetiváltozó-elnevezéseit és a PostgreSQL 18 PGDATA útvonalát használja, amelyet az n8n hosting projekt dokumentál:

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

A négy szolgáltatásnak eltérő feladata van: a PostgreSQL tárolja az adatbázist, az n8n futtatja a munkafolyamatokat, a n8n-runner azonosított verzióval és közös hitelesítési tokennel futtatja a taskokat, a Caddy pedig kezeli a nyilvános HTTPS-t. A külső task runner nem azonos a Redis queue móddal. Hosztportokat csak a Caddy tesz közzé. Ez az egyszerű példa egyetlen adatbázis-szerepkörrel dolgozik; a PostgreSQL-jogosultságok szigorúbb szétválasztásához lásd az n8n hivatalos PostgreSQL-telepítési példáját.

4. A HTTPS-hez szükséges Caddyfile létrehozása

Hozd létre a Caddyfile fájlt (nagy C-vel, kiterjesztés nélkül) a compose.yamlmellett. A példában szereplő hosztnevet mindenütt cseréld le a saját DNS-nevedre:

n8n.example.com {
    reverse_proxy n8n:5678
}

A Caddy akkor igényel és újít meg nyilvános TLS-tanúsítványokat, ha a domain helyesen oldódik fel, és a külső forgalom eléri a 80/443-as portokat. A DNS-t ne irányítsd a localhostcímre. Ha a Caddyt más fordított proxyval helyettesíted, továbbítsd az eredeti hosztnév-, protokoll- és klienscímet tartalmazó fejléceket, és állítsd be a N8N_PROXY_HOPS értékét a ténylegesen megbízható proxyugrások számának megfelelően.

5. A konténerek indítása és külső tesztelése

Mentés után futtassa ezeket a parancsokat a projektkönyvtárból .env, compose.yaml és Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

Az utolsó parancs ellenőrzi a nyilvános HTTPS egészségügyi végpont. Ha a tanúsítvány kiadása még függőben van, ellenőrizze a Caddy naplókat és DNS/portokat, mielőtt a n8n megszakadt. Nyissa meg https://n8n.example.com, azonnal hozza létre az első tulajdonosi fiókot, és engedélyezze a megfelelő bejelentkezési védelmet. Győződjön meg arról, hogy a példány valóban egy munkafolyamatot hajt végre, nem csupán azt, hogy a szerkesztő betölti:

  1. A szerkesztőben hozzon létre egy munkafolyamatot az a Webhook ravaszt. Állítsa be HTTP Módszer hogy GET, válassza ki a Path vps-check, és állítsa be Válaszolj hogy Azonnal. Mentse el a munkafolyamatot.
  2. Kattintson Hallgassa meg a teszt eseményt, másolja a teljes Teszt URL n8n mutatja, és egy másik eszközről fut curl -i 'PASTE_TEST_URL_HERE' a másolt URL-lel. Várja, hogy a HTTP sikeres válasza és a bejövő esemény megjelenjen a n8n szerkesztőben. A teszt URL-ek csak akkor működnek, amikor a n8n figyeli az eseményt.
  3. Közzététel a munkafolyamatot, kapcsolja át a csomópontot a megfelelőre Gyártási URL, másolja ki és futtassa curl -i 'PASTE_PRODUCTION_URL_HERE' újra. Erősítse meg a végrehajtást a munkafolyamat alatt Kivégzések lapon. Az éles webhook-kérelmeknek közzé kell tenni a munkafolyamatot, és nem jelennek meg a hasznos terhelésük a szerkesztő tesztnézetében.

Ez egy szándékosan egyszerű, nem hitelesített füstteszt: soha ne küldj neki titkokat. Tesztelés után vonja vissza a közzétételt/törölje, vagy konfigurálja a Webhook-hitelesítési/IP-korlátozásokat, mielőtt nyilvános végpontot használna valós adatokhoz. Tekintse meg a Webhook hivatalos teszt/gyártási dokumentációját.

6. A rögzített verziók módosítása előtt készítsen biztonsági másolatot

Mentse el a helyreállítható PostgreSQL kiírást és a tartós n8n adatmennyiség, .env/titkosítókulcsot és a szükséges külső fájlokat a kiszolgálón kívüli tárolásra. Ellenőrizze a visszaállítást a biztonsági mentési és helyreállítási útmutató a gyártás frissítése előtt. Példaparancsok:

# Back up the database, encryption key, instance data,
# and files before changing the pinned versions.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# After securing the backup outside this VPS:
docker compose pull
docker compose up -d
docker compose ps

Cserélje ki a rögzítettet N8N_VERSION csak a kiadási megjegyzések elolvasása után; a n8n és a futóképeknek együtt kell haladniuk. Ne fuss docker compose down -v rutin karbantartás során, mert ez törli a megnevezett adatköteteket. PostgreSQL A főbb verzióváltásokhoz adatbázis-frissítés vagy kiíratási/visszaállítási terv szükséges; a Postgres 18 képének másik fő címkére való lecserélése nem automatikus migráció.

Hiteles hivatkozások: n8n Docker Összeállítási útmutató, n8n fordított proxy/webhook konfiguráció és hivatalos PostgreSQL beépítési megjegyzések. Nem feltételezhető infrastruktúra-benchmark vagy szolgáltató-specifikus előre telepített szolgáltatás.

Gyakran ismételt kérdések

n8n telepítése Docker-al: gyakori kérdések

A n8n-nak szüksége van az PostgreSQL-ra a Docker használatakor?

A Docker nem követeli meg az PostgreSQL -t, és a kis bevetések használhatják a SQLite-t. A termelés-orientált VPS-os telepítéshez a PostgreSQL erősebb adatbázis-alapot biztosít, és támogatja a későbbi sormódú skálázást.

Miért tartsunk fenn tartós n8n-os kötetet, ha az PostgreSQL adatokat tárol?

Az állandó n8n könyvtár fontos példányállapotot és konfigurációt tartalmazhat. Őrizze meg a telepítési terv szerint, ahelyett, hogy azt feltételezné, hogy az adatbázis az egyetlen helyreállítási eszköz.

Miért jelenik meg a webhookom, hogy localhost?

A belső tároló címe eltér a nyilvános eredettől. Konfigurálja a külső gazdagépnevet, protokollt és webhook URL-t, és győződjön meg arról, hogy a fordított proxy átadja a szükséges fejléceket.

A 5678 port nyilvános legyen?

A fordított proxy mögötti normál éles üzembe helyezés esetén tegye közzé a HTTPS-t a proxynál, és tartsa belső az n8n-os alkalmazásportot, hacsak nincs konkrét működési ok, ami miatt nem.

Szükségem van a Redis-ra?

Nem szabványos egypéldányos Docker-os telepítéshez. Az Redis. -a akkor válik relevánssá, ha szándékosan sorban állásra vált és a dolgozókat.

A külső n8n feladatfutók ugyanazok, mint a sor módban dolgozók?

Nem. A külső feladatfutók a támogatott feladatkódot a n8n főfolyamattól elkülönítve hajtják végre, és megosztott hitelesítési tokent használnak. Az Redis. -a queue mode elosztja a munkafolyamat-végrehajtásokat, és saját infrastrukturális követelményei vannak. Ez a példa egy külső feladatfutót mutat be, nem a Redis várólista módot.
