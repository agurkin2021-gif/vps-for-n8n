REZERVNE KOPIJE I OPORAVAK

Rezervne kopije i vraćanje n8n

Za rezervnu kopiju i vraćanje n8n instalacije kojom sami upravljate sačuvajte SQLite bazu ili doslednu PostgreSQL kopiju, trajnu fasciklu .n8n i originalni ključ za šifrovanje, konfiguraciju instalacije i sve spoljne binarne podatke ili montirane datoteke koje aplikacija koristi. Šifrovanu kopiju čuvajte van VPS-a i testirajte oporavak u zasebnoj instanci. CLI izvoz radnih tokova i pristupnih podataka služi za selektivno vraćanje; same JSON datoteke nisu potpuna rezervna kopija servera.

BRZA KONTROLNA LISTA

Šta rezervna kopija n8n mora da sačuva

Baza podataka

Sačuvajte PostgreSQL bazu ili SQLite datoteku baze koju instanca koristi. Baza sadrži ključne n8n podatke kao što su radni tokovi, pristupni podaci i podaci o izvršavanjima.

Ključ za šifrovanje

Sačuvajte baš onaj n8n ključ za šifrovanje koji instanca koristi, odvojeno i bezbedno. Za vraćanje šifrovanih pristupnih podataka potreban je isti ključ.

Trajne datoteke

Uključite trajnu n8n fasciklu sa podacima, sve montirane datoteke, skladište binarnih podataka i druge resurse od kojih zavise radni tokovi.

Konfiguracija instalacije

Sačuvajte Compose i druge konfiguracione datoteke potrebne za ponovno postavljanje sistema, bez izlaganja tajnih podataka. Lozinke i druge tajne zaštitite odgovarajućom kontrolom pristupa.

DVA NIVOA REZERVNIH KOPIJA

Logički izvoz ili potpun oporavak posle otkaza

Izvoz radnih tokova i pristupnih podataka

Izvoz putem n8n CLI-ja koristan je za migraciju, čuvanje verzija radnih tokova i selektivno vraćanje. Pristupni podaci mogu se izvesti u šifrovanom obliku i kasnije uvesti uz odgovarajući ključ. Ako vraćate jedan radni tok, u editoru preko menija sa tri tačke preuzmite njegov JSON pomoću opcije Download, pa ga opcijom Import from File uvezite u novi radni tok za proveru ili zasebnu instancu. Pre zamene aktivnog toka proverite pristupne podatke, ID-jeve i parametre čvorova. Vraćanje JSON datoteke radnog toka ne vraća ceo server.

Izvoz entiteta baze

CLI omogućava izvoz entiteta iz baze za prenos podataka između podržanih tipova baza. Tabele istorije izvršavanja su opcione, jer mogu biti veoma velike.

Oporavak cele instance

Ako server prestane da radi, potrebni su stvarna baza, ključ za šifrovanje, trajni podaci i svi resursi neophodni za pokretanje. Nemojte pretpostaviti da JSON izvoz radnih tokova može ponovo izgraditi celu instancu.

Snimak stanja kod provajdera

VPS snapshot može biti dodatan nivo zaštite, ali ne treba da bude jedina kopija niti zamena za nezavisno proverenu rezervnu kopiju aplikacije i baze.

BAZA PODATAKA

Napravite doslednu rezervnu kopiju baze

PostgreSQL

Koristite metod koji pravi doslednu PostgreSQL kopiju i čuvajte je van VPS-a. Kopija baze na istom disku koji otkaže ne predstavlja oporavak od katastrofe.

SQLite

Ako instalacija koristi SQLite, sačuvajte datoteku baze iz trajne n8n fascikle. Izbegavajte kopiranje baze u nedoslednom stanju dok se aktivno menja.

Istorija izvršavanja

Odlučite da li je istorija izvršavanja deo vašeg plana oporavka. Ona može znatno povećati kopije, pa odluku zasnivajte na zahtevima za čuvanje podataka i propisima.

Verzija baze

Zabeležite sistem baze podataka i njegovu verziju u izvornoj instalaciji kako biste pripremili kompatibilno okruženje za oporavak.

PostgreSQL na VPS-u sa Docker Compose. Ako se PostgreSQL servis zove postgres a baza i korisnik se zovu n8n, sledeća komanda pravi dosledan PostgreSQL dump u prilagođenom formatu na samom serveru. Pre pokretanja proverite stvarnu Compose datoteku i prilagodite nazive servisa i pristupne podatke. pg_dump može napraviti logički dosledan snimak dok PostgreSQL radi, ali ne čuva zasebnu .n8n korisničku fasciklu niti spoljne binarne podatke.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Provera liste sadržaja arhive može otkriti očigledne probleme sa formatom, ali ne dokazuje da se podaci mogu vratiti. Šifrovanu kopiju premestite van servera i isprobajte oporavak. Za posebne opcije baze pogledajte zvaničnu dokumentaciju PostgreSQL komande pg_dump.

SQLite u Dockeru. Kod podrazumevane SQLite instalacije, database.sqlite i konfiguracija sa generisanim ključem za šifrovanje nalaze se u trajnoj .n8n fascikli, koja se obično montira na /home/node/.n8n. Nemojte smatrati običnu kopiju aktivne SQLite baze doslednom. Zaustavite n8n i sve druge procese koji upisuju podatke pre kopiranja fascikle ili upotrebite podržani mehanizam SQLite za rezervnu kopiju dok baza radi ako prekid nije moguć:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Ovo su primeri komandi za prikazane servise i putanje, ne univerzalna struktura volumena. Kopirana fascikla je u početku i dalje na istom VPS-u; premestite je i zaštitite van servera. Ako imate workere u režimu reda ili druge procese koji upisuju podatke, zaustavite i njih na odgovarajući način. Aktuelno n8n uputstvo za potpunu rezervnu kopiju opisuje zahteve za doslednost SQLite baze.

Vraćanje podrazumevane SQLite fascikle u prazno odredište: najpre zaustavite n8n servis i sve procese koji upisuju u bazu. Kada pripremite kompatibilan n8n kontejner i odredišni volumen, kopirajte sačuvani .n8n sadržaj nazad u istu trajnu fasciklu. Time se prepisuju odredišne datoteke, zato ne pokrećite komandu na instanci čije podatke morate sačuvati:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker može kopirati datoteke i u zaustavljene kontejnere, ali se vlasništvo i dozvole na odredištu mogu razlikovati. Pre pokretanja n8n proverite da proces može da čita i menja vraćenu konfiguraciju i bazu. Ako vaša Compose konfiguracija koristi drugu putanju ili bind mount, prilagodite kopiranje. Pogledajte referencu Docker Compose za kopiranje. Vraćanje samo n8n fascikle nije dovoljno kada instalacija koristi odvojenu PostgreSQL bazu.

VAŽNA TAJNA

Ključ za šifrovanje je neophodan za oporavak

n8n šifruje sačuvane pristupne podatke ključem za šifrovanje instance. Vraćanje baze ili šifrovanog izvoza bez istog ključa može sprečiti radne tokove da koriste postojeće pristupne podatke.

Ako ste podesili N8N_ENCRYPTION_KEY, morate vratiti potpuno istu tajnu vrednost. U suprotnom, generisani ključ je u trajnoj datoteci .n8n/config, koju treba zaštititi pri pravljenju kopije ili obnavljanju servera. Ključeve za oporavak čuvajte bezbedno van VPS-a. U režimu reda glavni proces i svi workeri moraju imati isti ključ.

UraditeSačuvajte zaštićenu kopiju tačno onog ključa koji koristi produkcija.
UraditePre provere pristupnih podataka utvrdite da okruženje za oporavak koristi isti ključ.
Nemojtese oslanjati na novogenerisani ključ nakon ponovnog postavljanja servera.
Nemojteslati ključ u javni repozitorijum niti ga čuvati uz nezaštićenu rezervnu kopiju.

DATOTEKE I BINARNI PODACI

Kopija baze ne obuhvata uvek sve zavisnosti radnog toka

Trajni podaci u .n8n

Pronađite i sačuvajte stvarnu korisničku fasciklu .n8n, a ne samo sliku kontejnera. Kod tipične Docker instalacije ona se montira na /home/node/.n8n, a van Dockera podrazumevana lokacija je ~/.n8n. Ako je podešen N8N_USER_FOLDER, n8n pravi .n8n u navedenoj roditeljskoj fascikli. Sačuvajte konfiguraciju i ključ, lokalnu SQLite bazu, binarne datoteke i podatke o izvršavanju koji se čuvaju u sistemu datoteka.

Montirane datoteke radnih tokova

Ako radni tokovi čitaju ili upisuju u fascikle montirane sa servera, sačuvajte i te fascikle zasebno. Bez njih radni tokovi mogu prestati da rade i kada su ostali podaci uspešno vraćeni.

Binarni podaci

Proverite način skladištenja i obezbedite kopiju svake spoljne zavisnosti. Binarni podaci i podaci o izvršavanjima mogu se čuvati u .n8n ili drugoj fascikli; S3, Azure Blob i druge spoljne usluge zahtevaju sopstvene rezervne kopije i podešavanja pristupa. Sam dump baze ne vraća te datoteke.

Čvorovi zajednice

Zabeležite pakete čvorova zajednice i njihove verzije. Sačuvajte i fascikle sa prilagođenim čvorovima koje koristi N8N_CUSTOM_EXTENSIONS. One mogu biti van .n8n, pa vraćanje baze i korisničke fascikle ne mora vratiti radne tokove sa tim čvorovima.

STRATEGIJA KOPIJA VAN SERVERA

Rezervna kopija na istom VPS-u samo je lokalna kopija

Lokalna kopijaDobra je za brz povratak na prethodno stanje, ali je ugrožena otkazom servera, kvarom diska ili greškom koja uništi podatke.
Kopija van serveraČuvajte bar jednu rezervnu kopiju na skladištu koje ne zavisi od produkcionog VPS-a.
Kopije iz različitih periodaSačuvajte više tačaka oporavka kako greška ili oštećenje podataka ne bi prepisali jedinu ispravnu kopiju.
Kontrola pristupaRezervne kopije mogu sadržati pristupne podatke, logiku radnih tokova i osetljive poslovne podatke. Šifrujte ih i ograničite pristup.
NadzorPostavite upozorenja ako zakazano pravljenje kopija ne uspe ili prestane da stvara nove tačke oporavka.

Merite uspešnost izrade rezervnih kopija. Beležite vreme svake uspešne kopije i završenog prenosa, veličinu datoteke, verziju izvorne baze, gde se može pronaći ključ za oporavak i vreme poslednjeg uspešnog testa vraćanja. Upozoravajte na nedostajuće, neuspešne ili neočekivano prazne kopije. Šifrujte arhive pre slanja sa VPS-a i ograničite pristup tajnama za oporavak. Kopije sa više datuma štite od situacije kada najnovija oštećena kopija prepiše poslednju ispravnu.

Na primer, ako možete izgubiti najviše šest sati izmena, uspešno pravljenje kopije svakih šest sati samo je početna mera, a ne garancija. Neuspele kopije i odloženi prenos na spoljašnje skladište povećavaju mogući gubitak. Period čuvanja i učestalost testiranja odredite prema svojim RPO, RTO i zahtevima, ne prema opštem pravilu od 7 ili 30 dana.

REDOSLED OPORAVKA

Vraćajte sistem kontrolisanim redosledom

1 · Pripremite okruženjePostavite kompatibilan server, bazu i okruženje za kontejnere i izvršavanje.
2 · Vratite tajneBezbedno podesite originalni n8n ključ za šifrovanje i ostale neophodne tajne instalacije.
3 · Vratite bazuVratite PostgreSQL ili SQLite i proverite da se n8n povezuje sa očekivanim podacima.
4 · Vratite datotekeVratite trajne fascikle, binarne podatke i montirane datoteke potrebne radnim tokovima.
5 · Pokrenite n8nPokrenite aplikaciju sa odgovarajućim imenom hosta, bazom i konfiguracijom okruženja.
6 · ProveriteProverite da se korisnici, radni tokovi i pristupni podaci učitavaju, pa pokrenite reprezentativne radne tokove i testirajte veb-hukove.

Primer oporavka PostgreSQL baze posle otkaza: na odvojenom, praznom odredištu za oporavak gde već postoji odgovarajuća uloga baze i prazna n8n baza, najpre pokrenite samo PostgreSQL. Sačekajte da baza bude spremna pre uvoza: docker compose up -d može se završiti dok se PostgreSQL još inicijalizuje, zbog čega naredni pg_restore može da ne uspe. Primer koristi --wait u savremenoj Compose instalaciji i nezavisno proverava pg_isready. Podesite odgovarajuću PostgreSQL proveru stanja ili eksplicitno potvrdite spremnost pre nastavka. Ne usmeravajte ovu komandu na produkcionu bazu koja već sadrži podatke i ne pokrećite n8n dok baza i odgovarajući .n8n ključ i podaci ne budu vraćeni.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Na odredištu su neophodni kompatibilna verzija PostgreSQL, dozvole korisničke uloge, proširenja i originalna n8n konfiguracija. Vratite .n8n u odgovarajući trajni volumen ili bind mount pomoću svog postupka za rezervne kopije, uz očuvanje vlasništva i dozvola. Vratite spoljne binarne datoteke, dodatne čvorove, Compose konfiguraciju i tajne, pa pokrenite kompatibilnu verziju n8n i proverite logove. Samo vraćanje baze ne vraća ključ: kod PostgreSQL instalacije ključ se nalazi u .n8n/config osim ako ste izričito podesili N8N_ENCRYPTION_KEY. Pogledajte dokumentaciju za pg_restore i redosled vraćanja cele n8n instance.

TEST OPORAVKA

Rezervna kopija nije potvrđena dok vraćanje ne uspe

Proverite u praznom okruženju

Pravi test mora dokazati da kopija može obnoviti instancu bez oslanjanja na dodatne datoteke koje su slučajno ostale na produkcionom serveru.

Proverite pristupne podatke

Nije dovoljno samo otvoriti radni tok. Proverite da se šifrovani pristupni podaci zaista mogu dešifrovati i koristiti za autentifikaciju.

Pokrenite reprezentativne radne tokove

Testirajte tokove koji koriste veb-hukove, spoljne API-je, montirane datoteke i čvorove zajednice, a ne samo jednostavnu automatizaciju.

Izmerite vreme oporavka

Zabeležite trajanje vraćanja i preostale ručne korake. Tako pretvarate pretpostavljenu rezervnu kopiju u pouzdan postupak oporavka.

Proveren test oporavka: SQLite i PostgreSQL

Test okruženje: n8n 2.42.5 u izolovanim Docker kontejnerima na privremenom GitHub Actions izvršiocu, sa probnim radnim tokom od dva čvora. Provere su izvedene 8. oktobra 2026., a ne na korisničkom ili produkcionom n8n serveru.

SQLite: PASSUvezen je probni radni tok, pa izvezen; zaustavljeni su svi procesi koji upisuju podatke, a trajna .n8n fascikla sa SQLite bazom i generisanim ključem za šifrovanje je arhivirana, vraćena na čist volumen i korišćena za pokretanje n8n. Zatim je vraćeni tok ponovo izvezen i izvršen.
PostgreSQL: PASSIsti probni radni tok je uvezen, napravljen je i pregledan dump u prilagođenom pg_dumpformatu, pa je vraćen komandom pg_restore u novu, praznu PostgreSQL bazu. Odvojena .n8n fascikla je vraćena, a oporavljeni tok ponovo izvezen i izvršen.
Šta potvrđuje PASSTestirani postupci su sačuvali radni tok, njegova dva čvora i njihove veze i omogućili izvršavanje nakon oporavka. To su ponovljivi funkcionalni testovi, a ne merenja performansi pod opterećenjem.
Šta nije testiranoDešifrovanje i autentifikacija stvarnih pristupnih podataka, produkcioni veb-hukovi, workeri i Redis u režimu reda, S3/Azure skladištenje binarnih podataka, prilagođeni čvorovi, pristup korisnika i projekata niti oporavak aktivne produkcione instance. Izvedite poseban test za svaku zavisnost koju zaista koristite.

Kako ponoviti test: koristite privremenu n8n instalaciju i napravite bezopasan radni tok sa dva čvora. Napravite kopiju baze i trajne fascikle, vratite je u čist volumen ili bazu i proverite čvorove, veze i stvarno izvršavanje. Na produkcionom sistemu proverite i šifrovane pristupne podatke, veb-hukove i spoljne datoteke pre nego što oporavak proglasite potvrđenim.

Uslovi za uspešan test vraćanja: koristite izolovani domen i okruženje. Proverite da su korisnici i tokovi prisutni, da se bar jedan postojeći šifrovani pristupni podatak autentifikuje bez ponovnog unosa, da produkcioni veb-huk pokreće odgovarajući vraćeni tok, da su montirane i binarne datoteke čitljive i da se potrebni čvorovi zajednice učitavaju. Potvrdite starost kopije, izmereno vreme prekida i dostupnost kopije van servera. Ako važna provera ne uspe, označite tu tačku oporavka kao neproverenu umesto da prijavite rezervnu kopiju kao potpunu.

OGRANIČENJA CLI REZERVNIH KOPIJA

Šta izvoz radnih tokova i pristupnih podataka ne vraća

CLI izvoz nije rezervna kopija cele instance

Izvoz radnih tokova i pristupnih podataka ne uključuje korisnike i uloge, istoriju izvršavanja i logove, promenljive niti podešavanja instance poput ključa za šifrovanje.

Nova instanca mora imati vlasnika

Na praznoj instanci prvo dovršite podešavanje vlasnika, pa tek onda uvozite pristupne podatke. Za više korisnika ili projekata mogu biti potrebna odgovarajuća dodeljivanja.

Uvezeni ID-jevi mogu prepisati postojeće stavke

Izvezeni radni tokovi i pristupni podaci zadržavaju izvorne ID-jeve. Uvoz u instancu koja već ima iste ID-jeve može zameniti postojeće stavke.

Promišljeno objavljujte uvezene radne tokove

Uvoz preko CLI-ja obično ostavlja radne tokove neaktivnim. U n8n 2.x proverite objavljeni status svakog uvezenog toka i objavite samo one koje želite pokretati. CLI za n8n sa samostalnim hostingom podržava i komandu n8n publish:workflow --id=YOUR_WORKFLOW_ID. Dok n8n radi, izmene statusa objavljivanja preko CLI-ja stupaju na snagu tek nakon ponovnog pokretanja n8n. Ponovo ga pokrenite pre provere zakazanih okidača, produkcionih veb-hukova ili preusmeravanja saobraćaja.

Primer grupnog izvoza pomoću Docker Compose: ako se vaš n8n servis zove n8n, možete pokrenuti zvanične CLI komande za pravljenje kopija. Izlaz se namerno čuva u montiranoj, trajnoj .n8n fascikli, jer proizvoljne putanje u kontejneru mogu nestati pri njegovom ponovnom kreiranju. Proverite da korisnik n8n u kontejneru ima dozvolu za upis. JSON datoteke radnih tokova i pristupnih podataka čuvajte u odvojenim fasciklama. n8n opisuje problem pri uvozu kada su obe vrste u istoj fascikli.

n8n 2.x: kopija nacrta naspram objavljene verzije: uobičajen --backup izvoz radnih tokova obuhvata trenutne nacrte, koji se mogu razlikovati od verzija objavljenih u produkciji. Da biste sačuvali stvarnu objavljenu verziju određenog toka, izvezite je zasebno komandom docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.jsonnakon što proverite da izlazna fascikla postoji i da se u nju može upisivati. CLI može izvesti i istorijsku verziju pomoću --version=VERSION_ID. Te kopije čuvajte van servera uz potpunu rezervnu kopiju. Nemojte pretpostavljati da JSON nacrta predstavlja verziju koja se izvršava u produkciji.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Kopirana ~/n8n-recovery/cli fascikla ostaje na VPS-u dok je ne premestite u bezbedno i nezavisno skladište. Izvoz pristupnih podataka je po pravilu šifrovan i za uvoz traži isti ključ. Izbegavajte komandu --decrypted osim za strogo kontrolisanu migraciju: ona zapisuje tajne u običnom tekstu. Nikada ne postavljajte izvoze sa osetljivom logikom ili pristupnim podacima u javni GitHub repozitorijum. Neki šabloni trećih strana za rezervne kopije na GitHub namerno izvoze dešifrovane tajne. Privatni repozitorijum ograničava pristup, ali nije šifrovanje. Proverite stvarna podešavanja izvoza i pristupa svakog šablona, šifrujte tajne pre slanja van servera i zamenite podatke koji su slučajno objavljeni kao običan tekst.

Primer grupnog uvoza: na čistom odredištu dovršite podešavanje vlasnika, unesite originalni ključ za šifrovanje i proverite da su datoteke kopije dostupne na VPS-u za oporavak. Sledeći postupak pravi odredišnu fasciklu i kopira workflows/ i credentials/ poddirektorijume sa servera u n8n kontejner. Ako raspored Docker volumena nije isti, prilagodite putanje:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Proverite vlasništvo i dozvole za korisnika n8n u kontejneru. Nemojte uvoziti u produkcionu instancu sa postojećim podacima bez potvrđenog plana za povratak, jer ID-jevi tokova i pristupnih podataka mogu prepisati zapise. Zatim pokrenite:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Uvezeni ID-jevi mogu zameniti postojeće tokove ili pristupne podatke. Probni uvoz uradite na izolovanoj instanci i zatim proverite podatke i status aktiviranja i objavljivanja. U n8n 2.x vraćanje JSON nacrta ne dokazuje da je radni tok objavljen i spreman za zakazane okidače. Bezbedan uvoz: na n8n instanci bez multi-main režima ranije aktivni cron okidači mogu nastaviti da rade posle CLI uvoza do ponovnog pokretanja instance. Zaustavite ili izolujte produkcione okidače i ponovo pokrenite n8n pre aktiviranja vraćenih zadataka. Proverite da ne dolazi do duplih izvršavanja. CLI izvozi ne sadrže originalne korisnike, logove izvršavanja, promenljive instance ili ključ za šifrovanje. --backup podešava --all --pretty --separate, a ne potpunu instancu. Izvori: aktuelni zvanični n8n vodič za rezervne kopije i oporavak i referenca CLI komandi.

Grupno vraćanje pomoću GitHub ili Google Drive šablona: ovo je alternativa samo za JSON radnih tokova, ne za bazu instance, korisnike, šifrovane pristupne podatke ili ključ. Pre pokretanja šablona zasnovanog na API-ju proverite n8n API i dozvole skladišta, verziju kopije i odredišnu instancu, da li ažurira iste ID-jeve i vraća obrisane tokove i kako objavljuje tokove. Ne kreira svaki šablon ID koji nedostaje na odredištu. To testirajte odvojeno pre oslanjanja na automatski oporavak.

ČESTA PITANJA

Rezervne kopije i vraćanje n8n: česta pitanja

Da li je izvoz radnih tokova dovoljan za n8n rezervnu kopiju?

Ne. Izvozi radnih tokova korisne su logičke kopije, ali potpun oporavak može zahtevati i pristupne podatke, isti ključ za šifrovanje, stanje baze, trajne datoteke i skladište binarnih podataka.

Da li mi treba n8n ključ za šifrovanje ako imam bazu?

Da, ako šifrovani pristupni podaci iz te baze treba da ostanu upotrebljivi. Originalni ključ čuvajte bezbedno.

Da li da sačuvam PostgreSQL bazu ili da izvezem tokove i pristupne podatke?

Za oporavak posle otkaza sačuvajte bazu i ključ za šifrovanje. Logički izvozi su korisni za migraciju i selektivno vraćanje, ali nisu zamena za celu instancu.

Da li VPS snapshot može biti moja jedina rezervna kopija?

Bolje ga koristite kao jedan od slojeva zaštite. Sačuvajte nezavisnu kopiju van VPS-a da kvar provajdera, naloga, servera ili snapshota ne ukloni sve tačke oporavka odjednom.

Kako da proverim da li rezervna kopija funkcioniše?

Vratite je u čisto probno okruženje, proverite dešifrovanje pristupnih podataka i pokrenite reprezentativne radne tokove. Uspešan zadatak izrade kopije sam po sebi ne dokazuje mogućnost oporavka.

Da li rezervne kopije radnih tokova na GitHub ili Google Drive uključuju tajne iz pristupnih podataka?

JSON kopije koje sadrže samo radne tokove ne uključuju tajne vrednosti kojima upravlja n8n skladište pristupnih podataka niti ključ instance. Međutim, izvezeni JSON može otkriti nazive i ID-jeve pristupnih podataka i tajne unete direktno u parametre čvorova, na primer HTTP zaglavlja za autentifikaciju. Proverite i zaštitite JSON pre slanja ili deljenja. Za potpun oporavak sačuvajte bazu i originalni ključ ili koristite podržan šifrovani CLI izvoz pristupnih podataka uz test vraćanja. Šablon koji čuva samo tokove na GitHub ili Google Drive nije potpun oporavak od katastrofe.

CILJEVI OPORAVKA

Odredite RPO i RTO pre incidenta

RPO je najveći prihvatljiv gubitak najnovijih izmena. Merite ga prema najnovijoj upotrebljivoj tački oporavka sačuvanoj nezavisno od servera. Zakazano pravljenje kopija svakih šest sati ne garantuje RPO od šest sati ako izvoz ili prenos nisu uspeli. RTO je najveće prihvatljivo vreme prekida. Merite ga tokom vraćanja u čisto probno okruženje i uključite preuzimanje tajni, vraćanje spoljnih datoteka, proveru pristupnih podataka i objavljivanje vraćenih tokova, a ne samo pokretanje kontejnera.

KLJUČ ZA OPORAVAK

Pronađite originalni ključ za šifrovanje pre ponovne instalacije

Ako je produkcija koristila N8N_ENCRYPTION_KEY, sačuvajte potpuno istu vrednost promenljive. Ako nije, sačuvajte generisani ključ iz originalne trajne .n8n/config datoteke. Pre uvoza šifrovanih pristupnih podataka proverite odakle vraćena instanca učitava ključ. Novi generisani ključ ne može dešifrovati pristupne podatke stare baze.
