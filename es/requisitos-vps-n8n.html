REQUISITOS DEL SERVIDOR

Requisitos de VPS para n8n

Para definir los requisitos de VPS de n8n, parte de tu carga de trabajo y no de un mínimo universal de hardware. Un VPS de 1 vCPU / 1 GB bien dimensionado puede ejecutar automatizaciones pequeñas siempre activas, mientras que 2 vCPU / 4 GB RAM es una clase inicial práctica para n8n con PostgreSQL y HTTPS. Los payloads grandes, ejecuciones simultáneas y procesamiento local requieren más margen; mide el uso real antes de elegir.

REQUISITOS RÁPIDOS

Mínimo, producción práctica y cargas más pesadas

Instancia ligera siempre activa

1 vCPU · 1–2 GB RAM

Un VPS real de 1 GB puede ejecutar workflows continuos y ligeros de n8n con límites cuidadosos cuando se verifica el margen de memoria y disco. La clase de 2 GB deja más espacio para Docker, pequeñas ráfagas y otros servicios. Ninguna cifra garantiza un número concreto de workflows.

Producción pequeña práctica

2 vCPU · 4 GB RAM

Una clase inicial equilibrada cuando n8n comparte el VPS con PostgreSQL, Docker y reverse proxy. Deja margen para ejecuciones solapadas y mantenimiento.

Carga pesada o intensiva en datos

4+ vCPU · 8 GB+ RAM

JSON grandes, archivos binarios, nodos Code, trabajo con navegador y muchas ejecuciones solapadas pueden justificar bastante más CPU y memoria.

Almacenamiento

SSD / NVMe con margen de crecimiento

La capacidad depende del crecimiento de PostgreSQL, retención de ejecuciones, datos binarios, logs, capas Docker y estrategia de copias, no solo de n8n.

MÍNIMO FRENTE A CAPACIDAD PRÁCTICA

¿Tiene n8n un tamaño mínimo oficial de VPS?

No para todas las cargas. Los ejemplos oficiales de requisitos previos de n8n describen un despliegue OEM ilustrativo y advierten explícitamente de que los requisitos varían según la carga. Esa documentación no garantiza universalmente que una asignación concreta de CPU, RAM o disco soporte automatizaciones de producción.

n8n indica que una instancia inactiva puede usar relativamente poca memoria, pero un nodo Code, un payload binario grande o ejecuciones simultáneas pueden aumentar mucho la demanda de memoria. Presupuesta aparte el sistema operativo, Docker, PostgreSQL y herramientas de copias/monitorización.

Fuentes técnicas: requisitos ilustrativos de n8n y guía oficial de memoria. Las cuatro filas anteriores son paquetes reales de recursos disponibles para compra, no requisitos oficiales prescritos por n8n.

RAM Y CPU

Qué consume realmente los recursos del servidor

Ejecuciones simultáneas

Varios workflows ejecutándose a la vez pueden importar más que el número total almacenado en n8n. Vigila picos de memoria y latencia de ejecución durante el solapamiento.

Tamaño del payload

Objetos JSON grandes, archivos y datos binarios aumentan la presión de memoria. Unas pocas ejecuciones intensivas en datos pueden requerir más RAM que muchas automatizaciones API ligeras.

Nodos intensivos en CPU

Code, transformaciones y otros pasos intensivos en cómputo pueden crear presión sostenida de CPU. Más núcleos ayudan cuando las ejecuciones compiten realmente por cómputo.

Servicios auxiliares

El sistema operativo, PostgreSQL, reverse proxy, monitorización y Docker también necesitan recursos. Dimensiona el stack completo, no solo el proceso n8n.

MIDE ANTES DE AMPLIAR

Cómo saber si n8n necesita más RAM, CPU o disco

Ejecuta el workflow más grande que esperes y una ráfaga realista de solapamiento; después inspecciona el servidor y los logs de ejecución de n8n. El número de workflows guardados en el editor por sí solo no es un benchmark útil de capacidad.

Memoria / OOM

Comprueba docker stats --no-stream y free -h. Si se agota la memoria, reduce primero payloads JSON o binarios, procesa importaciones grandes por lotes y evita pasos Code intensivos en memoria. Un error de heap de JavaScript no se soluciona necesariamente añadiendo vCPUs.

CPU / concurrencia

Mide si la CPU permanece ocupada durante transformaciones o si las tareas solo esperan APIs externas. En modo normal, considera un límite compatible de concurrencia de producción antes de escalar a workers. Aumentar CPU no acelera una API externa limitada por tasa.

Almacenamiento / base

Comprueba df -h, el tamaño de la base y el historial de ejecuciones conservado. Vigila el crecimiento del disco y las operaciones lentas de la base. Define la retención antes de pagar un disco mayor; conserva las copias de recuperación fuera del servidor.

Usa la guía de concurrencia de n8n y la explicación oficial de benchmarks. Cualquier cifra anunciada de workflows simultáneos sin conocer payloads y latencia de API es solo una estimación.

BASE DE DATOS Y ALMACENAMIENTO

SQLite, PostgreSQL y datos persistentes

SQLite

SQLite puede encajar en despliegues pequeños de una sola instancia y pruebas. Al crecer el uso en producción y la concurrencia, la elección de base se convierte en una restricción operativa y no en un detalle de instalación.

PostgreSQL

Para un stack VPS orientado a producción, PostgreSQL ofrece una base más sólida. Presupuesta RAM, CPU y disco para la propia base y monitoriza su crecimiento.

Datos persistentes de .n8n

No trates PostgreSQL como el único recurso persistente. Conserva el directorio de datos de n8n y protege la clave de cifrado necesaria para recuperar credenciales cifradas.

Crecimiento del disco

Historial de ejecuciones, datos binarios, archivos de base y logs pueden crecer con el tiempo. La retención y las copias fuera del servidor afectan directamente a la capacidad necesaria.

CAPACIDAD DE DISCO

Estima el almacenamiento del historial de n8n antes de pedir

Empieza con ejecuciones guardadas por día × bytes medios almacenados por ejecución × días de retención. Por ejemplo, 500 ejecuciones guardadas al día × 200 KB cada una × 14 días = 1.4 GB de datos de ejecución de ejemplo antes del overhead de la base. La suposición de 200 KB es ilustrativa, no un benchmark de n8n.

Reserva también disco para el SO, capas de imágenes Docker, índices de base, archivos binarios, logs de aplicación, actualizaciones y archivos temporales. Las copias fuera del servidor necesitan capacidad propia. Un disco de 10 GB puede servir para un stack ligero, pero deja mucho menos margen para archivos retenidos que uno de 40 u 80 GB.

n8n documenta el pruning predeterminado por antigüedad (336 horas / 14 días) o cantidad (10,000 ejecuciones), con excepciones. Comprueba tus ajustes reales y qué se conserva antes de cambiarlos. SQLite puede reutilizar espacio liberado en lugar de reducir automáticamente el archivo.

Fuente: n8n: gestión de datos de ejecución y pruning. Los requisitos de disco dependen de los tamaños observados de payloads guardados, no solo del número de nodos.

REQUISITOS DEL SISTEMA

Docker y overhead de producción

VPS Linux

Usa una distribución Linux mantenida con recursos suficientes para el sistema operativo y actualizaciones de seguridad además del stack de aplicación.

Docker y Compose

El despliegue en contenedores simplifica la repetibilidad pero no elimina el overhead de recursos. Mantén persistentes los datos de n8n y la base fuera de contenedores desechables.

HTTPS y reverse proxy

Los webhooks públicos requieren un hostname estable y HTTPS bien configurado. Incluye reverse proxy y la capa TLS en el diseño de producción.

Monitorización y copias

Controla RAM, CPU, disco y crecimiento de base. Mantén copias recuperables fuera del VPS y prueba restauración en lugar de suponer que un snapshot basta.

CONCURRENCIA

Cuando un VPS mayor deja de ser toda la solución

El escalado vertical es adecuado mientras una instancia pueda manejar la carga correctamente. Cuando la demanda paralela sostenida crea contención, evalúa modo cola y workers. El modo cola introduce Redis, PostgreSQL y uno o más workers; presupuesta RAM y CPU para cada componente, no solo n8n. n8n también documenta restricciones sobre almacenamiento binario en sistema de archivos en modo cola, así que valida un diseño de almacenamiento compatible antes de cambiar.

Leer la guía de modo cola y workers

Mantén una sola instanciaCuando CPU, RAM y latencia siguen cómodos bajo el solapamiento máximo.
Escala verticalmenteCuando la presión sostenida de CPU o memoria sea el factor limitante y la arquitectura siga siendo simple.
Considera modo colaCuando la demanda paralela medida justifique Redis y workers separados.
Revisa de nuevo el almacenamientoCuando el historial de ejecuciones, binarios o crecimiento de PostgreSQL se conviertan en la limitación principal.

NIVEL DE ENTRADA Y E/S DE ALMACENAMIENTO

Cómo usar un VPS de entrada de 1 GB

1 GB RAM

Es un nivel VPS real y funcional, no un producto solo de prueba. Puede servir para automatizaciones pequeñas siempre activas y trabajo API mayormente secuencial si mantienes memoria, uso de disco y tareas simultáneas dentro de límites medidos. Ofrece poco margen para PostgreSQL en el mismo servidor, payloads grandes o ejecuciones paralelas pesadas.

2 GB RAM

Usa 2 GB como base más segura para una instancia ligera cuando quieras más margen para el sistema operativo, Docker y pequeñas ráfagas sin pasar inmediatamente a un stack de tamaño de producción.

SSD vs NVMe

Un SSD estándar basta para automatización ligera. NVMe resulta más útil cuando PostgreSQL y el historial generan lecturas/escrituras frecuentes o cuando la latencia del disco aparece en el rendimiento medido del workflow.

Mide antes de ampliar

Usa CPU, memoria, crecimiento de disco y duración de ejecución bajo solapamiento máximo para decidir si el cuello es cómputo, memoria o almacenamiento, en lugar de suponer que un VPS mayor arregla toda lentitud.

FAQ

Requisitos VPS de n8n: preguntas frecuentes

¿Cuánta RAM necesita n8n?

No hay una cifra universal. La demanda de RAM cambia con concurrencia, tamaño del payload, comportamiento de ejecución y servicios auxiliares del VPS. Un servidor de 4 GB es una clase inicial práctica para pequeña producción, no un requisito garantizado para todas las cargas.

¿Cuántos núcleos de CPU debería usar?

Las cargas ligeras pueden empezar con poca CPU. Añade núcleos cuando la monitorización muestre presión sostenida de CPU o ejecuciones más lentas bajo concurrencia, no basándote solo en el número de workflows.

¿n8n requiere PostgreSQL?

Los despliegues pequeños pueden usar SQLite, pero PostgreSQL es la opción más sólida para producción al aumentar requisitos operativos y concurrencia.

¿Cuándo se necesita Redis?

Redis está asociado al modo cola. Un despliegue normal de una sola instancia no necesita Redis solo por ejecutarse en un VPS.

¿Cuánto espacio de disco debería reservar?

La demanda de disco depende del crecimiento de PostgreSQL, historial retenido, datos binarios, logs, capas de contenedores y copias. Monitoriza el crecimiento y deja margen en lugar de depender de una cifra universal fija.

¿Puedo ejecutar n8n continuamente en un VPS de 1 GB?

Sí, cuando la carga real encaja. Un VPS de 1 GB es un servidor real y puede soportar automatizaciones pequeñas y mayormente secuenciales, pero el margen de memoria es limitado. No supongas que cabrán PostgreSQL en el mismo servidor, tareas intensivas en binarios o varias ejecuciones grandes simultáneas. Monitoriza consumo y amplía según la presión observada.

¿Son mejores 2 GB o 4 GB RAM para un VPS n8n de producción?

Dos gigabytes dan más margen que una instancia ligera de 1 GB, mientras que 4 GB es una clase inicial práctica para evaluar n8n junto a PostgreSQL y HTTPS. No existe un mínimo universal garantizado de producción: la complejidad de carga, solapamiento máximo, configuración de contenedores y datos retenidos determinan la demanda real.

¿Los workflows de IA de n8n requieren GPU?

No cuando n8n solo llama a una API externa de modelo: el proveedor gestiona la inferencia y el VPS la orquestación, payloads y concurrencia. Ejecutar modelos de inferencia localmente es otra decisión de hardware que puede requerir mucha más RAM y recursos GPU adecuados.

¿Qué causa errores de falta de memoria en n8n?

Payloads JSON o binarios grandes, operaciones Code intensivas en memoria y ejecuciones solapadas son causas comunes. Revisa logs de runtime y picos de memoria, después reduce los datos mantenidos en una ejecución o asigna más RAM según el problema medido.
