COPIAS Y RECUPERACIÓN

Copias de seguridad y restauración de n8n

Para hacer copias y restaurar n8n autoalojado, protege la base SQLite o un dump coherente de PostgreSQL, la carpeta persistente .n8n y la clave de cifrado original, la configuración del despliegue y toda dependencia externa de datos binarios o archivos montados. Guarda una copia cifrada fuera del VPS y prueba la recuperación en una instancia separada. Usa las exportaciones CLI de workflows y credenciales para recuperación selectiva; las exportaciones JSON por sí solas no son una copia completa del servidor.

LISTA RÁPIDA

Qué debe proteger una copia de n8n

Base de datos

Haz copia de la base PostgreSQL o del archivo SQLite utilizado por la instancia. La base contiene el estado esencial de n8n, como workflows, credenciales y datos de ejecución.

Clave de cifrado

Conserva exactamente la misma clave de cifrado de n8n de forma separada y segura. Las credenciales cifradas restauradas dependen de esa misma clave.

Archivos persistentes

Incluye el directorio persistente de datos de n8n y cualquier archivo montado, almacenamiento de datos binarios o recursos de workflows de los que dependa el despliegue.

Configuración del despliegue

Conserva los archivos de Compose/configuración y la configuración no secreta necesaria para reconstruir el stack. Protege los secretos con controles de acceso adecuados.

DOS NIVELES DE COPIA

Exportación lógica frente a recuperación completa ante desastres

Exportación de workflows y credenciales

Las exportaciones mediante n8n CLI son útiles para migraciones, copias versionadas de workflows y restauración selectiva. Las credenciales pueden exportarse cifradas e importarse después con la clave correspondiente. Para recuperar un solo workflow, usa el menú de tres puntos del editor para descargar su JSON y después Import from File en un workflow de revisión nuevo o una instancia aislada. Comprueba credenciales, IDs de workflow y parámetros de nodos antes de sustituir un workflow activo: restaurar el JSON del workflow no restaura todo el servidor.

Exportación de entidades

La CLI puede exportar entidades de base de datos para mover datos entre tipos de base compatibles. Las tablas del historial de ejecuciones son opcionales porque pueden ser muy grandes.

Recuperación completa de la instancia

Para un escenario de servidor perdido, protege la base de datos real, la clave de cifrado, los datos persistentes y las dependencias del despliegue. No supongas que una exportación JSON de workflows reconstruye toda la instancia.

Snapshot del proveedor

Un snapshot del VPS es útil como capa adicional de recuperación, pero no debería ser la única copia ni sustituir una copia de aplicación/base de datos verificada de forma independiente.

BASE DE DATOS

Haz una copia coherente de la base de datos

PostgreSQL

Usa un método de copia coherente de PostgreSQL y guarda el resultado fuera del VPS. Una copia de la base en el mismo disco que falla no es recuperación ante desastres.

SQLite

Si el despliegue usa SQLite, protege el archivo de base de datos del directorio persistente de n8n. Evita copiar una base en un estado inseguro mientras se modifica activamente.

Historial de ejecuciones

Decide si los datos históricos de ejecución forman parte del objetivo de recuperación. Pueden aumentar mucho el tamaño de las copias, por lo que la retención y los requisitos de cumplimiento deben guiar la decisión.

Versión de la base de datos

Registra el motor y la versión de base de datos usados por el despliegue de origen para poder preparar un entorno de recuperación compatible.

PostgreSQL en un VPS con Docker Compose. Si el servicio PostgreSQL se llama postgres y tanto la base como el usuario son n8n, el siguiente comando crea en el host un dump coherente de PostgreSQL en formato custom. Revisa tu archivo Compose real antes de ejecutarlo y ajusta credenciales de base y nombres de servicio. pg_dump puede producir un snapshot lógicamente coherente mientras PostgreSQL está en ejecución; no copia la carpeta separada .n8n del usuario ni los datos binarios externos.

# En el proyecto Docker Compose; adapta nombres de servicio, base y usuario
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Comprueba que el archivo tenga una lista de objetos legible
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

La comprobación de la lista del archivo detecta problemas evidentes de formato, pero no demuestra que los datos puedan restaurarse. Guarda una copia cifrada fuera del servidor y ensaya una restauración. Usa la documentación oficial de PostgreSQL pg_dump para opciones específicas de la base.

SQLite en Docker. En el despliegue SQLite predeterminado, database.sqlite y la configuración de la clave de cifrado generada están dentro de la carpeta persistente .n8n (normalmente montada en /home/node/.n8n). Nunca consideres coherente una simple copia en vivo de SQLite. Detén n8n y otros procesos que escriban en la base antes de copiar la carpeta, o usa el mecanismo de copia online compatible de SQLite cuando no sea posible interrumpir:

# Solo para SQLite y el montaje predeterminado /home/node/.n8n
# Detén n8n (y cualquier otro proceso de escritura) antes de copiar SQLite
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Estos comandos son ilustrativos para el servicio y la ruta mostrados, no un diseño universal de volúmenes. La carpeta copiada sigue inicialmente en el mismo VPS; transfiérela y protégela fuera del servidor. Si existen workers de cola u otros escritores, detenlos también y sigue el diseño real del despliegue. La guía actual de copia completa de n8n documenta el requisito de coherencia de SQLite.

Restauración de la carpeta SQLite predeterminada en un destino limpio: primero detén el servicio n8n y todos los procesos que escriban en la base. Cuando exista un contenedor compatible del servicio n8n y su volumen de destino, copia el contenido respaldado de .n8n contenido de vuelta al mismo directorio persistente. Esto sobrescribe archivos de destino, así que no lo ejecutes en una instancia con datos que necesites conservar:

# Ejecuta solo en la instancia LIMPIA destinada a recuperación
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# ANTES del siguiente comando verifica propietario y permisos del usuario del contenedor n8n
# Inicia solo cuando n8n pueda leer y escribir los archivos restaurados
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker puede copiar a contenedores detenidos, pero la propiedad de los archivos en destino puede diferir; asegúrate de que la configuración restaurada y el archivo de base sean legibles y escribibles por el proceso n8n antes de arrancarlo. Si tu Compose real usa otra ruta o bind mount, adapta la copia. Referencia de copia de Docker Compose. Restaurar solo la carpeta n8n no basta en despliegues que usan una base PostgreSQL separada.

SECRETO CRÍTICO

La clave de cifrado forma parte de la recuperación

n8n cifra las credenciales almacenadas con una clave de cifrado de la instancia. Una base o exportación de credenciales cifradas sin la clave correspondiente puede dejar los workflows restaurados sin poder usar las credenciales guardadas.

Si configuraste N8N_ENCRYPTION_KEY, restaura exactamente ese secreto. En caso contrario, la clave generada está en el archivo persistente .n8n/config: protege esa configuración al hacer copias o reconstruir. Guarda las claves de recuperación de forma segura fuera del VPS. En modo cola, todos los procesos main y worker deben usar la misma clave.

HazConserva una copia protegida de la clave exacta usada en producción.
HazVerifica que el entorno de recuperación usa esa clave antes de probar credenciales.
No hagasNo dependas de una clave recién generada después de reconstruir el servidor.
No hagasNo subas la clave a un repositorio público ni la guardes junto a una copia sin proteger.

ARCHIVOS Y DATOS BINARIOS

La copia de la base puede no cubrir todas las dependencias del workflow

Datos persistentes de .n8n

Localiza y conserva la carpeta real de usuario .n8n, no solo la imagen del contenedor. En un despliegue Docker típico está montada en /home/node/.n8n; fuera de Docker, el valor predeterminado es ~/.n8n. Si se configura N8N_USER_FOLDER, n8n crea .n8n dentro de ese directorio padre. Incluye su clave de configuración y cualquier dato local SQLite, binario o de ejecuciones en sistema de archivos que use tu instalación.

Archivos de workflow montados

Si los workflows leen o escriben directorios montados desde el host, haz copia de esos directorios por separado. Restaurar n8n sin ellos puede romper workflows que por lo demás serían válidos.

Datos binarios

Identifica el modo de almacenamiento y restaura cada dependencia externa. Los datos binarios o de ejecución basados en sistema de archivos pueden estar en .n8n o en un directorio personalizado; S3/Azure Blob u otro almacenamiento externo configurado necesita su propia copia recuperable y ajustes de acceso. Un dump de la base por sí solo no sustituye esos archivos.

Nodos comunitarios

Registra paquetes comunitarios y versiones, y haz copia de cualquier directorio adicional de nodos personalizados configurado mediante N8N_CUSTOM_EXTENSIONS. Esos directorios pueden estar fuera de .n8n; restaurar solo la base y la carpeta de usuario puede dejar inutilizables los workflows con nodos personalizados.

ESTRATEGIA FUERA DEL SERVIDOR

Una copia en el mismo VPS es solo una copia local

Copia localÚtil para rollback rápido, pero vulnerable a pérdida del servidor, fallo de disco y errores destructivos.
Copia fuera del servidorConserva al menos una copia en almacenamiento independiente del VPS de producción.
Copias versionadasMantén varios puntos de recuperación para que la corrupción o un cambio incorrecto no sobrescriban la única copia utilizable.
Control de accesoLas copias pueden contener credenciales, lógica de workflows y datos empresariales sensibles. Cífralas y restringe el acceso adecuadamente.
MonitorizaciónGenera alertas cuando las copias programadas fallen o dejen de producir nuevos puntos de recuperación.

Haz que el calendario sea medible. Registra la hora de cada copia correcta, la finalización de la transferencia, tamaño del archivo, versión de la base de origen, ubicación de recuperación de la clave de cifrado y la última prueba de restauración correcta. Alerta sobre archivos ausentes, fallidos o inesperadamente vacíos. Cifra los archivos antes de enviarlos fuera del VPS y restringe el acceso a los secretos de recuperación. Varios puntos fechados protegen frente a descubrir corrupción después de que la copia más reciente haya sobrescrito la última sana.

Por ejemplo, si toleras como máximo seis horas de cambios perdidos, una copia correcta cada seis horas es un punto de partida, no una garantía: tareas fallidas y replicación retrasada fuera del servidor pueden aumentar la pérdida real. Define retención y frecuencia de restauración según tus propios RPO/RTO y requisitos de datos, no suponiendo una política universal de 7 o 30 días.

ORDEN DE RESTAURACIÓN

Recupera en una secuencia controlada

1 · PrepararPrepara un servidor, base de datos y entorno de contenedores/runtime compatibles.
2 · Restaurar secretosConfigura de forma segura la clave de cifrado original de n8n y los secretos necesarios del despliegue.
3 · Restaurar baseRecupera PostgreSQL o SQLite y verifica que n8n puede conectarse a los datos esperados.
4 · Restaurar archivosRecupera directorios persistentes, datos binarios y recursos de workflows montados.
5 · Iniciar n8nInicia la aplicación con el hostname, base de datos y configuración de entorno esperados.
6 · ValidarConfirma que cargan usuarios, workflows y credenciales; después ejecuta workflows representativos y rutas de webhook.

Ejemplo de recuperación ante desastres con PostgreSQL: en un destino de restauración separado y limpio que ya tenga el rol correcto y una base n8n vacía, inicia solo PostgreSQL. Espera a que esté listo antes de importar: docker compose up -d puede terminar mientras PostgreSQL aún se inicializa, por lo que un pg_restore posterior puede fallar. El ejemplo usa --wait en una instalación moderna de Compose y comprueba de forma independiente pg_isready. Configura un healthcheck adecuado de PostgreSQL para esperar de forma fiable o confirma explícitamente la disponibilidad antes de continuar. No ejecutes este comando contra una base de producción con datos ni inicies n8n antes de que la base y su .n8n clave/datos correspondientes estén restaurados.

# RESTAURA SOLO EN UNA BASE DE DESTINO NUEVA Y VACÍA
# Adapta nombres de servicio Postgres Compose, base y usuario
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

El destino debe tener una versión compatible de PostgreSQL, privilegios de roles, extensiones y la configuración original de n8n. Restaura .n8n en su volumen persistente o bind mount correcto mediante tu mecanismo de copia, conservando propiedad y permisos. Restaura archivos binarios externos, extensiones personalizadas, Compose y configuración de secretos; después inicia n8n en una versión compatible y revisa los logs. Restaurar solo la base no recupera la clave: un despliegue PostgreSQL guarda la clave en .n8n/config salvo que hayas configurado explícitamente N8N_ENCRYPTION_KEY. PRUEBA DE RESTAURACIÓN

Una copia no está demostrada hasta que la restauración funciona

Prueba en un entorno limpio

Una prueba real debe demostrar que la copia puede reconstruir una instancia sin depender de archivos no declarados que queden en el servidor de producción.

Comprueba credenciales

Abrir un workflow no basta. Confirma que las credenciales cifradas restauradas se descifran y autentican correctamente.

Ejecuta workflows representativos

Prueba workflows que dependan de webhooks, APIs externas, archivos montados y nodos comunitarios en lugar de validar solo una automatización trivial.

Mide el tiempo de recuperación

Registra cuánto tarda la restauración y qué pasos manuales quedan. Esto convierte una copia supuesta en un procedimiento operativo de recuperación.

Haz una prueba separada para cada dependencia que uses.

Cómo reproducirlo: usa una instalación desechable de n8n, crea un workflow inocuo de dos nodos, realiza la copia correspondiente de base y carpeta persistente, restaura en un volumen o base limpios y verifica nodos, conexiones y ejecución real del workflow restaurado. En producción, comprueba también credenciales cifradas, webhooks y archivos externos antes de considerar demostrada la recuperación.

Lista de aceptación de la prueba de restauración: usa un dominio/entorno aislado; comprueba que usuarios y workflows existen, que al menos una credencial cifrada existente autentica sin volver a introducirla, que un webhook de producción llama al workflow restaurado correcto, que los archivos montados y adjuntos binarios siguen siendo legibles y que cargan las integraciones con nodos comunitarios necesarios. Confirma antigüedad de la copia, downtime medido y accesibilidad fuera del servidor. Si falla una comprobación esencial, marca ese punto como no verificado en lugar de informar de la copia como completa.

LÍMITES DE LAS COPIAS CLI

Conoce exactamente qué no restauran las exportaciones de workflows y credenciales

Las exportaciones CLI no son una copia completa de la instancia

Las exportaciones de copia de workflows y credenciales no incluyen usuarios y roles, historial y logs de ejecuciones, variables ni ajustes de instancia como la clave de cifrado.

Restaurar en una instancia nueva requiere un owner

En una instancia limpia, completa la configuración del owner antes de importar credenciales. Las restauraciones multiusuario o de proyectos también pueden necesitar la asignación correcta de usuario o proyecto.

Los IDs importados pueden sobrescribir elementos existentes

Las exportaciones de workflows y credenciales conservan sus IDs originales. Importar en una instancia que ya contiene esos mismos IDs puede sustituir los elementos existentes.

Publica conscientemente los workflows importados

Las importaciones CLI normalmente dejan los workflows inactivos. En n8n 2.x, comprueba el estado publicado de cada workflow importado y publica solo los que pretendas ejecutar; la Server CLI autoalojada también admite n8n publish:workflow --id=YOUR_WORKFLOW_ID. Cuando n8n está en ejecución, los cambios publish/unpublish mediante Server CLI solo tienen efecto tras reiniciar n8n. Reinicia antes de verificar triggers programados y webhooks de producción o de cambiar el tráfico.

Ejemplo de exportación masiva para Docker Compose: si tu servicio n8n se llama n8npuedes ejecutar las copias oficiales CLI siguientes. La ruta de salida se coloca deliberadamente dentro de su directorio persistente montado .n8n porque los directorios arbitrarios dentro de un contenedor pueden desaparecer al recrearlo. Confirma que el directorio es escribible por el usuario del contenedor n8n. Guarda los JSON de workflows y credenciales en directorios separados—n8n documenta un problema de importación cuando ambos tipos comparten directorio.

n8n 2.x: copia de borrador frente a versión publicada: una exportación normal --backup de workflow captura los borradores actuales; pueden diferir de las versiones publicadas en producción. Para conservar la versión realmente publicada de un workflow concreto, expórtala por separado usando docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, tras asegurarte de que la carpeta de salida existe y es escribible. La CLI también puede exportar una versión histórica usando --version=VERSION_ID. Guarda estas capturas fuera del servidor junto a la copia completa; no supongas que el JSON del borrador representa el estado publicado en vivo.

# Ejecuta desde tu proyecto Docker Compose; el servicio n8n debe existir
# Guarda las copias de workflows y credenciales en carpetas DIFERENTES
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copia los directorios exportados FUERA del contenedor al host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

El directorio copiado ~/n8n-recovery/cli sigue en el VPS hasta que lo muevas a una ubicación de copia independiente y segura. La exportación de credenciales está cifrada por defecto y necesita la clave correspondiente al importar. Evita usar --decrypted salvo para una migración estrictamente controlada: escribe secretos en texto plano. Nunca subas exportaciones que contengan lógica sensible de workflows o credenciales a un repositorio público de GitHub. Algunas plantillas externas de copia de credenciales en GitHub exportan deliberadamente secretos descifrados; un repositorio privado restringe acceso, no cifra. Revisa la configuración real de exportación y permisos de almacenamiento de cada plantilla, cifra secretos antes de transferirlos fuera del servidor y rota cualquier credencial expuesta mediante una subida accidental en texto plano.

Ejemplo de importación masiva: en un destino limpio, completa la configuración del owner, proporciona la clave de cifrado original y asegúrate de que los archivos de copia estén disponibles en ese VPS de recuperación. Lo siguiente crea la carpeta de destino y copia las subcarpetas workflows/ y credentials/ desde el host al contenedor n8n; adapta las rutas si tu diseño de volúmenes Docker es distinto:

# Ejecuta solo en la instancia LIMPIA destinada a recuperación
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Comprueba propiedad y acceso de archivos para el usuario del contenedor n8n. No importes sobre una instancia de producción con datos sin un rollback verificado: los IDs de workflows y credenciales pueden sobrescribir entradas existentes. Después ejecuta:

# Tras configurar el owner de la instancia nueva Y proporcionar la clave correcta
# Copia de nuevo el contenido cli/ guardado a .n8n/backups/ del servicio n8n de destino
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Los IDs importados pueden sustituir workflows o credenciales existentes; usa una instancia aislada para pruebas y después comprueba credenciales y estados de activación/publicación. En n8n 2.x, restaurar el JSON del borrador no demuestra por sí solo que un workflow esté publicado y pueda ejecutar triggers programados. Seguridad de la importación: en una instancia n8n sin multi-main, triggers cron previamente activos pueden seguir ejecutándose después de importar por CLI hasta reiniciar la instancia. Detén o aísla triggers de producción y reinicia n8n antes de habilitar tareas restauradas; verifica que no haya ejecuciones duplicadas. Las exportaciones CLI no no contienen usuarios originales, logs de ejecución, variables de instancia ni la clave de cifrado. --backup configura --all --pretty --separate, no «instancia completa». Fuentes: guía oficial actual de copia/restauración de n8n y referencia de comandos n8n CLI.

Restauración masiva desde plantillas de GitHub o Google Drive: esto es una alternativa solo para JSON de workflows, no para la base de la instancia, usuarios, valores cifrados de credenciales o clave de cifrado. Antes de ejecutar una plantilla basada en API, verifica sus permisos de API n8n y almacenamiento, la versión de copia seleccionada y la instancia de destino, si actualiza IDs coincidentes y recrea workflows eliminados, y qué hace con la publicación. No todas las plantillas recrean un ID ausente en destino; prueba ese escenario de forma aislada antes de depender de restauración automática.

FAQ

Copias y restauración de n8n: preguntas frecuentes

¿Exportar workflows basta para hacer copia de n8n?

No. Las exportaciones de workflows son copias lógicas útiles, pero la recuperación completa también puede necesitar credenciales, la clave de cifrado correspondiente, estado de la base, archivos persistentes y almacenamiento de datos binarios.

¿Necesito la clave de cifrado de n8n si tengo la base?

Sí, si necesitas que las credenciales cifradas de esa base sigan siendo utilizables. Conserva de forma segura la clave original.

¿Debo copiar PostgreSQL o exportar workflows y credenciales?

Para recuperación ante desastres, protege la base y la clave de cifrado. Las exportaciones lógicas son una capa adicional útil para migración y recuperación selectiva, no un sustituto de todas las partes de la instancia.

¿Puede un snapshot del VPS ser mi única copia?

Es mejor tratarlo como una capa de recuperación. Mantén una copia independiente fuera del servidor para que un fallo del proveedor, cuenta, servidor o snapshot no elimine todos los puntos a la vez.

¿Cómo sé si mi copia funciona?

Restáurala en un entorno de prueba limpio, verifica que las credenciales se descifren y ejecuta workflows representativos. Que una tarea de copia termine correctamente no demuestra recuperabilidad.

¿Las copias de workflows en GitHub o Google Drive incluyen secretos de credenciales guardadas?

Las copias JSON solo de workflows no incluyen los valores secretos gestionados por el almacén de credenciales de n8n ni la clave de cifrado de la instancia. Sin embargo, el JSON exportado puede exponer nombres e IDs de credenciales y secretos escritos directamente en parámetros de nodos, como cabeceras de autenticación. Revisa y protege el JSON antes de subirlo o compartirlo. Para recuperación completa, copia la base y la clave original o usa exportaciones CLI cifradas de credenciales con restauración probada. Una plantilla de GitHub o Google Drive solo de workflows no es recuperación completa.

OBJETIVOS DE RECUPERACIÓN

Define RPO y RTO antes de un incidente

RPO es la pérdida máxima tolerable de cambios recientes. Mídelo desde el punto de recuperación utilizable más nuevo almacenado de forma independiente; una tarea programada cada seis horas no establece un RPO de seis horas si fallaron exportaciones o transferencias. RTO es la interrupción máxima tolerable. Mídela en una prueba limpia de restauración, incluyendo recuperación de secretos, archivos externos, nueva comprobación de credenciales y publicación de workflows recuperados, no solo arrancando un contenedor.

CLAVE DE RECUPERACIÓN

Encuentra la clave de cifrado original antes de reconstruir

Si producción configuró N8N_ENCRYPTION_KEY, conserva exactamente ese secreto de entorno. Si no, conserva la clave generada en el .n8n/config persistente original. Comprueba qué fuente usa realmente la instancia recuperada antes de importar credenciales cifradas; una clave nueva no puede descifrar las credenciales de la base antigua.
