SEGURIDAD EN PRODUCCIÓN

Proteger n8n en un VPS

Para proteger n8n en un VPS, mantén n8n (5678), PostgreSQL (5432) y el Redis opcional (6379) fuera de Internet público; usa reverse proxy HTTPS, claves SSH y MFA, conserva la clave de cifrado, autentica webhooks, limita capacidades de riesgo de los workflows y audita la instancia desplegada. Protege el editor por separado de las rutas públicas de webhook. HTTPS por sí solo no protege los servicios conectados.

LISTA RÁPIDA

Base mínima de seguridad antes de la exposición pública

Empieza por los puertos accesibles, HTTPS, acceso administrativo verificado, MFA y protección de credenciales guardadas. Autentica cada webhook entrante antes de que pueda activar acciones sensibles. Después de cambiar controles de acceso, verifica que los editores autorizados y las integraciones externas sigan funcionando y ejecuta la auditoría de seguridad de n8n.

Solo HTTPS

Coloca n8n detrás de un reverse proxy TLS bien configurado y usa de forma coherente la URL HTTPS pública para editor y webhooks.

Mínimo de puertos abiertos

Expón solo los puertos necesarios para tráfico público. Mantén PostgreSQL, Redis y los puertos internos de la aplicación fuera de Internet público.

Refuerza SSH

Administra mediante claves, limita quién puede iniciar sesión y mantén el sistema operativo actualizado.

Protege las credenciales

Mantén estable y secreta la clave de cifrado de n8n. Trata archivos de entorno, acceso a base y copias como activos sensibles.

BORDE DE RED

Reverse proxy, HTTPS y cabeceras de confianza

Terminación TLS

Usa un reverse proxy como Nginx, Caddy o Traefik para terminar HTTPS. Redirige HTTP simple y evita exponer directamente el puerto de la aplicación n8n cuando el proxy sea el punto de entrada previsto.

Configuración del proxy

Cuando n8n está detrás de reverse proxy, configura correctamente el número de saltos y pasa las cabeceras reenviadas que n8n necesita para reconstruir la solicitud original del cliente.

Cookies seguras

Sirve el editor mediante HTTPS para mantener seguras las cookies de autenticación. No soluciones una configuración TLS rota debilitando la seguridad de las cookies.

URL del webhook

Configura la URL pública de webhook con el hostname HTTPS accesible externamente para que los endpoints generados no apunten a un contenedor interno o una dirección HTTP.

Mantén privado el editor sin romper los webhooks. Restringe el acceso de gestión mediante VPN, política de IPs de confianza o proxy autenticado cuando sea práctico. Los receptores públicos de webhooks y callbacks OAuth pueden necesitar seguir accesibles; prueba tanto el acceso de un editor de confianza como un callback externo real antes de aplicar una regla de proxy. Reenvía cabeceras de dirección del cliente solo desde proxies de confianza, no desde cabeceras arbitrarias.

Autentica a quienes llaman los webhooks: en el nodo Webhook elige autenticación Basic, Header o JWT en lugar de None cuando el emisor lo permita. Usa su opción IP(s) Allowlist cuando corresponda y verifica las firmas del proveedor si la integración admite solicitudes firmadas. Una URL difícil de adivinar no es autenticación suficiente. Aplica límites de tasa en el proxy cuando proceda y confirma que las ráfagas válidas no se bloqueen. Opciones oficiales de autenticación Webhook.

REFUERZO DEL VPS

Reduce la superficie de ataque del servidor

Firewall

Deniega por defecto el tráfico entrante no solicitado y permite solo los servicios que deban ser accesibles. Los puertos de base y Redis normalmente deben estar en redes privadas/locales.

SSH

Prefiere claves SSH frente a contraseñas, desactiva vías de acceso innecesarias y limita el acceso administrativo. El acceso equivalente a root debe estar muy controlado.

Actualizaciones del sistema

Actualiza el host Linux y el runtime de contenedores. Reforzar la aplicación no compensa un sistema operativo expuesto u obsoleto.

Exposición de contenedores

Publica solo los puertos que necesiten acceso desde el host. Los servicios internos deben comunicarse por redes Docker privadas y no por interfaces públicas.

Inspecciona antes de cambiar firewall o SSH: comprueba los puertos en escucha con sudo ss -lntp, la publicación de Docker con docker compose ps desde el directorio del proyecto y la política de firewall del host con sudo ufw status verbose si usas UFW. Verifica el puerto SSH real y un inicio de sesión correcto con clave en una sesión separada antes de desactivar contraseñas. Los puertos publicados por Docker pueden saltarse reglas UFW; la página de estado del firewall por sí sola no demuestra que el puerto 5678 sea privado. Comprueba la accesibilidad externa real. Limitación Docker/UFW.

Comprueba las actualizaciones automáticas de seguridad de Ubuntu en vez de suponer que funcionan: inspecciona apt-config dump APT::Periodic::Unattended-Upgrade y el log /var/log/unattended-upgrades/unattended-upgrades.log. Si las actualizaciones desatendidas de seguridad están desactivadas, sudo dpkg-reconfigure unattended-upgrades ofrece un diálogo de configuración compatible. Revisa el comportamiento de reinicios del sistema y servicios antes de activarlo en un VPS operativo. Las actualizaciones APT de Ubuntu no actualizan automáticamente la imagen Docker de n8n ni todos los repositorios de software de terceros. Documentación de actualizaciones automáticas de Ubuntu.

Monitorización opcional de fuerza bruta SSH: Fail2Ban puede detectar intentos repetidos fallidos de SSH. Si está instalado y configurado para SSH, verifica la jail con sudo fail2ban-client status sshd y confirma que lee el log o journal real de autenticación SSH y coincide con el puerto configurado. Complementa claves SSH y restricciones de red; no las sustituye. No copies un puerto SSH fijo ni una regla de bloqueo sin comprobar primero el acceso existente. Guía de refuerzo SSH de Ubuntu.

BASE DE DATOS Y REDIS

Mantén privados los servicios backend

En una configuración típica Docker Compose, PostgreSQL y Redis de modo cola deben ser accesibles para los contenedores relevantes mediante red privada, no puertos publicados en el host. Verifica con docker compose ps que 5432 y 6379 no estén publicados públicamente; revisa aparte la exposición del firewall VPS/cloud. Las políticas de red no sustituyen credenciales de base con mínimo privilegio.

PostgreSQLVincúlalo a una interfaz privada o red de contenedores salvo que el acceso remoto sea explícitamente necesario y esté protegido por separado.
RedisRedis de modo cola es infraestructura, no un endpoint público. Restringe el acceso de red a los componentes n8n que lo necesiten.
CredencialesUsa credenciales dedicadas de base con solo los permisos necesarios para la aplicación y protégelas fuera del control de versiones.
TransporteCuando el tráfico de base atraviese redes no confiables, usa transporte cifrado adecuado en lugar de depender del cifrado de credenciales a nivel de aplicación.

SECRETOS DE N8N

Protege la clave de cifrado y el límite de credenciales

Clave de cifrado

n8n cifra las credenciales almacenadas usando su clave de cifrado. Conserva la misma clave entre reinicios y workers y protégela por separado del contenido normal de la aplicación.

Secretos de entorno

No subas contraseñas, tokens ni la clave de cifrado a un repositorio público. Restringe el acceso a archivos de entorno y secretos del despliegue.

Acceso de usuarios

Da acceso al editor solo a usuarios de confianza. Los workflows pueden conectarse a sistemas sensibles, procesar secretos o ejecutar nodos potentes.

Alcance de credenciales

Usa cuentas de servicio y tokens API con alcance reducido cuando sea posible. Un workflow comprometido no debería heredar automáticamente acceso amplio a sistemas no relacionados.

Configuración de n8n que revisar: N8N_BLOCK_ENV_ACCESS_IN_NODE=true impide que el nodo Code y las expresiones accedan a valores del entorno; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true solicita permisos solo para el propietario en el archivo de ajustes. Mantén N8N_ENCRYPTION_KEY persistente y con copia segura: n8n puede crear una clave aleatoria en el primer inicio, pero perderla puede volver inutilizables las credenciales cifradas existentes. No sustituyas una clave de producción a la ligera; usa un procedimiento oficial de rotación. Bloquear el acceso al entorno puede romper integraciones existentes, así que prueba antes de cambios en producción. Definiciones de variables de seguridad de n8n.

RIESGO DE WORKFLOWS

Los nodos pueden ampliar el límite de seguridad

El autoalojamiento da a los workflows bastante poder. La ejecución de código, acceso a shell, solicitudes HTTP arbitrarias y nodos comunitarios de terceros pueden aumentar el riesgo. Desactiva lo que no necesites y revisa importaciones de workflows no confiables antes de ejecutarlas.

Usa exactamente los controles compatibles: configura NODES_EXCLUDE con un array JSON de nodos que desactivar, como n8n-nodes-base.executeCommand and n8n-nodes-base.readWriteFile, si no los usas. Algunos nodos de alto riesgo ya están bloqueados por defecto en versiones recientes; revisa la lista real antes de cambiarla. Exclusiones oficiales de nodos.

En n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true activa comprobaciones para solicitudes HTTP salientes a rangos internos, loopback y direcciones de metadata. Workflows legítimos con APIs internas pueden dejar de funcionar; si es necesario, añade a allowlist solo destinos concretos que controles. Mantén la segmentación de red como defensa principal. Para aislar nodos Code, revisa task runners externos. Protección SSRF · Aislamiento de task runner.

Nodos comunitariosInstala solo paquetes en los que confíes; se ejecutan dentro de tu entorno n8n.
Nodos de riesgoExcluye nodos que tu despliegue no necesite cuando sus capacidades superen el límite previsto del workflow.
SSRFUsa la protección SSRF de n8n y controles de red cuando los workflows no deban poder alcanzar endpoints internos o de metadata.
Importaciones de workflowsRevisa workflows importados, credenciales, expresiones y pasos ejecutables antes de activarlos.

AUDITORÍA Y ACTUALIZACIONES

La seguridad es un proceso operativo

Ejecuta la auditoría de seguridad de n8n

El comando CLI oficial es n8n audit. Si tu servicio Docker Compose se llama n8n, ejecuta docker compose exec -T n8n n8n audit en el directorio del despliegue. Revisa las cinco categorías: credenciales no usadas, patrones SQL de riesgo, acceso al sistema de archivos, nodos de riesgo/comunitarios y riesgos de instancia, incluidos webhooks sin protección y versiones desactualizadas. Corrige hallazgos relevantes y vuelve a ejecutar. No es una prueba de penetración. Guía oficial de auditoría.

Actualiza deliberadamente

Mantén n8n suficientemente actualizado para recibir correcciones de seguridad. Revisa notas de versión y prueba actualizaciones importantes en vez de dejar una instancia expuesta a Internet permanentemente obsoleta.

Monitoriza la autenticación

Vigila patrones de acceso inesperados, cambios en workflows y fallos. Restringe más la interfaz del editor si tu modelo operativo no requiere amplia accesibilidad pública.

Prepara rollback y recuperación

Haz copias recuperables antes de actualizaciones importantes. El alcance detallado de copias y restauración pertenece a la guía separada de recuperación.

Minimiza el historial sensible de ejecuciones: las ejecuciones correctas pueden conservar datos de clientes y tokens. Cuando corresponda, configura EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, mantén EXECUTIONS_DATA_PRUNE=true, y elige un EXECUTIONS_DATA_MAX_AGE en horas, por ejemplo 168 (siete días). Son ejemplos configurables, no reglas legales de retención. Menos historial significa menos datos para depuración y análisis forense; ejecuciones en curso, en espera o anotadas pueden no depurarse del mismo modo. Retención oficial de ejecuciones.

Sospecha de compromiso: restringe el acceso malicioso sin destruir pruebas, inspecciona actividad de proxy, host y n8n y workflows modificados, revoca o rota credenciales externas posiblemente expuestas, corrige la causa y restaura solo desde copias recuperables probadas cuando sea necesario. Revisa URLs de webhooks afectadas, cuentas del editor y servicios conectados; no supongas que HTTPS, snapshots o comprar un VPS incluyen servicios de respuesta a incidentes.

CONTROLES DE CUENTA Y PLATAFORMA

Protege el editor además del VPS

Exige mayor protección de inicio de sesión

Activa autenticación de dos factores para cuentas del editor y aplica MFA mediante políticas de seguridad de n8n cuando tu edición admita políticas centralizadas.

Limita quién puede editar workflows

El acceso al editor es privilegiado: los workflows pueden leer credenciales, llamar sistemas internos y ejecutar nodos potentes. Mantén limitado el acceso de usuarios y elimina cuentas que ya no lo necesiten.

Desactiva capacidades que no uses

Reduce la superficie de ataque desactivando la API pública cuando no sea necesaria y bloqueando nodos o funciones de alto riesgo que tu modelo no necesite.

Usa deliberadamente controles SSRF y de secretos

Para workflows que puedan hacer solicitudes HTTP arbitrarias, evalúa la protección SSRF de n8n y mantén secretos fuera del código de workflows, repositorios públicos y archivos de entorno ampliamente legibles.

Restringe endpoints de gestión no usados: N8N_PUBLIC_API_DISABLED=true desactiva la API REST pública de n8n, y N8N_PUBLIC_API_SWAGGERUI_DISABLED=true desactiva por separado su API playground. Hazlo solo cuando tus integraciones no necesiten esas funciones. Desactivar REST API no autentica las URLs de webhook de workflows. Usa MFA para usuarios del editor y políticas centralizadas solo cuando tu edición de n8n las admita.

FAQ

Seguridad de n8n en VPS: preguntas frecuentes

¿Debe exponerse directamente el puerto de n8n?

Cuando reverse proxy sea el punto de entrada público, expón el proxy y mantén detrás el puerto de aplicación en lugar de publicar servicios innecesariamente.

¿Deben ser públicos PostgreSQL o Redis?

Normalmente no. Deben ser accesibles solo por los sistemas que los necesitan. La exposición pública aumenta la superficie de ataque sin ayudar al funcionamiento normal de n8n.

¿Por qué es importante la clave de cifrado de n8n?

Protege las credenciales almacenadas por n8n y debe mantenerse coherente en todo el despliegue. Perderla puede impedir que los datos recuperados produzcan credenciales cifradas utilizables.

¿Son seguros los nodos comunitarios?

Amplían n8n con código de terceros, así que deben tratarse como dependencias de software con sus propios riesgos de cadena de suministro y privilegios. Instala solo lo que necesites y en lo que confíes.

¿HTTPS hace segura una instancia n8n autoalojada?

No. HTTPS protege el transporte. La seguridad en producción también requiere refuerzo del host, control de acceso, backend privado, protección de secretos, capacidades seguras de workflows, monitorización y actualizaciones.

¿Puede el editor de n8n ser privado mientras siguen funcionando los webhooks de producción?

Sí. Un reverse proxy de confianza o VPN puede restringir acceso de editor/admin por separado de rutas públicas de webhooks de producción y callbacks OAuth. Prueba el acceso de confianza y la entrega externa de webhooks después de cada cambio de reglas para evitar bloquear integraciones accidentalmente.

¿Cómo autentico los webhooks entrantes de n8n?

Configura autenticación Basic, Header o JWT en el nodo Webhook cuando el emisor la admita. También puedes usar IP(s) Allowlist y verificar firmas del proveedor cuando estén disponibles. No dependas solo de una ruta que parezca secreta y valida las solicitudes antes de que activen acciones sensibles de API.
