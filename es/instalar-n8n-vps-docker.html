Una instalación de producción necesita persistencia, clave de cifrado estable, PostgreSQL, dominio, HTTPS y URL pública correcta para webhooks.

CONFIGURACIÓN

Define secretos, base de datos y URL pública antes del primer arranque

Clave de cifrado

Configura una clave estable antes de guardar credenciales y consérvala fuera del VPS para recuperación.

PostgreSQL

Usa credenciales dedicadas, un volumen persistente y una red privada entre n8n y la base.

Hostname público

Configura el dominio HTTPS real en lugar de localhost o del nombre interno del contenedor.

Webhook URL

Define la URL externa cuando la dirección interna de n8n no coincide con la que utilizan servicios de terceros.

PERSISTENCIA

Recrear un contenedor no debe borrar la instancia

n8nPersiste el directorio de datos necesario para conservar el estado de la instancia.
PostgreSQLMantén los datos de la base fuera del contenedor desechable.
PermisosLos volúmenes deben ser escribibles por el usuario correcto sin abrir permisos innecesarios en el host.
ArchivosPersiste también directorios y binary data que utilicen los workflows.

HTTPS Y PROXY INVERSO

Publica n8n detrás de TLS y verifica los webhooks desde Internet

Nginx, Caddy o Traefik

Usa un proxy inverso como entrada pública y deja el servicio interno de n8n fuera de exposición directa.

Certificado TLS

Emite un certificado válido para el dominio y redirige HTTP a HTTPS.

Forwarded headers

Transmite host y protocolo correctamente para que n8n reconstruya la URL pública esperada.

Prueba externa

Activa un webhook y llámalo desde fuera del VPS; confirma que la URL generada es HTTPS y públicamente alcanzable.

ACTUALIZACIONES

Actualiza contenedores sin tratar Docker como un backup

DespuésComprueba logs, editor, credenciales, webhooks y workflows representativos.

FALLOS COMUNES

Por qué una instalación funciona en local y falla en producción

Webhook apunta a localhost

La URL pública, protocolo o cabeceras del proxy están mal configurados.

Datos desaparecen

n8n o PostgreSQL no tienen persistencia correcta y el estado se pierde al recrear contenedores.

Credenciales rotas

La instancia reconstruida usa una clave de cifrado distinta de la original.

PostgreSQL público

La base se expone innecesariamente aunque solo n8n necesita acceder a ella.

Decisiones técnicas restantes

Validar el despliegue

1

Docker Compose debe mantener n8n y PostgreSQL con volúmenes persistentes y la base de datos sin exposición pública.

2

N8N_ENCRYPTION_KEY debe ser estable y guardarse fuera del contenedor.

3

Tras arrancar, verifica docker compose ps, logs y /healthz antes de activar webhooks de producción.

4

Fija la versión de n8n y no subas una versión mayor de PostgreSQL a ciegas sobre el mismo volumen.

¿1 GB es un VPS real?

Sí. Es un VPS de entrada real para cargas ligeras; la limitación es el margen de recursos.

¿Por qué 2 GB como base ligera?

Da más margen a Docker, sistema operativo y pequeños picos.

¿Por qué medir antes de escalar?

CPU, RAM, disco y latencia muestran el cuello real.
