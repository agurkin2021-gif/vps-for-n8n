INSTALACIÓN CON DOCKER

Instalar n8n en un VPS

Instala n8n en un VPS usando Docker Compose y PostgreSQL. Un despliegue de producción también necesita datos persistentes de la aplicación y la base, una N8N_ENCRYPTION_KEY, un hostname público, HTTPS y una configuración correcta de webhooks. Verifica estos elementos antes de activar workflows de producción.

REQUISITOS PREVIOS

Prepara el VPS antes de iniciar n8n

VPS Linux

Usa un servidor Linux con mantenimiento y recursos suficientes para n8n, PostgreSQL, Docker y el reverse proxy.

DNS

Apunta un dominio o subdominio al VPS antes de emitir certificados TLS y publicar URLs de webhook.

Docker Compose

Instala Docker Engine y el plugin Compose usando paquetes compatibles con el sistema operativo.

Firewall

Expón solo los puertos web y de administración necesarios. Mantén privados PostgreSQL y los servicios internos de la aplicación.

¿Instalas en un VPS que ya aloja sitios web? Puedes añadir n8n a un servidor que controlas si CPU, RAM y almacenamiento lo permiten. Sin embargo, si Nginx, Apache, Caddy u otro reverse proxy ya ocupa los puertos 80/443, no inicies sin cambios el contenedor Caddy del ejemplo: los puertos entrarán en conflicto. En su lugar, enruta un nuevo subdominio de n8n mediante tu reverse proxy actual con una red privada adecuada, o usa un VPS limpio para seguir exactamente el ejemplo Compose. Conserva los otros sitios y su configuración TLS; el ejemplo supone que los puertos 80/443 están disponibles.

INSTALACIÓN PARA COPIAR Y ADAPTAR

Instala n8n en tu VPS con Docker Compose

Usa este ejemplo para crear un despliegue de n8n en un VPS Linux autogestionado. Tú instalas y mantienes n8n; elegir un servidor mediante nuestro socio no incluye una instancia n8n preinstalada. El ejemplo combina n8n, PostgreSQL, un task runner externo y Caddy HTTPS en una red privada de Compose. Es una plantilla de configuración, no una afirmación de que el despliegue haya sido probado en vivo.

¿Prefieres la instalación nueva más rápida? n8n también ofrece una instalación oficial de Docker en una sola línea. Puedes descargar y revisar el script con curl -fsSL https://get.n8n.io -o get-n8n.sh antes de ejecutar sh get-n8n.sh. Esa opción inicia una instancia inicial con SQLite en una URL local e incluye servicios sandbox de n8n Assistant; no es lo mismo que este despliegue VPS con HTTPS público y PostgreSQL. El stack sandbox oficial completo necesita más RAM y CPU que una instalación ligera de n8n (su guía Compose especifica al menos 4 GB RAM / 2 vCPUs). Para un VPS de producción expuesto a Internet, continúa con el stack configurado manualmente que aparece abajo.

1. Prepara Docker, DNS y acceso

Conéctate por SSH con acceso sudo y apunta un registro DNS A para n8n.example.com a la dirección IPv4 de tu VPS. En un Ubuntu 22.04, 24.04 o 26.04 recién instalado VPS, los siguientes comandos instalan Docker Engine y el moderno plugin docker compose desde el repositorio oficial firmado de apt Docker:

# Instalación oficial nueva de Ubuntu 22.04 / 24.04 / 26.04
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Registra el repositorio apt firmado de Docker
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

Este es el método de repositorio orientado a producción de la guía oficial de instalación de Docker en Ubuntu. No reinstales ni elimines Docker a ciegas en un VPS que ya ejecuta contenedores u otros sitios; primero inspecciona la instalación existente y posibles conflictos de paquetes. Para Debian u otra distribución, usa las instrucciones oficiales correspondientes al sistema en lugar de comandos de Ubuntu.

Ahora verifica Docker, el plugin Compose, DNS y el directorio de trabajo:

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

Si getent hosts no devuelve ninguna dirección o devuelve una incorrecta, corrige DNS antes de iniciar Caddy; sustituye n8n.example.com en toda esta guía por tu hostname real. Docker normalmente requiere privilegios root: si tu usuario SSH no puede ejecutar directamente los siguientes docker compose comandos, antepón sudoAñadir un usuario al grupo docker concede acceso equivalente a root y no debe hacerse a la ligera en un servidor compartido.

Mantén accesible tu puerto real de administración SSH antes de activar un firewall. Permite HTTP (80) y HTTPS (443) entrantes para emitir certificados y acceder al editor. Los puertos de contenedor publicados por Docker pueden saltarse algunas reglas UFW, así que revisa la guía de firewall de Docker y publica solo los puertos previstos de Caddy. Este ejemplo Compose deliberadamente no no publica PostgreSQL (5432), n8n (5678) ni el broker del task runner (5679) en Internet público.

2. Crea valores de entorno y conserva la clave

Desde el directorio del proyecto, genera tres diferentes valores hexadecimales aleatorios con:

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

Crea un archivo llamado .env usando la plantilla siguiente, sustituye cada REPLACE_WITH_RANDOM_HEX por un valor generado distinto y cambia el hostname y la zona horaria. La etiqueta 2.42.5 mostrada corresponde a la versión estable indicada el 8 de octubre de 2026, usada aquí como ejemplo de configuración fechado, no una garantía de despliegue probado en vivo ni de seguridad futura. Antes de instalar, comprueba las versiones oficiales actuales de n8n y mantén n8n y su imagen de task runner en la misma versión verificada.

# .env — sustituye los tres secretos de ejemplo
# Fija una versión mantenida de n8n; mantén n8n y runner en la misma versión.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

Nunca subas .env a un repositorio público. Guarda la clave de cifrado y las instrucciones de recuperación de forma segura fuera del VPS. La clave debe seguir siendo la misma después de recrear contenedores o migrar.

3. Escribe compose.yaml para una instalación nueva

En el mismo directorio, crea compose.yamlEl ejemplo usa las convenciones oficiales de variables de entorno de n8n y la ruta PGDATA de PostgreSQL 18 documentada por el proyecto de hosting de n8n:

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

Los cuatro servicios tienen funciones distintas: PostgreSQL almacena el estado de la base, n8n ejecuta workflows, n8n-runner ejecuta tareas del runner con una versión coincidente y un token de autenticación compartido, y Caddy gestiona HTTPS público. Un task runner externo no es modo cola con Redis. Solo Caddy publica puertos del host. Este ejemplo ligero usa un único rol de base para la configuración; para separar mejor los privilegios de PostgreSQL, consulta el ejemplo oficial de despliegue PostgreSQL de n8n.

4. Crea el Caddyfile para HTTPS

Crea el archivo Caddyfile (C mayúscula, sin extensión) junto a compose.yaml. Sustituye en todas partes el hostname de ejemplo por tu nombre DNS:

n8n.example.com {
    reverse_proxy n8n:5678
}

Caddy solicita y renueva certificados TLS públicos cuando el dominio resuelve correctamente y el tráfico externo puede llegar a los puertos 80/443. No apuntes DNS a localhost. Si sustituyes Caddy por otro reverse proxy, reenvía las cabeceras originales de host, protocolo y dirección del cliente y ajusta N8N_PROXY_HOPS al número real de saltos de proxy de confianza.

5. Inicia los contenedores y prueba desde fuera

Ejecuta estos comandos desde el directorio del proyecto después de guardar .env, compose.yaml y Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

El último comando comprueba el endpoint de salud HTTPS público Si la emisión del certificado sigue pendiente, revisa los logs de Caddy y DNS/puertos antes de concluir que n8n está roto. Abre https://n8n.example.com, crea inmediatamente la primera cuenta owner y activa protecciones adecuadas de inicio de sesión. Confirma que la instancia ejecuta realmente un workflow, no solo que el editor carga:

  1. En el editor, crea un workflow con un trigger Webhook Configura HTTP Method como GET, elige Path vps-check, y configura Respond como Immediately. Guarda el workflow.
  2. Haz clic en Listen for Test Eventcopia la Test URL completa mostrada por n8n y, desde otro dispositivo, ejecuta curl -i 'PASTE_TEST_URL_HERE' con la URL copiada. Debes recibir una respuesta HTTP correcta y ver el evento entrante en el editor de n8n. Las URLs de prueba solo funcionan mientras n8n está escuchando el evento.
  3. Publica el workflow, cambia el nodo a su Production URL, cópiala y ejecuta curl -i 'PASTE_PRODUCTION_URL_HERE' de nuevo. Confirma la ejecución en la pestaña Executions del workflow. Las solicitudes de webhook de producción requieren que el workflow esté publicado y no muestran su payload en la vista de prueba del editor.

Es una prueba básica intencionadamente simple y sin autenticación: nunca envíes secretos. Despublícala o elimínala después de probar, o configura autenticación del Webhook/restricciones IP antes de usar un endpoint público con datos reales. Consulta la documentación oficial de Webhook de prueba/producción.

6. Haz una copia antes de cambiar versiones fijadas

Guarda un dump recuperable de PostgreSQL y el volumen persistente de datos de n8n, .env/clave de cifrado y los archivos externos necesarios en almacenamiento fuera de este servidor. Verifica una restauración usando la guía de copias y recuperación antes de actualizar producción. Comandos de ejemplo:

# Haz copia de la base de datos, clave de cifrado y datos de la instancia,
# y de los archivos antes de cambiar las versiones fijadas.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# Después de asegurar la copia fuera de este VPS:
docker compose pull
docker compose up -d
docker compose ps

Cambia la versión fijada N8N_VERSION solo después de leer las notas de versión; las imágenes de n8n y runner deben avanzar juntas. No ejecutes docker compose down -v durante el mantenimiento normal porque elimina los volúmenes de datos con nombre. Cambiar la versión mayor de PostgreSQL requiere una actualización de base o un plan dump/restauración; sustituir la imagen Postgres 18 por otro tag mayor no es una migración automática.

Referencias principales: guía Docker Compose de n8n, configuración de reverse proxy/webhooks de n8n y notas oficiales de despliegue PostgreSQL. No se presupone ningún benchmark de infraestructura ni función preinstalada específica de proveedor.

Configura secretos y URLs públicas de forma deliberada

Clave de cifrado

Configura y conserva una clave de cifrado fuerte de n8n antes de almacenar credenciales de producción. La misma clave será necesaria tras la recuperación.

Credenciales PostgreSQL

Usa credenciales dedicadas de base y mantén las contraseñas fuera del control de versiones público.

Hostname público

Configura el hostname externo real y el origen HTTPS, no una dirección interna del contenedor.

URL del webhook

Configura N8N_WEBHOOK_URL con la URL base HTTPS accesible públicamente y configura N8N_PROXY_HOPS=1 cuando haya un único reverse proxy de confianza. WEBHOOK_URL es un alias obsoleto en n8n 2.35.0 y posteriores; evita copiarlo de tutoriales antiguos.

FALLOS COMUNES

Por qué una instalación Docker de n8n funciona localmente pero falla en producción

URL de webhook incorrecta

Los callbacks apuntan a localhost, HTTP o un hostname interno en vez del origen HTTPS público.

Falta de persistencia

El estado de la aplicación o base desaparece al recrear un contenedor.

Clave de cifrado perdida

Las credenciales guardadas dejan de ser utilizables tras reconstruir porque la nueva instancia usa otra clave.

Puerto público de base

PostgreSQL está expuesto innecesariamente aunque solo n8n necesita acceder.

FAQ

Instalar n8n con Docker: preguntas frecuentes

¿n8n necesita PostgreSQL al usar Docker?

Docker no requiere PostgreSQL y los despliegues pequeños pueden usar SQLite. Para un VPS orientado a producción, PostgreSQL ofrece una base más sólida y permite escalar después con modo cola.

¿Por qué mantener un volumen persistente de n8n si PostgreSQL almacena datos?

El directorio persistente de n8n puede contener estado y configuración importantes. Consérvalo según el diseño del despliegue en lugar de suponer que la base es el único recurso de recuperación.

¿Por qué mi webhook muestra localhost?

La dirección interna del contenedor difiere del origen público. Configura el hostname externo, protocolo y URL del webhook, y asegúrate de que el reverse proxy pasa las cabeceras necesarias.

¿Debe ser público el puerto 5678?

En un despliegue normal de producción detrás de reverse proxy, expón HTTPS en el proxy y mantén interno el puerto de la aplicación n8n salvo una razón operativa específica.

¿Necesito Redis?

No para un despliegue Docker estándar de una sola instancia. Redis cobra relevancia cuando pasas deliberadamente a modo cola y workers.

¿Los task runners externos de n8n son lo mismo que los workers de modo cola?

No. Los task runners externos ejecutan código de tareas compatible separado del proceso principal de n8n y usan un token de autenticación compartido. El modo cola Redis distribuye ejecuciones de workflows y tiene sus propios requisitos de infraestructura. Este ejemplo muestra un task runner externo, no modo cola Redis. Haz coincidir la versión de la imagen del runner con la versión de n8n.
