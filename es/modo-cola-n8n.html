ESCALADO

Modo cola de n8n

El modo cola separa la ejecución de workflows del proceso principal de n8n. La instancia main recibe triggers y crea ejecuciones, Redis coordina la cola, los workers ejecutan tareas y PostgreSQL almacena los datos compartidos de workflows y ejecuciones.

DECISIÓN RÁPIDA

¿Realmente necesitas modo cola?

Mantén el modo normal cuando

Una sola instancia maneja con comodidad los picos de ejecuciones y CPU, RAM y latencia se mantienen estables. El modo cola añade componentes que todavía no necesitas.

Considera modo cola cuando

Las ejecuciones paralelas sostenidas crean contención, aumenta la latencia bajo carga o necesitas añadir capacidad ejecutando varios workers.

Escala verticalmente primero cuando

El cuello de botella sea simplemente CPU o RAM insuficientes y una instancia mayor todavía pueda manejar bien la carga.

Mide antes de cambiar la arquitectura

Usa concurrencia máxima, CPU, RAM, duración de ejecuciones, profundidad de cola y presión sobre la base para justificar el cambio.

ARQUITECTURA

Cómo funciona el modo cola de n8n

1 · MainRecibe temporizadores, webhooks y solicitudes de workflows y crea una ejecución en lugar de realizar por sí mismo la ejecución de producción.
2 · RedisActúa como broker de mensajes. Mantiene mensajes de ejecuciones pendientes para que el siguiente worker disponible pueda reclamar una tarea.
3 · WorkerRecibe el ID de ejecución, carga los datos del workflow desde la base compartida, ejecuta el workflow y escribe el resultado.
4 · PostgreSQLProporciona datos persistentes compartidos de workflows y ejecuciones. El modo cola distribuido no es compatible con SQLite.

REQUISITOS BÁSICOS

Qué necesita todo despliegue en modo cola

Redis

Todos los procesos main y worker necesitan acceso fiable al servicio Redis usado para coordinar la cola.

PostgreSQL

Main y workers deben compartir la base. El modo cola es una arquitectura distribuida y no debe diseñarse alrededor de SQLite.

Configuración de n8n coherente

Main y workers deben ejecutar modo cola y compartir la configuración necesaria para acceder a Redis, PostgreSQL y credenciales cifradas.

Capacidad de workers

Los workers necesitan suficiente CPU y RAM para los workflows que ejecutan. Añadir procesos no elimina el coste de recursos de cada ejecución.

Activa el modo cola en un stack autoalojado existente. Primero confirma que el servicio main de n8n y cada worker pueden alcanzar la misma base PostgreSQL y Redis mediante red privada. Configura EXECUTIONS_MODE=queue tanto en main como en workers, e indica QUEUE_BULL_REDIS_HOST=redis y QUEUE_BULL_REDIS_PORT=6379 cuando redis sea el nombre real de tu servicio Compose. Usa DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres y los valores correspondientes DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER y DB_POSTGRESDB_PASSWORD en cada proceso; sustituye los nombres de servicio de ejemplo por los tuyos. Proporciona exactamente la N8N_ENCRYPTION_KEY existente a todos. Nunca publiques puertos del host de Redis o PostgreSQL solo para conectar contenedores de la misma red Compose.

Inicia un ejecutor, no un segundo editor. Añade un servicio worker de n8n usando la misma versión fijada de imagen y los mismos ajustes compartidos que main, pero ejecútalo con el comando worker Si llamaste a ese servicio n8n-worker, inícialo con docker compose up -d n8n-worker. Después de confirmar una ejecución real en un worker, puedes usar docker compose up -d --scale n8n-worker=2 para iniciar un segundo worker desde ese servicio. Son añadidos a un stack Compose existente y correctamente configurado no un archivo de instalación independiente; conserva tus volúmenes persistentes, proxy HTTPS, secretos y copias existentes.

Fragmento Compose de modo cola para un stack existente. Integra el ejemplo siguiente en tu compose.yamlactual; no es un despliegue completo e independiente. Supone que ya tienes servicios persistentes y privados postgres y n8n además de una versión N8N_VERSION fijada en el entorno y tu propio POSTGRES_PASSWORD protegido y la N8N_ENCRYPTION_KEY. Haz coincidir nombres, volúmenes, base y versión de n8n con el proyecto existente. Añade también los ajustes Redis del modo cola y EXECUTIONS_MODE=queue al servicio main existente, como se describió arriba.

# Integra con los servicios existentes; no sustituyas tu archivo Compose completo.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

En este fragmento no se publica ningún puerto de host para Redis ni el worker. La persistencia append-only de Redis es una capa adicional de recuperación, no es no un sustituto de copias fuera del servidor. Mantén sin cambios la configuración existente de HTTPS y autenticación. Para nodos Code que requieran task runners externos, configura por separado los procesos runner para tu despliegue de workers; el modo cola no sustituye los task runners.

¿Convirtiendo una instancia SQLite existente? No cambies simplemente DB_TYPE y arranques contra una base PostgreSQL vacía: eso no migra los workflows y credenciales antiguos. Antes de cualquier cambio, haz copia de la base de origen, del directorio persistente .n8n y de la clave de cifrado original; usa un procedimiento compatible de exportación/importación o migración de n8n y verifica después workflows y credenciales cifradas en un destino separado. Conserva los archivos originales para rollback y usa la guía de Copia y restauración enlazada abajo para preparar la recuperación. Nunca elimines database.sqlite como atajo.

CONCURRENCIA DE WORKERS

Los workers escalan tanto por cantidad como por tareas por worker

Cada worker puede procesar varias tareas simultáneamente. La concurrencia predeterminada actual de un worker en n8n es 10 y la documentación recomienda 5 o más. Una concurrencia muy baja combinada con muchos workers puede crear conexiones innecesarias y agotar el pool de conexiones de la base.

Aumenta la concurrencia cuando

Un worker tenga CPU y RAM libres y los workflows estén principalmente esperando servicios externos en lugar de saturar cómputo o memoria.

Añade workers cuando

Un proceso worker se convierta en cuello de botella y la base, Redis y la infraestructura tengan capacidad para más ejecución paralela.

Reduce la concurrencia cuando

Los workflows individuales consuman mucha memoria o CPU y las tareas paralelas causen contención, presión OOM o tiempos de ejecución inestables.

Vigila PostgreSQL

Más workers y más concurrencia aumentan la actividad de la base. Escalar capacidad de ejecución sin capacidad de base puede desplazar el cuello de botella en vez de eliminarlo.

Conoce qué límite de concurrencia se aplica realmente. Un worker puede iniciarse con n8n worker --concurrency=5, o el comando equivalente en tu servicio Compose. Si N8N_CONCURRENCY_PRODUCTION_LIMIT se configura explícitamente con un valor distinto de -1, ese ajuste tiene prioridad en modo cola; de lo contrario n8n usa el valor --concurrency del worker o su valor predeterminado de 10. No multipliques el número de workers por un valor nominal y lo llames throughput garantizado: la capacidad real depende de duración de tareas, CPU, memoria, APIs externas y conexiones PostgreSQL.

WEBHOOKS

El modo cola puede añadir latencia al traspasar ejecuciones

El proceso main o webhook recibe la solicitud HTTP, pero un worker ejecuta el workflow. Ese traspaso por Redis añade overhead. Para webhooks sensibles a latencia, mide el tiempo de respuesta extremo a extremo en lugar de asumir que más workers aceleran automáticamente todas las solicitudes.

RecibirEl proceso main/webhook acepta la solicitud.
ColaLa ejecución se entrega a Redis.
EjecutarUn worker disponible ejecuta el workflow.
ResponderEl resultado vuelve por la ruta de la cola cuando sea necesario.

Dirige el tráfico de webhooks al proceso correcto. Con procesadores dedicados n8n webhook detrás de reverse proxy o balanceador, dirige las rutas de producción /webhook/* y /webhook-waiting/* a los procesadores webhook; mantén /webhook-test/*, las solicitudes del editor y API en main. No añadas main al pool de balanceo de webhooks de producción salvo que aceptes deliberadamente esa carga adicional. Un workflow Respond to Webhook puede mantener al cliente esperando hasta que el worker termine y devuelva la respuesta, así que el modo cola no promete respuestas HTTP instantáneas ni cero timeouts. Prueba el callback externo real y el comportamiento de respuesta antes de cambiar tráfico.

DATOS BINARIOS

No ignores el almacenamiento compartido

Limitación del sistema de archivos

El modo cola no admite almacenamiento binario basado en sistema de archivos como modelo de persistencia compartida para workers distribuidos.

Almacenamiento binario externo

Cuando los workflows deban persistir datos binarios entre workers distribuidos, usa un diseño de almacenamiento accesible para todas las instancias necesarias, como object storage externo compatible.

Respuestas grandes de webhook

Las respuestas de webhook de los workers regresan al proceso receptor. Bodies grandes pueden aumentar la presión de memoria en Redis y exigir una configuración deliberada de almacenamiento de respuestas.

Planifica antes de distribuir workers

Una carga que dependa mucho de archivos locales debe rediseñarse para persistencia compartida antes de repartir workers entre máquinas.

Límite de respuestas grandes de webhook. La documentación actual de n8n da a N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX un valor predeterminado de 64 MiB para la respuesta de un worker enviada de vuelta por la cola. Redis puede mantener varias copias en tránsito, así que reserva aproximadamente 1.5 veces el tamaño de la respuesta en memoria Redis por cada respuesta grande simultánea. Sin offloading, una respuesta demasiado grande falla en lugar de volverse mágicamente más rápida al añadir workers.

Límites de versión y licencia. Desde n8n 2.34.0, los workers pueden usar N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true para descargar bodies de respuesta demasiado grandes a almacenamiento binario compartido legible, pero primero actualiza todos los procesos main y webhook a 2.34.0 o posterior. El N8N_DEFAULT_BINARY_DATA_MODE seleccionado debe almacenar realmente datos y ser legible por cada proceso participante. El almacenamiento binario externo S3 y Azure requiere una licencia autoalojada válida Business o Enterprise ; no supongas que Community Edition puede habilitarlo. El modo binario database puede descargar una respuesta demasiado grande sin almacenamiento externo de pago, pero la instancia main carga todo el body almacenado en memoria y el almacenamiento de base tiene su propio límite de tamaño. Para el offload específico del body de respuesta, n8n también describe una opción compartida de filesystem cuando todas las instancias montan el mismo disco, pero explícitamente no recomienda esa disposición. No confundas esta ruta especial de offload con soporte de datos binarios persistentes basados en sistema de archivos en un despliegue distribuido de modo cola. Comprueba edición, versión y almacenamiento antes de habilitar offload.

MONITORIZACIÓN

Comprueba si la cola está ayudando

Profundidad de cola

Una cola que crece más rápido de lo que los workers la vacían indica capacidad insuficiente o un cuello de botella posterior.

CPU y RAM del worker

Mide saturación y picos de memoria por worker. Workers ociosos con una cola creciente apuntan a otra limitación.

Latencia de ejecución

Controla el retraso entre crear una ejecución y su inicio real, no solo la duración del workflow.

Comprobaciones de salud

Los endpoints de salud de workers pueden indicar si un worker está vivo y si sus conexiones con base y Redis están listas.

Verifica ejecución en un worker, no solo un contenedor en verde. Con un stack Compose correctamente configurado, comprueba docker compose ps y docker compose logs --tail=100 n8n-worker (sustituye el nombre del servicio si es distinto). Ejecuta un workflow inocuo publicado de producción usando un trigger programado o webhook de prueba, y relaciona su ejecución en la vista Executions de n8n con el procesamiento real en los logs del worker. Un editor que abre correctamente, un contenedor Redis activo o una ejecución en cola por sí solos no es no demuestran que un worker haya realizado la tarea.

Comprueba dependencias y disponibilidad. Con los nombres de servicio predeterminados del ejemplo, docker compose exec -T redis redis-cli ping debería recibir PONG cuando la autenticación de Redis lo permita, y docker compose exec -T postgres pg_isready -U n8n -d n8n comprueba la disponibilidad de PostgreSQL (adapta credenciales y nombres de servicio). Activa QUEUE_HEALTH_CHECK_ACTIVE=true en un worker cuando necesites sus endpoints privados /healthz y /healthz/readiness ; el endpoint de readiness comprueba conectividad Redis/base. No expongas esos endpoints públicamente solo para monitorizarlos.

Las ejecuciones manuales son una prueba diferente. Por defecto OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, por lo que ejecutar manualmente un workflow en el editor puede hacerlo en main incluso con modo cola bien configurado. Configúralo como true solo si pretendes enviar ejecuciones manuales a workers y has comprobado el cambio en staging. Los workers de modo cola también son distintos de los task runners externos de n8n, que tienen requisitos separados para ejecutar nodos Code.

LÍMITE DE ALTA DISPONIBILIDAD

El modo cola escala ejecuciones, pero no hace automáticamente altamente disponible al proceso main

Comparte la clave de cifrado

Cada worker debe usar la misma N8N_ENCRYPTION_KEY que la instancia main para poder descifrar credenciales necesarias para las ejecuciones.

Mantén las versiones alineadas

Los procesos main, webhook y worker deben ejecutar la misma versión de n8n. Mezclar versiones puede crear comportamientos incompatibles durante cambios rolling.

Los procesadores webhook son una capa de escalado separada

Cuando el volumen entrante de webhooks sea el cuello, los procesadores dedicados pueden situarse detrás de un balanceador mientras los workers manejan ejecuciones. No añadas esta capa salvo que el volumen medido lo justifique.

Multi-main es una función diferente

Ejecutar varios procesos main para alta disponibilidad no es lo mismo que el modo cola normal. n8n documenta actualmente multi-main como función Enterprise autoalojada con requisitos adicionales de balanceador y sesión.

FAQ

Modo cola de n8n: preguntas frecuentes

¿El modo cola de n8n requiere Redis?

Sí. Redis es el broker de mensajes que coordina ejecuciones pendientes entre la instancia main y los workers.

¿Puede el modo cola usar SQLite?

No para la arquitectura distribuida de modo cola. Main y workers necesitan acceso compartido a la base y n8n documenta PostgreSQL como la base para esta configuración.

¿Cuántos workers debería ejecutar?

No existe una cantidad universal. Parte de concurrencia medida y utilización de workers; añade capacidad mientras monitorizas PostgreSQL, Redis, CPU, RAM y profundidad de cola.

¿Qué es la concurrencia de workers de n8n?

Es el número de tareas que un worker puede procesar en paralelo. El valor predeterminado actual es 10 y n8n recomienda concurrencia de 5 o más en lugar de crear muchos workers con concurrencia baja.

¿Debería activar modo cola en un VPS pequeño?

Solo cuando la carga lo justifique. Un despliegue pequeño que funcione cómodamente como una instancia suele ser más sencillo de operar sin Redis ni workers separados.
