KEAMANAN PRODUKSI

Keamanan n8n di VPS

Untuk mengamankan n8n pada VPS, jauhkan n8n (5678), PostgreSQL (5432) dan opsional Redis (6379) dari internet publik; gunakan reverse proxy HTTPS, kunci SSH, dan MFA, pertahankan kunci enkripsi Anda, autentikasi webhook, batasi kemampuan workflow yang berisiko, dan audit instans yang diterapkan. Lindungi editor secara terpisah dari rute webhook publik. HTTPS saja tidak mengamankan layanan yang terhubung.

DAFTAR PERIKSA CEPAT

Baseline keamanan minimum sebelum akses publik

Mulailah dengan port yang dapat dijangkau, HTTPS, akses administratif terverifikasi, MFA dan perlindungan kredensial yang disimpan. Otentikasi setiap webhook yang masuk sebelum dapat memicu pekerjaan sensitif. Setelah mengubah kontrol akses, verifikasi bahwa editor yang dimaksud dan integrasi eksternal masih berfungsi, lalu jalankan audit keamanan n8n.

HTTPS saja

Letakkan n8n di belakang proxy terbalik TLS yang dikonfigurasi dengan benar dan gunakan URL publik HTTPS secara konsisten untuk editor dan webhook.

Port terbuka minimal

Ekspos hanya port yang diperlukan untuk traffic publik. Jauhkan PostgreSQL, Redis dan port aplikasi internal dari internet publik.

Hardening SSH

Gunakan administrasi berbasis kunci, batasi siapa yang dapat masuk, dan pertahankan sistem operasi tetap diperbarui.

Lindungi kredensial

Jaga agar kunci enkripsi n8n tetap stabil dan secret. Perlakukan file lingkungan, akses database, dan salinan backup sebagai aset sensitif.

TEPI JARINGAN

Reverse proxy, HTTPS, dan header tepercaya

TLS termination

Gunakan proxy terbalik seperti Nginx, Caddy atau Traefik untuk menghentikan HTTPS. Arahkan ulang HTTP biasa dan hindari mengekspos port aplikasi n8n secara langsung ketika proxy adalah titik masuk yang dituju.

Konfigurasi proksi

Ketika n8n berjalan di belakang proxy terbalik, konfigurasikan jumlah hop proxy dengan benar dan teruskan header yang diteruskan n8n yang diperlukan untuk merekonstruksi permintaan klien asli.

Amankan cookie

Sajikan editor melalui HTTPS sehingga cookie autentikasi tetap aman. Jangan mengatasi pengaturan TLS yang rusak dengan melemahkan keamanan cookie.

URL webhook

Tetapkan URL webhook publik ke hostname HTTPS yang dapat dijangkau secara eksternal sehingga endpoint webhook yang dihasilkan tidak mengarah ke container internal atau alamat HTTP.

Jaga kerahasiaan editor tanpa merusak webhook. Batasi akses manajemen menggunakan VPN, kebijakan IP tepercaya, atau proxy yang diautentikasi jika memungkinkan. Penerima webhook publik dan rute panggilan balik OAuth mungkin harus tetap dapat dijangkau; uji proses masuk editor tepercaya dan panggilan balik eksternal nyata sebelum menerapkan aturan proksi. Teruskan header alamat klien hanya dari proksi tepercaya, bukan header permintaan sembarangan.

Otentikasi penelepon webhook: di node Webhook pilih autentikasi Dasar, Header, atau JWT alih-alih Tidak Ada jika didukung oleh pengirim. Gunakan itu Daftar IP yang Diizinkan opsi jika sesuai, dan verifikasi tanda tangan penyedia di mana integrasi mendukung permintaan yang ditandatangani. URL yang sulit ditebak tidak cukup untuk autentikasi. Terapkan batas kecepatan pada proxy bila diperlukan dan konfirmasikan bahwa semburan yang valid tidak diblokir. Opsi autentikasi Webhook resmi.

VPS PENGERUSAN

Kurangi permukaan serangan server

firewall

Default-menolak traffic masuk yang tidak diminta dan hanya mengizinkan layanan yang harus dapat dijangkau. Basis data dan port Redis biasanya berada di jaringan pribadi/lokal.

SSH

Lebih suka kunci SSH daripada kata sandi, nonaktifkan jalur masuk yang tidak perlu dan batasi akses administratif. Akses yang setara dengan root harus dikontrol dengan ketat.

pembaruan sistem operasi

Patch runtime host dan container Linux. Pengerasan aplikasi tidak dapat mengimbangi sistem operasi yang terbuka atau usang.

Paparan container

Publikasikan hanya port yang memerlukan akses host. Layanan internal harus berkomunikasi pada jaringan Docker pribadi dan bukan melalui antarmuka publik.

Periksa sebelum mengubah pengaturan firewall atau SSH: periksa port pendengaran dengan sudo ss -lntp, Docker penerbitan dengan docker compose ps dari direktori proyek, dan menghosting kebijakan firewall dengan sudo ufw status verbose jika UFW digunakan. Verifikasi port SSH Anda yang sebenarnya dan login kunci yang berhasil di sesi terpisah sebelum menonaktifkan akses kata sandi. Port Docker yang diterbitkan dapat melewati aturan UFW; halaman status firewall saja tidak membuktikan port 5678 bersifat pribadi. Periksa jangkauan eksternal yang sebenarnya. Peringatan Docker/UFW.

Periksa pembaruan keamanan Ubuntu otomatis alih-alih berasumsi bahwa pembaruan tersebut berfungsi: memeriksa apt-config dump APT::Periodic::Unattended-Upgrade dan lognya /var/log/unattended-upgrades/unattended-upgrades.log. Jika peningkatan keamanan tanpa pengawasan dinonaktifkan, sudo dpkg-reconfigure unattended-upgrades menyediakan dialog konfigurasi yang didukung. Tinjau perilaku reboot dan restart layanan sebelum mengaktifkannya pada VPS yang berfungsi. Ubuntu Pembaruan APT dapat dilakukan tidak secara otomatis memperbarui gambar n8n Docker atau setiap repositori perangkat lunak pihak ketiga. Ubuntu dokumentasi pembaruan otomatis.

Opsional SSH pemantauan brute-force: Fail2Ban dapat mendeteksi login SSH yang gagal berulang kali. Jika diinstal dan dikonfigurasi untuk SSH, verifikasi jail dengan sudo fail2ban-client status sshd dan konfirmasikan bahwa itu membaca log atau jurnal autentikasi SSH Anda yang sebenarnya dan cocok dengan port yang dikonfigurasi. Ini melengkapi SSH kunci dan batasan jaringan; itu tidak menggantikan mereka. Jangan menyalin port SSH tetap atau aturan larangan tanpa memeriksa akses yang ada terlebih dahulu. Ubuntu SSH panduan pengerasan.

DATABASE & REDIS

Jaga layanan backend tetap privat

Dalam pengaturan Docker Compose pada umumnya, PostgreSQL dan Queue Mode Redis harus dapat dijangkau oleh container yang relevan melalui jaringan pribadi, bukan port yang diterbitkan host. Verifikasi dengan docker compose ps bahwa 5432 dan 6379 tidak dipublikasikan untuk umum; meninjau secara terpisah paparan VPS/cloud firewall. Kebijakan jaringan tidak menggantikan kredensial database dengan hak istimewa paling rendah.

RAHASIA N8N

Lindungi kunci enkripsi dan batas kredensial

Kunci enkripsi

n8n mengenkripsi kredensial yang disimpan menggunakan kunci enkripsinya. Pertahankan kunci yang sama saat restart dan worker dan lindungi secara terpisah dari konten aplikasi biasa.

Environment secret

Jangan memasukkan kata sandi, token, atau kunci enkripsi ke repositori publik. Batasi akses ke file lingkungan dan secret deployment.

Akses pengguna

Berikan akses editor hanya kepada pengguna tepercaya. Workflow dapat terhubung ke sistem sensitif dan dapat memproses secret atau mengeksekusi node yang kuat.

Cakupan kredensial

Gunakan akun layanan dengan cakupan sempit dan token API jika memungkinkan. Workflow yang disusupi tidak secara otomatis mewarisi akses luas ke sistem yang tidak terkait.

n8n konfigurasi untuk ditinjau: N8N_BLOCK_ENV_ACCESS_IN_NODE=true mencegah akses node kode dan ekspresi ke nilai lingkungan; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true meminta izin khusus pemilik pada file pengaturan. Simpan N8N_ENCRYPTION_KEY persisten dan dicadangkan dengan aman: n8n dapat membuat kunci acak pada permulaan pertama, namun kehilangan kunci tersebut dapat membuat kredensial terenkripsi yang ada tidak dapat digunakan. Jangan mengganti kunci enkripsi produksi begitu saja; gunakan prosedur rotasi yang didukung secara resmi. Memblokir akses lingkungan dapat merusak integrasi yang ada, jadi ujilah sebelum produksi berubah. n8n definisi variabel keamanan.

RISIKO ALUR KERJA

Node dapat memperluas batas keamanan

Self-hosting memberi workflow kekuatan yang besar. Eksekusi kode, akses shell, permintaan HTTP sewenang-wenang, dan node komunitas pihak ketiga dapat meningkatkan risiko. Nonaktifkan fungsionalitas yang tidak Anda perlukan dan tinjau impor workflow yang tidak tepercaya sebelum menjalankannya.

Gunakan kontrol yang didukung secara tepat: konfigurasikan NODES_EXCLUDE dengan array node JSON untuk dinonaktifkan, seperti n8n-nodes-base.executeCommand dan n8n-nodes-base.readWriteFile, jika tidak digunakan. Beberapa node berisiko tinggi sudah diblokir secara default di versi yang lebih baru; tinjau daftar sebenarnya sebelum mengubahnya. Pengecualian node resmi.

Dari n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true mengaktifkan pemeriksaan permintaan HTTP keluar ke rentang alamat internal, loopback, dan metadata. Workflow internal API yang sah mungkin berhenti berfungsi; jika perlu, masukkan hanya destinasi yang Anda kontrol saja ke dalam daftar yang diizinkan. Pertahankan segmentasi jaringan sebagai pertahanan utama. Untuk isolasi node kode, tinjau pelari tugas eksternal. Perlindungan SSRF · Isolasi pelaksana tugas.

AUDIT & PEMBARUAN

Keamanan adalah proses operasional berkelanjutanonal berkelanjutanonal berkelanjutanonal berkelanjutan

Jalankan audit keamanan n8n

Perintah resmi CLI adalah n8n audit. Jika layanan Docker Compose Anda diberi nama n8n, lari docker compose exec -T n8n n8n audit di direktori deployment itu. Tinjau lima kategori: kredensial yang tidak digunakan, pola kueri SQL yang berisiko, akses sistem file, node berisiko/komunitas, dan risiko instans termasuk webhook yang tidak dilindungi dan rilis yang sudah ketinggalan zaman. Perbaiki temuan yang relevan dan jalankan kembali. Ini bukan tes penetrasi. Panduan audit resmi.

Perbarui dengan sengaja

Jaga agar n8n tetap terkini untuk menerima perbaikan keamanan. Tinjau catatan rilis dan uji peningkatan penting daripada membiarkan mesin virtual yang terhubung ke internet menjadi basi secara permanen.

Pantau otentikasi

Perhatikan pola akses yang tidak terduga, perubahan dan kegagalan workflow. Batasi UI editor lebih lanjut bila model operasi Anda tidak memerlukan jangkauan publik yang luas.

Siapkan rollback dan pemulihan

Ambil backup yang dapat dipulihkan sebelum peningkatan signifikan. Cakupan backup dan pemulihan terperinci termasuk dalam panduan pemulihan terpisah.

Minimalkan riwayat eksekusi yang sensitif: proses yang berhasil dapat mempertahankan data dan token pelanggan. Bila sesuai ditetapkan EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, simpan EXECUTIONS_DATA_PRUNE=true, dan pilih sebuah EXECUTIONS_DATA_MAX_AGE dalam hitungan jam, seperti 168 (tujuh hari). Ini adalah contoh yang dapat dikonfigurasi, bukan aturan penyimpanan yang sah. Lebih sedikit riwayat berarti lebih sedikit debugging dan data forensik; eksekusi yang sedang berjalan, menunggu, atau diberi anotasi tidak dapat dipangkas dengan cara yang sama. Retensi eksekusi resmi.

Dugaan kompromi: membatasi akses berbahaya tanpa merusak bukti, memeriksa proksi, host, dan aktivitas n8n serta mengubah workflow, mencabut atau memutar kredensial hulu yang mungkin terekspos, menambal penyebabnya, dan memulihkan hanya dari backup yang dapat dipulihkan dan diuji bila diperlukan. Tinjau URL webhook yang terpengaruh, akun editor, dan layanan terhubung; jangan berasumsi HTTPS, snapshot atau pembelian VPS menyediakan layanan respons insiden.

KONTROL AKUN & PLATFORM

Lindungi editor serta VPS

Memerlukan perlindungan login yang lebih kuat

Aktifkan autentikasi dua faktor untuk akun editor dan terapkan kebijakan keamanan MFA hingga n8n bila edisi Anda mendukung deployment kebijakan terpusat.

Batasi siapa yang dapat mengedit workflow

Akses editor adalah akses istimewa: workflow dapat membaca kredensial, memanggil sistem internal, dan mengeksekusi node yang kuat. Jaga agar akses pengguna tetap sempit dan hapus akun yang tidak lagi memerlukannya.

Nonaktifkan kemampuan yang tidak Anda gunakan

Kurangi permukaan serangan aplikasi dengan menonaktifkan API publik jika tidak diperlukan dan memblokir node atau fitur berisiko tinggi yang tidak diperlukan oleh model operasi Anda.

Gunakan kontrol SSRF dan secret secara eksplisit

Untuk workflow yang dapat membuat permintaan HTTP sewenang-wenang, evaluasi perlindungan SSRF n8n dan jaga kerahasiaan kode workflow, repositori publik, dan file lingkungan yang dapat dibaca secara luas.

Batasi endpoint pengelolaan yang tidak digunakan: N8N_PUBLIC_API_DISABLED=true menonaktifkan n8n REST publik API, dan N8N_PUBLIC_API_SWAGGERUI_DISABLED=true menonaktifkan taman bermain API secara terpisah. Lakukan ini hanya jika integrasi Anda tidak memerlukan fitur tersebut. Menonaktifkan REST API tidak mengautentikasi URL webhook workflow. Gunakan MFA untuk pengguna editor, dan kebijakan terpusat hanya jika edisi n8n Anda mendukungnya.

FAQ

n8n VPS keamanan: pertanyaan umum

Haruskah port n8n diekspos secara langsung?

Ketika proxy terbalik adalah titik masuk publik, ekspos proxy tersebut dan pertahankan port aplikasi di belakangnya daripada mempublikasikan layanan yang tidak perlu secara luas.

Haruskah PostgreSQL atau Redis bersifat publik?

Biasanya tidak. Mereka hanya dapat dijangkau oleh sistem yang memerlukannya. Paparan publik meningkatkan permukaan serangan tanpa membantu operasi n8n normal.

Mengapa kunci enkripsi n8n penting?

Ini melindungi kredensial yang disimpan oleh n8n dan harus tetap konsisten di seluruh deployment. Kehilangannya dapat mencegah data yang dipulihkan menghasilkan kredensial terenkripsi yang dapat digunakan.

Apakah node komunitas aman?

Mereka memperluas n8n dengan kode pihak ketiga, sehingga mereka harus diperlakukan sebagai ketergantungan perangkat lunak dengan rantai pasokan dan risiko hak istimewa mereka sendiri. Instal hanya apa yang Anda percayai dan butuhkan.

Apakah HTTPS membuat instance n8n yang self-hosted aman?

No. HTTPS melindungi transportasi. Keamanan produksi juga memerlukan pengerasan host, kontrol akses, layanan backend pribadi, perlindungan secret, kemampuan workflow yang aman, pemantauan dan pembaruan.

Bisakah editor n8n bersifat pribadi sementara webhook produksi masih berjalan?

Ya. Reverse proxy atau VPN tepercaya dapat membatasi akses editor/admin secara terpisah dari webhook produksi publik dan jalur panggilan balik OAuth. Uji proses masuk tepercaya dan pengiriman webhook eksternal setelah setiap perubahan aturan akses untuk menghindari pemblokiran integrasi Anda secara tidak sengaja.

Bagaimana cara mengautentikasi webhook n8n yang masuk?

Konfigurasikan otentikasi Dasar, Header, atau JWT di node Webhook ketika pengirim mendukungnya. Anda juga dapat menggunakan Daftar IP yang Diizinkan dan memeriksa tanda tangan penyedia jika tersedia. Jangan hanya mengandalkan jalur yang tampak secret, dan validasi permintaan sebelum memicu tindakan API yang sensitif.
