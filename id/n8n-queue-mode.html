SKALA

n8n Queue Mode

Queue Mode memisahkan eksekusi workflow dari proses n8n utama. Mesin virtual utama menerima pemicu dan membuat eksekusi, Redis mengoordinasikan queue, worker menjalankan tugas, dan PostgreSQL menyimpan workflow bersama dan data eksekusi.

KEPUTUSAN CEPAT

Apakah Anda benar-benar memerlukan Queue Mode?

Tetap gunakan mode reguler ketika

Satu instance menangani eksekusi puncak dengan nyaman dan CPU, RAM serta latensi eksekusi tetap stabil. Queue Mode menambahkan komponen yang belum Anda perlukan.

Pertimbangkan Queue Mode ketika

Eksekusi paralel yang berkelanjutan menimbulkan perselisihan, latensi eksekusi meningkat karena beban, atau Anda perlu menambah kapasitas eksekusi dengan menjalankan banyak worker.

Skalakan secara vertikal terlebih dahulu ketika

Kemacetannya tidak cukup CPU atau RAM dan satu instance yang lebih besar masih dapat memenuhi beban kerja dengan baik.

Ukur sebelum mengubah arsitektur

Gunakan konkurensi puncak, CPU, RAM, durasi eksekusi, kedalaman queue, dan tekanan basis data untuk membenarkan perpindahan tersebut.

ARSITEKTUR

Cara kerja Queue Mode n8n

1 · UtamaMenerima permintaan pengatur waktu, webhook, dan workflow serta membuat eksekusi alih-alih melakukan eksekusi produksi itu sendiri.
2 · RedisBertindak sebagai perantara pesan. Ini menyimpan pesan eksekusi yang tertunda sehingga worker berikutnya yang tersedia dapat mengklaim pekerjaan.
3 · WorkerMenerima ID eksekusi, memuat data workflow dari database bersama, menjalankan workflow, dan menulis kembali hasilnya.
4 · PostgreSQLMenyediakan workflow persisten dan data eksekusi bersama. Queue Mode terdistribusi tidak didukung di SQLite.

PERSYARATAN INTI

Komponen yang dibutuhkan setiap deployment Queue Mode

Redis

Semua proses utama dan worker memerlukan akses yang andal ke layanan Redis yang digunakan untuk koordinasi queue.

PostgreSQL

Utama dan worker harus berbagi database. Queue Mode adalah arsitektur terdistribusi dan tidak boleh dirancang sekitar SQLite.

Konfigurasi n8n yang cocok

Utama dan worker harus menjalankan Queue Mode dan berbagi konfigurasi yang diperlukan untuk mengakses Redis, PostgreSQL dan kredensial terenkripsi.

Kapasitas worker

Worker membutuhkan CPU dan RAM yang cukup untuk workflow yang mereka jalankan. Menambahkan proses tidak menghilangkan biaya sumber daya dari setiap eksekusi.

Aktifkan Queue Mode pada stack yang self-hosted. Pertama konfirmasikan bahwa layanan utama n8n dan setiap worker dapat menjangkau database PostgreSQL dan Redis yang sama melalui jaringan pribadi. Tetapkan EXECUTIONS_MODE=queue pada utama dan worker, dan pasokan QUEUE_BULL_REDIS_HOST=redis dan QUEUE_BULL_REDIS_PORT=6379 kapan redis adalah nama layanan Compose Anda yang sebenarnya. Gunakan DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres dan mencocokkan DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER dan DB_POSTGRESDB_PASSWORD pada setiap proses; ganti contoh nama layanan dengan milik Anda. Berikan yang sebenarnya ada N8N_ENCRYPTION_KEY kepada mereka semua. Jangan pernah memublikasikan port host Redis atau PostgreSQL hanya untuk menghubungkan container di jaringan Compose yang sama.

Luncurkan eksekutor, bukan editor kedua. Tambahkan layanan worker n8n menggunakan versi gambar n8n yang disematkan dan pengaturan bersama sebagai yang utama, tetapi jalankan dengan worker perintah. Jika Anda menamai layanan itu n8n-worker, mulailah dengan docker compose up -d n8n-worker. Setelah mengonfirmasi eksekusi aktual pada satu worker, Anda dapat menggunakannya docker compose up -d --scale n8n-worker=2 untuk memulai worker kedua dari layanan itu. Ini adalah tambahan pada yang ada dikonfigurasi dengan benar Buat stack, bukan file instalasi mandiri; simpan volume persisten, HTTPS proxy, secret, dan backup Anda yang ada.

Queue Mode Tulis fragmen untuk stack yang ada. Gabungkan contoh di bawah ini ke dalam contoh Anda saat ini compose.yaml; itu tidak penyebaran yang berdiri sendiri secara lengkap. Ini mengasumsikan Anda sudah memiliki pribadi yang persisten postgres dan n8n layanan, yang sudah ada N8N_VERSION sematkan di lingkungan Anda dan perlindungan Anda sendiri POSTGRES_PASSWORD dan asli N8N_ENCRYPTION_KEY. Cocokkan nama, volume, database, dan versi n8n dengan proyek yang ada. Tambahkan pengaturan Queue Mode Redis dan EXECUTIONS_MODE=queue ke layanan utama yang ada juga, seperti dijelaskan di atas.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Tidak ada port host yang dipublikasikan untuk Redis atau worker dalam fragmen ini. Redis persistensi tambahan saja adalah lapisan pemulihan tambahan, tidak pengganti backup di luar server. Pertahankan HTTPS dan konfigurasi autentikasi yang ada tidak berubah. Untuk node Kode yang memerlukan runner tugas eksternal, konfigurasikan proses runner untuk deployment worker Anda secara terpisah; Queue Mode itu sendiri tidak menggantikan pelari tugas.

Mengonversi instance SQLite yang ada? Jangan sekadar berubah DB_TYPE dan memulai dengan database PostgreSQL yang kosong: hal ini tidak akan memigrasikan workflow dan kredensial lama. Sebelum peralihan apa pun, buat backup basis data sumber, tetap ada .n8n direktori dan kunci enkripsi asli; gunakan prosedur n8n ekspor/impor atau migrasi yang didukung, lalu verifikasi workflow dan kredensial terenkripsi pada target terpisah. Simpan file asli untuk rollback dan gunakan panduan Backup & Pemulihan yang ditautkan di bawah untuk persiapan pemulihan. Jangan pernah menghapus database.sqlite sebagai jalan pintas.

KONKURENSI PEKERJA

Skalakan worker berdasarkan jumlah dan concurrency per worker

Setiap worker dapat memproses beberapa pekerjaan secara bersamaan. Konkurensi worker default n8n saat ini adalah 10 dan dokumentasinya merekomendasikan konkurensi 5 atau lebih tinggi. Konkurensi yang sangat rendah dikombinasikan dengan banyak worker dapat membuat koneksi database yang tidak perlu dan menghabiskan kumpulan koneksi database.

Tingkatkan konkurensi ketika

Seorang worker memiliki backup CPU dan RAM dan sebagian besar workflow menunggu pada layanan eksternal daripada memenuhi komputasi atau memori.

Tambahkan worker ketika

Satu proses worker menjadi hambatan dan database, Redis dan infrastruktur memiliki kapasitas untuk eksekusi yang lebih paralel.

Kurangi konkurensi ketika

Workflow individual adalah pekerjaan yang penuh memori atau CPU dan pekerjaan paralel menyebabkan perselisihan, tekanan OOM, atau waktu eksekusi yang tidak stabil.

Pantau PostgreSQL

Lebih banyak worker dan lebih banyak konkurensi meningkatkan aktivitas database. Menskalakan kapasitas eksekusi tanpa kapasitas database dapat menghilangkan hambatan, bukan menghilangkannya.

Ketahui batas konkurensi mana yang benar-benar berlaku. Seorang worker dapat mulai menggunakan n8n worker --concurrency=5, atau perintah worker yang setara di layanan Compose Anda. Jika N8N_CONCURRENCY_PRODUCTION_LIMIT secara eksplisit disetel ke nilai selain -1, pengaturan tersebut diutamakan dalam Queue Mode; jika tidak, n8n menggunakan milik worker --concurrency nilai atau defaultnya 10. Jangan mengalikan jumlah worker dengan nominal default dan menyebutnya throughput terjamin: kapasitas aktual bergantung pada durasi pekerjaan, CPU, memori, API eksternal, dan koneksi PostgreSQL.

WEBHOOK

Queue Mode dapat menambah latensi handoff eksekusi

Proses utama atau webhook menerima permintaan HTTP, namun worker melakukan eksekusi workflow. Penyerahan melalui Redis menambah beberapa overhead. Untuk webhook yang sensitif terhadap latensi, ukur waktu respons menyeluruh daripada mengasumsikan lebih banyak worker secara otomatis membuat setiap permintaan menjadi lebih cepat.

TerimaProses utama/webhook menerima permintaan tersebut.
QueueEksekusi diserahkan kepada Redis.
JalankanWorker yang tersedia menjalankan workflow.
TanggapiHasilnya diteruskan kembali melalui jalur queue bila diperlukan.

Arahkan traffic webhook ke proses yang benar. Dengan berdedikasi n8n webhook prosesor di belakang proxy terbalik atau penyeimbang beban, merutekan jalur produksi /webhook/* dan /webhook-waiting/* ke pemroses webhook; simpan /webhook-test/*, editor dan permintaan API di main. Jangan memasukkan main ke dalam kumpulan penyeimbang beban webhook produksi kecuali Anda dengan sengaja menerima beban kerja tambahan tersebut. SEBUAH Tanggapi Webhook workflow mungkin membuat klien menunggu hingga worker selesai dan mengembalikan responsnya, jadi Queue Mode bukanlah janji respons instan HTTP atau waktu tunggu nol. Uji perilaku panggilan balik dan respons eksternal yang sebenarnya sebelum mengalihkan traffic.

DATA BINER

Jangan mengabaikan penyimpanan bersama

Batasan sistem file

Queue Mode tidak mendukung penyimpanan data biner sistem file sebagai model persistensi bersama untuk worker terdistribusi.

Penyimpanan biner eksternal

Ketika workflow harus mempertahankan data biner di seluruh worker yang terdistribusi, gunakan desain penyimpanan yang dapat diakses oleh setiap instans yang diperlukan, seperti penyimpanan objek eksternal yang didukung.

Respons webhook yang besar

Respons webhook dari worker kembali ke proses penerimaan. Badan respons yang besar dapat meningkatkan tekanan memori Redis dan memerlukan konfigurasi penyimpanan respons yang disengaja.

Rencanakan sebelum mendistribusikan worker

Beban kerja yang sangat bergantung pada file lokal harus didesain ulang untuk persistensi bersama sebelum worker disebar ke seluruh mesin.

Batas respons webhook yang besar. Dokumentasi n8n saat ini memberi N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX default dari 64 MiB untuk respons worker dikirim kembali melalui queue. Redis dapat menampung beberapa salinan dalam penerbangan, sehingga anggaran kira-kira 1.5 kali ukuran respons dalam memori Redis per respons besar secara bersamaan. Tanpa pembongkaran, respons yang terlalu besar akan gagal dan bukannya menjadi lebih cepat secara ajaib dengan menambahkan worker.

Batasan versi dan lisensi. Dari n8n 2.34.0, worker dapat menggunakan N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true untuk memindahkan badan respons webhook yang berukuran besar ke penyimpanan biner bersama yang dapat dibaca, tetapi tingkatkan terlebih dahulu setiap prosesor utama dan webhook hingga 2.34.0 atau lebih baru. Yang dipilih N8N_DEFAULT_BINARY_DATA_MODE harus benar-benar menyimpan data dan dapat dibaca oleh setiap proses yang berpartisipasi. Penyimpanan biner S3 dan Azure eksternal memerlukan self-host yang valid Bisnis atau Perusahaan lisensi; jangan berasumsi Edisi Komunitas dapat mengaktifkannya. Itu database mode biner dapat memindahkan respons berukuran besar tanpa penyimpanan eksternal berbayar, namun instance utama memuat seluruh isi yang disimpan ke dalam memori dan penyimpanan database memiliki batas ukuran filenya sendiri. Untuk pembongkaran badan respons secara khusus, n8n juga menjelaskan yang dibagikan filesystem pilihan ketika setiap instance memasang disk yang sama, namun secara eksplisit tidak merekomendasikan pengaturan itu. Jangan salah mengartikan jalur offload khusus ini sebagai dukungan terhadap data biner persisten berbasis sistem file dalam deployment Queue Mode terdistribusi. Periksa edisi, versi, dan konfigurasi penyimpanan Anda sebelum mengaktifkan offload.

PEMANTAUAN

Ukur apakah Queue Mode benar-benar membantu

Queue depth

Queue yang bertambah lebih cepat daripada yang terkuras oleh worker menunjukkan kapasitas eksekusi yang tidak mencukupi atau adanya hambatan di hilir.

CPU & RAM worker

Ukur saturasi dan puncak memori per worker. Worker yang menganggur dengan queue yang terus bertambah menunjukkan kendala lain.

Latensi eksekusi

Lacak penundaan antara eksekusi yang dibuat dan sebenarnya dimulai, tidak hanya waktu proses workflow itu sendiri.

Pemeriksaan kesehatan

Endpoint kesehatan worker dapat melaporkan apakah worker masih hidup dan apakah database serta koneksi Redis sudah siap.

Verifikasi eksekusi pada worker, bukan hanya container hijau. Dengan stack Compose yang dikonfigurasi dengan benar, periksa docker compose ps dan docker compose logs --tail=100 n8n-worker (ganti nama layanan jika berbeda). Jalankan yang tidak berbahaya produksi yang diterbitkan workflow menggunakan pemicu terjadwal atau webhook pengujian, lalu cocokkan eksekusinya dalam tampilan Eksekusi n8n dengan pemrosesan worker sebenarnya di log worker. Editor yang berhasil dibuka, container Redis yang sedang berjalan, atau eksekusi yang diantri saja bisa melakukannya tidak membuktikan bahwa seorang worker telah melakukan pekerjaannya.

Periksa ketergantungan dan kesiapan. Dengan contoh nama layanan default, docker compose exec -T redis redis-cli ping harus menerima PONG ketika Redis otentikasi mengizinkannya, dan docker compose exec -T postgres pg_isready -U n8n -d n8n memeriksa kesiapan PostgreSQL (menyesuaikan kredensial dan nama layanan). Aktifkan QUEUE_HEALTH_CHECK_ACTIVE=true pada seorang worker ketika Anda membutuhkan pribadinya /healthz dan /healthz/readiness endpoint; endpoint kesiapan memeriksa konektivitas Redis/database. Jangan mengekspos endpoint worker tersebut secara publik hanya untuk memantaunya.

Jalankan secara manual adalah ujian yang berbeda. Secara default OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, jadi menjalankan workflow secara manual di editor dapat dijalankan di main bahkan ketika Queue Mode dikonfigurasi dengan benar. Setel ke true hanya jika Anda bermaksud mengirimkan eksekusi manual ke worker dan telah memeriksa perubahan dalam lingkungan pementasan. Worker Queue Mode juga berbeda dari pelari tugas eksternal n8n, yang memiliki persyaratan konfigurasi terpisah untuk eksekusi node kode.

BATAS KETERSEDIAAN TINGGI

Queue Mode menskalakan eksekusi, namun tidak secara otomatis membuat proses utama menjadi sangat tersedia

Bagikan kunci enkripsi

Setiap worker harus menggunakan hal yang sama N8N_ENCRYPTION_KEY sebagai instans utama sehingga worker dapat mendekripsi kredensial yang diperlukan oleh eksekusi workflow.

Jaga agar versi tetap selaras

Proses utama, webhook, dan worker harus menjalankan versi n8n yang sama. Versi campuran dapat menimbulkan perilaku yang tidak kompatibel selama perubahan berkelanjutan.

Prosesor webhook adalah lapisan penskalaan terpisah

Ketika volume webhook yang masuk menjadi penghambat, pemroses webhook khusus dapat berada di belakang penyeimbang beban sementara worker menangani eksekusi. Jangan tambahkan lapisan ini kecuali volume permintaan yang diukur membenarkannya.

Multi-utama adalah fitur yang berbeda

Menjalankan beberapa proses utama untuk ketersediaan tinggi tidak sama dengan Queue Mode biasa. n8n saat ini mendokumentasikan multi-utama sebagai fitur Perusahaan yang self-hosted dengan penyeimbang beban tambahan dan persyaratan sesi.

FAQ

n8n Queue Mode: pertanyaan umum

Apakah Queue Mode n8n memerlukan Redis?

Ya. Redis adalah perantara pesan yang mengoordinasikan eksekusi yang tertunda antara instance utama dan worker.

Bisakah Queue Mode menggunakan SQLite?

Tidak untuk arsitektur Queue Mode terdistribusi. Utama dan worker memerlukan akses database bersama, dan n8n mendokumentasikan PostgreSQL sebagai database untuk pengaturan ini.

Berapa banyak worker yang harus saya jalankan?

Tidak ada hitungan universal. Mulai dari pengukuran konkurensi dan pemanfaatan worker, lalu tambahkan kapasitas sambil memantau PostgreSQL, Redis, CPU, RAM dan kedalaman queue.

Apa itu konkurensi worker n8n?

Ini adalah jumlah pekerjaan yang dapat diproses oleh seorang worker secara paralel. Default saat ini adalah 10, dan n8n merekomendasikan konkurensi worker 5 atau lebih tinggi daripada membuat banyak worker dengan konkurensi rendah.

Haruskah saya mengaktifkan Queue Mode pada VPS kecil?

Hanya jika beban kerja membenarkannya. Deployment kecil yang berjalan dengan nyaman sebagai satu instance biasanya lebih mudah dioperasikan tanpa Redis dan worker terpisah.
