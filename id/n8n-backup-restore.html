CADANGAN & PEMULIHAN

Backup dan Pemulihan n8n

Untuk mencadangkan dan memulihkan n8n yang self-hosted, lindungi database SQLite Anda atau dump PostgreSQL yang konsisten, folder .n8n yang persisten dan kunci enkripsi asli, konfigurasi deployment, dan setiap ketergantungan biner atau file terpasang eksternal. Simpan salinan terenkripsi dari VPS dan uji pemulihan pada instance terpisah. Gunakan workflow CLI dan ekspor kredensial untuk pemulihan selektif; JSON ekspor saja bukan merupakan backup server lengkap.

DAFTAR PERIKSA CEPAT

Apa yang harus dilindungi oleh backup n8n

Basis data

Cadangkan database PostgreSQL atau file database SQLite yang digunakan oleh instance. Basis data berisi status inti n8n seperti workflow, kredensial, dan data eksekusi.

Kunci enkripsi

Pertahankan kunci enkripsi n8n yang tepat secara terpisah dan aman. Kredensial terenkripsi yang dipulihkan bergantung pada kunci yang sama.

File persisten

Sertakan direktori data n8n yang persisten dan semua file terpasang, penyimpanan data biner, atau aset workflow yang diandalkan oleh deployment Anda.

Konfigurasi deployment

Simpan file Compose/konfigurasi dan konfigurasi non-secret yang diperlukan untuk membangun kembali stack. Lindungi secret dengan kontrol akses yang sesuai.

DUA TINGKAT CADANGAN

Ekspor logis vs pemulihan bencana lengkap

Ekspor workflow & kredensial

n8n CLI ekspor berguna untuk migrasi, salinan workflow berversi, dan restorasi selektif. Kredensial dapat diekspor dalam bentuk terenkripsi dan kemudian diimpor dengan kunci enkripsi yang cocok. Untuk memulihkan satu workflow saja, gunakan menu tiga titik editor workflow untuk Mengunduh JSON, lalu Impor dari File ke workflow tinjauan baru atau instans terisolasi. Periksa kredensial, ID workflow, dan parameter node sebelum mengganti workflow langsung: memulihkan workflow JSON tidak memulihkan seluruh server.

Ekspor entitas

CLI dapat mengekspor entitas database untuk memindahkan data antar tipe database yang didukung. Tabel riwayat eksekusi bersifat opsional karena ukurannya bisa sangat besar.

Pemulihan instans penuh

Untuk skenario server mati, lindungi database aktual, kunci enkripsi, data persisten, dan dependensi deployment. Jangan berasumsi workflow JSON ekspor merekonstruksi seluruh instance.

Snapshot penyedia

Snapshot VPS berguna sebagai lapisan pemulihan tambahan, namun tidak boleh menjadi satu-satunya salinan dan tidak boleh menggantikan backup aplikasi/database yang diverifikasi secara independen.

DATABASE

Cadangkan database secara konsisten

PostgreSQL

Gunakan metode backup PostgreSQL yang konsisten dan simpan backup yang dihasilkan jauh dari VPS. Salinan database pada disk gagal yang sama bukanlah pemulihan bencana.

SQLite

Jika deployment menggunakan SQLite, lindungi file database dari direktori data n8n yang persisten. Hindari menyalin database dalam keadaan tidak aman saat sedang dimodifikasi secara aktif.

Riwayat eksekusi

Putuskan apakah data eksekusi historis merupakan bagian dari tujuan pemulihan Anda. Hal ini dapat membuat backup jauh lebih besar, sehingga persyaratan retensi dan kepatuhan harus menentukan pilihan.

Versi basis data

Catat mesin database dan versi yang digunakan oleh penyebaran sumber sehingga lingkungan pemulihan dapat dipersiapkan dengan kompatibel.

PostgreSQL pada Docker Compose VPS. Jika layanan PostgreSQL diberi nama postgres dan database/penggunanya keduanya n8n, perintah berikut membuat dump format khusus PostgreSQL yang konsisten pada host. Periksa file Compose Anda yang sebenarnya sebelum menjalankannya, dan sesuaikan kredensial database dan nama layanan. pg_dump dapat menghasilkan snapshot yang konsisten secara logis saat PostgreSQL sedang berjalan; memang demikian tidak backup yang terpisah .n8n folder pengguna atau data biner eksternal.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Pemeriksaan daftar arsip menemukan masalah format yang jelas namun tidak membuktikan bahwa data dapat dipulihkan. Simpan salinan terenkripsi di luar server dan latih pemulihan. Gunakan dokumentasi resmi PostgreSQL pg_dump untuk opsi khusus basis data.

SQLite pada Docker. Untuk deployment SQLite default, database.sqlite dan konfigurasi kunci enkripsi yang dihasilkan berada di dalam persisten .n8n folder (biasanya dipasang di /home/node/.n8n). Jangan pernah memperlakukan salinan langsung SQLite sebagai sesuatu yang konsisten. Hentikan n8n dan penulis basis data lainnya sebelum menyalin folder, atau gunakan mekanisme backup online yang didukung SQLite ketika gangguan tidak mungkin dilakukan:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Ini adalah perintah ilustratif untuk layanan dan jalur yang ditampilkan, bukan tata letak volume universal. Folder yang disalin awalnya masih di VPS yang sama; mentransfer dan melindunginya di luar server. Jika ada worker queue atau penulis lain, hentikan juga dan ikuti desain deployment sebenarnya. Panduan backup penuh n8n saat ini mendokumentasikan persyaratan konsistensi SQLite.

Memulihkan folder SQLite default ke target yang bersih: pertama-tama hentikan layanan n8n dan semua penulis basis data. Setelah container layanan n8n yang kompatibel dan volume tujuannya ada, salin backupnya .n8n isinya kembali ke direktori persisten yang sama. Ini akan menimpa file target, jadi jangan jalankan pada instance dengan data yang perlu Anda simpan:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker dapat disalin ke container yang dihentikan, tetapi kepemilikan tujuan mungkin berbeda dari aslinya; pastikan konfigurasi yang dipulihkan dan file database dapat dibaca dan ditulis oleh proses n8n sebelum memulainya. Jika konfigurasi Compose Anda yang sebenarnya menggunakan jalur atau pengikatan yang berbeda, sesuaikan salinannya. Docker Compose referensi salinan. Memulihkan folder n8n saja tidak cukup untuk deployment yang menggunakan database PostgreSQL terpisah.

RAHASIA KRITIS

Kunci enkripsi adalah bagian dari pemulihan

n8n mengenkripsi kredensial yang disimpan dengan kunci enkripsi instans. Ekspor database atau kredensial terenkripsi tanpa kunci yang cocok dapat membuat workflow yang dipulihkan tidak dapat menggunakan kredensial yang disimpan.

Jika Anda menyetel N8N_ENCRYPTION_KEY, pulihkan secret persisnya. Jika tidak, kunci yang dihasilkan disimpan dalam file .n8n/config yang persisten: lindungi konfigurasi tersebut saat membuat backup atau membangun kembali. Simpan kunci pemulihan dengan aman di luar VPS. Dalam Queue Mode, semua proses utama dan worker harus menggunakan kunci yang sama.

LakukanSimpan salinan terlindungi dari kunci persis yang digunakan oleh produksi.
LakukanVerifikasikan lingkungan pemulihan menggunakan kunci tersebut sebelum menguji kredensial.
JanganAndalkan kunci yang baru dibuat setelah membangun kembali server.
JanganKomit kunci ke repositori publik atau simpan di samping backup yang tidak terlindungi.

FILE & DATA BINER

Backup database mungkin tidak mencakup setiap ketergantungan workflow

Data .n8n yang persisten

Temukan dan pertahankan folder pengguna .n8n yang sebenarnya, bukan hanya gambar container. Dalam deployment Docker tipikal, ini dipasang di /home/node/.n8n; di luar Docker defaultnya adalah ~/.n8n. Jika N8N_USER_FOLDER dikonfigurasi, n8n membuat .n8n di dalam direktori induk yang ditentukan. Sertakan kunci konfigurasinya dan data eksekusi SQLite, biner, atau sistem file lokal apa pun yang digunakan instalasi Anda.

File workflow yang terpasang

Jika workflow membaca atau menulis direktori yang dipasang di host, buat backup direktori tersebut secara terpisah. Memulihkan n8n tanpanya dapat menyebabkan workflow yang valid menjadi rusak.

Data biner

Identifikasi mode penyimpanan dan pulihkan setiap ketergantungan eksternal. Data biner atau eksekusi berbasis sistem file mungkin berada di .n8n atau direktori khusus; S3/Azure Blob atau penyimpanan eksternal terkonfigurasi lainnya memerlukan pengaturan salinan dan aksesnya sendiri yang dapat dipulihkan. Dump database saja tidak dapat menggantikan file-file tersebut.

Node komunitas

Rekam paket dan versi komunitas, dan buat backup direktori node khusus tambahan yang dikonfigurasi melalui N8N_CUSTOM_EXTENSIONS. Direktori tersebut dapat berada di luar .n8n; pemulihan database dan folder pengguna saja mungkin masih membuat workflow node kustom tidak dapat digunakan.

STRATEGI OFF-SERVER

Backup pada VPS yang sama hanyalah salinan lokal

Salinan lokalBerguna untuk rollback cepat, namun rentan terhadap kehilangan server, kegagalan disk, dan kesalahan destruktif.
Salinan di luar serverSimpan setidaknya satu backup di penyimpanan yang independen dari produksi VPS.
Salinan berversiPertahankan beberapa titik pemulihan sehingga kerusakan atau perubahan buruk tidak menimpa satu-satunya backup yang dapat digunakan.
Kontrol aksesBackup dapat berisi kredensial, logika workflow, dan data bisnis sensitif. Enkripsi dan batasi dengan tepat.
PemantauanPeringatan ketika backup terjadwal gagal atau berhenti menghasilkan titik pemulihan baru.

Buatlah jadwal terukur. Catat stempel waktu setiap backup yang berhasil, penyelesaian transfer, ukuran file, versi database sumber, lokasi pemulihan kunci enkripsi, dan pengujian pemulihan terbaru yang berhasil. Peringatan tentang file yang hilang, gagal, atau tiba-tiba kosong. Enkripsi arsip backup sebelum mengirimnya keluar dari VPS dan batasi akses ke secret pemulihan. Beberapa titik pemulihan bertanggal melindungi terhadap penemuan korupsi hanya setelah salinan terbaru menimpa salinan terakhir yang sehat.

Misalnya, jika Anda dapat mentolerir perubahan yang hilang paling lama enam jam, jadwal backup enam jam yang berhasil adalah titik awal, bukan jaminan: workeran yang gagal dan penundaan replikasi di luar server dapat meningkatkan kerugian sebenarnya. Tetapkan retensi dan pemulihan irama sesuai RPO/RTO dan persyaratan data Anda, daripada menerapkan kebijakan universal 7-hari atau 30-hari.

KEMBALIKAN PESANAN

Pulihkan dalam urutan yang terkendali

1 · MempersiapkanMenyediakan server, database, dan lingkungan container/runtime yang kompatibel.
2 · Kembalikan secretKonfigurasikan kunci enkripsi n8n asli dan secret deployment yang diperlukan dengan aman.
3 · Memulihkan basis dataPulihkan PostgreSQL atau SQLite dan verifikasi n8n dapat terhubung ke data yang diharapkan.
4 · Pulihkan filePulihkan direktori persisten, data biner, dan aset workflow yang terpasang.
5 · Mulai n8nTampilkan aplikasi dengan hostname, database, dan konfigurasi lingkungan yang diharapkan.
6 · ValidasiKonfirmasikan pepayload pengguna, workflow, dan kredensial, lalu jalankan workflow yang representatif dan jalur webhook.

PostgreSQL contoh pemulihan bencana: pada a target pemulihan yang terpisah dan bersih yang sudah memiliki peran database yang benar dan kosong n8n basis data, mulai saja PostgreSQL. Tunggu sampai sehat sebelum mengimpor: docker compose up -d sendiri dapat kembali saat PostgreSQL masih diinisialisasi, jadi berikut ini pg_restore bisa gagal. Contohnya menggunakan --wait pada instalasi Compose modern dan memeriksa secara independen pg_isready. Konfigurasikan pemeriksaan kesehatan PostgreSQL yang sesuai untuk penantian yang andal, atau konfirmasikan kesiapan secara eksplisit sebelum melanjutkan. Jangan arahkan perintah ini ke database produksi yang terisi atau mulai n8n sebelum database dan pencocokannya .n8n kunci/data dipulihkan.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Tujuan harus memiliki versi PostgreSQL yang kompatibel, hak peran, ekstensi, dan konfigurasi n8n asli. Pulihkan .n8n ke volume persisten yang benar atau ikat mount menggunakan mekanisme backup Anda, menjaga kepemilikan dan izin. Pulihkan file biner eksternal, ekstensi khusus, konfigurasi Tulis dan secret, lalu mulai n8n pada versi yang kompatibel dan periksa lognya. Memulihkan database saja tidak akan memulihkan kunci: deployment PostgreSQL akan mempertahankan kunci tersebut .n8n/config kecuali Anda mengkonfigurasi secara eksplisit N8N_ENCRYPTION_KEY. referensi pg_restore · n8n urutan pemulihan instance penuh.

UJI KEMBALIKAN

Backup belum terbukti sampai proses pemulihan berhasil

Uji pada lingkungan yang bersih

Latihan nyata harus membuktikan bahwa backup dapat membangun kembali sebuah instance tanpa bergantung pada file yang tidak dideklarasikan yang tersisa di server produksi.

Periksa kredensial

Membuka workflow saja tidak cukup. Konfirmasikan kredensial terenkripsi yang dipulihkan benar-benar berhasil mendekripsi dan mengautentikasi.

Jalankan workflow yang representatif

Uji workflow yang bergantung pada webhook, API eksternal, file terpasang, dan node komunitas, bukan hanya memvalidasi otomatisasi sepele.

Ukur waktu pemulihan

Catat berapa lama waktu yang dibutuhkan untuk pemulihan dan langkah manual apa yang tersisa. Ini mengubah backup yang diasumsikan menjadi prosedur pemulihan operasional.

Latihan pemulihan terverifikasi: SQLite dan PostgreSQL

Lingkungan pengujian: n8n 2.42.5 dalam container Docker terisolasi pada pelari Tindakan GitHub sekali pakai, menggunakan workflow dua node sintetis. Pemeriksaan ini terus berjalan 8 Oktober 2026, bukan di server n8n pelanggan atau produksi.

SQLite: LULUSMengimpor workflow pengujian, mengekspornya, menghentikan semua penulis, mengarsipkan persisten yang didukung SQLite .n8n folder dan kunci enkripsi yang dihasilkannya, dipulihkan ke volume bersih, dimulai n8n, lalu diekspor kembali dan menjalankan workflow yang dipulihkan.
PostgreSQL: LULUSMengimpor workflow pengujian yang sama, membuat dan memeriksa format khusus pg_dump, memulihkannya menggunakan pg_restore ke dalam database PostgreSQL baru yang kosong, pulihkan yang terpisah .n8n folder, lalu mengekspor ulang dan menjalankan workflow yang dipulihkan.
Apa yang PASS buatJalur backup yang diuji mempertahankan workflow ini, kedua nodenya, serta koneksinya dan memungkinkan eksekusi setelah pemulihan. Ini adalah pengujian asap fungsional yang dapat direproduksi, bukan tolok ukur beban kerja.
Apa yang tidak diujiDekripsi dan autentikasi kredensial nyata, webhook produksi, worker Queue Mode dan Redis, penyimpanan biner S3/Azure, node kustom, akses pengguna/proyek, atau pemulihan instans produksi langsung. Jalankan latihan terpisah untuk setiap ketergantungan yang sebenarnya Anda gunakan.

Cara memperbanyak: gunakan instalasi n8n sekali pakai, buat workflow dua node yang tidak berbahaya, jalankan database yang berlaku ditambah backup folder persisten, pulihkan ke volume atau database yang bersih, lalu verifikasi node, koneksi, dan eksekusi aktual workflow yang dipulihkan. Pada sistem produksi juga memeriksa kredensial terenkripsi, webhook, dan file eksternal sebelum menyatakan pemulihan bencana terbukti.

Kembalikan daftar periksa penerimaan bor: menggunakan domain/lingkungan yang terisolasi; memeriksa apakah pengguna dan workflow ada, satu kredensial terenkripsi yang ada mengautentikasi tanpa masuk kembali, webhook produksi memanggil workflow yang dipulihkan, file yang dipasang dan lampiran biner tetap dapat dibaca, dan integrasi dengan node komunitas yang diperlukan dimuat. Konfirmasikan usia backup, waktu henti terukur, dan aksesibilitas di luar server. Jika ada pemeriksaan penting yang gagal, tandai titik pemulihan tersebut belum terverifikasi daripada melaporkan backup sebagai selesai.

CLI BATAS CADANGAN

Ketahui secara pasti workflow dan ekspor kredensial apa yang tidak dapat dipulihkan

Ekspor CLI bukan backup instance lengkap

Ekspor backup workflow dan kredensial tidak mencakup pengguna dan peran, riwayat eksekusi dan log, variabel, atau pengaturan instans seperti kunci enkripsi.

Pemulihan instance baru memerlukan pemilik

Pada contoh yang bersih, selesaikan penyiapan pemilik sebelum mengimpor kredensial. Pemulihan multi-pengguna atau proyek mungkin juga memerlukan penetapan pengguna atau proyek yang benar.

ID yang diimpor dapat menimpa item yang sudah ada

Workflow dan ekspor kredensial mempertahankan ID aslinya. Mengimpor ke instance yang sudah berisi ID yang sama dapat menggantikan item yang sudah ada.

Publikasikan workflow yang diimpor dengan sengaja

CLI impor biasanya membuat workflow tidak aktif. Pada n8n 2.x, periksa status penerbitan setiap workflow yang diimpor dan publikasikan hanya workflow yang ingin Anda jalankan; Server yang self-hosted CLI juga mendukung n8n terbitkan: workflow --id=YOUR_WORKFLOW_ID. Ketika n8n berjalan, perubahan status publikasi/batalkan Server CLI hanya berlaku setelah memulai ulang n8n. Mulai ulang sebelum memverifikasi pemicu terjadwal dan webhook produksi atau mengalihkan traffic.

Contoh ekspor massal untuk Docker Compose: jika layanan n8n Anda diberi nama n8n, Anda dapat menjalankan backup resmi CLI di bawah. Jalur keluaran sengaja berada di dalam persisten yang dipasang .n8n direktori, karena direktori sembarang di dalam container mungkin hilang saat dibuat ulang. Konfirmasikan bahwa direktori dapat ditulis oleh pengguna container n8n. Pertahankan workflow dan kredensial JSON tetap masuk direktori terpisah—n8n mendokumentasikan masalah impor ketika kedua jenis berbagi direktori.

n8n 2.x draf versus backup yang dipublikasikan: normal --backup ekspor workflow menangkap draf saat ini; ini mungkin berbeda dari versi yang diterbitkan dalam produksi. Untuk mempertahankan versi aktual workflow tertentu yang dipublikasikan, ekspor secara terpisah menggunakan docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, setelah memastikan bahwa folder keluaran ada dan dapat ditulis. CLI juga dapat mengekspor versi historis menggunakan --version=VERSION_ID. Simpan tangkapan ini di luar server bersama dengan backup penuh; jangan menganggap draf JSON mencatat status publikasi langsung.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Yang disalin ~/n8n-recovery/cli direktori masih di VPS sampai Anda memindahkannya ke lokasi backup yang aman dan independen. Ekspor kredensial dienkripsi secara default dan memerlukan kunci enkripsi yang cocok saat mengimpor. Hindari menggunakan --decrypted kecuali untuk migrasi yang dikontrol ketat: ia menulis secret dalam teks biasa. Jangan pernah melakukan ekspor yang berisi logika atau kredensial workflow sensitif ke repositori GitHub publik. Beberapa templat backup kredensial GitHub pihak ketiga dengan sengaja mengekspor secret yang didekripsi; repositori pribadi adalah pembatasan akses, bukan enkripsi. Periksa pengaturan ekspor aktual dan izin penyimpanan setiap templat, enkripsi secret sebelum transfer ke luar server, dan putar kredensial apa pun yang terekspos melalui unggahan teks biasa yang tidak diinginkan.

Contoh impor massal: pada target yang bersih, selesaikan pengaturan pemilik, berikan kunci enkripsi asli dan pastikan file backup yang disimpan tersedia pada pemulihan itu VPS. Berikut ini membuat folder tujuan dan menyalinnya workflows/ dan credentials/ subfolder dari host ke dalam container n8n; sesuaikan jalur jika tata letak volume Docker Anda berbeda:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Periksa kepemilikan dan akses file untuk pengguna container n8n. Jangan mengimpor instans produksi yang terisi tanpa rollback terverifikasi: workflow dan ID kredensial dapat menimpa entri yang sudah ada. Kemudian jalankan:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

ID yang diimpor dapat menggantikan workflow atau kredensial yang ada; gunakan instance pengujian terisolasi untuk uji coba dan periksa kredensial serta status aktivasi/penerbitan setelahnya. Di n8n 2.x, memulihkan draf JSON tidak dengan sendirinya membuktikan workflow telah dipublikasikan dan dapat menjalankan pemicu terjadwal. Keamanan impor: pada instance n8n non-multi-utama, pemicu cron yang sebelumnya aktif dapat terus berjalan setelah impor CLI hingga instance dimulai ulang. Hentikan atau isolasi pemicu produksi dan mulai ulang n8n sebelum mengaktifkan workeran yang dipulihkan; verifikasi tidak ada eksekusi duplikat. CLI ekspor bisa tidak berisi pengguna asli, log eksekusi, variabel instan, atau kunci enkripsi. --backup set --all --pretty --separate, bukan 'contoh penuh'. Sumber: panduan backup/pemulihan n8n resmi terkini dan referensi perintah n8n CLI.

Pemulihan massal dari GitHub atau templat Google Drive: ini merupakan alternatif untuk workflow JSON saja, bukan untuk database instans, pengguna, nilai kredensial terenkripsi, atau kunci enkripsi. Sebelum menjalankan templat berbasis API, verifikasi n8n API dan izin penyimpanannya, versi backup yang dipilih dan instans target, apakah templat tersebut memperbarui ID yang cocok dan membuat ulang workflow yang dihapus, dan apa fungsinya dengan penerbitan workflow. Tidak semua template membuat ulang ID yang hilang dari target; uji skenario tersebut secara terpisah sebelum mengandalkan pemulihan otomatis.

FAQ

Backup dan pemulihan n8n: pertanyaan umum

Apakah mengekspor workflow cukup untuk mencadangkan n8n?

Tidak. Ekspor workflow adalah salinan logis yang berguna, namun pemulihan lengkap juga memerlukan kredensial, kunci enkripsi yang cocok, status database, file persisten, dan penyimpanan data biner.

Apakah saya memerlukan kunci enkripsi n8n jika saya memiliki database?

Ya, jika Anda memerlukan kredensial terenkripsi yang disimpan dalam database tersebut agar tetap dapat digunakan. Simpan kunci asli dengan aman.

Haruskah saya mencadangkan PostgreSQL atau mengekspor workflow dan kredensial?

Untuk pemulihan bencana, lindungi database dan kunci enkripsi. Ekspor logis lebih berharga sebagai lapisan migrasi tambahan dan pemulihan selektif, bukan sebagai pengganti setiap bagian dari proses tersebut.

Bisakah snapshot VPS menjadi satu-satunya backup saya?

Lebih baik diperlakukan sebagai satu lapisan pemulihan. Simpan backup di luar server yang independen sehingga kegagalan penyedia, akun, server, atau snapshot tidak menghapus setiap titik pemulihan sekaligus.

Bagaimana saya tahu backup saya berfungsi?

Pulihkan ke lingkungan pengujian yang bersih, verifikasi dekripsi kredensial, dan jalankan workflow yang representatif. Workeran backup yang berhasil saja tidak membuktikan kemampuan pemulihan.

Apakah GitHub atau backup workflow Google Drive menyertakan secret kredensial yang disimpan?

Backup JSON khusus workflow tidak menyertakan nilai secret yang dikelola oleh penyimpanan kredensial n8n atau kunci enkripsi instans. Namun, JSON yang diekspor dapat mengekspos nama kredensial dan ID serta secret yang diketik langsung ke dalam parameter node, seperti header autentikasi. Periksa dan lindungi JSON yang diekspor sebelum mengunggah atau membagikannya. Untuk pemulihan penuh, buat backup database dan kunci asli, atau gunakan ekspor kredensial terenkripsi yang didukung CLI dengan pemulihan yang diuji. Templat GitHub atau Google Drive khusus workflow bukanlah pemulihan bencana sepenuhnya.

TUJUAN PEMULIHAN

Tentukan RPO dan RTO sebelum kejadian

RPO adalah kerugian maksimum yang dapat ditoleransi dari perubahan terkini. Ukur dari titik pemulihan terbaru yang dapat digunakan dan disimpan secara independen; workeran enam jam yang dijadwalkan tidak menghasilkan RPO enam jam jika ekspor atau transfer gagal. RTO adalah pemadaman maksimum yang dapat ditoleransi. Ukur hal ini dalam latihan pemulihan yang bersih, termasuk mengambil secret, memulihkan file eksternal, memeriksa ulang kredensial, dan menerbitkan workflow yang dipulihkan—bukan hanya memulai sebuah container.

KUNCI PEMULIHAN

Temukan kunci enkripsi asli sebelum membangun kembali

Jika produksi ditetapkan N8N_ENCRYPTION_KEY, jaga environment secret tersebut. Jika tidak, pertahankan kunci yang dihasilkan dalam .n8n/config asli. Periksa sumber mana yang sebenarnya digunakan oleh instance yang dipulihkan sebelum mengimpor kredensial terenkripsi; kunci baru yang dihasilkan tidak dapat mendekripsi kredensial dari database lama.
