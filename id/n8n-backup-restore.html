BACKUP & PEMULIHAN

Backup dan Pemulihan n8n

Untuk melakukan backup dan pemulihan n8n self-hosted, lindungi basis data SQLite atau dump PostgreSQL yang konsisten, folder .n8n persisten dan kunci enkripsi asli, konfigurasi deployment, serta setiap dependensi biner eksternal atau file yang di-mount. Simpan salinan terenkripsi di luar VPS dan uji pemulihan pada instans terpisah. Gunakan ekspor workflow dan kredensial melalui CLI untuk pemulihan selektif; ekspor JSON saja bukan backup server lengkap.

DAFTAR PERIKSA SINGKAT

Apa yang harus dilindungi oleh backup n8n

Basis data

Backup basis data PostgreSQL atau file basis data SQLite yang digunakan instans. Basis data berisi status inti n8n seperti workflow, kredensial, dan data eksekusi.

Kunci enkripsi

Simpan kunci enkripsi n8n yang persis sama secara terpisah dan aman. Kredensial terenkripsi yang dipulihkan bergantung pada kunci yang sama.

File persisten

Sertakan direktori data n8n persisten dan semua file yang di-mount, penyimpanan data biner, atau aset workflow yang menjadi dependensi deployment Anda.

Konfigurasi deployment

Simpan file Compose/konfigurasi dan konfigurasi non-rahasia yang diperlukan untuk membangun ulang stack. Lindungi secret dengan kontrol akses yang sesuai.

DUA TINGKAT BACKUP

Ekspor logis vs pemulihan bencana lengkap

Ekspor workflow & kredensial

Ekspor CLI n8n berguna untuk migrasi, salinan workflow berversi, dan pemulihan selektif. Kredensial dapat diekspor dalam bentuk terenkripsi dan diimpor kemudian dengan kunci enkripsi yang sesuai. Untuk memulihkan satu workflow saja, gunakan menu tiga titik pada editor workflow untuk mengunduh JSON-nya, lalu gunakan Import from File ke workflow peninjauan baru atau instans terisolasi. Periksa kredensial, ID workflow, dan parameter node sebelum mengganti workflow aktif: memulihkan JSON workflow tidak memulihkan seluruh server.

Ekspor entitas

CLI dapat mengekspor entitas basis data untuk memindahkan data antar jenis basis data yang didukung. Tabel riwayat eksekusi bersifat opsional karena ukurannya dapat sangat besar.

Pemulihan instans lengkap

Untuk skenario server mati, lindungi basis data sebenarnya, kunci enkripsi, data persisten, dan dependensi deployment. Jangan menganggap ekspor JSON workflow dapat membangun ulang seluruh instans.

Snapshot penyedia

Snapshot VPS berguna sebagai lapisan pemulihan tambahan, tetapi tidak boleh menjadi satu-satunya salinan dan tidak boleh menggantikan backup aplikasi/basis data yang diverifikasi secara independen.

DATABASE

Backup basis data secara konsisten

PostgreSQL

Gunakan metode backup PostgreSQL yang konsisten dan simpan hasil backup jauh dari VPS. Salinan basis data pada disk gagal yang sama bukan pemulihan bencana.

SQLite

Jika deployment menggunakan SQLite, lindungi file basis data dari direktori data n8n persisten. Hindari menyalin basis data dalam keadaan tidak aman saat sedang aktif dimodifikasi.

Riwayat eksekusi

Tentukan apakah data riwayat eksekusi termasuk dalam tujuan pemulihan Anda. Data ini dapat membuat backup jauh lebih besar, sehingga persyaratan retensi dan kepatuhan harus menentukan pilihan.

Versi basis data

Catat mesin basis data dan versinya yang digunakan deployment sumber agar lingkungan pemulihan dapat disiapkan secara kompatibel.

PostgreSQL pada VPS Docker Compose. Jika layanan PostgreSQL bernama postgres dan basis data/penggunanya sama-sama n8n, perintah berikut membuat dump PostgreSQL format kustom yang konsisten pada host. Periksa file Compose Anda yang sebenarnya sebelum menjalankannya, lalu sesuaikan kredensial basis data dan nama layanan. pg_dump dapat menghasilkan snapshot yang konsisten secara logis saat PostgreSQL berjalan; perintah ini tidak membackup folder pengguna .n8n yang terpisah atau data biner eksternal.

# In the Docker Compose project; adapt service, DB dan user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Pemeriksaan daftar arsip menangkap masalah format yang jelas tetapi tidak membuktikan data dapat dipulihkan. Simpan salinan terenkripsi di luar server dan lakukan latihan pemulihan. Gunakan dokumentasi resmi PostgreSQL pg_dump untuk opsi khusus basis data.

SQLite pada Docker. Untuk deployment SQLite default, database.sqlite dan konfigurasi kunci enkripsi yang dihasilkan berada di dalam folder persisten .n8n (biasanya di-mount pada /home/node/.n8n). Jangan pernah menganggap salinan langsung sederhana SQLite sebagai konsisten. Hentikan n8n dan proses lain yang menulis ke basis data sebelum menyalin folder, atau gunakan mekanisme backup online SQLite yang didukung jika penghentian tidak memungkinkan:

# Only for SQLite dan the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Perintah ini hanya ilustrasi untuk layanan dan jalur yang ditampilkan, bukan tata letak volume universal. Folder yang disalin awalnya masih berada pada VPS yang sama; pindahkan dan lindungi di luar server. Jika ada queue worker atau penulis lain, hentikan juga aktivitasnya dan ikuti desain deployment yang sebenarnya. Panduan backup lengkap n8n saat ini mendokumentasikan persyaratan konsistensi SQLite.

Memulihkan folder SQLite default ke target bersih: pertama-tama hentikan layanan n8n dan semua penulis basis data. Setelah container layanan n8n yang kompatibel dan volume tujuan tersedia, salin isi .n8n yang sudah dibackup kembali ke direktori persisten yang sama. Ini menimpa file target, jadi jangan jalankan pada instans yang berisi data yang perlu dipertahankan:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership dan permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials dan workflow triggers

Docker dapat menyalin ke container yang dihentikan, tetapi kepemilikan tujuan mungkin berbeda dari aslinya; pastikan konfigurasi dan file basis data yang dipulihkan dapat dibaca dan ditulis oleh proses n8n sebelum memulainya. Jika konfigurasi Compose Anda menggunakan jalur atau bind mount yang berbeda, sesuaikan penyalinan. Referensi Docker Compose copy. Memulihkan folder n8n saja tidak cukup untuk deployment yang menggunakan basis data PostgreSQL terpisah.

SECRET KRITIS

Kunci enkripsi adalah bagian dari pemulihan

n8n mengenkripsi kredensial tersimpan dengan kunci enkripsi instans. Basis data atau ekspor kredensial terenkripsi tanpa kunci yang sesuai dapat membuat workflow yang dipulihkan tidak dapat menggunakan kredensial tersimpan.

Jika Anda menetapkan N8N_ENCRYPTION_KEY, pulihkan secret yang persis sama. Jika tidak, kunci yang dihasilkan disimpan dalam file persisten .n8n/config: lindungi konfigurasi itu saat melakukan backup atau membangun ulang. Simpan kunci pemulihan dengan aman di luar VPS. Dalam queue mode, semua proses utama dan worker harus menggunakan kunci yang sama.

LakukanSimpan salinan terlindungi dari kunci persis yang digunakan produksi.
LakukanPastikan lingkungan pemulihan menggunakan kunci tersebut sebelum menguji kredensial.
JanganJangan mengandalkan kunci baru yang dihasilkan setelah membangun ulang server.
JanganJangan commit kunci ke repositori publik atau menyimpannya bersama backup yang tidak terlindungi.

FILE & DATA BINER

Backup basis data mungkin tidak mencakup semua dependensi workflow

Data .n8n persisten

Temukan dan simpan folder pengguna .n8n yang sebenarnya, bukan hanya image container. Dalam deployment Docker umum, folder ini di-mount pada /home/node/.n8n; di luar Docker default-nya adalah ~/.n8n. Jika N8N_USER_FOLDER dikonfigurasi, n8n membuat .n8n di dalam direktori induk yang ditentukan. Sertakan kunci konfigurasinya dan setiap data eksekusi SQLite lokal, biner, atau filesystem yang digunakan instalasi Anda.

File workflow yang di-mount

Jika workflow membaca atau menulis direktori yang di-mount dari host, backup direktori tersebut secara terpisah. Memulihkan n8n tanpa direktori itu dapat membuat workflow yang sebenarnya valid menjadi rusak.

Data biner

Identifikasi mode penyimpanan dan pulihkan setiap dependensi eksternal. Data biner atau eksekusi berbasis filesystem mungkin berada di .n8n atau direktori kustom; S3/Azure Blob atau penyimpanan eksternal terkonfigurasi lainnya memerlukan salinan yang dapat dipulihkan dan pengaturan aksesnya sendiri. Dump basis data saja tidak dapat menggantikan file tersebut.

Node komunitas

Catat paket komunitas dan versinya, serta backup direktori node kustom tambahan yang dikonfigurasi melalui N8N_CUSTOM_EXTENSIONS. Direktori tersebut dapat berada di luar .n8n; pemulihan basis data dan folder pengguna saja masih dapat membuat workflow dengan node kustom tidak dapat digunakan.

STRATEGI DI LUAR SERVER

Backup pada VPS yang sama hanyalah salinan lokal

Salinan lokalBerguna untuk rollback cepat, tetapi rentan terhadap kehilangan server, kegagalan disk, dan kesalahan destruktif.
Salinan di luar serverSimpan setidaknya satu backup di penyimpanan yang independen dari VPS produksi.
Salinan berversiPertahankan beberapa titik pemulihan agar korupsi atau perubahan buruk tidak menimpa satu-satunya backup yang dapat digunakan.
Kontrol aksesBackup dapat berisi kredensial, logika workflow, dan data bisnis sensitif. Enkripsi dan batasi aksesnya secara tepat.
PemantauanBuat peringatan saat backup terjadwal gagal atau berhenti menghasilkan titik pemulihan baru.

Buat jadwal dapat diukur. Catat timestamp setiap backup yang berhasil, penyelesaian transfer, ukuran file, versi basis data sumber, lokasi pemulihan kunci enkripsi, dan pengujian pemulihan terakhir yang berhasil. Buat peringatan untuk file yang hilang, gagal, atau kosong secara tidak terduga. Enkripsi arsip backup sebelum mengirimkannya keluar VPS dan batasi akses ke secret pemulihan. Beberapa titik pemulihan bertanggal melindungi dari penemuan korupsi setelah salinan terbaru menimpa salinan sehat terakhir.

Sebagai contoh, jika Anda dapat menoleransi kehilangan perubahan maksimal enam jam, jadwal backup enam jam yang berhasil hanyalah titik awal, bukan jaminan: pekerjaan yang gagal dan replikasi ke luar server yang tertunda dapat meningkatkan kehilangan sebenarnya. Tetapkan retensi dan frekuensi pemulihan sesuai RPO/RTO serta kebutuhan data Anda sendiri, bukan menganggap kebijakan 7 hari atau 30 hari berlaku universal.

URUTAN PEMULIHAN

Pulihkan dengan urutan yang terkendali

1 · SiapkanSiapkan server, basis data, dan lingkungan container/runtime yang kompatibel.
2 · Pulihkan secretKonfigurasikan kunci enkripsi n8n asli dan secret deployment yang diperlukan dengan aman.
3 · Pulihkan basis dataPulihkan PostgreSQL atau SQLite dan pastikan n8n dapat terhubung ke data yang diharapkan.
4 · Pulihkan filePulihkan direktori persisten, data biner, dan aset workflow yang di-mount.
5 · Jalankan n8nJalankan aplikasi dengan hostname, basis data, dan konfigurasi lingkungan yang diharapkan.
6 · ValidasiPastikan pengguna, workflow, dan kredensial dimuat, lalu jalankan workflow representatif dan jalur webhook.

Contoh pemulihan bencana PostgreSQL: pada target pemulihan terpisah dan bersih yang sudah memiliki role basis data yang benar dan basis data n8n kosong, jalankan hanya PostgreSQL. Tunggu hingga sehat sebelum mengimpor: docker compose up -d saja dapat kembali saat PostgreSQL masih melakukan inisialisasi, sehingga pg_restore berikutnya dapat gagal. Contoh ini menggunakan --wait pada modern Compose installation dan independently checks pg_isready. Konfigurasikan healthcheck PostgreSQL yang sesuai agar penantian dapat diandalkan, atau konfirmasikan kesiapan secara eksplisit sebelum melanjutkan. Jangan arahkan perintah ini ke basis data produksi yang berisi data atau menjalankan n8n sebelum basis data dan .n8n yang sesuai beserta kunci/datanya dipulihkan.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database dan user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Tujuan harus memiliki versi PostgreSQL yang kompatibel, hak role, ekstensi, dan konfigurasi n8n asli. Pulihkan .n8n ke volume persisten atau bind mount yang benar menggunakan mekanisme backup Anda, dengan mempertahankan kepemilikan dan izin. Pulihkan file biner eksternal, ekstensi kustom, konfigurasi Compose dan secret, lalu jalankan n8n pada versi yang kompatibel dan periksa lognya. Memulihkan basis data saja tidak memulihkan kunci: deployment PostgreSQL menyimpan kunci di .n8n/config kecuali Anda secara eksplisit mengonfigurasi N8N_ENCRYPTION_KEY. UJI PEMULIHAN

Backup belum terbukti sampai pemulihan berhasil

Test pada clean environment

Latihan nyata harus membuktikan bahwa backup dapat membangun ulang instans tanpa bergantung pada file yang tidak tercatat dan tertinggal di server produksi.

Periksa kredensial

Membuka workflow saja tidak cukup. Pastikan kredensial terenkripsi yang dipulihkan benar-benar dapat didekripsi dan berhasil melakukan autentikasi.

Jalankan workflow representatif

Uji workflow yang bergantung pada webhook, API eksternal, file yang di-mount, dan node komunitas, bukan hanya memvalidasi otomatisasi sederhana.

Ukur waktu pemulihan

Catat berapa lama pemulihan berlangsung dan langkah manual apa yang masih diperlukan. Ini mengubah backup yang diasumsikan bekerja menjadi prosedur pemulihan operasional.

Latihan pemulihan terverifikasi: SQLite dan PostgreSQL

Lingkungan pengujian: n8n 2.42.5 in isolated Docker containers pada disposable GitHub Actions runner, using a synthetic two-node workflow. These checks ran on 8 October 2026, not pada customer's or production n8n server.

SQLite: PASSMengimpor workflow uji, mengekspornya, menghentikan semua penulis, mengarsipkan folder persisten .n8n berbasis SQLite dan kunci enkripsi yang dihasilkan, memulihkannya ke volume bersih, menjalankan n8n, lalu mengekspor ulang dan menjalankan workflow yang dipulihkan.
PostgreSQL: PASSMengimpor workflow uji yang sama, membuat dan memeriksa pg_dump, format kustom, memulihkannya menggunakan pg_restore ke basis data PostgreSQL kosong yang baru, memulihkan folder .n8n yang terpisah, lalu mengekspor ulang dan menjalankan workflow yang dipulihkan.
Apa yang dibuktikan PASSJalur backup yang diuji mempertahankan workflow ini, dua node beserta koneksinya, dan memungkinkan eksekusi setelah pemulihan. Ini adalah smoke test fungsional yang dapat direproduksi, bukan benchmark beban kerja.
Apa yang tidak diujiDekripsi dan autentikasi kredensial nyata, webhook produksi, worker queue mode dan Redis, penyimpanan biner S3/Azure, node kustom, akses pengguna/proyek, atau pemulihan instans produksi aktif. Jalankan latihan terpisah untuk setiap dependensi yang benar-benar Anda gunakan.

Cara mereproduksi: gunakan instalasi n8n sementara, buat workflow dua node yang aman, lakukan backup basis data ditambah folder persisten yang sesuai, pulihkan ke volume atau basis data bersih, lalu verifikasi node, koneksi, dan eksekusi aktual workflow yang dipulihkan. Pada sistem produksi, periksa juga kredensial terenkripsi, webhook, dan file eksternal sebelum menyatakan pemulihan bencana terbukti.

Daftar periksa penerimaan latihan pemulihan: gunakan domain/lingkungan terisolasi; periksa bahwa pengguna dan workflow tersedia, satu kredensial terenkripsi yang ada dapat mengautentikasi tanpa dimasukkan ulang, webhook produksi memanggil workflow yang dipulihkan dengan benar, file yang di-mount dan lampiran biner tetap dapat dibaca, serta integrasi dengan node komunitas yang diperlukan dapat dimuat. Konfirmasikan usia backup, downtime yang diukur, dan aksesibilitas di luar server. Jika pemeriksaan penting gagal, tandai titik pemulihan itu sebagai belum terverifikasi, bukan melaporkan backup sebagai lengkap.

BATAS BACKUP CLI

Ketahui secara tepat apa yang tidak dipulihkan oleh ekspor workflow dan kredensial

Ekspor CLI bukan backup instans lengkap

Ekspor backup workflow dan kredensial tidak mencakup pengguna dan role, riwayat eksekusi dan log, variabel, atau pengaturan instans seperti kunci enkripsi.

Pemulihan instans baru memerlukan owner

Pada instans bersih, selesaikan penyiapan owner sebelum mengimpor kredensial. Pemulihan multi-pengguna atau proyek juga mungkin memerlukan penetapan pengguna atau proyek yang benar.

ID yang diimpor dapat menimpa item yang ada

Ekspor workflow dan kredensial mempertahankan ID aslinya. Mengimpor ke instans yang sudah memiliki ID yang sama dapat mengganti item yang ada tersebut.

Publikasikan workflow yang diimpor dengan sengaja

Impor CLI biasanya meninggalkan workflow dalam keadaan tidak aktif. Pada n8n 2.x, periksa status publikasi setiap workflow yang diimpor dan publikasikan hanya workflow yang ingin dijalankan; Server CLI self-hosted juga mendukung n8n publish:workflow --id=YOUR_WORKFLOW_ID. Saat n8n berjalan, perubahan status publish/unpublish melalui Server CLI baru berlaku setelah n8n dimulai ulang. Mulai ulang sebelum memverifikasi trigger terjadwal dan webhook produksi atau mengalihkan trafik.

Contoh ekspor massal untuk Docker Compose: jika layanan n8n Anda bernama n8n, Anda dapat menjalankan backup CLI resmi di bawah ini. Jalur output sengaja berada di dalam direktori persisten .n8n yang di-mount, karena direktori sembarang di dalam container dapat hilang ketika dibuat ulang. Pastikan direktori dapat ditulis oleh pengguna container n8n. Simpan JSON workflow dan kredensial dalam direktori terpisah—n8n mendokumentasikan masalah impor ketika kedua jenis berbagi direktori yang sama.

Draft n8n 2.x vs backup yang dipublikasikan: ekspor workflow --backup normal menangkap draft saat ini; draft dapat berbeda dari versi yang dipublikasikan di produksi. Untuk mempertahankan versi terpublikasi aktual dari workflow tertentu, ekspor secara terpisah menggunakan docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, setelah memastikan folder output tersedia dan dapat ditulis. CLI juga dapat mengekspor versi historis menggunakan --version=VERSION_ID. Simpan tangkapan ini di luar server bersama backup lengkap; jangan menganggap JSON draft merekam status publikasi live.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow dan credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Direktori ~/n8n-recovery/cli yang disalin masih berada di VPS sampai Anda memindahkannya ke lokasi backup independen yang aman. Ekspor kredensial dienkripsi secara default dan memerlukan kunci enkripsi yang sesuai saat impor. Hindari penggunaan --decrypted kecuali untuk migrasi yang dikontrol ketat: opsi ini menulis secret sebagai plaintext. Jangan pernah commit ekspor yang berisi logika workflow sensitif atau kredensial ke repositori GitHub publik. Beberapa template backup kredensial GitHub pihak ketiga sengaja mengekspor secret yang didekripsi; repositori privat adalah pembatasan akses, bukan enkripsi. Periksa pengaturan ekspor dan izin penyimpanan sebenarnya dari setiap template, enkripsi secret sebelum transfer keluar server, dan rotasi kredensial yang terekspos melalui unggahan plaintext yang tidak disengaja.

Contoh impor massal: pada clean target, finish owner setup, provide the original encryption key dan ensure the saved backup files are available on that recovery VPS. The following creates the destination folder dan copies the workflows/ dan credentials/ dari host ke container n8n; sesuaikan jalur jika tata letak volume Docker Anda berbeda:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Check file ownership dan access for the n8n container user. Do not import over a populated production instance without a verified rollback: workflow dan credential IDs can overwrite existing entries. Then run:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ yang sudah dibackup back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Imported IDs can replace existing workflows or credentials; use an isolated test instance for dry runs dan check credentials dan activation/publishing states afterwards. In n8n 2.x, restoring the JSON draft does not by itself prove a workflow has been published dan can run scheduled triggers. Keamanan impor: pada non-multi-main n8n instance, previously active cron triggers can continue running after CLI import until the instance restarts. Stop or isolate production triggers dan restart n8n before enabling restored jobs; verify there is no duplicate execution. CLI exports do tidak berisi pengguna asli, log eksekusi, variabel instans, atau kunci enkripsi. --backup sets --all --pretty --separate, not 'full instance'. Sources: current official n8n backup/restore guide dan n8n CLI command reference.

Pemulihan massal dari template GitHub atau Google Drive: this is an alternative for workflow JSON only, not for the instance database, users, encrypted credential values or encryption key. Before running an API-based template, verify its n8n API dan storage permissions, the selected backup version dan target instance, whether it updates matching IDs dan recreates deleted workflows, dan what it does with workflow publishing. Not all templates recreate an ID missing from the target; test that scenario in isolation before relying on automatic restore.

FAQ

n8n backup dan restore: common questions

Apakah mengekspor workflow cukup untuk membackup n8n?

No. Workflow exports are useful logical copies, but complete recovery can also require credentials, the matching encryption key, database state, persistent files dan binary-data storage.

Apakah saya memerlukan kunci enkripsi n8n jika memiliki basis data?

Ya, jika Anda memerlukan kredensial terenkripsi yang tersimpan di basis data tersebut tetap dapat digunakan. Simpan kunci asli dengan aman.

Should I back up PostgreSQL or export workflows dan credentials?

For disaster recovery, protect the database dan the encryption key. Logical exports are valuable as an additional migration dan selective-recovery layer rather than a substitute for every part of the instance.

Bisakah snapshot VPS menjadi satu-satunya backup saya?

Lebih baik menganggapnya sebagai satu lapisan pemulihan. Simpan backup independen di luar server agar kegagalan penyedia, akun, server, atau snapshot tidak menghapus semua titik pemulihan sekaligus.

Bagaimana saya tahu backup saya berfungsi?

Restore it into a clean test environment, verify credentials decrypt, dan run representative workflows. A successful backup job alone does not prove recoverability.

Apakah backup workflow GitHub atau Google Drive menyertakan secret kredensial tersimpan?

Workflow-only JSON backups do not include the secret values managed by n8n's credential store or the instance encryption key. However, exported JSON can expose credential names dan IDs dan secrets typed directly into node parameters, such as authentication headers. Inspect dan protect exported JSON before uploading or sharing it. For full recovery, back up the database dan original key, or use supported encrypted credential CLI exports with a tested restore. A workflow-only GitHub or Google Drive template is not full disaster recovery.

TUJUAN PEMULIHAN

Define RPO dan RTO before an incident

RPO adalah kehilangan maksimum perubahan terbaru yang dapat ditoleransi. Ukur dari titik pemulihan terbaru yang dapat digunakan dan disimpan secara independen; pekerjaan terjadwal enam jam tidak berarti RPO enam jam jika ekspor atau transfer gagal. RTO is the maximum tolerable outage. Measure it in a clean restore drill, including retrieving secrets, restoring external files, rechecking credentials dan publishing recovered workflows—not just starting a container.

KUNCI PEMULIHAN

Temukan kunci enkripsi asli sebelum membangun ulang

Jika produksi menetapkan N8N_ENCRYPTION_KEY, preserve that exact environment secret. If it did not, preserve the generated key in the original persistent .n8n/config. Check which source the recovered instance actually uses before importing encrypted credentials; a fresh generated key cannot decrypt credentials from the old database.
