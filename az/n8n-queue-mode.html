MİQYASLANDIRMA

n8n növbə rejimi

Növbə rejimi iş axını icrasını n8n-in əsas prosesindən ayırır. Əsas instansiya tetikləyiciləri qəbul edib icralar yaradır, Redis növbəni əlaqələndirir, işçi proseslər tapşırıqları icra edir, PostgreSQL isə ortaq iş axını və icra məlumatlarını saxlayır.

QISA QƏRAR

Növbə rejiminə həqiqətən ehtiyacınız varmı?

Bu hallarda adi rejimdə qalın

Tək instansiya pik icraları rahat qarşılayırsa, CPU, RAM və icra gecikməsi sabit qalırsa, hələ ehtiyacınız olmayan komponentləri növbə rejimi ilə əlavə etməyin.

Bu hallarda növbə rejimini nəzərdən keçirin

Davamlı paralel icralar resurs rəqabəti yaradırsa, yük altında icra gecikməsi artırsa və ya bir neçə işçi proses işlədərək icra tutumunu böyütmək lazımdırsa.

Bu hallarda əvvəlcə server resurslarını artırın

Darboğaz sadəcə CPU və ya RAM çatışmazlığıdırsa və bir daha böyük instansiya hələ iş yükünü rahat qarşılaya bilirsə.

Arxitekturanı dəyişməzdən əvvəl ölçün

Növbə rejiminə keçidi əsaslandırmaq üçün pik paralellik, CPU, RAM, icra müddəti, növbə uzunluğu və verilənlər bazasının yükündən istifadə edin.

ƏSAS TƏLƏBLƏR

Hər növbə rejimi yerləşdirməsi üçün lazım olanlar

Redis

Bütün əsas və işçi proseslərin növbəni əlaqələndirən Redis xidmətinə etibarlı girişi olmalıdır.

PostgreSQL

Əsas və işçi proseslər eyni verilənlər bazasını paylaşmalıdır. Növbə rejimi paylanmış arxitekturadır və SQLite üzərində qurulmamalıdır.

Uyğunlaşdırılmış n8n konfiqurasiyası

Əsas və işçi proseslər növbə rejimində işləməli, Redis-ə, PostgreSQL-ə və şifrələnmiş giriş məlumatlarına çıxış üçün lazım olan ortaq konfiqurasiyadan istifadə etməlidir.

Worker-lərin iş tutumu

İşçi proseslər icra etdikləri iş axınları üçün yetərli CPU və RAM tələb edir. Proses sayını artırmaq hər icranın resurs xərcini aradan qaldırmır.

Mövcud öz serverinizdəki sistemdə növbə rejimini aktivləşdirin. Əvvəlcə n8n-in əsas xidməti və hər işçi prosesin özəl şəbəkə üzərindən eyni PostgreSQL bazasına və Redis-ə qoşula bildiyini təsdiqləyin. Təyin edin: EXECUTIONS_MODE=queue həm əsas, həm də işçi proseslərdə və təqdim edin: QUEUE_BULL_REDIS_HOST=redis və QUEUE_BULL_REDIS_PORT=6379 əgər: redis faktiki Compose xidmətinizin adıdır. İstifadə edin: DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres və uyğun DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER və DB_POSTGRESDB_PASSWORD hər prosesdə; nümunə xidmət adlarını öz adlarınızla əvəz edin. Mövcud faktiki N8N_ENCRYPTION_KEY hamısına. Eyni Compose şəbəkəsindəki konteynerlərə qoşulmaq üçün Redis və ya PostgreSQL-in host portlarını heç vaxt açıq yayımlamayın.

İkinci redaktoru deyil, icraçı prosesi başladın. Əsas proseslə eyni sabitlənmiş n8n təsvir versiyası və ortaq parametrlərdən istifadə edən əlavə n8n işçi xidməti yaradın, lakin onu worker əmri ilə başladın. Həmin xidmətin adını n8n-worker, onu aşağıdakı vasitə ilə başladın: docker compose up -d n8n-worker. Bir işçi prosesdə faktiki icranı təsdiqlədikdən sonra aşağıdakından istifadə edə bilərsiniz: docker compose up -d --scale n8n-worker=2 həmin xidmətdən ikinci işçi proses başlatmaq üçün. Bunlar mövcud mövcud düzgün qurulmuş Compose sisteminin parçasıdır, ayrıca quraşdırma faylı deyil; mövcud daimi disk sahələrini, HTTPS proksisini, sirləri və ehtiyat nüsxələri qoruyun.

Mövcud sistem üçün növbə rejimli Compose konfiqurasiya parçası. Aşağıdakı nümunəni mövcud compose.yaml; bu, deyil tam, ayrıca işləyən yerləşdirmə deyil. Bu nümunə artıq daimi və özəl postgres və n8n xidmətləri, mövcud N8N_VERSION mühitinizdə sabitlənmiş versiyanı və öz qorunan POSTGRES_PASSWORD və ilkin N8N_ENCRYPTION_KEY. Adları, disk sahələrini, verilənlər bazasını və n8n versiyasını mövcud layihəyə uyğunlaşdırın. Redis növbə rejimi parametrlərini və EXECUTIONS_MODE=queue yuxarıda göstərildiyi kimi mövcud əsas xidmətə də.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Bu parçada Redis və işçi proses üçün host portu yayımlanmır. Redis-in yalnız əlavələrə yazılan daimi saxlanması əlavə bərpa qatıdır, deyil serverdənkənar ehtiyat nüsxələrin əvəzi deyil. Mövcud HTTPS və autentifikasiya konfiqurasiyasını dəyişmədən saxlayın. Xarici tapşırıq icraçıları tələb edən Code qovşaqları üçün işçi yerləşdirmənizdə icraçı prosesləri ayrıca qurun; növbə rejimi özü tapşırıq icraçılarını əvəz etmir.

Mövcud SQLite instansiyasını köçürürsünüz? Sadəcə dəyişməyin: DB_TYPE və boş PostgreSQL bazasında başladın: bu, köhnə iş axınlarını və giriş məlumatlarını köçürmür. Keçiddən əvvəl mənbə verilənlər bazasının, daimi .n8n kataloqunun və ilkin şifrələmə açarının ehtiyat nüsxəsini yaradın; dəstəklənən n8n ixrac/idxal və ya miqrasiya prosedurundan istifadə edin, sonra ayrı hədəfdə iş axınları ilə şifrələnmiş giriş məlumatlarını yoxlayın. Geri qaytarmaq üçün ilkin faylları saxlayın və bərpaya hazırlıq üçün aşağıda keçidi verilmiş Ehtiyat Nüsxələmə və Bərpa bələdçisindən istifadə edin. Heç vaxt silməyin: database.sqlite qısa yol kimi.

İŞÇİ PROSESLƏRİN PARALEL İCRASI

Worker-lər həm sayına, həm də hər worker-in yerinə yetirdiyi tapşırıq sayına görə miqyaslanır

Hər işçi proses eyni vaxtda bir neçə tapşırıq işlədə bilər. n8n-də işçi proses üçün cari standart paralellik 10-dur və sənədlərdə 5 və ya daha yüksək paralellik tövsiyə edilir. Çoxsaylı, lakin az paralellikli işçi proseslər lazımsız verilənlər bazası bağlantıları yarada və bağlantı hovuzunu tükəndirə bilər.

Bu hallarda paralel icraların sayını artırın

İşçi prosesin boş CPU və RAM ehtiyatı var, iş axınları isə hesablama və yaddaşı tam yükləmək əvəzinə əsasən xarici xidmətləri gözləyir.

Bu hallarda worker əlavə edin

Bir işçi proses darboğaza çevrilibsə, verilənlər bazası, Redis və infrastrukturda əlavə paralel icra üçün resurs varsa.

Bu hallarda paralel icraların sayını azaldın

Ayrı-ayrı iş axınları çox yaddaş və ya CPU tələb edirsə, paralel tapşırıqlar resurs rəqabəti, OOM təzyiqi və ya qeyri-sabit icra müddəti yaradırsa.

PostgreSQL-in yükünü izləyin

Daha çox işçi proses və daha yüksək paralellik verilənlər bazası əməliyyatlarını artırır. Verilənlər bazasının tutumunu artırmadan icra tutumunu böyütmək darboğazı aradan qaldırmaq əvəzinə başqa yerə keçirə bilər.

Faktiki hansı paralellik limitinin tətbiq olunduğunu müəyyənləşdirin. İşçi prosesi aşağıdakı vasitə ilə başlatmaq olar: n8n worker --concurrency=5, yaxud Compose xidmətinizdə ekvivalent işçi əmri ilə başladın. Əgər N8N_CONCURRENCY_PRODUCTION_LIMIT açıq şəkildə standart dəyərdən fərqli təyin edilibsə: -1, bu parametr növbə rejimində üstün tutulur; əks halda n8n işçi prosesinin --concurrency dəyərinə və ya standart 10-a. İşçi proses sayını nominal standartla vurub zəmanətli məhsuldarlıq adlandırmayın: faktiki tutum tapşırıq müddətindən, CPU-dan, yaddaşdan, xarici API-lərdən və PostgreSQL bağlantılarından asılıdır.

VEBHUKLAR

Növbə rejimi icranın ötürülməsinə əlavə gecikmə yarada bilər

Əsas və ya vebhuk prosesi HTTP sorğusunu qəbul edir, lakin iş axınını işçi proses icra edir. Redis üzərindən ötürmə əlavə vaxt tələb edir. Gecikməyə həssas vebhuklarda işçi proses sayının artmasının hər sorğunu avtomatik sürətləndirdiyini düşünməyin, sorğudan cavaba qədər müddəti ölçün.

Qəbul edinƏsas/vebhuk prosesi sorğunu qəbul edir.
Növbəİcra Redis növbəsinə ötürülür.
İcra edin:Əlçatan işçi proses iş axınını icra edir.
CavabLazım gəldikdə nəticə növbə yolu ilə geri ötürülür.

Vebhuk trafikini düzgün prosesə yönləndirin. Ayrıca ayrılmış n8n webhook yük balanslaşdırıcısının və ya əks proksinin arxasındakı prosessorlarla istehsal yollarını yönləndirin: /webhook/* və /webhook-waiting/* vebhuk prosessorlarına; saxlayın: /webhook-test/*, redaktor və API sorğuları isə əsas prosesdə qalır. Əlavə yükü şüurlu şəkildə qəbul etmirsinizsə, əsas prosesi istehsal vebhuklarının yük balanslaşdırma qrupuna daxil etməyin. Bir Respond to Webhook iş axını işçi proses bitirib cavabı qaytarana qədər müştərini gözlədə bilər; buna görə növbə rejimi ani HTTP cavabları və ya sıfır vaxt aşımı vədi deyil. Trafiki dəyişməzdən əvvəl faktiki xarici geri çağırışın və cavabın davranışını sınaqdan keçirin.

İKİLİ VERİLƏNLƏR

Paylaşılan saxlama sistemini nəzərdən qaçırmayın

Fayl sisteminin məhdudiyyətləri

Növbə rejimi paylanmış işçi proseslər üçün ortaq daimi yaddaş modeli olaraq fayl sistemində ikili verilənlərin saxlanmasını dəstəkləmir.

Xarici ikilik məlumat saxlama sistemi

İş axınları ikili verilənləri paylanmış işçi proseslər arasında saxlamalıdırsa, tələb olunan hər instansiyanın istifadə edə bildiyi, məsələn dəstəklənən xarici obyekt yaddaşı kimi arxitekturadan istifadə edin.

Böyük webhook cavabları

İşçi proseslərdən gələn vebhuk cavabları sorğunu qəbul etmiş prosesə geri ötürülür. Böyük cavab gövdələri Redis yaddaşına təzyiqi artırır və cavabların saxlanması konfiqurasiyasını düşünərək seçməyi tələb edir.

Worker-ləri paylamazdan əvvəl plan qurun

Lokal fayllardan çox asılı olan iş yükü, işçi proseslər müxtəlif maşınlara paylanmazdan əvvəl ortaq daimi yaddaş üçün yenidən layihələndirilməlidir.

Böyük vebhuk cavabları üçün məhdudiyyət. n8n-in aktual sənədlərində N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX standart dəyər kimi 64 MiB işçi prosesin növbə üzərindən qaytarılan cavabı üçün. Redis-də eyni anda bir neçə surət saxlanıla bilər; buna görə hər böyük paralel cavab üçün Redis yaddaşında təxminən cavab ölçüsünün 1.5 misli qədər ehtiyat planlaşdırın. Ayrı yaddaşa ötürmə olmadan həddindən böyük cavab uğursuz olur; işçi proseslərin əlavə edilməsi onu avtomatik sürətləndirmir.

Versiya və lisenziya məhdudiyyətləri. n8n-dən 2.34.0, işçi proseslər istifadə edə bilər: N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true həddindən böyük vebhuk cavab gövdələrini bütün iştirakçılar tərəfindən oxuna bilən ortaq ikili yaddaşa ötürmək üçün, lakin əvvəlcə hər əsas prosesi və vebhuk prosessorunu 2.34.0 və ya sonrakı versiyaya. Seçilmiş N8N_DEFAULT_BINARY_DATA_MODE məlumatları həqiqətən saxlamalı və iştirak edən bütün proseslər tərəfindən oxuna bilməlidir. Xarici S3 və Azure ikili yaddaşı üçün uyğun, öz serverində işləyən Business və ya Enterprise lisenziyası tələb olunur; Community Edition-un bunları aktivləşdirə bildiyini fərz etməyin. Həmin database ikili məlumat rejimi ödənişli xarici yaddaş olmadan həddindən böyük cavabı ayrıca saxlayaraq yükü azalda bilər, lakin əsas instansiya saxlanmış cavab gövdəsinin hamısını yaddaşa yükləyir və verilənlər bazası yaddaşının öz fayl ölçüsü məhdudiyyəti var. Aşağıdakı xüsusilə cavab gövdəsini ayrı yaddaşa ötürmə, n8n həmçinin ortaq filesystem bütün instansiyalar eyni diski qoşduqda mümkün variantdır, lakin n8n bu quruluşu açıq şəkildə tövsiyə etmir. Bu xüsusi cavabın ayrı yaddaşa ötürülməsi yolunu paylanmış növbə rejimində fayl əsaslı daimi ikili yaddaşın dəstəklənməsi ilə qarışdırmayın. Aktivləşdirməzdən əvvəl versiyanızı, lisenziyanızı və saxlama konfiqurasiyanızı yoxlayın.

MONİTORİNQ

Növbə rejiminin fayda verib-vermədiyini müəyyən edin

Növbənin uzunluğu

İşçi proseslərin emal etməsindən daha sürətlə böyüyən növbə icra tutumunun çatmadığını və ya sonrakı xidmətlərdə darboğaz olduğunu göstərir.

Worker-in CPU və RAM istifadəsi

Hər işçi proses üzrə resursların dolmasını və yaddaş piklərini ölçün. Növbə böyüdüyü halda işçi proseslər boş qalırsa, başqa bir məhdudiyyət var.

İcra gecikməsi

Yalnız iş axınının öz icra müddətini deyil, icranın yaradılmasından həqiqətən başlamasına qədər gecikməni izləyin.

Sistem vəziyyətinin yoxlanması

İşçi proseslərin sağlamlıq son nöqtələri onların işlək olub-olmadığını və verilənlər bazası ilə Redis bağlantılarının hazır vəziyyətini göstərə bilər.

Yalnız yaşıl görünən konteyneri deyil, işçi prosesdə faktiki icranı təsdiqləyin. Düzgün qurulmuş Compose sistemi ilə yoxlayın: docker compose ps və docker compose logs --tail=100 n8n-worker (xidmətin adı fərqlidirsə, onu əvəz edin). Zərərsiz bir dərc olunmuş istehsal planlaşdırılmış tetikləyici və ya sınaq vebhuku ilə iş axını başladın, sonra n8n-in Executions görünüşündəki icranı işçi proses jurnallarındakı real emalla tutuşdurun. Redaktorun açılması, Redis konteynerinin işləməsi və ya tapşırığın növbəyə düşməsi təkbaşına deyil işçi prosesin tapşırığı icra etdiyini sübut etmir.

Asılılıqları və xidmətlərin hazır vəziyyətini yoxlayın. Standart nümunə xidmət adları ilə: docker compose exec -T redis redis-cli ping qəbul etməlidir: PONG Redis autentifikasiyası imkan verirsə və docker compose exec -T postgres pg_isready -U n8n -d n8n PostgreSQL-in hazır vəziyyətini yoxlayır (giriş məlumatlarını və xidmət adlarını uyğunlaşdırın). Aktivləşdirin: QUEUE_HEALTH_CHECK_ACTIVE=true onun özəl /healthz və /healthz/readiness son nöqtələrini; hazırlıq son nöqtəsi Redis/verilənlər bazası bağlantısını yoxlayır. Yalnız monitorinq üçün bu işçi proses son nöqtələrini açıq internetə çıxarmayın.

Əl ilə başladılan iş axınları fərqli sınaqdır. Standart olaraq OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, buna görə növbə rejimi düzgün qurulsa belə, redaktordan əl ilə başlatdığınız iş axını əsas prosesdə icra oluna bilər. Onu true yalnız əl ilə başladılan icraları işçi proseslərə göndərmək istəyirsinizsə və dəyişikliyi sınaq mühitində yoxlamısınızsa. Növbə rejiminin işçi prosesləri Code qovşaqlarının icrası üçün ayrıca konfiqurasiya tələb edən n8n xarici tapşırıq icraçılarından da fərqlidir.

Versiyaları uyğun saxlayın

Əsas, vebhuk və işçi proseslər eyni n8n versiyasında işləməlidir. Qarışıq versiyalar mərhələli yeniləmə zamanı uyğunsuz davranış yarada bilər.

Webhook prosessorları ayrıca miqyaslandırma qatıdır

Gələn vebhuk trafiki darboğaza çevriləndə ayrıca vebhuk prosessorları yük balanslaşdırıcısının arxasında yerləşə, işçi proseslər isə icraları yerinə yetirə bilər. Ölçülmüş sorğu həcmi tələb etmirsə, bu qatı əlavə etməyin.

Multi-main ayrıca funksiyadır

Yüksək əlçatanlıq üçün birdən çox əsas proses işlətmək adi növbə rejimi ilə eyni deyil. n8n hazırda multi-main funksiyasını əlavə yük balanslaşdırıcı və sessiya tələbləri olan öz serverində yerləşdirilən Enterprise funksiyası kimi sənədləşdirir.

n8n növbə rejimi Redis tələb edirmi?

Bəli. Redis əsas instansiya ilə işçi proseslər arasında gözləyən icraları əlaqələndirən mesaj vasitəçisidir.

Növbə rejimində SQLite istifadə edilə bilərmi?

Paylanmış növbə rejimi arxitekturası üçün xeyr. Əsas və işçi proseslər ortaq verilənlər bazasına giriş tələb edir və n8n bu quruluş üçün PostgreSQL-i sənədləşdirir.

Neçə işçi proses işlətməliyəm?

Universal say yoxdur. Ölçülmüş paralellik və işçi proseslərin yüklənməsindən başlayın, sonra PostgreSQL, Redis, CPU, RAM və növbə uzunluğunu izləyərək tutum əlavə edin.

n8n işçi prosesinin paralel icra sayı nədir?

Bu, bir işçi prosesin paralel emal edə biləcəyi tapşırıqların sayıdır. Cari standart dəyər 10-dur və n8n çoxsaylı aşağı paralellikli proseslər yaratmaq əvəzinə işçi prosesin paralelliyini ən azı 5 səviyyəsində saxlamağı tövsiyə edir.

Kiçik VPS-də növbə rejimini aktivləşdirməliyəmmi?

Yalnız iş yükü bunu əsaslandırdıqda. Tək instansiyada problemsiz işləyən kiçik sistemi Redis və ayrıca işçi proseslər olmadan idarə etmək adətən daha sadədir.
