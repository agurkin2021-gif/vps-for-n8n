SÜRƏTLİ YOXLAMA SİYAHISI

n8n-in ehtiyat nüsxəsi nələri qorumalıdır?

Verilənlər bazası

İnstansiyanın istifadə etdiyi PostgreSQL bazasının və ya SQLite verilənlər bazası faylının ehtiyat nüsxəsini yaradın. Verilənlər bazası iş axınları, giriş məlumatları və icra məlumatları kimi əsas n8n vəziyyətini saxlayır.

Şifrələmə açarı

n8n-in dəqiq şifrələmə açarını ayrıca və təhlükəsiz saxlayın. Bərpa edilən şifrələnmiş giriş məlumatları eyni açardan asılıdır.

Daimi saxlanılan fayllar

Daimi n8n məlumat kataloqunu, həmçinin yerləşdirmənin asılı olduğu qoşulmuş faylları, ikili verilənlər anbarını və iş axını resurslarını daxil edin.

Yerləşdirmə konfiqurasiyası

Compose/konfiqurasiya fayllarını və sistemi yenidən qurmaq üçün lazım olan məxfi olmayan parametrləri saxlayın. Sirləri uyğun giriş nəzarəti ilə qoruyun.

EHTİYAT NÜSXƏLƏMƏNİN İKİ SƏVİYYƏSİ

Məntiqi ixrac və tam qəza bərpasının fərqi

İş axınlarının və giriş məlumatlarının ixracı

n8n CLI ixracları miqrasiya, versiyalara ayrılmış iş axını surətləri və seçmə bərpa üçün faydalıdır. Giriş məlumatlarını şifrələnmiş formada ixrac edib sonra uyğun şifrələmə açarı ilə idxal etmək olar. Yalnız bir iş axınını bərpa etmək üçün redaktordakı üç nöqtəli menyudan JSON faylını endirin, sonra onu yeni yoxlama iş axınına və ya təcrid olunmuş instansiyaya «Import from File» vasitəsilə idxal edin. İşlək iş axınını əvəz etməzdən əvvəl giriş məlumatlarını, iş axını ID-lərini və qovşaq parametrlərini yoxlayın: iş axını JSON-unun bərpası bütün serveri bərpa etmir.

Obyektlərin ixracı

CLI məlumatları dəstəklənən verilənlər bazası növləri arasında köçürmək üçün bazanın obyektlərini ixrac edə bilər. İcra tarixçəsi cədvəlləri seçimlidir, çünki çox böyük ola bilər.

İnstansiyanın tam bərpası

Server tam sıradan çıxdıqda faktiki verilənlər bazasını, şifrələmə açarını, daimi məlumatları və yerləşdirmə asılılıqlarını qoruyun. İş axını JSON ixracının bütün instansiyanı yenidən qurduğunu fərz etməyin.

Provayderin sistem anlıq görüntüsü

VPS anlıq görüntüsü əlavə bərpa səviyyəsi kimi faydalıdır, lakin yeganə nüsxə olmamalı və ayrıca yoxlanılmış tətbiq/verilənlər bazası ehtiyat nüsxəsini əvəz etməməlidir.

VERİLƏNLƏR BAZASI

Verilənlər bazasının ardıcıl ehtiyat nüsxəsini yaradın

PostgreSQL

PostgreSQL bazasının tutarlı ehtiyat nüsxələmə üsulundan istifadə edin və alınan nüsxəni VPS-dən kənarda saxlayın. Eyni sıradan çıxmış diskdə qalan verilənlər bazası surəti fəlakətdən sonra bərpa deyil.

SQLite

Yerləşdirmə SQLite istifadə edirsə, daimi n8n məlumat qovluğundakı verilənlər bazası faylını qoruyun. Verilənlər bazası aktiv şəkildə dəyişdirildiyi vaxt onun təhlükəli vəziyyətdə köçürülməsindən çəkinin.

İcra tarixçəsi

Tarixi icra məlumatlarının bərpa məqsədinizə daxil olub-olmadığını müəyyənləşdirin. Onlar ehtiyat nüsxənin ölçüsünü xeyli artıra bilər; qərar saxlanma müddəti və uyğunluq tələblərinə əsaslanmalıdır.

Verilənlər bazasının versiyası

Mənbə yerləşdirməsinin verilənlər bazası mühərrikini və versiyasını qeyd edin ki, uyğun bərpa mühiti hazırlansın.

Docker Compose VPS-də PostgreSQL. PostgreSQL xidmətinin adı postgres və onun verilənlər bazası/istifadəçisi hər ikisi n8n, aşağıdakı əmr hostda PostgreSQL verilənlər bazasının ardıcıl, xüsusi formatlı ehtiyat nüsxəsini yaradır. Əmri işlətməzdən əvvəl öz Compose faylınızı yoxlayın, verilənlər bazasının giriş məlumatlarını və xidmət adlarını uyğunlaşdırın. pg_dump PostgreSQL işləyərkən məntiqi baxımdan tutarlı anlıq surət yarada bilər; o, deyil ayrıca .n8n istifadəçi qovluğunu və ya xarici ikili verilənləri.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Arxiv siyahısını yoxlamaq açıq format problemlərini aşkar edir, lakin verilənlərin həqiqətən bərpa edilə biləcəyini sübut etmir. Şifrələnmiş surəti serverdən kənarda saxlayın və bərpa məşqi keçirin. Bazaya xas seçimlər üçün PostgreSQL-in rəsmi pg_dump sənədlərinə baxın.

Docker-də SQLite. Standart SQLite yerləşdirməsində, database.sqlite və yaradılmış şifrələmə açarının konfiqurasiyası daimi .n8n qovluğunu (adətən /home/node/.n8n). SQLite bazasının sadəcə işlək vəziyyətdə kopyalanmasını etibarlı hesab etməyin. Qovluğu köçürməzdən əvvəl n8n-i və verilənlər bazasına yazan digər prosesləri dayandırın; işin dayandırılması mümkün deyilsə, SQLite-ın dəstəklədiyi onlayn ehtiyat nüsxələmə mexanizmindən istifadə edin:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Bunlar göstərilmiş xidmət və yol üçün nümunəvi əmrlərdir, bütün sistemlərə uyğun universal disk quruluşu deyil. Köçürülmüş qovluq əvvəlcə hələ də həmin VPS-də qalır; onu serverdən kənara köçürüb qoruyun. Növbə işçiləri və ya digər yazan proseslər varsa, onları da dayandırın və yerləşdirmənizin real quruluşuna əməl edin. n8n-in aktual tam ehtiyat nüsxələmə təlimatında SQLite tutarlılığı tələbi izah olunur.

Standart SQLite qovluğunun təmiz hədəfdə bərpası: əvvəlcə n8n xidmətini və verilənlər bazasına yazan bütün prosesləri dayandırın. Uyğun n8n xidmət konteyneri və təyinat disk sahəsi mövcud olduqdan sonra ehtiyat nüsxəsi alınmış .n8n məzmunu geri eyni daimi kataloqa. Bu, hədəf faylların üzərinə yazacaq; saxlanmalı məlumatları olan instansiyada işlətməyin:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker dayandırılmış konteynerlərə fayl köçürə bilər, lakin təyinatda fayl sahibliyi ilkin vəziyyətdən fərqlənə bilər. n8n-i işə salmazdan əvvəl bərpa olunmuş konfiqurasiyanın və verilənlər bazası faylının n8n prosesi üçün oxuna və yazıla bildiyinə əmin olun. Compose konfiqurasiyanız fərqli yol və ya bağlanan qovluq istifadə edirsə, köçürməni uyğunlaşdırın. Docker Compose köçürmə arayışı. Ayrıca PostgreSQL bazası olan yerləşdirmələrdə təkcə n8n qovluğunu bərpa etmək kifayət deyil.

FAYLLAR VƏ İKİLİ VERİLƏNLƏR

Daimi saxlanılan .n8n məlumatları

Yalnız konteyner təsvirini deyil, faktiki .n8n istifadəçi qovluğunu tapıb qoruyun. Tipik Docker yerləşdirməsində o, /home/node/.n8n yoluna qoşulur; Docker xaricində standart yol ~/.n8n-dir. N8N_USER_FOLDER təyin olunubsa, n8n həmin göstərilmiş əsas kataloqun daxilində .n8n yaradır. Konfiqurasiya açarını, lokal SQLite faylını və quraşdırmanızın istifadə etdiyi ikili və ya fayl sistemi icra məlumatlarını daxil edin.

İş axınına qoşulmuş fayllar

İş axınları hosta qoşulmuş kataloqlardan oxuyur və ya onlara yazırsa, həmin kataloqların ayrıca ehtiyat nüsxəsini yaradın. Onlarsız n8n-i bərpa etmək, başqa baxımdan düzgün olan iş axınlarını işləməz hala sala bilər.

İkilik məlumatlar

Saxlama rejimini müəyyənləşdirin və bütün xarici asılılıqları bərpa edin. Fayl sistemində saxlanan ikili və ya icra məlumatları .n8n qovluğunda və ya xüsusi kataloqda ola bilər; S3/Azure Blob və ya başqa konfiqurasiya olunmuş xarici saxlama üçün ayrıca bərpa edilə bilən nüsxə və giriş parametrləri lazımdır. Təkcə verilənlər bazasının surəti həmin faylları əvəz etmir.

İcma tərəfindən hazırlanmış node-lar

İcma paketlərini və versiyalarını qeyd edin, həmçinin N8N_CUSTOM_EXTENSIONS vasitəsilə göstərilmiş əlavə xüsusi qovşaq kataloqlarının ehtiyat nüsxəsini yaradın. Bu kataloqlar .n8n xaricində ola bilər; təkcə verilənlər bazası və istifadəçi qovluğunun bərpası xüsusi qovşaqlardan asılı iş axınlarını yenə də işləməz vəziyyətdə qoya bilər.

Bərpanı nəzarətli ardıcıllıqla həyata keçirin

1 · HazırlıqUyğun server, verilənlər bazası və konteyner/icra mühitini hazırlayın.
2 · Sirlərin bərpasın8n-in ilkin şifrələmə açarını və yerləşdirmə üçün tələb olunan sirləri təhlükəsiz şəkildə qurun.
3 · Verilənlər bazasının bərpasıPostgreSQL və ya SQLite bazasını bərpa edin və n8n-in gözlənilən məlumatlara qoşulduğunu yoxlayın.
4 · Faylların bərpasıDaimi qovluqları, ikili verilənləri və qoşulmuş iş axını resurslarını bərpa edin.
5 · n8n-i işə salınTətbiqi gözlənilən host adı, verilənlər bazası və mühit konfiqurasiyası ilə işə salın.
6 · Yoxlamaİstifadəçilərin, iş axınlarının və giriş məlumatlarının yükləndiyini təsdiqləyin, sonra tipik iş axınlarını və vebhuk yollarını icra edin.

PostgreSQL üçün fəlakətdən sonra bərpa nümunəsi: bir ayrıca, təmiz bərpa hədəfi artıq düzgün verilənlər bazası roluna və boş n8n verilənlər bazasını, işə salın yalnız PostgreSQL. İdxaldan əvvəl sağlam vəziyyətə çatmasını gözləyin: docker compose up -d təkbaşına PostgreSQL hələ başladığı halda geri qayıda bilər; buna görə növbəti pg_restore uğursuz ola bilər. Nümunədə --wait müasir Compose quraşdırmasında və ayrıca yoxlayır: pg_isready. Etibarlı gözləmə üçün uyğun PostgreSQL sağlamlıq yoxlaması qurun və ya davam etməzdən əvvəl hazır olduğunu ayrıca təsdiqləyin. Bu əmri məlumatı olan işlək verilənlər bazasına yönəltməyin; verilənlər bazası və ona uyğun .n8n açarı/məlumatları bərpa olunub.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Hədəf mühitində uyğun PostgreSQL versiyası, rol icazələri, genişlənmələr və ilkin n8n konfiqurasiyası olmalıdır. Bərpa edin .n8n ehtiyat nüsxələmə vasitənizlə düzgün daimi disk sahəsinə və ya hosta bağlanmış qovluğa bərpa edin, fayl sahibliyini və icazələri qoruyun. Xarici ikili faylları, xüsusi genişlənmələri, Compose və sirr konfiqurasiyasını bərpa edin; sonra n8n-i uyğun versiyada başladın və jurnallarını yoxlayın. Təkcə verilənlər bazasının bərpası açarı qaytarmır: PostgreSQL yerləşdirməsində açar .n8n/config açıq şəkildə konfiqurasiya etməmisinizsə N8N_ENCRYPTION_KEY. pg_restore arayışı · n8n instansiyasının tam bərpası ardıcıllığı.

Bərpanın nə qədər sürdüyünü və hansı əl ilə görülən addımların qaldığını qeyd edin. Beləcə ehtimal olunan ehtiyat nüsxə əməli bərpa proseduruna çevrilir.

Yoxlanılmış bərpa sınağı: SQLite və PostgreSQL

Sınaq mühiti: n8n 2.42.5 birdəfəlik GitHub Actions icraçısında təcrid olunmuş Docker konteynerlərində, iki qovşaqlı sintetik iş axınından istifadə etməklə. Bu yoxlamalar 8 oktyabr 2026, müştərinin və ya işlək n8n serverinin üzərində deyil.

SQLite: UĞURLUSınaq iş axınını idxal etdik, ixrac etdik, bütün yazan prosesləri dayandırdıq və SQLite istifadə edən daimi .n8n qovluğunu və oradakı yaradılmış şifrələmə açarını arxivləşdirdik, təmiz disk sahəsinə bərpa etdik, n8n-i başladıb bərpa olunan iş axınını yenidən ixrac etdik və işə saldıq.
PostgreSQL: UĞURLUEyni sınaq iş axınını idxal etdik, xüsusi formatlı pg_dump, onu aşağıdakı vasitə ilə bərpa etdik, pg_restore yeni, boş PostgreSQL bazasına bərpa etdik, ayrıca .n8n qovluğunu bərpa etdik, sonra bərpa olunan iş axınını yenidən ixrac etdik və işə saldıq.
UĞURLU nəticə nəyi təsdiqləyirSınaqdan keçirilmiş ehtiyat nüsxələmə yolları bu iş axınını, onun iki qovşağını və aralarındakı əlaqələri qorudu, həmçinin bərpadan sonra icrasına imkan verdi. Bunlar təkrarlana bilən funksional ilkin yoxlamalardır, iş yükü üzrə performans testləri deyil.
Nələr sınaqdan keçirilməyibHəqiqi giriş məlumatlarının deşifrə olunması və autentifikasiyası, istehsal vebhukları, növbə rejimində işçilər və Redis, S3/Azure ikili verilənlər anbarı, xüsusi qovşaqlar, istifadəçi/layihə girişi və ya işlək istehsal instansiyasının bərpası. Həqiqətən istifadə etdiyiniz hər asılılığı ayrıca sınaqdan keçirin.

Təkrarlamaq üçün addımlar: birdəfəlik n8n quraşdırmasından istifadə edin, zərərsiz iki qovşaqlı iş axını yaradın, müvafiq verilənlər bazasının və daimi qovluğun ehtiyat nüsxəsini alın, təmiz disk sahəsinə və ya bazaya bərpa edin, sonra iş axınının qovşaqlarını, əlaqələrini və faktiki icrasını yoxlayın. İstehsal sistemində isə fəlakətdən sonra bərpanı sübut olunmuş saymazdan əvvəl şifrələnmiş giriş məlumatlarını, vebhukları və xarici faylları da yoxlayın.

Bərpa sınağının qəbul yoxlama siyahısı: təcrid olunmuş domen/mühit istifadə edin; istifadəçilərin və iş axınlarının mövcudluğunu, əvvəlcədən saxlanmış ən azı bir şifrələnmiş giriş məlumatının yenidən daxil edilmədən autentifikasiyadan keçdiyini, istehsal vebhukunun nəzərdə tutulan bərpa edilmiş iş axınını çağırdığını, qoşulmuş faylların və ikili əlavələrin oxuna bildiyini və tələb olunan icma qovşaqları ilə inteqrasiyaların yükləndiyini yoxlayın. Ehtiyat nüsxənin yaşını, ölçülmüş dayanma müddətini və serverdənkənar əlçatanlığını təsdiqləyin. Vacib yoxlamalardan biri uğursuz olarsa, həmin bərpa nöqtəsini yoxlanılmamış ehtiyat nüsxəni tamamlanmış kimi bildirmək əvəzinə.

CLI İLƏ EHTİYAT NÜSXƏLƏMƏNİN MƏHDUDİYYƏTLƏRİ

İş axını və giriş məlumatları ixracının nələri bərpa etmədiyini dəqiq bilin

CLI ilə ixrac instansiyanın tam ehtiyat nüsxəsi deyil

İş axınları və giriş məlumatlarının ehtiyat ixraclarına istifadəçilər və rollar, icra tarixçəsi və jurnallar, dəyişənlər, yaxud şifrələmə açarı kimi instansiya parametrləri daxil deyil.

Yeni instansiyaya bərpa üçün sahib hesabı lazımdır

Təmiz instansiyada giriş məlumatlarını idxal etməzdən əvvəl sahib hesabının ilkin quraşdırılmasını tamamlayın. Bir neçə istifadəçi və ya layihənin bərpası üçün düzgün istifadəçi və ya layihə təyinatı da lazım ola bilər.

İdxal edilən identifikatorlar mövcud elementlərin üzərinə yazıla bilər

İş axını və giriş məlumatı ixracları ilkin ID-ləri saxlayır. Eyni ID-lər olan instansiyaya idxal ediləndə mövcud qeydləri əvəz edə bilərlər.

İdxal edilmiş iş axınlarını düşünülmüş şəkildə aktivləşdirin

CLI ilə idxal adətən iş axınlarını qeyri-aktiv saxlayır. n8n 2.x-də hər idxal olunmuş iş axınının dərc olunma vəziyyətini yoxlayın və yalnız işlətmək istədiyiniz axınları dərc edin. Öz serverinizdəki CLI, həmçinin n8n publish:workflow --id=YOUR_WORKFLOW_ID əmrini dəstəkləyir. n8n işləyərkən CLI ilə dərcin aktivləşdirilməsi və ya ləğvi yalnız n8n yenidən başladıqdan sonra qüvvəyə minir. Planlaşdırılmış tetikləyiciləri və istehsal vebhuklarını yoxlamazdan, yaxud trafiki yönləndirməzdən əvvəl xidməti yenidən başladın.

Docker Compose üçün toplu ixrac nümunəsi: n8n xidmətinizin adı belədirsə: n8n, aşağıdakı rəsmi CLI ehtiyat nüsxələmə əmrlərini işlədə bilərsiniz. Çıxış yolu qəsdən qoşulmuş daimi .n8n kataloqunda, çünki konteynerin içindəki ixtiyari kataloqlar yenidən yaradılarkən itə bilər. Kataloqun n8n konteyner istifadəçisi tərəfindən yazıla bildiyini təsdiqləyin. İş axını və giriş məlumatları JSON fayllarını ayrı-ayrı kataloqları—n8n bir kataloqda hər iki növ olduqda idxal problemi yarandığını sənədləşdirir.

n8n 2.x qaralama və dərc olunmuş versiyanın ehtiyat nüsxəsi: adi --backup iş axını ixracı cari qaralamaları saxlayır; bunlar istehsalda dərc edilmiş versiyalardan fərqlənə bilər. Müəyyən iş axınının faktiki dərc olunmuş versiyasını qorumaq üçün onu ayrıca aşağıdakı vasitə ilə ixrac edin: docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, çıxış qovluğunun mövcud və yazıla bilən olduğuna əmin olduqdan sonra. CLI həmçinin tarixi versiyanı ixrac edə bilər; bunun üçün --version=VERSION_ID. Bu nüsxələri tam ehtiyat nüsxə ilə birlikdə serverdən kənarda saxlayın; qaralama JSON-un istehsalda dərc olunmuş faktiki vəziyyəti əks etdirdiyini fərz etməyin.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Köçürülmüş ~/n8n-recovery/cli kataloqu VPS-də qalır, ta ki onu qorunan və müstəqil ehtiyat nüsxə yerinə köçürənədək. Giriş məlumatlarının ixracı standart olaraq şifrələnir və idxal zamanı uyğun şifrələmə açarı tələb edir. İstifadə etməyin: --decrypted (yalnız ciddi nəzarət olunan miqrasiya istisnadır): bu, sirləri açıq mətn şəklində yazır. Məxfi iş axını məntiqi və ya giriş məlumatları olan ixracları heç vaxt açıq GitHub repozitoriyasına göndərməyin. Bəzi üçüncü tərəf GitHub giriş məlumatı ehtiyat nüsxələmə şablonları deşifrə edilmiş sirləri bilərəkdən ixrac edir; özəl repozitoriya giriş məhdudiyyətidir, şifrələmə deyil. Hər şablonun faktiki ixrac parametrlərini və saxlama icazələrini yoxlayın, sirləri serverdən kənara göndərməzdən əvvəl şifrələyin və təsadüfən açıq mətn kimi yükləmə ilə ifşa olunmuş giriş məlumatlarını yeniləyin.

Toplu idxal nümunəsi: təmiz hədəfdə ilkin sahib hesabının quraşdırılmasını tamamlayın, ilkin şifrələmə açarını təqdim edin və saxlanmış ehtiyat fayllarının həmin bərpa VPS-ində əlçatan olduğuna əmin olun. Aşağıdakı əmrlər təyinat qovluğunu yaradır və workflows/ və credentials/ alt qovluqlarını hostdan n8n konteynerinə köçürür; Docker disk quruluşunuz fərqlidirsə, yolları uyğunlaşdırın:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

n8n konteyner istifadəçisinin fayllara sahiblik və giriş hüquqlarını yoxlayın. Təsdiqlənmiş geri qaytarma planı olmadan məlumatla dolu istehsal instansiyasına idxal etməyin: iş axınlarının və giriş məlumatlarının ID-ləri mövcud qeydlərin üzərinə yaza bilər. Sonra işlədin:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

İdxal olunan ID-lər mövcud iş axınlarını və ya giriş məlumatlarını əvəz edə bilər; sınaq idxalları üçün təcrid olunmuş instansiya istifadə edin, sonra giriş məlumatlarını və aktivləşdirmə/dərc vəziyyətlərini yoxlayın. n8n 2.x-də JSON qaralamasının bərpası iş axınının dərc olunduğunu və planlaşdırılmış tetikləyicilərlə işləyə biləcəyini özlüyündə sübut etmir. İdxal təhlükəsizliyi: bir neçə əsas prosesli olmayan n8n instansiyasında əvvəllər aktiv olmuş cron tetikləyiciləri CLI idxalından sonra instansiya yenidən başlayana qədər işləyə bilər. İstehsal tetikləyicilərini dayandırın və ya təcrid edin, bərpa olunmuş tapşırıqları aktivləşdirməzdən əvvəl n8n-i yenidən başladın; təkrar icranın olmadığını yoxlayın. CLI ixraclarına deyil ilkin istifadəçiləri, icra jurnallarını, instansiya dəyişənlərini və ya şifrələmə açarını ehtiva etmir. --backup təyin edir --all --pretty --separate, «tam instansiya» deyil. Mənbələr: n8n-in aktual rəsmi ehtiyat nüsxələmə və bərpa təlimatı, həmçinin n8n CLI əmrlərinin arayışı.

GitHub və ya Google Drive şablonlarından toplu bərpa: bu, yalnız iş axını JSON-u üçün alternativdir; instansiyanın verilənlər bazası, istifadəçilər, şifrələnmiş giriş məlumatlarının dəyərləri və şifrələmə açarı üçün deyil. API əsaslı şablonu işə salmazdan əvvəl onun n8n API və saxlama icazələrini, seçilmiş ehtiyat nüsxə versiyasını və hədəf instansiyanı, uyğun ID-ləri yeniləyib-yeniləmədiyini və silinmiş iş axınlarını yenidən yaradıb-yaratmadığını, həmçinin dərc etmə davranışını yoxlayın. Bütün şablonlar hədəfdə olmayan ID-ni yenidən yaratmır; avtomatik bərpaya güvənməzdən əvvəl bu ssenarini təcrid olunmuş mühitdə sınaqdan keçirin.

Tez-tez verilən suallar

n8n-in ehtiyat nüsxələnməsi və bərpası: tez-tez verilən suallar

n8n-in ehtiyat nüsxəsi üçün yalnız iş axınlarını ixrac etmək kifayətdirmi?

Xeyr. İş axını ixracları məntiqi surət kimi faydalıdır, lakin tam bərpa üçün giriş məlumatları, uyğun şifrələmə açarı, verilənlər bazasının vəziyyəti, daimi fayllar və ikili verilənlər anbarı da tələb oluna bilər.

Verilənlər bazam varsa, n8n şifrələmə açarı da lazımdırmı?

Bəli, əgər həmin bazada saxlanan şifrələnmiş giriş məlumatlarının işlək qalmasını istəyirsinizsə. İlkin açarı təhlükəsiz şəkildə qoruyun.

PostgreSQL bazasının ehtiyat nüsxəsini yaratmalıyam, yoxsa iş axınlarını və giriş məlumatlarını ixrac etməliyəm?

Fəlakətdən sonra bərpa üçün verilənlər bazasını və şifrələmə açarını qoruyun. Məntiqi ixraclar instansiyanın bütün hissələrini əvəz etmək üçün deyil, miqrasiya və seçmə bərpa üçün əlavə vasitə kimi dəyərlidir.

VPS anlıq görüntüsü yeganə ehtiyat nüsxəm ola bilərmi?

Bunu bərpanın bir səviyyəsi kimi qiymətləndirmək daha doğrudur. Ayrıca serverdənkənar ehtiyat nüsxə saxlayın ki, provayderin, hesabın, serverin və ya anlıq görüntünün sıradan çıxması bütün bərpa nöqtələrini eyni anda itirməsin.

Ehtiyat nüsxəmin işlədiyini necə yoxlaya bilərəm?

Ehtiyat nüsxəni təmiz sınaq mühitinə bərpa edin, giriş məlumatlarının deşifrə olunduğunu yoxlayın və tipik iş axınlarını işə salın. Ehtiyat nüsxələmə tapşırığının uğurlu başa çatması təkbaşına bərpa imkanını sübut etmir.

GitHub və ya Google Drive üzərindəki iş axını ehtiyat nüsxələrinə yadda saxlanmış giriş məlumatlarının gizli dəyərləri daxildirmi?

Yalnız iş axınlarından ibarət JSON ehtiyat nüsxələrinə n8n-in giriş məlumatları anbarında idarə olunan gizli dəyərlər və instansiyanın şifrələmə açarı daxil deyil. Bununla belə, ixrac edilən JSON giriş məlumatlarının adlarını və ID-lərini, eləcə də autentifikasiya başlıqları kimi birbaşa qovşaq parametrlərinə yazılmış sirləri aça bilər. JSON fayllarını yükləməzdən və ya paylaşmazdan əvvəl yoxlayıb qoruyun. Tam bərpa üçün verilənlər bazasının və ilkin açarın ehtiyat nüsxəsini yaradın və ya sınaqdan keçirilmiş bərpa ilə dəstəklənən şifrələnmiş CLI giriş məlumatı ixraclarından istifadə edin. Təkcə iş axınlarının GitHub və ya Google Drive şablonu fəlakətdən sonra tam bərpa deyil.
