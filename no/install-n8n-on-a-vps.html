INSTALLASJON MED DOCKER

Installer n8n på en VPS

Installer n8n på en VPS med Docker Compose og PostgreSQL. Et produksjonsoppsett trenger også vedvarende lagring av applikasjons- og databasedata, en stabil N8N_ENCRYPTION_KEY, et offentlig vertsnavn, HTTPS og riktig webhook-konfigurasjon. Kontroller disse delene før du aktiverer arbeidsflyter i produksjon.

FORUTSETNINGER

Klargjør VPS-en før du starter n8n

Linux-VPS

Bruk en vedlikeholdt Linux-server med nok ressurser til n8n, PostgreSQL, Docker og den omvendte proxyen.

DNS

Pek et domene eller underdomene mot VPS-en før du utsteder TLS-sertifikater og publiserer webhook-adresser.

Docker Compose

Installer Docker Engine og Compose-utvidelsen fra støttede pakker for operativsystemet.

Brannmur

Åpne bare portene som trengs til administrasjon og webtrafikk. Hold PostgreSQL og interne applikasjonstjenester utilgjengelige fra internett.

Skal du installere på en VPS som allerede kjører nettsteder? Du kan legge n8n til en server du administrerer selv, så lenge CPU, RAM og lagring har tilstrekkelig kapasitet. Men hvis Nginx, Apache, Caddy eller en annen omvendt proxy allerede bruker port 80/443, må du ikke starte Caddy-containeren i eksempelet nedenfor uten endringer: Portene vil kollidere. Rutt i stedet et nytt n8n-underdomene gjennom den eksisterende omvendte proxyen med passende privat nettverk, eller bruk en ny VPS til det nøyaktige Compose-eksempelet. Behold de andre nettstedene og TLS-oppsettet deres. Eksempelet forutsetter at port 80/443 er ledige.

INSTALLASJON DU KAN KOPIERE OG TILPASSE

Installer n8n på VPS-en med Docker Compose

Bruk dette eksempelet til å sette opp n8n på en selvadministrert Linux-VPS. Du installerer og vedlikeholder n8n selv. En server kjøpt gjennom partneren vår kommer ikke med n8n forhåndsinstallert. Eksempelet kombinerer n8n, PostgreSQL, en ekstern oppgavekjører og Caddy med HTTPS i et privat Compose-nettverk. Det er en konfigurasjonsmal, ikke en påstand om at oppsettet er testet i drift.

Vil du installere en ny instans raskest mulig? n8n tilbyr også et offisielt Docker-oppsett med én kommandolinje. Du kan laste ned og gjennomgå skriptet med curl -fsSL https://get.n8n.io -o get-n8n.sh før du kjører sh get-n8n.sh. Dette alternativet starter en første instans med SQLite på en lokal adresse og inkluderer sandkassetjenestene til n8n Assistant. Det er ikke det samme som VPS-oppsettet med offentlig HTTPS og PostgreSQL som beskrives her. Den offisielle komplette sandkassestakken trenger mer RAM og CPU enn en enkel n8n-installasjon (Compose-veiledningen angir minst 4 GB RAM / 2 vCPUs). Fortsett med den manuelt konfigurerte løsningen nedenfor for en produksjons-VPS som skal være tilgjengelig fra internett.

1. Klargjør Docker, DNS og tilgang

Koble til over SSH med sudo-tilgang, og pek en DNS A-oppføring for n8n.example.com mot VPS-ens IPv4-adresse. På en ny VPS med Ubuntu 22.04, 24.04 eller 26.04 installerer følgende kommandoer Docker Engine og den moderne docker compose utvidelsen fra Dockers offisielle signerte apt pakkekilde:

# Ny installasjon med offisiell Ubuntu 22.04 / 24.04 / 26.04
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Registrer den signerte apt-pakkekilden fra Docker
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

Dette er metoden som anbefales for produksjon i den offisielle installasjonsveiledningen for Docker på Ubuntu. Ikke installer eller fjern Docker ukritisk på en VPS som allerede kjører containere eller andre nettsteder. Undersøk først den eksisterende installasjonen og mulige pakkekonflikter. For Debian eller en annen distribusjon må du bruke den tilsvarende offisielle veiledningen for operativsystemet i stedet for Ubuntu-kommandoene.

Kontroller deretter Docker, Compose-utvidelsen, DNS og arbeidsmappen:

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

Hvis getent hosts ikke gir noen adresse eller gir feil adresse, må du rette DNS før Caddy startes. Erstatt n8n.example.com overalt i veiledningen med ditt faktiske vertsnavn. Docker krever vanligvis root-rettigheter. Hvis SSH-brukeren din ikke kan kjøre de senere docker compose kommandoene direkte, setter du sudoforan dem. Å legge en bruker til docker gruppen gir tilgang som tilsvarer root og bør ikke gjøres uten grundig vurdering på en delt server.

Sørg for at den faktiske porten for SSH-administrasjon fortsatt er tilgjengelig før du aktiverer en brannmur. Tillat innkommende HTTP (80) og HTTPS (443) for sertifikatutstedelse og redigeringsverktøyet. Porter som Docker publiserer fra containere, kan omgå enkelte UFW-regler. Les Dockers brannmurveiledning, og publiser bare Caddy-portene som er ment å være åpne. Dette Compose-eksempelet publiserer bevisst ikke PostgreSQL (5432), n8n (5678) eller oppgavekjørerens meldingsformidler (5679) på det offentlige internettet.

2. Opprett miljøverdier, og ta vare på nøkkelen

Kjør følgende kommando tre ganger i prosjektmappen for å generere tre ulike tilfeldige heksadesimale verdier:

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

Opprett filen .env med malen nedenfor. Erstatt hver forekomst av REPLACE_WITH_RANDOM_HEX med en ulik generert verdi, og endre vertsnavn og tidssone. Versjonsteggen 2.42.5 som vises, er den stabile versjonen oppført 8. oktober 2026, og brukes her som et datert konfigurasjonseksempel, ikke som noen garanti for at oppsettet er testet i drift eller vil forbli sikkert. Kontroller de nyeste offisielle n8n-utgivelsene før installasjon, og bruk samme verifiserte versjon for n8n-imaget og oppgavekjøreren.

# .env — erstatt de tre eksempelhemmelighetene
# Velg en vedlikeholdt n8n-versjon; bruk samme versjon for n8n og oppgavekjøreren.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

Legg aldri .env i et offentlig repositorium. Oppbevar krypteringsnøkkelen og instruksjoner for gjenoppretting sikkert utenfor VPS-en. Nøkkelen må være den samme etter at containere opprettes på nytt eller løsningen flyttes.

3. Skriv compose.yaml for en ny installasjon

Opprett filen compose.yamli samme mappe. Eksempelet følger n8ns offisielle konvensjoner for miljøvariabler og PostgreSQL 18-banen PGDATA som er dokumentert av prosjektet for n8n-hosting:

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

De fire tjenestene har hver sin rolle: PostgreSQL lagrer databasetilstanden, n8n kjører arbeidsflytene, n8n-runner utfører oppgaver med en samsvarende versjon og en felles autentiseringstoken, mens Caddy håndterer offentlig HTTPS. En ekstern oppgavekjører er ikke det samme som Redis-kømodus. Bare Caddy publiserer porter på vertsmaskinen. Dette enkle eksempelet bruker én databaserolle for oppsettet. Se det offisielle PostgreSQL-eksempelet fra n8n for bedre atskillelse av databasetilgang.

4. Opprett Caddyfile for HTTPS

Opprett filen Caddyfile (stor C og ingen filtype) ved siden av compose.yaml. Erstatt eksempelvertsnavnet overalt med ditt eget DNS-navn:

n8n.example.com {
    reverse_proxy n8n:5678
}

Caddy henter og fornyer offentlige TLS-sertifikater når domenet peker riktig og ekstern trafikk kan nå portene 80/443. Ikke pek DNS mot localhost. Hvis du erstatter Caddy med en annen omvendt proxy, må du videresende de opprinnelige headerne for vert, protokoll og klientadresse, og justere N8N_PROXY_HOPS etter det faktiske antallet betrodde proxyhopp.

5. Start containerne, og test fra et eksternt nettverk

Kjør kommandoene nedenfor fra prosjektmappen etter at du har lagret .env, compose.yaml og Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

Den siste kommandoen kontrollerer den offentlige HTTPS-adressen til helsesjekken. Hvis sertifikatet ennå ikke er utstedt, bør du undersøke Caddy-loggene, DNS og portene før du konkluderer med at n8n ikke fungerer. Åpne https://n8n.example.com, opprett den første eierkontoen med én gang, og aktiver passende beskyttelse av innloggingen. Kontroller at instansen faktisk kjører en arbeidsflyt, ikke bare at redigeringsverktøyet lastes inn:

  1. Opprett en arbeidsflyt med en Webhook utløser i redigeringsverktøyet. Sett HTTP Method til GET, velg Path vps-check, og sett Respond til Immediately. Lagre arbeidsflyten.
  2. Klikk på Listen for Test Event, kopier hele Test URL som vises i n8n, og kjør fra en annen enhet curl -i 'PASTE_TEST_URL_HERE' med den kopierte URL-en. Du skal få en vellykket HTTP-respons, og den innkommende hendelsen skal vises i redigeringsverktøyet til n8n. Test-URL-er fungerer bare mens n8n lytter etter hendelsen.
  3. Publiser arbeidsflyten, bytt noden til dens Production URL, kopier adressen og kjør curl -i 'PASTE_PRODUCTION_URL_HERE' på nytt. Bekreft kjøringen under fanen Executions til arbeidsflyten. Forespørsler til produksjons-webhooks krever at arbeidsflyten er publisert. Innholdet vises ikke i redigeringsverktøyets testvisning.

Dette er en bevisst enkel funksjonstest uten autentisering. Send aldri hemmeligheter til dette endepunktet. Avpubliser eller slett arbeidsflyten etter testen, eller konfigurer webhook-autentisering og IP-begrensninger før du bruker et offentlig endepunkt med ekte data. Se den offisielle dokumentasjonen om test- og produksjons-webhooks.

6. Ta sikkerhetskopi før du endrer fastsatte versjoner

Lagre en gjenopprettbar PostgreSQL-dump og det vedvarende datavolumet til n8n, .env/krypteringsnøkkelen og nødvendige eksterne filer på lagring utenfor serveren. Test gjenoppretting med guiden for sikkerhetskopiering og gjenoppretting før du oppdaterer produksjon. Eksempelkommandoer:

# Ta sikkerhetskopi av databasen, krypteringsnøkkelen og instansdataene,
# og filene før du endrer de fastsatte versjonene.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# Etter at sikkerhetskopien er sikret utenfor denne VPS-en:
docker compose pull
docker compose up -d
docker compose ps

Endre den fastsatte N8N_VERSION først etter at du har lest utgivelsesnotatene. Både n8n og oppgavekjørerens image må oppgraderes samtidig. Ikke kjør docker compose down -v under vanlig vedlikehold, siden det sletter navngitte datavolumer. Store versjonsoppgraderinger av PostgreSQL krever en plan for databaseoppgradering eller dump/gjenoppretting. Å erstatte imaget for PostgreSQL 18 med en annen hovedversjon er ikke automatisk migrering.

Autoritative kilder: n8ns Docker Compose-veiledning, n8ns konfigurasjon av omvendt proxy/webhooks og offisielle merknader om PostgreSQL-oppsett. Det gjøres ingen antakelser om ytelsestester av infrastrukturen eller leverandørspesifikke forhåndsinstallerte funksjoner.

VANLIGE SPØRSMÅL

Vanlige spørsmål om installasjon av n8n med Docker

Krever n8n PostgreSQL når det kjøres i Docker?

Docker krever ikke PostgreSQL, og små oppsett kan bruke SQLite. For produksjonsrettet drift på en VPS gir PostgreSQL et mer robust databasegrunnlag og støtter senere skalering med kømodus.

Hvorfor beholde et vedvarende n8n-volum når PostgreSQL lagrer data?

Den vedvarende n8n-mappen kan inneholde viktig instanstilstand og konfigurasjon. Ta vare på den i tråd med oppsettet i stedet for å anta at databasen er det eneste som trengs ved gjenoppretting.

Hvorfor viser webhooken min localhost?

Containerens interne adresse er forskjellig fra den offentlige adressen. Konfigurer eksternt vertsnavn, protokoll og webhook-URL, og sørg for at den omvendte proxyen videresender nødvendige headere.

Bør port 5678 være offentlig?

Ved vanlig produksjonsdrift bak en omvendt proxy åpner du HTTPS på proxyen og holder applikasjonsporten til n8n intern, med mindre det finnes en særskilt driftsmessig grunn til noe annet.

Trenger jeg Redis?

Ikke ved et vanlig Docker-oppsett med én instans. Redis blir aktuelt når du bevisst går over til kømodus og arbeidere.

Er eksterne oppgavekjørere i n8n det samme som arbeidere i kømodus?

Nei. Eksterne oppgavekjørere utfører støttet oppgavekode utenfor hovedprosessen til n8n og bruker en felles autentiseringstoken. Redis-kømodus fordeler kjøring av arbeidsflyter og har egne infrastrukturkrav. Dette eksempelet viser en ekstern oppgavekjører, ikke Redis-kømodus. Bruk samme image-versjon for oppgavekjøreren og n8n.
