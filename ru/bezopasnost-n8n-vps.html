Как защитить n8n на VPS

Чтобы защитить n8n на VPS, закройте n8n (5678), PostgreSQL (5432) и Redis (6379), если он используется, от публичного интернета. Используйте обратный прокси с HTTPS, SSH-ключи и MFA, сохраняйте ключ шифрования, проверяйте подлинность вызовов вебхуков, ограничивайте опасные возможности процессов и проводите аудит экземпляра. Защищайте редактор отдельно от публичных маршрутов вебхуков. Один HTTPS не обеспечивает безопасность подключённых сервисов.

КРАТКИЙ ЧЕК-ЛИСТ

Минимальная защита перед открытием доступа извне

Начните с доступных портов, HTTPS, проверенного административного доступа, MFA и защиты сохранённых учётных данных. Проверяйте подлинность каждого входящего вебхука до запуска чувствительных операций. После изменения правил доступа убедитесь, что нужные редакторы и внешние интеграции работают, затем выполните аудит безопасности n8n.

Только HTTPS

Разместите n8n за правильно настроенным обратным прокси с TLS и последовательно используйте публичный HTTPS-адрес для редактора и вебхуков.

Минимум открытых портов

Публикуйте только порты, необходимые для внешнего трафика. PostgreSQL, Redis и внутренние порты приложения закройте от интернета.

Усильте защиту SSH

Используйте ключи для администрирования, ограничивайте круг пользователей с доступом и устанавливайте исправления ОС.

Защитите учётные данные

Сохраняйте неизменный ключ шифрования n8n в секрете. Считайте файлы окружения, доступ к базе и резервные копии конфиденциальными ресурсами.

ГРАНИЦА СЕТИ

Обратный прокси, HTTPS и доверенные заголовки

Завершение TLS на прокси

Используйте Nginx, Caddy или Traefik для завершения HTTPS. Перенаправляйте обычный HTTP и не открывайте порт приложения n8n напрямую, если точкой входа должен быть прокси.

Настройка прокси

При работе n8n за обратным прокси правильно задайте число прокси в цепочке и передавайте заголовки, необходимые n8n для восстановления исходного запроса клиента.

Защищённые cookie

Предоставляйте редактор через HTTPS, чтобы cookie аутентификации оставались защищёнными. Не обходите неисправную настройку TLS ослаблением защиты cookie.

URL вебхуков

Укажите доступное извне доменное имя с HTTPS в публичном URL вебхуков, чтобы сгенерированные адреса не ссылались на внутренний контейнер или HTTP.

Закройте редактор, не нарушив работу вебхуков. По возможности ограничьте административный доступ VPN, доверенными IP или прокси с аутентификацией. Приёмники публичных вебхуков и маршруты обратного вызова OAuth могут требовать внешней доступности: перед применением правила прокси проверьте и вход доверенного редактора, и реальный внешний обратный вызов. Принимайте заголовки адреса клиента только от доверенных прокси, а не из произвольного запроса.

Проверяйте подлинность отправителей вебхуков: в узле Webhook выберите аутентификацию Basic, Header или JWT вместо None, если отправитель её поддерживает. При необходимости используйте параметр списка разрешённых IP и проверяйте подпись провайдера, если интеграция поддерживает подписанные запросы. Трудно угадываемый URL не заменяет аутентификацию. При необходимости ограничьте частоту запросов на прокси и убедитесь, что допустимые всплески не блокируются. Официальные варианты аутентификации Webhook.

УСИЛЕНИЕ ЗАЩИТЫ VPS

Сократите поверхность атаки сервера

Межсетевой экран

По умолчанию запрещайте незапрошенный входящий трафик и разрешайте только необходимые сервисы. Порты базы и Redis обычно должны оставаться в закрытых или локальных сетях.

SSH

Предпочитайте SSH-ключи паролям, отключайте ненужные способы входа и ограничивайте административный доступ. Права, эквивалентные root, должны строго контролироваться.

Обновления ОС

Обновляйте Linux-хост и среду контейнеров. Защита приложения не компенсирует уязвимую или устаревшую ОС.

Доступ к контейнерам

Публикуйте только порты, которым нужен доступ через хост. Внутренние сервисы должны общаться по закрытым сетям Docker, а не публичным интерфейсам.

Проверьте состояние перед изменением межсетевого экрана или SSH: проверьте прослушиваемые порты командой sudo ss -lntp, опубликованные порты Docker — командой docker compose ps из каталога проекта, а правила хоста — командой sudo ufw status verbose при использовании UFW. До отключения паролей проверьте фактический порт SSH и успешный вход по ключу в отдельной сессии. Опубликованные порты Docker могут обходить UFW; один статус межсетевого экрана не доказывает, что порт 5678 закрыт. Проверьте реальную доступность извне. Особенности Docker/UFW.

Проверьте автоматические обновления безопасности Ubuntu, не полагаясь на предположения: изучите apt-config dump APT::Periodic::Unattended-Upgrade и журнал /var/log/unattended-upgrades/unattended-upgrades.log. Если автоматические обновления безопасности отключены, команда sudo dpkg-reconfigure unattended-upgrades открывает поддерживаемый диалог настройки. Перед включением на рабочем VPS изучите поведение при перезагрузках и перезапусках сервисов. Обновления Ubuntu через APT не обновляют автоматически образ Docker n8n и все сторонние репозитории ПО. Документация Ubuntu по автоматическим обновлениям.

Дополнительный мониторинг перебора SSH: Fail2Ban обнаруживает повторяющиеся неудачные входы по SSH. Если он установлен и настроен для SSH, проверьте правило защиты командой sudo fail2ban-client status sshd и убедитесь, что оно читает фактический журнал аутентификации SSH или системный журнал и соответствует настроенному порту. Это дополняет SSH-ключи и сетевые ограничения, но не заменяет их. Не копируйте фиксированный порт SSH или правило блокировки без проверки существующего доступа. Рекомендации Ubuntu по защите SSH.

БАЗА ДАННЫХ И REDIS

Сохраняйте внутренние сервисы закрытыми

В обычном Docker Compose PostgreSQL и Redis режима очереди должны быть доступны нужным контейнерам через закрытую сеть, а не порты хоста. Проверьте командой docker compose ps , что 5432 и 6379 не опубликованы наружу; отдельно изучите правила межсетевого экрана VPS или облака. Сетевые правила не заменяют учётные данные базы с минимально необходимыми правами.

PostgreSQLПривяжите его к закрытому интерфейсу или сети контейнеров, если удалённый доступ не требуется явно и не защищён отдельно.
RedisRedis режима очереди — часть инфраструктуры, а не публичный сервис. Разрешите сетевой доступ только тем компонентам n8n, которым он нужен.
Учётные данныеИспользуйте отдельные учётные данные базы только с необходимыми приложению правами и защищайте их вне системы контроля версий.
Передача данныхЕсли трафик базы проходит через недоверенные сети, используйте подходящее шифрование транспорта, не полагаясь на шифрование учётных данных приложением.

СЕКРЕТЫ N8N

Защитите ключ шифрования и доступ к учётным данным

Ключ шифрования

n8n шифрует сохранённые учётные данные своим ключом. Используйте один и тот же ключ при перезапусках и на всех воркерах и защищайте его отдельно от обычного содержимого приложения.

Секреты окружения

Не добавляйте пароли, токены и ключ шифрования в публичный репозиторий. Ограничьте доступ к файлам окружения и секретам развёртывания.

Доступ пользователей

Давайте доступ к редактору только доверенным пользователям. Процессы могут подключаться к чувствительным системам, обрабатывать секреты и выполнять узлы с широкими возможностями.

Права учётных данных

По возможности используйте сервисные аккаунты и API-токены с узкими правами. Скомпрометированный процесс не должен автоматически получать широкий доступ к посторонним системам.

Настройки n8n, которые стоит проверить: N8N_BLOCK_ENV_ACCESS_IN_NODE=true блокирует доступ узлов Code и выражений к значениям окружения; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true задаёт права на файл настроек только для владельца. Сохраняйте N8N_ENCRYPTION_KEY неизменным и в защищённых резервных копиях: при первом запуске n8n может создать случайный ключ, но его потеря способна сделать сохранённые зашифрованные учётные данные непригодными. Не заменяйте рабочий ключ без подготовки; используйте официально поддерживаемую процедуру ротации. Блокировка доступа к окружению может нарушить интеграции, поэтому проверьте её до изменения рабочей системы. Описание переменных безопасности n8n.

РИСКИ РАБОЧИХ ПРОЦЕССОВ

Узлы могут расширять границы доступа

Самостоятельное размещение даёт процессам широкие возможности. Выполнение кода, доступ к командной оболочке, произвольные HTTP-запросы и сторонние узлы сообщества могут увеличить риски. Отключайте ненужные функции и проверяйте недоверенные импортированные процессы до запуска.

Используйте точные поддерживаемые настройки: задайте NODES_EXCLUDE как JSON-массив отключаемых узлов, например n8n-nodes-base.executeCommand и n8n-nodes-base.readWriteFile, если они не используются. В новых версиях некоторые опасные узлы уже заблокированы по умолчанию; перед изменением изучите фактический список. Официальное исключение узлов.

Начиная с n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true включает проверку исходящих HTTP-запросов к внутренним, петлевым адресам и диапазонам адресов метаданных. Допустимые процессы с внутренними API могут перестать работать; при необходимости разрешайте только конкретные подконтрольные вам адреса. Сегментация сети должна оставаться основной защитой. Для изоляции узлов Code изучите использование внешних исполнителей задач. Защита SSRF · Изоляция исполнителей задач.

Узлы сообществаУстанавливайте только доверенные пакеты: они выполняются внутри вашего окружения n8n.
Опасные узлыИсключайте ненужные узлы, если их возможности выходят за предполагаемые границы процессов.
SSRFИспользуйте защиту SSRF n8n и сетевые ограничения, если процессы не должны обращаться к внутренним адресам или сервисам метаданных.
Импорт процессовДо активации проверяйте импортированные процессы, учётные данные, выражения и исполняемые шаги.

АУДИТ И ОБНОВЛЕНИЯ

Безопасность требует постоянной работы

Выполните аудит безопасности n8n

Официальная команда CLI — n8n audit. Если сервис Docker Compose называется n8n, выполните docker compose exec -T n8n n8n audit в каталоге развёртывания. Изучите пять категорий: неиспользуемые учётные данные, опасные шаблоны SQL-запросов, доступ к файловой системе, опасные узлы и узлы сообщества, а также риски экземпляра, включая незащищённые вебхуки и устаревшие выпуски. Устраните применимые замечания и повторите проверку. Это не тест на проникновение. Официальное руководство по аудиту.

Обновляйте осознанно

Поддерживайте версию n8n достаточно актуальной для получения исправлений безопасности. Изучайте примечания к выпускам и проверяйте важные обновления, не оставляя доступный из интернета экземпляр постоянно устаревшим.

Следите за аутентификацией

Отслеживайте необычный доступ, изменения процессов и ошибки. Дополнительно ограничьте интерфейс редактора, если широкая публичная доступность не нужна.

Подготовьте откат и восстановление

Перед значительными обновлениями создавайте пригодные для восстановления копии. Подробный состав копий и процедура восстановления описаны в отдельном руководстве.

Сократите хранение чувствительных данных выполнений: успешные запуски могут сохранять клиентские данные и токены. При необходимости задайте EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, оставьте EXECUTIONS_DATA_PRUNE=trueи выберите EXECUTIONS_DATA_MAX_AGE в часах, например 168 (семь дней). Это настраиваемые примеры, а не юридические сроки хранения. Меньше истории — меньше данных для отладки и расследования; работающие, ожидающие и снабжённые примечаниями выполнения могут очищаться иначе. Официальные правила хранения выполнений.

При подозрении на компрометацию: ограничьте вредоносный доступ, не уничтожая доказательства; изучите активность прокси, хоста и n8n и изменённые процессы; отзовите или замените потенциально раскрытые учётные данные внешних сервисов; устраните причину и при необходимости восстанавливайтесь только из проверенных пригодных копий. Проверьте затронутые URL вебхуков, аккаунты редакторов и подключённые сервисы; не предполагайте, что HTTPS, снимки или покупка VPS включают реагирование на инциденты.

ЗАЩИТА АККАУНТОВ И ПЛАТФОРМЫ

Защитите редактор вместе с VPS

Усильте защиту входа

Включите двухфакторную аутентификацию аккаунтов редактора и требуйте MFA через политики безопасности n8n, если ваша редакция поддерживает централизованное применение политик.

Ограничьте право редактирования процессов

Доступ к редактору — привилегированный: процессы могут читать учётные данные, вызывать внутренние системы и запускать узлы с широкими возможностями. Ограничивайте круг пользователей и удаляйте аккаунты, которым доступ больше не нужен.

Отключите неиспользуемые возможности

Сократите поверхность атаки приложения: отключите ненужный публичный API и заблокируйте опасные узлы и функции, которые не нужны вашей системе.

Осознанно применяйте защиту SSRF и ограничения секретов

Для процессов с произвольными HTTP-запросами оцените защиту SSRF n8n и не храните секреты в коде процессов, публичных репозиториях и общедоступных файлах окружения.

Ограничьте неиспользуемые административные интерфейсы: N8N_PUBLIC_API_DISABLED=true отключает публичный REST API n8n, а N8N_PUBLIC_API_SWAGGERUI_DISABLED=true отдельно отключает интерактивную площадку API. Делайте это, только если интеграциям не нужны эти функции. Отключение REST API не добавляет аутентификацию URL вебхуков процессов. Используйте MFA для редакторов, а централизованные политики — только при поддержке вашей редакцией n8n.

Вопросы и ответы

Безопасность n8n на VPS: частые вопросы

Нужно ли открывать порт n8n напрямую?

Если публичная точка входа — обратный прокси, откройте его, а порт приложения оставьте за ним вместо широкой публикации ненужных сервисов.

Должны ли PostgreSQL и Redis быть публичными?

Обычно нет. Доступ нужен только использующим их системам. Публикация увеличивает поверхность атаки и не помогает обычной работе n8n.

Почему важен ключ шифрования n8n?

Он защищает сохранённые n8n учётные данные и должен оставаться одинаковым во всём развёртывании. Его потеря может лишить возможности использовать зашифрованные учётные данные из восстановленных данных.

Безопасны ли узлы сообщества?

Они расширяют n8n сторонним кодом, поэтому относятся к программным зависимостям с собственными рисками цепочки поставок и прав доступа. Устанавливайте только нужные и доверенные пакеты.

Делает ли HTTPS самостоятельно размещённый n8n безопасным?

Нет. HTTPS защищает передачу данных. Для безопасности рабочей системы также нужны защита хоста, контроль доступа, закрытые внутренние сервисы, защита секретов, безопасные возможности процессов, мониторинг и обновления.

Можно ли закрыть редактор n8n, сохранив работу публичных вебхуков?

Да. Доверенный обратный прокси или VPN может ограничивать доступ редакторов и администраторов отдельно от публичных маршрутов рабочих вебхуков и обратных вызовов OAuth. После каждого изменения правил проверяйте доверенный вход и доставку внешних вебхуков, чтобы случайно не заблокировать интеграции.

Как проверять подлинность входящих вебхуков n8n?

Настройте Basic, Header или JWT в узле Webhook, если отправитель это поддерживает. Также можно использовать список разрешённых IP и проверять подписи провайдера, если они доступны. Не полагайтесь только на секретный на вид путь: проверяйте запросы до запуска чувствительных действий через API.
