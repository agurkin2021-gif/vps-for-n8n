Режим очереди n8n: когда нужны Redis и workers

Queue mode нужен при устойчивой конкуренции и backlog, а не для каждого self-hosted n8n.

Архитектура queue mode

Main координирует, Redis переносит очередь, workers выполняют задачи, PostgreSQL хранит общее состояние. Encryption key должен совпадать у компонентов.

Когда масштабировать

Рост очереди и задержки запуска после оптимизации одной инстанции — сигнал добавлять workers. Не масштабируйте workers, если bottleneck находится в PostgreSQL или внешнем API.

Ключевые технические решения

Полностью спроектировать Queue Mode

1

Queue Mode использует PostgreSQL, Redis, main/webhook процессы и workers; всем workers нужен тот же N8N_ENCRYPTION_KEY.

2

Main, webhook processors и workers должны работать на одной версии n8n.

3

Измеряйте worker concurrency, queue depth и latency; дополнительные workers не исправят медленную БД или внешний API.

4

Webhook processors — отдельный слой масштабирования; multi-main/HA не равен обычному Queue Mode.

FAQ

Полностью спроектировать Queue Mode: FAQ

1 GB — это реальный VPS?

Да. Это реальный входной VPS для лёгкой нагрузки; ограничение только в небольшом запасе ресурсов.

Почему 2 GB — более спокойная база?

Docker, ОС и небольшие пики получают больше запаса.

Зачем измерять нагрузку?

CPU, RAM, диск и latency показывают настоящий bottleneck.
