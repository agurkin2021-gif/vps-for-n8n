МАСШТАБИРОВАНИЕ

Режим очереди n8n

Режим очереди отделяет выполнение процессов от основного процесса n8n. Основной экземпляр принимает триггеры и создаёт выполнения, Redis координирует очередь, воркеры выполняют задания, а PostgreSQL хранит общие данные процессов и выполнений.

БЫСТРОЕ РЕШЕНИЕ

Нужен ли вам режим очереди?

Оставайтесь в обычном режиме, если

один экземпляр уверенно справляется с пиковыми выполнениями, а CPU, RAM и время выполнения стабильны. Режим очереди добавит пока ненужные компоненты.

Рассмотрите режим очереди, если

постоянные параллельные выполнения конкурируют за ресурсы, задержки растут под нагрузкой или нужно увеличить мощность запуском нескольких воркеров.

Сначала увеличьте ресурсы сервера, если

причина ограничения — просто нехватка CPU или RAM, а один более мощный экземпляр всё ещё способен уверенно справляться с нагрузкой.

Измерьте нагрузку до смены архитектуры

Обоснуйте переход пиковым параллелизмом, CPU, RAM, длительностью выполнений, длиной очереди и нагрузкой на базу.

АРХИТЕКТУРА

Как работает режим очереди n8n

1 · Основной процессПринимает таймеры, вебхуки и запросы процессов и создаёт выполнение вместо самостоятельного выполнения рабочей задачи.
2 · RedisРаботает брокером сообщений. Хранит сообщения ожидающих выполнений, чтобы следующий свободный воркер мог забрать задание.
3 · ВоркерПолучает ID выполнения, загружает данные процесса из общей базы, выполняет процесс и записывает результат обратно.
4 · PostgreSQLПредоставляет общие постоянные данные процессов и выполнений. Распределённый режим очереди не поддерживается с SQLite.

ОСНОВНЫЕ ТРЕБОВАНИЯ

Что нужно каждому развёртыванию в режиме очереди

Redis

Всем основным процессам и воркерам нужен надёжный доступ к сервису Redis, координирующему очередь.

PostgreSQL

Основной процесс и воркеры должны использовать общую базу. Режим очереди — распределённая архитектура, которую не следует строить на SQLite.

Согласованная конфигурация n8n

Основной процесс и воркеры должны работать в режиме очереди и использовать общие настройки доступа к Redis, PostgreSQL и зашифрованным учётным данным.

Ресурсы воркеров

Воркерам нужны достаточные CPU и RAM для выполняемых процессов. Добавление процессов не устраняет расход ресурсов на каждое выполнение.

Включите режим очереди в существующем самостоятельно размещённом стеке. Сначала убедитесь, что основной сервис n8n и каждый воркер имеют доступ к одной базе PostgreSQL и Redis по закрытой сети. Задайте EXECUTIONS_MODE=queue и основному процессу, и воркерам, а также укажите QUEUE_BULL_REDIS_HOST=redis и QUEUE_BULL_REDIS_PORT=6379, если redis — фактическое имя вашего сервиса Compose. Используйте DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres и соответствующие DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER и DB_POSTGRESDB_PASSWORD в каждом процессе; замените имена сервисов примера своими. Передайте всем процессам точное существующее значение N8N_ENCRYPTION_KEY . Не публикуйте порты Redis или PostgreSQL на хосте только ради соединения контейнеров одной сети Compose.

Запускайте исполнитель, а не второй редактор. Добавьте сервис-воркер n8n с той же закреплённой версией образа и общими настройками, что у основного процесса, но запускайте его командой worker . Если вы назвали сервис n8n-worker, запустите его командой docker compose up -d n8n-worker. После подтверждения реального выполнения на одном воркере можно использовать docker compose up -d --scale n8n-worker=2 для запуска второго воркера этого сервиса. Это дополнения к существующему правильно настроенному стеку Compose, а не самостоятельный установочный файл; сохраните имеющиеся постоянные тома, HTTPS-прокси, секреты и копии.

Фрагмент Compose для режима очереди в существующем стеке. Добавьте пример ниже в свой текущий compose.yaml; это не полное самостоятельное развёртывание. Предполагается, что уже есть закрытые сервисы с постоянными данными postgres и n8n , закреплённая версия N8N_VERSION в окружении, а также защищённый пароль POSTGRES_PASSWORD и исходный N8N_ENCRYPTION_KEY. Приведите имена, тома, базу и версию n8n в соответствие с существующим проектом. Добавьте настройки Redis для режима очереди и EXECUTIONS_MODE=queue также в существующий основной сервис, как описано выше.

# Добавьте к существующим сервисам; не заменяйте весь файл Compose.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

В этом фрагменте порты Redis и воркера не публикуются на хосте. Постоянное хранение Redis через журнал добавления — дополнительный уровень восстановления, а не замена внешним копиям. Сохраните существующие настройки HTTPS и аутентификации. Для узлов Code с внешними исполнителями задач настройте их отдельно для развёртывания воркеров; сам режим очереди не заменяет исполнителей задач.

Переводите существующий экземпляр с SQLite? Не меняйте просто DB_TYPE с запуском на пустой базе PostgreSQL: это не перенесёт старые процессы и учётные данные. До переключения сохраните исходную базу, постоянный каталог .n8n и исходный ключ шифрования; используйте поддерживаемый экспорт/импорт или перенос n8n, затем проверьте процессы и зашифрованные учётные данные на отдельном экземпляре. Сохраните исходные файлы для отката и подготовьтесь к восстановлению по руководству «Резервное копирование и восстановление» ниже. Никогда не удаляйте database.sqlite ради упрощения перехода.

ПАРАЛЛЕЛИЗМ ВОРКЕРОВ

Масштабируйте и число воркеров, и число заданий на воркер

Каждый воркер может обрабатывать несколько заданий одновременно. Текущий параллелизм воркера n8n по умолчанию — 10, а документация рекомендует 5 и выше. Очень низкий параллелизм при большом числе воркеров создаёт лишние подключения к базе и может исчерпать пул соединений.

Увеличивайте параллелизм, если

у воркера есть запас CPU и RAM, а процессы в основном ждут внешние сервисы, а не исчерпывают вычислительные ресурсы или память.

Добавляйте воркеры, если

один процесс-воркер стал ограничением, а база, Redis и инфраструктура могут поддержать больше параллельных выполнений.

Снижайте параллелизм, если

отдельные процессы требуют много памяти или CPU, а параллельные задания вызывают конкуренцию за ресурсы, нехватку памяти и нестабильное время выполнения.

Следите за PostgreSQL

Больше воркеров и параллелизма — выше активность базы. Рост мощности выполнения без увеличения мощности базы может лишь перенести ограничение, а не устранить его.

Проверьте, какой лимит параллелизма фактически действует. Воркер можно запустить командой n8n worker --concurrency=5или эквивалентной командой воркера в сервисе Compose. Если для N8N_CONCURRENCY_PRODUCTION_LIMIT явно задано значение, отличное от -1, в режиме очереди эта настройка имеет приоритет; иначе n8n использует значение параметра воркера --concurrency или значение по умолчанию 10. Не умножайте число воркеров на номинальный лимит, называя результат гарантированной производительностью: реальная мощность зависит от длительности заданий, CPU, памяти, внешних API и подключений PostgreSQL.

ВЕБХУКИ

Режим очереди может добавить задержку передачи выполнения

Основной процесс или обработчик вебхуков принимает HTTP-запрос, а выполняет процесс воркер. Передача через Redis добавляет накладные расходы. Для чувствительных к задержке вебхуков измеряйте полное время ответа, не предполагая, что больше воркеров автоматически ускорит каждый запрос.

ПриёмОсновной процесс или обработчик вебхуков принимает запрос.
ОчередьВыполнение передаётся Redis.
ВыполнениеСвободный воркер выполняет процесс.
ОтветПри необходимости результат возвращается через очередь.

Направляйте трафик вебхуков нужному процессу. При выделенных обработчиках n8n webhook за обратным прокси или балансировщиком направляйте рабочие пути /webhook/* и /webhook-waiting/* обработчикам вебхуков; оставьте /webhook-test/*, запросы редактора и API основному процессу. Не включайте его в пул балансировки рабочих вебхуков, если намеренно не принимаете дополнительную нагрузку. Процесс с узлом «Ответ на вебхук» может заставлять клиента ждать завершения воркера и возврата ответа, поэтому режим очереди не гарантирует мгновенный HTTP-ответ или отсутствие тайм-аутов. До переключения трафика проверьте фактический внешний вызов и поведение ответа.

БИНАРНЫЕ ДАННЫЕ

Не забывайте об общем хранилище

Ограничение файловой системы

Режим очереди не поддерживает файловое хранение бинарных данных как общее постоянное хранилище распределённых воркеров.

Внешнее бинарное хранилище

Если процессы должны сохранять бинарные данные между распределёнными воркерами, используйте схему, доступную всем необходимым экземплярам, например поддерживаемое внешнее объектное хранилище.

Большие ответы вебхуков

Ответы вебхуков от воркеров возвращаются принимающему процессу. Крупные тела ответов увеличивают расход памяти Redis и требуют продуманной настройки хранения ответов.

Спланируйте хранение до распределения воркеров

Если нагрузка сильно зависит от локальных файлов, перейдите к общему постоянному хранению до разнесения воркеров по машинам.

Ограничение больших ответов вебхуков. В текущей документации n8n для N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX указано значение по умолчанию 64 MiB для ответа воркера, возвращаемого через очередь. Redis может одновременно удерживать несколько копий, поэтому рассчитывайте примерно на 1.5 размера ответа в памяти Redis на каждый параллельный крупный ответ. Без переноса тела в хранилище слишком большой ответ завершится ошибкой, а не ускорится от добавления воркеров.

Ограничения версии и лицензии. Начиная с n8n 2.34.0воркеры могут использовать N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true для переноса слишком больших тел ответов вебхуков в доступное для чтения общее бинарное хранилище, но сначала обновите все основные процессы и обработчики вебхуков до 2.34.0 или новее. Выбранный N8N_DEFAULT_BINARY_DATA_MODE должен действительно сохранять данные и быть доступным для чтения всем участвующим процессам. Внешние бинарные хранилища S3 и Azure требуют действительной лицензии самостоятельного размещения Business или Enterprise ; не считайте, что их можно включить в Community Edition. Бинарный режим database позволяет вынести слишком большой ответ без платного внешнего хранилища, но основной экземпляр загружает всё сохранённое тело в память, а хранилище базы имеет собственный предел размера файла. Именно для переноса тела ответа в хранилищеn8n также описывает общий вариант filesystem при подключении одного диска ко всем экземплярам, но прямо не рекомендует такую схему. Не путайте этот особый путь переноса ответа с поддержкой постоянного файлового хранения бинарных данных в распределённом режиме очереди. До включения проверьте редакцию, версию и конфигурацию хранилища.

МОНИТОРИНГ

Проверьте, помогает ли очередь

Длина очереди

Если очередь растёт быстрее, чем воркеры её обрабатывают, не хватает мощности выполнения либо есть ограничение в последующем сервисе.

CPU и RAM воркера

Измеряйте загрузку и пики памяти каждого воркера. Простаивающие воркеры при растущей очереди указывают на другое ограничение.

Задержка выполнения

Отслеживайте время между созданием выполнения и фактическим началом, а не только длительность самого процесса.

Проверки состояния

Маршруты проверки состояния воркера показывают, работает ли он и готовы ли подключения к базе и Redis.

Подтвердите выполнение на воркере, а не только исправность контейнера. В правильно настроенном стеке Compose проверьте docker compose ps и docker compose logs --tail=100 n8n-worker (замените имя сервиса, если отличается). Запустите безвредный опубликованный рабочий процесс триггером по расписанию или проверочным вебхуком, затем сопоставьте его выполнение в разделе «Выполнения» n8n с фактической обработкой в журнале воркера. Успешно открывшийся редактор, работающий контейнер Redis или одно лишь задание в очереди не доказывают, что воркер выполнил работу.

Проверьте зависимости и готовность. При стандартных именах сервисов из примера команда docker compose exec -T redis redis-cli ping должна получить PONG, если это позволяет аутентификация Redis, а docker compose exec -T postgres pg_isready -U n8n -d n8n проверяет готовность PostgreSQL (адаптируйте учётные данные и имена сервисов). Включите QUEUE_HEALTH_CHECK_ACTIVE=true на воркере, если нужны его закрытые маршруты /healthz и /healthz/readiness ; маршрут готовности проверяет подключение к Redis и базе. Не открывайте эти маршруты воркера публично только ради мониторинга.

Ручные запуски — другая проверка. По умолчанию OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, поэтому ручной запуск процесса в редакторе может выполняться на основном процессе даже при правильно настроенной очереди. Задайте true только если намерены отправлять ручные выполнения воркерам и проверили изменение в тестовом окружении. Воркеры очереди также отличаются от внешних исполнителей задач n8n, у которых отдельные требования к настройке выполнения узлов Code.

ГРАНИЦЫ ВЫСОКОЙ ДОСТУПНОСТИ

Режим очереди масштабирует выполнения, но не обеспечивает автоматически высокую доступность основного процесса

Используйте общий ключ шифрования

Каждый воркер должен использовать тот же N8N_ENCRYPTION_KEY , что и основной экземпляр, чтобы расшифровывать учётные данные для выполнения процессов.

Согласуйте версии

Основной процесс, обработчики вебхуков и воркеры должны работать на одной версии n8n. Разные версии могут вызывать несовместимое поведение при поэтапных изменениях.

Обработчики вебхуков — отдельный уровень масштабирования

Если ограничением стал объём входящих вебхуков, выделенные обработчики можно разместить за балансировщиком, пока воркеры выполняют процессы. Добавляйте этот уровень только при обосновании измеренным потоком запросов.

Несколько основных процессов — отдельная функция

Запуск нескольких основных процессов для высокой доступности не равнозначен обычному режиму очереди. Сейчас n8n описывает multi-main как функцию самостоятельно размещаемой Enterprise с дополнительными требованиями к балансировщику и сессиям.

Вопросы и ответы

Режим очереди n8n: частые вопросы

Нужен ли Redis режиму очереди n8n?

Да. Redis — брокер сообщений, координирующий ожидающие выполнения между основным экземпляром и воркерами.

Может ли режим очереди использовать SQLite?

Для распределённой архитектуры очереди — нет. Основному процессу и воркерам нужен общий доступ к базе, и документация n8n указывает PostgreSQL для такой схемы.

Сколько воркеров запускать?

Универсального числа нет. Начните с измеренного параллелизма и загрузки воркеров, затем добавляйте мощность, наблюдая за PostgreSQL, Redis, CPU, RAM и длиной очереди.

Что такое параллелизм воркера n8n?

Это число заданий, которые воркер может обрабатывать одновременно. Текущее значение по умолчанию — 10; n8n рекомендует параллелизм 5 и выше вместо множества воркеров с низким параллелизмом.

Стоит ли включать режим очереди на маленьком VPS?

Только если это оправдано нагрузкой. Небольшое развёртывание, уверенно работающее одним экземпляром, обычно проще обслуживать без Redis и отдельных воркеров.
