РЕЗЕРВНОЕ КОПИРОВАНИЕ И ВОССТАНОВЛЕНИЕ

Резервное копирование и восстановление n8n

Для резервного копирования и восстановления самостоятельно размещённого n8n сохраните базу SQLite или согласованный дамп PostgreSQL, постоянную папку .n8n и исходный ключ шифрования, конфигурацию развёртывания и все внешние бинарные данные и подключённые файлы, от которых зависит система. Храните зашифрованную копию вне VPS и проверяйте восстановление на отдельном экземпляре. Экспорт процессов и учётных данных через CLI используйте для выборочного восстановления: одни JSON-экспорты не являются полной резервной копией сервера.

КРАТКИЙ ЧЕК-ЛИСТ

Что должна сохранять резервная копия n8n

База данных

Сохраните базу PostgreSQL или файл базы SQLite, используемый экземпляром. База содержит основное состояние n8n: рабочие процессы, учётные данные и данные выполнений.

Ключ шифрования

Отдельно и в защищённом месте сохраните именно тот ключ шифрования, который использует n8n. Для восстановленных зашифрованных учётных данных нужен тот же ключ.

Постоянные файлы

Включите постоянный каталог данных n8n, а также подключённые файлы, хранилище бинарных данных и ресурсы рабочих процессов, от которых зависит развёртывание.

Конфигурация развёртывания

Сохраните файлы Compose и конфигурации, а также несекретные настройки, необходимые для повторного развёртывания стека. Защитите секреты соответствующими ограничениями доступа.

ДВА УРОВНЯ РЕЗЕРВНОГО КОПИРОВАНИЯ

Логический экспорт и полное аварийное восстановление

Экспорт процессов и учётных данных

Экспорт через CLI n8n полезен для переноса, хранения версий процессов и выборочного восстановления. Учётные данные можно экспортировать в зашифрованном виде и затем импортировать с соответствующим ключом. Чтобы восстановить один процесс, скачайте его JSON через пункт Download в меню с тремя точками в редакторе, затем выберите Import from File в новом процессе для проверки или на изолированном экземпляре. Перед заменой рабочего процесса проверьте учётные данные, ID процессов и параметры узлов: восстановление JSON процесса не восстанавливает весь сервер.

Экспорт сущностей

CLI позволяет экспортировать сущности базы для переноса между поддерживаемыми типами баз данных. Таблицы истории выполнений включаются по выбору, поскольку могут быть очень большими.

Восстановление всего экземпляра

На случай полной потери сервера сохраните саму базу данных, ключ шифрования, постоянные данные и зависимости развёртывания. Не рассчитывайте, что JSON-экспорт процессов восстановит весь экземпляр.

Снимок провайдера

Снимок VPS полезен как дополнительный уровень восстановления, но не должен быть единственной копией или заменять независимо проверенную резервную копию приложения и базы данных.

БАЗА ДАННЫХ

Создавайте согласованные копии базы данных

PostgreSQL

Используйте метод создания согласованной копии PostgreSQL и храните результат вне VPS. Копия базы на том же отказавшем диске не обеспечивает аварийного восстановления.

SQLite

Если используется SQLite, сохраните файл базы из постоянного каталога данных n8n. Не копируйте базу небезопасным способом, пока она активно изменяется.

История выполнений

Определите, нужно ли восстанавливать историю выполнений. Она может значительно увеличить размер копий, поэтому решение должно учитывать требования к хранению и соблюдению правил.

Версия базы данных

Запишите тип и версию СУБД исходного развёртывания, чтобы подготовить совместимое окружение для восстановления.

PostgreSQL на VPS с Docker Compose. Если сервис PostgreSQL называется postgres и имя базы и пользователя — n8n, следующая команда создаст на хосте согласованный дамп PostgreSQL в формате custom. Перед запуском проверьте свой файл Compose и скорректируйте учётные данные базы и имена сервисов. pg_dump может создать логически согласованный снимок во время работы PostgreSQL; эта команда не сохраняет отдельную пользовательскую папку .n8n или внешние бинарные данные.

# В проекте Docker Compose; укажите свои сервис, базу и пользователя
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Проверьте, что список объектов архива читается
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Проверка списка содержимого архива выявляет очевидные проблемы формата, но не доказывает возможность восстановления данных. Храните зашифрованную копию вне сервера и проведите пробное восстановление. Параметры для конкретной базы смотрите в официальной документации PostgreSQL по pg_dump.

SQLite в Docker. При стандартном развёртывании с SQLite файл database.sqlite и конфигурация со сгенерированным ключом шифрования находятся в постоянной папке .n8n (обычно подключённой по пути /home/node/.n8n). Не считайте простое копирование работающей SQLite согласованной копией. Перед копированием папки остановите n8n и другие процессы записи в базу либо используйте поддерживаемый SQLite механизм резервного копирования без остановки, если перерыв невозможен:

# Только для SQLite и стандартного тома /home/node/.n8n
# Перед копированием SQLite остановите n8n и остальные процессы записи
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Это примеры команд для указанного сервиса и пути, а не универсальная схема томов. Скопированная папка сначала остаётся на том же VPS — перенесите её за пределы сервера и защитите. Если есть воркеры очереди или другие процессы записи, приостановите и их, учитывая реальное устройство развёртывания. В текущем руководстве n8n по полному резервному копированию описаны требования к согласованности SQLite.

Восстановление стандартной папки SQLite на чистом целевом сервере: сначала остановите сервис n8n и все процессы записи в базу. Когда совместимый контейнер сервиса n8n и его целевой том уже созданы, перенесите из копии папки .n8n содержимое обратно в тот же постоянный каталог. Это перезапишет целевые файлы, поэтому не выполняйте команду на экземпляре с данными, которые нужно сохранить:

# Запускайте только на нужном ЧИСТОМ экземпляре восстановления
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# ДО следующей команды проверьте владельца и права пользователя контейнера n8n
# Запускайте, только когда n8n может читать и изменять восстановленные файлы
docker compose start n8n
# Проверьте журналы, восстановленные учётные данные и триггеры процессов

Docker может копировать файлы в остановленные контейнеры, но их владелец в целевом каталоге может отличаться от исходного. До запуска убедитесь, что процесс n8n может читать и изменять восстановленные конфигурацию и файл базы. Если в вашей конфигурации Compose указан другой путь или bind mount, измените команду соответственно. Справочник по копированию Docker Compose. Одной папки n8n недостаточно для восстановления развёртывания с отдельной базой PostgreSQL.

КРИТИЧЕСКИ ВАЖНЫЙ СЕКРЕТ

Ключ шифрования — часть восстановления

n8n шифрует сохранённые учётные данные ключом экземпляра. Если восстановить базу или зашифрованный экспорт учётных данных без соответствующего ключа, процессы могут потерять возможность использовать эти учётные данные.

Если вы задали N8N_ENCRYPTION_KEY, восстановите именно этот секрет. В противном случае сгенерированный ключ находится в постоянном файле .n8n/config: сохраняйте его при резервном копировании и повторном развёртывании. Храните ключи восстановления в защищённом месте вне VPS. В режиме очереди все основные процессы и воркеры должны использовать один и тот же ключ.

НужноХранить защищённую копию точного ключа рабочего экземпляра.
НужноДо проверки учётных данных убедиться, что окружение восстановления использует этот ключ.
НельзяПолагаться на новый ключ, сгенерированный после повторного развёртывания сервера.
НельзяДобавлять ключ в публичный репозиторий или хранить рядом с незащищённой резервной копией.

ФАЙЛЫ И БИНАРНЫЕ ДАННЫЕ

Копия базы может не включать все зависимости процессов

Постоянные данные .n8n

Найдите и сохраните фактическую пользовательскую папку .n8n, а не только образ контейнера. В типичном Docker-развёртывании она подключена по пути /home/node/.n8n; вне Docker по умолчанию используется ~/.n8n. Если настроен N8N_USER_FOLDER, n8n создаёт .n8n внутри указанного родительского каталога. Сохраните ключ из конфигурации, а также локальную SQLite, бинарные данные и данные выполнений в файловой системе, используемые вашей установкой.

Подключённые файлы процессов

Если процессы читают или записывают каталоги хоста, подключённые к контейнеру, копируйте их отдельно. После восстановления n8n без этих файлов даже корректные процессы могут не работать.

Бинарные данные

Определите режим хранения и восстановите все внешние зависимости. Бинарные данные или данные выполнений в файловой системе могут находиться в .n8n либо отдельном каталоге; для S3/Azure Blob и других внешних хранилищ нужны собственная восстанавливаемая копия и настройки доступа. Один дамп базы не заменяет эти файлы.

Узлы сообщества

Запишите пакеты сообщества и их версии, сохраните дополнительные каталоги пользовательских узлов, заданные через N8N_CUSTOM_EXTENSIONS. Они могут находиться вне .n8n, поэтому восстановления только базы и пользовательской папки может быть недостаточно для процессов с такими узлами.

КОПИИ ВНЕ СЕРВЕРА

Копия на том же VPS — только локальная копия

Локальная копияПолезна для быстрого отката, но уязвима при потере сервера, отказе диска и разрушительных ошибках.
Копия вне сервераХраните хотя бы одну копию в хранилище, независимом от рабочего VPS.
Несколько версий копийСохраняйте несколько точек восстановления, чтобы повреждение данных или неудачное изменение не перезаписало единственную пригодную копию.
Контроль доступаКопии могут содержать учётные данные, логику процессов и конфиденциальные данные бизнеса. Шифруйте их и ограничивайте доступ.
МониторингНастройте оповещения об ошибках планового копирования и прекращении создания новых точек восстановления.

Контролируйте выполнение расписания по измеримым показателям. Записывайте время каждой успешной копии, завершение передачи, размер файла, версию исходной базы, место защищённого хранения ключа шифрования и дату последней успешной проверки восстановления. Настройте оповещения об отсутствующих, ошибочных и неожиданно пустых файлах. Шифруйте архивы перед отправкой с VPS и ограничивайте доступ к секретам восстановления. Несколько копий с датами защитят от ситуации, когда повреждение обнаружено лишь после перезаписи последней исправной копии.

Например, если допустима потеря не более шести часов изменений, успешное копирование каждые шесть часов — отправная точка, а не гарантия: ошибки заданий и задержки передачи копий на внешний сервер могут увеличить фактическую потерю. Выбирайте срок хранения и периодичность проверок по своим RPO/RTO и требованиям к данным, а не по универсальному правилу 7 или 30 дней.

ПОРЯДОК ВОССТАНОВЛЕНИЯ

Восстанавливайте систему в контролируемой последовательности

1 · ПодготовкаПодготовьте совместимые сервер, базу данных и окружение контейнеров или среду выполнения.
2 · Восстановление секретовБезопасно настройте исходный ключ шифрования n8n и необходимые секреты развёртывания.
3 · Восстановление базыВосстановите PostgreSQL или SQLite и проверьте, что n8n подключается к нужным данным.
4 · Восстановление файловВосстановите постоянные каталоги, бинарные данные и подключённые ресурсы процессов.
5 · Запуск n8nЗапустите приложение с нужным доменным именем, базой и настройками окружения.
6 · ПроверкаУбедитесь, что пользователи, процессы и учётные данные загружаются, затем выполните типичные процессы и проверьте маршруты вебхуков.

Пример аварийного восстановления PostgreSQL: на отдельном чистом целевом сервере с уже созданной правильной ролью базы и пустой базой n8n запустите только PostgreSQL. Перед импортом дождитесь его готовности: docker compose up -d сама по себе может завершиться, пока PostgreSQL ещё инициализируется, поэтому следующая команда pg_restore может завершиться ошибкой. Пример использует --wait в современной версии Compose и отдельно проверяет pg_isready. Для надёжного ожидания настройте соответствующий healthcheck PostgreSQL либо явно подтвердите готовность до следующего шага. Не направляйте эту команду на заполненную рабочую базу и не запускайте n8n до восстановления базы и соответствующих ей ключа и данных .n8n .

# ВОССТАНАВЛИВАЙТЕ ТОЛЬКО В НОВУЮ ПУСТУЮ БАЗУ
# Укажите свои сервис Postgres в Compose, базу и пользователя
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

На целевом сервере должны быть совместимая версия PostgreSQL, права роли, расширения и исходная конфигурация n8n. Восстановите .n8n в нужный постоянный том или bind mount своим механизмом резервного копирования, сохраняя владельцев и права доступа. Восстановите внешние бинарные файлы, пользовательские расширения, Compose и секреты, затем запустите совместимую версию n8n и проверьте журналы. Восстановление одной базы не возвращает ключ: при использовании PostgreSQL ключ хранится в .n8n/config , если вы явно не настроили N8N_ENCRYPTION_KEY. ПРОВЕРКА ВОССТАНОВЛЕНИЯ

Копия считается проверенной только после успешного восстановления

Проверяйте в чистом окружении

Полноценная проверка должна показать, что копия позволяет восстановить экземпляр без зависимости от неучтённых файлов, оставшихся на рабочем сервере.

Проверьте учётные данные

Открыть рабочий процесс недостаточно. Убедитесь, что восстановленные зашифрованные учётные данные действительно расшифровываются и позволяют пройти аутентификацию.

Выполните типичные процессы

Проверьте процессы с вебхуками, внешними API, подключёнными файлами и узлами сообщества, а не только простейшую автоматизацию.

Измерьте время восстановления

Запишите длительность восстановления и оставшиеся ручные шаги. Так предполагаемая возможность восстановиться превращается в рабочую процедуру.

Проведённая проверка восстановления: SQLite и PostgreSQL

Тестовое окружение: n8n 2.42.5 в изолированных Docker-контейнерах на одноразовом раннере GitHub Actions с искусственным процессом из двух узлов. Проверки выполнены 8 октября 2026, а не на клиентском или рабочем сервере n8n.

SQLite: ПРОЙДЕНОТестовый процесс импортировали и экспортировали, остановили все процессы записи, заархивировали постоянную папку с SQLite .n8n и её сгенерированный ключ шифрования, восстановили в чистый том, запустили n8n, затем повторно экспортировали и выполнили восстановленный процесс.
PostgreSQL: ПРОЙДЕНОТот же тестовый процесс импортировали, создали и проверили дамп в формате custom через pg_dump, восстановили его с помощью pg_restore в новую пустую базу PostgreSQL, восстановили отдельную папку .n8n , затем повторно экспортировали и выполнили восстановленный процесс.
Что подтверждает успешная проверкаПроверенные способы копирования сохранили этот процесс, два его узла и связи между ними и позволили выполнить его после восстановления. Это воспроизводимые базовые функциональные проверки, а не тесты производительности под нагрузкой.
Что не проверялосьРасшифровка и аутентификация реальных учётных данных, рабочие вебхуки, воркеры режима очереди и Redis, бинарное хранилище S3/Azure, пользовательские узлы, доступ пользователей и проектов и восстановление действующего рабочего экземпляра. Проведите отдельную проверку каждой зависимости, которую используете.

Как повторить: используйте одноразовую установку n8n, создайте безвредный процесс из двух узлов, сохраните подходящим способом базу и постоянную папку, восстановите их в чистый том или базу, затем проверьте узлы, связи и фактическое выполнение восстановленного процесса. На рабочей системе также проверьте зашифрованные учётные данные, вебхуки и внешние файлы, прежде чем считать аварийное восстановление подтверждённым.

Критерии успешной проверки восстановления: используйте изолированный домен и окружение; убедитесь, что пользователи и процессы на месте, существующие зашифрованные учётные данные проходят аутентификацию без повторного ввода, рабочий вебхук вызывает нужный восстановленный процесс, подключённые файлы и бинарные вложения читаются, а интеграции с необходимыми узлами сообщества загружаются. Проверьте возраст копии, измеренный простой и доступность вне сервера. Если важная проверка не пройдена, отметьте эту точку восстановления как непроверенную вместо отчёта о полном резервном копировании.

ОГРАНИЧЕНИЯ КОПИРОВАНИЯ ЧЕРЕЗ CLI

Разберитесь, что именно не восстанавливает экспорт процессов и учётных данных

Экспорт CLI — не полная копия экземпляра

Резервный экспорт процессов и учётных данных не включает пользователей и роли, историю и журналы выполнений, переменные и настройки экземпляра, например ключ шифрования.

Для восстановления на новом экземпляре нужен владелец

На чистом экземпляре завершите настройку владельца до импорта учётных данных. При восстановлении нескольких пользователей или проектов также может потребоваться правильное назначение пользователя или проекта.

Импортируемые ID могут перезаписать существующие объекты

Экспорт процессов и учётных данных сохраняет исходные ID. Импорт в экземпляр, где уже есть такие ID, может заменить существующие объекты.

Публикуйте импортированные процессы осознанно

При импорте через CLI процессы обычно остаются неактивными. В n8n 2.x проверьте статус публикации каждого импортированного процесса и публикуйте только те, которые собираетесь запускать; серверный CLI самостоятельного размещения также поддерживает n8n publish:workflow --id=YOUR_WORKFLOW_ID. Если n8n работает, изменения публикации и снятия с публикации через Server CLI вступают в силу только после перезапуска n8n. Перезапустите экземпляр до проверки триггеров по расписанию, рабочих вебхуков и переключения трафика.

Пример массового экспорта для Docker Compose: если сервис n8n называется n8n, можно выполнить официальные команды копирования CLI ниже. Каталог вывода намеренно расположен внутри подключённого постоянного каталога .n8n , поскольку произвольные каталоги внутри контейнера могут исчезнуть при его пересоздании. Убедитесь, что пользователь контейнера n8n может записывать в этот каталог. Храните JSON процессов и учётных данных в разных каталогах— документация n8n описывает проблему импорта, когда оба типа находятся в одной папке.

Копирование черновиков и опубликованных версий в n8n 2.x: обычный экспорт процессов командой --backup сохраняет текущие черновики, которые могут отличаться от опубликованных рабочих версий. Чтобы сохранить фактически опубликованную версию определённого процесса, экспортируйте её отдельно с помощью docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, предварительно убедившись, что каталог вывода существует и доступен для записи. CLI также позволяет экспортировать историческую версию с помощью --version=VERSION_ID. Храните эти версии вне сервера вместе с полной копией; не считайте, что JSON черновика отражает текущее опубликованное состояние.

# Выполняйте из проекта Docker Compose; сервис n8n должен существовать
# Храните копии процессов и учётных данных в РАЗНЫХ папках
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Скопируйте каталоги экспорта ИЗ контейнера на хост
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Скопированный каталог ~/n8n-recovery/cli остаётся на VPS, пока вы не перенесёте его в защищённое независимое хранилище. Учётные данные по умолчанию экспортируются в зашифрованном виде, а при импорте нужен соответствующий ключ. Не используйте --decrypted, кроме строго контролируемого переноса: этот параметр записывает секреты открытым текстом. Не добавляйте экспорты с конфиденциальной логикой процессов или учётными данными в публичный репозиторий GitHub. Некоторые сторонние шаблоны копирования учётных данных в GitHub намеренно экспортируют расшифрованные секреты; приватный репозиторий ограничивает доступ, но не обеспечивает шифрование. Проверяйте фактические настройки экспорта и права хранилища каждого шаблона, шифруйте секреты перед передачей вне сервера и заменяйте учётные данные, раскрытые при непреднамеренной загрузке открытым текстом.

Пример массового импорта: на чистом целевом экземпляре завершите настройку владельца, задайте исходный ключ шифрования и убедитесь, что сохранённые файлы копии доступны на VPS восстановления. Следующие команды создают целевую папку и копируют подкаталоги workflows/ и credentials/ с хоста в контейнер n8n; адаптируйте пути, если схема томов Docker отличается:

# Запускайте только на нужном ЧИСТОМ экземпляре восстановления
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Проверьте владельцев файлов и права пользователя контейнера n8n. Не импортируйте данные поверх заполненного рабочего экземпляра без проверенного отката: ID процессов и учётных данных могут перезаписать существующие записи. Затем выполните:

# После настройки владельца нового экземпляра И задания правильного ключа
# Верните содержимое cli/ в .n8n/backups/ целевого сервиса n8n
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Импортируемые ID могут заменить существующие процессы или учётные данные; для пробного запуска используйте изолированный тестовый экземпляр, а затем проверьте учётные данные и состояние активации и публикации. В n8n 2.x восстановление JSON черновика само по себе не подтверждает, что процесс опубликован и способен запускать триггеры по расписанию. Безопасность импорта: в экземпляре n8n без нескольких основных процессов ранее активные cron-триггеры могут продолжить работу после импорта CLI до перезапуска. Остановите или изолируйте рабочие триггеры и перезапустите n8n перед включением восстановленных заданий; убедитесь, что нет повторных выполнений. Экспорты CLI не содержат исходных пользователей, журналов выполнений, переменных экземпляра или ключа шифрования. --backup задаёт --all --pretty --separate, а не «весь экземпляр». Источники: текущее официальное руководство n8n по резервному копированию и восстановлению и справочник команд CLI n8n.

Массовое восстановление через шаблоны GitHub или Google Drive: это вариант только для JSON процессов, а не для базы экземпляра, пользователей, зашифрованных значений учётных данных или ключа шифрования. Перед запуском шаблона через API проверьте его права в API n8n и хранилище, выбранную версию копии и целевой экземпляр, обновляет ли он совпадающие ID и пересоздаёт ли удалённые процессы, а также как работает с публикацией. Не все шаблоны восстанавливают ID, отсутствующий на целевом экземпляре; проверьте это в изоляции, прежде чем полагаться на автоматическое восстановление.

Вопросы и ответы

Резервное копирование и восстановление n8n: частые вопросы

Достаточно ли экспорта процессов для резервного копирования n8n?

Нет. Экспорты процессов полезны как логические копии, но полное восстановление также может требовать учётных данных, соответствующего ключа шифрования, состояния базы, постоянных файлов и хранилища бинарных данных.

Нужен ли ключ шифрования n8n, если у меня есть база данных?

Да, если нужно сохранить возможность использовать зашифрованные учётные данные из этой базы. Надёжно сохраните исходный ключ.

Копировать PostgreSQL или экспортировать процессы и учётные данные?

Для аварийного восстановления сохраняйте базу и ключ шифрования. Логические экспорты полезны как дополнительный уровень переноса и выборочного восстановления, но не заменяют все компоненты экземпляра.

Может ли снимок VPS быть единственной резервной копией?

Лучше считать его одним из уровней восстановления. Храните независимую копию вне сервера, чтобы сбой провайдера, аккаунта, сервера или снимка не уничтожил сразу все точки восстановления.

Как узнать, что резервная копия работает?

Восстановите её в чистом тестовом окружении, проверьте расшифровку учётных данных и выполните типичные процессы. Успешное задание копирования само по себе не доказывает возможность восстановления.

Включают ли копии процессов в GitHub или Google Drive сохранённые секреты учётных данных?

JSON-копии только рабочих процессов не включают секретные значения из хранилища учётных данных n8n и ключ шифрования экземпляра. Однако экспортированный JSON может раскрывать имена и ID учётных данных, а также секреты, введённые прямо в параметры узлов, например заголовки аутентификации. Проверяйте и защищайте JSON перед загрузкой или передачей. Для полного восстановления сохраняйте базу и исходный ключ либо используйте поддерживаемый зашифрованный экспорт учётных данных через CLI с проверенным восстановлением. Шаблон GitHub или Google Drive только для процессов не обеспечивает полного аварийного восстановления.

ЦЕЛИ ВОССТАНОВЛЕНИЯ

Определите RPO и RTO до инцидента

RPO — максимально допустимая потеря последних изменений. Считайте её от самой свежей пригодной точки восстановления в независимом хранилище: задание раз в шесть часов не обеспечивает шестичасовой RPO, если экспорт или передача завершились ошибкой. RTO — максимально допустимый простой. Измеряйте его при восстановлении в чистом окружении, включая получение секретов, восстановление внешних файлов, повторную проверку учётных данных и публикацию восстановленных процессов, а не только запуск контейнера.

КЛЮЧ ДЛЯ ВОССТАНОВЛЕНИЯ

Найдите исходный ключ шифрования до повторного развёртывания

Если в рабочем окружении задан N8N_ENCRYPTION_KEY, сохраните именно этот секрет окружения. Если нет — сохраните сгенерированный ключ из исходного постоянного файла .n8n/config. До импорта зашифрованных учётных данных проверьте, откуда восстановленный экземпляр фактически берёт ключ: новый сгенерированный ключ не расшифрует учётные данные старой базы.
