DOCKER-INSTALLATION

n8n auf einem VPS installieren

Installiere n8n auf einem VPS mit Docker Compose und PostgreSQL. Eine Produktionsbereitstellung benötigt außerdem persistente Anwendungs- und Datenbankdaten, eine stabile N8N_ENCRYPTION_KEY, einen öffentlichen Hostnamen, HTTPS und eine korrekte Webhook-Konfiguration. Prüfe diese Komponenten, bevor Produktions-Workflows aktiviert werden.

Installation auf einem VPS, der bereits Websites hostet? Du kannst n8n zu einem Server hinzufügen, den du kontrollierst, sofern CPU, RAM und Speicher ausreichen. Wenn Nginx, Apache, Caddy oder ein anderer Reverse Proxy bereits die Ports 80/443 belegt, nicht starte den unten gezeigten Caddy-Container nicht unverändert, da die Ports kollidieren. Route stattdessen eine neue n8n-Subdomain über deinen vorhandenen Reverse Proxy mit geeignetem privaten Netzwerk oder nutze für das exakte Compose-Beispiel einen sauberen VPS. Erhalte die anderen Websites und deren TLS-Konfiguration; das Beispiel setzt freie Ports 80/443 voraus.

INSTALLATION ZUM KOPIEREN UND ANPASSEN

n8n mit Docker Compose auf deinem VPS installieren

Nutze dieses Beispiel für eine n8n-Bereitstellung auf einem selbstverwalteten Linux-VPS. Du installierst und wartest n8n selbst; die Serverauswahl über unseren Partner enthält keine vorinstallierte n8n-Instanz. Das Beispiel kombiniert n8n, PostgreSQL, einen externen Task Runner und Caddy HTTPS in einem privaten Compose-Netzwerk. Es ist eine Konfigurationsvorlage, keine Aussage über eine live getestete Bereitstellung.

Möchtest du stattdessen die schnellste Neuinstallation? n8n bietet außerdem ein offizielles Einzeilen-Docker-Setup. Du kannst das Skript herunterladen und mit curl -fsSL https://get.n8n.io -o get-n8n.sh vor der Ausführung prüfen sh get-n8n.sh. Diese Option startet eine erste Instanz mit SQLite unter einer lokalen URL und enthält n8n-Assistant-Sandbox-Dienste; sie ist nicht dasselbe wie diese VPS-Bereitstellung mit öffentlichem HTTPS und PostgreSQL. Der vollständige offizielle Sandbox-Stack benötigt mehr RAM und CPU als eine schlanke n8n-Installation (die Compose-Anleitung nennt mindestens 4 GB RAM / 2 vCPUs). Für einen öffentlich erreichbaren Produktions-VPS fahre mit dem manuell konfigurierten Stack unten fort.

1. Docker, DNS und Zugriff vorbereiten

Verbinde dich per SSH mit sudo-Zugriff und richte einen DNS-A-Record für n8n.example.com auf die IPv4-Adresse deines VPS. Auf einem frischen Ubuntu 22.04, 24.04 oder 26.04 VPS installieren die folgenden Befehle Docker Engine und das moderne docker compose Plugin aus dem offiziell signierten apt Docker-Repository:

# Frische offizielle Ubuntu-22.04-/24.04-/26.04-Installation
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Signiertes apt-Repository von Docker registrieren
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

Das ist die produktionsorientierte Repository-Methode aus der offiziellen Docker-Ubuntu-Installationsanleitung. Installiere oder entferne Docker nicht blind auf einem VPS, auf dem bereits Container oder andere Websites laufen; prüfe zuerst die bestehende Installation und mögliche Paketkonflikte. Für Debian oder andere Distributionen nutze die entsprechenden offiziellen betriebssystemspezifischen Anweisungen statt Ubuntu-Befehlen.

Prüfe jetzt Docker selbst, das Compose-Plugin, DNS und das Arbeitsverzeichnis:

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

Wenn getent hosts keine oder eine falsche Adresse zurückgibt, korrigiere DNS vor dem Start von Caddy; ersetze n8n.example.com im gesamten Leitfaden durch deinen echten Hostnamen. Docker benötigt normalerweise Root-Rechte: Wenn dein SSH-Nutzer die späteren docker compose Befehle nicht direkt ausführen kann, stelle sudovoran. Einen Nutzer zur Gruppe docker hinzuzufügen gewährt Root-äquivalenten Zugriff und sollte auf einem gemeinsam genutzten Server nicht leichtfertig erfolgen.

Halte deinen tatsächlichen SSH-Administrationsport erreichbar, bevor eine Firewall aktiviert wird. Erlaube eingehendes HTTP (80) und HTTPS (443) für Zertifikatsausstellung und Editor. Von Docker veröffentlichte Containerports können einige UFW-Regeln umgehen; prüfe daher die Docker-Firewall-Hinweise und veröffentliche nur die vorgesehenen Caddy-Ports. Dieses Compose-Beispiel veröffentlicht bewusst nicht PostgreSQL (5432), n8n (5678) oder den Task-Runner-Broker (5679) nicht im öffentlichen Internet.

2. Umgebungswerte erstellen und Schlüssel sichern

Erzeuge im Projektverzeichnis drei unterschiedliche zufällige Hexadezimalwerte mit:

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

Erstelle eine Datei namens .env mit der Vorlage unten, ersetze jeden REPLACE_WITH_RANDOM_HEX durch einen anderen erzeugten Wert und ändere Hostname sowie Zeitzone. Der gezeigte 2.42.5 Tag entspricht dem stabilen Release vom 8. Oktober 2026, hier als datiertes Konfigurationsbeispiel verwendet, nicht als Garantie einer live getesteten Bereitstellung oder zukünftiger Sicherheit. Prüfe vor der Installation die aktuellen offiziellen n8n-Releases und halte n8n sowie das Task-Runner-Image auf derselben verifizierten Version.

# .env — die drei Beispiel-Secrets ersetzen
# Eine gepflegte n8n-Version fixieren; n8n und Runner auf gleicher Version halten.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

Committe niemals .env in ein öffentliches Repository. Bewahre Verschlüsselungsschlüssel und Wiederherstellungsanweisungen sicher außerhalb des VPS auf. Der Schlüssel muss nach Container-Neuerstellung oder Migration identisch bleiben.

3. compose.yaml für eine Neuinstallation erstellen

Erstelle im selben Verzeichnis compose.yamlDas Beispiel verwendet die offiziellen n8n-Konventionen für Umgebungsvariablen und den PostgreSQL-18- PGDATA Pfad aus dem n8n-Hosting-Projekt:

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

Die vier Dienste haben getrennte Aufgaben: PostgreSQL speichert den Datenbankzustand, n8n führt Workflows aus, n8n-runner führt Runner-Aufgaben mit passender Version und gemeinsamem Authentifizierungstoken aus, und Caddy übernimmt öffentliches HTTPS. Ein externer Task Runner ist nicht der Redis-Queue-Modus. Nur Caddy veröffentlicht Hostports. Dieses schlanke Beispiel nutzt eine einzige Datenbankrolle; für stärkere Trennung der PostgreSQL-Rechte siehe das offizielle n8n-PostgreSQL-Bereitstellungsbeispiel.

4. HTTPS-Caddyfile erstellen

Erstelle die Datei Caddyfile (großes C, keine Erweiterung) neben compose.yaml. Ersetze den Beispiel-Hostnamen überall durch deinen eigenen DNS-Namen:

n8n.example.com {
    reverse_proxy n8n:5678
}

Caddy fordert öffentliche TLS-Zertifikate an und erneuert sie, wenn die Domain korrekt aufgelöst wird und externer Traffic die Ports 80/443 erreicht. Richte DNS nicht auf localhost. Wenn Caddy durch einen anderen Reverse Proxy ersetzt wird, leite ursprünglichen Host, Protokoll und Client-Adress-Header weiter und passe N8N_PROXY_HOPS an die tatsächliche Zahl vertrauenswürdiger Proxy-Hops an.

5. Container starten und von außen testen

Führe diese Befehle im Projektverzeichnis aus, nachdem .env, compose.yaml und Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

gespeichert wurden. Der letzte Befehl prüft den öffentlichen HTTPS- Health-Endpoint. Wenn die Zertifikatsausstellung noch aussteht, prüfe Caddy-Logs sowie DNS/Ports, bevor n8n als defekt gilt. Öffne https://n8n.example.com, erstelle sofort das erste Owner-Konto und aktiviere geeigneten Anmeldeschutz. Bestätige, dass die Instanz tatsächlich einen Workflow ausführt und nicht nur der Editor lädt:

  1. Erstelle im Editor einen Workflow mit einem Webhook -Trigger. Setze HTTP Method auf GET, wähle Path vps-check, und setze Respond auf Immediately. Speichere den Workflow.
  2. Klicke auf Listen for Test Eventkopiere die vollständige Test URL von n8n angezeigte URL und führe auf einem anderen Gerät curl -i 'PASTE_TEST_URL_HERE' mit der kopierten URL aus. Erwarte eine erfolgreiche HTTP-Antwort und das eingehende Ereignis im n8n-Editor. Test-URLs funktionieren nur, solange n8n auf das Ereignis wartet.
  3. Veröffentliche den Workflow, wechsle den Node auf seine Production URL, kopiere sie und führe curl -i 'PASTE_PRODUCTION_URL_HERE' erneut aus. Bestätige die Ausführung unter dem Tab Executions des Workflows. Produktions-Webhook-Anfragen benötigen einen veröffentlichten Workflow und zeigen ihren Payload nicht in der Testansicht des Editors.

Dies ist absichtlich ein einfacher, nicht authentifizierter Smoke-Test: Sende niemals Secrets dorthin. Nimm ihn nach dem Test aus der Veröffentlichung oder lösche ihn, beziehungsweise konfiguriere Webhook-Authentifizierung/IP-Beschränkungen, bevor ein öffentlicher Endpoint echte Daten verarbeitet. Siehe offizielle Webhook-Test-/Produktionsdokumentation.

6. Vor Änderungen fixierter Versionen sichern

Speichere einen wiederherstellbaren PostgreSQL-Dump und das persistente n8n-Daten-Volume, .env/Verschlüsselungsschlüssel und benötigte externe Dateien in Speicher außerhalb dieses Servers. Verifiziere einen Restore mit dem Backup- und Wiederherstellungsleitfaden vor einem Produktionsupdate. Beispielbefehle:

# Datenbank, Verschlüsselungsschlüssel und Instanzdaten sichern,
# sowie Dateien vor Änderungen der fixierten Versionen.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# Nachdem das Backup außerhalb dieses VPS gesichert wurde:
docker compose pull
docker compose up -d
docker compose ps

Ändere die fixierte N8N_VERSION erst nach dem Lesen der Release Notes; n8n- und Runner-Images müssen gemeinsam aktualisiert werden. Führe docker compose down -v bei Routinewartung nicht aus, da dies benannte Daten-Volumes löscht. Änderungen der PostgreSQL-Hauptversion benötigen ein Datenbankupgrade oder einen Dump/Restore-Plan; das Ersetzen des Postgres-18-Images durch einen anderen Major-Tag ist keine automatische Migration.

PERSISTENZ

n8n und PostgreSQL getrennt persistent halten

n8n-Daten

Mounte persistenten Speicher für das n8n-Datenverzeichnis, damit kritischer Instanzzustand eine Container-Neuerstellung übersteht.

PostgreSQL-Daten

Halte das Datenbankverzeichnis unabhängig vom PostgreSQL-Container persistent.

Dateiberechtigungen

Mache gemountete Pfade für den vorgesehenen Container-Nutzer beschreibbar, ohne dem Hostspeicher unnötig breite Rechte zu geben.

Workflow-Dateien

Halte gemountete Dateien oder Binärdatenspeicher persistent, von denen Produktions-Workflows abhängen.

Warum eine n8n-Docker-Installation lokal funktioniert, aber in Produktion scheitert

Falsche Webhook-URL

Callbacks zeigen auf localhost, HTTP oder einen internen Hostnamen statt auf den öffentlichen HTTPS-Origin.

Fehlende Persistenz

Anwendungs- oder Datenbankzustand verschwindet bei einer Container-Neuerstellung.

Verlorener Verschlüsselungsschlüssel

PRÜFUNG NACH DER BEREITSTELLUNG

Zustand prüfen, bevor reale Workflows verbunden werden

Containerstatus prüfen

Führe docker compose ps aus und bestätige, dass Anwendungs- und Datenbankdienste erwartungsgemäß laufen, bevor die Bereitstellung als fehlerfrei gilt.

n8n-Health-Endpoint prüfen

Im obigen Compose-Beispiel wird Port 5678 nicht auf dem Host veröffentlicht. Prüfe den öffentlichen Endpoint mit curl -fsS https://n8n.example.com/healthz nach Anpassung des Hostnamens und nutze docker compose ps sowie Servicelogs, falls HTTPS oder Datenbank nicht bereit sind.

Anwendungsversionen fixieren

FAQ

n8n mit Docker installieren: häufige Fragen

Braucht n8n PostgreSQL bei Docker?

Docker erfordert kein PostgreSQL, und kleine Bereitstellungen können SQLite nutzen. Für einen produktionsorientierten VPS bietet PostgreSQL eine robustere Datenbankbasis und unterstützt spätere Skalierung im Queue-Modus.

Warum ein persistentes n8n-Volume behalten, wenn PostgreSQL Daten speichert?

Das persistente n8n-Verzeichnis kann wichtigen Instanzzustand und Konfiguration enthalten. Sichere es entsprechend dem Bereitstellungsdesign, statt die Datenbank als einziges Wiederherstellungsobjekt anzunehmen.

Warum zeigt mein Webhook localhost?

Die interne Containeradresse unterscheidet sich vom öffentlichen Origin. Konfiguriere externen Hostnamen, Protokoll und Webhook-URL und stelle sicher, dass der Reverse Proxy die benötigten Header weiterleitet.

Sollte Port 5678 öffentlich sein?

Bei einer normalen Produktionsbereitstellung hinter einem Reverse Proxy veröffentliche HTTPS am Proxy und halte den n8n-Anwendungsport intern, sofern kein konkreter betrieblicher Grund dagegen spricht.

Brauche ich Redis?

Nicht bei einer Standard-Docker-Bereitstellung mit einer Instanz. Redis wird relevant, wenn bewusst auf Queue-Modus und Worker umgestellt wird.

Sind externe n8n-Task-Runner dasselbe wie Queue-Modus-Worker?

Nein. Externe Task Runner führen unterstützten Task-Code getrennt vom n8n-Main-Prozess aus und nutzen ein gemeinsames Authentifizierungstoken. Der Redis-Queue-Modus verteilt Workflow-Ausführungen und hat eigene Infrastrukturanforderungen. Dieses Beispiel zeigt einen externen Task Runner, nicht den Redis-Queue-Modus. Gleiche die Runner-Image-Version an die n8n-Version an.
