ИНСТАЛИРАНЕ С DOCKER

Инсталиране на n8n на VPS

Инсталирайте n8n на VPS с Docker Compose и PostgreSQL. За продукционна инсталация са необходими и постоянно съхранение на данните на приложението и базата данни, постоянен N8N_ENCRYPTION_KEY, публично име на хост, HTTPS и правилна конфигурация на уебхуковете. Проверете тези компоненти, преди да активирате работни процеси в продукционна среда.

ПРЕДВАРИТЕЛНИ ИЗИСКВАНИЯ

Подгответе VPS, преди да стартирате n8n

Linux VPS

Използвайте поддържан Linux сървър с достатъчно ресурси за n8n, PostgreSQL, Docker и обратния прокси.

DNS

Насочете домейн или поддомейн към VPS, преди да издавате TLS сертификати и да публикувате URL адреси за уебхукове.

Docker Compose

Инсталирайте Docker Engine и плъгина Compose с поддържани пакети за операционната система.

Защитна стена

Отворете само необходимите портове за администрация и уеб трафик. Оставете PostgreSQL и вътрешните услуги на приложението недостъпни отвън.

Инсталирате на VPS, който вече хоства уебсайтове? Можете да добавите n8n към сървър, който управлявате, ако CPU, RAM и дисковото пространство са достатъчни. Ако обаче Nginx, Apache, Caddy или друг обратен прокси вече използва портове 80/443, не стартирайте показания по-долу контейнер Caddy без промени: портовете ще влязат в конфликт. Вместо това насочете нов поддомейн за n8n през съществуващия обратен прокси с подходяща частна мрежа или използвайте чист VPS за точния Compose пример. Запазете останалите сайтове и тяхната TLS конфигурация; примерът предполага, че портове 80/443 са свободни.

ИНСТАЛИРАНЕ ПО ПРИМЕР С АДАПТИРАНЕ

Инсталирайте n8n на своя VPS с Docker Compose

Използвайте този пример, за да изградите инсталация на n8n върху самостоятелно управляван Linux VPS. Вие сами инсталирате и поддържате n8n; изборът на сървър чрез нашия партньор не включва предварително инсталирана инстанция на n8n. Примерът комбинира n8n, PostgreSQL, външен изпълнител на задачи и Caddy HTTPS в частна Compose мрежа. Това е примерна конфигурация, а не твърдение за инсталация, тествана в реална среда.

Искате най-бързия начин за нова инсталация? n8n предлага и официална настройка на Docker с една команда. Можете да изтеглите и прегледате скрипта чрез curl -fsSL https://get.n8n.io -o get-n8n.sh , преди да изпълните sh get-n8n.sh. Този вариант стартира начална инстанция със SQLite на локален URL и включва sandbox услуги за n8n Assistant; той не е същият като описаната тук VPS конфигурация с публичен HTTPS и PostgreSQL. Официалният пълен sandbox набор изисква повече RAM и CPU от олекотена инсталация на n8n (ръководството му за Compose посочва поне 4 GB RAM / 2 vCPUs). За продукционен VPS с публичен достъп продължете с ръчно конфигурирания набор по-долу.

1. Подгответе Docker, DNS и достъпа

Свържете се чрез SSH с права за sudo и насочете DNS A запис за n8n.example.com към IPv4 адреса на вашия VPS. На нов VPS с Ubuntu 22.04, 24.04 или 26.04 следните команди инсталират Docker Engine и съвременния плъгин docker compose от официалното подписано хранилище на Docker за apt :

# Fresh official Ubuntu 22.04 / 24.04 / 26.04 installation
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Register Docker's signed apt repository
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

Това е методът с официално хранилище, предназначен за продукционна употреба, от ръководството на Docker за Ubuntu. Не преинсталирайте и не премахвайте Docker без проверка на VPS, на който вече работят контейнери или други уебсайтове; първо прегледайте съществуващата инсталация и възможните конфликти на пакети. За Debian или друга дистрибуция използвайте съответните официални инструкции за ОС вместо команди за Ubuntu.

Сега проверете Docker, плъгина Compose, DNS и работната директория:

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

Ако getent hosts не връща адрес или връща грешен адрес, коригирайте DNS, преди да стартирате Caddy; заменете n8n.example.com навсякъде в това ръководство с реалното име на вашия хост. Docker обикновено изисква права на root: ако вашият SSH потребител не може директно да изпълнява следващите команди docker compose , поставете пред тях sudo. Добавянето на потребител към групата docker предоставя достъп, еквивалентен на root, и не бива да се прави без преценка на споделен сървър.

Преди да включите защитна стена, запазете достъпа до действителния SSH порт за администрация. Разрешете входящ HTTP (80) и HTTPS (443) за издаването на сертификати и редактора. Публикуваните от Docker портове на контейнери могат да заобикалят някои правила на UFW, затова прегледайте указанията на Docker за защитната стена и публикувайте само предвидените портове на Caddy. Този Compose пример умишлено не публикува PostgreSQL (5432), n8n (5678) или брокера на изпълнителя на задачи (5679) в публичния интернет.

2. Създайте стойности на средата и запазете ключа

От директорията на проекта генерирайте три различни случайни шестнадесетични стойности с:

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

Създайте файл с име .env по шаблона по-долу, заменете всяко REPLACE_WITH_RANDOM_HEX с различна генерирана стойност и променете името на хоста и часовата зона. Показаният 2.42.5 таг е стабилната версия, посочена на 8 октомври 2026 г., използвана тук като примерна конфигурация с конкретна дата, а не гаранция за инсталация, тествана в реална среда, или за бъдеща сигурност. Преди инсталиране проверете текущите официални версии на n8n и след това използвайте една и съща проверена версия за образите на n8n и изпълнителя на задачи.

# .env — replace the three example secrets
# Pin a maintained n8n release; keep n8n and runner equal.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

Никога не записвайте .env в публично хранилище за код. Съхранявайте ключа за шифроване и инструкциите за възстановяване сигурно извън VPS. Ключът трябва да остане същият след пресъздаване на контейнера или миграция.

3. Създайте compose.yaml за нова инсталация

В същата директория създайте compose.yaml. Примерът използва официалните правила за променливи на средата на n8n и пътя PGDATA за PostgreSQL 18, документиран от проекта за хостинг на n8n:

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

Четирите услуги имат отделни роли: PostgreSQL съхранява базата данни, n8n изпълнява работните процеси, n8n-runner изпълнява задачите чрез същата версия и споделен токен за удостоверяване, а Caddy обслужва публичния HTTPS. Външният изпълнител на задачи не е режимът с опашка на Redis. Само Caddy публикува портове на хоста. Този олекотен пример използва една роля на базата данни за настройката; за по-строго разделяне на правата в PostgreSQL вижте официалния пример за внедряване на n8n с PostgreSQL.

4. Създайте Caddyfile за HTTPS

Създайте файл Caddyfile (с главна буква C, без разширение) до compose.yaml. Заменете примерното име на хоста навсякъде с реалния си DNS адрес:

n8n.example.com {
    reverse_proxy n8n:5678
}

Caddy заявява и подновява публични TLS сертификати, когато домейнът се разрешава правилно и външният трафик достига портове 80/443. Не насочвайте DNS към localhost. Ако замените Caddy с друг обратен прокси, препращайте оригиналните хедъри за хост, протокол и адрес на клиента и настройте N8N_PROXY_HOPS според действителния брой доверени прокси междинни стъпки.

5. Стартирайте контейнерите и тествайте отвън

Изпълнете тези команди от директорията на проекта след записване на .env, compose.yaml и Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

Последната команда проверява крайния адрес за състоянието през публичен HTTPS . Ако издаването на сертификата още не е приключило, проверете логовете на Caddy и DNS/портовете, преди да решите, че n8n е повреден. Отворете https://n8n.example.com, създайте незабавно първия акаунт на собственик и включете подходящи защити при вход. Потвърдете, че инстанцията действително изпълнява работен процес, а не само зарежда редактора:

  1. В редактора създайте работен процес със задействане Webhook . Задайте HTTP Method на GET, изберете Path vps-checkи задайте Respond на Immediately. Запазете работния процес.
  2. Натиснете Listen for Test Event, копирайте пълния Test URL URL, показан от n8n, и от друго устройство изпълнете curl -i 'PASTE_TEST_URL_HERE' с копирания адрес. Очаквайте успешен HTTP отговор и входящото събитие да се появи в редактора на n8n. Тестовите URL адреси работят само докато n8n изчаква събитието.
  3. Публикувайте работния процес, преминете към неговия Production URL, копирайте го и изпълнете отново curl -i 'PASTE_PRODUCTION_URL_HERE' . Потвърдете изпълнението в раздела Executions на работния процес. Заявките към продукционните уебхукове изискват процесът да е публикуван и не показват данните си в тестовия изглед на редактора.

Това умишлено е опростен, незащитен тест: никога не изпращайте тайни към него. Отменете публикуването или изтрийте тестовия процес след проверката, или конфигурирайте удостоверяване на Webhook и ограничения по IP, преди да използвате публичен адрес с реални данни. Вижте официалната документация за тестови и продукционни уебхукове.

6. Направете архив, преди да променяте фиксираните версии

Запазете възстановим архив на PostgreSQL и постоянния том с данните на n8n, .env/ключа за шифроване и необходимите външни файлове в хранилище извън този сървър. Проверете възстановяването чрез ръководството за архивиране и възстановяване , преди да актуализирате продукционната инсталация. Примерни команди:

# Back up the database, encryption key, instance data,
# and files before changing the pinned versions.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# After securing the backup outside this VPS:
docker compose pull
docker compose up -d
docker compose ps

Променяйте фиксираната N8N_VERSION едва след като сте прочели бележките към версията; образите на n8n и изпълнителя на задачи трябва да се обновяват заедно. Не изпълнявайте docker compose down -v при обичайна поддръжка, защото това изтрива именуваните томове с данни. Смяната на основната версия на PostgreSQL изисква план за надграждане или архивиране и възстановяване на базата данни; замяната на образа Postgres 18 с таг на друга основна версия не извършва автоматична миграция.

Авторитетни източници: ръководството на n8n за Docker Compose, конфигурацията на n8n за обратен прокси и уебхукове и официалните бележки за внедряване с PostgreSQL. Не се предполага измерена производителност на инфраструктурата или предварително инсталирана функционалност от конкретен доставчик.

КОНФИГУРАЦИЯ

Настройвайте тайните и публичните URL адреси съзнателно

Ключ за шифроване

Задайте и запазете силен ключ за шифроване на n8n, преди да съхранявате продукционни идентификационни данни. Същият ключ е необходим след възстановяване.

Идентификационни данни за PostgreSQL

Използвайте отделни идентификационни данни за базата и не записвайте пароли в публично хранилище за код.

Публично име на хоста

Конфигурирайте реалното външно име на хост и HTTPS адрес, а не вътрешен адрес на контейнер.

URL адрес на уебхук

Задайте N8N_WEBHOOK_URL на публично достъпния базов HTTPS URL адрес и задайте N8N_PROXY_HOPS=1 когато има един доверен обратен прокси. WEBHOOK_URL е остарял псевдоним в n8n 2.35.0 и следващите версии; не го копирайте от стари ръководства.

ПОСТОЯННО СЪХРАНЕНИЕ

Съхранявайте данните на n8n и PostgreSQL отделно

Данни на n8n

Монтирайте постоянно хранилище за директорията с данни на n8n, така че важното състояние на инстанцията да оцелее след пресъздаване на контейнера.

Данни на PostgreSQL

Съхранявайте директорията на базата данни независимо от контейнера PostgreSQL.

Права за файловете

Осигурете право на запис в монтираните пътища за предвидения потребител на контейнера, без да правите хранилището на хоста ненужно достъпно.

Файлове на работните процеси

Съхранявайте постоянно всички монтирани файлове или бинарни данни, от които зависят продукционните процеси.

POSTGRESQL

Свържете n8n с частната услуга на базата данни

Тип база данниКонфигурирайте n8n за PostgreSQL, вместо неволно да се върнете към SQLite.
ХостИзползвайте името на услугата PostgreSQL в частната Docker мрежа.
Идентификационни данниСъгласувайте предвидената база, потребителя на приложението и паролата.
ГотовностИзчакайте PostgreSQL да стане готов, преди да очаквате успешна инициализация на n8n.
МрежаДостъпът до базата между контейнерите не изисква публичен PostgreSQL порт.

HTTPS И ОБРАТЕН ПРОКСИ

Поставете публичния URL на n8n зад HTTPS

Обратен прокси

Използвайте Nginx, Caddy или Traefik като публична входна точка и препращайте трафика към частната услуга n8n.

TLS

Издайте валиден сертификат за публичното име на хост и пренасочвайте HTTP трафика към HTTPS.

Препратени хедъри

Предавайте информацията за хоста, протокола и клиента, необходима на n8n, и настройте очаквания брой прокси междинни стъпки.

ЧЕСТИ ПРОБЛЕМИ

Защо Docker инсталацията на n8n работи локално, но не и в продукционна среда

Неправилен URL адрес на уебхук

Обратните заявки сочат към localhost, HTTP или вътрешно име на хост вместо към публичния HTTPS адрес.

Липса на постоянно съхранение

Състоянието на приложението или базата данни изчезва при пресъздаване на контейнер.

Изгубен ключ за шифроване

Запазените идентификационни данни стават неизползваеми след преизграждане, защото новата инстанция използва друг ключ.

Публичен порт на базата данни

PostgreSQL е ненужно изложен отвън, въпреки че само n8n трябва да има достъп до него.

ПРОВЕРКИ СЛЕД ВНЕДРЯВАНЕ

Проверете състоянието, преди да свържете реални процеси

Проверете състоянието на контейнерите

Изпълнете docker compose ps и потвърдете, че приложението и базата данни работят според очакванията, преди да приемете инсталацията за изправна.

Проверете крайния адрес за състоянието на n8n

В Compose примера по-горе порт 5678 не е публикуван на хоста. Проверете публичния адрес с curl -fsS https://n8n.example.com/healthz след промяна на името на хоста и използвайте docker compose ps заедно с логовете на услугите, ако HTTPS или базата данни не са готови.

Фиксирайте версиите на приложението

Не приемайте автоматично обновяване на непроверен плаващ таг на образ за стратегия за поддръжка. Записвайте версията на n8n, четете бележките към версиите и архивирайте преди смяна.

Не сменяйте основните версии на PostgreSQL директно върху съществуващите данни

Промяната само на тага на основната версия на Postgres може да направи съществуващата директория с данни несъвместима. Архивирайте и следвайте процедурата за надграждане на базата данни, вместо да приемате, че пресъздаването на контейнера извършва миграцията.

ЧЗВ

Инсталиране на n8n с Docker: често задавани въпроси

Нужен ли е PostgreSQL за n8n при използване на Docker?

Docker не изисква PostgreSQL, а малки инсталации могат да използват SQLite. За VPS инсталация, предназначена за продукционна употреба, PostgreSQL осигурява по-надеждна основа за базата данни и поддържа бъдещо мащабиране с режим с опашка.

Защо е необходим постоянен том за n8n, ако PostgreSQL съхранява данните?

Постоянната директория на n8n може да съдържа важно състояние и конфигурация на инстанцията. Запазвайте я според архитектурата, вместо да приемате, че базата данни е единственият ресурс за възстановяване.

Защо уебхукът ми показва localhost?

Вътрешният адрес на контейнера е различен от публичния адрес. Конфигурирайте външното име на хост, протокола и URL адреса на уебхука и се уверете, че обратният прокси предава необходимите хедъри.

Трябва ли порт 5678 да е публичен?

При обичайна продукционна инсталация зад обратен прокси отворете HTTPS на проксито и оставете порта на приложението n8n вътрешен, освен ако има конкретна оперативна причина за друго.

Нужен ли ми е Redis?

Не за стандартна Docker инсталация с една инстанция. Redis става необходим, когато съзнателно преминете към режим с опашка и работници.

Едно и също ли са външните изпълнители на задачи за n8n и работниците в режим с опашка?

Не. Външните изпълнители на задачи изпълняват поддържан код отделно от основния процес на n8n и използват споделен токен за удостоверяване. Режимът с опашка на Redis разпределя изпълненията на работни процеси и има собствени инфраструктурни изисквания. Този пример показва външен изпълнител на задачи, а не режим с опашка на Redis.
