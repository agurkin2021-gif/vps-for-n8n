DUBLĒŠANA UN ATJAUNOŠANA

n8n rezerves kopijas un atjaunošana

Lai izveidotu un atjaunotu pašu mitināta n8n rezerves kopiju, saglabājiet SQLite datubāzi vai konsekventu PostgreSQL izdruku, pastāvīgo .n8n mapi un sākotnējo šifrēšanas atslēgu, izvietošanas konfigurāciju, kā arī visas ārējās bināro datu un montēto failu atkarības. Šifrētu kopiju glabājiet ārpus VPS un pārbaudiet atjaunošanu atsevišķā instancē. CLI darbplūsmu un piekļuves datu eksports ir paredzēts selektīvai atjaunošanai; tikai JSON eksports nav pilna servera rezerves kopija.

ĪSAIS KONTROLSARAKSTS

Kas jāiekļauj n8n rezerves kopijā

Datubāze

Dublējiet PostgreSQL datubāzi vai instances izmantoto SQLite datubāzes failu. Datubāzē glabājas n8n pamatdati, tostarp darbplūsmas, piekļuves dati un izpilžu dati.

Šifrēšanas atslēga

Atsevišķi un droši saglabājiet precīzu n8n šifrēšanas atslēgu. Atjaunoto šifrēto piekļuves datu izmantošanai vajadzīga tā pati atslēga.

Pastāvīgie faili

Iekļaujiet pastāvīgo n8n datu direktoriju, kā arī visus montētos failus, bināro datu glabātuves un darbplūsmu resursus, no kuriem atkarīga jūsu vide.

Izvietošanas konfigurācija

Saglabājiet Compose/konfigurācijas failus un neslepenos iestatījumus, kas vajadzīgi vides atjaunošanai. Noslēpumus aizsargājiet ar atbilstošu piekļuves kontroli.

DIVI DUBLĒŠANAS LĪMEŅI

Loģiskais eksports vai pilna atjaunošana pēc avārijas

Darbplūsmu un piekļuves datu eksports

n8n CLI eksports noder migrācijai, darbplūsmu versiju kopijām un atsevišķu objektu atjaunošanai. Piekļuves datus var eksportēt šifrētā formā un vēlāk importēt ar atbilstošo šifrēšanas atslēgu. Lai atjaunotu tikai vienu darbplūsmu, redaktorā atveriet trīs punktu izvēlni, lejupielādējiet tās JSON un importējiet to jaunā pārbaudes darbplūsmā vai izolētā instancē, izmantojot faila importu. Pirms dzīvas darbplūsmas aizstāšanas pārbaudiet piekļuves datus, darbplūsmu ID un mezglu parametrus: JSON atjaunošana neatjauno visu serveri.

Entītiju eksports

CLI var eksportēt datubāzes entītijas datu pārvietošanai starp atbalstītajiem datubāzu veidiem. Izpilžu vēstures tabulas nav obligātas, jo tās var būt ļoti apjomīgas.

Pilnas instances atjaunošana

Servera bojāejas gadījumam saglabājiet faktisko datubāzi, šifrēšanas atslēgu, pastāvīgos datus un izvietošanas atkarības. Neuzskatiet, ka darbplūsmas JSON eksports atjaunos visu instanci.

Pakalpojumu sniedzēja momentuzņēmums

VPS momentuzņēmums ir noderīgs kā papildu atjaunošanas slānis, taču tas nedrīkst būt vienīgā kopija vai aizstāt neatkarīgi pārbaudītu lietotnes/datubāzes rezerves kopiju.

DATUBĀZE

Veidojiet konsekventu datubāzes rezerves kopiju

PostgreSQL

Izmantojiet konsekventas PostgreSQL dublēšanas metodi un glabājiet rezultātu ārpus VPS. Datubāzes kopija tajā pašā bojātajā diskā nav aizsardzība avārijas gadījumam.

SQLite

Ja izmantojat SQLite, saglabājiet datubāzes failu no pastāvīgās n8n datu direktorijas. Nekopējiet aktīvi mainītu datubāzi veidā, kas var radīt nekonsekventu kopiju.

Izpilžu vēsture

Izlemiet, vai vēsturiskie izpilžu dati ietilpst jūsu atjaunošanas mērķī. Tie var būtiski palielināt kopiju apjomu, tādēļ jāvadās pēc glabāšanas un atbilstības prasībām.

Datubāzes versija

Pierakstiet sākotnējās vides datubāzes dzinēju un versiju, lai varētu sagatavot savietojamu atjaunošanas vidi.

PostgreSQL Docker Compose VPS vidē. Ja PostgreSQL servisa nosaukums ir postgres un tā datubāzes un lietotāja nosaukums ir n8n, šī komanda izveido konsekventu PostgreSQL pielāgotā formāta izdruku resursdatorā. Pirms izpildes pārbaudiet savu Compose failu un pielāgojiet datubāzes piekļuves datus un servisu nosaukumus. pg_dump var izveidot loģiski konsekventu momentuzņēmumu, kamēr PostgreSQL darbojas, taču tas neveido atsevišķās .n8n lietotāja mapes vai ārējo bināro datu rezerves kopiju.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Arhīva objektu saraksta pārbaude var atklāt acīmredzamas formāta problēmas, bet nepierāda, ka datus iespējams atjaunot. Šifrētu kopiju glabājiet ārpus servera un izmēģiniet atjaunošanu. Datubāzes specifiskās opcijas skatiet oficiālajā PostgreSQL pg_dump dokumentācijā.

SQLite Docker vidē. Noklusējuma SQLite izvietojumā database.sqlite un ģenerētās šifrēšanas atslēgas konfigurācija atrodas pastāvīgajā .n8n mapē (parasti tā ir montēta ceļā /home/node/.n8n). Neuzskatiet parastu aktīvas SQLite datubāzes kopēšanu par konsekventu. Pirms mapes kopēšanas apturiet n8n un citus procesus, kas raksta datubāzē, vai izmantojiet SQLite atbalstīto tiešsaistes dublēšanas mehānismu, ja pārtraukums nav iespējams:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Šīs ir ilustratīvas komandas norādītajam servisam un ceļam, nevis universāla sējumu konfigurācija. Nokopētā mape sākotnēji joprojām atrodas tajā pašā VPS; pārvietojiet un aizsargājiet to ārpus servera. Ja darbojas rindas izpildītāji vai citi rakstītāji, apturiet arī tos un ievērojiet faktiskās izvietošanas arhitektūru. Pašreizējā n8n pilnās dublēšanas rokasgrāmata apraksta SQLite konsekvences prasību.

Noklusējuma SQLite mapes atjaunošana tīrā mērķa vidē: vispirms apturiet n8n servisu un visus procesus, kas raksta datubāzē. Kad ir izveidots savietojams n8n servisa konteiners un mērķa sējums, kopējiet saglabāto .n8n saturu atpakaļ tajā pašā pastāvīgajā direktorijā. Tas pārraksta mērķa failus, tādēļ neveiciet šīs darbības instancē, kuras dati jāsaglabā:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker var kopēt failus arī apturētos konteineros, taču mērķa failu īpašnieks var atšķirties no sākotnējā. Pirms palaišanas nodrošiniet, lai n8n procesam būtu tiesības lasīt un rakstīt atjaunoto konfigurāciju un datubāzi. Ja jūsu Compose konfigurācijā ir cits ceļš vai saistītais montējums, atbilstoši pielāgojiet kopēšanu. Docker Compose kopēšanas atsauce. Vides ar atsevišķu PostgreSQL datubāzi nevar atjaunot, atjaunojot tikai n8n mapi.

KRITISKI SVARĪGS NOSLĒPUMS

Šifrēšanas atslēga ir atjaunošanas sastāvdaļa

n8n šifrē saglabātos piekļuves datus ar instances šifrēšanas atslēgu. Datubāzes vai šifrētu piekļuves datu eksports bez atbilstošās atslēgas var padarīt atjaunotās darbplūsmas nespējīgas izmantot saglabātos piekļuves datus.

Ja iestatījāt N8N_ENCRYPTION_KEY, atjaunojiet precīzi šo noslēpumu. Pretējā gadījumā ģenerētā atslēga glabājas pastāvīgajā .n8n/config failā: saglabājiet šo konfigurāciju dublēšanas un atjaunošanas laikā. Atjaunošanas atslēgas droši glabājiet ārpus VPS. Rindas režīmā visiem galvenajiem procesiem un izpildītājiem jāizmanto viena un tā pati atslēga.

DarietSaglabājiet aizsargātu precīzās produkcijas vides atslēgas kopiju.
DarietPirms piekļuves datu pārbaudes pārliecinieties, ka atjaunošanas vide izmanto šo atslēgu.
NedarietPēc servera atjaunošanas nepaļaujieties uz tikko ģenerētu atslēgu.
NedarietNeievietojiet atslēgu publiskā repozitorijā un neglabājiet to blakus neaizsargātai kopijai.

FAILI UN BINĀRIE DATI

Datubāzes kopija var neietvert visas darbplūsmu atkarības

Pastāvīgie .n8n dati

Atrodiet un saglabājiet faktisko .n8n lietotāja mapi, ne tikai konteinera attēlu. Tipiskā Docker vidē tā ir montēta ceļā /home/node/.n8n, bet ārpus Docker noklusējuma ceļš ir ~/.n8n. Ja ir konfigurēts N8N_USER_FOLDER, n8n izveido .n8n norādītajā vecākdirektorijā. Iekļaujiet tās konfigurācijas atslēgu un visus lokālos SQLite, bināros vai failu sistēmas izpilžu datus, ko izmanto instalācija.

Montētie darbplūsmu faili

Ja darbplūsmas lasa vai raksta resursdatorā montētās direktorijās, dublējiet tās atsevišķi. Bez tām atjaunotas darbplūsmas var nedarboties, pat ja citādi tās ir korektas.

Binārie dati

Noskaidrojiet glabāšanas režīmu un atjaunojiet visas ārējās atkarības. Failu sistēmā glabātie binārie vai izpilžu dati var atrasties .n8n vai pielāgotā direktorijā; S3/Azure Blob vai citai konfigurētai ārējai krātuvei vajadzīga sava atjaunojama kopija un piekļuves iestatījumi. Datubāzes izdruka viena pati šos failus neaizstās.

Kopienas mezgli

Pierakstiet kopienas pakotnes un versijas, kā arī dublējiet papildu pielāgoto mezglu direktorijas, kas konfigurētas ar N8N_CUSTOM_EXTENSIONS. Tās var atrasties ārpus .n8n; datubāzes un lietotāja mapes atjaunošana viena pati var nepadarīt pielāgoto mezglu darbplūsmas lietojamas.

Piemēram, ja varat pieļaut ne vairāk kā sešu stundu izmaiņu zudumu, veiksmīgs kopēšanas grafiks ik pēc sešām stundām ir sākumpunkts, nevis garantija: neveiksmīgi darbi un aizkavēta pārsūtīšana ārpus servera var palielināt faktisko zudumu. Nosakiet glabāšanas termiņus un atjaunošanas pārbaužu biežumu pēc sava RPO/RTO un datu prasībām, nevis pieņemiet universālu 7 vai 30 dienu politiku.

ATJAUNOŠANAS SECĪBA

Atjaunojiet kontrolētā secībā

1 · SagatavošanaIzveidojiet savietojamu serveri, datubāzi un konteineru/izpildvidi.
2 · Noslēpumu atjaunošanaDroši konfigurējiet sākotnējo n8n šifrēšanas atslēgu un nepieciešamos izvietošanas noslēpumus.
3 · Datubāzes atjaunošanaAtjaunojiet PostgreSQL vai SQLite un pārliecinieties, ka n8n var pieslēgties paredzētajiem datiem.
4 · Failu atjaunošanaAtjaunojiet pastāvīgās direktorijas, bināros datus un montētos darbplūsmu resursus.
5 · n8n palaišanaPalaidiet lietotni ar paredzēto resursdatora nosaukumu, datubāzi un vides konfigurāciju.
6 · PārbaudePārliecinieties, ka lietotāji, darbplūsmas un piekļuves dati ielādējas; pēc tam izpildiet raksturīgās darbplūsmas un tīmekļa aizķeres.

PostgreSQL avārijas atjaunošanas piemērs: uz atsevišķa, tīra atjaunošanas mērķa, kurā jau ir pareizā datubāzes loma un tukša n8n datubāze, palaidiet tikai PostgreSQL. Pirms importēšanas sagaidiet, līdz tā ir gatava darbam: docker compose up -d viena pati var beigties, kamēr PostgreSQL vēl inicializējas, tāpēc nākamā pg_restore var neizdoties. Piemērā izmantots --wait modernā Compose instalācijā, un neatkarīgi pārbaudīts pg_isready. Lai droši gaidītu, konfigurējiet atbilstošu PostgreSQL veselības pārbaudi vai pirms turpināšanas skaidri apstipriniet gatavību. Nenovirziet šo komandu uz aizpildītu produkcijas datubāzi un nepalaidiet n8n, pirms datubāze un tai atbilstošie .n8n atslēga/dati nav atjaunoti.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Mērķī jābūt savietojamai PostgreSQL versijai, lomu privilēģijām, paplašinājumiem un sākotnējai n8n konfigurācijai. Atjaunojiet .n8n pareizajā pastāvīgajā sējumā vai saistītajā montējumā ar savu dublēšanas mehānismu, saglabājot īpašnieku un tiesības. Atjaunojiet ārējos bināros failus, pielāgotos paplašinājumus, Compose un noslēpumu konfigurāciju, pēc tam palaidiet savietojamu n8n versiju un pārbaudiet žurnālus. Tikai datubāzes atjaunošana neatjauno atslēgu: PostgreSQL vidē tā glabājas .n8n/config ja vien neesat skaidri konfigurējuši N8N_ENCRYPTION_KEY. pg_restore atsauce · n8n pilnas instances atjaunošanas secība.

Pārbaudiet piekļuves datus

Nepietiek tikai atvērt darbplūsmu. Pārliecinieties, ka atjaunotie šifrētie piekļuves dati patiešām tiek atšifrēti un autentifikācija izdodas.

Izpildiet raksturīgās darbplūsmas

Pārbaudiet darbplūsmas, kurām vajadzīgas tīmekļa aizķeres, ārējie API, montētie faili un kopienas mezgli, nevis tikai elementāru automatizāciju.

Izmēriet atjaunošanas laiku

Pierakstiet atjaunošanai patērēto laiku un atlikušās manuālās darbības. Tā šķietamu kopiju pārvērš par praksē izmantojamu atjaunošanas procedūru.

PostgreSQL: IZDEVĀSImportējām to pašu testa darbplūsmu, izveidojām un pārbaudījām pielāgotā formāta pg_dump, atjaunojām to ar pg_restore jaunā tukšā PostgreSQL datubāzē, atjaunojām atsevišķo .n8n mapi un pēc tam atkārtoti eksportējām un izpildījām atjaunoto darbplūsmu.
Ko pierāda veiksmīga pārbaudeIzmēģinātās dublēšanas metodes saglabāja darbplūsmu, tās divus mezglus un savienojumus, un ļāva to izpildīt pēc atjaunošanas. Tie ir atkārtojami funkcionāli pamattesti, nevis slodzes etalontesti.
Kas netika pārbaudītsReālu piekļuves datu atšifrēšana un autentifikācija, produkcijas tīmekļa aizķeres, rindas režīma izpildītāji un Redis, S3/Azure bināro datu krātuves, pielāgotie mezgli, lietotāju/projektu piekļuve vai dzīvas produkcijas instances atjaunošana. Veiciet atsevišķu izmēģinājumu katrai patiesi izmantotajai atkarībai.

Kā atkārtot: izmantojiet īslaicīgu n8n instalāciju, izveidojiet nekaitīgu divu mezglu darbplūsmu, izveidojiet atbilstošo datubāzes un pastāvīgās mapes kopiju, atjaunojiet to tīrā sējumā vai datubāzē, pēc tam pārbaudiet atjaunotās darbplūsmas mezglus, savienojumus un faktisku izpildi. Produkcijas vidē pirms atjaunošanas atzīšanas par pierādītu pārbaudiet arī šifrētos piekļuves datus, tīmekļa aizķeres un ārējos failus.

Atjaunošanas pārbaudes pieņemšanas saraksts: izmantojiet izolētu domēnu/vidi; pārbaudiet lietotāju un darbplūsmu esamību, viena esoša šifrēta piekļuves datu komplekta autentifikāciju bez atkārtotas ievades, produkcijas tīmekļa aizķeres izsaukumu pareizajai atjaunotajai darbplūsmai, montēto failu un bināro pielikumu lasāmību un integrācijas ar nepieciešamajiem kopienas mezgliem. Apstipriniet kopijas vecumu, izmērīto dīkstāvi un pieejamību ārpus servera. Ja kāda būtiska pārbaude neizdodas, atzīmējiet atjaunošanas punktu kā nepārbaudītu , nevis ziņojiet, ka kopija ir pilnīga.

CLI DUBLĒŠANAS IEROBEŽOJUMI

Precīzi ziniet, ko darbplūsmu un piekļuves datu eksports neatjauno

CLI eksports nav pilna instances rezerves kopija

Darbplūsmu un piekļuves datu eksports neietver lietotājus un lomas, izpilžu vēsturi un žurnālus, mainīgos vai instances iestatījumus, piemēram, šifrēšanas atslēgu.

Jaunai instancei vajadzīgs īpašnieks

Tīrā instancē pirms piekļuves datu importēšanas pabeidziet īpašnieka konta iestatīšanu. Vairāku lietotāju vai projektu atjaunošanai var būt nepieciešama arī pareiza lietotāja vai projekta piesaiste.

Importētie ID var pārrakstīt esošos objektus

Darbplūsmu un piekļuves datu eksports saglabā sākotnējos ID. Importējot instancē, kurā jau ir tādi paši ID, esošie objekti var tikt aizstāti.

Publicējiet importētās darbplūsmas apzināti

CLI imports parasti atstāj darbplūsmas neaktīvas. n8n 2.x pārbaudiet katras importētās darbplūsmas publicēšanas stāvokli un publicējiet tikai tās, ko paredzēts darbināt; pašu mitinātais Server CLI atbalsta arī komandu n8n publish:workflow --id=YOUR_WORKFLOW_ID. Kad n8n darbojas, ar Server CLI veiktās publicēšanas stāvokļa izmaiņas stājas spēkā tikai pēc n8n restartēšanas. Pirms ieplānoto aktivizētāju un produkcijas tīmekļa aizķeru pārbaudes vai datplūsmas pārslēgšanas veiciet restartēšanu.

Masveida eksporta piemērs Docker Compose vidē: ja jūsu n8n serviss ir nosaukts n8n, varat izpildīt tālāk redzamās oficiālās CLI dublēšanas komandas. Izvades ceļš ir apzināti izvēlēts tā pastāvīgajā .n8n direktorijā, jo citas direktorijas konteinerā var pazust, to no jauna izveidojot. Pārliecinieties, ka n8n konteinera lietotājs drīkst rakstīt šajā direktorijā. Saglabājiet darbplūsmu un piekļuves datu JSON atsevišķās direktorijās— n8n dokumentācija apraksta importēšanas problēmu, ja abu veidu kopijas ir vienā direktorijā.

n8n 2.x melnraksta un publicētās versijas kopija: parasts --backup darbplūsmas eksports saglabā pašreizējos melnrakstus; tie var atšķirties no produkcijā publicētajām versijām. Lai saglabātu konkrētas darbplūsmas patiesi publicēto versiju, eksportējiet to atsevišķi ar docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, iepriekš pārliecinoties, ka izvades mape pastāv un tajā drīkst rakstīt. CLI var arī eksportēt vēsturisku versiju, izmantojot --version=VERSION_ID. Glabājiet šīs kopijas ārpus servera kopā ar pilno rezerves kopiju; nepieņemiet, ka melnraksta JSON atspoguļo publiski darbināto versiju.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Nokopētā ~/n8n-recovery/cli direktorija joprojām atrodas VPS, līdz pārvietojat to uz drošu, neatkarīgu rezerves krātuvi. Piekļuves datu eksports pēc noklusējuma ir šifrēts un importējot prasa atbilstošu šifrēšanas atslēgu. Neizmantojiet --decrypted , izņemot stingri kontrolētu migrāciju: tas ieraksta noslēpumus atklātā tekstā. Nekad neievietojiet eksportus ar sensitīvu darbplūsmu loģiku vai piekļuves datiem publiskā GitHub repozitorijā. Dažas trešo pušu GitHub piekļuves datu dublēšanas veidnes apzināti eksportē atšifrētus noslēpumus; privāts repozitorijs ierobežo piekļuvi, bet nav šifrēšana. Pārbaudiet katras veidnes faktiskos eksporta iestatījumus un krātuves atļaujas, pirms pārsūtīšanas šifrējiet noslēpumus un nomainiet jebkurus piekļuves datus, kas nejauši augšupielādēti atklātā tekstā.

Masveida importa piemērs: tīrā mērķī pabeidziet īpašnieka iestatīšanu, norādiet sākotnējo šifrēšanas atslēgu un pārliecinieties, ka saglabātie kopiju faili ir pieejami atjaunošanas VPS. Tālāk redzamās komandas izveido mērķa mapi un kopē workflows/ and credentials/ apakšmapes no resursdatora uz n8n konteineru; pielāgojiet ceļus, ja atšķiras Docker sējumu konfigurācija:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Pārbaudiet failu īpašnieku un piekļuves tiesības n8n konteinera lietotājam. Neimportējiet datus aizpildītā produkcijas instancē bez pārbaudītas atgriešanās iespējas: darbplūsmu un piekļuves datu ID var pārrakstīt esošos ierakstus. Pēc tam izpildiet:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Importētie ID var aizstāt esošās darbplūsmas vai piekļuves datus; izmēģinājumiem izmantojiet izolētu testa instanci un pēc tam pārbaudiet piekļuves datus, aktivizēšanas un publicēšanas stāvokļus. n8n 2.x JSON melnraksta atjaunošana pati par sevi nepierāda, ka darbplūsma ir publicēta un spēj palaist ieplānotos aktivizētājus. Importēšanas drošība: n8n instancē bez vairāku galveno procesu režīma iepriekš aktīvi cron aktivizētāji pēc CLI importa var turpināt darboties līdz instances restartēšanai. Apturiet vai izolējiet produkcijas aktivizētājus un restartējiet n8n pirms atjaunoto darbu ieslēgšanas; pārliecinieties, ka izpildes nedublējas. CLI eksports neveido neietver sākotnējos lietotājus, izpilžu žurnālus, instances mainīgos vai šifrēšanas atslēgu. --backup iestata --all --pretty --separate, nevis „pilnu instanci”. Avoti: pašreizējā oficiālā n8n dublēšanas un atjaunošanas rokasgrāmata un n8n CLI komandu dokumentācija.

Masveida atjaunošana no GitHub vai Google Drive veidnēm: tā ir alternatīva tikai darbplūsmu JSON, nevis instances datubāzei, lietotājiem, šifrētajiem piekļuves datiem vai šifrēšanas atslēgai. Pirms API veidnes palaišanas pārbaudiet tās n8n API un krātuves atļaujas, izvēlēto kopijas versiju un mērķa instanci, vai tā atjaunina sakrītošus ID, no jauna izveido dzēstās darbplūsmas un kā apstrādā darbplūsmu publicēšanu. Ne visas veidnes atjauno mērķī trūkstošu ID; pārbaudiet šo gadījumu izolēti, pirms paļaujaties uz automātisku atjaunošanu.

BUJ

n8n dublēšana un atjaunošana: biežākie jautājumi

Vai ar darbplūsmu eksportu pietiek n8n dublēšanai?

Nē. Darbplūsmu eksports ir noderīga loģiska kopija, taču pilnai atjaunošanai var vajadzēt arī piekļuves datus, atbilstošo šifrēšanas atslēgu, datubāzes stāvokli, pastāvīgos failus un bināro datu krātuvi.

Vai vajadzīga n8n šifrēšanas atslēga, ja ir datubāze?

Jā, ja vēlaties saglabāt datubāzē esošo šifrēto piekļuves datu izmantošanu. Droši saglabājiet sākotnējo atslēgu.

Vai dublēt PostgreSQL vai eksportēt darbplūsmas un piekļuves datus?

Atjaunošanai pēc avārijas saglabājiet datubāzi un šifrēšanas atslēgu. Loģiskais eksports noder kā papildu migrācijas un selektīvas atjaunošanas iespēja, nevis visu instances komponentu aizstājējs.

Vai VPS momentuzņēmums var būt vienīgā rezerves kopija?

Labāk uzskatīt to par vienu atjaunošanas slāni. Saglabājiet neatkarīgu kopiju ārpus servera, lai pakalpojumu sniedzēja, konta, servera vai momentuzņēmuma kļūme neiznīcinātu visus atjaunošanas punktus uzreiz.

Kā zināt, vai rezerves kopija darbojas?

Atjaunojiet to tīrā testa vidē, pārbaudiet šifrēto piekļuves datu atšifrēšanu un izpildiet raksturīgās darbplūsmas. Veiksmīgs dublēšanas uzdevums pats par sevi nepierāda atjaunojamību.

Vai GitHub vai Google Drive darbplūsmu kopijās ir saglabātie piekļuves datu noslēpumi?

Tikai darbplūsmu JSON kopijās nav n8n piekļuves datu krātuvē pārvaldīto slepeno vērtību vai instances šifrēšanas atslēgas. Tomēr eksportēts JSON var atklāt piekļuves datu nosaukumus un ID, kā arī noslēpumus, kas tieši ievadīti mezglu parametros, piemēram, autentifikācijas galvenēs. Pirms JSON augšupielādes vai kopīgošanas pārbaudiet un aizsargājiet to. Pilnai atjaunošanai dublējiet datubāzi un sākotnējo atslēgu vai izmantojiet atbalstītu šifrētu piekļuves datu CLI eksportu ar pārbaudītu atjaunošanu. Tikai darbplūsmu GitHub vai Google Drive veidne nav pilna avārijas atjaunošana.

ATJAUNOŠANAS MĒRĶI

Pirms incidenta nosakiet RPO un RTO

RPO ir maksimāli pieļaujamais neseno izmaiņu zudums. Mēriet to pēc jaunākā izmantojamā atjaunošanas punkta, kas glabājas neatkarīgi; ieplānots darbs ik pēc sešām stundām negarantē sešu stundu RPO, ja eksports vai pārsūtīšana nav izdevusies. RTO ir maksimāli pieļaujamais darbības pārtraukums. Mēriet to tīras atjaunošanas izmēģinājumā, ietverot noslēpumu saņemšanu, ārējo failu atjaunošanu, piekļuves datu pārbaudi un atjaunoto darbplūsmu publicēšanu — ne tikai konteinera palaišanu.

ATJAUNOŠANAS ATSLĒGA

Pirms servera atjaunošanas atrodiet sākotnējo šifrēšanas atslēgu

Ja produkcijas vidē bija iestatīts N8N_ENCRYPTION_KEY, saglabājiet precīzi šo vides noslēpumu. Ja tā nebija, saglabājiet ģenerēto atslēgu sākotnējā pastāvīgajā .n8n/config. Pirms šifrēto piekļuves datu importēšanas pārbaudiet, kuru avotu izmanto atjaunotā instance; jaunģenerēta atslēga nevar atšifrēt vecās datubāzes piekļuves datus.

Vai salīdzināt pakalpojumu sniedzējus?

Lai salīdzinātu pakalpojumu sniedzējus, vienklikšķa uzstādīšanu, atbalsta robežas, dublēšanu, migrāciju, reģionus un mērogošanu, skatiet Labākā n8n VPS salīdzinājumu. Resursu izvēlei atgriezieties pie galvenā n8n VPS ceļveža.
