n8n drošība VPS serverī

Lai aizsargātu n8n VPS serverī, nepadariet n8n (5678), PostgreSQL (5432) un izvēles Redis (6379) publiski pieejamus. Izmantojiet HTTPS reverso starpniekserveri, SSH atslēgas un daudzfaktoru autentifikāciju (MFA), saglabājiet šifrēšanas atslēgu, autentificējiet tīmekļa aizķeres, ierobežojiet riskantas darbplūsmu iespējas un veiciet izvietotās instances drošības auditu. Redaktora piekļuve jāaizsargā atsevišķi no publiskajiem tīmekļa aizķeru ceļiem. Ar HTTPS vien nepietiek, lai aizsargātu pieslēgtos pakalpojumus.

TĪKLA ĀRĒJĀ ROBEŽA

Reversais starpniekserveris, HTTPS un uzticamās galvenes

TLS savienojuma terminēšana

HTTPS savienojumiem izmantojiet reverso starpniekserveri, piemēram, Nginx, Caddy vai Traefik. Pāradresējiet parasto HTTP un neatveriet n8n lietotnes portu tieši, ja paredzētais publiskās piekļuves punkts ir starpniekserveris.

Starpniekservera konfigurācija

Ja n8n darbojas aiz reversā starpniekservera, pareizi iestatiet starpniekservera posmu skaitu un pārsūtiet galvenes, kas n8n vajadzīgas sākotnējā klienta pieprasījuma noteikšanai.

Drošas sīkdatnes

Nodrošiniet redaktora piekļuvi ar HTTPS, lai autentifikācijas sīkdatnes varētu palikt drošas. Neapejiet bojātu TLS konfigurāciju, vājinot sīkdatņu drošību.

Tīmekļa aizķeres URL

Iestatiet publiskās tīmekļa aizķeres URL uz ārēji sasniedzamu HTTPS resursdatora nosaukumu, lai ģenerētās adreses nenorādītu uz iekšējo konteineru vai HTTP.

Saglabājiet redaktoru privātu, netraucējot tīmekļa aizķeru darbībai. Ja iespējams, ierobežojiet administrēšanas piekļuvi ar VPN, uzticamu IP adrešu politiku vai autentificētu starpniekserveri. Publiskajiem tīmekļa aizķeru uztvērējiem un OAuth atzvanu ceļiem var būt jāpaliek sasniedzamiem; pirms starpniekservera noteikuma piemērošanas pārbaudiet gan uzticama redaktora lietotāja pierakstīšanos, gan reālu ārēju atzvanu. Pārsūtītās klienta adreses galvenes pieņemiet tikai no uzticamiem starpniekserveriem, nevis patvaļīgām pieprasījuma galvenēm.

Autentificējiet tīmekļa aizķeru izsaucējus: Webhook mezglā izvēlieties Basic, Header vai JWT autentifikāciju, nevis None, ja sūtītājs to atbalsta. Vajadzības gadījumā izmantojiet opciju IP(s) Allowlist un pārbaudiet pakalpojumu sniedzēja parakstus, ja integrācija atbalsta parakstītus pieprasījumus. Grūti uzminama URL adrese nav pietiekama autentifikācija. Vajadzības gadījumā starpniekserverī iestatiet pieprasījumu biežuma ierobežojumus un pārliecinieties, ka derīgi pieprasījumu pieaugumi netiek bloķēti. Oficiālās Webhook autentifikācijas iespējas.

Konteineru pieejamība

Publicējiet tikai tos portus, kuriem nepieciešama piekļuve no resursdatora. Iekšējiem pakalpojumiem jāsazinās pa privātiem Docker tīkliem, nevis publiskām saskarnēm.

Pirms ugunsmūra vai SSH iestatījumu maiņas pārbaudiet: klausīšanās portus ar komandu sudo ss -lntp, Docker publicētos portus ar komandu docker compose ps projekta direktorijā un resursdatora ugunsmūra politiku ar komandu sudo ufw status verbose , ja izmantojat UFW. Pirms paroles autentifikācijas atspējošanas citā sesijā pārbaudiet īsto SSH portu un veiksmīgu pierakstīšanos ar atslēgu. Docker publicētie porti var apiet UFW noteikumus; ugunsmūra statusa lapa vien nepierāda, ka ports 5678 ir privāts. Pārbaudiet faktisko sasniedzamību no ārpuses. Docker/UFW ierobežojumu skaidrojums.

Pārbaudiet automātiskos Ubuntu drošības atjauninājumus, nevis pieņemiet, ka tie darbojas: apskatiet apt-config dump APT::Periodic::Unattended-Upgrade un žurnālu /var/log/unattended-upgrades/unattended-upgrades.log. Ja automātiskie drošības jauninājumi ir atspējoti, sudo dpkg-reconfigure unattended-upgrades nodrošina atbalstītu konfigurācijas dialogu. Pirms ieslēgšanas strādājošā VPS pārskatiet restartēšanas un pakalpojumu pārstartēšanas darbību. Ubuntu APT atjauninājumi neatjaunina automātiski n8n Docker attēlu vai katru trešo pušu programmatūras repozitoriju. Ubuntu automātisko atjauninājumu dokumentācija.

SSH pārlases uzbrukumu uzraudzība pēc izvēles: Fail2Ban var noteikt atkārtotus neveiksmīgus SSH pieteikšanās mēģinājumus. Ja tas ir instalēts un konfigurēts SSH aizsardzībai, pārbaudiet aizsardzības noteikumu ar komandu sudo fail2ban-client status sshd un pārliecinieties, ka tiek izmantots pareizais SSH autentifikācijas žurnāls vai sistēmas žurnāls un konfigurētais ports. Tas papildina SSH atslēgas un tīkla ierobežojumus, bet tās neaizstāj. Nekopējiet fiksētu SSH portu vai bloķēšanas noteikumu, nepārbaudot esošo piekļuvi. Ubuntu SSH drošības nostiprināšanas norādes.

Sagatavojiet atgriešanos un atjaunošanu

Pirms būtiskiem atjauninājumiem izveidojiet atjaunojamas rezerves kopijas. Precīzs dublēšanas tvērums un atjaunošanas kārtība aprakstīta atsevišķā ceļvedī.

Samaziniet sensitīvas izpilžu vēstures glabāšanu: veiksmīgas izpildes var saglabāt klientu datus un marķierus. Ja piemērojams, iestatiet EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, saglabājiet EXECUTIONS_DATA_PRUNE=trueun izvēlieties EXECUTIONS_DATA_MAX_AGE stundās, piemēram, 168 (septiņas dienas). Šīs ir pielāgojamu iestatījumu ilustrācijas, nevis juridiski datu glabāšanas noteikumi. Mazāka vēsture nozīmē mazāk datu atkļūdošanai un incidentu izmeklēšanai; notiekošās, gaidošās vai anotētās izpildes var netikt dzēstas tāpat. Oficiālā izpilžu vēstures glabāšanas dokumentācija.

Ja ir aizdomas par kompromitēšanu: ierobežojiet ļaunprātīgo piekļuvi, neiznīcinot pierādījumus, pārbaudiet starpniekservera, resursdatora un n8n aktivitāti un izmainītās darbplūsmas, atsauciet vai nomainiet iespējami atklātos ārējo sistēmu piekļuves datus, novērsiet cēloni un, ja vajadzīgs, atjaunojiet tikai no pārbaudītām rezerves kopijām. Pārskatiet skartās tīmekļa aizķeru adreses, redaktora kontus un saistītos pakalpojumus; nepieņemiet, ka HTTPS, momentuzņēmumi vai VPS iegāde ietver incidentu reaģēšanas pakalpojumus.

Vai n8n ports jāatver publiski?

Ja reversais starpniekserveris ir publiskais piekļuves punkts, atveriet tā portus, bet lietotnes portu atstājiet aiz tā, nevis plaši publicējiet nevajadzīgus pakalpojumus.

Vai PostgreSQL vai Redis jābūt publiski pieejamiem?

Parasti nē. Tiem jābūt sasniedzamiem tikai sistēmām, kurām tie nepieciešami. Publiska piekļuve palielina uzbrukuma virsmu, neuzlabojot parastu n8n darbību.

Kāpēc n8n šifrēšanas atslēga ir svarīga?

Tā aizsargā n8n saglabātos piekļuves datus un tai jāpaliek nemainīgai visā izvietojumā. Atslēgas zuduma dēļ atjaunotajos datos esošie šifrētie piekļuves dati var kļūt nelietojami.

Vai kopienas mezgli ir droši?

Tie paplašina n8n ar trešo pušu kodu, tāpēc tie jāuzskata par programmatūras atkarībām ar saviem piegādes ķēdes un piekļuves tiesību riskiem. Instalējiet tikai uzticamus un nepieciešamus mezglus.

Vai HTTPS padara pašmitinātu n8n instanci drošu?
