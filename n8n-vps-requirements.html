MINIMUM VS PRACTICAL CAPACITY

Does n8n have one official minimum VPS size?

Not for every workload. n8n's official prerequisite examples describe an illustrative OEM deployment and explicitly warn that requirements vary by workload. That documentation is not a universal guarantee that any specific CPU, RAM or disk allocation will support production automations.

n8n notes that an idle instance may use relatively little memory, but a Code node, large binary payload or simultaneous execution can increase memory demand sharply. Budget separately for the operating system, Docker, PostgreSQL and backup/monitoring tools.

RAM & CPU

What actually consumes server resources

Concurrent executions

Several workflows running at the same time can matter more than the total number of workflows stored in n8n. Watch memory peaks and execution latency during overlap.

Payload size

Large JSON objects, files and binary data increase memory pressure. A few data-heavy executions can require more RAM than many lightweight API automations.

CPU-heavy nodes

Code, transformations and other compute-heavy steps can create sustained CPU pressure. More cores help when real executions compete for compute.

Supporting services

The operating system, PostgreSQL, reverse proxy, monitoring and Docker also need resources. Size the complete stack, not only the n8n process.

MEASURE BEFORE YOU UPGRADE

How to tell whether n8n needs more RAM, CPU or disk

Run your largest expected workflow and a realistic overlapping burst, then inspect the server and n8n execution logs. The number of workflows saved in the editor is not a useful capacity benchmark on its own.

Memory / OOM

Check docker stats --no-stream and free -h. If memory is exhausted, first reduce JSON or binary payloads, batch large imports and avoid memory-heavy Code steps. A JavaScript heap error is not necessarily fixed by adding vCPUs.

CPU / concurrency

Measure whether CPU stays busy during transformations or jobs only wait for external APIs. In regular mode, consider a supported production-concurrency limit before scaling to workers. Increasing CPU does not speed up an external rate-limited API.

Storage / database

Check df -h, database size and retained execution history. Watch disk growth and slow database operations. Set retention deliberately before paying for a larger disk; keep recovery copies off-server.

Use n8n's concurrency guidance and the official benchmarking explanation. Any number of concurrent workflows advertised without knowing their payloads and API latency is only an estimate.

DATABASE & STORAGE

SQLite, PostgreSQL and persistent data

SQLite

SQLite can fit small single-instance deployments and testing. As production usage and concurrency grow, database choice becomes an operational constraint rather than an installation detail.

PostgreSQL

For a production-oriented VPS stack, PostgreSQL provides a stronger database foundation. Budget RAM, CPU and disk for the database itself and monitor its growth.

Persistent .n8n data

Do not treat PostgreSQL as the only persistent asset. Preserve the n8n data directory and protect the encryption key required to recover encrypted credentials.

Disk growth

Execution history, binary data, database files and logs can expand over time. Retention settings and off-server backups directly affect required capacity.

DISK CAPACITY

Estimate n8n execution-history storage before ordering

Start with saved executions per day × average stored bytes per execution × retention days. For example, 500 saved executions per day × 200 KB each × 14 days = 1.4 GB of example execution data before database overhead. That 200 KB assumption is illustrative, not an n8n benchmark.

Also allocate disk for the OS, Docker image layers, database indexes, binary files, application logs, upgrades and temporary files. Off-server backups need their own capacity. A 10 GB disk can work for a lean stack but has much less room for retained files than a 40 or 80 GB disk.

n8n documents default execution pruning by age (336 hours / 14 days) or count (10,000 executions), with exceptions. Check your actual settings and verify what is retained before changing them. SQLite may reuse freed space rather than automatically shrinking its file.

Source: n8n: manage execution data and pruning. Disk requirements depend on observed saved payload sizes, not the number of nodes alone.

SYSTEM REQUIREMENTS

Docker and production overhead

Linux VPS

Use a maintained Linux distribution with enough resources for the operating system and security updates in addition to the application stack.

Docker & Compose

Container deployment simplifies repeatability but does not eliminate resource overhead. Persist n8n and database data outside disposable containers.

HTTPS & reverse proxy

Public webhooks require a stable hostname and correctly configured HTTPS. Include the reverse proxy and TLS layer in the production design.

Monitoring & backups

Track RAM, CPU, disk and database growth. Keep recoverable backups outside the VPS and test restoration rather than assuming a snapshot is enough.

CONCURRENCY

When a larger VPS stops being the whole answer

Vertical scaling is appropriate while one instance can handle the workload cleanly. When sustained parallel demand creates contention, evaluate queue mode and workers. Queue mode introduces Redis, PostgreSQL and one or more worker processes; budget RAM and CPU for every component, not just n8n. n8n also documents restrictions on filesystem binary-data storage in queue mode, so validate a compatible data-storage design before switching.

ENTRY TIER & STORAGE I/O

How to use a 1 GB entry VPS

1 GB RAM

This is a real working VPS tier, not a test-only product. It can be suitable for small always-on automations and mostly sequential API work when you keep memory, disk use and concurrent jobs within measured limits. It offers little headroom for PostgreSQL on the same server, large payloads or heavy parallel executions.

2 GB RAM

Use 2 GB as the safer light-instance baseline when you want more room for the operating system, Docker and small bursts without immediately moving to a production-sized stack.

SSD vs NVMe

Standard SSD is adequate for light automation. NVMe becomes more useful when PostgreSQL and execution history create frequent reads and writes or when disk latency shows up in measured workflow performance.

Measure before upgrading

Use CPU, memory, disk growth and execution duration under peak overlap to decide whether the bottleneck is compute, memory or storage rather than assuming a larger VPS fixes every slowdown.

FAQ

n8n VPS requirements: common questions

How much RAM does n8n need?

There is no universal figure. RAM demand changes with concurrency, payload size, execution behavior and the supporting services on the VPS. A 4 GB server is a practical small-production starting class, not a guaranteed requirement for every workload.

How many CPU cores should I use?

Light workloads can start with a small CPU allocation. Add cores when monitoring shows sustained CPU pressure or slower executions under concurrency rather than sizing from workflow count alone.

Does n8n require PostgreSQL?

Small deployments can use SQLite, but PostgreSQL is the stronger production-oriented choice as operational requirements and concurrency increase.

When is Redis required?

Redis is associated with queue mode. A normal single-instance deployment does not need Redis simply because it runs on a VPS.

How much disk space should I reserve?

Disk demand depends on PostgreSQL growth, retained execution history, binary data, logs, container layers and backups. Monitor growth and leave headroom instead of relying on a fixed universal number.

Can I run n8n continuously on a 1 GB VPS?

Yes, when the actual workload fits. A 1 GB VPS is a real working server and can support small, mostly sequential automations, but memory headroom is limited. Avoid assuming that a same-server PostgreSQL stack, binary-heavy jobs or multiple large concurrent executions will fit. Monitor consumption and upgrade based on observed resource pressure.

Is 2 GB or 4 GB RAM better for a production n8n VPS?

Two gigabytes gives more room than a lean 1 GB instance, while 4 GB is a practical starting class to assess n8n together with PostgreSQL and HTTPS. There is no universal guaranteed production minimum: workload complexity, peak overlap, container configuration and retained data determine real demand.

Do n8n AI workflows require a GPU?

Not when n8n only calls an external model API: the model provider handles inference, while the VPS handles orchestration, payloads and concurrency. Running inference models locally is a separate hardware decision that may require much more RAM and appropriate GPU resources.

What causes n8n out-of-memory errors?

Large JSON or binary payloads, memory-heavy Code operations and overlapping executions are common causes. Check runtime logs and peak memory use, then reduce data held in one execution or allocate more RAM based on the measured problem.
