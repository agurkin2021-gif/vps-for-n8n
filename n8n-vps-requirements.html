SERVER REQUIREMENTS

n8n VPS requirements: size the server for the workload

There is no single RAM or CPU number that fits every n8n installation. Practical requirements depend on concurrent executions, payload size, execution duration, database growth and the other services running beside n8n.

Light / entry instance

RAM & CPU

What actually consumes server resources

Concurrent executions

Several workflows running at the same time can matter more than the total number of workflows stored in n8n. Watch memory peaks and execution latency during overlap.

Payload size

Large JSON objects, files and binary data increase memory pressure. A few data-heavy executions can require more RAM than many lightweight API automations.

CPU-heavy nodes

Code, transformations and other compute-heavy steps can create sustained CPU pressure. More cores help when real executions compete for compute.

Supporting services

The operating system, PostgreSQL, reverse proxy, monitoring and Docker also need resources. Size the complete stack, not only the n8n process.

DATABASE & STORAGE

SQLite, PostgreSQL and persistent data

SQLite

SQLite can fit small single-instance deployments and testing. As production usage and concurrency grow, database choice becomes an operational constraint rather than an installation detail.

PostgreSQL

For a production-oriented VPS stack, PostgreSQL provides a stronger database foundation. Budget RAM, CPU and disk for the database itself and monitor its growth.

Persistent .n8n data

Do not treat PostgreSQL as the only persistent asset. Preserve the n8n data directory and protect the encryption key required to recover encrypted credentials.

Disk growth

Execution history, binary data, database files and logs can expand over time. Retention settings and off-server backups directly affect required capacity.

SYSTEM REQUIREMENTS

Docker and production overhead

Linux VPS

Use a maintained Linux distribution with enough resources for the operating system and security updates in addition to the application stack.

Docker & Compose

Container deployment simplifies repeatability but does not eliminate resource overhead. Persist n8n and database data outside disposable containers.

HTTPS & reverse proxy

Public webhooks require a stable hostname and correctly configured HTTPS. Include the reverse proxy and TLS layer in the production design.

Monitoring & backups

Track RAM, CPU, disk and database growth. Keep recoverable backups outside the VPS and test restoration rather than assuming a snapshot is enough.

CONCURRENCY

When a larger VPS stops being the whole answer

Vertical scaling is appropriate while one instance can handle the workload cleanly. When sustained parallel demand creates contention, evaluate queue mode and workers. Queue mode introduces Redis and worker processes, so it increases the resources and operational components that must be sized.

SIZING CHECKLIST

Define these before choosing a VPS

How much work overlaps?

Estimate peak concurrent executions, not only daily execution count.

How large is each execution?

Account for JSON size, files, binary data and memory-heavy transformations.

What shares the server?

Include PostgreSQL, proxy, monitoring and any other containers in the resource budget.

How quickly will data grow?

Estimate execution retention, database growth and backup storage before selecting disk capacity.

ENTRY TIER & STORAGE I/O

How to use a 1 GB entry VPS

1 GB RAM

A 1 GB plan can be useful for learning, light webhook checks and a very small single-instance workload, but it leaves little headroom for PostgreSQL, larger payloads, retained execution history or overlapping jobs.

2 GB RAM

Use 2 GB as the safer light-instance baseline when you want more room for the operating system, Docker and small bursts without immediately moving to a production-sized stack.

SSD vs NVMe

Standard SSD is adequate for light automation. NVMe becomes more useful when PostgreSQL and execution history create frequent reads and writes or when disk latency shows up in measured workflow performance.

Measure before upgrading

Use CPU, memory, disk growth and execution duration under peak overlap to decide whether the bottleneck is compute, memory or storage rather than assuming a larger VPS fixes every slowdown.

FAQ

n8n VPS requirements: common questions

How much RAM does n8n need?

There is no universal figure. RAM demand changes with concurrency, payload size, execution behavior and the supporting services on the VPS. A 4 GB server is a practical small-production starting class, not a guaranteed requirement for every workload.

How many CPU cores should I use?

Light workloads can start with a small CPU allocation. Add cores when monitoring shows sustained CPU pressure or slower executions under concurrency rather than sizing from workflow count alone.

Does n8n require PostgreSQL?

Small deployments can use SQLite, but PostgreSQL is the stronger production-oriented choice as operational requirements and concurrency increase.

When is Redis required?

Redis is associated with queue mode. A normal single-instance deployment does not need Redis simply because it runs on a VPS.

How much disk space should I reserve?

Disk demand depends on PostgreSQL growth, retained execution history, binary data, logs, container layers and backups. Monitor growth and leave headroom instead of relying on a fixed universal number.
