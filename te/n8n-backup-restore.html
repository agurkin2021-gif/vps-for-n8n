n8n బ్యాకప్ మరియు పునరుద్ధరణ

స్వీయ-హోస్ట్ చేసిన n8n ని బ్యాకప్ చేయడానికి మరియు పునరుద్ధరించడానికి, మీ SQLite డేటాబేస్ లేదా స్థిరమైన PostgreSQL డంప్, నిరంతర .n8n ఫోల్డర్ మరియు అసలైన ఎన్‌క్రిప్షన్ కీ, డిప్లాయ్‌మెంట్ కాన్ఫిగరేషన్ మరియు ప్రతి బాహ్య బైనరీ లేదా మౌంటెడ్-ఫైల్ డిపెండెన్సీని రక్షించండి. VPS నుండి ఎన్‌క్రిప్టెడ్ కాపీని ఉంచండి మరియు ప్రత్యేక సందర్భంలో రికవరీని పరీక్షించండి. ఎంపిక రికవరీ కోసం CLI వర్క్‌ఫ్లో మరియు క్రెడెన్షియల్ ఎగుమతులు ఉపయోగించండి; JSON ఎగుమతులు మాత్రమే పూర్తి సర్వర్ బ్యాకప్ కాదు.

n8n బ్యాకప్ దేనిని రక్షించాలి

డేటాబేస్

ఉదాహరణకు ఉపయోగించిన PostgreSQL డేటాబేస్ లేదా SQLite డేటాబేస్ ఫైల్‌ను బ్యాకప్ చేయండి. డేటాబేస్ వర్క్‌ఫ్లోలు, ఆధారాలు మరియు అమలు డేటా వంటి కోర్ n8n స్థితిని కలిగి ఉంది.

ఎన్క్రిప్షన్ కీ

ఖచ్చితమైన n8n ఎన్‌క్రిప్షన్ కీని విడిగా మరియు సురక్షితంగా భద్రపరచండి. పునరుద్ధరించబడిన ఎన్‌క్రిప్టెడ్ ఆధారాలు అదే కీపై ఆధారపడి ఉంటాయి.

శాశ్వతంగా నిల్వ చేసే ఫైళ్లు

స్థిరమైన n8n డేటా డైరెక్టరీ మరియు ఏదైనా మౌంటెడ్ ఫైల్‌లు, బైనరీ-డేటా నిల్వ లేదా మీ విస్తరణ ఆధారపడే వర్క్‌ఫ్లో ఆస్తులను చేర్చండి.

డిప్లాయ్‌మెంట్ కాన్ఫిగరేషన్

స్టాక్‌ను పునర్నిర్మించడానికి అవసరమైన కంపోజ్/కాన్ఫిగరేషన్ ఫైల్‌లు మరియు నాన్-సీక్రెట్ కాన్ఫిగరేషన్‌ను ఉంచండి. తగిన యాక్సెస్ నియంత్రణలతో రహస్యాలను రక్షించండి.

రెండు బ్యాకప్ స్థాయిలు

డేటా ఎక్స్‌పోర్ట్ vs విపత్తు తర్వాత పూర్తి పునరుద్ధరణ

వర్క్‌ఫ్లో & క్రెడెన్షియల్ ఎగుమతి

n8n CLI ఎగుమతులు వలస, సంస్కరణ వర్క్‌ఫ్లో కాపీలు మరియు ఎంపిక చేసిన పునరుద్ధరణకు ఉపయోగపడతాయి. ఆధారాలను గుప్తీకరించిన రూపంలో ఎగుమతి చేయవచ్చు మరియు సరిపోలే ఎన్‌క్రిప్షన్ కీతో తర్వాత దిగుమతి చేసుకోవచ్చు. కేవలం ఒక వర్క్‌ఫ్లోను పునరుద్ధరించడానికి, దాని JSON ని డౌన్‌లోడ్ చేయడానికి వర్క్‌ఫ్లో ఎడిటర్ యొక్క మూడు-చుక్కల మెనుని ఉపయోగించండి, ఆపై ఫైల్ నుండి కొత్త సమీక్ష వర్క్‌ఫ్లో లేదా వివిక్త ఉదాహరణకి దిగుమతి చేయండి. ప్రత్యక్ష వర్క్‌ఫ్లోను భర్తీ చేయడానికి ముందు ఆధారాలు, వర్క్‌ఫ్లో IDలు మరియు నోడ్ పారామితులను తనిఖీ చేయండి: వర్క్‌ఫ్లో JSON ని పునరుద్ధరించడం మొత్తం సర్వర్‌ను పునరుద్ధరించదు.

ఎంటిటీ ఎగుమతి

మద్దతు ఉన్న డేటాబేస్ రకాల మధ్య డేటాను తరలించడానికి CLI డేటాబేస్ ఎంటిటీలను ఎగుమతి చేయగలదు. అమలు-చరిత్ర పట్టికలు ఐచ్ఛికం ఎందుకంటే అవి చాలా పెద్దవిగా ఉంటాయి.

మొత్తం n8n ఇన్‌స్టాన్స్ పునరుద్ధరణ

డెడ్-సర్వర్ దృష్టాంతం కోసం, వాస్తవ డేటాబేస్, ఎన్‌క్రిప్షన్ కీ, నిరంతర డేటా మరియు డిప్లాయ్‌మెంట్ డిపెండెన్సీలను రక్షించండి. వర్క్‌ఫ్లో JSON ఎగుమతి మొత్తం ఉదాహరణను పునర్నిర్మించిందని అనుకోవద్దు.

ప్రొవైడర్ స్నాప్‌షాట్

ఒక VPS స్నాప్‌షాట్ అదనపు పునరుద్ధరణ లేయర్‌గా ఉపయోగపడుతుంది, అయితే ఇది మాత్రమే కాపీ కాకూడదు మరియు స్వతంత్రంగా ధృవీకరించబడిన అప్లికేషన్/డేటాబేస్ బ్యాకప్‌ను భర్తీ చేయకూడదు.

డేటాబేస్

డేటాబేస్‌కు సుసంగతమైన బ్యాకప్ తీసుకోండి

PostgreSQL

స్థిరమైన PostgreSQL బ్యాకప్ పద్ధతిని ఉపయోగించండి మరియు ఫలితంగా బ్యాకప్‌ను VPS కి దూరంగా నిల్వ చేయండి. అదే విఫలమైన డిస్క్‌లోని డేటాబేస్ కాపీ విపత్తు రికవరీ కాదు.

SQLite

విస్తరణ SQLite ని ఉపయోగిస్తుంటే, నిరంతర n8n డేటా డైరెక్టరీ నుండి డేటాబేస్ ఫైల్‌ను రక్షించండి. డేటాబేస్ సక్రియంగా సవరించబడుతున్నప్పుడు అసురక్షిత స్థితిలో కాపీ చేయడాన్ని నివారించండి.

అమలు చరిత్ర

హిస్టారికల్ ఎగ్జిక్యూషన్ డేటా మీ పునరుద్ధరణ లక్ష్యంలో భాగమేనా అని నిర్ణయించుకోండి. ఇది బ్యాకప్‌లను గణనీయంగా పెద్దదిగా చేస్తుంది, కాబట్టి నిలుపుదల మరియు సమ్మతి అవసరాలు ఎంపికను నడిపించాలి.

డేటాబేస్ వెర్షన్

సోర్స్ డిప్లాయ్‌మెంట్ ఉపయోగించే డేటాబేస్ ఇంజిన్ మరియు వెర్షన్‌ను రికార్డ్ చేయండి, తద్వారా రికవరీ వాతావరణం అనుకూలంగా తయారు చేయబడుతుంది.

Docker కంపోజ్ VPS పై PostgreSQL. PostgreSQL సేవ పేరు పెట్టబడితే postgres మరియు దాని డేటాబేస్/యూజర్ రెండూ n8n, కింది ఆదేశం హోస్ట్‌పై స్థిరమైన PostgreSQL అనుకూల-ఫార్మాట్ డంప్‌ను సృష్టిస్తుంది. మీ అసలు కంపోజ్ ఫైల్‌ని అమలు చేయడానికి ముందు దాన్ని తనిఖీ చేయండి మరియు డేటాబేస్ ఆధారాలు మరియు సేవా పేర్లను సర్దుబాటు చేయండి. pg_dump PostgreSQL నడుస్తున్నప్పుడు తార్కికంగా స్థిరమైన స్నాప్‌షాట్‌ను ఉత్పత్తి చేయగలదు; అది చేస్తుంది కాదు విడిగా బ్యాకప్ చేయండి .n8n వినియోగదారు ఫోల్డర్ లేదా బాహ్య బైనరీ డేటా.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

ఆర్కైవ్-జాబితా తనిఖీ స్పష్టమైన ఫార్మాట్ సమస్యలను క్యాచ్ చేస్తుంది కానీ డేటా పునరుద్ధరించబడుతుందని నిరూపించలేదు. గుప్తీకరించిన కాపీని ఆఫ్-సర్వర్‌ని నిల్వ చేయండి మరియు పునరుద్ధరణను రిహార్సల్ చేయండి. డేటాబేస్-నిర్దిష్ట ఎంపికల కోసం అధికారిక PostgreSQL pg_dump డాక్యుమెంటేషన్ ఉపయోగించండి.

Docker లో SQLite. డిఫాల్ట్ SQLite విస్తరణ కోసం, database.sqlite మరియు ఉత్పత్తి చేయబడిన ఎన్‌క్రిప్షన్-కీ కాన్ఫిగర్ పర్‌సిస్టెంట్‌లో ప్రత్యక్షంగా ఉంటుంది .n8n ఫోల్డర్ (సాధారణంగా మౌంట్ /home/node/.n8n) SQLite యొక్క సాధారణ ప్రత్యక్ష కాపీని ఎప్పుడూ స్థిరంగా పరిగణించవద్దు. ఫోల్డర్‌ను కాపీ చేయడానికి ముందు n8n మరియు ఇతర డేటాబేస్ రైటర్‌లను ఆపివేయండి లేదా అంతరాయం అసాధ్యం అయినప్పుడు SQLite యొక్క మద్దతు ఉన్న ఆన్‌లైన్ బ్యాకప్ మెకానిజంను ఉపయోగించండి:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

ఇవి చూపబడిన సేవ మరియు మార్గం కోసం సచిత్ర ఆదేశాలు, సార్వత్రిక వాల్యూమ్ లేఅవుట్ కాదు. కాపీ చేయబడిన ఫోల్డర్ ప్రారంభంలో అదే VPS లో ఉంది; దానిని సర్వర్ నుండి బదిలీ చేయండి మరియు రక్షించండి. క్యూ వర్కర్లు లేదా ఇతర రచయితలు ఉన్నప్పుడు, వారిని కూడా ఉపశమింపజేసి, వారి వాస్తవ విస్తరణ రూపకల్పనను అనుసరించండి. n8n యొక్క ప్రస్తుత పూర్తి-బ్యాకప్ మార్గదర్శకత్వం SQLite అనుగుణ్యత అవసరాన్ని డాక్యుమెంట్ చేస్తుంది.

డిఫాల్ట్ SQLite ఫోల్డర్‌ని క్లీన్ టార్గెట్‌కి రీస్టోర్ చేస్తోంది: ముందుగా n8n సేవ మరియు అన్ని డేటాబేస్ రైటర్‌లను ఆపండి. ఒకసారి అనుకూలమైన n8n సర్వీస్ కంటైనర్ మరియు దాని డెస్టినేషన్ వాల్యూమ్ ఉనికిలో ఉంటే, బ్యాకప్ చేసిన దాన్ని కాపీ చేయండి .n8n విషయాలు తిరిగి అదే నిరంతర డైరెక్టరీకి. ఇది లక్ష్య ఫైల్‌లను ఓవర్‌రైట్ చేస్తుంది, కాబట్టి మీరు ఉంచాల్సిన డేటాతో దీన్ని అమలు చేయవద్దు:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n

శుభ్రమైన సందర్భంలో, ఆధారాలను దిగుమతి చేసుకునే ముందు యజమాని సెటప్‌ను పూర్తి చేయండి. బహుళ-వినియోగదారు లేదా ప్రాజెక్ట్ పునరుద్ధరణలకు సరైన వినియోగదారు లేదా ప్రాజెక్ట్ అసైన్‌మెంట్ కూడా అవసరం కావచ్చు.

దిగుమతి చేసుకున్న IDలు ఇప్పటికే ఉన్న అంశాలను ఓవర్‌రైట్ చేయగలవు

వర్క్‌ఫ్లో మరియు క్రెడెన్షియల్ ఎగుమతులు వాటి అసలు IDలను భద్రపరుస్తాయి. ఇప్పటికే అదే IDలను కలిగి ఉన్న ఉదాహరణకి దిగుమతి చేయడం వలన ఇప్పటికే ఉన్న ఆ ఐటెమ్‌లను భర్తీ చేయవచ్చు.

దిగుమతి చేసుకున్న వర్క్‌ఫ్లోలను ఉద్దేశపూర్వకంగా ప్రచురించండి

CLI దిగుమతులు సాధారణంగా వర్క్‌ఫ్లోలను క్రియారహితంగా ఉంచుతాయి. n8n 2.xలో, ప్రతి దిగుమతి వర్క్‌ఫ్లో యొక్క ప్రచురించబడిన స్థితిని తనిఖీ చేయండి మరియు మీరు అమలు చేయాలనుకుంటున్న వర్క్‌ఫ్లోలను మాత్రమే ప్రచురించండి; స్వీయ-హోస్ట్ చేసిన సర్వర్ CLI కూడా n8n ప్రచురణకు మద్దతు ఇస్తుంది:workflow --id=YOUR_WORKFLOW_ID. n8n అమలులో ఉన్నప్పుడు, సర్వర్ CLI పబ్లిష్/పబ్లిష్ చేయని స్థితి మార్పులు n8n ని పునఃప్రారంభించిన తర్వాత మాత్రమే అమలులోకి వస్తాయి. షెడ్యూల్ చేయబడిన ట్రిగ్గర్‌లు మరియు ఉత్పత్తి వెబ్‌హుక్‌లను ధృవీకరించడానికి లేదా ట్రాఫిక్‌ను మార్చడానికి ముందు పునఃప్రారంభించండి.

Docker కంపోజ్ కోసం బల్క్ ఎగుమతి ఉదాహరణ: మీ n8n సేవ పేరు పెట్టబడితే n8n, మీరు దిగువ అధికారిక CLI బ్యాకప్‌లను అమలు చేయవచ్చు. అవుట్‌పుట్ మార్గం ఉద్దేశపూర్వకంగా దాని మౌంటెడ్ పెర్సిస్టెంట్‌లో ఉంది .n8n డైరెక్టరీ, ఎందుకంటే కంటైనర్‌లో ఉన్న ఏకపక్ష డైరెక్టరీలు మళ్లీ సృష్టించబడినప్పుడు అదృశ్యం కావచ్చు. డైరెక్టరీని n8n కంటైనర్ వినియోగదారు వ్రాయగలరని నిర్ధారించండి. వర్క్‌ఫ్లో మరియు క్రెడెన్షియల్‌ను JSON లో ఉంచండి ప్రత్యేక డైరెక్టరీలు— n8n రెండు రకాలు డైరెక్టరీని పంచుకున్నప్పుడు దిగుమతి సమస్యను డాక్యుమెంట్ చేస్తుంది.

n8n 2.x డ్రాఫ్ట్ వర్సెస్ ప్రచురించిన బ్యాకప్: ఒక సాధారణ --backup వర్క్‌ఫ్లో ఎగుమతి ప్రస్తుత చిత్తుప్రతులను సంగ్రహిస్తుంది; ఇవి ఉత్పత్తిలో ప్రచురించబడిన సంస్కరణల నుండి భిన్నంగా ఉండవచ్చు. నిర్దిష్ట వర్క్‌ఫ్లో యొక్క వాస్తవ ప్రచురించిన సంస్కరణను సంరక్షించడానికి, దాన్ని ఉపయోగించి విడిగా ఎగుమతి చేయండి docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, అవుట్‌పుట్ ఫోల్డర్ ఉందని మరియు వ్రాయదగినదని నిర్ధారించుకున్న తర్వాత. CLI ఉపయోగించి చారిత్రక సంస్కరణను కూడా ఎగుమతి చేయవచ్చు --version=VERSION_ID. పూర్తి బ్యాకప్‌తో పాటు ఈ క్యాప్చర్‌లను ఆఫ్-సర్వర్‌లో ఉంచండి; డ్రాఫ్ట్ JSON ప్రత్యక్షంగా ప్రచురించబడిన స్థితిని నమోదు చేస్తుందని భావించవద్దు.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

కాపీ చేయబడింది ~/n8n-recovery/cli మీరు దానిని సురక్షితమైన, స్వతంత్ర బ్యాకప్ స్థానానికి తరలించే వరకు డైరెక్టరీ ఇప్పటికీ VPS లో ఉంటుంది. క్రెడెన్షియల్ ఎగుమతి డిఫాల్ట్‌గా గుప్తీకరించబడింది మరియు దిగుమతిపై సరిపోలే ఎన్‌క్రిప్షన్ కీ అవసరం. ఉపయోగించడం మానుకోండి --decrypted ఖచ్చితంగా నియంత్రిత మైగ్రేషన్ మినహా: ఇది సాదాపాఠంలో రహస్యాలను వ్రాస్తుంది. పబ్లిక్ GitHub రిపోజిటరీకి సున్నితమైన వర్క్‌ఫ్లో లాజిక్ లేదా ఆధారాలను కలిగి ఉన్న ఎగుమతులను ఎప్పుడూ చేయవద్దు. కొన్ని మూడవ పక్షం GitHub క్రెడెన్షియల్-బ్యాకప్ టెంప్లేట్‌లు ఉద్దేశపూర్వకంగా డీక్రిప్ట్ చేయబడిన రహస్యాలను ఎగుమతి చేస్తాయి; ప్రైవేట్ రిపోజిటరీ అనేది యాక్సెస్ పరిమితి, ఎన్‌క్రిప్షన్ కాదు. ప్రతి టెంప్లేట్ యొక్క వాస్తవ ఎగుమతి సెట్టింగ్‌లు మరియు నిల్వ అనుమతులను తనిఖీ చేయండి, ఆఫ్-సర్వర్ బదిలీకి ముందు రహస్యాలను ఎన్‌క్రిప్ట్ చేయండి మరియు అనాలోచిత సాదా వచన అప్‌లోడ్ ద్వారా బహిర్గతమయ్యే ఏవైనా ఆధారాలను తిప్పండి.

బల్క్ దిగుమతి ఉదాహరణ: క్లీన్ టార్గెట్‌పై, ఓనర్ సెటప్‌ను పూర్తి చేయండి, అసలు ఎన్‌క్రిప్షన్ కీని అందించండి మరియు సేవ్ చేసిన బ్యాకప్ ఫైల్‌లు ఆ రికవరీ VPS లో అందుబాటులో ఉన్నాయని నిర్ధారించుకోండి. కిందిది డెస్టినేషన్ ఫోల్డర్‌ని సృష్టించి, కాపీ చేస్తుంది workflows/ మరియు credentials/ హోస్ట్ నుండి n8n కంటైనర్‌లోకి సబ్‌ఫోల్డర్‌లు; మీ Docker వాల్యూమ్ లేఅవుట్ భిన్నంగా ఉంటే మార్గాలను స్వీకరించండి:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

n8n కంటైనర్ వినియోగదారు కోసం ఫైల్ యాజమాన్యాన్ని మరియు యాక్సెస్‌ని తనిఖీ చేయండి. ధృవీకరించబడిన రోల్‌బ్యాక్ లేకుండా జనాభా కలిగిన ఉత్పత్తి ఉదాహరణపై దిగుమతి చేయవద్దు: వర్క్‌ఫ్లో మరియు క్రెడెన్షియల్ IDలు ఇప్పటికే ఉన్న ఎంట్రీలను ఓవర్‌రైట్ చేయగలవు. ఆపై అమలు చేయండి:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

దిగుమతి చేసుకున్న IDలు ఇప్పటికే ఉన్న వర్క్‌ఫ్లోలు లేదా ఆధారాలను భర్తీ చేయగలవు; డ్రై రన్‌ల కోసం వివిక్త పరీక్ష ఉదాహరణను ఉపయోగించండి మరియు ఆధారాలు మరియు యాక్టివేషన్/పబ్లిషింగ్ స్టేట్‌లను తనిఖీ చేయండి. n8n 2.xలో, JSON డ్రాఫ్ట్‌ను పునరుద్ధరించడం అనేది వర్క్‌ఫ్లో ప్రచురించబడిందని నిరూపించదు మరియు షెడ్యూల్ చేయబడిన ట్రిగ్గర్‌లను అమలు చేయగలదు. దిగుమతి భద్రత: నాన్-మల్టీ-మెయిన్ n8n ఉదాహరణలో, మునుపు క్రియాశీలంగా ఉన్న క్రాన్ ట్రిగ్గర్‌లు CLI దిగుమతి తర్వాత ఇన్‌స్టాన్స్ పునఃప్రారంభమయ్యే వరకు అమలులో కొనసాగవచ్చు. ఉత్పత్తి ట్రిగ్గర్‌లను ఆపివేయండి లేదా వేరుచేయండి మరియు పునరుద్ధరించబడిన ఉద్యోగాలను ప్రారంభించే ముందు n8n ని పునఃప్రారంభించండి; డూప్లికేట్ ఎగ్జిక్యూషన్ లేదని ధృవీకరించండి. CLI ఎగుమతులు చేస్తాయి కాదు ఒరిజినల్ యూజర్లు, ఎగ్జిక్యూషన్ లాగ్‌లు, ఇన్‌స్టాన్స్ వేరియబుల్స్ లేదా ఎన్‌క్రిప్షన్ కీని కలిగి ఉంటాయి. --backup సెట్లు --all --pretty --separate, 'పూర్తి ఉదాహరణ' కాదు. మూలాధారాలు: ప్రస్తుత అధికారిక n8n బ్యాకప్/పునరుద్ధరణ గైడ్ మరియు n8n CLI కమాండ్ రిఫరెన్స్.

నా దగ్గర డేటాబేస్ ఉంటే n8n ఎన్‌క్రిప్షన్ కీ అవసరమా?
