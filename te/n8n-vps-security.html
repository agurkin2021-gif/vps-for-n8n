ప్రొడక్షన్ భద్రత

VPSలో n8nను సురక్షితంగా ఉంచండి

VPS లో n8n ని భద్రపరచడానికి, పబ్లిక్ ఇంటర్నెట్‌లో n8n (5678), PostgreSQL (5432) మరియు ఐచ్ఛిక Redis (6379)ని ఉంచండి; HTTPS రివర్స్ ప్రాక్సీ, SSH కీలు మరియు MFA ని ఉపయోగించండి, మీ ఎన్‌క్రిప్షన్ కీని భద్రపరచండి, వెబ్‌హూక్‌లను ప్రామాణీకరించండి, ప్రమాదకర వర్క్‌ఫ్లో సామర్థ్యాలను పరిమితం చేయండి మరియు అమలు చేయబడిన ఉదాహరణను ఆడిట్ చేయండి. పబ్లిక్ వెబ్‌హుక్ మార్గాల నుండి విడిగా ఎడిటర్‌ను రక్షించండి. HTTPS మాత్రమే కనెక్ట్ చేయబడిన సేవలను సురక్షితం చేయదు.

n8n కోసం VPS ని ఎంచుకోండి

భాగస్వామి లింక్: మేము కొనుగోళ్ల నుండి కమీషన్ పొందవచ్చు.

త్వరిత తనిఖీ జాబితా

పబ్లిక్ ఎక్స్‌పోజర్‌కు ముందు కనీస భద్రతా బేస్‌లైన్

మీ చేరుకోగల పోర్ట్‌లు, HTTPS, ధృవీకరించబడిన అడ్మినిస్ట్రేటివ్ యాక్సెస్, MFA మరియు సేవ్ చేసిన ఆధారాలతో ప్రారంభించండి. ప్రతి ఇన్‌కమింగ్ వెబ్‌హుక్ సున్నితమైన పనిని ట్రిగ్గర్ చేయడానికి ముందు దానిని ప్రామాణీకరించండి. యాక్సెస్ నియంత్రణలను మార్చిన తర్వాత, ఉద్దేశించిన ఎడిటర్‌లు మరియు బాహ్య ఏకీకరణలు ఇప్పటికీ పని చేస్తున్నాయని ధృవీకరించండి, ఆపై n8n భద్రతా ఆడిట్‌ను అమలు చేయండి.

HTTPS మాత్రమే

సరిగ్గా కాన్ఫిగర్ చేయబడిన TLS రివర్స్ ప్రాక్సీ వెనుక n8n ఉంచండి మరియు ఎడిటర్ మరియు వెబ్‌హుక్స్ కోసం పబ్లిక్ HTTPS URLని స్థిరంగా ఉపయోగించండి.

అవసరమైన పోర్టులనే తెరిచి ఉంచండి

పబ్లిక్ ట్రాఫిక్ కోసం అవసరమైన పోర్టులను మాత్రమే బహిర్గతం చేయండి. PostgreSQL, Redis మరియు అంతర్గత అప్లికేషన్ పోర్ట్‌లను పబ్లిక్ ఇంటర్నెట్ నుండి దూరంగా ఉంచండి.

SSH భద్రతను బలోపేతం చేయండి

కీ-ఆధారిత అడ్మినిస్ట్రేషన్‌ని ఉపయోగించండి, ఎవరు లాగిన్ చేయవచ్చో పరిమితం చేయండి మరియు ఆపరేటింగ్ సిస్టమ్‌ను ప్యాచ్‌గా ఉంచండి.

ఆధారాలను రక్షించండి

n8n ఎన్‌క్రిప్షన్ కీని స్థిరంగా మరియు రహస్యంగా ఉంచండి. పర్యావరణ ఫైల్‌లు, డేటాబేస్ యాక్సెస్ మరియు బ్యాకప్ కాపీలను సున్నితమైన ఆస్తులుగా పరిగణించండి.

నెట్‌వర్క్ ప్రవేశ స్థాయి

రివర్స్ ప్రాక్సీ, HTTPS మరియు విశ్వసనీయ శీర్షికలు

TLS టెర్మినేషన్

HTTPS ని ముగించడానికి Nginx, Caddy లేదా Traefik వంటి రివర్స్ ప్రాక్సీని ఉపయోగించండి. సాదా HTTP ని దారి మళ్లించండి మరియు ప్రాక్సీ ఉద్దేశించిన ఎంట్రీ పాయింట్ అయినప్పుడు నేరుగా n8n అప్లికేషన్ పోర్ట్‌ను బహిర్గతం చేయకుండా ఉండండి.

ప్రాక్సీ కాన్ఫిగరేషన్

n8n రివర్స్ ప్రాక్సీ వెనుక నడుస్తున్నప్పుడు, ప్రాక్సీ హాప్ కౌంట్‌ను సరిగ్గా కాన్ఫిగర్ చేయండి మరియు ఫార్వార్డ్ చేయబడిన హెడర్‌లను పాస్ చేయండి n8n అసలు క్లయింట్ అభ్యర్థనను పునర్నిర్మించాల్సిన అవసరం ఉంది.

సురక్షిత కుకీలు

HTTPS కంటే ఎక్కువ ఎడిటర్‌కు అందించండి, తద్వారా ప్రామాణీకరణ కుక్కీలు సురక్షితంగా ఉంటాయి. కుక్కీ భద్రతను బలహీనపరచడం ద్వారా విరిగిన TLS సెటప్ చుట్టూ పని చేయవద్దు.

Webhook URL

పబ్లిక్ వెబ్‌హుక్ URLను బాహ్యంగా చేరుకోగల HTTPS హోస్ట్ పేరుకు సెట్ చేయండి, తద్వారా ఉత్పత్తి చేయబడిన వెబ్‌హూక్ ఎండ్‌పాయింట్‌లు అంతర్గత కంటైనర్ లేదా HTTP చిరునామాను సూచించవు.

వెబ్‌హుక్స్‌ను విచ్ఛిన్నం చేయకుండా ఎడిటర్‌ను ప్రైవేట్‌గా ఉంచండి. ఆచరణాత్మకంగా ఉన్నప్పుడు VPN, విశ్వసనీయ-IP విధానం లేదా ప్రామాణీకరించబడిన ప్రాక్సీని ఉపయోగించి నిర్వహణ ప్రాప్యతను పరిమితం చేయండి. పబ్లిక్ వెబ్‌హుక్ రిసీవర్‌లు మరియు OAuth కాల్‌బ్యాక్ రూట్‌లు అందుబాటులో ఉండవలసి ఉంటుంది; ప్రాక్సీ నియమాన్ని అమలు చేయడానికి ముందు విశ్వసనీయ ఎడిటర్ సైన్-ఇన్ మరియు నిజమైన బాహ్య కాల్‌బ్యాక్ రెండింటినీ పరీక్షించండి. క్లయింట్-అడ్రస్ హెడర్‌లను విశ్వసనీయ ప్రాక్సీల నుండి మాత్రమే ఫార్వార్డ్ చేయండి, ఏకపక్ష అభ్యర్థన శీర్షికలు కాదు.

వెబ్‌హుక్ కాలర్‌లను ప్రామాణీకరించండి: Webhook నోడ్‌లో పంపినవారు మద్దతు ఇచ్చినప్పుడు ఏదీ లేదు అనే దానికి బదులుగా ప్రాథమిక, హెడర్ లేదా JWT ప్రమాణీకరణను ఎంచుకోండి. దాని ఉపయోగించండి IP(లు) అనుమతి జాబితా సముచితమైన చోట ఎంపిక, మరియు సంతకం చేసిన అభ్యర్థనలకు ఇంటిగ్రేషన్ మద్దతు ఇచ్చే ప్రొవైడర్ సంతకాలను ధృవీకరించండి. ఊహించడం కష్టతరమైన URL తగినంత ప్రమాణీకరణ కాదు. సముచితమైనప్పుడు ప్రాక్సీ వద్ద రేట్ పరిమితులను వర్తింపజేయండి మరియు చెల్లుబాటు అయ్యే బరస్ట్‌లు బ్లాక్ చేయబడలేదని నిర్ధారించండి. అధికారిక Webhook ప్రమాణీకరణ ఎంపికలు.

VPS భద్రతను బలోపేతం చేయండి

సర్వర్‌పై దాడి జరిగే అవకాశాలను తగ్గించండి

ఫైర్‌వాల్

డిఫాల్ట్-అయాచిత ఇన్‌బౌండ్ ట్రాఫిక్‌ను తిరస్కరించండి మరియు తప్పనిసరిగా చేరుకోగల సేవలను మాత్రమే అనుమతించండి. డేటాబేస్ మరియు Redis పోర్ట్‌లు సాధారణంగా ప్రైవేట్/లోకల్ నెట్‌వర్క్‌లకు చెందినవి.

SSH

పాస్‌వర్డ్‌ల కంటే SSH కీలను ఇష్టపడండి, అనవసరమైన లాగిన్ మార్గాలను నిలిపివేయండి మరియు పరిపాలనా ప్రాప్యతను పరిమితం చేయండి. రూట్-సమానమైన యాక్సెస్ కఠినంగా నియంత్రించబడాలి.

OS నవీకరణలు

Linux హోస్ట్ మరియు కంటైనర్ రన్‌టైమ్‌ను ప్యాచ్ చేయండి. అప్లికేషన్ గట్టిపడటం అనేది బహిర్గతమైన లేదా వాడుకలో లేని ఆపరేటింగ్ సిస్టమ్‌ను భర్తీ చేయదు.

కంటైనర్ ఎక్స్పోజర్

హోస్ట్ యాక్సెస్ అవసరమయ్యే పోర్ట్‌లను మాత్రమే ప్రచురించండి. అంతర్గత సేవలు పబ్లిక్ ఇంటర్‌ఫేస్‌ల ద్వారా కాకుండా ప్రైవేట్ Docker నెట్‌వర్క్‌లలో కమ్యూనికేట్ చేయాలి.

ఫైర్‌వాల్ లేదా SSH సెట్టింగ్‌లను మార్చే ముందు తనిఖీ చేయండి: దీనితో లిజనింగ్ పోర్ట్‌లను తనిఖీ చేయండి sudo ss -lntp, Docker ప్రచురణతో docker compose ps ప్రాజెక్ట్ డైరెక్టరీ మరియు హోస్ట్ ఫైర్‌వాల్ పాలసీ నుండి sudo ufw status verbose UFW ఉపయోగించినట్లయితే. పాస్‌వర్డ్ యాక్సెస్‌ని డిసేబుల్ చేసే ముందు ప్రత్యేక సెషన్‌లో మీ వాస్తవ SSH పోర్ట్ మరియు విజయవంతమైన కీ లాగిన్‌ని ధృవీకరించండి. ప్రచురించబడిన Docker పోర్ట్‌లు UFW నియమాలను దాటవేయగలవు; ఫైర్‌వాల్ స్థితి పేజీ మాత్రమే పోర్ట్ 5678 ప్రైవేట్ అని నిరూపించదు. నిజమైన బాహ్య చేరువను తనిఖీ చేయండి. Docker/UFW హెచ్చరిక.

ఆటోమేటిక్ Ubuntu భద్రతా అప్‌డేట్‌లు పనిచేస్తాయని భావించే బదులు వాటిని తనిఖీ చేయండి: తనిఖీ apt-config dump APT::Periodic::Unattended-Upgrade మరియు లాగ్ /var/log/unattended-upgrades/unattended-upgrades.log. గమనింపబడని భద్రతా అప్‌గ్రేడ్‌లు నిలిపివేయబడితే, sudo dpkg-reconfigure unattended-upgrades మద్దతు ఉన్న కాన్ఫిగరేషన్ డైలాగ్‌ను అందిస్తుంది. పని చేసే VPS లో దాన్ని ప్రారంభించే ముందు రీబూట్ మరియు సర్వీస్-రీస్టార్ట్ ప్రవర్తనను సమీక్షించండి. Ubuntu APT నవీకరణలు చేస్తాయి కాదు స్వయంచాలకంగా n8n Docker చిత్రం లేదా ప్రతి మూడవ పక్ష సాఫ్ట్‌వేర్ రిపోజిటరీని నవీకరించండి. Ubuntu ఆటోమేటిక్-నవీకరణ డాక్యుమెంటేషన్.

ఐచ్ఛిక SSH బ్రూట్-ఫోర్స్ పర్యవేక్షణ: Fail2Ban పునరావృత విఫలమైన SSH లాగిన్‌లను గుర్తించగలదు. SSH కోసం ఇన్‌స్టాల్ చేసి, కాన్ఫిగర్ చేసినట్లయితే, దీనితో జైలును ధృవీకరించండి sudo fail2ban-client status sshd మరియు ఇది మీ వాస్తవ SSH ప్రమాణీకరణ లాగ్ లేదా జర్నల్‌ని చదివినట్లు మరియు కాన్ఫిగర్ చేయబడిన పోర్ట్‌తో సరిపోలుతుందని నిర్ధారించండి. ఇది SSH కీలు మరియు నెట్‌వర్క్ పరిమితులను పూర్తి చేస్తుంది; అది వాటిని భర్తీ చేయదు. ముందుగా ఉన్న యాక్సెస్‌ని తనిఖీ చేయకుండా స్థిర SSH పోర్ట్ లేదా నిషేధ నియమాన్ని కాపీ చేయవద్దు. Ubuntu SSH గట్టిపడే మార్గదర్శకత్వం.

డేటాబేస్ మరియు Redis

బ్యాకెండ్ సేవలను ప్రైవేట్‌గా ఉంచండి

సాధారణ Docker కంపోజ్ సెటప్‌లో, PostgreSQL మరియు క్యూ-మోడ్ Redis ని సంబంధిత కంటైనర్‌ల ద్వారా ప్రైవేట్ నెట్‌వర్కింగ్ ద్వారా చేరుకోవాలి, హోస్ట్-ప్రచురించిన పోర్ట్‌లు కాదు. తో ధృవీకరించండి docker compose ps 5432 మరియు 6379 బహిరంగంగా ప్రచురించబడలేదు; VPS/క్లౌడ్ ఫైర్‌వాల్ ఎక్స్‌పోజర్‌ని విడిగా సమీక్షించండి. నెట్‌వర్క్ విధానాలు కనీసం ప్రత్యేక హక్కు డేటాబేస్ ఆధారాలకు ప్రత్యామ్నాయం కావు.

PostgreSQLరిమోట్ యాక్సెస్ స్పష్టంగా అవసరం మరియు స్వతంత్రంగా సురక్షితంగా ఉంటే తప్ప, దానిని ప్రైవేట్ ఇంటర్‌ఫేస్ లేదా కంటైనర్ నెట్‌వర్క్‌కు బంధించండి.
Redisక్యూ-మోడ్ Redis అవస్థాపన, పబ్లిక్ ఎండ్ పాయింట్ కాదు. నెట్‌వర్క్ యాక్సెస్‌ని అవసరమైన n8n భాగాలకు పరిమితం చేయండి.
ఆధారాలుఅనువర్తనానికి అవసరమైన అనుమతులతో మాత్రమే అంకితమైన డేటాబేస్ ఆధారాలను ఉపయోగించండి మరియు వాటిని మూల నియంత్రణ వెలుపల రక్షించండి.
రవాణాడేటాబేస్ ట్రాఫిక్ అవిశ్వసనీయ నెట్‌వర్క్‌లను దాటినప్పుడు, అప్లికేషన్-స్థాయి క్రెడెన్షియల్ ఎన్‌క్రిప్షన్‌పై ఆధారపడకుండా తగిన ఎన్‌క్రిప్టెడ్ రవాణాను ఉపయోగించండి.

n8n రహస్య కీలు

ఎన్‌క్రిప్షన్ కీ మరియు క్రెడెన్షియల్ సరిహద్దును రక్షించండి

ఎన్క్రిప్షన్ కీ

n8n దాని ఎన్‌క్రిప్షన్ కీని ఉపయోగించి నిల్వ చేసిన ఆధారాలను ఎన్‌క్రిప్ట్ చేస్తుంది. రీస్టార్ట్‌లు మరియు వర్కర్లలో ఒకే కీని భద్రపరచండి మరియు సాధారణ అప్లికేషన్ కంటెంట్ నుండి విడిగా రక్షించండి.

ఎన్విరాన్‌మెంట్‌లోని రహస్య విలువలు

పాస్‌వర్డ్‌లు, టోకెన్‌లు లేదా ఎన్‌క్రిప్షన్ కీని పబ్లిక్ రిపోజిటరీకి అప్పగించవద్దు. పర్యావరణ ఫైల్‌లు మరియు విస్తరణ రహస్యాలకు యాక్సెస్‌ని పరిమితం చేయండి.

వినియోగదారు యాక్సెస్

విశ్వసనీయ వినియోగదారులకు మాత్రమే ఎడిటర్ యాక్సెస్ ఇవ్వండి. వర్క్‌ఫ్లోలు సున్నితమైన సిస్టమ్‌లకు కనెక్ట్ చేయగలవు మరియు రహస్యాలను ప్రాసెస్ చేయవచ్చు లేదా శక్తివంతమైన నోడ్‌లను అమలు చేయవచ్చు.

క్రెడెన్షియల్ పరిధి

సాధ్యమైన చోట ఇరుకైన స్కోప్డ్ సేవా ఖాతాలు మరియు API టోకెన్‌లను ఉపయోగించండి. రాజీపడిన వర్క్‌ఫ్లో సంబంధం లేని సిస్టమ్‌లకు స్వయంచాలకంగా విస్తృత యాక్సెస్‌ను పొందకూడదు.

సమీక్షించడానికి n8n కాన్ఫిగరేషన్: N8N_BLOCK_ENV_ACCESS_IN_NODE=true పర్యావరణ విలువలకు కోడ్-నోడ్ మరియు వ్యక్తీకరణ యాక్సెస్ నిరోధిస్తుంది; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true సెట్టింగ్‌ల ఫైల్‌లో యజమాని-మాత్రమే అనుమతులను అభ్యర్థిస్తుంది. ఉంచండి N8N_ENCRYPTION_KEY స్థిరంగా మరియు సురక్షితంగా బ్యాకప్ చేయబడుతుంది: n8n మొదటి స్టార్టప్‌లో యాదృచ్ఛిక కీని సృష్టించగలదు, కానీ దానిని పోగొట్టుకోవడం వలన ఇప్పటికే ఉన్న ఎన్‌క్రిప్టెడ్ ఆధారాలు ఉపయోగించలేనివిగా మారవచ్చు. ఉత్పత్తి ఎన్‌క్రిప్షన్ కీని సాధారణంగా భర్తీ చేయవద్దు; అధికారికంగా మద్దతు ఇచ్చే భ్రమణ విధానాన్ని ఉపయోగించండి. ఎన్విరాన్‌మెంట్ యాక్సెస్‌ను నిరోధించడం వల్ల ఇప్పటికే ఉన్న ఇంటిగ్రేషన్‌లను విచ్ఛిన్నం చేయవచ్చు, కాబట్టి ఉత్పత్తి మార్పులకు ముందు పరీక్షించండి. n8n సెక్యూరిటీ వేరియబుల్ నిర్వచనాలు.

వర్క్‌ఫ్లో ప్రమాదాలు

నోడ్‌లు భద్రతా సరిహద్దును విస్తరించగలవు

స్వీయ-హోస్టింగ్ వర్క్‌ఫ్లోలకు గణనీయమైన శక్తిని ఇస్తుంది. కోడ్ అమలు, షెల్ యాక్సెస్, ఏకపక్ష HTTP అభ్యర్థనలు మరియు థర్డ్-పార్టీ కమ్యూనిటీ నోడ్‌లు ప్రమాదాన్ని పెంచుతాయి. మీకు అవసరం లేని కార్యాచరణను నిలిపివేయండి మరియు వాటిని అమలు చేయడానికి ముందు అవిశ్వసనీయ వర్క్‌ఫ్లో దిగుమతులను సమీక్షించండి.

ఖచ్చితమైన మద్దతు ఉన్న నియంత్రణలను ఉపయోగించండి: కాన్ఫిగర్ చేయండి NODES_EXCLUDE వంటి డిసేబుల్ నోడ్‌ల JSON శ్రేణితో n8n-nodes-base.executeCommand మరియు n8n-nodes-base.readWriteFile, ఉపయోగించకపోతే. కొన్ని హై-రిస్క్ నోడ్‌లు ఇప్పటికే కొత్త వెర్షన్‌లలో డిఫాల్ట్‌గా బ్లాక్ చేయబడ్డాయి; మార్చడానికి ముందు వాస్తవ జాబితాను సమీక్షించండి. అధికారిక నోడ్ మినహాయింపులు.

n8n నుండి 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true అంతర్గత, లూప్‌బ్యాక్ మరియు మెటాడేటా-చిరునామా పరిధులకు అవుట్‌బౌండ్ HTTP అభ్యర్థనల కోసం తనిఖీలను ప్రారంభిస్తుంది. చట్టబద్ధమైన అంతర్గత API వర్క్‌ఫ్లోలు పనిచేయడం ఆగిపోవచ్చు; అవసరమైతే, మీరు నియంత్రించే గమ్యస్థానాలను మాత్రమే తృటిలో అనుమతించండి. నెట్‌వర్క్ విభజనను ప్రాథమిక రక్షణగా ఉంచండి. కోడ్-నోడ్ ఐసోలేషన్ కోసం, బాహ్య టాస్క్ రన్నర్‌లను సమీక్షించండి. SSRF రక్షణ · టాస్క్-రన్నర్ ఐసోలేషన్.

కమ్యూనిటీ నోడ్స్మీరు విశ్వసించే ప్యాకేజీలను మాత్రమే ఇన్‌స్టాల్ చేయండి; అవి మీ n8n వాతావరణంలో అమలు చేస్తాయి.
ప్రమాదకర నోడ్స్వాటి సామర్థ్యాలు ఉద్దేశించిన వర్క్‌ఫ్లో సరిహద్దును అధిగమించినప్పుడు మీ విస్తరణ అవసరం లేని నోడ్‌లను మినహాయించండి.
SSRFవర్క్‌ఫ్లోలు అంతర్గత లేదా మెటాడేటా ముగింపు పాయింట్‌లను చేరుకోలేని చోట n8n యొక్క SSRF రక్షణ మరియు నెట్‌వర్క్ నియంత్రణలను ఉపయోగించండి.
వర్క్‌ఫ్లో దిగుమతులుసక్రియం చేయడానికి ముందు దిగుమతి చేసుకున్న వర్క్‌ఫ్లోలు, ఆధారాలు, వ్యక్తీకరణలు మరియు ఎక్జిక్యూటబుల్ దశలను సమీక్షించండి.

ఆడిట్ మరియు అప్‌డేట్‌లు

భద్రత నిరంతర నిర్వహణ ప్రక్రియ

n8n భద్రతా తనిఖీని అమలు చేయండి

అధికారిక CLI ఆదేశం n8n audit. మీ Docker కంపోజ్ సేవ పేరు ఉంటే n8n, పరుగు docker compose exec -T n8n n8n audit ఆ విస్తరణ డైరెక్టరీలో. ఐదు వర్గాలను సమీక్షించండి: ఉపయోగించని ఆధారాలు, ప్రమాదకర SQL-ప్రశ్న నమూనాలు, ఫైల్-సిస్టమ్ యాక్సెస్, ప్రమాదకర/కమ్యూనిటీ నోడ్‌లు మరియు అసురక్షిత వెబ్‌హుక్‌లు మరియు పాత విడుదలలతో సహా ఉదాహరణ రిస్క్‌లు. సంబంధిత అన్వేషణలను పరిష్కరించండి మరియు మళ్లీ అమలు చేయండి. ఇది చొచ్చుకుపోయే పరీక్ష కాదు. అధికారిక ఆడిట్ గైడ్.

ఉద్దేశపూర్వకంగా నవీకరించండి

భద్రతా పరిష్కారాలను స్వీకరించడానికి తగినంతగా n8n ని ఉంచండి. విడుదల గమనికలను సమీక్షించండి మరియు ఇంటర్నెట్‌ను ఎదుర్కొనే సందర్భాన్ని శాశ్వతంగా పాతిపెట్టకుండా ముఖ్యమైన అప్‌గ్రేడ్‌లను పరీక్షించండి.

మానిటర్ ప్రమాణీకరణ

ఊహించని యాక్సెస్ నమూనాలు, వర్క్‌ఫ్లో మార్పులు మరియు వైఫల్యాలను చూడండి. మీ ఆపరేటింగ్ మోడల్‌కు విస్తృత పబ్లిక్ రీచ్‌బిలిటీ అవసరం లేనప్పుడు ఎడిటర్ UIని మరింత పరిమితం చేయండి.

రోల్‌బ్యాక్ మరియు రికవరీని సిద్ధం చేయండి

ముఖ్యమైన అప్‌గ్రేడ్‌లకు ముందు తిరిగి పొందగలిగే బ్యాకప్‌లను తీసుకోండి. వివరణాత్మక బ్యాకప్ పరిధి మరియు పునరుద్ధరణ ప్రత్యేక రికవరీ గైడ్‌కు చెందినవి.

సెన్సిటివ్ ఎగ్జిక్యూషన్ హిస్టరీని కనిష్టీకరించండి: విజయవంతమైన పరుగులు కస్టమర్ డేటా మరియు టోకెన్‌లను కొనసాగించగలవు. తగిన సెట్ చేసినప్పుడు EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, ఉంచండి EXECUTIONS_DATA_PRUNE=true, మరియు ఒక ఎంచుకోండి EXECUTIONS_DATA_MAX_AGE వంటి గంటలలో 168 (ఏడు రోజులు). ఇవి కాన్ఫిగర్ చేయదగిన ఉదాహరణలు, చట్టపరమైన నిలుపుదల నియమాలు కాదు. తక్కువ చరిత్ర అంటే తక్కువ డీబగ్గింగ్ మరియు ఫోరెన్సిక్ డేటా; రన్నింగ్, వెయిటింగ్ లేదా ఉల్లేఖన అమలులు ఒకే విధంగా కత్తిరించబడకపోవచ్చు. అధికారిక అమలు నిలుపుదల.

అనుమానిత రాజీ: సాక్ష్యాలను నాశనం చేయకుండా హానికరమైన యాక్సెస్‌ను పరిమితం చేయండి, ప్రాక్సీ, హోస్ట్ మరియు n8n కార్యాచరణ మరియు మార్చబడిన వర్క్‌ఫ్లోలను తనిఖీ చేయండి, బహుశా బహిర్గతమైన అప్‌స్ట్రీమ్ ఆధారాలను రద్దు చేయండి లేదా తిప్పండి, కారణాన్ని పాచ్ చేయండి మరియు అవసరమైనప్పుడు పరీక్షించబడిన తిరిగి పొందగలిగే బ్యాకప్‌ల నుండి మాత్రమే పునరుద్ధరించండి. ప్రభావిత వెబ్‌హుక్ URLలు, ఎడిటర్ ఖాతాలు మరియు కనెక్ట్ చేయబడిన సేవలను సమీక్షించండి; HTTPS, స్నాప్‌షాట్‌లు లేదా VPS కొనుగోలు సంఘటన-ప్రతిస్పందన సేవలను అందజేస్తాయని భావించవద్దు.

డిప్లాయ్‌మెంట్ క్రమం

ప్రొడక్షన్ వర్క్‌ఫ్లోలను యాక్టివేట్ చేయడానికి ముందు స్టాక్‌ను భద్రపరచండి

1VPS ని ప్యాచ్ చేయండి, నియంత్రిత అడ్మినిస్ట్రేటివ్ యాక్సెస్‌ని సృష్టించండి మరియు ఫైర్‌వాల్‌ను కాన్ఫిగర్ చేయండి.
2ప్రైవేట్ కంటైనర్/నెట్‌వర్క్ సరిహద్దులపై n8n మరియు PostgreSQL ని అమలు చేయండి.
3ఆధారాలను నిల్వ చేయడానికి ముందు ఎన్‌క్రిప్షన్ కీ మరియు విస్తరణ రహస్యాలను కాన్ఫిగర్ చేయండి.
4రివర్స్ ప్రాక్సీ, HTTPS, పబ్లిక్ హోస్ట్ పేరు, ఫార్వార్డ్ చేసిన హెడర్‌లు మరియు వెబ్‌హుక్ URLని జోడించండి.
5వినియోగదారులు, నోడ్‌లు మరియు నెట్‌వర్క్ రీచ్‌బిలిటీని వర్క్‌ఫ్లోలు వాస్తవానికి అవసరమైన వాటికి పరిమితం చేయండి.
6భద్రతా ఆడిట్‌ను అమలు చేయండి, బ్యాకప్‌లను ధృవీకరించండి, ఆపై ఉత్పత్తి వర్క్‌ఫ్లోలను బహిర్గతం చేయండి.
తాజా సురక్షిత విస్తరణ కోసం VPS ని ఎంచుకోండి

భాగస్వామి లింక్: మేము కొనుగోళ్ల నుండి కమీషన్ పొందవచ్చు.

బలమైన లాగిన్ రక్షణ అవసరం

ఎడిటర్ ఖాతాల కోసం రెండు-కారకాల ప్రామాణీకరణను ప్రారంభించండి మరియు మీ ఎడిషన్ కేంద్రీకృత విధాన అమలుకు మద్దతు ఇచ్చినప్పుడు n8n భద్రతా విధానాల ద్వారా MFA ని అమలు చేయండి.

వర్క్‌ఫ్లోలను సవరించగల వారిని పరిమితం చేయండి

ఎడిటర్ యాక్సెస్ అనేది ప్రివిలేజ్డ్ యాక్సెస్: వర్క్‌ఫ్లోలు ఆధారాలను చదవగలవు, అంతర్గత సిస్టమ్‌లకు కాల్ చేయగలవు మరియు శక్తివంతమైన నోడ్‌లను అమలు చేయగలవు. వినియోగదారు ప్రాప్యతను ఇరుకైనదిగా ఉంచండి మరియు ఇకపై అవసరం లేని ఖాతాలను తీసివేయండి.

మీరు ఉపయోగించని సామర్థ్యాలను నిలిపివేయండి

పబ్లిక్ API అనవసరమైనప్పుడు దాన్ని నిలిపివేయడం ద్వారా మరియు మీ ఆపరేటింగ్ మోడల్‌కు అవసరం లేని హై-రిస్క్ నోడ్‌లు లేదా ఫీచర్‌లను బ్లాక్ చేయడం ద్వారా అప్లికేషన్ దాడి ఉపరితలాన్ని తగ్గించండి.

SSRF మరియు రహస్య నియంత్రణలను ఉద్దేశపూర్వకంగా ఉపయోగించండి

ఏకపక్ష HTTP అభ్యర్థనలను చేయగల వర్క్‌ఫ్లోల కోసం, n8n యొక్క SSRF రక్షణను మూల్యాంకనం చేయండి మరియు వర్క్‌ఫ్లో కోడ్, పబ్లిక్ రిపోజిటరీలు మరియు విస్తృతంగా చదవగలిగే ఎన్విరాన్‌మెంట్ ఫైల్‌ల నుండి రహస్యాలను ఉంచండి.

ఉపయోగించని నిర్వహణ ముగింపు పాయింట్లను పరిమితం చేయండి: N8N_PUBLIC_API_DISABLED=true n8n పబ్లిక్ REST API ని నిలిపివేస్తుంది మరియు N8N_PUBLIC_API_SWAGGERUI_DISABLED=true దాని API ప్లేగ్రౌండ్‌ని విడిగా నిలిపివేస్తుంది. మీ ఇంటిగ్రేషన్‌లకు ఆ లక్షణాలు అవసరం లేనప్పుడు మాత్రమే దీన్ని చేయండి. REST API ని నిలిపివేయడం వలన వర్క్‌ఫ్లో వెబ్‌హుక్ URLలు ప్రమాణీకరించబడవు. ఎడిటర్ వినియోగదారుల కోసం MFA ని ఉపయోగించండి మరియు మీ n8n ఎడిషన్ వారికి మద్దతు ఇచ్చే కేంద్రీకృత విధానాలను మాత్రమే ఉపయోగించండి.

అధికారిక డాక్యుమెంటేషన్: పబ్లిక్ API ని నిలిపివేయండి · భద్రతా విధాన వేరియబుల్స్ · ఆడిట్ ఆదేశాలు.

తరచుగా అడిగే ప్రశ్నలు

n8n VPS భద్రత: సాధారణ ప్రశ్నలు

n8n పోర్ట్ నేరుగా బహిర్గతం చేయాలా?

రివర్స్ ప్రాక్సీ పబ్లిక్ ఎంట్రీ పాయింట్ అయినప్పుడు, అనవసరమైన సేవలను విస్తృతంగా ప్రచురించడం కంటే ప్రాక్సీని బహిర్గతం చేయండి మరియు అప్లికేషన్ పోర్ట్‌ను దాని వెనుక ఉంచండి.

PostgreSQL లేదా Redis పబ్లిక్‌గా ఉండాలా?

సాధారణంగా లేదు. వాటిని అవసరమైన వ్యవస్థల ద్వారా మాత్రమే చేరుకోవాలి. పబ్లిక్ ఎక్స్పోజర్ సాధారణ n8n ఆపరేషన్‌కు సహాయం చేయకుండా దాడి ఉపరితలాన్ని పెంచుతుంది.

n8n ఎన్‌క్రిప్షన్ కీ ఎందుకు ముఖ్యమైనది?

ఇది n8n ద్వారా నిల్వ చేయబడిన ఆధారాలను రక్షిస్తుంది మరియు విస్తరణ అంతటా స్థిరంగా ఉండాలి. దాన్ని పోగొట్టుకోవడం వలన రికవర్ చేసిన డేటా ఉపయోగించదగిన ఎన్‌క్రిప్టెడ్ ఆధారాలను అందించకుండా నిరోధించవచ్చు.

కమ్యూనిటీ నోడ్‌లు సురక్షితంగా ఉన్నాయా?

వారు థర్డ్-పార్టీ కోడ్‌తో n8n ని పొడిగిస్తారు, కాబట్టి వాటిని వారి స్వంత సరఫరా-గొలుసు మరియు ప్రత్యేక హక్కులతో కూడిన సాఫ్ట్‌వేర్ డిపెండెన్సీలుగా పరిగణించాలి. మీరు విశ్వసించే మరియు అవసరమైన వాటిని మాత్రమే ఇన్‌స్టాల్ చేయండి.

HTTPS స్వీయ-హోస్ట్ చేసిన n8n ఉదాహరణను సురక్షితంగా చేస్తుందా?
