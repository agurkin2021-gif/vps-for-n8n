МАСШТАБТАУ

n8n Queue Mode

Queue mode жұмыс процестерін орындауды негізгі n8n процесінен бөледі. Негізгі инстанс триггерлерді қабылдап, орындалуларды жасайды, Redis кезекті үйлестіреді, worker-лер тапсырмаларды орындайды, ал PostgreSQL ортақ жұмыс процесі мен орындалу деректерін сақтайды.

ҚЫСҚА ШЕШІМ

Сізге queue mode шынымен қажет пе?

Қалыпты режимде қалыңыз, егер

Бір инстанс ең жоғары жүктемені еркін көтеріп, CPU, RAM және орындалу кідірісі тұрақты болса. Queue mode әзірге қажет емес қосымша компоненттерді енгізеді.

Queue mode қарастырыңыз, егер

Ұзақ параллель орындалу ресурстарға талас тудырса, жүктеме кезінде орындалу кідірісі өссе немесе бірнеше worker іске қосып орындау қуатын арттыру қажет болса.

Алдымен вертикалды масштабтаңыз, егер

Тар орын тек CPU немесе RAM жетіспеуі болса және бір үлкенірек инстанс жүктемені әлі де қалыпты көтере алса.

Архитектураны өзгертпес бұрын өлшеңіз

Queue mode-қа көшудің қажеттілігін ең жоғары бір мезгілдегі орындалу, CPU, RAM, орындалу ұзақтығы, кезек тереңдігі және дерекқор жүктемесі арқылы негіздеңіз.

АРХИТЕКТУРА

n8n queue mode қалай жұмыс істейді

1 · MainТаймерлерді, вебхуктарды және жұмыс процесі сұрауларын қабылдап, өндірістік орындалуды өзі орындаудың орнына орындалуды жасайды.
2 · RedisХабарлама брокері ретінде жұмыс істейді. Келесі бос worker тапсырманы алу үшін күтіп тұрған орындалу хабарламаларын сақтайды.
3 · WorkerОрындалу ID-ін қабылдап, ортақ дерекқордан жұмыс процесінің деректерін жүктейді, жұмыс процесін орындайды және нәтижені қайта жазады.
4 · PostgreSQLОртақ тұрақты жұмыс процесі және орындалу деректерін сақтайды. Таратылған queue mode SQLite арқылы қолдау көрсетілмейді.

НЕГІЗГІ ТАЛАПТАР

Әр queue mode орнатуына не қажет

Redis

Main және барлық worker процестері кезекті үйлестіруге арналған Redis сервисіне сенімді қол жеткізе алуы тиіс.

PostgreSQL

Main мен worker-лер ортақ дерекқорды пайдалануы керек. Queue mode — таратылған архитектура, сондықтан оны SQLite негізінде құруға болмайды.

Сәйкес n8n конфигурациясы

Main мен worker-лер queue mode-та жұмыс істеп, Redis, PostgreSQL және шифрланған тіркелгі деректеріне қол жеткізу үшін бірдей қажетті конфигурацияны қолдануы тиіс.

Worker ресурстары

Worker-лер орындайтын жұмыс процестеріне жеткілікті CPU және RAM қажет. Процестер санын көбейту әр орындалудың ресурс құнын жоймайды.

Бар self-hosted стекке queue mode қосыңыз. Алдымен n8n main сервисі мен әр worker бір PostgreSQL дерекқоры мен Redis-ке жеке желі арқылы қол жеткізе алатынын тексеріңіз. Main мен барлық worker-де EXECUTIONS_MODE=queue орнатыңыз. Егер Compose сервисіңіздің атауы redis болса, QUEUE_BULL_REDIS_HOST=redis және QUEUE_BULL_REDIS_PORT=6379 мәндерін беріңіз. Әр процесте DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres және сәйкес DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER, DB_POSTGRESDB_PASSWORD параметрлерін қолданыңыз; мысалдағы сервис атауларын өз жобаңызға сәйкестендіріңіз. Барлық процеске қолданыстағы дәл N8N_ENCRYPTION_KEY кілті берілуі тиіс. Бір Compose желісіндегі контейнерлерді байланыстыру үшін Redis немесе PostgreSQL хост порттарын интернетке жарияламаңыз.

Екінші редакторды емес, орындаушы worker-ді іске қосыңыз. Main сервисіндегі бекітілген n8n image нұсқасы мен ортақ параметрлерді пайдаланатын n8n worker сервисін қосып, оны worker командасымен іске қосыңыз. Егер сервис n8n-worker деп аталса, docker compose up -d n8n-worker командасын пайдаланыңыз. Бір worker нақты тапсырма орындағанын растағаннан кейін сол сервистен екінші worker іске қосу үшін docker compose up -d --scale n8n-worker=2 командасын қолдануға болады. Бұл — дұрыс бапталған қолданыстағы Compose стекке қосымша; жеке орнату файлы емес. Қолданыстағы тұрақты volume-дарды, HTTPS проксиін, құпия мәндерді және резервтік көшірмелерді сақтаңыз.

Қолданыстағы стекке арналған queue mode Compose фрагменті. Төмендегі мысалды қолданыстағы compose.yaml файлына біріктіріңіз; бұл толық жеке орнату емес. Мысал сізде persistent әрі жеке postgres және n8n сервистері, environment ішінде бекітілген N8N_VERSION, қорғалған POSTGRES_PASSWORD және бастапқы N8N_ENCRYPTION_KEY бар деп есептейді. Атауларды, volume-дарды, дерекқорды және n8n нұсқасын қолданыстағы жобаға сәйкестендіріңіз. Жоғарыда көрсетілгендей queue mode Redis параметрлері мен EXECUTIONS_MODE=queue мәнін қолданыстағы main сервисіне де қосыңыз.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Бұл фрагментте Redis немесе worker үшін хост порты жарияланбайды. Redis append-only persistence — қосымша қалпына келтіру қабаты, бірақ серверден тыс резервтік көшірмені алмастырмайды. Қолданыстағы HTTPS және аутентификация конфигурациясын өзгертпеңіз. Сыртқы task runner қажет ететін Code node-тар үшін runner процестерін worker орнатуына бөлек баптаңыз; queue mode task runner-ді алмастырмайды.

Қолданыстағы SQLite инстансын ауыстырып жатырсыз ба? DB_TYPE мәнін ғана өзгертіп, бос PostgreSQL дерекқорымен іске қоспаңыз: бұл ескі жұмыс процестері мен тіркелгі деректерін көшірмейді. Көшу алдында бастапқы дерекқордың, persistent .n8n бумасының және бастапқы шифрлау кілтінің резервтік көшірмесін жасаңыз. n8n қолдайтын экспорт/импорт немесе миграция процедурасын пайдаланып, кейін жұмыс процестері мен шифрланған тіркелгі деректерін бөлек мақсатты ортада тексеріңіз. Кері қайтару үшін бастапқы файлдарды сақтап, қалпына келтіруге дайындық үшін төмендегі резервтік көшіру және қалпына келтіру нұсқаулығын пайдаланыңыз. database.sqlite файлын «миграцияның қысқа жолы» ретінде ешқашан өшірмеңіз.

WORKER ПАРАЛЛЕЛЬДІГІ

Worker-лер саны бойынша да, әр worker-дегі тапсырма саны бойынша да масштабталады

Әр worker бірнеше тапсырманы бір мезгілде орындай алады. n8n-нің қазіргі әдепкі worker параллельдігі мәні 10, ал құжаттама 5 немесе одан жоғары параллельдік мәнін ұсынады. Өте төмен параллельдік пен көп worker қажетсіз дерекқор қосылымдарын жасап, қосылым пулын тауысып жіберуі мүмкін.

Параллельдікті арттырыңыз, егер

Worker-де бос CPU және RAM болса, ал жұмыс процестері есептеу қуатын немесе жадты толық жүктеудің орнына көбіне сыртқы сервистерді күтсе.

Worker қосыңыз, егер

Бір worker процесі тар орынға айналса және дерекқор, Redis пен инфрақұрылым көбірек параллель орындалуға жеткілікті ресурсқа ие болса.

Параллельдікті азайтыңыз, егер

Жеке жұмыс процестері жадты немесе CPU-ды көп пайдаланса және параллель тапсырмалар ресурстарға талас, OOM қысымы немесе тұрақсыз орындалу уақытын тудырса.

PostgreSQL-ді бақылаңыз

Worker саны мен параллельдік өскен сайын дерекқор белсенділігі де артады. Дерекқор қуатын өсірмей орындау қуатын масштабтау тар орынды жоюдың орнына басқа жерге ауыстыруы мүмкін.

Қай параллельдік лимиті нақты қолданылатынын біліңіз. Worker мына командамен іске қосыла алады: n8n worker --concurrency=5, немесе Compose сервисіңіздегі соған тең worker командасымен. Егер N8N_CONCURRENCY_PRODUCTION_LIMIT мәні -1мәнінен басқа нақты мәнге орнатылса, queue mode-та сол параметр басым болады; әйтпесе n8n worker-дің --concurrency мәнін немесе әдепкі 10 мәнін пайдаланады. Worker санын номиналды әдепкі параллельдікке көбейтіп, оны кепілдендірілген өткізу қабілеті деп есептемеңіз: нақты нақты қуат тапсырма ұзақтығына, CPU, жад, сыртқы API және PostgreSQL қосылым санына байланысты.

WEBHOOK-ТАР

Queue mode орындалуды worker-ге беруге байланысты кідірісті қосуы мүмкін

Main немесе webhook процесі HTTP сұрауын қабылдайды, бірақ жұмыс процесін worker орындайды. Орындалуды Redis арқылы worker-ге беру қосымша кідіріс енгізеді. Кідіріске сезімтал вебхуктар үшін worker санын көбейту әр сұрауды автоматты түрде жылдамдатады деп есептемей, сұраудан жауапқа дейінгі толық уақытты өлшеңіз.

ҚабылдауMain/webhook процесі сұрауды қабылдайды.
КезекОрындалу Redis-ке беріледі.
ОрындауБос worker жұмыс процесін орындайды.
Жауап беруҚажет кезде нәтиже кезек жолы арқылы кері жеткізіледі.

Вебхук трафигін дұрыс процеске бағыттаңыз. Арнайы n8n webhook процестері кері прокси немесе load balancer артында тұрса, өндірістік /webhook/* және /webhook-waiting/* жолдарын вебхук процессорларына бағыттаңыз; ал /webhook-test/*, редактор және API сұрауларын main-да қалдырыңыз. Қосымша жүктемені әдейі қабылдамасаңыз, main-ды өндірістік вебхук load-balancing пулына қоспаңыз. Respond to Webhook node-ы worker аяқтап, жауап қайтарғанша клиентті күттіріп қоюы мүмкін, сондықтан queue mode лезде HTTP жауап немесе timeout болмайды деген кепілдік бермейді. Трафикті ауыстырмас бұрын нақты сыртқы callback пен жауап беру тәртібін тексеріңіз.

БИНАРЛЫҚ ДЕРЕКТЕР

Ортақ сақтау орнын елемеңіз

Файлдық жүйе шектеуі

Queue mode таратылған worker-лер үшін ортақ тұрақты сақтау моделі ретінде файлдық жүйедегі бинарлық деректерді сақтауды қолдамайды.

Сыртқы бинарлық деректер сақтау орны

Жұмыс процестері бинарлық деректерді таратылған worker-лер арасында сақтауы керек болса, барлық қажетті инстанс қол жеткізе алатын сақтау архитектурасын қолданыңыз, мысалы қолдау көрсетілетін сыртқы объектілік сақтау орнын.

Үлкен вебхук жауаптары

Worker-ден вебхук жауаптары қабылдаушы процеске кері өтеді. Үлкен жауап денесі Redis жад қысымын арттырып, жауаптарды сақтауды арнайы баптауды қажет етуі мүмкін.

Worker-лерді таратпас бұрын жоспарлаңыз

Жергілікті файлдарға қатты тәуелді жүктеме worker-лер бірнеше машинаға таратылмай тұрып ортақ тұрақты сақтау үшін қайта жобалануы тиіс.

Үлкен вебхук жауаптарының шегі. Қазіргі n8n құжаттамасында worker жауабы queue арқылы кері жіберілген кезде N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX параметрінің әдепкі мәні 64 MiB екені көрсетілген. Redis бір уақытта бірнеше көшірмені ұстай алады, сондықтан әр бір мезгілдегі үлкен жауап үшін Redis жадында жауап көлемінің шамамен 1.5 есесін жоспарлаңыз. Offload қолданылмаса, тым үлкен жауап worker қосқаннан автоматты түрде жылдамдамайды, керісінше сәтсіз аяқталады.

Нұсқа және лицензия шектеулері. n8n 2.34.0 нұсқасынан бастап worker-лер N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true арқылы тым үлкен вебхук жауаптарының денесін оқылатын ортақ бинарлық сақтау орнына бөлек сақтауға жібере алады, бірақ алдымен барлық main және webhook процессорларын 2.34.0 немесе одан кейінгі нұсқаға жаңартыңыз. Таңдалған N8N_DEFAULT_BINARY_DATA_MODE нақты деректерді сақтап, барлық қатысушы процесс оқи алуы тиіс. Сыртқы S3 және Azure бинарлық сақтау орындарын пайдалану үшін жарамды self-hosted Business немесе Enterprise лицензиясы қажет; Community Edition бұл мүмкіндікті береді деп есептемеңіз. database binary mode режимі ақылы сыртқы сақтау орнын қолданбай-ақ тым үлкен жауапты бөлек сақтауға жібере алады, бірақ main инстанс сақталған жауап денесін толық жадқа жүктейді және дерекқор сақтау орнының өз файл көлемі шегі бар. Жауап денесін бөлек сақтауға жіберу үшін, n8n барлық инстанс бір дискіні mount еткен жағдайда ортақ filesystem опциясын да сипаттайды, бірақ бұл конфигурацияны нақты ұсынбайды. Осы арнайы offload жолын таратылған queue mode орнатуында filesystem негізіндегі тұрақты бинарлық деректер қолдауы деп шатастырмаңыз. Offload қоспас бұрын n8n нұсқасын, лицензияны және сақтау конфигурациясын тексеріңіз.

МОНИТОРИНГ

Кезек шынымен көмектесіп жатқанын біліңіз

Кезек тереңдігі

Worker-лер өңдегеннен жылдам өсетін кезек орындау қуаты жетіспейтінін немесе төменгі деңгейдегі тар орын бар екенін көрсетеді.

Worker CPU және RAM

Әр worker үшін жүктелу деңгейі мен жад шыңдарын өлшеңіз. Кезек өсіп тұрса, ал worker бос болса, шектеу басқа жерде.

Орындалу кідірісі

Тек жұмыс процесінің орындалу уақытын емес, орындалу құрылған сәт пен нақты басталған сәт арасындағы кідірісті бақылаңыз.

Күйді тексеру

Worker күйін тексеру endpoint-тері worker жұмыс істеп тұрғанын және дерекқор мен Redis қосылымдары дайын екенін көрсете алады.

Тек жасыл контейнерді емес, worker-де нақты орындалуды тексеріңіз. Дұрыс бапталған Compose стекінде docker compose ps және docker compose logs --tail=100 n8n-worker командаларын тексеріңіз (сервис атауы өзгеше болса, ауыстырыңыз). Зиянсыз жарияланған өндірістік жұмыс процесін жоспарланған триггер немесе тест вебхук арқылы іске қосып, n8n-нің Executions бөліміндегі орындалуды worker логтарындағы нақты өңдеумен салыстырыңыз. Редактордың ашылуы, Redis контейнерінің жұмыс істеуі немесе орындалудың кезекке қойылуы worker тапсырманы шынымен орындады дегенді білдірмейді.

Тәуелділіктер мен дайындық күйін тексеріңіз. Мысалдағы әдепкі сервис атауларымен docker compose exec -T redis redis-cli ping командасы Redis аутентификациясы рұқсат етсе PONG жауабын алуы тиіс. docker compose exec -T postgres pg_isready -U n8n -d n8n PostgreSQL дайындық күйін тексереді (тіркелгі деректері мен сервис атауларын өз ортаңызға бейімдеңіз). Қажет болса worker-де QUEUE_HEALTH_CHECK_ACTIVE=true қосып, оның жеке /healthz және /healthz/readiness endpoint-терін пайдаланыңыз; дайындық endpoint-і Redis пен дерекқор байланысын тексереді. Тек мониторинг үшін бұл worker endpoint-терін интернетке ашпаңыз.

Қолмен іске қосу — бөлек тест. Әдепкіде OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, сондықтан queue mode дұрыс бапталғанның өзінде редактордан жұмыс процесін қолмен іске қосу main-да орындалуы мүмкін. Оны true мәніне тек қолмен орындалуды worker-лерге жібергіңіз келсе және өзгерісті staging ортада тексерсеңіз ғана орнатыңыз. Queue mode worker-лері Code node орындалуы үшін бөлек конфигурация талап ететін n8n сыртқы task runner-лерден өзгеше.

МАСШТАБТАУ ЖОЛЫ

Бір уақытта бір тар орынды масштабтаңыз

1-кезеңPostgreSQL бар бір n8n инстансы; ең жоғары CPU, RAM және параллельдікті өлшеңіз.
2-кезеңВертикалды масштабтау өлшенген тар орынды әлі тиімді шешсе, VPS ресурстарын арттырыңыз.
3-кезеңҰзақ параллель жүктеме таратылған орындауды ақтағанда Redis пен worker-лерді қосыңыз.
4-кезеңPostgreSQL, Redis және орындалу кідірісін бақылай отырып worker қосыңыз немесе worker параллельдігін баптаңыз.
5-кезеңҚуат, қолжетімділік немесе операциялық талаптар қосымша күрделілікті ақтағанда ғана компоненттерді бірнеше серверге бөліңіз.
Масштабтау қажет етсе, көбірек VPS ресурсын таңдаңыз

Серіктестік сілтеме: сатып алудан комиссия алуымыз мүмкін.

ЖОҒАРЫ ҚОЛЖЕТІМДІЛІК ШЕКАРАСЫ

Queue mode орындалуларды масштабтайды, бірақ main процесін автоматты түрде жоғары қолжетімді етпейді

Шифрлау кілтін ортақ пайдаланыңыз

Әр worker main инстанспен бірдей N8N_ENCRYPTION_KEY қолдануы тиіс, сонда worker-лер жұмыс процесін орындауға қажет тіркелгі деректерінің шифрын аша алады.

Нұсқаларды бірдей ұстаңыз

Main, webhook және worker процестері бір n8n нұсқасында жұмыс істеуі тиіс. Аралас нұсқалармен кезең-кезең жаңарту үйлесімсіз мінез-құлық тудыруы мүмкін.

Вебхук процессорлары — бөлек масштабтау қабаты

Кіріс вебхук көлемі тар орынға айналса, арнайы webhook процессорларын load balancer артына орналастырып, worker-лер жұмыс процестерін орындай алады. Өлшенген сұрау көлемі мұны қажет етпесе, бұл қабатты қоспаңыз.

Multi-main — бөлек функция

High availability үшін бірнеше main процесс іске қосу кәдімгі queue mode-пен бірдей емес. n8n қазір multi-main-ды қосымша load balancer және session талаптары бар self-hosted Enterprise функциясы ретінде құжаттайды.

FAQ

n8n queue mode: жиі қойылатын сұрақтар

n8n queue mode үшін Redis қажет пе?

Иә. Redis — main инстанс пен worker-лер арасындағы күтіп тұрған орындалуларды үйлестіретін хабарлама брокері.

Queue mode SQLite пайдалана ала ма?

Таратылған queue mode архитектурасы үшін жоқ. Main мен worker-лер ортақ дерекқорға қол жеткізуі тиіс, ал n8n бұл конфигурация үшін PostgreSQL-ді құжаттайды.

Қанша worker іске қосу керек?

Әмбебап сан жоқ. Өлшенген параллельдік пен worker жүктелу деңгейінен бастаңыз, кейін PostgreSQL, Redis, CPU, RAM және кезек тереңдігін бақылай отырып қуатты арттырыңыз.

n8n worker параллельдігі деген не?

Бұл — бір worker параллель орындай алатын тапсырма саны. Қазіргі әдепкі мән — 10, ал n8n көп параллельдігі төмен worker жасаудың орнына worker параллельдігі мәнін 5 немесе одан жоғары ұсынады.

Шағын VPS-те queue mode қосу керек пе?

Тек жүктеме қажет етсе. Бір инстанс ретінде еркін жұмыс істейтін шағын орнату Redis пен бөлек worker-лерсіз әдетте қарапайымырақ басқарылады.

Провайдер таңдау, бір басумен орнату, қолдау шекарасы, резервтік көшіру, миграция, аймақ және масштабтау үшін n8n-ге арналған үздік VPS салыстыруын. Ресурс көлемін таңдау үшін n8n-ге арналған негізгі VPS нұсқаулығына оралыңыз.
