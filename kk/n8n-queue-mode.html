МАСШТАБТАУ

n8n Queue Mode

Queue mode жұмыс процестерін орындауды негізгі n8n процесінен бөледі. Негізгі инстанс триггерлерді қабылдап, орындалуларды жасайды, Redis кезекті үйлестіреді, worker-лер тапсырмаларды орындайды, ал PostgreSQL ортақ жұмыс процесі мен орындалу деректерін сақтайды.

ҚЫСҚА ШЕШІМ

Сізге queue mode шынымен қажет пе?

Қалыпты режимде қалыңыз, егер

Бір инстанс ең жоғары жүктемені еркін көтеріп, CPU, RAM және орындалу кідірісі тұрақты болса. Queue mode әзірге қажет емес қосымша компоненттерді енгізеді.

Queue mode қарастырыңыз, егер

Ұзақ параллель орындалу ресурстарға талас тудырса, жүктеме кезінде орындалу кідірісі өссе немесе бірнеше worker іске қосып орындау қуатын арттыру қажет болса.

Алдымен вертикалды масштабтаңыз, егер

Тар орын тек CPU немесе RAM жетіспеуі болса және бір үлкенірек инстанс жүктемені әлі де қалыпты көтере алса.

Архитектураны өзгертпес бұрын өлшеңіз

Queue mode-қа көшудің қажеттілігін ең жоғары бір мезгілдегі орындалу, CPU, RAM, орындалу ұзақтығы, кезек тереңдігі және дерекқор жүктемесі арқылы негіздеңіз.

АРХИТЕКТУРА

n8n queue mode қалай жұмыс істейді

1 · MainТаймерлерді, вебхуктарды және жұмыс процесі сұрауларын қабылдап, өндірістік орындалуды өзі орындаудың орнына execution жасайды.
2 · RedisХабарлама брокері ретінде жұмыс істейді. Келесі бос worker тапсырманы алу үшін күтіп тұрған execution хабарламаларын сақтайды.
3 · WorkerExecution ID-ін қабылдап, ортақ дерекқордан жұмыс процесінің деректерін жүктейді, workflow-ды орындайды және нәтижені қайта жазады.
4 · PostgreSQLОртақ тұрақты жұмыс процесі және орындалу деректерін сақтайды. Таратылған queue mode SQLite арқылы қолдау көрсетілмейді.

НЕГІЗГІ ТАЛАПТАР

Әр queue mode орнатуына не қажет

Redis

Main және барлық worker процестері кезекті үйлестіруге арналған Redis сервисіне сенімді қол жеткізе алуы тиіс.

PostgreSQL

Main мен worker-лер ортақ дерекқорды пайдалануы керек. Queue mode — таратылған архитектура, сондықтан оны SQLite негізінде құруға болмайды.

Сәйкес n8n конфигурациясы

Main мен worker-лер queue mode-та жұмыс істеп, Redis, PostgreSQL және шифрланған тіркелгі деректеріне қол жеткізу үшін бірдей қажетті конфигурацияны қолдануы тиіс.

Worker ресурстары

Worker-лер орындайтын жұмыс процестеріне жеткілікті CPU және RAM қажет. Процестер санын көбейту әр орындалудың ресурс құнын жоймайды.

Бар self-hosted стекке queue mode қосыңыз. Алдымен n8n main сервисі мен әр worker бір PostgreSQL дерекқоры мен Redis-ке жеке желі арқылы қол жеткізе алатынын тексеріңіз. Main мен worker-лерде EXECUTIONS_MODE=queue орнатыңыз және QUEUE_BULL_REDIS_HOST=redis және QUEUE_BULL_REDIS_PORT=6379 егер redis Compose сервисіңіздің нақты атауы болса, пайдаланыңыз: DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres және сәйкес DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER және DB_POSTGRESDB_PASSWORD мәндерін әр процесте пайдаланыңыз; мысалдағы сервис атауларын өз атауларыңызбен ауыстырыңыз. Қолданыстағы дәл N8N_ENCRYPTION_KEY кілті барлық процеске берілуі тиіс. Бір Compose желісіндегі контейнерлерді байланыстыру үшін Redis немесе PostgreSQL host порттарын ешқашан интернетке жарияламаңыз.

Екінші редакторды емес, орындаушы worker-ді іске қосыңыз. Main-дағы бекітілген n8n image нұсқасы мен ортақ параметрлерді пайдаланатын n8n worker сервисін қосыңыз, бірақ оны worker командасымен іске қосыңыз. Егер сервис атауы n8n-worker, болса, оны мына командамен іске қосыңыз: docker compose up -d n8n-worker. Бір worker нақты тапсырма орындағанын тексергеннен кейін екінші worker-ді іске қосу үшін docker compose up -d --scale n8n-worker=2 командасын пайдалана аласыз. Бұл — дұрыс бапталған қолданыстағы Compose стекке қосымша, жеке орнату файлы емес; қолданыстағы persistent volume-дарды, HTTPS proxy-ді, secret-терді және backup-тарды сақтаңыз.

Қолданыстағы стекке арналған queue mode Compose фрагменті. Төмендегі мысалды қолданыстағы compose.yamlфайлына біріктіріңіз; бұл емес толық жеке deployment. Ол сізде persistent, жеке postgres және n8n сервистері, environment ішінде бекітілген N8N_VERSION және қорғалған POSTGRES_PASSWORD сонымен қатар бастапқы N8N_ENCRYPTION_KEY. Атауларды, volume-дарды, дерекқор мен n8n нұсқасын қолданыстағы жобаға сәйкестендіріңіз. Queue mode Redis параметрлерін және EXECUTIONS_MODE=queue мәнін жоғарыда көрсетілгендей қолданыстағы main сервисіне де қосыңыз.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Бұл фрагментте Redis немесе worker үшін host порты жарияланбайды. Redis append-only persistence — қосымша recovery қабаты, емес серверден тыс backup-тың орнына жүрмейді. Қолданыстағы HTTPS және аутентификация конфигурациясын өзгертпеңіз. Сыртқы task runner қажет ететін Code node-тар үшін runner процестерін worker deployment-қа бөлек баптаңыз; queue mode task runner-ді алмастырмайды.

Қолданыстағы SQLite инстансын ауыстырып жатырсыз ба? Тек DB_TYPE мәнін өзгертіп, бос PostgreSQL дерекқорымен іске қоспаңыз: бұл ескі жұмыс процестері мен credentials-ты көшірмейді. Көшу алдында бастапқы дерекқорды, persistent .n8n бумасын және бастапқы шифрлау кілтін backup жасаңыз; n8n қолдайтын export/import немесе migration процедурасын пайдаланыңыз, кейін workflow-лар мен шифрланған credentials-ты бөлек target ортада тексеріңіз. Rollback үшін бастапқы файлдарды сақтап, қалпына келтіруге дайындық үшін төмендегі Backup & Restore нұсқаулығын пайдаланыңыз. Ешқашан database.sqlite файлын shortcut ретінде өшірмеңіз.

WORKER ПАРАЛЛЕЛЬДІЛІГІ

Worker-лер саны бойынша да, әр worker-дегі тапсырма саны бойынша да масштабталады

Әр worker бірнеше тапсырманы бір мезгілде орындай алады. n8n-нің қазіргі әдепкі worker concurrency мәні 10, ал құжаттама 5 немесе одан жоғары concurrency ұсынады. Өте төмен concurrency мен көп worker қажетсіз дерекқор connection жасап, connection pool-ды тауысып жіберуі мүмкін.

Concurrency-ді арттырыңыз, егер

Worker-де бос CPU және RAM болса, ал жұмыс процестері compute немесе memory-ді толық жүктеудің орнына көбіне сыртқы сервистерді күтсе.

Worker қосыңыз, егер

Бір worker процесі тар орынға айналса және дерекқор, Redis пен инфрақұрылым көбірек параллель орындалуға жеткілікті ресурсқа ие болса.

Concurrency-ді азайтыңыз, егер

Жеке workflow-лар жадты немесе CPU-ды көп пайдаланса және параллель тапсырмалар resource contention, OOM қысымы немесе тұрақсыз execution time тудырса.

PostgreSQL-ді бақылаңыз

Worker саны мен concurrency өскен сайын дерекқор белсенділігі де артады. Дерекқор қуатын өсірмей execution capacity-ді масштабтау тар орынды жоюдың орнына басқа жерге ауыстыруы мүмкін.

Қай concurrency лимиті нақты қолданылатынын біліңіз. Worker мына командамен іске қосыла алады: n8n worker --concurrency=5, немесе Compose сервисіңіздегі соған тең worker командасымен. Егер N8N_CONCURRENCY_PRODUCTION_LIMIT мәні -1мәнінен басқа нақты мәнге орнатылса, queue mode-та сол параметр басым болады; әйтпесе n8n worker-дің --concurrency мәнін немесе әдепкі 10 мәнін пайдаланады. Worker санын номиналды default concurrency-ге көбейтіп, оны кепілдендірілген throughput деп есептемеңіз: нақты capacity тапсырма ұзақтығына, CPU, memory, сыртқы API және PostgreSQL connection санына байланысты.

WEBHOOK-ТАР

Queue mode execution handoff кідірісін қосуы мүмкін

Main немесе webhook процесі HTTP сұрауын қабылдайды, бірақ workflow execution-ды worker орындайды. Redis арқылы handoff қосымша overhead береді. Latency-sensitive webhook үшін worker санын көбейту әр сұрауды автоматты жылдамдатады деп есептемей, end-to-end response time өлшеңіз.

ҚабылдауMain/webhook процесі сұрауды қабылдайды.
КезекExecution Redis-ке беріледі.
ОрындауБос worker workflow-ды орындайды.
Жауап беруҚажет кезде нәтиже queue path арқылы кері жеткізіледі.

Webhook трафигін дұрыс процеске бағыттаңыз. Арнайы n8n webhook процестері reverse proxy немесе load balancer артында тұрса, production path-тарды /webhook/* және /webhook-waiting/* webhook процессорларына бағыттаңыз; ал /webhook-test/*, editor және API сұрауларын main-да қалдырыңыз. Қосымша жүктемені саналы қабылдамасаңыз, main-ды production webhook load-balancing pool-ға қоспаңыз. Respond to Webhook workflow worker аяқтап, жауап қайтарғанша клиентті күттіріп қоюы мүмкін, сондықтан queue mode лезде HTTP жауап немесе zero timeout кепілдігі емес. Трафикті ауыстырмас бұрын нақты external callback және response behavior-ды тексеріңіз.

БИНАРЛЫҚ ДЕРЕКТЕР

Ортақ storage-ты елемеңіз

Filesystem шектеуі

Queue mode таратылған worker-лер үшін ортақ persistence моделі ретінде filesystem binary-data storage-ты қолдамайды.

Сыртқы binary storage

Workflow-лар binary data-ны таратылған worker-лер арасында сақтауы керек болса, барлық қажетті инстанс қол жеткізе алатын storage design қолданыңыз, мысалы қолдау көрсетілетін сыртқы object storage.

Үлкен webhook жауаптары

Worker-ден webhook жауаптары қабылдаушы процеске кері өтеді. Үлкен response body Redis жад қысымын арттырып, response storage-ты арнайы баптауды қажет етуі мүмкін.

Worker-лерді таратпас бұрын жоспарлаңыз

Жергілікті файлдарға қатты тәуелді workload worker-лер бірнеше машинаға таратылмай тұрып ортақ persistence үшін қайта жобалануы тиіс.

Үлкен webhook жауаптарының шегі. Қазіргі n8n құжаттамасында N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX әдепкі мәні 64 MiB worker жауабы queue арқылы кері жіберілгенде қолданылады. Redis бір уақытта бірнеше көшірмені ұстай алады, сондықтан әр concurrent үлкен жауап үшін Redis жадында response size-тың шамамен 1.5 есесін жоспарлаңыз. Offload болмаса, тым үлкен жауап worker қосқаннан автоматты түрде жылдамдамайды, керісінше сәтсіз аяқталады.

Нұсқа және лицензия шектеулері. n8n 2.34.0нұсқасынан бастап worker-лер N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true арқылы тым үлкен webhook response body-ларды оқылатын ортақ binary storage-қа offload жасай алады, бірақ алдымен барлық main және webhook процессорларын 2.34.0 немесе одан кейінгі нұсқаға жаңартыңыз. Таңдалған N8N_DEFAULT_BINARY_DATA_MODE нақты деректерді сақтап, барлық қатысушы процесс оқи алуы тиіс. Сыртқы S3 және Azure binary storage үшін жарамды self-hosted Business немесе Enterprise лицензиясы қажет; Community Edition мұны қоса алады деп есептемеңіз. database binary mode ақылы сыртқы storage қолданбай-ақ oversized response-ты offload жасай алады, бірақ main инстанс сақталған body-ді толық жадқа жүктейді және database storage-тың өз file-size limit-і бар. Response body offload үшін, n8n ортақ filesystem опциясын да сипаттайды, егер барлық инстанс бір disk-ті mount етсе, бірақ бұл конфигурацияны нақты ұсынбайды. Осы арнайы offload path-ты таратылған queue mode deployment-та filesystem негізіндегі persistent binary data қолдауы деп шатастырмаңыз. Offload қоспас бұрын edition, version және storage configuration-ды тексеріңіз.

МОНИТОРИНГ

Кезек шынымен көмектесіп жатқанын біліңіз

Кезек тереңдігі

Worker-лер өңдегеннен жылдам өсетін кезек execution capacity жетіспейтінін немесе downstream bottleneck бар екенін көрсетеді.

Worker CPU және RAM

Әр worker үшін saturation және memory peak өлшеңіз. Queue өсіп тұрса, ал worker бос болса, шектеу басқа жерде.

Орындалу кідірісі

Тек workflow runtime-ты емес, execution жасалған сәт пен нақты басталған сәт арасындағы кідірісті бақылаңыз.

Health checks

Worker health endpoint-тері worker жұмыс істеп тұрғанын және дерекқор мен Redis connection дайын екенін көрсете алады.

Тек жасыл контейнерді емес, worker-де нақты орындалуды тексеріңіз. Дұрыс бапталған Compose stack-та тексеріңіз: docker compose ps және docker compose logs --tail=100 n8n-worker (service name өзгеше болса ауыстырыңыз). Зиянсыз published production workflow-ды schedule trigger немесе test webhook арқылы іске қосып, n8n Executions view-дағы execution-ды worker log-тарындағы нақты өңдеумен салыстырыңыз. Редактордың ашылуы, Redis контейнерінің жұмыс істеуі немесе кезекке қойылған execution-ның өзі емес worker тапсырманы орындағанын дәлелдемейді.

Тәуелділіктер мен readiness-ті тексеріңіз. Мысалдағы әдепкі service name-дермен docker compose exec -T redis redis-cli ping командасы PONG жауабын алуы тиіс, егер Redis authentication рұқсат етсе; ал docker compose exec -T postgres pg_isready -U n8n -d n8n PostgreSQL readiness-ті тексереді (credentials пен service name-дерді бейімдеңіз). Қажет болса worker-де QUEUE_HEALTH_CHECK_ACTIVE=true қосып, оның жеке /healthz және /healthz/readiness endpoint-терін қолданыңыз; readiness endpoint Redis/database connectivity-ді тексереді. Тек monitoring үшін бұл worker endpoint-терін интернетке ашпаңыз.

Қолмен іске қосу — бөлек тест. Әдепкіде OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, сондықтан queue mode дұрыс бапталғанның өзінде редактордан workflow-ды қолмен іске қосу main-да орындалуы мүмкін. Оны true мәніне тек manual execution-ды worker-лерге жібергіңіз келсе және өзгерісті staging ортада тексерсеңіз ғана орнатыңыз. Queue mode worker-лері Code node execution үшін бөлек конфигурация талап ететін n8n external task runner-лерінен өзгеше.

FAQ

n8n queue mode: жиі қойылатын сұрақтар

n8n queue mode үшін Redis қажет пе?

Иә. Redis — main инстанс пен worker-лер арасындағы күтіп тұрған execution-дарды үйлестіретін message broker.

Queue mode SQLite пайдалана ала ма?

Таратылған queue mode архитектурасы үшін жоқ. Main мен worker-лер ортақ дерекқорға қол жеткізуі тиіс, ал n8n бұл конфигурация үшін PostgreSQL-ді құжаттайды.

Қанша worker іске қосу керек?

Әмбебап сан жоқ. Өлшенген concurrency және worker utilization-нан бастаңыз, кейін PostgreSQL, Redis, CPU, RAM және queue depth-ті бақылай отырып capacity қосыңыз.

n8n worker concurrency деген не?

Бұл — бір worker параллель орындай алатын тапсырма саны. Қазіргі default — 10, ал n8n көп low-concurrency worker жасаудың орнына worker concurrency мәнін 5 немесе одан жоғары ұсынады.

Шағын VPS-те queue mode қосу керек пе?

Тек жүктеме қажет етсе. Бір инстанс ретінде еркін жұмыс істейтін шағын deployment Redis пен бөлек worker-лерсіз әдетте қарапайымырақ басқарылады.
