ӨНДІРІСТІК ҚАУІПСІЗДІК

n8n-ді VPS-те қауіпсіздендіру

VPS-тегі n8n-ді қауіпсіздендіру үшін n8n (5678), PostgreSQL (5432) және қажет болса Redis (6379) порттарын ашық интернетке шығармаңыз; HTTPS кері проксиін, SSH кілттерін және MFA пайдаланыңыз, шифрлау кілтін сақтаңыз, вебхуктарды аутентификациялаңыз, қауіпті жұмыс процесі мүмкіндіктерін шектеңіз және орнатылған инстансқа аудит жасаңыз. Редакторды ашық вебхук маршруттарынан бөлек қорғаңыз. Тек HTTPS қолдану қосылған сервистердің бәрін қауіпсіз етпейді.

n8n үшін VPS таңдаңыз

Серіктестік сілтеме: сатып алудан комиссия алуымыз мүмкін.

ҚЫСҚА ЧЕК-ПАРАҚ

Интернетке ашпас бұрынғы базалық қауіпсіздік минимумы

Алдымен сырттан қолжетімді порттарды, HTTPS-ті, тексерілген әкімшілік қолжетімділікті, MFA-ны және сақталған тіркелгі деректерінің қорғалуын тексеріңіз. Әр кіріс вебхук құпия әрекетті іске қоспас бұрын аутентификациядан өтуі тиіс. Қолжетімділік ережелерін өзгерткеннен кейін қажетті редакторлар мен сыртқы интеграциялар әлі жұмыс істейтінін тексеріп, содан кейін n8n қауіпсіздік аудитін іске қосыңыз.

Тек HTTPS

n8n-ді дұрыс бапталған TLS кері проксиінің артына орналастырып, редактор мен вебхуктар үшін бірдей ашық HTTPS URL пайдаланыңыз.

Минималды ашық порттар

Тек ашық трафикке қажет порттарды ғана жариялаңыз. PostgreSQL, Redis және қолданбаның ішкі порттарын ашық интернеттен жабыңыз.

SSH қорғауын күшейтіңіз

Кілтке негізделген әкімшілендіруді пайдаланыңыз, жүйеге кім кіре алатынын шектеңіз және операциялық жүйені уақтылы жаңартыңыз.

Тіркелгі деректерін қорғаңыз

n8n шифрлау кілтін өзгеріссіз және құпия сақтаңыз. Орта файлдары, дерекқорға қолжетімділік және резервтік көшірмелер құпия активтер ретінде қорғалуы тиіс.

ЖЕЛІ ШЕКАРАСЫ

Кері прокси, HTTPS және сенімді HTTP header-лері

TLS аяқтау

HTTPS-ті аяқтау үшін Nginx, Caddy немесе Traefik сияқты кері прокси пайдаланыңыз. Қарапайым HTTP трафигін HTTPS-ке бағыттаңыз және негізгі кіру нүктесі прокси болса, n8n қолданба портын тікелей ашпаңыз.

Прокси конфигурациясы

n8n кері прокси артында жұмыс істесе, прокси өтулерінің санын дұрыс баптап, n8n-ге бастапқы клиент сұрауын қалпына келтіруге қажет forwarded header-лерін өткізіңіз.

Қауіпсіз cookie файлдары

Аутентификация cookie файлдары қауіпсіз қалуы үшін редакторды HTTPS арқылы беріңіз. TLS дұрыс бапталмаған жағдайда cookie қауіпсіздігін әлсірету арқылы мәселені айналып өтпеңіз.

Webhook URL

Ашық вебхук URL-ін сырттан қолжетімді HTTPS хост атауына орнатыңыз, сонда жасалған вебхук endpoint-тері ішкі контейнерге немесе HTTP мекенжайына бағытталмайды.

Вебхуктарды бұзбай, редакторды жабық ұстаңыз. Мүмкін болса, басқару қолжетімділігін VPN, сенімді IP саясаты немесе аутентификацияланған прокси арқылы шектеңіз. Ашық вебхук қабылдағыштары мен OAuth callback маршруттары қолжетімді болып қалуы мүмкін; прокси ережесін қатаңдатпас бұрын сенімді редактор арқылы кіруді және нақты сыртқы callback-ты тексеріңіз. Клиент мекенжайы header-лерін тек сенімді проксилерден қабылдаңыз, кез келген сұрау header-іне сенбеңіз.

Вебхук жіберушілерін аутентификациялаңыз: Webhook node ішінде жіберуші қолдаса, None орнына Basic, Header немесе JWT аутентификациясын таңдаңыз. Қажет болғанда IP(s) Allowlist опциясын пайдаланыңыз және интеграция signed request қолдаса, провайдер қолтаңбасын тексеріңіз. Болжауы қиын URL өздігінен жеткілікті аутентификация емес. Қажет жерде прокси деңгейінде сұрау жиілігіне шектеу орнатып, заңды қысқа жүктеме шарықтауы бұғатталмайтынын тексеріңіз. Ресми Webhook аутентификация опциялары.

VPS ҚОРҒАУЫН КҮШЕЙТУ

Сервердің шабуыл бетін азайтыңыз

Желілік экран

Сұралмаған кіріс трафикті әдепкіде бұғаттап, тек сырттан қолжетімді болуы тиіс сервистерге рұқсат беріңіз. Дерекқор мен Redis порттары әдетте жеке немесе жергілікті желіде қалуы керек.

SSH

Құпиясөз орнына SSH кілттерін пайдаланыңыз, қажет емес кіру тәсілдерін өшіріңіз және әкімшілік қолжетімділікті шектеңіз. Root деңгейіне тең құқық қатаң бақылануы тиіс.

ОЖ жаңартулары

Linux хостын және container runtime-ды жаңартып отырыңыз. Қолданбаны күшейту ашық немесе ескірген операциялық жүйені өтей алмайды.

Контейнер порттарын жариялау

Хост арқылы қолжетімді болуы қажет порттарды ғана жариялаңыз. Ішкі сервистер ашық интерфейстер арқылы емес, жеке Docker желілері арқылы байланысуы тиіс.

Желілік экран немесе SSH параметрлерін өзгертпес бұрын тексеріңіз: Тыңдап тұрған порттарды мына командамен тексеріңіз: sudo ss -lntp, Docker жариялаған порттарды docker compose ps жоба бумасынан тексеріңіз, ал хосттың желілік экран саясатын sudo ufw status verbose UFW қолданылса осы командамен тексеріңіз. Құпиясөзбен кіруді өшірмес бұрын нақты SSH порты мен кілт арқылы сәтті кіруді бөлек сессияда тексеріңіз. Docker жариялаған порттар кейбір UFW ережелерін айналып өте алады; желілік экран күйінің өзі 5678 порты жабық екенін дәлелдемейді. Нақты сыртқы қолжетімділікті тексеріңіз. Docker/UFW ескертуі.

Ubuntu автоматты қауіпсіздік жаңартулары жұмыс істейді деп ойламай, нақты тексеріңіз: apt-config dump APT::Periodic::Unattended-Upgrade мәнін және мына логты тексеріңіз: /var/log/unattended-upgrades/unattended-upgrades.log. Егер автоматты security upgrade өшірулі болса, sudo dpkg-reconfigure unattended-upgrades қолдау көрсетілетін конфигурация диалогын ашады. Жұмыс істеп тұрған VPS-те оны қоспас бұрын reboot және service restart тәртібін қарап шығыңыз. Ubuntu APT жаңартулары автоматты түрде n8n Docker image-ін немесе барлық үшінші тарап software repository-лерін жаңартпайды. Ubuntu автоматты жаңарту құжаттамасы.

Қосымша SSH brute-force мониторингі: Fail2Ban қайталанатын сәтсіз SSH кіру әрекеттерін анықтай алады. SSH үшін орнатылып, бапталған болса, jail күйін мына командамен тексеріңіз: sudo fail2ban-client status sshd командасын орындап, оның нақты SSH аутентификация логын немесе журналды оқитынын және бапталған портқа сәйкес келетінін растаңыз. Бұл SSH кілттері мен желілік шектеулерді толықтырады, бірақ олардың орнын баспайды. Қолданыстағы қолжетімділікті тексермей тұрақты SSH порты немесе бұғаттау ережесін көшірмеңіз. Ubuntu SSH қорғауын күшейту нұсқаулығы.

ДЕРЕКҚОР ЖӘНЕ REDIS

Ішкі сервистерді жабық ұстаңыз

Әдеттегі Docker Compose конфигурациясында PostgreSQL және queue mode Redis тиісті контейнерлерге жеке желі арқылы қолжетімді болуы керек, хостта жарияланған порттар арқылы емес. docker compose ps командасымен 5432 және 6379 порттары ашық жарияланбағанын тексеріңіз; VPS/cloud желілік экран экспозициясын бөлек қарап шығыңыз. Желілік саясат ең аз құқық қағидасына сай дерекқор тіркелгі деректерінің орнын баспайды.

PostgreSQLҚашықтан қолжетімділік нақты қажет болып, бөлек қорғалмаған болса, PostgreSQL-ді жеке интерфейске немесе контейнер желісіне байлаңыз.
RedisQueue-mode Redis — инфрақұрылым компоненті, ашық endpoint емес. Желілік қолжетімділікті Redis қажет ететін n8n компоненттерімен шектеңіз.
Тіркелгі деректеріҚолданбаға қажет минималды құқықтары бар жеке дерекқор тіркелгі деректері пайдаланыңыз және оларды нұсқаларды басқару жүйесінен тыс қорғаңыз.
ТасымалдауДерекқор трафигі сенімсіз желілер арқылы өтсе, тек қолданба деңгейіндегі тіркелгі деректерін шифрлауға сүйенбей, тиісті шифрланған transport пайдаланыңыз.

N8N ҚҰПИЯ ДЕРЕКТЕРІ

Шифрлау кілті мен тіркелгі деректері шекарасын қорғаңыз

Шифрлау кілті

n8n сақталған тіркелгі деректерін өзінің шифрлау кілтімен шифрлайды. Қайта іске қосулар мен worker-лер арасында сол бір кілтті сақтап, оны кәдімгі қолданба контентінен бөлек қорғаңыз.

Орта құпиялары

Құпиясөздерді, токендерді немесе шифрлау кілтін ашық репозиторийге сақтамаңыз. Орта файлдары мен орнату құпияларына қолжетімділікті шектеңіз.

Пайдаланушы қолжетімділігі

Редакторға қолжетімділікті тек сенімді пайдаланушыларға беріңіз. Жұмыс процестері құпия жүйелерге қосылып, құпия деректерді өңдеуі немесе жоғары құқықты node-тарды іске қосуы мүмкін.

Тіркелгі деректерінің құқық ауқымы

Мүмкін болғанда құқықтары тар қызметтік аккаунттар мен API токендерін пайдаланыңыз. Бұзылған бұзылған жұмыс процесі байланысы жоқ жүйелерге кең қолжетімділікті автоматты түрде алмауы тиіс.

Тексерілетін n8n конфигурациясы: N8N_BLOCK_ENV_ACCESS_IN_NODE=true Code node және expression арқылы орта айнымалыларына қолжетімділікті бұғаттайды; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true settings файлына тек иесі қол жеткізе алатындай құқықтарды сұратады. Мына кілтті N8N_ENCRYPTION_KEY тұрақты әрі қауіпсіз резервтік көшірмемен сақтаңыз: n8n алғашқы іске қосуда кездейсоқ кілт жасай алады, бірақ оны жоғалту бұрынғы шифрланған тіркелгі деректерін жарамсыз етуі мүмкін. Өндірістік шифрлау кілтін себепсіз ауыстырмаңыз; ресми қолдау көрсетілетін кілтті ауыстыру процедурасын пайдаланыңыз. Орта айнымалыларына қолжетімділікті бұғаттау қолданыстағы интеграцияларды бұзуы мүмкін, сондықтан өндірістік ортадағы өзгеріске дейін тексеріңіз. n8n қауіпсіздік айнымалыларының анықтамалары.

ЖҰМЫС ПРОЦЕСІ ТӘУЕКЕЛДЕРІ

Node-тар қауіпсіздік шекарасын кеңейте алады

Self-hosting жұмыс процестеріне үлкен мүмкіндік береді. Код орындау, shell қолжетімділігі және еркін HTTP сұраулар және үшінші тарап community node-тары тәуекелді арттыруы мүмкін. Қажет емес функцияларды өшіріп, сенімсіз жұмыс процесі импорттарын іске қоспас бұрын тексеріңіз.

Қолдау көрсетілетін нақты басқару параметрлерін пайдаланыңыз: Баптаңыз: NODES_EXCLUDE өшірілетін node-тардың JSON массивімен, мысалы: n8n-nodes-base.executeCommand және n8n-nodes-base.readWriteFile, егер олар пайдаланылмаса. Жаңа нұсқаларда кейбір қауіпті node әдепкіде бұғатталған; өзгертпес бұрын нақты тізімді тексеріңіз. Ресми node-тарды өшіру нұсқаулығы.

n8n 2.12.0 нұсқасынан бастап, N8N_SSRF_PROTECTION_ENABLED=true ішкі, loopback және metadata-address диапазондарына шығатын HTTP сұрауларын тексеруді қосады. Заңды ішкі API жұмыс процестері жұмысын тоқтатуы мүмкін; қажет болса, тек өзіңіз басқаратын мекенжайларды тар рұқсат етілген тізімге қосыңыз. Негізгі қорғаныс ретінде желіні сегментациялауды сақтаңыз. Code node оқшаулау үшін сыртқы task runner-лерді қараңыз. SSRF қорғанысы · Task runner оқшаулауы.

Community node-тарТек сенетін пакеттерді орнатыңыз; олар n8n ортасының ішінде орындалады.
Қауіпті node-тарОрнатуға қажет емес және мүмкіндіктері жұмыс процесінің шекарасынан асатын node-тарды өшіріңіз.
SSRFЖұмыс процестері ішкі немесе metadata endpoint-теріне жете алмауы тиіс жерде n8n SSRF қорғанысы мен желілік басқаруды пайдаланыңыз.
Жұмыс процесі импорттарыИмпортталған жұмыс процестерін, тіркелгі деректерін, expression және орындалатын қадамдарды іске қоспас бұрын тексеріңіз.

АУДИТ ЖӘНЕ ЖАҢАРТУЛАР

Қауіпсіздік — тұрақты операциялық процесс

n8n қауіпсіздік аудитін іске қосыңыз

Ресми CLI командасы: n8n audit. Егер Docker Compose сервисіңіз n8n деп аталса, сол орнату бумасында docker compose exec -T n8n n8n audit командасын орындаңыз. Бес санатты тексеріңіз: пайдаланылмайтын тіркелгі деректері, қауіпті SQL query үлгілері, файлдық жүйеге қолжетімділік, қауіпті/community node-тар және қорғалмаған вебхук пен ескірген релиз сияқты инстанс тәуекелдері. Маңызды табылған мәселелерді түзетіп, аудитті қайта іске қосыңыз. Бұл penetration test емес. Ресми аудит нұсқаулығы.

Жаңартуды саналы түрде жасаңыз

Қауіпсіздік түзетулерін алу үшін n8n-ді жеткілікті жаңа күйде ұстаңыз. Интернетке ашық инстансты ұзақ уақыт ескірген күйде қалдырмай, релиз ескертпелерін қарап, маңызды жаңартуларды тексеріңіз.

Аутентификацияны бақылаңыз

Күтпеген қолжетімділік үлгілерін, жұмыс процесі өзгерістерін және қателерді бақылаңыз. Жұмыс моделіңізге кең ашық қолжетімділік қажет болмаса, редактор интерфейсінің қолжетімділігін одан әрі шектеңіз.

Кері қайтару және қалпына келтіруге дайын болыңыз

Маңызды жаңарту алдында қалпына келтіруге жарамды резервтік көшірме жасаңыз. Резервтік көшірменің құрамы мен қалпына келтіру тәртібі бөлек нұсқаулықта.

Құпия орындалу тарихының көлемін азайтыңыз: Сәтті орындалулар клиент деректері мен токендерді сақтап қалуы мүмкін. Қажет болса, EXECUTIONS_DATA_SAVE_ON_SUCCESS=none мәнін орнатыңыз, EXECUTIONS_DATA_PRUNE=true параметрін қосулы ұстаңыз және EXECUTIONS_DATA_MAX_AGE мәнін сағатпен, мысалы 168 (жеті күн), етіп белгілеңіз. Бұлар — конфигурация мысалдары, заңдық сақтау мерзімі ережелері емес. Тарих азайса, диагностика мен forensic деректер де азаяды; орындалып жатқан, күтіп тұрған немесе аннотацияланған орындалулар дәл сол тәртіппен автоматты тазаланбауы мүмкін. Ресми орындалу тарихын сақтау нұсқаулығын қараңыз.

Бұзылу күдігі болса: Дәлелдерді жоймай зиянды қолжетімділікті шектеңіз, прокси, хост және n8n белсенділігін, сондай-ақ өзгертілген жұмыс процестерін тексеріңіз, жария болуы мүмкін сыртқы тіркелгі деректерін кері қайтарып немесе ауыстырыңыз және себепті түзетіңіз және қажет болса тек тексерілген қалпына келетін резервтік көшірмеден қалпына келтіріңіз. Әсер еткен вебхук URL-дерін, редактор аккаунттарын және қосылған сервистерді тексеріңіз; HTTPS, snapshot немесе VPS сатып алу инцидентке әрекет ету қызметін автоматты береді деп есептемеңіз.

1VPS-ті жаңартып, бақыланатын әкімшілік қолжетімділік жасап, желілік экранды баптаңыз.

3Тіркелгі деректерін сақтамас бұрын шифрлау кілті мен орнату құпияларын баптаңыз.
4Кері проксиді, HTTPS-ті, ашық хост атауын, forwarded header-лерін және вебхук URL-ін баптаңыз.
5Пайдаланушылар, node-тар және желілік қолжетімділікті жұмыс процестеріне нақты қажет деңгеймен шектеңіз.
6Қауіпсіздік аудитін іске қосып, резервтік көшірмелерді тексергеннен кейін ғана өндірістік жұмыс процестерін ашыңыз.

АККАУНТ ЖӘНЕ ПЛАТФОРМАНЫ БАСҚАРУ

VPS-пен бірге редакторды да қорғаңыз

Кіру қорғанысын күшейтіңіз

Редактор аккаунттары үшін екі факторлы аутентификацияны қосыңыз және n8n нұсқасы орталық қауіпсіздік саясатын қолдаса, MFA-ны сол саясат арқылы міндеттеңіз.

Жұмыс процесін кім өзгерте алатынын шектеңіз

Редакторға қолжетімділік — жоғары құқықты қолжетімділік: жұмыс процестері тіркелгі деректерін оқи алады, ішкі жүйелерді шақырады және жоғары құқықты node-тарды орындай алады. Пайдаланушы қолжетімділігін тар ұстап, енді қажет емес аккаунттарды өшіріңіз.

Пайдаланбайтын мүмкіндіктерді өшіріңіз

Қажет болмаса ашық API-ді өшіріп, жұмыс моделіңіз талап етпейтін қауіпті node-тар мен мүмкіндіктерді бұғаттау арқылы қолданбаның шабуыл бетін азайтыңыз.

SSRF және құпия деректерді басқаруды саналы түрде қолданыңыз

Еркін HTTP сұрауларын жасай алатын жұмыс процестері үшін n8n SSRF қорғанысын пайдаланып, құпия деректерді workflow кодында, ашық репозиторийде және кең қолжетімді орта файлдарында сақтамаңыз.

Пайдаланылмайтын басқару endpoint-терін шектеңіз: N8N_PUBLIC_API_DISABLED=true n8n ашық REST API-ін өшіреді, ал N8N_PUBLIC_API_SWAGGERUI_DISABLED=true API тест интерфейсін бөлек өшіреді. Бұл мүмкіндіктер интеграцияларға қажет болмаса ғана жасаңыз. REST API-ді өшіру жұмыс процесінің вебхук URL-дерін аутентификацияламайды. Редактор пайдаланушылары үшін MFA қолданыңыз, ал орталық саясаттарды тек n8n нұсқасы қолдайтын жерде пайдаланыңыз.

Ресми құжаттама: Public API-ді өшіру · Қауіпсіздік саясаты айнымалылары · Аудит командалары.

FAQ

n8n VPS қауіпсіздігі: жиі қойылатын сұрақтар

n8n портын тікелей интернетке ашу керек пе?

Ашық кіру нүктесі кері прокси болса, проксиді ғана жариялап, қажет емес сервистерді кең ашудың орнына қолданба портын оның артында қалдырыңыз.

PostgreSQL немесе Redis интернетке ашық болуы керек пе?

Әдетте жоқ. Олар тек қажет жүйелерге қолжетімді болуы тиіс. Ашық жариялау n8n қалыпты жұмысына көмектеспей, attack surface-ты арттырады.

n8n шифрлау кілті неге маңызды?

Ол n8n сақтайтын тіркелгі деректерін қорғайды және орнату бойы өзгермеуі тиіс. Оны жоғалту қалпына келген деректердегі шифрланған тіркелгі деректерін пайдалануға кедергі келтіруі мүмкін.

Community node-тар қауіпсіз бе?

Олар n8n-ді үшінші тарап коды арқылы кеңейтеді, сондықтан өз жеткізу тізбегі мен құқық тәуекелі бар бағдарламалық тәуелділік ретінде қарастырылуы тиіс. Тек сенетін және қажет пакеттерді орнатыңыз.

HTTPS self-hosted n8n инстансын толық қауіпсіз ете ме?

Жоқ. HTTPS деректер тасымалын қорғайды. Өндірістік қауіпсіздік үшін хостты қорғауды күшейту, қолжетімділікті басқару, жабық backend сервистер, құпия деректерді қорғау, қауіпсіз workflow мүмкіндіктері, мониторинг және жаңартулар да қажет.

Өндірістік вебхуктар жұмыс істеп тұрғанда n8n редакторын жабық ұстауға бола ма?

Иә. Сенімді кері прокси немесе VPN редактор/әкімші қолжетімділігін ашық өндірістік вебхук және OAuth callback маршруттарынан бөлек шектей алады. Интеграцияларды байқамай бұғаттамау үшін әр қолжетімділік ережесі өзгергеннен кейін сенімді кіруді және сыртқы вебхук жеткізілуін тексеріңіз.

Кіріс n8n webhook-тарын қалай аутентификациялауға болады?

Жіберуші қолдаса, Webhook node ішінде Basic, Header немесе JWT аутентификациясын баптаңыз. Сондай-ақ IP(s) Allowlist қолданып, бар болса провайдердің қолтаңбасын тексеріңіз. Тек құпия болып көрінетін path-қа сенбеңіз және сұрауды сезімтал API әрекетін іске қоспас бұрын тексеріңіз.

Провайдерлерді салыстырып жатырсыз ба?

Self-managed VPS сатып алу n8n орнатуы, қорғауды күшейту, қолданба жаңартулары немесе тексерілген қалпына келтіру қызметтері автоматты түрде кіреді дегенді білдірмейді. Бұл қорғаныстар басқарылатын деп ойламай, әр қызметтің нақты шекарасын тексеріңіз. Провайдер таңдау, бір басумен орнату, қолдау шекарасы, резервтік көшіру, миграция, аймақ және масштабтау үшін n8n-ге арналған үздік VPS салыстыруын. Ресурс көлемін таңдау үшін n8n-ге арналған негізгі VPS нұсқаулығына оралыңыз.
