РЕЗЕРВТІК КӨШІРУ ЖӘНЕ ҚАЛПЫНА КЕЛТІРУ

n8n резервтік көшіру және қалпына келтіру

Self-hosted n8n жүйесін толық қалпына келтіру үшін SQLite дерекқорын немесе тұтас PostgreSQL dump-ын, тұрақты .n8n бумасын және бастапқы шифрлау кілтін, deployment конфигурациясын, сондай-ақ сыртқы бинарлық деректер мен mounted файлдарға тәуелділіктерді қорғаңыз. Шифрланған көшірмені VPS-тен бөлек сақтап, қалпына келтіруді жеке инстанста тексеріңіз. Жекелеген жұмыс процестерін қалпына келтіру үшін CLI арқылы workflow пен credentials экспортын пайдаланыңыз; тек JSON экспорты сервердің толық резервтік көшірмесі болып саналмайды.

ҚЫСҚА ЧЕК-ПАРАҚ

n8n резервтік көшірмесі нені қамтуы керек

Дерекқор

Инстанс пайдаланатын PostgreSQL дерекқорын немесе SQLite дерекқор файлын резервтік көшірмеге қосыңыз. Дерекқорда n8n-нің негізгі күйі сақталады: жұмыс процестері, тіркелгі деректері және орындалу деректері.

Шифрлау кілті

n8n пайдаланатын дәл сол шифрлау кілтін бөлек әрі қауіпсіз сақтаңыз. Қалпына келтірілген шифрланған тіркелгі деректері сол кілтке тәуелді.

Тұрақты файлдар

Тұрақты n8n деректер бумасын, сондай-ақ deployment тәуелді болатын mounted файлдарды, бинарлық деректер қоймасын және жұмыс процесі файлдарын резервтік көшірмеге қосыңыз.

Deployment конфигурациясы

Стекті қайта құруға қажет Compose/конфигурация файлдарын және құпия емес параметрлерді сақтаңыз. Құпия деректерге тиісті қолжетімділік шектеулерін қолданыңыз.

РЕЗЕРВТІК КӨШІРУДІҢ ЕКІ ДЕҢГЕЙІ

Логикалық экспорт және апаттан кейін толық қалпына келтіру

Жұмыс процестері мен тіркелгі деректерін экспорттау

n8n CLI экспорты миграцияға, жұмыс процестерінің нұсқаланған көшірмелеріне және таңдаулы қалпына келтіруге ыңғайлы. Тіркелгі деректерін шифрланған түрде экспорттап, кейін сәйкес шифрлау кілтімен импорттауға болады. Бір ғана жұмыс процесін қалпына келтіру үшін редактордағы үш нүктелі мәзірден оның JSON файлын жүктеп, кейін Import from File арқылы жаңа тексеру процесіне немесе оқшауланған инстансқа импорттаңыз. Жұмыс істеп тұрған процесті ауыстырмас бұрын тіркелгі деректерін, workflow ID-лерін және node параметрлерін тексеріңіз: workflow JSON-ын қалпына келтіру бүкіл серверді қалпына келтірмейді.

Entity экспорты

CLI қолдау көрсетілетін дерекқор түрлері арасында деректерді көшіру үшін database entity-лерін экспорттай алады. Орындалу тарихының кестелері міндетті емес, себебі олардың көлемі өте үлкен болуы мүмкін.

Инстансты толық қалпына келтіру

Сервер толық істен шыққан жағдайға нақты дерекқорды, шифрлау кілтін, тұрақты деректерді және deployment тәуелділіктерін сақтаңыз. Workflow JSON экспорты бүкіл инстансты қайта құрады деп есептемеңіз.

Провайдер snapshot-ы

VPS snapshot-ы қосымша қалпына келтіру деңгейі ретінде пайдалы, бірақ жалғыз көшірме болмауы және бөлек тексерілген қолданба/дерекқор резервтік көшірмесін алмастырмауы керек.

ДЕРЕКҚОР

Дерекқорды тұтас күйде резервтік көшіріңіз

PostgreSQL

PostgreSQL үшін тұтастықты сақтайтын резервтік көшіру тәсілін қолданыңыз және алынған көшірмені VPS-тен бөлек сақтаңыз. Істен шыққан сол дискінің өзіндегі дерекқор көшірмесі апаттан қалпына келтіру болып саналмайды.

SQLite

Deployment SQLite пайдаланса, тұрақты n8n деректер бумасындағы дерекқор файлын қорғаңыз. Дерекқор белсенді өзгертіліп жатқан кезде оны қауіпсіз емес күйде көшірмеңіз.

Орындалу тарихы

Тарихи орындалу деректері қалпына келтіру мақсатына кіре ме — соны алдын ала анықтаңыз. Олар резервтік көшірменің көлемін едәуір арттыруы мүмкін, сондықтан сақтау мерзімі мен compliance талаптарына сүйеніңіз.

Дерекқор нұсқасы

Қалпына келтіру ортасын үйлесімді дайындау үшін бастапқы deployment пайдаланған дерекқор қозғалтқышы мен нұсқасын жазып қойыңыз.

Docker Compose VPS-тегі PostgreSQL. Егер PostgreSQL сервисі postgres деп аталып, дерекқор мен пайдаланушы атауы екеуі де n8n болса, төмендегі команда хостта PostgreSQL-дің тұтас custom-format dump-ын жасайды. Іске қоспас бұрын нақты Compose файлын тексеріп, дерекқор тіркелгі деректері мен сервис атауларын сәйкестендіріңіз. pg_dump PostgreSQL жұмыс істеп тұрған кезде логикалық тұрғыдан тұтас snapshot жасай алады, бірақ бөлек .n8n пайдаланушы бумасын немесе сыртқы бинарлық деректерді резервтік көшірмеге қоспайды.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Архив объектілерінің тізімін тексеру анық формат қателерін табады, бірақ деректердің шынымен қалпына келетінін дәлелдемейді. Шифрланған көшірмені серверден тыс сақтап, қалпына келтіруді тәжірибеде тексеріңіз. Дерекқорға тән параметрлер үшін PostgreSQL-дің ресми pg_dump құжаттамасын пайдаланыңыз.

Docker-тағы SQLite. Әдепкі SQLite орнатуында database.sqlite файлы мен автоматты түрде жасалған шифрлау кілтінің конфигурациясы тұрақты .n8n бумасында орналасады (әдетте /home/node/.n8n). SQLite белсенді жұмыс істеп тұрған кезде жасалған қарапайым файл көшірмесін тұтас резервтік көшірме деп есептемеңіз. Буманы көшірмес бұрын n8n мен дерекқорға жазатын басқа процестерді тоқтатыңыз; жұмысты тоқтату мүмкін болмаса, SQLite қолдайтын online backup механизмін пайдаланыңыз:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Бұл командалар көрсетілген сервис пен жолға арналған мысал ғана; олар барлық volume конфигурацияларына бірдей жарамайды. Көшірілген бума бастапқыда сол VPS-тің өзінде қалады, сондықтан оны серверден тыс қауіпсіз сақтау орнына тасымалдаңыз. Queue worker-лері немесе дерекқорға жазатын басқа процестер болса, оларды да тоқтатып, нақты орнату архитектурасына сай әрекет етіңіз. n8n-нің қазіргі толық резервтік көшіру нұсқаулығында SQLite тұтастығына қойылатын талап сипатталған.

Әдепкі SQLite бумасын таза ортаға қалпына келтіру: алдымен n8n сервисін және дерекқорға жазатын барлық процестерді тоқтатыңыз. Үйлесімді n8n контейнері мен мақсатты volume дайын болғаннан кейін резервтік көшірмедегі .n8n мазмұнын қайтадан сол тұрақты бумаға көшіріңіз. Бұл мақсатты файлдардың үстінен жазылады, сондықтан сақталуы тиіс деректері бар инстанста бұл әрекетті орындамаңыз:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker тоқтатылған контейнерге де файл көшіре алады, бірақ мақсатты файлдардың иесі мен рұқсаттары бастапқыдан өзгеше болуы мүмкін. n8n-ді іске қоспас бұрын қалпына келтірілген конфигурация мен дерекқор файлын n8n процесі оқып-жаза алатынын тексеріңіз. Нақты Compose конфигурациясында басқа жол немесе bind mount қолданылса, көшіру командасын соған бейімдеңіз. Docker Compose copy анықтамасы. Бөлек PostgreSQL дерекқорын пайдаланатын орнатуда тек n8n бумасын қалпына келтіру жеткіліксіз.

МАҢЫЗДЫ ҚҰПИЯ ДЕРЕК

Шифрлау кілті — қалпына келтірудің бір бөлігі

n8n сақталған тіркелгі деректерін инстанстың шифрлау кілтімен шифрлайды. Сәйкес кілті жоқ дерекқор немесе шифрланған credentials экспорты қалпына келтірілген жұмыс процестерінің сақталған тіркелгі деректерін пайдалануына мүмкіндік бермеуі мүмкін.

Егер N8N_ENCRYPTION_KEY орнатылған болса, дәл сол secret мәнін қалпына келтіріңіз. Әйтпесе жасалған кілт тұрақты .n8n/config файлында сақталады: резервтік көшіру немесе қайта құру кезінде осы конфигурацияны қорғаңыз. Қалпына келтіру кілттерін VPS-тен бөлек қауіпсіз сақтаңыз. Queue mode-та main және worker процестерінің барлығы бір кілтті пайдалануы тиіс.

КерекProduction ортасында қолданылатын дәл сол кілттің қорғалған көшірмесін сақтаңыз.
КерекТіркелгі деректерін тексермес бұрын қалпына келтіру ортасы сол кілтті қолданып тұрғанын тексеріңіз.
БолмайдыСерверді қайта құрғаннан кейін жаңадан жасалған кілтке сенуге болмайды.
БолмайдыКілтті ашық репозиторийге commit жасауға немесе қорғалмаған резервтік көшірменің жанында сақтауға болмайды.

ФАЙЛДАР ЖӘНЕ БИНАРЛЫҚ ДЕРЕКТЕР

Дерекқор резервтік көшірмесі жұмыс процесінің барлық тәуелділігін қамтымауы мүмкін

Тұрақты .n8n деректері

Тек container image-ін емес, нақты .n8n пайдаланушы бумасын тауып, сақтаңыз. Әдеттегі Docker deployment-ында ол /home/node/.n8n path-ына mounted болады; Docker-дан тыс әдепкі path — ~/.n8n. N8N_USER_FOLDER бапталған болса, n8n .n8n бумасын көрсетілген parent directory ішінде жасайды. Оның config кілтін және инсталляция пайдаланатын жергілікті SQLite, бинарлық немесе filesystem орындалу деректерін де қосыңыз.

Mounted жұмыс процесі файлдары

Жұмыс процестері host-қа mounted бумалардан оқыса немесе соларға жазса, бұл бумаларды бөлек резервтік көшіріңіз. Оларсыз n8n-ді қалпына келтіру басқа жағынан дұрыс жұмыс процестерін істемейтін күйге қалдыруы мүмкін.

Бинарлық деректер

Сақтау режимін анықтап, барлық сыртқы тәуелділікті қалпына келтіріңіз. Filesystem негізіндегі бинарлық немесе орындалу деректері .n8n ішінде не custom бумасында орналасуы мүмкін; S3/Azure Blob немесе басқа сыртқы storage үшін бөлек қалпына келтірілетін көшірме және access параметрлері қажет. Дерекқор dump-ы бұл файлдарды алмастырмайды.

Community node-тар

Community package-тер мен олардың нұсқаларын жазып қойыңыз, сондай-ақ N8N_CUSTOM_EXTENSIONS арқылы бапталған қосымша custom node бумаларын резервтік көшіріңіз. Бұл бумалар .n8n сыртында орналасуы мүмкін; сондықтан тек дерекқор мен пайдаланушы бумасын қалпына келтіру custom node қолданатын жұмыс процестерін жұмыс істемейтін күйде қалдыруы мүмкін.

СЕРВЕРДЕН ТЫС САҚТАУ СТРАТЕГИЯСЫ

Сол VPS-тегі резервтік көшірме — тек жергілікті көшірме

Жергілікті көшірмеЖылдам rollback үшін пайдалы, бірақ сервер жоғалса, диск істен шықса немесе қате әрекет жасалса, бұл көшірме де жоғалуы мүмкін.
Серверден тыс көшірмеКемінде бір резервтік көшірмені production VPS-тен тәуелсіз сақтау орнында ұстаңыз.
Нұсқаланған көшірмелерБүліну немесе қате өзгеріс жалғыз жарамды көшірмені үстінен жазып кетпеуі үшін бірнеше recovery point сақтаңыз.
Қолжетімділікті басқаруРезервтік көшірмелерде тіркелгі деректері, жұмыс процесінің логикасы және құпия бизнес деректері болуы мүмкін. Оларды шифрлап, қолжетімділікті шектеңіз.
МониторингЖоспарланған резервтік көшіру сәтсіз аяқталса немесе жаңа recovery point жасамай қалса, хабарлама берілсін.

Кестені өлшенетін етіңіз. Әр сәтті резервтік көшірменің уақытын, тасымалдаудың аяқталуын, файл көлемін, бастапқы дерекқор нұсқасын, шифрлау кілтін қалпына келтіру орнын және соңғы сәтті restore тестін тіркеңіз. Жоқ, сәтсіз немесе күтпеген жерден бос файлдар туралы alert беріңіз. Backup архивтерін VPS-тен шығармас бұрын шифрлап, recovery secret-теріне қолжетімділікті шектеңіз. Күні көрсетілген бірнеше recovery point соңғы көшірме соңғы сау нұсқаны үстінен жазып кеткеннен кейін ғана бүлінуді байқап қалудан қорғайды.

Мысалы, ең көбі алты сағаттық өзгерісті жоғалтуға жол берсеңіз, әр алты сағат сайын сәтті backup жасау — бастапқы нүкте ғана, кепілдік емес: сәтсіз job-тар мен серверден тыс replication кідірісі нақты жоғалтуды арттыруы мүмкін. 7 немесе 30 күндік әмбебап саясатты қабылдамай, сақтау мерзімі мен restore жиілігін өз RPO/RTO және деректер талаптарына сай белгілеңіз.

ҚАЛПЫНА КЕЛТІРУ РЕТІ

Қалпына келтіруді бақыланатын ретпен орындаңыз

1 · ДайындауҮйлесімді серверді, дерекқорды және container/runtime ортасын дайындаңыз.
2 · Құпия деректерді қалпына келтіруБастапқы n8n шифрлау кілтін және deployment-қа қажет secret-терді қауіпсіз баптаңыз.
3 · Дерекқорды қалпына келтіруPostgreSQL немесе SQLite-ты қалпына келтіріп, n8n қажетті деректерге қосыла алатынын тексеріңіз.
4 · Файлдарды қалпына келтіруТұрақты бумаларды, бинарлық деректерді және mounted жұмыс процесі файлдарын қалпына келтіріңіз.
5 · n8n-ді іске қосуҚолданбаны қажетті hostname, дерекқор және environment конфигурациясымен іске қосыңыз.
6 · ТексеруПайдаланушылар, жұмыс процестері және тіркелгі деректері жүктелетінін тексеріп, кейін негізгі жұмыс процестері мен webhook жолдарын орындап көріңіз.

PostgreSQL апаттан қалпына келтіру мысалы: мынадай бөлек, таза қалпына келтіру ортасында дұрыс database role және бос n8n дерекқоры бар болса, тек PostgreSQL-ді іске қосыңыз. Импорт алдында PostgreSQL толық дайын болғанша күтіңіз: docker compose up -d командасы PostgreSQL әлі инициализацияланып жатқанда аяқталуы мүмкін, сондықтан кейінгі pg_restore командасы сәтсіз болуы мүмкін. Мысалда --wait қазіргі Compose нұсқасында пайдаланылады және бөлек pg_isready. Сенімді күту үшін PostgreSQL healthcheck баптаңыз немесе келесі қадамға өтпес бұрын дайындықты нақты тексеріңіз. Бұл команданы деректері бар production дерекқорына бағыттамаңыз және дерекқор мен оған сәйкес .n8n кілт/деректер қалпына келтірілмей тұрып n8n-ді іске қоспаңыз.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Мақсатты ортада PostgreSQL-дің үйлесімді нұсқасы, қажетті role рұқсаттары, extensions және бастапқы n8n конфигурациясы болуы тиіс. Резервтік көшіру механизмі арқылы .n8n бумасын дұрыс persistent volume немесе bind mount орнына қалпына келтіріп, файл иесі мен рұқсаттарын сақтаңыз. Сыртқы бинарлық файлдарды, custom extensions, Compose конфигурациясын және secret мәндерін қалпына келтіріңіз, содан кейін n8n-нің үйлесімді нұсқасын іске қосып, логтарды тексеріңіз. Тек дерекқорды қалпына келтіру шифрлау кілтін қайтармайды: егер N8N_ENCRYPTION_KEY арнайы орнатылмаған болса, PostgreSQL қолданатын n8n конфигурациясында кілт .n8n/config ішінде сақталады. pg_restore анықтамасы · n8n инстансын толық қалпына келтіру реті.

Таза сервер қажет болса, қалпына келтіруге арналған VPS таңдаңыз

Серіктестік сілтеме: сатып алудан комиссия алуымыз мүмкін.

ҚАЛПЫНА КЕЛТІРУ ТЕСТІ

Қалпына келтіру сәтті өтпейінше резервтік көшірме тексерілген болып саналмайды

Таза ортада тексеріңіз

Нақты тест резервтік көшірме production серверінде қалған, құжатталмаған файлдарға сүйенбей инстансты қайта құра алатынын дәлелдеуі керек.

Тіркелгі деректерін тексеріңіз

Жұмыс процесінің ашылуы жеткіліксіз. Қалпына келтірілген шифрланған тіркелгі деректері шынымен decrypt болып, аутентификациядан сәтті өтетінін тексеріңіз.

Негізгі жұмыс процестерін іске қосыңыз

Тек қарапайым автоматтандыруды емес, webhook, сыртқы API, mounted файлдар және community node-тарға тәуелді жұмыс процестерін тексеріңіз.

Қалпына келтіру уақытын өлшеңіз

Қалпына келтіруге қанша уақыт кететінін және қандай қолмен жасалатын қадамдар қалатынын тіркеңіз. Осылайша жай backup нақты операциялық recovery процедурасына айналады.

Тексерілген restore тесті: SQLite және PostgreSQL

Тест ортасы: n8n 2.42.5 оқшауланған Docker контейнерлерінде, уақытша GitHub Actions runner-де және екі node-тан тұратын синтетикалық жұмыс процесімен тексерілді. Тест күні: 2026 жылғы 8 қазан. Бұл клиенттің немесе production n8n серверінің үстінде жүргізілген жоқ.

SQLite: PASSТест жұмыс процесі импортталды және экспортталды, барлық writer тоқтатылды, SQLite негізіндегі тұрақты .n8n бумасы мен жасалған шифрлау кілті архивтелді, таза volume-ға қалпына келтірілді, n8n іске қосылды, кейін қалпына келген жұмыс процесі қайта экспортталып, орындалды.
PostgreSQL: PASSСол тест жұмыс процесі импортталды, custom-format pg_dumpжасалып, тексерілді; кейін ол pg_restore арқылы жаңа бос PostgreSQL дерекқорына қалпына келтірілді, бөлек .n8n бумасы қалпына келтірілді, кейін жұмыс процесі қайта экспортталып, орындалды.
PASS нені дәлелдейдіТексерілген backup жолдары осы жұмыс процесін, оның екі node-ын және олардың байланыстарын сақтап, қалпына келтіруден кейін орындауға мүмкіндік берді. Бұл — қайталанатын функционалдық smoke test, жүктеме benchmark-і емес.
Не тексерілген жоқНақты тіркелгі деректерін decrypt ету және аутентификациялау, production webhook-тар, queue-mode worker-лері мен Redis, S3/Azure бинарлық storage, custom nodes, пайдаланушы/жоба қолжетімділігі және жұмыс істеп тұрған production инстансты қалпына келтіру тексерілген жоқ. Нақты пайдаланатын әр тәуелділік үшін бөлек тест жасаңыз.

Қалай қайталауға болады: Уақытша n8n инсталляциясын пайдаланып, қауіпсіз екі node-ты жұмыс процесін жасаңыз; қажетті дерекқор мен тұрақты бума backup-ын орындаңыз; таза volume немесе дерекқорға қалпына келтіріңіз; кейін node-тарды, байланыстарды және нақты орындалуды тексеріңіз. Production жүйесінде disaster recovery дайын деп есептемес бұрын шифрланған тіркелгі деректерін, webhook-тарды және сыртқы файлдарды да тексеріңіз.

Restore тестін қабылдау чек-парағы: оқшауланған domain/environment пайдаланыңыз; пайдаланушылар мен жұмыс процестерінің барын, кемінде бір шифрланған credential қайта енгізусіз аутентификацияланатынын, production webhook қажетті қалпына келтірілген жұмыс процесін шақыратынын, mounted файлдар мен binary attachment-тердің оқылатынын және қажетті community node интеграциялары жүктелетінін тексеріңіз. Backup жасын, өлшенген downtime-ды және серверден тыс көшірменің қолжетімділігін растаңыз. Маңызды тексерулердің бірі өтпесе, сол recovery point-ты тексерілмеген деп белгілеңіз; оны толық дайын резервтік көшірме деп көрсетпеңіз.

CLI BACKUP ШЕКТЕУЛЕРІ

Workflow және credentials экспорты нені қалпына келтірмейтінін нақты біліңіз

CLI экспорты — инстанстың толық backup-ы емес

Workflow және credentials экспорты пайдаланушылар мен рөлдерді, орындалу тарихы мен логтарды, айнымалыларды және шифрлау кілті сияқты инстанс параметрлерін қамтымайды.

Таза инстансты қалпына келтіру үшін owner қажет

Таза инстанста credentials импорттамас бұрын owner setup-ты аяқтаңыз. Көп пайдаланушысы бар немесе project restore кезінде дұрыс user/project assignment қажет болуы мүмкін.

Импортталған ID бар объектілерді үстінен жазуы мүмкін

Workflow және credentials экспорты бастапқы ID-лерді сақтайды. Сол ID-лері бар инстансқа импорт жасасаңыз, бар объектілер ауыстырылуы мүмкін.

Импортталған workflow-ларды саналы түрде publish етіңіз

CLI импорты әдетте workflow-ларды inactive күйде қалдырады. n8n 2.x нұсқасында әр импортталған workflow-дың published күйін тексеріп, тек іске қосқыңыз келетіндерін publish етіңіз; self-hosted Server CLI n8n publish:workflow --id=YOUR_WORKFLOW_ID командасын да қолдайды. n8n жұмыс істеп тұрғанда Server CLI арқылы publish/unpublish күйінің өзгеруі тек n8n қайта іске қосылғаннан кейін күшіне енеді. Жоспарланған триггерлерді және production webhook-тарды тексермес немесе трафикті ауыстырмас бұрын n8n-ді қайта іске қосыңыз.

Docker Compose үшін жаппай экспорт мысалы: егер n8n сервисі n8n деп аталса, төмендегі ресми CLI резервтік көшіру командаларын іске қосуға болады. Шығыс жолы әдейі mounted тұрақты .n8n бумасының ішінде көрсетілген, себебі контейнер қайта жасалғанда оның ішіндегі басқа бумалар жоғалуы мүмкін. Бұл бумаға n8n контейнерінің пайдаланушысы жаза алатынын тексеріңіз. Workflow және credential JSON файлдарын бөлек бумаларда сақтаңыз — n8n құжаттамасында екі түр бір бумада жатқанда импорт мәселесі болуы мүмкін екені көрсетілген.

n8n 2.x: draft және published backup айырмашылығы: кәдімгі --backup workflow экспорты ағымдағы draft нұсқаларын сақтайды; олар production-да published нұсқадан өзгеше болуы мүмкін. Белгілі бір workflow-дың нақты published нұсқасын сақтау үшін оны бөлек мына командамен экспорттаңыз: docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, бұған дейін output бумасының бар екенін және оған жазуға болатынын тексеріңіз. CLI historical version-ды мына параметрмен де экспорттай алады: --version=VERSION_ID. Бұл көшірмелерді толық backup-пен бірге серверден тыс сақтаңыз; draft JSON production-да белсенді published күйді көрсетеді деп есептемеңіз.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Көшірілген ~/n8n-recovery/cli бумасы оны қорғалған тәуелсіз backup storage-қа көшіргенге дейін VPS-тің өзінде қалады. Credential экспорты әдепкіде шифрланған және импорт кезінде сәйкес шифрлау кілтін қажет етеді. Мына параметрді қолданбаңыз: --decrypted тек қатаң бақыланатын миграцияда ғана қолдануға болады, себебі ол secret-терді plaintext түрінде жазады. Құпия workflow логикасы немесе credentials бар экспорттарды ешқашан ашық GitHub репозиторийіне commit жасамаңыз. Кейбір үшінші тарап GitHub credential-backup шаблондары decrypt етілген secret-терді әдейі экспорттайды; private repository — тек access restriction, шифрлау емес. Әр шаблонның нақты export параметрлері мен storage permissions-ын тексеріңіз, серверден тыс тасымалдау алдында secret-терді шифрлаңыз және байқамай plaintext жүктелген credentials-ты ауыстырыңыз.

Жаппай импорт мысалы: таза мақсатты ортада owner баптауын аяқтап, бастапқы шифрлау кілтін беріңіз және сақталған резервтік көшірме файлдары recovery VPS-те қолжетімді екенін тексеріңіз. Төмендегі командалар мақсатты буманы жасап, workflows/ және credentials/ ішкі бумаларын хосттан n8n контейнеріне көшіреді; Docker volume конфигурациясы өзгеше болса, жолдарды бейімдеңіз:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

n8n контейнер пайдаланушысы үшін файл ownership және access мәндерін тексеріңіз. Verified rollback жоспары жоқ болса, деректері бар production инстанстың үстіне импорт жасамаңыз: workflow және credential ID-лері бар объектілерді үстінен жазуы мүмкін. Содан кейін іске қосыңыз:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Импортталған ID-лер бар workflow немесе credentials объектілерін ауыстыруы мүмкін; dry run үшін оқшауланған тест инстансын пайдаланып, кейін credentials және activation/publishing күйін тексеріңіз. n8n 2.x нұсқасында JSON draft-ты қалпына келтіру workflow published болып, жоспарланған триггерлерді іске қоса алатынын өздігінен дәлелдемейді. Import қауіпсіздігі: non-multi-main n8n инстансында бұрын белсенді болған cron trigger-лер CLI import-тан кейін инстанс қайта іске қосылғанға дейін жұмысын жалғастыруы мүмкін. Қалпына келтірілген job-тарды қосар алдында production trigger-лерді тоқтатыңыз немесе оқшаулаңыз және n8n-ді қайта іске қосыңыз; duplicate execution жоқ екенін тексеріңіз. CLI экспорты емес бастапқы пайдаланушыларды, орындалу логтарын, инстанс айнымалыларын немесе шифрлау кілтін қамтымайды. --backup параметрі --all --pretty --separate, мәндерін орнатады; бұл «full instance» backup емес. Дереккөздер: қазіргі ресми n8n backup/restore нұсқаулығы және n8n CLI command reference.

GitHub немесе Google Drive шаблондарынан bulk restore: Бұл тек workflow JSON үшін балама тәсіл; ол инстанс дерекқорын, пайдаланушыларды, шифрланған credential мәндерін немесе шифрлау кілтін қалпына келтірмейді. API негізіндегі шаблонды іске қоспас бұрын n8n API және storage permissions-ын, таңдалған backup нұсқасын және target инстансты, matching ID-лерді жаңартатынын және өшірілген workflow-ларды қайта жасайтынын, сондай-ақ publishing-пен не істейтінін тексеріңіз. Барлық шаблон target-та жоқ ID-ді қайта жасай бермейді; автоматты restore-ға сенбес бұрын бұл сценарийді оқшауланған ортада тексеріңіз.

FAQ

n8n резервтік көшіру және қалпына келтіру: жиі қойылатын сұрақтар

n8n-ді резервтік көшіру үшін workflow экспорттау жеткілікті ме?

Жоқ. Workflow экспорты пайдалы логикалық көшірме, бірақ толық қалпына келтіру үшін credentials, сәйкес шифрлау кілті, дерекқор күйі, тұрақты файлдар және бинарлық деректер storage-ы да қажет болуы мүмкін.

Дерекқор бар болса да n8n шифрлау кілті керек пе?

Иә, егер сол дерекқорда сақталған шифрланған credentials әрі қарай жұмыс істеуі керек болса. Бастапқы кілтті қауіпсіз сақтаңыз.

PostgreSQL-ді backup жасау керек пе, әлде workflow мен credentials экспорттау жеткілікті ме?

Disaster recovery үшін дерекқор мен шифрлау кілтін қорғаңыз. Логикалық экспорттар инстанстың барлық бөлігін алмастырмайды; олар миграция және таңдаулы қалпына келтіру үшін қосымша деңгей ретінде пайдалы.

VPS snapshot жалғыз резервтік көшірме бола ала ма?

Оны қалпына келтірудің бір деңгейі ретінде қарастырған дұрыс. Провайдер, аккаунт, сервер немесе snapshot мәселесі барлық recovery point-ты бірден жоймауы үшін тәуелсіз серверден тыс backup сақтаңыз.

Резервтік көшірме жұмыс істейтінін қалай білемін?

Оны таза тест ортасына қалпына келтіріп, credentials decrypt болатынын тексеріңіз және негізгі workflow-ларды іске қосыңыз. Backup job-тың сәтті аяқталуы өздігінен қалпына келтіруге болатынын дәлелдемейді.

GitHub немесе Google Drive-тағы workflow backup сақталған credential secret-терін қамти ма?

Тек workflow JSON сақтайтын backup n8n credential store басқаратын secret мәндерін немесе инстанстың шифрлау кілтін қамтымайды. Бірақ экспортталған JSON credential атаулары мен ID-лерін және node параметрлеріне тікелей енгізілген secret-терді, мысалы authentication header-лерін, ашып көрсетуі мүмкін. JSON-ды жүктеу немесе бөлісу алдында тексеріп, қорғаңыз. Толық қалпына келтіру үшін дерекқор мен бастапқы кілтті backup жасаңыз немесе тексерілген restore-пен бірге қолдау көрсетілетін шифрланған credential CLI экспортын пайдаланыңыз. Тек workflow сақтайтын GitHub немесе Google Drive шаблоны толық disaster recovery емес.

ҚАЛПЫНА КЕЛТІРУ МАҚСАТТАРЫ

Инцидентке дейін RPO және RTO мәндерін анықтаңыз

RPO — соңғы өзгерістердің жол беруге болатын ең үлкен жоғалту көлемі. Оны бөлек сақталған, пайдалануға жарамды ең жаңа recovery point-тен есептеңіз; экспорт немесе тасымалдау сәтсіз болса, әр алты сағатқа жоспарланған job алты сағаттық RPO-ны қамтамасыз етпейді. RTO — жүйенің тоқтап тұруының жол беруге болатын ең ұзақ уақыты. Оны таза restore тестінде өлшеңіз: secret-терді алу, сыртқы файлдарды қалпына келтіру, credentials-ты қайта тексеру және қалпына келген workflow-ларды publish ету уақытын да қосыңыз; тек контейнерді іске қосу жеткіліксіз.

ҚАЛПЫНА КЕЛТІРУ КІЛТІ

Қайта құру алдында бастапқы шифрлау кілтін табыңыз

Егер production ортада N8N_ENCRYPTION_KEY орнатылған болса, environment secret-тің дәл сол мәнін сақтаңыз. Орнатылмаған болса, бастапқы тұрақты .n8n/config ішіндегі автоматты түрде жасалған кілтті сақтаңыз. Шифрланған credentials импорттамас бұрын қалпына келтірілген инстанс кілтті қай жерден алатынын тексеріңіз; жаңадан жасалған кілт ескі дерекқордағы credentials-ты decrypt ете алмайды.
