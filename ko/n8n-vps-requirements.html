최소 용량과 실제 용량

n8n 에는 공식적인 최소 VPS 크기가 하나 있습니까?

모든 작업 부하에 해당되는 것은 아닙니다. n8n 의 공식 전제 조건 예는 예시적인 OEM 배포를 설명하고 요구 사항이 워크로드에 따라 다르다는 점을 명시적으로 경고합니다. 해당 문서는 특정 CPU, RAM 또는 디스크 할당이 생산 자동화를 지원한다는 것을 보편적으로 보장하지 않습니다.

n8n 에서는 유휴 인스턴스가 상대적으로 적은 메모리를 사용할 수 있지만 코드 노드, 대규모 바이너리 페이로드 또는 동시 실행으로 인해 메모리 수요가 급격히 증가할 수 있음을 지적합니다. 운영 체제, Docker, PostgreSQL 및 백업/모니터링 도구에 대해 별도로 예산을 책정합니다.

기술 소스: n8n 의 예시 전제 조건 및 공식 메모리 가이드. 위의 4개 행은 규정된 공식 n8n 요구 사항이 아닌 실제 구매 가능한 리소스 번들입니다.

RAM 및 CPU

실제로 서버 자원을 소비하는 것은 무엇입니까?

동시 실행

동시에 실행되는 여러 워크플로는 n8n 에 저장된 총 워크플로 수보다 더 중요할 수 있습니다. 겹치는 동안 메모리 최대치와 실행 대기 시간을 관찰하세요.

페이로드 크기

대규모 JSON 개체, 파일 및 바이너리 데이터는 메모리 압박을 증가시킵니다. 데이터가 많은 몇 가지 실행에는 많은 경량 API 자동화보다 더 많은 RAM 이 필요할 수 있습니다.

CPU-헤비 노드

코드, 변환 및 기타 컴퓨팅 집약적인 단계로 인해 지속적인 CPU 압력이 발생할 수 있습니다. 실제 실행이 컴퓨팅을 위해 경쟁할 때 더 많은 코어가 도움이 됩니다.

지원 서비스

운영 체제, PostgreSQL, 역방향 프록시, 모니터링 및 Docker 에도 리소스가 필요합니다. n8n 프로세스뿐만 아니라 전체 스택의 크기를 조정하십시오.

업그레이드하기 전에 측정하세요

n8n 에 RAM, CPU 또는 디스크가 더 필요한지 확인하는 방법

예상되는 가장 큰 워크플로우와 현실적인 중첩 버스트를 실행한 다음 서버 및 n8n 실행 로그를 검사하십시오. 편집기에 저장된 워크플로우 수는 그 자체로는 유용한 용량 벤치마크가 아닙니다.

기억 / OOM

확인 docker stats --no-stream 그리고 free -h. 메모리가 소진된 경우 먼저 JSON 또는 바이너리 페이로드를 줄이고 대규모 가져오기를 일괄 처리하며 메모리가 많이 사용되는 코드 단계를 피하세요. vCPU를 추가한다고 해서 JavaScript 힙 오류가 반드시 해결되는 것은 아닙니다.

CPU / 동시성

변환 중에 CPU 이 계속 사용 중인지 또는 작업이 외부 API를 기다리는지 여부를 측정합니다. 일반 모드에서는 작업자로 확장하기 전에 지원되는 프로덕션 동시성 제한을 고려하세요. CPU 을 늘려도 외부 속도가 제한된 API 의 속도는 빨라지지 않습니다.

스토리지/데이터베이스

확인 df -h, 데이터베이스 크기 및 유지된 실행 기록. 디스크 증가와 느린 데이터베이스 작업을 관찰하세요. 더 큰 디스크에 대한 비용을 지불하기 전에 의도적으로 보존을 설정하십시오. 복구 복사본을 서버 외부에 보관하세요.

n8n 의 동시성 지침과 공식 벤치마킹 설명을 사용하세요. 페이로드 및 API 대기 시간을 알지 못한 채 광고되는 동시 워크플로의 수는 추정치일 뿐입니다.

데이터베이스 및 스토리지

SQLite, PostgreSQL 및 영구 데이터

SQLite

SQLite 은 소규모 단일 인스턴스 배포 및 테스트에 적합합니다. 프로덕션 사용량과 동시성이 증가함에 따라 데이터베이스 선택은 설치 세부 사항이 아닌 운영상의 제약이 됩니다.

PostgreSQL

프로덕션 지향 VPS 스택의 경우 PostgreSQL 은 더욱 강력한 데이터베이스 기반을 제공합니다. 데이터베이스 자체에 RAM, CPU 및 디스크 예산을 책정하고 데이터베이스 증가를 모니터링합니다.

영구 .n8n 데이터

PostgreSQL 을 유일한 영구 자산으로 취급하지 마십시오. n8n 데이터 디렉터리를 보존하고 암호화된 자격 증명을 복구하는 데 필요한 암호화 키를 보호합니다.

디스크 증가

실행 기록, 바이너리 데이터, 데이터베이스 파일 및 로그는 시간이 지남에 따라 확장될 수 있습니다. 보존 설정 및 서버 외부 백업은 필요한 용량에 직접적인 영향을 미칩니다.

디스크 용량

주문 전 n8n 실행 내역 저장 공간 추정

다음으로 시작 일일 저장된 실행 × 실행당 평균 저장 바이트 × 보존 일수. 예를 들어, 하루에 500 저장된 실행 × 각각 200 KB × 14 일 = 1.4 GB 데이터베이스 오버헤드 이전의 실행 데이터 예시입니다. 200 KB 가정은 n8n 벤치마크가 아니라 설명을 위한 것입니다.

또한 OS, Docker 이미지 레이어, 데이터베이스 인덱스, 바이너리 파일, 애플리케이션 로그, 업그레이드 및 임시 파일을 위한 디스크를 할당합니다. 서버 외부 백업에는 자체 용량이 필요합니다. 10 GB 디스크는 린 스택에 적합하지만 40 또는 80 GB 디스크보다 파일을 보관할 공간이 훨씬 적습니다.

n8n 에서는 예외를 제외하고 기간(336 시간/14 일) 또는 개수(10,000 실행)별로 기본 실행 정리를 문서화합니다. 실제 설정을 확인하고 변경하기 전에 무엇이 유지되는지 확인하세요. SQLite 는 파일을 자동으로 축소하는 대신 여유 공간을 재사용할 수 있습니다.

출처: n8n: 실행 데이터 및 정리를 관리합니다. 디스크 요구 사항은 노드 수에만 의존하는 것이 아니라 관찰된 저장된 페이로드 크기에 따라 달라집니다.

시스템 요구사항

Docker 및 생산 간접비

Linux VPS

애플리케이션 스택 외에 운영 체제 및 보안 업데이트를 위한 충분한 리소스가 포함된 유지 관리된 Linux 배포판을 사용하세요.

Docker 및 작성

컨테이너 배포는 반복성을 단순화하지만 리소스 오버헤드를 제거하지는 않습니다. 일회용 컨테이너 외부에 n8n 및 데이터베이스 데이터를 유지합니다.

HTTPS 및 역방향 프록시

공개 웹후크에는 안정적인 호스트 이름이 필요하고 올바르게 구성된 HTTPS 이 필요합니다. 프로덕션 디자인에 역방향 프록시와 TLS 레이어를 포함합니다.

모니터링 및 백업

RAM, CPU, 디스크 및 데이터베이스 증가를 추적합니다. 스냅샷이 충분하다고 가정하기보다는 VPS 외부에서 복구 가능한 백업을 유지하고 복원을 테스트하세요.

동시성

더 큰 VPS 가 전체 답변이 아닌 경우

하나의 인스턴스가 워크로드를 깔끔하게 처리할 수 있으면 수직 확장이 적합합니다. 지속적인 병렬 수요로 인해 경합이 발생하면 대기열 모드와 작업자를 평가하세요. 대기열 모드에는 Redis, PostgreSQL 및 하나 이상의 작업자 프로세스가 도입됩니다. n8n 뿐만 아니라 모든 구성 요소에 대해 RAM 및 CPU 예산을 책정합니다. n8n 에는 대기열 모드의 파일 시스템 바이너리 데이터 저장소에 대한 제한 사항도 문서화되어 있으므로 전환하기 전에 호환되는 데이터 저장소 설계를 검증하십시오.

대기열 모드 고려측정된 병렬 수요는 Redis 및 별도의 작업자를 정당화합니다.

How to use a 1 GB entry VPS

1 GB RAM

이는 테스트 전용 제품이 아닌 실제 작동하는 VPS 계층입니다. 메모리, 디스크 사용 및 동시 작업을 측정된 한도 내에서 유지하는 경우 소규모의 상시 자동화 및 대부분 순차적인 API 작업에 적합할 수 있습니다. 동일한 서버에서 PostgreSQL 에 대한 여유 공간이 적고, 페이로드가 크거나 병렬 실행이 과중합니다.

2 GB RAM

프로덕션 규모의 스택으로 즉시 이동하지 않고 운영 체제, Docker 및 소규모 버스트를 위한 더 많은 공간을 원할 경우 2 GB 를 보다 안전한 라이트 인스턴스 기준으로 사용하십시오.

SSD 대 NVMe

Standard SSD 은 조명 자동화에 적합합니다. NVMe 는 PostgreSQL 및 실행 기록으로 인해 읽기 및 쓰기가 자주 발생하거나 측정된 워크플로 성능에 디스크 대기 시간이 나타나는 경우 더 유용합니다.

업그레이드 전 측정

속도가 느려질 때마다 더 큰 VPS 수정을 가정하는 대신 CPU, 메모리, 디스크 증가 및 최고 중첩 시 실행 기간을 사용하여 병목 현상이 컴퓨팅, 메모리 또는 스토리지인지 결정합니다.

n8n VPS 요구 사항: 일반적인 질문

n8n 에는 얼마나 많은 RAM 이 필요합니까?

보편적인 인물은 없습니다. RAM 수요는 VPS 의 동시성, 페이로드 크기, 실행 동작 및 지원 서비스에 따라 변경됩니다. 4 GB 서버는 실용적인 소규모 생산 시작 클래스이며 모든 워크로드에 대해 보장된 요구 사항은 아닙니다.

CPU 코어를 몇 개 사용해야 합니까?

가벼운 워크로드는 작은 CPU 할당으로 시작할 수 있습니다. 모니터링에서 워크플로 수만으로 크기를 조정하는 대신 동시성에서 지속적인 CPU 압력 또는 느린 실행을 보여줄 때 코어를 추가하세요.

n8n 에는 PostgreSQL 이 필요합니까?

소규모 배포에서는 SQLite 을 사용할 수 있지만 운영 요구 사항 및 동시성이 증가함에 따라 PostgreSQL 이 프로덕션 중심 선택으로 더 강력해졌습니다.

Redis 은 언제 필요합니까?

Redis 은 대기열 모드와 연관되어 있습니다. 일반적인 단일 인스턴스 배포에는 VPS 에서 실행되기 때문에 Redis 이 필요하지 않습니다.

얼마나 많은 디스크 공간을 예약해야 합니까?

디스크 수요는 PostgreSQL 증가, 유지된 실행 기록, 바이너리 데이터, 로그, 컨테이너 계층 및 백업에 따라 달라집니다. 고정된 범용 수치에 의존하는 대신 성장을 모니터링하고 여유 공간을 확보하세요.

1 GB VPS 에서 n8n 을 계속해서 실행할 수 있나요?

예, 실제 작업 부하가 적합할 경우 가능합니다. 1 GB VPS 는 실제 작동하는 서버이며 소규모의 순차적 자동화를 지원할 수 있지만 메모리 헤드룸은 제한되어 있습니다. 동일한 서버 PostgreSQL 스택, 바이너리가 많은 작업 또는 여러 개의 대규모 동시 실행이 적합하다고 가정하지 마십시오. 관찰된 리소스 압력을 기반으로 소비 및 업그레이드를 모니터링합니다.

2 GB 또는 4 GB RAM 가 프로덕션 n8n VPS 에 더 좋습니까?

2GB는 린 1 GB 인스턴스보다 더 많은 공간을 제공하는 반면, 4 GB 는 PostgreSQL 및 HTTPS 와 함께 n8n 를 평가하기 위한 실용적인 시작 클래스입니다. 보편적으로 보장되는 생산 최소값은 없습니다. 워크로드 복잡성, 최대 중복, 컨테이너 구성 및 보유 데이터가 실제 수요를 결정합니다.

n8n AI 워크플로에는 GPU 이 필요합니까?

n8n 이 외부 모델 API 만 호출하는 경우는 아닙니다. 모델 공급자는 추론을 처리하고 VPS 는 오케스트레이션, 페이로드 및 동시성을 처리합니다. 추론 모델을 로컬에서 실행하는 것은 훨씬 더 많은 RAM 및 적절한 GPU 리소스가 필요할 수 있는 별도의 하드웨어 결정입니다.

n8n 메모리 부족 오류의 원인은 무엇입니까?

큰 JSON 또는 바이너리 페이로드, 메모리를 많이 사용하는 코드 작업 및 중복 실행이 일반적인 원인입니다. 런타임 로그와 최대 메모리 사용량을 확인한 다음 한 번의 실행에 보관된 데이터를 줄이거나 측정된 문제에 따라 더 많은 RAM 을 할당합니다.
