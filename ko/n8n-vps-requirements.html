n8n VPS 사양: RAM·CPU·디스크는 workload로 정하세요

모든 self-hosted n8n에 적용되는 하나의 공식 “최소 4 GB” 같은 숫자는 없습니다. 실제 서버 크기는 동시에 겹치는 실행 수 × 각 실행이 처리하는 데이터 크기에 PostgreSQL, 파일 처리, 로그와 다른 컨테이너의 자원을 더해 결정합니다.

먼저 구분

공식 예시와 실제 VPS 권장치는 같은 숫자가 아닙니다

n8n 공식 문서

공식 prerequisite에는 Cloud 기반의 설명용 sizing 예시가 있으며 실제 요구량은 사용자, workflow와 execution에 따라 달라진다고 명시합니다. 이것을 일반 VPS의 보장된 최소 사양으로 읽으면 안 됩니다.

실제 self-hosted VPS

운영 서버에는 n8n뿐 아니라 OS, Docker, reverse proxy, PostgreSQL, monitoring과 여유 자원까지 들어갑니다. 그래서 앱이 켜지는 최소치와 production에서 편하게 운영할 용량은 다릅니다.

실용적인 시작점

1·2·4·8 GB는 “규칙”이 아니라 출발점입니다

1 GB · 테스트용

학습, 짧은 테스트, 작은 webhook 확인 정도. PostgreSQL과 여러 컨테이너를 같이 두는 production에는 여유가 매우 작습니다.

2 GB · 가벼운 자동화

작은 JSON, 낮은 동시 실행, 외부 API 호출 위주의 workflow에 검토할 수 있습니다. 큰 payload나 실행 겹침이 시작되면 빠르게 한계가 올 수 있습니다.

4 GB · 소규모 production 시작점

n8n + PostgreSQL + reverse proxy를 한 VPS에서 운영하는 소규모 환경의 실용적인 출발점입니다. 모든 workflow에 충분하다는 보장은 아닙니다.

8 GB+ · 무거운 workload

큰 JSON·binary file, CPU-heavy Code node, 여러 동시 실행 또는 추가 서비스가 많을 때 검토합니다. Queue Mode는 별도의 분산 구조 문제입니다.

구매 전 검증

사양표를 믿기 전에 내 workflow로 직접 측정하세요

검색 결과의 “최소 2 GB”, “권장 4 GB”, “production 8 GB” 같은 숫자는 서로 다릅니다. 가장 안전한 방법은 대표 workflow와 실제 peak 조건을 작은 서버에서 재현하고 CPU·RAM·실행 지연을 측정한 뒤 확장하는 것입니다. n8n 공식 문서도 workload 유형과 사용 가능한 자원에 따라 성능이 달라지므로 자체 benchmark를 권장합니다.

1. 대표 workload 선택가장 자주 실행되는 workflow뿐 아니라 가장 큰 JSON·파일·Code node를 쓰는 workflow도 포함합니다.
2. Peak 동시 실행 재현하루 평균이 아니라 가장 바쁜 시간대처럼 여러 production execution이 겹치는 상황을 만듭니다.
3. CPU·RAM 관찰host 모니터링이나 docker stats로 메모리, CPU와 restart/OOM 여부를 확인합니다.
4. 응답 지연 확인webhook 응답과 execution 시작 시간이 부하가 커질수록 급격히 느려지는지 봅니다.
5. 여유가 없으면 확장정상 peak workload에서 메모리·CPU가 계속 포화되거나 지연이 커지면 다음 사양으로 올립니다.

n8n의 공식 단일 인스턴스 benchmark에는 4 GB RAM 서버가 사용되지만, 매우 단순한 Webhook + Edit Fields workflow를 측정한 예시입니다. 따라서 “n8n은 4 GB면 충분하다”는 일반 규칙으로 사용할 수 없습니다.

동시 실행 제어

서버를 키우기 전에 concurrency를 제한할 수도 있습니다

regular mode에서는 production execution의 동시 실행 수가 기본적으로 제한되지 않아 너무 많은 실행이 한꺼번에 몰리면 성능이 급격히 떨어질 수 있습니다. n8n은 N8N_CONCURRENCY_PRODUCTION_LIMIT으로 production concurrency를 제한하고 초과 실행을 queue에 대기시키는 기능을 제공합니다.

언제 유용한가

짧은 burst 때문에 RAM이 순간적으로 치솟지만 전체 처리량은 충분한 경우, 무조건 VPS를 키우기 전에 peak 동시 실행을 제어할 수 있습니다.

무엇을 해결하지 못하나

한 execution 자체가 너무 큰 JSON·binary data를 처리해 메모리를 소진한다면 concurrency 제한만으로는 부족합니다. workflow 데이터 구조나 서버 자원을 함께 봐야 합니다.

RAM 계산

평균이 아니라 가장 바쁜 순간을 계산하세요

1. n8n 기본 사용량프로세스 자체와 UI가 쓰는 메모리.
2. Peak concurrency가장 바쁜 순간 동시에 살아 있는 execution 수.
3. Execution data각 실행이 들고 있는 JSON, item, binary data와 Code node의 복사·변환 비용.
4. 같은 VPS의 서비스PostgreSQL, reverse proxy, monitoring, 다른 container의 메모리.
5. 여유 용량업데이트, 일시적 burst, 큰 payload가 겹칠 때 바로 OOM이 나지 않도록 headroom 확보.

workflow 개수 자체는 좋은 sizing 단위가 아닙니다. 100개의 거의 실행되지 않는 workflow보다 큰 파일을 동시에 처리하는 몇 개의 execution이 더 많은 RAM을 쓸 수 있습니다.

RAM을 크게 만드는 것

n8n에서 메모리를 실제로 잡아먹는 네 가지

큰 JSON과 많은 item

한 execution이 많은 데이터를 메모리에 유지할수록 사용량이 커집니다.

Binary data

이미지, PDF, 오디오, 동영상은 작은 JSON API 호출과 완전히 다른 부하를 만듭니다.

Code node와 변환

복잡한 JavaScript, 데이터 복사, 파싱과 변환은 메모리와 CPU를 함께 올릴 수 있습니다.

동시 실행

같은 workflow라도 여러 execution이 동시에 겹치면 각각의 메모리 사용이 합쳐집니다.

CPU

n8n은 항상 CPU가 병목인 애플리케이션은 아닙니다

외부 API 대기가 대부분

HTTP 요청과 SaaS API 응답을 기다리는 workflow는 CPU보다 RAM, latency와 concurrency 관리가 더 중요할 수 있습니다.

서버가 직접 계산

Code node, 압축, 대형 JSON 변환, 문서·파일 처리 비중이 높으면 vCPU가 더 중요해집니다.

Hosted AI API

외부 AI 제공자가 추론하면 VPS는 orchestration과 데이터 전달을 담당합니다. GPU가 자동으로 필요한 것은 아닙니다.

Local AI

같은 서버에서 모델을 직접 실행하면 n8n 사양과 별도로 모델용 RAM·CPU·GPU를 계산해야 합니다.

DATABASE

PostgreSQL을 같은 VPS에 두면 그 자원도 합산합니다

SQLite

단순한 시작에는 편하지만 production 확장 판단은 n8n workload와 데이터 보존 요구를 함께 봐야 합니다.

PostgreSQL

n8n과 같은 VPS에 두면 DB 메모리, connection, disk I/O와 backup 공간이 모두 같은 자원을 사용합니다.

DB를 분리할 때

n8n CPU/RAM과 database I/O가 서로 영향을 주거나 확장 주기가 달라지면 별도 DB로 분리할 수 있습니다.

Queue Mode

worker를 늘리는 단계에서는 PostgreSQL과 Redis, connection pool까지 함께 설계해야 합니다. 자세한 구조는 Queue Mode 가이드로 분리합니다.

STORAGE

디스크는 설치 용량보다 execution 보존량이 더 중요합니다

OS + Docker기본 시스템과 image/volume 여유.
Databaseworkflow, credential metadata와 execution history.
Binary data파일 workflow가 많다면 별도 storage 전략까지 고려.
LogsDocker와 reverse proxy 로그의 보존 기간.
Backup운영 데이터와 같은 디스크 한 곳에만 backup을 두지 않음.
execution 데이터의 간단한 추정

하루 저장 execution 수 × 평균 저장 크기 × 보존 일수로 데이터 증가량을 먼저 잡고, DB index·로그·OS·container와 여유 공간을 추가합니다.

n8n의 execution pruning도 디스크 계산에 포함

현재 n8n은 finished execution pruning을 기본 활성화하며 기본 기준은 14일 또는 10,000개입니다. 필요한 기록만 저장하고 보존 기간·개수를 실제 운영 요구에 맞추면 DB가 무한히 커지는 것을 막을 수 있습니다. SQLite에서는 pruning 후 파일 크기가 즉시 줄어들지 않고 내부 공간이 재사용될 수 있으므로 단순 파일 크기만 보고 판단하지 않습니다.

FAQ

n8n VPS 사양 자주 묻는 질문

n8n에는 최소 몇 GB RAM이 필요한가요?

모든 self-hosted 환경에 적용되는 하나의 공식 최소 RAM 숫자는 없습니다. 실제 필요량은 workflow 데이터, peak concurrency, binary data와 같은 서버에서 실행하는 서비스에 따라 달라집니다.

production은 4 GB면 충분한가요?

n8n + PostgreSQL 소규모 production의 실용적인 시작점으로 사용할 수 있지만 보장된 기준은 아닙니다. 실제 workflow를 돌려 peak memory, CPU와 execution 지연을 확인해야 합니다.

workflow가 많으면 무조건 큰 서버가 필요한가요?

아닙니다. workflow 개수보다 동시에 실행되는 수와 각 execution이 다루는 데이터 크기가 서버 부하를 더 직접적으로 결정합니다.

AI workflow에는 GPU가 필요한가요?

OpenAI·Claude 같은 외부 API를 호출하는 경우 일반적으로 필요하지 않습니다. 로컬 모델을 같은 서버에서 실행할 때 별도의 GPU와 추가 RAM 요구가 생깁니다.
