DOCKER COMPOSE · PRODUCTION INSTALL

n8n VPS 설치: 컨테이너 실행이 아니라 운영 가능한 상태까지

n8n이 브라우저에서 열리는 순간은 설치의 중간입니다. production 완료 기준은 데이터가 재시작 후에도 남고, 외부 webhook이 HTTPS 주소로 정상 호출되며, credentials를 복호화할 키와 실제 복구 가능한 backup이 있는 상태입니다.

공식 문서 선택

Docker Compose 가이드가 두 개인 이유부터 구분하세요

일반 VPS 배포

Linux VPS에 n8n을 올리는 목적이면 cloud-provider용 Docker Compose 경로가 직접적입니다. DNS, reverse proxy, HTTPS와 persistent data를 한 흐름으로 다룹니다.

Assistant sandbox 스택

별도의 최신 Compose 가이드는 n8n Assistant용 sandbox까지 포함합니다. 여기의 4 GB RAM·2 vCPU 요구는 sandbox stack 기준이므로 일반 단일 n8n VPS의 보편 최소 사양으로 해석하면 안 됩니다.

이 페이지의 범위

여기서는 일반 VPS production 배포를 기준으로 설명합니다. 서버 크기 판단은 VPS 사양 가이드로 분리합니다.

문서가 충돌해 보일 때

설치 목적이 다른 문서를 섞지 말고, 현재 버전의 공식 변수명과 release note를 우선 확인합니다.

설치 흐름

VPS에서 n8n을 배포하는 8단계

1. VPS 준비Linux 서버, SSH 접근, 필요한 CPU/RAM/storage를 준비합니다.
2. Docker 확인Docker Engine과 Docker Compose v2를 설치하고 docker compose version으로 확인합니다.
3. DNS 연결n8n.example.com 같은 전용 subdomain을 VPS IP로 연결합니다.
4. Persistent data/home/node/.n8n이 영구 volume에 저장되도록 구성합니다.
5. Database테스트는 SQLite로 가능하지만 지속적으로 운영할 production은 PostgreSQL 구성을 검토합니다.
6. HTTPSCaddy, Nginx, Traefik 같은 reverse proxy를 앞에 두고 443으로 TLS를 제공합니다.
7. Public URLN8N_WEBHOOK_URL과 proxy 설정을 외부 HTTPS 주소에 맞춥니다.
8. 검증restart, production webhook, schedule, backup/restore와 update 절차를 실제로 시험합니다.

DOCKER COMPOSE

왜 VPS에서는 Compose가 편한가

서비스를 한 번에 정의

n8n, PostgreSQL, reverse proxy와 volumes를 하나의 구성으로 관리할 수 있습니다.

재현 가능

새 VPS로 옮길 때 설치 과정을 기억에 의존하지 않고 같은 설정으로 다시 만들 수 있습니다.

시작 전 검사

docker compose config --quiet으로 문법과 변수 치환을 확인한 뒤 docker compose up -d로 실행합니다.

상태와 로그

docker compose ps와 docker compose logs로 container 상태와 시작 오류를 바로 확인합니다.

COPY · VERIFY

배포 전에 고정할 핵심 값과 실행 순서

전체 compose 파일을 무작정 복사하기보다 공개 URL, encryption key, database와 proxy 경계를 먼저 고정하세요. n8n 2.35.0 이후 reverse proxy의 public webhook base URL은 N8N_WEBHOOK_URL이 현재 변수입니다.

N8N_ENCRYPTION_KEY=<long-random-secret>
N8N_HOST=n8n.example.com
N8N_PROTOCOL=https
N8N_WEBHOOK_URL=https://n8n.example.com/
N8N_EDITOR_BASE_URL=https://n8n.example.com/
N8N_PROXY_HOPS=1
GENERIC_TIMEZONE=Asia/Seoul
N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true

docker compose config --quiet
docker compose up -d
docker compose ps
curl -fsS https://n8n.example.com/healthz
curl -fsS https://n8n.example.com/healthz/readiness

/healthz는 프로세스가 응답하는지 확인하고, /healthz/readiness는 database 연결과 migration 완료 여부까지 확인합니다. reverse proxy가 한 단계가 아니라면 N8N_PROXY_HOPS도 실제 hop 수에 맞춰야 합니다.

DATA PERSISTENCE

컨테이너를 지워도 workflow와 credentials가 남아야 합니다

n8n data volume

공식 Docker 구성은 /home/node/.n8n에 workflow 관련 데이터와 중요한 instance 정보를 저장합니다. 이 경로는 persistent volume에 둡니다.

Encryption key

N8N_ENCRYPTION_KEY를 고정해 별도로 안전하게 보관하면 재배포나 migration 때 credentials 복호화에 필요한 키를 잃을 위험을 줄일 수 있습니다.

PostgreSQL

production에서 PostgreSQL을 사용한다면 DB volume과 DB backup도 n8n data와 별도로 관리합니다.

Container ≠ backup

실행 중인 container image를 보존하는 것만으로는 복구 계획이 되지 않습니다. data, DB, encryption key가 함께 복원돼야 합니다.

PUBLIC HTTPS

Webhook을 쓰려면 외부 주소와 proxy 설정이 맞아야 합니다

n8n은 내부에서 5678 포트로 실행되더라도 외부에서는 reverse proxy가 443 HTTPS로 노출할 수 있습니다. 이 경우 n8n이 외부 주소를 정확히 알도록 설정해야 합니다.

N8N_WEBHOOK_URL

현재 n8n 문서 기준 외부 webhook base URL입니다.

N8N_WEBHOOK_URL=https://n8n.example.com/

N8N_PROXY_HOPS

reverse proxy가 한 단계라면 N8N_PROXY_HOPS=1을 사용합니다. proxy 단계가 다르면 실제 경로에 맞춰야 합니다.

Forwarded headers

마지막 reverse proxy가 X-Forwarded-For, X-Forwarded-Host, X-Forwarded-Proto를 전달하도록 구성합니다.

5678 직접 공개

일반 production에서는 n8n의 내부 포트를 인터넷에 그대로 노출하기보다 reverse proxy 뒤에 두는 구성이 관리하기 쉽습니다.

주의: 오래된 가이드의 WEBHOOK_URL은 현재 N8N_WEBHOOK_URL의 deprecated alias입니다.

DATABASE

SQLite로 시작할 수 있지만 production에서는 DB 선택을 먼저 끝내세요

작은 테스트·단일 인스턴스

SQLite는 n8n의 기본 database이며 persistent volume을 제대로 잡으면 단일 인스턴스에서도 사용할 수 있습니다.

지속적인 production

현재 n8n의 최신 Compose 설치 가이드는 production 인스턴스에서 PostgreSQL로 교체하도록 안내합니다. 특히 확장과 Queue Mode를 고려하면 PostgreSQL을 초기에 선택하는 편이 명확합니다.

나중에 바꾸면?

새 PostgreSQL을 붙인다고 기존 SQLite 데이터가 자동으로 이동되는 것은 아닙니다. DB 선택을 초기 production 설계에서 정하는 편이 안전합니다.

Queue Mode

worker 확장 단계에서는 PostgreSQL과 Redis 구조가 필요하므로 Queue Mode 페이지에서 별도로 다룹니다.

TIMEZONE & URLS

한국에서 자주 놓치는 두 설정

Timezone

Schedule Trigger를 한국 시간 기준으로 운영한다면 container와 n8n의 timezone을 Asia/Seoul로 맞추고 예약 실행을 실제로 확인합니다.

Editor와 webhook 주소

브라우저 editor가 열리는 것만 보고 끝내지 말고 editor에 표시되는 production webhook URL이 실제 HTTPS 도메인인지 확인합니다.

UPDATE PATH

업데이트는 pull 한 번이 아니라 rollback까지 포함합니다

버전 확인

production에서는 자동으로 아무 버전이나 따라가기보다 적용할 stable 버전을 확인하고 계획적으로 업데이트합니다.

업데이트 전 backup

DB, n8n data와 encryption key를 먼저 보존합니다.

Compose 재배포

새 image를 준비한 뒤 Compose로 재기동하고 health, editor, webhook과 workflow 실행을 다시 확인합니다.

Rollback

database migration이 포함된 버전은 단순히 예전 image로 내리는 것만으로 충분하지 않을 수 있으므로 release note와 rollback 절차를 함께 확인합니다.

COMMON FAILURES

설치는 됐는데 production에서 깨지는 대표적인 경우

Webhook 주소가 localhost

reverse proxy 외부 URL이 n8n에 제대로 전달되지 않은 경우를 먼저 확인합니다.

재배포 후 credentials 오류

persistent volume 또는 encryption key가 바뀌었는지 확인합니다.

시간 예약이 틀림

container timezone과 n8n timezone 설정을 확인합니다.

DB가 새것처럼 보임

PostgreSQL volume 경로와 DB 설정이 실제 persistent volume을 바라보는지 확인합니다.

FAQ

n8n VPS Docker 설치 자주 묻는 질문

n8n은 Docker와 Docker Compose 중 무엇으로 설치하는 것이 좋나요?

단일 container 테스트는 docker run으로 가능하지만, VPS production에서는 database, reverse proxy, volumes와 업데이트를 함께 관리하기 쉬운 Docker Compose 구성이 더 실용적입니다.

reverse proxy 뒤에서 webhook URL은 무엇을 설정하나요?

n8n 2.35.0 이후 공식 문서는 외부 HTTPS 주소에 N8N_WEBHOOK_URL을 사용하고, reverse proxy 한 단계를 사용하는 경우 N8N_PROXY_HOPS=1을 설정하도록 안내합니다.

컨테이너만 backup하면 credentials도 복구되나요?

아닙니다. persistent n8n data, database와 encryption key를 함께 보존하고 실제 restore를 시험해야 credentials와 workflow 복구를 검증할 수 있습니다.
