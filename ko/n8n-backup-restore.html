DISASTER RECOVERY · 2026

n8n 백업 복구: workflow JSON과 전체 instance backup은 다릅니다

한국어 검색 결과에는 workflow JSON을 Google Drive나 파일로 저장하는 방법이 많이 나오지만, 새 VPS에서 n8n 전체를 되살리는 복구에는 그것만으로 부족합니다. 완전한 backup은 .n8n 폴더 + database + encryption key + binary/external storage + custom nodes/deployment config까지 포함해야 합니다.

VDSina VPS 보기설치 가이드

BACKUP LEVELS

먼저 “무엇을 복구하려는지”에 따라 backup 수준을 나누세요

Workflow export

개별 workflow 정의를 잃지 않기 위한 최소 보호. 다른 instance로 workflow를 옮길 때 유용하지만 사용자, execution history, instance 설정까지 복원하지는 않습니다.

CLI workflows + credentials

export:workflow --backup과 export:credentials --backup으로 workflow와 credential JSON을 분리해 보관합니다. 전체 instance backup은 아닙니다.

Full instance backup

VPS 손실, 디스크 장애, 실패한 업데이트나 전체 서버 migration에서 원래 instance를 최대한 되살리기 위한 backup입니다.

Disaster recovery

backup 파일만 있는 것이 아니라 RPO·RTO, off-site copy, 복구 순서와 실제 restore drill까지 준비된 상태입니다.

FULL INSTANCE

전체 n8n backup에 반드시 포함할 것

.n8n user folder기본 ~/.n8n. config와 credential encryption key가 있으며 SQLite를 쓰면 database 파일도 여기 있습니다.
PostgreSQL외부 PostgreSQL을 쓰면 database 자체 backup이 별도로 필요합니다. .n8n 폴더도 계속 필요합니다.
Binary / execution storagefilesystem, S3, Azure Blob 또는 custom path에 저장한 binary/execution data가 있다면 그 저장소도 backup합니다.
Custom nodesN8N_CUSTOM_EXTENSIONS로 별도 디렉터리를 쓰면 그 디렉터리도 보존합니다.
Deployment configdatabase 연결, external storage, domain/proxy, custom N8N_ENCRYPTION_KEY 등 instance를 다시 연결하는 설정을 보존합니다.
Off-site copy운영 VPS와 같은 disk 한 곳에만 backup을 두지 않습니다.

ENCRYPTION KEY

PostgreSQL이 살아 있어도 encryption key가 없으면 credentials를 못 살릴 수 있습니다

n8n은 credentials를 database에 암호화해 저장합니다. 복구된 database나 암호화된 credential export를 다시 읽으려면 원래 key가 필요합니다.

기본 key

기본 구성에서는 .n8n/config 안의 key가 중요합니다. PostgreSQL만 dump하고 이 파일을 잃으면 credential 복구가 막힐 수 있습니다.

Custom key

N8N_ENCRYPTION_KEY를 직접 설정했다면 같은 값을 안전하게 별도로 보관해야 합니다.

Decrypted export

CLI의 --decrypted 옵션은 credential을 평문으로 내보낼 수 있지만 매우 민감한 파일이 됩니다. 일반 backup 기본값으로 쓰기보다 제한된 migration 상황에서만 신중하게 사용합니다.

Restore test

복구 후 credential이 실제 API에 연결되는지 확인해야 key가 제대로 보존됐다는 것을 검증할 수 있습니다.

CLI EXPORT

CLI backup은 “workflow 이동용”과 “전체 복구용”을 구분해서 쓰세요

n8n export:workflow --backup --output=backups/workflows/
n8n export:credentials --backup --output=backups/credentials/

n8n import:workflow --separate --input=backups/workflows/
n8n import:credentials --separate --input=backups/credentials/

서로 다른 폴더

workflow와 credential backup은 다른 output 디렉터리에 저장합니다. 현재 알려진 문제 때문에 같은 폴더를 섞으면 credential import가 실패할 수 있습니다.

Container 내부만 저장하지 않기

Docker container 안의 backups/는 기본 persistent volume이 아닙니다. host bind mount나 외부 저장소로 옮깁니다.

CLI가 포함하지 않는 것

users/roles, execution history, logs, variables, instance settings와 encryption key는 CLI backup만으로 복구되지 않습니다.

ID와 활성 상태

import 파일은 기존 ID를 포함하므로 target instance에 같은 ID가 있으면 overwrite될 수 있습니다. imported workflow는 기본적으로 inactive 상태입니다.

SQLITE VS POSTGRESQL

database 방식에 따라 backup 순서가 달라집니다

SQLite

기본 SQLite를 쓰면 n8n을 멈춘 뒤 .n8n 폴더를 복사하는 것이 안전합니다. 쓰기 중인 SQLite 파일을 단순 복사하면 일관되지 않은 backup이 될 수 있습니다.

PostgreSQL

PostgreSQL은 database 도구로 일관된 dump/backup을 만들고, 동시에 .n8n 폴더의 encryption key도 보존합니다.

External binary storage

S3나 다른 외부 저장소를 쓰면 DB와 .n8n만 복원해도 binary data는 돌아오지 않습니다. 별도 backup 범위에 포함합니다.

Custom filesystem path

binary/execution data를 custom filesystem 경로에 두었다면 그 경로도 함께 backup합니다.

RESTORE BY INCIDENT

사고 유형에 따라 필요한 복구 범위가 다릅니다

Workflow 하나 삭제개별 JSON/CLI workflow export에서 복구. 다른 instance 데이터까지 되돌릴 필요는 없습니다.
잘못된 업데이트업데이트 전 full backup으로 DB + .n8n + config를 복원하고 version/rollback 호환성을 확인.
VPS 전체 손실새 서버에 deployment config, .n8n, PostgreSQL, external storage와 custom nodes까지 복원.
새 VPS로 migration원본을 멈추거나 쓰기 정지 구간을 만들고 최종 DB/data snapshot을 복원한 뒤 webhook/DNS를 전환.
Credential만 문제원래 encryption key와 credential backup이 맞는지 확인. 평문 decrypted export는 특별한 경우에만 사용.

FULL RESTORE

전체 instance 복구 순서

1. n8n 정지복구 중 새 쓰기와 충돌하지 않게 합니다.
2. .n8n 복원원래 위치에 user folder와 config/encryption key를 복구합니다.
3. PostgreSQL 복원외부 DB를 사용했다면 backup에서 database를 복원합니다.
4. External storage 복원S3/Blob/custom filesystem의 binary/execution data를 복원합니다.
5. Deployment config 복원DB 연결, encryption key, external storage, proxy/domain 환경 변수를 다시 설정합니다.
6. Custom nodes 복원workflow가 참조하는 custom extension 디렉터리를 복원합니다.
7. n8n 시작로그인과 startup logs를 확인합니다.
8. 실제 기능 검증credentials, webhook, schedule, binary data와 대표 workflow를 실행합니다.

RPO / RTO

backup 주기는 “하루 한 번”이 아니라 허용 가능한 손실 시간으로 정합니다

RPO

최대 얼마만큼의 최신 데이터를 잃어도 되는가. 예를 들어 RPO 4시간이면 하루 1회 backup은 부족합니다.

RTO

장애 후 몇 시간 안에 서비스를 다시 띄워야 하는가. 복구 매뉴얼과 자동화 수준이 RTO를 결정합니다.

3-2-1

중요한 production이라면 여러 복사본, 서로 다른 저장 매체/위치, off-site copy를 두는 방식이 기본 방어선이 됩니다.

Restore drill

분기/월 단위 등 정해진 주기로 별도 환경에 실제 복원해 봅니다. 파일 생성 성공은 restore 성공과 다릅니다.

RESTORE CHECKLIST

복구가 끝났다고 판단하기 전에 확인할 것

Owner / projectsCLI import만 한 fresh instance라면 owner/project 할당이 의도대로 되었는지 확인.
Credentials실제 외부 API 호출이 성공하는지 확인.
Workflow active stateimported workflow는 기본 inactive이므로 의도한 것만 다시 활성화.
Webhook외부 서비스에서 production webhook을 호출해 endpoint와 domain 전환을 확인.
Scheduletimezone과 예약 workflow가 정상 실행되는지 확인.
Binary data과거 execution이나 workflow가 참조하는 파일을 실제로 읽을 수 있는지 확인.
Duplicate / overwriteimport ID 충돌로 기존 workflow/credential이 덮어써지지 않았는지 확인.

BEFORE UPDATE

업데이트 전에 “되돌릴 수 있는 full backup”을 먼저 만드세요

n8n 공식 문서도 업데이트 전에 full backup을 권장합니다. production 업데이트의 완료 조건은 새 image가 뜨는 것이 아니라 문제가 생겼을 때 DB, .n8n, key와 설정을 이용해 원래 상태로 돌아갈 수 있는 것입니다.

SELF-HOSTED VPS

복구 가능한 서버를 운영하려면 backup 위치를 VPS 밖에도 두세요

VDSina 같은 self-managed VPS를 사용한다면 서버 자체와 backup 저장 위치를 같은 장애 영역 하나에만 두지 않는 것이 중요합니다. 이 사이트는 VDSina를 n8n managed backup 서비스로 표현하지 않습니다.

FAQ

n8n 백업 복구 자주 묻는 질문

workflow JSON만 백업하면 전체 복구가 가능한가요?

아닙니다. workflow 정의는 보호하지만 전체 instance 복구에는 .n8n, database, encryption key, external storage와 deployment config가 필요합니다.

PostgreSQL dump만 있으면 credentials도 복구되나요?

원래 encryption key가 없으면 암호화된 credentials를 풀 수 없을 수 있습니다. .n8n config 또는 같은 N8N_ENCRYPTION_KEY를 함께 보존하세요.

Docker 안에 backup을 만들어두면 충분한가요?

기본 container filesystem은 재생성 시 사라질 수 있습니다. host bind mount나 외부 저장소로 복사해야 합니다.

backup 성공 여부는 어떻게 확인하나요?

별도 환경에서 restore drill을 수행해 login, credentials, workflow, webhook, schedule, database와 binary data를 실제로 검증해야 합니다.
