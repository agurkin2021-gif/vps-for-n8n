백업 및 복구

n8n 백업 및 복원

자체 호스팅 n8n 을 백업 및 복원하려면 SQLite 데이터베이스 또는 일관된 PostgreSQL 덤프, 영구 .n8n 폴더 및 원래 암호화 키, 배포 구성, 모든 외부 바이너리 또는 탑재된 파일 종속성을 보호하세요. VPS 에서 암호화된 복사본을 보관하고 별도의 인스턴스에서 복구를 테스트하세요. 선택적 복구를 위해 CLI 워크플로 및 자격 증명 내보내기를 사용합니다. JSON 내보내기만으로는 전체 서버 백업이 아닙니다.

n8n 에 대해 VPS 을 선택하세요.

파트너 링크: 구매 시 수수료를 받을 수 있습니다.

빠른 체크리스트

n8n 백업이 보호해야 하는 것

데이터베이스

인스턴스에서 사용하는 PostgreSQL 데이터베이스 또는 SQLite 데이터베이스 파일을 백업합니다. 데이터베이스에는 워크플로, 자격 증명 및 실행 데이터와 같은 핵심 n8n 상태가 포함되어 있습니다.

암호화 키

정확한 n8n 암호화 키를 별도로 안전하게 보관하세요. 복원된 암호화된 자격 증명은 동일한 키에 따라 달라집니다.

영구 파일

영구 n8n 데이터 디렉터리와 탑재된 파일, 바이너리 데이터 저장소 또는 배포에 의존하는 워크플로 자산을 포함합니다.

배포 구성

스택을 다시 빌드하는 데 필요한 작성/구성 파일과 비밀이 아닌 구성을 유지합니다. 적절한 액세스 제어를 통해 비밀을 보호하세요.

두 가지 백업 수준

논리적 내보내기와 전체 재해 복구

워크플로 및 자격 증명 내보내기

n8n CLI 내보내기는 마이그레이션, 버전이 지정된 워크플로 복사본 및 선택적 복원에 유용합니다. 자격 증명은 암호화된 형식으로 내보내고 나중에 일치하는 암호화 키를 사용하여 가져올 수 있습니다. 하나의 워크플로만 복구하려면 워크플로 편집기의 점 3개 메뉴를 사용하여 해당 JSON 를 다운로드한 다음 파일에서 새 검토 워크플로 또는 격리된 인스턴스로 가져옵니다. 라이브 워크플로를 교체하기 전에 자격 증명, 워크플로 ID 및 노드 매개 변수를 확인하십시오. 워크플로 JSON 을 복원해도 전체 서버가 복원되지는 않습니다.

엔터티 내보내기

CLI 은 지원되는 데이터베이스 유형 간에 데이터를 이동하기 위해 데이터베이스 엔터티를 내보낼 수 있습니다. 실행 기록 테이블은 매우 클 수 있으므로 선택 사항입니다.

전체 인스턴스 복구

서버가 작동하지 않는 시나리오의 경우 실제 데이터베이스, 암호화 키, 영구 데이터 및 배포 종속성을 보호하세요. 워크플로 JSON 내보내기가 전체 인스턴스를 재구성한다고 가정하지 마십시오.

공급자 스냅샷

VPS 스냅샷은 추가 복구 계층으로 유용하지만 유일한 복사본이 되어서는 안 되며 독립적으로 검증된 애플리케이션/데이터베이스 백업을 대체해서는 안 됩니다.

데이터베이스

데이터베이스를 지속적으로 백업

PostgreSQL

일관된 PostgreSQL 백업 방법을 사용하고 결과 백업을 VPS 에서 멀리 저장합니다. 오류가 발생한 동일한 디스크의 데이터베이스 복사본은 재해 복구가 아닙니다.

SQLite

배포에서 SQLite 을 사용하는 경우 영구 n8n 데이터 디렉터리에서 데이터베이스 파일을 보호합니다. 데이터베이스가 수정되는 동안 안전하지 않은 상태의 데이터베이스를 복사하지 마십시오.

실행 이력

기록 실행 데이터가 복구 목표의 일부인지 결정하세요. 백업 용량이 상당히 커질 수 있으므로 보존 및 규정 준수 요구 사항에 따라 선택해야 합니다.

데이터베이스 버전

복구 환경이 호환 가능하게 준비될 수 있도록 원본 배포에서 사용되는 데이터베이스 엔진과 버전을 기록합니다.

Docker 작성 VPS 에 대한 PostgreSQL. PostgreSQL 서비스 이름이 지정된 경우 postgres 해당 데이터베이스/사용자는 둘 다입니다. n8n, 다음 명령은 호스트에 일관된 PostgreSQL 사용자 지정 형식 덤프를 생성합니다. 실제 Compose 파일을 실행하기 전에 확인하고 데이터베이스 자격 증명 및 서비스 이름을 조정하세요. pg_dump PostgreSQL 이 실행되는 동안 논리적으로 일관된 스냅샷을 생성할 수 있습니다. 그렇죠 아니 별도로 백업하세요 .n8n 사용자 폴더 또는 외부 바이너리 데이터.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

아카이브 목록 검사는 명백한 형식 문제를 포착하지만 데이터가 복원될 수 있음을 증명하지는 않습니다. 암호화된 복사본을 서버 외부에 저장하고 복원을 연습합니다. 데이터베이스별 옵션에 대해서는 공식 PostgreSQL pg_dump 문서를 사용하세요.

Docker 의 SQLite. 기본 SQLite 배포의 경우 database.sqlite 생성된 암호화 키 구성은 영구 내부에 있습니다. .n8n 폴더(일반적으로 다음 위치에 마운트됨) /home/node/.n8n). SQLite 의 단순한 Live Copy를 일관성 있는 것으로 취급하지 마십시오. 폴더를 복사하기 전에 n8n 및 기타 데이터베이스 작성자를 중지하거나 중단이 불가능할 경우 SQLite 에서 지원하는 온라인 백업 메커니즘을 사용하십시오.

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

이는 범용 볼륨 레이아웃이 아닌 표시된 서비스 및 경로에 대한 예시 명령입니다. 복사된 폴더는 처음에는 여전히 동일한 VPS 에 있습니다. 서버 외부로 전송하고 보호하세요. 큐 작업자나 다른 작성자가 있는 경우 이들도 일시 중지하고 실제 배포 설계를 따릅니다. n8n 의 현재 전체 백업 지침은 SQLite 일관성 요구 사항을 문서화합니다.

기본 SQLite 폴더를 깨끗한 대상으로 복원: 먼저 n8n 서비스와 모든 데이터베이스 작성자를 중지하십시오. 호환 가능한 n8n 서비스 컨테이너와 해당 대상 볼륨이 존재하면 백업된 .n8n 내용 뒤로 동일한 영구 디렉토리에. 이는 대상 파일을 덮어쓰므로 유지해야 하는 데이터가 있는 인스턴스에서 실행하지 마십시오.

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker 은 중지된 컨테이너에 복사할 수 있지만 대상 소유권은 원본과 다를 수 있습니다. 시작하기 전에 n8n 프로세스에서 복원된 구성 및 데이터베이스 파일을 읽고 쓸 수 있는지 확인하십시오. 실제 Compose 구성이 다른 경로나 바인드 마운트를 사용하는 경우 그에 따라 복사본을 조정하세요. Docker 사본 참조 작성. 별도의 PostgreSQL 데이터베이스를 사용하는 배포에서는 n8n 폴더만 복원하는 것만으로는 충분하지 않습니다.

중요한 비밀

암호화 키는 복구의 일부입니다

n8n 은 인스턴스 암호화 키를 사용하여 저장된 자격 증명을 암호화합니다. 일치하는 키 없이 데이터베이스 또는 암호화된 자격 증명을 내보내면 복원된 워크플로에서 저장된 자격 증명을 사용할 수 없게 될 수 있습니다.

N8N_ENCRYPTION_KEY 을 설정한 경우 정확한 비밀을 복원하세요. 그렇지 않으면 생성된 키가 영구 .n8n/config 파일에 저장됩니다. 백업하거나 재구축할 때 해당 구성을 보호하세요. 복구 키를 VPS 외부에 안전하게 저장하세요. 대기열 모드에서는 모든 기본 프로세스와 작업자 프로세스가 동일한 키를 사용해야 합니다.

마프로덕션에 사용되는 정확한 키의 보호된 사본을 보관하세요.
마자격 증명을 테스트하기 전에 복구 환경에서 해당 키를 사용하는지 확인하세요.
하지 마십시오서버를 재구축한 후 새로 생성된 키를 사용하세요.
하지 마십시오키를 공용 저장소에 커밋하거나 보호되지 않는 백업 옆에 저장하세요.

파일 및 바이너리 데이터

데이터베이스 백업이 모든 워크플로 종속성을 포괄하지 못할 수 있음

영구 .n8n 데이터

컨테이너 이미지뿐만 아니라 실제 .n8n 사용자 폴더를 찾아 보존합니다. 일반적인 Docker 배포에서는 /home/node/.n8n 에 마운트됩니다. Docker 외부에서는 기본값은 ~/.n8n 입니다. N8N_USER_FOLDER 가 구성된 경우 n8n 은 지정된 상위 디렉터리 내에 .n8n 을 생성합니다. 구성 키와 설치에서 사용하는 로컬 SQLite, 바이너리 또는 파일 시스템 실행 데이터를 포함합니다.

마운트된 워크플로 파일

워크플로가 호스트 탑재 디렉터리를 읽거나 쓰는 경우 해당 디렉터리를 별도로 백업하십시오. n8n 을 복원하지 않고 복원하면 유효한 워크플로가 손상될 수 있습니다.

바이너리 데이터

스토리지 모드를 식별하고 모든 외부 종속성을 복원합니다. 파일 시스템 기반 바이너리 또는 실행 데이터는 .n8n 또는 사용자 정의 디렉터리에 있을 수 있습니다. S3/Azure Blob 또는 기타 구성된 외부 스토리지에는 복구 가능한 자체 복사본 및 액세스 설정이 필요합니다. 데이터베이스 덤프만으로는 해당 파일을 대체할 수 없습니다.

커뮤니티 노드

커뮤니티 패키지 및 버전을 기록하고 N8N_CUSTOM_EXTENSIONS 을 통해 구성된 추가 사용자 정의 노드 디렉터리를 백업합니다. 해당 디렉토리는 .n8n; 외부에 있을 수 있습니다. 데이터베이스 및 사용자 폴더 복원만으로는 사용자 정의 노드 워크플로우를 계속 사용할 수 없게 될 수 있습니다.

오프서버 전략

동일한 VPS 의 백업은 로컬 복사본일 뿐입니다.

로컬 사본빠른 롤백에 유용하지만 서버 손실, 디스크 오류 및 파괴적인 실수에 취약합니다.
서버 외부 사본프로덕션 VPS 과 별개로 저장소에 하나 이상의 백업을 보관합니다.
버전이 지정된 복사본손상이나 잘못된 변경으로 인해 사용 가능한 유일한 백업을 덮어쓰지 않도록 여러 복구 지점을 보존합니다.
접근 통제백업에는 자격 증명, 워크플로 논리 및 민감한 비즈니스 데이터가 포함될 수 있습니다. 적절하게 암호화하고 제한하십시오.
모니터링예약된 백업이 실패하거나 새 복구 지점 생성이 중지되면 경고합니다.

일정을 측정 가능하게 만드세요. 각 성공적인 백업의 타임스탬프, 전송 완료, 파일 크기, 소스 데이터베이스 버전, 암호화 키 복구 위치 및 최근 성공한 복원 테스트를 기록합니다. 누락, 실패 또는 예기치 않게 빈 파일에 대한 경고입니다. 백업 아카이브를 VPS 로 보내기 전에 암호화하고 복구 비밀에 대한 액세스를 제한하세요. 날짜가 여러 개인 복구 지점은 최신 복사본이 마지막 정상 복사본을 덮어쓴 후에만 손상 발견을 방지합니다.

예를 들어 변경 사항 손실을 최대 6시간까지 허용할 수 있는 경우 성공적인 6시간 백업 일정은 시작점일 뿐 보장되지는 않습니다. 실패한 작업과 지연된 서버 외부 복제는 실제 손실을 증가시킬 수 있습니다. 보편적인 7 일 또는 30 일 정책을 가정하는 대신 자체 RPO/RTO 및 데이터 요구 사항에 맞게 보존 및 복원 주기를 설정하세요.

복원 주문

통제된 순서에 따라 복구

1 · 준비호환 가능한 서버, 데이터베이스, 컨테이너/런타임 환경을 프로비저닝합니다.
2 · 비밀 복원원래 n8n 암호화 키와 필수 배포 비밀을 안전하게 구성하세요.
3 · 데이터베이스 복원PostgreSQL 또는 SQLite 을 복구하고 n8n 가 예상 데이터에 연결할 수 있는지 확인합니다.
4 · 파일 복원영구 디렉터리, 바이너리 데이터 및 탑재된 워크플로 자산을 복구합니다.
5 · 시작 n8n예상되는 호스트 이름, 데이터베이스 및 환경 구성으로 애플리케이션을 시작합니다.
6 · 검증사용자, 워크플로 및 자격 증명 로드를 확인한 다음 대표적인 워크플로 및 웹훅 경로를 실행합니다.

PostgreSQL 재해 복구 예: 에 별도의 깨끗한 복원 대상 이미 올바른 데이터베이스 역할이 있고 비어 있습니다. n8n 데이터베이스, 시작 만 PostgreSQL. 가져오기 전에 정상 상태가 될 때까지 기다리십시오. docker compose up -d PostgreSQL 가 초기화되는 동안 단독으로 반환할 수 있으므로 다음과 같습니다. pg_restore 실패할 수 있습니다. 예제에서는 --wait 최신 Compose 설치에서 독립적으로 확인합니다. pg_isready. 안정적인 대기를 위해 적절한 PostgreSQL 상태 확인을 구성하거나 계속 진행하기 전에 명시적으로 준비 상태를 확인하세요. 채워진 프로덕션 데이터베이스에서 이 명령을 지정하거나 데이터베이스 및 일치 항목 이전에 n8n 을 시작하지 마십시오. .n8n 키/데이터가 복원됩니다.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

대상에는 호환 가능한 PostgreSQL 버전, 역할 권한, 확장 및 원래 n8n 구성이 있어야 합니다. 복원 .n8n 올바른 영구 볼륨에 연결하거나 백업 메커니즘을 사용하여 바인드 마운트하여 소유권과 권한을 보존합니다. 외부 바이너리 파일, 사용자 정의 확장, Compose 및 비밀 구성을 복원한 다음 호환되는 버전에서 n8n 을 시작하고 해당 로그를 확인하세요. 데이터베이스만 복원하면 키가 복구되지 않습니다. PostgreSQL 배포에서는 키를 .n8n/config 명시적으로 구성하지 않는 한 N8N_ENCRYPTION_KEY. pg_restore 참조 · n8n 전체 인스턴스 복원 순서.

깨끗한 서버가 필요한 경우 복구 VPS 를 선택하세요.

검증된 복원 훈련: SQLite 및 PostgreSQL

테스트 환경: n8n 2.42.5 일회용 GitHub 작업 실행기의 격리된 Docker 컨테이너에서 합성 2노드 워크플로를 사용합니다. 이 수표는 다음과 같이 실행되었습니다. 8 10월 2026, 고객 또는 프로덕션 n8n 서버가 아닙니다.

SQLite: 통과테스트 워크플로를 가져오고, 내보내고, 모든 작성자를 중지하고, SQLite 지원 영구 파일을 보관했습니다. .n8n 폴더 및 생성된 암호화 키를 클린 볼륨으로 복원하고 n8n 을 시작한 다음 복구된 워크플로를 다시 내보내고 실행했습니다.
PostgreSQL: 통과동일한 테스트 워크플로우를 가져오고 사용자 정의 형식을 생성 및 검사했습니다. pg_dump, 다음을 사용하여 복원했습니다. pg_restore 새로운 빈 PostgreSQL 데이터베이스에 별도의 데이터베이스를 복원했습니다. .n8n 폴더로 이동한 다음 복구된 워크플로를 다시 내보내고 실행했습니다.
PASS가 설정하는 것테스트된 백업 경로는 이 워크플로우, 두 개의 노드 및 해당 연결을 유지하고 복구 후 실행을 허용했습니다. 이는 워크로드 벤치마크가 아닌 재현 가능한 기능 연기 테스트입니다.
테스트되지 않은 것실제 자격 증명, 프로덕션 웹훅, 큐 모드 작업자 및 Redis, S3/Azure 바이너리 스토리지, 사용자 지정 노드, 사용자/프로젝트 액세스 또는 라이브 프로덕션 인스턴스 복구의 암호 해독 및 인증. 실제로 사용하는 각 종속성에 대해 별도의 드릴을 실행하세요.

재현 방법: 일회용 n8n 설치를 사용하고, 무해한 2노드 워크플로를 생성하고, 해당 데이터베이스와 영구 폴더 백업을 수행하고, 깨끗한 볼륨이나 데이터베이스로 복원한 다음 복원된 워크플로의 노드, 연결 및 실제 실행을 확인합니다. 프로덕션 시스템에서는 재해 복구가 입증되었다고 선언하기 전에 암호화된 자격 증명, 웹후크 및 외부 파일도 확인하세요.

훈련 수락 체크리스트 복원: 격리된 도메인/환경을 사용합니다. 사용자 및 워크플로가 있는지 확인하고, 기존의 암호화된 자격 증명 중 하나가 재입력 없이 인증되고, 프로덕션 웹후크가 의도한 복원된 워크플로를 호출하고, 마운트된 파일과 바이너리 첨부 파일을 읽을 수 있는 상태로 유지하고, 필수 커뮤니티 노드와의 통합이 로드되는지 확인합니다. 백업 기간, 측정된 가동 중지 시간, 서버 외부 접근성을 확인하세요. 필수 점검이 실패하면 해당 복구 지점을 표시하십시오. 확인되지 않은 백업이 완료된 것으로 보고하는 대신

CLI 백업 제한

어떤 작업흐름과 자격 증명 내보내기가 복원하지 못하는지 정확히 파악하세요.

CLI 내보내기는 전체 인스턴스 백업이 아닙니다.

워크플로 및 자격 증명 백업 내보내기에는 사용자 및 역할, 실행 기록 및 로그, 변수 또는 암호화 키와 같은 인스턴스 설정이 포함되지 않습니다.

새로운 인스턴스 복원에는 소유자가 필요합니다.

클린 인스턴스에서는 자격 증명을 가져오기 전에 소유자 설정을 완료하세요. 다중 사용자 또는 프로젝트 복원에는 올바른 사용자 또는 프로젝트 할당이 필요할 수도 있습니다.

가져온 ID는 기존 항목을 덮어쓸 수 있습니다.

워크플로 및 자격 증명 내보내기는 원래 ID를 유지합니다. 이미 동일한 ID가 포함된 인스턴스로 가져오면 기존 항목을 대체할 수 있습니다.

가져온 워크플로를 의도적으로 게시

CLI 가져오기는 일반적으로 워크플로를 비활성 상태로 둡니다. n8n 2.x에서 가져온 각 워크플로의 게시 상태를 확인하고 실행하려는 워크플로만 게시합니다. 자체 호스팅 서버 CLI 는 n8n 게시:워크플로 --id=YOUR_WORKFLOW_ID도 지원합니다. n8n 가 실행 중일 때 서버 CLI 게시/게시 취소 상태 변경 사항은 n8n 을 다시 시작한 후에만 적용됩니다. 예약된 트리거 및 프로덕션 웹후크를 확인하거나 트래픽을 전환하기 전에 다시 시작하세요.

Docker Compose에 대한 대량 내보내기 예: 귀하의 n8n 서비스 이름이 지정된 경우 n8n, 아래의 공식 CLI 백업을 실행할 수 있습니다. 출력 경로는 의도적으로 마운트된 영구 내부에 있습니다. .n8n 컨테이너 내부의 임의의 디렉터리는 다시 생성될 때 사라질 수 있기 때문입니다. n8n 컨테이너 사용자가 디렉터리에 쓸 수 있는지 확인합니다. 워크플로 및 자격 증명 JSON 유지 별도의 디렉토리—n8n 은 두 종류가 모두 디렉토리를 공유할 때의 가져오기 문제를 문서화합니다.

n8n 2.x 초안과 게시된 백업: 정상 --backup 워크플로 내보내기는 현재 초안을 캡처합니다. 이는 프로덕션에 게시된 버전과 다를 수 있습니다. 특정 워크플로우의 실제 게시된 버전을 보존하려면 다음을 사용하여 별도로 내보내십시오. docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, 출력 폴더가 존재하고 쓰기 가능한지 확인한 후. CLI 은 다음을 사용하여 기록 버전을 내보낼 수도 있습니다. --version=VERSION_ID. 전체 백업과 함께 이러한 캡처를 서버 외부에 보관합니다. 초안 JSON 이 실시간 게시 상태를 기록한다고 가정하지 마세요.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

복사된 ~/n8n-recovery/cli 디렉터리는 안전하고 독립적인 백업 위치로 이동할 때까지 여전히 VPS 에 있습니다. 자격 증명 내보내기는 기본적으로 암호화되며 가져올 때 일치하는 암호화 키가 필요합니다. 사용을 피하세요 --decrypted 엄격하게 제어되는 마이그레이션을 제외하고는 비밀을 일반 텍스트로 기록합니다. 민감한 워크플로 논리나 자격 증명이 포함된 내보내기를 공개 GitHub 저장소에 커밋하지 마세요. 일부 타사 GitHub 자격 증명 백업 템플릿은 의도적으로 해독된 비밀을 내보냅니다. 개인 저장소는 암호화가 아닌 액세스 제한입니다. 모든 템플릿의 실제 내보내기 설정 및 저장 권한을 검사하고, 서버 외부로 전송하기 전에 비밀을 암호화하고, 의도하지 않은 일반 텍스트 업로드를 통해 노출된 자격 증명을 교체하세요.

대량 가져오기 예: 깨끗한 대상에서 소유자 설정을 완료하고 원래 암호화 키를 제공하고 해당 복구 시 저장된 백업 파일을 사용할 수 있는지 확인하세요. VPS. 다음은 대상 폴더를 생성하고 workflows/ 그리고 credentials/ 호스트의 하위 폴더를 n8n 컨테이너로 Docker 볼륨 레이아웃이 다른 경우 경로를 조정합니다.

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

n8n 컨테이너 사용자의 파일 소유권과 액세스 권한을 확인하세요. 확인된 롤백 없이 채워진 프로덕션 인스턴스를 가져오지 마십시오. 워크플로 및 자격 증명 ID가 기존 항목을 덮어쓸 수 있습니다. 그런 다음 다음을 실행하십시오.

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

가져온 ID는 기존 워크플로나 자격 증명을 대체할 수 있습니다. 연습 실행을 위해 격리된 테스트 인스턴스를 사용하고 나중에 자격 증명 및 활성화/게시 상태를 확인하세요. n8n 2.x에서 JSON 초안을 복원하는 것만으로는 워크플로가 게시되었으며 예약된 트리거를 실행할 수 있음을 증명하지 않습니다. 수입 안전: 멀티 메인이 아닌 n8n 인스턴스에서는 이전에 활성화된 cron 트리거가 CLI 가져오기 이후 인스턴스가 다시 시작될 때까지 계속 실행될 수 있습니다. 복원된 작업을 활성화하기 전에 프로덕션 트리거를 중지하거나 격리하고 n8n 를 다시 시작하십시오. 중복 실행이 없는지 확인하십시오. CLI 수출은 아니 원래 사용자, 실행 로그, 인스턴스 변수 또는 암호화 키를 포함합니다. --backup 세트 --all --pretty --separate, '전체 인스턴스'가 아닙니다. 출처: 현재 공식 n8n 백업/복원 가이드 및 n8n CLI 명령 참조.

GitHub 또는 Google 드라이브 템플릿에서 대량 복원: 이는 인스턴스 데이터베이스, 사용자, 암호화된 자격 증명 값 또는 암호화 키가 아닌 워크플로 JSON 에 대한 대안입니다. API 기반 템플릿을 실행하기 전에 n8n API 및 스토리지 권한, 선택한 백업 버전 및 대상 인스턴스, 일치하는 ID를 업데이트하고 삭제된 워크플로를 다시 생성하는지 여부, 워크플로 게시로 수행되는 작업을 확인하세요. 모든 템플릿이 대상에서 누락된 ID를 다시 생성하는 것은 아닙니다. 자동 복원을 사용하기 전에 해당 시나리오를 별도로 테스트하세요.

n8n 백업 및 복원: 일반적인 질문

워크플로 내보내기가 n8n 을 백업하기에 충분합니까?

아니요. 워크플로 내보내기는 유용한 논리적 복사본이지만 전체 복구에는 자격 증명, 일치하는 암호화 키, 데이터베이스 상태, 영구 파일 및 바이너리 데이터 저장소가 필요할 수도 있습니다.

데이터베이스가 있는 경우 n8n 암호화 키가 필요합니까?

예, 계속 사용할 수 있도록 해당 데이터베이스에 저장된 암호화된 자격 증명이 필요한 경우입니다. 원래 키를 안전하게 보관하세요.

PostgreSQL 을 백업해야 합니까, 아니면 워크플로 및 자격 증명을 내보내야 합니까?

재해 복구를 위해 데이터베이스와 암호화 키를 보호하세요. 논리적 내보내기는 인스턴스의 모든 부분을 대체하는 것이 아니라 추가 마이그레이션 및 선택적 복구 계층으로 가치가 있습니다.

VPS 스냅샷이 유일한 백업이 될 수 있나요?

하나의 복구 레이어로 처리하는 것이 더 좋습니다. 공급자, 계정, 서버 또는 스냅샷 오류로 인해 모든 복구 지점이 한꺼번에 제거되지 않도록 독립적인 오프서버 백업을 유지하세요.

백업이 작동하는지 어떻게 알 수 있나요?

깨끗한 테스트 환경으로 복원하고, 자격 증명 암호 해독을 확인하고, 대표적인 워크플로를 실행하세요. 성공적인 백업 작업만으로는 복구 가능성이 입증되지 않습니다.

GitHub 또는 Google Drive 워크플로 백업에 저장된 자격증명 비밀번호가 포함되나요?

워크플로 전용 JSON 백업에는 n8n 의 자격 증명 저장소 또는 인스턴스 암호화 키에서 관리하는 비밀 값이 포함되지 않습니다. 그러나 내보낸 JSON 는 인증 헤더와 같은 노드 매개변수에 직접 입력된 자격 증명 이름과 ID 및 비밀을 노출할 수 있습니다. 내보낸 JSON 을 업로드하거나 공유하기 전에 검사하고 보호하세요. 전체 복구를 위해서는 데이터베이스와 원본 키를 백업하거나 테스트된 복원과 함께 지원되는 암호화된 자격 증명 CLI 내보내기를 사용하세요. 워크플로 전용 GitHub 또는 Google 드라이브 템플릿은 전체 재해 복구가 아닙니다.

복구 목표

사고 발생 전 RPO 및 RTO 정의

RPO 최근 변경 사항의 최대 허용 가능한 손실입니다. 독립적으로 저장된 최신 사용 가능한 복구 지점에서 측정합니다. 내보내기 또는 전송이 실패한 경우 예약된 6시간 작업은 6시간 RPO를 설정하지 않습니다. RTO 허용 가능한 최대 정전입니다. 단순히 컨테이너를 시작하는 것이 아니라 비밀 검색, 외부 파일 복원, 자격 증명 다시 확인, 복구된 워크플로 게시 등을 포함한 완전한 복원 훈련으로 이를 측정합니다.

복구 키

재구축하기 전에 원래 암호화 키 찾기

생산이 설정된 경우 N8N_ENCRYPTION_KEY, 정확한 환경 비밀을 유지하십시오. 그렇지 않은 경우 생성된 키를 원래 영구 .n8n/config에 보존하세요. 암호화된 자격 증명을 가져오기 전에 복구된 인스턴스가 실제로 사용하는 소스를 확인하세요. 새로 생성된 키는 이전 데이터베이스의 자격 증명을 해독할 수 없습니다.

제공업체를 비교하시나요?

공급자 선택, 원클릭 설정, 지원 경계, 백업, 마이그레이션, 지역 및 확장을 위해 다음을 사용하세요. n8n 비교에 가장 적합한 VPS. 리소스 크기를 조정하려면 n8n 가이드의 경우 메인 VPS.
