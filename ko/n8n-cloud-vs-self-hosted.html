DEPLOYMENT DECISION · 2026

n8n Cloud vs Self-hosted: “누가 서버를 운영할 것인가”부터 결정하세요

이 비교의 핵심은 단순히 “Cloud는 비싸고 Self-hosted는 싸다”가 아닙니다. 첫 번째 결정은 인프라를 n8n이 운영할지 내가 운영할지, 두 번째 결정은 Community·Business·Enterprise 중 어떤 기능 에디션이 필요한지입니다. 이 두 축을 섞으면 비용과 기능 비교가 틀어집니다.

QUICK VERDICT

이 네 문장으로 먼저 방향을 정할 수 있습니다

Cloud

서버·업데이트·확장·기본 인프라 운영을 직접 하고 싶지 않다면 Cloud가 맞습니다. 빠르게 시작하고 workflow 제작에 집중하는 선택입니다.

Self-hosted Community

배포 위치, 네트워크, custom 환경을 직접 통제하고 Linux/Docker 운영을 감당할 수 있다면 맞습니다. 소프트웨어 자체는 $0이지만 인프라와 운영은 무료가 아닙니다.

Self-hosted Business / Enterprise

Self-hosted라고 모든 조직 기능이 무료인 것은 아닙니다. SSO, 환경 분리, Git 기반 version control 같은 요구가 있다면 유료 에디션 비용까지 계산합니다.

Managed self-hosted

Self-hosted의 전용 instance나 데이터 위치는 원하지만 Linux 운영은 하기 싫다면 제3자 managed self-hosting도 중간 선택지입니다. provider마다 지원·backup·root 범위가 다르므로 계약 범위를 따로 확인해야 합니다.

PLAN ≠ DEPLOYMENT

Cloud/Self-hosted와 플랜·에디션은 별개의 결정입니다

Cloud Starter월 2,500 workflow executions · 5 concurrent executions · n8n hosted.
Cloud Pro월 10,000 workflow executions · 최대 50 concurrent executions · n8n hosted.
Business현재 self-hosted only · 월 40,000 executions · SSO/LDAP, 여러 환경, Git version control 등 조직 기능.
EnterpriseCloud 또는 self-hosted · custom execution volume · 더 높은 governance와 dedicated support/SLA.
Community Edition무료 self-hosted 버전. vendor execution quota 대신 실제 한계는 당신의 인프라 자원과 운영 방식이 결정합니다.

Cloud 요금은 workflow가 처음부터 끝까지 한 번 실행될 때 1 execution으로 계산되며 step 수나 workflow 복잡도 자체로 추가 계산되지 않습니다. 반대로 self-hosted Community는 vendor execution quota가 없지만 서버 자원과 안정성은 무제한이 아닙니다.

REAL COST

Self-hosted의 실제 비용은 VPS 청구서가 아니라 “운영 전체”입니다

InfrastructureVPS, storage, traffic, 추가 IP 또는 별도 database.
Backupoff-server copy, snapshot, retention과 실제 restore test.
MonitoringCPU/RAM/disk, uptime, workflow failures와 알림.
MaintenanceOS·Docker·n8n·database 업데이트와 rollback.
SecurityTLS, firewall, 접근 제어, 저장 데이터 암호화와 patching.
Human time정기 유지보수, 장애 대응, 복구와 원인 분석에 드는 담당자 시간.
Paid editionBusiness/Enterprise 기능이 필요하면 self-hosted라도 라이선스 비용을 추가.
비교식

Self-hosted TCO = 서버 + 저장소/backup + monitoring + 유료 에디션(필요 시) + 월 운영 시간 × 담당자 시간당 비용 + 장애 리스크. Cloud와 비교할 때는 같은 기간, 같은 execution volume, 같은 기능 요구로 맞춰야 합니다.

그래서 “월 $6 VPS vs Cloud 구독”처럼 인프라 하나만 비교하면 실제 비용 비교가 아닙니다. 반대로 이미 Docker/서버를 운영하는 팀이라면 추가 운영 비용이 작아져 Self-hosted가 훨씬 유리해질 수 있습니다.

COST DRIVER

Cloud에서는 workflow의 복잡도보다 실행 빈도가 비용을 바꿉니다

긴 workflow 1회

노드가 많아도 한 번 시작해 끝까지 실행되면 1 execution입니다. step 수만 늘어나는 것은 Cloud execution 수를 직접 늘리지 않습니다.

짧은 polling workflow

5분마다 실행되는 단순 workflow는 복잡한 장기 workflow보다 월 execution 수가 훨씬 커질 수 있습니다.

재시도·수동 실행

오류 재시도, 테스트, 수동 재실행과 별도 후속 workflow가 실제 월 사용량을 예상보다 키울 수 있습니다.

Self-hosted

execution 횟수보다 CPU, RAM, database, storage와 concurrency가 비용을 결정합니다. 빈도가 높아도 인프라 여유가 있으면 구독 execution 단가는 없습니다.

DATA & SECURITY

“내 서버 = 자동으로 더 안전”도, “Cloud = 데이터 통제 없음”도 너무 단순합니다

n8n Cloud

현재 n8n Cloud는 Microsoft Azure를 사용하고 고객 데이터는 유럽연합 내에 호스팅됩니다. n8n이 TLS, 저장 데이터 암호화, 네트워크 보호와 Cloud backup 운영을 담당합니다.

Self-hosted

서버 위치와 네트워크를 직접 선택할 수 있지만 TLS, 저장 데이터 암호화, firewall, patching, backup과 접근 제어도 직접 책임집니다.

Private API / internal DB

사내망이나 private subnet 안의 시스템에 직접 붙어야 하는 경우 Self-hosted가 구조적으로 유리할 수 있습니다.

Compliance

Self-hosted라는 사실만으로 compliance가 충족되지는 않습니다. 로그, retention, 접근 권한, 암호화, backup과 운영 절차가 실제 요구사항을 만족해야 합니다.

MIGRATION GAP

Cloud → Self-hosted는 “JSON export/import 한 번”으로 끝나지 않습니다

1. WorkflowsCloud에서 workflow를 export합니다. bulk export는 최신 backup 기준이라 최근 수정이 빠질 수 있어 중요한 workflow는 개별 export도 확인합니다.
2. Credentialsworkflow JSON은 credential secret을 이전하지 않습니다. Self-hosted에서 credentials를 다시 만들고 OAuth 연결은 재승인이 필요할 수 있습니다.
3. Environmentdomain, HTTPS, database, encryption key, variables와 network access를 새 환경에 다시 구성합니다.
4. WebhooksCloud URL에서 새 Self-hosted URL로 endpoint가 바뀌므로 외부 서비스의 webhook/callback 주소를 교체합니다.
5. Cutover두 환경에서 동시에 같은 trigger가 실행되지 않도록 activation 순서와 DNS/callback 전환 시간을 계획합니다.
6. Verificationcredentials, schedules, webhooks, binary data와 실패 경로를 실제로 실행해 확인한 뒤 Cloud를 종료합니다.

즉, workflow 정의를 옮기는 것과 production instance를 마이그레이션하는 것은 다른 작업입니다. 이 부분이 현재 비교 글에서 가장 자주 축약되는 지점입니다.

MIDDLE GROUND

Self-hosted가 필요하지만 서버 운영은 싫다면

검색 결과에는 managed self-hosting을 Cloud와 DIY Self-hosted 사이의 제3의 선택으로 제시하는 글이 늘고 있습니다. 다만 “managed”의 의미가 provider마다 다릅니다. OS patch만 해주는지, n8n 업데이트·backup·restore·monitoring까지 포함하는지, root와 migration 권한을 유지하는지 반드시 구분해야 합니다.

Cloud

n8n이 플랫폼을 운영. 가장 단순한 공식 hosted 경로.

DIY Self-hosted

가장 높은 인프라 통제. 운영 책임도 가장 큼.

Managed Self-hosted

전용 instance와 일부 인프라 통제를 유지하면서 운영 업무를 provider에 맡기는 중간 모델.

확인할 계약 범위

업데이트, restore, monitoring, n8n application support, root, data location, renewal과 migration 권한을 따로 확인합니다.

SELF-HOSTED OPTION

직접 운영을 선택한다면 서버는 그다음 결정입니다

Self-hosted를 선택한 뒤에야 CPU/RAM과 provider를 고릅니다. VDSina는 이 사이트에서 다루는 self-managed VPS 옵션이며, entry 서버는 $0.07/day부터입니다. 이것은 n8n managed 서비스나 preinstalled n8n이라는 뜻이 아닙니다.

FAQ

n8n Cloud vs Self-hosted 자주 묻는 질문

n8n Cloud와 Self-hosted 중 무엇이 더 저렴한가요?

보편적인 승자는 없습니다. Cloud는 execution allowance와 운영 편의를 구독으로 사고, Self-hosted는 서버와 운영 시간을 부담합니다. 이미 서버 운영 역량이 있는 팀과 그렇지 않은 팀의 손익분기점은 완전히 다릅니다.

Self-hosted n8n은 모든 기능이 무료인가요?

아닙니다. Community Edition은 무료 self-hosted 옵션이지만 일부 조직 기능은 Business/Enterprise 같은 유료 에디션에 있습니다.

Cloud에서 Self-hosted로 JSON만 옮기면 되나요?

아닙니다. workflow export 외에 credentials 재생성·OAuth 재승인, domain/HTTPS/database/network 설정과 webhook cutover가 필요합니다.

Self-hosted가 더 안전한가요?

직접 통제할 수 있는 범위는 커지지만 보안 운영도 직접 책임집니다. 잘 관리된 Cloud보다 잘못 관리된 Self-hosted가 더 안전하다고 볼 수는 없습니다.
