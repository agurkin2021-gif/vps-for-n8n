SELF-HOSTED SECURITY · 2026

n8n VPS 보안: HTTPS보다 중요한 것은 공격 경로를 줄이는 것입니다

n8n은 API key, database credential, webhook, SSH/HTTP 접근과 내부 시스템 연결을 한 instance에 모을 수 있습니다. 그래서 보안은 VPS → n8n instance → workflow/node → credentials → webhook → 복구의 여러 층으로 설계해야 합니다. 한 층만 안전해도 전체가 안전해지는 구조가 아닙니다.

VDSina VPS 보기설치 가이드

5-LAYER MODEL

보안을 5개 층으로 나누면 빠뜨릴 항목이 줄어듭니다

1. VPS / Network

SSH key, 최소 open port, OS patch, firewall, reverse proxy, HTTPS. n8n의 5678 포트를 인터넷에 직접 노출하지 않는 구성이 기본입니다.

2. Account / Access

강한 계정 보호, 2FA, 필요 최소 권한, 사용하지 않는 사용자·API key 제거.

3. n8n Application

n8n audit, risky node 제한, env/file 접근 제한, public API와 community node 검토.

4. Workflow / Webhook

webhook 인증·서명 검증, least-privilege credential, outbound HTTP/SSRF, Code/SSH/파일 접근 검토.

5. Recovery

credential 노출·실패한 update·VPS 손실 때 돌아갈 수 있도록 encryption key와 DB를 포함한 backup/restore 경로 유지.

BASELINE

처음 15분 안에 확인할 보안 기준선

HTTPS onlyeditor와 production webhook을 TLS 뒤에서 제공.

Auditn8n audit 결과를 baseline으로 저장.
Webhook민감한 endpoint가 인증/서명 검증 없이 공개되지 않았는지 확인.
BackupDB뿐 아니라 encryption key까지 실제 restore 가능한 상태인지 확인.

NATIVE AUDIT

n8n 자체 보안 감사부터 실행하세요

n8n audit

공식 security audit은 다섯 영역을 검사합니다. 이것은 penetration test가 아니라 현재 instance에서 흔한 위험을 빠르게 찾는 기준선입니다.

Credentials

사용되지 않거나 active workflow에서 쓰이지 않거나 최근 workflow에서 사용되지 않은 credential을 찾습니다.

Database

SQL node의 Execute Query/Query Parameters에 expression을 사용하는 위험 신호를 확인합니다.

Filesystem

host 파일 시스템을 읽거나 쓰는 node를 식별합니다.

Nodes

official risky nodes, community nodes, custom nodes를 보고합니다.

Instance

보호되지 않은 webhook, 누락된 security setting, 오래된 instance를 확인합니다.

PASS ≠ 안전 인증. audit은 workflow business logic, 과도한 API 권한, 잘못된 secret 공유, reverse proxy/firewall 구성 전체를 대신 검사하지 않습니다.

ACCOUNT SECURITY

2FA는 “선택 기능”보다 기본 계정 보호로 보는 편이 안전합니다

사용자별 2FA

n8n은 authenticator app 기반 2FA를 지원합니다. recovery code는 instance와 다른 안전한 장소에 보관합니다.

조직 전체 강제

현재 보안 정책을 environment variable로 관리하는 구성에서는 N8N_MFA_ENFORCED_ENABLED=true로 전체 사용자 2FA를 강제할 수 있습니다.

Least privilege

owner/admin 계정을 일상 workflow 편집용으로 남용하지 말고 필요한 권한만 줍니다.

Offboarding

퇴사·역할 변경 시 사용자, API key, 공유 credential, webhook secret과 외부 SaaS token까지 함께 회수합니다.

RISKY NODES

“사용자가 workflow를 만들 수 있다”는 것은 서버 권한으로 이어질 수 있습니다

공식 문서는 특정 node를 사용자에게서 숨기거나 막을 수 있도록 NODES_EXCLUDE를 제공합니다. 특히 shell/file-system 계열은 실제 필요가 없다면 노출 이유가 적습니다.

NODES_EXCLUDE='["n8n-nodes-base.executeCommand","n8n-nodes-base.readWriteFile"]'

Execute Command

host/container에서 명령 실행 경로가 될 수 있어 필요성·사용자 신뢰·runtime 격리를 함께 검토합니다.

Read/Write Files

filesystem 접근이 필요 없다면 block 후보입니다. 파일 접근이 필요하면 허용 경로를 최소화합니다.

Community / custom nodes

설치 전 source, maintainer, release 상태와 필요한 권한을 검토하고 사용하지 않는 package는 제거합니다.

Node block ≠ sandbox

하나의 node를 막았다고 모든 코드 실행·network 접근 위험이 사라지는 것은 아닙니다. 전체 node set과 task runner 구조를 함께 봅니다.

ENV & FILE ACCESS

workflow에서 host secret과 .n8n 파일을 읽을 수 있는 범위를 줄이세요

N8N_BLOCK_ENV_ACCESS_IN_NODE=trueexpression과 Code node에서 environment variable 접근이 필요 없다면 차단.
N8N_BLOCK_FILE_ACCESS_TO_N8N_FILES=true.n8n 디렉터리와 사용자 정의 config 파일 접근을 차단. 현재 기본값도 true입니다.
N8N_RESTRICT_FILE_ACCESS_TO=...파일 node가 접근할 수 있는 디렉터리를 allowlist 방식으로 제한.
N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=truesettings 파일에 owner read/write 중심의 0600 권한 적용을 시도.
N8N_SECURE_COOKIE=truecookie를 HTTPS에서만 전송. 현재 기본값 true.

필요한 workflow가 env/file 접근을 실제로 요구하는지 먼저 확인하고, 필요하지 않은 capability는 제거하는 방식이 안전합니다.

SSRF

HTTP Request node가 내부망·localhost·metadata endpoint로 가는 경로를 막으세요

n8n 2.12.0부터 self-hosted instance에 application-level SSRF 보호를 켤 수 있습니다. 이것은 firewall을 대체하지 않고 추가 방어층입니다.

N8N_SSRF_PROTECTION_ENABLED=true

기본 차단

활성화하면 private, loopback, link-local과 여러 reserved range를 기본적으로 차단합니다.

Redirect / DNS

redirect target과 DNS resolution도 검증해 단순한 우회 기법을 줄입니다.

내부 API 필요

합법적인 internal service가 필요하면 hostname/IP allowlist를 최소 범위로 지정합니다.

Network first

cloud metadata, internal DB, admin service는 firewall/security group/network policy에서도 차단합니다.

WEBHOOK SECURITY

공개 webhook은 “URL을 아는 사람 누구나 호출”하는 endpoint가 되지 않게 하세요

Authentication가능하면 credential/auth 기능을 사용하고 민감한 endpoint를 anonymous로 두지 않음.
SignatureStripe/GitHub 등 source가 서명 검증을 지원하면 body/header signature를 검증.
Replay / freshnesstimestamp/nonce가 제공되면 재전송 공격을 줄이도록 검증.
Rate / abusereverse proxy 또는 앞단에서 반복 요청과 비정상 traffic을 제한.
Least privilege credentialwebhook workflow가 필요 이상의 API scope를 가진 credential을 사용하지 않음.
Input validationworkflow 시작부에서 expected method/header/body/schema를 확인.

CORS는 브라우저 정책이지 webhook 인증 방식이 아닙니다. 민감한 webhook을 보호하려면 실제 인증·서명·입력 검증이 필요합니다.

CREDENTIALS

secret을 암호화하는 것과 secret의 권한을 줄이는 것은 다른 문제입니다

Encryption key

credential 복호화에 필요한 key를 backup하면서 접근 권한은 최소화합니다. key가 노출된 incident와 key가 분실된 disaster는 둘 다 위험합니다.

Scope

Google, GitHub, database, cloud token 등은 가능하면 읽기 전용·특정 project·특정 resource 범위로 발급합니다.

No hard-code

Code/Set/HTTP body 안에 secret을 평문으로 넣기보다 credential store나 외부 secret 관리 방식을 사용합니다.

Rotation

credential 노출 시 어떤 token을 폐기하고 어떤 workflow가 영향을 받는지 추적할 수 있게 inventory를 유지합니다.

PUBLIC SURFACE

인터넷에서 보이는 면적을 줄이는 것이 가장 값싼 방어입니다

Editor

필요한 사용자만 접근하도록 하고 별도 VPN/IP restriction을 적용할 수 있다면 검토합니다.

Public API

API를 사용하지 않는 instance라면 공식 disable 기능을 검토하고, 사용하는 경우 API key를 최소 권한·별도 관리합니다.

Unused webhooks

더 이상 쓰지 않는 active workflow/webhook을 비활성화해 공개 endpoint 수를 줄입니다.

Ports

공개 80/443과 관리용 SSH 등 필요한 port만 남기고 DB/Redis/n8n 내부 port는 외부에 열지 않습니다.

INCIDENT READY

“막는 보안”만큼 “터졌을 때 범위를 줄이는 보안”도 필요합니다

Credential leak외부 API token 폐기 → n8n credential 교체 → 관련 workflow 점검 → execution/log 노출 범위 확인.
Account compromise세션/접근 회수 → password/2FA/API key 교체 → 공유 workflow/credential 변경 내역 검토.
Malicious nodenode/package 제거 → host/container/network 영향 조사 → secret rotation → clean restore 검토.
Server compromise같은 host에서 “청소”만 하지 말고 신뢰 가능한 backup과 새 VPS로 rebuild하는 시나리오를 준비.
Failed updateDB + .n8n + encryption key를 포함한 full backup에서 rollback/restore할 수 있어야 함.

SELF-HOSTED VPS

VPS provider가 n8n application 보안을 대신해 주는 것은 아닙니다

VDSina 같은 self-managed VPS를 선택해도 n8n 계정, node, webhook, credential, application update와 backup 정책은 사용자가 설계해야 합니다. provider의 24/7 infrastructure support와 n8n managed security는 같은 의미가 아닙니다.

FAQ

n8n VPS 보안 자주 묻는 질문

HTTPS만 설정하면 충분한가요?

아닙니다. HTTPS는 전송 구간만 보호합니다. 서버 port/SSH, 사용자 2FA, risky node, env/file 접근, webhook, SSRF, credentials와 restore를 함께 관리해야 합니다.

n8n 자체 보안 점검 명령이 있나요?

n8n audit가 있습니다. credentials, SQL expression, filesystem node, risky/community/custom nodes, unprotected webhook, missing security settings와 outdated instance를 점검합니다.

Execute Command 같은 node를 막을 수 있나요?

네. NODES_EXCLUDE로 특정 node를 사용자에게서 차단할 수 있습니다. 공식 문서는 Execute Command와 Read/Write Files from Disk를 대표적인 검토 대상으로 제시합니다.

SSRF protection을 켜면 firewall은 필요 없나요?

아닙니다. n8n 공식 문서도 network-level firewall/security group/network policy를 1차 방어선으로 두고 SSRF protection은 추가 방어층으로 설명합니다.
