VPS 에 대한 n8n 보안

VPS 에서 n8n 을 보호하려면 n8n(5678), PostgreSQL(5432) 및 선택 사항인 Redis(6379)을 공용 인터넷에서 차단하세요. HTTPS 역방향 프록시, SSH 키 및 MFA 를 사용하고, 암호화 키를 보존하고, 웹후크를 인증하고, 위험한 워크플로 기능을 제한하고, 배포된 인스턴스를 감사합니다. 공개 웹훅 경로와 별도로 편집기를 보호하세요. HTTPS 만으로는 연결된 서비스가 보호되지 않습니다.

n8n 에 대해 VPS 을 선택하세요.

빠른 체크리스트

공개되기 전 최소 보안 기준

연결 가능한 포트, HTTPS, 확인된 관리 액세스, MFA 및 저장된 자격 증명 보호부터 시작하세요. 민감한 작업을 트리거하기 전에 들어오는 각 웹후크를 인증하세요. 액세스 제어를 변경한 후 의도한 편집기와 외부 통합이 여전히 작동하는지 확인한 다음 n8n 보안 감사를 실행하세요.

HTTPS 만

올바르게 구성된 TLS 역방향 프록시 뒤에 n8n 을 배치하고 편집기와 웹훅에 대해 공개 HTTPS URL을 일관되게 사용합니다.

최소한의 열린 포트

공용 트래픽에 필요한 포트만 노출합니다. PostgreSQL, Redis 및 내부 애플리케이션 포트를 공용 인터넷에서 분리하세요.

강화 SSH

키 기반 관리를 사용하고, 로그인할 수 있는 사람을 제한하고, 운영 체제 패치를 유지하세요.

자격 증명을 보호하세요

n8n 암호화 키를 안정적이고 비밀스럽게 유지하세요. 환경 파일, 데이터베이스 액세스 및 백업 복사본을 민감한 자산으로 취급하십시오.

네트워크 엣지

역방향 프록시, HTTPS 및 신뢰할 수 있는 헤더

TLS 종료

HTTPS 을 종료하려면 Nginx, Caddy 또는 Traefik과 같은 역방향 프록시를 사용하세요. 일반 HTTP 를 리디렉션하고 프록시가 의도된 진입점일 때 n8n 애플리케이션 포트를 직접 노출하지 마세요.

프록시 구성

n8n 이 역방향 프록시 뒤에서 실행되는 경우 프록시 홉 수를 올바르게 구성하고 n8n 이 원래 클라이언트 요청을 재구성하는 데 필요한 전달된 헤더를 전달합니다.

안전한 쿠키

인증 쿠키가 안전하게 유지될 수 있도록 HTTPS 을 통해 편집자에게 서비스를 제공하세요. 쿠키 보안을 약화시켜 손상된 TLS 설정을 해결하지 마십시오.

웹훅 URL

생성된 웹훅 엔드포인트가 내부 컨테이너 또는 HTTP 주소를 가리키지 않도록 공개 웹훅 URL을 외부에서 연결할 수 있는 HTTPS 호스트 이름으로 설정하세요.

웹훅을 중단하지 않고 편집기를 비공개로 유지하세요. 가능하다면 VPN, 신뢰할 수 있는 IP 정책 또는 인증된 프록시를 사용하여 관리 액세스를 제한하세요. 공개 웹훅 수신기 및 OAuth 콜백 경로는 계속 연결 가능해야 할 수 있습니다. 프록시 규칙을 시행하기 전에 신뢰할 수 있는 편집자 로그인과 실제 외부 콜백을 모두 테스트하세요. 임의의 요청 헤더가 아닌 신뢰할 수 있는 프록시에서만 클라이언트 주소 헤더를 전달하세요.

웹훅 호출자를 인증합니다. Webhook 노드에서 보낸 사람이 지원하는 경우 없음 대신 기본, 헤더 또는 JWT 인증을 선택합니다. 그것을 사용하십시오 IP 허용 목록 적절한 경우 옵션을 선택하고 통합이 서명된 요청을 지원하는 경우 공급자 서명을 확인하세요. 추측하기 어려운 URL은 충분한 인증이 아닙니다. 적절한 경우 프록시에 속도 제한을 적용하고 유효한 버스트가 차단되지 않았는지 확인하십시오. 공식 Webhook 인증 옵션.

VPS 강화

서버 공격 표면 감소

방화벽

원치 않는 인바운드 트래픽을 기본적으로 거부하고 연결해야 하는 서비스만 허용합니다. 데이터베이스 및 Redis 포트는 일반적으로 개인/로컬 네트워크에 속합니다.

SSH

비밀번호보다 SSH 키를 선호하고, 불필요한 로그인 경로를 비활성화하고, 관리 액세스를 제한하세요. 루트와 동등한 액세스는 엄격하게 제어되어야 합니다.

OS 업데이트

Linux 호스트 및 컨테이너 런타임을 패치합니다. 애플리케이션 강화는 노출되거나 더 이상 사용되지 않는 운영 체제를 보완할 수 없습니다.

컨테이너 노출

호스트 액세스가 필요한 포트만 게시하세요. 내부 서비스는 공용 인터페이스가 아닌 개인 Docker 네트워크에서 통신해야 합니다.

방화벽 또는 SSH 설정을 변경하기 전에 검사하십시오. 청취 포트를 확인하십시오 sudo ss -lntp, Docker 게시: docker compose ps 프로젝트 디렉터리 및 호스트 방화벽 정책에서 sudo ufw status verbose UFW를 사용하는 경우. 비밀번호 액세스를 비활성화하기 전에 별도의 세션에서 실제 SSH 포트와 성공적인 키 로그인을 확인하세요. 게시된 Docker 포트는 UFW 규칙을 우회할 수 있습니다. 방화벽 상태 페이지만으로는 포트 5678 가 개인용임을 증명할 수 없습니다. 실제 외부 연결 가능성을 확인하세요. Docker/UFW 주의 사항.

작동한다고 가정하는 대신 자동 Ubuntu 보안 업데이트를 확인하세요. 검사하다 apt-config dump APT::Periodic::Unattended-Upgrade 그리고 로그 /var/log/unattended-upgrades/unattended-upgrades.log. 무인 보안 업그레이드가 비활성화된 경우, sudo dpkg-reconfigure unattended-upgrades 지원되는 구성 대화 상자를 제공합니다. 작동 중인 VPS 에서 활성화하기 전에 재부팅 및 서비스 재시작 동작을 검토하세요. Ubuntu APT 업데이트는 아니 n8n Docker 이미지 또는 모든 타사 소프트웨어 저장소를 자동으로 업데이트합니다. Ubuntu 자동 업데이트 문서.

선택적 SSH 무차별 모니터링: Fail2Ban은 반복적으로 실패한 SSH 로그인을 감지할 수 있습니다. SSH 에 대해 설치 및 구성된 경우 다음을 사용하여 감옥을 확인하십시오. sudo fail2ban-client status sshd 실제 SSH 인증 로그 또는 저널을 읽고 구성된 포트와 일치하는지 확인하세요. 이는 SSH 키 및 네트워크 제한을 보완합니다. 그것은 그들을 대체하지 않습니다. 기존 액세스를 먼저 확인하지 않고 고정 SSH 포트 또는 금지 규칙을 복사하지 마십시오. Ubuntu SSH 강화 지침.

데이터베이스 및 Redis

백엔드 서비스를 비공개로 유지

일반적인 Docker Compose 설정에서 PostgreSQL 및 대기열 모드 Redis 는 호스트 게시 포트가 아닌 개인 네트워킹을 통해 관련 컨테이너에서 연결할 수 있어야 합니다. 확인 docker compose ps 5432 및 6379 은 공개적으로 게시되지 않습니다. VPS/클라우드 방화벽 노출을 별도로 검토하세요. 네트워크 정책은 최소 권한 데이터베이스 자격 증명을 대체하지 않습니다.

PostgreSQL원격 액세스가 명시적으로 필요하고 독립적으로 보호되지 않는 한 개인 인터페이스 또는 컨테이너 네트워크에 바인딩합니다.
Redis대기열 모드 Redis 은 공용 엔드포인트가 아닌 인프라입니다. 이를 필요로 하는 n8n 구성 요소에 대한 네트워크 액세스를 제한합니다.
자격 증명애플리케이션에 필요한 권한만 있는 전용 데이터베이스 자격 증명을 사용하고 소스 제어 외부에서 보호하세요.
운송데이터베이스 트래픽이 신뢰할 수 없는 네트워크를 통과하는 경우 애플리케이션 수준 자격 증명 암호화에 의존하기보다는 적절한 암호화된 전송을 사용하십시오.

N8N 비밀

암호화 키 및 자격 증명 경계를 보호하세요.

암호화 키

n8n 은 암호화 키를 사용하여 저장된 자격 증명을 암호화합니다. 재시작 및 작업자 간에 동일한 키를 유지하고 일반 애플리케이션 콘텐츠와 별도로 보호합니다.

환경 비밀

비밀번호, 토큰 또는 암호화 키를 공개 저장소에 커밋하지 마십시오. 환경 파일 및 배포 비밀에 대한 액세스를 제한합니다.

사용자 액세스

신뢰할 수 있는 사용자에게만 편집자 액세스 권한을 부여하세요. 워크플로는 민감한 시스템에 연결할 수 있으며 비밀을 처리하거나 강력한 노드를 실행할 수 있습니다.

자격 증명 범위

가능하면 범위가 좁은 서비스 계정과 API 토큰을 사용하세요. 손상된 워크플로는 관련 없는 시스템에 대한 광범위한 액세스를 자동으로 상속해서는 안 됩니다.

n8n 검토할 구성: N8N_BLOCK_ENV_ACCESS_IN_NODE=true 환경 값에 대한 코드 노드 및 표현식 액세스를 방지합니다. N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true 설정 파일에 대한 소유자 전용 권한을 요청합니다. 유지하다 N8N_ENCRYPTION_KEY 지속적이고 안전하게 백업됨: n8n 은 처음 시작할 때 임의의 키를 생성할 수 있지만 이를 분실하면 기존의 암호화된 자격 증명을 사용할 수 없게 될 수 있습니다. 프로덕션 암호화 키를 임의로 교체하지 마십시오. 공식적으로 지원되는 교체 절차를 사용하세요. 환경 액세스를 차단하면 기존 통합이 중단될 수 있으므로 프로덕션 변경 전에 테스트하세요. n8n 보안 변수 정의.

워크플로 위험

노드는 보안 경계를 확장할 수 있습니다.

자체 호스팅은 워크플로에 상당한 힘을 제공합니다. 코드 실행, 셸 액세스, 임의 HTTP 요청 및 타사 커뮤니티 노드는 위험을 증가시킬 수 있습니다. 필요하지 않은 기능을 비활성화하고 신뢰할 수 없는 워크플로 가져오기를 실행하기 전에 검토하십시오.

정확하게 지원되는 컨트롤을 사용하세요. 구성 NODES_EXCLUDE 비활성화할 JSON 노드 배열을 사용합니다. n8n-nodes-base.executeCommand 그리고 n8n-nodes-base.readWriteFile, 미사용인 경우. 일부 고위험 노드는 최신 버전에서 기본적으로 이미 차단되어 있습니다. 변경하기 전에 실제 목록을 검토하세요. 공식 노드 제외.

n8n 부터 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true 내부, 루프백 및 메타데이터 주소 범위에 대한 아웃바운드 HTTP 요청을 확인할 수 있습니다. 합법적인 내부 API 작업 흐름이 작동을 멈출 수 있습니다. 필요한 경우 귀하가 제어하는 ​​대상만 허용 목록에 추가하세요. 네트워크 세분화를 기본 방어 수단으로 유지하십시오. 코드 노드 격리의 경우 외부 작업 실행기를 검토하세요. SSRF 보호 · 작업 실행기 격리.

커뮤니티 노드신뢰할 수 있는 패키지만 설치하세요. n8n 환경 내에서 실행됩니다.
위험한 노드해당 기능이 의도한 워크플로 경계를 초과하는 경우 배포에 필요하지 않은 노드를 제외합니다.
SSRF워크플로가 내부 또는 메타데이터 엔드포인트에 도달할 수 없어야 하는 경우 n8n 의 SSRF 보호 및 네트워크 제어를 사용하세요.
워크플로 가져오기활성화하기 전에 가져온 워크플로, 자격 증명, 표현식 및 실행 가능한 단계를 검토하세요.

감사 및 업데이트

보안은 운영 프로세스이다

n8n 보안 감사 실행

공식 CLI 명령은 다음과 같습니다. n8n audit. Docker Compose 서비스 이름이 지정된 경우 n8n, 달리다 docker compose exec -T n8n n8n audit 해당 배포 디렉터리에 있습니다. 미사용 자격 증명, 위험한 SQL 쿼리 패턴, 파일 시스템 액세스, 위험한/커뮤니티 노드, 보호되지 않은 웹후크 및 오래된 릴리스를 포함한 인스턴스 위험 등 5가지 범주를 검토합니다. 관련 발견 사항을 수정하고 다시 실행하세요. 이것은 침투 테스트가 아닙니다. 공식 감사 가이드.

의도적으로 업데이트

보안 수정 사항을 받을 수 있을 만큼 n8n 을 최신 상태로 유지하세요. 인터넷 연결 인스턴스를 영구적으로 오래된 상태로 두는 대신 릴리스 노트를 검토하고 중요한 업그레이드를 테스트하십시오.

모니터 인증

예상치 못한 액세스 패턴, 워크플로 변경 및 실패를 관찰하세요. 운영 모델에 광범위한 공개 접근성이 필요하지 않은 경우 편집기 UI를 더 제한합니다.

롤백 및 복구 준비

중요한 업그레이드 전에 복구 가능한 백업을 수행하십시오. 자세한 백업 범위 및 복원은 별도의 복구 가이드에 속합니다.

민감한 실행 기록을 최소화합니다. 성공적인 실행은 고객 데이터와 토큰을 유지할 수 있습니다. 적절한 설정 시 EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, 유지 EXECUTIONS_DATA_PRUNE=true을 선택하고 EXECUTIONS_DATA_MAX_AGE 몇 시간 안에 168 (7일). 이는 법적 보관 규칙이 아닌 구성 가능한 예시입니다. 기록이 적다는 것은 디버깅 및 포렌식 데이터가 적다는 것을 의미합니다. 실행 중, 대기 중 또는 주석이 달린 실행은 같은 방식으로 정리되지 않을 수 있습니다. 공식적인 집행 유지.

의심되는 손상: 증거를 파괴하지 않고 악의적인 액세스를 제한하고, 프록시, 호스트 및 n8n 활동과 변경된 워크플로를 검사하고, 노출되었을 수 있는 업스트림 자격 증명을 취소 또는 교체하고, 원인을 패치하고, 필요할 경우 테스트된 복구 가능한 백업에서만 복원합니다. 영향을 받은 웹훅 URL, 편집자 계정 및 연결된 서비스를 검토하세요. HTTPS, 스냅샷 또는 VPS 구매가 사고 대응 서비스를 제공한다고 가정하지 마십시오.

배포 순서

생산 워크플로우를 활성화하기 전에 스택을 보호하세요

1VPS 을 패치하고 제어된 관리 액세스를 생성하고 방화벽을 구성합니다.
2프라이빗 컨테이너/네트워크 경계에 n8n 및 PostgreSQL 을 배포합니다.
3자격 증명을 저장하기 전에 암호화 키와 배포 비밀을 구성하세요.
4역방향 프록시, HTTPS, 공개 호스트 이름, 전달된 헤더 및 웹훅 URL을 추가합니다.
5사용자, 노드 및 네트워크 연결성을 워크플로에 실제로 필요한 것으로 제한합니다.
6보안 감사를 실행하고 백업을 확인한 다음 프로덕션 워크플로를 공개합니다.
새로운 보안 배포를 위해 VPS 을 선택하세요.

파트너 링크: 구매 시 수수료를 받을 수 있습니다.

계정 및 플랫폼 제어

편집자와 VPS 를 보호하세요.

더 강력한 로그인 보호가 필요합니다

귀하의 에디션이 중앙 집중식 정책 시행을 지원하는 경우 편집자 계정에 대해 2단계 인증을 활성화하고 MFA~n8n 보안 정책을 시행하세요.

워크플로를 편집할 수 있는 사람 제한

편집자 액세스는 특권 액세스입니다. 워크플로는 자격 증명을 읽고, 내부 시스템을 호출하고, 강력한 노드를 실행할 수 있습니다. 사용자 액세스 범위를 좁히고 더 이상 필요하지 않은 계정을 제거하세요.

사용하지 않는 기능 비활성화

불필요한 경우 공개 API 을 비활성화하고 운영 모델에 필요하지 않은 고위험 노드나 기능을 차단하여 애플리케이션 공격 표면을 줄입니다.

SSRF 및 비밀 제어를 의도적으로 사용

임의의 HTTP 요청을 할 수 있는 워크플로의 경우 n8n 의 SSRF 보호를 평가하고 워크플로 코드, 공개 저장소 및 광범위하게 읽을 수 있는 환경 파일에서 비밀을 유지하세요.

사용하지 않는 관리 엔드포인트를 제한합니다. N8N_PUBLIC_API_DISABLED=true n8n 공개 REST API 을 비활성화합니다. N8N_PUBLIC_API_SWAGGERUI_DISABLED=true API 놀이터를 별도로 비활성화합니다. 통합에 해당 기능이 필요하지 않은 경우에만 이 작업을 수행하십시오. REST API 을 비활성화하면 워크플로 웹훅 URL이 인증되지 않습니다. 편집자 사용자에게는 MFA 를 사용하고, n8n 버전이 이를 지원하는 경우에만 중앙 집중식 정책을 사용하십시오.

공식 문서: 공개 API · 보안 정책 변수 · 감사 명령을 비활성화합니다.

자주 묻는 질문

n8n VPS 보안: 일반적인 질문

n8n 포트가 직접 노출되어야 합니까?

역방향 프록시가 공용 진입점인 경우 불필요한 서비스를 광범위하게 게시하는 대신 프록시를 노출하고 그 뒤에 애플리케이션 포트를 유지하십시오.

PostgreSQL 또는 Redis 을 공개해야 합니까?

일반적으로 아니요. 이를 필요로 하는 시스템에서만 접근할 수 있어야 합니다. 공개 노출은 정상적인 n8n 작업을 지원하지 않고도 공격 표면을 증가시킵니다.

n8n 암호화 키가 왜 중요한가요?

n8n 에 의해 저장된 자격 증명을 보호하며 배포 전반에 걸쳐 일관성을 유지해야 합니다. 이를 분실하면 복구된 데이터에서 사용 가능한 암호화된 자격 증명을 생성하지 못할 수 있습니다.

커뮤니티 노드는 안전한가요?

타사 코드로 n8n 을 확장하므로 자체 공급망 및 권한 위험이 있는 소프트웨어 종속성으로 처리되어야 합니다. 신뢰하고 필요한 것만 설치하세요.

HTTPS 는 자체 호스팅 n8n 인스턴스를 안전하게 보호합니까?

HTTPS 은 운송을 보호합니다. 프로덕션 보안에는 호스트 강화, 액세스 제어, 프라이빗 백엔드 서비스, 비밀 보호, 안전한 워크플로 기능, 모니터링 및 업데이트도 필요합니다.

프로덕션 웹훅이 계속 실행되는 동안 n8n 편집기를 비공개로 설정할 수 있나요?

그렇습니다. 신뢰할 수 있는 역방향 프록시 또는 VPN은 공개 프로덕션 웹훅 및 OAuth 콜백 경로와 별도로 편집자/관리자 액세스를 제한할 수 있습니다. 실수로 통합이 차단되는 것을 방지하려면 액세스 규칙이 변경될 때마다 신뢰할 수 있는 로그인 및 외부 웹후크 전달을 테스트하세요.

들어오는 n8n 웹훅을 어떻게 인증하나요?

발신자가 지원하는 경우 Webhook 노드에서 기본, 헤더 또는 JWT 인증을 구성합니다. IP 허용 목록을 사용하고 가능한 경우 공급자 서명을 확인할 수도 있습니다. 비밀스러워 보이는 경로에만 의존하지 말고 민감한 API 작업을 트리거하기 전에 요청을 검증하십시오.
