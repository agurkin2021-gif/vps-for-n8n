SCALING N8N · 2026

n8n Queue Mode: Redis를 넣기 전에 regular concurrency부터 확인하세요

Queue Mode는 “workflow가 많다”는 이유로 켜는 기능이 아닙니다. 목표가 단일 instance 과부하 방지라면 먼저 concurrency 제한으로 해결할 수 있습니다. main에서 실행을 분리하고 여러 worker로 수평 확장해야 할 때 Queue Mode가 필요한 것입니다.

FIRST DECISION

Queue Mode 전에 regular mode concurrency limit으로 충분한지 확인하세요

Regular + limit

한 서버에서 계속 운영하되 production execution이 동시에 너무 많이 실행되어 event loop와 메모리를 압박하는 것이 문제라면 N8N_CONCURRENCY_PRODUCTION_LIMIT으로 먼저 제한할 수 있습니다.

Queue Mode

실행 자체를 main과 분리하고 worker를 추가·제거하며 처리량을 수평 확장해야 한다면 Queue Mode가 맞습니다.

중요한 차이

regular concurrency control은 “한 instance 안에서 몇 개를 동시에 실행할지”를 제한합니다. Queue Mode는 “누가 실행할지”를 main과 worker로 분리합니다.

무조건 빠른 것은 아님

Queue Mode는 Redis와 DB hop을 추가합니다. 낮은 트래픽·낮은 latency가 우선이면 단순한 regular mode가 더 효율적일 수 있습니다.

ARCHITECTURE

Queue Mode는 main·Redis·worker·PostgreSQL의 분산 실행 구조입니다

Main→Redis→Worker↔PostgreSQL

Main

timer와 webhook을 받고 execution을 생성하지만 production workflow 로직은 worker로 넘깁니다.

Redis

pending execution ID를 보관하고 다음 worker에게 전달하는 message broker입니다. workflow 데이터의 영구 저장소가 아닙니다.

Worker

Redis에서 job을 가져오고 PostgreSQL에서 workflow 정보를 읽어 실제 execution을 수행한 뒤 결과를 DB에 기록합니다.

PostgreSQL

모든 process가 공유하는 persistent database입니다. 분산 Queue Mode를 SQLite로 운영하는 것은 지원되지 않습니다.

NON-NEGOTIABLES

Queue Mode 전환 전에 맞춰야 하는 공통 조건

PostgreSQLmain과 모든 worker가 동일한 PostgreSQL을 사용.
Redismain과 worker가 동일한 queue backend에 연결. 외부 Redis라면 private network, auth/TLS를 검토.
Encryption keymain, worker, webhook processor가 같은 N8N_ENCRYPTION_KEY를 사용해야 credentials를 복호화할 수 있음.
n8n version분산 process 간 버전을 맞춰 운영.
Binary storageQueue Mode는 filesystem binary storage를 지원하지 않으므로 persistent binary가 필요하면 S3 external storage를 사용.
Backup전환 전 PostgreSQL, .n8n, encryption key와 설정의 복구 지점을 확보.

MINIMUM CONFIG

최소 Queue Mode 구성

EXECUTIONS_MODE=queue
DB_TYPE=postgresdb
QUEUE_BULL_REDIS_HOST=redis
QUEUE_BULL_REDIS_PORT=6379
N8N_ENCRYPTION_KEY=<same-key-on-main-and-workers>

# worker
n8n worker --concurrency=10

Redis username/password/TLS, DB credentials, host/domain 등 production 설정은 환경에 맞게 별도로 구성합니다. Redis 6379나 PostgreSQL 5432를 공용 인터넷에 그대로 노출하는 구성은 피합니다.

CONCURRENCY

worker 수보다 “총 동시 실행 × DB connection”을 먼저 계산하세요

현재 공식 문서 기준 worker concurrency 기본값은 10이며 n8n은 worker당 5 이상을 권장합니다. 낮은 concurrency의 worker를 너무 많이 만드는 방식은 PostgreSQL connection pool을 소진해 처리 지연과 실패를 만들 수 있습니다.

Worker concurrency

n8n worker --concurrency=10처럼 worker 하나가 동시에 처리할 job 수를 정합니다.

Global production limit

N8N_CONCURRENCY_PRODUCTION_LIMIT을 설정했다면 queue mode에서도 유효한 상한으로 작동할 수 있으므로 worker flag와 함께 확인해야 합니다.

DB connection

worker와 concurrency를 늘릴수록 PostgreSQL connection/I/O가 새로운 bottleneck이 될 수 있습니다.

실제 병목

CPU 100%가 아니어도 외부 API wait, DB I/O, 큰 payload, binary data가 병목일 수 있으므로 worker 추가 전에 측정합니다.

MANUAL EXECUTIONS

production 실행과 수동 실행이 같은 경로를 쓰는 것은 아닙니다

Queue Mode에서 production execution은 worker가 처리합니다. 그러나 현재 기본 설정에서는 manual execution이 main에서 실행될 수 있습니다. 수동 실행까지 worker로 보내려면 OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=true를 검토합니다.

왜 중요한가

production은 worker로 잘 분산되는데 editor에서 큰 manual test를 돌릴 때 main이 느려지는 현상을 설명할 수 있습니다.

운영 확인

“Queue Mode인데 왜 main CPU가 오르지?”를 볼 때 manual execution과 webhook/UI load를 먼저 분리해 확인합니다.

BINARY DATA

PDF·이미지·오디오 workflow라면 storage가 Queue Mode의 선행 조건입니다

공식 문서는 Queue Mode와 filesystem binary storage 조합을 지원하지 않습니다. 여러 worker가 persistent binary data를 다뤄야 한다면 S3 external storage 같은 공유 object storage 구조가 필요합니다.

DB만 공유하면 부족

workflow 상태는 PostgreSQL에서 공유해도 binary 파일이 worker 로컬 disk에만 있으면 다른 process가 읽을 수 없습니다.

메모리도 capacity

큰 파일은 worker RAM, network, object storage I/O까지 영향을 주므로 단순 execution 수만 보고 capacity를 계산하지 않습니다.

WEBHOOK SCALE

worker를 늘렸는데 webhook 수신이 병목이면 webhook processor를 분리하세요

Queue Mode에서는 webhook 요청을 받은 process가 execution을 Redis에 넣고 worker가 실제 workflow를 수행하므로 약간의 overhead가 생깁니다. 요청 수신 자체가 병목이면 별도 webhook processor를 load balancer 뒤에 두는 단계가 필요할 수 있습니다.

Main 보호

UI/API와 고빈도 webhook intake가 같은 main 자원을 놓고 경쟁하지 않게 역할을 분리할 수 있습니다.

Response size

현재 공식 문서에서 worker→webhook response relay 기본 상한은 64 MiB이며, 응답이 전송 중일 때 Redis는 응답 크기의 약 1.5배 메모리를 사용할 수 있습니다.

큰 응답

큰 binary/JSON 응답을 자주 반환하면 worker 수뿐 아니라 Redis memory와 response design도 capacity 계획에 포함합니다.

HEALTH & OBSERVABILITY

Queue Mode는 worker가 살아 있는지보다 “DB와 Redis까지 준비됐는지”를 봐야 합니다

QUEUE MODE ≠ HA

worker 여러 개는 고가용성 전체를 의미하지 않습니다

Worker redundancy

한 worker가 내려가도 다른 worker가 execution을 처리할 여지는 생깁니다.

Single main

main이 하나면 UI/API, trigger orchestration 측면에서 단일 장애점이 남을 수 있습니다.

Redis / PostgreSQL

각각 한 instance라면 Queue Mode를 켜도 여전히 single point of failure가 될 수 있습니다.

Multi-main

여러 main을 쓰는 HA 구성은 별도 기능이며 self-hosted Enterprise에서 제공됩니다. load balancer sticky session 등 추가 구성이 필요합니다.

MIGRATION PATH

Single instance에서 Queue Mode로 넘어가는 안전한 순서

1. Measure현재 concurrency, CPU/RAM, execution latency와 DB 부하를 기록.
2. Try regular limit목표가 과부하 제어라면 먼저 regular concurrency limit으로 해결되는지 확인.
3. BackupDB, .n8n, encryption key와 deployment config를 복구 가능하게 backup.
4. PostgreSQLSQLite라면 Queue Mode 전에 PostgreSQL로 이전하고 정상 동작 검증.
5. Redisprivate queue backend를 추가하고 auth/connectivity 확인.
6. One worker한 worker로 production execution, credentials, webhook 결과를 검증.
7. Healthhealth/readiness, DB connections, Redis와 execution metrics 확인.
8. Scalequeue depth가 지속적으로 쌓일 때 worker/concurrency를 단계적으로 증가.

FAILURE PATTERNS

Queue Mode에서 자주 놓치는 실패 원인

Encryption key 불일치

worker가 DB의 credentials를 복호화하지 못합니다.

SQLite 유지

분산 Queue Mode의 shared DB 요구와 맞지 않습니다.

Worker만 증설

PostgreSQL pool/I/O 또는 Redis가 먼저 포화되면 처리량이 늘지 않습니다.

Manual test 착시

production은 worker로 가도 manual execution은 main에서 돌 수 있어 “queue가 안 된다”고 오해할 수 있습니다.

Filesystem binary

분산 worker가 persistent binary data를 공유할 수 없는 구조가 됩니다.

Queue Mode = HA 가정

main/Redis/PostgreSQL redundancy를 따로 설계하지 않으면 단일 장애점이 남습니다.

SELF-HOSTED VPS

Queue Mode는 VPS 한 대를 고르는 문제보다 서비스 수가 늘어나는 문제입니다

VDSina 같은 self-managed VPS에서도 n8n, PostgreSQL, Redis와 worker를 구성할 수 있지만, Queue Mode 자체가 managed n8n 기능으로 제공된다는 뜻은 아닙니다. 실제 배치는 CPU/RAM과 장애 격리 요구에 따라 한 서버 또는 여러 서버로 나눠야 합니다.

FAQ

n8n Queue Mode 자주 묻는 질문

n8n이 느려지면 바로 Queue Mode로 바꿔야 하나요?

아닙니다. 먼저 실제 bottleneck과 concurrency를 확인하세요. 단일 instance를 보호하는 것이 목적이면 regular production concurrency limit으로 충분할 수 있습니다.

Redis와 PostgreSQL이 둘 다 필요한가요?

네. Redis는 execution queue 전달용이고 PostgreSQL은 main과 worker가 공유하는 persistent database입니다. SQLite 기반 분산 Queue Mode는 지원되지 않습니다.

worker concurrency는 얼마가 적당한가요?

현재 기본값은 10이고 공식 문서는 worker당 5 이상을 권장합니다. 하지만 CPU/RAM뿐 아니라 DB connection과 queue depth를 보고 조정해야 합니다.

Queue Mode면 HA까지 끝난 건가요?

아닙니다. worker scaling과 전체 고가용성은 다릅니다. main, Redis, PostgreSQL redundancy는 별도 설계가 필요하고 multi-main은 self-hosted Enterprise 기능입니다.
