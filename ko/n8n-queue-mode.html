n8n 대기열 모드

대기열 모드는 워크플로 실행을 기본 n8n 프로세스와 분리합니다. 기본 인스턴스는 트리거를 수신하고 실행을 생성하며, Redis 은 대기열을 조정하고, 작업자는 작업을 실행하며, PostgreSQL 는 공유 워크플로 및 실행 데이터를 저장합니다.

빠른 결정

실제로 대기열 모드가 필요합니까?

다음과 같은 경우 일반 모드를 유지하세요.

단일 인스턴스는 최대 실행을 편안하게 처리하고 CPU, RAM 및 실행 대기 시간을 안정적으로 유지합니다. 대기열 모드는 아직 필요하지 않은 구성 요소를 추가합니다.

다음과 같은 경우 대기열 모드를 고려하세요.

지속적인 병렬 실행은 경합을 일으키고, 로드 시 실행 지연 시간이 증가하거나, 여러 작업자를 실행하여 실행 용량을 추가해야 합니다.

다음과 같은 경우 수직으로 먼저 크기를 조정하세요.

병목 현상은 CPU 또는 RAM 만으로는 충분하지 않으며 하나의 더 큰 인스턴스가 여전히 작업 부하를 깔끔하게 충족할 수 있습니다.

아키텍처를 변경하기 전 측정

최대 동시성, CPU, RAM, 실행 기간, 대기열 깊이 및 데이터베이스 압력을 사용하여 이동을 정당화합니다.

아키텍처

n8n 대기열 모드 작동 방식

1 · 메인타이머, 웹후크 및 워크플로 요청을 수신하고 프로덕션 실행 자체를 수행하는 대신 실행을 생성합니다.
2 · Redis메시지 브로커 역할을 합니다. 다음으로 사용 가능한 작업자가 작업을 요청할 수 있도록 보류 중인 실행 메시지를 보관합니다.
3 · 근로자실행 ID를 수신하고, 공유 데이터베이스에서 워크플로 데이터를 로드하고, 워크플로를 실행하고 결과를 다시 씁니다.
4 · PostgreSQL공유된 지속적인 워크플로 및 실행 데이터를 제공합니다. SQLite 에서는 분산 대기열 모드가 지원되지 않습니다.

핵심 요구사항

모든 대기열 모드 배포에 필요한 것

Redis

모든 기본 및 작업자 프로세스에는 대기열 조정에 사용되는 Redis 서비스에 대한 안정적인 액세스가 필요합니다.

PostgreSQL

메인과 작업자는 데이터베이스를 공유해야 합니다. 대기열 모드는 분산 아키텍처이므로 SQLite 을 기준으로 설계하면 안 됩니다.

n8n 구성 일치

기본 및 작업자는 대기열 모드를 실행하고 Redis, PostgreSQL 및 암호화된 자격 증명에 액세스하는 데 필요한 구성을 공유해야 합니다.

작업자 역량

작업자는 자신이 실행하는 워크플로에 충분한 CPU 및 RAM 가 필요합니다. 프로세스를 추가해도 각 실행의 리소스 비용이 제거되지는 않습니다.

기존 자체 호스팅 스택에서 대기열 모드를 활성화합니다. 먼저 n8n 기본 서비스와 모든 작업자가 개인 네트워크를 통해 동일한 PostgreSQL 데이터베이스 및 Redis 에 연결할 수 있는지 확인합니다. 세트 EXECUTIONS_MODE=queue 주 작업자와 작업자 모두 및 공급 장치에 대해 QUEUE_BULL_REDIS_HOST=redis 그리고 QUEUE_BULL_REDIS_PORT=6379 언제 redis 실제 Compose 서비스 이름입니다. 사용 DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres 그리고 매칭 DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER 그리고 DB_POSTGRESDB_PASSWORD 모든 프로세스에서; 예제 서비스 이름을 귀하의 이름으로 바꾸십시오. 정확한 기존 정보 제공 N8N_ENCRYPTION_KEY 그들 모두에게. 단순히 동일한 Compose 네트워크의 컨테이너를 연결하기 위해 Redis 또는 PostgreSQL 호스트 포트를 게시하지 마십시오.

두 번째 편집기가 아닌 실행기를 시작합니다. 기본과 동일한 고정된 n8n 이미지 버전 및 공유 설정을 사용하여 n8n 작업자 서비스를 추가하되 worker 명령. 해당 서비스의 이름을 지정했다면 n8n-worker, 시작해 보세요 docker compose up -d n8n-worker. 하나의 작업자에 대한 실제 실행을 확인한 후 사용할 수 있습니다. docker compose up -d --scale n8n-worker=2 해당 서비스에서 두 번째 작업자를 시작합니다. 이것들은 다음에 대한 추가 사항입니다. 기존에 올바르게 구성됨 독립 실행형 설치 파일이 아닌 스택을 작성하십시오. 기존 영구 볼륨, HTTPS 프록시, 비밀 및 백업을 유지하세요.

기존 스택에 대한 대기열 모드 Compose 조각입니다. 아래 예시를 현재 예시로 병합하세요. compose.yaml; 그것은이다 아니 완전한 독립 실행형 배포. 그것은 당신이 이미 지속적이고 개인적인 것을 가지고 있다고 가정합니다. postgres 그리고 n8n 서비스, 기존 N8N_VERSION 귀하의 환경에 고정하고 귀하 자신을 보호하십시오 POSTGRES_PASSWORD 그리고 원본 N8N_ENCRYPTION_KEY. 이름, 볼륨, 데이터베이스 및 n8n 버전을 기존 프로젝트와 일치시킵니다. 대기열 모드 Redis 설정을 추가하고 EXECUTIONS_MODE=queue 위에서 설명한 대로 기존 기본 서비스에도 적용됩니다.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Redis 또는 이 조각의 작업자에 대해 호스트 포트가 게시되지 않습니다. Redis 추가 전용 지속성은 추가 복구 계층입니다. 아니 서버 외부 백업을 대체합니다. 기존 HTTPS 및 인증 구성을 변경하지 않고 유지합니다. 외부 작업 실행기가 필요한 코드 노드의 경우 작업자 배포를 위한 실행기 프로세스를 별도로 구성하십시오. 대기열 모드 자체는 작업 실행기를 대체하지 않습니다.

기존 SQLite 인스턴스를 변환하시나요? 단순히 바꾸지 말고 DB_TYPE 빈 PostgreSQL 데이터베이스에 대해 시작합니다. 그렇게 해도 이전 워크플로와 자격 증명은 마이그레이션되지 않습니다. 컷오버 전에 소스 데이터베이스를 영구 백업합니다. .n8n 디렉터리 및 원래 암호화 키 지원되는 n8n 내보내기/가져오기 또는 마이그레이션 절차를 사용한 다음 별도의 대상에서 워크플로 및 암호화된 자격 증명을 확인하세요. 롤백을 위해 원본 파일을 보관하고, 복구 준비를 위해 아래 링크된 백업 및 복원 가이드를 활용하세요. 삭제하지 않음 database.sqlite 단축키로.

작업자 동시성

작업자는 수와 작업자당 작업을 기준으로 확장됩니다.

각 작업자는 여러 작업을 동시에 처리할 수 있습니다. n8n 의 현재 기본 작업자 동시성은 10 이며 문서에서는 5 이상의 동시성을 권장합니다. 많은 작업자와 결합된 매우 낮은 동시성은 불필요한 데이터베이스 연결을 생성하고 데이터베이스 연결 풀을 고갈시킬 수 있습니다.

동시성을 높이는 경우

작업자에게는 여분의 CPU 및 RAM 이 있고 워크플로는 컴퓨팅이나 메모리를 포화시키기보다는 대부분 외부 서비스를 기다리고 있습니다.

다음과 같은 경우 작업자를 추가하세요.

하나의 작업자 프로세스가 병목 현상을 일으키고 데이터베이스, Redis 및 인프라는 더 많은 병렬 실행을 위한 용량을 갖습니다.

동시성을 줄이는 경우

개별 워크플로는 메모리를 많이 사용하거나 CPU 을 많이 사용하며 병렬 작업은 경합, OOM 압력 또는 불안정한 실행 시간을 유발합니다.

PostgreSQL 보기

더 많은 작업자와 더 많은 동시성으로 인해 데이터베이스 활동이 증가합니다. 데이터베이스 용량 없이 실행 용량을 확장하면 병목 현상을 제거하기보다는 오히려 이동할 수 있습니다.

실제로 적용되는 동시성 제한을 알아보세요. 작업자는 다음을 사용하여 시작할 수 있습니다. n8n worker --concurrency=5또는 Compose 서비스의 동등한 작업자 명령입니다. 만약에 N8N_CONCURRENCY_PRODUCTION_LIMIT 명시적으로 다른 값으로 설정되었습니다. -1, 해당 설정은 대기열 모드에서 우선 적용됩니다. 그렇지 않은 경우 n8n 은 근로자의 --concurrency 값 또는 기본값인 10 입니다. 작업자 수에 명목상 기본값을 곱하지 말고 보장된 처리량이라고 부르세요. 실제 용량은 작업 기간, CPU, 메모리, 외부 API 및 PostgreSQL 연결에 따라 달라집니다.

웹훅

대기열 모드는 실행 핸드오프 대기 시간을 추가할 수 있습니다.

기본 또는 웹훅 프로세스는 HTTP 요청을 수신하지만 작업자가 워크플로 실행을 수행합니다. Redis 을 통한 핸드오프는 약간의 오버헤드를 추가합니다. 지연 시간에 민감한 웹후크의 경우 더 많은 작업자가 자동으로 모든 요청을 더 빠르게 한다고 가정하는 대신 엔드투엔드 응답 시간을 측정합니다.

수신기본/웹훅 프로세스가 요청을 수락합니다.
대기열실행은 Redis 에 전달됩니다.
실행사용 가능한 작업자가 워크플로를 실행합니다.
응답하다결과는 필요할 때 대기열 경로를 통해 다시 전달됩니다.

웹훅 트래픽을 올바른 프로세스로 라우팅합니다. 전용으로 n8n webhook 역방향 프록시 또는 로드 밸런서 뒤의 프로세서, 프로덕션 경로 라우팅 /webhook/* 그리고 /webhook-waiting/* 웹훅 프로세서에; 유지하다 /webhook-test/*, 편집자 및 메인에 대한 API 요청. 추가된 워크로드를 의도적으로 수락하지 않는 한 프로덕션 웹훅 로드 밸런싱 풀에 main을 넣지 마십시오. 에이 웹훅에 응답 워크플로는 작업자가 완료하고 응답을 반환할 때까지 클라이언트를 기다리게 할 수 있으므로 대기열 모드는 즉각적인 HTTP 응답이나 시간 초과 제로를 약속하지 않습니다. 트래픽을 전환하기 전에 실제 외부 콜백 및 응답 동작을 테스트하십시오.

바이너리 데이터

공유 스토리지를 간과하지 마세요

파일 시스템 제한

대기열 모드는 분산 작업자를 위한 공유 지속성 모델로 파일 시스템 바이너리 데이터 저장소를 지원하지 않습니다.

외부 바이너리 저장소

워크플로가 분산된 작업자 간에 이진 데이터를 유지해야 하는 경우 지원되는 외부 개체 스토리지와 같이 모든 필수 인스턴스가 액세스할 수 있는 스토리지 설계를 사용하세요.

대규모 웹훅 응답

작업자의 웹훅 응답은 수신 프로세스로 다시 이동합니다. 큰 응답 본문은 Redis 메모리 압력을 증가시킬 수 있으며 의도적인 응답 저장 구성이 필요할 수 있습니다.

인력 배치 전 계획

로컬 파일에 크게 의존하는 워크로드는 작업자가 여러 컴퓨터에 분산되기 전에 공유 지속성을 위해 다시 설계되어야 합니다.

큰 웹훅 응답 경계. 현재 n8n 문서는 다음을 제공합니다. N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX 기본값 64 MiB 대기열을 통해 다시 전송된 작업자의 응답입니다. Redis 는 전송 중에 여러 복사본을 보유할 수 있으므로 동시 대규모 응답당 Redis 메모리의 응답 크기를 약 1.5 배로 예산을 책정합니다. 오프로드하지 않으면 작업자를 추가하여 마술처럼 더 빨라지는 대신 대규모 응답이 실패합니다.

버전 및 라이센스 제한. n8n 부터 2.34.0, 작업자가 사용할 수 있습니다. N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true 대용량 웹훅 응답 본문을 읽기 가능한 공유 바이너리 저장소로 오프로드하지만 먼저 업그레이드합니다. 모든 메인 및 웹훅 프로세서 2.34.0 이상으로. 선택된 N8N_DEFAULT_BINARY_DATA_MODE 실제로 데이터를 저장하고 참여하는 모든 프로세스에서 읽을 수 있어야 합니다. 외부 S3 및 Azure 바이너리 스토리지에는 유효한 자체 호스팅이 필요합니다. 비즈니스 또는 기업 라이센스; Community Edition이 이를 활성화할 수 있다고 가정하지 마십시오. 는 database 바이너리 모드는 유료 외부 저장소 없이 대용량 응답을 오프로드할 수 있지만 기본 인스턴스는 저장된 전체 본문을 메모리에 로드하고 데이터베이스 저장소에는 자체 파일 크기 제한이 있습니다. 에 대한 구체적으로 응답 본문 오프로드, n8n 에서는 공유 항목도 설명합니다. filesystem 옵션은 모든 인스턴스가 동일한 디스크를 마운트할 때 사용되지만 해당 배열을 명시적으로 권장하지는 않습니다. 분산 대기열 모드 배포에서 파일 시스템 기반 영구 바이너리 데이터를 지원하기 위해 이 특수 오프로드 경로를 착각하지 마십시오. 오프로드를 활성화하기 전에 에디션, 버전 및 스토리지 구성을 확인하세요.

대기열이 도움이 되는지 확인

대기열 깊이

작업자가 소모하는 것보다 빠르게 증가하는 대기열은 실행 용량이 부족하거나 다운스트림 병목 현상이 있음을 나타냅니다.

근로자 CPU & RAM

작업자당 포화도 및 메모리 피크를 측정합니다. 대기열이 늘어나는 유휴 작업자는 또 다른 제약 조건을 가리킵니다.

실행 대기 시간

워크플로 런타임 자체뿐만 아니라 실행 생성과 실제로 시작 사이의 지연을 추적합니다.

건강검진

작업자 상태 엔드포인트는 작업자가 살아 있는지, 해당 데이터베이스와 Redis 연결이 준비되었는지 여부를 보고할 수 있습니다.

녹색 컨테이너뿐만 아니라 작업자의 실행을 확인합니다. 올바르게 구성된 Compose 스택을 사용하여 확인하세요. docker compose ps 그리고 docker compose logs --tail=100 n8n-worker (다른 경우 서비스 이름을 바꾸십시오). 무해한 실행 출판물 예약된 트리거를 사용하거나 웹후크를 테스트한 다음 n8n 의 실행 보기의 실행을 작업자 로그의 실제 작업자 처리와 일치시킵니다. 성공적으로 열리는 편집기, 실행 중인 Redis 컨테이너 또는 대기 중인 실행만 실행됩니다. 아니 근로자가 해당 업무를 수행했음을 증명합니다.

종속성과 준비 상태를 확인하세요. 기본 예제 서비스 이름을 사용하면 docker compose exec -T redis redis-cli ping 받아야 한다 PONG Redis 인증이 허용하는 경우 docker compose exec -T postgres pg_isready -U n8n -d n8n PostgreSQL 준비 상태를 확인합니다(자격 증명 및 서비스 이름 조정). 활성화 QUEUE_HEALTH_CHECK_ACTIVE=true 비공개가 필요할 때 작업자에 대해 /healthz 그리고 /healthz/readiness 엔드포인트; 준비 끝점은 Redis/database 연결을 확인합니다. 단지 모니터링을 위해 해당 작업자 엔드포인트를 공개적으로 노출하지 마세요.

수동 실행은 다른 테스트입니다. 기본적으로 OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, 따라서 대기열 모드가 올바르게 구성된 경우에도 편집기에서 워크플로를 수동으로 실행하면 기본에서 실행될 수 있습니다. 다음으로 설정하세요 true 작업자에게 수동 실행을 보내려고 하고 스테이징 환경에서 변경 사항을 확인한 경우에만 가능합니다. 대기열 모드 작업자는 코드 노드 실행을 위한 별도의 구성 요구 사항이 있는 n8n 외부 작업 실행자와도 구별됩니다.

확장 경로

한 번에 하나의 병목 현상 확장

1 단계PostgreSQL 이 포함된 단일 n8n 인스턴스; 피크 CPU, RAM 및 동시성을 측정합니다.
2 단계수직 확장으로 측정된 병목 현상이 여전히 깔끔하게 해결되면 VPS 리소스를 늘리세요.
3 단계지속적인 병렬 요구가 분산 실행을 정당화하는 경우 Redis 및 작업자를 도입합니다.
4 단계PostgreSQL, Redis 및 실행 대기 시간을 관찰하면서 작업자를 추가하거나 작업자 동시성을 조정합니다.
5 단계용량, 가용성 또는 운영 요구 사항이 추가된 복잡성을 정당화하는 경우에만 서버 전체에 구성 요소를 분리하십시오.
확장이 필요한 경우 더 많은 VPS 용량을 선택하세요.

고가용성 경계

대기열 모드는 실행을 확장하지만 기본 프로세스의 가용성을 자동으로 높이지는 않습니다.

암호화 키 공유

모든 작업자는 동일한 것을 사용해야 합니다. N8N_ENCRYPTION_KEY 작업자가 워크플로 실행에 필요한 자격 증명을 해독할 수 있도록 기본 인스턴스로 사용합니다.

버전 정렬 유지

기본, 웹훅 및 작업자 프로세스는 동일한 n8n 버전을 실행해야 합니다. 혼합 버전은 롤링 변경 중에 호환되지 않는 동작을 일으킬 수 있습니다.

웹훅 프로세서는 별도의 확장 레이어입니다.

수신 웹훅 볼륨에 병목 현상이 발생하면 작업자가 실행을 처리하는 동안 전용 웹훅 프로세서가 로드 밸런서 뒤에 있을 수 있습니다. 측정된 요청 볼륨이 정당화되지 않는 한 이 레이어를 추가하지 마십시오.

멀티메인은 다른 기능입니다

고가용성을 위해 여러 기본 프로세스를 실행하는 것은 일반 대기열 모드와 다릅니다. n8n 에는 현재 추가 로드 밸런서 및 세션 요구 사항이 있는 자체 호스팅 엔터프라이즈 기능으로 멀티 메인이 설명되어 있습니다.

자주 묻는 질문

n8n 대기열 모드: 일반적인 질문

n8n 대기열 모드에는 Redis 이 필요합니까?

그렇습니다. Redis 은 기본 인스턴스와 작업자 간에 보류 중인 실행을 조정하는 메시지 브로커입니다.

대기열 모드에서 SQLite 을 사용할 수 있나요?

분산 대기열 모드 아키텍처의 경우 아니요. 메인 및 작업자는 공유 데이터베이스 액세스가 필요하며 이 설정을 위한 데이터베이스로 n8n 문서 PostgreSQL 가 필요합니다.

얼마나 많은 작업자를 운영해야 합니까?

보편적인 카운트가 없습니다. 측정된 동시성 및 작업자 활용도에서 시작한 다음 PostgreSQL, Redis, CPU, RAM 및 대기열 깊이를 모니터링하면서 용량을 추가합니다.

n8n 작업자 동시성이란 무엇입니까?

작업자가 동시에 처리할 수 있는 작업 수입니다. 현재 기본값은 10 이며, n8n 에서는 동시성이 낮은 작업자를 많이 만드는 것보다 5 이상의 작업자 동시성을 권장합니다.

소규모 VPS 에서 대기열 모드를 활성화해야 합니까?

워크로드가 이를 정당화하는 경우에만 가능합니다. 하나의 인스턴스로 편안하게 실행되는 소규모 배포는 일반적으로 Redis 및 별도의 작업자 없이 작동하기가 더 간단합니다.
