NUSXALANG VA MOSLASHTIRING

n8n-ni VPS-ga Docker Compose orqali o‘rnating

Bu misoldan o‘zingiz boshqaradigan Linux VPSda n8n o‘rnatilishini yaratish uchun foydalaning. n8n-ni o‘zingiz o‘rnatasiz va unga xizmat ko‘rsatasiz; hamkorimiz orqali server tanlash oldindan o‘rnatilgan n8n instansini o‘z ichiga olmaydi. Misol n8n, PostgreSQL, tashqi task runner va Caddy HTTPS-ni yopiq Compose tarmog‘ida birlashtiradi. Bu konfiguratsiya shabloni, live muhitda sinovdan o‘tgan deployment haqidagi da’vo emas.

Eng tez yangi o‘rnatish kerakmi? n8n rasmiy bir qatorli Docker o‘rnatish usulini ham beradi. Skriptni ishga tushirishdan oldin curl -fsSL https://get.n8n.io -o get-n8n.sh komandasi bilan yuklab olib tekshirishingiz, keyin sh get-n8n.shni ishga tushirishingiz mumkin. Bu variant lokal URL-da SQLite bilan boshlang‘ich instansni ishga tushiradi va n8n Assistant sandbox servislarini ham qo‘shadi; u bir xil emas ushbu ochiq HTTPS va PostgreSQL asosidagi VPS o‘rnatilishi bilan. Rasmiy to‘liq sandbox steki yengil n8n o‘rnatilishidan ko‘proq RAM va CPU talab qiladi (Compose qo‘llanmasida kamida 4 GB RAM / 2 vCPU ko‘rsatilgan). Internetga ochiq production VPS uchun quyidagi qo‘lda sozlanadigan stek bilan davom eting.

1. Docker, DNS va kirishni tayyorlang

sudo huquqi bilan SSH orqali ulang va n8n.example.com uchun DNS A record-ni VPS IPv4 manzilingizga yo‘naltiring. Quyidagi yangi Ubuntu 22.04, 24.04 yoki 26.04 VPS-da quyidagi komandalar Docker Engine va zamonaviy docker compose pluginini Docker-ning rasmiy imzolangan apt repository-sidan o‘rnatadi:

# Fresh official Ubuntu 22.04 / 24.04 / 26.04 installation
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Register Docker's signed apt repository
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

Bu rasmiy Docker Ubuntu o‘rnatish qo‘llanmasidagi production-ga yo‘naltirilgan repository usuli. Konteynerlar yoki boshqa saytlar allaqachon ishlayotgan VPS-da Docker-ni ko‘r-ko‘rona qayta o‘rnatmang yoki o‘chirmang; avval mavjud o‘rnatish va ehtimoliy paket to‘qnashuvlarini tekshiring. Debian yoki boshqa distributiv uchun Ubuntu komandalarini emas, tegishli rasmiy OS-specific ko‘rsatmalarni ishlating.

Endi Docker, Compose plugini, DNS va ishchi papkani tekshiring:

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

Agar getent hosts manzil qaytarmasa yoki noto‘g‘ri manzil ko‘rsatsa, Caddy-ni ishga tushirishdan oldin DNS-ni tuzating; ushbu qo‘llanmadagi n8n.example.com ni haqiqiy hostname-ingiz bilan almashtiring. Docker odatda root huquqlarini talab qiladi: SSH foydalanuvchingiz keyingi docker compose komandalarini bevosita bajara olmasa, ularning oldiga sudoqo‘shing. Foydalanuvchini docker guruhiga qo‘shish root-ga teng huquq beradi, shuning uchun umumiy serverda buni ehtiyotsizlik bilan qilmang.

Firewall-ni yoqishdan oldin haqiqiy SSH administrator portingiz ochiq qolishini tekshiring. Sertifikat olish va editor uchun kiruvchi HTTP (80) va HTTPS (443) ga ruxsat bering. Docker e’lon qilgan konteyner portlari ayrim UFW qoidalarini chetlab o‘tishi mumkin, shuning uchun Docker firewall yo‘riqnomasini ko‘rib chiqing va faqat kerakli Caddy portlarini e’lon qiling. Ushbu Compose misoli ataylab emas PostgreSQL (5432), n8n (5678) yoki task-runner broker (5679) portlarini internetga ochmaydi.

2. Environment qiymatlarini yarating va kalitni saqlang

Loyiha papkasidan uchta turli tasodifiy hexadecimal qiymat yarating:

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

Quyidagi nom bilan fayl yarating: .env Quyidagi shablondan foydalanib, har bir REPLACE_WITH_RANDOM_HEX ni alohida yaratilgan qiymat bilan almashtiring, hostname va timezone-ni ham o‘zgartiring. Ko‘rsatilgan 2.42.5 tag — 2026-yil 8-oktabrda stable sifatida ko‘rsatilgan reliz, bu yerda sanasi ko‘rsatilgan konfiguratsiya misoli sifatida ishlatiladi, live muhitda sinovdan o‘tgan deployment yoki kelajakdagi xavfsizlik kafolati emasO‘rnatishdan oldin amaldagi rasmiy n8n relizlarini tekshiring, keyin n8n va uning task-runner image-larini bir xil tekshirilgan versiyada saqlang.

# .env — replace the three example secrets
# Pin a maintained n8n release; keep n8n and runner equal.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

Hech qachon .env faylini ochiq repozitoriyga commit qilmang. Shifrlash kaliti va tiklash ko‘rsatmalarini VPS-dan tashqarida xavfsiz saqlang. Konteyner qayta yaratilganda yoki migratsiyada kalit o‘zgarmasligi kerak.

3. Yangi o‘rnatish uchun compose.yaml yozing

Shu papkada compose.yamlfaylini yarating. Misolda rasmiy n8n environment variable konvensiyalari va PostgreSQL 18 uchun PGDATA path-dan foydalaniladi; u n8n hosting loyihasida hujjatlashtirilgan:

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

To‘rtta servisning vazifasi alohida: PostgreSQL ma’lumotlar bazasi holatini saqlaydi, n8n ish jarayonlarini bajaradi, n8n-runner mos versiya va umumiy authentication token bilan runner vazifalarini bajaradi, Caddy esa ochiq HTTPS-ni boshqaradi. Tashqi task runner Redis queue mode emas. Faqat Caddy host portlarini e’lon qiladi. Ushbu yengil misolda o‘rnatish uchun bitta database role ishlatiladi; PostgreSQL huquqlarini kuchliroq ajratish uchun rasmiy n8n PostgreSQL deployment misolini ko‘ring.

4. HTTPS Caddyfile yarating

Fayl yarating: Caddyfile (katta C harfi, extension yo‘q), compose.yamlyonida. Misoldagi hostname-ni hamma joyda o‘z DNS nomingiz bilan almashtiring:

n8n.example.com {
    reverse_proxy n8n:5678
}

Domen to‘g‘ri resolve bo‘lsa va tashqi trafik 80/443 portlariga yetib borsa, Caddy ochiq TLS sertifikatlarini so‘raydi va yangilaydi. DNS-ni localhostga yo‘naltirmang. Caddy o‘rniga boshqa reverse proxy ishlatsangiz, asl host, protocol va client-address header-larini uzating va N8N_PROXY_HOPS ni haqiqiy ishonchli proxy hop soniga moslang.

5. Konteynerlarni ishga tushiring va tashqaridan tekshiring

Loyiha papkasida, quyidagi fayllarni saqlagandan keyin komandalarni ishga tushiring: .env, compose.yaml and Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

Oxirgi komanda ochiq HTTPS health endpoint-ni tekshiradi. Sertifikat hali berilmagan bo‘lsa, n8n ishlamayapti degan xulosaga kelishdan oldin Caddy loglari va DNS/portlarni tekshiring. Ochish: https://n8n.example.com, birinchi owner account-ni darhol yarating va mos sign-in himoyalarini yoqing. Faqat editor ochilishini emas, instans haqiqatan workflow bajarayotganini tekshiring:

  1. Editorda Webhook triggerli workflow yarating. HTTP Method ni GETga o‘rnating, Path vps-checkni tanlang va Respond ni Immediatelyga o‘rnating. Workflow-ni saqlang.
  2. Bosing: Listen for Test Eventto‘liq Test URL ni n8n-dan nusxalang va boshqa qurilmadan ishga tushiring: curl -i 'PASTE_TEST_URL_HERE' nusxalangan URL bilan. HTTP muvaffaqiyat javobini va kelgan event n8n editorida paydo bo‘lishini kuting. Test URL faqat n8n event-ni tinglayotganda ishlaydi.
  3. Publish workflow-ni publish qiling, node-ni Production URLga o‘tkazing, nusxalang va yana ishga tushiring: curl -i 'PASTE_PRODUCTION_URL_HERE' Workflow-ning Executions tabida bajarilishni tekshiring. Production webhook so‘rovlari uchun workflow published bo‘lishi kerak va ularning payload-i editor test view-da ko‘rinmaydi.

Bu ataylab sodda, autentifikatsiyasiz smoke test: unga hech qachon secret yubormang. Testdan keyin uni unpublish/delete qiling yoki real ma’lumot uchun ochiq endpoint ishlatishdan oldin Webhook authentication/IP restriction sozlang. Rasmiy Webhook test/production hujjatlarini ko‘ring.

6. Birkiktirilgan versiyalarni o‘zgartirishdan oldin zaxiralang

Tiklash mumkin bo‘lgan PostgreSQL dumpni and doimiy n8n data volume, .env/shifrlash kaliti va zarur tashqi fayllarni ushbu serverdan tashqaridagi saqlash joyiga saqlang. Production-ni yangilashdan oldin zaxira nusxa va tiklash qo‘llanmasi yordamida restore-ni tekshiring. Misol komandalar:

# Back up the database, encryption key, instance data,
# and files before changing the pinned versions.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# After securing the backup outside this VPS:
docker compose pull
docker compose up -d
docker compose ps

Biriktirilgan N8N_VERSION ni faqat release note-larni o‘qigandan keyin o‘zgartiring; n8n va runner image birga yangilanishi kerak. Ishga tushirmang: docker compose down -v oddiy maintenance paytida, chunki bu named data volume-larni o‘chiradi. PostgreSQL major version o‘zgarishi database upgrade yoki dump/restore rejasini talab qiladi; Postgres 18 image-ni boshqa major tag bilan almashtirish avtomatik migratsiya emas.

Asosiy manbalar: n8n Docker Compose qo‘llanmasi, n8n reverse-proxy/webhook konfiguratsiyasi va rasmiy PostgreSQL deployment izohlari. Hech qanday infratuzilma benchmarki yoki provayderga xos oldindan o‘rnatilgan imkoniyat taxmin qilinmaydi.

FAQ

n8n-ni Docker bilan o‘rnatish: ko‘p beriladigan savollar

Docker ishlatilganda n8n-ga PostgreSQL kerakmi?

Docker PostgreSQL-ni majburiy qilmaydi, kichik o‘rnatishlar SQLite ishlatishi mumkin. Production-ga yo‘naltirilgan VPS o‘rnatilishida PostgreSQL kuchliroq database asosini beradi va keyinchalik queue mode masshtablashini qo‘llaydi.

PostgreSQL ma’lumotlarni saqlasa, nega doimiy n8n volume kerak?

Doimiy n8n directory muhim instans holati va konfiguratsiyasini saqlashi mumkin. Database yagona recovery asset deb hisoblamang; uni deployment dizayniga muvofiq saqlang.

Nega webhook localhost-ni ko‘rsatadi?

Ichki konteyner manzili ochiq origin-dan farq qiladi. Tashqi hostname, protocol va webhook URL-ni sozlang, reverse proxy kerakli header-larni uzatayotganini tekshiring.

5678 porti ochiq bo‘lishi kerakmi?

Reverse proxy ortidagi odatiy production deployment uchun HTTPS-ni proxy-da oching va alohida operatsion sabab bo‘lmasa n8n ilova portini ichki tarmoqda saqlang.

Redis kerakmi?

Standart bir instansli Docker deployment uchun yo‘q. Queue mode va worker-larga ongli o‘tganda Redis kerak bo‘ladi.

Tashqi n8n task runner-lar queue mode worker-lari bilan bir xilmi?

Yo‘q. Tashqi task runner-lar qo‘llab-quvvatlanadigan task code-ni n8n main jarayonidan alohida bajaradi va umumiy authentication token ishlatadi. Redis queue mode workflow bajarilishlarini taqsimlaydi va o‘z infratuzilma talablariga ega. Ushbu misolda Redis queue mode emas, tashqi task runner ko‘rsatilgan.
