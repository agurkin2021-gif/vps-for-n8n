ZAXIRA NUSXA VA TIKLASH

n8n zaxira nusxasi va tiklash

Self-hosted n8n-ni zaxiralash va tiklash uchun SQLite ma’lumotlar bazasi yoki izchil PostgreSQL dumpini, doimiy .n8n papkasini va asl shifrlash kalitini, o‘rnatish konfiguratsiyasini hamda barcha tashqi binar yoki mounted-file bog‘liqliklarini himoya qiling. Shifrlangan nusxani VPS-dan tashqarida saqlang va tiklashni alohida instansda sinang. Tanlab tiklash uchun CLI orqali ish jarayonlari va tizimga kirish ma’lumotlarini eksport qiling; faqat JSON eksportlari serverning to‘liq zaxira nusxasi emas.

n8n uchun VPS tanlang

Hamkorlik havolasi: xariddan komissiya olishimiz mumkin.

QISQA CHEK-LIST

n8n zaxira nusxasi nimalarni himoya qilishi kerak

Ma’lumotlar bazasi

Instans foydalanadigan PostgreSQL ma’lumotlar bazasi yoki SQLite database faylining zaxira nusxasini yarating. Ma’lumotlar bazasida ish jarayonlari, tizimga kirish ma’lumotlari va bajarilish ma’lumotlari kabi asosiy n8n holati saqlanadi.

Shifrlash kaliti

n8n-ning aynan o‘sha shifrlash kalitini alohida va xavfsiz saqlang. Tiklangan shifrlangan tizimga kirish ma’lumotlari shu kalitga bog‘liq.

Doimiy fayllar

Doimiy n8n ma’lumotlar papkasi, mounted fayllar, binar ma’lumotlar saqlash joyi va o‘rnatishingiz tayanadigan ish jarayoni resurslarini zaxiraga kiriting.

O‘rnatish konfiguratsiyasi

Stekni qayta tiklash uchun kerak bo‘ladigan Compose/konfiguratsiya fayllari va maxfiy bo‘lmagan sozlamalarni saqlang. Maxfiy qiymatlarni tegishli kirish nazorati bilan himoya qiling.

ZAXIRALASHNING IKKI DARAJASI

Mantiqiy eksport va to‘liq avariya tiklashi

Ish jarayonlari va tizimga kirish ma’lumotlarini eksport qilish

n8n CLI eksportlari migratsiya, ish jarayonlarining versiyalangan nusxalari va tanlab tiklash uchun foydali. Tizimga kirish ma’lumotlarini shifrlangan holda eksport qilib, keyin mos shifrlash kaliti bilan import qilish mumkin. Faqat bitta ish jarayonini tiklash uchun ish jarayoni muharriridagi uch nuqta menyusidan «Download» orqali uning JSON faylini yuklab oling, so‘ng yangi tekshiruv ish jarayoniga yoki izolyatsiyalangan instansga «Import from File» orqali kiriting. Ishlayotgan ish jarayonini almashtirishdan oldin tizimga kirish ma’lumotlari, workflow ID-lari va node parametrlarini tekshiring: workflow JSON-ni tiklash butun serverni tiklamaydi.

Entity eksporti

CLI qo‘llab-quvvatlanadigan ma’lumotlar bazasi turlari orasida ko‘chirish uchun database entity-larni eksport qila oladi. Bajarilish tarixi jadvallari ixtiyoriy, chunki ular juda katta bo‘lishi mumkin.

To‘liq instansni tiklash

Server butunlay ishlamay qolgan holat uchun haqiqiy ma’lumotlar bazasi, shifrlash kaliti, doimiy ma’lumotlar va o‘rnatish bog‘liqliklarini himoya qiling. Workflow JSON eksporti butun instansni qayta yaratadi deb hisoblamang.

Provayder snapshoti

VPS snapshot qo‘shimcha tiklash qatlami sifatida foydali, ammo yagona nusxa bo‘lmasligi va mustaqil tekshirilgan ilova/ma’lumotlar bazasi zaxira nusxasini almashtirmasligi kerak.

MA’LUMOTLAR BAZASI

Ma’lumotlar bazasini izchil zaxiralang

PostgreSQL

Izchil PostgreSQL zaxiralash usulidan foydalaning va olingan nusxani VPS-dan tashqarida saqlang. Ishdan chiqqan o‘sha diskdagi database nusxasi avariya tiklashi hisoblanmaydi.

SQLite

O‘rnatish SQLite ishlatsa, doimiy n8n ma’lumotlar papkasidagi database faylini himoya qiling. Ma’lumotlar bazasi faol o‘zgartirilayotgan paytda xavfsiz bo‘lmagan holatda nusxa olishdan saqlaning.

Bajarilish tarixi

Tarixiy bajarilish ma’lumotlari tiklash maqsadingizga kiradimi — aniqlang. U zaxira nusxalarni ancha kattalashtirishi mumkin, shuning uchun tanlovni saqlash muddati va compliance talablari belgilashi kerak.

Ma’lumotlar bazasi versiyasi

Tiklash muhitini mos tayyorlash uchun manba o‘rnatishda ishlatilgan database engine va versiyani qayd eting.

Docker Compose VPS-dagi PostgreSQL. Agar PostgreSQL servisi postgres deb atalib, ma’lumotlar bazasi va foydalanuvchi nomi n8n bo‘lsa, quyidagi komanda hostda izchil PostgreSQL custom-format dump yaratadi. Uni ishga tushirishdan oldin haqiqiy Compose faylingizni tekshirib, ma’lumotlar bazasi uchun tizimga kirish ma’lumotlari va servis nomlarini moslang. pg_dump PostgreSQL ishlayotgan paytda mantiqan izchil snapshot yaratishi mumkin, ammo alohida .n8n foydalanuvchi papkasi yoki tashqi binar ma’lumotlarni zaxiralamaydi.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Arxiv ro‘yxatini tekshirish aniq format muammolarini topadi, ammo ma’lumotlar tiklanishini isbotlamaydi. Shifrlangan nusxani serverdan tashqarida saqlang va restore-ni amalda sinang. Ma’lumotlar bazasiga xos opsiyalar uchun rasmiy PostgreSQL pg_dump hujjatlaridan foydalaning.

Docker-dagi SQLite. Standart SQLite o‘rnatilishida database.sqlite va yaratilgan shifrlash kaliti konfiguratsiyasi doimiy .n8n papkasida joylashadi (odatda /home/node/.n8n). Ishlayotgan SQLite faylining oddiy nusxasini izchil backup deb hisoblamang. Papkani nusxalashdan oldin n8n va ma’lumotlar bazasiga yozayotgan boshqa jarayonlarni to‘xtating; uzilish mumkin bo‘lmasa, SQLite qo‘llaydigan online backup mexanizmidan foydalaning:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Bu komandalar ko‘rsatilgan servis va path uchun misol, universal volume tuzilmasi emas. Nusxalangan papka dastlab o‘sha VPS-da qoladi; uni serverdan tashqariga ko‘chirib, himoya qiling. Queue worker yoki ma’lumotlar bazasiga yozadigan boshqa jarayonlar bo‘lsa, ularni ham to‘xtatib, haqiqiy o‘rnatish arxitekturasiga amal qiling. n8n-ning amaldagi to‘liq backup yo‘riqnomasi SQLite izchilligi talabini hujjatlashtiradi.

Standart SQLite papkasini toza target-ga tiklash: avval n8n servisi va ma’lumotlar bazasiga yozadigan barcha jarayonlarni to‘xtating. Mos n8n servis konteyneri va maqsad volume yaratilgach, zaxiralangan .n8n tarkibini yana o‘sha doimiy papkaga ko‘chiring. Bu target fayllar ustidan yozadi, shuning uchun saqlab qolish kerak bo‘lgan ma’lumotlari bor instansda buni bajarmang:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker to‘xtatilgan konteynerlarga ham nusxa ko‘chira oladi, ammo target fayllarning ownership-i aslidan farq qilishi mumkin; ishga tushirishdan oldin tiklangan konfiguratsiya va ma’lumotlar bazasi fayli n8n jarayoni tomonidan o‘qilishi va yozilishi mumkinligini tekshiring. Haqiqiy Compose konfiguratsiyangiz boshqa path yoki bind mount ishlatsa, nusxalashni shunga moslashtiring. Docker Compose copy ma’lumotnomasi. Alohida PostgreSQL ma’lumotlar bazasidan foydalanadigan o‘rnatishlar uchun faqat n8n papkasini tiklash yetarli emas.

MUHIM MAXFIY MA’LUMOT

Shifrlash kaliti tiklashning bir qismi

n8n saqlangan tizimga kirish ma’lumotlarini instansning shifrlash kaliti bilan shifrlaydi. Mos kalitsiz ma’lumotlar bazasi yoki shifrlangan credential eksporti tiklangan ish jarayonlarini saqlangan tizimga kirish ma’lumotlaridan foydalana olmaydigan holatda qoldirishi mumkin.

Agar N8N_ENCRYPTION_KEY o‘rnatilgan bo‘lsa, aynan shu maxfiy qiymatni tiklang. Aks holda yaratilgan kalit doimiy .n8n/config faylida saqlanadi: zaxiralash yoki qayta qurishda shu konfiguratsiyani himoya qiling. Tiklash kalitlarini VPS-dan tashqarida xavfsiz saqlang. Queue mode-da barcha main va worker jarayonlari bir xil kalitdan foydalanishi kerak.

FAYLLAR VA BINAR MA’LUMOTLAR

Ma’lumotlar bazasi zaxira nusxasi har bir ish jarayoni bog‘liqligini qamramasligi mumkin

Doimiy .n8n ma’lumotlari

Faqat container image-ni emas, haqiqiy .n8n user papkasini topib saqlang. Odatdagi Docker o‘rnatilishida u /home/node/.n8n ga mount qilinadi; Docker-dan tashqarida standart manzil ~/.n8n. Agar N8N_USER_FOLDER sozlangan bo‘lsa, n8n .n8n papkasini ko‘rsatilgan parent directory ichida yaratadi. Uning config kaliti va o‘rnatishingiz ishlatadigan lokal SQLite, binar yoki filesystem bajarilish ma’lumotlarini ham kiriting.

Mounted ish jarayoni fayllari

Agar ish jarayonlari host-mounted papkalardan o‘qisa yoki yozsa, u papkalarni alohida zaxiralang. Ularsiz n8n-ni tiklash boshqa tomondan to‘g‘ri ish jarayonlarini ishlamaydigan holga keltirishi mumkin.

Binar ma’lumotlar

Saqlash rejimini aniqlang va barcha tashqi bog‘liqliklarni tiklang. Filesystem asosidagi binar yoki bajarilish ma’lumotlari .n8n yoki maxsus papkada bo‘lishi mumkin; S3/Azure Blob yoki boshqa sozlangan tashqi storage uchun alohida tiklanadigan nusxa va access sozlamalari kerak. Faqat database dump bu fayllarni almashtira olmaydi.

Community node-lar

Community paketlari va versiyalarini qayd eting, N8N_CUSTOM_EXTENSIONS orqali sozlangan qo‘shimcha custom node papkalarini ham zaxiralang. Bu papkalar .n8n tashqarisida bo‘lishi mumkin; faqat database va user-folder restore custom node ishlatadigan workflow-larni ishlamaydigan holatda qoldirishi mumkin.

Jadvalni o‘lchash mumkin bo‘ladigan qiling. Har bir muvaffaqiyatli backup vaqti, ko‘chirish yakunlangan vaqti, fayl hajmi, source database versiyasi, shifrlash kalitini tiklash joyi va so‘nggi muvaffaqiyatli restore testini qayd eting. Yo‘qolgan, muvaffaqiyatsiz yoki kutilmaganda bo‘sh fayllar haqida ogohlantiring. Backup arxivlarini VPS-dan tashqariga yuborishdan oldin shifrlang va recovery secret-lariga kirishni cheklang. Sana bilan saqlangan bir nechta tiklash nuqtalari buzilish faqat eng yangi nusxa so‘nggi sog‘lom nusxa ustidan yozgandan keyin aniqlanishidan himoya qiladi.

Masalan, eng ko‘pi bilan olti soatlik o‘zgarishlarni yo‘qotishga chidashingiz mumkin bo‘lsa, muvaffaqiyatli olti soatlik backup jadvali faqat boshlang‘ich nuqta, kafolat emas: muvaffaqiyatsiz vazifalar va kechikkan off-server replikatsiya haqiqiy yo‘qotishni oshirishi mumkin. Universal 7 yoki 30 kunlik siyosatni taxmin qilish o‘rniga retention va restore davriyligini o‘z RPO/RTO hamda ma’lumot talablaringizga moslang.

TIKLASH TARTIBI

Nazoratli ketma-ketlikda tiklang

1 · TayyorlashMos server, ma’lumotlar bazasi va container/runtime muhitini tayyorlang.
2 · Maxfiy qiymatlarni tiklashAsl n8n shifrlash kaliti va zarur o‘rnatish secret-larini xavfsiz sozlang.
3 · Ma’lumotlar bazasini tiklashPostgreSQL yoki SQLite-ni tiklang va n8n kutilgan ma’lumotlarga ulana olishini tekshiring.
4 · Fayllarni tiklashDoimiy papkalar, binar ma’lumotlar va mounted workflow resurslarini tiklang.
5 · n8n-ni ishga tushirishIlovani kutilgan hostname, database va environment konfiguratsiyasi bilan ishga tushiring.
6 · TekshirishFoydalanuvchilar, workflow-lar va credentials yuklanishini tasdiqlang, keyin namunaviy ish jarayonlari va webhook path-larni bajaring.

PostgreSQL avariya tiklash misoli: kerakli database role va bo‘sh n8n ma’lumotlar bazasi allaqachon yaratilgan alohida, toza tiklash targetida faqat PostgreSQL-ni ishga tushiring. Import qilishdan oldin PostgreSQL to‘liq tayyor bo‘lishini kuting: docker compose up -d PostgreSQL hali initializatsiya qilinayotgan paytda qaytishi mumkin, shuning uchun undan keyingi pg_restore muvaffaqiyatsiz bo‘lishi mumkin. Misolda zamonaviy Compose o‘rnatilishidagi --wait ishlatiladi va tayyorlik pg_isready bilan alohida tekshiriladi. Ishonchli kutish uchun mos PostgreSQL healthcheck sozlang yoki davom etishdan oldin readiness-ni aniq tekshiring. Bu komandani ma’lumotlari bor production database-ga yo‘naltirmang va ma’lumotlar bazasi hamda unga mos .n8n kaliti/ma’lumotlari tiklanmasdan n8n-ni ishga tushirmang.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Target muhitda mos PostgreSQL versiyasi, role huquqlari, extension-lar va asl n8n konfiguratsiyasi bo‘lishi kerak. .n8n papkasini backup mexanizmingiz orqali to‘g‘ri persistent volume yoki bind mount-ga tiklang va ownership hamda permission-larni saqlang. Tashqi binar fayllar, custom extension-lar, Compose va maxfiy konfiguratsiyalarni tiklang, keyin n8n-ni mos versiyada ishga tushirib loglarini tekshiring. Faqat ma’lumotlar bazasini tiklash shifrlash kalitini tiklamaydi: agar N8N_ENCRYPTION_KEY alohida sozlanmagan bo‘lsa, PostgreSQL o‘rnatilishi kalitni .n8n/config ichida saqlaydi. pg_restore ma’lumotnomasi · n8n to‘liq instans tiklash ketma-ketligi.

TIKLASH TESTI

Tiklash muvaffaqiyatli bo‘lmaguncha zaxira nusxa isbotlangan hisoblanmaydi

Toza muhitda sinang

Haqiqiy test zaxira nusxa production serverda qolgan yashirin fayllarga tayanmasdan instansni qayta qura olishini isbotlashi kerak.

Tizimga kirish ma’lumotlarini tekshiring

Workflow ochilishi yetarli emas. Tiklangan shifrlangan tizimga kirish ma’lumotlari haqiqatan decrypt bo‘lib, muvaffaqiyatli autentifikatsiya qilinishini tekshiring.

Namunaviy ish jarayonlarini ishga tushiring

Faqat oddiy avtomatlashtirishni emas, webhooklar, tashqi API-lar, mounted fayllar va community node-larga bog‘liq workflow-larni ham sinang.

Tiklash vaqtini o‘lchang

Tiklash qancha vaqt olishi va qaysi qo‘lda bajariladigan qadamlar qolishini qayd eting. Bu taxminiy zaxira nusxani haqiqiy operatsion tiklash jarayoniga aylantiradi.

Tekshirilgan tiklash testi: SQLite va PostgreSQL

Test muhiti: n8n 2.42.5 izolyatsiyalangan Docker konteynerlarida, vaqtinchalik GitHub Actions runner-da, sun’iy ikki node-li workflow bilan. Bu tekshiruvlar 2026-yil 8-oktabrda, mijoz yoki production n8n serverida emas, bajarilgan.

SQLite: PASSTest workflow import qilindi, eksport qilindi, ma’lumotlar bazasiga yozadigan barcha jarayonlar to‘xtatildi, SQLite asosidagi doimiy .n8n papka va uning yaratilgan shifrlash kaliti arxivlandi, toza volume-ga tiklandi, n8n ishga tushirildi, so‘ng tiklangan workflow qayta eksport qilinib bajarildi.
PostgreSQL: PASSXuddi shu test workflow import qilindi, custom-format pg_dump yaratilib tekshirildi, keyin pg_restore yordamida yangi bo‘sh PostgreSQL database-ga tiklandi, alohida .n8n papka tiklandi, so‘ng tiklangan workflow qayta eksport qilinib bajarildi.
PASS nimani tasdiqlaydiSinovdan o‘tgan backup yo‘llari ushbu workflow, uning ikki node-i va ular orasidagi connection-larni saqlab qoldi hamda tiklashdan keyin bajarishga imkon berdi. Bu qayta bajarish mumkin bo‘lgan funksional smoke testlar, yuklama benchmarklari emas.
Nimalar sinovdan o‘tkazilmadiHaqiqiy credentials-ni decrypt va authenticate qilish, production webhooklar, queue-mode worker-lar va Redis, S3/Azure binary storage, custom node-lar, user/project access yoki live production instansni tiklash sinovdan o‘tkazilmadi. Haqiqatan foydalanadigan har bir bog‘liqlik uchun alohida test o‘tkazing.

Qanday takrorlash mumkin: Vaqtinchalik n8n o‘rnatilishidan foydalaning, xavfsiz ikki node-li workflow yarating, mos database va persistent-folder backup-ni oling, uni toza volume yoki database-ga tiklang, keyin tiklangan workflow node-lari, connection-lari va haqiqiy bajarilishini tekshiring. Production tizimda disaster recovery isbotlangan deb hisoblashdan oldin shifrlangan credentials, webhooklar va tashqi fayllarni ham tekshiring.

Restore testi qabul qilish chek-listi: izolyatsiyalangan domen/muhitdan foydalaning; foydalanuvchilar va workflow-lar mavjudligini, mavjud shifrlangan credential qayta kiritmasdan autentifikatsiya qilishini, production webhook kerakli tiklangan workflow-ni chaqirishini, mounted fayllar va binar attachment-lar o‘qilishini hamda kerakli community node integratsiyalari yuklanishini tekshiring. Backup yoshi, o‘lchangan downtime va off-server accessibility-ni tasdiqlang. Muhim tekshiruvlardan biri ishlamasa, tiklash nuqtasini tekshirilmagan deb belgilang; backup-ni to‘liq deb ko‘rsatmang.

CLI ZAXIRALASH CHEKLOVLARI

Workflow va credential eksportlari nimalarni tiklamasligini aniq biling

CLI eksportlari instansning to‘liq zaxira nusxasi emas

Workflow va credential backup eksportlariga foydalanuvchilar va rollar, bajarilish tarixi va loglar, variable-lar yoki shifrlash kaliti kabi instans sozlamalari kirmaydi.

Yangi instansni tiklashda owner kerak

Toza instansda credentials import qilishdan oldin owner setup-ni yakunlang. Multi-user yoki project restore uchun to‘g‘ri user yoki project assignment ham kerak bo‘lishi mumkin.

Import qilingan ID-lar mavjud elementlar ustidan yozishi mumkin

Workflow va credential eksportlari asl ID-larini saqlaydi. Xuddi shu ID-lar mavjud bo‘lgan instansga import qilish mavjud elementlarni almashtirishi mumkin.

Import qilingan workflow-larni ataylab publish qiling

CLI importlari odatda workflow-larni inactive holatda qoldiradi. n8n 2.x da har bir import qilingan workflow-ning published holatini tekshirib, faqat ishga tushirmoqchi bo‘lgan workflow-larni publish qiling; self-hosted Server CLI n8n publish:workflow --id=YOUR_WORKFLOW_ID-ni ham qo‘llaydi. n8n ishlayotgan paytda Server CLI publish/unpublish holati o‘zgarishlari faqat n8n qayta ishga tushirilgandan keyin kuchga kiradi. Scheduled trigger va production webhooklarni tekshirish yoki trafikni almashtirishdan oldin restart qiling.

Docker Compose uchun bulk export misoli: agar n8n servisingiz n8n deb atalgan bo‘lsa, quyidagi rasmiy CLI backup komandalarini ishga tushirishingiz mumkin. Output path ataylab uning mounted persistent .n8n papkasining ichida, chunki konteyner ichidagi ixtiyoriy papkalar qayta yaratilganda yo‘qolishi mumkin. Papkaga n8n konteyner foydalanuvchisi yoza olishini tekshiring. Workflow va credential JSON fayllarini alohida papkalarda saqlang — n8n ikkala tur bitta papkada bo‘lganda import muammosini hujjatlashtirgan.

n8n 2.x draft va published backup: oddiy --backup workflow eksporti joriy draft-larni saqlaydi; ular production-da published qilingan versiyalardan farq qilishi mumkin. Muayyan workflow-ning haqiqiy published versiyasini saqlash uchun, output papkasi mavjud va yozish mumkinligini tekshirgach, uni alohida docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json komandasi bilan eksport qiling. CLI tarixiy versiyani --version=VERSION_ID parametri bilan ham eksport qila oladi. Bu nusxalarni to‘liq backup bilan birga serverdan tashqarida saqlang; draft JSON live published holatni qayd etadi deb hisoblamang.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Nusxalangan ~/n8n-recovery/cli papka uni xavfsiz, mustaqil backup joyiga ko‘chirmaguningizcha VPS-da qoladi. Credential export default bo‘yicha shifrlangan va import vaqtida mos shifrlash kalitini talab qiladi. Quyidagi parametrdan foydalanmang: --decrypted faqat qat’iy nazorat qilinadigan migratsiya bundan mustasno: u secret-larni plaintext ko‘rinishda yozadi. Maxfiy workflow mantiqi yoki credentials bo‘lgan eksportlarni ochiq GitHub repozitoriyiga hech qachon commit qilmang. Ba’zi uchinchi tomon GitHub credential-backup shablonlari ataylab decrypted secret-larni eksport qiladi; private repository faqat access restriction, encryption emas. Har bir shablonning haqiqiy export sozlamalari va storage permission-larini tekshiring, secret-larni off-server transferdan oldin shifrlang va noto‘g‘ri plaintext upload orqali oshkor bo‘lgan credentials-ni almashtiring.

Bulk import misoli: toza target-da owner setup-ni yakunlang, asl shifrlash kalitini bering va saqlangan backup fayllari tiklash VPS-ida mavjudligini tekshiring. Quyidagi komanda maqsad papkani yaratib, workflows/ va credentials/ subfolder-larini hostdan n8n konteyneriga nusxalaydi; Docker volume tuzilmasi boshqacha bo‘lsa path-larni moslang:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

n8n konteyner foydalanuvchisi uchun file ownership va access-ni tekshiring. Tekshirilgan rollback bo‘lmasa, ma’lumotlari bor production instans ustiga import qilmang: workflow va credential ID-lari mavjud yozuvlar ustidan yozishi mumkin. Keyin ishga tushiring:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Import qilingan ID-lar mavjud workflow yoki credentials-ni almashtirishi mumkin; dry run uchun izolyatsiyalangan test instansdan foydalaning va keyin tizimga kirish ma’lumotlari hamda activation/publishing holatlarini tekshiring. n8n 2.x da JSON draft-ni tiklashning o‘zi workflow published qilinganini va scheduled triggerlarni ishga tushira olishini isbotlamaydi. Import xavfsizligi: non-multi-main n8n instansida oldindan active cron triggerlar CLI importdan keyin instans restart bo‘lguncha ishlashda davom etishi mumkin. Tiklangan job-larni yoqishdan oldin production triggerlarni to‘xtating yoki izolyatsiya qiling va n8n-ni restart qiling; duplicate execution yo‘qligini tekshiring. CLI eksportlari asl foydalanuvchilar, execution loglari, instans variable-lari yoki shifrlash kalitini o‘z ichiga olmaydi. --backup --all --pretty --separate parametrlarini o‘rnatadi; bu 'full instance' backup emas. Manbalar: amaldagi rasmiy n8n backup/restore qo‘llanmasi va n8n CLI command reference.

GitHub yoki Google Drive shablonlaridan bulk restore: Bu faqat workflow JSON uchun alternativ, instans database, foydalanuvchilar, shifrlangan credential qiymatlari yoki encryption key uchun emas. API asosidagi shablonni ishga tushirishdan oldin uning n8n API va storage permission-lari, tanlangan backup versiyasi va target instans, matching ID-larni update qilishi va deleted workflow-larni qayta yaratishi, shuningdek workflow publishing bilan nima qilishini tekshiring. Barcha shablonlar target-da yo‘q ID-ni qayta yaratmaydi; automatic restore-ga tayanishdan oldin bu holatni izolyatsiyada sinang.

FAQ

n8n zaxira nusxasi va tiklash: ko‘p beriladigan savollar

n8n-ni zaxiralash uchun workflow eksporti yetarlimi?

Yo‘q. Workflow eksportlari foydali mantiqiy nusxalar, ammo to‘liq tiklash uchun credentials, mos encryption key, database holati, persistent fayllar va binary-data storage ham kerak bo‘lishi mumkin.

Database bo‘lsa ham n8n encryption key kerakmi?

Ha, agar database ichidagi shifrlangan credentials ishlashda davom etishi kerak bo‘lsa. Asl kalitni xavfsiz saqlang.

PostgreSQL backup qilish kerakmi yoki workflow va credentials eksport qilinsinmi?

Disaster recovery uchun database va encryption key-ni himoya qiling. Mantiqiy eksportlar instansning barcha qismini almashtirish emas, balki qo‘shimcha migratsiya va selective-recovery qatlami sifatida foydali.

VPS snapshot yagona zaxira nusxa bo‘lishi mumkinmi?

Uni bitta recovery qatlami sifatida ko‘rish yaxshiroq. Provayder, account, server yoki snapshot nosozligi barcha recovery point-larni bir vaqtda yo‘q qilmasligi uchun mustaqil off-server backup saqlang.

Zaxira nusxa ishlashini qanday bilaman?

Uni toza test muhitiga restore qiling, credentials decrypt bo‘lishini tekshiring va namunaviy workflow-larni ishga tushiring. Faqat backup job muvaffaqiyatli tugashi recoverability-ni isbotlamaydi.

GitHub yoki Google Drive workflow backup-lari saqlangan credential secret-larini o‘z ichiga oladimi?

Faqat workflow JSON backup-lari n8n credential store boshqaradigan secret qiymatlarini yoki instans encryption key-ni o‘z ichiga olmaydi. Ammo eksport qilingan JSON credential nomlari va ID-larini hamda node parametrlariga bevosita yozilgan secret-larni, masalan authentication header-larni, oshkor qilishi mumkin. JSON-ni upload yoki ulashishdan oldin tekshirib, himoya qiling. To‘liq recovery uchun database va asl kalitni backup qiling yoki tested restore bilan qo‘llab-quvvatlanadigan encrypted credential CLI export-laridan foydalaning. Faqat workflow uchun GitHub yoki Google Drive shabloni to‘liq disaster recovery emas.

TIKLASH MAQSADLARI

Nosozlik yuz berishidan oldin RPO va RTO-ni belgilang

RPO — so‘nggi o‘zgarishlarning chidash mumkin bo‘lgan maksimal yo‘qotilishi. Uni eng yangi yaroqli, mustaqil saqlangan recovery point-dan o‘lchang; eksport yoki transfer ishlamagan bo‘lsa, har olti soatda rejalashtirilgan job olti soatlik RPO-ni kafolatlamaydi. RTO — chidash mumkin bo‘lgan maksimal downtime. Uni toza restore testida o‘lchang: secret-larni olish, tashqi fayllarni tiklash, credentials-ni qayta tekshirish va tiklangan workflow-larni publish qilishni ham kiriting; faqat konteynerni ishga tushirishni emas.

TIKLASH KALITI

Qayta qurishdan oldin asl shifrlash kalitini toping

Agar production muhitida N8N_ENCRYPTION_KEY o‘rnatilgan bo‘lsa, aynan shu environment secret-ni saqlang. Aks holda asl persistent .n8n/config ichidagi yaratilgan kalitni saqlang. Shifrlangan credentials-ni import qilishdan oldin tiklangan instans qaysi kalit manbasidan foydalanayotganini tekshiring; yangi yaratilgan kalit eski ma’lumotlar bazasidagi credentials-ni decrypt qila olmaydi.

Provayderlarni taqqoslayapsizmi?

Provayder tanlash, bir klikli o‘rnatish, qo‘llab-quvvatlash chegaralari, zaxira nusxa, migratsiya, mintaqa va masshtablash uchun n8n uchun eng yaxshi VPS taqqoslanishidan foydalaning. Resurs hajmini tanlash uchun n8n uchun asosiy VPS qo‘llanmasiga qayting.
