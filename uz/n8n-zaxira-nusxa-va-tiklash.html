ZAXIRA NUSXA VA TIKLASH

n8n zaxira nusxasi va tiklash

Self-hosted n8n-ni zaxiralash va tiklash uchun SQLite ma’lumotlar bazasi yoki izchil PostgreSQL dumpini, doimiy .n8n papkasini va asl shifrlash kalitini, o‘rnatish konfiguratsiyasini hamda barcha tashqi binar yoki mounted-file bog‘liqliklarini himoya qiling. Shifrlangan nusxani VPS-dan tashqarida saqlang va tiklashni alohida instansda sinang. Tanlab tiklash uchun CLI orqali ish jarayonlari va tizimga kirish ma’lumotlarini eksport qiling; faqat JSON eksportlari serverning to‘liq zaxira nusxasi emas.

QISQA CHEK-LIST

n8n zaxira nusxasi nimalarni himoya qilishi kerak

Ma’lumotlar bazasi

Instans foydalanadigan PostgreSQL ma’lumotlar bazasi yoki SQLite database faylining zaxira nusxasini yarating. Ma’lumotlar bazasida ish jarayonlari, tizimga kirish ma’lumotlari va bajarilish ma’lumotlari kabi asosiy n8n holati saqlanadi.

Shifrlash kaliti

n8n-ning aynan o‘sha shifrlash kalitini alohida va xavfsiz saqlang. Tiklangan shifrlangan tizimga kirish ma’lumotlari shu kalitga bog‘liq.

Doimiy fayllar

Doimiy n8n ma’lumotlar papkasi, mounted fayllar, binar ma’lumotlar saqlash joyi va o‘rnatishingiz tayanadigan ish jarayoni resurslarini zaxiraga kiriting.

O‘rnatish konfiguratsiyasi

Stekni qayta tiklash uchun kerak bo‘ladigan Compose/konfiguratsiya fayllari va maxfiy bo‘lmagan sozlamalarni saqlang. Maxfiy qiymatlarni tegishli kirish nazorati bilan himoya qiling.

ZAXIRALASHNING IKKI DARAJASI

Faqat bitta ish jarayonini tiklash uchun workflow editoridagi uch nuqta menyusidan uning JSON faylini Download qiling, so‘ng yangi tekshiruv ish jarayoniga yoki izolyatsiyalangan instansga Import from File orqali kiriting. Entity eksporti

To‘liq instansni tiklash

Server butunlay ishlamay qolgan holat uchun haqiqiy ma’lumotlar bazasi, shifrlash kaliti, doimiy ma’lumotlar va o‘rnatish bog‘liqliklarini himoya qiling. Workflow JSON eksporti butun instansni qayta yaratadi deb hisoblamang.

MA’LUMOTLAR BAZASI

Ma’lumotlar bazasini izchil zaxiralang

PostgreSQL

Izchil PostgreSQL zaxiralash usulidan foydalaning va olingan nusxani VPS-dan tashqarida saqlang. Ishdan chiqqan o‘sha diskdagi database nusxasi avariya tiklashi hisoblanmaydi.

SQLite

O‘rnatish SQLite ishlatsa, doimiy n8n ma’lumotlar papkasidagi database faylini himoya qiling. Ma’lumotlar bazasi faol o‘zgartirilayotgan paytda xavfsiz bo‘lmagan holatda nusxa olishdan saqlaning.

Bajarilish tarixi

Tarixiy bajarilish ma’lumotlari tiklash maqsadingizga kiradimi — aniqlang. U zaxira nusxalarni ancha kattalashtirishi mumkin, shuning uchun tanlovni saqlash muddati va compliance talablari belgilashi kerak.

Ma’lumotlar bazasi versiyasi

Tiklash muhitini mos tayyorlash uchun manba o‘rnatishda ishlatilgan database engine va versiyani qayd eting.

Docker Compose VPS-dagi PostgreSQL. Agar PostgreSQL servisi postgres deb atalib, database va user ikkalasi ham n8nbo‘lsa, quyidagi komanda hostda izchil PostgreSQL custom-format dump yaratadi. Uni ishga tushirishdan oldin haqiqiy Compose faylingizni tekshirib, database credentials va servis nomlarini moslang. pg_dump PostgreSQL ishlayotgan paytda mantiqan izchil snapshot yaratishi mumkin, lekin u emas alohida .n8n user papkasi yoki tashqi binar ma’lumotlarni zaxiralamaydi.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Arxiv ro‘yxatini tekshirish aniq format muammolarini topadi, ammo ma’lumotlar tiklanishini isbotlamaydi. Shifrlangan nusxani serverdan tashqarida saqlang va restore-ni amalda sinang. Database-ga xos opsiyalar uchun rasmiy PostgreSQL pg_dump hujjatlaridan foydalaning.

Docker-dagi SQLite. Standart SQLite o‘rnatilishida database.sqlite va yaratilgan shifrlash kaliti konfiguratsiyasi doimiy .n8n papkasida joylashadi (odatda /home/node/.n8n). Oddiy live SQLite nusxasini izchil deb hisoblamang. Papkani nusxalashdan oldin n8n va boshqa database writer-larni to‘xtating; to‘xtatish imkonsiz bo‘lsa, SQLite qo‘llaydigan online backup mexanizmidan foydalaning:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Bu komandalar ko‘rsatilgan servis va path uchun misol, universal volume layout emas. Nusxalangan papka dastlab o‘sha VPS-da qoladi; uni serverdan tashqariga ko‘chirib, himoya qiling. Queue worker yoki boshqa writer-lar bo‘lsa, ularni ham to‘xtatib, haqiqiy o‘rnatish arxitekturasiga amal qiling. n8n-ning amaldagi full-backup yo‘riqnomasi SQLite izchilligi talabini hujjatlashtiradi.

Standart SQLite papkasini toza target-ga tiklash: avval n8n servisi va barcha database writer-larni to‘xtating. Mos n8n servis konteyneri va destination volume yaratilgach, zaxiralangan .n8n tarkibini qayta o‘sha doimiy papkaga ko‘chiring. Bu target fayllarni ustidan yozadi, shuning uchun saqlash kerak bo‘lgan ma’lumotlari bor instansda buni bajarmang:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker to‘xtatilgan konteynerlarga ham nusxa ko‘chira oladi, ammo destination ownership aslidan farq qilishi mumkin; ishga tushirishdan oldin tiklangan konfiguratsiya va database fayli n8n jarayoni tomonidan o‘qilishi va yozilishi mumkinligini tekshiring. Haqiqiy Compose konfiguratsiyangiz boshqa path yoki bind mount ishlatsa, nusxalashni shunga moslashtiring. Docker Compose copy ma’lumotnomasi. Alohida PostgreSQL database ishlatadigan o‘rnatishlar uchun faqat n8n papkasini tiklash yetarli emas.

PostgreSQL disaster-recovery example: on a separate, clean restore target that already has the correct database role and an empty n8n database, start only PostgreSQL. Wait until it is healthy before importing: docker compose up -d alone can return while PostgreSQL is still initializing, so a following pg_restore can fail. The example uses --wait on a modern Compose installation and independently checks pg_isready. Configure an appropriate PostgreSQL healthcheck for reliable waiting, or confirm readiness explicitly before moving on. Do not point this command at a populated production database or start n8n before the database and its matching .n8n key/data are restored.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

The destination must have a compatible PostgreSQL version, role privileges, extensions and original n8n configuration. Restore .n8n to its correct persistent volume or bind mount using your backup mechanism, preserving ownership and permissions. Restore external binary files, custom extensions, Compose and secrets configuration, then start n8n at a compatible version and check its logs. Restoring the database alone does not recover the key: a PostgreSQL deployment keeps the key in .n8n/config unless you explicitly configured N8N_ENCRYPTION_KEY. pg_restore reference · n8n full-instance restore sequence.

RESTORE TEST

A backup is not proven until restoration succeeds

Test on a clean environment

A real drill should prove that the backup can rebuild an instance without relying on undeclared files left on the production server.

Check credentials

Opening a workflow is not enough. Confirm restored encrypted credentials actually decrypt and authenticate successfully.

Run representative workflows

Test workflows that depend on webhooks, external APIs, mounted files and community nodes rather than validating only a trivial automation.

Measure recovery time

Record how long the restore takes and what manual steps remain. This converts an assumed backup into an operational recovery procedure.

Verified restore drill: SQLite and PostgreSQL

Test environment: n8n 2.42.5 in isolated Docker containers on a disposable GitHub Actions runner, using a synthetic two-node workflow. These checks ran on 8 October 2026, not on a customer's or production n8n server.

SQLite: PASSImported a test workflow, exported it, stopped all writers, archived the SQLite-backed persistent .n8n folder and its generated encryption key, restored into a clean volume, started n8n, then re-exported and executed the recovered workflow.
PostgreSQL: PASSImported the same test workflow, created and inspected a custom-format pg_dump, restored it using pg_restore into a new empty PostgreSQL database, restored the separate .n8n folder, then re-exported and executed the recovered workflow.
What PASS establishesThe tested backup paths preserved this workflow, its two nodes and their connections and allowed execution after recovery. These are reproducible functional smoke tests, not workload benchmarks.
What was not testedDecryption and authentication of real credentials, production webhooks, queue-mode workers and Redis, S3/Azure binary storage, custom nodes, user/project access or the recovery of a live production instance. Run a separate drill for each dependency you actually use.

How to reproduce: use a disposable n8n installation, create a harmless two-node workflow, perform the applicable database plus persistent-folder backup, restore to a clean volume or database, then verify the restored workflow's nodes, connections and actual execution. On the production system also check encrypted credentials, webhooks and external files before declaring disaster recovery proven.

Restore drill acceptance checklist: use an isolated domain/environment; check that users and workflows are present, one existing encrypted credential authenticates without re-entry, a production webhook invokes the intended restored workflow, mounted files and binary attachments remain readable, and integrations with required community nodes load. Confirm backup age, measured downtime and off-server accessibility. If any essential check fails, mark that recovery point unverified rather than reporting the backup as complete.

CLI BACKUP LIMITS

Know exactly what workflow and credential exports do not restore

CLI exports are not a full instance backup

Workflow and credential backup exports do not include users and roles, execution history and logs, variables, or instance settings such as the encryption key.

Fresh-instance restore needs an owner

On a clean instance, complete owner setup before importing credentials. Multi-user or project restores may also need the correct user or project assignment.

Imported IDs can overwrite existing items

Workflow and credential exports preserve their original IDs. Importing into an instance that already contains the same IDs can replace those existing items.

Publish imported workflows deliberately

CLI imports normally leave workflows inactive. On n8n 2.x, check each imported workflow's published state and publish only the workflows you intend to run; the self-hosted Server CLI also supports n8n publish:workflow --id=YOUR_WORKFLOW_ID. When n8n is running, Server CLI publish/unpublish state changes take effect only after restarting n8n. Restart before verifying scheduled triggers and production webhooks or switching traffic.

Bulk export example for Docker Compose: if your n8n service is named n8n, you can run the official CLI backups below. The output path is deliberately inside its mounted persistent .n8n directory, because arbitrary directories inside a container may disappear when it is recreated. Confirm the directory is writable by the n8n container user. Keep workflow and credential JSON in separate directories—n8n documents an import problem when both kinds share a directory.

n8n 2.x draft versus published backup: a normal --backup workflow export captures current drafts; these can differ from the versions published in production. To preserve the actual published version of a particular workflow, export it separately using docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, after ensuring that output folder exists and is writable. The CLI can also export a historical version using --version=VERSION_ID. Keep these captures off-server alongside the full backup; do not assume draft JSON records the live published state.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

The copied ~/n8n-recovery/cli directory is still on the VPS until you move it to a secured, independent backup location. Credential export is encrypted by default and needs the matching encryption key on import. Avoid using --decrypted except for a strictly controlled migration: it writes secrets in plaintext. Never commit exports containing sensitive workflow logic or credentials to a public GitHub repository. Some third-party GitHub credential-backup templates deliberately export decrypted secrets; a private repository is an access restriction, not encryption. Inspect every template's actual export settings and storage permissions, encrypt secrets before off-server transfer, and rotate any credentials exposed through an unintended plaintext upload.

Bulk import example: on a clean target, finish owner setup, provide the original encryption key and ensure the saved backup files are available on that recovery VPS. The following creates the destination folder and copies the workflows/ and credentials/ subfolders from the host into the n8n container; adapt paths if your Docker volume layout differs:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Check file ownership and access for the n8n container user. Do not import over a populated production instance without a verified rollback: workflow and credential IDs can overwrite existing entries. Then run:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Imported IDs can replace existing workflows or credentials; use an isolated test instance for dry runs and check credentials and activation/publishing states afterwards. In n8n 2.x, restoring the JSON draft does not by itself prove a workflow has been published and can run scheduled triggers. Import safety: on a non-multi-main n8n instance, previously active cron triggers can continue running after CLI import until the instance restarts. Stop or isolate production triggers and restart n8n before enabling restored jobs; verify there is no duplicate execution. CLI exports do emas contain original users, execution logs, instance variables or the encryption key. --backup sets --all --pretty --separate, not 'full instance'. Sources: current official n8n backup/restore guide and n8n CLI command reference.

Bulk restore from GitHub or Google Drive templates: this is an alternative for workflow JSON only, not for the instance database, users, encrypted credential values or encryption key. Before running an API-based template, verify its n8n API and storage permissions, the selected backup version and target instance, whether it updates matching IDs and recreates deleted workflows, and what it does with workflow publishing. Not all templates recreate an ID missing from the target; test that scenario in isolation before relying on automatic restore.

FAQ

n8n backup and restore: common questions

Is exporting workflows enough to back up n8n?

No. Workflow exports are useful logical copies, but complete recovery can also require credentials, the matching encryption key, database state, persistent files and binary-data storage.

Do I need the n8n encryption key if I have the database?

Yes if you need the encrypted credentials stored in that database to remain usable. Preserve the original key securely.

Should I back up PostgreSQL or export workflows and credentials?

For disaster recovery, protect the database and the encryption key. Logical exports are valuable as an additional migration and selective-recovery layer rather than a substitute for every part of the instance.

Can a VPS snapshot be my only backup?

It is better treated as one recovery layer. Keep an independent off-server backup so a provider, account, server or snapshot failure does not remove every recovery point at once.

How do I know my backup works?

Restore it into a clean test environment, verify credentials decrypt, and run representative workflows. A successful backup job alone does not prove recoverability.

Do GitHub or Google Drive workflow backups include saved credential secrets?

Workflow-only JSON backups do not include the secret values managed by n8n's credential store or the instance encryption key. However, exported JSON can expose credential names and IDs and secrets typed directly into node parameters, such as authentication headers. Inspect and protect exported JSON before uploading or sharing it. For full recovery, back up the database and original key, or use supported encrypted credential CLI exports with a tested restore. A workflow-only GitHub or Google Drive template is not full disaster recovery.

RECOVERY OBJECTIVES

Define RPO and RTO before an incident

RPO is the maximum tolerable loss of recent changes. Measure it from the newest usable, independently stored recovery point; a scheduled six-hour job does not establish a six-hour RPO if exports or transfers failed. RTO is the maximum tolerable outage. Measure it in a clean restore drill, including retrieving secrets, restoring external files, rechecking credentials and publishing recovered workflows—not just starting a container.

RECOVERY KEY

Find the original encryption key before rebuilding

If production set N8N_ENCRYPTION_KEY, preserve that exact environment secret. If it did not, preserve the generated key in the original persistent .n8n/config. Check which source the recovered instance actually uses before importing encrypted credentials; a fresh generated key cannot decrypt credentials from the old database.
