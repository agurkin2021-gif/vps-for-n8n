PRODUCTION XAVFSIZLIGI

n8n-ni VPS-da xavfsizlashtirish

n8n-ni VPS-da xavfsiz ishlatish uchun n8n (5678), PostgreSQL (5432) va ixtiyoriy Redis (6379) portlarini ochiq internetdan yoping; HTTPS reverse proxy, SSH kalitlari va MFA-dan foydalaning, shifrlash kalitini saqlang, webhook chaqiruvchilarini autentifikatsiya qiling, xavfli workflow imkoniyatlarini cheklang va o‘rnatilgan instansni audit qiling. Editorni ochiq webhook yo‘llaridan alohida himoya qiling. Faqat HTTPS ulangan servislarning barchasini xavfsiz qilmaydi.

n8n uchun VPS tanlang

Hamkorlik havolasi: xariddan komissiya olishimiz mumkin.

QISQA CHEK-LIST

Internetga ochishdan oldingi minimal xavfsizlik bazasi

Avval tashqaridan ochiq portlar, HTTPS, tekshirilgan administrator kirishi, MFA va saqlangan tizimga kirish ma’lumotlari himoyasini tekshiring. Har bir kiruvchi webhook maxfiy ishni boshlashidan oldin chaqiruvchini autentifikatsiya qiling. Kirish qoidalarini o‘zgartirgandan keyin kerakli editorlar va tashqi integratsiyalar ishlashini tekshiring, so‘ng n8n xavfsizlik auditini ishga tushiring.

Faqat HTTPS

n8n-ni to‘g‘ri sozlangan TLS reverse proxy ortiga joylashtiring va editor hamda webhooklar uchun ochiq HTTPS URL-dan izchil foydalaning.

Minimal ochiq portlar

Faqat ochiq trafik uchun zarur portlarni e’lon qiling. PostgreSQL, Redis va ilovaning ichki portlarini internetdan yopiq saqlang.

SSH-ni mustahkamlang

Kalit asosidagi administrator kirishidan foydalaning, kim login qila olishini cheklang va operatsion tizimni patchlangan holda saqlang.

Tizimga kirish ma’lumotlarini himoya qiling

n8n shifrlash kalitini o‘zgarmas va maxfiy saqlang. Environment fayllari, ma’lumotlar bazasiga kirish va zaxira nusxalarni maxfiy aktivlar deb hisoblang.

TARMOQ CHEGARASI

Reverse proxy, HTTPS va ishonchli header-lar

TLS termination

HTTPS termination uchun Nginx, Caddy yoki Traefik kabi reverse proxy ishlating. Oddiy HTTP-ni HTTPS-ga yo‘naltiring va proxy asosiy kirish nuqtasi bo‘lsa, n8n ilova portini to‘g‘ridan-to‘g‘ri internetga ochmang.

Proxy konfiguratsiyasi

n8n reverse proxy ortida ishlaganda proxy hop sonini to‘g‘ri sozlang va n8n asl mijoz so‘rovini qayta tiklashi uchun kerakli forwarded header-larni uzating.

Xavfsiz cookie-lar

Autentifikatsiya cookie-lari xavfsiz qolishi uchun editorni HTTPS orqali bering. Noto‘g‘ri TLS sozlamasini cookie xavfsizligini pasaytirish orqali aylanib o‘tmang.

Webhook URL

Ochiq webhook URL-ni tashqaridan kirish mumkin bo‘lgan HTTPS hostname-ga o‘rnating, shunda yaratiladigan webhook endpoint-lar ichki konteyner yoki HTTP manziliga yo‘nalmaydi.

Webhooklarni buzmasdan editorni yopiq saqlang. Amaliy bo‘lsa, boshqaruv kirishini VPN, ishonchli IP siyosati yoki autentifikatsiyalangan proxy orqali cheklang. Ochiq webhook qabul qiluvchilari va OAuth callback yo‘llari tashqaridan ochiq qolishi kerak bo‘lishi mumkin; proxy qoidasini majburan qo‘llashdan oldin ishonchli editor loginini ham, haqiqiy tashqi callback-ni ham sinang. Client-address header-larini faqat ishonchli proxy-lardan qabul qiling, ixtiyoriy so‘rov header-laridan emas.

Webhook chaqiruvchilarini autentifikatsiya qiling: jo‘natuvchi qo‘llasa, Webhook node-da None o‘rniga Basic, Header yoki JWT authentication-ni tanlang. Kerak bo‘lsa uning IP(s) Allowlist opsiyasidan foydalaning va integratsiya signed request-larni qo‘llasa, provayder imzolarini tekshiring. Topish qiyin bo‘lgan URL o‘zi yetarli autentifikatsiya emas. Kerak bo‘lsa proxy-da rate limit qo‘ying va haqiqiy yuklama cho‘qqilari bloklanmasligini tekshiring. Rasmiy Webhook authentication opsiyalari.

VPS-NI MUSTAHKAMLASH

Server hujum yuzasini kamaytiring

Firewall

Kutilmagan kiruvchi trafikni default-deny qiling va faqat tashqaridan kirish zarur bo‘lgan servislarni ruxsat eting. Ma’lumotlar bazasi va Redis portlari odatda yopiq/lokal tarmoqlarda bo‘lishi kerak.

SSH

Parollardan ko‘ra SSH kalitlarini afzal ko‘ring, keraksiz login yo‘llarini o‘chiring va administrator kirishini cheklang. Root-ga teng huquq qat’iy nazorat qilinishi kerak.

OS yangilanishlari

Linux host va konteyner runtime-ni patchlab boring. Ilovani mustahkamlash ochiq yoki eskirgan operatsion tizim o‘rnini bosa olmaydi.

Konteyner portlarini ochish

Faqat host orqali kirish kerak bo‘lgan portlarni e’lon qiling. Ichki servislar ochiq interfeyslar orqali emas, yopiq Docker tarmoqlari orqali aloqa qilishi kerak.

Firewall yoki SSH sozlamalarini o‘zgartirishdan oldin tekshiring: tinglayotgan portlarni sudo ss -lntp bilan, Docker e’lon qilgan portlarni loyiha papkasida docker compose ps bilan, UFW ishlatilsa host firewall siyosatini sudo ufw status verbose bilan tekshiring. Parol bilan kirishni o‘chirishdan oldin haqiqiy SSH portingizni va alohida sessiyada kalit bilan muvaffaqiyatli loginni tekshiring. Docker e’lon qilgan portlar ayrim UFW qoidalarini chetlab o‘tishi mumkin; firewall statusining o‘zi 5678 port yopiq ekanini isbotlamaydi. Haqiqiy tashqi kirish imkonini tekshiring. Docker/UFW izohi.

Ubuntu avtomatik xavfsizlik yangilanishlari ishlayapti deb taxmin qilmasdan tekshiring: apt-config dump APT::Periodic::Unattended-Upgrade natijasini va /var/log/unattended-upgrades/unattended-upgrades.log logini ko‘ring. Agar unattended xavfsizlik yangilanishlari o‘chirilgan bo‘lsa, sudo dpkg-reconfigure unattended-upgrades qo‘llab-quvvatlanadigan konfiguratsiya dialogini ochadi. Ishlayotgan VPS-da yoqishdan oldin reboot va servis restart xatti-harakatini ko‘rib chiqing. Ubuntu APT yangilanishlari n8n Docker image-ni yoki barcha uchinchi tomon software repository-larini avtomatik yangilamaydi. Ubuntu avtomatik yangilanish hujjatlari.

Ixtiyoriy SSH brute-force monitoring: Fail2Ban takroriy muvaffaqiyatsiz SSH loginlarini aniqlashi mumkin. O‘rnatilgan va SSH uchun sozlangan bo‘lsa, sudo fail2ban-client status sshd bilan SSH jail holatini tekshiring va u haqiqiy SSH authentication log yoki journal-ni o‘qishini hamda sozlangan portga mos kelishini tasdiqlang. Bu SSH kalitlari va tarmoq cheklovlarini to‘ldiradi, ularning o‘rnini bosmaydi. Mavjud kirishni tekshirmasdan qat’iy SSH port yoki ban qoidasini ko‘chirmang. Ubuntu SSH hardening qo‘llanmasi.

MA’LUMOTLAR BAZASI VA REDIS

Backend servislarini yopiq saqlang

Odatdagi Docker Compose konfiguratsiyasida PostgreSQL va queue-mode Redis tegishli konteynerlardan yopiq tarmoq orqali kiriladigan bo‘lishi kerak, hostda e’lon qilingan portlar orqali emas. docker compose ps orqali 5432 va 6379 portlari internetga e’lon qilinmaganini tekshiring; alohida VPS/cloud firewall ochiqligini ham ko‘rib chiqing. Tarmoq siyosati ilovaga faqat zarur huquqlar berilgan ma’lumotlar bazasi credentials-lari o‘rnini bosa olmaydi.

PostgreSQLMasofaviy kirish aniq talab qilinib, alohida himoyalanmagan bo‘lsa, uni yopiq interfeys yoki konteyner tarmog‘iga bog‘lang.
RedisQueue-mode Redis infratuzilma komponenti, ochiq endpoint emas. Tarmoq kirishini faqat unga ehtiyoji bor n8n komponentlari bilan cheklang.
Tizimga kirish ma’lumotlariIlova uchun zarur huquqlargina berilgan alohida ma’lumotlar bazasi tizimga kirish ma’lumotlaridan foydalaning va ularni source control-dan tashqarida himoya qiling.
TransportMa’lumotlar bazasi trafiki ishonchsiz tarmoqlardan o‘tsa, faqat ilova darajasidagi credential shifrlashga tayanmasdan mos shifrlangan transportdan foydalaning.

N8N MAXFIY MA’LUMOTLARI

Shifrlash kaliti va tizimga kirish ma’lumotlari chegarasini himoya qiling

Shifrlash kaliti

n8n saqlangan tizimga kirish ma’lumotlarini o‘z shifrlash kaliti bilan shifrlaydi. Restart va worker-lar orasida aynan bir xil kalitni saqlang va uni oddiy ilova kontentidan alohida himoya qiling.

Muhit maxfiy qiymatlari

Parollar, tokenlar yoki shifrlash kalitini ochiq repozitoriyga commit qilmang. Muhit fayllari va o‘rnatish maxfiy qiymatlariga kirishni cheklang.

Foydalanuvchi kirishi

Editor kirishini faqat ishonchli foydalanuvchilarga bering. Workflow-lar maxfiy tizimlarga ulanishi, maxfiy qiymatlarni qayta ishlashi yoki kuchli node-larni bajarishi mumkin.

Tizimga kirish huquqi doirasi

Imkon qadar tor huquqli service account va API tokenlardan foydalaning. Buzilgan workflow avtomatik ravishda aloqasiz tizimlarga keng kirish huquqini olmasligi kerak.

Tekshiriladigan n8n konfiguratsiyasi: N8N_BLOCK_ENV_ACCESS_IN_NODE=true Code node va expression-larning muhit qiymatlariga kirishini bloklaydi; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true settings fayli uchun faqat owner huquqlarini so‘raydi. N8N_ENCRYPTION_KEY ni doimiy va xavfsiz zaxiralangan holda saqlang: n8n birinchi ishga tushishda tasodifiy kalit yaratishi mumkin, ammo uni yo‘qotish mavjud shifrlangan tizimga kirish ma’lumotlarini ishlatib bo‘lmaydigan qilishi mumkin. Production shifrlash kalitini beparvo almashtirmang; rasmiy qo‘llab-quvvatlanadigan rotation jarayonidan foydalaning. Muhit qiymatlariga kirishni bloklash mavjud integratsiyalarni buzishi mumkin, shuning uchun production o‘zgarishlaridan oldin sinang. n8n xavfsizlik variable ta’riflari.

ISH JARAYONI XAVFI

Node-lar xavfsizlik chegarasini kengaytirishi mumkin

Self-hosting ish jarayonlariga katta imkoniyat beradi. Code execution, shell access, ixtiyoriy HTTP so‘rovlari va uchinchi tomon community node-lari xavfni oshirishi mumkin. Kerak bo‘lmagan funksiyalarni o‘chiring va ishonchsiz ish jarayoni importlarini ishga tushirishdan oldin tekshiring.

Aniq qo‘llab-quvvatlanadigan boshqaruvlardan foydalaning: NODES_EXCLUDE ni o‘chiriladigan node-larning JSON massivi bilan sozlang; masalan, n8n-nodes-base.executeCommand va n8n-nodes-base.readWriteFile ishlatilmasa, ularni chiqarib tashlash mumkin. Yangi versiyalarda ayrim yuqori xavfli node-lar default bo‘yicha allaqachon bloklangan; o‘zgartirishdan oldin haqiqiy ro‘yxatni tekshiring. Rasmiy node exclusions.

n8n 2.12.0 versiyasidan boshlab N8N_SSRF_PROTECTION_ENABLED=true ichki, loopback va metadata-address diapazonlariga chiquvchi HTTP so‘rovlarini tekshirishni yoqadi. Haqiqiy ichki API ish jarayonlari ishlamay qolishi mumkin; zarur bo‘lsa faqat o‘zingiz boshqaradigan manzillarni tor allowlist-ga kiriting. Asosiy himoya sifatida tarmoq segmentatsiyasini saqlang. Code node izolyatsiyasi uchun tashqi task runner-larni ko‘rib chiqing. SSRF protection · Task-runner isolation.

Community node-larFaqat ishonadigan paketlarni o‘rnating; ular n8n muhiti ichida bajariladi.
Xavfli node-larImkoniyatlari ko‘zlangan workflow chegarasidan oshib ketadigan, o‘rnatishga kerak bo‘lmagan node-larni chiqarib tashlang.
SSRFIsh jarayonlari ichki yoki metadata endpoint-larga kira olmasligi kerak bo‘lgan joylarda n8n SSRF himoyasi va tarmoq nazoratidan foydalaning.
Ish jarayoni importlariImport qilingan workflow-lar, tizimga kirish ma’lumotlari, expression-lar va bajariladigan qadamlarni faollashtirishdan oldin tekshiring.

AUDIT VA YANGILANISHLAR

Xavfsizlik — doimiy operatsion jarayon

n8n xavfsizlik auditini ishga tushiring

Rasmiy CLI komandasi n8n audit. Agar Docker Compose servisingiz n8n deb atalgan bo‘lsa, shu o‘rnatish papkasida docker compose exec -T n8n n8n audit ni ishga tushiring. Beshta kategoriyani ko‘rib chiqing: ishlatilmayotgan tizimga kirish ma’lumotlari, xavfli SQL-query pattern-lar, file-system access, xavfli/community node-lar hamda himoyalanmagan webhooklar va eskirgan relizlarni o‘z ichiga olgan instans xavflari. Tegishli topilmalarni tuzating va auditni qayta ishga tushiring. Bu penetration test emas. Rasmiy audit qo‘llanmasi.

Yangilanishlarni ongli bajaring

Xavfsizlik tuzatishlarini olish uchun n8n-ni yetarlicha yangilab boring. Internetga ochiq instansni doim eskirgan holda qoldirish o‘rniga release note-larni o‘qing va muhim yangilanishlarni sinang.

Autentifikatsiyani kuzating

Kutilmagan kirish pattern-lari, ish jarayoni o‘zgarishlari va xatolarni kuzating. Operatsion modelingiz keng ochiq kirishni talab qilmasa, editor UI kirishini yanada cheklang.

Orqaga qaytish va tiklashni tayyorlang

Muhim yangilanishlardan oldin tiklanadigan zaxira nusxa oling. Batafsil zaxiralash doirasi va tiklash alohida recovery qo‘llanmasida.

Maxfiy bajarilish tarixini kamaytiring: muvaffaqiyatli bajarilishlar mijoz ma’lumotlari va tokenlarni saqlashi mumkin. Kerak bo‘lsa EXECUTIONS_DATA_SAVE_ON_SUCCESS=none ni o‘rnating, EXECUTIONS_DATA_PRUNE=true ni saqlang va EXECUTIONS_DATA_MAX_AGE uchun soatlarda qiymat tanlang, masalan 168 (yetti kun). Bular konfiguratsiya misollari, huquqiy saqlash qoidalari emas. Kamroq tarix debugging va forensic ma’lumotlar ham kamroq bo‘lishini anglatadi; running, waiting yoki annotated execution-lar bir xil usulda tozalanmasligi mumkin. Rasmiy execution retention.

Buzilishdan shubha bo‘lsa: dalillarni yo‘q qilmasdan zararli kirishni cheklang, proxy, host va n8n faolligi hamda o‘zgargan workflow-larni tekshiring, ehtimol oshkor bo‘lgan tashqi tizim credentials-larini bekor qiling yoki almashtiring, sababni tuzating va zarur bo‘lsa faqat sinovdan o‘tgan tiklanadigan zaxira nusxalardan restore qiling. Ta’sirlangan webhook URL-lari, editor account-lari va ulangan servislarni tekshiring; HTTPS, snapshot yoki VPS xaridi incident-response xizmatini taqdim etadi deb hisoblamang.

ACCOUNT VA PLATFORMA BOSHQARUVI

Editorni ham VPS kabi himoya qiling

Kuchliroq kirish himoyasini talab qiling

Editor account-lari uchun ikki faktorli autentifikatsiyani yoqing va n8n edition-ingiz markazlashtirilgan siyosatlarni qo‘llasa, xavfsizlik siyosatlari orqali MFA-ni majburiy qiling.

Ish jarayonlarini kim tahrir qila olishini cheklang

Editor kirishi imtiyozli kirishdir: ish jarayonlari tizimga kirish ma’lumotlarini o‘qishi, ichki tizimlarni chaqirishi va kuchli node-larni bajarishi mumkin. Foydalanuvchi kirishini tor saqlang va endi kerak bo‘lmagan account-larni olib tashlang.

Ishlatmaydigan imkoniyatlarni o‘chiring

Kerak bo‘lmasa ochiq API-ni o‘chirib, operatsion modelingizga kerak bo‘lmagan yuqori xavfli node yoki funksiyalarni bloklab ilova hujum yuzasini kamaytiring.

SSRF va maxfiy qiymatlar nazoratidan ongli foydalaning

Ixtiyoriy HTTP so‘rovlarini yubora oladigan ish jarayonlari uchun n8n SSRF himoyasini baholang va maxfiy qiymatlarni workflow kodi, ochiq repozitoriylar hamda keng o‘qiladigan muhit fayllaridan tashqarida saqlang.

Ishlatilmaydigan boshqaruv endpoint-larini cheklang: N8N_PUBLIC_API_DISABLED=true n8n public REST API-ni o‘chiradi, N8N_PUBLIC_API_SWAGGERUI_DISABLED=true esa uning API playground-ini alohida o‘chiradi. Buni faqat integratsiyalaringizga bu funksiyalar kerak bo‘lmasa qiling. REST API-ni o‘chirish workflow webhook URL-larini autentifikatsiya qilmaydi. Editor foydalanuvchilari uchun MFA-dan, markazlashtirilgan siyosatlardan esa faqat n8n edition qo‘llaydigan joylarda foydalaning.

Rasmiy hujjatlar: Public API-ni o‘chirish · Security policy variable-lari · Audit komandalar.

FAQ

n8n VPS xavfsizligi: ko‘p beriladigan savollar

n8n portini to‘g‘ridan-to‘g‘ri ochish kerakmi?

Reverse proxy ochiq kirish nuqtasi bo‘lsa, proxy-ni oching va keraksiz servislarni keng e’lon qilish o‘rniga ilova portini uning ortida saqlang.

PostgreSQL yoki Redis ochiq bo‘lishi kerakmi?

Odatda yo‘q. Ularga faqat ehtiyoji bor tizimlar kira olishi kerak. Ochiq internetga chiqarish odatiy n8n ishlashiga yordam bermasdan hujum yuzasini oshiradi.

n8n shifrlash kaliti nega muhim?

U n8n saqlaydigan tizimga kirish ma’lumotlarini himoya qiladi va butun deployment bo‘ylab bir xil qolishi kerak. Uni yo‘qotish tiklangan ma’lumotlardan ishlaydigan shifrlangan tizimga kirish ma’lumotlarini olishga to‘sqinlik qilishi mumkin.

Community node-lar xavfsizmi?

Ular n8n-ni uchinchi tomon kodi bilan kengaytiradi, shuning uchun o‘z supply-chain va privilege xavflariga ega dasturiy bog‘liqlik sifatida qarash kerak. Faqat ishonadigan va kerak bo‘lgan paketlarni o‘rnating.

HTTPS self-hosted n8n instansini xavfsiz qiladimi?

Yo‘q. HTTPS transportni himoya qiladi. Production xavfsizligi hostni mustahkamlash, kirish nazorati, yopiq backend servislar, maxfiy qiymatlar himoyasi, xavfsiz workflow imkoniyatlari, monitoring va yangilanishlarni ham talab qiladi.

Production webhooklar ishlayotganda n8n editor yopiq bo‘lishi mumkinmi?

Ha. Ishonchli reverse proxy yoki VPN editor/admin kirishini ochiq production webhook va OAuth callback yo‘llaridan alohida cheklashi mumkin. Integratsiyalarni tasodifan bloklamaslik uchun har bir kirish qoidasi o‘zgarishidan keyin ishonchli login va tashqi webhook yetkazilishini sinang.

Kiruvchi n8n webhooklarini qanday autentifikatsiya qilaman?

Jo‘natuvchi qo‘llasa, Webhook node-da Basic, Header yoki JWT authentication-ni sozlang. IP(s) Allowlist-dan foydalanishingiz va mavjud bo‘lsa provayder imzolarini tekshirishingiz mumkin. Faqat maxfiy ko‘rinadigan yo‘lga tayanmang va maxfiy API amallarini ishga tushirishdan oldin so‘rovlarni tekshiring.
