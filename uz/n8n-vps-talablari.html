MINIMAL VA AMALIY QUVVAT

n8n uchun bitta rasmiy minimal VPS hajmi bormi?

Har bir yuklama uchun emas. n8n-ning rasmiy prerequisite misollari tushuntiruvchi OEM deployment-ni ko‘rsatadi va talablar yuklamaga qarab o‘zgarishini aniq ogohlantiradi. Bu hujjat ma’lum bir CPU, RAM yoki disk hajmi production avtomatlashtirishlarni albatta qo‘llab-quvvatlaydi degan universal kafolat emas.

n8n idle instans nisbatan kam xotira ishlatishi mumkinligini qayd etadi, ammo Code node, katta binar payload yoki bir vaqtdagi bajarilish xotira talabini keskin oshirishi mumkin. Operatsion tizim, Docker, PostgreSQL va backup/monitoring vositalari uchun resursni alohida hisoblang.

Texnik manbalar: n8n-ning tushuntiruvchi prerequisite-lari va rasmiy memory guide. Yuqoridagi to‘rt qator sotib olish mumkin bo‘lgan haqiqiy resurs to‘plamlari, rasmiy n8n talablari emas.

Bir vaqtdagi bajarilishlar

Bir vaqtda ishlaydigan bir nechta workflow n8n-da saqlangan workflow-larning umumiy sonidan muhimroq bo‘lishi mumkin. Ustma-ust bajarilish paytida xotira cho‘qqilari va execution latency-ni kuzating.

Payload hajmi

Katta JSON obyektlari, fayllar va binar ma’lumotlar xotira bosimini oshiradi. Bir nechta ma’lumotga boy bajarilish ko‘p yengil API avtomatlashtirishlardan ko‘proq RAM talab qilishi mumkin.

CPU-ni ko‘p ishlatadigan node-lar

Code, transformatsiyalar va boshqa hisoblashga og‘ir qadamlar doimiy CPU bosimini keltirishi mumkin. Haqiqiy bajarilishlar hisoblash quvvati uchun raqobat qilganda ko‘proq yadro yordam beradi.

Operatsion tizim, PostgreSQL, reverse proxy, monitoring va Docker ham resurs talab qiladi. Faqat n8n jarayonini emas, butun stekni o‘lchang.

YANGILASHDAN OLDIN O‘LCHANG

n8n-ga ko‘proq RAM, CPU yoki disk kerakligini qanday aniqlash mumkin

Kutilayotgan eng katta workflow va haqiqiy bir vaqtdagi yuklama cho‘qqisini ishga tushiring, keyin server va n8n execution loglarini tekshiring. Editorda saqlangan workflow-lar soni o‘zi alohida foydali capacity benchmark emas.

Xotira / OOM

Tekshiring: docker stats --no-stream and free -h. Xotira tugasa, avval JSON yoki binar payloadlarni kamaytiring, katta importlarni batch-larga bo‘ling va xotirani ko‘p ishlatadigan Code qadamlaridan qoching. JavaScript heap xatosi vCPU qo‘shish bilan albatta tuzalmaydi.

CPU / parallel bajarilish

Transformatsiyalar paytida CPU haqiqatan bandmi yoki vazifalar faqat tashqi API-ni kutyaptimi — o‘lchang. Oddiy rejimda worker-larga o‘tishdan oldin qo‘llab-quvvatlanadigan production concurrency limitini ko‘rib chiqing. CPU-ni oshirish tashqi rate-limited API-ni tezlashtirmaydi.

Disk / ma’lumotlar bazasi

Tekshiring: df -h, database hajmi va saqlanayotgan bajarilish tarixini tekshiring. Disk o‘sishi va sekin database operatsiyalarini kuzating. Kattaroq disk uchun to‘lashdan oldin retention-ni ongli sozlang; tiklash nusxalarini serverdan tashqarida saqlang.

n8n concurrency qo‘llanmasi va rasmiy benchmarking tushuntirishidan foydalaning. Payload va API latency noma’lum bo‘lsa, reklama qilingan har qanday concurrent workflow soni faqat taxmindir.

MA’LUMOTLAR BAZASI VA DISK

SQLite, PostgreSQL va doimiy ma’lumotlar

SQLite

SQLite kichik bir instansli o‘rnatishlar va test uchun mos bo‘lishi mumkin. Production ishlatish va concurrency oshganda database tanlovi oddiy o‘rnatish detali emas, operatsion cheklovga aylanadi.

PostgreSQL

Production-ga yo‘naltirilgan VPS stekida PostgreSQL kuchliroq database asosini beradi. Ma’lumotlar bazasining o‘zi uchun RAM, CPU va diskni hisoblang va uning o‘sishini kuzating.

Doimiy .n8n ma’lumotlari

PostgreSQL-ni yagona doimiy asset deb hisoblamang. n8n data directory-ni saqlang va shifrlangan credentials-ni tiklash uchun kerakli encryption key-ni himoya qiling.

Disk o‘sishi

Bajarilish tarixi, binar ma’lumotlar, database fayllari va loglar vaqt o‘tishi bilan o‘sishi mumkin. Retention sozlamalari va serverdan tashqari backup-lar kerakli disk hajmiga bevosita ta’sir qiladi.

DISK HAJMI

Buyurtmadan oldin n8n bajarilish tarixi uchun diskni hisoblang

Quyidagi formuladan boshlang: kuniga saqlanadigan bajarilishlar × har bir bajarilishning o‘rtacha saqlangan bayti × retention kunlari. Masalan, kuniga 500 saqlangan bajarilish × har biri 200 KB × 14 kun = 1.4 GB database overhead-dan oldingi misol bajarilish ma’lumotlari. 200 KB taxmini tushuntiruvchi raqam, n8n benchmarki emas.

OS, Docker image qatlamlari, database indexlari, binar fayllar, ilova loglari, upgrade va vaqtinchalik fayllar uchun ham disk ajrating. Serverdan tashqari backup-larga alohida joy kerak. 10 GB disk yengil stek uchun ishlashi mumkin, ammo 40 yoki 80 GB diskka qaraganda saqlanadigan fayllar uchun ancha kam zaxira beradi.

n8n default execution pruning-ni yosh (336 soat / 14 kun) yoki son (10 000 bajarilish) bo‘yicha hujjatlashtiradi, ayrim istisnolar mavjud. Sozlamalarni o‘zgartirishdan oldin haqiqiy konfiguratsiyangiz va nimalar saqlanayotganini tekshiring. SQLite bo‘shagan joyni qayta ishlatishi mumkin, ammo fayl avtomatik kichraymasligi mumkin.

Manba: n8n execution ma’lumotlarini boshqarish va pruning. Disk talabi faqat node soniga emas, kuzatilgan saqlangan payload hajmlariga bog‘liq.

PARALLEL BAJARILISH

Qachon kattaroq VPS yagona yechim bo‘lmay qoladi

Bitta instans yuklamani bemalol ko‘tara olayotgan paytda vertikal masshtablash mos. Uzoq davom etadigan parallel talab resurslar uchun raqobat tug‘dirsa, queue mode va worker-larni baholang. Queue mode Redis, PostgreSQL va bir yoki bir nechta worker jarayonini qo‘shadi; RAM va CPU-ni faqat n8n uchun emas, har bir komponent uchun hisoblang. n8n queue mode-da filesystem binary-data storage bo‘yicha cheklovlarni ham hujjatlashtiradi, shuning uchun o‘tishdan oldin mos data-storage dizaynini tekshiring.

FAQ

n8n VPS talablari: ko‘p beriladigan savollar

n8n-ga qancha RAM kerak?

Universal raqam yo‘q. RAM talabi concurrency, payload hajmi, execution xatti-harakati va VPS-dagi yordamchi servislarga qarab o‘zgaradi. 4 GB server amaliy kichik production boshlang‘ich sinfi, har bir yuklama uchun kafolatlangan talab emas.

Nechta CPU yadro ishlatish kerak?

Yengil yuklamalar kichik CPU allocation bilan boshlashi mumkin. Faqat workflow soniga qarab emas, monitoring doimiy CPU bosimi yoki concurrency paytida sekinroq bajarilishlarni ko‘rsatsa, yadro qo‘shing.

n8n PostgreSQL talab qiladimi?

Kichik o‘rnatishlar SQLite ishlatishi mumkin, ammo operatsion talablar va concurrency oshganda PostgreSQL production uchun kuchliroq tanlov.

Redis qachon kerak?

Redis queue mode bilan bog‘liq. Oddiy bir instansli deployment faqat VPS-da ishlagani uchun Redis talab qilmaydi.

Qancha disk joyi ajratish kerak?

Disk talabi PostgreSQL o‘sishi, saqlanadigan execution history, binar ma’lumotlar, loglar, konteyner qatlamlari va backup-larga bog‘liq. Qat’iy universal raqamga tayanish o‘rniga o‘sishni kuzating va zaxira qoldiring.

n8n-ni 1 GB VPS-da doimiy ishlata olamanmi?

Ha, agar haqiqiy yuklama sig‘sa. 1 GB VPS haqiqiy ishlaydigan server va kichik, asosan ketma-ket avtomatlashtirishlarni qo‘llashi mumkin, ammo xotira zaxirasi cheklangan. Shu serverdagi PostgreSQL steki, binar ma’lumotga og‘ir vazifalar yoki bir nechta katta parallel bajarilishlar sig‘adi deb hisoblamang. Sarfni kuzating va kuzatilgan resurs bosimiga qarab upgrade qiling.

Production n8n VPS uchun 2 GB yoki 4 GB RAM yaxshiroqmi?

2 GB yengil 1 GB instansga qaraganda ko‘proq joy beradi, 4 GB esa n8n-ni PostgreSQL va HTTPS bilan birga baholash uchun amaliy boshlang‘ich sinf. Universal kafolatlangan production minimum yo‘q: haqiqiy talabni yuklama murakkabligi, peak overlap, konteyner konfiguratsiyasi va saqlanadigan ma’lumotlar belgilaydi.

n8n AI workflow-lari GPU talab qiladimi?

n8n faqat tashqi model API-sini chaqirsa, yo‘q: inference-ni model provayderi bajaradi, VPS esa orchestration, payload va concurrency-ni boshqaradi. Inference modellarni lokal ishlatish alohida apparat qarori bo‘lib, ancha ko‘proq RAM va mos GPU resurslarini talab qilishi mumkin.

n8n out-of-memory xatolariga nima sabab bo‘ladi?

Katta JSON yoki binar payloadlar, xotirani ko‘p ishlatadigan Code operatsiyalari va ustma-ust bajarilishlar keng tarqalgan sabablar. Runtime loglari va peak xotira sarfini tekshiring, keyin bitta execution ichida ushlab turiladigan ma’lumotni kamaytiring yoki o‘lchangan muammoga qarab ko‘proq RAM ajrating.
