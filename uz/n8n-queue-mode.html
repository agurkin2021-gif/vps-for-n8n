MASSHTABLASH

n8n Queue Mode

Queue mode workflow bajarilishini asosiy n8n jarayonidan ajratadi. Main instans triggerlarni qabul qilib bajarilishlar yaratadi, Redis navbatni muvofiqlashtiradi, worker-lar vazifalarni bajaradi, PostgreSQL esa umumiy workflow va bajarilish ma’lumotlarini saqlaydi.

QISQA QAROR

Sizga haqiqatan queue mode kerakmi?

Oddiy rejimda qoling, agar

Bitta instans peak bajarilishlarni bemalol ko‘tarsa va CPU, RAM hamda bajarilish kechikishi barqaror bo‘lsa. Queue mode hozircha kerak bo‘lmagan qo‘shimcha komponentlarni qo‘shadi.

Queue mode-ni ko‘rib chiqing, agar

Uzoq davom etadigan parallel bajarilishlar resurslar uchun raqobat tug‘dirsa, yuklama ostida bajarilish kechikishi oshsa yoki bir nechta worker ishga tushirib bajarish quvvatini oshirish kerak bo‘lsa.

Avval vertikal masshtablang, agar

Tor joy faqat CPU yoki RAM yetishmasligi bo‘lsa va bitta kattaroq instans yuklamani hali ham bemalol ko‘tara olsa.

Arxitekturani o‘zgartirishdan oldin o‘lchang

O‘tishni asoslash uchun peak parallel bajarilish, CPU, RAM, bajarilish davomiyligi, queue depth va ma’lumotlar bazasi bosimini o‘lchang.

ARXITEKTURA

n8n queue mode qanday ishlaydi

1 · MainTimerlar, webhooklar va workflow so‘rovlarini qabul qiladi hamda production bajarilishni o‘zi bajarish o‘rniga execution yaratadi.
2 · RedisMessage broker sifatida ishlaydi. Navbatdagi bo‘sh worker vazifani olishi uchun kutilayotgan execution xabarlarini saqlaydi.
3 · WorkerExecution ID-ni oladi, umumiy ma’lumotlar bazasidan workflow ma’lumotlarini yuklaydi, workflow-ni bajaradi va natijani qayta yozadi.
4 · PostgreSQLUmumiy doimiy workflow va execution ma’lumotlarini saqlaydi. Taqsimlangan queue mode SQLite bilan qo‘llab-quvvatlanmaydi.

ASOSIY TALABLAR

Har bir queue mode o‘rnatilishiga nimalar kerak

Redis

Barcha main va worker jarayonlari navbatni muvofiqlashtirish uchun ishlatiladigan Redis servisiga ishonchli kirishi kerak.

PostgreSQL

Main va worker-lar bir xil ma’lumotlar bazasidan foydalanishi kerak. Queue mode taqsimlangan arxitektura bo‘lib, SQLite atrofida qurilmasligi kerak.

Mos n8n konfiguratsiyasi

Main va worker-lar queue mode-da ishlashi hamda Redis, PostgreSQL va shifrlangan credentials-ga kirish uchun bir xil kerakli konfiguratsiyadan foydalanishi kerak.

Worker quvvati

Worker-larga bajaradigan workflow-lari uchun yetarli CPU va RAM kerak. Jarayonlar sonini oshirish har bir execution resurs xarajatini yo‘q qilmaydi.

Mavjud self-hosted stekda queue mode-ni yoqing. Avval n8n main servisi va har bir worker yopiq tarmoq orqali bir xil PostgreSQL ma’lumotlar bazasi va Redis-ga kira olishini tekshiring. Main va barcha worker-larda EXECUTIONS_MODE=queue ni o‘rnating. Agar haqiqiy Compose servis nomingiz redis bo‘lsa, QUEUE_BULL_REDIS_HOST=redis va QUEUE_BULL_REDIS_PORT=6379 ni ham kiriting. Har bir jarayonda DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres hamda bir xil DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER va DB_POSTGRESDB_PASSWORD qiymatlaridan foydalaning; misoldagi servis nomlarini o‘zingiznikiga moslang. Barcha jarayonlarga aynan mavjud N8N_ENCRYPTION_KEY ni bering. Bir xil Compose tarmog‘idagi konteynerlarni ulash uchungina Redis yoki PostgreSQL host portlarini internetga e’lon qilmang.

Ikkinchi editor emas, executor ishga tushiring. Main bilan bir xil biriktirilgan n8n image versiyasi va umumiy sozlamalardan foydalanadigan n8n worker servisini qo‘shing, ammo uni worker komandasi bilan ishga tushiring. Agar servisni n8n-worker deb nomlagan bo‘lsangiz, docker compose up -d n8n-worker bilan ishga tushiring. Bitta worker-da haqiqiy bajarilishni tasdiqlagandan keyin docker compose up -d --scale n8n-worker=2 orqali shu servisning ikkinchi worker nusxasini ishga tushirishingiz mumkin. Bular to‘g‘ri sozlangan mavjud Compose stekiga qo‘shimchalar, mustaqil o‘rnatish fayli emas; mavjud persistent volume-lar, HTTPS proxy, maxfiy qiymatlar va zaxira nusxalarni saqlang.

Mavjud stek uchun queue mode Compose fragmenti. Quyidagi misolni joriy compose.yaml faylingizga qo‘shing; bu to‘liq mustaqil deployment emas. Misolda sizda allaqachon doimiy va yopiq postgres hamda n8n servislari, muhitda biriktirilgan N8N_VERSION, himoyalangan POSTGRES_PASSWORD va asl N8N_ENCRYPTION_KEY bor deb hisoblanadi. Servis nomlari, volume-lar, ma’lumotlar bazasi va n8n versiyasini mavjud loyihaga moslang. Yuqorida ko‘rsatilgan queue mode Redis sozlamalari va EXECUTIONS_MODE=queue ni mavjud main servisiga ham qo‘shing.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Bu fragmentda Redis yoki worker uchun host port e’lon qilinmaydi. Redis append-only persistence qo‘shimcha tiklash qatlami, ammo serverdan tashqari zaxira nusxalarning o‘rnini bosmaydi. Mavjud HTTPS va authentication konfiguratsiyasini o‘zgartirmang. Tashqi task runner talab qiladigan Code node-lar uchun worker deployment-ingizga runner jarayonlarini alohida sozlang; queue mode task runner-larning o‘rnini bosmaydi.

Mavjud SQLite instansini ko‘chiryapsizmi? Faqat DB_TYPE ni o‘zgartirib, bo‘sh PostgreSQL ma’lumotlar bazasiga ulash eski workflow va credentials-ni ko‘chirmaydi. Har qanday cutover-dan oldin manba ma’lumotlar bazasi, doimiy .n8n papkasi va asl shifrlash kalitini zaxiralang. Qo‘llab-quvvatlanadigan n8n export/import yoki migratsiya usulidan foydalaning, keyin workflow-lar va shifrlangan credentials-ni alohida target-da tekshiring. Rollback uchun asl fayllarni saqlang va tiklashga tayyorlanish uchun quyidagi Backup & Restore qo‘llanmasidan foydalaning. database.sqlite faylini qisqa yo‘l sifatida hech qachon o‘chirmang.

WORKER PARALLELLIGI

Worker-lar soni va har bir worker-dagi vazifalar soni bo‘yicha masshtablanadi

Har bir worker bir nechta vazifani parallel qayta ishlashi mumkin. n8n-ning joriy default worker concurrency-si 10, hujjatlarda esa 5 yoki undan yuqori concurrency tavsiya qilinadi. Juda past concurrency va ko‘p worker ortiqcha ma’lumotlar bazasi ulanishlarini yaratib, connection pool-ni tugatishi mumkin.

Concurrency-ni oshiring, agar

Worker-da bo‘sh CPU va RAM bo‘lsa, workflow-lar esa asosan compute yoki memory-ni to‘ldirish o‘rniga tashqi servislarni kutsa.

Worker qo‘shing, agar

Bitta worker jarayoni bottleneck-ga aylansa va ma’lumotlar bazasi, Redis hamda infratuzilma ko‘proq parallel bajarilishga yetarli quvvatga ega bo‘lsa.

Concurrency-ni kamaytiring, agar

Alohida workflow-lar xotira yoki CPU-ni ko‘p ishlatsa va parallel vazifalar contention, OOM bosimi yoki beqaror bajarilish vaqtini keltirsa.

PostgreSQL-ni kuzating

Ko‘proq worker va concurrency ma’lumotlar bazasi faolligini oshiradi. Ma’lumotlar bazasi quvvatini oshirmasdan execution capacity-ni masshtablash bottleneck-ni yo‘qotmay, boshqa joyga ko‘chirishi mumkin.

Qaysi concurrency limiti amalda ishlashini biling. Worker-ni n8n worker --concurrency=5 yoki Compose servisingizdagi unga teng worker komandasi bilan ishga tushirish mumkin. Agar N8N_CONCURRENCY_PRODUCTION_LIMIT -1 dan boshqa qiymatga aniq o‘rnatilgan bo‘lsa, queue mode-da shu sozlama ustuvor bo‘ladi; aks holda n8n worker-ning --concurrency qiymati yoki standart 10 dan foydalanadi. Worker sonini nominal standart qiymatga ko‘paytirib kafolatlangan throughput deb hisoblamang: haqiqiy quvvat vazifa davomiyligi, CPU, xotira, tashqi API-lar va PostgreSQL ulanishlariga bog‘liq.

WEBHOOKLAR

Queue mode execution handoff kechikishini qo‘shishi mumkin

Main yoki webhook jarayoni HTTP so‘rovini qabul qiladi, ammo workflow execution-ni worker bajaradi. Redis orqali handoff qo‘shimcha overhead beradi. Latency muhim bo‘lgan webhooklarda ko‘proq worker har bir so‘rovni avtomatik tezlashtiradi deb hisoblamang; end-to-end javob vaqtini o‘lchang.

Qabul qilishMain/webhook jarayoni so‘rovni qabul qiladi.
NavbatExecution Redis-ga uzatiladi.
BajarishBo‘sh worker workflow-ni bajaradi.
JavobKerak bo‘lsa natija queue yo‘li orqali qaytariladi.

Webhook trafikini to‘g‘ri jarayonga yo‘naltiring. Alohida n8n webhook processor-lar reverse proxy yoki load balancer ortida bo‘lsa, production path-lari /webhook/* va /webhook-waiting/* ni webhook processor-larga yo‘naltiring; /webhook-test/*, editor va API so‘rovlarini main-da qoldiring. Qo‘shimcha yuklamani ataylab qabul qilmasangiz, main-ni production webhook load-balancing pool-ga qo‘shmang. Respond to Webhook ishlatilgan workflow klientni worker ishini tugatib javob qaytarguncha kutdirishi mumkin, shuning uchun queue mode darhol HTTP javobi yoki timeout bo‘lmasligini kafolatlamaydi. Trafikni almashtirishdan oldin haqiqiy tashqi callback va javob xatti-harakatini sinang.

BINAR MA’LUMOTLAR

Umumiy saqlash joyini e’tibordan chetda qoldirmang

Filesystem cheklovi

Queue mode taqsimlangan worker-lar uchun umumiy persistence modeli sifatida filesystem binary-data storage-ni qo‘llab-quvvatlamaydi.

Tashqi binar saqlash

Workflow-lar taqsimlangan worker-lar o‘rtasida binar ma’lumotlarni saqlashi kerak bo‘lsa, barcha kerakli instanslar kira oladigan, masalan qo‘llab-quvvatlanadigan tashqi object storage-dan foydalaning.

Katta webhook javoblari

Worker-lardan webhook javoblari qabul qiluvchi jarayonga qaytadi. Katta response body-lar Redis xotira bosimini oshirishi va maxsus response-storage konfiguratsiyasini talab qilishi mumkin.

Worker-larni taqsimlashdan oldin rejalashtiring

Lokal fayllarga kuchli bog‘liq workload worker-lar turli mashinalarga tarqatilishidan oldin umumiy persistence uchun qayta loyihalanishi kerak.

Katta webhook javobi chegarasi. Joriy n8n hujjatlarida worker javobini queue orqali qaytarish uchun N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX ning standart qiymati 64 MiB deb ko‘rsatilgan. Redis bir nechta nusxani bir vaqtda ushlab turishi mumkin, shuning uchun har bir parallel katta javob uchun Redis xotirasida response hajmining taxminan 1.5 baravarini rejalashtiring. Offload bo‘lmasa, juda katta javob worker qo‘shish bilan tezlashmaydi — u xato bilan tugaydi.

Versiya va litsenziya cheklovlari. n8n 2.34.0 dan boshlab worker-lar N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true orqali juda katta webhook response body-larini o‘qiladigan umumiy binar storage-ga offload qilishi mumkin, ammo avval barcha main va webhook processor-larni 2.34.0 yoki undan keyingi versiyaga yangilang. Tanlangan N8N_DEFAULT_BINARY_DATA_MODE haqiqatan ma’lumot saqlashi va barcha qatnashuvchi jarayonlar tomonidan o‘qilishi kerak. Tashqi S3 va Azure binary storage uchun amaldagi self-hosted Business or Enterprise litsenziya talab qilinadi; Community Edition ularni yoqa oladi deb hisoblamang. database binary mode katta response-ni pullik tashqi storage-siz offload qilishi mumkin, ammo main instans saqlangan body-ni to‘liq xotiraga yuklaydi va database storage-ning o‘z file-size limiti bor. Aynan response-body offload uchun n8n umumiy filesystem opsiyasini ham tasvirlaydi: bunda har bir instans bir xil diskni mount qiladi, ammo n8n bunday sxemani aniq tavsiya etmaydi. Ushbu maxsus offload yo‘lini taqsimlangan queue mode deployment-da filesystem asosidagi doimiy binar ma’lumotni umumiy saqlash sifatida qo‘llab-quvvatlash deb adashtirmang. Offload-ni yoqishdan oldin edition, versiya va storage konfiguratsiyangizni tekshiring.

MONITORING

Queue foyda berayotganini biling

Queue chuqurligi

Queue worker-lar bo‘shata olishidan tezroq o‘ssa, execution capacity yetishmayotgani yoki downstream bottleneck borligini ko‘rsatadi.

Worker CPU va RAM

Har bir worker uchun saturation va xotira peak-larini o‘lchang. Queue o‘sib turganda worker-lar bo‘sh bo‘lsa, boshqa cheklov bor.

Bajarilish kechikishi

Faqat workflow runtime-ni emas, execution yaratilishi bilan haqiqiy boshlanishi orasidagi kechikishni kuzating.

Health check-lar

Worker health endpoint-lari worker ishlayotganini va uning ma’lumotlar bazasi hamda Redis ulanishlari tayyorligini ko‘rsatishi mumkin.

Faqat yashil konteynerni emas, worker-da haqiqiy bajarilishni tekshiring. To‘g‘ri sozlangan Compose stekda docker compose ps va docker compose logs --tail=100 n8n-worker ni tekshiring (servis nomi boshqacha bo‘lsa almashtiring). Zararsiz, production uchun publish qilingan workflow-ni scheduled trigger yoki test webhook bilan ishga tushiring, so‘ng n8n Executions ko‘rinishidagi execution-ni worker loglaridagi haqiqiy worker ishlashi bilan moslang. Editor muvaffaqiyatli ochilishi, Redis konteyneri ishlashi yoki queue-dagi executionning o‘zi worker vazifani bajarganini isbotlamaydi.

Bog‘liqliklar va readiness-ni tekshiring. Standart misol servis nomlari bilan docker compose exec -T redis redis-cli ping Redis authentication ruxsat bersa PONG javobini olishi kerak. docker compose exec -T postgres pg_isready -U n8n -d n8n PostgreSQL readiness-ni tekshiradi; credentials va servis nomlarini o‘zingiznikiga moslang. Worker-ning yopiq /healthz va /healthz/readiness endpoint-lari kerak bo‘lsa, QUEUE_HEALTH_CHECK_ACTIVE=true ni yoqing. Readiness endpoint Redis va ma’lumotlar bazasi ulanishlarini tekshiradi. Faqat monitoring uchun worker endpoint-larini internetga ochmang.

Manual bajarilishlar boshqa test. Standart holatda OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, shuning uchun editorda workflow-ni qo‘lda ishga tushirish queue mode to‘g‘ri sozlangan bo‘lsa ham main-da bajarilishi mumkin. Manual execution-larni worker-larga yubormoqchi bo‘lsangiz va o‘zgarishni staging muhitda tekshirgan bo‘lsangizgina qiymatni true ga o‘zgartiring. Queue mode worker-lari n8n tashqi task runner-laridan ham farq qiladi; Code node execution uchun ularda alohida konfiguratsiya talablari bor.

YUQORI MAVJUDLIK CHEGARASI

Queue mode execution-larni masshtablaydi, ammo main jarayonni avtomatik high availability qilmaydi

Shifrlash kalitini umumiy qiling

Har bir worker main instans bilan bir xil N8N_ENCRYPTION_KEY dan foydalanishi kerak, shunda worker-lar workflow execution uchun kerakli shifrlangan credentials-ni ochib ishlata oladi.

Versiyalarni bir xil saqlang

Main, webhook va worker jarayonlari bir xil n8n versiyasida ishlashi kerak. Aralash versiyalar rolling o‘zgarishlarda mos kelmaydigan xatti-harakat yaratishi mumkin.

Webhook processor-lar alohida masshtablash qatlami

Kiruvchi webhook hajmi bottleneck-ga aylansa, alohida webhook processor-lar load balancer ortida ishlashi, worker-lar esa execution-ni bajarishi mumkin. O‘lchangan so‘rov hajmi oqlamaguncha bu qatlamni qo‘shmang.

Multi-main boshqa funksiya

High availability uchun bir nechta main jarayonini ishlatish oddiy queue mode bilan bir xil emas. n8n hozir multi-main-ni qo‘shimcha load-balancer va session talablari bo‘lgan self-hosted Enterprise funksiyasi sifatida hujjatlashtiradi.

FAQ

n8n queue mode: ko‘p beriladigan savollar

n8n queue mode Redis talab qiladimi?

Ha. Redis main instans va worker-lar orasidagi kutilayotgan execution-larni muvofiqlashtiradigan message broker.

Queue mode SQLite ishlata oladimi?

Taqsimlangan queue mode arxitekturasi uchun yo‘q. Main va worker-larga umumiy ma’lumotlar bazasi kirishi kerak, n8n bu setup uchun PostgreSQL-ni hujjatlashtiradi.

Nechta worker ishga tushirish kerak?

Universal son yo‘q. O‘lchangan concurrency va worker utilization-dan boshlang, keyin PostgreSQL, Redis, CPU, RAM va queue depth-ni kuzatib quvvat qo‘shing.

n8n worker concurrency nima?

Bu worker parallel qayta ishlashi mumkin bo‘lgan vazifalar soni. Joriy default 10, n8n esa ko‘p low-concurrency worker yaratish o‘rniga worker concurrency-ni 5 yoki undan yuqori qilishni tavsiya etadi.

Kichik VPS-da queue mode-ni yoqish kerakmi?

Faqat yuklama oqlasa. Bitta instans sifatida bemalol ishlaydigan kichik deployment odatda Redis va alohida worker-larsiz boshqarish uchun sodda.
