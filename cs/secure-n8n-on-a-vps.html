ZABEZPEČENÍ VÝROBY

Jak zabezpečit n8n na VPS

Chcete-li zabezpečit n8n na VPS, ponechejte n8n (5678), PostgreSQL (5432) a volitelně Redis (6379) mimo veřejný internet; použijte HTTPS reverzní proxy, SSH klíče a MFA, zachovejte svůj šifrovací klíč, ověřte webhooky, omezte rizikové možnosti pracovních postupů a proveďte audit nasazené instance. Chraňte editor odděleně od veřejných tras webhooku. Samotný HTTPS nezajišťuje připojené služby.

RYCHLÝ KONTROLNÍ SEZNAM

Minimální bezpečnostní základ před vystavením veřejnosti

Začněte svými dosažitelnými porty, HTTPS, ověřeným administrativním přístupem, MFA a ochranou uložených přihlašovacích údajů. Ověřte každý příchozí webhook dříve, než může spustit citlivou práci. Po změně řízení přístupu ověřte, že zamýšlené editory a externí integrace stále fungují, a poté spusťte bezpečnostní audit n8n.

Pouze HTTPS

Umístěte n8n za správně nakonfigurovaný reverzní proxy TLS a konzistentně používejte veřejnou adresu URL HTTPS pro editor a webhooky.

Minimální počet otevřených portů

Vystavte pouze porty potřebné pro veřejný provoz. Udržujte PostgreSQL, Redis a interní aplikační porty mimo veřejný internet.

Kalení SSH

Používejte správu založenou na klíčích, omezte, kdo se může přihlásit, a udržujte operační systém opravený.

Chraňte přihlašovací údaje

Udržujte šifrovací klíč n8n stabilní a tajný. Zacházejte se soubory prostředí, přístupem k databázi a záložními kopiemi jako s citlivými aktivy.

OKRAJ SÍTĚ

Reverzní proxy, HTTPS a důvěryhodné hlavičky

Ukončení TLS

K ukončení HTTPS použijte reverzní proxy, jako je Nginx, Caddy nebo Traefik. Přesměrujte prostý HTTP a vyhněte se přímému odhalení aplikačního portu n8n, když je proxy zamýšleným vstupním bodem.

Konfigurace proxy

Když n8n běží za reverzním proxy, nakonfigurujte správně počet skoků proxy a předejte předávané hlavičky, které n8n potřebuje k rekonstrukci původního požadavku klienta.

Zabezpečené soubory cookie

Obsluhujte editora přes HTTPS, aby ověřovací soubory cookie mohly zůstat v bezpečí. Neobcházejte nefunkční nastavení TLS oslabením zabezpečení souborů cookie.

Adresa URL webhooku

Nastavte adresu URL veřejného webhooku na externě dostupný název hostitele HTTPS, aby vygenerované koncové body webhooku nesměřovaly na interní kontejner nebo adresu HTTP.

Udržujte editor v soukromí, aniž byste narušili webhooky. Pokud je to možné, omezte přístup ke správě pomocí VPN, zásad důvěryhodné IP nebo ověřeného proxy. Veřejné přijímače webhooku a trasy zpětného volání OAuth mohou muset zůstat dostupné; před vynucením pravidla proxy otestujte přihlášení důvěryhodného editora i skutečné externí zpětné volání. Předávání hlaviček klientské adresy pouze z důvěryhodných proxy serverů, nikoli libovolných hlaviček požadavků.

Ověření volajících webhooku: v uzlu Webhook vyberte ověřování Basic, Header nebo JWT namísto None, pokud je to podporováno odesílatelem. Použijte jeho Seznam povolených IP adres tam, kde je to vhodné, a ověřte podpisy poskytovatele tam, kde integrace podporuje podepsané požadavky. Obtížně uhodnutelné URL není dostatečné ověření. Pokud je to vhodné, použijte na proxy limity rychlosti a potvrďte, že platné dávky nejsou blokovány. Oficiální možnosti ověření Webhooku.

VPS TVRZENÍ

Snižte plochu útoku na server

Firewall

Výchozí odepřít nevyžádaný příchozí provoz a povolit pouze služby, které musí být dosažitelné. Databáze a porty Redis normálně patří do privátních/místních sítí.

SSH

Upřednostněte klíče SSH před hesly, zakažte zbytečné přihlašovací cesty a omezte přístup pro správce. Přístup ekvivalentní kořenům by měl být přísně kontrolován.

aktualizace OS

Opravte běhové prostředí hostitele a kontejneru Linux. Zpevnění aplikací nemůže kompenzovat odhalený nebo zastaralý operační systém.

Expozice kontejneru

Publikujte pouze porty, které potřebují přístup k hostiteli. Interní služby by měly komunikovat v soukromých sítích Docker spíše než prostřednictvím veřejných rozhraní.

Před změnou nastavení firewallu nebo SSH zkontrolujte: zkontrolujte naslouchací porty pomocí sudo ss -lntp, Docker publikování s docker compose ps z adresáře projektu a hostitelské zásady brány firewall s sudo ufw status verbose pokud se používá UFW. Než zakážete přístup pomocí hesla, ověřte svůj skutečný port SSH a úspěšné přihlášení pomocí klíče v samostatné relaci. Publikované porty Docker mohou obejít pravidla UFW; samotná stránka stavu brány firewall neprokazuje, že port 5678 je soukromý. Zkontrolujte skutečnou externí dosažitelnost. Docker/UFW upozornění.

Zkontrolujte automatické Ubuntu bezpečnostní aktualizace místo toho, abyste předpokládali, že fungují: prohlédnout apt-config dump APT::Periodic::Unattended-Upgrade a log /var/log/unattended-upgrades/unattended-upgrades.log. Pokud jsou bezobslužné aktualizace zabezpečení zakázány, sudo dpkg-reconfigure unattended-upgrades poskytuje podporovaný konfigurační dialog. Před povolením na funkčním VPS zkontrolujte chování restartování a restartování služby. Ubuntu Aktualizace APT ano ne automaticky aktualizujte obrázek n8n Docker nebo každé softwarové úložiště třetí strany. Ubuntu automatická aktualizace dokumentace.

Volitelné SSH monitorování hrubou silou: Fail2Ban dokáže detekovat opakovaná neúspěšná SSH přihlášení. Pokud je nainstalováno a nakonfigurováno pro SSH, ověřte vězení pomocí sudo fail2ban-client status sshd a potvrďte, že čte váš aktuální ověřovací protokol nebo deník SSH a odpovídá nakonfigurovanému portu. To doplňuje SSH klíče a síťová omezení; nenahrazuje je. Nekopírujte pevný SSH port nebo pravidlo zákazu, aniž byste nejprve zkontrolovali existující přístup. Ubuntu SSH návod na kalení.

DATABÁZE A REDIS

Udržujte backendové služby soukromé

V typickém nastavení Docker skládání by PostgreSQL a režim fronty Redis měly být dostupné příslušnými kontejnery prostřednictvím privátní sítě, nikoli portů publikovaných hostitelem. Ověřte pomocí docker compose ps že 5432 a 6379 nejsou veřejně zveřejněny; samostatně si přečtěte VPS/vystavení cloudovému firewallu. Síťové zásady nenahrazují pověření databáze s nejnižším oprávněním.

PostgreSQLNavažte jej na privátní rozhraní nebo kontejnerovou síť, pokud není vzdálený přístup výslovně vyžadován a nezávisle zabezpečen.
RedisRežim fronty Redis je infrastruktura, nikoli veřejný koncový bod. Omezte přístup k síti na komponenty n8n, které to vyžadují.
PověřeníPoužívejte vyhrazená databázová pověření pouze s oprávněními, která aplikace potřebuje, a chraňte je mimo kontrolu zdroje.
DopravaKdyž databázový provoz prochází nedůvěryhodnými sítěmi, použijte vhodný šifrovaný přenos, než se spoléhat na šifrování pověření na úrovni aplikace.

N8N TAJEMSTVÍ

Chraňte šifrovací klíč a hranici pověření

Šifrovací klíč

n8n zašifruje uložené přihlašovací údaje pomocí svého šifrovacího klíče. Zachovejte stejný klíč mezi restarty a pracovníky a chraňte jej odděleně od běžného obsahu aplikace.

Tajemství životního prostředí

Nezadávejte hesla, tokeny nebo šifrovací klíč do veřejného úložiště. Omezte přístup k souborům prostředí a tajným klíčům nasazení.

Uživatelský přístup

Udělte přístup editoru pouze důvěryhodným uživatelům. Pracovní postupy se mohou připojit k citlivým systémům a mohou zpracovávat tajemství nebo spouštět výkonné uzly.

Rozsah pověření

Kde je to možné, používejte úzce vymezené servisní účty a tokeny API. Ohrožený pracovní postup by neměl automaticky zdědit široký přístup k nesouvisejícím systémům.

n8n konfigurace ke kontrole: N8N_BLOCK_ENV_ACCESS_IN_NODE=true zabraňuje přístupu kódového uzlu a výrazu k hodnotám prostředí; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true požaduje oprávnění pouze vlastníka k souboru nastavení. Nechat N8N_ENCRYPTION_KEY perzistentní a bezpečně zálohované: n8n může vytvořit náhodný klíč při prvním spuštění, ale jeho ztráta může způsobit, že stávající šifrované přihlašovací údaje nebudou použitelné. Nenahrazujte produkční šifrovací klíč náhodně; používat oficiálně podporovaný postup rotace. Blokování přístupu k prostředí může narušit stávající integrace, proto před produkčními změnami otestujte. n8n definice bezpečnostních proměnných.

RIZIKO PRACOVNÍHO TOKU

Uzly mohou rozšířit hranici zabezpečení

Vlastní hosting dává pracovním tokům značnou sílu. Spouštění kódu, přístup k shellu, libovolné požadavky HTTP a uzly komunity třetích stran mohou zvýšit riziko. Vypněte funkce, které nepotřebujete, a před jejich spuštěním zkontrolujte nedůvěryhodné importy pracovních postupů.

Používejte přesné podporované ovládací prvky: konfigurovat NODES_EXCLUDE s polem JSON uzlů k deaktivaci, jako je např n8n-nodes-base.executeCommand a n8n-nodes-base.readWriteFile, pokud se nepoužívá. Některé vysoce rizikové uzly jsou v novějších verzích již ve výchozím nastavení blokovány; zkontrolujte skutečný seznam, než jej změníte. Oficiální výjimky uzlů.

Od n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true umožňuje kontroly odchozích požadavků HTTP na interní, zpětné smyčky a rozsahy metadat. Legitimní interní pracovní postupy API mohou přestat fungovat; v případě potřeby zařaďte do seznamu povolených pouze cíle, které ovládáte. Segmentaci sítě ponechte jako primární obranu. Pokud jde o izolaci kódových uzlů, zkontrolujte externí spouštěče úloh. SSRF ochrana · Task-runner izolace.

Komunitní uzlyInstalujte pouze balíčky, kterým důvěřujete; provádějí se uvnitř vašeho n8n prostředí.
Rizikové uzlyVylučte uzly, které vaše nasazení nepotřebuje, když jejich schopnosti překračují zamýšlenou hranici pracovního postupu.
SSRFPoužijte ochranu SSRF a síťové ovládací prvky n8n tam, kde by pracovní postupy neměly být schopny dosáhnout interních koncových bodů nebo koncových bodů metadat.
Importy pracovních postupůPřed aktivací zkontrolujte importované pracovní postupy, pověření, výrazy a spustitelné kroky.

AUDIT A AKTUALIZACE

Zabezpečení je provozní proces

Spusťte n8n bezpečnostní audit

Oficiální příkaz CLI je n8n audit. Pokud je vaše služba Docker Compose pojmenována n8n, běhat docker compose exec -T n8n n8n audit v tomto adresáři nasazení. Projděte si pět kategorií: nepoužívané přihlašovací údaje, rizikové vzory dotazů SQL, přístup k souborovému systému, rizikové/komunitní uzly a rizika instancí včetně nechráněných webhooků a zastaralých verzí. Opravte relevantní nálezy a spusťte znovu. Nejedná se o penetrační test. Oficiální průvodce auditem.

Aktualizujte záměrně

Udržujte n8n dostatečně aktuální, abyste mohli přijímat bezpečnostní opravy. Prohlédněte si poznámky k vydání a otestujte důležité upgrady místo toho, abyste nechali instanci připojenou k internetu trvale zastaralou.

Sledovat autentizaci

Sledujte neočekávané vzorce přístupu, změny pracovních postupů a selhání. Pokud váš operační model nevyžaduje širokou veřejnou dosažitelnost, omezte uživatelské rozhraní editoru dále.

Připravte vrácení a obnovení

Před významnými aktualizacemi si pořiďte obnovitelné zálohy. Podrobný rozsah zálohování a obnovení patří do samostatného průvodce obnovením.

Minimalizovat citlivou historii provádění: úspěšné běhy mohou uchovávat zákaznická data a tokeny. Když je to vhodné, nastavte EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, zachovat EXECUTIONS_DATA_PRUNE=truea vyberte EXECUTIONS_DATA_MAX_AGE v hodinách, jako např 168 (sedm dní). Toto jsou konfigurovatelné příklady, nikoli zákonná pravidla uchovávání. Méně historie znamená méně ladění a forenzních dat; běžící, čekající nebo komentované exekuce nelze ořezávat stejným způsobem. Oficiální zadržení provedení.

Podezření na kompromis: omezte škodlivý přístup bez zničení důkazů, kontrolujte aktivitu proxy, hostitele a n8n a změněné pracovní postupy, zrušte nebo otočte možná vystavená pověření upstream, opravte příčinu a v případě potřeby obnovte pouze z testovaných obnovitelných záloh. Zkontrolujte adresy URL dotčených webhooků, účty editorů a připojené služby; nepředpokládejte, že HTTPS, snímky nebo nákup VPS poskytují služby reakce na incidenty.

OVLÁDÁNÍ ÚČTU A PLATFORMY

Chraňte editor i VPS

Vyžadovat silnější ochranu přihlášení

Povolte dvoufaktorové ověřování pro účty editorů a vynucujte bezpečnostní zásady MFA až n8n, když vaše vydání podporuje centralizované vynucování zásad.

Omezte, kdo může upravovat pracovní postupy

Přístup editora je privilegovaný přístup: pracovní postupy mohou číst přihlašovací údaje, volat interní systémy a spouštět výkonné uzly. Udržujte uživatelský přístup úzký a odstraňte účty, které jej již nepotřebují.

Zakažte funkce, které nepoužíváte

Snižte povrch útoků aplikací deaktivací veřejných API, když je to zbytečné, a zablokováním vysoce rizikových uzlů nebo funkcí, které váš operační model nepotřebuje.

Používejte SSRF a tajné kontroly záměrně

U pracovních postupů, které mohou klást libovolné požadavky HTTP, vyhodnoťte ochranu SSRF podle n8n a udržujte tajemství mimo kód pracovního postupu, veřejná úložiště a široce čitelné soubory prostředí.

Omezit nepoužívané koncové body správy: N8N_PUBLIC_API_DISABLED=true deaktivuje n8n veřejný REST API a N8N_PUBLIC_API_SWAGGERUI_DISABLED=true deaktivuje své hřiště API samostatně. Udělejte to pouze v případě, že vaše integrace tyto funkce nevyžadují. Zakázání REST API neověřuje adresy URL webhooku pracovního postupu. Použijte MFA pro uživatele editorů a centralizované zásady pouze tam, kde je vaše verze n8n podporuje.

Časté dotazy

n8n VPS zabezpečení: běžné otázky

Měl by být port n8n vystaven přímo?

Pokud je veřejným vstupním bodem reverzní proxy, odkryjte proxy a ponechte za ním aplikační port, než abyste plošně publikovali nepotřebné služby.

Měl by být PostgreSQL nebo Redis veřejný?

Normálně ne. Měly by být dosažitelné pouze systémy, které je vyžadují. Veřejné vystavení zvyšuje útočnou plochu, aniž by napomáhalo normálnímu n8n provozu.

Proč je důležitý šifrovací klíč n8n?

Chrání přihlašovací údaje uložené v n8n a musí zůstat konzistentní v celém nasazení. Jeho ztráta může zabránit tomu, aby obnovená data poskytovala použitelná šifrovaná pověření.

Jsou komunitní uzly bezpečné?

Rozšiřují n8n o kód třetích stran, takže by se s nimi mělo zacházet jako se softwarovými závislostmi s vlastním rizikem dodavatelského řetězce a privilegií. Instalujte pouze to, čemu důvěřujete a co potřebujete.

Zabezpečuje HTTPS samostatně hostovanou instanci n8n?

Č. HTTPS chrání přepravu. Zabezpečení výroby také vyžaduje posílení hostitele, řízení přístupu, soukromé backendové služby, tajnou ochranu, možnosti bezpečného workflow, monitorování a aktualizace.

Může být editor n8n soukromý, zatímco produkční webhooky stále běží?

Ano. Důvěryhodný reverzní proxy nebo VPN může omezit přístup editora/administrátora odděleně od veřejných produkčních webhooků a cest zpětného volání OAuth. Po každé změně pravidel přístupu otestujte důvěryhodné přihlášení a externí webhook, abyste předešli náhodnému zablokování vašich integrací.

Jak mohu ověřit příchozí n8n webhooky?

Nakonfigurujte ověřování Basic, Header nebo JWT v uzlu Webhook, pokud to odesílatel podporuje. Můžete také použít seznam povolených IP adres a zkontrolovat podpisy poskytovatelů, pokud jsou k dispozici. Nespoléhejte se pouze na tajně vypadající cestu a ověřte požadavky dříve, než spustí citlivé API akce.
