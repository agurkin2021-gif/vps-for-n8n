ZÁLOHA A OBNOVA

Zálohování a obnova n8n

Pro zálohování a obnovu n8n provozovaného na vlastním serveru uchovávejte databázi SQLite nebo konzistentní zálohu PostgreSQL, trvalou složku .n8n s původním šifrovacím klíčem, konfiguraci nasazení a všechny externí binární soubory či připojené soubory, na nichž workflow závisejí. Šifrovanou kopii uchovávejte mimo VPS a obnovu otestujte na samostatné instanci. Exporty workflow a přihlašovacích údajů přes CLI slouží k výběrové obnově; samotné exporty JSON nejsou úplnou zálohou serveru.

Vyberte VPS pro n8n

Partnerský odkaz: můžeme získat provizi z nákupů.

STRUČNÝ KONTROLNÍ SEZNAM

Co musí záloha n8n obsahovat

Databáze

Zálohujte databázi PostgreSQL nebo soubor databáze SQLite používaný instancí. Databáze uchovává základní data n8n, například workflow, přihlašovací údaje a historii spuštění.

Šifrovací klíč

Přesný šifrovací klíč n8n uchovávejte odděleně a bezpečně. Obnovené šifrované přihlašovací údaje vyžadují stejný klíč.

Trvale ukládané soubory

Zahrňte trvalý datový adresář n8n a všechny připojené soubory, úložiště binárních dat a soubory potřebné pro vaše workflow.

Konfigurace nasazení

Uchovávejte soubory Docker Compose a další konfiguraci nutnou k opětovnému sestavení prostředí, která neobsahuje tajné údaje. Tajné údaje zabezpečte odpovídajícím řízením přístupu.

DVA ZPŮSOBY ZÁLOHOVÁNÍ

Logický export versus úplná obnova po havárii

Export workflow a přihlašovacích údajů

Exporty přes CLI n8n jsou užitečné pro migraci, verzované kopie workflow a výběrovou obnovu. Přihlašovací údaje lze exportovat šifrovaně a později importovat se stejným šifrovacím klíčem. Chcete-li obnovit jediné workflow, otevřete nabídku se třemi tečkami v editoru, zvolte Download a stáhněte soubor JSON. Poté jej pomocí Import from File načtěte do nového workflow určeného ke kontrole nebo do izolované instance. Před nahrazením živého workflow zkontrolujte přihlašovací údaje, ID workflow a parametry uzlů. Obnovení JSON workflow neobnoví celý server.

Export databázových entit

CLI umožňuje export databázových entit při přesunu dat mezi podporovanými typy databází. Export historie spuštění je volitelný, protože tyto tabulky mohou být velmi rozsáhlé.

Obnova celé instance

Pro obnovu po výpadku celého serveru zálohujte skutečnou databázi, šifrovací klíč, trvalá data a související konfiguraci nasazení. Nepředpokládejte, že export workflow do JSON obnoví celou instanci.

Snapshot od poskytovatele

Snapshot VPS je užitečnou další vrstvou obnovy, neměl by však být jedinou kopií ani nahrazovat nezávisle ověřenou zálohu aplikace a databáze.

DATABÁZE

Zálohujte databázi konzistentně

PostgreSQL

Zvolte metodu vytvářející konzistentní zálohu PostgreSQL a ukládejte ji mimo VPS. Kopie databáze na stejném disku, který selže, vám obnovu po havárii nezajistí.

SQLite

Pokud používáte SQLite, zálohujte databázový soubor v trvalém datovém adresáři n8n. Nekopírujte databázi nekonzistentním způsobem během souběžného zápisu.

Historie spuštění

Rozhodněte, zda do cíle obnovy patří také historie spuštění. Může výrazně zvětšit zálohy, proto se řiďte požadovanou dobou uchovávání dat a právními či interními pravidly.

Verze databáze

Zaznamenejte databázový systém a verzi původního nasazení, abyste pro obnovu mohli připravit kompatibilní prostředí.

PostgreSQL na VPS s Docker Compose. Pokud se služba PostgreSQL jmenuje postgres a databáze i databázový uživatel se jmenují n8n, následující příkaz vytvoří na hostitelském serveru konzistentní zálohu PostgreSQL ve vlastním formátu. Před spuštěním zkontrolujte skutečný soubor Compose a případně upravte názvy služeb a přihlašovací údaje. pg_dump dokáže při běžícím PostgreSQL vytvořit logicky konzistentní zálohu, ale nezálohuje samostatnou .n8n uživatelskou složku ani externí binární data.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Kontrola seznamu souborů v archivu odhalí zjevné problémy s formátem, ale sama nedokazuje, že je zálohu možné obnovit. Šifrovanou kopii uložte mimo server a obnovu nacvičte. Možnosti specifické pro databázi najdete v oficiální dokumentaci PostgreSQL k pg_dump.

SQLite v Dockeru. Při výchozím nasazení se SQLite jsou soubor database.sqlite a konfigurační soubor s vygenerovaným šifrovacím klíčem uloženy v trvalé složce .n8n (obvykle připojené jako /home/node/.n8n). Prosté kopírování právě používané databáze SQLite nepovažujte za konzistentní zálohu. Před kopírováním složky zastavte n8n a všechny ostatní procesy zapisující do databáze; pokud provoz nelze přerušit, použijte podporovaný mechanismus online zálohování SQLite:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Jde pouze o ukázkové příkazy pro uvedenou službu a cestu, nikoli o univerzální strukturu svazků. Zkopírovaná složka zůstává zpočátku na stejném VPS; přeneste ji do zabezpečeného úložiště mimo server. Pokud existují workery režimu fronty nebo další zapisující procesy, zastavte jejich zápisy a postupujte podle skutečné architektury nasazení. Aktuální návod n8n k úplnému zálohování vysvětluje požadavek na konzistenci SQLite.

Obnovení výchozí složky SQLite do čistého cílového prostředí: nejprve zastavte n8n i všechny procesy zapisující do databáze. Jakmile budou připraveny kompatibilní kontejner n8n a cílový svazek, vraťte zálohovanou složku .n8n včetně veškerého obsahu zpět do stejného trvalého adresáře. Postup přepíše cílové soubory, proto jej nespouštějte na instanci obsahující data, která chcete zachovat:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker umožňuje kopírovat soubory i do zastavených kontejnerů, ale vlastník cílových souborů se může lišit. Před spuštěním zajistěte, aby proces n8n mohl obnovenou konfiguraci a databázi číst i zapisovat. Pokud vaše konfigurace Compose používá jinou cestu nebo bind mount, příkaz odpovídajícím způsobem upravte. Dokumentace příkazu Docker Compose cp. Pouhé obnovení složky n8n nestačí, pokud instalace používá samostatnou databázi PostgreSQL.

ZÁSADNÍ TAJNÝ ÚDAJ

Šifrovací klíč je součástí obnovy

n8n šifruje uložené přihlašovací údaje klíčem dané instance. Bez odpovídajícího klíče mohou být po obnově databáze nebo exportovaných šifrovaných přihlašovacích údajů tyto údaje nepoužitelné.

Pokud jste nastavili N8N_ENCRYPTION_KEY, obnovte přesně tento tajný klíč. Jinak je vygenerovaný klíč uložen v trvalém souboru .n8n/config, který musíte při zálohování a obnově zachovat. Klíče pro obnovu uchovávejte bezpečně mimo VPS. V režimu fronty musí hlavní proces i všechny workery používat stejný klíč.

DoporučenoUchovávejte bezpečnou kopii přesného klíče používaného v produkci.
DoporučenoPřed testováním přihlašovacích údajů ověřte, že obnovená instance používá tento klíč.
NedělejtePo obnově serveru se nespoléhejte na nově vygenerovaný klíč.
NedělejteNeukládejte klíč do veřejného repozitáře ani vedle nezabezpečené zálohy.

SOUBORY A BINÁRNÍ DATA

Záloha databáze nemusí pokrývat všechny závislosti workflow

Trvalá data .n8n

Najděte a zálohujte skutečnou uživatelskou složku .n8n, nikoli pouze obraz kontejneru. V běžném nasazení Docker je připojena na /home/node/.n8n; mimo Docker je výchozí cesta ~/.n8n. Pokud je nastaveno N8N_USER_FOLDER, n8n vytvoří složku .n8n uvnitř uvedeného nadřazeného adresáře. Zahrňte konfigurační soubor s klíčem, místní databázi SQLite a případná binární data či data spuštění uložená v souborovém systému.

Soubory workflow na připojených svazcích

Pokud workflow čtou nebo zapisují do adresářů připojených z hostitelského serveru, zálohujte tyto adresáře zvlášť. Bez jejich obnovení mohou jinak funkční workflow přestat pracovat.

Binární data

Zjistěte používaný režim ukládání dat a obnovte všechny externí závislosti. Binární data nebo data spuštění uložená v souborovém systému mohou být ve složce .n8n či ve vlastním adresáři; úložiště S3/Azure Blob nebo jiná nakonfigurovaná externí úložiště vyžadují samostatnou obnovitelnou kopii a nastavení přístupu. Samotný databázový dump tyto soubory nenahradí.

Komunitní uzly

Zaznamenejte používané komunitní balíčky a jejich verze. Zálohujte také adresáře vlastních uzlů nastavené pomocí N8N_CUSTOM_EXTENSIONS. Mohou ležet mimo .n8n, takže obnova samotné databáze a uživatelské složky nemusí stačit k fungování workflow s vlastními uzly.

STRATEGIE ZÁLOH MIMO SERVER

Záloha na stejném VPS je pouze místní kopií

Místní kopieMístní kopie pomůže s rychlým návratem k předchozímu stavu, ale neochrání před ztrátou serveru, poruchou disku nebo závažnou chybou.
Kopie mimo serverAlespoň jednu zálohu uchovávejte v úložišti nezávislém na produkčním VPS.
Zálohy s historií verzíUchovávejte více bodů obnovy, aby poškození dat nebo chybná změna nepřepsaly jedinou použitelnou zálohu.
Řízení přístupuZálohy mohou obsahovat přihlašovací údaje, logiku workflow i citlivá firemní data. Odpovídajícím způsobem je šifrujte a omezte k nim přístup.
MonitorováníNastavte upozornění na selhání plánovaných záloh nebo zastavení vytváření nových bodů obnovy.

Sledujte plnění harmonogramu záloh. Zaznamenávejte čas úspěšného dokončení každé zálohy a přenosu, velikost souboru, verzi původní databáze, místo bezpečného uložení šifrovacího klíče a datum posledního úspěšného testu obnovy. Upozorňujte na chybějící, neúspěšné nebo nečekaně prázdné zálohy. Před odesláním mimo VPS archivy zašifrujte a omezte přístup k tajným údajům pro obnovu. Více časově označených bodů obnovy pomáhá i tehdy, když poškození zjistíte až poté, co nejnovější kopie přepsala poslední funkční zálohu.

Pokud například můžete přijít nejvýše o šest hodin změn, zálohování každých šest hodin je výchozí bod, nikoli záruka: neúspěšná úloha nebo zpožděné kopírování mimo server mohou skutečnou ztrátu zvětšit. Dobu uchovávání a četnost testů obnovy nastavte podle vlastních cílů RPO/RTO a požadavků na data, nikoli podle domnělé univerzální politiky 7 či 30 dní.

POŘADÍ OBNOVY

Obnovujte v řízeném pořadí

1 · PřípravaPřipravte kompatibilní server, databázi a prostředí pro kontejnery nebo běh aplikace.
2 · Obnova tajných údajůBezpečně nastavte původní šifrovací klíč n8n a další požadované tajné údaje nasazení.
3 · Obnova databázeObnovte PostgreSQL nebo SQLite a ověřte, že se n8n dokáže připojit k očekávaným datům.
4 · Obnova souborůObnovte trvalé adresáře, binární data a soubory workflow na připojených svazcích.
5 · Spuštění n8nSpusťte aplikaci s očekávaným názvem hostitele a konfigurací databáze i prostředí.
6 · OvěřeníOvěřte načtení uživatelů, workflow a přihlašovacích údajů; poté spusťte reprezentativní workflow a otestujte webhooky.

Příklad obnovy PostgreSQL po havárii: na samostatném čistém cílovém serveru s již vytvořenou odpovídající databázovou rolí a prázdnou databází n8n spusťte pouze PostgreSQL. Před importem počkejte, až bude databáze připravena: docker compose up -d se může dokončit ještě během inicializace PostgreSQL, takže následný příkaz pg_restore může selhat. V příkladu se používá --wait v novější instalaci Compose a nezávislá kontrola pomocí pg_isready. Pro spolehlivé čekání nastavte odpovídající kontrolu stavu PostgreSQL nebo připravenost databáze výslovně ověřte. Příkaz nikdy nepouštějte na již naplněnou produkční databázi a n8n nespouštějte, dokud neobnovíte databázi a odpovídající .n8n soubory a šifrovací klíč.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Cílové prostředí musí mít kompatibilní verzi PostgreSQL, oprávnění rolí, rozšíření a původní konfiguraci n8n. Obnovte .n8n do správného trvalého svazku nebo připojeného adresáře podle svého zálohovacího postupu a zachovejte vlastníka i přístupová práva. Obnovte také externí binární soubory, vlastní rozšíření, konfiguraci Compose a tajné údaje. Poté spusťte kompatibilní verzi n8n a zkontrolujte logy. Samotná obnova databáze klíč nevrátí: při nasazení s PostgreSQL je uložen v souboru .n8n/config pokud jste jej výslovně nenastavili proměnnou N8N_ENCRYPTION_KEY. Dokumentace pg_restore · Postup obnovy celé instance n8n.

TEST OBNOVENÍ

Úspěšnost zálohy prokáže až funkční obnova

Testujte v čistém prostředí

Skutečný test musí prokázat, že ze zálohy dokážete znovu vytvořit instanci bez souborů, které náhodou zůstaly na produkčním serveru a nejsou součástí deklarované zálohy.

Zkontrolujte přihlašovací údaje

Nestačí jen otevřít workflow. Ověřte, že se obnovené šifrované přihlašovací údaje skutečně dešifrují a umožňují úspěšné ověření.

Spusťte reprezentativní workflow

Otestujte také workflow závislá na webhoocích, externích API, připojených souborech a komunitních uzlech, nikoli pouze jednoduchou automatizaci.

Změřte dobu obnovy

Zaznamenejte dobu obnovy i zbývající ruční kroky. Ze samotné existence zálohy tak vznikne ověřený provozní postup.

Ověřený test obnovy: SQLite a PostgreSQL

Testovací prostředí: n8n 2.42.5 v izolovaných kontejnerech Docker na jednorázovém runneru GitHub Actions se syntetickým workflow o dvou uzlech. Tyto testy proběhly 8. října 2026, nikoli na zákaznickém nebo produkčním serveru n8n.

SQLite: PASSImportovali jsme testovací workflow, exportovali je, zastavili všechny procesy zapisující do databáze a archivovali trvalou složku .n8n s databází SQLite a jejím vygenerovaným šifrovacím klíčem. Poté jsme data obnovili do čistého svazku, spustili n8n a obnovené workflow znovu exportovali a provedli.
PostgreSQL: PASSImportovali jsme stejné testovací workflow a vytvořili i zkontrolovali zálohu ve vlastním formátu pomocí pg_dump, obnovil jej pomocí pg_restore do nové prázdné databáze PostgreSQL, obnovil oddělenou .n8n složku a nakonec obnovené workflow znovu exportovali a provedli.
Co výsledek PASS potvrzujeTestované postupy zachovaly dané workflow, jeho dva uzly i propojení a umožnily spuštění po obnově. Jde o reprodukovatelné funkční testy základní obnovy, nikoli o výkonnostní benchmarky.
Co nebylo testovánoNetestovalo se dešifrování a ověřování skutečných přihlašovacích údajů, produkční webhooky, workery režimu fronty ani Redis, binární úložiště S3/Azure, vlastní uzly, přístup uživatelů či projektů ani obnova živé produkční instance. Každou skutečně používanou závislost je nutné otestovat samostatně.

Jak test zopakovat: Použijte jednorázovou instalaci n8n, vytvořte neškodné workflow se dvěma uzly, proveďte příslušnou zálohu databáze a trvalé složky a obnovte ji do čistého svazku nebo databáze. Poté ověřte uzly, jejich propojení i skutečné spuštění obnoveného workflow. V produkci navíc ověřte šifrované přihlašovací údaje, webhooky a externí soubory, než obnovu po havárii prohlásíte za ověřenou.

Kontrolní seznam pro úspěšný test obnovy: Použijte izolovanou doménu nebo prostředí. Ověřte přítomnost uživatelů a workflow, že se alespoň jedny existující šifrované přihlašovací údaje úspěšně ověří bez opětovného zadání, že produkční webhook spouští správné obnovené workflow, že připojené soubory a binární přílohy zůstaly čitelné a že fungují integrace s požadovanými komunitními uzly. Zkontrolujte stáří zálohy, naměřený výpadek a dostupnost kopie mimo server. Pokud některý zásadní test selže, označte daný bod obnovy jako neověřeno místo abyste zálohu považovali za kompletní.

OMEZENÍ ZÁLOHOVÁNÍ PŘES CLI

Co exporty workflow a přihlašovacích údajů neobnovují

Exporty CLI nejsou zálohou celé instance

Exporty workflow a přihlašovacích údajů nezahrnují uživatele a role, historii spuštění a logy, proměnné ani nastavení instance, například šifrovací klíč.

U nové instance je nejprve nutné nastavit vlastníka

Na čisté instanci dokončete nastavení vlastníka ještě před importem přihlašovacích údajů. Při obnově více uživatelů nebo projektů může být také potřeba správně přiřadit uživatele či projekty.

Importovaná ID mohou přepsat existující položky

Exporty workflow a přihlašovacích údajů zachovávají původní ID. Import do instance se stejnými ID může nahradit existující položky.

Importovaná workflow publikujte vědomě

Import přes CLI běžně zanechává workflow neaktivní. U n8n 2.x zkontrolujte stav publikování každého importovaného workflow a publikujte pouze ta, která chcete provozovat. CLI vlastní instalace také podporuje příkaz n8n publish:workflow --id=YOUR_WORKFLOW_ID. Pokud n8n běží, změny stavu publikování nebo zrušení publikování provedené přes Server CLI se projeví až po restartu n8n. Před ověřováním plánovaných spouštěčů a produkčních webhooků nebo přesměrováním provozu proto instanci restartujte.

Příklad hromadného exportu v Docker Compose: pokud je vaše služba n8n pojmenována n8n, můžete spustit následující oficiální příkazy CLI pro zálohování. Výstupní adresář je záměrně umístěn v trvalé připojené složce .n8n protože jiné adresáře uvnitř kontejneru mohou při jeho novém vytvoření zmizet. Ověřte, že uživatel kontejneru n8n smí do tohoto adresáře zapisovat. Soubory JSON s workflow a přihlašovacími údaji uchovávejte v oddělených adresářích—n8n upozorňuje na problém při importu, pokud jsou oba typy exportu ve stejném adresáři.

Záloha konceptů a publikovaných verzí v n8n 2.x: běžný --backup export workflow zachycuje současné koncepty, které se mohou lišit od verzí publikovaných v produkci. Chcete-li zachovat skutečně publikovanou verzi konkrétního workflow, exportujte ji zvlášť příkazem docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, až ověříte, že výstupní složka existuje a lze do ní zapisovat. CLI také umožňuje export historické verze pomocí --version=VERSION_ID. Tyto exporty uchovávejte mimo server společně s úplnou zálohou; nepředpokládejte, že JSON konceptu odpovídá aktuálně publikované verzi.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Zkopírované ~/n8n-recovery/cli adresář zůstává na VPS, dokud jej nepřesunete do zabezpečeného nezávislého úložiště záloh. Exportované přihlašovací údaje jsou ve výchozím stavu šifrované a k importu potřebují stejný šifrovací klíč. Nepoužívejte přepínač --decrypted s výjimkou přísně kontrolované migrace: ukládá tajné údaje v čitelné podobě. Nikdy neukládejte exporty obsahující citlivou logiku workflow nebo přihlašovací údaje do veřejného repozitáře GitHub. Některé šablony třetích stran pro zálohování přihlašovacích údajů na GitHub záměrně exportují tajné údaje bez šifrování. Soukromý repozitář omezuje přístup, ale sám data nešifruje. U každé šablony prověřte skutečná nastavení exportu a oprávnění úložiště, tajné údaje před přenosem mimo server zašifrujte a v případě nechtěného zveřejnění nešifrovaných údajů příslušná přihlašovací data změňte.

Příklad hromadného importu: na čisté cílové instanci nejprve nastavte vlastníka, poskytněte původní šifrovací klíč a zajistěte, aby na obnovovacím VPS byly dostupné soubory zálohy. Následující příkazy vytvoří cílový adresář a zkopírují podsložky workflows/ a credentials/ z hostitelského serveru do kontejneru n8n; pokud používáte jiné uspořádání svazků Dockeru, upravte cesty:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Zkontrolujte vlastníka souborů a přístupová práva uživatele kontejneru n8n. Bez ověřené možnosti návratu k předchozímu stavu neimportujte data do již používané produkční instance: shodná ID workflow a přihlašovacích údajů mohou přepsat existující položky. Poté spusťte:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Importovaná ID mohou nahradit existující workflow nebo přihlašovací údaje. Pro zkušební import použijte izolovanou testovací instanci a následně ověřte přihlašovací údaje, aktivaci a stav publikování. V n8n 2.x samotné obnovení konceptu z JSON nedokazuje, že workflow bylo publikováno ani že lze spouštět jeho plánované spouštěče. Bezpečnost při importu: u instance n8n bez režimu multi-main mohou dříve aktivní plánované spouštěče cron po importu přes CLI pokračovat až do restartu. Před povolením obnovených úloh zastavte nebo izolujte produkční spouštěče a restartujte n8n; ověřte, že nedochází k duplicitnímu spuštění. Exporty CLI neobsahují původní uživatele, logy spuštění, proměnné instance ani šifrovací klíč. --backup nastavuje přepínače --all --pretty --separate, nikoli úplné zálohování instance. Zdroje: aktuální oficiální návod n8n k zálohování a obnově a přehled příkazů CLI.

Hromadná obnova ze šablon GitHub nebo Google Drive: jde o alternativní způsob zálohování a obnovy samotných workflow v JSON, nikoli databáze instance, uživatelů, šifrovaných přihlašovacích údajů nebo šifrovacího klíče. Před spuštěním šablony využívající API ověřte její oprávnění pro n8n API a úložiště, vybranou verzi zálohy a cílovou instanci, zda aktualizuje položky se stejným ID, obnovuje smazaná workflow a jak pracuje s publikováním. Ne všechny šablony dokážou znovu vytvořit položku s ID, které v cíli chybí; před spoléháním na automatickou obnovu tento scénář otestujte izolovaně.

Časté dotazy

Zálohování a obnova n8n: časté dotazy

Stačí export pracovních postupů k zálohování n8n?

Ne. Exporty workflow jsou užitečnými logickými kopiemi, ale úplná obnova může vyžadovat také přihlašovací údaje, odpovídající šifrovací klíč, databázi, trvalé soubory a úložiště binárních dat.

Potřebuji šifrovací klíč n8n, pokud mám databázi?

Ano, pokud potřebujete po obnově nadále používat přihlašovací údaje zašifrované v databázi. Původní klíč uchovávejte bezpečně.

Mám zálohovat PostgreSQL nebo exportovat pracovní postupy a přihlašovací údaje?

Pro obnovu po havárii zálohujte databázi a šifrovací klíč. Logické exporty jsou užitečné pro migraci a výběrovou obnovu, ale nenahrazují všechny součásti instance.

Může být snímek VPS mojí jedinou zálohou?

Snapshot považujte za jednu z vrstev obnovy. Uchovávejte nezávislou zálohu mimo server, aby selhání poskytovatele, účtu, serveru nebo samotného snapshotu nezničilo všechny body obnovy najednou.

Jak poznám, že záloha funguje?

Zálohu obnovte do čistého testovacího prostředí, ověřte dešifrování přihlašovacích údajů a spusťte reprezentativní workflow. Úspěšné dokončení zálohovací úlohy samo o sobě neprokazuje možnost obnovy.

Obsahují zálohy workflow na GitHub nebo Google Drive také uložená tajná přihlašovací data?

Zálohy obsahující pouze JSON workflow nezahrnují hodnoty tajných údajů spravovaných úložištěm přihlašovacích údajů n8n ani šifrovací klíč instance. Exportovaný JSON však může prozradit názvy a ID přihlašovacích údajů i tajné hodnoty zadané přímo do parametrů uzlů, například autorizačních hlaviček. Před odesláním či sdílením soubor vždy prověřte a zabezpečte. Pro úplnou obnovu zálohujte databázi a původní klíč nebo použijte podporované šifrované exporty přihlašovacích údajů přes CLI s otestovanou obnovou. Samotná šablona pro zálohování workflow na GitHub či Google Drive není úplným řešením obnovy po havárii.

CÍLE OBNOVY

Definujte RPO a RTO ještě před incidentem

RPO znamená maximální přijatelnou ztrátu nedávných změn. Posuzujte ji podle nejnovějšího použitelného bodu obnovy uloženého nezávisle na serveru. Naplánovaná úloha každých šest hodin nezaručuje šestihodinové RPO, pokud export nebo přenos zálohy selhal. RTO znamená maximální přijatelnou dobu výpadku. Změřte ji při testu obnovy do čistého prostředí včetně získání tajných klíčů, obnovení externích souborů, kontroly přihlašovacích údajů a publikování obnovených workflow, nikoli pouze podle času potřebného ke spuštění kontejneru.

ŠIFROVACÍ KLÍČ PRO OBNOVU

Před opětovným sestavením serveru najděte původní šifrovací klíč

Pokud produkční prostředí používá proměnnou N8N_ENCRYPTION_KEY, zachovejte přesně její hodnotu. Pokud ji nepoužívá, uchovejte vygenerovaný klíč z původního trvalého souboru .n8n/config. Před importem šifrovaných přihlašovacích údajů ověřte, který klíč obnovená instance skutečně používá; nový vygenerovaný klíč nedokáže dešifrovat přihlašovací údaje ze staré databáze.
