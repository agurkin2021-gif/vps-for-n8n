ZÁLOHA A OBNOVA

Zálohování a obnova n8n

Chcete-li zálohovat a obnovit vlastní hostovaný n8n, chraňte svou databázi SQLite nebo konzistentní výpis PostgreSQL, trvalou složku .n8n a původní šifrovací klíč, konfiguraci nasazení a všechny závislosti externích binárních souborů nebo připojených souborů. Ponechte si zašifrovanou kopii mimo VPS a otestujte obnovu na samostatné instanci. Použijte CLI workflow a exporty pověření pro selektivní obnovu; Samotné exporty JSON nejsou úplnou zálohou serveru.

Vyberte VPS pro n8n

Partnerský odkaz: můžeme získat provizi z nákupů.

RYCHLÝ KONTROLNÍ SEZNAM

Co by měla záloha n8n chránit

Databáze

Zálohujte databázi PostgreSQL nebo databázový soubor SQLite používaný instancí. Databáze obsahuje základní stav n8n, jako jsou pracovní postupy, pověření a data provádění.

Šifrovací klíč

Uchovejte přesný n8n šifrovací klíč samostatně a bezpečně. Obnovené zašifrované přihlašovací údaje závisí na stejném klíči.

Trvale ukládané soubory

Zahrňte trvalý datový adresář n8n a všechny připojené soubory, úložiště binárních dat nebo aktiva pracovních postupů, na které vaše nasazení spoléhá.

Konfigurace nasazení

Uchovávejte soubory Compose/configuration a netajnou konfiguraci potřebnou k opětovnému sestavení zásobníku. Chraňte tajemství pomocí vhodného řízení přístupu.

DVĚ ÚROVNĚ ZÁLOHY

Logický export versus úplná obnova po havárii

Pracovní postup a export pověření

n8n CLI exporty jsou užitečné pro migraci, verzované kopie pracovního postupu a selektivní obnovení. Pověření lze exportovat v zašifrované podobě a později importovat pomocí odpovídajícího šifrovacího klíče. Chcete-li obnovit pouze jeden pracovní postup, použijte třítečkovou nabídku editoru pracovních postupů ke stažení jeho JSON a poté Import ze souboru do nového pracovního postupu recenze nebo izolované instance. Před nahrazením živého pracovního postupu zkontrolujte přihlašovací údaje, ID pracovního postupu a parametry uzlů: obnovení pracovního postupu JSON neobnoví celý server.

Export entity

V CLI lze exportovat databázové entity pro přesun dat mezi podporovanými typy databází. Tabulky historie provádění jsou volitelné, protože mohou být velmi velké.

Úplné obnovení instance

V případě mrtvého serveru chraňte skutečnou databázi, šifrovací klíč, trvalá data a závislosti nasazení. Nepředpokládejte, že pracovní postup JSON export rekonstruuje celou instanci.

Snímek poskytovatele

Snímek VPS je užitečný jako další vrstva obnovy, ale neměl by být jedinou kopií a neměl by nahrazovat nezávisle ověřenou zálohu aplikace/databáze.

DATABÁZE

Důsledně zálohujte databázi

PostgreSQL

Použijte konzistentní metodu zálohování PostgreSQL a výslednou zálohu uložte mimo VPS. Kopie databáze na stejném disku se selháním nepředstavuje obnovu po havárii.

SQLite

Pokud nasazení používá SQLite, chraňte databázový soubor před trvalým adresářem dat n8n. Vyhněte se kopírování databáze v nebezpečném stavu, když je aktivně upravována.

Historie provedení

Rozhodněte se, zda jsou součástí vašeho cíle obnovy údaje o historickém provádění. Zálohy mohou být podstatně větší, takže výběr by měly řídit požadavky na zachování a shodu.

Verze databáze

Zaznamenejte databázový stroj a verzi používanou zdrojovým nasazením, aby bylo možné připravit prostředí pro obnovu kompatibilní.

PostgreSQL na Docker Vytvořte VPS. Pokud je služba PostgreSQL pojmenována postgres a jeho databáze/uživatel jsou obojí n8n, následující příkaz vytvoří konzistentní výpis PostgreSQL vlastního formátu na hostiteli. Zkontrolujte svůj skutečný soubor Compose před jeho spuštěním a upravte přihlašovací údaje databáze a názvy služeb. pg_dump může vytvořit logicky konzistentní snímek, když je spuštěn PostgreSQL; to dělá ne zálohovat oddělené .n8n uživatelská složka nebo externí binární data.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Kontrola seznamu archivů zachytí zjevné problémy s formátem, ale neprokáže, že data lze obnovit. Uložte zašifrovanou kopii mimo server a nacvičte obnovu. Pro možnosti specifické pro databázi použijte oficiální dokumentaci PostgreSQL pg_dump.

SQLite na Docker. Pro výchozí nasazení SQLite, database.sqlite a vygenerovaná konfigurace šifrovacího klíče žije uvnitř persistentu .n8n složka (normálně připevněná na /home/node/.n8n). Nikdy nepovažujte jednoduchou živou kopii SQLite za konzistentní. Před zkopírováním složky zastavte n8n a další zapisovače databází, nebo použijte podporovaný online zálohovací mechanismus SQLite, pokud přerušení není možné:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Toto jsou ilustrativní příkazy pro zobrazenou službu a cestu, nikoli univerzální rozložení svazků. Zkopírovaná složka je zpočátku stále na stejném VPS; přenést a chránit mimo server. Pokud existují pracovníci fronty nebo jiní zapisovači, uveďte je také do klidu a postupujte podle jejich skutečného návrhu nasazení. Aktuální pokyny k úplnému zálohování n8n dokumentují požadavek na konzistenci SQLite.

Obnovení výchozí složky SQLite na čistý cíl: nejprve zastavte službu n8n a všechny zapisovače databáze. Jakmile existuje kompatibilní kontejner služby n8n a jeho cílový svazek, zkopírujte zálohu .n8n obsahu zpět do stejného trvalého adresáře. To přepíše cílové soubory, takže to nespouštějte na instanci s daty, která potřebujete zachovat:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker lze kopírovat do zastavených kontejnerů, ale vlastnictví místa určení se může lišit od originálu; zajistěte, aby obnovený konfigurační a databázový soubor byl čitelný a zapisovatelný procesem n8n před jeho spuštěním. Pokud vaše skutečná konfigurace Compose používá jinou cestu nebo připojení vazby, přizpůsobte odpovídajícím způsobem kopii. Docker Vytvořte odkaz na kopii. Samotné obnovení složky n8n nestačí pro nasazení, která používají samostatnou databázi PostgreSQL.

KRITICKÉ TAJEMSTVÍ

Šifrovací klíč je součástí obnovy

n8n zašifruje uložené přihlašovací údaje pomocí šifrovacího klíče instance. Export databáze nebo šifrovaného pověření bez odpovídajícího klíče může způsobit, že obnovené pracovní postupy nebudou moci používat svá uložená pověření.

Pokud nastavíte N8N_ENCRYPTION_KEY, obnovte přesně toto tajemství. Jinak je vygenerovaný klíč uložen v trvalém souboru .n8n/config: chraňte tuto konfiguraci při zálohování nebo přestavbě. Uložte klíče pro obnovení bezpečně mimo VPS. V režimu fronty musí všechny hlavní a pracovní procesy používat stejný klíč.

dělatUchovávejte chráněnou kopii přesného klíče používaného výrobou.
dělatPřed testováním přihlašovacích údajů ověřte, že prostředí pro obnovení používá tento klíč.
NeSpolehněte se na nově vygenerovaný klíč po opětovném sestavení serveru.
NeOdevzdejte klíč do veřejného úložiště nebo jej uložte vedle nechráněné zálohy.

SOUBORY A BINÁRNÍ DATA

Záloha databáze nemusí pokrýt všechny závislosti pracovního postupu

Trvalá data .n8n

Najděte a zachovejte skutečnou uživatelskou složku .n8n, nejen obrázek kontejneru. V typickém nasazení Docker je připojen na /home/node/.n8n; mimo Docker výchozí je ~/.n8n. Pokud je nakonfigurován N8N_USER_FOLDER, n8n vytvoří .n8n v uvedeném nadřazeném adresáři. Zahrňte jeho konfigurační klíč a všechna místní SQLite, binární data nebo data spuštění souborového systému, která vaše instalace používá.

Připojené soubory pracovního postupu

Pokud pracovní postupy čtou nebo zapisují adresáře připojené k hostiteli, zálohujte tyto adresáře samostatně. Obnovení n8n bez nich může způsobit přerušení jinak platných pracovních postupů.

Binární data

Identifikujte režim úložiště a obnovte všechny externí závislosti. Binární nebo spouštěcí data založená na souborovém systému mohou být uložena v .n8n nebo ve vlastním adresáři; S3/Azure Blob nebo jiné nakonfigurované externí úložiště potřebuje vlastní obnovitelnou kopii a nastavení přístupu. Samotný výpis databáze nemůže tyto soubory nahradit.

Komunitní uzly

Zaznamenávejte komunitní balíčky a verze a zálohujte všechny další uživatelské adresáře uzlů nakonfigurované pomocí N8N_CUSTOM_EXTENSIONS. Tyto adresáře mohou být umístěny mimo .n8n; samotná obnova databáze a uživatelské složky může stále ponechat pracovní postupy vlastních uzlů nepoužitelné.

STRATEGIE OFF-SERVER

Záloha na stejném VPS je pouze místní kopií

Místní kopieUžitečné pro rychlé vrácení zpět, ale náchylné ke ztrátě serveru, selhání disku a destruktivním chybám.
Kopie mimo serverUdržujte alespoň jednu zálohu v úložišti nezávisle na produkci VPS.
Verzované kopieZachovejte více bodů obnovy, aby poškození nebo špatná změna nepřepsala jedinou použitelnou zálohu.
Kontrola přístupuZálohy mohou obsahovat přihlašovací údaje, logiku pracovního postupu a citlivá obchodní data. Zašifrujte je a vhodně omezte.
SledováníUpozornit, když selžou naplánované zálohy nebo přestanou vytvářet nové body obnovy.

Udělejte rozvrh měřitelným. Zaznamenejte si časové razítko každé úspěšné zálohy, dokončení přenosu, velikost souboru, verzi zdrojové databáze, umístění obnovy šifrovacího klíče a poslední úspěšný test obnovy. Upozornění na chybějící, neúspěšné nebo neočekávaně prázdné soubory. Zašifrujte archivy záloh před jejich odesláním z VPS a omezte přístup k tajným informacím pro obnovu. Více datovaných bodů obnovy chrání před odhalením poškození až poté, co nejnovější kopie přepíše poslední zdravou.

Pokud například dokážete tolerovat maximálně šest hodin ztracených změn, úspěšný šestihodinový plán zálohování je výchozím bodem, nikoli zárukou: neúspěšné úlohy a zpožděná replikace mimo server mohou zvýšit skutečné ztráty. Nastavte uchovávání a obnovovací kadenci na své vlastní RPO/RTO a požadavky na data, spíše než převzít univerzální 7-denní nebo 30-denní politiku.

OBNOVIT OBJEDNÁVKU

Obnovte v řízeném pořadí

1 · Připravte sePoskytování kompatibilního serveru, databáze a prostředí kontejneru/běhu.
2 · Obnovit tajemstvíBezpečně nakonfigurujte původní n8n šifrovací klíč a požadovaná tajemství nasazení.
3 · Obnovení databázeObnovte PostgreSQL nebo SQLite a ověřte, zda se n8n může připojit k očekávaným datům.
4 · Obnovit souboryObnovte trvalé adresáře, binární data a připojené prostředky pracovního postupu.
5 · Spustit n8nSpusťte aplikaci s očekávaným názvem hostitele, databází a konfigurací prostředí.
6 · PotvrditPotvrďte načtení uživatelů, pracovních postupů a pověření a poté spusťte reprezentativní pracovní postupy a cesty webhooku.

PostgreSQL příklad obnovy po havárii: na a samostatný, čistý cíl obnovení který již má správnou databázovou roli a je prázdný n8n databáze, start pouze PostgreSQL. Před importem počkejte, až bude v pořádku: docker compose up -d sám se může vrátit, když se PostgreSQL stále inicializuje, takže následující pg_restore může selhat. Příklad používá --wait na moderní instalaci Compose a nezávisle kontroluje pg_isready. Nakonfigurujte odpovídající PostgreSQL zdravotní kontrolu pro spolehlivé čekání nebo výslovně potvrďte připravenost, než budete pokračovat. Nemiřte tímto příkazem na naplněnou produkční databázi ani nespouštějte n8n před databází a jejím párováním .n8n klíč/data jsou obnovena.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Cíl musí mít kompatibilní verzi PostgreSQL, oprávnění role, rozšíření a původní konfiguraci n8n. Obnovit .n8n na správný trvalý svazek nebo připojení pomocí vašeho zálohovacího mechanismu, přičemž zachováte vlastnictví a oprávnění. Obnovte externí binární soubory, vlastní rozšíření, konfiguraci vytváření a tajných klíčů, poté spusťte n8n v kompatibilní verzi a zkontrolujte jeho protokoly. Samotné obnovení databáze klíč neobnoví: nasazení podle PostgreSQL ponechá klíč uvnitř .n8n/config pokud jste to výslovně nenastavili N8N_ENCRYPTION_KEY. pg_restore reference · n8n sekvence obnovení plné instance.

TEST OBNOVENÍ

Záloha se neprokáže, dokud nebude obnovení úspěšné

Vyzkoušejte v čistém prostředí

Skutečné cvičení by mělo prokázat, že záloha může znovu sestavit instanci, aniž by se spoléhala na nedeklarované soubory ponechané na produkčním serveru.

Zkontrolujte přihlašovací údaje

Otevření pracovního postupu nestačí. Potvrďte, že obnovená zašifrovaná pověření skutečně dešifrují a úspěšně se ověří.

Spusťte reprezentativní pracovní postupy

Otestujte pracovní postupy, které závisí na webhoocích, externích rozhraních API, připojených souborech a komunitních uzlech, než abyste ověřovali pouze triviální automatizaci.

Změřte dobu zotavení

Zaznamenejte, jak dlouho obnovení trvá a jaké ruční kroky zbývají. Tím se předpokládaná záloha převede na proceduru provozní obnovy.

Ověřený postup obnovení: SQLite a PostgreSQL

Testovací prostředí: n8n 2.42.5 v izolovaných nádobách Docker na jednorázovém GitHub Akce runner, používající syntetický dvouuzlový pracovní postup. Tyto kontroly pokračovaly 8 říjen 2026, nikoli na zákaznickém nebo produkčním n8n serveru.

SQLite: PASSImportoval testovací pracovní postup, exportoval jej, zastavil všechny zapisovače, archivoval perzistenci zálohované SQLite .n8n složku a její vygenerovaný šifrovací klíč, obnovit do čistého svazku, spustit n8n, poté znovu exportovat a spustit obnovený pracovní postup.
PostgreSQL: PASSImportoval stejný testovací pracovní postup, vytvořil a zkontroloval vlastní formát pg_dump, obnovil jej pomocí pg_restore do nové prázdné databáze PostgreSQL, obnovil oddělenou .n8n složku, poté znovu exportovat a spustit obnovený pracovní postup.
Co zakládá PASSTestované cesty zálohování zachovaly tento pracovní postup, jeho dva uzly a jejich připojení a umožnily spuštění po obnovení. Jedná se o reprodukovatelné funkční kouřové testy, nikoli o benchmarky pracovní zátěže.
Co nebylo testovánoDešifrování a ověřování skutečných přihlašovacích údajů, produkčních webhooků, pracovníků v režimu fronty a Redis, binárního úložiště S3/Azure, vlastních uzlů, přístupu uživatele/projektu nebo obnovení živé produkční instance. Spusťte samostatné cvičení pro každou závislost, kterou skutečně používáte.

Jak reprodukovat: použijte jednorázovou instalaci n8n, vytvořte neškodný pracovní postup se dvěma uzly, proveďte příslušnou databázi a zálohu trvalé složky, obnovte na čistý svazek nebo databázi a poté ověřte uzly, připojení a skutečné provedení obnoveného pracovního postupu. V produkčním systému také zkontrolujte zašifrované přihlašovací údaje, webhooky a externí soubory, než prohlásíte obnovu po havárii za prokázanou.

Obnovení kontrolního seznamu pro přijetí cvičení: používat izolovanou doménu/prostředí; zkontrolujte, zda jsou přítomni uživatelé a pracovní postupy, jedno existující šifrované pověření se ověřuje bez opětovného zadání, produkční webhook vyvolá zamýšlený obnovený pracovní postup, připojené soubory a binární přílohy zůstávají čitelné a integrace s požadovanými uzly komunity se načítají. Potvrďte stáří zálohy, naměřené prostoje a dostupnost mimo server. Pokud některá základní kontrola selže, označte tento bod obnovy neověřeno místo nahlášení zálohy jako dokončené.

CLI ZÁLOŽNÍ LIMITY

Přesně víte, jaký pracovní postup a exporty pověření neobnoví

Exporty CLI nejsou zálohou plné instance

Exporty zálohování pracovních postupů a pověření nezahrnují uživatele a role, historii a protokoly provádění, proměnné nebo nastavení instancí, jako je šifrovací klíč.

Obnova čerstvé instance potřebuje vlastníka

V čisté instanci dokončete před importem přihlašovacích údajů nastavení vlastníka. Obnovení více uživatelů nebo projektů může také vyžadovat správné přiřazení uživatele nebo projektu.

Importovaná ID mohou přepsat existující položky

Exporty pracovních postupů a pověření zachovají svá původní ID. Import do instance, která již obsahuje stejná ID, může nahradit tyto existující položky.

Záměrně publikujte importované pracovní postupy

CLI importy obvykle ponechávají pracovní postupy neaktivní. Na n8n 2.x, zkontrolujte publikovaný stav každého importovaného pracovního postupu a publikujte pouze pracovní postupy, které chcete spustit; server s vlastním hostitelem CLI také podporuje n8n publikovat:pracovní postup --id=ID VAŠEHO_PRACOVNÍHO_TOKU. Když n8n běží, Server CLI změny stavu publikování/zrušení publikování se projeví až po restartování n8n. Před ověřením naplánovaných spouštěčů a produkčních webhooků nebo přepnutím provozu restartujte.

Příklad hromadného exportu pro Docker Vytvořte: pokud je vaše služba n8n pojmenována n8n, můžete spustit oficiální zálohy CLI níže. Výstupní cesta je záměrně uvnitř svého namontovaného persistentu .n8n adresář, protože libovolné adresáře uvnitř kontejneru mohou zmizet, když je znovu vytvořen. Potvrďte, že do adresáře může zapisovat uživatel kontejneru n8n. Udržujte pracovní postup a pověření JSON v samostatné adresáře—n8n dokumentuje problém s importem, když oba druhy sdílejí adresář.

n8n 2.x koncept versus publikovaná záloha: normální --backup export pracovního postupu zachycuje aktuální koncepty; ty se mohou lišit od verzí publikovaných ve výrobě. Chcete-li zachovat aktuální publikovanou verzi konkrétního pracovního postupu, exportujte jej samostatně pomocí docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.jsonpoté, co se ujistíte, že výstupní složka existuje a je možné do ní zapisovat. Pomocí CLI lze také exportovat historickou verzi --version=VERSION_ID. Udržujte tyto zachycení mimo server spolu s plnou zálohou; nepředpokládejte, že návrh JSON zaznamenává živě publikovaný stav.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Zkopírované ~/n8n-recovery/cli adresář je stále v VPS, dokud jej nepřesunete do zabezpečeného nezávislého umístění zálohy. Export pověření je ve výchozím nastavení šifrován a při importu vyžaduje odpovídající šifrovací klíč. Vyhněte se používání --decrypted kromě přísně kontrolované migrace: píše tajemství v otevřeném textu. Nikdy neposílejte exporty obsahující citlivou logiku pracovního postupu nebo pověření do veřejného GitHub úložiště. Některé šablony GitHub pro zálohování pověření od třetích stran záměrně exportují dešifrovaná tajemství; soukromé úložiště je omezení přístupu, nikoli šifrování. Zkontrolujte skutečná nastavení exportu a oprávnění úložiště každé šablony, zašifrujte tajemství před přenosem mimo server a otočte všechna pověření odhalená prostřednictvím nechtěného nahrání prostého textu.

Příklad hromadného importu: na čistém cíli dokončete nastavení vlastníka, poskytněte původní šifrovací klíč a ujistěte se, že uložené záložní soubory jsou k dispozici na tomto obnovení VPS. Následující vytvoří cílovou složku a zkopíruje ji workflows/ a credentials/ podsložky z hostitele do kontejneru n8n; přizpůsobte cesty, pokud se vaše rozložení hlasitosti Docker liší:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Zkontrolujte vlastnictví souboru a přístup pro uživatele kontejneru n8n. Neimportujte přes naplněnou produkční instanci bez ověřeného vrácení zpět: ID pracovního postupu a pověření mohou přepsat existující položky. Pak spusťte:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Importovaná ID mohou nahradit stávající pracovní postupy nebo přihlašovací údaje; použijte izolovanou testovací instanci pro suché běhy a poté zkontrolujte přihlašovací údaje a stavy aktivace/publikování. V n8n 2.x obnovení návrhu JSON samo o sobě neprokazuje, že byl pracovní postup zveřejněn, a může spouštět naplánované spouštěče. Bezpečnost dovozu: na nemultimain instanci n8n mohou dříve aktivní spouštěče cron pokračovat po importu CLI, dokud se instance nerestartuje. Zastavte nebo izolujte produkční spouštěče a restartujte n8n před povolením obnovených úloh; ověřte, že nedochází k duplicitnímu provedení. CLI exporty ano ne obsahovat původní uživatele, protokoly provádění, proměnné instance nebo šifrovací klíč. --backup sady --all --pretty --separate, nikoli „plná instance“. Zdroje: aktuální oficiální průvodce zálohováním/obnovením n8n a odkaz na příkaz n8n CLI.

Hromadné obnovení ze šablon GitHub nebo Disku Google: toto je alternativa pouze pro pracovní postup JSON, nikoli pro databázi instance, uživatele, zašifrované hodnoty pověření nebo šifrovací klíč. Před spuštěním šablony založené na API ověřte její n8n API a oprávnění k úložišti, vybranou verzi zálohy a cílovou instanci, zda aktualizuje odpovídající ID a znovu vytváří odstraněné pracovní postupy a co dělá s publikováním pracovního postupu. Ne všechny šablony znovu vytvoří ID chybějící v cíli; otestujte tento scénář izolovaně, než se spolehnete na automatické obnovení.

Časté dotazy

n8n zálohování a obnovení: běžné otázky

Stačí export pracovních postupů k zálohování n8n?

Ne. Exporty pracovního postupu jsou užitečné logické kopie, ale úplná obnova může také vyžadovat přihlašovací údaje, odpovídající šifrovací klíč, stav databáze, trvalé soubory a úložiště binárních dat.

Potřebuji šifrovací klíč n8n, pokud mám databázi?

Ano, pokud potřebujete, aby šifrované přihlašovací údaje uložené v této databázi zůstaly použitelné. Originální klíč bezpečně uschovejte.

Mám zálohovat PostgreSQL nebo exportovat pracovní postupy a přihlašovací údaje?

Pro obnovu po havárii chraňte databázi a šifrovací klíč. Logické exporty jsou cenné spíše jako další vrstva migrace a selektivní obnovy než jako náhrada za každou část instance.

Může být snímek VPS mojí jedinou zálohou?

Lépe se s ní zachází jako s jednou obnovovací vrstvou. Udržujte nezávislou zálohu mimo server, aby selhání poskytovatele, účtu, serveru nebo snímku neodstranilo všechny body obnovy najednou.

Jak poznám, že záloha funguje?

Obnovte jej do čistého testovacího prostředí, ověřte dešifrování přihlašovacích údajů a spusťte reprezentativní pracovní postupy. Úspěšná úloha zálohování sama o sobě neprokazuje obnovitelnost.

Zahrnují zálohy pracovních postupů GitHub nebo Disku Google uložená tajná pověření?

Zálohy JSON pouze pro pracovní postup nezahrnují tajné hodnoty spravované úložištěm pověření n8n nebo šifrovacím klíčem instance. Exportovaný JSON však může odhalit jména pověření a ID a tajemství zadaná přímo do parametrů uzlu, jako jsou autentizační hlavičky. Před nahráním nebo sdílením exportovaný JSON zkontrolujte a chraňte jej. Pro úplné obnovení zálohujte databázi a původní klíč nebo použijte podporované exporty šifrovaných pověření CLI s testovanou obnovou. Šablona GitHub nebo Disk Google pouze pro pracovní postup nepředstavuje úplnou obnovu po havárii.

CÍLE OBNOVY

Definujte RPO a RTO před incidentem

RPO je maximální tolerovatelná ztráta posledních změn. Změřte to z nejnovějšího použitelného, ​​nezávisle uloženého bodu obnovy; plánovaná šestihodinová úloha nezakládá šestihodinovou RPO, pokud exporty nebo přenosy selhaly. RTO je maximální tolerovatelný výpadek. Změřte to v vrtání čisté obnovy, včetně získávání tajných informací, obnovování externích souborů, opětovné kontroly přihlašovacích údajů a publikování obnovených pracovních postupů – nejen spuštění kontejneru.

OBNOVA KLÍČ

Před obnovením najděte původní šifrovací klíč

Pokud je nastavena výroba N8N_ENCRYPTION_KEY, zachovejte to přesné tajemství prostředí. Pokud ne, zachovejte vygenerovaný klíč v původním trvalém souboru .n8n/config. Před importem zašifrovaných přihlašovacích údajů zkontrolujte, který zdroj obnovená instance skutečně používá; nově vygenerovaný klíč nemůže dešifrovat pověření ze staré databáze.
