VIETNAMESE SERP · INTENT-SPECIFIC

n8n Queue Mode

SERP Việt Nam đã có hướng dẫn Docker/Redis khá tốt. Khoảng trống quan trọng là khi nào nên scale, bottleneck nào worker không giải quyết và ranh giới Queue Mode với HA.

SCALING ARCHITECTURE

Queue Mode = PostgreSQL + Redis + workers + shared config

Main processĐiều phối trigger/timer và chuyển execution vào queue.
RedisMessage broker cho pending executions.
PostgreSQLShared database cho distributed deployment; SQLite không phù hợp cho Queue Mode phân tán.
WorkersThực thi jobs; scale số worker/concurrency theo workload.
Encryption keyMain, workers và webhook processors dùng cùng N8N_ENCRYPTION_KEY.
Version parityCác process phải chạy cùng n8n version để giảm lỗi không tương thích.

Thêm worker không chữa mọi bottleneck

DB bottleneck

PostgreSQL chậm hoặc disk I/O kém có thể tệ hơn khi tăng worker.

API bottleneck

Rate limit/latency của API bên ngoài không biến mất khi thêm worker.

Webhook processors

Đây là lớp scale incoming webhook riêng, không phải worker execution.

Queue depth

Theo dõi pending jobs, worker utilization và execution latency để biết có thật sự thiếu capacity.

Binary data

File-heavy queue cần storage model phù hợp; filesystem cục bộ tạo giới hạn khi scale nhiều process/server.

HA boundary

Queue workers và full multi-main/high-availability không phải một khái niệm; kiểm tra edition/feature hiện hành.

FAQ n8n Queue Mode

Queue Mode có cần Redis không?

Có trong kiến trúc Queue Mode hiện tại của n8n.

Có cần PostgreSQL không?

Distributed Queue Mode dùng shared database; PostgreSQL là lựa chọn chuẩn.

Workers có dùng cùng encryption key không?

Có, để credentials có thể được decrypt nhất quán.

Khi nào nên dùng Queue Mode?

Khi single-instance execution capacity là bottleneck thật, không chỉ vì muốn kiến trúc phức tạp hơn.
