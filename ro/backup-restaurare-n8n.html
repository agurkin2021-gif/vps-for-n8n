BACKUP & RECUPERARE

Backup și restaurare n8n

Pentru a face copii de rezervă și a restabili n8n self-hosted, protejați baza de date SQLite sau un dump constant PostgreSQL, folderul persistent .n8n și cheia de criptare originală, configurația de implementare și fiecare dependență externă de fișiere binar sau montate. Păstrați o copie criptată în afara VPS și testați recuperarea pe o instanță separată. Utilizați fluxul de lucru CLI și exporturile de acreditări pentru recuperarea selectivă; Doar exporturile JSON nu reprezintă o copie de rezervă completă a serverului.

LISTA DE VERIFICARE RAPIDĂ

Ce trebuie să protejeze un backup n8n

Baza de date

Faceți o copie de rezervă a bazei de date PostgreSQL sau a fișierului bazei de date SQLite utilizat de instanță. Baza de date conține starea de bază n8n, cum ar fi fluxurile de lucru, acreditările și datele de execuție.

Cheie de criptare

Păstrați cheia de criptare exactă n8n separat și în siguranță. Acreditările criptate restaurate depind de aceeași cheie.

Fișiere persistente

Includeți directorul de date persistent n8n și orice fișiere montate, stocare de date binare sau active de flux de lucru pe care se bazează implementarea dvs.

Configurație de implementare

Păstrați fișierele Compuse/configuration și configurația non-secretă necesară pentru a reconstrui stack-ul. Protejați secretele cu controale de acces adecvate.

DOUĂ NIVELURI DE BACKUP

Export logic vs recuperare completă în caz de dezastru

Export de workflow-uri și acreditări

Exporturile n8n CLI sunt utile pentru migrare, copii ale fluxului de lucru cu versiuni și restaurare selectivă. Acreditările pot fi exportate în formă criptată și importate ulterior cu cheia de criptare corespunzătoare. Pentru a recupera un singur flux de lucru, utilizați meniul cu trei puncte al editorului de flux de lucru pentru a descărca JSON al acestuia, apoi Importați din fișier într-un nou flux de lucru de revizuire sau o instanță izolată. Verificați acreditările, ID-urile fluxului de lucru și parametrii nodului înainte de a înlocui un flux de lucru activ: restaurarea fluxului de lucru JSON nu restaurează întregul server.

Export de entități

CLI poate exporta entități de bază de date pentru mutarea datelor între tipurile de baze de date acceptate. Tabelele cu istoricul execuției sunt opționale deoarece pot fi foarte mari.

Recuperare completă a instanței

Pentru un scenariu de server mort, protejați baza de date reală, cheia de criptare, datele persistente și dependențele de implementare. Nu presupuneți că un flux de lucru JSON export reconstruiește întreaga instanță.

Snapshot al furnizorului

Un instantaneu VPS este util ca un strat suplimentar de recuperare, dar nu ar trebui să fie singura copie și nu ar trebui să înlocuiască o copie de rezervă a aplicației/bazei de date verificată independent.

BAZĂ DE DATE

Faceți backup consistent bazei de date

PostgreSQL

Utilizați o metodă consecventă de rezervă PostgreSQL și stocați backupul rezultat departe de VPS. O copie a bazei de date pe același disc eșuat nu este recuperare în caz de dezastru.

SQLite

Dacă implementarea folosește SQLite, protejați fișierul bazei de date de directorul de date persistent n8n. Evitați copierea unei baze de date într-o stare nesigură în timp ce aceasta este în curs de modificare.

Istoricul execuției

Decideți dacă datele de execuție istorice fac parte din obiectivul dvs. de recuperare. Poate face backup-urile substanțial mai mari, așa că cerințele de păstrare și conformitate ar trebui să conducă la alegere.

Versiunea bazei de date

Înregistrați motorul bazei de date și versiunea utilizată de implementarea sursă, astfel încât un mediu de recuperare să poată fi pregătit compatibil.

PostgreSQL pe un Docker Compose VPS. Dacă serviciul PostgreSQL este numit postgres și baza de date/utilizatorul acesteia sunt ambele n8n, următoarea comandă creează un dump coerent în format personalizat PostgreSQL pe gazdă. Verificați fișierul Compose real înainte de a-l rula și ajustați acreditările bazei de date și numele serviciilor. pg_dump poate produce un instantaneu consistent logic în timp ce PostgreSQL rulează; o face nu susține separat .n8n folderul utilizatorului sau datele binare externe.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Verificarea listei de arhive detectează probleme evidente de format, dar nu dovedește că datele pot fi restaurate. Stocați o copie criptată în afara serverului și repetați o restaurare. Utilizați documentația oficială PostgreSQL pg_dump pentru opțiunile specifice bazei de date.

SQLite pe Docker. Pentru implementarea implicită SQLite, database.sqlite iar configurația generată a cheii de criptare trăiește în interiorul persistent .n8n folder (montat în mod normal la /home/node/.n8n). Nu tratați niciodată o simplă copie live a SQLite ca fiind consecventă. Opriți n8n și alți scriitori de baze de date înainte de a copia folderul sau utilizați mecanismul de backup online acceptat de SQLite atunci când întreruperea este imposibilă:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Acestea sunt comenzi ilustrative pentru serviciul și calea afișate, nu un aspect de volum universal. Dosarul copiat este inițial încă pe același VPS; transferați și protejați-l în afara serverului. Atunci când există workeri la coadă sau alți scriitori, opriți-i și pe aceștia și urmați-le proiectul real de implementare. Îndrumarea actuală pentru backup complet al n8n documentează cerința de consistență SQLite.

Restaurarea folderului implicit SQLite la o țintă curată: mai întâi opriți serviciul n8n și toți scriitorii de baze de date. Odată ce un container de servicii n8n compatibil și volumul său de destinație există, copiați copia de rezervă .n8n continuturi înapoi în același director persistent. Aceasta suprascrie fișierele țintă, așa că nu le rulați pe o instanță cu date pe care trebuie să le păstrați:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker poate copia în containere oprite, dar dreptul de proprietate asupra destinației poate diferi de originalul; asigurați-vă că configurația restaurată și fișierul bazei de date pot fi citite și scrise de procesul n8n înainte de a-l porni. Dacă configurația dvs. reală Compose utilizează o cale diferită sau o montare de legătură diferită, adaptați copia în consecință. Docker Composeți referința la copiere. Restaurarea unui folder n8n singură nu este suficientă pentru implementările care utilizează o bază de date separată PostgreSQL.

SECRET CRITIC

Cheia de criptare face parte din recuperare

n8n criptează acreditările stocate cu o cheie de criptare a instanței. O bază de date sau exportul de acreditări criptate fără cheia potrivită poate lăsa fluxurile de lucru restaurate să nu poată utiliza acreditările salvate.

Dacă setați N8N_ENCRYPTION_KEY, restaurați exact acel secret. În caz contrar, cheia generată este stocată în fișierul persistent .n8n/config: protejați acea configurație atunci când faceți backup sau reconstruiți. Păstrați cheile de recuperare în siguranță în afara punctului VPS. În Queue Mode, toate procesele principale și de lucru trebuie să utilizeze aceeași cheie.

FăPăstrați o copie protejată a cheii exacte utilizate de producție.
FăVerificați că mediul de recuperare utilizează acea cheie înainte de a testa acreditările.
NuBazați-vă pe o cheie nou generată după reconstruirea serverului.
NuTrimiteți cheia într-un depozit public sau stocați-o lângă o copie de rezervă neprotejată.

FIȘIERE ȘI DATE BINARE

Backupul bazei de date poate să nu acopere toate dependențele workflow-urilor

Date persistente .n8n

Localizați și păstrați folderul utilizatorului actual .n8n, nu numai imaginea containerului. Într-o implementare tipică Docker este montat la /home/node/.n8n; în afara Docker implicit este ~/.n8n. Dacă N8N_USER_FOLDER este configurat, n8n creează .n8n în acel director părinte specificat. Includeți cheia de configurare a acesteia și orice date locale SQLite, binare sau de execuție a sistemului de fișiere pe care le folosește instalația dvs.

Fișiere de flux de lucru montate

Dacă fluxurile de lucru citesc sau scriu directoare montate pe gazdă, faceți o copie de rezervă a acestor directoare separat. Restaurarea n8n fără ele poate lăsa întrerupte fluxurile de lucru altfel valabile.

Date binare

Identificați modul de stocare și restaurați fiecare dependență externă. Datele binare sau de execuție bazate pe sistemul de fișiere pot locui în .n8n sau într-un director personalizat; S3/Azure Blob sau alt spațiu de stocare extern configurat are nevoie de propriile setări de copiere și acces recuperabile. Numai o descărcare a bazei de date nu poate înlocui acele fișiere.

Noduri comunitare

Înregistrați pachetele și versiunile comunității și faceți copii de siguranță ale tuturor directoarelor de noduri personalizate suplimentare configurate prin N8N_CUSTOM_EXTENSIONS. Acele directoare pot sta în afara .n8n; numai o bază de date și o restaurare a folderului utilizatorului poate lăsa în continuare inutilizabile fluxurile de lucru cu noduri personalizate.

STRATEGIE OFF-SERVER

Un backup pe același VPS este doar o copie locală

Copie localăUtil pentru derularea rapidă, dar vulnerabil la pierderea serverului, defecțiunea discului și greșelile distructive.
Copie în afara serveruluiPăstrați cel puțin o copie de rezervă în stocare independentă de producție VPS.
Copii versiuniPăstrați mai multe puncte de recuperare, astfel încât corupția sau o modificare proastă să nu suprascrie singura copie de rezervă utilizabilă.
Control accesBackup-urile pot conține acreditări, logica fluxului de lucru și date sensibile de afaceri. Criptați și restricționați-le în mod corespunzător.
MonitorizareAlertă când backup-urile programate eșuează sau nu mai produc noi puncte de recuperare.

Faceți programul măsurabil. Înregistrați marca de timp pentru fiecare copie de rezervă reușită, finalizarea transferului, dimensiunea fișierului, versiunea bazei de date sursă, locația de recuperare a cheii de criptare și cel mai recent test de restaurare cu succes. Alertă privind fișierele lipsă, eșuate sau goale în mod neașteptat. Criptați arhivele de rezervă înainte de a le trimite din VPS și restricționați accesul la secretele de recuperare. Mai multe puncte de recuperare datate protejează împotriva descoperirii corupției numai după ce cea mai nouă copie a suprascris-o pe ultima sănătoasă.

De exemplu, dacă puteți tolera cel mult șase ore de modificări pierdute, o programare de backup de șase ore reușită este un punct de plecare, nu o garanție: joburile eșuate și replicarea întârziată în afara serverului pot crește pierderea reală. Setați reținerea și restabiliți cadența la propriile dvs. cerințe RPO/RTO și date, în loc să presupuneți o politică universală de 7-zi sau 30-zi.

RESTAURARE COMANDA

Recuperați într-o secvență controlată

1 · PregătițiFurnizați un server compatibil, bază de date și mediu container/runtime.
2 · Restaurarea secretelorConfigurați în siguranță cheia de criptare originală n8n și secretele de implementare necesare.
3 · Restaurare baza de dateRecuperați PostgreSQL sau SQLite și verificați că n8n se poate conecta la datele așteptate.
4 · Restaurare fișiereRecuperați directoare persistente, date binare și active montate ale fluxului de lucru.
5 · Începe n8nAfișați aplicația cu numele de gazdă așteptate, baza de date și configurația mediului.
6 · ValidareConfirmați încărcarea utilizatorilor, a fluxurilor de lucru și a acreditărilor, apoi executați fluxuri de lucru reprezentative și căi de webhook.

PostgreSQL exemplu de recuperare în caz de dezastru: pe a ținta de restaurare separată și curată care are deja rolul corect de bază de date și un gol n8n baza de date, începe numai PostgreSQL. Așteptați până când este sănătos înainte de a importa: docker compose up -d singur poate reveni în timp ce PostgreSQL încă se inițializează, deci un următor pg_restore poate eșua. Exemplul folosește --wait pe o instalație Compose modernă și verificări independente pg_isready. Configurați o verificare de sănătate potrivită PostgreSQL pentru o așteptare sigură sau confirmați în mod explicit pregătirea înainte de a continua. Nu îndreptați această comandă către o bază de date de producție populată și nu începeți n8n înaintea bazei de date și a potrivirii acesteia .n8n cheia/datele sunt restaurate.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Destinația trebuie să aibă o versiune compatibilă PostgreSQL, privilegii de rol, extensii și configurație originală n8n. Restaurați .n8n la volumul său persistent corect sau montarea legăturii folosind mecanismul dumneavoastră de rezervă, păstrând dreptul de proprietate și permisiunile. Restaurați fișierele binare externe, extensiile personalizate, configurația Compuse și secrete, apoi începeți n8n la o versiune compatibilă și verificați jurnalele acesteia. Numai restaurarea bazei de date nu recuperează cheia: o implementare PostgreSQL păstrează cheia .n8n/config cu excepția cazului în care ați configurat în mod explicit N8N_ENCRYPTION_KEY. referință pg_restore · n8n secvență de restaurare a instanței complete.

TEST DE RESTAURARE

Un backup nu este verificat până când restaurarea nu reușește

Testați într-un mediu curat

Un drill real ar trebui să demonstreze că backup-ul poate reconstrui o instanță fără a se baza pe fișierele nedeclarate rămase pe serverul de producție.

Verificați acreditările

Deschiderea unui flux de lucru nu este suficientă. Confirmați că acreditările criptate restaurate sunt decriptate și autentificate cu succes.

Rulați fluxuri de lucru reprezentative

Testați fluxurile de lucru care depind de webhook-uri, API-uri externe, fișiere montate și noduri ale comunității, mai degrabă decât de a valida doar o automatizare banală.

Măsurați timpul de recuperare

Înregistrați cât durează restaurarea și ce pași manuali rămân. Aceasta transformă o copie de rezervă presupusă într-o procedură de recuperare operațională.

Exercițiu de restaurare verificat: SQLite și PostgreSQL

Mediu de testare: n8n 2.42.5 în containere izolate Docker pe un rulator de acțiuni GitHub de unică folosință, folosind un flux de lucru sintetic cu două noduri. Aceste verificări au continuat 8 octombrie 2026, nu pe serverul unui client sau de producție n8n.

SQLite: PASSA importat un flux de lucru de testare, l-a exportat, a oprit toți scriitorii, a arhivat persistentul susținut de SQLite .n8n folderul și cheia sa de criptare generată, restaurate într-un volum curat, au pornit n8n, apoi au reexportat și au executat fluxul de lucru recuperat.
PostgreSQL: PASSImportat același flux de lucru de testare, creat și inspectat un format personalizat pg_dump, l-a restaurat folosind pg_restore într-o nouă bază de date goală PostgreSQL, a restaurat separat .n8n folder, apoi a reexportat și a executat fluxul de lucru recuperat.
Ce stabilește PASSCăile de backup testate au păstrat acest flux de lucru, cele două noduri ale sale și conexiunile lor și au permis execuția după recuperare. Acestea sunt teste de fum funcționale reproductibile, nu benchmark-uri ale sarcinii de lucru.
Ce nu a fost testatDecriptarea și autentificarea acreditărilor reale, webhook-uri de producție, workeri în Queue Mode și Redis, stocare binară S3/Azure, noduri personalizate, acces utilizator/proiect sau recuperarea unei instanțe de producție live. Rulați un exercițiu separat pentru fiecare dependență pe care o utilizați de fapt.

Cum se reproduce: utilizați o instalare de unică folosință n8n, creați un flux de lucru inofensiv cu două noduri, efectuați baza de date aplicabilă plus backup-ul folderului persistent, restaurați într-un volum curat sau bază de date, apoi verificați nodurile fluxului de lucru restaurat, conexiunile și execuția reală. Pe sistemul de producție, verificați, de asemenea, acreditările criptate, webhook-urile și fișierele externe înainte de a declara recuperarea în caz de dezastru dovedită.

Restabiliți lista de verificare pentru acceptarea forajului: utilizați un domeniu/mediu izolat; verificați dacă utilizatorii și fluxurile de lucru sunt prezente, o acreditare criptată existentă se autentifică fără reintrare, un webhook de producție invocă fluxul de lucru restaurat intenționat, fișierele montate și atașamentele binare rămân lizibile și integrările cu nodurile comunitare necesare se încarcă. Confirmați vârsta de rezervă, timpul de nefuncționare măsurat și accesibilitatea în afara serverului. Dacă vreo verificare esențială eșuează, marcați acel punct de recuperare neverificat mai degrabă decât raportarea copiei de rezervă ca fiind completă.

CLI LIMITE DE BACKUP

Aflați exact ce nu restaurează exporturile de workflow-uri și acreditări

Exporturile CLI nu reprezintă un backup complet al instanței

Exporturile de backup pentru fluxul de lucru și acreditările nu includ utilizatori și roluri, istoricul de execuție și jurnalele, variabilele sau setările instanței, cum ar fi cheia de criptare.

Restaurarea pe o instanță nouă necesită configurarea proprietarului

Într-o instanță curată, finalizați configurarea proprietarului înainte de a importa acreditările. Restaurările pentru mai mulți utilizatori sau proiecte pot necesita, de asemenea, utilizatorul sau atribuirea corectă a proiectului.

ID-urile importate pot suprascrie elementele existente

Fluxul de lucru și exporturile de acreditări își păstrează ID-urile originale. Importarea într-o instanță care conține deja aceleași ID-uri poate înlocui acele elemente existente.

Publicați fluxurile de lucru importate în mod deliberat

Importurile CLI lasă în mod normal fluxurile de lucru inactive. Pe n8n 2.x, verificați starea publicată a fiecărui flux de lucru importat și publicați numai fluxurile de lucru pe care intenționați să le rulați; serverul self-hosted CLI acceptă și n8n publish:workflow --id=YOUR_WORKFLOW_ID. Când n8n rulează, modificările stării de publicare/anul publicării Server CLI au efect numai după repornirea n8n. Reporniți înainte de a verifica declanșatoarele programate și webhook-urile de producție sau de comutare a traficului.

Exemplu de export în bloc pentru Docker Compose: dacă serviciul dvs. n8n este numit n8n, puteți rula backup-urile oficiale CLI de mai jos. Calea de ieșire este în mod deliberat în interiorul său persistent montat .n8n director, deoarece directoarele arbitrare din interiorul unui container pot dispărea atunci când este recreat. Confirmați că directorul poate fi scris de către utilizatorul containerului n8n. Păstrați fluxul de lucru și acreditările JSON în directoare separate—n8n documentează o problemă de import atunci când ambele tipuri partajează un director.

n8n 2.x schiță versus backup publicat: un normal --backup exportul fluxului de lucru captează schițele curente; acestea pot diferi de versiunile publicate în producție. Pentru a păstra versiunea publicată reală a unui anumit flux de lucru, exportați-o separat folosind docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, după ce ne-am asigurat că folderul de ieșire există și poate fi scris. CLI poate exporta, de asemenea, o versiune istorică folosind --version=VERSION_ID. Păstrați aceste capturi în afara serverului alături de backup complet; nu presupune că proiectul JSON înregistrează starea publicată în direct.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Cea copiată ~/n8n-recovery/cli directorul este încă în VPS până când îl mutați într-o locație de rezervă securizată, independentă. Exportul de acreditări este criptat în mod implicit și necesită cheia de criptare corespunzătoare la import. Evitați utilizarea --decrypted cu excepția unei migrari strict controlate: scrie secrete în text clar. Nu trimiteți niciodată exporturi care conțin logica de flux de lucru sensibilă sau acreditări într-un depozit public GitHub. Unele șabloane terțe de rezervă GitHub exportă în mod deliberat secrete decriptate; un depozit privat este o restricție de acces, nu o criptare. Inspectați setările reale de export și permisiunile de stocare ale fiecărui șablon, criptați secretele înainte de transferul în afara serverului și rotiți orice acreditări expuse printr-o încărcare neintenționată de text simplu.

Exemplu de import în bloc: pe o țintă curată, finalizați configurarea proprietarului, furnizați cheia de criptare originală și asigurați-vă că fișierele de rezervă salvate sunt disponibile pentru recuperarea respectivă VPS. Următoarele creează folderul de destinație și copiază workflows/ şi credentials/ subfolderele de la gazdă în containerul n8n; adaptați căile dacă aspectul dvs. de volum Docker diferă:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Verificați proprietatea și accesul fișierului pentru utilizatorul containerului n8n. Nu importați peste o instanță de producție populată fără o derulare verificată: ID-urile de flux de lucru și de acreditări pot suprascrie intrările existente. Apoi rulați:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/

ID-urile importate pot înlocui fluxurile de lucru sau acreditările existente; utilizați o instanță de testare izolată pentru rulări uscate și verificați ulterior acreditările și stările de activare/publicare. În n8n 2.x, restaurarea schiței JSON nu dovedește în sine că un flux de lucru a fost publicat și poate rula declanșatoare programate. Siguranța importului: pe o instanță n8n non-multi-principală, declanșatoarele cron active anterior pot continua să ruleze după importul CLI până când instanța repornește. Opriți sau izolați declanșatoarele de producție și reporniți n8n înainte de a activa joburile restaurate; verificați că nu există o execuție duplicată. CLI exporturile fac nu conțin utilizatori originali, jurnalele de execuție, variabile de instanță sau cheia de criptare. --backup seturi --all --pretty --separate, nu „instanță completă”. Surse: ghid oficial curent n8n pentru backup/restaurare și referință pentru comandă n8n CLI.

Restaurare în bloc din șabloanele GitHub sau Google Drive: aceasta este o alternativă numai pentru fluxul de lucru JSON, nu pentru baza de date de instanță, utilizatori, valori de acreditări criptate sau cheie de criptare. Înainte de a rula un șablon bazat pe API, verificați permisiunile n8n API și de stocare ale acestuia, versiunea de rezervă selectată și instanța țintă, dacă actualizează ID-urile potrivite și recreează fluxurile de lucru șterse și ce face cu publicarea fluxului de lucru. Nu toate șabloanele recreează un ID care lipsește din țintă; testați acel scenariu izolat înainte de a vă baza pe restaurarea automată.

Întrebări frecvente

Backup și restaurare n8n: întrebări frecvente

Exportarea fluxurilor de lucru este suficientă pentru a face backup pentru n8n?

Nu. Exporturile fluxului de lucru sunt copii logice utile, dar recuperarea completă poate necesita, de asemenea, acreditări, cheia de criptare potrivită, starea bazei de date, fișiere persistente și stocare de date binare.

Am nevoie de cheia de criptare n8n dacă am baza de date?

Da, dacă aveți nevoie de acreditările criptate stocate în acea bază de date pentru a rămâne utilizabile. Păstrați în siguranță cheia originală.

Ar trebui să fac backup pentru PostgreSQL sau să export fluxurile de lucru și acreditările?

Pentru recuperarea în caz de dezastru, protejați baza de date și cheia de criptare. Exporturile logice sunt valoroase ca un nivel suplimentar de migrare și recuperare selectivă, mai degrabă decât un substitut pentru fiecare parte a instanței.

Poate un instantaneu VPS să fie singura mea copie de rezervă?

Este mai bine tratat ca un singur strat de recuperare. Păstrați o copie de rezervă independentă în afara serverului, astfel încât o eroare de furnizor, cont, server sau instantaneu să nu elimine fiecare punct de recuperare simultan.

Cum știu că funcționează backup-ul meu?

Restaurați-l într-un mediu de testare curat, verificați acreditările, decriptați și rulați fluxuri de lucru reprezentative. O lucrare de backup de succes în sine nu dovedește recuperabilitatea.

Copiile de rezervă ale fluxului de lucru GitHub sau Google Drive includ secrete de acreditări salvate?

Backup-urile JSON numai pentru fluxul de lucru nu includ valorile secrete gestionate de magazinul de acreditări n8n sau cheia de criptare a instanței. Totuși, JSON exportat poate expune nume de acreditări și ID-uri și secrete introduse direct în parametrii nodului, cum ar fi anteturile de autentificare. Inspectați și protejați exportul JSON înainte de a-l încărca sau de a-l partaja. Pentru o recuperare completă, faceți o copie de rezervă a bazei de date și a cheii originale sau utilizați acreditările criptate acceptate pentru exporturile CLI cu o restaurare testată. Un șablon numai pentru fluxul de lucru GitHub sau Google Drive nu este o recuperare completă în caz de dezastru.

OBIECTIVE DE RECUPERARE

Stabiliți RPO și RTO înainte de un incident

RPO este pierderea maximă tolerabilă a modificărilor recente. Măsurați-l de la cel mai nou punct de recuperare utilizabil, stocat independent; un job programat de șase ore nu stabilește un RPO de șase ore dacă exporturile sau transferurile nu au reușit. RTO este întreruperea maximă tolerabilă. Măsurați-l într-un exercițiu de restaurare curată, inclusiv regăsirea secretelor, restaurarea fișierelor externe, reverificarea acreditărilor și publicarea fluxurilor de lucru recuperate, nu doar pornirea unui container.

CHEIE DE RECUPERARE

Găsiți cheia de criptare originală înainte de a reconstrui

Dacă producția este stabilită N8N_ENCRYPTION_KEY, păstrați exact acel secret de mediu. Dacă nu a făcut-o, păstrați cheia generată în .n8n/config. Verificați ce sursă folosește de fapt instanța recuperată înainte de a importa acreditările criptate; o cheie proaspătă generată nu poate decripta acreditările din vechea bază de date.
