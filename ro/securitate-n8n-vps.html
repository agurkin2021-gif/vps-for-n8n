SECURITATEA PRODUCȚIEI

Securitate n8n pe VPS

Pentru a securiza n8n pe un VPS, păstrați n8n (5678), PostgreSQL (5432) și opțional Redis (6379) de pe internetul public; utilizați un proxy inversat HTTPS, cheile SSH și MFA, păstrați-vă cheia de criptare, autentificați webhook-urile, limitați capabilitățile de flux de lucru riscante și auditați instanța implementată. Protejați editorul separat de rutele webhook publice. Doar HTTPS nu securizează serviciile conectate.

LISTA DE VERIFICARE RAPIDĂ

Nivelul minim de securitate înainte de expunerea publică

Începeți cu porturile dvs. accesibile, HTTPS, acces administrativ verificat, MFA și protecția acreditărilor salvate. Autentificați fiecare webhook primit înainte ca acesta să poată declanșa lucrări sensibile. După modificarea controalelor de acces, verificați dacă editorii și integrările externe preconizate încă funcționează, apoi executați auditul de securitate n8n.

Doar HTTPS

Puneți n8n în spatele unui proxy invers TLS configurat corect și utilizați în mod constant adresa URL publică HTTPS pentru editor și webhook-uri.

Porturi deschise minime

Expuneți numai porturile necesare pentru traficul public. Păstrați PostgreSQL, Redis și porturile de aplicații interne în afara internetului public.

Hardening SSH

Utilizați administrarea bazată pe chei, restricționați cine se poate autentifica și mențineți sistemul de operare corectat.

Protejați acreditările

Păstrați cheia de criptare n8n stabilă și secretă. Tratați fișierele de mediu, accesul la baze de date și copiile de rezervă ca active sensibile.

BORCHIA REȚELEI

Proxy invers, HTTPS și anteturi de încredere

Terminare TLS

Utilizați un proxy invers, cum ar fi Nginx, Caddy sau Traefik pentru a încheia HTTPS. Redirecționați simplu HTTP și evitați expunerea directă a portului aplicației n8n atunci când proxy-ul este punctul de intrare dorit.

Configurare proxy

Când n8n rulează în spatele unui proxy invers, configurați corect numărul de hop proxy și transmiteți anteturile redirecționate, n8n de care are nevoie pentru a reconstrui cererea originală a clientului.

Cookie-uri securizate

Serviți editorul peste HTTPS, astfel încât cookie-urile de autentificare să rămână în siguranță. Nu rezolvați o configurare defectă TLS prin slăbirea securității cookie-urilor.

URL webhook

Setați URL-ul webhook-ului public la numele de gazdă HTTPS accesibil din exterior, astfel încât punctele finale webhook generate să nu indice un container intern sau o adresă HTTP.

Păstrați editorul privat fără a întrerupe webhook-urile. Restricționați accesul de gestionare utilizând un VPN, o politică IP de încredere sau un proxy autentificat atunci când este posibil. Este posibil ca receptoarele publice webhook și rutele de apel invers OAuth să rămână accesibile; testați atât o conectare cu un editor de încredere, cât și un apel invers extern real înainte de a aplica o regulă proxy. Redirecționați anteturile de adresă client numai de la proxy-uri de încredere, nu antete de solicitare arbitrară.

Autentificați apelanții webhook: în nodul Webhook, alegeți Autentificare de bază, Antet sau JWT în loc de Niciunul atunci când este acceptat de expeditor. Folosește-l Lista de IP(uri) permisă opțiunea, acolo unde este cazul, și verificați semnăturile furnizorului în cazul în care integrarea acceptă cererile semnate. O adresă URL dificil de ghicit nu este o autentificare suficientă. Aplicați limite de rată la proxy atunci când este cazul și confirmați că exploziile valide nu sunt blocate. VPS CALIRE

Reduceți suprafața de atac a serverului

Firewall

În mod implicit, interziceți traficul de intrare nesolicitat și permiteți numai serviciile care trebuie să fie accesibile. Baza de date și porturile Redis aparțin în mod normal rețelelor private/locale.

SSH

Preferați cheile SSH în locul parolelor, dezactivați căile de conectare inutile și limitați accesul administrativ. Accesul echivalent la rădăcină ar trebui să fie strict controlat.

Actualizări ale sistemului de operare

Corectați gazda și rularea containerului Linux. Întărirea aplicației nu poate compensa un sistem de operare expus sau învechit.

Expunerea containerului

Publicați numai porturile care necesită acces gazdă. Serviciile interne ar trebui să comunice pe rețele private Docker, mai degrabă decât prin interfețe publice.

Verificați înainte de a schimba setările paravanului de protecție sau SSH: verificați porturile de ascultare cu sudo ss -lntp, Docker publicarea cu docker compose ps din directorul de proiect și politica de firewall gazdă cu sudo ufw status verbose dacă se utilizează UFW. Verificați portul actual SSH și conectarea cu cheie cu succes într-o sesiune separată înainte de a dezactiva accesul prin parolă. Porturile publicate Docker pot ocoli regulile UFW; numai o pagină de stare firewall nu dovedește că portul 5678 este privat. Verificați accesibilitatea externă reală. Docker/Avertisment UFW.

Verificați actualizările automate de securitate Ubuntu în loc să presupuneți că funcționează: inspectează apt-config dump APT::Periodic::Unattended-Upgrade și jurnalul /var/log/unattended-upgrades/unattended-upgrades.log. Dacă upgrade-urile de securitate nesupravegheate sunt dezactivate, sudo dpkg-reconfigure unattended-upgrades oferă un dialog de configurare acceptat. Examinați comportamentul de repornire și repornire a serviciului înainte de a le activa pe un VPS care funcționează. Ubuntu Actualizările APT fac nu actualizați automat imaginea n8n Docker sau fiecare depozit de software terță parte. Ubuntu documentație de actualizare automată.

Opțional SSH monitorizare forță brută: Fail2Ban poate detecta conectări repetate eșuate SSH. Dacă este instalat și configurat pentru SSH, verificați închisoarea cu sudo fail2ban-client status sshd și confirmați că citește jurnalul sau jurnalul de autentificare actual SSH și se potrivește cu portul configurat. Aceasta completează cheile SSH și restricțiile de rețea; nu le înlocuiește. Nu copiați un port fix SSH sau o regulă de interzicere fără a verifica mai întâi accesul existent. Ubuntu SSH îndrumare de călire.

BAZĂ DE DATE & REDIS

Păstrați serviciile de backend private

Într-o configurație tipică Docker Compose, PostgreSQL și Queue Mode Redis ar trebui să fie accesibile de către containerele relevante prin rețea privată, nu porturi publicate de gazdă. Verificați cu docker compose ps că 5432 și 6379 nu sunt publicate public; revizuiți separat expunerea VPS/cloud firewall. Politicile de rețea nu înlocuiesc acreditările de bază de date cu privilegii minime.

PostgreSQLLegați-l la o interfață privată sau la o rețea de containere, cu excepția cazului în care accesul la distanță este necesar în mod explicit și securizat în mod independent.
RedisQueue Mode Redis este o infrastructură, nu un endpoint public. Restricționați accesul la rețea la componentele n8n care necesită acest lucru.
AcredităriUtilizați acreditările de bază de date dedicate doar cu permisiunile de care are nevoie aplicația și protejați-le în afara controlului sursei.
TransportCând traficul bazei de date traversează rețele care nu sunt de încredere, utilizați transportul criptat adecvat, în loc să vă bazați pe criptarea acreditărilor la nivel de aplicație.

N8N SECRETE

Protejați cheia de criptare și domeniul acreditărilor

Cheie de criptare

n8n criptează acreditările stocate folosind cheia de criptare. Păstrați aceeași cheie între reporniri și workeri și protejați-o separat de conținutul obișnuit al aplicației.

Secrete de mediu

Nu trimiteți parole, jetoane sau cheia de criptare într-un depozit public. Restricționați accesul la fișierele de mediu și secretele de implementare.

Accesul utilizatorului

Oferiți acces editor numai utilizatorilor de încredere. Fluxurile de lucru se pot conecta la sisteme sensibile și pot procesa secrete sau pot executa noduri puternice.

Domeniul acreditărilor

Folosiți conturi de serviciu limitate și jetoane API acolo unde este posibil. Un flux de lucru compromis nu ar trebui să moștenească automat acces larg la sistemele care nu au legătură.

n8n configurație de revizuit: N8N_BLOCK_ENV_ACCESS_IN_NODE=true împiedică accesul nodului cod și al expresiei la valorile mediului; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true solicită permisiuni numai de proprietar pentru fișierul de setări. Păstrează N8N_ENCRYPTION_KEY persistentă și se face backup în siguranță: n8n poate crea o cheie aleatorie la prima pornire, dar pierderea acesteia poate face ca acreditările criptate existente să nu fie utilizate. Nu înlocuiți o cheie de criptare de producție întâmplător; utilizați o procedură de rotație susținută oficial. Blocarea accesului la mediu poate rupe integrările existente, așa că testați înainte de modificările de producție. n8n definiţiile variabilelor de securitate.

RISCUL FLUXULUI DE LUCRU

Nodurile pot extinde perimetrul de securitate

Self-hosting oferă fluxurilor de lucru o putere substanțială. Execuția codului, accesul la shell, solicitările arbitrare HTTP și nodurile comunității terțe pot crește riscul. Dezactivați funcționalitatea de care nu aveți nevoie și examinați importurile de flux de lucru care nu sunt de încredere înainte de a le rula.

Utilizați comenzile exacte acceptate: configurați NODES_EXCLUDE cu o matrice JSON de noduri de dezactivat, cum ar fi n8n-nodes-base.executeCommand şi n8n-nodes-base.readWriteFile, dacă nu este folosit. Unele noduri cu risc ridicat sunt deja blocate implicit în versiunile mai noi; revizuiți lista reală înainte de a o schimba. Excluderi oficiale de noduri.

De la n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true permite verificări pentru cererile de ieșire HTTP către intervalele de adrese interne, loopback și metadate. Fluxurile de lucru interne legitime API pot înceta să funcționeze; dacă este necesar, listați în mod restrâns numai destinațiile pe care le controlați. Păstrați segmentarea rețelei ca apărare principală. Pentru izolarea nodului de cod, examinați rulatorii de activități externe. Protecție SSRF · Izolarea task-runner.

Noduri comunitareInstalați numai pachete în care aveți încredere; se execută în interiorul mediului dumneavoastră n8n.
Noduri riscanteExcludeți nodurile de care implementarea dvs. nu are nevoie atunci când capacitățile lor depășesc limita dorită a fluxului de lucru.
SSRFUtilizați protecția SSRF și controalele de rețea din n8n acolo unde fluxurile de lucru nu ar trebui să poată ajunge la punctele finale interne sau metadate.
Importuri de flux de lucruExaminați fluxurile de lucru importate, acreditările, expresiile și pașii executabili înainte de activare.

AUDIT ȘI ACTUALIZĂRI

Securitatea este un proces operațional continuu

Rulați auditul de securitate n8n

Comanda oficială CLI este n8n audit. Dacă serviciul dvs. de redactare Docker este numit n8n, fugi docker compose exec -T n8n n8n audit în acel director de implementare. Examinați cele cinci categorii: acreditări neutilizate, modele de interogare SQL riscante, acces la sistemul de fișiere, noduri riscante/comunității și riscuri de instanță, inclusiv webhook-uri neprotejate și versiuni învechite. Remediați constatările relevante și reluați. Acesta nu este un test de penetrare. Ghid oficial de audit.

Actualizați în mod deliberat

Păstrați n8n suficient de actual pentru a primi remedieri de securitate. Examinați notele de lansare și testați upgrade-uri importante, în loc să lăsați o instanță care se confruntă cu internetul permanent.

Monitorizați autentificarea

Urmăriți modelele de acces neașteptate, modificările fluxului de lucru și eșecurile. Restricționați și mai mult interfața de utilizare a editorului atunci când modelul dvs. de operare nu necesită accesibilitate publică largă.

Pregătiți rollback-ul și recuperarea

Faceți copii de rezervă recuperabile înainte de upgrade-uri semnificative. Domeniul de aplicare detaliat al backup-ului și restaurarea aparțin ghidului separat de recuperare.

Minimizați istoricul de execuție sensibil: executările de succes pot persista datele și jetoanele clienților. Când este cazul, setați EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, păstrați EXECUTIONS_DATA_PRUNE=true, și alegeți un EXECUTIONS_DATA_MAX_AGE în ore, cum ar fi 168 (șapte zile). Acestea sunt exemple configurabile, nu reguli legale de păstrare. Mai puțin istoric înseamnă mai puține date de depanare și criminalistice; execuțiile în curs, în așteptare sau adnotate nu pot fi tăiate în același mod. Reținerea execuției oficiale.

Suspect de compromis: restricționați accesul rău intenționat fără a distruge dovezi, inspectați proxy-ul, gazda și activitatea n8n și fluxurile de lucru modificate, revocați sau rotiți acreditările eventual expuse în amonte, corectați cauza și restaurați numai din backup-uri recuperabile testate atunci când este necesar. Examinați URL-urile webhook afectate, conturile de editor și serviciile conectate; nu presupuneți că HTTPS, instantanee sau o achiziție VPS oferă servicii de răspuns la incident.

CONTROLE ȘI PLATFORMĂ

Protejați editorul, precum și VPS

Impuneți protecție mai puternică la autentificare

Activați autentificarea cu doi factori pentru conturile de editor și aplicați politicile de securitate de la MFA la n8n atunci când ediția dvs. acceptă aplicarea centralizată a politicii.

Limitați cine poate edita fluxurile de lucru

Accesul la editor este un acces privilegiat: fluxurile de lucru pot citi acreditările, pot apela sistemele interne și pot executa noduri puternice. Mențineți accesul utilizatorilor restrâns și eliminați conturile care nu mai au nevoie de el.

Dezactivați capabilitățile pe care nu le utilizați

Reduceți suprafața de atac a aplicației prin dezactivarea publicului API atunci când nu este necesar și blocând nodurile sau funcțiile cu risc ridicat de care modelul dvs. de operare nu are nevoie.

Folosiți explicit controale SSRF și pentru secrete

Pentru fluxurile de lucru care pot face solicitări arbitrare HTTP, evaluați protecția SSRF a n8n și păstrați secretele din codul fluxului de lucru, depozitele publice și fișierele de mediu care pot fi citite pe scară largă.

Limitați punctele finale de gestionare neutilizate: N8N_PUBLIC_API_DISABLED=true dezactivează n8n REST public API și N8N_PUBLIC_API_SWAGGERUI_DISABLED=true își dezactivează locul de joacă API separat. Faceți acest lucru numai atunci când integrările dvs. nu necesită aceste caracteristici. Dezactivarea REST API nu autentifică adresele URL ale fluxului de lucru webhook. Utilizați MFA pentru utilizatorii editorului și politicile centralizate numai acolo unde ediția dvs. n8n le acceptă.

Întrebări frecvente

Securitate VPS pentru n8n: întrebări frecvente

Ar trebui expus direct portul n8n?

Când un proxy invers este punctul de intrare public, expuneți proxy-ul și păstrați portul aplicației în spatele lui, mai degrabă decât să publicați servicii inutile în general.

Ar trebui PostgreSQL sau Redis să fie public?

In mod normal nu. Acestea ar trebui să fie accesibile numai de sistemele care le necesită. Expunerea publicului mărește suprafața de atac fără a ajuta la funcționarea normală n8n.

De ce este importantă cheia de criptare n8n?

Protejează acreditările stocate de n8n și trebuie să rămână consecvent pe parcursul implementării. Pierderea acestuia poate împiedica datele recuperate să producă acreditări criptate utilizabile.

Sunt nodurile comunității sigure?

Ele extind n8n cu cod de la terți, așa că ar trebui tratate ca dependențe de software cu propriile lor riscuri de aprovizionare și privilegii. Instalați doar ceea ce aveți încredere și aveți nevoie.

HTTPS face o instanță self-hostedă n8n securizată?

Nr. HTTPS protejează transportul. Securitatea producției necesită, de asemenea, consolidarea gazdei, controlul accesului, servicii backend private, protecție secretă, capabilități sigure de flux de lucru, monitorizare și actualizări.

Editorul n8n poate fi privat în timp ce webhook-urile de producție încă rulează?

Da. Un proxy invers sau VPN de încredere poate restricționa accesul editor/administrator separat de webhook de producție publică și căile de apel invers OAuth. Testați conectarea de încredere și livrarea webhook extern după fiecare modificare a regulilor de acces pentru a evita blocarea accidentală a integrărilor dvs.

Cum autentific webhook-urile n8n primite?

Configurați autentificarea de bază, antet sau JWT în nodul Webhook atunci când expeditorul o acceptă. De asemenea, puteți utiliza lista de IP-uri permise și verificați semnăturile furnizorilor, acolo unde este disponibil. Nu vă bazați doar pe o cale secretă și validați cererile înainte ca acestea să declanșeze acțiuni sensibile API.
