SCALARE

n8n Queue Mode

Queue Mode separă execuția fluxului de lucru de procesul principal n8n. Instanța principală primește declanșatoare și creează execuții, Redis coordonează coada, workerii execută lucrări și PostgreSQL stochează fluxul de lucru partajat și datele de execuție.

DECIZIE RAPIDA

Aveți cu adevărat nevoie de Queue Mode?

Rămâneți în modul obișnuit când

O singură instanță gestionează execuțiile de vârf în mod confortabil, iar CPU, RAM și latența de execuție rămân stabile. Queue Mode adaugă componente de care nu aveți nevoie încă.

Luați în considerare Queue Mode când

Execuțiile paralele susținute creează dispute, latența de execuție crește sub sarcină sau trebuie să adăugați capacitate de execuție prin rularea mai multor workeri.

Scalați vertical mai întâi când

Gâtul de sticlă este pur și simplu insuficient CPU sau RAM și o instanță mai mare poate încă face față în mod curat sarcinii de lucru.

Măsurați înainte de a schimba arhitectura

Utilizați concurența maximă, CPU, RAM, durata execuției, adâncimea cozii și presiunea bazei de date pentru a justifica mutarea.

ARHITECTURA

Cum funcționează Queue Mode în n8n

1 · PrincipalPrimește cronometre, webhook-uri și solicitări de flux de lucru și creează o execuție în loc să facă execuția de producție în sine.
2 · RedisAcționează ca broker de mesaje. Deține mesaje de execuție în așteptare, astfel încât următorul worker disponibil să poată revendica un loc de muncă.
3 · WorkerPrimește ID-ul de execuție, încarcă datele fluxului de lucru din baza de date partajată, rulează fluxul de lucru și scrie rezultatul înapoi.
4 · PostgreSQLOferă fluxuri de lucru persistente partajate și date de execuție. Modul de coadă distribuită nu este acceptat peste SQLite.

CERINȚE DE bază

De ce are nevoie orice deployment Queue Mode

Redis

Toate procesele principale și de lucru au nevoie de acces fiabil la serviciul Redis utilizat pentru coordonarea cozii.

PostgreSQL

Principalul și workerii trebuie să partajeze baza de date. Queue Mode este o arhitectură distribuită și nu ar trebui proiectat în jurul SQLite.

Configurație n8n identică

Principalul și workerii trebuie să ruleze Queue Mode și să partajeze configurația necesară pentru a accesa Redis, PostgreSQL și acreditările criptate.

Capacitatea workerului

Workerii au nevoie de suficiente CPU și RAM pentru fluxurile de lucru pe care le execută. Adăugarea de procese nu înlătură costul resurselor fiecărei execuții.

Activați Queue Mode pe o stack self-hostedă existentă. Mai întâi, confirmați că serviciul principal n8n și fiecare worker pot accesa aceeași bază de date PostgreSQL și Redis printr-o rețea privată. Setați EXECUTIONS_MODE=queue atât pe principal, cât și pe workeri și pe aprovizionare QUEUE_BULL_REDIS_HOST=redis şi QUEUE_BULL_REDIS_PORT=6379 când redis este numele dvs. real al serviciului Compose. Utilizați DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres si potrivire DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER şi DB_POSTGRESDB_PASSWORD pe fiecare proces; înlocuiți exemplele de nume de servicii cu ale dvs. Furnizați exact existentul N8N_ENCRYPTION_KEY tuturor. Nu publicați niciodată porturile gazdă Redis sau PostgreSQL doar pentru a conecta containere în aceeași rețea Compose.

Lansați un executor, nu un al doilea editor. Adăugați un serviciu de lucru n8n utilizând aceeași versiune de imagine n8n fixată și setări partajate ca principale, dar rulați-l cu worker comanda. Dacă ai denumit acel serviciu n8n-worker, începe cu docker compose up -d n8n-worker. După confirmarea execuției efective pe un worker, puteți utiliza docker compose up -d --scale n8n-worker=2 pentru a începe un al doilea worker din acel serviciu. Acestea sunt completări la un existente configurate corect Compose stack, nu un fișier de instalare independent; păstrați volumele persistente existente, proxy HTTPS, secrete și copii de rezervă.

Queue Mode Compune fragment pentru o stack existentă. Îmbină exemplul de mai jos cu curentul tău compose.yaml; este nu o implementare completă de sine stătătoare. Se presupune că aveți deja persistente, private postgres şi n8n servicii, un existent N8N_VERSION pin în mediul tău și propriul tău protejat POSTGRES_PASSWORD si originala N8N_ENCRYPTION_KEY. Potriviți numele, volumele, baza de date și versiunea n8n cu proiectul existent. Adăugați setările modului coadă Redis și EXECUTIONS_MODE=queue și la serviciul principal existent, așa cum este descris mai sus.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Niciun port gazdă nu este publicat pentru Redis sau workerul din acest fragment. Redis persistența numai pentru atașare este un strat suplimentar de recuperare, nu un substitut pentru backup-uri off-server. Păstrați neschimbate HTTPS și configurația de autentificare existente. Pentru nodurile de cod care necesită executori de sarcini externi, configurați separat procesele de rulare pentru implementarea workerului dvs.; Queue Mode în sine nu înlocuiește rulatorii de activități.

Convertiți o instanță existentă SQLite? Nu vă schimbați pur și simplu DB_TYPE și începeți cu o bază de date goală PostgreSQL: acest lucru nu migrează fluxurile de lucru și acreditările vechi. Înainte de orice tăiere, faceți o copie de rezervă a bazei de date sursă, persistentă .n8n director și cheie de criptare originală; utilizați o procedură acceptată de export/import sau migrare n8n, apoi verificați fluxurile de lucru și acreditările criptate pe o țintă separată. Păstrați fișierele originale pentru derulare și utilizați ghidul Backup & Restore de mai jos pentru pregătirea recuperării. Nu șterge niciodată database.sqlite ca o scurtătură.

CONCURENȚA WORKERILOR

Capacitatea crește prin numărul de workeri și concurența per worker

Fiecare worker poate procesa mai multe lucrări simultan. Concurența curentă implicită a workerului n8n este 10 și documentația sa recomandă o concurență de 5 sau mai mare. Concurența foarte scăzută, combinată cu mulți workeri, pot crea conexiuni inutile la baze de date și pot epuiza pool-ul de conexiuni la baza de date.

Creșteți concurența când

Un worker are CPU și RAM de rezervă, iar fluxurile de lucru așteaptă în mare parte servicii externe, mai degrabă decât să sature calculul sau memoria.

Adăugați workeri când

Un proces de lucru devine un blocaj, iar baza de date, Redis și infrastructura au capacitate pentru mai multă execuție paralelă.

Reduceți concurența când

Fluxurile de lucru individuale sunt grele de memorie sau CPU-grele și lucrările paralele provoacă dispute, presiune OOM sau timpi de execuție instabili.

Monitorizați PostgreSQL

Mai mulți angajați și mai multă concurență cresc activitatea bazei de date. Scalarea capacității de execuție fără capacitatea bazei de date poate muta blocajul, mai degrabă decât să-l elimine.

Aflați ce limită de concurență se aplică de fapt. Un worker poate fi început să folosească n8n worker --concurrency=5, sau comanda worker echivalentă din serviciul dvs. Compose. Dacă N8N_CONCURRENCY_PRODUCTION_LIMIT este setată în mod explicit la o altă valoare decât -1, acea setare are prioritate în Queue Mode; in caz contrar n8n foloseste a lucratorului --concurrency valoarea sau implicită a acesteia de 10. Nu înmulțiți numărul de workeri cu o valoare implicită nominală și numiți-o debit garantat: capacitatea reală depinde de durata lucrării, CPU, memorie, API-uri externe și conexiuni PostgreSQL.

WEBHOOK-URI

Queue Mode poate adăuga latență la transferul execuției

Procesul principal sau webhook primește cererea HTTP, dar un worker realizează execuția fluxului de lucru. Acea transferare prin Redis adaugă unele cheltuieli generale. Pentru webhook-urile sensibile la latență, măsurați timpul de răspuns end-to-end, mai degrabă decât să presupuneți că mai mulți workeri fac automat fiecare solicitare mai rapid.

PrimeșteProcesul principal/webhook acceptă cererea.
coadăExecutarea se preda Redis.
ExecutăUn worker disponibil conduce fluxul de lucru.
RăspundeRezultatul este transmis înapoi prin calea de coadă atunci când este necesar.

Dirijați traficul webhook către procesul potrivit. Cu dedicat n8n webhook procesoarele din spatele unui proxy invers sau al unui echilibrator de încărcare, direcționează căile de producție /webhook/* şi /webhook-waiting/* către procesoarele webhook; păstrează /webhook-test/*, editor și solicitări API pe main. Nu puneți principal în pool-ul de echilibrare a încărcăturii webhook de producție decât dacă acceptați în mod deliberat acea sarcină de lucru adăugată. A Răspunde la Webhook fluxul de lucru poate face clientul să aștepte până când workerul termină și returnează răspunsul său, astfel încât Queue Mode nu este o promisiune de răspunsuri instant HTTP sau zero timeouts. Testați comportamentul real de apelare externă și răspuns înainte de a schimba traficul.

DATE BINARE

Nu treceți cu vederea stocarea partajată

Limitarea sistemului de fișiere

Queue Mode nu acceptă stocarea datelor binare în sistemul de fișiere ca model de persistență partajată pentru workerii distribuiți.

Stocare binară externă

Când fluxurile de lucru trebuie să persiste date binare între workerii distribuiți, utilizați un design de stocare pe care să îl poată accesa fiecare instanță necesară, cum ar fi stocarea de obiecte externe acceptată.

Răspunsuri mari la webhook

Răspunsurile Webhook de la workeri se deplasează înapoi spre procesul de primire. Corpurile de răspuns mari pot crește presiunea memoriei Redis și necesită o configurație deliberată de stocare a răspunsului.

Planificați înainte de a distribui workerii

Un volum de lucru care depinde în mare măsură de fișierele locale trebuie reproiectat pentru persistență partajată înainte ca workerii să fie răspândiți pe mașini.

Limită mare de răspuns la webhook. Documentatia n8n curenta da N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX un implicit al 64 MiB pentru răspunsul unui worker trimis înapoi prin coadă. Redis poate deține mai multe copii în zbor, așa că bugetați aproximativ 1.5 ori dimensiunea răspunsului din memoria Redis per răspuns mare simultan. Fără descărcare, un răspuns supradimensionat eșuează în loc să devină magic mai rapid prin adăugarea de workeri.

Limitele de versiune și licență. De la n8n 2.34.0, workerii pot folosi N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true pentru a descărca corpuri de răspuns webhook supradimensionate în spațiul de stocare binar partajat lizibil, dar mai întâi actualizați fiecare procesor principal și webhook la 2.34.0 sau mai târziu. Cel selectat N8N_DEFAULT_BINARY_DATA_MODE trebuie să stocheze efectiv date și să poată fi citite de fiecare proces participant. Stocarea binară externă S3 și Azure necesită o configurație self-hosted validă Afaceri sau Întreprinderi licență; nu presupuneți că Community Edition le poate activa. The database Modul binar poate descărca un răspuns supradimensionat fără stocare externă plătită, dar instanța principală încarcă întregul corp stocat în memorie, iar stocarea bazei de date are propria limită de dimensiune a fișierului. Pentru răspuns-descărcarea corpului în mod specific, n8n descrie, de asemenea, un partajat filesystem opțiune când fiecare instanță montează același disc, dar nu recomandă în mod explicit acest aranjament. Nu confundați această cale specială de descărcare cu suportul datelor binare persistente bazate pe sistemul de fișiere într-o implementare distribuită în Queue Mode. Verificați ediția, versiunea și configurația de stocare înainte de a activa descărcarea.

MONITORIZARE

Măsurați dacă Queue Mode ajută efectiv

Adâncimea cozii

O coadă care crește mai repede decât epuizează workerii indică o capacitate de execuție insuficientă sau un blocaj în aval.

Worker CPU & RAM

Măsurați saturația și vârfurile de memorie per worker. Workerii inactivi cu o coadă în creștere indică o altă constrângere.

Latența de execuție

Urmăriți întârzierea dintre crearea unei execuții și începerea efectivă, nu numai timpul de execuție a fluxului de lucru în sine.

Verificări de health

Punctele finale de sănătate a workerilor pot raporta dacă un worker este în viață și dacă baza de date și conexiunile Redis sunt gata.

Verificați execuția unui worker, nu doar a unui container verde. Cu o stack Compose configurată corect, verificați docker compose ps şi docker compose logs --tail=100 n8n-worker (înlocuiți numele serviciului dacă este diferit). Fugi un inofensiv producție publicată flux de lucru utilizând un declanșator programat sau un webhook de testare, apoi potriviți execuția acestuia în vizualizarea Execuții din n8n cu procesarea efectivă a workerului din jurnalele workerilor. Un editor care se deschide cu succes, un container Redis care rulează sau o execuție pusă în coadă o face nu dovediți că un worker a îndeplinit locul de muncă.

Verificați dependențele și pregătirea. Cu exemple implicite de nume de servicii, docker compose exec -T redis redis-cli ping ar trebui să primească PONG când autentificarea Redis o permite și docker compose exec -T postgres pg_isready -U n8n -d n8n verifică starea PostgreSQL (adaptarea acreditărilor și a numelor de servicii). Activați QUEUE_HEALTH_CHECK_ACTIVE=true asupra unui worker atunci când ai nevoie de privat /healthz şi /healthz/readiness puncte finale; endpoint-ul de pregătire verifică conectivitatea Redis/bază de date. Nu expuneți în mod public acele puncte finale ale workerilor doar pentru a le monitoriza.

Rularile manuale sunt un test diferit. Implicit OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, deci rularea manuală a unui flux de lucru în editor se poate executa pe main chiar și atunci când Queue Mode este configurat corect. Setează-l la true numai dacă intenționați să trimiteți execuții manuale workerilor și ați verificat modificarea într-un mediu de staging. Workerii în Queue Mode sunt, de asemenea, distincți de executatorii de sarcini externe n8n, care au cerințe de configurare separate pentru execuția nodului de cod.

LIMITĂ DE ÎNALTĂ DISPONIBILITATE

Queue Mode scalează execuțiile, dar nu face automat procesul principal high-availability

Partajați cheia de criptare

Fiecare worker trebuie să folosească același lucru N8N_ENCRYPTION_KEY ca instanță principală, astfel încât workerii să poată decripta acreditările necesare execuțiilor fluxului de lucru.

Păstrați versiunile aliniate

Procesele principale, webhook și worker ar trebui să ruleze aceeași versiune n8n. Versiunile mixte pot crea un comportament incompatibil în timpul modificărilor de rulare.

Procesoarele webhook reprezintă un strat separat de scalare

Când volumul webhook-ului primit devine un blocaj, procesoarele webhook dedicate pot sta în spatele unui echilibrator de încărcare, în timp ce workerii se ocupă de execuție. Nu adăugați acest strat decât dacă volumul de solicitare măsurat justifică acest lucru.

Multi-main este o funcționalitate diferită

Rularea mai multor procese principale pentru disponibilitate ridicată nu este același lucru cu modul obișnuit de coadă. n8n documentează în prezent multi-main ca o caracteristică Enterprise self-hostedă, cu cerințe suplimentare de echilibrare a încărcăturii și de sesiune.

Arhitectura și configurația oficială a modului coadă

Întrebări frecvente

n8n Queue Mode: întrebări frecvente

n8n Queue Mode necesită Redis?

Da. Redis este brokerul de mesaje care coordonează execuțiile în așteptare între instanța principală și workeri.

Queue Mode poate folosi SQLite?

Nu pentru arhitectura distribuită în Queue Mode. Principalul și workerii au nevoie de acces la baza de date partajată, iar n8n documente PostgreSQL ca bază de date pentru această configurare.

Câți workeri ar trebui să conduc?

Nu există un număr universal. Începeți de la concurența măsurată și de la utilizarea workerilor, apoi adăugați capacitatea în timp ce monitorizați PostgreSQL, Redis, CPU, RAM și adâncimea cozii.

Ce este concurența workerului n8n?

Este numărul de joburi pe care un worker le poate procesa în paralel. Valoarea implicită curentă este 10, iar n8n recomandă concurența workerilor de 5 sau mai degrabă decât crearea multor workeri cu concurență redusă.

Ar trebui să activez Queue Mode pe un mic VPS?

Doar atunci când volumul de muncă o justifică. O implementare mică care rulează confortabil ca o singură instanță este de obicei mai simplu de operat fără Redis și workeri separați.
