স্কেলিং

n8n কিউ মোড

Queue mode workflow execution-কে main n8n process থেকে আলাদা করে। Main instance trigger receive করে ও execution তৈরি করে, Redis queue coordinate করে, worker job execute করে এবং PostgreSQL shared workflow ও execution data store করে।

দ্রুত সিদ্ধান্ত

আপনার আসলেই queue mode দরকার?

Regular mode-এ থাকুন যখন

একটি instance peak execution comfortably handle করে এবং CPU, RAM ও execution latency stable থাকে। Queue mode এমন component যোগ করে যা এখনও দরকার নেই।

Queue mode বিবেচনা করুন যখন

Sustained parallel execution contention তৈরি করে, load-এ execution latency বাড়ে, অথবা multiple worker চালিয়ে execution capacity বাড়াতে হয়।

প্রথমে vertically scale করুন যখন

Bottleneck শুধু insufficient CPU বা RAM এবং একটি বড় instance এখনও workload cleanly সামলাতে পারে।

Architecture বদলানোর আগে measure করুন

Move justify করতে peak concurrency, CPU, RAM, execution duration, queue depth ও database pressure ব্যবহার করুন।

আর্কিটেকচার

n8n queue mode কীভাবে কাজ করে

1 · MainTimer, webhook ও workflow request receive করে এবং production execution নিজে করার বদলে execution তৈরি করে।
2 · RedisMessage broker হিসেবে কাজ করে। Pending execution message ধরে রাখে যাতে পরের available worker job claim করতে পারে।
3 · WorkerExecution ID receive করে, shared database থেকে workflow data load করে, workflow run করে এবং result write back করে।
4 · PostgreSQLShared persistent workflow ও execution data দেয়। Distributed queue mode SQLite-এর উপর supported নয়।

CORE রিকোয়ারমেন্ট

প্রতিটি queue-mode deployment-এর যা দরকার

Redis

সব main ও worker process-এর queue coordination-এ ব্যবহৃত Redis service-এ reliable access দরকার।

PostgreSQL

Main ও worker একই database share করবে। Queue mode distributed architecture এবং SQLite কেন্দ্র করে design করা উচিত নয়।

মিল থাকা n8n কনফিগারেশন

Main ও worker queue mode চালাবে এবং Redis, PostgreSQL ও encrypted credential access-এর দরকারি configuration share করবে।

ওয়ার্কারের সক্ষমতা

Worker যে workflow execute করে তার জন্য যথেষ্ট CPU ও RAM দরকার। Process যোগ করলে প্রতিটি execution-এর resource cost দূর হয় না।

Existing self-hosted stack-এ queue mode enable করুন। প্রথমে confirm করুন n8n main service ও প্রতিটি worker private network দিয়ে একই PostgreSQL database ও Redis-এ পৌঁছাতে পারে। Set করুন EXECUTIONS_MODE=queue main ও worker দুটিতেই, এবং দিন QUEUE_BULL_REDIS_HOST=redis এবং QUEUE_BULL_REDIS_PORT=6379 যখন redis আপনার actual Compose service name। ব্যবহার করুন DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres এবং matching DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER এবং DB_POSTGRESDB_PASSWORD প্রতিটি process-এ; example service name নিজেরটা দিয়ে replace করুন। Exact existing N8N_ENCRYPTION_KEY সব process-এ দিন। একই Compose network-এ container connect করার জন্য Redis বা PostgreSQL host port কখনো publish করবেন না।

দ্বিতীয় editor নয়, executor launch করুন। Main-এর same pinned n8n image version ও shared setting ব্যবহার করে n8n worker service যোগ করুন, তবে চালান worker command দিয়ে। Service-এর নাম যদি n8n-worker, তাহলে start করুন docker compose up -d n8n-worker. এক worker-এ actual execution confirm করার পর ব্যবহার করতে পারেন docker compose up -d --scale n8n-worker=2 সেই service থেকে second worker start করতে। এগুলো addition একটি আগে থেকেই সঠিকভাবে কনফিগার করা Compose stack-এ, standalone installation file নয়; existing persistent volume, HTTPS proxy, secret ও backup রাখুন।

Existing stack-এর queue-mode Compose fragment। নিচের example current compose.yaml-এর সঙ্গে merge করুন; এটি না complete stand-alone deployment। ধরে নেওয়া হয়েছে আপনার আগে থেকেই persistent private postgres এবং n8n service, existing N8N_VERSION environment-এ pin এবং নিজের protected POSTGRES_PASSWORD ও original N8N_ENCRYPTION_KEY. Name, volume, database ও n8n version existing project-এর সঙ্গে match করুন। Queue-mode Redis setting ও EXECUTIONS_MODE=queue উপরে বলা মতো existing main service-এও যোগ করুন।

# Existing service-এর সঙ্গে merge করুন; পুরো Compose file replace করবেন না।
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

এই fragment-এ Redis বা worker-এর host port publish করা নেই। Redis append-only persistence extra recovery layer, না off-server backup-এর substitute নয়। Existing HTTPS ও authentication configuration unchanged রাখুন। External task runner দরকার এমন Code node-এর জন্য worker deployment-এর runner process separately configure করুন; queue mode নিজে task runner replace করে না।

Existing SQLite instance convert করছেন? শুধু change করবেন না DB_TYPE এবং empty PostgreSQL database-এর বিরুদ্ধে start করবেন না: এতে old workflow ও credential migrate হয় না। Cutover-এর আগে source database, persistent .n8n directory ও original encryption key backup করুন; supported n8n export/import বা migration procedure ব্যবহার করুন, তারপর separate target-এ workflow ও encrypted credential verify করুন। Rollback-এর জন্য original file রাখুন এবং recovery preparation-এর জন্য নিচের Backup & Restore guide ব্যবহার করুন। কখনো delete করবেন না database.sqlite shortcut হিসেবে।

ওয়ার্কারের সমান্তরাল কাজ

Worker count ও প্রতি worker job—দুইভাবেই scale করে

প্রতিটি worker একসঙ্গে multiple job process করতে পারে। n8n-এর current default worker concurrency 10 এবং documentation 5 বা তার বেশি recommend করে। খুব low concurrency + অনেক worker unnecessary database connection তৈরি করে connection pool exhaust করতে পারে।

Concurrency বাড়ান যখন

Worker-এর spare CPU ও RAM আছে এবং workflow compute/memory saturate করার বদলে external service-এর অপেক্ষায় থাকে।

Worker যোগ করুন যখন

এক worker process bottleneck হয় এবং database, Redis ও infrastructure-এর বেশি parallel execution capacity আছে।

Concurrency কমান যখন

Individual workflow memory-heavy বা CPU-heavy এবং parallel job contention, OOM pressure বা unstable execution time তৈরি করে।

PostgreSQL monitor করুন

বেশি worker ও concurrency database activity বাড়ায়। Database capacity ছাড়া execution capacity scale করলে bottleneck remove না হয়ে অন্য জায়গায় যেতে পারে।

কোন concurrency limit আসলে apply করে জানুন। Worker start করা যায় n8n worker --concurrency=5, অথবা Compose service-এর equivalent worker command দিয়ে। যদি N8N_CONCURRENCY_PRODUCTION_LIMIT explicitly এমন value-এ set করা হয় যা -1, তাহলে queue mode-এ সেটি precedence পায়; অন্যথায় n8n worker-এর --concurrency value বা default 10 ব্যবহার করে। Worker count-কে nominal default দিয়ে multiply করে guaranteed throughput বলবেন না: actual capacity job duration, CPU, memory, external API ও PostgreSQL connection-এর উপর নির্ভর করে।

WEBHOOK

Queue mode execution handoff latency যোগ করতে পারে

Main বা webhook process HTTP request receive করে, কিন্তু worker workflow execution করে। Redis-এর মাধ্যমে handoff কিছু overhead যোগ করে। Latency-sensitive webhook-এর জন্য বেশি worker automatically সব request দ্রুত করবে ধরে না নিয়ে end-to-end response time measure করুন।

ReceiveMain/webhook process request accept করে।
QueueExecution Redis-এ handoff হয়।
ExecuteAvailable worker workflow চালায়।
Respondদরকার হলে result queue path দিয়ে relay back হয়।

Webhook traffic সঠিক process-এ route করুন। Dedicated n8n webhook processor reverse proxy বা load balancer-এর পিছনে থাকলে production path route করুন /webhook/* এবং /webhook-waiting/* webhook processor-এ; রাখুন /webhook-test/*, editor ও API request main-এ। Added workload consciously accept না করলে main-কে production webhook load-balancing pool-এ রাখবেন না। Respond to Webhook workflow worker finish করে response দেওয়া পর্যন্ত client অপেক্ষা করাতে পারে, তাই queue mode instant HTTP response বা zero timeout-এর promise নয়। Traffic switch করার আগে actual external callback ও response behavior test করুন।

BINARY DATA

Shared storage উপেক্ষা করবেন না

ফাইলসিস্টেমের সীমাবদ্ধতা

Distributed worker-এর shared persistence model হিসেবে queue mode filesystem binary-data storage support করে না।

বাহ্যিক বাইনারি স্টোরেজ

Distributed worker জুড়ে binary data persist করতে হলে এমন storage design ব্যবহার করুন যা প্রতিটি required instance access করতে পারে, যেমন supported external object storage।

Large webhook response

Worker-এর webhook response receiving process-এর দিকে ফিরে আসে। Large response body Redis memory pressure বাড়াতে পারে এবং deliberate response-storage configuration দরকার হতে পারে।

Worker distribute করার আগে plan করুন

Local file-এর উপর heavily dependent workload worker machine-এ ছড়ানোর আগে shared persistence-এর জন্য redesign করতে হবে।

Large webhook response boundary। Current n8n documentation দেয় N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX default 64 MiB queue দিয়ে ফেরত পাঠানো worker response-এর জন্য। Redis in-flight একাধিক copy ধরে রাখতে পারে, তাই প্রতি concurrent large response-এর জন্য Redis memory-তে response size-এর প্রায় 1.5 গুণ budget করুন। Offloading ছাড়া oversized response worker যোগ করলেই magically faster না হয়ে fail করে।

Version ও license limit। n8n 2.34.0, থেকে worker ব্যবহার করতে পারে N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true oversized webhook response body readable shared binary storage-এ offload করতে, তবে আগে upgrade করুন প্রতিটি main ও webhook processor 2.34.0 বা পরে। Selected N8N_DEFAULT_BINARY_DATA_MODE আসলেই data store করবে এবং প্রতিটি participating process দ্বারা readable হতে হবে। External S3 ও Azure binary storage-এর জন্য valid self-hosted Business বা Enterprise license দরকার; Community Edition এগুলো enable করতে পারে ধরে নেবেন না। database binary mode paid external storage ছাড়া oversized response offload করতে পারে, কিন্তু main instance পুরো stored body memory-তে load করে এবং database storage-এর নিজস্ব file-size limit আছে। বিশেষভাবে response-body offload-এর জন্য, n8n shared filesystem option-ও বর্ণনা করে যখন প্রতিটি instance একই disk mount করে, তবে arrangement explicitly recommend করে না। এই special offload path-কে distributed queue-mode deployment-এ filesystem-based persistent binary data support ভাববেন না। Offload enable করার আগে edition, version ও storage configuration check করুন।

MONITORING

Queue সাহায্য করছে কিনা জানুন

Queue depth

Worker যত দ্রুত drain করে তার চেয়ে queue দ্রুত বাড়লে insufficient execution capacity বা downstream bottleneck নির্দেশ করে।

ওয়ার্কারের CPU ও RAM

প্রতি worker saturation ও memory peak measure করুন। Growing queue-সহ idle worker অন্য constraint নির্দেশ করে।

এক্সিকিউশনে বিলম্ব

শুধু workflow runtime নয়, execution তৈরি হওয়া ও আসলে start হওয়ার মধ্যে delay track করুন।

Health check

Worker health endpoint জানাতে পারে worker alive কিনা এবং database ও Redis connection ready কিনা।

শুধু green container নয়, worker-এ execution verify করুন। Correctly configured Compose stack-এ check করুন docker compose ps এবং docker compose logs --tail=100 n8n-worker (service name আলাদা হলে replace করুন)। Harmless প্রোডাকশনে প্রকাশিত workflow scheduled trigger বা test webhook দিয়ে চালান, তারপর n8n Executions view-এর execution worker log-এর actual processing-এর সঙ্গে match করুন। Successfully open হওয়া editor, running Redis container বা queued execution একা না প্রমাণ করে না worker job perform করেছে।

Dependency ও readiness check করুন। Default example service name দিয়ে docker compose exec -T redis redis-cli ping পাওয়া উচিত PONG যখন Redis authentication allow করে, এবং docker compose exec -T postgres pg_isready -U n8n -d n8n PostgreSQL readiness check করে (credential ও service name adapt করুন)। Enable করুন QUEUE_HEALTH_CHECK_ACTIVE=true worker-এ যখন private /healthz এবং /healthz/readiness endpoint দরকার; readiness endpoint Redis/database connectivity check করে। শুধু monitor করার জন্য worker endpoint publicly expose করবেন না।

Manual run আলাদা test। Default-এ OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, তাই queue mode correctly configured হলেও editor-এ manually workflow run main-এ execute হতে পারে। Set করুন true শুধু manual execution worker-এ পাঠাতে চান এবং staging environment-এ change check করেছেন হলে। Queue-mode worker n8n external task runner থেকেও আলাদা, যাদের Code-node execution-এর separate configuration requirement আছে।

HIGH AVAILABILITY সীমা

Queue mode execution scale করে, কিন্তু main process automatically highly available করে না

Encryption key share করুন

প্রতিটি worker একই N8N_ENCRYPTION_KEY main instance-এর মতো ব্যবহার করবে যাতে worker workflow execution-এর required credential decrypt করতে পারে।

Version aligned রাখুন

Main, webhook ও worker process একই n8n version চালাবে। Mixed version rolling change-এর সময় incompatible behavior তৈরি করতে পারে।

Webhook processor আলাদা scaling layer

Incoming webhook volume bottleneck হলে dedicated webhook processor load balancer-এর পিছনে থাকতে পারে, worker execution handle করবে। Measured request volume justify না করলে এই layer যোগ করবেন না।

Multi-main আলাদা feature

High availability-এর জন্য multiple main process চালানো ordinary queue mode-এর সমান নয়। n8n বর্তমানে multi-main-কে additional load-balancer ও session requirement-সহ self-hosted Enterprise feature হিসেবে document করে।

FAQ

n8n queue mode: সাধারণ প্রশ্ন

n8n queue mode-এর Redis দরকার?

হ্যাঁ। Redis message broker যা main instance ও worker-এর মধ্যে pending execution coordinate করে।

Queue mode SQLite ব্যবহার করতে পারে?

Distributed queue-mode architecture-এর জন্য না। Main ও worker shared database access চায়, এবং n8n এই setup-এর database হিসেবে PostgreSQL document করে।

কত worker চালাব?

Universal count নেই। Measured concurrency ও worker utilization থেকে শুরু করুন, তারপর PostgreSQL, Redis, CPU, RAM ও queue depth monitor করতে করতে capacity যোগ করুন।

n8n worker concurrency কী?

এটি worker parallel-এ কত job process করতে পারে তার সংখ্যা। Current default 10, এবং n8n অনেক low-concurrency worker তৈরির বদলে 5 বা তার বেশি worker concurrency recommend করে।

Small VPS-এ queue mode enable করা উচিত?

শুধু workload justify করলে। একটি instance হিসেবে comfortably চলা small deployment Redis ও separate worker ছাড়া সাধারণত operate করা সহজ।
