SCALING

n8n Queue Mode

Queue mode workflow execution-কে main n8n process থেকে আলাদা করে। Main instance trigger receive করে ও execution তৈরি করে, Redis queue coordinate করে, worker job execute করে এবং PostgreSQL shared workflow ও execution data store করে।

QUICK DECISION

আপনার আসলেই queue mode দরকার?

Regular mode-এ থাকুন যখন

একটি instance peak execution comfortably handle করে এবং CPU, RAM ও execution latency stable থাকে। Queue mode এমন component যোগ করে যা এখনও দরকার নেই।

Queue mode বিবেচনা করুন যখন

Sustained parallel execution contention তৈরি করে, load-এ execution latency বাড়ে, অথবা multiple worker চালিয়ে execution capacity বাড়াতে হয়।

প্রথমে vertically scale করুন যখন

Bottleneck শুধু insufficient CPU বা RAM এবং একটি বড় instance এখনও workload cleanly সামলাতে পারে।

Architecture বদলানোর আগে measure করুন

Move justify করতে peak concurrency, CPU, RAM, execution duration, queue depth ও database pressure ব্যবহার করুন।

ARCHITECTURE

n8n queue mode কীভাবে কাজ করে

1 · MainTimer, webhook ও workflow request receive করে এবং production execution নিজে করার বদলে execution তৈরি করে।
2 · RedisMessage broker হিসেবে কাজ করে। Pending execution message ধরে রাখে যাতে পরের available worker job claim করতে পারে।
3 · WorkerExecution ID receive করে, shared database থেকে workflow data load করে, workflow run করে এবং result write back করে।
4 · PostgreSQLShared persistent workflow ও execution data দেয়। Distributed queue mode SQLite-এর উপর supported নয়।

CORE REQUIREMENTS

প্রতিটি queue-mode deployment-এর যা দরকার

Redis

সব main ও worker process-এর queue coordination-এ ব্যবহৃত Redis service-এ reliable access দরকার।

PostgreSQL

Main ও worker একই database share করবে। Queue mode distributed architecture এবং SQLite কেন্দ্র করে design করা উচিত নয়।

Matching n8n configuration

Main ও worker queue mode চালাবে এবং Redis, PostgreSQL ও encrypted credential access-এর দরকারি configuration share করবে।

Worker capacity

Worker যে workflow execute করে তার জন্য যথেষ্ট CPU ও RAM দরকার। Process যোগ করলে প্রতিটি execution-এর resource cost দূর হয় না।

Existing self-hosted stack-এ queue mode enable করুন। প্রথমে confirm করুন n8n main service ও প্রতিটি worker private network দিয়ে একই PostgreSQL database ও Redis-এ পৌঁছাতে পারে। Set করুন EXECUTIONS_MODE=queue main ও worker দুটিতেই, এবং দিন QUEUE_BULL_REDIS_HOST=redis এবং QUEUE_BULL_REDIS_PORT=6379 যখন redis আপনার actual Compose service name। ব্যবহার করুন DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres এবং matching DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER এবং DB_POSTGRESDB_PASSWORD প্রতিটি process-এ; example service name নিজেরটা দিয়ে replace করুন। Exact existing N8N_ENCRYPTION_KEY সব process-এ দিন। একই Compose network-এ container connect করার জন্য Redis বা PostgreSQL host port কখনো publish করবেন না।

দ্বিতীয় editor নয়, executor launch করুন। Main-এর same pinned n8n image version ও shared setting ব্যবহার করে n8n worker service যোগ করুন, তবে চালান worker command দিয়ে। Service-এর নাম যদি n8n-worker, তাহলে start করুন docker compose up -d n8n-worker. এক worker-এ actual execution confirm করার পর ব্যবহার করতে পারেন docker compose up -d --scale n8n-worker=2 সেই service থেকে second worker start করতে। এগুলো addition একটি existing correctly configured Compose stack-এ, standalone installation file নয়; existing persistent volume, HTTPS proxy, secret ও backup রাখুন।

Existing stack-এর queue-mode Compose fragment। নিচের example current compose.yaml-এর সঙ্গে merge করুন; এটি না complete stand-alone deployment। ধরে নেওয়া হয়েছে আপনার আগে থেকেই persistent private postgres এবং n8n service, existing N8N_VERSION environment-এ pin এবং নিজের protected POSTGRES_PASSWORD ও original N8N_ENCRYPTION_KEY. Name, volume, database ও n8n version existing project-এর সঙ্গে match করুন। Queue-mode Redis setting ও EXECUTIONS_MODE=queue উপরে বলা মতো existing main service-এও যোগ করুন।

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

এই fragment-এ Redis বা worker-এর host port publish করা নেই। Redis append-only persistence extra recovery layer, না off-server backup-এর substitute নয়। Existing HTTPS ও authentication configuration unchanged রাখুন। External task runner দরকার এমন Code node-এর জন্য worker deployment-এর runner process separately configure করুন; queue mode নিজে task runner replace করে না।

Existing SQLite instance convert করছেন? শুধু change করবেন না DB_TYPE এবং empty PostgreSQL database-এর বিরুদ্ধে start করবেন না: এতে old workflow ও credential migrate হয় না। Cutover-এর আগে source database, persistent .n8n directory ও original encryption key backup করুন; supported n8n export/import বা migration procedure ব্যবহার করুন, তারপর separate target-এ workflow ও encrypted credential verify করুন। Rollback-এর জন্য original file রাখুন এবং recovery preparation-এর জন্য নিচের Backup & Restore guide ব্যবহার করুন। কখনো delete করবেন না database.sqlite shortcut হিসেবে।

WORKER CONCURRENCY

Worker count ও প্রতি worker job—দুইভাবেই scale করে

প্রতিটি worker একসঙ্গে multiple job process করতে পারে। n8n-এর current default worker concurrency 10 এবং documentation 5 বা তার বেশি recommend করে। খুব low concurrency + অনেক worker unnecessary database connection তৈরি করে connection pool exhaust করতে পারে।

Concurrency বাড়ান যখন

Worker-এর spare CPU ও RAM আছে এবং workflow compute/memory saturate করার বদলে external service-এর অপেক্ষায় থাকে।

Worker যোগ করুন যখন

এক worker process bottleneck হয় এবং database, Redis ও infrastructure-এর বেশি parallel execution capacity আছে।

Concurrency কমান যখন

Individual workflow memory-heavy বা CPU-heavy এবং parallel job contention, OOM pressure বা unstable execution time তৈরি করে।

PostgreSQL monitor করুন

বেশি worker ও concurrency database activity বাড়ায়। Database capacity ছাড়া execution capacity scale করলে bottleneck remove না হয়ে অন্য জায়গায় যেতে পারে।

কোন concurrency limit আসলে apply করে জানুন। Worker start করা যায় n8n worker --concurrency=5, অথবা Compose service-এর equivalent worker command দিয়ে। যদি N8N_CONCURRENCY_PRODUCTION_LIMIT explicitly এমন value-এ set করা হয় যা -1, তাহলে queue mode-এ সেটি precedence পায়; অন্যথায় n8n worker-এর --concurrency value বা default 10 ব্যবহার করে। Worker count-কে nominal default দিয়ে multiply করে guaranteed throughput বলবেন না: actual capacity job duration, CPU, memory, external API ও PostgreSQL connection-এর উপর নির্ভর করে।

WEBHOOKS

Queue mode execution handoff latency যোগ করতে পারে

Main বা webhook process HTTP request receive করে, কিন্তু worker workflow execution করে। Redis-এর মাধ্যমে handoff কিছু overhead যোগ করে। Latency-sensitive webhook-এর জন্য বেশি worker automatically সব request দ্রুত করবে ধরে না নিয়ে end-to-end response time measure করুন।

ReceiveMain/webhook process request accept করে।
QueueExecution Redis-এ handoff হয়।
ExecuteAvailable worker workflow চালায়।
Respondদরকার হলে result queue path দিয়ে relay back হয়।

Webhook traffic সঠিক process-এ route করুন। Dedicated n8n webhook processor reverse proxy বা load balancer-এর পিছনে থাকলে production path route করুন /webhook/* এবং /webhook-waiting/* webhook processor-এ; রাখুন /webhook-test/*, editor ও API request main-এ। Added workload consciously accept না করলে main-কে production webhook load-balancing pool-এ রাখবেন না। Respond to Webhook workflow worker finish করে response দেওয়া পর্যন্ত client অপেক্ষা করাতে পারে, তাই queue mode instant HTTP response বা zero timeout-এর promise নয়। Traffic switch করার আগে actual external callback ও response behavior test করুন।

BINARY DATA

Shared storage উপেক্ষা করবেন না

Filesystem limitation

Queue mode does not support filesystem binary-data storage as the shared persistence model for distributed workers.

External binary storage

When workflows must persist binary data across distributed workers, use a storage design that every required instance can access, such as supported external object storage.

Large webhook responses

Webhook responses from workers travel back toward the receiving process. Large response bodies can increase Redis memory pressure and require deliberate response-storage configuration.

Plan before distributing workers

A workload that depends heavily on local files must be redesigned for shared persistence before workers are spread across machines.

Large webhook response boundary. Current n8n documentation gives N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX a default of 64 MiB for a worker's response sent back through the queue. Redis can hold several copies in flight, so budget roughly 1.5 times the response size in Redis memory per concurrent large response. Without offloading, an oversized response fails instead of becoming magically faster by adding workers.

Version and license limits. From n8n 2.34.0, workers can use N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true to offload oversized webhook response bodies to readable shared binary storage, but first upgrade every main and webhook processor to 2.34.0 or later. The selected N8N_DEFAULT_BINARY_DATA_MODE must actually store data and be readable by every participating process. External S3 and Azure binary storage require a valid self-hosted Business or Enterprise license; do not assume Community Edition can enable them. The database binary mode can offload an oversized response without paid external storage, but the main instance loads the whole stored body into memory and database storage has its own file-size limit. For response-body offload specifically, n8n also describes a shared filesystem option when every instance mounts the same disk, but explicitly does not recommend that arrangement. Do not mistake this special offload path for support of filesystem-based persistent binary data in a distributed queue-mode deployment. Check your edition, version and storage configuration before enabling offload.

MONITORING

Know whether the queue is helping

Queue depth

A queue that grows faster than workers drain it indicates insufficient execution capacity or a downstream bottleneck.

Worker CPU & RAM

Measure saturation and memory peaks per worker. Idle workers with a growing queue point to another constraint.

Execution latency

Track the delay between an execution being created and actually starting, not only the workflow runtime itself.

Health checks

Worker health endpoints can report whether a worker is alive and whether its database and Redis connections are ready.

Verify execution on a worker, not just a green container. With a correctly configured Compose stack, check docker compose ps এবং docker compose logs --tail=100 n8n-worker (replace the service name if different). Run a harmless published production workflow using a scheduled trigger or test webhook, then match its execution in n8n's Executions view to actual worker processing in the worker logs. An editor that opens successfully, a running Redis container or a queued execution alone does না prove a worker has performed the job.

Check dependencies and readiness. With default example service names, docker compose exec -T redis redis-cli ping should receive PONG when Redis authentication permits it, and docker compose exec -T postgres pg_isready -U n8n -d n8n checks PostgreSQL readiness (adapt credentials and service names). Enable QUEUE_HEALTH_CHECK_ACTIVE=true on a worker when you need its private /healthz এবং /healthz/readiness endpoints; the readiness endpoint checks Redis/database connectivity. Do not expose those worker endpoints publicly just to monitor them.

Manual runs are a different test. By default OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, so manually running a workflow in the editor can execute on main even when queue mode is correctly configured. Set it to true only if you intend to send manual executions to workers and have checked the change in a staging environment. Queue-mode workers are also distinct from n8n external task runners, which have separate configuration requirements for Code-node execution.

HIGH AVAILABILITY BOUNDARY

Queue mode scales executions, but it does not automatically make the main process highly available

Share the encryption key

Every worker must use the same N8N_ENCRYPTION_KEY as the main instance so workers can decrypt credentials required by workflow executions.

Keep versions aligned

Main, webhook and worker processes should run the same n8n version. Mixed versions can create incompatible behavior during rolling changes.

Webhook processors are a separate scaling layer

When incoming webhook volume becomes the bottleneck, dedicated webhook processors can sit behind a load balancer while workers handle execution. Do not add this layer unless measured request volume justifies it.

Multi-main is a different feature

Running multiple main processes for high availability is not the same as ordinary queue mode. n8n currently documents multi-main as a self-hosted Enterprise feature with additional load-balancer and session requirements.

FAQ

n8n queue mode: common questions

Does n8n queue mode require Redis?

Yes. Redis is the message broker that coordinates pending executions between the main instance and workers.

Can queue mode use SQLite?

No for the distributed queue-mode architecture. Main and workers need shared database access, and n8n documents PostgreSQL as the database for this setup.

How many workers should I run?

There is no universal count. Start from measured concurrency and worker utilization, then add capacity while monitoring PostgreSQL, Redis, CPU, RAM and queue depth.

What is n8n worker concurrency?

It is the number of jobs a worker may process in parallel. The current default is 10, and n8n recommends worker concurrency of 5 or higher rather than creating many low-concurrency workers.

Should I enable queue mode on a small VPS?

Only when the workload justifies it. A small deployment that runs comfortably as one instance is usually simpler to operate without Redis and separate workers.
