QUICK CHECKLIST

n8n backup-এ কী সুরক্ষিত থাকা উচিত

Database

PostgreSQL database বা instance ব্যবহৃত SQLite database file-এর backup নিন। Database-এ workflow, credential এবং execution data-র মতো core n8n state থাকে।

Encryption key

ঠিক একই n8n encryption key আলাদা ও নিরাপদভাবে সংরক্ষণ করুন। Restored encrypted credential একই key-এর উপর নির্ভর করে।

Persistent file

Persistent n8n data directory এবং deployment যে mounted file, binary-data storage বা workflow asset-এর উপর নির্ভর করে সেগুলো অন্তর্ভুক্ত করুন।

Deployment configuration

Stack rebuild করতে দরকারি Compose/configuration file এবং non-secret configuration সংরক্ষণ করুন। Secret যথাযথ access control দিয়ে সুরক্ষিত রাখুন।

দুই BACKUP LEVEL

Logical export বনাম complete disaster recovery

Workflow & credential export

n8n CLI export migration, versioned workflow copy এবং selective restoration-এর জন্য উপকারী। Credential encrypted form-এ export করে matching encryption key দিয়ে পরে import করা যায়। একটি workflow recover করতে workflow editor-এর three-dot menu থেকে JSON Download করুন, তারপর নতুন review workflow বা isolated instance-এ Import from File করুন। Live workflow replace করার আগে credential, workflow ID এবং node parameter check করুন: workflow JSON restore করলে পুরো server restore হয় না।

Entity export

CLI supported database type-এর মধ্যে data move করতে database entity export করতে পারে। Execution-history table optional, কারণ এগুলো খুব বড় হতে পারে।

Full instance recovery

Dead-server scenario-তে actual database, encryption key, persistent data এবং deployment dependency সুরক্ষিত রাখুন। Workflow JSON export পুরো instance reconstruct করবে—এমন ধরে নেবেন না।

Provider snapshot

VPS snapshot additional recovery layer হিসেবে উপকারী, তবে এটি একমাত্র copy হওয়া উচিত নয় এবং independently verified application/database backup-এর বিকল্প নয়।

DATABASE

Database consistentভাবে backup নিন

PostgreSQL

Consistent PostgreSQL backup method ব্যবহার করুন এবং backup VPS থেকে দূরে রাখুন। একই failed disk-এ database copy disaster recovery নয়।

SQLite

Deployment SQLite ব্যবহার করলে persistent n8n data directory-এর database file সুরক্ষিত রাখুন। Database actively modify হওয়ার সময় unsafe state-এ copy করবেন না।

Execution history

Historical execution data recovery objective-এর অংশ কিনা ঠিক করুন। এতে backup অনেক বড় হতে পারে, তাই retention ও compliance requirement অনুযায়ী সিদ্ধান্ত নিন।

Database version

Source deployment-এর database engine ও version record করুন যাতে compatible recovery environment প্রস্তুত করা যায়।

Docker Compose VPS-এ PostgreSQL। PostgreSQL service-এর নাম যদি postgres এবং database/user দুটোই যদি n8n, তাহলে নিচের command host-এ consistent PostgreSQL custom-format dump তৈরি করে। চালানোর আগে actual Compose file check করুন এবং database credential ও service name adjust করুন। pg_dump PostgreSQL চলার সময় logically consistent snapshot তৈরি করতে পারে; এটি না আলাদা .n8n user folder বা external binary data backup করে না।

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Archive-list check স্পষ্ট format problem ধরতে পারে, কিন্তু data restore করা যাবে তা প্রমাণ করে না। Encrypted copy off-server রাখুন এবং restore rehearsal করুন। Database-specific option-এর জন্য official PostgreSQL pg_dump documentation ব্যবহার করুন।

Docker-এ SQLite। Default SQLite deployment-এ database.sqlite এবং generated encryption-key config persistent .n8n folder-এর মধ্যে থাকে (সাধারণত mount হয় /home/node/.n8n)। SQLite-এর simple live copy-কে consistent ভাববেন না। Folder copy করার আগে n8n ও অন্য database writer বন্ধ করুন, অথবা interruption সম্ভব না হলে SQLite-এর supported online backup mechanism ব্যবহার করুন:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

এগুলো দেখানো service ও path-এর illustrative command, universal volume layout নয়। Copied folder শুরুতে একই VPS-এ থাকে; সেটি off-server transfer ও protect করুন। Queue worker বা অন্য writer থাকলে সেগুলোকেও quiesce করুন এবং actual deployment design follow করুন। n8n-এর current full-backup guidance SQLite consistency requirement document করে।

Default SQLite folder clean target-এ restore করা: প্রথমে n8n service এবং সব database writer বন্ধ করুন। Compatible n8n service container ও destination volume তৈরি হলে backed-up .n8n content ফিরিয়ে একই persistent directory-তে copy করুন। এতে target file overwrite হবে, তাই দরকারি data থাকা instance-এ এটি চালাবেন না:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker stopped container-এ copy করতে পারে, কিন্তু destination ownership original থেকে আলাদা হতে পারে; start করার আগে নিশ্চিত করুন restored configuration ও database file n8n process দ্বারা readable/writable। Actual Compose configuration আলাদা path বা bind mount ব্যবহার করলে copy accordingly adapt করুন। Docker Compose copy reference। Separate PostgreSQL database ব্যবহার করা deployment-এ শুধু n8n folder restore যথেষ্ট নয়।

CRITICAL SECRET

Encryption key recovery-এর অংশ

n8n stored credential instance encryption key দিয়ে encrypt করে। Matching key ছাড়া database বা encrypted credential export restore করলে workflow saved credential ব্যবহার করতে নাও পারে।

N8N_ENCRYPTION_KEY set করলে ঠিক সেই secret restore করুন। না করলে generated key persistent .n8n/config file-এ থাকে: backup বা rebuild-এর সময় config protect করুন। Recovery key VPS-এর বাইরে নিরাপদে রাখুন। Queue mode-এ সব main ও worker process একই key ব্যবহার করবে।

করুনProduction-এ ব্যবহৃত exact key-এর protected copy রাখুন।
করুনCredential test করার আগে verify করুন recovery environment সেই key ব্যবহার করছে।
করবেন নাServer rebuild-এর পর newly generated key-এর উপর নির্ভর করবেন না।
করবেন নাKey public repository-তে commit করবেন না বা unprotected backup-এর পাশে রাখবেন না।

FILES & BINARY DATA

Database backup সব workflow dependency cover নাও করতে পারে

Persistent .n8n data

Actual .n8n user folder locate ও preserve করুন, শুধু container image নয়। Typical Docker deployment-এ এটি /home/node/.n8n-এ mounted থাকে; Docker-এর বাইরে default ~/.n8n। N8N_USER_FOLDER configured হলে n8n specified parent directory-এর মধ্যে .n8n তৈরি করে। Config key এবং installation ব্যবহৃত local SQLite, binary বা filesystem execution data অন্তর্ভুক্ত করুন।

Mounted workflow file

Workflow host-mounted directory read/write করলে directory-গুলোর আলাদা backup নিন। সেগুলো ছাড়া n8n restore করলে অন্যথায় valid workflow ভাঙা থাকতে পারে।

Binary data

Storage mode identify করুন এবং সব external dependency restore করুন। Filesystem-based binary বা execution data .n8n বা custom directory-তে থাকতে পারে; S3/Azure Blob বা অন্য configured external storage-এর নিজস্ব recoverable copy ও access setting দরকার। শুধু database dump সেই file replace করতে পারে না।

Community node

Community package ও version record করুন এবং N8N_CUSTOM_EXTENSIONS-এর মাধ্যমে configured additional custom node directory backup করুন। Directory .n8n-এর বাইরে থাকতে পারে; শুধু database ও user-folder restore করলেও custom-node workflow unusable থাকতে পারে।

OFF-SERVER STRATEGY

একই VPS-এর backup শুধু local copy

Local copyQuick rollback-এর জন্য উপকারী, কিন্তু server loss, disk failure ও destructive mistake-এর ঝুঁকি থাকে।
Off-server copyকমপক্ষে একটি backup production VPS থেকে independent storage-এ রাখুন।
Versioned copyMultiple recovery point retain করুন যাতে corruption বা খারাপ change একমাত্র usable backup overwrite না করে।
Access controlBackup-এ credential, workflow logic ও sensitive business data থাকতে পারে। উপযুক্তভাবে encrypt ও restrict করুন।
MonitoringScheduled backup fail হলে বা নতুন recovery point তৈরি বন্ধ হলে alert দিন।

Schedule measurable করুন। প্রতিটি successful backup-এর timestamp, transfer completion, file size, source database version, encryption-key recovery location এবং latest successful restore test record করুন। Missing, failed বা unexpectedly empty file-এ alert দিন। Backup archive VPS-এর বাইরে পাঠানোর আগে encrypt করুন এবং recovery secret-এর access restrict করুন। Multiple dated recovery point corruption দেরিতে ধরা পড়লেও last healthy copy হারানো থেকে রক্ষা করে।

উদাহরণ হিসেবে সর্বোচ্চ ছয় ঘণ্টার change loss tolerate করতে পারলে successful six-hour backup schedule শুধু starting point, guarantee নয়: failed job ও delayed off-server replication actual loss বাড়াতে পারে। Universal 7-day বা 30-day policy ধরে না নিয়ে নিজের RPO/RTO ও data requirement অনুযায়ী retention ও restore cadence set করুন।

RESTORE ORDER

Controlled sequence-এ recover করুন

1 · প্রস্তুত করুনCompatible server, database এবং container/runtime environment provision করুন।
2 · Secret restore করুনOriginal n8n encryption key ও required deployment secret নিরাপদে configure করুন।
3 · Database restore করুনPostgreSQL বা SQLite recover করুন এবং verify করুন n8n expected data-তে connect করতে পারে।
4 · File restore করুনPersistent directory, binary data ও mounted workflow asset recover করুন।
5 · n8n start করুনExpected hostname, database ও environment configuration দিয়ে application start করুন।
6 · Validate করুনConfirm করুন user, workflow ও credential load হয়; তারপর representative workflow ও webhook path execute করুন।

PostgreSQL disaster-recovery example: একটি আলাদা clean restore target-এ যেখানে আগে থেকেই সঠিক database role এবং empty n8n database আছে, start করুন শুধু PostgreSQL। Import-এর আগে healthy হওয়া পর্যন্ত wait করুন: docker compose up -d PostgreSQL initialize হওয়ার সময় একাই return করতে পারে, তাই পরের pg_restore fail করতে পারে। Example ব্যবহার করে --wait modern Compose installation-এ এবং independently check করে pg_isready. Reliable wait-এর জন্য appropriate PostgreSQL healthcheck configure করুন, অথবা এগোনোর আগে readiness explicitly confirm করুন। এই command populated production database-এ চালাবেন না এবং database ও matching .n8n key/data restore হওয়ার আগে n8n start করবেন না।

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Destination-এ compatible PostgreSQL version, role privilege, extension এবং original n8n configuration থাকতে হবে। Restore করুন .n8n Backup mechanism ব্যবহার করে সঠিক persistent volume বা bind mount-এ, ownership ও permission preserve করে। External binary file, custom extension, Compose ও secret configuration restore করুন, তারপর compatible version-এ n8n start করে log check করুন। শুধু database restore করলে key recover হয় না: PostgreSQL deployment key রাখে .n8n/config যদি না explicitly configure করে থাকেন N8N_ENCRYPTION_KEY. pg_restore reference · n8n full-instance restore sequence.

CLI import সাধারণত workflow inactive রাখে। n8n 2.x-এ প্রতিটি imported workflow-এর published state check করুন এবং শুধু intended workflow publish করুন; self-hosted Server CLI n8n publish:workflow --id=YOUR_WORKFLOW_ID support করে। n8n চলতে থাকলে Server CLI publish/unpublish state change restart-এর পর কার্যকর হয়। Scheduled trigger/production webhook verify বা traffic switch করার আগে restart করুন।

Docker Compose-এর bulk export example: n8n service-এর নাম যদি n8n, তাহলে নিচের official CLI backup চালাতে পারেন। Output path ইচ্ছাকৃতভাবে mounted persistent .n8n directory-এর মধ্যে, কারণ container recreate হলে arbitrary directory হারাতে পারে। Confirm করুন directory n8n container user দ্বারা writable। Workflow ও credential JSON রাখুন আলাদা directory-তে—দুই ধরনের file একই directory share করলে n8n import problem document করে।

n8n 2.x draft বনাম published backup: সাধারণ --backup workflow export current draft capture করে; production-এ published version আলাদা হতে পারে। কোনো workflow-এর actual published version preserve করতে separately export করুন docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, output folder আছে ও writable নিশ্চিত করার পর। CLI historical version-ও export করতে পারে --version=VERSION_ID. এই capture full backup-এর সঙ্গে off-server রাখুন; draft JSON live published state record করে ধরে নেবেন না।

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Copied ~/n8n-recovery/cli directory secured independent backup location-এ move না করা পর্যন্ত VPS-এ থাকে। Credential export default encrypted এবং import-এ matching encryption key লাগে। ব্যবহার এড়িয়ে চলুন --decrypted শুধু strictly controlled migration ছাড়া: এটি secret plaintext-এ লেখে। Sensitive workflow logic বা credential থাকা export public GitHub repository-তে commit করবেন না। কিছু third-party GitHub credential-backup template ইচ্ছাকৃতভাবে decrypted secret export করে; private repository access restriction, encryption নয়। প্রতিটি template-এর actual export setting ও storage permission inspect করুন, off-server transfer-এর আগে secret encrypt করুন এবং unintended plaintext upload-এ exposed credential rotate করুন।

Bulk import example: Clean target-এ owner setup শেষ করুন, original encryption key দিন এবং saved backup file recovery VPS-এ available আছে নিশ্চিত করুন। নিচের command destination folder তৈরি করে এবং workflows/ এবং credentials/ subfolder host থেকে n8n container-এ copy করে; Docker volume layout আলাদা হলে path adapt করুন:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

n8n container user-এর file ownership ও access check করুন। Verified rollback ছাড়া populated production instance-এর উপর import করবেন না: workflow ও credential ID existing entry overwrite করতে পারে। তারপর run করুন:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Imported ID existing workflow বা credential replace করতে পারে; dry run-এর জন্য isolated test instance ব্যবহার করুন এবং পরে credential ও activation/publishing state check করুন। n8n 2.x-এ JSON draft restore হওয়া নিজে প্রমাণ করে না workflow published এবং scheduled trigger চালাতে পারে। Import safety: Non-multi-main n8n instance-এ আগে active cron trigger CLI import-এর পর restart না হওয়া পর্যন্ত চলতে পারে। Restored job enable করার আগে production trigger stop/isolate করুন এবং n8n restart করুন; duplicate execution নেই verify করুন। CLI export না original user, execution log, instance variable বা encryption key contain করে না। --backup set করে --all --pretty --separate, 'full instance' নয়। Source: current official n8n backup/restore guide এবং n8n CLI command reference।

GitHub বা Google Drive template থেকে bulk restore: এটি শুধু workflow JSON-এর alternative, instance database, user, encrypted credential value বা encryption key-এর জন্য নয়। API-based template চালানোর আগে n8n API ও storage permission, selected backup version ও target instance verify করুন; matching ID update ও deleted workflow recreate করে কিনা এবং workflow publishing কীভাবে handle করে দেখুন। সব template target-এ missing ID recreate করে না; automatic restore-এর উপর নির্ভর করার আগে scenario isolation-এ test করুন।

FAQ

n8n backup ও restore: সাধারণ প্রশ্ন

n8n backup-এর জন্য workflow export যথেষ্ট?

না। Workflow export useful logical copy, কিন্তু complete recovery-তে credential, matching encryption key, database state, persistent file ও binary-data storage-ও লাগতে পারে।

Database থাকলেও n8n encryption key দরকার?

হ্যাঁ, যদি database-এ stored encrypted credential usable রাখতে চান। Original key নিরাপদে preserve করুন।

PostgreSQL backup নেব, নাকি workflow ও credential export করব?

Disaster recovery-এর জন্য database ও encryption key protect করুন। Logical export instance-এর সব অংশের substitute নয়; এটি additional migration ও selective-recovery layer হিসেবে valuable।

Can a VPS snapshot be my only backup?

It is better treated as one recovery layer. Keep an independent off-server backup so a provider, account, server or snapshot failure does not remove every recovery point at once.

How do I know my backup works?

Restore it into a clean test environment, verify credentials decrypt, and run representative workflows. A successful backup job alone does not prove recoverability.

Do GitHub or Google Drive workflow backups include saved credential secrets?

Workflow-only JSON backups do not include the secret values managed by n8n's credential store or the instance encryption key. However, exported JSON can expose credential names and IDs and secrets typed directly into node parameters, such as authentication headers. Inspect and protect exported JSON before uploading or sharing it. For full recovery, back up the database and original key, or use supported encrypted credential CLI exports with a tested restore. A workflow-only GitHub or Google Drive template is not full disaster recovery.

RECOVERY OBJECTIVES

Define RPO and RTO before an incident

RPO is the maximum tolerable loss of recent changes. Measure it from the newest usable, independently stored recovery point; a scheduled six-hour job does not establish a six-hour RPO if exports or transfers failed. RTO is the maximum tolerable outage. Measure it in a clean restore drill, including retrieving secrets, restoring external files, rechecking credentials and publishing recovered workflows—not just starting a container.

RECOVERY KEY

Find the original encryption key before rebuilding

If production set N8N_ENCRYPTION_KEY, preserve that exact environment secret. If it did not, preserve the generated key in the original persistent .n8n/config. Check which source the recovered instance actually uses before importing encrypted credentials; a fresh generated key cannot decrypt credentials from the old database.
