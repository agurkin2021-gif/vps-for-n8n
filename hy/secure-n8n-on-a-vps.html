PRODUCTION ՄԻՋԱՎԱՅՐԻ ԱՆՎՏԱՆԳՈՒԹՅՈՒՆ

n8n-ի անվտանգությունը VPS-ում

n8n-ը VPS-ում անվտանգ պահելու համար n8n-ը (5678), PostgreSQL-ը (5432) և optional Redis-ը (6379) մի հրապարակեք ինտերնետում․ օգտագործեք HTTPS reverse proxy, SSH key-եր և MFA, պահպանեք encryption key-ը, authenticate արեք webhook-ները, սահմանափակեք վտանգավոր workflow հնարավորությունները և audit արեք տեղակայված instance-ը։ Editor-ը պաշտպանեք public webhook route-երից առանձին։ Միայն HTTPS-ը չի ապահովում միացված ծառայությունների անվտանգությունը։

Ընտրել VPS n8n-ի համար

Գործընկերային հղում․ գնումներից կարող ենք միջնորդավճար ստանալ։

ԱՐԱԳ ՍՏՈՒԳԱԹԵՐԹ

Անվտանգության նվազագույն հիմքը՝ մինչև հանրային հասանելիություն տալը

Սկսեք հասանելի port-երից, HTTPS-ից, ստուգված administrative access-ից, MFA-ից և պահպանված credential-ների պաշտպանությունից։ Յուրաքանչյուր մուտքային webhook authenticate արեք մինչև այն կարողանա զգայուն գործողություն գործարկել։ Access control-ները փոխելուց հետո ստուգեք, որ նախատեսված editor-ներն ու արտաքին integration-ները շարունակում են աշխատել, ապա գործարկեք n8n security audit-ը։

Միայն HTTPS

n8n-ը տեղադրեք ճիշտ կարգավորված TLS reverse proxy-ի հետևում և editor-ի ու webhook-ների համար հետևողականորեն օգտագործեք public HTTPS URL-ը։

Նվազագույն բաց port-եր

Բացեք միայն public traffic-ի համար անհրաժեշտ port-երը։ PostgreSQL-ը, Redis-ը և application-ի ներքին port-երը մի հրապարակեք ինտերնետում։

Ամրացրեք SSH-ը

Օգտագործեք key-based administration, սահմանափակեք մուտք գործելու իրավունք ունեցողներին և օպերացիոն համակարգը պահեք թարմացված։

Պաշտպանեք credential-ները

n8n encryption key-ը պահեք անփոփոխ և գաղտնի։ Environment file-երը, database access-ը և backup copy-ները դիտարկեք որպես զգայուն ակտիվներ։

ՑԱՆՑԻ ԱՐՏԱՔԻՆ ՍԱՀՄԱՆ

Reverse proxy, HTTPS և վստահելի header-ներ

TLS termination

HTTPS-ը terminate անելու համար օգտագործեք reverse proxy, օրինակ՝ Nginx, Caddy կամ Traefik։ Plain HTTP-ը redirect արեք և n8n application port-ը ուղղակիորեն մի բացեք, երբ նախատեսված մուտքի կետը proxy-ն է։

Proxy-ի կարգավորում

Երբ n8n-ն աշխատում է reverse proxy-ի հետևում, ճիշտ կարգավորեք proxy hop count-ը և փոխանցեք այն forwarded header-ները, որոնք n8n-ին անհրաժեշտ են սկզբնական client request-ը վերականգնելու համար։

Անվտանգ cookie-ներ

Editor-ը մատուցեք HTTPS-ով, որպեսզի authentication cookie-ները մնան անվտանգ։ Խափանված TLS կարգավորումը մի շրջանցեք cookie-ների անվտանգությունը թուլացնելով։

Webhook URL

Public webhook URL-ը սահմանեք արտաքինից հասանելի HTTPS hostname-ի վրա, որպեսզի ստեղծվող webhook endpoint-ները չհղվեն ներքին container-ի կամ HTTP հասցեի վրա։

Editor-ը պահեք private՝ առանց webhook-ները խափանելու։ Հնարավորության դեպքում management access-ը սահմանափակեք VPN-ով, trusted-IP policy-ով կամ authenticated proxy-ով։ Public webhook receiver-ներն ու OAuth callback route-երը կարող են պետք լինել հասանելի թողնել․ proxy rule-ը պարտադրելուց առաջ փորձարկեք և՛ վստահելի editor-ի մուտքը, և՛ իրական արտաքին callback-ը։ Client address header-ները փոխանցեք միայն վստահելի proxy-ներից, ոչ թե կամայական request header-ներից։

Authenticate արեք webhook կանչողներին․ Webhook node-ում None-ի փոխարեն ընտրեք Basic, Header կամ JWT authentication, երբ ուղարկողը դա աջակցում է։ Անհրաժեշտության դեպքում օգտագործեք նաև IP(s) Allowlist տարբերակը, իսկ signed request աջակցող integration-ների դեպքում ստուգեք provider signature-ները։ Դժվար գուշակվող URL-ը բավարար authentication չէ։ Անհրաժեշտության դեպքում proxy-ում կիրառեք rate limit-եր և համոզվեք, որ օրինական burst-երը չեն արգելափակվում։ Webhook authentication-ի պաշտոնական տարբերակները։

VPS-Ի ԱՄՐԱՑՈՒՄ

Նվազեցրեք սերվերի attack surface-ը

Firewall

Չնախաձեռնված inbound traffic-ի համար օգտագործեք default-deny և թույլատրեք միայն այն ծառայությունները, որոնք պետք է հասանելի լինեն։ Database-ի և Redis-ի port-երը սովորաբար պետք է գտնվեն private/local ցանցերում։

SSH

Password-ների փոխարեն նախընտրեք SSH key-եր, անջատեք ավելորդ login path-երը և սահմանափակեք administrative access-ը։ Root-ին համարժեք access-ը պետք է խիստ վերահսկվի։

OS update-ներ

Թարմացրեք Linux host-ը և container runtime-ը։ Application hardening-ը չի կարող փոխհատուցել բաց կամ հնացած օպերացիոն համակարգը։

Container-ների հասանելիություն

Publish արեք միայն այն port-երը, որոնք host access են պահանջում։ Ներքին ծառայությունները պետք է հաղորդակցվեն private Docker ցանցերով, ոչ թե public interface-ներով։

Firewall-ի կամ SSH-ի կարգավորումները փոխելուց առաջ ստուգեք․ listening port-երը՝ sudo ss -lntp հրամանով, Docker publishing-ը՝ docker compose ps հրամանով project directory-ից, իսկ host firewall policy-ն՝ sudo ufw status verbose հրամանով, եթե օգտագործվում է UFW։ Password access-ը անջատելուց առաջ առանձին session-ում ստուգեք ձեր իրական SSH port-ը և key-ով հաջող login-ը։ Published Docker port-երը կարող են շրջանցել UFW rule-երը․ միայն firewall status էջը չի ապացուցում, որ 5678 port-ը private է։ Ստուգեք իրական արտաքին հասանելիությունը։ Հաշվի առեք Docker/UFW-ի այս սահմանափակումը։

Ստուգեք Ubuntu-ի ավտոմատ security update-ները՝ դրանց աշխատանքը պարզապես ենթադրելու փոխարեն․ ստուգեք apt-config dump APT::Periodic::Unattended-Upgrade արժեքը և /var/log/unattended-upgrades/unattended-upgrades.log log-ը։ Եթե unattended security upgrade-ներն անջատված են, sudo dpkg-reconfigure unattended-upgrades հրամանը տրամադրում է աջակցվող configuration dialog։ Աշխատող VPS-ում դա միացնելուց առաջ ստուգեք reboot-ի և service restart-ի վարքը։ Ubuntu APT update-ները չեն ավտոմատ թարմացնում n8n Docker image-ը կամ բոլոր third-party software repository-ները։ Ubuntu-ի automatic update-ների պաշտոնական փաստաթղթերը։

Optional SSH brute-force monitoring․ Fail2Ban-ը կարող է հայտնաբերել կրկնվող անհաջող SSH login-ները։ Եթե այն տեղադրված և SSH-ի համար կարգավորված է, jail-ը ստուգեք sudo fail2ban-client status sshd հրամանով և համոզվեք, որ այն կարդում է ձեր իրական SSH authentication log-ը կամ journal-ը և համապատասխանում է կարգավորված port-ին։ Սա լրացնում է SSH key-երն ու network restriction-ները, բայց չի փոխարինում դրանց։ Մի պատճենեք ֆիքսված SSH port կամ ban rule՝ առանց նախ առկա access-ը ստուգելու։ Ubuntu SSH hardening-ի պաշտոնական ուղեցույցը։

ՏՎՅԱԼՆԵՐԻ ԲԱԶԱ & REDIS

Backend ծառայությունները պահեք private

Սովորական Docker Compose setup-ում PostgreSQL-ը և queue mode Redis-ը համապատասխան container-ների համար պետք է հասանելի լինեն private networking-ով, ոչ թե host-ում published port-երով։ docker compose ps հրամանով ստուգեք, որ 5432 և 6379 port-երը public չեն հրապարակված, և առանձին ստուգեք VPS/cloud firewall exposure-ը։ Network policy-ները չեն փոխարինում least-privilege database credential-ներին։

PostgreSQLԿապեք այն private interface-ի կամ container network-ի հետ, եթե remote access-ը հստակ անհրաժեշտ և առանձին պաշտպանված չէ։
RedisQueue mode Redis-ը ենթակառուցվածք է, ոչ public endpoint։ Network access-ը սահմանափակեք այն n8n բաղադրիչներով, որոնց դա անհրաժեշտ է։
Credential-ներՕգտագործեք առանձին database credential-ներ միայն application-ին անհրաժեշտ permission-ներով և պաշտպանեք դրանք source control-ից դուրս։
Տրանսպորտային պաշտպանությունԵրբ database traffic-ն անցնում է անվստահելի ցանցերով, օգտագործեք համապատասխան encrypted transport՝ application-level credential encryption-ի վրա հույս դնելու փոխարեն։

N8N ԳԱՂՏՆԻՔՆԵՐ

Պաշտպանեք encryption key-ը և credential boundary-ն

Encryption key

n8n-ը պահպանված credential-ները encrypt է անում իր encryption key-ով։ Նույն key-ը պահպանեք restart-ների և worker-ների միջև և այն պաշտպանեք սովորական application content-ից առանձին։

Environment գաղտնիքներ

Password-ներ, token-ներ կամ encryption key-ը մի commit արեք public repository-ում։ Սահմանափակեք access-ը environment file-երին և deployment secret-ներին։

Օգտատերերի access

Editor access տվեք միայն վստահելի օգտատերերին։ Workflow-ները կարող են միանալ զգայուն համակարգերին, մշակել secret-ներ կամ գործարկել հզոր node-եր։

Credential-ի scope

Հնարավորության դեպքում օգտագործեք նեղ scope-ով service account-ներ և API token-ներ։ Compromised workflow-ը չպետք է ավտոմատ ստանա լայն access՝ կապ չունեցող համակարգերին։

Ստուգման ենթակա n8n configuration․ N8N_BLOCK_ENV_ACCESS_IN_NODE=true արգելում է Code node-ին և expression-ներին հասնել environment value-ներին, իսկ N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true settings file-ի համար պահանջում է միայն owner-ի permission-ներ։ N8N_ENCRYPTION_KEY-ը պահեք մշտական և ապահով backup-ով․ n8n-ը առաջին startup-ի ժամանակ կարող է random key ստեղծել, բայց այն կորցնելը կարող է առկա encrypted credential-ները անօգտագործելի դարձնել։ Production encryption key-ը մի փոխարինեք պատահականորեն․ օգտագործեք պաշտոնապես աջակցվող rotation procedure։ Environment access-ի արգելափակումը կարող է խափանել գործող integration-ները, ուստի production փոփոխություններից առաջ փորձարկեք։ n8n security variable-ների պաշտոնական սահմանումները։

WORKFLOW ՌԻՍԿԵՐ

Node-երը կարող են ընդլայնել անվտանգության սահմանը

Self-hosting-ը workflow-ներին զգալի հնարավորություններ է տալիս։ Code execution-ը, shell access-ը, կամայական HTTP request-ները և third-party community node-երը կարող են մեծացնել ռիսկը։ Անջատեք չօգտագործվող functionality-ն և գործարկելուց առաջ ստուգեք անվստահելի workflow import-ները։

Օգտագործեք ճշգրիտ աջակցվող control-ները․ NODES_EXCLUDE-ը կարգավորեք անջատվող node-երի JSON array-ով, օրինակ՝ n8n-nodes-base.executeCommand և n8n-nodes-base.readWriteFile, եթե դրանք չեն օգտագործվում։ Որոշ high-risk node-եր նոր տարբերակներում արդեն default-ով արգելափակված են․ փոփոխելուց առաջ ստուգեք իրական ցանկը։ Node exclusion-ների պաշտոնական փաստաթղթերը։

n8n 2.12.0-ից սկսած՝ N8N_SSRF_PROTECTION_ENABLED=true միացնում է outbound HTTP request-ների ստուգումները դեպի internal, loopback և metadata address range-եր։ Օրինական internal API workflow-ները կարող են դադարել աշխատել․ անհրաժեշտության դեպքում allowlist արեք միայն ձեր վերահսկողության տակ գտնվող destination-ները։ Network segmentation-ը պահեք որպես հիմնական պաշտպանություն։ Code node-ի isolation-ի համար ուսումնասիրեք external task runner-ները։ SSRF protection · Task-runner isolation։

Community node-երՏեղադրեք միայն վստահելի package-ներ․ դրանք գործարկվում են ձեր n8n environment-ի ներսում։
Վտանգավոր node-երԲացառեք այն node-երը, որոնք deployment-ին պետք չեն, երբ դրանց հնարավորությունները գերազանցում են նախատեսված workflow boundary-ն։
SSRFՕգտագործեք n8n-ի SSRF protection-ը և network control-ները այնտեղ, որտեղ workflow-ները չպետք է կարողանան հասնել internal կամ metadata endpoint-ներին։
Workflow import-ներActivation-ից առաջ ստուգեք imported workflow-ները, credential-ները, expression-ները և executable step-երը։

AUDIT & ԹԱՐՄԱՑՈՒՄՆԵՐ

Անվտանգությունը շարունակական գործառնական գործընթաց է

Գործարկեք n8n security audit

Պաշտոնական CLI command-ն է n8n audit։ Եթե ձեր Docker Compose service-ի անունը n8n է, այդ deployment directory-ում գործարկեք docker compose exec -T n8n n8n audit։ Ստուգեք հինգ category-ն՝ unused credential-ներ, risky SQL query pattern-ներ, file-system access, risky/community node-եր և instance risk-եր՝ ներառյալ չպաշտպանված webhook-ներն ու հնացած release-ները։ Ուղղեք համապատասխան finding-ները և նորից գործարկեք audit-ը։ Սա penetration test չէ։ Audit-ի պաշտոնական ուղեցույցը։

Թարմացրեք վերահսկված կերպով

n8n-ը պահեք բավականաչափ արդիական՝ security fix-երը ստանալու համար։ Internet-facing instance-ը մշտապես հնացած թողնելու փոխարեն ստուգեք release note-երը և փորձարկեք կարևոր upgrade-ները։

Վերահսկեք authentication-ը

Հետևեք անսպասելի access pattern-ներին, workflow փոփոխություններին և failure-ներին։ Editor UI-ի access-ը լրացուցիչ սահմանափակեք, երբ ձեր operating model-ը լայն public reachability չի պահանջում։

Պատրաստեք rollback և recovery

Կարևոր upgrade-ներից առաջ ստեղծեք վերականգնելի backup-ներ։ Backup scope-ի և restoration-ի մանրամասները ներկայացված են առանձին recovery ուղեցույցում։

Նվազեցրեք զգայուն execution history-ն․ հաջող run-երը կարող են պահպանել հաճախորդների տվյալներ և token-ներ։ Անհրաժեշտության դեպքում սահմանեք EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, պահեք EXECUTIONS_DATA_PRUNE=true, իսկ EXECUTIONS_DATA_MAX_AGE-ը սահմանեք ժամերով, օրինակ՝ 168 (յոթ օր)։ Սրանք կարգավորվող օրինակներ են, ոչ իրավական retention rule-եր։ Ավելի քիչ history նշանակում է ավելի քիչ debugging և forensic data․ running, waiting կամ annotated execution-ները կարող են նույն կերպ չմաքրվել։ Execution retention-ի պաշտոնական փաստաթղթերը։

Կասկածվող compromise․ սահմանափակեք վնասակար access-ը՝ առանց ապացույցները ոչնչացնելու, ստուգեք proxy-ի, host-ի և n8n-ի activity-ն ու փոփոխված workflow-ները, revoke կամ rotate արեք հնարավոր արտահոսած upstream credential-ները, վերացրեք պատճառը և անհրաժեշտության դեպքում restore արեք միայն փորձարկված վերականգնելի backup-ներից։ Ստուգեք ազդված webhook URL-ները, editor account-ները և միացված ծառայությունները․ մի ենթադրեք, որ HTTPS-ը, snapshot-ները կամ VPS-ի գնումը ներառում են incident-response ծառայություններ։

DEPLOYMENT-Ի ՀԵՐԹԱԿԱՆՈՒԹՅՈՒՆ

Production workflow-ները ակտիվացնելուց առաջ ապահովեք stack-ի անվտանգությունը

6Գործարկեք security audit, ստուգեք backup-ները և միայն դրանից հետո հրապարակեք production workflow-ները։

ACCOUNT & PLATFORM CONTROL-ՆԵՐ

Պաշտպանեք և՛ editor-ը, և՛ VPS-ը

Պահանջեք ավելի ուժեղ login պաշտպանություն

Editor account-ների համար միացրեք two-factor authentication և MFA-ն պարտադրեք n8n security policy-ներով, երբ ձեր edition-ը աջակցում է centralized policy enforcement։

Սահմանափակեք workflow խմբագրելու իրավունքը

Editor access-ը privileged access է․ workflow-ները կարող են կարդալ credential-ներ, կանչել internal system-ներ և գործարկել հզոր node-եր։ User access-ը պահեք սահմանափակ և հեռացրեք այլևս չպահանջվող account-ները։

Անջատեք չօգտագործվող հնարավորությունները

Նվազեցրեք application attack surface-ը՝ անջատելով public API-ն, երբ այն պետք չէ, և արգելափակելով high-risk node-երը կամ feature-ները, որոնք ձեր operating model-ին անհրաժեշտ չեն։

SSRF և secret control-ները կիրառեք նպատակային

Կամայական HTTP request կատարող workflow-ների համար գնահատեք n8n-ի SSRF protection-ը և secret-ները պահեք workflow code-ից, public repository-ներից և լայնորեն ընթեռնելի environment file-երից դուրս։

Սահմանափակեք չօգտագործվող management endpoint-ները․ N8N_PUBLIC_API_DISABLED=true անջատում է n8n public REST API-ն, իսկ N8N_PUBLIC_API_SWAGGERUI_DISABLED=true առանձին անջատում է նրա API playground-ը։ Դա արեք միայն այն դեպքում, երբ ձեր integration-ներին այդ feature-ները պետք չեն։ REST API-ն անջատելը չի authenticate անում workflow webhook URL-ները։ Editor օգտատերերի համար օգտագործեք MFA, իսկ centralized policy-ներ՝ միայն այնտեղ, որտեղ ձեր n8n edition-ը դրանք աջակցում է։

Պաշտոնական փաստաթղթեր՝ Public API-ի անջատում · Security policy variable-ներ · Audit command-ներ։

FAQ

n8n VPS-ի անվտանգություն․ հաճախ տրվող հարցեր

Պե՞տք է n8n port-ը բացել ուղղակիորեն։

Երբ reverse proxy-ն public entry point-ն է, հրապարակեք proxy-ն, իսկ application port-ը պահեք դրա հետևում՝ ավելորդ ծառայությունները լայնորեն հրապարակելու փոխարեն։

Պե՞տք է PostgreSQL-ը կամ Redis-ը public լինեն։

Սովորաբար՝ ոչ։ Դրանք պետք է հասանելի լինեն միայն այն համակարգերին, որոնց անհրաժեշտ են։ Public exposure-ը մեծացնում է attack surface-ը՝ առանց n8n-ի սովորական աշխատանքին օգնելու։

Ինչո՞ւ է n8n encryption key-ը կարևոր։

Այն պաշտպանում է n8n-ի պահպանած credential-ները և deployment-ի ամբողջ ընթացքում պետք է նույնը մնա։ Այն կորցնելը կարող է թույլ չտալ վերականգնված տվյալներից օգտագործելի encrypted credential-ներ ստանալ։

Community node-երը անվտանգ ե՞ն։

Դրանք n8n-ը ընդլայնում են third-party code-ով, ուստի պետք է դիտարկվեն որպես software dependency-ներ՝ իրենց supply-chain և privilege risk-երով։ Տեղադրեք միայն այն, ինչին վստահում եք և ինչն անհրաժեշտ է։

HTTPS-ը self-hosted n8n instance-ը անվտանգ դարձնո՞ւմ է։

Ոչ։ HTTPS-ը պաշտպանում է transport-ը։ Production անվտանգությունը պահանջում է նաև host hardening, access control, private backend ծառայություններ, secret-ների պաշտպանություն, անվտանգ workflow հնարավորություններ, monitoring և update-ներ։

Կարո՞ղ է n8n editor-ը private լինել, մինչ production webhook-ները շարունակում են աշխատել։

Այո։ Վստահելի reverse proxy-ն կամ VPN-ը կարող է editor/admin access-ը սահմանափակել public production webhook և OAuth callback path-երից առանձին։ Ամեն access rule-ի փոփոխությունից հետո փորձարկեք վստահելի login-ը և արտաքին webhook delivery-ն, որպեսզի պատահաբար չարգելափակեք integration-ները։

Ինչպե՞ս authenticate անել մուտքային n8n webhook-ները։

Webhook node-ում կարգավորեք Basic, Header կամ JWT authentication, երբ ուղարկողը դա աջակցում է։ Կարող եք նաև օգտագործել IP(s) Allowlist և առկայության դեպքում ստուգել provider signature-ները։ Մի վստահեք միայն secret-ի նմանվող path-ին և request-ները validate արեք մինչև դրանք զգայուն API գործողություններ գործարկեն։
