ՊԱՀՈՒՍՏԱՎՈՐՈՒՄ ԵՎ ՎԵՐԱԿԱՆԳՆՈՒՄ

n8n-ի պահուստավորում և վերականգնում

Self-hosted n8n-ը պահուստավորելու և վերականգնելու համար պաշտպանեք SQLite տվյալների բազան կամ համաձայնեցված PostgreSQL dump-ը, մշտական .n8n պանակն ու սկզբնական գաղտնագրման բանալին, տեղակայման կոնֆիգուրացիան և արտաքին binary կամ mount արված ֆայլերից յուրաքանչյուր կախվածությունը։ Կոդավորված պատճենը պահեք VPS-ից դուրս և վերականգնումը փորձարկեք առանձին instance-ում։ Ընտրովի վերականգնման համար օգտագործեք CLI-ով աշխատանքային հոսքերի և credentials-ի արտահանումը․ միայն JSON արտահանումները ամբողջական սերվերային backup չեն։

Ընտրեք VPS n8n-ի համար

Գործընկերային հղում․ գնումներից մենք կարող ենք միջնորդավճար ստանալ։

ԱՐԱԳ ՍՏՈՒԳԱԹԵՐԹ

Ինչ պետք է պաշտպանի n8n-ի backup-ը

Տվյալների բազա

Պահուստավորեք PostgreSQL տվյալների բազան կամ instance-ի օգտագործած SQLite տվյալների բազայի ֆայլը։ Տվյալների բազան պարունակում է n8n-ի հիմնական վիճակը՝ աշխատանքային հոսքեր, credentials և execution տվյալներ։

Գաղտնագրման բանալի

n8n-ի ճշգրիտ գաղտնագրման բանալին պահեք առանձին և անվտանգ։ Վերականգնված կոդավորված credentials-ը կախված են նույն բանալուց։

Մշտական ֆայլեր

Ներառեք n8n-ի մշտական տվյալների պանակը և բոլոր mount արված ֆայլերը, binary տվյալների պահեստը կամ աշխատանքային հոսքերի այն ռեսուրսները, որոնցից կախված է ձեր տեղակայումը։

Տեղակայման կոնֆիգուրացիա

Պահեք Compose/կոնֆիգուրացիայի ֆայլերը և stack-ը վերակառուցելու համար անհրաժեշտ ոչ գաղտնի կարգավորումները։ Գաղտնիքները պաշտպանեք համապատասխան հասանելիության վերահսկմամբ։

ՊԱՀՈՒՍՏԱՎՈՐՄԱՆ ԵՐԿՈՒ ՄԱԿԱՐԴԱԿ

Տրամաբանական արտահանում ընդդեմ աղետից ամբողջական վերականգնման

Աշխատանքային հոսքերի և credentials-ի արտահանում

n8n CLI արտահանումները օգտակար են միգրացիայի, աշխատանքային հոսքերի տարբերակավորված պատճենների և ընտրովի վերականգնման համար։ Credentials-ը կարելի է արտահանել կոդավորված ձևով և հետո ներմուծել համապատասխան գաղտնագրման բանալիով։ Միայն մեկ աշխատանքային հոսք վերականգնելու համար workflow editor-ի երեք կետով մենյուից ներբեռնեք դրա JSON-ը, ապա Import from File-ով ներմուծեք նոր ստուգման workflow կամ մեկուսացված instance։ Live workflow-ը փոխարինելուց առաջ ստուգեք credentials-ը, workflow ID-ները և node պարամետրերը․ workflow JSON-ի վերականգնումը չի վերականգնում ամբողջ սերվերը։

Entity-ների արտահանում

CLI-ն կարող է արտահանել տվյալների բազայի entity-ները՝ աջակցվող տվյալների բազաների տեսակների միջև տվյալները տեղափոխելու համար։ Execution history աղյուսակները կամընտիր են, քանի որ կարող են շատ մեծ լինել։

Ամբողջ instance-ի վերականգնում

Սերվերի ամբողջական կորստի սցենարի համար պաշտպանեք իրական տվյալների բազան, գաղտնագրման բանալին, մշտական տվյալներն ու տեղակայման կախվածությունները։ Մի ենթադրեք, որ workflow JSON արտահանումը վերակառուցում է ամբողջ instance-ը։

Մատակարարի snapshot

VPS snapshot-ը օգտակար է որպես վերականգնման լրացուցիչ շերտ, բայց չպետք է լինի միակ պատճենը և չպետք է փոխարինի առանձին ստուգված հավելվածի/տվյալների բազայի backup-ին։

ՏՎՅԱԼՆԵՐԻ ԲԱԶԱ

Տվյալների բազան պահուստավորեք համաձայնեցված վիճակում

PostgreSQL

Օգտագործեք PostgreSQL-ի համաձայնեցված backup մեթոդ և ստացված պատճենը պահեք VPS-ից հեռու։ Նույն խափանված սկավառակի վրա տվյալների բազայի պատճենը աղետից վերականգնում չէ։

SQLite

Եթե տեղակայումը օգտագործում է SQLite, պաշտպանեք տվյալների բազայի ֆայլը n8n-ի մշտական տվյալների պանակից։ Մի պատճենեք տվյալների բազան վտանգավոր վիճակում, երբ այն ակտիվորեն փոփոխվում է։

Execution պատմություն

Որոշեք՝ պատմական execution տվյալները մտնո՞ւմ են ձեր վերականգնման նպատակի մեջ։ Դրանք կարող են զգալիորեն մեծացնել backup-ները, ուստի ընտրությունը պետք է որոշեն retention-ի և համապատասխանության պահանջները։

Տվյալների բազայի տարբերակ

Գրանցեք սկզբնական տեղակայման տվյալների բազայի engine-ն ու տարբերակը, որպեսզի վերականգնման միջավայրը հնարավոր լինի համատեղելի ձևով պատրաստել։

PostgreSQL-ը Docker Compose VPS-ում։ Եթե PostgreSQL ծառայության անունը postgres է, իսկ տվյալների բազան և օգտատերը երկուսն էլ n8nեն, ապա հետևյալ հրամանը host-ում ստեղծում է համաձայնեցված PostgreSQL custom-format dump։ Գործարկելուց առաջ ստուգեք ձեր իրական Compose ֆայլը և համապատասխանեցրեք տվյալների բազայի credentials-ն ու ծառայությունների անունները։ pg_dump կարող է տրամաբանորեն համաձայնեցված snapshot ստեղծել PostgreSQL-ի աշխատանքի ընթացքում․ այն չի պահուստավորում առանձին .n8n user պանակը կամ արտաքին binary տվյալները։

# Docker Compose նախագծում․ համապատասխանեցրեք service, DB և user անունները
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Ստուգեք, որ archive-ը ունի ընթեռնելի object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Archive list-ի ստուգումը հայտնաբերում է ձևաչափի ակնհայտ խնդիրները, բայց չի ապացուցում, որ տվյալները հնարավոր է վերականգնել։ Կոդավորված պատճենը պահեք սերվերից դուրս և փորձնական վերականգնում կատարեք։ Տվյալների բազային հատուկ տարբերակների համար օգտագործեք PostgreSQL pg_dump-ի պաշտոնական փաստաթղթերը։

SQLite-ը Docker-ում։ Լռելյայն SQLite տեղակայման դեպքում database.sqlite և գեներացված գաղտնագրման բանալու config-ը գտնվում են մշտական .n8n պանակում (սովորաբար mount է արված /home/node/.n8n)։ SQLite-ի սովորական live պատճենը երբեք մի համարեք համաձայնեցված։ Պանակը պատճենելուց առաջ կանգնեցրեք n8n-ը և տվյալների բազա գրող մյուս process-ները, իսկ երբ ընդհատումն անհնար է՝ օգտագործեք SQLite-ի աջակցվող online backup մեխանիզմը․

# Միայն SQLite-ի և լռելյայն /home/node/.n8n mount-ի համար
# SQLite տվյալների բազան պատճենելուց առաջ կանգնեցրեք n8n-ը և մյուս գրող process-ները
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Սրանք ցուցադրական հրամաններ են նշված ծառայության և ուղու համար, ոչ համընդհանուր volume layout։ Պատճենված պանակը սկզբում դեռ նույն VPS-ում է․ տեղափոխեք և պաշտպանեք այն սերվերից դուրս։ Եթե կան queue worker-ներ կամ այլ գրող process-ներ, դրանք նույնպես կանգնեցրեք և հետևեք իրական տեղակայման կառուցվածքին։ n8n-ի ընթացիկ ամբողջական backup ուղեցույցը փաստաթղթավորում է SQLite-ի համաձայնեցվածության պահանջը։

Լռելյայն SQLite պանակի վերականգնումը մաքուր target-ում․ նախ կանգնեցրեք n8n ծառայությունն ու տվյալների բազա գրող բոլոր process-ները։ Երբ գոյություն ունեն համատեղելի n8n service container-ը և դրա նպատակային volume-ը, պատճենեք պահուստավորված .n8n բովանդակությունը կրկին նույն մշտական պանակ։ Սա վերագրում է target ֆայլերը, ուստի մի գործարկեք այն այնպիսի instance-ում, որտեղ կան պահպանելու ենթակա տվյալներ․

# Գործարկեք միայն նախատեսված ՄԱՔՈՒՐ recovery instance-ում
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Հաջորդ հրամանից ԱՌԱՋ ստուգեք ownership-ն ու permissions-ը n8n container user-ի համար
# Գործարկեք միայն այն բանից հետո, երբ վերականգնված ֆայլերը n8n-ի համար ընթեռնելի/գրելի են
docker compose start n8n
# Ստուգեք log-երը, վերականգնված credentials-ը և workflow trigger-ները

Docker-ը կարող է պատճենել կանգնեցված container-ներ, բայց նպատակային ownership-ը կարող է տարբերվել սկզբնականից։ Մեկնարկից առաջ համոզվեք, որ վերականգնված config-ն ու տվյալների բազայի ֆայլը n8n process-ի համար ընթեռնելի և գրելի են։ Եթե ձեր իրական Compose կոնֆիգուրացիան օգտագործում է այլ ուղի կամ bind mount, համապատասխանեցրեք պատճենումը։ Docker Compose copy reference։ Միայն n8n պանակի վերականգնումը բավարար չէ առանձին PostgreSQL տվյալների բազա օգտագործող տեղակայումների համար։

ԿՐԻՏԻԿԱԿԱՆ ԳԱՂՏՆԻՔ

Գաղտնագրման բանալին վերականգնման մաս է

n8n-ը պահպանված credentials-ը կոդավորում է instance-ի գաղտնագրման բանալիով։ Տվյալների բազայի կամ կոդավորված credentials-ի արտահանումը առանց համապատասխան բանալու կարող է հանգեցնել նրան, որ վերականգնված workflow-ները չկարողանան օգտագործել պահպանված credentials-ը։

Եթե սահմանել եք N8N_ENCRYPTION_KEY, վերականգնեք հենց այդ secret-ը։ Հակառակ դեպքում գեներացված բանալին պահվում է մշտական .n8n/config ֆայլում․ backup-ի կամ վերակառուցման ժամանակ պաշտպանեք այդ config-ը։ Վերականգնման բանալիները անվտանգ պահեք VPS-ից դուրս։ Queue mode-ում բոլոր main և worker process-ները պետք է օգտագործեն նույն բանալին։

ԱրեքՊահեք production-ում օգտագործվող ճշգրիտ բանալու պաշտպանված պատճենը։
ԱրեքCredentials-ը փորձարկելուց առաջ հաստատեք, որ վերականգնման միջավայրն օգտագործում է այդ բանալին։
Մի արեքՍերվերը վերակառուցելուց հետո մի ապավինեք նոր գեներացված բանալուն։
Մի արեքԲանալին մի commit արեք հանրային repository և մի պահեք անպաշտպան backup-ի կողքին։

ՖԱՅԼԵՐ ԵՎ BINARY ՏՎՅԱԼՆԵՐ

Տվյալների բազայի backup-ը կարող է չներառել workflow-ի բոլոր կախվածությունները

Մշտական .n8n տվյալներ

Գտեք և պահպանեք իրական .n8n user պանակը, ոչ միայն container image-ը։ Տիպիկ Docker տեղակայման մեջ այն mount է արված /home/node/.n8n-ում, իսկ Docker-ից դուրս լռելյայնը ~/.n8n է։ Եթե N8N_USER_FOLDER-ը կարգավորված է, n8n-ը .n8n է ստեղծում նշված parent directory-ի ներսում։ Ներառեք դրա config key-ն և տեղային SQLite, binary կամ filesystem execution տվյալները, որոնք օգտագործում է ձեր տեղադրումը։

Mount արված workflow ֆայլեր

Եթե workflow-ները կարդում կամ գրում են host-ում mount արված պանակներ, այդ պանակները պահուստավորեք առանձին։ Առանց դրանց n8n-ի վերականգնումը կարող է չաշխատող դարձնել այլապես ճիշտ workflow-ները։

Binary տվյալներ

Որոշեք storage mode-ը և վերականգնեք յուրաքանչյուր արտաքին կախվածություն։ Filesystem-ի վրա հիմնված binary կամ execution տվյալները կարող են գտնվել .n8n-ում կամ custom պանակում, իսկ S3/Azure Blob-ը կամ այլ կարգավորված արտաքին storage-ը պահանջում է իր սեփական վերականգնելի պատճենն ու access settings-ը։ Միայն database dump-ը չի կարող փոխարինել այդ ֆայլերին։

Community node-եր

Գրանցեք community package-ներն ու տարբերակները և պահուստավորեք N8N_CUSTOM_EXTENSIONS-ով կարգավորված բոլոր լրացուցիչ custom node պանակները։ Այդ պանակները կարող են գտնվել .n8n-ից դուրս․ միայն տվյալների բազայի և user-folder-ի վերականգնումը կարող է դեռ չաշխատող թողնել custom-node workflow-ները։

ՍԵՐՎԵՐԻՑ ԴՈՒՐՍ ՊԱՀՈՒՍՏԱՎՈՐՄԱՆ ՌԱԶՄԱՎԱՐՈՒԹՅՈՒՆ

Նույն VPS-ում backup-ը պարզապես տեղային պատճեն է

Տեղային պատճենՕգտակար է արագ rollback-ի համար, բայց խոցելի է սերվերի կորստի, սկավառակի խափանման և կործանարար սխալների նկատմամբ։
Սերվերից դուրս պատճենԱռնվազն մեկ backup պահեք production VPS-ից անկախ storage-ում։
Տարբերակավորված պատճեններՊահեք վերականգնման մի քանի կետ, որպեսզի վնասված տվյալները կամ սխալ փոփոխությունը չվերագրեն միակ օգտագործելի backup-ը։
Հասանելիության վերահսկումBackup-ները կարող են պարունակել credentials, workflow logic և բիզնեսի զգայուն տվյալներ։ Դրանք կոդավորեք և համապատասխան կերպով սահմանափակեք հասանելիությունը։
ՄոնիթորինգԾանուցում ստացեք, երբ պլանավորված backup-ները ձախողվում են կամ դադարում են ստեղծել վերականգնման նոր կետեր։

Backup ժամանակացույցը դարձրեք չափելի։ Գրանցեք յուրաքանչյուր հաջող backup-ի timestamp-ը, փոխանցման ավարտը, ֆայլի չափը, սկզբնական տվյալների բազայի տարբերակը, գաղտնագրման բանալու վերականգնման վայրը և վերջին հաջող restore փորձարկումը։ Ծանուցում ստացեք բացակայող, ձախողված կամ անսպասելիորեն դատարկ ֆայլերի դեպքում։ Backup archive-ները կոդավորեք մինչև VPS-ից դուրս ուղարկելը և սահմանափակեք հասանելիությունը վերականգնման secret-ներին։ Ամսաթվով մի քանի recovery point-եր պաշտպանում են այն իրավիճակից, երբ վնասվածությունը նկատվում է միայն այն բանից հետո, երբ նորագույն պատճենը վերագրել է վերջին առողջ տարբերակը։

Օրինակ՝ եթե կարող եք հանդուրժել առավելագույնը վեց ժամվա փոփոխությունների կորուստ, հաջող վեցժամյա backup ժամանակացույցը միայն մեկնարկային կետ է, ոչ երաշխիք․ ձախողված job-երն ու սերվերից դուրս ուշացած replication-ը կարող են մեծացնել իրական կորուստը։ Retention-ի և restore-ի հաճախականությունը սահմանեք ձեր սեփական RPO/RTO-ի և տվյալների պահանջների համաձայն, ոչ թե ենթադրելով համընդհանուր 7-օրյա կամ 30-օրյա քաղաքականություն։

ՎԵՐԱԿԱՆԳՆՄԱՆ ՀԵՐԹԱԿԱՆՈՒԹՅՈՒՆ

Վերականգնեք վերահսկվող հաջորդականությամբ

1 · ՊատրաստեքՊատրաստեք համատեղելի սերվեր, տվյալների բազա և container/runtime միջավայր։
2 · Վերականգնեք secret-ներըԱնվտանգ կարգավորեք n8n-ի սկզբնական գաղտնագրման բանալին և տեղակայման անհրաժեշտ secret-ները։
3 · Վերականգնեք տվյալների բազանՎերականգնեք PostgreSQL-ը կամ SQLite-ը և հաստատեք, որ n8n-ը կարող է միանալ սպասվող տվյալներին։
4 · Վերականգնեք ֆայլերըՎերականգնեք մշտական պանակները, binary տվյալները և mount արված workflow ռեսուրսները։
5 · Գործարկեք n8n-ըԳործարկեք հավելվածը սպասվող hostname-ով, տվյալների բազայով և environment կոնֆիգուրացիայով։
6 · ՍտուգեքՀաստատեք, որ օգտատերերը, workflow-ներն ու credentials-ը բեռնվում են, ապա գործարկեք ներկայացուցչական workflow-ներ և webhook ուղիներ։

PostgreSQL-ի disaster recovery օրինակ՝ առանձին, մաքուր վերականգնման target-ում որտեղ արդեն կա տվյալների բազայի ճիշտ role-ը և դատարկ n8n տվյալների բազան, գործարկեք միայն PostgreSQL-ը։ Ներմուծումից առաջ սպասեք, մինչև այն healthy լինի․ docker compose up -d հրամանը կարող է ավարտվել, երբ PostgreSQL-ը դեռ initialize է լինում, ուստի հաջորդ pg_restore կարող է ձախողվել։ Օրինակում օգտագործվում է --wait ժամանակակից Compose տեղադրման մեջ և առանձին ստուգվում է pg_isready։ Հուսալի սպասման համար կարգավորեք համապատասխան PostgreSQL healthcheck կամ շարունակելուց առաջ հստակ հաստատեք պատրաստ լինելը։ Այս հրամանը մի ուղղեք տվյալներով լցված production տվյալների բազայի վրա և n8n-ը մի գործարկեք մինչև տվյալների բազան ու դրան համապատասխան .n8n բանալին/տվյալները վերականգնված լինեն։

# ՎԵՐԱԿԱՆԳՆԵՔ ՄԻԱՅՆ ՆՈՐ, ԴԱՏԱՐԿ TARGET ՏՎՅԱԼՆԵՐԻ ԲԱԶԱՅՈՒՄ
# Համապատասխանեցրեք Postgres Compose service-ի, database-ի և user-ի անունները
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Նպատակային միջավայրը պետք է ունենա համատեղելի PostgreSQL տարբերակ, role privileges, extensions և n8n-ի սկզբնական կոնֆիգուրացիան։ Վերականգնեք .n8n իր ճիշտ persistent volume կամ bind mount-ում՝ ձեր backup մեխանիզմով, պահպանելով ownership-ն ու permissions-ը։ Վերականգնեք արտաքին binary ֆայլերը, custom extensions-ը, Compose և secrets կոնֆիգուրացիան, ապա գործարկեք n8n-ի համատեղելի տարբերակը և ստուգեք log-երը։ Միայն տվյալների բազայի վերականգնումը չի վերադարձնում բանալին․ PostgreSQL տեղակայման դեպքում բանալին պահվում է .n8n/config եթե հստակ չեք կարգավորել N8N_ENCRYPTION_KEY։ pg_restore reference · n8n-ի ամբողջական instance-ի վերականգնման հաջորդականություն։

Ընտրեք վերականգնման VPS, եթե պետք է մաքուր սերվեր

Գործընկերային հղում․ գնումներից մենք կարող ենք միջնորդավճար ստանալ։

ՎԵՐԱԿԱՆԳՆՄԱՆ ՓՈՐՁԱՐԿՈՒՄ

Backup-ը հաստատված չէ, քանի դեռ վերականգնումը չի հաջողվել

Փորձարկեք մաքուր միջավայրում

Իրական փորձարկումը պետք է ապացուցի, որ backup-ը կարող է վերակառուցել instance-ը՝ առանց production սերվերում մնացած, չհայտարարված ֆայլերից կախված լինելու։

Ստուգեք credentials-ը

Workflow-ը բացելը բավարար չէ։ Հաստատեք, որ վերականգնված կոդավորված credentials-ը իրականում հաջողությամբ decrypt և authenticate են լինում։

Գործարկեք ներկայացուցչական workflow-ներ

Փորձարկեք workflow-ներ, որոնք կախված են webhook-ներից, արտաքին API-ներից, mount արված ֆայլերից և community node-երից, ոչ միայն պարզ ավտոմատացում։

Չափեք վերականգնման ժամանակը

Գրանցեք, թե restore-ը որքան ժամանակ է տևում և ձեռքով ինչ քայլեր են մնում։ Սա ենթադրյալ backup-ը վերածում է գործնական վերականգնման ընթացակարգի։

Ստուգված restore փորձարկում՝ SQLite և PostgreSQL

Փորձարկման միջավայր՝ n8n 2.42.5 մեկուսացված Docker container-ներում, ժամանակավոր GitHub Actions runner-ի վրա՝ օգտագործելով սինթետիկ երկու-node workflow։ Այս ստուգումները կատարվել են 2026 թվականի հոկտեմբերի 8-ին՝ ոչ հաճախորդի կամ production n8n սերվերի վրա։

SQLite՝ PASSՆերմուծվել է փորձնական workflow, արտահանվել, կանգնեցվել են բոլոր գրող process-ները, archive է արվել SQLite-ի վրա հիմնված մշտական .n8n պանակն ու դրա գեներացված գաղտնագրման բանալին, վերականգնվել մաքուր volume-ում, գործարկվել է n8n-ը, այնուհետև վերականգնված workflow-ը կրկին արտահանվել և գործարկվել է։
PostgreSQL՝ PASSՆերմուծվել է նույն փորձնական workflow-ը, ստեղծվել և ստուգվել է custom-format pg_dumpև այն վերականգնվել է՝ օգտագործելով pg_restore նոր դատարկ PostgreSQL տվյալների բազայում, ապա վերականգնվել է առանձին .n8n պանակը, այնուհետև վերականգնված workflow-ը կրկին արտահանվել և գործարկվել է։
Ինչ է հաստատում PASS-ըՓորձարկված backup ուղիները պահպանել են այս workflow-ը, դրա երկու node-երը և դրանց կապերը ու թույլ տվել գործարկում վերականգնումից հետո։ Սրանք վերարտադրելի ֆունկցիոնալ smoke test-եր են, ոչ ծանրաբեռնվածության benchmark-ներ։
Ինչը չի փորձարկվելԻրական credentials-ի decrypt և authentication-ը, production webhook-ները, queue-mode worker-ներն ու Redis-ը, S3/Azure binary storage-ը, custom node-երը, user/project հասանելիությունը կամ live production instance-ի վերականգնումը չեն փորձարկվել։ Առանձին փորձարկում անցկացրեք յուրաքանչյուր կախվածության համար, որն իրականում օգտագործում եք։

Ինչպես վերարտադրել՝ օգտագործեք ժամանակավոր n8n տեղադրում, ստեղծեք անվնաս երկու-node workflow, կատարեք համապատասխան տվյալների բազայի և persistent-folder backup-ը, վերականգնեք մաքուր volume-ում կամ տվյալների բազայում, ապա ստուգեք վերականգնված workflow-ի node-երը, կապերը և իրական execution-ը։ Production համակարգում նաև ստուգեք կոդավորված credentials-ը, webhook-ներն ու արտաքին ֆայլերը՝ մինչև disaster recovery-ն հաստատված համարելը։

Restore փորձարկման ընդունման ստուգաթերթ՝ օգտագործեք մեկուսացված domain/environment, ստուգեք, որ օգտատերերն ու workflow-ները առկա են, գոյություն ունեցող մեկ կոդավորված credential-ը authenticate է լինում առանց նորից մուտքագրելու, production webhook-ը կանչում է նախատեսված վերականգնված workflow-ը, mount արված ֆայլերն ու binary attachment-ները մնում են ընթեռնելի, և պահանջվող community node-երի ինտեգրացիաները բեռնվում են։ Հաստատեք backup-ի տարիքը, չափված downtime-ը և սերվերից դուրս հասանելիությունը։ Եթե որևէ էական ստուգում ձախողվի, այդ recovery point-ը նշեք որպես չստուգված ՝ backup-ը ամբողջական հայտարարվելու փոխարեն։

CLI BACKUP-Ի ՍԱՀՄԱՆԱՓԱԿՈՒՄՆԵՐ

Հստակ իմացեք, թե workflow-ի և credentials-ի արտահանումները ինչը չեն վերականգնում

CLI արտահանումները ամբողջ instance-ի backup չեն

Workflow և credentials backup արտահանումները չեն ներառում օգտատերերին ու role-երը, execution history-ն ու log-երը, variable-ները կամ instance-ի կարգավորումները, օրինակ՝ գաղտնագրման բանալին։

Թարմ instance-ի restore-ին owner է պետք

Մաքուր instance-ում credentials ներմուծելուց առաջ ավարտեք owner setup-ը։ Multi-user կամ project restore-ների համար կարող է նաև պետք լինել ճիշտ user կամ project assignment։

Ներմուծված ID-ները կարող են վերագրել գոյություն ունեցող տարրերը

Workflow և credential արտահանումները պահպանում են իրենց սկզբնական ID-ները։ Ներմուծումը instance-ի մեջ, որտեղ նույն ID-ներն արդեն կան, կարող է փոխարինել այդ գոյություն ունեցող տարրերը։

Ներմուծված workflow-ները publish արեք գիտակցված

CLI ներմուծումները սովորաբար workflow-ները թողնում են inactive։ n8n 2.x-ում ստուգեք յուրաքանչյուր ներմուծված workflow-ի published վիճակը և publish արեք միայն այն workflow-ները, որոնք նախատեսում եք գործարկել․ self-hosted Server CLI-ն նաև աջակցում է n8n publish:workflow --id=YOUR_WORKFLOW_ID հրամանին։ Երբ n8n-ը աշխատում է, Server CLI-ի publish/unpublish վիճակի փոփոխությունները ուժի մեջ են մտնում միայն n8n-ի restart-ից հետո։ Restart արեք մինչև scheduled trigger-ներն ու production webhook-ները ստուգելը կամ traffic-ը փոխելը։

Bulk export-ի օրինակ Docker Compose-ի համար՝ եթե ձեր n8n ծառայության անունը n8nէ, կարող եք գործարկել ստորև բերված պաշտոնական CLI backup-ները։ Output path-ը միտումնավոր գտնվում է դրա mount արված persistent .n8n պանակի ներսում, քանի որ container-ի ներսում կամայական պանակները կարող են անհետանալ այն վերաստեղծելիս։ Հաստատեք, որ պանակը գրելի է n8n container user-ի համար։ Workflow-ի և credential-ի JSON-ը պահեք առանձին պանակներում—n8n-ը փաստաթղթավորում է import-ի խնդիր, երբ երկու տեսակն էլ նույն պանակում են։

n8n 2.x draft-ն ընդդեմ published backup-ի՝ սովորական --backup workflow export-ը պահպանում է ընթացիկ draft-երը, որոնք կարող են տարբերվել production-ում published տարբերակներից։ Որոշակի workflow-ի իրական published տարբերակը պահպանելու համար այն առանձին արտահանեք՝ օգտագործելով docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json՝ նախ համոզվելով, որ output պանակը գոյություն ունի և գրելի է։ CLI-ն կարող է նաև արտահանել պատմական տարբերակ՝ օգտագործելով --version=VERSION_ID։ Այս պատճենները ամբողջական backup-ի հետ պահեք սերվերից դուրս․ մի ենթադրեք, որ draft JSON-ը գրանցում է live published վիճակը։

# Գործարկեք ձեր Docker Compose նախագծից․ n8n service-ը պետք է գոյություն ունենա
# Workflow և credential backup-ները պահեք ՏԱՐԲԵՐ պանակներում
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Պահպանված export պանակները պատճենեք container-ից ԴՈՒՐՍ՝ host-ի վրա
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Պատճենված ~/n8n-recovery/cli պանակը դեռ VPS-ում է, մինչև այն տեղափոխեք անվտանգ, անկախ backup վայր։ Credential export-ը լռելյայն կոդավորված է և import-ի ժամանակ պահանջում է համապատասխան գաղտնագրման բանալին։ Խուսափեք --decrypted օգտագործելուց՝ բացառությամբ խիստ վերահսկվող միգրացիայի․ այն secret-ները գրում է plaintext-ով։ Երբեք հանրային GitHub repository մի commit արեք արտահանումներ, որոնք պարունակում են զգայուն workflow logic կամ credentials։ Երրորդ կողմի որոշ GitHub credential-backup template-ներ դիտավորյալ արտահանում են decrypted secret-ներ․ private repository-ն հասանելիության սահմանափակում է, ոչ կոդավորում։ Ստուգեք յուրաքանչյուր template-ի իրական export settings-ն ու storage permissions-ը, կոդավորեք secret-ները մինչև սերվերից դուրս փոխանցելը և rotate արեք պատահաբար plaintext upload-ի միջոցով բացահայտված credentials-ը։

Bulk import-ի օրինակ՝ մաքուր target-ում ավարտեք owner setup-ը, տրամադրեք սկզբնական գաղտնագրման բանալին և համոզվեք, որ պահպանված backup ֆայլերը հասանելի են այդ recovery VPS-ում։ Հետևյալը ստեղծում է նպատակային պանակը և host-ից պատճենում է workflows/ և credentials/ ենթապանակները n8n container-ի մեջ․ համապատասխանեցրեք ուղիները, եթե ձեր Docker volume layout-ը տարբերվում է․

# Գործարկեք միայն նախատեսված ՄԱՔՈՒՐ recovery instance-ում
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Ստուգեք ֆայլերի ownership-ն ու հասանելիությունը n8n container user-ի համար։ Առանց ստուգված rollback-ի մի import արեք տվյալներով լցված production instance-ի վրա․ workflow և credential ID-ները կարող են վերագրել գոյություն ունեցող գրառումները։ Այնուհետև գործարկեք․

# Պահպանված cli/ բովանդակությունը պատճենեք target n8n service-ի .n8n/backups/ պանակի տակ
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Ներմուծված ID-ները կարող են փոխարինել գոյություն ունեցող workflow-ներին կամ credentials-ին․ dry run-երի համար օգտագործեք մեկուսացված test instance և հետո ստուգեք credentials-ն ու activation/publishing վիճակները։ n8n 2.x-ում JSON draft-ի վերականգնումն ինքնին չի ապացուցում, որ workflow-ը published է և կարող է գործարկել scheduled trigger-ներ։ Import-ի անվտանգություն՝ non-multi-main n8n instance-ում նախկինում active cron trigger-ները կարող են շարունակել աշխատել CLI import-ից հետո մինչև instance-ի restart-ը։ Կանգնեցրեք կամ մեկուսացրեք production trigger-ները և վերականգնված job-երը միացնելուց առաջ restart արեք n8n-ը․ հաստատեք, որ կրկնակի execution չկա։ CLI export-ները չի պարունակում սկզբնական օգտատերերին, execution log-երը, instance variable-ները կամ գաղտնագրման բանալին։ --backup սահմանում է --all --pretty --separate՝ ոչ թե «ամբողջ instance»։ Աղբյուրներ՝ n8n-ի ընթացիկ պաշտոնական backup/restore ուղեցույց և n8n CLI command reference։

Bulk restore GitHub կամ Google Drive template-ներից՝ սա այլընտրանք է միայն workflow JSON-ի համար, ոչ instance-ի տվյալների բազայի, օգտատերերի, կոդավորված credential value-ների կամ գաղտնագրման բանալու համար։ API-ի վրա հիմնված template գործարկելուց առաջ ստուգեք դրա n8n API և storage permissions-ը, ընտրված backup տարբերակն ու target instance-ը, արդյոք այն թարմացնում է համընկնող ID-ները և վերաստեղծում ջնջված workflow-ները, ինչպես նաև ինչ է անում workflow publishing-ի հետ։ Ոչ բոլոր template-ներն են վերաստեղծում target-ում բացակայող ID-ն․ այդ սցենարը մեկուսացված փորձարկեք մինչև automatic restore-ին ապավինելը։

FAQ

n8n-ի պահուստավորում և վերականգնում․ հաճախ տրվող հարցեր

Workflow-ների արտահանումը բավարա՞ր է n8n-ը պահուստավորելու համար։

Ոչ։ Workflow export-ները օգտակար տրամաբանական պատճեններ են, բայց ամբողջական վերականգնման համար կարող են նաև պահանջվել credentials-ը, համապատասխան գաղտնագրման բանալին, տվյալների բազայի վիճակը, մշտական ֆայլերը և binary-data storage-ը։

Պե՞տք է n8n-ի գաղտնագրման բանալին, եթե տվյալների բազան ունեմ։

Այո, եթե պետք է այդ տվյալների բազայում պահված կոդավորված credentials-ը շարունակեն օգտագործելի լինել։ Սկզբնական բանալին անվտանգ պահպանեք։

Պե՞տք է backup անել PostgreSQL-ը, թե արտահանել workflow-ներն ու credentials-ը։

Disaster recovery-ի համար պաշտպանեք տվյալների բազան և գաղտնագրման բանալին։ Տրամաբանական export-ները արժեքավոր են որպես միգրացիայի և ընտրովի վերականգնման լրացուցիչ շերտ, ոչ որպես instance-ի բոլոր մասերի փոխարինում։

Կարո՞ղ է VPS snapshot-ը լինել իմ միակ backup-ը։

Ավելի ճիշտ է այն դիտարկել որպես վերականգնման մեկ շերտ։ Պահեք անկախ off-server backup, որպեսզի մատակարարի, account-ի, սերվերի կամ snapshot-ի խափանումը միանգամից չվերացնի վերականգնման բոլոր կետերը։

Ինչպե՞ս իմանալ, որ backup-ը աշխատում է։

Վերականգնեք այն մաքուր test միջավայրում, հաստատեք credentials-ի decrypt-ը և գործարկեք ներկայացուցչական workflow-ներ։ Միայն հաջող backup job-ը չի ապացուցում վերականգնելիությունը։

GitHub կամ Google Drive workflow backup-ները ներառո՞ւմ են պահպանված credential secret-ները։

Միայն workflow-ի JSON backup-ները չեն ներառում n8n credential store-ի կառավարվող secret value-ները կամ instance-ի գաղտնագրման բանալին։ Սակայն արտահանված JSON-ը կարող է բացահայտել credential անուններն ու ID-ները և անմիջապես node parameter-ներում մուտքագրված secret-ները, օրինակ՝ authentication header-ները։ Upload կամ sharing անելուց առաջ ստուգեք և պաշտպանեք արտահանված JSON-ը։ Ամբողջական վերականգնման համար backup արեք տվյալների բազան և սկզբնական բանալին կամ օգտագործեք աջակցվող կոդավորված credential CLI export-ներ՝ փորձարկված restore-ով։ Միայն workflow-ի GitHub կամ Google Drive template-ը ամբողջական disaster recovery չէ։

Սահմանեք RPO-ն և RTO-ն մինչև միջադեպը

RPO վերջին փոփոխությունների առավելագույն թույլատրելի կորուստն է։ Այն չափեք նորագույն օգտագործելի, անկախ պահվող recovery point-ից․ պլանավորված վեցժամյա job-ը չի ապահովում վեցժամյա RPO, եթե export-ները կամ փոխանցումները ձախողվել են։ RTO առավելագույն թույլատրելի downtime-ն է։ Այն չափեք մաքուր restore փորձարկման ընթացքում՝ ներառելով secret-ների ստացումը, արտաքին ֆայլերի վերականգնումը, credentials-ի կրկին ստուգումը և վերականգնված workflow-ների publishing-ը, ոչ միայն container-ի գործարկումը։

ՎԵՐԱԿԱՆԳՆՄԱՆ ԲԱՆԱԼԻ

Վերակառուցելուց առաջ գտեք սկզբնական գաղտնագրման բանալին

Եթե production-ում սահմանել եք N8N_ENCRYPTION_KEY՝ պահպանեք հենց այդ environment secret-ը։ Եթե ոչ, պահպանեք սկզբնական persistent .n8n/config-ում գեներացված բանալին։ Կոդավորված credentials ներմուծելուց առաջ ստուգեք, թե վերականգնված instance-ն իրականում որ source-ն է օգտագործում․ նոր գեներացված բանալին չի կարող decrypt անել հին տվյալների բազայի credentials-ը։
