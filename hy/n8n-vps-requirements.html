n8n VPS-ի պահանջներ

n8n VPS-ի պահանջները որոշելիս սկսեք ձեր ծանրաբեռնվածությունից, ոչ համընդհանուր hardware minimum-ից։ Ճիշտ չափված 1 vCPU / 1 GB VPS-ը կարող է գործարկել փոքր, մշտապես աշխատող ավտոմատացումներ, իսկ 2 vCPU / 4 GB RAM-ը գործնական մեկնարկային դաս է n8n-ի համար PostgreSQL-ի և HTTPS-ի հետ։ Մեծ payload-ները, միաժամանակյա գործարկումները և տեղային տվյալների մշակումը պահանջում են ավելի մեծ ռեսուրսային պաշար․ ընտրությունից առաջ չափեք իրական օգտագործումը։

Գործնական փոքր production

2 vCPU · 4 GB RAM

Հավասարակշռված մեկնարկային դաս, երբ n8n-ը VPS-ը կիսում է PostgreSQL-ի, Docker-ի և reverse proxy-ի հետ։ Պահեք ռեսուրսային պաշար համընկնող execution-ների և սպասարկման համար։

Ծանր կամ տվյալատար

4+ vCPU · 8 GB+ RAM

Մեծ JSON-ը, binary ֆայլերը, Code node-երը, browser work-ը և բազմաթիվ համընկնող execution-ները կարող են պահանջել զգալիորեն ավելի շատ CPU և memory։

n8n-ն ունի՞ մեկ պաշտոնական minimum VPS չափ։

Ոչ՝ յուրաքանչյուր ծանրաբեռնվածության համար։ n8n-ի պաշտոնական prerequisite օրինակները նկարագրում են ցուցադրական OEM deployment և հստակ զգուշացնում, որ պահանջները փոխվում են ըստ ծանրաբեռնվածության։ Այդ փաստաթուղթը համընդհանուր երաշխիք չէ, որ CPU-ի, RAM-ի կամ disk-ի որևէ կոնկրետ allocation կսպասարկի production ավտոմատացումներ։

n8n-ը նշում է, որ idle instance-ը կարող է համեմատաբար քիչ memory օգտագործել, սակայն Code node-ը, մեծ binary payload-ը կամ միաժամանակյա execution-ը կարող են կտրուկ մեծացնել memory demand-ը։ Առանձին հաշվեք օպերացիոն համակարգի, Docker-ի, PostgreSQL-ի և backup/monitoring գործիքների ռեսուրսները։

Տեխնիկական աղբյուրներ՝ n8n-ի illustrative prerequisite-ները և պաշտոնական memory guide-ը։ Վերևի չորս տողերը իրական գնվող resource bundle-ներ են, ոչ n8n-ի պարտադիր պաշտոնական պահանջներ։

RAM ԵՎ CPU

Ինչն է իրականում սպառում սերվերի ռեսուրսները

Concurrent execution-ներ

Միաժամանակ աշխատող մի քանի workflow կարող են ավելի կարևոր լինել, քան n8n-ում պահված workflow-ների ընդհանուր քանակը։ Համընկնման ժամանակ հետևեք memory peak-երին և execution latency-ին։

Payload-ի չափ

Մեծ JSON object-ները, ֆայլերն ու binary data-ն մեծացնում են memory pressure-ը։ Մի քանի data-heavy execution կարող են ավելի շատ RAM պահանջել, քան բազմաթիվ թեթև API ավտոմատացումներ։

CPU-ծանր node-եր

Code-ը, transformation-ներն ու այլ compute-heavy քայլերը կարող են ստեղծել կայուն CPU pressure։ Ավելի շատ core օգնում է, երբ իրական execution-ները մրցում են compute-ի համար։

Օժանդակ ծառայություններ

Օպերացիոն համակարգը, PostgreSQL-ը, reverse proxy-ն, monitoring-ը և Docker-ը նույնպես ռեսուրսներ են պահանջում։ Չափեք ամբողջ stack-ը, ոչ միայն n8n process-ը։

ՉԱՓԵՔ ՄԻՆՉԵՎ ԹԱՐՄԱՑՆԵԼԸ

Ինչպես հասկանալ՝ n8n-ին ավելի շատ RAM, CPU թե disk է պետք

Գործարկեք ձեր ամենախոշոր սպասվող workflow-ը և իրատեսական overlapping burst, ապա ուսումնասիրեք server-ի և n8n execution log-երը։ Editor-ում պահպանված workflow-ների քանակն ինքնուրույն օգտակար capacity benchmark չէ։

Հիշողություն / OOM

Ստուգեք docker stats --no-stream և free -h։ Եթե memory-ն սպառվում է, նախ նվազեցրեք JSON կամ binary payload-ները, մեծ import-ները բաժանեք batch-երի և խուսափեք memory-heavy Code քայլերից։ JavaScript heap error-ը պարտադիր չէ լուծվի vCPU ավելացնելով։

CPU / զուգահեռություն

Չափեք՝ CPU-ն զբաղվա՞ծ է մնում transformation-ների ընթացքում, թե job-երը պարզապես սպասում են արտաքին API-ներին։ Regular mode-ում մինչև worker-ների անցնելը դիտարկեք աջակցվող production-concurrency limit։ CPU-ի ավելացումը չի արագացնում արտաքին rate-limited API-ն։

Storage / տվյալների բազա

Ստուգեք df -h, տվյալների բազայի չափը և պահպանվող execution history-ն։ Հետևեք disk growth-ին և դանդաղ database operation-ներին։ Retention-ը գիտակցված կարգավորեք մինչև ավելի մեծ disk-ի համար վճարելը, իսկ recovery copy-ները պահեք off-server։

Օգտագործեք n8n-ի concurrency guidance-ը և պաշտոնական benchmarking բացատրությունը։ Concurrent workflow-ների ցանկացած գովազդվող թիվ, առանց payload-ների և API latency-ի իմացության, միայն գնահատական է։

ՏՎՅԱԼՆԵՐԻ ԲԱԶԱ ԵՎ ՊԱՀԵՍՏ

SQLite, PostgreSQL և persistent data

SQLite

SQLite-ը կարող է հարմար լինել փոքր single-instance տեղակայումների և testing-ի համար։ Production օգտագործման և concurrency-ի աճի հետ տվյալների բազայի ընտրությունը դառնում է գործառնական սահմանափակում, ոչ պարզապես տեղադրման մանրուք։

PostgreSQL

Production-ին ուղղված VPS stack-ի համար PostgreSQL-ը տալիս է ավելի ամուր տվյալների բազայի հիմք։ RAM, CPU և disk հատկացրեք նաև հենց տվյալների բազային և հետևեք դրա աճին։

Persistent .n8n տվյալներ

PostgreSQL-ը մի համարեք միակ persistent asset-ը։ Պահպանեք n8n data directory-ն և պաշտպանեք encrypted credential-ները վերականգնելու համար անհրաժեշտ encryption key-ը։

Disk-ի աճ

Execution history-ն, binary data-ն, database file-երն ու log-երը ժամանակի ընթացքում կարող են աճել։ Retention setting-ներն ու off-server backup-ները ուղղակիորեն ազդում են անհրաժեշտ capacity-ի վրա։

DISK ՏԱՐՈՂՈՒԹՅՈՒՆ

Պատվիրելուց առաջ գնահատեք n8n execution history-ի պահեստը

Սկսեք հետևյալից՝ օրական պահպանված execution-ներ × մեկ execution-ի միջին պահպանված byte-եր × retention օրեր։ Օրինակ՝ օրական 500 պահպանված execution × յուրաքանչյուրը 200 KB × 14 օր = 1.4 GB օրինակային execution data՝ մինչև database overhead-ը։ 200 KB ենթադրությունը ցուցադրական է, ոչ n8n benchmark։

Disk հատկացրեք նաև OS-ի, Docker image layer-երի, database index-ների, binary file-երի, application log-երի, upgrade-ների և temporary file-երի համար։ Off-server backup-ներին անհրաժեշտ է իրենց capacity-ն։ 10 GB disk-ը կարող է բավարարել թեթև stack-ին, բայց պահպանվող ֆայլերի համար շատ ավելի քիչ տեղ ունի, քան 40 կամ 80 GB disk-ը։

n8n-ը փաստաթղթավորում է լռելյայն execution pruning՝ ըստ տարիքի (336 ժամ / 14 օր) կամ քանակի (10,000 execution), բացառություններով։ Փոփոխելուց առաջ ստուգեք ձեր իրական setting-ները և ինչն է պահպանվում։ SQLite-ը կարող է կրկին օգտագործել ազատված տարածքը՝ առանց իր ֆայլը ավտոմատ փոքրացնելու։

Աղբյուր՝ n8n՝ execution data-ի և pruning-ի կառավարում։ Disk պահանջները կախված են դիտարկված պահպանված payload չափերից, ոչ միայն node-երի քանակից։

Docker և production overhead

Linux VPS

Օգտագործեք աջակցվող Linux distribution՝ application stack-ից բացի նաև օպերացիոն համակարգի և security update-ների համար բավարար ռեսուրսներով։

Docker ԵՎ Compose

Container deployment-ը պարզեցնում է կրկնելիությունը, բայց չի վերացնում resource overhead-ը։ n8n-ի և տվյալների բազայի տվյալները պահեք disposable container-ներից դուրս։

HTTPS ԵՎ reverse proxy

Հանրային webhook-ները պահանջում են կայուն hostname և ճիշտ կարգավորված HTTPS։ Production design-ում ներառեք reverse proxy-ն և TLS layer-ը։

Monitoring և backup-ներ

Հետևեք RAM-ին, CPU-ին, disk-ին և տվյալների բազայի աճին։ Վերականգնելի backup-ները պահեք VPS-ից դուրս և փորձարկեք restoration-ը՝ snapshot-ը բավարար չհամարելով։

ԶՈՒԳԱՀԵՌՈՒԹՅՈՒՆ

Երբ ավելի մեծ VPS-ն այլևս ամբողջ պատասխանը չէ

Vertical scaling-ը հարմար է, քանի դեռ մեկ instance-ը կարող է մաքուր սպասարկել ծանրաբեռնվածությունը։ Երբ կայուն parallel demand-ը contention է ստեղծում, գնահատեք queue mode-ը և worker-ները։ Queue mode-ը ավելացնում է Redis, PostgreSQL և մեկ կամ մի քանի worker process․ RAM և CPU հատկացրեք յուրաքանչյուր բաղադրիչի, ոչ միայն n8n-ի համար։ n8n-ը նաև փաստաթղթավորում է filesystem binary-data storage-ի սահմանափակումները queue mode-ում, ուստի անցնելուց առաջ ստուգեք համատեղելի data-storage design։

Կարդացեք queue mode-ի և worker-ների ուղեցույցը

Մնացեք single-instanceԵրբ CPU-ն, RAM-ը և execution latency-ն peak overlap-ի ժամանակ մնում են ընդունելի։

Դիտարկեք queue mode-ըԵրբ չափված parallel demand-ը արդարացնում է Redis-ը և առանձին worker-ները։

2 GB RAM

SSD ընդդեմ NVMe

Standard SSD-ը բավարար է թեթև ավտոմատացման համար։ NVMe-ն ավելի օգտակար է դառնում, երբ PostgreSQL-ն ու execution history-ն հաճախակի read/write են ստեղծում կամ disk latency-ն երևում է չափված workflow performance-ում։

Չափեք մինչև upgrade-ը

FAQ

n8n VPS-ի պահանջներ․ հաճախ տրվող հարցեր

Որքա՞ն RAM է պետք n8n-ին։

Համընդհանուր թիվ չկա։ RAM demand-ը փոխվում է concurrency-ից, payload-ի չափից, execution behavior-ից և VPS-ում աշխատող supporting service-ներից կախված։ 4 GB սերվերը գործնական փոքր production մեկնարկային դաս է, ոչ երաշխավորված պահանջ յուրաքանչյուր ծանրաբեռնվածության համար։

Քանի՞ CPU core օգտագործել։

Թեթև ծանրաբեռնվածությունները կարող են սկսել փոքր CPU allocation-ից։ Core ավելացրեք, երբ monitoring-ը ցույց է տալիս կայուն CPU pressure կամ concurrency-ի ժամանակ ավելի դանդաղ execution-ներ՝ workflow count-ով միայն sizing անելու փոխարեն։

n8n-ը PostgreSQL պահանջո՞ւմ է։

Փոքր տեղակայումները կարող են օգտագործել SQLite, բայց operational requirement-ների և concurrency-ի աճի հետ PostgreSQL-ը ավելի ուժեղ production-oriented ընտրություն է։

Ե՞րբ է Redis պետք։

Redis-ը կապված է queue mode-ի հետ։ Սովորական single-instance deployment-ին Redis պետք չէ միայն այն պատճառով, որ այն աշխատում է VPS-ում։

Որքա՞ն disk space պահել։

Disk demand-ը կախված է PostgreSQL-ի աճից, պահպանվող execution history-ից, binary data-ից, log-երից, container layer-երից և backup-ներից։ Հետևեք աճին և պահեք headroom՝ ֆիքսված համընդհանուր թվին ապավինելու փոխարեն։

Կարո՞ղ եմ n8n-ը շարունակաբար աշխատեցնել 1 GB VPS-ում։

Այո, երբ իրական ծանրաբեռնվածությունը տեղավորվում է։ 1 GB VPS-ը իրական աշխատող սերվեր է և կարող է սպասարկել փոքր, հիմնականում հաջորդական ավտոմատացումներ, բայց memory headroom-ը սահմանափակ է։ Մի ենթադրեք, որ նույն սերվերում PostgreSQL stack-ը, binary-heavy job-երը կամ մի քանի մեծ concurrent execution կտեղավորվեն։ Հետևեք սպառմանը և upgrade արեք դիտարկված resource pressure-ի հիման վրա։

Production n8n VPS-ի համար 2 GB թե 4 GB RAM-ն է ավելի լավ։

Երկու GB-ն ավելի շատ տեղ է տալիս, քան թեթև 1 GB instance-ը, իսկ 4 GB-ը գործնական մեկնարկային դաս է n8n-ը PostgreSQL-ի և HTTPS-ի հետ միասին գնահատելու համար։ Համընդհանուր երաշխավորված production minimum չկա․ իրական պահանջարկը որոշում են workload complexity-ն, peak overlap-ը, container configuration-ը և պահպանվող տվյալները։

n8n AI workflow-ներին GPU պե՞տք է։

Ոչ, երբ n8n-ը միայն արտաքին model API է կանչում․ model provider-ը կատարում է inference-ը, իսկ VPS-ը՝ orchestration-ը, payload-ները և concurrency-ն։ Inference model-ները տեղային գործարկելն առանձին hardware որոշում է, որը կարող է պահանջել շատ ավելի RAM և համապատասխան GPU resources։

Ինչի՞ց են առաջանում n8n out-of-memory error-ները։

Մեծ JSON կամ binary payload-ները, memory-heavy Code operation-ները և համընկնող execution-ները տարածված պատճառներ են։ Ստուգեք runtime log-երն ու peak memory use-ը, ապա նվազեցրեք մեկ execution-ում պահվող տվյալները կամ ավելացրեք RAM՝ չափված խնդրի հիման վրա։
