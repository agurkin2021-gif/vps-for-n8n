n8n-ի տեղադրում VPS-ում

Տեղադրեք n8n-ը VPS-ում՝ Docker Compose-ի և PostgreSQL-ի միջոցով։ Production տեղակայման համար նաև անհրաժեշտ են հավելվածի և տվյալների բազայի մշտական տվյալներ, կայուն N8N_ENCRYPTION_KEY՝ հանրային hostname, HTTPS և webhook-ի ճիշտ կարգավորում։ Ստուգեք այս բաղադրիչները մինչև production workflow-ները ակտիվացնելը։

Պատրաստեք VPS-ը մինչև n8n-ը գործարկելը

Linux VPS

Օգտագործեք աջակցվող Linux սերվեր՝ n8n-ի, PostgreSQL-ի, Docker-ի և reverse proxy-ի համար բավարար ռեսուրսներով։

DNS

Մինչև TLS certificate-ներ ստանալն ու webhook URL-ներ հրապարակելը domain-ը կամ subdomain-ը ուղղեք VPS-ին։

Docker Compose

Տեղադրեք Docker Engine-ը և Compose plugin-ը՝ օգտագործելով օպերացիոն համակարգի համար աջակցվող package-ները։

Firewall

Բացեք միայն ադմինիստրավորման և web-ի համար անհրաժեշտ port-երը։ PostgreSQL-ն ու հավելվածի ներքին ծառայությունները պահեք private։

Տեղադրո՞ւմ եք VPS-ում, որտեղ արդեն կայքեր կան։ Եթե CPU-ն, RAM-ը և պահեստը բավարար են, կարող եք n8n ավելացնել ձեր կառավարվող սերվերին։ Սակայն եթե Nginx-ը, Apache-ը, Caddy-ն կամ մեկ այլ reverse proxy արդեն զբաղեցնում է 80/443 port-երը, ապա մի գործարկեք ստորև բերված Caddy container-ը առանց փոփոխության․ port-երը կբախվեն։ Փոխարենը նոր n8n subdomain-ը route արեք ձեր գործող reverse proxy-ով՝ համապատասխան private networking-ով, կամ ճշգրիտ Compose օրինակի համար օգտագործեք մաքուր VPS։ Պահպանեք մյուս կայքերն ու դրանց TLS կոնֆիգուրացիան․ օրինակը ենթադրում է, որ 80/443 port-երը ազատ են։

n8nԳործարկում է editor-ը, trigger-ներն ու workflow-ները՝ հավելվածի մշտական տվյալներով։

Persistent volume-ներՀավելվածի և տվյալների բազայի վիճակը պահեք ժամանակավոր container-ներից դուրս։
Հանրային DNSEditor-ի և webhook provider-ների օգտագործած hostname-ը կապում է VPS-ի հետ։

Տեղադրեք n8n-ը ձեր VPS-ում Docker Compose-ով

Այս օրինակով ստեղծեք n8n տեղակայում ինքնուրույն կառավարվող Linux VPS-ում։ n8n-ը տեղադրում և սպասարկում եք ինքներդ․ մեր գործընկերոջ միջոցով սերվեր ընտրելը չի ներառում նախապես տեղադրված n8n instance։ Օրինակը private Compose ցանցում միավորում է n8n-ը, PostgreSQL-ը, արտաքին task runner-ը և Caddy HTTPS-ը։ Սա կոնֆիգուրացիայի template է, ոչ թե live միջավայրում փորձարկված տեղակայման մասին պնդում։

Փոխարենը ուզո՞ւմ եք ամենաարագ նոր տեղադրումը։ n8n-ը նաև տրամադրում է պաշտոնական մեկ տողով Docker setup։ Դրա script-ը կարող եք ներբեռնել և ուսումնասիրել՝ curl -fsSL https://get.n8n.io -o get-n8n.sh մինչև գործարկելը՝ sh get-n8n.sh։ Այդ տարբերակը տեղային URL-ում գործարկում է նախնական instance SQLite-ով և ներառում է n8n Assistant sandbox ծառայությունները․ այն նույնը չէ ինչ այս public-HTTPS, PostgreSQL-ի վրա հիմնված VPS տեղակայումը։ Պաշտոնական ամբողջական sandbox stack-ը պահանջում է ավելի շատ RAM և CPU, քան թեթև n8n տեղադրումը (դրա Compose ուղեցույցը նշում է առնվազն 4 GB RAM / 2 vCPU)։ Internet-facing production VPS-ի համար շարունակեք ստորև բերված ձեռքով կարգավորվող stack-ով։

1. Պատրաստեք Docker-ը, DNS-ը և հասանելիությունը

Միացեք SSH-ով՝ sudo հասանելիությամբ, և DNS A record-ը n8n.example.com ուղղեք ձեր VPS-ի IPv4 հասցեին։ Նոր Ubuntu 22.04, 24.04 կամ 26.04 VPS-ում հետևյալ հրամանները տեղադրում են Docker Engine-ը և ժամանակակից docker compose plugin-ը Docker-ի պաշտոնական ստորագրված apt repository-ից՝

# Fresh official Ubuntu 22.04 / 24.04 / 26.04 installation
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Register Docker's signed apt repository
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

Սա պաշտոնական Docker Ubuntu տեղադրման ուղեցույցի production-ին ուղղված repository մեթոդն է։ Մի վերատեղադրեք կամ հեռացրեք Docker-ը առանց ստուգելու այն VPS-ում, որտեղ արդեն աշխատում են container-ներ կամ այլ կայքեր․ նախ ուսումնասիրեք գործող տեղադրումն ու հնարավոր package conflict-ները։ Debian-ի կամ այլ distribution-ի համար Ubuntu հրամանների փոխարեն օգտագործեք համապատասխան պաշտոնական OS-specific հրահանգները։

Այժմ ստուգեք Docker-ը, Compose plugin-ը, DNS-ը և աշխատանքային պանակը․

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

Եթե getent hosts չի վերադարձնում հասցե կամ վերադարձնում է սխալ հասցե, շտկեք DNS-ը մինչև Caddy-ն գործարկելը․ n8n.example.com այս ամբողջ ուղեցույցում փոխարինեք ձեր իրական hostname-ով։ Docker-ը սովորաբար պահանջում է root privileges․ եթե ձեր SSH user-ը չի կարող անմիջապես գործարկել հետագա docker compose հրամանները, դրանց սկզբում ավելացրեք sudo։ User-ին docker խմբում ավելացնելը տալիս է root-ին համարժեք հասանելիություն և shared server-ում չպետք է արվի առանց անհրաժեշտության։

Մինչև firewall-ը միացնելը համոզվեք, որ ձեր իրական SSH ադմինիստրավորման port-ը հասանելի է։ Certificate ստանալու և editor-ի համար թույլատրեք incoming HTTP (80) և HTTPS (443)։ Docker-ի հրապարակած container port-երը կարող են շրջանցել UFW-ի որոշ կանոններ, ուստի ուսումնասիրեք Docker-ի firewall ուղեցույցը և հրապարակեք միայն նախատեսված Caddy port-երը։ Այս Compose օրինակը դիտավորյալ մի չի հրապարակում PostgreSQL-ը (5432), n8n-ը (5678) կամ task-runner broker-ը (5679) հանրային ինտերնետում։

2. Ստեղծեք environment արժեքները և պահպանեք բանալին

Նախագծի պանակից գեներացրեք երեք տարբեր պատահական hexadecimal արժեք՝ հետևյալ հրամանով․

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

Ստեղծեք ֆայլ՝ .env օգտագործելով ստորև բերված template-ը․ յուրաքանչյուր REPLACE_WITH_RANDOM_HEX փոխարինեք տարբեր գեներացված արժեքով և փոխեք hostname-ն ու timezone-ը։ Նշված 2.42.5 tag-ը 2026 թվականի հոկտեմբերի 8-ին նշված stable release-ն է, որը այստեղ օգտագործվում է որպես ամսաթվով կոնֆիգուրացիայի օրինակ, ոչ live-tested տեղակայման կամ ապագա անվտանգության երաշխիք։ Տեղադրումից առաջ ստուգեք n8n-ի ընթացիկ պաշտոնական release-ները, ապա n8n-ն ու դրա task-runner image-ը պահեք նույն ստուգված տարբերակի վրա։

# .env — replace the three example secrets
# Pin a maintained n8n release; keep n8n and runner equal.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

Երբեք commit մի արեք .env հանրային repository-ում։ Գաղտնագրման բանալին և վերականգնման հրահանգները անվտանգ պահեք VPS-ից դուրս։ Container-ի վերաստեղծումից կամ միգրացիայից հետո բանալին պետք է մնա նույնը։

3. Նոր տեղադրման համար ստեղծեք compose.yaml

Նույն պանակում ստեղծեք compose.yaml։ Օրինակը օգտագործում է n8n-ի պաշտոնական environment-variable ձևաչափերը և PostgreSQL 18-ի PGDATA ուղին, որը փաստաթղթավորված է n8n hosting նախագծում․

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

Չորս ծառայություններն ունեն տարբեր դերեր․ PostgreSQL-ը պահպանում է տվյալների բազայի վիճակը, n8n-ը գործարկում է workflow-ները, n8n-runner կատարում է runner task-երը նույն տարբերակով և shared authentication token-ով, իսկ Caddy-ն սպասարկում է հանրային HTTPS-ը։ Արտաքին task runner-ը Redis queue mode չէ։ Միայն Caddy-ն է հրապարակում host port-երը։ Այս թեթև օրինակում setup-ի համար օգտագործվում է մեկ database role․ PostgreSQL privilege-ների ավելի խիստ տարանջատման համար տեսեք n8n-ի պաշտոնական PostgreSQL deployment օրինակը։

4. Create the HTTPS Caddyfile

Create the file Caddyfile (capital C, no extension) alongside compose.yaml. Replace the example hostname everywhere with your own DNS name:

n8n.example.com {
    reverse_proxy n8n:5678
}

Caddy requests and renews public TLS certificates when the domain resolves correctly and external traffic can reach ports 80/443. Do not point DNS to localhost. If you replace Caddy with another reverse proxy, forward the original host, protocol and client-address headers and adjust N8N_PROXY_HOPS for the actual number of trusted proxy hops.

5. Start the containers and test from outside

Run these commands from the project directory after saving .env, compose.yaml and Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

The last command checks the public HTTPS health endpoint. If certificate issuance is still pending, inspect Caddy logs and DNS/ports before concluding n8n is broken. Open https://n8n.example.com, create the first owner account immediately and enable appropriate sign-in protections. Confirm that the instance actually executes a workflow, not merely that the editor loads:

  1. In the editor, create a workflow with a Webhook trigger. Set HTTP Method to GET, choose the Path vps-check, and set Respond to Immediately. Save the workflow.
  2. Click Listen for Test Event, copy the full Test URL shown by n8n, and from another device run curl -i 'PASTE_TEST_URL_HERE' with the copied URL. Expect an HTTP success response and the incoming event to appear in the n8n editor. Test URLs work only while n8n is listening for the event.
  3. Publish the workflow, switch the node to its Production URL, copy it and run curl -i 'PASTE_PRODUCTION_URL_HERE' again. Confirm the execution under the workflow's Executions tab. Production webhook requests need the workflow to be published and do not show their payload in the editor's test view.

This is a deliberately simple, unauthenticated smoke test: never send secrets to it. Unpublish/delete it after testing, or configure Webhook authentication/IP restrictions before using a public endpoint for real data. See the official Webhook test/production documentation.

6. Back up before changing pinned versions

Save a recoverable PostgreSQL dump and the persistent n8n data volume, .env/encryption key and required external files to storage outside this server. Verify a restore using the backup and recovery guide before updating production. Example commands:

# Back up the database, encryption key, instance data,
# and files before changing the pinned versions.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# After securing the backup outside this VPS:
docker compose pull
docker compose up -d
docker compose ps

Change the pinned N8N_VERSION only after reading release notes; both n8n and runner images must advance together. Do not run docker compose down -v during routine maintenance because that deletes named data volumes. PostgreSQL major-version changes require a database upgrade or dump/restore plan; replacing the Postgres 18 image with a different major tag is not an automatic migration.

COMMON FAILURES

Why an n8n Docker install works locally but fails in production

Wrong webhook URL

Callbacks point to localhost, HTTP or an internal hostname instead of the public HTTPS origin.

Missing persistence

Application or database state disappears when a container is recreated.

Lost encryption key

Saved credentials become unusable after rebuilding because the new instance uses a different key.

Public database port

PostgreSQL is exposed unnecessarily even though only n8n needs to reach it.

POST-DEPLOY VERIFICATION

Verify health before connecting real workflows

Check container state

Run docker compose ps and confirm the application and database services are running as expected before treating the deployment as healthy.

Check the n8n health endpoint

With the Compose example above, port 5678 is not published on the host. Check the public endpoint with curl -fsS https://n8n.example.com/healthz after changing the hostname, and use docker compose ps plus service logs if HTTPS or the database is not ready.

Pin application versions

Do not treat an unreviewed floating image update as a maintenance strategy. Record the n8n version you run, read release notes and back up before changing it.

Do not bump PostgreSQL major versions in place

Changing only the Postgres major image tag can make an existing data directory incompatible. Back up and follow the database upgrade procedure instead of assuming container recreation performs a major-version migration.

FAQ

Installing n8n with Docker: common questions

Does n8n need PostgreSQL when using Docker?

Docker does not require PostgreSQL, and small deployments can use SQLite. For a production-oriented VPS deployment, PostgreSQL provides a stronger database foundation and supports later queue-mode scaling.

Why keep a persistent n8n volume if PostgreSQL stores data?

The persistent n8n directory can contain important instance state and configuration. Preserve it according to the deployment design instead of assuming the database is the only recovery asset.

Why does my webhook show localhost?

The internal container address differs from the public origin. Configure the external hostname, protocol and webhook URL, and ensure the reverse proxy passes the required headers.

Should port 5678 be public?

For a normal production deployment behind a reverse proxy, expose HTTPS at the proxy and keep the n8n application port internal unless there is a specific operational reason not to.

Do I need Redis?

Not for a standard single-instance Docker deployment. Redis becomes relevant when you deliberately move to queue mode and workers.

Are external n8n task runners the same as queue mode workers?

No. External task runners execute supported task code separately from the n8n main process and use a shared authentication token. Redis queue mode distributes workflow executions and has its own infrastructure requirements. This example shows an external task runner, not Redis queue mode. Match the runner image version to the n8n version.
