n8n-ի տեղադրում VPS-ում

Տեղադրեք n8n-ը VPS-ում՝ Docker Compose-ի և PostgreSQL-ի միջոցով։ Production տեղակայման համար նաև անհրաժեշտ են հավելվածի և տվյալների բազայի մշտական տվյալներ, կայուն N8N_ENCRYPTION_KEY՝ հանրային hostname, HTTPS և webhook-ի ճիշտ կարգավորում։ Ստուգեք այս բաղադրիչները մինչև production workflow-ները ակտիվացնելը։

Պատրաստեք VPS-ը մինչև n8n-ը գործարկելը

Linux VPS

Օգտագործեք աջակցվող Linux սերվեր՝ n8n-ի, PostgreSQL-ի, Docker-ի և reverse proxy-ի համար բավարար ռեսուրսներով։

DNS

Մինչև TLS certificate-ներ ստանալն ու webhook URL-ներ հրապարակելը domain-ը կամ subdomain-ը ուղղեք VPS-ին։

Docker Compose

Տեղադրեք Docker Engine-ը և Compose plugin-ը՝ օգտագործելով օպերացիոն համակարգի համար աջակցվող package-ները։

Ֆայրվոլ

Բացեք միայն ադմինիստրավորման և web-ի համար անհրաժեշտ port-երը։ PostgreSQL-ն ու հավելվածի ներքին ծառայությունները պահեք private։

Տեղադրո՞ւմ եք VPS-ում, որտեղ արդեն կայքեր կան։ Եթե CPU-ն, RAM-ը և պահեստը բավարար են, կարող եք n8n ավելացնել ձեր կառավարվող սերվերին։ Սակայն եթե Nginx-ը, Apache-ը, Caddy-ն կամ մեկ այլ reverse proxy արդեն զբաղեցնում է 80/443 port-երը, ապա մի գործարկեք ստորև բերված Caddy container-ը առանց փոփոխության․ port-երը կբախվեն։ Փոխարենը նոր n8n subdomain-ը route արեք ձեր գործող reverse proxy-ով՝ համապատասխան private networking-ով, կամ ճշգրիտ Compose օրինակի համար օգտագործեք մաքուր VPS։ Պահպանեք մյուս կայքերն ու դրանց TLS կոնֆիգուրացիան․ օրինակը ենթադրում է, որ 80/443 port-երը ազատ են։

Կարգավորվող բաղադրիչները

Reverse proxyՍտանում է հանրային HTTPS տրաֆիկը և փոխանցում n8n-ին։
n8nԳործարկում է editor-ը, trigger-ներն ու workflow-ները՝ հավելվածի մշտական տվյալներով։
PostgreSQLՊահպանում է production տեղակայման workflow-ների, credential-ների և execution-ների վիճակը։
Persistent volume-ներՀավելվածի և տվյալների բազայի վիճակը պահեք ժամանակավոր container-ներից դուրս։
Հանրային DNSEditor-ի և webhook provider-ների օգտագործած hostname-ը կապում է VPS-ի հետ։

Տեղադրեք n8n-ը ձեր VPS-ում Docker Compose-ով

Այս օրինակով ստեղծեք n8n տեղակայում ինքնուրույն կառավարվող Linux VPS-ում։ n8n-ը տեղադրում և սպասարկում եք ինքներդ․ մեր գործընկերոջ միջոցով սերվեր ընտրելը չի ներառում նախապես տեղադրված n8n instance։ Օրինակը private Compose ցանցում միավորում է n8n-ը, PostgreSQL-ը, արտաքին task runner-ը և Caddy HTTPS-ը։ Սա կոնֆիգուրացիայի template է, ոչ թե live միջավայրում փորձարկված տեղակայման մասին պնդում։

Փոխարենը ուզո՞ւմ եք ամենաարագ նոր տեղադրումը։ n8n-ը նաև տրամադրում է պաշտոնական մեկ տողով Docker setup։ Դրա script-ը կարող եք ներբեռնել և ուսումնասիրել՝ curl -fsSL https://get.n8n.io -o get-n8n.sh մինչև գործարկելը՝ sh get-n8n.sh։ Այդ տարբերակը տեղային URL-ում գործարկում է նախնական instance SQLite-ով և ներառում է n8n Assistant sandbox ծառայությունները․ այն նույնը չէ ինչ այս public-HTTPS, PostgreSQL-ի վրա հիմնված VPS տեղակայումը։ Պաշտոնական ամբողջական sandbox stack-ը պահանջում է ավելի շատ RAM և CPU, քան թեթև n8n տեղադրումը (դրա Compose ուղեցույցը նշում է առնվազն 4 GB RAM / 2 vCPU)։ Internet-facing production VPS-ի համար շարունակեք ստորև բերված ձեռքով կարգավորվող stack-ով։

1. Պատրաստեք Docker-ը, DNS-ը և հասանելիությունը

Միացեք SSH-ով՝ sudo հասանելիությամբ, և DNS A record-ը n8n.example.com ուղղեք ձեր VPS-ի IPv4 հասցեին։ Նոր Ubuntu 22.04, 24.04 կամ 26.04 VPS-ում հետևյալ հրամանները տեղադրում են Docker Engine-ը և ժամանակակից docker compose plugin-ը Docker-ի պաշտոնական ստորագրված apt repository-ից՝

# Նոր պաշտոնական Ubuntu 22.04 / 24.04 / 26.04 տեղադրում
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Գրանցեք Docker-ի ստորագրված apt repository-ն
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

Սա պաշտոնական Docker Ubuntu տեղադրման ուղեցույցի production-ին ուղղված repository մեթոդն է։ Մի վերատեղադրեք կամ հեռացրեք Docker-ը առանց ստուգելու այն VPS-ում, որտեղ արդեն աշխատում են container-ներ կամ այլ կայքեր․ նախ ուսումնասիրեք գործող տեղադրումն ու հնարավոր package conflict-ները։ Debian-ի կամ այլ distribution-ի համար Ubuntu հրամանների փոխարեն օգտագործեք համապատասխան պաշտոնական OS-specific հրահանգները։

Այժմ ստուգեք Docker-ը, Compose plugin-ը, DNS-ը և աշխատանքային պանակը․

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

Եթե getent hosts չի վերադարձնում հասցե կամ վերադարձնում է սխալ հասցե, շտկեք DNS-ը մինչև Caddy-ն գործարկելը․ n8n.example.com այս ամբողջ ուղեցույցում փոխարինեք ձեր իրական hostname-ով։ Docker-ը սովորաբար պահանջում է root privileges․ եթե ձեր SSH user-ը չի կարող անմիջապես գործարկել հետագա docker compose հրամանները, դրանց սկզբում ավելացրեք sudo։ User-ին docker խմբում ավելացնելը տալիս է root-ին համարժեք հասանելիություն և shared server-ում չպետք է արվի առանց անհրաժեշտության։

Մինչև firewall-ը միացնելը համոզվեք, որ ձեր իրական SSH ադմինիստրավորման port-ը հասանելի է։ Certificate ստանալու և editor-ի համար թույլատրեք incoming HTTP (80) և HTTPS (443)։ Docker-ի հրապարակած container port-երը կարող են շրջանցել UFW-ի որոշ կանոններ, ուստի ուսումնասիրեք Docker-ի firewall ուղեցույցը և հրապարակեք միայն նախատեսված Caddy port-երը։ Այս Compose օրինակը դիտավորյալ մի չի հրապարակում PostgreSQL-ը (5432), n8n-ը (5678) կամ task-runner broker-ը (5679) հանրային ինտերնետում։

2. Ստեղծեք environment արժեքները և պահպանեք բանալին

Նախագծի պանակից գեներացրեք երեք տարբեր պատահական hexadecimal արժեք՝ հետևյալ հրամանով․

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

Ստեղծեք ֆայլ՝ .env օգտագործելով ստորև բերված template-ը․ յուրաքանչյուր REPLACE_WITH_RANDOM_HEX փոխարինեք տարբեր գեներացված արժեքով և փոխեք hostname-ն ու timezone-ը։ Նշված 2.42.5 tag-ը 2026 թվականի հոկտեմբերի 8-ին նշված stable release-ն է, որը այստեղ օգտագործվում է որպես ամսաթվով կոնֆիգուրացիայի օրինակ, ոչ live-tested տեղակայման կամ ապագա անվտանգության երաշխիք։ Տեղադրումից առաջ ստուգեք n8n-ի ընթացիկ պաշտոնական release-ները, ապա n8n-ն ու դրա task-runner image-ը պահեք նույն ստուգված տարբերակի վրա։

# .env — փոխարինեք երեք օրինակային secret-ները
# Ֆիքսեք աջակցվող n8n release-ը․ n8n-ի և runner-ի տարբերակները պահեք նույնը։
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

Երբեք commit մի արեք .env հանրային repository-ում։ Գաղտնագրման բանալին և վերականգնման հրահանգները անվտանգ պահեք VPS-ից դուրս։ Container-ի վերաստեղծումից կամ միգրացիայից հետո բանալին պետք է մնա նույնը։

3. Նոր տեղադրման համար ստեղծեք compose.yaml

Նույն պանակում ստեղծեք compose.yaml։ Օրինակը օգտագործում է n8n-ի պաշտոնական environment-variable ձևաչափերը և PostgreSQL 18-ի PGDATA ուղին, որը փաստաթղթավորված է n8n hosting նախագծում․

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

Չորս ծառայություններն ունեն տարբեր դերեր․ PostgreSQL-ը պահպանում է տվյալների բազայի վիճակը, n8n-ը գործարկում է workflow-ները, n8n-runner կատարում է runner task-երը նույն տարբերակով և shared authentication token-ով, իսկ Caddy-ն սպասարկում է հանրային HTTPS-ը։ Արտաքին task runner-ը Redis queue mode չէ։ Միայն Caddy-ն է հրապարակում host port-երը։ Այս թեթև օրինակում setup-ի համար օգտագործվում է մեկ database role․ PostgreSQL privilege-ների ավելի խիստ տարանջատման համար տեսեք n8n-ի պաշտոնական PostgreSQL deployment օրինակը։

4. Ստեղծեք HTTPS Caddyfile-ը

Ստեղծեք ֆայլը Caddyfile (մեծատառ C-ով, առանց ընդլայնման)՝ compose.yaml-ի կողքին։ Օրինակի hostname-ը ամենուր փոխարինեք ձեր DNS անունով․

n8n.example.com {
    reverse_proxy n8n:5678
}

Caddy-ն ստանում և թարմացնում է հանրային TLS certificate-ները, երբ domain-ը ճիշտ է resolve լինում, իսկ արտաքին տրաֆիկը հասնում է 80/443 port-երին։ DNS-ը մի ուղղեք localhost։ Եթե Caddy-ն փոխարինեք մեկ այլ reverse proxy-ով, փոխանցեք սկզբնական host, protocol և client-address header-ները և համապատասխանեցրեք N8N_PROXY_HOPS վստահելի proxy hop-երի իրական քանակին։

5. Գործարկեք container-ները և փորձարկեք դրսից

Այս հրամանները գործարկեք նախագծի պանակից՝ պահպանելուց հետո .env՝ compose.yaml և Caddyfile․

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

Վերջին հրամանը ստուգում է հանրային HTTPS health endpoint-ը։ Եթե certificate-ի թողարկումը դեռ սպասման մեջ է, մինչև n8n-ը խափանված համարելը ստուգեք Caddy log-երը և DNS/port-երը։ Բացեք https://n8n.example.com՝ անմիջապես ստեղծեք առաջին owner account-ը և միացրեք համապատասխան sign-in պաշտպանությունը։ Հաստատեք, որ instance-ը իրականում կատարում է workflow, ոչ թե պարզապես բացվում է editor-ը․

  1. Editor-ում ստեղծեք workflow՝ Webhook trigger-ով։ Սահմանեք HTTP Method որպես GETընտրեք Path vps-checkև սահմանեք Respond որպես Immediately։ Պահպանեք workflow-ը։
  2. Սեղմեք Listen for Test Eventպատճենեք ամբողջ Test URL որը ցույց է տալիս n8n-ը, և մեկ այլ սարքից գործարկեք curl -i 'PASTE_TEST_URL_HERE' պատճենված URL-ով։ Սպասեք HTTP հաջող պատասխան և incoming event-ի հայտնվելուն n8n editor-ում։ Test URL-ները աշխատում են միայն այն ժամանակ, երբ n8n-ը սպասում է event-ին։
  3. Publish workflow-ը, node-ը փոխեք դրա Production URLպատճենեք այն և կրկին գործարկեք curl -i 'PASTE_PRODUCTION_URL_HERE' ։ Execution-ը հաստատեք workflow-ի Executions tab-ում։ Production webhook request-ների համար workflow-ը պետք է published լինի, և դրանց payload-ը editor-ի test view-ում չի ցուցադրվում։

Սա դիտավորյալ պարզ, առանց authentication-ի smoke test է․ երբեք դրա միջոցով secret-ներ մի ուղարկեք։ Փորձարկումից հետո unpublish/delete արեք այն կամ իրական տվյալների համար հանրային endpoint օգտագործելուց առաջ կարգավորեք Webhook authentication/IP սահմանափակումներ։ Տեսեք Webhook-ի պաշտոնական test/production փաստաթղթերը։

6. Backup արեք մինչև pinned տարբերակները փոխելը

Պահպանեք վերականգնելի PostgreSQL dump և n8n-ի մշտական data volume-ը, .env/գաղտնագրման բանալին և անհրաժեշտ արտաքին ֆայլերը՝ այս սերվերից դուրս storage-ում։ Restore-ը ստուգեք backup-ի և վերականգնման ուղեցույցով մինչև production-ը թարմացնելը։ Հրամանների օրինակներ․

# Backup արեք տվյալների բազան, գաղտնագրման բանալին և instance-ի տվյալները,
# ինչպես նաև ֆայլերը՝ մինչև pinned տարբերակները փոխելը։
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# Backup-ը այս VPS-ից դուրս անվտանգ պահելուց հետո՝
docker compose pull
docker compose up -d
docker compose ps

Pinned N8N_VERSION փոխեք միայն release note-երը կարդալուց հետո․ n8n և runner image-ները պետք է թարմացվեն միասին։ Մի գործարկեք docker compose down -v սովորական սպասարկման ժամանակ, քանի որ այն ջնջում է named data volume-ները։ PostgreSQL major version-ի փոփոխությունները պահանջում են տվյալների բազայի upgrade կամ dump/restore պլան․ Postgres 18 image-ը այլ major tag-ով փոխարինելը ավտոմատ միգրացիա չէ։

Հեղինակավոր աղբյուրներ՝ n8n Docker Compose ուղեցույցը, n8n reverse-proxy/webhook կոնֆիգուրացիան և PostgreSQL deployment-ի պաշտոնական նշումները։ Ենթակառուցվածքային benchmark կամ մատակարարին հատուկ նախապես տեղադրված հնարավորություն չի ենթադրվում։

ԿՈՆՖԻԳՈՒՐԱՑԻԱ

Secret-ներն ու հանրային URL-ները կարգավորեք գիտակցված

Production credential-ներ պահպանելուց առաջ սահմանեք և պահպանեք ուժեղ n8n գաղտնագրման բանալի։ Վերականգնումից հետո պահանջվում է նույն բանալին։

PostgreSQL-ի մուտքային տվյալներ

Օգտագործեք տվյալների բազայի առանձին credentials և գաղտնաբառերը պահեք հանրային source control-ից դուրս։

Հանրային hostname

Կարգավորեք իրական արտաքին hostname-ը և HTTPS origin-ը, ոչ թե container-ի ներքին հասցեն։

Webhook-ի URL

Սահմանեք N8N_WEBHOOK_URL որպես հանրայնորեն հասանելի HTTPS base URL և սահմանեք N8N_PROXY_HOPS=1 երբ կա մեկ վստահելի reverse proxy։ WEBHOOK_URL n8n 2.35.0-ից սկսած հնացած alias է․ մի պատճենեք այն հին tutorial-ներից։

ՄՇՏԱԿԱՆ ՊԱՀՊԱՆՈՒՄ

n8n-ի և PostgreSQL-ի տվյալները պահեք առանձին

n8n տվյալներ

n8n data directory-ի համար mount արեք persistent storage, որպեսզի instance-ի կարևոր վիճակը պահպանվի container-ի վերաստեղծումից հետո։

PostgreSQL տվյալներ

Տվյալների բազայի պանակը պահեք PostgreSQL container-ից անկախ։

Ֆայլերի permissions

Mount արված ուղիները գրելի դարձրեք նախատեսված container user-ի համար՝ host storage-ը անհարկի բաց չթողնելով։

Workflow ֆայլեր

Մշտապես պահպանեք բոլոր mount արված ֆայլերը կամ binary-data storage-ը, որոնցից կախված են production workflow-ները։

POSTGRESQL

Միացրեք n8n-ը private տվյալների բազայի ծառայությանը

Տվյալների բազայի տեսակn8n-ը կարգավորեք PostgreSQL-ի համար, որպեսզի պատահմամբ չանցնի SQLite-ի։
HostPrivate Docker ցանցում օգտագործեք PostgreSQL service-ի անունը։
CredentialsՀամապատասխանեցրեք նախատեսված տվյալների բազան, application user-ը և գաղտնաբառը։
Պատրաստ վիճակՄինչև n8n-ի հաջող initialize-ը սպասելը թույլ տվեք PostgreSQL-ին պատրաստ վիճակի անցնել։
NetworkContainer-ների միջև տվյալների բազայի հասանելիության համար հանրային PostgreSQL port պետք չէ։

HTTPS ԵՎ PROXY

Հանրային n8n URL-ը սպասարկեք HTTPS-ի հետևում

Reverse proxy

Որպես հանրային entry point օգտագործեք Nginx, Caddy կամ Traefik և տրաֆիկը փոխանցեք private n8n service-ին։

TLS

Հանրային hostname-ի համար ստացեք վավեր certificate և HTTP տրաֆիկը redirect արեք HTTPS-ի։

Փոխանցվող header-ներ

Փոխանցեք n8n-ին անհրաժեշտ host, protocol և client տվյալները և կարգավորեք սպասվող proxy hop-երի քանակը։

Webhook-ի ստուգում

Webhook գործարկեք VPS-ից դուրս և հաստատեք, որ n8n-ը գեներացնում է արտաքինից հասանելի HTTPS URL։

Production անվտանգության ամբողջական ստուգաթերթ

ԱՌԱՋԻՆ ԳՈՐԾԱՐԿՈՒՄ

Մինչև production օգտագործումը ստուգեք persistent պահպանումը

Container-ներՀաստատեք, որ n8n-ը, PostgreSQL-ը և proxy-ն startup-ից ու restart-ից հետո մնում են healthy։
EditorԲացեք հանրային HTTPS hostname-ը և հաստատեք, որ authentication-ը ճիշտ է աշխատում։
DatabaseՍտեղծեք test state, վերաստեղծեք container-ները և հաստատեք, որ վիճակը պահպանվում է։
WebhookԳործարկեք արտաքին webhook test՝ DNS-ը, TLS-ը, proxying-ը և հանրային callback URL-ը ստուգելու համար։
CredentialsՀաստատեք, որ կոդավորված credentials-ը n8n restart-ից հետո շարունակում են օգտագործելի մնալ։

ԹԱՐՄԱՑՈՒՄՆԵՐ

Թարմացրեք Docker տեղակայումը՝ container-ները backup չհամարելով

Կարդացեք release note-երը

Թարմացումից առաջ ուսումնասիրեք n8n-ի կարևոր փոփոխությունները, հատկապես եթե մի քանի տարբերակ եք բաց թողնում։

Նախ backup արեք

Մինչև production image-ը փոխելը ստեղծեք տվյալների բազայի և instance-ի վերականգնելի backup։

Վերաստեղծեք անվտանգ

Pull արեք ընտրված image-ը և վերաստեղծեք հավելվածի container-ները՝ պահպանելով persistent volume-ները։

Ստուգեք թարմացումից հետո

Մինչև տեղակայումը healthy համարելը ստուգեք log-երը, editor-ի հասանելիությունը, credentials-ը և ներկայացուցչական workflow-ները։

Backup և restore ուղեցույց

ՏԱՐԱԾՎԱԾ ԽԱՓԱՆՈՒՄՆԵՐ

Ինչու n8n Docker տեղադրումը աշխատում է տեղային, բայց ձախողվում production-ում

Սխալ webhook URL

Callback-ները հանրային HTTPS origin-ի փոխարեն ուղղվում են localhost-ին, HTTP-ին կամ ներքին hostname-ին։

Persistent պահպանում չկա

Հավելվածի կամ տվյալների բազայի վիճակը կորչում է container-ի վերաստեղծման ժամանակ։

Կորած գաղտնագրման բանալի

Պահպանված credentials-ը վերակառուցումից հետո դառնում են անօգտագործելի, քանի որ նոր instance-ը այլ բանալի է օգտագործում։

Հանրային տվյալների բազայի port

PostgreSQL-ը անհարկի բաց է հանրային ցանցում, թեև դրան պետք է հասնի միայն n8n-ը։

ՏԵՂԱԿԱՅՈՒՄԻՑ ՀԵՏՈ ՍՏՈՒԳՈՒՄ

Մինչև իրական workflow-ները միացնելը ստուգեք համակարգի վիճակը

Ստուգեք container-ների վիճակը

Գործարկեք docker compose ps և մինչև տեղակայումը healthy համարելը հաստատեք, որ հավելվածի և տվյալների բազայի ծառայություններն աշխատում են սպասված ձևով։

Ստուգեք n8n health endpoint-ը

Վերևի Compose օրինակում 5678 port-ը host-ում չի հրապարակվում։ Հանրային endpoint-ը ստուգեք curl -fsS https://n8n.example.com/healthz hostname-ը փոխելուց հետո, իսկ docker compose ps և service log-երն օգտագործեք, եթե HTTPS-ը կամ տվյալների բազան պատրաստ չեն։

Ֆիքսեք հավելվածի տարբերակները

Չստուգված floating image update-ը մի համարեք սպասարկման ռազմավարություն։ Գրանցեք ձեր օգտագործած n8n տարբերակը, կարդացեք release note-երը և այն փոխելուց առաջ backup արեք։

PostgreSQL major տարբերակը տեղում մի բարձրացրեք

Միայն Postgres major image tag-ը փոխելը կարող է գործող data directory-ն անհամատեղելի դարձնել։ Backup արեք և հետևեք տվյալների բազայի upgrade ընթացակարգին՝ փոխարենը ենթադրելու, որ container-ի վերաստեղծումը կատարում է major-version միգրացիա։

Docker Compose-ի ընթացիկ պաշտոնական ուղեցույց

FAQ

n8n-ի տեղադրում Docker-ով․ հաճախ տրվող հարցեր

Docker օգտագործելիս n8n-ին պե՞տք է PostgreSQL։

Docker-ը PostgreSQL չի պահանջում, և փոքր տեղակայումները կարող են օգտագործել SQLite։ Production-ին ուղղված VPS տեղակայման համար PostgreSQL-ը տալիս է ավելի ամուր տվյալների բազայի հիմք և աջակցում հետագա queue-mode մասշտաբավորմանը։

Ինչո՞ւ պահել persistent n8n volume, եթե տվյալները պահում է PostgreSQL-ը։

Persistent n8n պանակը կարող է պարունակել instance-ի կարևոր վիճակ և կոնֆիգուրացիա։ Այն պահպանեք տեղակայման կառուցվածքին համապատասխան՝ փոխարենը ենթադրելու, որ տվյալների բազան վերականգնման միակ ռեսուրսն է։

Ինչո՞ւ է իմ webhook-ը ցույց տալիս localhost։

Container-ի ներքին հասցեն տարբերվում է հանրային origin-ից։ Կարգավորեք արտաքին hostname-ը, protocol-ը և webhook URL-ը և համոզվեք, որ reverse proxy-ն փոխանցում է անհրաժեշտ header-ները։

5678 port-ը պե՞տք է հանրային լինի։

Reverse proxy-ի հետևում սովորական production տեղակայման դեպքում HTTPS-ը բացեք proxy-ում, իսկ n8n հավելվածի port-ը պահեք ներքին, եթե հակառակի համար կոնկրետ գործառնական պատճառ չկա։

Պե՞տք է Redis։

Սովորական single-instance Docker տեղակայման համար՝ ոչ։ Redis-ը պետք է, երբ գիտակցված անցնում եք queue mode-ի և worker-ների։

Արտաքին n8n task runner-ները նույնն ե՞ն, ինչ queue mode worker-ները։

Ոչ։ Արտաքին task runner-ները աջակցվող task code-ը կատարում են n8n main process-ից առանձին և օգտագործում են shared authentication token։ Redis queue mode-ը բաշխում է workflow execution-ները և ունի իր ենթակառուցվածքային պահանջները։ Այս օրինակը ցույց է տալիս արտաքին task runner, ոչ Redis queue mode։ Runner image-ի տարբերակը համապատասխանեցրեք n8n տարբերակին։
