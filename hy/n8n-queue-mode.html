n8n Queue Mode

Queue mode-ը workflow execution-ը առանձնացնում է հիմնական n8n process-ից։ Հիմնական instance-ը ստանում է trigger-ները և ստեղծում execution-ներ, Redis-ը համակարգում է queue-ն, worker-ները կատարում են job-երը, իսկ PostgreSQL-ը պահպանում է ընդհանուր workflow և execution տվյալները։

ԱՐԱԳ ՈՐՈՇՈՒՄ

Իրո՞ք պետք է queue mode-ը։

Մնացեք սովորական mode-ում, երբ

Մեկ instance-ը առանց խնդիրների սպասարկում է peak execution-ները, իսկ CPU-ն, RAM-ը և execution latency-ն կայուն են։ Queue mode-ը ավելացնում է բաղադրիչներ, որոնք դեռ պետք չեն։

Դիտարկեք queue mode-ը, երբ

Կայուն parallel execution-ները contention են ստեղծում, ծանրաբեռնվածության տակ execution latency-ն աճում է, կամ execution capacity-ն մեծացնելու համար պետք է գործարկել մի քանի worker։

Նախ vertical scaling արեք, երբ

Bottleneck-ը պարզապես CPU-ի կամ RAM-ի պակասն է, և մեկ ավելի մեծ instance-ը դեռ կարող է մաքուր սպասարկել workload-ը։

Չափեք մինչև architecture-ը փոխելը

Անցումը հիմնավորեք peak concurrency-ի, CPU-ի, RAM-ի, execution duration-ի, queue depth-ի և database pressure-ի չափումներով։

ՃԱՐՏԱՐԱՊԵՏՈՒԹՅՈՒՆ

Ինչպես է աշխատում n8n queue mode-ը

1 · MainՍտանում է timer-ներ, webhook-ներ և workflow request-ներ ու ստեղծում execution՝ production execution-ը ինքնուրույն կատարելու փոխարեն։
2 · RedisԱշխատում է որպես message broker։ Այն պահում է pending execution message-ները, որպեսզի հաջորդ հասանելի worker-ը վերցնի job-ը։
3 · WorkerՍտանում է execution ID-ն, ընդհանուր database-ից բեռնում workflow-ի տվյալները, գործարկում workflow-ը և արդյունքը գրում հետ։
4 · PostgreSQLՏրամադրում է ընդհանուր persistent workflow և execution տվյալներ։ Distributed queue mode-ը SQLite-ի վրա չի աջակցվում։

ՀԻՄՆԱԿԱՆ ՊԱՀԱՆՋՆԵՐ

Ինչ է անհրաժեշտ յուրաքանչյուր queue mode deployment-ին

Redis

Բոլոր main և worker process-ներին անհրաժեշտ է վստահելի access դեպի queue coordination-ի համար օգտագործվող Redis service-ը։

PostgreSQL

Main-ը և worker-ները պետք է օգտագործեն նույն database-ը։ Queue mode-ը distributed architecture է և չպետք է կառուցվի SQLite-ի շուրջ։

Համապատասխան n8n configuration

Main-ը և worker-ները պետք է աշխատեն queue mode-ում և ունենան Redis, PostgreSQL ու encrypted credential-ներ հասնելու համար անհրաժեշտ նույն configuration-ը։

Worker-ի capacity

Worker-ներին պետք է բավարար CPU և RAM իրենց կատարած workflow-ների համար։ Process-ներ ավելացնելը չի վերացնում յուրաքանչյուր execution-ի resource cost-ը։

Միացրեք queue mode-ը գործող self-hosted stack-ում։ Նախ համոզվեք, որ n8n main service-ը և յուրաքանչյուր worker private network-ով հասնում են նույն PostgreSQL database-ին ու Redis-ին։ Սահմանեք EXECUTIONS_MODE=queue և main-ի, և worker-ների վրա, նաև սահմանեք QUEUE_BULL_REDIS_HOST=redis և QUEUE_BULL_REDIS_PORT=6379 երբ redis ձեր իրական Compose service name-ն է։ Օգտագործեք DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres և համապատասխան DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER և DB_POSTGRESDB_PASSWORD յուրաքանչյուր process-ի վրա․ օրինակ service name-երը փոխարինեք ձեր անուններով։ Բոլորին փոխանցեք գործող ճշգրիտ N8N_ENCRYPTION_KEY ։ Մի publish արեք Redis-ի կամ PostgreSQL-ի host port-երը միայն նույն Compose network-ի container-ները միացնելու համար։

Գործարկեք executor, ոչ երկրորդ editor։ Ավելացրեք n8n worker service՝ նույն pinned n8n image version-ով և main-ի հետ ընդհանուր setting-ներով, բայց գործարկեք այն worker command-ով։ Եթե այդ service-ը անվանել եք n8n-worker՝ գործարկեք այն docker compose up -d n8n-worker։ Մեկ worker-ի վրա իրական execution-ը հաստատելուց հետո կարող եք օգտագործել docker compose up -d --scale n8n-worker=2 ՝ այդ service-ից երկրորդ worker գործարկելու համար։ Սրանք հավելումներ են գործող և ճիշտ կարգավորված Compose stack-ին, ոչ standalone installation file։ Պահպանեք գործող persistent volume-ները, HTTPS proxy-ն, secret-ները և backup-ները։

Queue mode Compose fragment՝ գործող stack-ի համար։ Ստորև բերված օրինակը merge արեք ձեր գործող compose.yamlֆայլի մեջ․ դա չէ ամբողջական standalone deployment։ Այն ենթադրում է, որ արդեն ունեք persistent, private postgres և n8n service-ներ, գործող N8N_VERSION pin environment-ում և ձեր պաշտպանված POSTGRES_PASSWORD ու սկզբնական N8N_ENCRYPTION_KEY։ Նրա անունները, volume-ները, database-ը և n8n version-ը համապատասխանեցրեք գործող project-ին։ Queue mode Redis setting-ները և EXECUTIONS_MODE=queue ավելացրեք նաև գործող main service-ին, ինչպես նկարագրված է վերևում։

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Այս fragment-ում Redis-ի կամ worker-ի համար host port չի հրապարակվում։ Redis append-only persistence-ը լրացուցիչ recovery layer է, չէ off-server backup-ների փոխարինող չէ։ Գործող HTTPS և authentication configuration-ը թողեք անփոփոխ։ External task runner պահանջող Code node-երի համար worker deployment-ի runner process-ները կարգավորեք առանձին․ queue mode-ը ինքնին չի փոխարինում task runner-ներին։

Փոխարկո՞ւմ եք գործող SQLite instance-ը։ Պարզապես մի փոխեք DB_TYPE և մի գործարկեք դատարկ PostgreSQL database-ի վրա․ դա չի migrate անում հին workflow-ներն ու credential-ները։ Ցանկացած cutover-ից առաջ backup արեք source database-ը, persistent .n8n directory-ն և սկզբնական encryption key-ը․ օգտագործեք աջակցվող n8n export/import կամ migration procedure, ապա առանձին target-ում ստուգեք workflow-ներն ու encrypted credential-ները։ Սկզբնական file-երը պահեք rollback-ի համար և recovery preparation-ի համար օգտագործեք ստորև հղված Backup & Restore ուղեցույցը։ Երբեք մի ջնջեք database.sqlite որպես shortcut։

WORKER CONCURRENCY

Worker-ները scale են լինում և՛ քանակով, և՛ մեկ worker-ի job-երի քանակով

Յուրաքանչյուր worker կարող է միաժամանակ մշակել մի քանի job։ n8n-ի ընթացիկ default worker concurrency-ն 10 է, իսկ documentation-ը խորհուրդ է տալիս 5 կամ ավելի concurrency։ Շատ ցածր concurrency-ն բազմաթիվ worker-ների հետ կարող է ստեղծել ավելորդ database connection-ներ և սպառել database connection pool-ը։

Բարձրացրեք concurrency-ն, երբ

Worker-ն ունի ազատ CPU և RAM, իսկ workflow-ները հիմնականում սպասում են արտաքին service-ների, ոչ թե հագեցնում compute-ը կամ memory-ն։

Ավելացրեք worker-ներ, երբ

Մեկ worker process-ը դառնում է bottleneck, իսկ database-ը, Redis-ը և ենթակառուցվածքն ունեն capacity ավելի շատ parallel execution-ի համար։

Նվազեցրեք concurrency-ն, երբ

Առանձին workflow-ները memory-heavy կամ CPU-heavy են, իսկ parallel job-երը ստեղծում են contention, OOM pressure կամ անկայուն execution time-եր։

Հետևեք PostgreSQL-ին

Ավելի շատ worker և ավելի մեծ concurrency մեծացնում են database activity-ն։ Execution capacity-ն առանց database capacity-ի մեծացնելը կարող է bottleneck-ը պարզապես տեղափոխել, ոչ վերացնել։

Հստակ իմացեք, թե որ concurrency limit-ն է իրականում գործում։ Worker-ը կարելի է գործարկել n8n worker --concurrency=5հրամանով կամ ձեր Compose service-ի համարժեք worker command-ով։ Եթե N8N_CONCURRENCY_PRODUCTION_LIMIT հստակ սահմանված է այլ արժեքի, քան -1՝ queue mode-ում այդ setting-ն ունի առաջնահերթություն․ հակառակ դեպքում n8n-ը օգտագործում է worker-ի --concurrency արժեքը կամ default 10-ը։ Worker-ների քանակը մի բազմապատկեք nominal default-ով և մի անվանեք դա երաշխավորված throughput․ իրական capacity-ն կախված է job duration-ից, CPU-ից, memory-ից, արտաքին API-ներից և PostgreSQL connection-ներից։

WEBHOOK-ՆԵՐ

Queue mode-ը կարող է ավելացնել execution handoff latency

Main կամ webhook process-ը ստանում է HTTP request-ը, բայց workflow execution-ը կատարում է worker-ը։ Redis-ի միջով այդ handoff-ը որոշ overhead է ավելացնում։ Latency-sensitive webhook-ների համար չափեք end-to-end response time-ը՝ փոխանակ ենթադրելու, որ ավելի շատ worker ավտոմատ արագացնում է յուրաքանչյուր request։

ՍտացումMain/webhook process-ը ընդունում է request-ը։
QueueExecution-ը փոխանցվում է Redis-ին։
ԿատարումՀասանելի worker-ը գործարկում է workflow-ը։
ՊատասխանԱնհրաժեշտության դեպքում արդյունքը queue path-ով փոխանցվում է հետ։

Webhook traffic-ը ուղղեք ճիշտ process-ին։ Dedicated n8n webhook processor-ների դեպքում reverse proxy-ի կամ load balancer-ի հետևում production path-երը ուղղեք /webhook/* և /webhook-waiting/* webhook processor-ներին, իսկ /webhook-test/*editor և API request-ները պահեք main-ի վրա։ Main-ը մի ներառեք production webhook load-balancing pool-ում, եթե գիտակցաբար չեք ընդունում լրացուցիչ workload-ը։ Respond to Webhook workflow-ը կարող է client-ին սպասեցնել մինչև worker-ը ավարտի և վերադարձնի պատասխանը, ուստի queue mode-ը instant HTTP response-ների կամ zero timeout-ների խոստում չէ։ Traffic-ը փոխելուց առաջ փորձարկեք իրական արտաքին callback-ը և response behavior-ը։

ԵՐԿՈՒԱԿԱՆ ՏՎՅԱԼՆԵՐ

Մի անտեսեք shared storage-ը

Filesystem սահմանափակում

Queue mode-ը distributed worker-ների համար filesystem binary-data storage-ը որպես shared persistence model չի աջակցում։

Արտաքին binary storage

Երբ workflow-ները պետք է binary data պահպանեն distributed worker-ների միջև, օգտագործեք storage design, որը հասանելի է բոլոր անհրաժեշտ instance-ներին, օրինակ՝ աջակցվող external object storage։

Մեծ webhook response-ներ

Worker-ների webhook response-ները հետ են անցնում դեպի ընդունող process։ Մեծ response body-ները կարող են բարձրացնել Redis memory pressure-ը և պահանջել նպատակային response-storage configuration։

Պլանավորեք worker-ները բաշխելուց առաջ

Local file-երից մեծապես կախված workload-ը պետք է վերաձևավորվի shared persistence-ի համար մինչև worker-ները տարբեր machine-ների վրա բաշխելը։

Մեծ webhook response-ի սահմանը։ Ընթացիկ n8n documentation-ը N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX համար սահմանում է default 64 MiB worker-ի queue-ով հետ ուղարկվող response-ի համար։ Redis-ը կարող է միաժամանակ պահել մի քանի copy, ուստի յուրաքանչյուր concurrent մեծ response-ի համար Redis memory-ում հաշվարկեք մոտ 1.5 անգամ response size։ Առանց offloading-ի չափազանց մեծ response-ը fail կլինի, ոչ թե worker-ներ ավելացնելով հրաշքով կարագանա։

Version-ի և license-ի սահմանափակումներ։ n8n 2.34.0-ից սկսած worker-ները կարող են օգտագործել N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true ՝ չափազանց մեծ webhook response body-ները readable shared binary storage offload անելու համար, բայց նախ upgrade արեք բոլոր main և webhook processor-ները մինչև 2.34.0 կամ ավելի նոր։ Ընտրված N8N_DEFAULT_BINARY_DATA_MODE իրականում պետք է պահի տվյալները և ընթեռնելի լինի յուրաքանչյուր մասնակցող process-ի համար։ External S3 և Azure binary storage-ը պահանջում է վավեր self-hosted Business կամ Enterprise license․ մի ենթադրեք, որ Community Edition-ը կարող է դրանք միացնել։ database binary mode-ը կարող է չափազանց մեծ response offload անել առանց վճարովի external storage-ի, բայց main instance-ը ամբողջ պահպանված body-ն բեռնում է memory, իսկ database storage-ն ունի իր file-size limit-ը։ Հատկապես response-body offload-ի համարn8n-ը նաև նկարագրում է shared filesystem տարբերակ, երբ յուրաքանչյուր instance mount է անում նույն disk-ը, բայց հստակ չի խորհուրդ տալիս այդ arrangement-ը։ Այս հատուկ offload path-ը մի շփոթեք distributed queue-mode deployment-ում filesystem-based persistent binary data-ի աջակցության հետ։ Offload-ը միացնելուց առաջ ստուգեք ձեր edition-ը, version-ը և storage configuration-ը։

ՄՈՆԻՏՈՐԻՆԳ

Իմացեք՝ queue-ն օգնում է, թե ոչ

Queue-ի խորություն

Queue-ն, որը աճում է ավելի արագ, քան worker-ները դատարկում են այն, ցույց է տալիս execution capacity-ի պակաս կամ downstream bottleneck։

Worker-ի CPU & RAM

Չափեք saturation-ը և memory peak-երը յուրաքանչյուր worker-ի համար։ Աճող queue-ի հետ idle worker-ները ցույց են տալիս այլ constraint։

Execution-ի ուշացում

Հետևեք execution-ի ստեղծման և իրական մեկնարկի միջև delay-ին, ոչ միայն workflow runtime-ին։

Health check-եր

Worker health endpoint-ները կարող են ցույց տալ՝ worker-ը կենդանի է, թե ոչ, և database/Redis connection-ները ready են, թե ոչ։

Ստուգեք execution-ը worker-ի վրա, ոչ միայն green container-ը։ Ճիշտ կարգավորված Compose stack-ում ստուգեք docker compose ps և docker compose logs --tail=100 n8n-worker (service name-ը փոխարինեք, եթե այլ է)։ Գործարկեք անվնաս հրապարակված production workflow՝ scheduled trigger-ով կամ test webhook-ով, ապա n8n-ի Executions view-ում դրա execution-ը համադրեք worker log-երում իրական worker processing-ի հետ։ Հաջող բացվող editor-ը, աշխատող Redis container-ը կամ միայն queued execution-ը չէ չի ապացուցում, որ worker-ը կատարել է job-ը։

Ստուգեք dependency-ները և readiness-ը։ Default օրինակ service name-երով docker compose exec -T redis redis-cli ping պետք է ստանա PONG երբ Redis authentication-ը թույլ է տալիս, իսկ docker compose exec -T postgres pg_isready -U n8n -d n8n ստուգում է PostgreSQL readiness-ը (հարմարեցրեք credential-ներն ու service name-երը)։ Միացրեք QUEUE_HEALTH_CHECK_ACTIVE=true worker-ի վրա, երբ պետք են նրա private /healthz և /healthz/readiness endpoint-ները․ readiness endpoint-ը ստուգում է Redis/database connectivity-ն։ Մի expose արեք այդ worker endpoint-ները public միայն monitoring-ի համար։

Manual run-երը այլ test են։ Default-ով OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=falseուստի editor-ում workflow-ի manual run-ը կարող է կատարվել main-ի վրա նույնիսկ ճիշտ կարգավորված queue mode-ի դեպքում։ Սահմանեք true միայն եթե ցանկանում եք manual execution-ները ուղարկել worker-ներին և փոփոխությունը ստուգել եք staging environment-ում։ Queue-mode worker-ները նաև տարբերվում են n8n external task runner-ներից, որոնք Code node execution-ի համար ունեն առանձին configuration requirement-ներ։

ՄԱՍՇՏԱԲԱՎՈՐՄԱՆ ՈՒՂԻ

Scale արեք մեկ bottleneck միաժամանակ

Փուլ 1Մեկ n8n instance PostgreSQL-ով․ չափեք peak CPU-ն, RAM-ը և concurrency-ն։
Փուլ 2Ավելացրեք VPS resource-ները, երբ vertical scaling-ը դեռ մաքուր լուծում է չափված bottleneck-ը։
Փուլ 3Ավելացրեք Redis և worker-ներ, երբ կայուն parallel demand-ը հիմնավորում է distributed execution-ը։
Փուլ 4Ավելացրեք worker-ներ կամ կարգավորեք worker concurrency-ն՝ միաժամանակ հետևելով PostgreSQL-ին, Redis-ին և execution latency-ին։
Փուլ 5Բաղադրիչները տարբեր server-ների վրա բաժանեք միայն այն ժամանակ, երբ capacity-ի, availability-ի կամ operational requirement-ների պատճառով լրացուցիչ complexity-ն հիմնավորված է։
Ընտրել ավելի մեծ VPS capacity, երբ scaling-ը դա պահանջում է

Գործընկերային հղում․ գնումներից կարող ենք միջնորդավճար ստանալ։

HIGH AVAILABILITY-Ի ՍԱՀՄԱՆԸ

Queue mode-ը scale է անում execution-ները, բայց main process-ը ավտոմատ highly available չի դարձնում

Կիսեք encryption key-ը

Յուրաքանչյուր worker պետք է օգտագործի նույն N8N_ENCRYPTION_KEY ինչ main instance-ը, որպեսզի worker-ները կարողանան decrypt անել workflow execution-ներին անհրաժեշտ credential-ները։

Version-ները պահեք նույնը

Main, webhook և worker process-ները պետք է աշխատեն նույն n8n version-ով։ Տարբեր version-ները rolling change-երի ժամանակ կարող են առաջացնել անհամատեղելի վարք։

Webhook processor-ները scaling-ի առանձին layer են

Երբ incoming webhook volume-ը դառնում է bottleneck, dedicated webhook processor-ները կարող են աշխատել load balancer-ի հետևում, մինչ worker-ները կատարում են execution-ը։ Այս layer-ը մի ավելացրեք, եթե չափված request volume-ը դա չի հիմնավորում։

Multi-main-ը այլ feature է

High availability-ի համար մի քանի main process գործարկելն այն չէ, ինչ սովորական queue mode-ը։ n8n-ն այժմ multi-main-ը փաստաթղթավորում է որպես self-hosted Enterprise feature՝ լրացուցիչ load-balancer և session requirement-ներով։

FAQ

n8n queue mode․ հաճախ տրվող հարցեր

n8n queue mode-ը Redis պահանջո՞ւմ է։

Այո։ Redis-ը message broker է, որը main instance-ի և worker-ների միջև համակարգում է pending execution-ները։

Queue mode-ը կարո՞ղ է SQLite օգտագործել։

Distributed queue-mode architecture-ի համար՝ ոչ։ Main-ին և worker-ներին պետք է shared database access, իսկ n8n-ն այս setup-ի database-ը փաստաթղթավորում է PostgreSQL-ը։

Քանի՞ worker գործարկել։

Համընդհանուր թիվ չկա։ Սկսեք չափված concurrency-ից և worker utilization-ից, ապա capacity ավելացրեք՝ հետևելով PostgreSQL-ին, Redis-ին, CPU-ին, RAM-ին և queue depth-ին։

Ի՞նչ է n8n worker concurrency-ն։

Դա այն job-երի քանակն է, որոնք worker-ը կարող է parallel մշակել։ Ընթացիկ default-ը 10 է, իսկ n8n-ը խորհուրդ է տալիս worker concurrency 5 կամ ավելի՝ բազմաթիվ low-concurrency worker ստեղծելու փոխարեն։

Պե՞տք է queue mode միացնել փոքր VPS-ում։

Միայն երբ workload-ը դա հիմնավորում է։ Փոքր deployment-ը, որը մեկ instance-ով հանգիստ աշխատում է, սովորաբար ավելի պարզ է կառավարել առանց Redis-ի և առանձին worker-ների։
