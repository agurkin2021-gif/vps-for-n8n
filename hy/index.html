Գործարկեք ձեր ընտրած stack-ը, միացրեք ներքին ծառայությունները և թարմացումները պլանավորեք ձեր բիզնեսի ռեժիմին համապատասխան։ Սա հարմար է Linux-ին և Docker-ին տիրապետող թիմերի համար, որոնք ցանկանում են ինքնուրույն կառավարել ենթակառուցվածքը։

Կառավարվող հոսթինգի համար ընտրեք Cloud

n8n Cloud-ը հոգում է հոսթինգի հարթակի մասին։ Համեմատեք դրա execution սահմանաչափերն ու ներառված հնարավորությունները ձեր ծանրաբեռնվածության հետ, երբ գործառնական հարմարությունն ավելի կարևոր է, քան սերվերի մակարդակի հարմարեցումը։

Մեկ սեղմումով image-ը արագացնում է տեղադրումը, իսկ հավելվածի շարունակական կառավարումը առանձին ծառայություն է։ Համեմատեք VPS-ը և n8n Cloud-ը.

ԳՆԵՔ ԱՅՆ ՌԵՍՈՒՐՍԸ, ՈՐԸ ՕԳՏԱԳՈՐԾՈՒՄ ԵՆ ՁԵՐ WORKFLOW-ՆԵՐԸ

Ինչին ուշադրություն դարձնել n8n VPS ընտրելիս

Աշխատանքային տվյալների համար առաջնահերթություն տվեք RAM-ին, տեղային մշակման համար՝ CPU-ին, իսկ պահվող պատմության և ֆայլերի համար՝ պահեստին։ Հաշվի առեք նաև տվյալների բազան և VPS-ը կիսող մյուս հավելվածները։

Գնահատեք execution պատմության պահեստային ծավալը

Օգտագործեք օրական պահպանված execution-ներ × միջին պահպանված չափ × պահպանման օրեր։ Օրինակ՝ 1,000 պահպանված execution × 200 KB × 14 օր՝ մոտ 2.8 GB պահպանված execution տվյալներ՝ տասնորդական միավորներով։

Ավելացրեք տարածք տվյալների բազայի index-ների և log-երի, OS-ի, container-ների և workflow ֆայլերի համար։ Հաշվարկում օգտագործեք ձեր իրականում դիտարկված պահպանված չափը։ Retention-ը կարող է նվազեցնել պահեստի պահանջը՝ առանց CPU-ն կամ RAM-ը փոխելու։ Execution-data կարգավորումներ։

ՀիշողությունՌեսուրս թողեք n8n-ի, տվյալների բազայի և համընկնող գործարկումների ընթացքում պահվող տվյալների համար։ Մեծ ֆայլերն ու փոխակերպումները պահանջը փոխում են ավելի շատ, քան պահպանված workflow-ների քանակը։
CPUՏևական տեղային հաշվարկների համար ընտրեք ավելի մեծ հաշվարկային հզորություն։ Համեմատեք ոչ միայն միջուկների քանակը, այլ նաև CPU-ի հատկացումը․ shared և dedicated առաջարկները տարբեր են։
ՊահեստՕգտագործեք SSD կամ NVMe պահեստ և ընտրեք ծավալ՝ ըստ իրականում պահվող տվյալների։ Վերականգնման պատճենները պահեք սերվերից դուրս, որպեսզի դրանք պահպանվեն VPS-ի կորստի դեպքում։
ՄիջավայրԸնտրեք Linux՝ ադմինիստրատիվ հասանելիությամբ և Docker-ի աջակցությամբ։ Webhook-ների համար օգտագործեք հանրային HTTPS hostname, իսկ հավելվածի ծառայությունների միջև՝ մասնավոր ցանց։
Ցանց և տարածաշրջանԵթե մատակարարն առաջարկում է մի քանի տարածաշրջան, VPS-ը տեղադրեք այն տվյալների բազաների, API-ների կամ օգտատերերի մոտ, որոնք ստեղծում են հիմնական network round-trip-երը։ Ֆայլատար workflow-ների դեպքում bandwidth-ն ու transfer policy-ն նույնպես դառնում են ռեսուրսային ընտրության մաս, իսկ տարածաշրջանը կարող է կարևոր լինել տվյալների տեղակայման պահանջների համար։
Աջակցության սահմաններըՎճարումից առաջ ճշտեք, թե մատակարարն ինչ է աջակցում։ Ինքնուրույն կառավարվող VPS-ի դեպքում նախատեսեք, որ n8n-ի թարմացումները, կոնֆիգուրացիան և վերականգնումը ձեր պատասխանատվությունն են, եթե հավելվածի մակարդակի կառավարումը հստակ ներառված չէ։

ՀՍՏԱԿ ՄԱՍՇՏԱԲԱՎՈՐՄԱՆ ՈՒՂԻ

Սկսեք մեկ instance-ից։ Worker-ներ ավելացրեք ըստ անհրաժեշտության։

Հանրային HTTPS→Reverse proxy→n8n↔PostgreSQL

Մեկ n8n instance-ը փոքր տեղակայումը պարզ է պահում։ Երբ առաջադրանքները կուտակվում են execution հզորության սահմանափակման պատճառով, queue mode-ը մուտքային trigger-ները բաժանում է workflow-ները կատարող worker գործընթացներից։

Պլանավորեք ռեսուրսներ հիմնական process-ի, PostgreSQL-ի, Redis-ի և յուրաքանչյուր worker-ի համար։ Worker-ները կիսում են տվյալների բազայի և կոդավորման բանալու հասանելիությունը։ Ֆայլատար queue-ների համար ընտրեք աջակցվող shared binary storage։ Պլանավորեք queue mode-ը և worker-ները · Queue architecture-ի պաշտոնական նկարագրություն։

ԱՎԱՐՏԵՔ ՁԵՐ ՏԵՂԱԿԱՅՈՒՄԸ

Պատրաստեք ձեր n8n միջավայրը ամենօրյա աշխատանքի համար

01

Ապահովեք տվյալների կայուն պահպանումը

n8n-ին և տվյալների բազային տվեք persistent volume-ներ։ Ստուգեք, որ workflow-ներն ու credentials-ը հասանելի են մնում container-ի վերագործարկումից հետո։

02

Միացրեք անվտանգ endpoint

Կարգավորեք HTTPS-ն ու authentication-ը, սահմանեք հանրային webhook URL-ը և տվյալների բազայի ներքին port-երը պահեք փակ։ Անվտանգության ստուգաթերթ.

03

Վերականգնումը պարզ պահեք

Տվյալների բազան, կոնֆիգուրացիան, կոդավորման բանալին և անհրաժեշտ ֆայլերը backup արեք առանձին վայրում։ Ստուգեք վերականգնման գործընթացը։ Backup և վերականգնում.

04

Պլանավորեք սպասարկումը

Որոշեք՝ երբ թարմացնել հավելվածը, ուսումնասիրեք release-ի փոփոխությունները և թարմացումներից հետո ստուգեք կարևոր workflow-ները։ Հետևեք execution ձախողումներին, ռեսուրսների օգտագործմանը և certificate-ի թարմացմանը։

ԲՅՈՒՋԵՆ ՈՒՂՂԵՔ ԱՅՆՏԵՂ, ՈՐՏԵՂ ԱՅՆ ՕԳՏԱԿԱՐ Է

Ավելի շատ RAM, ավելի շատ CPU, թե՞ workflow-ի փոփոխություն։

01 · ՀԻՇՈՂՈՒԹՅՈՒՆ

Խոշոր աշխատանքային dataset-ների համար

Ստուգեք հիշողության օգտագործումը, երբ ձեր ամենախոշոր առաջադրանքները համընկնում են։ Ներմուծումները մշակեք ավելի փոքր խմբաքանակներով և վերադարձեք միայն հաջորդ քայլին անհրաժեշտ տվյալները։

Ավելացրեք RAM-ը երբ այդ փոփոխություններից հետո ծանրաբեռնվածությունը դեռ լցնում է հիշողությունը։

02 · ՄՇԱԿՈՒՄ

Դանդաղ փոխակերպումների համար

Համեմատեք տեղային մշակման ժամանակը արտաքին ծառայությունների սպասման ժամանակի հետ։ Տեղային աշխատանքի ընթացքում երկարատև CPU ծանրաբեռնվածությունը ցույց է տալիս ավելի շատ հաշվարկային հզորության կարիք։

Պահեք CPU-ի ներկա մակարդակը երբ սահմանափակող գործոնը API-ի պատասխանն է կամ rate limit-ը։

03 · ՊԱՀԵՍՏ

Աճող execution պատմության համար

Որոշեք՝ execution-ի որ արդյունքները պահել և որքան ժամանակ։ Պահեստի բյուջեում ներառեք workflow ֆայլերն ու տվյալների բազայի աճը։

Ընտրեք ավելի մեծ սկավառակ երբ պահպանման ենթակա պատմությունը գերազանցում է հասանելի տարածքը։

04 · ԶՈՒԳԱՀԵՌ ԱՌԱՋԱԴՐԱՆՔՆԵՐ

Համընկնող կտրուկ հոսքերի համար

Նախ ժամանակով բաժանեք պլանավորված ներմուծումները։ Worker-ներ ավելացրեք, երբ սպասող առաջադրանքները ցույց են տալիս execution հզորության սահմանափակում, իսկ տվյալների բազան և worker ռեսուրսները կարող են սպասարկել ավելի շատ զուգահեռ աշխատանք։

Worker-ներն ու նրանց ռեսուրսները մեծացրեք միասին։

Docker տեղակայման համար վճարովի web-hosting panel-ը պարտադիր չէ։ Հոսթինգավորված AI API կանչերի համար տեղային GPU hardware պետք չէ։ Բյուջեն պահեք այն RAM-ի, մշակման, պահեստի և վերականգնման համար, որոնք ձեր իրական workflow-ին անհրաժեշտ են։

Օգտագործեք docker stats, host-ի սկավառակի օգտագործումն ու execution log-երը՝ փոփոխությունից առաջ և հետո ամենածանրաբեռնված շրջանը համեմատելու համար։ n8n performance-ի չափում · Concurrency control-ներ։

ՀԱՍԿԱՆԱԼԻ ԲՅՈՒՋԵ

Ինչի համար եք վճարում n8n-ը ինքնուրույն հոսթինգ անելիս
