உற்பத்தி பாதுகாப்பு

VPS இல் n8n பாதுகாக்கவும்

VPS இல் n8n ஐப் பாதுகாக்க, n8n (5678), PostgreSQL (5432) மற்றும் விருப்பமான Redis (6379) ஆகியவற்றைப் பொது இணையத்திலிருந்து விலக்கி வைக்கவும்; HTTPS தலைகீழ் ப்ராக்ஸி, SSH விசைகள் மற்றும் MFA ஐப் பயன்படுத்தவும், உங்கள் குறியாக்க விசையைப் பாதுகாக்கவும், வெப்ஹூக்குகளை அங்கீகரிக்கவும், அபாயகரமான பணிப்பாய்வு திறன்களைக் கட்டுப்படுத்தவும் மற்றும் பயன்படுத்தப்பட்ட நிகழ்வைத் தணிக்கை செய்யவும். பொது வெப்ஹூக் வழிகளிலிருந்து தனித்தனியாக எடிட்டரைப் பாதுகாக்கவும். HTTPS மட்டும் இணைக்கப்பட்ட சேவைகளைப் பாதுகாக்காது.

n8n க்கு VPS ஐத் தேர்ந்தெடுக்கவும்

கூட்டாளர் இணைப்பு: வாங்குதல்களிலிருந்து நாங்கள் கமிஷனைப் பெறலாம்.

விரைவான சரிபார்ப்பு பட்டியல்

பொது வெளிப்பாட்டிற்கு முன் குறைந்தபட்ச பாதுகாப்பு அடிப்படை

உங்கள் அணுகக்கூடிய போர்ட்கள், HTTPS, சரிபார்க்கப்பட்ட நிர்வாக அணுகல், MFA மற்றும் சேமிக்கப்பட்ட நற்சான்றிதழ்களின் பாதுகாப்பு ஆகியவற்றுடன் தொடங்கவும். ஒவ்வொரு உள்வரும் வெப்ஹூக்கையும் அது முக்கியமான வேலையைத் தூண்டும் முன் அங்கீகரிக்கவும். அணுகல் கட்டுப்பாடுகளை மாற்றிய பிறகு, எடிட்டர்கள் மற்றும் வெளிப்புற ஒருங்கிணைப்புகள் இன்னும் செயல்படுகின்றனவா என்பதைச் சரிபார்த்து, n8n பாதுகாப்பு தணிக்கையை இயக்கவும்.

HTTPS மட்டுமே

சரியாக உள்ளமைக்கப்பட்ட TLS ரிவர்ஸ் ப்ராக்ஸியின் பின்னால் n8n ஐ வைத்து, எடிட்டர் மற்றும் வெப்ஹூக்குகளுக்கு பொது HTTPS URL ஐ தொடர்ந்து பயன்படுத்தவும்.

குறைந்தபட்ச திறந்த துறைமுகங்கள்

பொது போக்குவரத்துக்கு தேவையான துறைமுகங்களை மட்டும் அம்பலப்படுத்தவும். PostgreSQL, Redis மற்றும் உள் பயன்பாட்டு போர்ட்களை பொது இணையத்திலிருந்து விலக்கி வைக்கவும்.

கடினப்படுத்து SSH

விசை அடிப்படையிலான நிர்வாகத்தைப் பயன்படுத்தவும், யார் உள்நுழையலாம் என்பதைக் கட்டுப்படுத்தவும் மற்றும் இயக்க முறைமையை இணைக்கவும்.

நற்சான்றிதழ்களைப் பாதுகாக்கவும்

n8n குறியாக்க விசையை நிலையானதாகவும் ரகசியமாகவும் வைத்திருங்கள். சூழல் கோப்புகள், தரவுத்தள அணுகல் மற்றும் காப்பு பிரதிகள் ஆகியவற்றை முக்கியமான சொத்துகளாகக் கருதுங்கள்.

நெட்வொர்க் எட்ஜ்

ரிவர்ஸ் ப்ராக்ஸி, HTTPS மற்றும் நம்பகமான தலைப்புகள்

TLS முடித்தல்

HTTPS ஐ முடிக்க Nginx, Caddy அல்லது Traefik போன்ற தலைகீழ் ப்ராக்ஸியைப் பயன்படுத்தவும். சாதாரண HTTP ஐத் திருப்பிவிடவும் மற்றும் ப்ராக்ஸியானது நுழைவுப் புள்ளியாக இருக்கும் போது n8n பயன்பாட்டு போர்ட்டை நேரடியாக வெளிப்படுத்துவதைத் தவிர்க்கவும்.

ப்ராக்ஸி கட்டமைப்பு

n8n ஒரு தலைகீழ் ப்ராக்ஸிக்கு பின்னால் இயங்கும் போது, ப்ராக்ஸி ஹாப் எண்ணிக்கையை சரியாக உள்ளமைத்து, அசல் கிளையன்ட் கோரிக்கையை மறுகட்டமைக்க n8n க்கு அனுப்பப்பட்ட தலைப்புகளை அனுப்பவும்.

பாதுகாப்பான குக்கீகள்

HTTPS க்கு மேல் எடிட்டரைப் பரிமாறவும், இதனால் அங்கீகரிப்பு குக்கீகள் பாதுகாப்பாக இருக்கும். குக்கீ பாதுகாப்பை பலவீனப்படுத்துவதன் மூலம் உடைந்த TLS அமைப்பைச் சுற்றி வேலை செய்ய வேண்டாம்.

Webhook URL

பொது வெப்ஹூக் URL ஐ வெளிப்புறமாக அணுகக்கூடிய HTTPS ஹோஸ்ட்பெயருக்கு அமைக்கவும், அதனால் உருவாக்கப்பட்ட வெப்ஹூக் எண்ட்பாயிண்ட்கள் உள் கொள்கலன் அல்லது HTTP முகவரியைக் குறிக்காது.

வெப்ஹூக்குகளை உடைக்காமல் எடிட்டரை தனிப்பட்டதாக வைத்திருங்கள். நடைமுறையில் VPN, நம்பகமான-IP கொள்கை அல்லது அங்கீகரிக்கப்பட்ட ப்ராக்ஸியைப் பயன்படுத்தி நிர்வாக அணுகலைக் கட்டுப்படுத்தவும். பொது வெப்ஹூக் பெறுநர்கள் மற்றும் OAuth திரும்ப அழைக்கும் வழிகள் தொடர்ந்து அணுகக்கூடியதாக இருக்க வேண்டும்; ப்ராக்ஸி விதியைச் செயல்படுத்துவதற்கு முன் நம்பகமான எடிட்டர் உள்நுழைவு மற்றும் உண்மையான வெளிப்புற அழைப்பு இரண்டையும் சோதிக்கவும். வாடிக்கையாளர்-முகவரி தலைப்புகளை நம்பகமான ப்ராக்ஸிகளிடமிருந்து மட்டுமே அனுப்பவும், தன்னிச்சையான கோரிக்கை தலைப்புகள் அல்ல.

வெப்ஹூக் அழைப்பாளர்களை அங்கீகரிக்கவும்: Webhook முனையில் அனுப்புநர் ஆதரிக்கும் போது இல்லை என்பதற்குப் பதிலாக அடிப்படை, தலைப்பு அல்லது JWT அங்கீகாரத்தைத் தேர்ந்தெடுக்கவும். அதை பயன்படுத்தவும் IP(கள்) அனுமதிப்பட்டியல் பொருத்தமான இடத்தில் விருப்பம், மற்றும் கையொப்பமிடப்பட்ட கோரிக்கைகளை ஒருங்கிணைப்பு ஆதரிக்கும் வழங்குநரின் கையொப்பங்களை சரிபார்க்கவும். யூகிக்க கடினமான URL போதுமான அங்கீகாரம் இல்லை. பொருத்தமான போது ப்ராக்ஸியில் கட்டண வரம்புகளைப் பயன்படுத்தவும் மற்றும் சரியான வெடிப்புகள் தடுக்கப்படவில்லை என்பதை உறுதிப்படுத்தவும். அதிகாரப்பூர்வ Webhook அங்கீகார விருப்பங்கள்.

VPS கடினப்படுத்துதல்

சர்வர் தாக்குதல் மேற்பரப்பைக் குறைக்கவும்

ஃபயர்வால்

இயல்புநிலை - கோரப்படாத உள்வரும் போக்குவரத்தை மறுத்து, அணுகக்கூடிய சேவைகளை மட்டும் அனுமதிக்கவும். தரவுத்தளம் மற்றும் Redis போர்ட்கள் பொதுவாக தனியார்/உள்ளூர் நெட்வொர்க்குகளுக்கு சொந்தமானது.

SSH

கடவுச்சொற்களை விட SSH விசைகளை விரும்பவும், தேவையற்ற உள்நுழைவு பாதைகளை முடக்கவும் மற்றும் நிர்வாக அணுகலை கட்டுப்படுத்தவும். ரூட் சமமான அணுகல் இறுக்கமாக கட்டுப்படுத்தப்பட வேண்டும்.

OS புதுப்பிப்புகள்

Linux ஹோஸ்ட் மற்றும் கொள்கலன் இயக்க நேரத்தை இணைக்கவும். பயன்பாட்டு கடினப்படுத்துதல் வெளிப்பட்ட அல்லது காலாவதியான இயக்க முறைமைக்கு ஈடுசெய்ய முடியாது.

கொள்கலன் வெளிப்பாடு

ஹோஸ்ட் அணுகல் தேவைப்படும் போர்ட்களை மட்டும் வெளியிடவும். உள் சேவைகள் பொது இடைமுகங்கள் மூலம் அல்லாமல் தனியார் Docker நெட்வொர்க்குகளில் தொடர்பு கொள்ள வேண்டும்.

ஃபயர்வால் அல்லது SSH அமைப்புகளை மாற்றுவதற்கு முன் சரிபார்க்கவும்: கேட்கும் துறைமுகங்களைச் சரிபார்க்கவும் sudo ss -lntp, Docker உடன் வெளியிடுதல் docker compose ps திட்டக் கோப்பகத்திலிருந்து, மற்றும் ஹோஸ்ட் ஃபயர்வால் கொள்கை sudo ufw status verbose UFW பயன்படுத்தப்பட்டால். கடவுச்சொல் அணுகலை முடக்கும் முன், உங்கள் உண்மையான SSH போர்ட் மற்றும் வெற்றிகரமான கீ உள்நுழைவை தனி அமர்வில் சரிபார்க்கவும். வெளியிடப்பட்ட Docker போர்ட்கள் UFW விதிகளைத் தவிர்க்கலாம்; ஒரு ஃபயர்வால் நிலைப் பக்கம் மட்டும் போர்ட் 5678 தனிப்பட்டது என்பதை நிரூபிக்கவில்லை. உண்மையான வெளிப்புற அணுகலைச் சரிபார்க்கவும். Docker/UFW எச்சரிக்கை.

தானாக Ubuntu பாதுகாப்பு புதுப்பிப்புகள் செயல்படுகின்றன என்று கருதுவதற்குப் பதிலாக அவற்றைச் சரிபார்க்கவும்: ஆய்வு apt-config dump APT::Periodic::Unattended-Upgrade மற்றும் பதிவு /var/log/unattended-upgrades/unattended-upgrades.log. கவனிக்கப்படாத பாதுகாப்பு மேம்படுத்தல்கள் முடக்கப்பட்டால், sudo dpkg-reconfigure unattended-upgrades ஆதரிக்கப்படும் கட்டமைப்பு உரையாடலை வழங்குகிறது. பணிபுரியும் VPS இல் அதை இயக்குவதற்கு முன் மறுதொடக்கம் மற்றும் சேவை-மறுதொடக்கம் நடத்தையை மதிப்பாய்வு செய்யவும். Ubuntu APT புதுப்பிப்புகள் செய்யப்படுகின்றன இல்லை n8n Docker படத்தை அல்லது ஒவ்வொரு மூன்றாம் தரப்பு மென்பொருள் களஞ்சியத்தையும் தானாகவே புதுப்பிக்கவும். Ubuntu தானியங்கு-புதுப்பிப்பு ஆவணங்கள்.

விருப்பமான SSH ப்ரூட்-ஃபோர்ஸ் கண்காணிப்பு: மீண்டும் மீண்டும் தோல்வியடைந்த SSH உள்நுழைவுகளை Fail2Ban கண்டறிய முடியும்.
