விரைவான முடிவு

உங்களுக்கு உண்மையில் வரிசை முறை தேவையா?

எப்போது வழக்கமான பயன்முறையில் இருங்கள்

ஒரு ஒற்றை நிகழ்வு உச்சநிலைச் செயலாக்கங்களை வசதியாகக் கையாளுகிறது மற்றும் CPU, RAM மற்றும் செயல்படுத்தல் தாமதம் நிலையாக இருக்கும். வரிசை முறை உங்களுக்கு இதுவரை தேவையில்லாத கூறுகளைச் சேர்க்கிறது.

எப்போது வரிசை பயன்முறையைக் கவனியுங்கள்

தொடர்ச்சியான இணையான மரணதண்டனைகள் சர்ச்சையை உருவாக்குகின்றன, செயல்படுத்தல் தாமதம் சுமையின் கீழ் அதிகரிக்கிறது அல்லது பல பணியாளர்களை இயக்குவதன் மூலம் நீங்கள் செயல்படுத்தும் திறனைச் சேர்க்க வேண்டும்.

எப்போது செங்குத்தாக முதலில் அளவிடவும்

இடையூறு CPU அல்லது RAM போதுமானதாக இல்லை, மேலும் ஒரு பெரிய நிகழ்வு இன்னும் பணிச்சுமையை சுத்தமாக சந்திக்க முடியும்.

கட்டிடக்கலையை மாற்றுவதற்கு முன் அளவிடவும்

நகர்வை நியாயப்படுத்த, உச்சநிலை ஒத்திசைவு, CPU, RAM, செயல்படுத்தும் காலம், வரிசை ஆழம் மற்றும் தரவுத்தள அழுத்தம் ஆகியவற்றைப் பயன்படுத்தவும்.

கட்டிடக்கலை

n8n வரிசை முறை எவ்வாறு செயல்படுகிறது

1 · முதன்மைடைமர்கள், வெப்ஹூக்குகள் மற்றும் பணிப்பாய்வு கோரிக்கைகளைப் பெறுகிறது மற்றும் உற்பத்தி செயல்படுத்தலைச் செய்வதற்குப் பதிலாக ஒரு செயல்பாட்டை உருவாக்குகிறது.
2 · Redisசெய்தி தரகராக செயல்படுகிறது. இது நிலுவையில் உள்ள செயல்படுத்தல் செய்திகளை வைத்திருப்பதால், அடுத்து கிடைக்கும் தொழிலாளி வேலையைக் கோர முடியும்.
3 · தொழிலாளிசெயல்படுத்தல் ஐடியைப் பெறுகிறது, பகிரப்பட்ட தரவுத்தளத்திலிருந்து பணிப்பாய்வு தரவை ஏற்றுகிறது, பணிப்பாய்வுகளை இயக்குகிறது மற்றும் முடிவை மீண்டும் எழுதுகிறது.
4 · PostgreSQLபகிரப்பட்ட நிலையான பணிப்பாய்வு மற்றும் செயல்படுத்தல் தரவை வழங்குகிறது. SQLite க்கு மேல் விநியோகிக்கப்பட்ட வரிசை முறை ஆதரிக்கப்படவில்லை.

முக்கிய தேவைகள்

ஒவ்வொரு வரிசை-முறை வரிசைப்படுத்தலுக்கும் என்ன தேவை

Redis

அனைத்து முக்கிய மற்றும் பணியாளர் செயல்முறைகளுக்கும் வரிசை ஒருங்கிணைப்புக்குப் பயன்படுத்தப்படும் Redis சேவைக்கு நம்பகமான அணுகல் தேவை.

PostgreSQL

முக்கிய மற்றும் தொழிலாளர்கள் தரவுத்தளத்தை பகிர்ந்து கொள்ள வேண்டும். வரிசை முறை என்பது விநியோகிக்கப்பட்ட கட்டமைப்பு மற்றும் SQLite சுற்றி வடிவமைக்கப்படக்கூடாது.

பொருந்தும் n8n உள்ளமைவு

பிரதான மற்றும் பணியாளர்கள் வரிசை பயன்முறையை இயக்க வேண்டும் மற்றும் Redis, PostgreSQL மற்றும் மறைகுறியாக்கப்பட்ட நற்சான்றிதழ்களை அணுக தேவையான உள்ளமைவைப் பகிர்ந்து கொள்ள வேண்டும்.

தொழிலாளர் திறன்

தொழிலாளர்களுக்கு அவர்கள் செயல்படுத்தும் பணிப்பாய்வுகளுக்கு போதுமான CPU மற்றும் RAM தேவை. செயல்முறைகளைச் சேர்ப்பது, ஒவ்வொரு செயல்பாட்டின் ஆதாரச் செலவையும் அகற்றாது.

ஏற்கனவே உள்ள சுய-ஹோஸ்ட் செய்யப்பட்ட அடுக்கில் வரிசை பயன்முறையை இயக்கவும். n8n பிரதான சேவையும் ஒவ்வொரு தொழிலாளியும் ஒரே PostgreSQL தரவுத்தளத்தையும் Redis ஐயும் தனிப்பட்ட நெட்வொர்க்கில் அடையலாம் என்பதை முதலில் உறுதிப்படுத்தவும். அமைக்கவும் EXECUTIONS_MODE=queue பிரதான மற்றும் தொழிலாளர்கள் மற்றும் விநியோகம் ஆகிய இரண்டிலும் QUEUE_BULL_REDIS_HOST=redis மற்றும் QUEUE_BULL_REDIS_PORT=6379 எப்போது redis உங்கள் உண்மையான கம்போஸ் சேவைப் பெயர். பயன்படுத்தவும் DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres மற்றும் பொருத்தம் DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER மற்றும் DB_POSTGRESDB_PASSWORD ஒவ்வொரு செயல்முறையிலும்; உங்களின் உதாரண சேவைப் பெயர்களை மாற்றவும். ஏற்கனவே உள்ளதை சரியாக வழங்கவும் N8N_ENCRYPTION_KEY அவர்கள் அனைவருக்கும். Redis அல்லது PostgreSQL ஹோஸ்ட் போர்ட்களை ஒரே கம்போஸ் நெட்வொர்க்கில் கன்டெய்னர்களை இணைப்பதற்காக வெளியிட வேண்டாம்.

செயல்படுத்துபவரைத் தொடங்கவும், இரண்டாவது எடிட்டரை அல்ல. அதே பின் செய்யப்பட்ட n8n பட பதிப்பு மற்றும் பகிரப்பட்ட அமைப்புகளைப் பயன்படுத்தி n8n பணியாளர் சேவையைச் சேர்க்கவும், ஆனால் அதை இயக்கவும் worker கட்டளை. நீங்கள் அந்த சேவைக்கு பெயரிட்டிருந்தால் n8n-worker, அதை தொடங்கவும் docker compose up -d n8n-worker. ஒரு தொழிலாளியின் உண்மையான மரணதண்டனை உறுதிப்படுத்திய பிறகு, நீங்கள் பயன்படுத்தலாம் docker compose up -d --scale n8n-worker=2 அந்த சேவையில் இருந்து இரண்டாவது தொழிலாளியை தொடங்க வேண்டும். இவை ஒரு சேர்த்தல் ஏற்கனவே சரியாக உள்ளமைக்கப்பட்டுள்ளது ஸ்டாக் எழுதவும், ஒரு முழுமையான நிறுவல் கோப்பு அல்ல; உங்கள் தற்போதைய நிலையான தொகுதிகள், HTTPS ப்ராக்ஸி, ரகசியங்கள் மற்றும் காப்புப்பிரதிகளை வைத்திருங்கள்.

வரிசை-முறை ஏற்கனவே உள்ள அடுக்கிற்கான துண்டுகளை எழுதுதல். கீழே உள்ள உதாரணத்தை உங்கள் நடப்பில் இணைக்கவும் compose.yaml; அது இல்லை ஒரு முழுமையான தனித்த வரிசைப்படுத்தல். உங்களிடம் ஏற்கனவே உறுதியான, தனிப்பட்ட தன்மை இருப்பதாக இது கருதுகிறது postgres மற்றும் n8n சேவைகள், ஏற்கனவே உள்ளது N8N_VERSION உங்கள் சுற்றுச்சூழலில் முள் மற்றும் உங்கள் சொந்த பாதுகாக்கப்பட்ட POSTGRES_PASSWORD மற்றும் அசல் N8N_ENCRYPTION_KEY. அதன் பெயர்கள், தொகுதிகள், தரவுத்தளம் மற்றும் n8n பதிப்பை ஏற்கனவே உள்ள திட்டத்துடன் பொருத்தவும். வரிசை முறை Redis அமைப்புகளைச் சேர்க்கவும் EXECUTIONS_MODE=queue மேலே விவரிக்கப்பட்டுள்ளபடி, தற்போதுள்ள முக்கிய சேவைக்கும்.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Redis அல்லது இந்த துண்டில் உள்ள பணியாளருக்கு எந்த ஹோஸ்ட் போர்ட் வெளியிடப்படவில்லை. Redis append-only persistence என்பது கூடுதல் மீட்பு அடுக்கு, இல்லை ஆஃப்-சர்வர் காப்புப்பிரதிகளுக்கு மாற்றாக. ஏற்கனவே உள்ள HTTPS மற்றும் அங்கீகார உள்ளமைவை மாற்றாமல் வைத்திருங்கள். வெளிப்புற டாஸ்க் ரன்னர்கள் தேவைப்படும் குறியீட்டு முனைகளுக்கு, உங்கள் பணியாளர் பணியமர்த்தலுக்கான ரன்னர் செயல்முறைகளை தனித்தனியாக உள்ளமைக்கவும்; வரிசை முறையே டாஸ்க் ரன்னர்களை மாற்றாது.

ஏற்கனவே உள்ள SQLite நிகழ்வை மாற்றவா? வெறுமனே மாற்ற வேண்டாம் DB_TYPE மற்றும் ஒரு வெற்று PostgreSQL தரவுத்தளத்திற்கு எதிராக தொடங்கவும்: அவ்வாறு செய்வது பழைய பணிப்பாய்வுகள் மற்றும் நற்சான்றிதழ்களை மாற்றாது. எந்தவொரு வெட்டுக்கும் முன், மூல தரவுத்தளத்தை, தொடர்ந்து காப்புப் பிரதி எடுக்கவும் .n8n அடைவு மற்றும் அசல் குறியாக்க விசை; ஆதரிக்கப்படும் n8n ஏற்றுமதி/இறக்குமதி அல்லது இடம்பெயர்வு நடைமுறையைப் பயன்படுத்தவும், பின்னர் ஒரு தனி இலக்கில் பணிப்பாய்வுகள் மற்றும் மறைகுறியாக்கப்பட்ட சான்றுகளை சரிபார்க்கவும். மறுபரிசீலனைக்காக அசல் கோப்புகளை வைத்து, மீட்புத் தயாரிப்பிற்கு கீழே இணைக்கப்பட்டுள்ள காப்புப் பிரதி & மீட்டமை வழிகாட்டியைப் பயன்படுத்தவும். ஒருபோதும் நீக்க வேண்டாம் database.sqlite குறுக்குவழியாக.

ஒரு தொழிலாளியின் எண்ணிக்கை மற்றும் வேலைகள் இரண்டிலும் தொழிலாளர்கள் அளவிடுகின்றனர்

ஒவ்வொரு தொழிலாளியும் ஒரே நேரத்தில் பல வேலைகளைச் செய்ய முடியும். n8n இன் தற்போதைய இயல்புநிலை பணியாளரின் ஒத்திசைவு 10 ஆகும், மேலும் அதன் ஆவணங்கள் 5 அல்லது அதற்கும் அதிகமான ஒத்திசைவை பரிந்துரைக்கிறது. பல தொழிலாளர்களுடன் இணைந்து மிகக் குறைந்த ஒத்திசைவு தேவையற்ற தரவுத்தள இணைப்புகளை உருவாக்கி தரவுத்தள இணைப்புக் குளத்தை வெளியேற்றும்.

எப்போது ஒத்திசைவை அதிகரிக்கவும்

ஒரு தொழிலாளிக்கு உதிரி CPU மற்றும் RAM உள்ளது மற்றும் பணிப்பாய்வுகள் பெரும்பாலும் கணக்கீடு அல்லது நினைவகத்தை நிறைவு செய்வதை விட வெளிப்புற சேவைகளில் காத்திருக்கின்றன.

எப்போது தொழிலாளர்களைச் சேர்க்கவும்

ஒரு தொழிலாளி செயல்முறை ஒரு இடையூறாக மாறும் மற்றும் தரவுத்தளம், Redis மற்றும் உள்கட்டமைப்பு ஆகியவை அதிக இணையான செயல்பாட்டிற்கான திறனைக் கொண்டுள்ளன.

எப்போது ஒத்திசைவைக் குறைக்கவும்

தனிப்பட்ட பணிப்பாய்வுகள் நினைவகம்-அதிகமானவை அல்லது CPU-கனமான மற்றும் இணையான வேலைகள் சச்சரவு, OOM அழுத்தம் அல்லது நிலையற்ற செயலாக்க நேரங்கள்.

பார்க்க PostgreSQL

அதிக வேலையாட்கள் மற்றும் அதிக ஒத்திசைவு தரவுத்தள செயல்பாட்டை அதிகரிக்கிறது. தரவுத்தள திறன் இல்லாமல் செயல்படுத்தும் திறனை அளவிடுதல் தடையை அகற்றுவதற்கு பதிலாக அதை நகர்த்தலாம்.

எந்த ஒத்திசைவு வரம்பு உண்மையில் பொருந்தும் என்பதை அறியவும். ஒரு தொழிலாளி பயன்படுத்தத் தொடங்கலாம் n8n worker --concurrency=5, அல்லது உங்கள் கம்போஸ் சேவையில் அதற்கு சமமான பணியாளர் கட்டளை. என்றால் N8N_CONCURRENCY_PRODUCTION_LIMIT தவிர வேறு ஒரு மதிப்பிற்கு வெளிப்படையாக அமைக்கப்பட்டுள்ளது -1, அந்த அமைப்பு வரிசை முறையில் முன்னுரிமை பெறுகிறது; இல்லையெனில் n8n தொழிலாளியைப் பயன்படுத்துகிறது --concurrency மதிப்பு அல்லது அதன் இயல்புநிலை 10. பணியாளரின் எண்ணிக்கையை பெயரளவிலான இயல்புநிலையால் பெருக்க வேண்டாம் மற்றும் அதை உத்தரவாதமான செயல்திறன் என்று அழைக்கவும்: உண்மையான திறன் வேலை காலம், CPU, நினைவகம், வெளிப்புற APIகள் மற்றும் PostgreSQL இணைப்புகளைப் பொறுத்தது.

வலைப்பதிவுகள்

வரிசை பயன்முறையானது செயல்படுத்தல் ஹேண்ட்ஆஃப் தாமதத்தை சேர்க்கலாம்

பிரதான அல்லது வெப்ஹூக் செயல்முறை HTTP கோரிக்கையைப் பெறுகிறது, ஆனால் ஒரு தொழிலாளி பணிப்பாய்வு செயல்படுத்தலைச் செய்கிறார். Redis மூலம் அந்த ஒப்படைப்பு சில மேல்நிலையைச் சேர்க்கிறது. தாமத உணர்திறன் கொண்ட வெப்ஹூக்குகளுக்கு, அதிகமான பணியாளர்கள் தானாகவே ஒவ்வொரு கோரிக்கையையும் விரைவாகச் செய்வார்கள் எனக் கருதுவதற்குப் பதிலாக, இறுதி முதல் இறுதி வரை பதிலளிக்கும் நேரத்தை அளவிடவும்.

பெறுமுதன்மை/வெப்ஹூக் செயல்முறை கோரிக்கையை ஏற்றுக்கொள்கிறது.
வரிசைசெயல்படுத்தல் Redis க்கு ஒப்படைக்கப்பட்டது.
செயல்படுத்துகிடைக்கக்கூடிய பணியாளர் பணிப்பாய்வுகளை இயக்குகிறார்.
பதிலளிக்கவும்தேவைப்படும் போது முடிவு வரிசைப் பாதை வழியாக மீண்டும் அனுப்பப்படும்.

வெப்ஹூக் போக்குவரத்தை சரியான செயல்முறைக்கு வழிசெலுத்தவும். அர்ப்பணிப்புடன் n8n webhook தலைகீழ் ப்ராக்ஸி அல்லது லோட் பேலன்சருக்குப் பின்னால் உள்ள செயலிகள், வழி உற்பத்தி பாதைகள் /webhook/* மற்றும் /webhook-waiting/* வெப்ஹூக் செயலிகளுக்கு; வைத்து /webhook-test/*, எடிட்டர் மற்றும் API முக்கிய கோரிக்கைகள். கூடுதல் பணிச்சுமையை நீங்கள் வேண்டுமென்றே ஏற்கும் வரை, உற்பத்தி வெப்ஹூக் சுமை சமநிலைக் குளத்தில் பிரதானத்தை வைக்க வேண்டாம். ஏ Webhook க்கு பதிலளிக்கவும் பணிப்பாய்வு கிளையண்டைத் தொழிலாளி முடித்து அதன் பதிலைத் தரும் வரை காத்திருக்க வைக்கலாம், எனவே வரிசை முறையானது உடனடி HTTP பதில்கள் அல்லது பூஜ்ஜிய காலக்கெடுவின் வாக்குறுதி அல்ல. ட்ராஃபிக்கை மாற்றுவதற்கு முன் உண்மையான வெளிப்புற அழைப்பு மற்றும் மறுமொழி நடத்தையை சோதிக்கவும்.

பணிப்பாய்வுகள் விநியோகிக்கப்பட்ட தொழிலாளர்கள் முழுவதும் பைனரி தரவு தொடர்ந்து இருக்க வேண்டும் என்றால், ஆதரிக்கப்படும் வெளிப்புற பொருள் சேமிப்பு போன்ற ஒவ்வொரு தேவையான நிகழ்வுகளும் அணுகக்கூடிய சேமிப்பக வடிவமைப்பைப் பயன்படுத்தவும்.

பெரிய வெப்ஹூக் பதில்கள்

தொழிலாளர்களிடமிருந்து Webhook பதில்கள் பெறும் செயல்முறையை நோக்கி பயணிக்கின்றன. பெரிய பதில் அமைப்புகள் Redis நினைவக அழுத்தத்தை அதிகரிக்கலாம் மற்றும் வேண்டுமென்றே பதில்-சேமிப்பு உள்ளமைவு தேவைப்படுகிறது.

தொழிலாளர்களை விநியோகிக்கும் முன் திட்டமிடுங்கள்

இயந்திரங்கள் முழுவதும் தொழிலாளர்கள் பரவுவதற்கு முன், உள்ளூர் கோப்புகளை பெரிதும் சார்ந்திருக்கும் பணிச்சுமை பகிரப்பட்ட நிலைத்தன்மைக்காக மறுவடிவமைப்பு செய்யப்பட வேண்டும்.

பெரிய வெப்ஹூக் பதில் எல்லை. தற்போதைய n8n ஆவணம் கொடுக்கிறது N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX ஒரு இயல்புநிலை 64 MiB ஒரு தொழிலாளியின் பதிலுக்கு வரிசை வழியாக திருப்பி அனுப்பப்பட்டது. Redis விமானத்தில் பல நகல்களை வைத்திருக்க முடியும், எனவே ஒரே நேரத்தில் பெரிய பதிலுக்கு Redis ​​நினைவகத்தில் பட்ஜெட் அளவை விட தோராயமாக 1.5 மடங்கு. ஆஃப்லோடிங் இல்லாமல், தொழிலாளர்களைச் சேர்ப்பதன் மூலம் மாயமாக வேகமாக மாறுவதற்குப் பதிலாக, பெரிதாக்கப்பட்ட பதில் தோல்வியடைகிறது.

பதிப்பு மற்றும் உரிம வரம்புகள். n8n இலிருந்து 2.34.0, தொழிலாளர்கள் பயன்படுத்தலாம் N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true படிக்கக்கூடிய பகிரப்பட்ட பைனரி சேமிப்பகத்திற்கு பெரிதாக்கப்பட்ட வெப்ஹூக் மறுமொழி உடல்களை ஆஃப்லோட் செய்ய, ஆனால் முதலில் மேம்படுத்தவும் ஒவ்வொரு முக்கிய மற்றும் webhook செயலி 2.34.0 அல்லது அதற்குப் பிறகு. தேர்ந்தெடுக்கப்பட்ட N8N_DEFAULT_BINARY_DATA_MODE உண்மையில் தரவைச் சேமித்து, ஒவ்வொரு பங்கேற்பு செயல்முறையிலும் படிக்கக்கூடியதாக இருக்க வேண்டும். வெளிப்புற S3 மற்றும் Azure பைனரி சேமிப்பகத்திற்கு சரியான சுய-ஹோஸ்ட் தேவை வணிகம் அல்லது நிறுவனம் உரிமம்; சமூகப் பதிப்பில் அவற்றை இயக்க முடியும் என்று நினைக்க வேண்டாம். தி database பைனரி பயன்முறையானது, பணம் செலுத்திய வெளிப்புற சேமிப்பிடம் இல்லாமல் பெரிதாக்கப்பட்ட பதிலை ஏற்றலாம், ஆனால் முக்கிய நிகழ்வானது, சேமிக்கப்பட்ட முழு உடலையும் நினைவகத்தில் ஏற்றுகிறது மற்றும் தரவுத்தள சேமிப்பகத்திற்கு அதன் சொந்த கோப்பு அளவு வரம்பு உள்ளது. க்கு பதில்-உடல் ஆஃப்லோட் குறிப்பாக, n8n பகிரப்பட்டதையும் விவரிக்கிறது filesystem ஒவ்வொரு நிகழ்வும் ஒரே வட்டை ஏற்றும்போது விருப்பம், ஆனால் அந்த ஏற்பாட்டை வெளிப்படையாக பரிந்துரைக்கவில்லை. விநியோகிக்கப்பட்ட வரிசை-முறை வரிசைப்படுத்தலில் கோப்பு முறைமை அடிப்படையிலான நிலையான பைனரி தரவின் ஆதரவிற்காக இந்த சிறப்பு ஆஃப்லோட் பாதையை தவறாகப் பயன்படுத்த வேண்டாம். ஆஃப்லோடை இயக்கும் முன் உங்கள் பதிப்பு, பதிப்பு மற்றும் சேமிப்பக உள்ளமைவைச் சரிபார்க்கவும்.

கண்காணிப்பு

வரிசை உதவுகிறதா என்பதை அறியவும்

வரிசை ஆழம்

தொழிலாளர்கள் வடிகட்டுவதை விட வேகமாக வளரும் வரிசையானது, போதுமான செயல்படுத்தும் திறன் அல்லது கீழ்நிலை தடையை குறிக்கிறது.

தொழிலாளி CPU & RAM

ஒரு தொழிலாளிக்கு செறிவு மற்றும் நினைவக உச்சநிலைகளை அளவிடவும். வளர்ந்து வரும் வரிசையுடன் சும்மா இருக்கும் தொழிலாளர்கள் மற்றொரு தடையை சுட்டிக்காட்டுகின்றனர்.

செயல்படுத்தல் தாமதம்

பணிப்பாய்வு இயக்க நேரம் மட்டும் இல்லாமல், செயல்படுத்தல் உருவாக்கப்படுவதற்கும் உண்மையில் தொடங்குவதற்கும் இடையே உள்ள தாமதத்தைக் கண்காணிக்கவும்.

சுகாதார சோதனைகள்

ஒரு தொழிலாளி உயிருடன் இருக்கிறாரா என்பதையும், அதன் தரவுத்தளம் மற்றும் Redis இணைப்புகள் தயாராக உள்ளதா என்பதையும் பணியாளர் சுகாதார இறுதிப்புள்ளிகள் தெரிவிக்கலாம்.

ஒரு பணியாளரின் மரணதண்டனையை சரிபார்க்கவும், ஒரு பச்சை கொள்கலன் மட்டும் அல்ல. சரியாக உள்ளமைக்கப்பட்ட கம்போஸ் ஸ்டேக் மூலம், சரிபார்க்கவும் docker compose ps மற்றும் docker compose logs --tail=100 n8n-worker (வேறுபட்டால் சேவையின் பெயரை மாற்றவும்). பாதிப்பில்லாத ஒன்றை இயக்கவும் வெளியிடப்பட்ட தயாரிப்பு திட்டமிடப்பட்ட தூண்டுதல் அல்லது சோதனை வெப்ஹூக்கைப் பயன்படுத்தி பணிப்பாய்வு, பின்னர் n8n இன் எக்ஸிகியூஷன்ஸ் பார்வையில் அதன் செயல்பாட்டினை தொழிலாளர் பதிவுகளில் உள்ள உண்மையான தொழிலாளர் செயலாக்கத்துடன் பொருத்தவும். வெற்றிகரமாகத் திறக்கும் எடிட்டர், இயங்கும் Redis கண்டெய்னர் அல்லது வரிசைப்படுத்தப்பட்ட செயல்படுத்தல் மட்டுமே செய்கிறது இல்லை ஒரு தொழிலாளி அந்த வேலையைச் செய்திருப்பதை நிரூபிக்கவும்.

சார்புகளையும் தயார்நிலையையும் சரிபார்க்கவும். இயல்புநிலை எடுத்துக்காட்டு சேவை பெயர்களுடன், docker compose exec -T redis redis-cli ping பெற வேண்டும் PONG Redis அங்கீகாரம் அதை அனுமதிக்கும் போது, மற்றும் docker compose exec -T postgres pg_isready -U n8n -d n8n PostgreSQL தயார்நிலையை சரிபார்க்கிறது (நற்சான்றிதழ்கள் மற்றும் சேவை பெயர்களை மாற்றியமைக்கவும்). இயக்கு QUEUE_HEALTH_CHECK_ACTIVE=true ஒரு தொழிலாளியின் மீது உங்களுக்கு அதன் தனிப்பட்ட தேவை ஏற்படும் போது /healthz மற்றும் /healthz/readiness இறுதிப்புள்ளிகள்; தயார்நிலை இறுதிப்புள்ளி Redis/தரவுத்தள இணைப்பைச் சரிபார்க்கிறது. அவர்களைக் கண்காணிக்க அந்தத் தொழிலாளியின் இறுதிப்புள்ளிகளை பொதுவில் அம்பலப்படுத்தாதீர்கள்.

கைமுறை ஓட்டங்கள் ஒரு வித்தியாசமான சோதனை. இயல்பாக OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, எனவே எடிட்டரில் பணிப்பாய்வுகளை கைமுறையாக இயக்குவது, வரிசை பயன்முறை சரியாக உள்ளமைக்கப்பட்டிருந்தாலும் கூட, பிரதானத்தில் இயக்க முடியும். அதை அமைக்கவும் true நீங்கள் தொழிலாளர்களுக்கு கைமுறையாக மரணதண்டனைகளை அனுப்ப உத்தேசித்திருந்தால் மற்றும் ஒரு ஸ்டேஜிங் சூழலில் மாற்றத்தை சரிபார்த்திருந்தால் மட்டுமே. க்யூ-மோட் வேலையாட்களும் n8n வெளிப்புற டாஸ்க் ரன்னர்களில் இருந்து வேறுபட்டவர்கள், அவை கோட்-நோட் செயல்பாட்டிற்கான தனி கட்டமைப்பு தேவைகளைக் கொண்டுள்ளன.

அளவிடுதல் பாதை

ஒரு நேரத்தில் ஒரு தடையை அளவிடவும்

நிலை 1PostgreSQL உடன் ஒற்றை n8n நிகழ்வு; உச்சநிலை CPU, RAM மற்றும் ஒத்திசைவு.
நிலை 2செங்குத்து அளவிடுதல் இன்னும் அளவிடப்பட்ட சிக்கலைத் தீர்க்கும் போது VPS வளங்களை அதிகரிக்கவும்.
நிலை 3Redis மற்றும் தொழிலாளர்களை அறிமுகப்படுத்துதல்.
நிலை 4PostgreSQL, Redis மற்றும் செயல்படுத்தல் தாமதத்தைப் பார்க்கும்போது தொழிலாளர்களைச் சேர்க்கவும் அல்லது பணியாளரின் ஒத்திசைவை மாற்றவும்.

அளவிடுதல் தேவைப்படும்போது அதிக VPS திறனைத் தேர்ந்தெடுக்கவும்

கூட்டாளர் இணைப்பு: வாங்குதல்களிலிருந்து நாங்கள் கமிஷனைப் பெறலாம்.

அதிக கிடைக்கும் எல்லை

வரிசை முறையானது செயல்படுத்தல்களை அளவிடுகிறது, ஆனால் அது தானாகவே முக்கிய செயல்முறையை அதிக அளவில் கிடைக்கச் செய்யாது

குறியாக்க விசையைப் பகிரவும்

ஒவ்வொரு தொழிலாளியும் இதையே பயன்படுத்த வேண்டும் N8N_ENCRYPTION_KEY முக்கிய நிகழ்வாக, பணியாளர்கள் பணிப்பாய்வு செயல்படுத்தல் மூலம் தேவைப்படும் நற்சான்றிதழ்களை மறைகுறியாக்க முடியும்.

பதிப்புகளை சீரமைத்து வைத்திருங்கள்

முதன்மை, வெப்ஹூக் மற்றும் பணியாளரின் செயல்முறைகள் ஒரே n8n பதிப்பில் இயங்க வேண்டும். உருட்டல் மாற்றங்களின் போது கலப்பு பதிப்புகள் இணக்கமற்ற நடத்தையை உருவாக்கலாம்.

Webhook செயலிகள் ஒரு தனி அளவிடும் அடுக்கு

உள்வரும் வெப்ஹூக் வால்யூம் இடையூறாக மாறும் போது, பிரத்யேக வெப்ஹூக் செயலிகள் சுமை பேலன்சரின் பின்னால் அமர முடியும். அளவிடப்பட்ட கோரிக்கை அளவு அதை நியாயப்படுத்தும் வரை இந்த லேயரைச் சேர்க்க வேண்டாம்.

மல்டி மெயின் என்பது ஒரு வித்தியாசமான அம்சம்
