DOCKER INSTALLATION

Install n8n on a VPS

Install n8n on a VPS using Docker Compose and PostgreSQL. A production deployment also needs persistent application and database data, a stable N8N_ENCRYPTION_KEY, a public hostname, HTTPS and correct webhook configuration. Verify these pieces before activating production workflows.

PREREQUISITES

Prepare the VPS before starting n8n

Linux VPS

Use a maintained Linux server sized for n8n, PostgreSQL, Docker and the reverse proxy.

DNS

Point a domain or subdomain at the VPS before issuing TLS certificates and publishing webhook URLs.

Docker Compose

Install Docker Engine and the Compose plugin using supported packages for the operating system.

Firewall

Expose only required administration and web ports. Keep PostgreSQL and internal application services private.

Installing on a VPS that already hosts websites? You can add n8n to a server you control when CPU, RAM and storage allow it. However, if Nginx, Apache, Caddy or another reverse proxy already owns ports 80/443, do not start the example Caddy container below unchanged: the ports will conflict. Instead, route a new n8n subdomain through your existing reverse proxy with appropriate private networking, or use a clean VPS for the exact Compose example. Preserve the other sites and their TLS configuration; the example assumes that ports 80/443 are available.

COPY-AND-ADAPT INSTALLATION

Install n8n on your VPS with Docker Compose

Use this example to build an n8n deployment on a self-managed Linux VPS. You install and maintain n8n yourself; choosing a server through our partner does not include a preinstalled n8n instance. The example combines n8n, PostgreSQL, an external task runner and Caddy HTTPS in a private Compose network. It is a configuration template, not a claim of a live-tested deployment.

Want the fastest fresh installation instead? n8n also provides an official one-line Docker setup. You can download and review its script with curl -fsSL https://get.n8n.io -o get-n8n.sh before running sh get-n8n.sh. That option launches an initial instance with SQLite at a local URL and includes n8n Assistant sandbox services; it is not the same as this public-HTTPS, PostgreSQL-backed VPS deployment. The official full sandbox stack needs more RAM and CPU than a lean n8n installation (its Compose guide specifies at least 4 GB RAM / 2 vCPUs). For an internet-facing production VPS, continue with the manually configured stack below.

1. Prepare Docker, DNS and access

Connect over SSH with sudo access and point a DNS A record for n8n.example.com to your VPS IPv4 address. On a fresh Ubuntu 22.04, 24.04 or 26.04 VPS, the following commands install Docker Engine and the modern docker compose plugin from Docker's official signed apt repository:

# Fresh official Ubuntu 22.04 / 24.04 / 26.04 installation
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Register Docker's signed apt repository
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

This is the production-oriented repository method in the official Docker Ubuntu installation guide. Do not blindly reinstall or remove Docker on a VPS already running containers or other websites; first inspect the existing installation and possible package conflicts. For Debian or another distribution, use the corresponding official OS-specific instructions instead of Ubuntu commands.

Now verify Docker itself, the Compose plugin, DNS and the working directory:

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

If getent hosts returns no address or the wrong address, correct your DNS before starting Caddy; replace n8n.example.com throughout this guide with your real hostname. Docker normally requires root privileges: if your SSH user cannot run the later docker compose commands directly, prefix them with sudo. Adding a user to the docker group grants root-equivalent access and should not be done casually on a shared server.

Keep your actual SSH administration port reachable before enabling a firewall. Allow inbound HTTP (80) and HTTPS (443) for certificate issuance and the editor. Docker-published container ports can bypass some UFW rules, so review Docker's firewall guidance and publish only the intended Caddy ports. This Compose example deliberately does not publish PostgreSQL (5432), n8n (5678) or task-runner broker (5679) to the public internet.

2. Create environment values and preserve the key

From the project directory, generate three different random hexadecimal values with:

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

Create a file named .env using the template below, replace every REPLACE_WITH_RANDOM_HEX with a different generated value, and change the hostname and timezone. The shown 2.42.5 tag is the stable release listed on 8 October 2026, used here as a dated configuration example, not a guarantee of a live-tested deployment or of future security. Before installing, check the current official n8n releases, then keep n8n and its task-runner image on the same verified version.

# .env — replace the three example secrets
# Pin a maintained n8n release; keep n8n and runner equal.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

Never commit .env to a public repository. Store the encryption key and recovery instructions securely off the VPS. The key must stay the same after container recreation or migration.

3. Write compose.yaml for a fresh installation

In the same directory, create compose.yaml. The example uses the official n8n environment-variable conventions and the PostgreSQL 18 PGDATA path documented by the n8n hosting project:

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

The four services have distinct roles: PostgreSQL stores database state, n8n runs workflows, n8n-runner executes runner tasks with a matching version and shared authentication token, and Caddy handles public HTTPS. An external task runner is not Redis queue mode. Only Caddy publishes host ports. This lean illustration uses a single database role for setup; for stronger separation of PostgreSQL privileges, consult the official n8n PostgreSQL deployment example.

4. Create the HTTPS Caddyfile

Create the file Caddyfile (capital C, no extension) alongside compose.yaml. Replace the example hostname everywhere with your own DNS name:

n8n.example.com {
    reverse_proxy n8n:5678
}

Caddy requests and renews public TLS certificates when the domain resolves correctly and external traffic can reach ports 80/443. Do not point DNS to localhost. If you replace Caddy with another reverse proxy, forward the original host, protocol and client-address headers and adjust N8N_PROXY_HOPS for the actual number of trusted proxy hops.

5. Start the containers and test from outside

Run these commands from the project directory after saving .env, compose.yaml and Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

The last command checks the public HTTPS health endpoint. If certificate issuance is still pending, inspect Caddy logs and DNS/ports before concluding n8n is broken. Open https://n8n.example.com, create the first owner account immediately and enable appropriate sign-in protections. Confirm that the instance actually executes a workflow, not merely that the editor loads:

  1. In the editor, create a workflow with a Webhook trigger. Set HTTP Method to GET, choose the Path vps-check, and set Respond to Immediately. Save the workflow.
  2. Click Listen for Test Event, copy the full Test URL shown by n8n, and from another device run curl -i 'PASTE_TEST_URL_HERE' with the copied URL. Expect an HTTP success response and the incoming event to appear in the n8n editor. Test URLs work only while n8n is listening for the event.
  3. Publish the workflow, switch the node to its Production URL, copy it and run curl -i 'PASTE_PRODUCTION_URL_HERE' again. Confirm the execution under the workflow's Executions tab. Production webhook requests need the workflow to be published and do not show their payload in the editor's test view.

This is a deliberately simple, unauthenticated smoke test: never send secrets to it. Unpublish/delete it after testing, or configure Webhook authentication/IP restrictions before using a public endpoint for real data. See the official Webhook test/production documentation.

6. Back up before changing pinned versions

Save a recoverable PostgreSQL dump and the persistent n8n data volume, .env/encryption key and required external files to storage outside this server. Verify a restore using the backup and recovery guide before updating production. Example commands:

# Back up the database, encryption key, instance data,
# and files before changing the pinned versions.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# After securing the backup outside this VPS:
docker compose pull
docker compose up -d
docker compose ps

Change the pinned N8N_VERSION only after reading release notes; both n8n and runner images must advance together. Do not run docker compose down -v during routine maintenance because that deletes named data volumes. PostgreSQL major-version changes require a database upgrade or dump/restore plan; replacing the Postgres 18 image with a different major tag is not an automatic migration.

Authoritative references: n8n Docker Compose guide, n8n reverse-proxy/webhook configuration, and official PostgreSQL deployment notes. No infrastructure benchmark or provider-specific preinstalled feature is assumed.

CONFIGURATION

Set secrets and public URLs deliberately

Encryption key

Set and preserve a strong n8n encryption key before storing production credentials. The same key is required after recovery.

PostgreSQL credentials

Use dedicated database credentials and keep passwords outside public source control.

Public hostname

Configure the real external hostname and HTTPS origin rather than an internal container address.

Webhook URL

Set N8N_WEBHOOK_URL to the publicly reachable HTTPS base URL and set N8N_PROXY_HOPS=1 when there is one trusted reverse proxy. WEBHOOK_URL is a deprecated alias in n8n 2.35.0 and later; avoid copying it from older tutorials.

PERSISTENCE

Persist n8n and PostgreSQL separately

n8n data

Mount persistent storage for the n8n data directory so critical instance state survives container recreation.

PostgreSQL data

Persist the database directory independently from the PostgreSQL container.

File permissions

Make mounted paths writable by the intended container user without making host storage unnecessarily permissive.

Workflow files

Persist any mounted files or binary-data storage that production workflows depend on.

HTTPS & PROXY

Reverse proxy

Use Nginx, Caddy or Traefik as the public entry point and forward traffic to the private n8n service.

TLS

Issue a valid certificate for the public hostname and redirect HTTP traffic to HTTPS.

Forwarded headers

Webhook verification

Trigger a webhook from outside the VPS and confirm n8n generates the externally reachable HTTPS URL.

COMMON FAILURES

Why an n8n Docker install works locally but fails in production

Wrong webhook URL

Callbacks point to localhost, HTTP or an internal hostname instead of the public HTTPS origin.

Missing persistence

Application or database state disappears when a container is recreated.

Lost encryption key

Saved credentials become unusable after rebuilding because the new instance uses a different key.

Public database port

PostgreSQL is exposed unnecessarily even though only n8n needs to reach it.

POST-DEPLOY VERIFICATION

Verify health before connecting real workflows

Check container state

Run docker compose ps and confirm the application and database services are running as expected before treating the deployment as healthy.

Check the n8n health endpoint

With the Compose example above, port 5678 is not published on the host. Check the public endpoint with curl -fsS https://n8n.example.com/healthz after changing the hostname, and use docker compose ps plus service logs if HTTPS or the database is not ready.

Pin application versions

Do not treat an unreviewed floating image update as a maintenance strategy. Record the n8n version you run, read release notes and back up before changing it.

Do not bump PostgreSQL major versions in place

Changing only the Postgres major image tag can make an existing data directory incompatible. Back up and follow the database upgrade procedure instead of assuming container recreation performs a major-version migration.

FAQ

Installing n8n with Docker: common questions

Does n8n need PostgreSQL when using Docker?

Docker does not require PostgreSQL, and small deployments can use SQLite. For a production-oriented VPS deployment, PostgreSQL provides a stronger database foundation and supports later queue-mode scaling.

Why keep a persistent n8n volume if PostgreSQL stores data?

The persistent n8n directory can contain important instance state and configuration. Preserve it according to the deployment design instead of assuming the database is the only recovery asset.

Why does my webhook show localhost?

The internal container address differs from the public origin. Configure the external hostname, protocol and webhook URL, and ensure the reverse proxy passes the required headers.

Should port 5678 be public?

For a normal production deployment behind a reverse proxy, expose HTTPS at the proxy and keep the n8n application port internal unless there is a specific operational reason not to.

Do I need Redis?

Not for a standard single-instance Docker deployment. Redis becomes relevant when you deliberately move to queue mode and workers.

Are external n8n task runners the same as queue mode workers?

No. External task runners execute supported task code separately from the n8n main process and use a shared authentication token. Redis queue mode distributes workflow executions and has its own infrastructure requirements. This example shows an external task runner, not Redis queue mode. Match the runner image version to the n8n version.
