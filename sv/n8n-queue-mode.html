SCALING

Köläge i n8n

Queue-läge skiljer utförande av arbetsflödet från huvudprocessen n8n. Huvudinstansen tar emot triggers och skapar körningar, Redis samordnar kön, arbetstagare utför jobb och PostgreSQL lagrar de delade arbetsflödes- och verkställighetsdata.

QUICK DECISION

Behöver du faktiskt köläge?

Stanna i vanlig läge när

Ett enskilt fall hanterar toppkörningar bekvämt och CPU, RAM och utförande latens förblir stabila. Queue läge lägger till komponenter du inte behöver ännu.

Överväg köläge när

Hålla parallella körningar skapar påstående, exekvering latens stiger under belastning, eller du måste lägga till exekvering kapacitet genom att köra flera arbetare.

Skala vertikalt först när

Flaskan är helt enkelt otillräcklig CPU eller RAM och en större instans kan fortfarande uppfylla arbetsbelastningen rent.

Mät innan du ändrar arkitektur

Använd peak concurrency, CPU, RAM, execution duration, ködjup och databastryck för att motivera flytten.

Arkitektur

Hur n8n köläge fungerar

1 · MainFår timers, webhooks och workflow-förfrågningar och skapar en avrättning istället för att göra själva produktionsutförandet.
2 RedisAgerar som meddelande mäklare. Det håller på att avrätta meddelanden så att nästa tillgängliga arbetstagare kan göra anspråk på ett jobb.
3 · ArbetareFår exekvering ID, laddar arbetsflödesdata från den delade databasen, kör arbetsflödet och skriver resultatet tillbaka.
4 PostgreSQLGer delat ihållande arbetsflöde och utförande data. Distribuerat köläge stöds inte över SQLite.

Kärnrekvisita

Vad varje queue-mode distribution behöver

Redis

Alla huvud- och arbetsprocesser behöver tillförlitlig tillgång till Redis service som används för kösamordning.

PostgreSQL

Huvud och arbetstagare måste dela databasen. Queue mode är en distribuerad arkitektur och bör inte utformas runt SQLite.

Matcha n8n konfiguration

Huvud och arbetstagare måste köra köläge och dela den konfiguration som behövs för att komma åt Redis, PostgreSQL och krypterade referenser.

Arbetsförmåga

Arbetare behöver tillräckligt med CPU och RAM för de arbetsflöden de utför. Att lägga till processer tar inte bort resurskostnaden för varje utförande.

Aktivera köläge på en befintlig egenhostad stack. För det första bekräftar du att n8n huvudtjänsten och varje arbetstagare kan nå samma PostgreSQL-databas och Redis över ett privat nätverk. Set EXECUTIONS_MODE=queue på både huvud- och arbetstagare och försörjning QUEUE_BULL_REDIS_HOST=redis och QUEUE_BULL_REDIS_PORT=6379 När när redis är ditt faktiska Compose service namn. Användning DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres och matchning DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER och DB_POSTGRESDB_PASSWORD på varje process; ersätt exemplet med dina. Ge exakt befintlig N8N_ENCRYPTION_KEY till alla. Publicera aldrig Redis eller PostgreSQL värdportar bara för att ansluta behållare på samma Compose-nätverk.

Starta en exekutör, inte en andra redaktör. Lägg till en n8n arbetstagartjänst med samma fasta n8n bildversion och delade inställningar som huvudsakliga, men kör den med worker kommandot. Om du namngav den tjänsten n8n-workerBörja det med docker compose up -d n8n-workerEfter att ha bekräftat faktisk utförande på en arbetstagare kan du använda docker compose up -d --scale n8n-worker=2 att starta en andra arbetstagare från den tjänsten. Dessa är tillägg till en befintlig korrekt konfigurerad Komponera stack, inte en fristående installationsfil; håll dina befintliga ihållande volymer, HTTPS proxy, hemligheter och säkerhetskopior.

Queue-mode komponera fragment för en befintlig stack. Sammanfoga exemplet nedan i din nuvarande compose.yamlDen är Inte inte En komplett fristående distribution. Det förutsätter att du redan har ihållande, privat postgres och n8n tjänster, en befintlig N8N_VERSION stift i din miljö och ditt eget skyddade POSTGRES_PASSWORD och original N8N_ENCRYPTION_KEYMatch dess namn, volymer, databas och n8n version till det befintliga projektet. Lägg till köläget Redis inställningar och EXECUTIONS_MODE=queue till den befintliga huvudtjänsten också, enligt beskrivningen ovan.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Ingen värdport publiceras för Redis eller arbetstagaren i detta fragment. Redis Append-only persistence är ett extra återhämtningsskikt, Inte inte ett substitut för off-server backups. Håll den befintliga HTTPS och autentiseringskonfigurationen oförändrad. För kodnoder som kräver externa aktivitetslöpare, konfigurera löparprocesserna för din arbetstagares distribution separat; köläge i sig ersätter inte aktivitetslöpare.

Omvandling av en befintlig SQLite 0 instans? Ändra inte bara DB_TYPE och börja mot en tom databas med PostgreSQL 0 : att göra det migrerar inte de gamla arbetsflödena och referenserna. Innan någon cutover, säkerhetskopiera källdatabasen, ihållande .n8n katalog och originalkrypteringsnyckel; använd en stödd n8n export / import eller migrationsprocedur, kontrollera sedan arbetsflöden och krypterade referenser på ett separat mål. Håll originalfilerna för återgång och använd Backup & Restore-guiden länkad nedan för återställningspreparat. Aldrig raderas aldrig database.sqlite Som en genväg.

Arbetarkonkurrens

Arbetare skala både genom räkning och av jobb per arbetstagare

Varje arbetstagare kan bearbeta flera jobb samtidigt. n8n nuvarande standardkonkurrens är 10 och dess dokumentation rekommenderar att 5 samlas eller högre. Mycket låg konkurrency i kombination med många arbetstagare kan skapa onödiga databasanslutningar och uttömma databasen.

Öka valutan när

En arbetare har reserv CPU och RAM och arbetsflödena väntar mest på externa tjänster istället för att mätta beräkning eller minne.

Lägg till arbetstagare när

En arbetsprocess blir en flaskhals och databasen, Redis och infrastrukturen har kapacitet för mer parallellt utförande.

Minska valutan när

Individuella arbetsflöden är minnes-tunga eller CPU-tunga och parallella jobb orsakar påstående, OOM tryck eller instabila utförandetider.

Se PostgreSQL

Fler arbetstagare och mer valuta ökar databasaktiviteten. Skalförmåga utan databaskapacitet kan flytta flaskhalsen istället för att ta bort den.

Vet vilken valutagräns som faktiskt gäller. En arbetstagare kan börja använda n8n worker --concurrency=5eller motsvarande befälhavare i din Compose-tjänst. Om N8N_CONCURRENCY_PRODUCTION_LIMIT är uttryckligen inställd på ett annat värde än -1Den inställningen tar företräde i köläge; annars använder n8n arbetstagarens --concurrency värde eller dess standard på 10. Multiplicera inte arbetstagare räknas av ett nominellt standard och kalla det garanterad genomströmning: faktisk kapacitet beror på arbetstid, CPU, minne, externa API och PostgreSQL anslutningar.

WEBHOOKS

Queue mode kan lägga till exekvering handoff latens

Den huvudsakliga eller webhook processen får HTTP begäran, men en arbetstagare utför arbetsflödesutförandet. Den handen genom Redis lägger till lite överhuvud. För latenskänsliga webhooks, mäta end-to-end svarstid snarare än att anta fler arbetstagare automatiskt göra varje begäran snabbare.

FåHuvud/webhook-processen accepterar begäran.
QueueAvrättning överlämnas till Redis.
UtförligEn tillgänglig arbetare driver arbetsflödet.
SvaraResultatet vidarebefordras genom kövägen när det behövs.

Route webhook trafik till rätt process. Med dedikerad n8n webhook processorer bakom en omvänd proxy eller lastbalanser, väg produktionsvägar /webhook/* och /webhook-waiting/* till webhook processorer; hålla /webhook-test/*, redaktör och API-anrop i huvudsak. Placera inte huvudet i produktionen webhook load-balanseringspool om du medvetet accepterar den extra arbetsbelastningen. Ett Svara på Webhook arbetsflödet kan hålla kunden väntar tills arbetaren slutar och returnerar sitt svar, så köläge är inte ett löfte om omedelbara HTTP svar eller noll timeouts. Testa det faktiska externa återkopplings- och responsbeteendet innan du byter trafik.

BINARY DATA

Förbise inte delad lagring

Filsystembegränsning

Queue mode stöder inte filsystem binär datalagring som den delade uthållighetsmodellen för distribuerade arbetstagare.

Extern binär lagring

När arbetsflöden måste bestå av binära data över distribuerade arbetstagare, använd en lagringsdesign som alla nödvändiga instanser kan komma åt, till exempel stödd extern objektlagring.

Stora webhook svar

Webhooks svar från arbetare reser tillbaka mot mottagandet. Stora svarsorgan kan öka Redis minnestrycket och kräver avsiktlig responslagringskonfiguration.

Planera innan de distribuerar arbetare

En arbetsbelastning som är starkt beroende av lokala filer måste omformas för delad uthållighet innan arbetarna sprids över maskiner.

Stor webhook svar gräns. Aktuell n8n dokumentation ger N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX ett standard 64 MiB för en arbetares svar skickas tillbaka genom köen. Redis kan hålla flera kopior i flygning, så budgeten ungefär 1.5 gånger svarsstorleken i Redis minne per samtidigt stort svar. Utan överbelastning misslyckas ett överdimensionerat svar istället för att bli magiskt snabbare genom att lägga till arbetare.

Version och licensgränser. Från n8n 2.34.0arbetstagare kan använda N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true för att överbelasta överdimensionerade webhook-responsorgan för läsbar delad binär lagring, men först uppgradera Alla huvud- och webhook-processorer 2.34.0 eller senare. Den valda N8N_DEFAULT_BINARY_DATA_MODE måste faktiskt lagra data och läsas av varje deltagande process. Extern S3 och Azure binär lagring kräver en giltig egenhostaderad Företag eller Enterprise licens; anta inte Community Edition kan göra det möjligt för dem. och database binärt läge kan överbelasta ett överdimensionerat svar utan betald extern lagring, men huvudinstansen laddar hela lagrad kropp till minne och databaslagring har sin egen filstorleksgräns. För Respons-body offload specifiktn8n beskriver också en delad filesystem alternativ när varje instans monterar samma disk, men uttryckligen inte rekommenderar det arrangemanget. Missa inte denna speciella avlastningsväg för stöd av filsystembaserade ihållande binära data i en distribuerad kö-läge driftsättning. Kontrollera din utgåva, version och lagringskonfiguration innan du aktiverar offload.

Meddelanden

Vet om köen hjälper

Queue Depth

En kö som växer snabbare än arbetarna dränerar det indikerar otillräcklig utförandekapacitet eller en nedströms flaskhals.

Arbetare CPU & RAM

Mät mättnad och minne toppar per arbetare. Idle arbetare med en växande köpunkt till en annan begränsning.

Exekverings latens

Spåra fördröjningen mellan en avrättning som skapas och faktiskt startar, inte bara själva arbetsflödet.

Hälsokontroller

Arbetstagarhälsoproblem kan rapportera om en arbetstagare lever och om dess databas och Redis-anslutningar är klara.

Kontrollera utförande på en arbetare, inte bara en grön behållare. Med en korrekt konfigurerad komponeringsstapel, kontrollera docker compose ps och docker compose logs --tail=100 n8n-worker (ersätt servicenamnet om det är annorlunda). Kör en ofarlig publicerad produktion arbetsflöde med hjälp av en schemalagd trigger eller test webhook, matcha sedan dess utförande i n8n Avrättningsvyn till faktisk arbetstagare bearbetning i arbetarloggarna. En redaktör som öppnar framgångsrikt, en löpande Redis behållare eller en kö utförande ensam gör Inte inte bevisa att en arbetare har utfört jobbet.

Kontrollera beroende och beredskap. Med standardexempel på servicenamn, docker compose exec -T redis redis-cli ping bör ta emot PONG när Redis autentisering tillåter det, och docker compose exec -T postgres pg_isready -U n8n -d n8n kontroller PostgreSQL beredskap (anpassar referenser och servicenamn). Aktivera QUEUE_HEALTH_CHECK_ACTIVE=true på en arbetstagare när du behöver sin privata /healthz och /healthz/readiness endpoints; beredskapsslutpunkten kontrollerar Redis/databasanslutning. Utsätt inte dessa arbetstagare slutpunkter offentligt bara för att övervaka dem.

Manuella körningar är ett annat test. Som standard OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=falseSå manuellt kör ett arbetsflöde i redaktören kan utföra på huvudet även när köläge är korrekt konfigurerat. Ställ den för true endast om du avser att skicka manuella körningar till arbetstagare och har kontrollerat förändringen i en iscensättningsmiljö. Queue-mode-arbetare skiljer sig också från n8n externa aktivitetslöpare, som har separata konfigurationskrav för kod-nod-utförande.

HIGH AVAILABILITY BOUNDARY

Köläge skalar körningar, men det gör inte automatiskt huvudprocessen mycket tillgänglig

Dela krypteringsnyckeln

Varje arbetare måste använda samma N8N_ENCRYPTION_KEY som huvudinstans så att arbetare kan dekryptera referenser som krävs genom utförande av arbetsflöden.

Håll versioner anpassade

Huvud-, webhook- och arbetsprocesser bör köra samma n8n-version. Blandade versioner kan skapa oförenligt beteende under rullande förändringar.

Webhook processorer är ett separat skallager

När inkommande webhook volym blir flaskhalsen, kan dedikerade webhook processorer sitta bakom en lastbalans medan arbetare hanterar utförande. Lägg inte till detta lager om inte uppmätt begäran volym motiverar det.

Multi-main är en annan funktion

Att köra flera huvudprocesser för hög tillgänglighet är inte detsamma som vanligt köläge. n8n för närvarande dokumenterar multi-main som en egenhostad Enterprise-funktion med ytterligare belastnings- och sessionskrav.

Officiell kö-läge arkitektur och konfiguration

Vanliga frågor

n8n köläge: gemensamma frågor

Behöver n8n köläge Redis?

Ja. Redis är den meddelandemäklare som samordnar i väntan på körningar mellan huvudinstansen och arbetarna.

Kan köläge använda SQLite?

Nej för den distribuerade kö-mode arkitekturen. Huvud- och arbetstagare behöver delad databasåtkomst och n8n dokument PostgreSQL som databasen för denna inställning.

Hur många arbetare ska jag springa?

Det finns ingen universell räkning. Börja från mätt samkurs- och arbetarutnyttjande, lägg sedan till kapacitet medan du övervakar PostgreSQL, Redis, CPU, RAM och ködjup.

Vad är n8n arbetstagarkonkurrens?

Det är antalet jobb en arbetstagare kan behandla parallellt. Den nuvarande standarden är 10, och n8n rekommenderar arbetstagarens samtidighet av 5 eller högre snarare än att skapa många lågkonkurrensarbetare.

Ska jag aktivera köläge på en liten VPS?

Först när arbetsbelastningen motiverar det. En liten driftsättning som fungerar bekvämt som ett exempel är oftast enklare att arbeta utan Redis och separata arbetare.
