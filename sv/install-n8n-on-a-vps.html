INSTALLATION MED DOCKER

Installera n8n på en VPS

Installera n8n på en VPS med Docker Compose och PostgreSQL. En produktionsmiljö behöver också beständig lagring för applikationens och databasens data, en oförändrad N8N_ENCRYPTION_KEY, ett publikt värdnamn, HTTPS och korrekta webhook-inställningar. Kontrollera detta innan du aktiverar arbetsflöden i produktion.

FÖRBEREDELSER

Linux-VPS

Använd en Linux-server som fortfarande får uppdateringar och har tillräckliga resurser för n8n, PostgreSQL, Docker och en omvänd proxy.

DNS

Låt en domän eller underdomän peka på din VPS innan du skaffar TLS-certifikat och publicerar webhook-adresser.

Docker Compose

Installera Docker Engine och Compose-pluginet med paket som stöds av operativsystemet.

Brandvägg

Öppna bara de portar som behövs för administration och webbtrafik. Håll PostgreSQL och interna applikationstjänster oåtkomliga utifrån.

Ska du installera n8n på en VPS som redan har webbplatser? Du kan lägga till n8n på en server du själv hanterar om CPU, RAM och lagring räcker. Men om Nginx, Apache, Caddy eller en annan omvänd proxy redan använder portarna 80/443 ska du inte starta Caddy-containern i exemplet nedan utan ändringar: portarna kommer att krocka. Låt i stället din befintliga omvända proxy hantera en ny underdomän för n8n via ett lämpligt privat nätverk, eller använd en separat VPS för exakt detta Compose-exempel. Behåll de andra webbplatserna och deras TLS-inställningar. Exemplet förutsätter att portarna 80/443 är lediga.

INSTALLATION: KOPIERA OCH ANPASSA

Installera n8n på din VPS med Docker Compose

Använd exemplet för att installera n8n på en självhanterad Linux-VPS. Du installerar och underhåller n8n själv. En server som köps via vår partner levereras inte med n8n förinstallerat. Exemplet kombinerar n8n, PostgreSQL, en extern task runner och HTTPS via Caddy i ett privat Compose-nätverk. Det är en konfigurationsmall, inte ett påstående om att installationen har testats i verklig drift.

Vill du komma igång snabbare med en ny installation? n8n erbjuder också en officiell Docker-installation med ett enda kommando. Du kan ladda ned och granska skriptet med curl -fsSL https://get.n8n.io -o get-n8n.sh innan du kör sh get-n8n.sh. Det alternativet startar en första instans med SQLite på en lokal adress och innehåller även sandbox-tjänster för n8n Assistant. Det är inte samma sak som den här VPS-installationen med publik HTTPS och PostgreSQL. Den fullständiga officiella sandbox-miljön behöver mer RAM och CPU än en enkel n8n-installation (enligt Compose-guiden minst 4 GB RAM / 2 vCPU). För en produktionsserver som ska nås från internet fortsätter du med den manuellt konfigurerade miljön nedan.

1. Förbered Docker, DNS och åtkomst

Anslut via SSH med sudo-behörighet och låt en DNS-post av typen A för n8n.example.com peka på din VPS IPv4-adress. På en ny VPS med Ubuntu 22.04, 24.04 eller 26.04 installerar följande kommandon Docker Engine och det moderna pluginet docker compose från Dockers officiella signerade paketförråd för apt:

# Fresh official Ubuntu 22.04 / 24.04 / 26.04 installation
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Register Docker's signed apt repository
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

Detta är metoden med paketförråd för produktionsmiljöer som beskrivs i Dockers officiella installationsguide för Ubuntu. Installera inte om eller ta bort Docker utan att först kontrollera en VPS där containrar eller andra webbplatser redan körs; undersök först den befintliga installationen och möjliga paketkonflikter. Om du använder Debian eller en annan distribution ska du följa de officiella instruktionerna för det operativsystemet i stället för Ubuntu-kommandona.

Kontrollera nu Docker, Compose-pluginet, DNS och arbetskatalogen:

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

Om getent hosts inte ger någon adress eller ger fel adress ska du rätta DNS innan du startar Caddy. Ersätt n8n.example.com genom hela guiden med ditt riktiga värdnamn. Docker kräver normalt root-behörighet. Om din SSH-användare inte kan köra följande docker compose kommandon direkt ska du skriva sudo före dem. Att lägga till en användare i gruppen docker ger behörigheter motsvarande root och bör inte göras lättvindigt på en delad server.

Se till att den SSH-port du faktiskt använder fortfarande går att nå innan du aktiverar brandväggen. Tillåt inkommande HTTP (80) och HTTPS (443) för certifikat och redigeraren. Docker-publicerade containerportar kan kringgå vissa UFW-regler. Läs därför Dockers brandväggsanvisningar och publicera bara de avsedda Caddy-portarna. Detta Compose-exempel publicerar med avsikt inte PostgreSQL (5432), n8n (5678) eller task runner-brokern (5679) mot internet.

2. Skapa miljövariabler och bevara krypteringsnyckeln

Generera tre olika slumpmässiga hexadecimala värden från projektkatalogen:

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

Skapa en fil med namnet .env utifrån mallen nedan. Ersätt varje REPLACE_WITH_RANDOM_HEX med ett eget genererat värde och ändra värdnamn och tidszon. Taggen 2.42.5 motsvarar den stabila version som angavs den 8 oktober 2026. Den används som ett daterat konfigurationsexempel, inte som en garanti för att installationen har driftstestats eller kommer att vara säker framöver. Kontrollera aktuella officiella n8n-versioner före installationen och använd samma verifierade version för både n8n och dess task runner-avbildning.

# .env — replace the three example secrets
# Pin a maintained n8n release; keep n8n and runner equal.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

Lägg aldrig upp .env i ett offentligt kodförråd. Förvara krypteringsnyckeln och återställningsinstruktionerna säkert utanför VPS:en. Nyckeln måste vara densamma även efter att containrar har återskapats eller installationen har flyttats.

3. Skapa compose.yaml för en ny installation

Skapa i samma katalog filen compose.yaml. Exemplet följer n8n:s officiella konventioner för miljövariabler och sökvägen PGDATA för PostgreSQL 18 enligt dokumentationen för n8n:s hostingprojekt:

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

De fyra tjänsterna har olika uppgifter: PostgreSQL lagrar databasdata, n8n kör arbetsflöden, n8n-runner kör uppgifter med matchande version och gemensam autentiseringstoken, och Caddy hanterar offentlig HTTPS. En extern task runner är inte samma sak som köläge med Redis. Bara Caddy publicerar portar på värdservern. Det här resurssnåla exemplet använder en enda databasroll för installationen. För bättre åtskillnad av PostgreSQL-behörigheter, se n8n:s officiella exempel med PostgreSQL.

4. Skapa Caddyfile för HTTPS

Skapa filen Caddyfile (stort C, utan filändelse) bredvid compose.yaml. Ersätt exempelvärdnamnet överallt med ditt eget DNS-namn:

n8n.example.com {
    reverse_proxy n8n:5678
}

Caddy begär och förnyar publika TLS-certifikat när domänen pekar rätt och extern trafik når portarna 80/443. Låt inte DNS peka på localhost. Om du använder en annan omvänd proxy än Caddy måste du vidarebefordra rätt värdnamn, protokoll och klientadress i HTTP-headers och justera N8N_PROXY_HOPS efter det faktiska antalet betrodda proxysteg.

5. Starta containrarna och testa utifrån

Kör följande kommandon från projektkatalogen efter att du har sparat .env, compose.yaml och Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

Det sista kommandot kontrollerar hälsostatusen via publik HTTPS. Om certifikatet fortfarande håller på att utfärdas ska du kontrollera Caddy-loggarna samt DNS och portar innan du antar att n8n är trasigt. Öppna https://n8n.example.com, skapa omedelbart det första ägarkontot och aktivera lämpligt inloggningsskydd. Kontrollera även att instansen kan köra ett arbetsflöde och inte bara visa redigeraren:

  1. Skapa ett arbetsflöde i redigeraren med triggern Webhook. Välj HTTP Method som GET, ange Path som vps-check och ställ in Respond på Immediately. Spara arbetsflödet.
  2. Klicka på Listen for Test Event, kopiera den fullständiga Test URL som n8n visar och kör från en annan enhet curl -i 'PASTE_TEST_URL_HERE' med den kopierade adressen. Du ska få ett lyckat HTTP-svar och se den inkommande händelsen i n8n-redigeraren. Testadressen fungerar bara så länge n8n lyssnar efter händelsen.
  3. Publicera arbetsflödet, byt nodens adress till Production URL, kopiera den och kör curl -i 'PASTE_PRODUCTION_URL_HERE' igen. Kontrollera körningen under fliken Executions för arbetsflödet. För att webhooks i produktion ska fungera måste arbetsflödet vara publicerat. Förfrågningarnas data visas inte i redigerarens testvy.

Det här är avsiktligt ett enkelt funktionstest utan autentisering. Skicka aldrig hemligheter till det. Avpublicera eller ta bort arbetsflödet efteråt, eller konfigurera autentisering för Webhook och IP-begränsningar innan du använder en publik adress för riktiga data. Se n8n:s officiella dokumentation om test- och produktionsadresser för Webhook.

6. Säkerhetskopiera före ändring av låsta versioner

Spara en återställningsbar PostgreSQL-dump och den beständiga datavolymen för n8n, .env-filen med krypteringsnyckeln samt nödvändiga externa filer på en plats utanför servern. Testa återställning enligt guiden för säkerhetskopiering och återställning innan du uppdaterar produktionsmiljön. Exempel på kommandon:

# Back up the database, encryption key, instance data,
# and files before changing the pinned versions.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# After securing the backup outside this VPS:
docker compose pull
docker compose up -d
docker compose ps

Ändra den låsta N8N_VERSION först efter att du har läst versionsinformationen. n8n-avbildningen och task runner-avbildningen måste uppdateras till samma version. Kör inte docker compose down -v vid normalt underhåll eftersom det tar bort namngivna datavolymer. Större versionsbyten av PostgreSQL kräver uppgradering av databasen eller en plan för dump och återställning. Att bara byta ut Postgres 18-avbildningen mot en annan huvudversion migrerar inte databasen automatiskt.

Officiella källor: n8n:s guide för Docker Compose, anvisningar för omvänd proxy och webhooks samt PostgresSQL:s officiella driftsättningsdokumentation. Inga prestandatester av infrastrukturen eller förinstallerade leverantörsfunktioner förutsätts.

VANLIGA FEL

Varför fungerar en n8n-installation med Docker lokalt men inte i produktion?

Fel webhook-adress

Callback-adresser pekar på localhost, HTTP eller ett internt värdnamn i stället för den publika HTTPS-adressen.

Ingen beständig lagring

Applikations- eller databasdata försvinner när en container återskapas.

Förlorad krypteringsnyckel

Sparade inloggningsuppgifter slutar fungera efter en ominstallation eftersom den nya instansen använder en annan nyckel.

Publik databasport

PostgreSQL är onödigt exponerat för internet trots att bara n8n behöver ansluta till databasen.

VANLIGA FRÅGOR

Installera n8n med Docker: vanliga frågor

Behöver n8n PostgreSQL när det körs i Docker?

Docker kräver inte PostgreSQL; små installationer kan använda SQLite. För en produktionsinriktad VPS-installation ger PostgreSQL en robustare databasgrund och möjliggör senare skalning med köläge.

Varför behövs en beständig n8n-volym om PostgreSQL lagrar data?

Den beständiga n8n-katalogen kan innehålla viktigt instanstillstånd och konfiguration. Bevara den enligt installationsupplägget i stället för att anta att databasen är den enda resurs som behövs för återställning.

Varför visar min webhook localhost?

Den interna containeradressen skiljer sig från den publika adressen. Ange externt värdnamn, protokoll och webhook-URL och kontrollera att den omvända proxyn vidarebefordrar nödvändiga headers.

Ska port 5678 vara publik?

Vid normal produktionsdrift bakom en omvänd proxy ska HTTPS vara publikt via proxyn, medan n8n:s applikationsport förblir intern om du inte har ett särskilt skäl att göra annat.

Behöver jag Redis?

Inte för en vanlig Docker-installation med en n8n-instans. Redis blir relevant när du väljer köläge och separata workers.

Är externa task runners samma sak som workers i köläge?

Nej. Externa task runners kör stödd uppgiftskod separat från n8n:s huvudprocess och använder en gemensam autentiseringstoken. Köläge med Redis fördelar körningar av arbetsflöden och har egna infrastrukturkrav. Exemplet här visar en extern task runner, inte köläge med Redis. Task runner-avbildningen ska ha samma version som n8n.
