Säkra n8n på en VPS

För att säkra n8n på en VPS, hålla n8n (5678), PostgreSQL (5432) och valfri Redis (6379) utanför det offentliga internet; använd en HTTPS omvänd proxy, SSH nycklar och MFA, bevara din krypteringsnyckel, autentisera webhooks, begränsa riskfyllda arbetsflödesfunktioner och granska det utplacerade exemplet. Skydda redaktören separat från de offentliga webhook-rutterna. HTTPS ensam inte säkra de uppkopplade tjänsterna.

NETWORK EDGE

Omvänd proxy, HTTPS och betrodda rubriker

TLS-terminering

Använd en omvänd proxy som Nginx, Caddy eller Traefik för att avsluta HTTPS. Omdirigera enkel HTTP och undvik att exponera ansökningsporten n8n direkt när proxyn är den avsedda ingångspunkten.

Proxy konfiguration

När n8n löper bakom en omvänd proxy, konfigurera proxy hop-räkningen korrekt och passera de vidarebefordrade rubrikerna n8n måste rekonstruera den ursprungliga klientförfrågan.

Säker cookies

Servera redaktören över HTTPS så autentiseringscookies kan förbli säkra. Arbeta inte runt en trasig TLS-inställning genom att försvaga cookie-säkerheten.

Webhook URL

Ange den offentliga webhook-adressen till det externt nåbara HTTPS-värdnamnet så genererade webhook endpoints pekar inte på en intern behållare eller HTTP-adress.

Håll redaktören privat utan att bryta webhooks. Begränsad åtkomst med hjälp av en VPN, betrodd IP-policy eller en autentiserad proxy när det är praktiskt. Offentliga webhook mottagare och OAuth uppringningsrutter kan behöva förbli nåbara; testa både en betrodd redaktör inloggning och en verklig extern uppmaning innan verkställa en proxy regel. Framåt klient-adress rubriker endast från betrodda proxys, inte godtyckliga begäran rubriker.

Autenticate webhook callers: i Webhook-noden väljer Basic, Header eller JWT-autentisering istället för Ingen när den stöds av avsändaren. Använd dess IP(s) Allowlist om så är lämpligt och verifiera leverantörssignaturer där integrationen stöder undertecknade förfrågningar. En svår att gissa URL är inte tillräcklig autentisering. Applicera räntebegränsningar vid proxy när det är lämpligt och bekräfta giltiga utbrott blockeras inte. Officiella Webhook-autentiseringsalternativ.

VPS HARDENING

Minska serverattackens yta

Brandvägg

Standardförnekelse oönskad inkommande trafik och tillåter endast tjänster som måste nås. Databas och Redis hamnar normalt på privata/lokala nätverk.

SSH

Föredra SSH nycklar över lösenord, inaktivera onödiga inloggningsvägar och begränsa administrativ åtkomst. Rot-ekvivalent tillgång bör kontrolleras hårt.

OS-uppdateringar

Patch the Linux värd och container runtime. Tillämpningshärdning kan inte kompensera för ett exponerat eller föråldrat operativsystem.

Container exponering

Publicera endast de hamnar som behöver värdåtkomst. Interna tjänster bör kommunicera på privata Docker-nät snarare än genom offentliga gränssnitt.

Inspektera innan du ändrar brandvägg eller SSH inställningar: kontrollera lyssningsportar med sudo ss -lntp, Docker Publicering med docker compose ps från projektkatalogen och värd brandväggspolicy med sudo ufw status verbose Om UFW används. Kontrollera din faktiska SSH-port och framgångsrik nyckelinloggning i en separat session innan du inaktiverar lösenordsåtkomst. Publicerade Docker-portar kan kringgå UFW-reglerna; endast en sidoväggsstatus bevisar inte port 5678 är privat. Kontrollera verklig extern tillgänglighet. Docker/UFW-kaveat.

Kontrollera automatiska säkerhetsuppdateringar Ubuntu istället för att anta att de fungerar: Inspekt apt-config dump APT::Periodic::Unattended-Upgrade och loggen /var/log/unattended-upgrades/unattended-upgrades.logOm obevakade säkerhetsuppgraderingar är inaktiverade, sudo dpkg-reconfigure unattended-upgrades ger en stödd konfigurationsdialog. Granska omstart och servicestart beteende innan du aktiverar det på en fungerande VPS. Ubuntu APT-uppdateringar gör Inte inte Uppdatera automatiskt n8n Docker-bilden eller varje tredjepartsprogramvara. Ubuntu automatisk uppdaterad dokumentation.

Valfritt SSH brute-force övervakning: Fail2Ban kan upptäcka upprepade misslyckade SSH Inloggningar. Om installerad och konfigurerad för SSHverifiera fängelset med sudo fail2ban-client status sshd och bekräfta att den läser din faktiska SSH autentiseringslogg eller tidskrift och matchar den konfigurerade porten. Detta kompletterar SSH nycklar och nätrestriktioner; det ersätter dem inte. Kopiera inte en fast SSH-port eller förbudsregel utan att först kontrollera befintlig åtkomst. Ubuntu SSH härdande vägledning.

N8N SECRETS

Skydda krypteringsnyckeln och kreditgränsen

Krypteringsnyckeln

n8n krypterar lagrade referenser med hjälp av sin krypteringsnyckel. Bevara samma nyckel över omstart och arbetstagare och skydda den separat från vanligt applikationsinnehåll.

Miljöhemligheter

Begå inte lösenord, tokens eller krypteringsnyckeln till ett offentligt förvar. Begränsa tillgången till miljöfiler och distributionshemligheter.

Användaråtkomst

Ge redaktör tillgång endast till pålitliga användare. Arbetsflöden kan ansluta till känsliga system och kan bearbeta hemligheter eller utföra kraftfulla noder.

Behörig omfattning

Använd snävare servicekonton och API tokens där så är möjligt. Ett komprometterat arbetsflöde bör inte automatiskt ärva bred tillgång till orelaterade system.

n8n konfiguration för att granska: N8N_BLOCK_ENV_ACCESS_IN_NODE=true förhindrar kodnod och uttrycksåtkomst till miljövärden, N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true begär endast ägarbehörigheter i inställningarna. Håll N8N_ENCRYPTION_KEY ihållande och säkerhetskopierad säkert: n8n kan skapa en slumpmässig nyckel vid första starten, men att förlora det kan göra befintliga krypterade referenser oanvändbara. Byt inte ut en produktionskrypteringsnyckel tillfälligt; använd en officiellt stödd rotationsprocedur. Blockering av miljöåtkomst kan bryta befintliga integrationer, så testa innan produktionen förändras. n8n Säkerhetsvariabla definitioner.

Noder kan utöka säkerhetsgränsen

Självvärdering ger arbetsflöden betydande makt. Kodutförande, skaltillgång, godtyckliga HTTP förfrågningar och tredje parts gemenskapsnoder kan öka risken. Inaktivera funktionalitet du inte behöver och granska opålitlig arbetsflöde import innan du kör dem.

Använd exakta stödda kontroller: Konfigurera NODES_EXCLUDE med en JSON samling noder att inaktivera, såsom n8n-nodes-base.executeCommand och n8n-nodes-base.readWriteFileOm oanvänd. Vissa högrisknoder blockeras redan som standard i nyare versioner; granska den faktiska listan innan du ändrar den. Officiella nod-uteslutningar.

Från n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true möjliggör kontroller för utgående HTTP-förfrågningar till interna, loopback- och metadataadressområden. Legitima interna API arbetsflöden kan sluta fungera, om nödvändigt, smalt tillåtna endast destinationer du kontrollerar. Håll nätverkssegmentering som primärförsvar. För kodnod isolering, granska externa aktivitetslöpare. SSRF-skydd · Task-runner isolering.

Uppdatera medvetet

Monitor autentisering

Titta på oväntade åtkomstmönster, arbetsflödesförändringar och misslyckanden. Begränsa redaktören UI ytterligare när din operativa modell inte kräver bred publik tillgänglighet.

Förbered återhämtning och återhämtning

Ta återställningsbara säkerhetskopior innan betydande uppgraderingar. Detaljerad backup omfattning och restaurering tillhör den separata återställningsguiden.

Minimera känslig utförandehistorik: framgångsrika körningar kan kvarstå kunddata och tokens. När det är lämpligt EXECUTIONS_DATA_SAVE_ON_SUCCESS=noneHåll EXECUTIONS_DATA_PRUNE=trueoch välj en EXECUTIONS_DATA_MAX_AGE i timmar, till exempel 168 (Sju dagar). Dessa är konfigurerbara exempel, inte lagstadgade lagringsregler. Mindre historia betyder mindre felsökning och rättsmedicinsk data; löpning, väntan eller annoterade avrättningar får inte beskäras på samma sätt. Officiell avrättning lagring.

Misstänkt kompromiss: begränsa skadlig tillgång utan att förstöra bevis, inspektera proxy, värd och n8n aktivitet och ändrade arbetsflöden, återkalla eller rotera eventuellt exponerade uppströmsuppgifter, patch orsaken och återställa endast från testade återställningsbara säkerhetskopior när det behövs. Granska drabbade webhook-adresser, redaktörskonton och anslutna tjänster; anta inte HTTPS, ögonblicksbilder eller ett köp av VPS ger incident-responstjänster.

Kräver starkare inloggningsskydd

Aktivera tvåfaktorsautentisering för redaktörskonton och genomdriva MFA genom n8n säkerhetspolicyer när din utgåva stöder centraliserad politik.

Begränsa vem som kan redigera arbetsflöden

Redaktörsåtkomst är privilegierad åtkomst: arbetsflöden kan läsa referenser, ringa interna system och utföra kraftfulla noder. Håll användaråtkomsten smal och ta bort konton som inte längre behöver den.

Inaktivera funktioner som du inte använder

Minska ansökningsattackytan genom att inaktivera den offentliga API när det är onödigt och blockera högrisknoder eller funktioner som din operativa modell inte behöver.

Använd SSRF och hemliga kontroller medvetet

För arbetsflöden som kan göra godtyckliga HTTP-förfrågningar, utvärdera n8n SSRF-skydd och hålla hemligheter ur arbetsflödeskod, offentliga repositorier och allmänt läsbara miljöfiler.

Begränsa outnyttjade förvaltnings endpoints: N8N_PUBLIC_API_DISABLED=true inaktiverar n8n offentliga REST API, och N8N_PUBLIC_API_SWAGGERUI_DISABLED=true inaktiverar sin API lekplats separat. Gör detta endast när dina integrationer inte kräver dessa funktioner. Inaktivera REST API autentiserar inte arbetsflödesadresser. Vanliga frågor

n8n VPS Säkerhet: gemensamma frågor

Ska n8n hamnen exponeras direkt?

När en omvänd proxy är den offentliga ingången, exponera proxy och hålla ansökningsporten bakom den snarare än att publicera onödiga tjänster i stort.

Ska PostgreSQL eller Redis vara offentliga?

Normalt nej. De bör endast nås av de system som kräver dem. Offentlig exponering ökar attackytan utan att hjälpa normal n8n operation.

Varför är krypteringsnyckeln n8n viktig?

Det skyddar uppgifter som lagras av n8n och måste förbli konsekventa över utplaceringen. Att förlora det kan förhindra återställda data från att ge användbara krypterade referenser.

Är gemenskapsnoder säkra?

De förlänger n8n med tredjepartskod, så de bör behandlas som mjukvaruberoende med sina egna försörjningskedjor och privilegier. Installera bara vad du litar på och behöver.

Gör HTTPS en självhävd n8n instans säker?

HTTPS skyddar transporten. Produktionssäkerhet kräver också värdhärdning, åtkomstkontroll, privata backendtjänster, hemligt skydd, säkra arbetsflödesfunktioner, övervakning och uppdateringar.

Kan n8n redaktören vara privat medan produktionsrobotar fortfarande körs?

Ja. En betrodd omvänd proxy eller VPN kan begränsa redaktör / admin åtkomst separat från offentlig produktion webhook och OAuth callback vägar. Testa pålitlig inloggning och extern webhook leverans efter varje åtkomst regeländring för att undvika oavsiktligt blockera dina integrationer.

Hur autentiserar jag inkommande n8n webhooks?

Konfigurera Basic, Header eller JWT-autentisering i Webhook-noden när avsändaren stöder den. Du kan också använda IP(s) Tillåt lista och kontrollera leverantörssignaturer där de finns tillgängliga. Förlita dig inte bara på en hemlig väg, och validera förfrågningar innan de utlöser känsliga API åtgärder.
