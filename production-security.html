PRODUCTION SECURITY

Secure n8n on a VPS: production hardening checklist

A public n8n instance can hold API keys, OAuth tokens, database credentials and automation access to other systems. Production security therefore starts at the VPS edge and continues through n8n configuration, credentials, nodes and update policy.

QUICK CHECKLIST

Minimum security baseline before public exposure

HTTPS only

Put n8n behind a correctly configured TLS reverse proxy and use the public HTTPS URL consistently for the editor and webhooks.

Minimal open ports

Expose only the ports required for public traffic. Keep PostgreSQL, Redis and internal application ports off the public internet.

Harden SSH

Use key-based administration, restrict who can log in and keep the operating system patched.

Protect credentials

Keep the n8n encryption key stable and secret. Treat environment files, database access and backup copies as sensitive assets.

NETWORK EDGE

Reverse proxy, HTTPS and trusted headers

TLS termination

Use a reverse proxy such as Nginx, Caddy or Traefik to terminate HTTPS. Redirect plain HTTP and avoid exposing the n8n application port directly when the proxy is the intended entry point.

Proxy configuration

When n8n runs behind a reverse proxy, configure the proxy hop count correctly and pass the forwarded headers n8n needs to reconstruct the original client request.

Secure cookies

Serve the editor over HTTPS so authentication cookies can remain secure. Do not work around a broken TLS setup by weakening cookie security.

Webhook URL

Set the public webhook URL to the externally reachable HTTPS hostname so generated webhook endpoints do not point at an internal container or HTTP address.

VPS HARDENING

Reduce the server attack surface

Firewall

Default-deny unsolicited inbound traffic and permit only services that must be reachable. Database and Redis ports normally belong on private/local networks.

SSH

Prefer SSH keys over passwords, disable unnecessary login paths and limit administrative access. Root-equivalent access should be tightly controlled.

OS updates

Patch the Linux host and container runtime. Application hardening cannot compensate for an exposed or obsolete operating system.

Container exposure

Publish only the ports that need host access. Internal services should communicate on private Docker networks rather than through public interfaces.

DATABASE & REDIS

Keep backend services private

PostgreSQLBind it to a private interface or container network unless remote access is explicitly required and independently secured.
RedisQueue-mode Redis is infrastructure, not a public endpoint. Restrict network access to the n8n components that require it.
CredentialsUse dedicated database credentials with only the permissions the application needs and protect them outside source control.
TransportWhen database traffic crosses untrusted networks, use appropriate encrypted transport rather than relying on application-level credential encryption.

N8N SECRETS

Protect the encryption key and credential boundary

Encryption key

n8n encrypts stored credentials using its encryption key. Preserve the same key across restarts and workers and protect it separately from ordinary application content.

Environment secrets

Do not commit passwords, tokens or the encryption key to a public repository. Restrict access to environment files and deployment secrets.

User access

Give editor access only to trusted users. Workflows can connect to sensitive systems and may process secrets or execute powerful nodes.

Credential scope

Use narrowly scoped service accounts and API tokens where possible. A compromised workflow should not automatically inherit broad access to unrelated systems.

WORKFLOW RISK

Nodes can expand the security boundary

Self-hosting gives workflows substantial power. Code execution, shell access, arbitrary HTTP requests and third-party community nodes can increase risk. Disable functionality you do not need and review untrusted workflow imports before running them.

Community nodesInstall only packages you trust; they execute inside your n8n environment.
Risky nodesExclude nodes that your deployment does not need when their capabilities exceed the intended workflow boundary.
SSRFUse n8n's SSRF protection and network controls where workflows should not be able to reach internal or metadata endpoints.
Workflow importsReview imported workflows, credentials, expressions and executable steps before activation.

AUDIT & UPDATES

Security is an operating process

Run n8n security audit

Use n8n's security audit capability to identify common configuration and workflow risks. Treat it as a diagnostic layer, not a replacement for host security.

Update deliberately

Keep n8n current enough to receive security fixes. Review release notes and test important upgrades rather than leaving an internet-facing instance permanently stale.

Monitor authentication

Watch unexpected access patterns, workflow changes and failures. Restrict the editor UI further when your operating model does not require broad public reachability.

Prepare rollback and recovery

Take recoverable backups before significant upgrades. Detailed backup scope and restoration belong to the separate recovery guide.

ACCOUNT & PLATFORM CONTROLS

Protect the editor as well as the VPS

Require stronger login protection

Enable two-factor authentication for editor accounts and enforce MFA through n8n security policies when your edition supports centralized policy enforcement.

Limit who can edit workflows

Editor access is privileged access: workflows can read credentials, call internal systems and execute powerful nodes. Keep user access narrow and remove accounts that no longer need it.

Disable capabilities you do not use

Reduce application attack surface by disabling the public API when it is unnecessary and blocking high-risk nodes or features that your operating model does not need.

Use SSRF and secret controls deliberately

For workflows that can make arbitrary HTTP requests, evaluate n8n's SSRF protection and keep secrets out of workflow code, public repositories and broadly readable environment files.

FAQ

n8n VPS security: common questions

Should the n8n port be exposed directly?

When a reverse proxy is the public entry point, expose the proxy and keep the application port behind it rather than publishing unnecessary services broadly.

Should PostgreSQL or Redis be public?

Normally no. They should be reachable only by the systems that require them. Public exposure increases attack surface without helping normal n8n operation.

Why is the n8n encryption key important?

It protects credentials stored by n8n and must remain consistent across the deployment. Losing it can prevent recovered data from yielding usable encrypted credentials.

Are community nodes safe?

They extend n8n with third-party code, so they should be treated as software dependencies with their own supply-chain and privilege risks. Install only what you trust and need.

Does HTTPS make a self-hosted n8n instance secure?

No. HTTPS protects transport. Production security also requires host hardening, access control, private backend services, secret protection, safe workflow capabilities, monitoring and updates.
