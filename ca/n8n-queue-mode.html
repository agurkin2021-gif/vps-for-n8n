ESCALABILITAT

Mode de cua de n8n

El mode de cua separa l'execució dels fluxos de treball del procés principal d'n8n. La instància principal rep els activadors i crea les execucions, Redis coordina la cua, els workers executen les tasques i PostgreSQL desa les dades compartides dels fluxos de treball i de les execucions.

DECISIÓ RÀPIDA

Realment necessiteu el mode de cua?

Manteniu el mode normal si

Una sola instància gestiona sense problemes els pics d'execucions i la CPU, la RAM i la latència es mantenen estables. El mode de cua afegiria components que encara no necessiteu.

Valoreu el mode de cua si

Les execucions paral·leles sostingudes provoquen competència pels recursos, la latència augmenta amb la càrrega o necessiteu ampliar la capacitat d'execució amb diversos workers.

Amplieu primer els recursos del servidor si

El coll d'ampolla és simplement la manca de CPU o RAM i una sola instància més potent encara pot gestionar adequadament la càrrega de treball.

Mesureu abans de canviar l'arquitectura

Justifiqueu el canvi amb dades sobre pics d'execucions simultànies, CPU, RAM, durada de les execucions, tasques pendents a la cua i càrrega de la base de dades.

ARQUITECTURA

Com funciona el mode de cua d'n8n

1 · Procés principalRep els activadors programats, els webhooks i les sol·licituds d'execució dels fluxos de treball. Crea l'execució en lloc de processar-la directament.
2 · RedisActua com a intermediari de missatges. Manté els missatges de les execucions pendents perquè el següent worker disponible pugui assumir la tasca.
3 · WorkerRep l'identificador de l'execució, carrega les dades del flux de treball des de la base de dades compartida, executa el flux i desa el resultat.
4 · PostgreSQLProporciona dades persistents compartides dels fluxos de treball i de les execucions. El mode de cua distribuït no és compatible amb SQLite.

REQUISITS BÀSICS

Què necessita qualsevol desplegament amb mode de cua?

Redis

Tant el procés principal com els workers necessiten accés fiable al servei Redis que coordina la cua.

PostgreSQL

El procés principal i els workers han de compartir la mateixa base de dades. El mode de cua és una arquitectura distribuïda i no s'ha de dissenyar al voltant de SQLite.

Configuració coherent d'n8n

El procés principal i els workers han d'utilitzar el mode de cua i compartir la configuració necessària per accedir a Redis, PostgreSQL i les credencials xifrades.

Capacitat dels workers

Els workers necessiten prou CPU i RAM per als fluxos que executen. Afegir processos no elimina el consum de recursos de cada execució.

Activeu el mode de cua en una instal·lació autoallotjada existent. Primer comproveu que el servei principal d'n8n i tots els workers poden accedir a la mateixa base de dades PostgreSQL i al mateix Redis per una xarxa privada. Establiu EXECUTIONS_MODE=queue al procés principal i a tots els workers, i configureu QUEUE_BULL_REDIS_HOST=redis i QUEUE_BULL_REDIS_PORT=6379 quan redis sigui el nom real del vostre servei de Docker Compose. Utilitzeu DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres i els valors corresponents de DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER i DB_POSTGRESDB_PASSWORD a tots els processos; substituïu els noms dels serveis de l'exemple pels del vostre desplegament. Proporcioneu la clau original N8N_ENCRYPTION_KEY a tots els processos. No publiqueu els ports de Redis ni PostgreSQL a l'amfitrió només per connectar contenidors que ja comparteixen una xarxa de Compose.

Inicieu un worker, no un segon editor. Afegiu un servei worker d'n8n que utilitzi la mateixa versió fixada de la imatge d'n8n i la mateixa configuració compartida que el procés principal, però executeu-lo amb l'ordre worker . Si heu anomenat aquest servei n8n-worker, inicieu-lo amb docker compose up -d n8n-worker. Després de verificar que un worker executa realment els fluxos de treball, podeu utilitzar docker compose up -d --scale n8n-worker=2 per iniciar un segon worker del mateix servei. Són modificacions d'una instal·lació existent configurada correctament amb Compose, no un fitxer d'instal·lació independent. Manteniu els volums persistents, el proxy HTTPS, els secrets i les còpies de seguretat existents.

Fragment de Docker Compose per afegir el mode de cua a una instal·lació existent. Integreu l'exemple següent al fitxer actual compose.yaml; aquest fragment no és un desplegament complet ni independent. Pressuposa que ja disposeu dels serveis privats i persistents postgres i n8n , d'una versió d'n8n fixada amb N8N_VERSION al vostre entorn i de la contrasenya protegida POSTGRES_PASSWORD i la clau de xifratge original N8N_ENCRYPTION_KEY. Adapteu els noms dels serveis, els volums, la base de dades i la versió d'n8n al projecte existent. Afegiu les opcions de Redis per al mode de cua i EXECUTIONS_MODE=queue també al servei principal existent, com s'ha indicat abans.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

En aquest fragment no es publica cap port de Redis ni dels workers a l'amfitrió. La persistència append-only de Redis aporta una capa addicional de recuperació, però no substitueix les còpies de seguretat fora del servidor. Manteniu sense canvis la configuració actual d'HTTPS i d'autenticació. Si els nodes Code necessiten executors de tasques externs, configureu-los per separat al desplegament dels workers; el mode de cua no substitueix aquests executors.

Voleu convertir una instància de SQLite existent? No canvieu simplement el valor de DB_TYPE ni inicieu n8n amb una base de dades PostgreSQL buida: això no migra els fluxos de treball ni les credencials antics. Abans del canvi, feu una còpia de seguretat de la base de dades d'origen i del directori persistent .n8n i la clau de xifratge original. Utilitzeu un procediment compatible d'exportació, importació o migració d'n8n i després comproveu els fluxos de treball i les credencials xifrades en un entorn de destinació separat. Conserveu els fitxers originals per poder revertir el canvi i consulteu la guia de còpies de seguretat i restauració enllaçada més avall per preparar la recuperació. No suprimiu mai database.sqlite com a drecera.

CONCURRÈNCIA DELS WORKERS

La capacitat dels workers depèn tant del nombre de processos com de les tasques simultànies que executa cadascun

Cada worker pot processar diverses tasques simultàniament. Actualment, la concurrència predeterminada d'un worker d'n8n és de 10 i la documentació recomana un valor de 5 o superior. Configurar molts workers amb una concurrència molt baixa pot provocar connexions innecessàries a la base de dades i esgotar-ne el conjunt de connexions disponibles.

Augmenteu la concurrència si

Un worker disposa de CPU i RAM lliures i els fluxos de treball passen bona part del temps esperant serveis externs, sense saturar el processador ni la memòria.

Afegiu workers si

Un sol procés worker esdevé el coll d'ampolla i PostgreSQL, Redis i la infraestructura poden suportar més execucions paral·leles.

Reduïu la concurrència si

Els fluxos individuals consumeixen molta memòria o CPU i les tasques paral·leles provoquen competència pels recursos, errors de manca de memòria (OOM) o temps d'execució inestables.

Superviseu PostgreSQL

Afegir workers i augmentar la concurrència incrementa l'activitat de la base de dades. Ampliar la capacitat d'execució sense ampliar també la de la base de dades pot desplaçar el coll d'ampolla en lloc d'eliminar-lo.

Comproveu quin límit de concurrència s'aplica realment. Podeu iniciar un worker amb n8n worker --concurrency=5, o amb l'ordre equivalent del worker al vostre servei de Docker Compose. Si N8N_CONCURRENCY_PRODUCTION_LIMIT s'ha establert explícitament en un valor diferent de -1, aquesta configuració té prioritat en mode de cua; en cas contrari, n8n utilitza el valor de --concurrency del worker o el valor predeterminat de 10. No multipliqueu simplement el nombre de workers per la concurrència nominal i considereu el resultat un rendiment garantit: la capacitat real depèn de la durada de les tasques, la CPU, la memòria, les API externes i les connexions a PostgreSQL.

WEBHOOKS

El mode de cua pot afegir latència en transferir les execucions

El procés principal o el procés de webhooks rep la petició HTTP, però és un worker qui executa el flux de treball. Aquesta transferència a través de Redis afegeix certa sobrecàrrega. Per als webhooks sensibles a la latència, mesureu el temps total de resposta en lloc de suposar que afegir workers accelera automàticament totes les peticions.

RecepcióEl procés principal o de webhooks accepta la petició.
CuaL'execució s'envia a la cua coordinada per Redis.
ExecucióUn worker disponible executa el flux de treball.
RespostaSi cal, el resultat torna al procés receptor a través del sistema de cua.

Encamineu el trànsit dels webhooks cap al procés adequat. Si utilitzeu processos dedicats n8n webhook darrere d'un proxy invers o d'un equilibrador de càrrega, encamineu les rutes de producció /webhook/* i /webhook-waiting/* als processos de webhooks; manteniu /webhook-test/*, l'editor i les peticions a l'API al procés principal. No inclogueu el procés principal al conjunt de balanceig dels webhooks de producció, llevat que accepteu expressament aquesta càrrega addicional. Un flux de treball amb el node Respond to Webhook pot mantenir el client esperant fins que el worker acabi i retorni la resposta. Per tant, el mode de cua no garanteix respostes HTTP immediates ni l'absència de temps d'espera esgotats. Proveu les crides de retorn externes i el comportament real de la resposta abans de redirigir el trànsit.

DADES BINÀRIES

No passeu per alt l'emmagatzematge compartit

Limitacions del sistema de fitxers

El mode de cua no admet l'emmagatzematge de dades binàries al sistema de fitxers com a model de persistència compartida entre workers distribuïts.

Emmagatzematge extern de dades binàries

Si els fluxos de treball han de conservar dades binàries entre workers distribuïts, utilitzeu un sistema d'emmagatzematge accessible a totes les instàncies que el necessitin, com ara un servei compatible d'emmagatzematge extern d'objectes.

Respostes de webhook voluminoses

Les respostes de webhook generades pels workers tornen cap al procés receptor. Si el cos de la resposta és gran, pot augmentar el consum de memòria de Redis i cal configurar expressament com s'emmagatzema la resposta.

Planifiqueu abans de distribuir els workers

Si una càrrega de treball depèn molt de fitxers locals, haureu d'adaptar-la a un sistema de persistència compartida abans de distribuir els workers entre diferents màquines.

Límit de mida de les respostes de webhook voluminoses. La documentació vigent d'n8n indica que N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX té un valor predeterminat de 64 MiB per a les respostes d'un worker que es transmeten a través de la cua. Redis pot mantenir diverses còpies d'una resposta en trànsit; per això, pressuposteu aproximadament 1.5 vegades la mida de la resposta en memòria de Redis per cada resposta voluminosa simultània. Sense desviar l'emmagatzematge del cos, una resposta massa gran falla: afegir workers no la fa més ràpida automàticament.

Límits segons la versió i la llicència. A partir d'n8n 2.34.0, els workers poden establir N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true per desviar els cossos de resposta de webhook massa grans a un emmagatzematge binari compartit i llegible, però abans cal actualitzar tots els processos principals i de webhooks a la versió 2.34.0 o posterior. El mode seleccionat amb N8N_DEFAULT_BINARY_DATA_MODE ha de desar realment les dades, que han de ser accessibles per a tots els processos implicats. L'emmagatzematge extern de dades binàries amb S3 o Azure requereix una llicència vàlida de les edicions autoallotjades Business o Enterprise ; no doneu per fet que Community Edition permet activar aquestes opcions. El mode binari database pot desviar una resposta massa gran sense emmagatzematge extern de pagament, però la instància principal carrega tot el cos emmagatzemat a la memòria i l'emmagatzematge de la base de dades també té un límit de mida de fitxer. Per a desviar específicament el cos de les respostes, n8n també documenta una opció compartida basada en filesystem quan totes les instàncies munten el mateix disc, però desaconsella expressament aquesta configuració. No confongueu aquesta via específica per desviar respostes amb l'admissió de dades binàries persistents al sistema de fitxers en un desplegament distribuït amb mode de cua. Comproveu l'edició, la versió i l'emmagatzematge abans d'activar aquesta funció.

SUPERVISIÓ

Com saber si el mode de cua aporta millores

Tasques pendents a la cua

Si la cua creix més de pressa del que els workers poden processar les tasques, pot faltar capacitat d'execució o existir un coll d'ampolla en un servei posterior.

CPU i RAM dels workers

Mesureu la saturació i els pics de memòria de cada worker. Si la cua creix mentre els workers estan inactius, la limitació pot ser en un altre component.

Latència de les execucions

Superviseu el temps transcorregut entre la creació d'una execució i el seu inici real, no només el temps que triga a executar-se el flux de treball.

Comprovacions d'estat

Els endpoints de salut dels workers poden indicar si el procés està actiu i si les connexions a PostgreSQL i Redis estan preparades.

Comproveu que el worker executa tasques, no només que el contenidor està actiu. En una instal·lació de Compose ben configurada, comproveu docker compose ps i docker compose logs --tail=100 n8n-worker (substituïu el nom del servei si és diferent). Executeu un flux de treball inofensiu publicat en producció mitjançant un activador programat o un webhook de prova. A continuació, contrasteu-ne l'execució a la vista Executions d'n8n amb el processament real que registren els workers. Que l'editor s'obri correctament, que Redis funcioni o que aparegui una execució pendent, per si sols, no demostren que un worker hagi executat la tasca.

Comproveu les dependències i que els serveis estiguin preparats. Amb els noms de servei predeterminats de l'exemple, docker compose exec -T redis redis-cli ping hauria de retornar PONG quan l'autenticació de Redis ho permeti, i docker compose exec -T postgres pg_isready -U n8n -d n8n comprova que PostgreSQL està preparat (adapteu les credencials i els noms de servei). Activeu QUEUE_HEALTH_CHECK_ACTIVE=true en un worker si necessiteu els seus endpoints privats /healthz i /healthz/readiness ; l'endpoint de comprovació de preparació verifica la connectivitat amb Redis i la base de dades. No exposeu públicament aquests endpoints dels workers només per poder supervisar-los.

Les execucions manuals són una prova diferent. Per defecte, OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, de manera que executar manualment un flux a l'editor pot fer que s'executi al procés principal, encara que el mode de cua estigui configurat correctament. Establiu aquesta opció com a true només si voleu enviar també les execucions manuals als workers i heu provat el canvi en un entorn de preproducció. Els workers del mode de cua no són el mateix que els executors de tasques externs d'n8n, que requereixen una configuració específica per executar els nodes Code.

LÍMITS DE L'ALTA DISPONIBILITAT

El mode de cua amplia la capacitat d'execució, però no proporciona automàticament alta disponibilitat al procés principal

Compartiu la clau de xifratge

Tots els workers han d'utilitzar la mateixa clau N8N_ENCRYPTION_KEY que la instància principal per poder desxifrar les credencials necessàries durant l'execució dels fluxos de treball.

Manteniu les versions sincronitzades

Els processos principals, de webhooks i workers han d'executar la mateixa versió d'n8n. Barrejar versions pot causar incompatibilitats durant les actualitzacions progressives.

Els processos dedicats a webhooks formen una capa d'escalat independent

Si el volum de webhooks entrants esdevé el coll d'ampolla, podeu situar processos de webhooks dedicats darrere d'un equilibrador de càrrega mentre els workers executen els fluxos. No afegiu aquesta capa si les dades sobre el volum de peticions no ho justifiquen.

Multi-main és una funció diferent

Executar diversos processos principals per obtenir alta disponibilitat no és el mateix que el mode de cua habitual. Actualment, n8n documenta multi-main com una funció de l'edició Enterprise autoallotjada que exigeix també un equilibrador de càrrega i una configuració específica de sessions.

PREGUNTES FREQÜENTS

Mode de cua d'n8n: preguntes freqüents

El mode de cua d'n8n necessita Redis?

Sí. Redis és l'intermediari de missatges que coordina les execucions pendents entre la instància principal i els workers.

Es pot utilitzar SQLite amb el mode de cua?

No, si es tracta de l'arquitectura de mode de cua distribuït. El procés principal i els workers necessiten accés a una base de dades compartida, i la documentació d'n8n estableix PostgreSQL com la base de dades d'aquesta configuració.

Quants workers he d'executar?

No hi ha cap quantitat universal. Partiu de les execucions simultànies i de la utilització real dels workers; afegiu capacitat mentre superviseu PostgreSQL, Redis, CPU, RAM i les tasques pendents a la cua.

Què és la concurrència d'un worker d'n8n?

És el nombre de tasques que un worker pot processar alhora. El valor predeterminat actual és 10 i n8n recomana una concurrència de 5 o superior per worker, en lloc d'utilitzar molts workers amb poca concurrència.

Convé activar el mode de cua en un VPS petit?

Només si la càrrega de treball ho justifica. Un desplegament petit que funciona bé amb una sola instància sol ser més fàcil d'administrar sense Redis ni workers separats.
