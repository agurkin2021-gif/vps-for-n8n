ESCALAT

n8n Mode de cua

El mode de cua separa l'execució del flux de treball del procés principal n8n. La instància principal rep activadors i crea execucions, Redis coordina la cua, els treballadors executen treballs i PostgreSQL emmagatzema el flux de treball compartit i les dades d'execució.

DECISIÓ RÀPIDA

Realment necessiteu el mode de cua?

Mantingueu-vos en mode normal quan

Una sola instància gestiona còmodament les execucions màximes i CPU, RAM i la latència d'execució es mantenen estables. El mode de cua afegeix components que encara no necessiteu.

Penseu en el mode de cua quan

Les execucions paral·leles sostingudes creen contenció, la latència d'execució augmenta sota càrrega o cal afegir capacitat d'execució executant diversos treballadors.

Escala verticalment primer quan

El coll d'ampolla és simplement insuficient CPU o RAM i una instància més gran encara pot satisfer la càrrega de treball de manera neta.

Mesurar abans de canviar l'arquitectura

Utilitzeu la concurrència màxima, CPU, RAM, la durada de l'execució, la profunditat de la cua i la pressió de la base de dades per justificar el moviment.

ARQUITECTURA

Com funciona el mode de cua n8n

1 · PrincipalRep temporitzadors, webhooks i sol·licituds de flux de treball i crea una execució en lloc de fer l'execució de producció pròpiament dita.
2 · RedisActua com a intermediari de missatges. Conté missatges d'execució pendents perquè el següent treballador disponible pugui reclamar una feina.
3 · TreballadorRep l'ID d'execució, carrega les dades del flux de treball de la base de dades compartida, executa el flux de treball i torna a escriure el resultat.
4 · PostgreSQLProporciona dades d'execució i flux de treball persistents compartits. El mode de cua distribuïda no és compatible amb SQLite.

REQUISITS BÀSICS

El que necessita cada desplegament en mode de cua

Redis

Tots els processos principals i de treball necessiten un accés fiable al servei Redis utilitzat per a la coordinació de la cua.

PostgreSQL

El principal i els treballadors han de compartir la base de dades. El mode de cua és una arquitectura distribuïda i no s'ha de dissenyar al voltant de SQLite.

Configuració que coincideix amb n8n

El principal i els treballadors han d'executar el mode de cua i compartir la configuració necessària per accedir a Redis, PostgreSQL i credencials encriptades.

Capacitat del treballador

Els treballadors necessiten suficients CPU i RAM per als fluxos de treball que executen. L'addició de processos no elimina el cost dels recursos de cada execució.

Activa el mode de cua en una pila autoallotjada existent. Primer confirmeu que el servei principal n8n i tots els treballadors poden accedir a la mateixa base de dades PostgreSQL i Redis a través d'una xarxa privada. Set EXECUTIONS_MODE=queue tant a principal com a treballadors, i subministrament QUEUE_BULL_REDIS_HOST=redis i QUEUE_BULL_REDIS_PORT=6379 quan redis és el nom real del servei de redacció. Ús DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres i emparellament DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER i DB_POSTGRESDB_PASSWORD en cada procés; substituïu els noms de servei d'exemple pel vostre. Proporcioneu l'existent exacte N8N_ENCRYPTION_KEY a tots ells. No publiqueu mai els ports d'amfitrió Redis o PostgreSQL només per connectar contenidors a la mateixa xarxa de Compose.

Llançar un executor, no un segon editor. Afegiu un servei de treball n8n utilitzant la mateixa versió d'imatge fixada n8n i la mateixa configuració compartida com a principal, però executeu-lo amb el worker comandament. Si heu posat el nom d'aquest servei n8n-worker, comença amb docker compose up -d n8n-worker. Després de confirmar l'execució real d'un treballador, podeu utilitzar docker compose up -d --scale n8n-worker=2 iniciar un segon treballador d'aquest servei. Són addicions a un existent correctament configurat Compose stack, no un fitxer d'instal·lació autònom; manteniu els vostres volums persistents existents, el proxy HTTPS, els secrets i les còpies de seguretat.

Mode de cua Composa un fragment per a una pila existent. Combina l'exemple següent amb el teu actual compose.yaml; ho és no un desplegament autònom complet. S'assumeix que ja tens un caràcter persistent i privat postgres i n8n serveis, un existent N8N_VERSION pin al vostre entorn i el vostre propi protegit POSTGRES_PASSWORD i original N8N_ENCRYPTION_KEY. Relaciona els seus noms, volums, base de dades i versió n8n amb el projecte existent. Afegiu la configuració del mode de cua Redis i EXECUTIONS_MODE=queue també al servei principal existent, tal com es descriu anteriorment.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

No es publica cap port d'amfitrió per a Redis o el treballador en aquest fragment. Redis La persistència només per afegir és una capa de recuperació addicional, no un substitut de les còpies de seguretat fora del servidor. Manteniu el HTTPS existent i la configuració d'autenticació sense canvis. Per als nodes de codi que requereixen executadors de tasques externs, configureu els processos de l'executor per al desplegament del vostre treballador per separat; El mode de cua en si no substitueix els corredors de tasques.

Vols convertir una instància de SQLite existent? No canvieu simplement DB_TYPE i començar amb una base de dades PostgreSQL buida: fer-ho no migraran els antics fluxos de treball i credencials. Abans de qualsevol tall, feu una còpia de seguretat de la base de dades d'origen, persistent .n8n directori i clau de xifratge original; utilitzeu un procediment d'exportació/importació o migració compatible amb n8n i, a continuació, verifiqueu els fluxos de treball i les credencials xifrades en un objectiu independent. Conserveu els fitxers originals per a la recuperació i utilitzeu la guia de còpia de seguretat i restauració enllaçada a continuació per a la preparació de la recuperació. No esborreu mai database.sqlite com a drecera.

CONCURRÈNCIA OBRERA

Els treballadors escalen tant per recompte com per llocs de treball per treballador

Cada treballador pot processar múltiples treballs simultàniament. La concurrència de treball predeterminada actual de n8n és 10 i la seva documentació recomana la concurrència de 5 o superior. La concurrència molt baixa combinada amb molts treballadors pot crear connexions de base de dades innecessàries i esgotar el conjunt de connexions de la base de dades.

Augmentar la concurrència quan

Un treballador té CPU i RAM de recanvi i els fluxos de treball estan esperant principalment a serveis externs en lloc de saturar el càlcul o la memòria.

Afegeix treballadors quan

Un procés de treball es converteix en un coll d'ampolla i la base de dades, Redis i la infraestructura tenen capacitat per a una execució més paral·lela.

Reduir la concurrència quan

Els fluxos de treball individuals són pesats en memòria o CPU i els treballs paral·lels provoquen conflictes, pressió OOM o temps d'execució inestables.

Mira PostgreSQL

Més treballadors i més concurrència augmenten l'activitat de la base de dades. Escalar la capacitat d'execució sense capacitat de base de dades pot moure el coll d'ampolla en lloc d'eliminar-lo.

Saber quin límit de concurrència s'aplica realment. Es pot començar a utilitzar un treballador n8n worker --concurrency=5, o l'ordre de treball equivalent al servei de redacció. Si N8N_CONCURRENCY_PRODUCTION_LIMIT s'estableix explícitament en un valor diferent de -1, aquesta configuració té prioritat en el mode de cua; en cas contrari n8n utilitza la del treballador --concurrency valor o el seu valor predeterminat de 10. No multipliqueu el recompte de treballadors per un valor predeterminat nominal i anomeneu-lo rendiment garantit: la capacitat real depèn de la durada del treball, CPU, la memòria, les API externes i les connexions PostgreSQL.

WEBHOOKS

El mode de cua pot afegir latència de transferència d'execució

El procés principal o webhook rep la sol·licitud HTTP, però un treballador realitza l'execució del flux de treball. Aquesta transferència a través de Redis afegeix una mica de sobrecàrrega. Per als webhooks sensibles a la latència, mesureu el temps de resposta d'extrem a extrem en lloc de suposar que més treballadors fan automàticament cada sol·licitud més ràpid.

RebreEl procés principal/webhook accepta la sol·licitud.
CuaL'execució es lliura al Redis.
ExecutarUn treballador disponible executa el flux de treball.
ResponEl resultat es retransmet a través del camí de la cua quan cal.

Encamina el trànsit del webhook al procés correcte. Amb dedicat n8n webhook processadors darrere d'un servidor intermediari invers o equilibrador de càrrega, encaminen les rutes de producció /webhook/* i /webhook-waiting/* als processadors de webhook; mantenir /webhook-test/*, l'editor i les sol·licituds API a main. No introduïu principal al grup d'equilibri de càrrega del webhook de producció tret que accepteu deliberadament aquesta càrrega de treball afegida. A Respon a Webhook El flux de treball pot mantenir el client esperant fins que el treballador acabi i retorni la seva resposta, de manera que el mode de cua no és una promesa de respostes instantànies HTTP o temps d'espera zero. Proveu la devolució de trucada externa real i el comportament de resposta abans de canviar el trànsit.

DADES BINÀRIES

No oblideu l'emmagatzematge compartit

Limitació del sistema de fitxers

El mode de cua no admet l'emmagatzematge de dades binàries del sistema de fitxers com a model de persistència compartida per als treballadors distribuïts.

Emmagatzematge binari extern

Quan els fluxos de treball han de conservar dades binàries entre els treballadors distribuïts, utilitzeu un disseny d'emmagatzematge al qual pugui accedir totes les instàncies necessàries, com ara l'emmagatzematge d'objectes extern compatible.

Grans respostes de webhook

Les respostes del webhook dels treballadors viatgen de nou cap al procés de recepció. Els cossos de resposta grans poden augmentar la pressió de memòria Redis i requereixen una configuració deliberada d'emmagatzematge de resposta.

Planificar abans de distribuir els treballadors

Una càrrega de treball que depèn en gran mesura dels fitxers locals s'ha de redissenyar per a una persistència compartida abans que els treballadors es distribueixin entre les màquines.

Gran límit de resposta del webhook. La documentació actual n8n dóna N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX un predeterminat de 64 MiB per a la resposta d'un treballador enviada a través de la cua. Redis pot contenir diverses còpies en vol, de manera que pressuposteu aproximadament 1.5 vegades la mida de la resposta a la memòria Redis per resposta gran simultània. Sense descàrrega, una resposta sobredimensionada falla en lloc de ser màgicament més ràpida afegint treballadors.

Límits de versió i llicència. Des de n8n 2.34.0, els treballadors poden utilitzar N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true per descarregar cossos de resposta de webhook de gran mida a l'emmagatzematge binari compartit llegible, però primer actualitzeu-lo cada processador principal i webhook a 2.34.0 o posterior. El seleccionat N8N_DEFAULT_BINARY_DATA_MODE han d'emmagatzemar dades i ser llegibles per tots els processos participants. L'emmagatzematge binari S3 extern i Azure requereixen un autoallotjat vàlid Empresa o empresa llicència; no assumeixis que Community Edition els pugui habilitar. El database El mode binari pot descarregar una resposta de gran mida sense emmagatzematge extern de pagament, però la instància principal carrega tot el cos emmagatzemat a la memòria i l'emmagatzematge de la base de dades té el seu propi límit de mida de fitxer. Per Descàrrega del cos de resposta específicament, n8n també descriu un compartit filesystem opció quan cada instància munta el mateix disc, però explícitament no recomana aquesta disposició. No confongueu aquesta ruta de descàrrega especial amb el suport de dades binàries persistents basades en el sistema de fitxers en un desplegament en mode de cua distribuït. Comproveu la vostra edició, versió i configuració d'emmagatzematge abans d'activar la descàrrega.

SEGUIMENT

Saber si la cua està ajudant

Profunditat de la cua

Una cua que creix més ràpidament del que els treballadors esgoten, indica una capacitat d'execució insuficient o un coll d'ampolla aigües avall.

Treballador CPU i RAM

Mesura la saturació i els pics de memòria per treballador. Els treballadors inactius amb una cua creixent assenyalen una altra limitació.

Latència d'execució

Feu un seguiment del retard entre la creació d'una execució i l'inici, no només el temps d'execució del flux de treball.

Controls de salut

Els punts finals de salut del treballador poden informar si un treballador està viu i si la seva base de dades i les connexions Redis estan preparades.

Verifiqueu l'execució d'un treballador, no només d'un contenidor verd. Amb una pila Compose correctament configurada, comproveu docker compose ps i docker compose logs --tail=100 n8n-worker (substituïu el nom del servei si és diferent). Executar un inofensiu producció publicada flux de treball mitjançant un activador programat o un webhook de prova i, a continuació, relacionar la seva execució a la vista d'execucions de n8n amb el processament real del treballador als registres del treballador. Un editor que s'obre correctament, un contenidor Redis en execució o una execució en cua només ho fa no demostrar que un treballador ha realitzat la feina.

Comproveu les dependències i la preparació. Amb exemples de noms de servei predeterminats, docker compose exec -T redis redis-cli ping hauria de rebre PONG quan l'autenticació Redis ho permeti, i docker compose exec -T postgres pg_isready -U n8n -d n8n comprova la preparació PostgreSQL (adaptar credencials i noms de servei). Activa QUEUE_HEALTH_CHECK_ACTIVE=true a un treballador quan necessiteu el seu privat /healthz i /healthz/readiness punts finals; el punt final de preparació comprova la connectivitat Redis/base de dades. No exposeu públicament aquests punts finals de treball només per supervisar-los.

Les execucions manuals són una prova diferent. Per defecte OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, de manera que l'execució manual d'un flux de treball a l'editor es pot executar a main fins i tot quan el mode de cua està configurat correctament. Estableix-ho a true només si teniu intenció d'enviar execucions manuals als treballadors i heu comprovat el canvi en un entorn de prova. Els treballadors en mode de cua també són diferents dels executadors de tasques externs n8n, que tenen requisits de configuració separats per a l'execució del node de codi.

LÍMIT D'ALTA DISPONIBILITAT

El mode de cua escala les execucions, però no fa que automàticament el procés principal estigui altament disponible

Comparteix la clau de xifratge

Cada treballador ha d'utilitzar el mateix N8N_ENCRYPTION_KEY com a instància principal perquè els treballadors puguin desxifrar les credencials requerides per les execucions del flux de treball.

Mantenir les versions alineades

Els processos principal, webhook i de treball haurien d'executar la mateixa versió n8n. Les versions mixtes poden crear un comportament incompatible durant els canvis continuats.

Els processadors Webhook són una capa d'escala independent

Quan el volum del webhook entrant es converteix en el coll d'ampolla, els processadors de webhook dedicats es poden asseure darrere d'un equilibrador de càrrega mentre els treballadors gestionen l'execució. No afegiu aquesta capa tret que el volum de sol·licitud mesurat ho justifiqui.

Multi-principal és una característica diferent

Executar diversos processos principals per a una alta disponibilitat no és el mateix que el mode de cua normal. n8n actualment documenta la multiprincipal com una funció d'empresa autoallotjada amb un equilibrador de càrrega addicional i requisits de sessió.

Arquitectura i configuració oficials en mode de cua

Preguntes freqüents

n8n mode cua: preguntes habituals

El mode de cua n8n requereix Redis?

Sí. Redis és l'agent de missatges que coordina les execucions pendents entre la instància principal i els treballadors.

El mode de cua pot utilitzar SQLite?

No per a l'arquitectura en mode de cua distribuïda. Principal i els treballadors necessiten accés a la base de dades compartida, i n8n documents PostgreSQL com a base de dades per a aquesta configuració.

Quants treballadors he de dirigir?

No hi ha un recompte universal. Comenceu des de la concurrència mesurada i la utilització dels treballadors i, a continuació, afegiu capacitat mentre controleu PostgreSQL, Redis, CPU, RAM i la profunditat de la cua.

Què és la concurrència del treballador n8n?

És el nombre de treballs que un treballador pot tramitar en paral·lel. El valor predeterminat actual és 10, i n8n recomana la concurrència dels treballadors de 5 o superior en lloc de crear molts treballadors de baixa concurrència.

He d'activar el mode de cua en un VPS petit?

Només quan la càrrega de treball ho justifiqui. Un desplegament petit que s'executa còmodament com una instància sol ser més senzill d'operar sense Redis i treballadors separats.
