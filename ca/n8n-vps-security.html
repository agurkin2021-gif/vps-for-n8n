SEGURETAT EN PRODUCCIÓ

Com protegir n8n en un VPS

Per protegir n8n en un VPS, manteniu els ports de n8n (5678), PostgreSQL (5432) i Redis opcional (6379) fora de l'accés públic a Internet. Utilitzeu un proxy invers amb HTTPS, claus SSH i autenticació multifactor (MFA), preserveu la clau de xifratge, autentiqueu els webhooks, limiteu les funcions de risc dels fluxos de treball i auditeu la instància desplegada. Protegiu l'accés a l'editor independentment de les rutes públiques dels webhooks. HTTPS, per si sol, no protegeix els serveis connectats.

LLISTA DE COMPROVACIÓ RÀPIDA

Mesures mínimes de seguretat abans d'exposar el servei a Internet

Comenceu per revisar els ports accessibles, HTTPS, l'accés administratiu verificat, l'MFA i la protecció de les credencials desades. Autentiqueu els webhooks entrants abans que puguin activar tasques sensibles. Després de modificar els controls d'accés, comproveu que els usuaris autoritzats poden entrar a l'editor i que les integracions externes continuen funcionant. Finalment, executeu l'auditoria de seguretat d'n8n.

Només HTTPS

Situeu n8n darrere d'un proxy invers amb TLS ben configurat i utilitzeu de manera coherent l'URL públic HTTPS tant per a l'editor com per als webhooks.

Mínim de ports oberts

Exposeu només els ports necessaris per al trànsit públic. Manteniu PostgreSQL, Redis i els ports interns de l'aplicació fora de l'accés públic a Internet.

Reforceu la seguretat d'SSH

Administreu el servidor amb claus SSH, restringiu qui pot iniciar sessió i manteniu actualitzat el sistema operatiu.

Protegiu les credencials

Manteniu estable i secreta la clau de xifratge d'n8n. Tracteu els fitxers de variables d'entorn, l'accés a la base de dades i les còpies de seguretat com a dades sensibles.

PERÍMETRE DE XARXA

Proxy invers, HTTPS i capçaleres de confiança

Terminació TLS

Utilitzeu un proxy invers com Nginx, Caddy o Traefik per gestionar HTTPS. Redirigiu el trànsit HTTP sense xifrar i eviteu exposar directament el port d'n8n quan el proxy sigui el punt d'entrada públic previst.

Configuració del proxy

Si n8n s'executa darrere d'un proxy invers, configureu correctament el nombre de salts de proxy i reenvieu les capçaleres necessàries perquè n8n pugui reconstruir la sol·licitud original del client.

Galetes segures

Serviu l'editor mitjançant HTTPS perquè les galetes d'autenticació es mantinguin protegides. No debiliteu la seguretat de les galetes per compensar una configuració TLS defectuosa.

URL dels webhooks

Configureu l'URL públic dels webhooks amb un nom d'amfitrió HTTPS accessible des de fora, perquè els endpoints generats no apuntin a un contenidor intern ni a una adreça HTTP.

Manteniu privat l'editor sense interrompre els webhooks. Quan sigui viable, restringiu l'accés d'administració mitjançant una VPN, una política d'IP de confiança o un proxy autenticat. Pot ser necessari mantenir accessibles els receptors de webhooks públics i les rutes de retorn OAuth. Abans d'aplicar una regla al proxy, proveu tant l'inici de sessió d'un editor autoritzat com una crida de retorn externa real. Accepteu les capçaleres que indiquen l'adreça del client només de proxies de confiança, no de qualsevol petició arbitrària.

Autentiqueu les peticions als webhooks: al node Webhook, trieu l'autenticació Basic, Header o JWT en lloc de None quan l'emissor ho admeti. Feu servir l'opció IP(s) Allowlist quan sigui adequada i verifiqueu les signatures del proveïdor quan la integració admeti peticions signades. Un URL difícil d'endevinar no constitueix una autenticació suficient. Apliqueu límits de peticions al proxy quan convingui i comproveu que no bloquegen ràfegues legítimes. Consulteu les opcions oficials d'autenticació dels webhooks.

REFORÇ DE LA SEGURETAT DEL VPS

Reduïu la superfície d'atac del servidor

Tallafoc

Denegueu per defecte el trànsit entrant no sol·licitat i permeteu només els serveis als quals cal accedir. Normalment, els ports de la base de dades i de Redis han de quedar en xarxes privades o locals.

SSH

Preferiu les claus SSH a les contrasenyes, desactiveu els mètodes d'accés innecessaris i limiteu l'accés administratiu. Controleu estrictament els permisos equivalents als de root.

Actualitzacions del sistema operatiu

Apliqueu els pedaços de seguretat al servidor Linux i a l'entorn d'execució dels contenidors. Endurir l'aplicació no compensa tenir un sistema operatiu obsolet o exposat.

Exposició dels contenidors

Publiqueu només els ports que necessiten accés des de l'amfitrió. Els serveis interns s'han de comunicar per xarxes privades de Docker, no per interfícies públiques.

Comproveu-ho abans de modificar el tallafoc o la configuració SSH: reviseu els ports en escolta amb sudo ss -lntp, els ports publicats per Docker amb docker compose ps des del directori del projecte, i les regles del tallafoc de l'amfitrió amb sudo ufw status verbose si utilitzeu UFW. Abans de desactivar l'accés per contrasenya, comproveu el port SSH real i que podeu iniciar sessió amb clau des d'una altra sessió. Els ports publicats per Docker poden eludir les regles d'UFW; la pantalla d'estat del tallafoc, tota sola, no demostra que el port 5678 sigui privat. Verifiqueu l'accessibilitat externa real. Consulteu l'advertiment de Docker sobre UFW.

Comproveu que les actualitzacions automàtiques de seguretat d'Ubuntu funcionen, en lloc de donar-ho per fet: reviseu apt-config dump APT::Periodic::Unattended-Upgrade i el fitxer de registre /var/log/unattended-upgrades/unattended-upgrades.log. Si les actualitzacions automàtiques de seguretat estan desactivades, sudo dpkg-reconfigure unattended-upgrades obre un diàleg de configuració oficial. Abans d'activar-les en un VPS en funcionament, reviseu com es gestionen els reinicis del servidor i dels serveis. Les actualitzacions APT d'Ubuntu no actualitzen automàticament la imatge Docker d'n8n ni tots els repositoris de programari de tercers. Consulteu la documentació d'Ubuntu sobre actualitzacions automàtiques.

Supervisió opcional dels intents d'accés SSH per força bruta: Fail2Ban pot detectar intents repetits d'inici de sessió SSH fallits. Si l'heu instal·lat i configurat per a SSH, comproveu el jail amb sudo fail2ban-client status sshd i confirmeu que consulta el registre o el diari d'autenticació SSH real i que coincideix amb el port configurat. Complementa les claus SSH i les restriccions de xarxa, però no les substitueix. No copieu cap port SSH ni cap regla de bloqueig predeterminats sense comprovar abans que mantindreu l'accés. Consulteu les recomanacions d'Ubuntu per reforçar SSH.

BASE DE DADES I REDIS

Manteniu privats els serveis interns

En una configuració habitual de Docker Compose, PostgreSQL i Redis per al mode de cua han de ser accessibles als contenidors que els necessiten mitjançant xarxes privades, no mitjançant ports publicats per l'amfitrió. Comproveu-ho amb docker compose ps per verificar que els ports 5432 i 6379 no estan exposats públicament; reviseu també per separat el tallafoc del VPS o del proveïdor. Les restriccions de xarxa no substitueixen les credencials de base de dades amb els mínims privilegis necessaris.

PostgreSQLVinculeu PostgreSQL a una interfície privada o a una xarxa de contenidors, llevat que necessiteu expressament accés remot i l'hàgiu protegit de manera independent.
RedisRedis utilitzat pel mode de cua és un servei d'infraestructura, no un endpoint públic. Restringiu-ne l'accés de xarxa als components d'n8n que el necessiten.
CredencialsUtilitzeu credencials específiques per a la base de dades, amb només els permisos que necessita l'aplicació, i manteniu-les fora dels repositoris de codi.
TransportSi el trànsit de la base de dades travessa xarxes que no són de confiança, utilitzeu un transport xifrat adequat i no confieu exclusivament en el xifratge de les credencials dins de l'aplicació.

SECRETS D'N8N

Protegiu la clau de xifratge i l'accés a les credencials

Clau de xifratge

n8n xifra les credencials desades amb la seva clau de xifratge. Conserveu la mateixa clau després dels reinicis i per a tots els workers, i protegiu-la independentment del contingut ordinari de l'aplicació.

Secrets de les variables d'entorn

No incorporeu contrasenyes, tokens ni la clau de xifratge a un repositori públic. Restringiu l'accés als fitxers de variables d'entorn i als secrets de desplegament.

Accés dels usuaris

Doneu accés a l'editor només a usuaris de confiança. Els fluxos de treball poden connectar-se a sistemes sensibles, tractar secrets o executar nodes amb permisos elevats.

Abast de les credencials

Sempre que sigui possible, utilitzeu comptes de servei i tokens d'API amb permisos limitats. Un flux de treball compromès no hauria d'obtenir automàticament accés ampli a sistemes que no hi estan relacionats.

Configuració d'n8n que cal revisar: N8N_BLOCK_ENV_ACCESS_IN_NODE=true impedeix que els nodes Code i les expressions accedeixin als valors de les variables d'entorn; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true sol·licita permisos exclusius del propietari al fitxer de configuració. Manteniu N8N_ENCRYPTION_KEY estable i amb una còpia de seguretat protegida: n8n pot generar una clau aleatòria en el primer inici, però perdre-la pot fer inutilitzables les credencials xifrades existents. No substituïu una clau de producció sense planificació; utilitzeu un procediment oficialment admès per rotar-la. Bloquejar l'accés a les variables d'entorn pot interrompre integracions existents; feu proves abans d'aplicar el canvi en producció. Consulteu la documentació de variables de seguretat d'n8n.

RISCOS DELS FLUXOS DE TREBALL

Els nodes poden ampliar la superfície d'atac

Autoallotjar n8n dona als fluxos de treball un grau de control considerable. L'execució de codi, l'accés a l'intèrpret d'ordres, les peticions HTTP arbitràries i els nodes de la comunitat de tercers poden augmentar els riscos. Desactiveu les funcions que no necessiteu i reviseu els fluxos de treball importats de fonts no fiables abans d'executar-los.

Utilitzeu els controls compatibles indicats a la documentació: configureu NODES_EXCLUDE amb una matriu JSON dels nodes que vulgueu desactivar, com ara n8n-nodes-base.executeCommand i n8n-nodes-base.readWriteFile, si no els feu servir. Alguns nodes de risc elevat ja estan bloquejats per defecte en versions més recents; reviseu la llista real abans de modificar-la. Consulteu la documentació oficial d'exclusió de nodes.

A partir de la versió d'n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true activa comprovacions de peticions HTTP sortints dirigides a adreces internes, de loopback o de metadades. Això pot impedir el funcionament de fluxos legítims que utilitzen API internes; si cal, afegiu a la llista de destinacions permeses únicament les que controleu. Manteniu la segmentació de xarxa com a defensa principal. Per aïllar els nodes Code, reviseu els executors de tasques externs. Protecció contra SSRF · Aïllament dels executors de tasques.

Nodes de la comunitatInstal·leu només paquets que considereu fiables; s'executen dins del vostre entorn d'n8n.
Nodes de riscExcloeu els nodes que el vostre desplegament no necessiti si les seves funcions excedeixen els permisos previstos per als fluxos de treball.
SSRFUtilitzeu els controls de xarxa i la protecció contra SSRF d'n8n si els fluxos de treball no han de poder accedir a endpoints interns o de metadades.
Importació de fluxos de treballReviseu els fluxos de treball importats, les credencials, les expressions i els passos executables abans d'activar-los.

AUDITORIA I ACTUALITZACIONS

La seguretat requereix un manteniment continu

Executeu l'auditoria de seguretat d'n8n

L'ordre oficial de la CLI és n8n audit. Si el servei de Docker Compose s'anomena n8n, executeu docker compose exec -T n8n n8n audit al directori del desplegament. Reviseu les cinc categories: credencials no utilitzades, patrons de consultes SQL de risc, accés al sistema de fitxers, nodes de risc o de la comunitat i riscos de la instància, inclosos els webhooks sense protecció i les versions obsoletes. Corregiu els problemes pertinents i repetiu l'auditoria. No és una prova d'intrusió. Consulteu la guia oficial d'auditoria.

Actualitzeu amb criteri

Manteniu n8n prou actualitzat per rebre correccions de seguretat. Llegiu les notes de les versions i proveu les actualitzacions importants, en lloc de deixar una instància exposada a Internet permanentment desactualitzada.

Superviseu l'autenticació

Vigileu els patrons d'accés inesperats, els canvis als fluxos de treball i els errors. Restringiu encara més l'accés a l'editor si el vostre model operatiu no requereix que sigui públic.

Prepareu un pla de reversió i recuperació

Feu còpies de seguretat recuperables abans de les actualitzacions importants. Els components que cal incloure a les còpies i el procediment de restauració s'expliquen a la guia de recuperació específica.

Minimitzeu l'historial d'execucions amb dades sensibles: les execucions completades correctament poden conservar dades de clients i tokens. Quan sigui adequat, establiu EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, manteniu EXECUTIONS_DATA_PRUNE=truei configureu EXECUTIONS_DATA_MAX_AGE en hores, per exemple 168 (set dies). Són exemples de configuració, no normes legals de retenció. Conservar menys historial també deixa menys dades per diagnosticar problemes o investigar incidències; les execucions en curs, en espera o anotades poden no depurar-se de la mateixa manera. Consulteu la documentació oficial sobre retenció d'execucions.

Si sospiteu que la instància s'ha vist compromesa: restringiu l'accés maliciós sense destruir les proves, examineu els registres del proxy, del servidor i d'n8n, així com els fluxos de treball modificats. Revoqueu o renoveu les credencials dels serveis externs que puguin haver quedat exposades, corregiu la causa de la vulnerabilitat i restaureu només a partir de còpies de seguretat recuperables que hàgiu provat, quan sigui necessari. Reviseu els URL dels webhooks, els comptes de l'editor i els serveis connectats afectats. No doneu per fet que HTTPS, les instantànies o la compra d'un VPS incloguin serveis de resposta a incidents.

CONTROLS DELS COMPTES I DE LA PLATAFORMA

Protegiu tant l'editor com el VPS

Exigiu una protecció més robusta per iniciar sessió

Activeu l'autenticació de dos factors als comptes de l'editor i imposeu MFA mitjançant les polítiques de seguretat d'n8n quan la vostra edició permeti aplicar polítiques centralitzades.

Limiteu els usuaris que poden editar fluxos de treball

L'accés a l'editor implica permisos elevats: els fluxos de treball poden llegir credencials, fer peticions a sistemes interns i executar nodes amb moltes capacitats. Doneu accés només a qui el necessiti i elimineu els comptes que ja no l'hagin de tenir.

Desactiveu les funcions que no utilitzeu

Reduïu la superfície d'atac de l'aplicació desactivant l'API pública si no és necessària i bloquejant nodes o funcions de risc elevat que el vostre desplegament no necessiti.

Utilitzeu els controls contra SSRF i de protecció dels secrets amb criteri

Per als fluxos de treball que puguin fer peticions HTTP arbitràries, valoreu la protecció contra SSRF d'n8n i manteniu els secrets fora del codi dels fluxos, dels repositoris públics i dels fitxers d'entorn accessibles a massa usuaris.

Restringiu els endpoints d'administració que no utilitzeu: N8N_PUBLIC_API_DISABLED=true desactiva l'API REST pública d'n8n, mentre que N8N_PUBLIC_API_SWAGGERUI_DISABLED=true desactiva per separat l'entorn de proves interactiu de l'API. Feu-ho només si les vostres integracions no necessiten aquestes funcions. Desactivar l'API REST no autentica els URL dels webhooks dels fluxos de treball. Utilitzeu MFA per als comptes de l'editor i les polítiques centralitzades només si la vostra edició d'n8n les admet.

Preguntes freqüents

Seguretat d'n8n en un VPS: preguntes freqüents

Cal exposar directament el port d'n8n?

Si un proxy invers és el punt d'entrada públic, exposeu el proxy i manteniu el port de l'aplicació al darrere, sense publicar innecessàriament altres serveis.

Han d'estar exposats públicament PostgreSQL o Redis?

Normalment, no. Només han de ser accessibles als sistemes que els necessiten. Exposar-los públicament amplia la superfície d'atac sense aportar cap benefici al funcionament habitual d'n8n.

Per què és important la clau de xifratge d'n8n?

Protegeix les credencials que desa n8n i ha de ser la mateixa a tot el desplegament. Si la perdeu, és possible que no pugueu utilitzar les credencials xifrades a partir de les dades restaurades.

Són segurs els nodes de la comunitat?

Amplien n8n amb codi de tercers i, per tant, cal tractar-los com a dependències de programari amb riscos propis de la cadena de subministrament i dels permisos que poden obtenir. Instal·leu només els que siguin fiables i necessaris.

HTTPS garanteix la seguretat d'una instància d'n8n autoallotjada?

No. HTTPS protegeix les comunicacions en trànsit. La seguretat en producció també exigeix reforçar el servidor, controlar els accessos, mantenir privats els serveis interns, protegir els secrets, limitar les funcions de risc dels fluxos, supervisar el sistema i aplicar actualitzacions.

Pot ser privat l'editor d'n8n mentre funcionen els webhooks de producció?

Sí. Un proxy invers o una VPN de confiança poden restringir l'accés a l'editor i a l'administració independentment de les rutes públiques dels webhooks de producció i dels retorns OAuth. Després de canviar qualsevol regla d'accés, proveu l'inici de sessió autoritzat i la recepció de webhooks externs per evitar bloquejar integracions per error.

Com puc autenticar els webhooks entrants d'n8n?

Configureu l'autenticació Basic, Header o JWT al node Webhook quan l'emissor ho admeti. També podeu utilitzar l'opció IP(s) Allowlist i comprovar les signatures del proveïdor, si estan disponibles. No confieu només en una ruta d'aspecte secret i valideu les peticions abans que activin accions sensibles amb API.
