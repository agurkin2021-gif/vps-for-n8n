SEGURETAT DE LA PRODUCCIÓ

Com protegir n8n en un VPS

Per protegir n8n en un VPS, mantingueu n8n (5678), PostgreSQL (5432) i Redis opcional (6379) fora d'Internet pública; utilitzeu un proxy invers HTTPS, claus SSH i MFA, preserveu la vostra clau de xifratge, autentiqueu els webhooks, limiteu les capacitats de flux de treball de risc i auditeu la instància desplegada. Protegiu l'editor per separat de les rutes públiques de webhook. El HTTPS per si sol no assegura els serveis connectats.

Autentiqueu cada webhook entrant abans que pugui desencadenar treballs sensibles. Després de canviar els controls d'accés, verifiqueu que els editors previstos i les integracions externes encara funcionin i, a continuació, executeu l'auditoria de seguretat n8n.

Només HTTPS

Col·loqueu n8n darrere d'un proxy invers TLS configurat correctament i utilitzeu l'URL públic HTTPS de manera coherent per a l'editor i els webhooks.

Ports oberts mínims

Exposa només els ports necessaris per al trànsit públic. Manteniu PostgreSQL, Redis i els ports d'aplicacions interns fora d'Internet pública.

Endurir SSH

Utilitzeu l'administració basada en claus, restringiu qui pot iniciar sessió i mantingueu el sistema operatiu pegat.

Protegiu les credencials

Mantingueu la clau de xifratge n8n estable i secreta. Tracteu els fitxers d'entorn, l'accés a la base de dades i les còpies de seguretat com a actius sensibles.

BORDE DE XARXA

Proxy invers, HTTPS i capçaleres de confiança

Terminació TLS

Utilitzeu un proxy invers com Nginx, Caddy o Traefik per finalitzar HTTPS. Redirigeix ​​HTTP i evita exposar directament el port d'aplicació n8n quan el proxy és el punt d'entrada previst.

Configuració del servidor intermediari

Quan n8n s'executa darrere d'un proxy invers, configureu el recompte de salts del servidor intermediari correctament i passeu les capçaleres reenviades que el n8n necessita per reconstruir la sol·licitud del client original.

Cookies segures

Doneu servei a l'editor a HTTPS perquè les galetes d'autenticació puguin romandre segures. No eviteu una configuració de TLS trencada debilitant la seguretat de les galetes.

URL del webhook

Estableix l'URL del webhook públic al nom d'amfitrió HTTPS accessible des de l'exterior, de manera que els punts finals del webhook generats no apuntin a un contenidor intern o a una adreça HTTP.

Mantingueu l'editor privat sense trencar els webhooks. Restringeix l'accés de gestió mitjançant una VPN, una política d'IP de confiança o un servidor intermediari autenticat quan sigui pràctic. És possible que els receptors de webhook públics i les rutes de devolució de trucada OAuth hagin de romandre accessibles; Proveu tant un inici de sessió d'editor de confiança com una devolució de trucada externa real abans d'aplicar una regla de proxy. Reenvia capçaleres d'adreça de client només des de servidors intermediaris de confiança, no capçaleres de sol·licitud arbitràries.

Autentiqueu les trucades del webhook: al node Webhook, trieu Autenticació bàsica, capçalera o JWT en lloc de Cap quan el remitent ho admet. Utilitzeu-ne Llista d'IP(s) permeses opció si escau i verifiqueu les signatures del proveïdor quan la integració admeti sol·licituds signades. Un URL difícil d'endevinar no és una autenticació suficient. Apliqueu límits de velocitat al proxy quan sigui necessari i confirmeu que les ràfegues vàlides no estan bloquejades. Opcions oficials d'autenticació de Webhook.

VPS ENDURIMENT

Redueix la superfície d'atac del servidor

Tallafoc

Per defecte, denegueu el trànsit d'entrada no sol·licitat i permeteu només els serveis als quals s'ha de poder accedir. Els ports de base de dades i Redis normalment pertanyen a xarxes privades/locals.

SSH

Preferiu les claus SSH sobre les contrasenyes, desactiveu les rutes d'inici de sessió innecessàries i limiteu l'accés administratiu. L'accés equivalent a l'arrel s'ha de controlar estrictament.

Actualitzacions del sistema operatiu

Apliqueu el pedaç a l'amfitrió Linux i al temps d'execució del contenidor. L'enduriment de l'aplicació no pot compensar un sistema operatiu exposat o obsolet.

Exposició del contenidor

Publiqueu només els ports que necessiten accés a l'amfitrió. Els serveis interns haurien de comunicar-se en xarxes privades Docker en comptes de fer-ho mitjançant interfícies públiques.

Inspeccioneu abans de canviar la configuració del tallafoc o SSH: comproveu els ports d'escolta amb sudo ss -lntp, Docker publicant amb docker compose ps des del directori del projecte i la política de tallafocs amb sudo ufw status verbose si s'utilitza UFW. Verifiqueu el vostre port SSH real i l'inici de sessió amb clau correcta en una sessió independent abans de desactivar l'accés amb contrasenya. Els ports Docker publicats poden saltar les regles UFW; una pàgina d'estat del tallafoc per si sola no demostra que el port 5678 sigui privat. Comproveu l'accessibilitat externa real. Advertència Docker/UFW.

Comproveu les actualitzacions de seguretat automàtiques Ubuntu en lloc de suposar que funcionen: inspeccionar apt-config dump APT::Periodic::Unattended-Upgrade i el registre /var/log/unattended-upgrades/unattended-upgrades.log. Si les actualitzacions de seguretat desateses estan desactivades, sudo dpkg-reconfigure unattended-upgrades proporciona un diàleg de configuració compatible. Reviseu el comportament de reinici i reinici del servei abans d'activar-lo en un VPS que funcioni. Ubuntu Les actualitzacions d'APT sí no actualitzar automàticament la imatge n8n Docker o tots els dipòsits de programari de tercers. Ubuntu documentació d'actualització automàtica.

Supervisió de força bruta SSH opcional: Fail2Ban pot detectar inicis de sessió fallits de SSH repetits. Si està instal·lat i configurat per a SSH, verifiqueu la presó amb sudo fail2ban-client status sshd i confirmeu que llegeix el vostre registre o diari d'autenticació SSH real i coincideix amb el port configurat. Això complementa les claus SSH i les restriccions de xarxa; no els substitueix. No copieu un port fix SSH o una regla de prohibició sense comprovar primer l'accés existent. Ubuntu SSH guia d'enduriment.

BASE DE DADES I REDIS

Mantingueu els serveis de backend privats

En una configuració típica de Docker Compose, PostgreSQL i mode de cua Redis haurien de ser accessibles pels contenidors rellevants mitjançant xarxes privades, no ports publicats per l'amfitrió. Verifica amb docker compose ps que 5432 i 6379 no es publiquen públicament; reviseu per separat l'exposició del tallafoc al núvol VPS/núvol. Les polítiques de xarxa no substitueixen les credencials de base de dades amb privilegis mínims.

PostgreSQLEnllaceu-lo a una interfície privada o a una xarxa de contenidors, tret que l'accés remot sigui explícit i segur de manera independent.
RedisEl mode de cua Redis és una infraestructura, no un punt final públic. Restringeix l'accés a la xarxa als components n8n que ho requereixen.
CredencialsUtilitzeu credencials de base de dades dedicades només amb els permisos que l'aplicació necessita i protegiu-les fora del control de fonts.
TransportQuan el trànsit de la base de dades travessa xarxes no fiables, utilitzeu el transport xifrat adequat en lloc de confiar en el xifratge de credencials a nivell d'aplicació.

N8N SECRETS

Protegiu la clau de xifratge i el límit de la credencial

Clau de xifratge

n8n xifra les credencials emmagatzemades mitjançant la seva clau de xifratge. Preserveu la mateixa clau durant els reinicis i els treballadors i protegiu-la per separat del contingut normal de l'aplicació.

Secrets del medi ambient

No envieu contrasenyes, testimonis o la clau de xifratge a un repositori públic. Restringeix l'accés als fitxers de l'entorn i als secrets de desplegament.

Accés d'usuari

Doneu accés a l'editor només als usuaris de confiança. Els fluxos de treball es poden connectar a sistemes sensibles i poden processar secrets o executar nodes potents.

Àmbit de la credencial

Utilitzeu comptes de servei d'abast restringit i testimonis API sempre que sigui possible. Un flux de treball compromès no hauria d'heretar automàticament un ampli accés a sistemes no relacionats.

n8n configuració per revisar: N8N_BLOCK_ENV_ACCESS_IN_NODE=true impedeix l'accés de codi i expressió als valors de l'entorn; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true sol·licita permisos només del propietari al fitxer de configuració. Mantenir N8N_ENCRYPTION_KEY persistent i amb una còpia de seguretat segura: n8n pot crear una clau aleatòria al primer inici, però perdre-la pot inutilitzar les credencials xifrades existents. No substituïu una clau de xifratge de producció casualment; utilitzar un procediment de rotació amb suport oficial. Bloquejar l'accés a l'entorn pot trencar les integracions existents, així que proveu abans dels canvis de producció. n8n definicions de variables de seguretat.

RISC DEL FLUX DE TREBALL

Els nodes poden ampliar el límit de seguretat

L'allotjament automàtic ofereix als fluxos de treball una potència substancial. L'execució de codi, l'accés a l'intèrpret d'ordres, les sol·licituds arbitràries HTTP i els nodes de la comunitat de tercers poden augmentar el risc. Desactiveu la funcionalitat que no necessiteu i reviseu les importacions de flux de treball no fiables abans d'executar-les.

Utilitzeu els controls compatibles exactes: configurar NODES_EXCLUDE amb una matriu JSON de nodes per desactivar, com ara n8n-nodes-base.executeCommand i n8n-nodes-base.readWriteFile, si no s'utilitza. Alguns nodes d'alt risc ja estan bloquejats per defecte en les versions més noves; reviseu la llista real abans de canviar-la. Exclusions de nodes oficials.

Des de n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true habilita comprovacions de sol·licituds HTTP sortints a intervals d'adreces internes, de loopback i de metadades. Els fluxos de treball interns legítims API poden deixar de funcionar; si cal, només permet llistar les destinacions que controleu. Mantingueu la segmentació de la xarxa com a defensa principal. Per a l'aïllament del node de codi, reviseu els corredors de tasques externs. Protecció SSRF · Aïllament del corredor de tasques.

Nodes de comunitatInstal·leu només paquets de confiança; s'executen dins del vostre entorn n8n.
Nodes de riscExclou els nodes que la vostra implementació no necessita quan les seves capacitats superin el límit del flux de treball previst.
SSRFUtilitzeu la protecció SSRF i els controls de xarxa de n8n on els fluxos de treball no haurien de poder arribar als punts finals interns o de metadades.
Importacions de flux de treballReviseu els fluxos de treball, les credencials, les expressions i els passos executables importats abans de l'activació.

AUDITORIA I ACTUALITZACIONS

La seguretat és un procés operatiu

Executeu l'auditoria de seguretat n8n

L'ordre oficial CLI és n8n audit. Si el vostre servei de redacció Docker s'anomena n8n, córrer docker compose exec -T n8n n8n audit en aquest directori de desplegament. Reviseu les cinc categories: credencials no utilitzades, patrons de consulta SQL arriscats, accés al sistema de fitxers, nodes de risc/comunitat i riscos d'instància, inclosos els webhooks no protegits i les versions obsoletes. Corregiu les troballes rellevants i torneu-la a executar. Aquesta no és una prova de penetració. Guia oficial d'auditoria.

Actualitzar deliberadament

Manteniu el n8n prou actual per rebre solucions de seguretat. Reviseu les notes de la versió i proveu les actualitzacions importants en lloc de deixar una instància amb connexió a Internet permanentment obsoleta.

Supervisar l'autenticació

Observa patrons d'accés inesperats, canvis de flux de treball i errors. Limiteu encara més la interfície d'usuari de l'editor quan el vostre model operatiu no requereixi una àmplia accessibilitat pública.

Prepareu la restauració i la recuperació

Feu còpies de seguretat recuperables abans d'actualitzacions importants. L'abast detallat de la còpia de seguretat i la restauració pertanyen a la guia de recuperació independent.

Minimitzar l'historial d'execucions sensibles: les execucions reeixides poden persistir dades i testimonis dels clients. Quan correspongui establir EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, mantenir EXECUTIONS_DATA_PRUNE=true, i tria un EXECUTIONS_DATA_MAX_AGE en hores, com ara 168 (set dies). Aquests són exemples configurables, no normes legals de retenció. Menys historial significa menys depuració i dades forenses; Les execucions en execució, en espera o anotades no es poden podar de la mateixa manera. Retenció de l'execució oficial.

Sospita de compromís: restringir l'accés maliciós sense destruir proves, inspeccionar el servidor intermediari, l'amfitrió i l'activitat n8n i els fluxos de treball canviats, revocar o girar les credencials aigües amunt possiblement exposades, pegar la causa i restaurar només a partir de còpies de seguretat recuperables provades quan sigui necessari. Reviseu els URL de webhook afectats, els comptes d'editor i els serveis connectats; no assumis que HTTPS, instantànies o una compra VPS proporcionen serveis de resposta a incidents.

CONTROLS DE COMPTE I PLATAFORMA

Protegiu l'editor així com el VPS

Requereix una protecció d'inici de sessió més forta

Activeu l'autenticació de dos factors per als comptes d'editor i feu complir les polítiques de seguretat de MFA a n8n quan la vostra edició admeti l'aplicació de polítiques centralitzada.

Limiteu qui pot editar fluxos de treball

L'accés a l'editor és un accés privilegiat: els fluxos de treball poden llegir credencials, trucar a sistemes interns i executar nodes potents. Manteniu l'accés dels usuaris restringit i suprimiu els comptes que ja no el necessiten.

Desactiveu les capacitats que no feu servir

Reduïu la superfície d'atac de l'aplicació desactivant el API públic quan no sigui necessari i bloquejant nodes o funcions d'alt risc que el vostre model operatiu no necessita.

Utilitzeu SSRF i controls secrets deliberadament

Per als fluxos de treball que poden fer sol·licituds arbitràries HTTP, avalueu la protecció SSRF de n8n i manteniu els secrets fora del codi de flux de treball, repositoris públics i fitxers d'entorn de lectura àmplia.

Restringeix els punts finals de gestió no utilitzats: N8N_PUBLIC_API_DISABLED=true desactiva el n8n REST públic API, i N8N_PUBLIC_API_SWAGGERUI_DISABLED=true desactiva el seu parc infantil API per separat. Feu-ho només quan les vostres integracions no requereixin aquestes funcions. La desactivació de REST API no autentica els URL del webhook del flux de treball. Utilitzeu MFA per als usuaris de l'editor i les polítiques centralitzades només quan la vostra edició n8n les admeti.

Preguntes freqüents

n8n VPS seguretat: preguntes habituals

S'ha d'exposar directament el port n8n?

Quan un proxy invers és el punt d'entrada públic, exposa el servidor intermediari i mantén el port de l'aplicació darrere d'ell en lloc de publicar serveis innecessaris de manera àmplia.

PostgreSQL o Redis hauria de ser públic?

Normalment no. Només haurien de ser accessibles pels sistemes que els requereixin. L'exposició pública augmenta la superfície d'atac sense ajudar al funcionament normal de n8n.

Per què és important la clau de xifratge n8n?

Protegeix les credencials emmagatzemades per n8n i ha de ser coherent durant tot el desplegament. Perdre-la pot evitar que les dades recuperades proporcionin credencials xifrades utilitzables.

Els nodes de la comunitat són segurs?

Amplien n8n amb codi de tercers, de manera que s'han de tractar com a dependències de programari amb la seva pròpia cadena de subministrament i riscos de privilegis. Instal·leu només el que confieu i necessiteu.

HTTPS fa que una instància n8n autoallotjada sigui segura?

No. HTTPS protegeix el transport. La seguretat de la producció també requereix l'enduriment de l'amfitrió, el control d'accés, els serveis de backend privats, la protecció secreta, les capacitats de flux de treball segurs, la supervisió i les actualitzacions.

L'editor n8n pot ser privat mentre encara s'executen els webhooks de producció?

Sí. Un proxy invers o VPN de confiança pot restringir l'accés de l'editor/administrador per separat del webhook de producció pública i els camins de retorn de trucada OAuth. Proveu l'inici de sessió de confiança i el lliurament de webhook extern després de cada canvi de regla d'accés per evitar bloquejar accidentalment les vostres integracions.

Com puc autenticar els webhooks n8n entrants?

Configureu l'autenticació bàsica, de capçalera o JWT al node Webhook quan el remitent ho admeti. També podeu utilitzar la llista d'IP(s) permesos i comprovar les signatures del proveïdor quan estiguin disponibles. No confieu només en un camí d'aspecte secret i valideu les sol·licituds abans que desencadenin accions sensibles API.
