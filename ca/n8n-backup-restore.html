Còpies de seguretat i recuperació

n8n Còpia de seguretat i restauració

Per fer una còpia de seguretat i restaurar n8n autoallotjada, protegiu la vostra base de dades SQLite o un abocament coherent de PostgreSQL, la carpeta persistent .n8n i la clau de xifratge original, la configuració de desplegament i totes les dependències de fitxers binaris o muntats externs. Manteniu una còpia xifrada fora del VPS i proveu la recuperació en una instància independent. Utilitzeu el flux de treball CLI i les exportacions de credencials per a la recuperació selectiva; Les exportacions JSON per si soles no són una còpia de seguretat completa del servidor.

LLISTA DE VERIFICACIÓ RÀPIDA

Què hauria de protegir una còpia de seguretat n8n

Base de dades

Feu una còpia de seguretat de la base de dades PostgreSQL o del fitxer de base de dades SQLite utilitzat per la instància. La base de dades conté l'estat bàsic n8n com ara fluxos de treball, credencials i dades d'execució.

Clau de xifratge

Preserveu la clau de xifratge exacta n8n per separat i de manera segura. Les credencials xifrades restaurades depenen de la mateixa clau.

Fitxers persistents

Inclou el directori de dades persistent n8n i qualsevol fitxer muntat, emmagatzematge de dades binàries o actius de flux de treball en què es basa el teu desplegament.

Configuració del desplegament

Conserveu els fitxers de redacció/configuració i la configuració no secreta necessària per reconstruir la pila. Protegiu els secrets amb controls d'accés adequats.

DOS NIVELLS DE CÒPIA DE Seguretat

Exportació lògica vs recuperació completa de desastres

Exportació de credencials i flux de treball

Les exportacions n8n CLI són útils per a la migració, les còpies de flux de treball versionades i la restauració selectiva. Les credencials es poden exportar en forma xifrada i importar-les més tard amb la clau de xifratge corresponent. Per recuperar només un flux de treball, utilitzeu el menú de tres punts de l'editor de flux de treball per baixar el seu JSON i, a continuació, importar des del fitxer a un nou flux de treball de revisió o una instància aïllada. Comproveu les credencials, els ID de flux de treball i els paràmetres del node abans de substituir un flux de treball en directe: la restauració del flux de treball JSON no restaura tot el servidor.

Exportació d'entitats

El CLI pot exportar entitats de base de dades per moure dades entre els tipus de bases de dades compatibles. Les taules d'historial d'execució són opcionals perquè poden ser molt grans.

Recuperació completa de la instància

Per a un escenari de servidor mort, protegiu la base de dades real, la clau de xifratge, les dades persistents i les dependències de desplegament. No suposeu que l'exportació de flux de treball JSON reconstrueix tota la instància.

Instantània del proveïdor

Una instantània VPS és útil com a capa de recuperació addicional, però no hauria de ser l'única còpia i no hauria de substituir una còpia de seguretat d'aplicació/base de dades verificada de manera independent.

BASE DE DADES

Feu una còpia de seguretat de la base de dades de manera coherent

PostgreSQL

Utilitzeu un mètode de còpia de seguretat coherent PostgreSQL i deseu la còpia de seguretat resultant lluny del VPS. Una còpia de la base de dades al mateix disc fallit no és recuperació de desastres.

SQLite

Si el desplegament utilitza SQLite, protegiu el fitxer de base de dades del directori de dades persistent n8n. Eviteu copiar una base de dades en un estat no segur mentre s'està modificant activament.

Historial d'execució

Decidiu si les dades històriques d'execució formen part del vostre objectiu de recuperació. Pot fer que les còpies de seguretat siguin substancialment més grans, de manera que els requisits de retenció i compliment haurien de guiar l'elecció.

Versió de la base de dades

Enregistreu el motor de la base de dades i la versió utilitzada pel desplegament d'origen perquè un entorn de recuperació es pugui preparar de manera compatible.

PostgreSQL sobre un Docker Composa VPS. Si s'anomena el servei PostgreSQL postgres i la seva base de dades/usuari són tots dos n8n, l'ordre següent crea un abocament coherent de format personalitzat PostgreSQL a l'amfitrió. Comproveu el vostre fitxer Compose real abans d'executar-lo i ajusteu les credencials de la base de dades i els noms dels serveis. pg_dump pot produir una instantània lògicament coherent mentre s'està executant PostgreSQL; ho fa no fes una còpia de seguretat del separat .n8n carpeta d'usuari o dades binàries externes.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

La comprovació de la llista d'arxiu detecta problemes de format evidents, però no demostra que les dades es puguin restaurar. Emmagatzema una còpia xifrada fora del servidor i assaja una restauració. Utilitzeu la documentació oficial PostgreSQL pg_dump per a opcions específiques de la base de dades.

SQLite a Docker. Per al desplegament predeterminat SQLite, database.sqlite i la configuració de clau de xifratge generada viu dins del persistent .n8n carpeta (normalment es munta a /home/node/.n8n). No tracteu mai una còpia en directe de SQLite com a coherent. Atureu n8n i altres escriptors de bases de dades abans de copiar la carpeta, o utilitzeu el mecanisme de còpia de seguretat en línia admès per SQLite quan la interrupció sigui impossible:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Aquestes són ordres il·lustratives per al servei i la ruta que es mostren, no un disseny de volum universal. La carpeta copiada es troba inicialment al mateix VPS; transferir-lo i protegir-lo fora del servidor. Quan hi hagi treballadors de cua o altres escriptors, atureu-los també i seguiu el seu disseny de desplegament real. La guia actual de còpia de seguretat completa de n8n documenta el requisit de coherència SQLite.

Restauració de la carpeta SQLite predeterminada a un objectiu net: primer atureu el servei n8n i tots els escriptors de bases de dades. Un cop existeixi un contenidor de servei n8n compatible i el seu volum de destinació, copieu la còpia de seguretat .n8n continguts enrere al mateix directori persistent. Això sobreescriu els fitxers de destinació, així que no els executeu en una instància amb dades que necessiteu conservar:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker pot copiar als contenidors aturats, però la propietat de destinació pot ser diferent de l'original; Assegureu-vos que la configuració restaurada i el fitxer de base de dades siguin llegibles i escrivibles pel procés n8n abans d'iniciar-lo. Si la vostra configuració de Compose real utilitza un camí o un muntatge d'enllaç diferent, adapteu la còpia en conseqüència. Docker Redactar una referència de còpia. La restauració d'una carpeta n8n per si sola no és suficient per als desplegaments que utilitzen una base de dades PostgreSQL independent.

SECRET CRÍTIC

La clau de xifratge forma part de la recuperació

n8n xifra les credencials emmagatzemades amb una clau de xifratge d'instància. Una base de dades o una exportació de credencials xifrades sense la clau coincident pot deixar que els fluxos de treball restaurats no puguin utilitzar les seves credencials desades.

Si configureu N8N_ENCRYPTION_KEY, restaureu aquest secret exacte. En cas contrari, la clau generada s'emmagatzema al fitxer persistent .n8n/config: protegiu aquesta configuració quan feu una còpia de seguretat o reconstruïu. Emmagatzemeu les claus de recuperació de manera segura fora del VPS. En mode de cua, tots els processos principals i de treball han d'utilitzar la mateixa clau.

FesConserveu una còpia protegida de la clau exacta utilitzada per la producció.
FesComproveu que l'entorn de recuperació faci servir aquesta clau abans de provar les credencials.
No ho facisConfieu en una clau generada recentment després de reconstruir el servidor.
No ho facisEnvieu la clau a un repositori públic o emmagatzemeu-la al costat d'una còpia de seguretat sense protecció.

FITXERS I DADES BINARIES

És possible que la còpia de seguretat de la base de dades no cobreixi totes les dependències del flux de treball

Dades persistents .n8n

Localitzeu i preserveu la carpeta d'usuari .n8n real, no només la imatge del contenidor. En un desplegament típic de Docker es munta a /home/node/.n8n; fora de Docker el valor predeterminat és ~/.n8n. Si es configura N8N_USER_FOLDER, n8n crea .n8n dins del directori principal especificat. Incloeu la seva clau de configuració i qualsevol dada local SQLite, binària o d'execució del sistema de fitxers que utilitzi la vostra instal·lació.

Fitxers de flux de treball muntats

Si els fluxos de treball llegeixen o escriuen directoris muntats a l'amfitrió, feu una còpia de seguretat d'aquests directoris per separat. Restaurar n8n sense ells pot deixar trencats els fluxos de treball vàlids.

Dades binàries

Identifiqueu el mode d'emmagatzematge i restaureu totes les dependències externes. Les dades binàries o d'execució basades en el sistema de fitxers poden viure en .n8n o en un directori personalitzat; S3/Azure Blob o un altre emmagatzematge extern configurat necessita la seva pròpia configuració d'accés i còpia recuperable. Un bolcat de base de dades per si sol no pot substituir aquests fitxers.

Nodes de comunitat

Enregistreu paquets i versions de la comunitat i feu una còpia de seguretat de qualsevol directori de nodes personalitzat addicional configurat mitjançant N8N_CUSTOM_EXTENSIONS. Aquests directoris poden estar fora de .n8n; només una restauració de la base de dades i de la carpeta d'usuari pot deixar inutilitzables els fluxos de treball de nodes personalitzats.

ESTRATÈGIA FORA DEL SERVIDOR

Una còpia de seguretat al mateix VPS és només una còpia local

Còpia localÚtil per a una recuperació ràpida, però vulnerable a la pèrdua del servidor, fallades del disc i errors destructius.
Còpia fora del servidorMantenir almenys una còpia de seguretat a l'emmagatzematge independent de la producció VPS.
Còpies versionadesConserveu diversos punts de recuperació perquè la corrupció o un canvi dolent no sobreescriu l'única còpia de seguretat utilitzable.
Control d'accésLes còpies de seguretat poden contenir credencials, lògica de flux de treball i dades empresarials sensibles. Xifreu-los i restringiu-los adequadament.
SeguimentAlerta quan fallen les còpies de seguretat programades o deixen de produir nous punts de recuperació.

Fes que el calendari sigui mesurable. Enregistreu la marca de temps de cada còpia de seguretat correcta, la finalització de la transferència, la mida del fitxer, la versió de la base de dades d'origen, la ubicació de recuperació de la clau de xifratge i la darrera prova de restauració correcta. Alerta de fitxers que falten, que han fallat o que s'han buit de manera inesperada. Xifreu els arxius de còpia de seguretat abans d'enviar-los fora del VPS i restringiu l'accés als secrets de recuperació. Diversos punts de recuperació datats protegeixen contra el descobriment de corrupció només després que la còpia més recent sobreescrigui l'última sana.

Per exemple, si podeu tolerar com a màxim sis hores de canvis perduts, una programació de còpies de seguretat de sis hores satisfactòria és un punt de partida, no una garantia: les feines fallides i la rèplica fora del servidor retardada poden augmentar la pèrdua real. Estableix la retenció i restaura la cadència als teus propis requisits de RPO/RTO i de dades, en lloc d'assumir una política universal de 7 dia o 30 dia.

RESTAURAR L'ORDRE

Recuperació en una seqüència controlada

1 · PrepararProporcioneu un servidor, una base de dades i un entorn de contenidor/temps d'execució compatibles.
2 · Restaurar secretsConfigureu la clau de xifratge n8n original i els secrets de desplegament necessaris de manera segura.
3 · Restaurar base de dadesRecupereu PostgreSQL o SQLite i verifiqueu que n8n es pot connectar a les dades esperades.
4 · Restaurar fitxersRecupereu directoris persistents, dades binàries i actius de flux de treball muntats.
5 · Inici n8nObre l'aplicació amb el nom d'amfitrió, la base de dades i la configuració de l'entorn esperats.
6 · ValidarConfirmeu la càrrega d'usuaris, fluxos de treball i credencials i, a continuació, executeu fluxos de treball representatius i rutes de webhook.

PostgreSQL Exemple de recuperació de desastres: en a objectiu de restauració net i separat que ja té el rol de base de dades correcte i un buit n8n base de dades, començar només PostgreSQL. Espereu fins que estigui saludable abans d'importar: docker compose up -d només pot tornar mentre PostgreSQL encara s'està inicialitzant, per tant, un següent pg_restore pot fallar. L'exemple utilitza --wait en una instal·lació Compose moderna i comprova de forma independent pg_isready. Configureu un control de salut PostgreSQL adequat per a una espera fiable o confirmeu explícitament la preparació abans de continuar. No apunteu aquesta ordre a una base de dades de producció poblada ni comenceu n8n abans de la base de dades i la seva concordança .n8n es restauren les claus/dades.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

La destinació ha de tenir una versió compatible PostgreSQL, privilegis de rol, extensions i configuració original n8n. Restaurar .n8n al seu volum persistent correcte o muntatge d'enllaç mitjançant el vostre mecanisme de còpia de seguretat, preservant la propietat i els permisos. Restaura els fitxers binaris externs, les extensions personalitzades, la configuració de la redacció i els secrets i, a continuació, inicieu n8n amb una versió compatible i comproveu-ne els registres. La restauració de la base de dades sola no recupera la clau: un desplegament PostgreSQL manté la clau dins .n8n/config tret que ho hàgiu configurat explícitament N8N_ENCRYPTION_KEY. referència pg_restore · n8n seqüència de restauració d'instància completa.

PROVA DE RESTAURACIÓ

No es prova una còpia de seguretat fins que la restauració tingui èxit

Prova en un entorn net

Un exercici real hauria de demostrar que la còpia de seguretat pot reconstruir una instància sense dependre dels fitxers no declarats deixats al servidor de producció.

Comproveu les credencials

No n'hi ha prou amb obrir un flux de treball. Confirmeu que les credencials xifrades restaurades realment desxifra i s'autentiquen correctament.

Executeu fluxos de treball representatius

Proveu els fluxos de treball que depenen de webhooks, API externes, fitxers muntats i nodes de comunitat en lloc de validar només una automatització trivial.

Mesura el temps de recuperació

Anoteu quant de temps triga la restauració i quins passos manuals queden. Això converteix una còpia de seguretat suposada en un procediment de recuperació operatiu.

Exercici de restauració verificat: SQLite i PostgreSQL

Entorn de prova: n8n 2.42.5 en contenidors aïllats Docker en un corredor d'accions GitHub d'un sol ús, utilitzant un flux de treball sintètic de dos nodes. Aquestes comprovacions van continuar 8 Octubre 2026, no al servidor n8n d'un client o de producció.

SQLite: PASSATS'ha importat un flux de treball de prova, l'ha exportat, ha aturat tots els escriptors, s'ha arxivat el persistent amb suport SQLite .n8n carpeta i la seva clau de xifratge generada, restaurada en un volum net, va iniciar n8n, després es va tornar a exportar i va executar el flux de treball recuperat.
PostgreSQL: PASSATS'ha importat el mateix flux de treball de prova, ha creat i inspeccionat un format personalitzat pg_dump, el va restaurar utilitzant pg_restore en una nova base de dades buida PostgreSQL, restaurada la separada .n8n carpeta, després va tornar a exportar i executar el flux de treball recuperat.
El que estableix el PASSLes rutes de còpia de seguretat provades van preservar aquest flux de treball, els seus dos nodes i les seves connexions i van permetre l'execució després de la recuperació. Aquestes són proves de fum funcionals reproduïbles, no punts de referència de càrrega de treball.
El que no es va provarDesxifrat i autenticació de credencials reals, webhooks de producció, treballadors en mode de cua i Redis, emmagatzematge binari S3/Azure, nodes personalitzats, accés d'usuari/projecte o recuperació d'una instància de producció en directe. Executeu un exercici independent per a cada dependència que utilitzeu realment.

Com reproduir-se: utilitzeu una instal·lació d'un sol ús n8n, creeu un flux de treball inofensiu de dos nodes, realitzeu la base de dades aplicable més la còpia de seguretat de la carpeta persistent, restaurau-lo a un volum o una base de dades nets i, a continuació, verifiqueu els nodes, les connexions i l'execució real del flux de treball restaurat. Al sistema de producció també comproveu les credencials xifrades, els webhooks i els fitxers externs abans de declarar la recuperació de desastres provada.

Llista de verificació d'acceptació de l'exercici de restauració: utilitzar un domini/entorn aïllat; comproveu que els usuaris i els fluxos de treball estan presents, una credencial xifrada existent s'autentica sense tornar a entrar, un webhook de producció invoca el flux de treball restaurat previst, els fitxers muntats i els fitxers adjunts binaris es poden llegir i les integracions amb els nodes de la comunitat necessaris es carreguen. Confirmeu l'edat de la còpia de seguretat, el temps d'inactivitat mesurat i l'accessibilitat fora del servidor. Si alguna comprovació essencial falla, marqueu aquest punt de recuperació sense verificar en lloc d'informar de la còpia de seguretat com a completa.

CLI LÍMITS DE CÒPIES DE Seguretat

Conegueu exactament quin flux de treball i les exportacions de credencials no es restauren

Les exportacions de CLI no són una còpia de seguretat de la instància completa

Les exportacions de còpies de seguretat de credencials i de flux de treball no inclouen usuaris i rols, historial d'execucions i registres, variables o paràmetres de la instància, com ara la clau de xifratge.

La restauració de la nova instància necessita un propietari

En una instància neta, completeu la configuració del propietari abans d'importar les credencials. Les restauracions de projectes o multiusuari també poden necessitar l'assignació correcta de l'usuari o del projecte.

Els identificadors importats poden sobreescriure els elements existents

Les exportacions de flux de treball i credencials conserven els seus identificadors originals. La importació a una instància que ja conté els mateixos identificadors pot substituir els elements existents.

Publiqueu els fluxos de treball importats de manera deliberada

Les importacions de CLI normalment deixen inactius els fluxos de treball. A n8n 2.x, comproveu l'estat publicat de cada flux de treball importat i publiqueu només els fluxos de treball que voleu executar; el servidor autoallotjat CLI també admet n8n publish:workflow --id=YOUR_WORKFLOW_ID. Quan s'està executant n8n, els canvis d'estat de publicació/despublicació del servidor CLI només tenen efecte després de reiniciar n8n. Reinicieu abans de verificar els activadors programats i els webhooks de producció o canviar el trànsit.

Exemple d'exportació massiva per a Docker Compose: si el vostre servei n8n s'anomena n8n, podeu executar les còpies de seguretat oficials CLI a continuació. El camí de sortida es troba deliberadament dins del seu persistent muntat .n8n directori, perquè els directoris arbitraris dins d'un contenidor poden desaparèixer quan es recrea. Confirmeu que l'usuari del contenidor n8n pot escriure al directori. Mantenir el flux de treball i la credencial JSON a directoris separats—n8n documenta un problema d'importació quan tots dos tipus comparteixen un directori.

n8n 2.x esborrany versus còpia de seguretat publicada: un normal --backup l'exportació del flux de treball captura els esborranys actuals; aquestes poden diferir de les versions publicades en producció. Per conservar la versió publicada real d'un flux de treball concret, exporteu-lo per separat mitjançant docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, després d'assegurar-vos que la carpeta de sortida existeix i es pot escriure. El CLI també pot exportar una versió històrica utilitzant --version=VERSION_ID. Mantingueu aquestes captures fora del servidor juntament amb la còpia de seguretat completa; no assumis que l'esborrany JSON registra l'estat publicat en directe.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

El copiat ~/n8n-recovery/cli El directori encara es troba al VPS fins que el moveu a una ubicació de còpia de seguretat independent i segura. L'exportació de credencials està xifrada per defecte i necessita la clau de xifratge corresponent a la importació. Eviteu utilitzar --decrypted llevat d'una migració estrictament controlada: escriu secrets en text pla. No comprometeu mai exportacions que continguin lògica de flux de treball sensible o credencials a un repositori públic GitHub. Algunes plantilles de còpia de seguretat de credencials GitHub de tercers exporten deliberadament secrets desxifrats; un repositori privat és una restricció d'accés, no un xifratge. Inspeccioneu la configuració real d'exportació i els permisos d'emmagatzematge de cada plantilla, encripteu els secrets abans de la transferència fora del servidor i gireu les credencials exposades a través d'una càrrega de text sense intencions.

Exemple d'importació massiva: en un objectiu net, acabeu la configuració del propietari, proporcioneu la clau de xifratge original i assegureu-vos que els fitxers de còpia de seguretat desats estiguin disponibles en aquesta recuperació VPS. El següent crea la carpeta de destinació i copia el fitxer workflows/ i credentials/ subcarpetes de l'amfitrió al contenidor n8n; adapteu camins si la vostra disposició de volum de Docker és diferent:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Comproveu la propietat i l'accés del fitxer per a l'usuari del contenidor n8n. No importeu sobre una instància de producció emplenada sense una reversió verificada: els ID de credencials i de flux de treball poden sobreescriure les entrades existents. A continuació, executeu:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Els identificadors importats poden substituir els fluxos de treball o les credencials existents; utilitzeu una instància de prova aïllada per a execucions en sec i comproveu les credencials i els estats d'activació/publicació després. A n8n 2.x, la restauració de l'esborrany de JSON no demostra per si mateix que s'ha publicat un flux de treball i pot executar activadors programats. Seguretat d'importació: en una instància n8n no multiprincipal, els activadors de cron actius anteriorment poden continuar executant-se després de la importació CLI fins que es reinicia la instància. Atureu o aïlleu els activadors de producció i reinicieu n8n abans d'habilitar els treballs restaurats; comproveu que no hi ha cap execució duplicada. CLI exportacions fan no conté usuaris originals, registres d'execució, variables d'instància o la clau de xifratge. --backup conjunts --all --pretty --separate, no "instància completa". Fonts: guia de còpia de seguretat/restauració oficial actual n8n i referència de comandaments n8n CLI.

Restauració massiva des de GitHub o plantilles de Google Drive: aquesta és una alternativa només per al flux de treball JSON, no per a la base de dades d'instàncies, usuaris, valors de credencials xifrats o clau de xifratge. Abans d'executar una plantilla basada en API, verifiqueu el seu n8n API i els permisos d'emmagatzematge, la versió de còpia de seguretat seleccionada i la instància de destinació, si actualitza els ID coincidents i recrea els fluxos de treball suprimits i què fa amb la publicació del flux de treball. No totes les plantilles recreen un identificador que falta a l'objectiu; Proveu aquest escenari de manera aïllada abans de confiar en la restauració automàtica.

Preguntes freqüents

n8n còpia de seguretat i restauració: preguntes habituals

L'exportació de fluxos de treball és suficient per fer una còpia de seguretat de n8n?

No. Les exportacions de flux de treball són còpies lògiques útils, però la recuperació completa també pot requerir credencials, la clau de xifratge coincident, l'estat de la base de dades, fitxers persistents i emmagatzematge de dades binàries.

Necessito la clau de xifratge n8n si tinc la base de dades?

Sí, si necessiteu que les credencials xifrades emmagatzemades a aquesta base de dades es puguin utilitzar. Preserveu la clau original de manera segura.

He de fer una còpia de seguretat de PostgreSQL o exportar els fluxos de treball i les credencials?

Per a la recuperació de desastres, protegiu la base de dades i la clau de xifratge. Les exportacions lògiques són valuoses com a capa addicional de migració i recuperació selectiva més que com a substitut de cada part de la instància.

Pot ser la meva única còpia de seguretat una instantània VPS?

Es tracta millor com una capa de recuperació. Mantingueu una còpia de seguretat fora del servidor independent perquè un proveïdor, un compte, un servidor o un error d'instantània no eliminen tots els punts de recuperació alhora.

Com sé que funciona la meva còpia de seguretat?

Restaureu-lo en un entorn de prova net, verifiqueu les credencials, desxifrau-lo i executeu fluxos de treball representatius. Una tasca de còpia de seguretat exitosa per si sola no demostra la capacitat de recuperació.

Les còpies de seguretat del flux de treball GitHub o de Google Drive inclouen secrets de credencials desats?

Les còpies de seguretat de JSON només de flux de treball no inclouen els valors secrets gestionats pel magatzem de credencials de n8n ni la clau de xifratge de la instància. Tanmateix, el JSON exportat pot exposar noms de credencials i identificadors i secrets escrits directament als paràmetres del node, com ara les capçaleres d'autenticació. Inspeccioneu i protegiu l'exportació JSON abans de pujar-la o compartir-la. Per a una recuperació completa, feu una còpia de seguretat de la base de dades i la clau original, o utilitzeu les exportacions de credencials xifrades admeses CLI amb una restauració provada. Una plantilla només de flux de treball GitHub o de Google Drive no és una recuperació completa en cas de desastre.

OBJECTIUS DE RECUPERACIÓ

Definir RPO i RTO abans d'un incident

RPO és la pèrdua màxima tolerable dels canvis recents. Mesureu-lo des del punt de recuperació utilitzable i emmagatzemat de manera independent; un treball programat de sis hores no estableix un RPO de sis hores si les exportacions o les transferències fallaven. RTO és la màxima interrupció tolerable. Mesureu-lo en un exercici de restauració net, que inclou la recuperació de secrets, la restauració de fitxers externs, la comprovació de les credencials i la publicació de fluxos de treball recuperats, no només iniciar un contenidor.

CLAU DE RECUPERACIÓ

Trobeu la clau de xifratge original abans de reconstruir-la

Si s'estableix la producció N8N_ENCRYPTION_KEY, preservar aquest exacte secret ambiental. Si no ho va fer, conserveu la clau generada en el .n8n/config original persistent. Comproveu quina font utilitza realment la instància recuperada abans d'importar credencials xifrades; una nova clau generada no pot desxifrar les credencials de la base de dades antiga.
