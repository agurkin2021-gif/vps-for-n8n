CÒPIES DE SEGURETAT I RECUPERACIÓ

Còpia de seguretat i restauració de n8n

Per fer una còpia de seguretat i restaurar una instal·lació de n8n autoallotjada, protegiu la base de dades SQLite o un bolcat coherent de PostgreSQL, la carpeta persistent .n8n i la clau de xifratge original, la configuració del desplegament i qualsevol dependència de dades binàries externes o fitxers muntats. Deseu una còpia xifrada fora del VPS i proveu-ne la recuperació en una instància separada. Utilitzeu les exportacions de fluxos de treball i credencials mitjançant la CLI per a recuperacions selectives; les exportacions JSON, per si soles, no constitueixen una còpia de seguretat completa del servidor.

LLISTA DE COMPROVACIÓ RÀPIDA

Què ha de protegir una còpia de seguretat de n8n

Base de dades

Feu una còpia de seguretat de la base de dades PostgreSQL o del fitxer de SQLite que utilitza la instància. La base de dades conté informació essencial de n8n, com ara els fluxos de treball, les credencials i les dades d'execució.

Clau de xifratge

Deseu una còpia segura i independent de la mateixa clau de xifratge de n8n. Les credencials xifrades restaurades només funcionaran amb la clau corresponent.

Fitxers persistents

Incloeu-hi el directori de dades persistents de n8n, els fitxers muntats, l'emmagatzematge de dades binàries i qualsevol altre recurs del qual depenguin els fluxos de treball.

Configuració del desplegament

Conserveu els fitxers de Docker Compose i de configuració, així com els paràmetres no secrets necessaris per reconstruir els serveis. Protegiu les dades secretes amb controls d'accés adequats.

DOS NIVELLS DE CÒPIA DE SEGURETAT

Exportació lògica o recuperació completa després d'un desastre

Exportació de fluxos de treball i credencials

Les exportacions mitjançant la CLI de n8n són útils per migrar, conservar versions dels fluxos de treball i restaurar elements concrets. Les credencials es poden exportar xifrades i importar posteriorment amb la mateixa clau de xifratge. Per recuperar un únic flux de treball, obriu el menú de tres punts de l'editor, descarregueu-ne el fitxer JSON i utilitzeu l'opció d'importació des de fitxer en un flux de treball nou per revisar-lo o en una instància aïllada. Comproveu les credencials, els identificadors dels fluxos de treball i els paràmetres dels nodes abans de substituir un flux de treball actiu: restaurar-ne el JSON no equival a restaurar tot el servidor.

Exportació d'entitats

La CLI pot exportar entitats de la base de dades per traslladar dades entre tipus de base de dades compatibles. Les taules de l'historial d'execucions són opcionals perquè poden ser molt voluminoses.

Recuperació completa de la instància

Si el servidor deixa de funcionar definitivament, necessitareu la base de dades real, la clau de xifratge, les dades persistents i les dependències del desplegament. No suposeu que una exportació JSON dels fluxos de treball pugui reconstruir tota la instància.

Instantània del proveïdor

Una instantània del VPS és útil com a mesura addicional de recuperació, però no ha de ser l'única còpia ni substituir una còpia de seguretat de l'aplicació i la base de dades verificada de manera independent.

BASE DE DADES

Feu còpies coherents de la base de dades

PostgreSQL

Utilitzeu un mètode coherent de còpia de seguretat de PostgreSQL i deseu el resultat fora del VPS. Una còpia de la base de dades al mateix disc que ha fallat no permet recuperar-se d'un desastre.

SQLite

Si utilitzeu SQLite, protegiu el fitxer de la base de dades situat al directori persistent de n8n. Eviteu copiar-lo mentre es modifica activament, perquè la còpia podria quedar en un estat incoherent.

Historial d'execució

Decidiu si heu de recuperar també l'historial d'execucions. Aquestes dades poden augmentar molt la mida de les còpies, de manera que la retenció ha de respondre a les vostres necessitats i als requisits de compliment normatiu.

Versió de la base de dades

Anoteu el motor i la versió de la base de dades del desplegament original per poder preparar un entorn de recuperació compatible.

PostgreSQL en un VPS amb Docker Compose. Si el servei de PostgreSQL s'anomena postgres i tant la base de dades com l'usuari s'anomenen n8n, l'ordre següent crea al servidor amfitrió un bolcat coherent de PostgreSQL en format personalitzat. Reviseu el fitxer real de Compose abans d'executar-la i adapteu-hi les credencials i els noms dels serveis. pg_dump pot crear una instantània lògicament coherent mentre PostgreSQL continua funcionant, però no fa una còpia de seguretat de la carpeta d'usuari .n8n ni de les dades binàries externes.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Comprovar la llista d'objectes de l'arxiu permet detectar problemes evidents de format, però no demostra que les dades es puguin restaurar. Deseu-ne una còpia xifrada fora del servidor i feu un assaig de restauració. Consulteu la documentació oficial de pg_dump de PostgreSQL per a les opcions específiques de la base de dades.

SQLite amb Docker. En una instal·lació predeterminada amb SQLite, database.sqlite i el fitxer de configuració que conté la clau de xifratge generada es troben a la carpeta persistent .n8n (que normalment es munta a /home/node/.n8n). No doneu mai per coherent una còpia simple de SQLite feta mentre la base de dades està en ús. Atureu n8n i els altres processos que hi escriuen abans de copiar la carpeta, o utilitzeu el mecanisme de còpia de seguretat en línia admès per SQLite si no podeu interrompre el servei:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Aquestes ordres són exemples per al servei i la ruta indicats, no una configuració universal dels volums. Inicialment, la carpeta copiada continua al mateix VPS: traslladeu-la fora del servidor i protegiu-la. Si hi ha workers del mode de cua o altres processos que escriguin a la base de dades, atureu-ne també l'activitat i adapteu el procediment al desplegament real. La guia oficial actual de còpia de seguretat completa de n8n explica aquest requisit de coherència de SQLite.

Per restaurar la carpeta de SQLite predeterminada en una destinació buida: primer atureu n8n i tots els processos que escriguin a la base de dades. Quan tingueu un contenidor de n8n compatible i el volum de destinació, copieu el contingut de la carpeta .n8n de la còpia de seguretat de nou al directori persistent corresponent. Això sobreescriu els fitxers de destinació; per tant, no ho feu en una instància que contingui dades que vulgueu conservar:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker permet copiar fitxers a contenidors aturats, però el propietari dels fitxers de destinació pot ser diferent de l'original. Abans d'iniciar el servei, assegureu-vos que el procés de n8n pot llegir i escriure la configuració restaurada i el fitxer de la base de dades. Si feu servir una altra ruta o un muntatge de directori de l'amfitrió, adapteu la còpia. Consulteu la referència de còpia de Docker Compose. Restaurar només la carpeta de n8n no és suficient quan la instal·lació utilitza una base de dades PostgreSQL separada.

SECRET CRÍTIC

La clau de xifratge forma part de la recuperació

n8n xifra les credencials desades mitjançant una clau de xifratge pròpia de la instància. Si restaureu una base de dades o credencials exportades sense la mateixa clau, és possible que els fluxos de treball recuperats no puguin utilitzar les credencials desades.

Si heu configurat N8N_ENCRYPTION_KEY, restaureu exactament el mateix secret. Si no, la clau generada es desa al fitxer persistent .n8n/config: protegiu aquest fitxer tant en les còpies de seguretat com en reconstruir el servei. Deseu les claus de recuperació fora del VPS, amb les mesures de seguretat adequades. En mode de cua, el procés principal i tots els workers han d'utilitzar la mateixa clau.

Feu-hoConserveu una còpia protegida de la clau exacta que utilitza la instal·lació de producció.
Feu-hoComproveu que l'entorn de recuperació fa servir aquesta clau abans de provar les credencials.
No ho feuConfiar en una clau acabada de generar després de reconstruir el servidor.
No ho feuPujar la clau a un repositori públic ni desar-la juntament amb una còpia de seguretat sense protecció.

FITXERS I DADES BINÀRIES

La còpia de seguretat de la base de dades pot no incloure totes les dependències dels fluxos de treball

Dades persistents de .n8n

Localitzeu i conserveu la carpeta d'usuari real .n8n, no només la imatge del contenidor. En un desplegament habitual amb Docker es munta a /home/node/.n8n; fora de Docker, la ruta predeterminada és ~/.n8n. Si configureu N8N_USER_FOLDER, n8n crea .n8n dins del directori principal que hàgiu indicat. Incloeu la clau de configuració, la base de dades SQLite si és local i les dades binàries o d'execució del sistema de fitxers que utilitzeu.

Fitxers muntats dels fluxos de treball

Si els fluxos de treball llegeixen o escriuen en directoris de l'amfitrió muntats dins del contenidor, feu-ne còpies de seguretat independents. Restaurar n8n sense aquests directoris pot deixar inoperatius fluxos de treball que, altrament, serien vàlids.

Dades binàries

Identifiqueu el mode d'emmagatzematge i restaureu totes les dependències externes. Les dades binàries o d'execució desades al sistema de fitxers poden trobar-se a .n8n o en un directori personalitzat; si feu servir S3, Azure Blob o un altre sistema extern, també cal una còpia recuperable i la configuració d'accés corresponent. Un bolcat de la base de dades no pot substituir aquests fitxers.

Nodes de la comunitat

Anoteu els paquets i les versions dels nodes de la comunitat, i feu una còpia dels directoris addicionals de nodes personalitzats configurats amb N8N_CUSTOM_EXTENSIONS. Aquests directoris poden estar fora de .n8n; restaurar únicament la base de dades i la carpeta d'usuari pot deixar inutilitzables els fluxos de treball que requereixen nodes personalitzats.

ESTRATÈGIA DE CÒPIES EXTERNES

Una còpia de seguretat desada al mateix VPS continua sent només una còpia local

Còpia localPot servir per recuperar ràpidament un estat anterior, però és vulnerable a la pèrdua del servidor, les fallades de disc i els errors destructius.
Còpia fora del servidorConserveu com a mínim una còpia de seguretat en un sistema d'emmagatzematge independent del VPS de producció.
Còpies amb versionsConserveu diversos punts de recuperació per evitar que les dades malmeses o un canvi erroni sobreescriguin l'única còpia que funciona.
Control d'accésLes còpies de seguretat poden contenir credencials, la lògica dels fluxos de treball i dades empresarials sensibles. Xifreu-les i restringiu-hi l'accés adequadament.
SupervisióConfigureu alertes si fallen les còpies de seguretat programades o deixen de generar punts de recuperació nous.

Controleu que la programació es compleix. Registreu la data i l'hora de cada còpia completada correctament, la confirmació de la transferència, la mida del fitxer, la versió de la base de dades d'origen, on es pot recuperar la clau de xifratge i el resultat de l'última prova de restauració. Configureu alertes per als fitxers absents, les còpies fallides o els arxius inesperadament buits. Xifreu els arxius abans de transferir-los fora del VPS i limiteu l'accés als secrets de recuperació. Mantenir diversos punts de recuperació amb data evita que una corrupció detectada tard us deixi sense l'última còpia en bon estat.

Per exemple, si podeu assumir com a màxim sis hores de canvis perduts, fer una còpia correcta cada sis hores és un punt de partida, no una garantia: els processos fallits o la replicació externa endarrerida poden augmentar la pèrdua real. Definiu el període de retenció i la freqüència de les proves de restauració segons els vostres objectius RPO/RTO i les necessitats de dades, en lloc de donar per bona una política universal de 7 o 30 dies.

ORDRE DE RESTAURACIÓ

Restaureu els components en una seqüència controlada

1 · Prepareu l'entornPrepareu un servidor, una base de dades i un entorn de contenidors o d'execució compatibles.
2 · Restaureu els secretsConfigureu de manera segura la clau de xifratge original de n8n i els secrets necessaris per al desplegament.
3 · Restaureu la base de dadesRestaureu PostgreSQL o SQLite i comproveu que n8n es pot connectar a les dades previstes.
4 · Restaureu els fitxersRecupereu els directoris persistents, les dades binàries i els fitxers muntats que utilitzen els fluxos de treball.
5 · Inicieu n8nInicieu l'aplicació amb el nom d'amfitrió, la base de dades i les variables d'entorn esperats.
6 · Verifiqueu la restauracióComproveu que es carreguen els usuaris, els fluxos de treball i les credencials; després, executeu fluxos representatius i proveu les rutes dels webhooks.

Exemple de recuperació després d'un desastre amb PostgreSQL: en una destinació de restauració independent i buida que ja disposi del rol de base de dades adequat i d'una base de dades n8n buida, inicieu només PostgreSQL. Espereu que estigui preparat abans d'importar-hi les dades: docker compose up -d per si sola pot acabar mentre PostgreSQL encara s'està inicialitzant; per això una ordre posterior pg_restore pot fallar. L'exemple utilitza --wait amb una instal·lació moderna de Compose i comprova també pg_isready. Configureu una comprovació d'estat de PostgreSQL adequada per esperar que estigui llest de manera fiable, o verifiqueu explícitament que accepta connexions abans de continuar. No executeu aquesta ordre contra una base de dades de producció que ja contingui dades, ni inicieu n8n abans que la base de dades i la clau i les dades corresponents de .n8n s'hagin restaurat.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

La destinació ha de disposar d'una versió de PostgreSQL compatible, els permisos del rol necessaris, les extensions i la configuració original de n8n. Restaureu .n8n al volum persistent o al muntatge de directori corresponent, amb el vostre sistema de còpies i conservant-ne el propietari i els permisos. Restaureu els fitxers binaris externs, les extensions personalitzades, els fitxers de Docker Compose i la configuració dels secrets. Després, inicieu una versió compatible de n8n i reviseu-ne els registres. Restaurar únicament la base de dades no recupera la clau: en un desplegament amb PostgreSQL, la clau es conserva a .n8n/config llevat que hàgiu configurat explícitament N8N_ENCRYPTION_KEY. PROVA DE RESTAURACIÓ

Una còpia de seguretat només queda validada quan la restauració funciona

Proveu-la en un entorn net

Una prova real ha de demostrar que podeu reconstruir la instància sense dependre de fitxers no documentats que hagin quedat al servidor de producció.

Comproveu les credencials

Obrir un flux de treball no és suficient. Comproveu que les credencials xifrades restaurades es poden desxifrar i autenticar correctament.

Executeu fluxos de treball representatius

Proveu fluxos de treball que depenguin de webhooks, API externes, fitxers muntats i nodes de la comunitat; no us limiteu a validar una automatització senzilla.

Mesureu el temps de recuperació

Registreu quant de temps dura la restauració i quins passos manuals cal fer. Així, una còpia de seguretat teòrica es converteix en un procediment de recuperació aplicable.

Prova de restauració verificada: SQLite i PostgreSQL

Entorn de prova: n8n 2.42.5 en contenidors Docker aïllats, executats en un runner temporal de GitHub Actions, amb un flux de treball sintètic de dos nodes. Aquestes comprovacions es van fer el 8 d'octubre de 2026, no en cap servidor de n8n de clients ni de producció.

SQLite: PASSEs va importar un flux de treball de prova i es va exportar, es van aturar tots els processos que escrivien dades i es va arxivar la carpeta persistent .n8n amb SQLite i la clau de xifratge generada. Després es va restaurar en un volum buit, es va iniciar n8n i es va tornar a exportar i executar el flux de treball recuperat.
PostgreSQL: PASSEs va importar el mateix flux de treball de prova, es va crear i comprovar un bolcat amb format personalitzat de pg_dump, es va restaurar mitjançant pg_restore en una base de dades PostgreSQL nova i buida, es va restaurar també la carpeta separada .n8n i, finalment, es va tornar a exportar i executar el flux de treball recuperat.
Què demostra el resultat PASSEls procediments de còpia provats van conservar el flux de treball, els dos nodes i les seves connexions, i van permetre executar-lo després de la restauració. Són proves funcionals bàsiques reproduïbles, no proves comparatives de rendiment amb càrrega.
Què no es va provarNo es van provar el desxifratge i l'autenticació de credencials reals, els webhooks de producció, els workers i Redis en mode de cua, l'emmagatzematge binari a S3/Azure, els nodes personalitzats, l'accés d'usuaris o projectes ni la recuperació d'una instància de producció en funcionament. Feu una prova independent per a cada dependència que utilitzeu.

Com reproduir la prova: utilitzeu una instal·lació temporal de n8n, creeu un flux de treball innocu de dos nodes, feu una còpia de la base de dades i la carpeta persistent segons el sistema que utilitzeu i restaureu-les en un volum o una base de dades buits. Després, comproveu els nodes, les connexions i l'execució real del flux restaurat. Al sistema de producció, comproveu també les credencials xifrades, els webhooks i els fitxers externs abans de considerar validada la recuperació en cas de desastre.

Llista de comprovació per acceptar la prova de restauració: utilitzeu un domini o entorn aïllat; comproveu que hi ha els usuaris i els fluxos de treball, que una credencial xifrada existent autentica sense tornar-la a introduir, que un webhook de producció activa el flux de treball restaurat previst, que els fitxers muntats i les dades binàries continuen sent llegibles i que es carreguen les integracions que depenen dels nodes de la comunitat necessaris. Comproveu l'antiguitat de la còpia, el temps d'inactivitat mesurat i l'accés a les còpies externes. Si falla qualsevol comprovació essencial, marqueu aquest punt de recuperació com a no verificat en lloc d'indicar que la còpia de seguretat és completa.

LÍMITS DE LES CÒPIES VIA CLI

Què no restauren les exportacions de fluxos de treball i credencials

Les exportacions de la CLI no són una còpia completa de la instància

Les exportacions de fluxos de treball i credencials no inclouen els usuaris ni els rols, l'historial i els registres d'execució, les variables ni la configuració de la instància, com ara la clau de xifratge.

Per restaurar en una instància nova cal configurar-ne el propietari

En una instància neta, completeu la configuració del compte de propietari abans d'importar les credencials. Les restauracions amb diversos usuaris o projectes també poden requerir l'assignació adequada d'usuaris o projectes.

Els identificadors importats poden sobreescriure elements existents

Les exportacions dels fluxos de treball i les credencials conserven els identificadors originals. Si importeu dades en una instància que ja tingui els mateixos identificadors, podeu substituir els elements existents.

Publiqueu expressament els fluxos de treball importats

Les importacions mitjançant la CLI normalment deixen inactius els fluxos de treball. A n8n 2.x, comproveu l'estat de publicació de cada flux importat i publiqueu només els que voleu executar. La CLI del servidor autoallotjat també admet n8n publish:workflow --id=YOUR_WORKFLOW_ID. Si n8n està funcionant, els canvis d'estat de publicació o retirada de publicació fets amb la CLI només tenen efecte després de reiniciar-lo. Reinicieu-lo abans de comprovar els activadors programats i els webhooks de producció o de redirigir-hi el trànsit.

Exemple d'exportació massiva amb Docker Compose: si el servei de n8n s'anomena n8n, podeu executar les ordres oficials de còpia amb la CLI que es mostren a continuació. La ruta de sortida es troba expressament dins del directori persistent muntat .n8n perquè els directoris arbitraris dins d'un contenidor poden desaparèixer quan es recrea. Comproveu que l'usuari del contenidor n8n pot escriure en aquest directori. Deseu els fitxers JSON dels fluxos de treball i de les credencials en directoris separats— n8n documenta un problema d'importació quan tots dos tipus de fitxer comparteixen directori.

Còpia dels esborranys i de les versions publicades a n8n 2.x: una exportació habitual amb --backup dels fluxos de treball captura els esborranys actuals; aquests poden ser diferents de les versions publicades en producció. Per conservar la versió publicada d'un flux concret, exporteu-la per separat amb docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, després de comprovar que la carpeta de destinació existeix i s'hi pot escriure. La CLI també pot exportar una versió històrica mitjançant --version=VERSION_ID. Deseu aquestes còpies fora del servidor juntament amb la còpia completa; no suposeu que el JSON de l'esborrany representa la versió realment publicada.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

El directori copiat ~/n8n-recovery/cli continua al VPS fins que el traslladeu a una ubicació de còpia de seguretat independent i protegida. Les credencials s'exporten xifrades per defecte i necessiten la mateixa clau de xifratge en importar-les. Eviteu utilitzar --decrypted excepte en una migració estrictament controlada: aquesta opció escriu els secrets en text pla. No pugeu mai a un repositori públic de GitHub exportacions que continguin credencials o informació sensible dels fluxos de treball. Algunes plantilles de tercers per copiar credencials a GitHub exporten expressament secrets desxifrats; un repositori privat limita l'accés, però no xifra les dades. Comproveu les opcions reals d'exportació i els permisos d'emmagatzematge de cada plantilla, xifreu els secrets abans de transferir-los fora del servidor i canvieu les credencials que s'hagin exposat per error en una pujada de fitxers en text pla.

Exemple d'importació massiva: en una instància de destinació buida, completeu la configuració del propietari, faciliteu la clau de xifratge original i assegureu-vos que els fitxers de la còpia estan disponibles al VPS de recuperació. Les ordres següents creen la carpeta de destinació i copien les subcarpetes workflows/ i credentials/ des de l'amfitrió al contenidor de n8n; adapteu les rutes si utilitzeu una distribució de volums de Docker diferent:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Comproveu el propietari dels fitxers i els permisos d'accés de l'usuari del contenidor n8n. No importeu dades sobre una instància de producció que ja contingui informació sense un procediment verificat per tornar a l'estat anterior: els identificadors dels fluxos de treball i les credencials poden sobreescriure elements existents. Després, executeu:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Els identificadors importats poden substituir fluxos de treball o credencials existents. Feu proves en una instància aïllada i comproveu després les credencials i els estats d'activació i publicació. A n8n 2.x, restaurar l'esborrany JSON no demostra, per si sol, que el flux de treball estigui publicat ni que pugui executar activadors programats. Precaucions durant la importació: en una instància de n8n sense múltiples processos principals, els activadors cron que ja estaven actius poden continuar executant-se després d'importar dades amb la CLI fins que es reiniciï la instància. Atureu o aïlleu els activadors de producció i reinicieu n8n abans d'activar les tasques restaurades; comproveu que no s'executen per duplicat. Les exportacions fetes amb la CLI no inclouen els usuaris originals, els registres d'execució, les variables de la instància ni la clau de xifratge. --backup estableix les opcions --all --pretty --separate; no fa una còpia de la «instància completa». Fonts: guia oficial actual de còpia de seguretat i restauració de n8n i referència d'ordres de la CLI de n8n.

Restauració massiva amb plantilles de GitHub o Google Drive: aquesta és una alternativa només per als fitxers JSON dels fluxos de treball, no per a la base de dades de la instància, els usuaris, els valors secrets de les credencials xifrades ni la clau de xifratge. Abans d'executar una plantilla basada en l'API, comproveu els permisos de l'API de n8n i de l'emmagatzematge, la versió de la còpia i la instància de destinació seleccionades, si actualitza els identificadors coincidents, si recrea els fluxos suprimits i com gestiona la publicació dels fluxos de treball. No totes les plantilles tornen a crear els identificadors que falten a la destinació; proveu aquest cas en un entorn aïllat abans de confiar en una restauració automàtica.

Preguntes freqüents

Còpia de seguretat i restauració de n8n: preguntes freqüents

N'hi ha prou d'exportar els fluxos de treball per tenir una còpia de seguretat de n8n?

No. Les exportacions dels fluxos de treball són còpies lògiques útils, però per recuperar completament la instància també poden ser necessàries les credencials, la clau de xifratge corresponent, l'estat de la base de dades, els fitxers persistents i l'emmagatzematge de dades binàries.

Necessito la clau de xifratge de n8n si ja tinc la base de dades?

Sí, si voleu continuar utilitzant les credencials xifrades desades a la base de dades. Conserveu la clau original de manera segura.

He de copiar PostgreSQL o exportar els fluxos de treball i les credencials?

Per recuperar-vos d'un desastre, protegiu la base de dades i la clau de xifratge. Les exportacions lògiques són un complement útil per a migracions i recuperacions selectives, però no substitueixen tots els components de la instància.

Una instantània del VPS pot ser la meva única còpia de seguretat?

És preferible considerar-la una mesura de recuperació més. Conserveu una còpia independent fora del servidor perquè una fallada del proveïdor, del compte, del servidor o de les instantànies no elimini tots els punts de recuperació alhora.

Com puc comprovar que la còpia de seguretat funciona?

Restaureu-la en un entorn de prova buit, comproveu que les credencials es poden desxifrar i executeu fluxos de treball representatius. Que el procés de còpia hagi acabat correctament no demostra, per si sol, que les dades es puguin recuperar.

Les còpies dels fluxos de treball a GitHub o Google Drive inclouen les dades secretes de les credencials desades?

Les còpies JSON que només contenen fluxos de treball no inclouen els valors secrets gestionats pel magatzem de credencials de n8n ni la clau de xifratge de la instància. Tanmateix, el JSON exportat pot revelar noms i identificadors de credencials i secrets introduïts directament en els paràmetres dels nodes, com ara les capçaleres d'autenticació. Reviseu i protegiu el JSON abans de pujar-lo o compartir-lo. Per a una recuperació completa, copieu la base de dades i la clau original o utilitzeu exportacions xifrades de credencials mitjançant la CLI, amb una restauració provada. Una plantilla de GitHub o Google Drive que només desa fluxos de treball no permet una recuperació completa després d'un desastre.

OBJECTIUS DE RECUPERACIÓ

Definiu l'RPO i l'RTO abans d'un incident

RPO és la pèrdua màxima tolerable de canvis recents. Calculeu-la a partir del punt de recuperació més recent que sigui utilitzable i estigui desat independentment; un procés programat cada sis hores no garanteix un RPO de sis hores si fallen les exportacions o les transferències. RTO és el temps màxim tolerable d'interrupció del servei. Mesureu-lo en una prova de restauració en un entorn net, incloent-hi la recuperació de secrets, els fitxers externs, la comprovació de les credencials i la publicació dels fluxos restaurats, no només l'inici d'un contenidor.

CLAU DE RECUPERACIÓ

Localitzeu la clau de xifratge original abans de reconstruir el servidor

Si a producció heu establert N8N_ENCRYPTION_KEY, conserveu exactament aquest secret de l'entorn. Si no l'heu establert, preserveu la clau generada al fitxer persistent original .n8n/config. Abans d'importar credencials xifrades, comproveu quina clau utilitza realment la instància restaurada: una clau nova generada automàticament no pot desxifrar les credencials de la base de dades antiga.
