CAPACITAT MÍNIMA VS PRÀCTICA

n8n té una mida mínima oficial de VPS?

No per a totes les càrregues de treball. Els exemples oficials de requisits previs de n8n descriuen un desplegament OEM il·lustratiu i adverteixen explícitament que els requisits varien segons la càrrega de treball. Aquesta documentació no és una garantia universal que qualsevol CPU, RAM o assignació de disc específica admetrà les automatitzacions de producció.

n8n assenyala que una instància inactiva pot utilitzar relativament poca memòria, però un node de codi, una gran càrrega útil binària o una execució simultània poden augmentar la demanda de memòria dràsticament. Pressupost per separat per al sistema operatiu, Docker, PostgreSQL i eines de còpia de seguretat/vigilància.

MESURA ABANS D'ACTUALITZAR

Com saber si n8n necessita més RAM, CPU o disc

Executeu el vostre flux de treball més gran esperat i una ràfega realista superposada i, a continuació, inspeccioneu el servidor i els registres d'execució de n8n. El nombre de fluxos de treball desats a l'editor no és un punt de referència de capacitat útil per si sol.

Memòria / OOM

Comproveu docker stats --no-stream i free -h. Si la memòria s'esgota, primer reduïu JSON o les càrregues útils binàries, agrupa les importacions grans i eviteu els passos del codi amb molta memòria. Un error de pila de JavaScript no es corregeix necessàriament afegint vCPU.

CPU / concurrència

Mesureu si CPU es manté ocupat durant les transformacions o les feines només esperen API externes. En mode normal, considereu un límit de concurrència de producció compatible abans d'escalar als treballadors. L'augment de CPU no accelera un API de tarifa externa limitada.

Emmagatzematge / base de dades

Comproveu df -h, la mida de la base de dades i l'historial d'execució retingut. Observa el creixement del disc i les operacions de base de dades lentes. Establiu la retenció deliberadament abans de pagar per un disc més gran; mantenir les còpies de recuperació fora del servidor.

Utilitzeu la guia de concurrència de n8n i l'explicació oficial de benchmarking. Qualsevol nombre de fluxos de treball concurrents anunciats sense conèixer les seves càrregues útils i la latència API és només una estimació.

BASE DE DADES I EMMAGATZEMATGE

SQLite, PostgreSQL i dades persistents

SQLite

SQLite pot adaptar-se a petits desplegaments i proves d'una sola instància. A mesura que l'ús de la producció i la concurrència creixen, l'elecció de la base de dades es converteix en una limitació operativa més que en un detall d'instal·lació.

PostgreSQL

Per a una pila VPS orientada a la producció, PostgreSQL proporciona una base de dades més sòlida. Pressupost RAM, CPU i disc per a la pròpia base de dades i supervisar-ne el creixement.

Dades persistents .n8n

No tracteu PostgreSQL com l'únic actiu persistent. Preserveu el directori de dades n8n i protegiu la clau de xifratge necessària per recuperar les credencials xifrades.

Creixement del disc

L'historial d'execució, les dades binàries, els fitxers de base de dades i els registres es poden expandir amb el temps. La configuració de retenció i les còpies de seguretat fora del servidor afecten directament la capacitat necessària.

CAPACITAT DEL DISC

Estimar n8n emmagatzematge de l'historial d'execució abans de fer la comanda

Comença amb execucions desades per dia × bytes emmagatzemats mitjans per execució × dies de retenció. Per exemple, 500 execucions desades per dia × 200 KB cada × 14 dies = 1.4 GB de dades d'execució d'exemple abans de la sobrecàrrega de la base de dades. Aquesta suposició de 200 KB és il·lustrativa, no una referència de n8n.

També assigneu disc per al sistema operatiu, capes d'imatge Docker, índexs de bases de dades, fitxers binaris, registres d'aplicacions, actualitzacions i fitxers temporals. Les còpies de seguretat fora del servidor necessiten la seva pròpia capacitat. Un disc 10 GB pot funcionar per a una pila ajustada, però té molt menys espai per als fitxers retinguts que un disc 40 o 80 GB.

n8n documenta la poda d'execució per defecte per edat (336 hores / 14 dies) o recompte (10,000 execucions), amb excepcions. Comproveu la vostra configuració real i comproveu què es conserva abans de canviar-los. SQLite pot reutilitzar l'espai alliberat en lloc de reduir automàticament el seu fitxer.

Font: n8n: gestionar dades d'execució i poda. Els requisits del disc depenen de les mides de càrrega útil desades observades, no només del nombre de nodes.

CONCURRÈNCIA

Quan un VPS més gran deixa de ser la resposta sencera

L'escala vertical és adequada mentre que una instància pot gestionar la càrrega de treball de manera neta. Quan la demanda paral·lela sostinguda crea contenció, avalueu el mode de cua i els treballadors. El mode de cua introdueix Redis, PostgreSQL i un o més processos de treball; pressupost RAM i CPU per a cada component, no només n8n. n8n també documenta les restriccions sobre l'emmagatzematge de dades binàries del sistema de fitxers en mode de cua, així que valideu un disseny d'emmagatzematge de dades compatible abans de canviar.

NIVEL D'ENTRADA I EMMAGATZEMATGE I/O

Com utilitzar una entrada 1 GB VPS

1 GB RAM

Aquest és un nivell VPS que funciona real, no un producte només de prova. Pot ser adequat per a petites automatitzacions permanents i, sobretot, per a treballs seqüencials API quan manteniu la memòria, l'ús del disc i els treballs concurrents dins dels límits mesurats. Ofereix poc marge per a PostgreSQL al mateix servidor, grans càrregues útils o execucions paral·leles pesades.

2 GB RAM

Utilitzeu 2 GB com a línia de base de la instància de llum més segura quan vulgueu més espai per al sistema operatiu, Docker i petites ràfegues sense passar immediatament a una pila de mida de producció.

SSD vs NVMe

Standard SSD és adequat per a l'automatització de la llum. NVMe es fa més útil quan PostgreSQL i l'historial d'execucions creen lectures i escriptures freqüents o quan la latència del disc es mostra en el rendiment mesurat del flux de treball.

Mesura abans d'actualitzar

Utilitzeu CPU, la memòria, el creixement del disc i la durada de l'execució sota superposició màxima per decidir si el coll d'ampolla és de càlcul, memòria o emmagatzematge en lloc de suposar que un VPS més gran soluciona cada desacceleració.

Preguntes freqüents

n8n VPS requisits: preguntes habituals

Quant necessita RAM n8n?

No hi ha cap figura universal. RAM exigeix ​​canvis amb la concurrència, la mida de la càrrega útil, el comportament d'execució i els serveis de suport al VPS. Un servidor 4 GB és una classe inicial pràctica de petita producció, no un requisit garantit per a cada càrrega de treball.

Quants nuclis CPU he d'utilitzar?

Les càrregues de treball lleugeres poden començar amb una petita assignació de CPU. Afegiu nuclis quan el seguiment mostri una pressió sostinguda CPU o execucions més lentes en concurrència en lloc de dimensionar només a partir del recompte de flux de treball.

n8n requereix PostgreSQL?

Els desplegaments petits poden utilitzar SQLite, però PostgreSQL és l'opció més forta orientada a la producció a mesura que augmenten els requisits operatius i la concurrència.

Quan es requereix Redis?

Redis està associat al mode de cua. Un desplegament normal d'una sola instància no necessita Redis simplement perquè s'executa en un VPS.

Quant espai en disc he de reservar?

La demanda de disc depèn del creixement de PostgreSQL, l'historial d'execució retingut, les dades binàries, els registres, les capes de contenidors i les còpies de seguretat. Superviseu el creixement i deixeu el marge en lloc de confiar en un nombre universal fix.

Puc executar n8n contínuament en un 1 GB VPS?

Sí, quan la càrrega de treball real s'ajusti. Un 1 GB VPS és un servidor de treball real i pot suportar automatitzacions petites, majoritàriament seqüencials, però l'espai de memòria és limitat. Eviteu suposar que hi caben una pila PostgreSQL del mateix servidor, treballs pesats en binaris o múltiples execucions simultànies grans. Superviseu el consum i l'actualització en funció de la pressió dels recursos observada.

És millor 2 GB o 4 GB RAM per a una producció n8n VPS?

Dos gigabytes donen més espai que una instància magra 1 GB, mentre que 4 GB és una classe inicial pràctica per avaluar n8n juntament amb PostgreSQL i HTTPS. No hi ha un mínim de producció garantit universal: la complexitat de la càrrega de treball, la superposició màxima, la configuració del contenidor i les dades retinguts determinen la demanda real.

Els fluxos de treball d'IA n8n requereixen un GPU?

No quan n8n només crida a un model extern API: el proveïdor de models gestiona la inferència, mentre que el VPS gestiona l'orquestració, les càrregues útils i la concurrència. L'execució de models d'inferència localment és una decisió de maquinari independent que pot requerir molts més recursos RAM i adequats GPU.

Què causa els errors de falta de memòria n8n?

Les grans càrregues útils JSON o binàries, les operacions de codi amb molta memòria i les execucions superposades són causes habituals. Comproveu els registres del temps d'execució i l'ús màxim de la memòria i, a continuació, reduïu les dades retinguts en una execució o assigneu més RAM en funció del problema mesurat.
