REQUISITS DEL SERVIDOR

Requisits del VPS per a n8n

Per determinar els requisits d'un VPS per a n8n, partiu de la càrrega de treball, no d'un mínim de maquinari universal. Un VPS d'1 vCPU i 1 GB de RAM, dimensionat amb cura, pot executar petites automatitzacions permanents, mentre que 2 vCPU i 4 GB de RAM són un punt de partida pràctic per a n8n amb PostgreSQL i HTTPS. Les dades voluminoses, les execucions simultànies i el processament local necessiten més marge. Mesureu-ne l'ús real abans de triar el servidor.

REQUISITS ESSENCIALS

Instàncies lleugeres, producció de petita escala i càrregues exigents

Instància lleugera, sempre activa

1 vCPU · 1–2 GB RAM

Un VPS real amb 1 GB de RAM pot executar fluxos lleugers d'n8n de manera continuada si limiteu la càrrega de treball i comproveu el marge de memòria i disc. Amb 2 GB hi ha més marge per a Docker, petits pics de càrrega i altres serveis. Cap d'aquestes xifres garanteix un nombre concret de fluxos de treball.

Producció de petita escala

2 vCPU · 4 GB RAM

És un punt de partida equilibrat quan n8n comparteix el VPS amb PostgreSQL, Docker i un proxy invers. Reserveu recursos per a les execucions simultànies i el manteniment.

Càrregues exigents o intensives en dades

4+ vCPU · 8 GB+ RAM

Els JSON voluminosos, els fitxers binaris, els nodes Code, les tasques de navegador i moltes execucions simultànies poden requerir molta més CPU i memòria.

Emmagatzematge

SSD / NVMe amb marge de creixement

La capacitat necessària depèn del creixement de PostgreSQL, la retenció de l'historial d'execucions, les dades binàries, els registres, les capes de Docker i l'estratègia de còpies de seguretat, no només d'n8n.

CAPACITAT MÍNIMA I CAPACITAT PRÀCTICA

Hi ha una configuració mínima oficial de VPS per a n8n?

No n'hi ha una que serveixi per a totes les càrregues de treball. Els exemples oficials de requisits previs d'n8n descriuen un desplegament OEM il·lustratiu i adverteixen expressament que els recursos necessaris varien segons la càrrega de treball. Aquesta documentació no garanteix que una determinada combinació de CPU, RAM i disc sigui suficient per a qualsevol automatització en producció.

n8n indica que una instància inactiva pot consumir relativament poca memòria, però un node Code, un fitxer binari voluminós o diverses execucions simultànies poden fer augmentar molt el consum de RAM. Reserveu recursos addicionals per al sistema operatiu, Docker, PostgreSQL i les eines de supervisió i còpies de seguretat.

Fonts tècniques: exemples de requisits previs d'n8n i guia oficial de memòria. Les quatre opcions de la taula són configuracions reals de recursos que es poden contractar, no requisits oficials prescrits per n8n.

RAM i CPU

Què consumeix realment els recursos del servidor?

Execucions simultànies

Diversos fluxos de treball executats alhora poden consumir més recursos que no pas el nombre total de fluxos desats a n8n. Superviseu els pics de memòria i la latència quan coincideixen execucions.

Mida de les dades processades

Els objectes JSON voluminosos, els fitxers i les dades binàries incrementen el consum de memòria. Unes poques execucions amb moltes dades poden necessitar més RAM que nombroses automatitzacions senzilles amb API.

Nodes que consumeixen molta CPU

Els nodes Code, les transformacions i altres operacions de càlcul intensiu poden mantenir la CPU saturada. Tenir més nuclis ajuda quan diverses execucions competeixen pels recursos de processament.

Serveis auxiliars

El sistema operatiu, PostgreSQL, el proxy invers, la supervisió i Docker també consumeixen recursos. Dimensioneu tot el conjunt, no només el procés n8n.

MESUREU ABANS D'AMPLIAR RECURSOS

Com saber si n8n necessita més RAM, CPU o disc

Executeu el flux de treball més exigent que preveieu i simuleu un pic realista d'execucions simultànies. Després, reviseu l'estat del servidor i els registres d'execució d'n8n. El nombre de fluxos desats a l'editor no és, per si sol, una mesura útil de capacitat.

Memòria / OOM

Comproveu docker stats --no-stream i free -h. Si la memòria s'esgota, primer reduïu les dades JSON o binàries, processeu les importacions grans per lots i eviteu els nodes Code que consumeixen molta memòria. Afegir vCPU no resol necessàriament un error de memòria heap de JavaScript.

CPU / execucions simultànies

Mesureu si la CPU es manté ocupada durant les transformacions o si les tasques només esperen la resposta d'API externes. En el mode estàndard, valoreu un límit de concurrència en producció compatible abans de passar als workers. Augmentar la CPU no accelera una API externa limitada en el nombre de sol·licituds.

Emmagatzematge / base de dades

Comproveu df -h, la mida de la base de dades i l'historial d'execucions conservat. Vigileu el creixement del disc i les consultes lentes. Ajusteu conscientment la retenció abans de pagar per un disc més gran; manteniu les còpies de recuperació fora del servidor.

Consulteu les recomanacions d'n8n sobre concurrència i l'explicació oficial de les proves de rendiment. Qualsevol xifra d'execucions simultànies anunciada sense conèixer la mida de les dades i la latència de les API és només una estimació.

BASE DE DADES I EMMAGATZEMATGE

SQLite, PostgreSQL i dades persistents

SQLite

SQLite pot ser suficient per a instal·lacions petites d'una sola instància i entorns de prova. Quan augmenten l'ús en producció i les execucions simultànies, la tria de la base de dades esdevé una decisió operativa important.

PostgreSQL

Per a un VPS orientat a producció, PostgreSQL ofereix una base més sòlida. Reserveu RAM, CPU i disc per a la mateixa base de dades i superviseu-ne el creixement.

Dades persistents de .n8n

No considereu PostgreSQL l'únic element que cal conservar. Manteniu el directori de dades d'n8n i protegiu la clau de xifratge necessària per recuperar les credencials xifrades.

Creixement del disc

L'historial d'execucions, les dades binàries, els fitxers de base de dades i els registres poden créixer amb el temps. La política de retenció i les còpies de seguretat fora del servidor afecten directament l'espai necessari.

CAPACITAT DEL DISC

Calculeu l'espai per a l'historial d'execucions d'n8n abans de contractar un VPS

Comenceu amb la fórmula execucions desades al dia × mida mitjana en bytes de cada execució × dies de retenció. Per exemple, 500 execucions desades al dia × 200 KB cadascuna × 14 dies = 1.4 GB de dades d'execució en aquest exemple, abans de comptar l'espai addicional de la base de dades. Els 200 KB són una hipòtesi il·lustrativa, no un resultat de proves d'n8n.

Reserveu també espai per al sistema operatiu, les capes d'imatges Docker, els índexs de base de dades, els fitxers binaris, els registres de l'aplicació, les actualitzacions i els fitxers temporals. Les còpies de seguretat externes necessiten capacitat pròpia. Un disc de 10 GB pot ser suficient per a una instal·lació lleugera, però ofereix molt menys espai per als fitxers conservats que un disc de 40 o 80 GB.

n8n documenta que, per defecte, depura l'historial d'execucions segons l'antiguitat (336 hores / 14 dies) o la quantitat (10,000 execucions), amb excepcions. Reviseu la configuració real i què es conserva abans de modificar-la. SQLite pot reutilitzar l'espai alliberat sense reduir automàticament la mida del fitxer.

Font: documentació d'n8n sobre gestió i depuració de dades d'execució. L'espai de disc necessari depèn de la mida observada de les dades desades, no només del nombre de nodes.

REQUISITS DEL SISTEMA

Docker i recursos addicionals per a producció

VPS Linux

Utilitzeu una distribució Linux amb manteniment vigent i recursos suficients per al sistema operatiu i les actualitzacions de seguretat, a més dels serveis de l'aplicació.

Docker i Compose

Els contenidors faciliten que el desplegament sigui reproduïble, però no eliminen el consum de recursos. Conserveu les dades d'n8n i de la base de dades fora dels contenidors que es poden eliminar i recrear.

HTTPS i proxy invers

Els webhooks públics necessiten un nom d'amfitrió estable i HTTPS ben configurat. Incloeu el proxy invers i la capa TLS al disseny de producció.

Supervisió i còpies de seguretat

Superviseu la RAM, la CPU, el disc i el creixement de la base de dades. Manteniu còpies de seguretat recuperables fora del VPS i proveu la restauració; no doneu per fet que una instantània és suficient.

CONCURRÈNCIA

Quan ampliar el VPS ja no és suficient

L'escalat vertical és adequat mentre una sola instància pugui gestionar la càrrega sense problemes. Si la demanda sostinguda d'execucions paral·leles provoca competència pels recursos, valoreu el mode de cua i els workers. El mode de cua incorpora Redis, PostgreSQL i un o diversos processos worker; reserveu RAM i CPU per a cada component, no només per a n8n. n8n també documenta restriccions per emmagatzemar dades binàries al sistema de fitxers en mode de cua; valideu un sistema d'emmagatzematge compatible abans de fer el canvi.

LLISTA DE COMPROVACIÓ DEL DIMENSIONAMENT

Definiu aquests factors abans de triar un VPS

Quantes execucions coincideixen en el temps?

Estimeu el pic d'execucions simultànies, no només el nombre d'execucions diàries.

Quina mida té cada execució?

Tingueu en compte la mida dels JSON, els fitxers, les dades binàries i les transformacions que consumeixen molta memòria.

Quins serveis comparteixen el servidor?

Incloeu PostgreSQL, el proxy, la supervisió i qualsevol altre contenidor en el càlcul dels recursos.

Amb quina rapidesa creixeran les dades?

Estimeu la retenció de l'historial d'execucions, el creixement de la base de dades i l'espai per a còpies de seguretat abans de decidir la capacitat del disc.

GAMMA BÀSICA I E/S D'EMMAGATZEMATGE

Com utilitzar un VPS bàsic d'1 GB

1 GB RAM

Aquest és un VPS real i operatiu, no un producte només per fer proves. Pot ser adequat per a petites automatitzacions permanents i tasques d'API principalment seqüencials, sempre que el consum de memòria, l'espai de disc i les execucions simultànies es mantinguin dins de límits comprovats. Ofereix poc marge per a PostgreSQL al mateix servidor, dades voluminoses o moltes execucions paral·leles.

2 GB RAM

Feu servir 2 GB com a punt de partida més segur per a una instància lleugera si voleu més marge per al sistema operatiu, Docker i petits pics de càrrega sense passar directament a una configuració de producció més gran.

SSD vs NVMe

Un SSD convencional és suficient per a automatitzacions lleugeres. NVMe és més útil quan PostgreSQL i l'historial d'execucions fan moltes lectures i escriptures o quan la latència del disc afecta el rendiment mesurat dels fluxos de treball.

Mesureu abans d'ampliar el servidor

Mesureu la CPU, la memòria, el creixement del disc i la durada de les execucions als pics de concurrència. Així podreu determinar si el coll d'ampolla és el processador, la memòria o l'emmagatzematge, sense donar per fet que un VPS més gran resol qualsevol alentiment.

PREGUNTES FREQÜENTS

Requisits del VPS per a n8n: preguntes habituals

Quanta RAM necessita n8n?

No hi ha una xifra universal. El consum de RAM varia segons les execucions simultànies, la mida de les dades, el comportament dels fluxos i els serveis auxiliars del VPS. Un servidor de 4 GB és un punt de partida pràctic per a producció de petita escala, no un requisit garantit per a qualsevol càrrega de treball.

Quants nuclis de CPU necessito?

Les càrregues lleugeres poden començar amb pocs recursos de CPU. Afegiu nuclis quan la supervisió mostri una saturació sostinguda o execucions més lentes en moments de concurrència, en lloc de dimensionar només segons el nombre de fluxos.

n8n necessita PostgreSQL?

Les instal·lacions petites poden utilitzar SQLite, però PostgreSQL és una opció més sòlida per a producció quan augmenten les necessitats operatives i la concurrència.

Quan cal Redis?

Redis està relacionat amb el mode de cua. Un desplegament habitual amb una sola instància no necessita Redis només pel fet d'executar-se en un VPS.

Quant espai de disc he de reservar?

L'espai necessari depèn del creixement de PostgreSQL, la retenció de l'historial d'execucions, les dades binàries, els registres, les capes dels contenidors i les còpies de seguretat. Superviseu-ne el creixement i deixeu marge, en lloc de confiar en una xifra fixa universal.

Puc executar n8n contínuament en un VPS d'1 GB?

Sí, si la càrrega de treball real hi cap. Un VPS d'1 GB és un servidor funcional que pot executar petites automatitzacions, sobretot seqüencials, però té un marge de memòria limitat. No pressuposeu que hi cabran PostgreSQL al mateix servidor, tasques amb molts fitxers binaris o diverses execucions voluminoses simultànies. Superviseu el consum i amplieu recursos segons els valors observats.

Per a un VPS n8n de producció, és millor 2 GB o 4 GB de RAM?

Amb 2 GB teniu més marge que amb una instal·lació mínima d'1 GB; 4 GB són un punt de partida pràctic per avaluar n8n amb PostgreSQL i HTTPS. No existeix cap mínim universal garantit per a producció: la complexitat dels fluxos, els pics de concurrència, la configuració dels contenidors i les dades conservades determinen el consum real.

Els fluxos de treball d'IA d'n8n necessiten una GPU?

No, si n8n només crida una API externa d'un model: el proveïdor del model executa la inferència, mentre que el VPS gestiona l'orquestració, les dades i les execucions simultànies. Executar models d'inferència localment és una altra decisió de maquinari que pot requerir molta més RAM i una GPU adequada.

Què provoca els errors de manca de memòria a n8n?

Les dades JSON o binàries voluminoses, les operacions Code que consumeixen molta memòria i les execucions simultànies són causes habituals. Reviseu els registres i els pics de consum, després reduïu les dades carregades en cada execució o augmenteu la RAM segons el problema mesurat.
