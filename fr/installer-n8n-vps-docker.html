Installer le n8n sur un VPS

Installez n8n sur un VPS en utilisant Docker Compose et PostgreSQL. Un déploiement de production nécessite également des données d'application et de base de données persistantes, un support stable. N8N_ENCRYPTION_KEY, un nom d'hôte public, HTTPS et une configuration correcte du webhook. Vérifiez ces pièces avant d’activer les flux de production.

Préparez le VPS avant de commencer le n8n

Linux VPS

Utilisez un serveur Linux maintenu et dimensionné pour les n8n, PostgreSQL, Docker et le proxy inverse.

Pointez un domaine ou un sous-domaine vers le VPS avant d'émettre des certificats TLS et de publier des URL de webhook.

Pare-feu

Vous installez sur un VPS qui héberge déjà des sites Web ? Vous pouvez ajouter du n8n à un serveur que vous contrôlez lorsque les CPU, RAM et le stockage le permettent. Cependant, si Nginx, Apache, Caddy ou un autre proxy inverse possède déjà les ports 80/443, faites pas démarrez l'exemple de conteneur Caddy ci-dessous inchangé : les ports seront en conflit. Au lieu de cela, acheminez un nouveau sous-domaine n8n via votre proxy inverse existant avec un réseau privé approprié, ou utilisez un VPS propre pour l'exemple exact de Compose. Préserver les autres sites et leur configuration TLS ; l'exemple suppose que les ports 80/443 sont disponibles.

INSTALLATION COPIER ET ADAPTER

Installez n8n sur votre VPS avec Docker Compose

Utilisez cet exemple pour créer un déploiement n8n sur un autogéré Linux VPS. Vous installez et maintenez vous-même le n8n ; le choix d'un serveur via notre partenaire n'inclut pas d'instance n8n préinstallée. L'exemple combine n8n, PostgreSQL, un exécuteur de tâches externe et Caddy HTTPS dans un réseau Compose privé. C'est un modèle de configuration, il ne s'agit pas d'une affirmation d'un déploiement testé en direct.

Vous souhaitez plutôt la nouvelle installation la plus rapide ? n8n fournit également une configuration officielle Docker sur une seule ligne. Vous pouvez télécharger et revoir son script avec curl -fsSL https://get.n8n.io -o get-n8n.sh avant de courir sh get-n8n.sh. Cette option lance une instance initiale avec SQLite à une URL locale et inclut les services sandbox n8n Assistant ; c'est pas pareil comme ce déploiement VPS soutenu par le public HTTPS, PostgreSQL. La pile sandbox complète officielle a besoin de plus de RAM et CPU qu'une installation allégée n8n (son guide Compose spécifie au moins 4 GB RAM / 2 vCPU). Pour une production orientée Internet VPS, continuez avec la pile configurée manuellement ci-dessous.

1. Préparer les Docker, DNS et accéder

Connectez-vous via SSH avec l'accès sudo et pointez un DNS Un enregistrement pour n8n.example.com à votre adresse IPv4 VPS. Sur un frais Ubuntu 22.04, 24.04 ou 26.04 VPS, les commandes suivantes installent Docker Engine et le moderne docker compose plugin du responsable officiel du Docker signé apt référentiel :

# Fresh official Ubuntu 22.04 / 24.04 / 26.04 installation
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Register Docker's signed apt repository
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

Il s'agit de la méthode de référentiel orientée production dans le guide d'installation officiel Docker Ubuntu. Ne réinstallez pas ou ne supprimez pas aveuglément le Docker sur un VPS qui exécute déjà des conteneurs ou d'autres sites Web.; inspectez d’abord l’installation existante et les éventuels conflits de packages. Pour Debian ou une autre distribution, utilisez les instructions officielles spécifiques au système d'exploitation correspondantes au lieu des commandes Ubuntu.

Vérifiez maintenant le Docker lui-même, le plugin Compose, le DNS et le répertoire de travail :

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

Si getent hosts ne renvoie aucune adresse ou une mauvaise adresse, corrigez votre DNS avant de commencer le Caddy ; remplacer n8n.example.com tout au long de ce guide avec votre véritable nom d'hôte. Docker nécessite normalement les privilèges root : si votre utilisateur SSH ne peut pas exécuter cette version ultérieure docker compose commandes directement, préfixez-les avec sudo. Ajout d'un utilisateur au docker Le groupe accorde un accès équivalent à la racine et ne doit pas être effectué de manière fortuite sur un serveur partagé.

Gardez votre port d'administration SSH réel accessible avant d'activer un pare-feu. Autoriser les HTTP (80) et HTTPS (443) entrants pour l'émission du certificat et l'éditeur. Les ports de conteneurs publiés au Docker peuvent contourner certaines règles UFW, alors consultez les instructions de pare-feu du Docker et publiez uniquement les ports Caddy prévus. Cet exemple de Compose fait délibérément pas publier PostgreSQL (5432), n8n (5678) ou un courtier d'exécution de tâches (5679) sur l'Internet public.

2. Créer des valeurs d'environnement et préserver la clé

Depuis le répertoire du projet, générez trois différent valeurs hexadécimales aléatoires avec :

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

Créez un fichier nommé .env en utilisant le modèle ci-dessous, remplacez chaque REPLACE_WITH_RANDOM_HEX avec une valeur générée différente et modifiez le nom d'hôte et le fuseau horaire. Le montré 2.42.5 la balise est la version stable répertoriée au 8 octobre 2026, utilisé ici comme exemple de configuration daté, pas une garantie d'un déploiement testé en direct ou d'une sécurité future. Avant l'installation, vérifiez les versions officielles n8n actuelles, puis conservez n8n et son image d'exécution de tâches sur la même version vérifiée.

# .env — replace the three example secrets
# Pin a maintained n8n release; keep n8n and runner equal.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

Ne vous engagez jamais .env vers un référentiel public. Conservez la clé de cryptage et les instructions de récupération en toute sécurité hors du VPS. La clé doit rester la même après la recréation ou la migration du conteneur.

3. Écrivez compose.yaml pour une nouvelle installation

Dans le même répertoire, créez compose.yaml. L'exemple utilise les conventions officielles n8n sur les variables d'environnement et les PostgreSQL 18 PGDATA chemin documenté par le projet d'hébergement n8n :

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

Les quatre services ont des rôles distincts : PostgreSQL stocke l'état de la base de données, n8n exécute les workflows, n8n-runner exécute les tâches d'exécution avec une version correspondante et un jeton d'authentification partagé, et Caddy gère le HTTPS public. Un externe coureur de tâches n'est pas le mode file d'attente Redis. Seul le Caddy publie les ports hôtes. Cette illustration simplifiée utilise un seul rôle de base de données pour la configuration ; pour une séparation plus forte des privilèges PostgreSQL, consultez l'exemple de déploiement officiel n8n PostgreSQL.

4. Créer le fichier Caddy HTTPS

Créer le fichier Caddyfile (C majuscule, pas d'extension) à côté compose.yaml. Remplacez partout l'exemple de nom d'hôte par votre propre nom DNS :

n8n.example.com {
    reverse_proxy n8n:5678
}

Caddy demande et renouvelle les certificats publics TLS lorsque le domaine est résolu correctement et que le trafic externe peut atteindre les ports 80/443. Ne pointez pas le DNS vers localhost. Si vous remplacez Caddy par un autre proxy inverse, transférez les en-têtes d'hôte, de protocole et d'adresse client d'origine et ajustez N8N_PROXY_HOPS pour le nombre réel de sauts de proxy approuvés.

5. Démarrez les conteneurs et testez de l’extérieur

Exécutez ces commandes à partir du répertoire du projet après avoir enregistré .env, compose.yaml et Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

La dernière commande vérifie le publique HTTPS point final de santé. Si la délivrance du certificat est toujours en attente, inspectez les journaux Caddy et DNS/ports avant de conclure que le n8n est rompu. Ouvert https://n8n.example.com, créez immédiatement le premier compte propriétaire et activez les protections de connexion appropriées. Confirmez que l'instance exécute réellement un workflow, et pas seulement que l'éditeur charge :

  1. Dans l'éditeur, créez un workflow avec un Webhook déclencheur. Ensemble HTTP Méthode à GET, choisissez le Path vps-check, et définissez Répondre à Immédiatement. Enregistrez le flux de travail.
  2. Cliquez Écoutez l'événement test, copiez l'intégralité Tester l'URL indiqué par n8n, et depuis un autre appareil, exécutez curl -i 'PASTE_TEST_URL_HERE' avec l'URL copiée. Attendez-vous à une réponse de réussite HTTP et à l'événement entrant qui apparaît dans l'éditeur n8n. Les URL de test ne fonctionnent que lorsque le n8n écoute l'événement.
  3. Publier le workflow, basculez le nœud vers son URL de production, copiez-le et exécutez curl -i 'PASTE_PRODUCTION_URL_HERE' encore une fois. Confirmez l'exécution sous le workflow Exécutions onglet. Les demandes de webhook de production nécessitent que le flux de travail soit publié et n'affichent pas leur charge utile dans la vue test de l'éditeur.

Il s’agit d’un test de fumée volontairement simple et non authentifié : ne lui envoyez jamais de secrets. Dépublier/supprimez-le après le test, ou configurez les restrictions d'authentification/IP Webhook avant d'utiliser un point de terminaison public pour des données réelles. Consultez la documentation officielle de test/production du Webhook.

6. Sauvegarder avant de modifier les versions épinglées

Enregistrer un dump PostgreSQL récupérable et le volume de données n8n persistant, .env/clé de chiffrement et fichiers externes requis pour le stockage en dehors de ce serveur. Vérifiez une restauration à l'aide du guide de sauvegarde et de récupération avant de mettre à jour la production. Exemples de commandes :

# Back up the database, encryption key, instance data,
# and files before changing the pinned versions.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# After securing the backup outside this VPS:
docker compose pull
docker compose up -d
docker compose ps

Changer l'épinglé N8N_VERSION seulement après avoir lu les notes de version ; les images du n8n et du coureur doivent avancer ensemble. Ne cours pas docker compose down -v lors de la maintenance de routine, car cela supprime les volumes de données nommés. PostgreSQL les modifications de version majeure nécessitent une mise à niveau de la base de données ou un plan de vidage/restauration ; le remplacement de l'image Postgres 18 par une balise majeure différente n'est pas une migration automatique.

Références faisant autorité : n8n Docker Guide de composition, n8n configuration du proxy inverse/webhook et notes de déploiement officielles PostgreSQL. Aucune référence d'infrastructure ou fonctionnalité préinstallée spécifique au fournisseur n'est supposée.

PANNES COURANTES

Pourquoi une installation n8n Docker fonctionne localement mais échoue en production

Mauvaise URL du webhook

Les rappels pointent vers localhost, HTTP ou un nom d'hôte interne au lieu de l'origine publique HTTPS.

Persistance manquante

L’état de l’application ou de la base de données disparaît lorsqu’un conteneur est recréé.

Clé de cryptage perdue

Les informations d'identification enregistrées deviennent inutilisables après la reconstruction, car la nouvelle instance utilise une clé différente.

Port de base de données publique

Le PostgreSQL est exposé inutilement même si seul le n8n doit l'atteindre.

VÉRIFICATION POST-DÉPLOIEMENT

Vérifiez l'état de santé avant de connecter de vrais flux de travail

Vérifier l'état du conteneur

Courir docker compose ps et confirmez que les services d'application et de base de données fonctionnent comme prévu avant de traiter le déploiement comme sain.

Vérifier le critère de santé n8n

Avec l'exemple Compose ci-dessus, le port 5678 n'est pas publié sur l'hôte. Vérifiez le point de terminaison public avec curl -fsS https://n8n.example.com/healthz après avoir changé le nom d'hôte, et utilisez docker compose ps plus les journaux de service si HTTPS ou si la base de données n'est pas prête.

Épingler les versions de l'application

Ne considérez pas une mise à jour d’image flottante non vérifiée comme une stratégie de maintenance. Enregistrez la version n8n que vous exécutez, lisez les notes de version et sauvegardez avant de la modifier.

Ne remplacez pas les versions majeures PostgreSQL

Changer uniquement la balise d'image majeure de Postgres peut rendre un répertoire de données existant incompatible. Sauvegardez et suivez la procédure de mise à niveau de la base de données au lieu de supposer que la récréation du conteneur effectue une migration de version majeure.

FAQ

Installer le n8n avec le Docker : questions courantes

Le n8n a-t-il besoin du PostgreSQL lors de l'utilisation du Docker ?

Le Docker ne nécessite pas le PostgreSQL, et les petits déploiements peuvent utiliser le SQLite. Pour un déploiement VPS orienté production, PostgreSQL fournit une base de base de données plus solide et prend en charge la mise à l'échelle ultérieure en mode file d'attente.

Pourquoi conserver un volume n8n persistant si PostgreSQL stocke des données ?

Le répertoire n8n persistant peut contenir l'état et la configuration importants de l'instance. Conservez-le conformément à la conception du déploiement au lieu de supposer que la base de données est le seul actif de récupération.

Pourquoi mon webhook affiche-t-il localhost ?

L'adresse interne du conteneur diffère de l'origine publique. Configurez le nom d'hôte externe, le protocole et l'URL du webhook, et assurez-vous que le proxy inverse transmet les en-têtes requis.

Le port 5678 doit-il être public ?

Pour un déploiement de production normal derrière un proxy inverse, exposez HTTPS au niveau du proxy et conservez le port d'application n8n interne, sauf s'il existe une raison opérationnelle spécifique de ne pas le faire.

Ai-je besoin du Redis ?

Pas pour un déploiement Docker standard à instance unique. Le Redis devient pertinent lorsque vous passez délibérément en mode file d'attente et aux travailleurs.

Les exécuteurs de tâches n8n externes sont-ils les mêmes que les travailleurs en mode file d'attente ?

Les exécuteurs de tâches externes exécutent le code de tâche pris en charge séparément du processus principal n8n et utilisent un jeton d'authentification partagé. Le mode file d'attente Redis distribue les exécutions de flux de travail et a ses propres exigences en matière d'infrastructure. Cet exemple montre un exécuteur de tâches externe, et non le mode file d'attente Redis. Faites correspondre la version de l'image du coureur à la version n8n.
