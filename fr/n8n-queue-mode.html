MISE À L'ÉCHELLE

n8n Mode file d'attente

Le mode file d'attente sépare l'exécution du workflow du processus n8n principal. L'instance principale reçoit des déclencheurs et crée des exécutions, Redis coordonne la file d'attente, les travailleurs exécutent les tâches et PostgreSQL stocke le flux de travail partagé et les données d'exécution.

DÉCISION RAPIDE

Avez-vous réellement besoin du mode file d’attente ?

Restez en mode normal lorsque

Une seule instance gère confortablement les pics d'exécutions et les CPU, RAM et la latence d'exécution restent stables. Le mode file d'attente ajoute les composants dont vous n'avez pas encore besoin.

Envisagez le mode file d'attente lorsque

Les exécutions parallèles soutenues créent des conflits, la latence d'exécution augmente sous la charge ou vous devez ajouter de la capacité d'exécution en exécutant plusieurs nœuds de calcul.

Échelle verticale d'abord lorsque

Le goulot d'étranglement est tout simplement insuffisant CPU ou RAM et une instance plus grande peut toujours répondre proprement à la charge de travail.

Mesurer avant de changer d'architecture

Utilisez la concurrence de pointe, les CPU, RAM, la durée d'exécution, la profondeur de la file d'attente et la pression de la base de données pour justifier le déplacement.

ARCHITECTURE

Comment fonctionne le mode file d'attente n8n

1 · PrincipalReçoit les minuteurs, les webhooks et les demandes de flux de travail et crée une exécution au lieu d'effectuer l'exécution de production elle-même.
2 · RedisAgit en tant que courtier de messages. Il conserve les messages d'exécution en attente afin que le prochain travailleur disponible puisse réclamer un travail.
3 · TravailleurReçoit l'ID d'exécution, charge les données du flux de travail à partir de la base de données partagée, exécute le flux de travail et réécrit le résultat.
4 · PostgreSQLFournit des données persistantes partagées sur le flux de travail et l’exécution. Le mode de file d'attente distribuée n'est pas pris en charge sur SQLite.

EXIGENCES DE BASE

Ce dont chaque déploiement en mode file d'attente a besoin

Redis

Tous les processus principaux et de travail nécessitent un accès fiable au service Redis utilisé pour la coordination de la file d'attente.

PostgreSQL

Le principal et les travailleurs doivent partager la base de données. Le mode file d'attente est une architecture distribuée et ne doit pas être conçu autour du SQLite.

Configuration n8n correspondante

Le principal et les travailleurs doivent exécuter le mode file d'attente et partager la configuration nécessaire pour accéder aux Redis, PostgreSQL et aux informations d'identification cryptées.

Capacité des travailleurs

Les travailleurs ont besoin de suffisamment de CPU et RAM pour les flux de travail qu'ils exécutent. L'ajout de processus ne supprime pas le coût en ressources de chaque exécution.

Activez le mode file d'attente sur une pile auto-hébergée existante. Confirmez d'abord que le service principal n8n et chaque travailleur peuvent accéder à la même base de données PostgreSQL et Redis sur un réseau privé. Ensemble EXECUTIONS_MODE=queue sur les principaux et les travailleurs, et l'approvisionnement QUEUE_BULL_REDIS_HOST=redis et QUEUE_BULL_REDIS_PORT=6379 quand redis est le nom réel de votre service Compose. Utiliser DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres et correspondant DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER et DB_POSTGRESDB_PASSWORD sur chaque processus ; remplacez les exemples de noms de services par les vôtres. Fournir l'existant exact N8N_ENCRYPTION_KEY à eux tous. Ne publiez jamais les ports hôtes Redis ou PostgreSQL simplement pour connecter des conteneurs sur le même réseau Compose.

Lancez un exécuteur, pas un deuxième éditeur. Ajoutez un service de travail n8n en utilisant la même version d'image n8n épinglée et les mêmes paramètres partagés comme principal, mais exécutez-le avec le worker commande. Si vous avez nommé ce service n8n-worker, commence par docker compose up -d n8n-worker. Après avoir confirmé l'exécution réelle sur un travailleur, vous pouvez utiliser docker compose up -d --scale n8n-worker=2 pour démarrer un deuxième travailleur de ce service. Il s'agit d'ajouts à un existant correctement configuré Composez la pile, pas un fichier d'installation autonome ; conservez vos volumes persistants existants, HTTPS proxy, secrets et sauvegardes.

Fragment de composition en mode file d'attente pour une pile existante. Fusionnez l'exemple ci-dessous dans votre compose.yaml; c'est pas un déploiement autonome complet. Cela suppose que vous disposez déjà d'un postgres et n8n services, un existant N8N_VERSION épingler dans votre environnement et le vôtre protégé POSTGRES_PASSWORD et originale N8N_ENCRYPTION_KEY. Faites correspondre ses noms, volumes, base de données et version n8n au projet existant. Ajoutez les paramètres Redis du mode file d'attente et EXECUTIONS_MODE=queue au service principal existant également, comme décrit ci-dessus.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Aucun port hôte n'est publié pour Redis ou pour le travailleur dans ce fragment. Redis La persistance en ajout uniquement est une couche de récupération supplémentaire, pas un substitut aux sauvegardes hors serveur. Conservez le HTTPS existant et la configuration d'authentification inchangés. Pour les nœuds Code nécessitant des exécuteurs de tâches externes, configurez séparément les processus d'exécution pour votre déploiement de nœuds de calcul ; le mode file d'attente lui-même ne remplace pas les exécuteurs de tâches.

Conversion d'une instance SQLite existante ? Ne changez pas simplement DB_TYPE et commencez avec une base de données PostgreSQL vide : cela ne migre pas les anciens flux de travail et informations d'identification. Avant tout basculement, sauvegardez la base de données source, persistante .n8n répertoire et clé de cryptage originale ; utilisez une procédure d'exportation/importation ou de migration n8n prise en charge, puis vérifiez les flux de travail et les informations d'identification chiffrées sur une cible distincte. Conservez les fichiers d'origine pour la restauration et utilisez le guide de sauvegarde et de restauration lié ci-dessous pour la préparation à la récupération. Ne jamais supprimer database.sqlite comme raccourci.

CONCURRENCE DES TRAVAILLEURS

Les travailleurs évoluent à la fois en nombre et en emplois par travailleur

Chaque travailleur peut traiter plusieurs tâches simultanément. La concurrence d'accès par défaut actuelle du n8n est 10 et sa documentation recommande une concurrence d'accès de 5 ou supérieure. Une très faible concurrence combinée à de nombreux nœuds de calcul peut créer des connexions de base de données inutiles et épuiser le pool de connexions à la base de données.

Augmenter la simultanéité lorsque

Un travailleur dispose de CPU et RAM de rechange et les flux de travail attendent principalement des services externes plutôt que de saturer le calcul ou la mémoire.

Ajouter des travailleurs quand

Un processus de travail devient un goulot d'étranglement et la base de données, Redis et l'infrastructure ont la capacité d'une exécution plus parallèle.

Réduire la simultanéité lorsque

Les flux de travail individuels sont gourmands en mémoire ou en CPU et les tâches parallèles provoquent des conflits, une pression OOM ou des temps d'exécution instables.

Regarder PostgreSQL

Plus de travailleurs et plus de concurrence augmentent l'activité des bases de données. La mise à l'échelle de la capacité d'exécution sans capacité de base de données peut déplacer le goulot d'étranglement plutôt que de le supprimer.

Sachez quelle limite de concurrence s’applique réellement. Un travailleur peut commencer à utiliser n8n worker --concurrency=5, ou la commande de travail équivalente dans votre service Compose. Si N8N_CONCURRENCY_PRODUCTION_LIMIT est explicitement défini sur une valeur autre que -1, ce paramètre est prioritaire en mode file d'attente ; sinon le n8n utilise le --concurrency valeur ou sa valeur par défaut de 10. Ne multipliez pas le nombre de travailleurs par une valeur par défaut nominale et appelez cela un débit garanti : la capacité réelle dépend de la durée de la tâche, du CPU, de la mémoire, des API externes et des connexions PostgreSQL.

WEBHOOKS

Le mode file d'attente peut ajouter une latence de transfert d'exécution

Le processus principal ou webhook reçoit la requête HTTP, mais un travailleur effectue l'exécution du workflow. Ce transfert via le Redis ajoute des frais généraux. Pour les webhooks sensibles à la latence, mesurez le temps de réponse de bout en bout plutôt que de supposer que davantage de travailleurs effectuent automatiquement chaque demande plus rapidement.

RecevoirLe processus principal/webhook accepte la demande.
File d'attenteL'exécution est confiée au Redis.
ExécuterUn travailleur disponible exécute le flux de travail.
RépondreLe résultat est relayé via le chemin de file d'attente lorsque cela est nécessaire.

Acheminez le trafic des webhooks vers le bon processus. Avec dédié n8n webhook processeurs derrière un proxy inverse ou un équilibreur de charge, acheminent les chemins de production /webhook/* et /webhook-waiting/* aux processeurs webhook ; garder /webhook-test/*, éditeur et requêtes API sur main. Ne placez pas main dans le pool d'équilibrage de charge du webhook de production, sauf si vous acceptez délibérément cette charge de travail supplémentaire. Un Répondre au Webhook Le workflow peut faire attendre le client jusqu'à ce que le travailleur termine et renvoie sa réponse, donc le mode file d'attente n'est pas une promesse de réponses instantanées HTTP ou de zéro délai d'attente. Testez le comportement réel des rappels et des réponses externes avant de changer de trafic.

DONNÉES BINAIRES

Ne négligez pas le stockage partagé

Limitation du système de fichiers

Le mode file d'attente ne prend pas en charge le stockage de données binaires du système de fichiers en tant que modèle de persistance partagée pour les nœuds de calcul distribués.

Stockage binaire externe

Lorsque les flux de travail doivent conserver des données binaires sur des nœuds de travail distribués, utilisez une conception de stockage à laquelle chaque instance requise peut accéder, comme le stockage d'objets externes pris en charge.

Réponses de webhooks volumineux

Les réponses des webhooks des travailleurs retournent vers le processus de réception. Les corps de réponse volumineux peuvent augmenter la pression de la mémoire Redis et nécessiter une configuration délibérée du stockage des réponses.

Planifier avant de répartir les travailleurs

Une charge de travail qui dépend fortement des fichiers locaux doit être repensée pour une persistance partagée avant que les travailleurs ne soient répartis sur les machines.

Grande limite de réponse du webhook. La documentation actuelle n8n donne N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX un défaut de 64 MiB pour la réponse d'un travailleur renvoyée via la file d'attente. Redis peut contenir plusieurs copies en vol, donc prévoyez environ 1.5 fois la taille de réponse dans la mémoire Redis par grande réponse simultanée. Sans déchargement, une réponse surdimensionnée échoue au lieu de devenir comme par magie plus rapide en ajoutant des travailleurs.

Limites de version et de licence. À partir du n8n 2.34.0, les travailleurs peuvent utiliser N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true pour décharger les corps de réponse de webhook surdimensionnés vers un stockage binaire partagé lisible, mais d'abord mettre à niveau chaque processeur principal et webhook au 2.34.0 ou plus tard. Les sélectionnés N8N_DEFAULT_BINARY_DATA_MODE doit réellement stocker des données et être lisible par tous les processus participants. Le stockage binaire externe S3 et Azure nécessite un auto-hébergé valide Entreprise ou entreprise permis; ne présumez pas que Community Edition peut les activer. Le database le mode binaire peut décharger une réponse surdimensionnée sans stockage externe payant, mais l'instance principale charge l'intégralité du corps stocké en mémoire et le stockage de base de données a sa propre limite de taille de fichier. Pour déchargement du corps de réponse spécifiquement, n8n décrit également un partage filesystem option lorsque chaque instance monte le même disque, mais ne recommande explicitement pas cette disposition. Ne confondez pas ce chemin de déchargement spécial avec la prise en charge des données binaires persistantes basées sur le système de fichiers dans un déploiement en mode file d'attente distribué. Vérifiez votre édition, votre version et votre configuration de stockage avant d'activer le déchargement.

SURVEILLANCE

Sachez si la file d'attente aide

Profondeur de la file d'attente

Une file d’attente qui croît plus rapidement que les travailleurs ne la vident indique une capacité d’exécution insuffisante ou un goulot d’étranglement en aval.

Travailleur CPU & RAM

Mesurez la saturation et les pics de mémoire par travailleur. Les travailleurs inactifs avec une file d’attente croissante indiquent une autre contrainte.

Latence d'exécution

Suivez le délai entre la création d'une exécution et son démarrage réel, et pas seulement l'exécution du workflow lui-même.

Bilans de santé

Les points de terminaison de santé des travailleurs peuvent indiquer si un travailleur est en vie et si sa base de données et ses connexions Redis sont prêtes.

Vérifiez l'exécution sur un travailleur, pas seulement sur un conteneur vert. Avec une pile Compose correctement configurée, vérifiez docker compose ps et docker compose logs --tail=100 n8n-worker (remplacez le nom du service s'il est différent). Exécutez un inoffensif production publiée workflow à l'aide d'un déclencheur planifié ou d'un webhook de test, puis faites correspondre son exécution dans la vue Exécutions du n8n au traitement réel des travailleurs dans les journaux des travailleurs. Un éditeur qui s'ouvre avec succès, un conteneur Redis en cours d'exécution ou une exécution en file d'attente seul le fait pas prouver qu'un travailleur a effectué le travail.

Vérifiez les dépendances et la préparation. Avec des exemples de noms de services par défaut, docker compose exec -T redis redis-cli ping devrait recevoir PONG lorsque l'authentification Redis le permet, et docker compose exec -T postgres pg_isready -U n8n -d n8n vérifie l'état de préparation du PostgreSQL (adapter les informations d'identification et les noms de service). Activer QUEUE_HEALTH_CHECK_ACTIVE=true sur un travailleur lorsque vous avez besoin de son privé /healthz et /healthz/readiness points finaux ; le point final de préparation vérifie la connectivité Redis/base de données. N'exposez pas publiquement ces points de terminaison de travail uniquement pour les surveiller.

Les exécutions manuelles sont un test différent. Par défaut OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, donc l'exécution manuelle d'un workflow dans l'éditeur peut s'exécuter sur main même lorsque le mode file d'attente est correctement configuré. Réglez-le sur true uniquement si vous avez l'intention d'envoyer des exécutions manuelles aux travailleurs et que vous avez vérifié le changement dans un environnement intermédiaire. Les travailleurs en mode file d'attente sont également distincts des exécuteurs de tâches externes n8n, qui ont des exigences de configuration distinctes pour l'exécution du nœud de code.

LIMITE DE HAUTE DISPONIBILITÉ

Le mode file d'attente adapte les exécutions, mais il ne rend pas automatiquement le processus principal hautement disponible

Partager la clé de cryptage

Chaque travailleur doit utiliser le même N8N_ENCRYPTION_KEY comme instance principale afin que les travailleurs puissent déchiffrer les informations d'identification requises par les exécutions de flux de travail.

Gardez les versions alignées

Les processus principaux, webhook et de travail doivent exécuter la même version n8n. Les versions mixtes peuvent créer un comportement incompatible lors des modifications progressives.

Les processeurs Webhook constituent une couche de mise à l'échelle distincte

Lorsque le volume du webhook entrant devient un goulot d'étranglement, les processeurs de webhook dédiés peuvent s'asseoir derrière un équilibreur de charge pendant que les travailleurs gèrent l'exécution. N'ajoutez pas cette couche à moins que le volume de demandes mesuré ne le justifie.

Le multi-main est une fonctionnalité différente

L’exécution de plusieurs processus principaux pour une haute disponibilité n’est pas la même chose qu’un mode file d’attente ordinaire. n8n documente actuellement le multi-main en tant que fonctionnalité d'entreprise auto-hébergée avec des exigences supplémentaires en matière d'équilibrage de charge et de session.

FAQ

Mode file d'attente n8n : questions courantes

Le mode file d'attente n8n nécessite-t-il Redis ?

Oui. Redis est le courtier de messages qui coordonne les exécutions en attente entre l'instance principale et les travailleurs.

Le mode file d'attente peut-il utiliser le SQLite ?

Non pour l'architecture en mode file d'attente distribuée. Le principal et les travailleurs ont besoin d'un accès partagé à la base de données, et n8n documente PostgreSQL comme base de données pour cette configuration.

Combien de travailleurs dois-je exécuter ?

Il n’existe pas de décompte universel. Commencez par mesurer la simultanéité et l'utilisation des travailleurs, puis ajoutez de la capacité tout en surveillant les PostgreSQL, Redis, CPU, RAM et la profondeur de la file d'attente.

Qu'est-ce que la simultanéité des travailleurs n8n ?

Il s'agit du nombre d'emplois qu'un travailleur peut effectuer en parallèle. La valeur par défaut actuelle est 10, et n8n recommande une concurrence de travail de 5 ou plus plutôt que de créer de nombreux travailleurs à faible concurrence.

Dois-je activer le mode file d'attente sur un petit VPS ?

Seulement lorsque la charge de travail le justifie. Un petit déploiement qui fonctionne confortablement comme une seule instance est généralement plus simple à exploiter sans Redis et sans travailleurs séparés.
