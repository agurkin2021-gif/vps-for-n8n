n8n Queue Mode : Redis et workers sans sur-complexifier

Queue Mode n’est pas la première réponse à un n8n lent. Commencez par mesurer CPU, RAM, durée d’exécution et concurrence. Passez à Redis + workers lorsque le goulot vient réellement du nombre d’exécutions simultanées et que vous avez besoin de scale-out.

SERP / INTENT

Les guides expliquent Redis ; peu expliquent quand ne pas l’ajouter

Guides n8n

Décrivent main, Redis et workers, souvent correctement.

Vidéos / blogs

Présentent Queue Mode comme “production scaling”, parfois sans vérifier si une instance simple suffit.

Gap

La concurrence régulière, le pool PostgreSQL, la readiness et les points uniques de panne sont moins couverts.

Décision

Scale-out seulement après mesure : queue depth, latence, CPU/RAM workers, DB connections et Redis.

ARCHITECTURE

Main → Redis → workers ↔ PostgreSQL

Main→Redis→Workers↔PostgreSQL

Le main reçoit timers/webhooks et crée l’exécution. Redis maintient la file. Un worker récupère l’ID, lit les données dans PostgreSQL, exécute le workflow puis écrit le résultat.

NON NÉGOCIABLE

Pré-requis Queue Mode

PostgreSQLBase partagée ; SQLite n’est pas supportée pour le système distribué.
RedisBroker de file accessible au main et aux workers.
Encryption keyLa même clé doit être partagée entre toutes les instances.
Version n8nMain et workers doivent rester cohérents.
Binary dataLe stockage filesystem n’est pas supporté en Queue Mode distribué ; prévoyez un stockage externe adapté si nécessaire.

CONFIG MINIMALE

Variables essentielles

EXECUTIONS_MODE=queue
DB_TYPE=postgresdb
QUEUE_BULL_REDIS_HOST=redis
QUEUE_BULL_REDIS_PORT=6379
N8N_ENCRYPTION_KEY=<même-clé-partout>
n8n worker --concurrency=10

GAP · CONCURRENCE

Workers × concurrence = pression sur PostgreSQL

Le nombre de workers n’est pas une métrique de capacité à lui seul. Chaque worker peut traiter plusieurs exécutions simultanées et ouvrir des connexions à la base. Trop de petits workers à faible concurrence peuvent saturer le pool DB sans améliorer le débit.

Worker concurrency

La valeur par défaut documentée est 10. Commencez proche de cette valeur et mesurez.

DB pool

Surveillez les connexions et la latence PostgreSQL avant d’ajouter davantage de workers.

Global limit

Une limite globale de production peut aussi plafonner le débit total.

Queue depth

Une file qui grandit durablement est un meilleur signal de scale-out qu’un simple pic ponctuel.

MANUAL EXECUTIONS

Pourquoi un test manuel peut donner l’impression que Queue Mode ne marche pas

Selon la configuration, les exécutions manuelles peuvent rester sur le main. Si vous voulez les déléguer aux workers, utilisez le réglage d’offload prévu et vérifiez son comportement dans votre version.

OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=true

HEALTH

Process up ≠ prêt à exécuter

QUEUE_HEALTH_CHECK_ACTIVE=true
/healthz
/healthz/readiness

/healthz indique que le worker répond ; /healthz/readiness vérifie aussi les connexions nécessaires comme DB/Redis. Utilisez readiness pour savoir s’il est réellement prêt à prendre du travail.

WEBHOOKS

Le scale-out ajoute aussi de la latence et du trafic interne

Les webhooks peuvent être reçus par le main ou des webhook processors puis exécutés par workers. Ce saut ajoute un peu d’overhead. Pour les réponses synchrones volumineuses, mesurez aussi l’impact mémoire et Redis.

QUEUE MODE ≠ HA

Multiplier les workers ne supprime pas tous les points uniques de panne

Workers

Ils peuvent être redondants.

Redis

Un Redis unique peut rester un SPOF.

PostgreSQL

Une base unique peut rester un SPOF.

Main

La haute disponibilité du main est une problématique séparée du simple Queue Mode.

MIGRATION

Passer à Queue Mode sans sauter d’étapes

1. MesurerConcurrence, temps d’attente, CPU/RAM et DB.
2. LimiterTestez d’abord le contrôle de concurrence sur une instance simple.
3. BackupCréez un point de retour.
4. PostgreSQLPréparez la base partagée correctement.
5. RedisAjoutez le broker.
6. Un workerValidez avant de multiplier.
7. HealthActivez health/readiness.
8. ScaleAjoutez des workers seulement si la file le justifie.

VPS

Queue Mode coûte plus en complexité qu’en simple RAM

Sur un VPS self-managed comme VDSina, vous pouvez répartir main, Redis, PostgreSQL et workers selon vos besoins, mais l’architecture et sa disponibilité restent sous votre responsabilité. Ne passez pas en Queue Mode uniquement parce que le serveur actuel est “petit”.

FAQ

Questions fréquentes

Redis est-il obligatoire ?

Oui pour Queue Mode, car il transporte la file d’exécutions entre main et workers.

SQLite fonctionne-t-il en Queue Mode distribué ?

Non. Utilisez PostgreSQL partagé.

Queue Mode est-il du HA ?

Non. Il scale les workers ; Redis, PostgreSQL et main demandent une stratégie HA séparée.
