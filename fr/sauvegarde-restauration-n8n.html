BACKUP / RESTORE · 2026

Sauvegarde et restauration n8n : backup complet

Exporter des workflows n’est pas sauvegarder une instance n8n. Une restauration complète doit pouvoir recréer l’instance, la base, les credentials, les fichiers persistants et la clé de chiffrement, puis remettre les workflows en service sans surprise.

SERP FRANÇAIS

Les concurrents parlent souvent de JSON ; le vrai sujet est la reprise complète

Formation Automatisation IA

Très bon protocole récent : base, clé, custom nodes, variables, RPO/RTO et test de restauration.

Selfhostr / Lumivi

Incluent backup dans un guide self-hosted global, mais le restore détaillé reste souvent secondaire.

Blogs Docker

Beaucoup copient volumes et JSON sans distinguer cohérence SQLite, dump PostgreSQL et clé de chiffrement.

Gap réel

Le backup utile est celui qu’on sait restaurer dans un nouvel environnement, pas celui qui “existe quelque part”.

4 NIVEAUX

Workflow export, CLI backup, instance backup et disaster recovery

Export workflow

Pratique pour déplacer ou versionner des workflows. Ne couvre pas toute l’instance.

Export workflows + credentials

Meilleur que le JSON seul, mais ne remplace pas la base, les utilisateurs, l’historique, les variables et la clé.

Backup instance

Dossier .n8n + base externe + données binaires + custom nodes + configuration + clé.

Disaster recovery

Backup hors serveur, RPO/RTO, procédure documentée et test de restauration régulier.

CE QU’IL FAUT SAUVEGARDER

Inventaire minimum

.n8nClé, configuration locale, données importantes de l’instance.
PostgreSQLDump cohérent si la base est externe.
SQLiteArrêtez n8n ou utilisez un snapshot cohérent avant de copier la base.
Binary dataVolumes ou stockage externe utilisés par les exécutions.
Custom nodesPaquets ou dossiers nécessaires à vos workflows.
DéploiementCompose, reverse proxy, variables et secrets — sans stocker les secrets en clair dans Git.

CLÉ DE CHIFFREMENT

Sans la bonne clé, vos credentials peuvent devenir inutilisables

Traitez N8N_ENCRYPTION_KEY comme un secret de reprise. Conservez-la hors du VPS et assurez-vous que l’environnement restauré reprend exactement la même clé avant d’importer ou d’ouvrir les credentials.

RESTORE RUNBOOK

Ordre de restauration

1. InfrastructureVPS, Docker, volumes et réseau.
2. CléRestaurer la clé avant les credentials.
3. BaseRestaurer PostgreSQL ou SQLite de manière cohérente.
4. Données.n8n, binary data, custom nodes et config.
5. DémarrageLancer n8n et vérifier logs/migrations.
6. ValidationLogin, credentials, webhooks, schedules et workflows critiques.

RPO / RTO

Définissez la perte de données et le délai de reprise acceptables

RPO

Combien de minutes ou heures de changements pouvez-vous perdre ?

RTO

Combien de temps l’instance peut-elle rester indisponible ?

3-2-1

Plusieurs copies, supports distincts et au moins une copie hors serveur.

Restore drill

Testez réellement la restauration, idéalement dans un environnement isolé.

AVANT UPDATE

Le meilleur moment pour tester le backup est avant une mise à jour

Avant une upgrade n8n ou PostgreSQL, créez un point de retour vérifié. Une sauvegarde non testée n’est pas un plan de rollback.

INFRASTRUCTURE

Le fournisseur peut protéger le VPS sans connaître votre stack n8n

VDSina reste ici une infrastructure self-managed : le support du serveur n’équivaut pas à une restauration applicative complète de n8n. Votre runbook doit rester sous votre contrôle.

FAQ

Questions fréquentes

Exporter les workflows suffit-il ?

Non. C’est utile pour la portabilité, pas pour restaurer toute l’instance.

Faut-il sauvegarder .n8n avec PostgreSQL ?

Oui. Le dossier contient encore des éléments importants de l’instance.

Comment vérifier un backup ?

Restaurez-le dans un environnement isolé et testez credentials, webhooks, schedules et workflows critiques.
