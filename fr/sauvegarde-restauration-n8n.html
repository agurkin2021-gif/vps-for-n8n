SAUVEGARDE ET RÉCUPÉRATION

n8n Sauvegarde et restauration

Pour sauvegarder et restaurer n8n auto-hébergé, protégez votre base de données SQLite ou un vidage PostgreSQL cohérent, le dossier .n8n persistant et la clé de chiffrement d'origine, la configuration de déploiement et chaque dépendance de fichier binaire ou monté externe. Conservez une copie chiffrée du VPS et testez la récupération sur une instance distincte. Utilisez le flux de travail CLI et les exportations d'informations d'identification pour une récupération sélective ; Les exportations JSON ne constituent pas à elles seules une sauvegarde complète du serveur.

LISTE DE CONTRÔLE RAPIDE

Ce qu'une sauvegarde n8n doit protéger

Base de données

Sauvegardez la base de données PostgreSQL ou le fichier de base de données SQLite utilisé par l'instance. La base de données contient l'état de base n8n tel que les flux de travail, les informations d'identification et les données d'exécution.

Clé de chiffrement

Conservez la clé de cryptage n8n exacte séparément et en toute sécurité. Les informations d'identification chiffrées restaurées dépendent de la même clé.

Fichiers persistants

Incluez le répertoire de données n8n persistant et tous les fichiers montés, le stockage de données binaires ou les actifs de flux de travail sur lesquels repose votre déploiement.

Configuration du déploiement

Conservez les fichiers Compose/configuration et la configuration non secrète nécessaires à la reconstruction de la pile. Protégez les secrets avec des contrôles d'accès appropriés.

DEUX NIVEAUX DE SAUVEGARDE

Exportation logique ou reprise après sinistre complète

Exportation du flux de travail et des informations d'identification

Les exportations n8n CLI sont utiles pour la migration, les copies de flux de travail versionnées et la restauration sélective. Les informations d'identification peuvent être exportées sous forme cryptée et importées ultérieurement avec la clé de cryptage correspondante. Pour récupérer un seul workflow, utilisez le menu à trois points de l'éditeur de workflow pour télécharger son JSON, puis Importer depuis un fichier dans un nouveau workflow de révision ou une instance isolée. Vérifiez les informations d'identification, les ID de workflow et les paramètres de nœud avant de remplacer un workflow en direct : la restauration du workflow JSON ne restaure pas l'intégralité du serveur.

Exportation d'entité

Le CLI peut exporter des entités de base de données pour déplacer des données entre les types de bases de données pris en charge. Les tables d'historique d'exécution sont facultatives car elles peuvent être très volumineuses.

Récupération complète de l'instance

Dans un scénario de serveur mort, protégez la base de données réelle, la clé de chiffrement, les données persistantes et les dépendances de déploiement. Ne présumez pas qu’une exportation JSON de workflow reconstruit l’intégralité de l’instance.

Instantané du fournisseur

Un instantané VPS est utile en tant que couche de récupération supplémentaire, mais il ne doit pas être la seule copie et ne doit pas remplacer une sauvegarde d'application/de base de données vérifiée de manière indépendante.

BASE DE DONNÉES

Sauvegardez la base de données de manière cohérente

PostgreSQL

Utilisez une méthode de sauvegarde PostgreSQL cohérente et stockez la sauvegarde résultante loin du VPS. Une copie de base de données sur le même disque défaillant ne constitue pas une reprise après sinistre.

SQLite

Si le déploiement utilise SQLite, protégez le fichier de base de données du répertoire de données persistant n8n. Évitez de copier une base de données dans un état dangereux alors qu'elle est en cours de modification.

Historique d'exécution

Décidez si les données d’exécution historiques font partie de votre objectif de récupération. Cela peut rendre les sauvegardes considérablement plus volumineuses, c'est pourquoi les exigences de conservation et de conformité doivent guider le choix.

Version de la base de données

Enregistrez le moteur de base de données et la version utilisée par le déploiement source afin qu'un environnement de récupération puisse être préparé de manière compatible.

PostgreSQL sur un Docker Composer VPS. Si le service PostgreSQL est nommé postgres et sa base de données/utilisateur sont tous deux n8n, la commande suivante crée un vidage cohérent au format personnalisé PostgreSQL sur l'hôte. Vérifiez votre fichier Compose actuel avant de l'exécuter et ajustez les informations d'identification de la base de données et les noms de service. pg_dump peut produire un instantané logiquement cohérent pendant l'exécution du PostgreSQL ; ça fait pas sauvegarder le séparé .n8n dossier utilisateur ou données binaires externes.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

La vérification de la liste d'archives détecte des problèmes de format évidents mais ne prouve pas que les données peuvent être restaurées. Stockez une copie chiffrée hors serveur et répétez une restauration. Utilisez la documentation officielle PostgreSQL pg_dump pour les options spécifiques à la base de données.

SQLite au Docker. Pour le déploiement SQLite par défaut, database.sqlite et la configuration de clé de chiffrement générée se trouve dans le fichier persistant .n8n dossier (normalement monté sur /home/node/.n8n). Ne traitez jamais une simple copie dynamique du SQLite comme cohérente. Arrêtez n8n et les autres rédacteurs de bases de données avant de copier le dossier, ou utilisez le mécanisme de sauvegarde en ligne pris en charge par SQLite lorsque l'interruption est impossible :

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Il s'agit de commandes illustrant le service et le chemin indiqués, et non une disposition de volume universelle. Le dossier copié se trouve initialement toujours au même VPS ; transférer et protéger hors serveur. Lorsque des agents de file d'attente ou d'autres rédacteurs existent, mettez-les également au repos et suivez leur conception de déploiement réelle. Les directives actuelles de sauvegarde complète du n8n documentent l'exigence de cohérence du SQLite.

Restauration du dossier SQLite par défaut sur une cible propre : arrêtez d'abord le service n8n et tous les rédacteurs de bases de données. Une fois qu'un conteneur de services n8n compatible et son volume de destination existent, copiez le fichier sauvegardé .n8n contenu retour dans le même répertoire persistant. Cela écrase les fichiers cibles, ne l'exécutez donc pas sur une instance contenant des données que vous devez conserver :

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker peut copier vers des conteneurs arrêtés, mais la propriété de la destination peut différer de l'original ; assurez-vous que la configuration restaurée et le fichier de base de données sont lisibles et inscriptibles par le processus n8n avant de le démarrer. Si votre configuration réelle de Compose utilise un chemin ou un montage de liaison différent, adaptez la copie en conséquence. Docker Rédiger la copie de référence. La restauration d'un dossier n8n seule ne suffit pas pour les déploiements qui utilisent une base de données PostgreSQL distincte.

SECRET CRITIQUE

La clé de cryptage fait partie de la récupération

n8n chiffre les informations d'identification stockées avec une clé de chiffrement d'instance. Une base de données ou une exportation d'identifiants chiffrés sans la clé correspondante peut empêcher les flux de travail restaurés d'utiliser leurs informations d'identification enregistrées.

Si vous définissez N8N_ENCRYPTION_KEY, restaurez ce secret exact. Sinon, la clé générée est stockée dans le fichier persistant .n8n/config : protégez cette configuration lors de la sauvegarde ou de la reconstruction. Stockez les clés de récupération en toute sécurité en dehors du VPS. En mode file d'attente, tous les processus principaux et de travail doivent utiliser la même clé.

FaireConservez une copie protégée de la clé exacte utilisée par la production.
FaireVérifiez que l'environnement de récupération utilise cette clé avant de tester les informations d'identification.
NeFiez-vous à une clé nouvellement générée après la reconstruction du serveur.
NeEnregistrez la clé dans un référentiel public ou stockez-la à côté d’une sauvegarde non protégée.

FICHIERS ET DONNÉES BINAIRES

La sauvegarde de la base de données peut ne pas couvrir toutes les dépendances du flux de travail

Données .n8n persistantes

Localisez et conservez le dossier utilisateur .n8n réel, pas seulement l'image du conteneur. Dans un déploiement Docker typique, il est monté sur /home/node/.n8n ; en dehors du Docker, la valeur par défaut est ~/.n8n. Si N8N_USER_FOLDER est configuré, n8n crée .n8n dans ce répertoire parent spécifié. Incluez sa clé de configuration et toutes les données locales SQLite, binaires ou d'exécution du système de fichiers que votre installation utilise.

Fichiers de workflow montés

Si les flux de travail lisent ou écrivent des répertoires montés sur l'hôte, sauvegardez ces répertoires séparément. La restauration du n8n sans eux peut interrompre des flux de travail autrement valides.

Données binaires

Identifiez le mode de stockage et restaurez chaque dépendance externe. Les données binaires ou d'exécution basées sur le système de fichiers peuvent résider dans .n8n ou dans un répertoire personnalisé ; S3/Azure Blob ou tout autre stockage externe configuré nécessite ses propres paramètres de copie et d'accès récupérables. Un vidage de base de données ne peut à lui seul remplacer ces fichiers.

Nœuds communautaires

Enregistrez les packages et les versions de la communauté et sauvegardez tous les répertoires de nœuds personnalisés supplémentaires configurés via N8N_CUSTOM_EXTENSIONS. Ces répertoires peuvent se trouver à l'extérieur du .n8n ; une restauration de base de données et de dossiers utilisateur à elle seule peut toujours rendre les flux de travail de nœuds personnalisés inutilisables.

STRATÉGIE HORS SERVEUR

Une sauvegarde sur le même VPS n'est qu'une copie locale

Copie localeUtile pour une restauration rapide, mais vulnérable à la perte du serveur, aux pannes de disque et aux erreurs destructrices.
Copie hors serveurConserver au moins une sauvegarde en stockage indépendant de la production VPS.
Copies versionnéesConservez plusieurs points de récupération afin qu'une corruption ou une mauvaise modification n'écrase pas la seule sauvegarde utilisable.
Contrôle d'accèsLes sauvegardes peuvent contenir des informations d'identification, une logique de flux de travail et des données commerciales sensibles. Chiffrez-les et limitez-les de manière appropriée.
SurveillanceAlerte lorsque les sauvegardes planifiées échouent ou cessent de produire de nouveaux points de récupération.

Rendez le calendrier mesurable. Enregistrez l'horodatage de chaque sauvegarde réussie, l'achèvement du transfert, la taille du fichier, la version de la base de données source, l'emplacement de récupération de la clé de chiffrement et le dernier test de restauration réussi. Alerte sur les fichiers manquants, défaillants ou vides de manière inattendue. Cryptez les archives de sauvegarde avant de les envoyer hors du VPS et restreignez l'accès aux secrets de récupération. Plusieurs points de récupération datés protègent contre la découverte de corruption uniquement après que la copie la plus récente a écrasé la dernière copie saine.

Par exemple, si vous pouvez tolérer au maximum six heures de perte de modifications, une planification de sauvegarde réussie de six heures est un point de départ et non une garantie : les tâches échouées et la réplication hors serveur retardée peuvent augmenter les pertes réelles. Définissez la cadence de conservation et de restauration en fonction de vos propres RPO/RTO et exigences en matière de données, plutôt que de supposer une politique universelle 7-jour ou 30-jour.

Rétablir l'ordre

Récupérer dans une séquence contrôlée

1 · PréparerMettez en place un serveur, une base de données et un environnement de conteneur/d'exécution compatibles.
2 · Restaurer les secretsConfigurez la clé de chiffrement n8n d'origine et les secrets de déploiement requis en toute sécurité.
3 · Restaurer la base de donnéesRécupérez PostgreSQL ou SQLite et vérifiez que n8n peut se connecter aux données attendues.
4 · Restaurer les fichiersRécupérez les répertoires persistants, les données binaires et les actifs de flux de travail montés.
5 · Début n8nAffichez l'application avec la configuration attendue du nom d'hôte, de la base de données et de l'environnement.
6 · ValiderConfirmez le chargement des utilisateurs, des flux de travail et des informations d’identification, puis exécutez des flux de travail représentatifs et des chemins de webhook.

PostgreSQL Exemple de reprise après sinistre : sur un cible de restauration séparée et propre qui a déjà le rôle de base de données correct et un vide n8n base de données, démarrer seulement PostgreSQL. Attendez qu'il soit sain avant d'importer : docker compose up -d seul peut revenir pendant que PostgreSQL est encore en cours d'initialisation, donc un suivant pg_restore peut échouer. L'exemple utilise --wait sur une installation Compose moderne et vérifie indépendamment pg_isready. Configurez un contrôle de santé PostgreSQL approprié pour une attente fiable, ou confirmez explicitement l'état de préparation avant de continuer. Ne pointez pas cette commande sur une base de données de production remplie et ne démarrez pas le n8n avant la base de données et sa correspondance .n8n les clés/données sont restaurées.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

La destination doit avoir une version PostgreSQL compatible, des privilèges de rôle, des extensions et une configuration n8n originale. Restaurer .n8n à son volume persistant correct ou à un montage lié à l'aide de votre mécanisme de sauvegarde, en préservant la propriété et les autorisations. Restaurez les fichiers binaires externes, les extensions personnalisées, la configuration de Compose et des secrets, puis démarrez n8n sur une version compatible et vérifiez ses journaux. La restauration seule de la base de données ne récupère pas la clé : un déploiement PostgreSQL conserve la clé dans .n8n/config sauf si vous avez explicitement configuré N8N_ENCRYPTION_KEY. Référence pg_restore · n8n séquence de restauration d'instance complète.

TEST DE RESTAURATION

Une sauvegarde n'est pas prouvée tant que la restauration n'a pas réussi

Test sur un environnement propre

Un véritable exercice devrait prouver que la sauvegarde peut reconstruire une instance sans s'appuyer sur des fichiers non déclarés laissés sur le serveur de production.

Vérifier les informations d'identification

Ouvrir un workflow ne suffit pas. Confirmez que les informations d'identification chiffrées restaurées sont effectivement déchiffrées et authentifiées avec succès.

Exécutez des flux de travail représentatifs

Testez les workflows qui dépendent de webhooks, d'API externes, de fichiers montés et de nœuds de communauté plutôt que de valider uniquement une automatisation triviale.

Mesurer le temps de récupération

Enregistrez la durée de la restauration et les étapes manuelles restantes. Cela convertit une sauvegarde supposée en une procédure de récupération opérationnelle.

Exercice de restauration vérifié : SQLite et PostgreSQL

Environnement de test : n8n 2.42.5 dans des conteneurs Docker isolés sur un coureur d'actions GitHub jetable, en utilisant un flux de travail synthétique à deux nœuds. Ces contrôles ont eu lieu 8 octobre 2026, pas sur le serveur n8n d'un client ou de production.

Exécutez un exercice distinct pour chaque dépendance que vous utilisez réellement.

Comment reproduire : utilisez une installation n8n jetable, créez un flux de travail inoffensif à deux nœuds, effectuez la base de données applicable ainsi que la sauvegarde du dossier persistant, restaurez sur un volume ou une base de données propre, puis vérifiez les nœuds, les connexions et l'exécution réelle du flux de travail restauré. Sur le système de production, vérifiez également les informations d'identification chiffrées, les webhooks et les fichiers externes avant de déclarer une reprise après sinistre prouvée.

Liste de contrôle d’acceptation de l’exercice de restauration : utiliser un domaine/environnement isolé ; vérifiez que les utilisateurs et les flux de travail sont présents, qu'un identifiant crypté existant s'authentifie sans nouvelle saisie, qu'un webhook de production appelle le flux de travail restauré prévu, que les fichiers montés et les pièces jointes binaires restent lisibles et que les intégrations avec les nœuds de communauté requis se chargent. Confirmez l’âge de la sauvegarde, les temps d’arrêt mesurés et l’accessibilité hors serveur. Si une vérification essentielle échoue, marquez ce point de récupération non vérifié plutôt que de signaler la sauvegarde comme terminée.

CLI LIMITES DE SAUVEGARDE

Sachez exactement quels flux de travail et les exportations d'informations d'identification ne restaurent pas

Les exportations CLI ne sont pas une sauvegarde d'instance complète

Les exportations de sauvegarde de flux de travail et d'informations d'identification n'incluent pas les utilisateurs et les rôles, l'historique et les journaux d'exécution, les variables ou les paramètres d'instance tels que la clé de chiffrement.

La restauration d'une nouvelle instance nécessite un propriétaire

Sur une instance propre, terminez la configuration du propriétaire avant d'importer les informations d'identification. Les restaurations multi-utilisateurs ou par projet peuvent également nécessiter l'affectation correcte de l'utilisateur ou du projet.

Les identifiants importés peuvent remplacer les éléments existants

Les exportations de flux de travail et d’informations d’identification conservent leurs identifiants d’origine. L'importation dans une instance contenant déjà les mêmes ID peut remplacer ces éléments existants.

Publier délibérément les workflows importés

Les importations CLI laissent normalement les workflows inactifs. Au n8n 2.x, vérifiez l'état publié de chaque workflow importé et publiez uniquement les workflows que vous avez l'intention d'exécuter ; le serveur auto-hébergé CLI prend également en charge n8n publish:workflow --id=YOUR_WORKFLOW_ID. Lorsque le n8n est en cours d'exécution, les changements d'état de publication/dépublication du serveur CLI ne prennent effet qu'après le redémarrage du n8n. Redémarrez avant de vérifier les déclencheurs planifiés et les webhooks de production ou de changer de trafic.

Exemple d'exportation groupée pour Docker Compose : si votre service n8n est nommé n8n, vous pouvez exécuter les sauvegardes officielles CLI ci-dessous. Le chemin de sortie est délibérément à l'intérieur de son fichier persistant monté. .n8n répertoire, car des répertoires arbitraires à l’intérieur d’un conteneur peuvent disparaître lors de sa recréation. Confirmez que le répertoire est accessible en écriture par l'utilisateur du conteneur n8n. Conservez le flux de travail et les informations d'identification JSON dans répertoires séparés—n8n documente un problème d'importation lorsque les deux types partagent un répertoire.

n8n 2.x brouillon versus sauvegarde publiée : une normale --backup l'exportation du flux de travail capture les brouillons actuels ; celles-ci peuvent différer des versions publiées en production. Pour conserver la version réellement publiée d'un flux de travail particulier, exportez-la séparément à l'aide de docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, après vous être assuré que le dossier de sortie existe et est accessible en écriture. Le CLI peut également exporter une version historique en utilisant --version=VERSION_ID. Conservez ces captures hors serveur avec la sauvegarde complète ; ne supposez pas que le projet JSON enregistre l'état publié en direct.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Le copié ~/n8n-recovery/cli Le répertoire est toujours sur le VPS jusqu'à ce que vous le déplaciez vers un emplacement de sauvegarde sécurisé et indépendant. L'exportation des informations d'identification est chiffrée par défaut et nécessite la clé de chiffrement correspondante lors de l'importation. Évitez d'utiliser --decrypted sauf migration strictement contrôlée : il écrit les secrets en clair. Ne validez jamais les exportations contenant une logique de flux de travail ou des informations d'identification sensibles dans un référentiel GitHub public. Certains modèles tiers de sauvegarde des informations d'identification GitHub exportent délibérément les secrets déchiffrés ; un référentiel privé est une restriction d'accès, pas un cryptage. Inspectez les paramètres d'exportation et les autorisations de stockage réels de chaque modèle, chiffrez les secrets avant le transfert hors serveur et alternez toutes les informations d'identification exposées via un téléchargement de texte brut involontaire.

Exemple d'importation groupée : sur une cible propre, terminez la configuration du propriétaire, fournissez la clé de cryptage d'origine et assurez-vous que les fichiers de sauvegarde enregistrés sont disponibles sur cette récupération VPS. Ce qui suit crée le dossier de destination et copie le workflows/ et credentials/ sous-dossiers de l'hôte dans le conteneur n8n ; adaptez les chemins si la disposition de votre volume Docker diffère :

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Vérifiez la propriété et l'accès au fichier pour l'utilisateur du conteneur n8n. N'importez pas sur une instance de production remplie sans une restauration vérifiée : les ID de flux de travail et d'informations d'identification peuvent écraser les entrées existantes. Puis exécutez :

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Les identifiants importés peuvent remplacer les flux de travail ou les informations d'identification existants ; utilisez une instance de test isolée pour les essais à sec et vérifiez ensuite les informations d'identification et les états d'activation/publication. Dans n8n 2.x, la restauration du brouillon JSON ne prouve pas en soi qu'un workflow a été publié et peut exécuter des déclencheurs planifiés. Sécurité des importations : sur une instance n8n non multi-principale, les déclencheurs cron précédemment actifs peuvent continuer à s'exécuter après l'importation CLI jusqu'au redémarrage de l'instance. Arrêter ou isoler les déclencheurs de production et redémarrer n8n avant d'activer les tâches restaurées ; vérifiez qu’il n’y a pas d’exécution en double. CLI les exportations le font pas contiennent les utilisateurs d'origine, les journaux d'exécution, les variables d'instance ou la clé de chiffrement. --backup ensembles --all --pretty --separate, pas « instance complète ». Sources : guide officiel actuel de sauvegarde/restauration n8n et référence des commandes n8n CLI.

Restauration groupée à partir de GitHub ou de modèles Google Drive : il s'agit d'une alternative pour le workflow JSON uniquement, et non pour la base de données d'instance, les utilisateurs, les valeurs d'identification chiffrées ou la clé de chiffrement. Avant d'exécuter un modèle basé sur API, vérifiez ses n8n API et ses autorisations de stockage, la version de sauvegarde sélectionnée et l'instance cible, s'il met à jour les ID correspondants et recrée les flux de travail supprimés, et ce qu'il fait avec la publication du flux de travail. Tous les modèles ne recréent pas un ID manquant dans la cible ; testez ce scénario de manière isolée avant de vous fier à la restauration automatique.

FAQ

n8n sauvegarde et restauration : questions courantes

L'exportation des workflows est-elle suffisante pour sauvegarder le n8n ?

Les exportations de workflow sont des copies logiques utiles, mais une récupération complète peut également nécessiter des informations d'identification, la clé de chiffrement correspondante, l'état de la base de données, les fichiers persistants et le stockage des données binaires.

Ai-je besoin de la clé de cryptage n8n si je dispose de la base de données ?

Oui, si vous avez besoin que les informations d'identification cryptées stockées dans cette base de données restent utilisables. Conservez la clé originale en toute sécurité.

Dois-je sauvegarder PostgreSQL ou exporter les flux de travail et les informations d'identification ?

En cas de reprise après sinistre, protégez la base de données et la clé de chiffrement. Les exportations logiques sont utiles en tant que couche de migration et de récupération sélective supplémentaire plutôt qu'en remplacement de chaque partie de l'instance.

Un instantané VPS peut-il être ma seule sauvegarde ?

Il est préférable de le traiter comme une seule couche de récupération. Conservez une sauvegarde indépendante hors serveur afin qu'une défaillance d'un fournisseur, d'un compte, d'un serveur ou d'un instantané ne supprime pas tous les points de récupération en même temps.

Comment puis-je savoir si ma sauvegarde fonctionne ?

Restaurez-le dans un environnement de test propre, vérifiez le déchiffrement des informations d'identification et exécutez des flux de travail représentatifs. Un travail de sauvegarde réussi ne prouve pas à lui seul la récupérabilité.

Les sauvegardes de flux de travail GitHub ou Google Drive incluent-elles les secrets d'identification enregistrés ?

Les sauvegardes JSON de workflow uniquement n'incluent pas les valeurs secrètes gérées par le magasin d'informations d'identification du n8n ou la clé de chiffrement de l'instance. Cependant, les JSON exportés peuvent exposer les noms d'informations d'identification, les identifiants et les secrets saisis directement dans les paramètres du nœud, tels que les en-têtes d'authentification. Inspectez et protégez les JSON exportés avant de les télécharger ou de les partager. Pour une récupération complète, sauvegardez la base de données et la clé d'origine, ou utilisez les exportations d'informations d'identification cryptées CLI prises en charge avec une restauration testée. Un modèle GitHub ou Google Drive uniquement axé sur le flux de travail ne constitue pas une reprise après sinistre complète.

OBJECTIFS DE RÉCUPÉRATION

Définir le RPO et le RTO avant un incident

RPO est la perte maximale tolérable des modifications récentes. Mesurez-le à partir du point de récupération utilisable et stocké indépendamment le plus récent ; un travail programmé de six heures n'établit pas de RPO de six heures en cas d'échec des exportations ou des transferts. RTO est la panne maximale tolérable. Mesurez-le lors d'un exercice de restauration propre, y compris la récupération des secrets, la restauration des fichiers externes, la revérification des informations d'identification et la publication des flux de travail récupérés, et pas seulement le démarrage d'un conteneur.

CLÉ DE RÉCUPÉRATION

Recherchez la clé de cryptage d'origine avant de reconstruire

Si la production est définie N8N_ENCRYPTION_KEY, préservez le secret exact de cet environnement. Si ce n’est pas le cas, conservez la clé générée dans le fichier .n8n/config persistant d’origine. Vérifiez quelle source l'instance récupérée utilise réellement avant d'importer les informations d'identification chiffrées ; une clé nouvellement générée ne peut pas déchiffrer les informations d'identification de l'ancienne base de données.
