生產安全

在 VPS 上保護 n8n

為了確保 VPS 上的 n8n 的安全，請將 n8n (5678)、PostgreSQL (5432) 和可選的 Redis (6379) 遠離公共網際網路；使用 HTTPS 反向代理、SSH 密鑰和 MFA，保留您的加密密鑰、驗證 Webhook、限制有風險的工作流程功能並審核已部署的實例。將編輯器與公用 Webhook 路由分開保護。 HTTPS 本身並不能保證連結服務的安全。

公開曝光前的最低安全基線

從可訪問的端口開始，HTTPS，經過驗證的管理訪問，MFA 以及對已保存憑證的保護。在每個傳入的 Webhook 觸發敏感工作之前對其進行身份驗證。更改存取控制後，驗證預期的編輯器和外部整合是否仍然有效，然後執行 n8n 安全審核。

僅 HTTPS

將 n8n 放在正確配置的 TLS 反向代理後面，並為編輯器和Webhook一致使用公共 HTTPS URL。

最少開放埠

僅公開公共流量所需的連接埠。保持 PostgreSQL、Redis 和內部應用程式連接埠遠離公共網際網路。

強化 SSH 安全性

使用基於金鑰的管理，限制可以登入的人員並保持作業系統修補。

保護憑證

保持 n8n 加密密鑰穩定且保密。將環境文件、資料庫存取和備份副本視為敏感資產。

網路邊緣

反向代理、HTTPS 和可信標頭

TLS 終止

使用反向代理人（例如 Nginx、Caddy 或 Traefik）來終止 HTTPS。當代理程式是預期入口點時，重定向普通 HTTP 並避免直接暴露 n8n 應用程式連接埠。

代理配置

當 n8n 在反向代理後面執行時，正確配置代理跳數並傳遞轉送的標頭 n8n 需要重建原始客戶端請求。

安全 cookie

為編輯者提供超過 HTTPS 的服務，以便身分驗證 cookie 保持安全。不要透過削弱 cookie 安全性來解決損壞的 TLS 設定。

Webhook URL

將公用 Webhook URL 設定為外部可存取的 HTTPS 主機名，以便產生的 Webhook 端點不會指向內部容器或 HTTP 位址。

在不破壞 webhook 的情況下保持編輯器的隱私。 在可行的情況下，使用 VPN、可信任 IP 策略或經過驗證的代理來限制管理存取。公共 webhook 接收器和 OAuth 回呼路由可能需要保持可存取；在執行代理規則之前測試受信任的編輯器登入和真實的外部回呼。僅轉送來自受信任代理的客戶端位址標頭，而不是任意請求標頭。

對 Webhook 呼叫者進行身份驗證： 在 Webhook 節點中，如果寄件者支持，請選擇基本、標頭或 JWT 身份驗證，而不是「無」。使用其 IP 授權名單 選項（在適當的情況下），並在整合支援簽章請求的情況下驗證供應商簽章。難以猜測的 URL 不足以進行身份驗證。適當時在代理上應用速率限制，並確認有效的突發未被阻止。官方 Webhook 身份驗證選項。

VPS 硬化

減少伺服器攻擊面

防火牆

預設拒絕未經請求的入站流量，僅允許必須可達的服務。資料庫和 Redis 連接埠通常屬於專用/本地網路。

SSH

優先使用 SSH 密鑰而不是密碼，停用不必要的登入路徑並限制管理存取。應嚴格控制根等效存取。

作業系統更新

修補 Linux 主機和容器運行時。應用程式強化無法彌補暴露或過時的作業系統。

容器暴露

僅發布需要主機存取的連接埠。內部服務應在專用 Docker 網路上進行通信，而不是透過公共介面進行通信。

更改防火牆或 SSH 設定之前檢查： 請先檢查監聽中的連接埠（sudo ss -lntp）、從專案目錄查看 Docker 連接埠發布狀態（docker compose ps），若使用 UFW，則檢查主機防火牆規則（sudo ufw status verbose）。在停用密碼存取之前，請在單獨的會話中驗證您的實際 SSH 連接埠和成功的金鑰登入。已發布的 Docker 連接埠可以繞過UFW規則；僅防火牆狀態頁面並不能證明連接埠 5678 是私有的。檢查真實的外部可及性。 Docker/UFW 警告。

檢查自動 Ubuntu 安全更新，而不是假設它們有效： 檢查 apt-config dump APT::Periodic::Unattended-Upgrade 和日誌 /var/log/unattended-upgrades/unattended-upgrades.log。如果停用無人安全升級， sudo dpkg-reconfigure unattended-upgrades 提供支援的配置對話框。在工作 VPS 上啟用之前，請檢查重新啟動和服務重新啟動行為。 Ubuntu APT 更新可以 不 自動更新 n8n Docker 映像或每個第三方軟體儲存庫。 Ubuntu 自動更新文件。

可選的 SSH 強力監控： Fail2Ban 可以偵測重複失敗的 SSH 登入。如果已安裝並配置為 SSH，請使用以下命令檢查 Fail2Ban jail 狀態 sudo fail2ban-client status sshd 並確認它讀取您實際的 SSH 身份驗證日誌或日誌並匹配配置的連接埠。這補充了 SSH 密鑰和網路限制；它不會取代它們。在未先檢查現有存取權限的情況下，請勿複製固定的 SSH 連接埠或禁止規則。 Ubuntu SSH 強化指導。

資料庫和Redis

保持後端服務的私密性

在典型的 Docker Compose 設定中，相關容器應可透過專用網路（而非主機發佈的連接埠）存取 PostgreSQL 和佇列模式 Redis。驗證與 docker compose ps 5432 和 6379 未公開發布；單獨審查 VPS/雲端防火牆暴露。網路策略不能取代最低權限的資料庫憑證。

PostgreSQL將其綁定到私有介面或容器網絡，除非明確需要遠端存取並獨立保護。
Redis隊列模式 Redis 是基礎設施，而不是公共端點。限制對需要它的 n8n 組件的網路存取。
憑證僅使用具有應用程式所需權限的專用資料庫憑證，並在原始碼控制之外保護它們。
交通當資料庫流量穿過不受信任的網路時，請使用適當的加密傳輸，而不是依賴應用程式級憑證加密。

N8N 的秘密

保護加密金鑰和憑證邊界

加密金鑰

n8n 使用其加密金鑰對儲存的憑證進行加密。在重新啟動和工作期間保留相同的金鑰，並將其與普通應用程式內容分開保護。

環境秘密

不要將密碼、令牌或加密金鑰提交到公共儲存庫。限制對環境文件和部署機密的存取。

使用者存取

僅向受信任的使用者授予編輯器存取權限。工作流程可以連接到敏感系統，並可以處理秘密或執行強大的節點。

憑證範圍

盡可能使用範圍狹窄的服務帳戶和 API 令牌。受損的工作流程不應自動繼承對不相關係統的廣泛存取權。

n8n 要審查的配置： N8N_BLOCK_ENV_ACCESS_IN_NODE=true 防止程式碼節點和表達式存取環境值； N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true 請求對設定檔的僅所有者權限。保留 N8N_ENCRYPTION_KEY 持久且安全備份：n8n 可以在首次啟動時建立隨機金鑰，但遺失它可能會使現有的加密憑證無法使用。不要隨意更換生產密鑰；使用官方支援的輪換程序。阻止環境存取可能會破壞現有集成，因此在生產變更之前進行測試。 n8n 安全變數定義。

工作流程風險

節點可以擴展安全邊界

自託管為工作流程提供了強大的功能。程式碼執行、shell 存取、任意 HTTP 請求和第三方社群節點都會增加風險。停用不需要的功能，並在執行不受信任的工作流程匯入之前對其進行檢查。

使用精確支援的控制項： 配置 NODES_EXCLUDE 具有要停用的 JSON 節點數組，例如 n8n-nodes-base.executeCommand 和 n8n-nodes-base.readWriteFile，如果未使用。一些高風險節點在新版本中已經預設被屏蔽；在更改之前查看實際清單。官方節點排除。

從 n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true 啟用對內部、環回和元資料位址範圍的出站 HTTP 請求的檢查。合法的內部 API 工作流程可能會停止工作；如有必要，僅將您控制的目的地列入允許範圍。將網路分段作為主要防禦措施。對於程式碼節點隔離，請查看外部任務運行程式。 SSRF 保護 · 任務運行程序隔離。

社群節點僅安裝您信任的軟體包；它們在您的 n8n 環境中執行。
風險節點當部署不需要的節點的功能超出預期的工作流程邊界時，請排除這些節點。
SSRF在工作流程不應到達內部或元資料端點的情況下，使用 n8n 的 SSRF 保護和網路控制。
工作流程匯入啟動前檢查匯入的工作流程、憑證、表達式和可執行步驟。

審計和更新

安全是一個運行過程

執行 n8n 安全稽核

官方的 CLI 命令是 n8n audit。如果您的 Docker Compose 服務已命名 n8n，運行 docker compose exec -T n8n n8n audit 在該部署目錄中。查看五個類別：未使用的憑證、有風險的 SQL 查詢模式、檔案系統存取、有風險/社群節點以及實例風險（包括不受保護的 Webhook 和過時的版本）。修復相關發現並重新執行。這不是滲透測試。官方審核指南。

刻意更新

保持 n8n 足夠最新以接收安全修復。查看發行說明並測試重要的升級，而不是讓面向網際網路的實例永久陳舊。

監控認證

觀察意外的存取模式、工作流程變化和故障。當您的操作模型不需要廣泛的公眾可及性時，進一步限制編輯器 UI。

準備回滾和復原

在重大升級之前進行可復原的備份。詳細的備份範圍和復原屬於單獨的復原指南。

最小化敏感執行歷史記錄： 成功運行可以保留客戶資料和令牌。適當時設定 EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, 保留 EXECUTIONS_DATA_PRUNE=true，並選擇一個 EXECUTIONS_DATA_MAX_AGE 以小時為單位，例如 168 （七天）。這些是可配置的範例，而不是法律保留規則。更少的歷史記錄意味著更少的調試和取證資料；正在運行、正在等待或帶註釋的執行可能不會以相同的方式進行修剪。正式執行保留。

疑似遭入侵： 在不破壞證據的前提下限制惡意存取，檢查代理伺服器、主機與 n8n 活動以及遭變更的工作流程，撤銷或輪替可能外洩的上游憑證，修補根本原因，必要時僅從經過測試且可復原的備份進行還原。檢查受影響的 webhook URL、編輯器帳戶和連結的服務；請勿假設 HTTPS、快照或 VPS 購買提供事件回應服務。

帳戶和平台控制

保護編輯者以及 VPS

需要更強的登入保護

當您的版本支援集中策略實施時，為編輯者帳戶啟用雙重認證並實施 MFA 至 n8n 安全性策略。

限制誰可以編輯工作流程

編輯者存取權限是特權存取權限：工作流程可以讀取憑證、呼叫內部系統並執行強大的節點。縮小使用者存取範圍並刪除不再需要的帳戶。

停用您不使用的功能

透過在不必要時停用公共 API 並阻止您的操作模型不需要的高風險節點或功能來減少應用程式攻擊面。

故意使用 SSRF 和秘密控制

對於可以發出任意 HTTP 請求的工作流程，評估 n8n 的 SSRF 保護，並在工作流程代碼、公共儲存庫和廣泛可讀的環境文件中保密。

限制未使用的管理端點： N8N_PUBLIC_API_DISABLED=true 禁用 n8n 公共 REST API，並且 N8N_PUBLIC_API_SWAGGERUI_DISABLED=true 單獨禁用其 API 遊樂場。僅當您的整合不需要這些功能時才執行此操作。停用 REST API 不會驗證工作流程 Webhook URL。對編輯器使用者使用 MFA，僅在您的 n8n 版本支援的情況下使用集中策略。

常見問題

n8n VPS 安全：常見問題

n8n 端口是否應該直接暴露？

當反向代理是公共入口點時，公開代理並將應用程式連接埠保留在其後面，而不是廣泛發布不必要的服務。

PostgreSQL 或 Redis 應該公開嗎？

通常不會。它們應該只能由需要它們的系統存取。公開曝光會增加攻擊面，但不會幫助正常的 n8n 操作。

為什麼 n8n 加密金鑰很重要？

它保護 n8n 儲存的憑證，並且必須在整個部署中保持一致。丟失它可能會阻止復原的資料產生可用的加密憑證。

社區節點安全嗎？

它們以第三方程式碼擴展了 n8n，因此它們應該被視為具有自己的供應鏈和特權風險的軟體依賴項。僅安裝您信任和需要的內容。

HTTPS 是否使自託管 n8n 執行個體安全？

第 HTTPS 條保護運輸。生產安全還需要主機強化、存取控制、私有後端服務、秘密保護、安全工作流程能力、監控和更新。

當生產 webhook 仍然運作時，n8n 編輯器可以是私有的嗎？

是的。受信任的反向代理或 VPN 可以獨立於公共生產 Webhook 和 OAuth 回呼路徑來限制編輯者/管理員存取。每次存取規則變更後測試可信任登入和外部 Webhook 傳送，以避免意外阻止您的整合。

如何驗證傳入的 n8n webhook？

當發送者支援時，在 Webhook 節點中配置基本、標頭或 JWT 身份驗證。您也可以使用 IP 白名單並檢查供應商簽名（如果可用）。不要只依賴看似秘密的路徑，並在請求觸發敏感的 API 操作之前對其進行驗證。
