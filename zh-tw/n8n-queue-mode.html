縮放

n8n 隊列模式

佇列模式將工作流程執行與主 n8n 流程分開。主實例接收觸發器並建立執行，Redis 協調佇列，worker執行作業，PostgreSQL 儲存共用工作流程和執行資料。

快速決策

你真的需要隊列模式嗎？

保持常規模式時

單一實例可以輕鬆處理峰值執行，並且 CPU、RAM 和執行延遲保持穩定。隊列模式新增了您還不需要的元件。

當以下情況時考慮佇列模式

持續的並行執行會產生爭用，負載下執行延遲會增加，或者您需要透過執行多個worker來增加執行能力。

首先垂直縮放

瓶頸只是不夠 CPU 或 RAM，一個更大的實例仍然可以乾淨地滿足工作負載。

更改架構之前先進行測量

使用峰值並發性、CPU、RAM、執行持續時間、隊列深度和資料庫壓力來證明移動的合理性。

大樓

n8n 隊列模式如何運作

1· 主要接收計時器、Webhook 和工作流程請求並建立執行，而不是自行執行生產執行。
2·Redis充當訊息代理。它保存掛起的執行訊息，以便下一個可用的worker 可以領取工作。
3·worker接收執行 ID，從共享資料庫載入工作流程數據，運行工作流程並將結果寫回。
4·PostgreSQL提供共享的持久工作流程和執行資料。 SQLite 不支援分散式佇列模式。

核心要求

每個隊列模式部署需要什麼

Redis

所有主進程和工作進程都需要可靠地存取用於隊列協調的 Redis 服務。

PostgreSQL

Main 和worker 必須共用資料庫。隊列模式是分散式架構，不應該圍繞 SQLite 來設計。

匹配 n8n 配置

Main 和 Worker 必須運行佇列模式並共用存取 Redis、PostgreSQL 和加密憑證所需的設定。

worker容量

worker需要足夠的 CPU 和 RAM 來執行他們執行的工作流程。增加進程並不會消除每次執行的資源成本。

在現有自承載堆疊上啟用佇列模式。 首先確認 n8n 主要服務和每個worker都可以透過專用網路存取相同的 PostgreSQL 資料庫和 Redis。套裝 EXECUTIONS_MODE=queue 主要和worker，以及供應 QUEUE_BULL_REDIS_HOST=redis 和 QUEUE_BULL_REDIS_PORT=6379 當 redis 是您實際的 Compose 服務名稱。使用 DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres 和匹配 DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER 和 DB_POSTGRESDB_PASSWORD 在每個過程中；將範例服務名稱替換為您的服務名稱。提供準確的現有資訊 N8N_ENCRYPTION_KEY 對他們所有人。切勿僅為了連接同一 Compose 網路上的容器而發布 Redis 或 PostgreSQL 主機連接埠。

啟動一個執行器，而不是第二個編輯器。 使用與主要相同的固定 n8n 映像版本和共用設定來新增 n8n 輔助服務，但使用 worker 命令。如果您將該服務命名為 n8n-worker, 開始於 docker compose up -d n8n-worker。確認一個worker 的實際執行後，您可以使用 docker compose up -d --scale n8n-worker=2 從該服務啟動第二個worker。這些是對 現有的正確配置 Compose 堆疊，而不是獨立的安裝文件；保留現有的持久性磁碟區、HTTPS 代理、機密和備份。

佇列模式為現有堆疊編寫片段。 將下面的範例合併到您目前的範例中 compose.yaml;是的 不 完整的獨立部署。它假設你已經擁有持久的、私有的 postgres 和 n8n 服務，現有的 N8N_VERSION 固定在您的環境和您自己的受保護的環境中 POSTGRES_PASSWORD 和原本的 N8N_ENCRYPTION_KEY。將其名稱、磁碟區、資料庫和 n8n 版本與現有項目相符。新增隊列模式 Redis 設定並 EXECUTIONS_MODE=queue 如上所述，也適用於現有的主要服務。

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

沒有為 Redis 或此片段中的工作程序發布主機連接埠。 Redis 僅附加持久性是一個額外的恢復層， 不 離線備份的替代品。保持現有 HTTPS 和身分驗證配置不變。對於需要外部任務運行程序的程式碼節點，請單獨為您的工作部署配置運行程序進程；佇列模式本身並不能取代任務運行器。

轉換現有的 SQLite 實例？ 不要簡單地改變 DB_TYPE 並從空的 PostgreSQL 資料庫開始：這樣做不會遷移舊的工作流程和憑證。在任何切換之前，備份來源資料庫，持久化 .n8n 目錄和原始加密金鑰；使用受支援的 n8n 匯出/匯入或遷移程序，然後在單獨的目標上驗證工作流程和加密憑證。保留原始檔案以進行回滾，並使用下面連結的備份和復原指南進行還原準備。永不刪除 database.sqlite 作為捷徑。

worker並行

worker按數量和每個worker 的工作量進行擴展

每個worker 可以同時處理多個作業。 n8n 目前的預設worker並發度為 10，其文件建議並發度為 5 或更高。非常低的並發性與許多工作線程相結合可能會創建不必要的資料庫連線並耗盡資料庫連線池。

當以下情況時增加並發性：

worker有空閒的 CPU 和 RAM，且工作流程主要等待外部服務，而不是使計算或記憶體飽和。

增加worker時

一個工作流程成為瓶頸，資料庫、Redis 和基礎設施有能力進行更多並行執行。

當以下情況時減少並發

各個工作流程記憶體繁重或 CPU 重，並行作業會導致爭用、OOM 壓力或不穩定的執行時間。

觀看 PostgreSQL

更多的worker和更多的並發性會增加資料庫活動。在沒有資料庫容量的情況下擴展執行容量可以移動而不是消除瓶頸。

了解實際適用的並發限制。 一個worker 可以開始使用 n8n worker --concurrency=5，或 Compose 服務中的等效工作命令。如果 N8N_CONCURRENCY_PRODUCTION_LIMIT 顯式設定為除 -1，該設定在隊列模式下優先；否則 n8n 使用worker 的 --concurrency 值或其預設值 10。不要將worker數乘以名目預設值，並稱為保證吞吐量：實際容量取決於作業持續時間、CPU、記憶體、外部 API 和 PostgreSQL 連線。

Webhook

隊列模式會增加執行切換延遲

主程序或 Webhook 程序接收 HTTP 請求，但worker執行工作流程執行。透過 Redis 的切換增加了一些開銷。對於延遲敏感的 Webhook，測量端到端回應時間，而不是假設更多worker自動使每個請求更快。

接收Main/webhook 程序接受請求。
佇列執行交給 Redis。
執行可用的worker運行工作流程。
回應當需要時，結果會透過佇列路徑轉送回來。

將 Webhook 流量路由到正確的進程。 附專用 n8n webhook 反向代理或負載平衡器後面的處理器，路由生產路徑 /webhook/* 和 /webhook-waiting/* 到 webhook 處理器；保留 /webhook-test/*、編輯器和 API 對 main 的請求。不要將 main 放入生產 Webhook 負載平衡池中，除非您故意接受增加的工作負載。一個 回應 Webhook 工作流程可能會讓客戶端等待，直到工作程序完成並回傳其回應，因此佇列模式並不能保證即時 HTTP 回應或零逾時。在切換流量之前測試實際的外部回調和回應行為。

二進位數據

不要忽視共享存儲

檔案系統限制

佇列模式不支援檔案系統二進位資料儲存作為分散式worker 的共用持久性模型。

外部二進位存儲

當工作流程必須跨分散式worker保存二進位資料時，請使用每個所需實例都可以存取的儲存設計，例如支援的外部物件儲存。

大型 Webhook 回應

來自worker 的 Webhook 回應會回到接收程序。大型反應主體會增加 Redis 記憶體壓力，並且需要精心設計的反應儲存配置。

在分配worker之前做好計劃

在worker跨機器分佈之前，必須重新設計嚴重依賴本機檔案的工作負載以實現共享持久性。

大型 Webhook 回應邊界。 目前 n8n 文件指出，透過佇列轉送 worker 回應時，N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX 的預設值為 64 MiB。 Redis 可以在運行中保存多個副本，因此每個並發大型回應的預算大約是 Redis 記憶體中回應大小的 1.5 倍。如果沒有卸載，過大的回應就會失敗，而不是透過增加worker來神奇地變得更快。

版本和許可證限制。 從 n8n 2.34.0，worker 可以使用 N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true 將過大的 Webhook 回應主體卸載到可讀的共用二進位存儲，但首先升級 每個主處理器和 Webhook 處理器 到 2.34.0 或更高版本。所選擇的 N8N_DEFAULT_BINARY_DATA_MODE 必須實際儲存資料並且可由每個參與進程讀取。外部 S3 和 Azure 二進位儲存需要有效的自架 商業或企業 許可證；不要假設社群版可以啟用它們。的 database 二進位模式可以卸載超大回應，無需付費外部存儲，但主實例將整個存儲體加載到記憶體中，並且資料庫存儲有自己的檔案大小限制。對於 專門卸載回應主體，n8n 也說明了一種共用 filesystem 的方式 當每個實例安裝同一磁碟時的選項，但明確不建議這種安排。不要將此特殊的卸載路徑誤認為是在分散式佇列模式部署中支援基於檔案系統的持久性二進位資料。在啟用卸載之前，請檢查您的版本、版本和儲存配置。

監控

了解隊列是否有幫助

隊列深度

隊列的成長速度快於worker 的消耗速度，顯示執行能力不足或存在下游瓶頸。

worker CPU 和 RAM

測量每個worker 的飽和度和記憶體峰值。隊列不斷增加的閒置的 worker指出了另一個限制。

執行延遲

追蹤創建執行和實際啟動之間的延遲，而不僅僅是工作流程運行時本身。

健康檢查

worker執行狀況端點可以報告worker是否處於活動狀態以及其資料庫和 Redis 連線是否已準備就緒。

驗證worker 的執行情況，而不僅僅是綠色容器。 使用正確配置的 Compose 堆疊，檢查 docker compose ps 和 docker compose logs --tail=100 n8n-worker （如果不同，請替換服務名稱）。運作無害 已發布的工作流程 使用計劃觸發器或測試 Webhook 運行工作流程，然後將 n8n 的執行視圖中的執行與工作日誌中的實際工作處理進行比對。成功開啟的編輯器、正在運行的 Redis 容器或單獨的排隊執行 不 確認 worker 已完成該工作。

檢查依賴性和準備。 使用預設範例服務名稱， docker compose exec -T redis redis-cli ping 應該收到 PONG 當 Redis 身份驗證允許時，並且 docker compose exec -T postgres pg_isready -U n8n -d n8n 檢查 PostgreSQL 準備狀況（調整憑證和服務名稱）。啟用 QUEUE_HEALTH_CHECK_ACTIVE=true 當你需要它的私有時，在worker身上 /healthz 和 /healthz/readiness 終點；就緒端點檢查 Redis/資料庫連線。不要僅僅為了監視而公開這些工作端點。

手動運行是一種不同的測試。 預設情況下 OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false，因此即使正確配置了佇列模式，在編輯器中手動執行工作流程也可以在 main 上執行。將其設定為 true 僅當您打算向worker發送手動執行並已在暫存環境中檢查變更時。佇列模式worker也不同於 n8n 外部任務運行程序，後者對程式碼節點執行有單獨的設定要求。

擴充路徑

一次擴充一個瓶頸

階段 1帶有 PostgreSQL 的單一 n8n 實例；測量峰值 CPU、RAM 和並發性。
階段 2當垂直擴展仍然可以乾淨地解決測量的瓶頸時，增加 VPS 資源。
階段 3當持續的平行需求證明分散式執行合理時，引入 Redis 和worker。
階段 4新增worker或調整worker並發性，同時觀察 PostgreSQL、Redis 和執行延遲。
階段 5僅當容量、可用性或操作要求證明增加的複雜性合理時，才在伺服器之間分離元件。
當擴充需要時選擇更多 VPS 容量

高可用性邊界

佇列模式可擴展執行，但它不會自動使主程序具有高可用性

共享加密金鑰

每個worker必須使用相同的 N8N_ENCRYPTION_KEY 作為主實例，以便worker 可以解密工作流程執行所需的憑證。

保持版本一致

主進程、Webhook 進程和工作進程應運行相同的 n8n 版本。混合版本可能會在滾動變更期間產生不相容的行為。

Webhook 處理器是一個單獨的擴充層

當傳入的 Webhook 量變成瓶頸時，專用的 Webhook 處理器可以位於負載平衡器後面，同時worker處理執行。除非測量的請求量證明其合理，否則不要添加此層。

多主是不同的功能

為了高可用性而執行多個 main process，與一般的佇列模式並不相同。n8n 目前將 multi-main 架構列為自行託管 Enterprise 功能，並且需要額外的負載平衡與工作階段設定。

常見問題

n8n 隊列模式：常見問題

n8n 隊列模式是否需要 Redis？

是的。 Redis 是協調主實例和worker之間待處理執行的訊息代理程式。

隊列模式可以使用 SQLite 嗎？

對於分散式佇列模式架構來說不是。 Main 和 Workers 需要共用資料庫訪問，並且 n8n 文件 PostgreSQL 作為此設定的資料庫。

我應該運行多少個worker？

沒有通用的計數。從測量的並發性和worker利用率開始，然後在監控 PostgreSQL、Redis、CPU、RAM 和隊列深度的同時添加容量。

什麼是 n8n worker併發？

它是一個worker 可以並行處理的作業數量。目前預設值為 10，n8n 建議worker並發度為 5 或更高，而不是建立許多低並發worker。

我應該在小 VPS 上啟用佇列模式嗎？

僅當工作量證明合理時。作為一個執行個體輕鬆運行的小型部署通常更容易操作，無需 Redis 和單獨的worker。
