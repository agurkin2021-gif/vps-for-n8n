備份與復原

n8n 備份與復原

要備份和還原自託管 n8n，請保護您的 SQLite 資料庫或一致的 PostgreSQL 轉儲、持久性.n8n 資料夾和原始加密金鑰、部署配置以及每個外部二進位或已安裝文件依賴項。將加密副本保留在 VPS 之外，並在單獨的執行個體上測試復原。使用 CLI 工作流程和憑證匯出進行選擇性復原； JSON 單獨匯出並不是完整的伺服器備份。

快速清单

n8n 備份應保護什麼

資料庫

備份執行個體所使用的 PostgreSQL 資料庫或 SQLite 資料庫檔案。此資料庫包含核心 n8n 狀態，例如工作流程、憑證和執行資料。

加密金鑰

單獨且安全地保存準確的 n8n 加密金鑰。復原的加密憑證依賴相同的金鑰。

持久文件

包括持久性 n8n 資料目錄以及您的部署所依賴的任何已安裝文件、二進位資料儲存或工作流程資產。

部署配置

保留重建堆疊所需的 Compose/設定檔和非秘密配置。透過適當的存取控制來保護秘密。

兩個備份級別

邏輯匯出與完整災難復原

工作流程和憑證導出

n8n CLI 匯出對於遷移、版本化工作流程副本和選擇性復原非常有用。憑證可以以加密形式匯出，並在稍後使用匹配的加密金鑰匯入。若要僅還原工作流程，請使用工作流程編輯器的三點選單下載其 JSON，然後從檔案匯入到新的審閱工作流程或隔離實例中。在替換即時工作流程之前檢查憑證、工作流程 ID 和節點參數：恢復工作流程 JSON 不會恢復整個伺服器。

實體匯出

CLI 可以匯出資料庫實體，以便在支援的資料庫類型之間移動資料。執行歷史表是可選的，因為它們可能非常大。

完整實例恢復

對於死伺服器場景，保護實際資料庫、加密金鑰、持久性資料和部署相依性。不要假設工作流程 JSON 導出會重建整個實例。

供應商快照

VPS 快照可作為額外的復原層，但不應是唯一的備份副本，也不能取代經獨立驗證的應用程式與資料庫備份。

資料庫

一致地備份資料庫

PostgreSQL

使用一致的 PostgreSQL 備份方法並將產生的備份儲存在遠離 VPS 的地方。同一故障磁碟上的資料庫副本不是災難復原。

SQLite

如果部署使用 SQLite，請保護資料庫檔案免受持久 n8n 資料目錄的影響。避免在主動修改資料庫時複製處於不安全狀態的資料庫。

執行歷史

確定歷史執行資料是否是您的復原目標的一部分。它可以使備份變得更大，因此保留和合規性要求應該推動選擇。

数据库版本

記錄來源部署使用的資料庫引擎和版本，以便可以相容地準備復原環境。

PostgreSQL 在 Docker Compose VPS 上。 如果 PostgreSQL 服務被命名 postgres 它的資料庫/使用者都是 n8n，以下命令在主機上建立一致的 PostgreSQL 自訂格式轉儲。在運行之前檢查實際的 Compose 文件，並調整資料庫憑證和服務名稱。 pg_dump PostgreSQL 運行時可以產生邏輯上一致的快照；確實如此 不 備份單獨的 .n8n 使用者資料夾或外部二進位資料。

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

存檔清單檢查可以捕獲明顯的格式問題，但不能證明資料可以恢復。在伺服器外儲存加密副本並演練恢復。使用官方 PostgreSQL pg_dump 文件了解特定於資料庫的選項。

SQLite 關於 Docker。 對於預設的 SQLite 部署， database.sqlite 並且產生的加密金鑰配置存在於持久性文件中 .n8n 資料夾（通常安裝在 /home/node/.n8n）。切勿將 SQLite 的簡單即時副本視為一致。在複製資料夾之前停止 n8n 和其他資料庫編寫器，或在不可能中斷時使用 SQLite 支援的線上備份機制：

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

這些是所示服務和路徑的說明性命令，而不是通用磁碟區佈局。複製的資料夾最初仍在同一個 VPS 上；在伺服器外傳輸並保護它。當佇列工作人員或其他寫入程式存在時，也將其停頓並遵循其實際部署設計。 n8n's current full-backup guidance documents the SQLite consistency requirement.

將預設的 SQLite 資料夾恢復到乾淨的目標： 首先停止 n8n 服務和所有資料庫編寫器。一旦存在相容的 n8n 服務容器及其目標卷，複製備份的 .n8n 內容 回來 到同一個持久目錄。這會覆蓋目標文件，因此不要在包含需要保留資料的實例上運行它：

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker 可以複製到已停止的容器，但目的地所有權可能與原始容器不同；在啟動之前，確保 n8n 程序可以讀取和寫入恢復的配置和資料庫文件。如果您的真實 Compose 配置使用不同的路徑或綁定安裝，請相應地調整副本。 Docker Compose副本參考。對於使用單獨的 PostgreSQL 資料庫的部署來說，單獨復原 n8n 資料夾是不夠的。

關鍵秘密

加密金鑰是復原的一部分

n8n 使用實例加密金鑰對儲存的憑證進行加密。沒有符合金鑰的資料庫或加密憑證匯出可能會使復原的工作流程無法使用其已儲存的憑證。

如果您設定 N8N_ENCRYPTION_KEY，則恢復該確切的秘密。否則，產生的金鑰將儲存在持久的 .n8n/config 檔案中：在備份或重建時保護該配置。將復原金鑰安全地儲存在 VPS 之外。在佇列模式下，所有主程序和工作程序必須使用相同的金鑰。

做保留生產所使用的確切密鑰的受保護副本。
做測試憑證之前，請確認復原環境使用的是該加密金鑰。
不重建伺服器後依賴新產生的金鑰。
不將金鑰提交到公共儲存庫或將其儲存在不受保護的備份旁邊。

文件和二進位數據

資料庫備份可能無法涵蓋每個工作流程依賴項

持久 .n8n 數據

找到並保留實際的 .n8n 使用者資料夾，而不僅僅是容器映像。在典型的 Docker 部署中，它安裝在/home/node/.n8n；在 Docker 之外，預設值為 ~/.n8n。如果配置了 N8N_USER_FOLDER，則 n8n 會在指定的父目錄中建立.n8n。包括其設定金鑰以及您的安裝所使用的任何本機 SQLite、二進位或檔案系統執行資料。

已安裝的工作流程文件

如果工作流程讀取或寫入主機安裝的目錄，請單獨備份這些目錄。在沒有它們的情況下恢復 n8n 可能會導致其他有效的工作流程被破壞。

二進位數據

識別儲存模式並恢復每個外部相依性。基於檔案系統的二進位或執行資料可能位於.n8n 或自訂目錄中；S3/Azure Blob 或其他配置的外部儲存需要其自己的可復原副本和存取設定。僅資料庫轉儲無法取代這些檔案。

社群節點

記錄社群包和版本，並備份透過 N8N_CUSTOM_EXTENSIONS 配置的任何其他自訂節點目錄。這些目錄可以位於 .n8n; 之外僅還原資料庫和使用者資料夾可能仍會使自訂節點工作流程無法使用。

離線策略

同一 VPS 上的備份只是本地副本

本地副本對於快速回滾很有用，但容易受到伺服器遺失、磁碟故障和破壞性錯誤的影響。
離線副本在儲存中至少保留一份獨立於生產的備份 VPS。
版本控制副本保留多個復原點，以便損壞或錯誤變更不會覆蓋唯一可用的備份。
存取控制備份可以包含憑證、工作流程邏輯和敏感業務資料。適當地加密和限制它們。
監控當計劃的備份失敗或停止產生新的復原點時發出警報。

使時間表可衡量。 記錄每個成功備份的時間戳記、傳輸完成、檔案大小、來源資料庫版本、加密金鑰復原位置以及最近成功的復原測試。文件遺失、失敗或意外為空時發出警報。在將備份存檔發送出去之前對其進行加密 VPS 並限制對復原機密資訊的存取。多個過時的復原點可以防止僅在最新副本覆蓋最後一個正常副本後才發現損壞。

例如，如果您最多可以容忍六個小時的變更遺失，那麼成功的六小時備份計畫只是一個起點，而不是保證：失敗的作業和延遲的伺服器外複製可能會增加實際損失。根據您自己的 RPO/RTO 和資料要求設定保留和恢復節奏，而不是採用通用的 7 天或 30 天政策。

恢復秩序

按受控順序恢復

1·準備提供相容的伺服器、資料庫和容器/運行時環境。
2·恢復秘密安全地配置原始 n8n 加密金鑰和所需的部署機密。
3·復原資料庫恢復 PostgreSQL 或 SQLite 並驗證 n8n 可以連結到預期資料。
4·恢復文件恢復持久目錄、二進位資料和已安裝的工作流程資產。
5·開始 n8n使用預期的主機名稱、資料庫和環境配置啟動應用程式。
6·驗證確認使用者、工作流程和憑證加載，然後執行代表性工作流程和 Webhook 路徑。

PostgreSQL 災難復原範例： 在一個 獨立、乾淨的復原目標 已經具有正確的資料庫角色和空的 n8n 資料庫，啟動 僅 PostgreSQL。 等到它健康後再導入： docker compose up -d 當 PostgreSQL 仍在初始化時，單獨可以返回，因此以下 pg_restore 可能會失敗。此範例使用 --wait 現代 Compose 安裝並獨立檢查 pg_isready。配置適當的 PostgreSQL 運作狀況檢查以實現可靠的等待，或在繼續之前明確確認準備。不要將此命令指向已填充的生產資料庫或在資料庫及其匹配之前啟動 n8n .n8n 密鑰/資料已恢復。

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

目標必須具有相容的 PostgreSQL 版本、角色權限、擴充和原始 n8n 配置。恢復 .n8n 到其正確的持久性磁碟區或使用備份機制綁定安裝，保留所有權和權限。還原外部二進位檔案、自訂擴充功能、Compose 和機密配置，然後在相容版本上啟動 n8n 並檢查其日誌。單獨復原資料庫並不能還原金鑰：PostgreSQL 部署將金鑰保留在其中 .n8n/config 除非你明確配置 N8N_ENCRYPTION_KEY。 pg_restore 參考·n8n 全實例復原序列。

恢复测试

在恢復成功之前備份無法得到驗證

在乾淨的環境中進行測試

真正的演習應該證明備份可以重建實例，而不依賴生產伺服器上留下的未聲明的檔案。

檢查憑證

打開工作流程還不夠。確認恢復的加密憑證確實成功解密和驗證。

運行代表性工作流程

測試依賴 webhook、外部 API、已安裝檔案和社群節點的工作流程，而不是僅驗證簡單的自動化。

測量恢復時間

記錄恢復需要多長時間以及剩餘的手動步驟。这将假定的备份转换为可操作的恢复过程。

已驗證的恢復練習：SQLite 和 PostgreSQL

測試環境： n8n 2.42.5 使用合成的兩節點工作流程，在一次性 GitHub 操作運行器上的隔離 Docker 容器中。這些檢查持續進行 8 十月 2026，不在客戶或生產 n8n 伺服器。

SQLite：透過導入測試工作流程，匯出它，停止所有編寫器，存檔 SQLite 支援的持久性 .n8n 資料夾及其產生的加密金鑰，恢復到乾淨的磁碟區中，開始 n8n，然後重新匯出並執行復原的工作流程。
PostgreSQL：透過匯入相同的測試工作流程，建立並檢查自訂格式 pg_dump，使用恢復它 pg_restore 到一個新的空 PostgreSQL 資料庫中，恢復單獨的 .n8n 資料夾，然後重新匯出並執行復原的工作流程。

什麼沒有測試過真實憑證、生產 Webhooks、佇列模式工作執行緒和 Redis、S3/Azure 二進位儲存、自訂節點、使用者/專案存取或即時生產執行個體的復原的解密和身分驗證。為您實際使用的每個依賴項執行單獨的演練。

如何重現： 使用一次性 n8n 安裝，建立無害的兩節點工作流程，執行適用的資料庫和持久資料夾備份，還原到乾淨的磁碟區或資料庫，然後驗證復原的工作流程的節點、連線和實際執行。在宣布災難復原經過驗證之前，在生產系統上還要檢查加密憑證、Webhook和外部檔案。

恢復鑽探驗收清單： 使用隔離的網域/環境；檢查使用者和工作流程是否存在，現有的加密憑證無需重新輸入即可進行身份驗證，生產 Webhook 呼叫預期恢復的工作流程，已安裝的文件和二進位附件保持可讀，以及與所需社區節點加載的整合。確認備份期限、測量的停機時間和伺服器外可存取性。如果任何重要檢查失敗，請標記該復原點 未經驗證 而不是報告備份已完成。

CLI 備份限制

準確了解哪些工作流程和憑證匯出不會恢復

CLI 匯出不是完整實例備份

工作流和凭证备份导出不包括用户和角色、执行历史记录和日志、变量或实例设置（例如加密密钥）。

全新執行個體復原需要擁有者

在乾淨的實例上，在匯入憑證之前完成所有者設定。多用戶或項目恢復可能還需要正確的使用者或項目分配。

導入的 ID 可以覆蓋現有項目

工作流程和憑證匯出保留其原始 ID。导入到已包含相同 ID 的实例中可以替换那些现有项目。

有意發布導入的工作流程

CLI 匯入通常會使工作流程處於非活動狀態。在 n8n 2.x 上，檢查每個匯入的工作流程的發布狀態並僅發布您想要運行的工作流程；自託管伺服器 CLI 也支援 n8n 發布：工作流程--id=YOUR_WORKFLOW_ID。當 n8n 運作時，伺服器 CLI 發布/取消發布狀態變更僅在重新啟動 n8n 後生效。在驗證計劃的觸發器和生產 Webhook 或切換流量之前重新啟動。

Docker Compose 的批次匯出範例： 如果您的 n8n 服務已命名 n8n，您可以執行下面的官方 CLI 備份。輸出路徑故意位於其安裝的持久性內部 .n8n 目錄，因為容器內的任意目錄在重新建立時可能會消失。確認目錄可由 n8n 容器使用者寫入。保留工作流程和憑證 JSON 單獨的目錄—n8n 記錄了兩種共享目錄時的導入問題。

n8n 2.x 草稿與已發布的備份： 一個正常的 --backup 工作流程匯出捕獲當前草稿；這些可能與生產中發布的版本不同。要保留特定工作流程的實際發布版本，請使用以下命令單獨匯出它 docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json，在確保輸出資料夾存在並且可寫入之後。 CLI 也可以使用匯出歷史版本 --version=VERSION_ID。将这些捕获与完整备份一起保存在服务器外；不要假设草稿 JSON 记录了实时发布的状态。

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

複製的 ~/n8n-recovery/cli 目錄仍位於 VPS 上，直到您將其移至安全、獨立的備份位置。憑證匯出預設加密，匯入時需要匹配的加密金鑰。避免使用 --decrypted 除了嚴格控制的遷移：它以明文形式寫入秘密。切勿將包含敏感工作流程邏輯或憑證的匯出提交至公用 GitHub 儲存庫。有些第三方 GitHub 憑證備份範本故意匯出解密的秘密；私有儲存庫是一種存取限制，而不是加密。檢查每個模板的實際匯出設定和儲存權限，在伺服器外傳輸之前加密機密，並輪換透過意外的純文字上傳暴露的任何憑證。

批次導入範例： 在乾淨的目標上，完成所有者設置，提供原始加密金鑰並確保保存的備份文件在該恢復中可用 VPS。以下建立目標資料夾並複製 workflows/ 和 credentials/ 從主機到 n8n 容器的子資料夾；如果您的 Docker 磁碟區佈局不同，請調整路徑：

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

檢查 n8n 容器使用者的文件所有權和存取權限。請勿在未經過驗證回溯的情況下匯入已填入的生產實例：工作流程和憑證 ID 可能會覆寫現有條目。然後運行：

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

匯入的 ID 可以取代現有的工作流程或憑證；使用隔離的測試實例進行試運行，然後檢查憑證和啟動/發布狀態。在 n8n 2.x 中，恢復 JSON 草稿本身並不能證明工作流程已發布並且可以運行計劃的觸發器。 進口安全： 在非多主 n8n 執行個體上，先前活動的 cron 觸發器可以在 CLI 匯入後繼續執行，直到執行個體重新啟動。在啟用復原作業之前停止或隔離生產觸發器並重新啟動 n8n；驗證沒有重複執行。 CLI 出口做 不 包含原始使用者、執行日誌、實例變數或加密金鑰。 --backup 套 --all --pretty --separate，而不是「完整實例」。來源：目前官方 n8n 備份/復原指南和 n8n CLI 命令參考。

從 GitHub 或 Google 雲端硬碟範本批次恢復： 這只是工作流程 JSON 的替代方案，不適用於實例資料庫、使用者、加密憑證值或加密金鑰。在執行基於 API 的範本之前，請先驗證其 n8n API 和儲存權限、選定的備份版本和目標實例、是否更新符合 ID 並重新建立已刪除的工作流程，以及它對工作流程發布的作用。並非所有範本都會重新建立目標中缺少的 ID；在依賴自動復原之前單獨測試該場景。

常見問題

n8n 備份與還原：常見問題

匯出工作流程是否足以備份 n8n？

不會。工作流程匯出是有用的邏輯副本，但完整復原也可能需要憑證、匹配的加密金鑰、資料庫狀態、持久性檔案和二進位資料儲存。

如果我有資料庫，我是否需要 n8n 加密金鑰？

是，如果您需要儲存在該資料庫中的加密憑證保持可用。妥善保存原始密鑰。

我應該備份 PostgreSQL 還是匯出工作流程和憑證？

為了進行災難恢復，請保護資料庫和加密金鑰。邏輯匯出作為額外的遷移和選擇性恢復層很有價值，而不是替代實例的每個部分。

VPS 快照可以作為我唯一的備份嗎？

最好將其視為一層恢復層。保留獨立的伺服器外備份，以便供應商、帳戶、伺服器或快照故障不會立即刪除每個復原點。

我如何知道我的備份有效？

將其恢復到乾淨的測試環境中，驗證憑證解密並執行代表性工作流程。僅成功的備份作業並不能證明可恢復性。

GitHub 或 Google Drive 工作流程備份是否包含已儲存的憑證機密？

僅工作流程 JSON 備份不包括由 n8n 的憑證儲存或實例加密金鑰管理的秘密值。但是，匯出的 JSON 可以公開直接輸入到節點參數（例如身分驗證標頭）中的憑證名稱、ID 和秘密。在上傳或共享之前檢查並保護導出的 JSON。若要完全恢復，請備份資料庫和原始金鑰，或使用受支援的加密憑證 CLI 匯出以及經過測試的還原。僅限工作流程的 GitHub 或 Google 雲端硬碟範本不是完整的災難復原。

恢复目标

在事件發生之前定義 RPO 和 RTO

復原點目標 是最近變化的最大可容忍損失。從最新可用的、獨立儲存的復原點開始測量；如果匯出或傳輸失敗，計劃的六小時作業不會建立六小時 RPO。 RTO 是最大可容忍中斷。透過乾淨的復原練習來衡量它，包括檢索機密、恢復外部文件、重新檢查憑證和發布復原的工作流程，而不僅僅是啟動容器。

恢復密鑰

重建前找到原始加密金鑰

如果生產集 N8N_ENCRYPTION_KEY，保留確切的環境秘密。如果沒有，請將產生的金鑰保留在原始持久性 .n8n/config 中。在匯入加密憑證之前檢查復原的執行個體實際使用哪個來源；新產生的金鑰無法解密舊資料庫中的憑證。
