n8n VPS 要求

對於 n8n VPS 要求，從您的工作負載開始，而不是從通用硬體最低限度開始。精心設計的 1 vCPU / 1 GB VPS 可以運行小型始終在線的自動化，而 2 vCPU / 4 GB RAM 是 n8n、PostgreSQL 和 HTTPS 的實用起始類別。大有效負載、同時運作和本地資料處理需要更多的空間；選擇前先衡量實際使用情況。

實用小製作

2 vCPU · 4 GB RAM

當 n8n 與 PostgreSQL、Docker 和反向代理共享 VPS 時，這是一個平衡的起始類別。為重疊執行和維護保留空間。

繁重或數據密集型

4+ vCPU · 8 GB+ RAM

大型 JSON、二進位檔案、程式碼節點、瀏覽器工作和許多重疊執行可以證明更多的 CPU 和記憶體是合理的。

最小容量與實際容量

n8n 是否有一個官方的最小 VPS 尺寸？

不適用於所有工作負載。 n8n 的官方先決條件範例描述了示例性 OEM 部署，並明確警告要求因工作負載而異。該文件並不能普遍保證任何特定的 CPU、RAM 或磁碟分配將支援生產自動化。

n8n 指出，空閒實例可能使用相對較少的內存，但程式碼節點、大型二進位負載或同時執行可能會急劇增加內存需求。分別為操作系統、Docker、PostgreSQL 和備份/監控工具制定預算。

RAM 和 CPU

實際消耗伺服器資源的是什麼

並發執行

同時運行的多個工作流程可能比 n8n 中儲存的工作流程總數更重要。觀察重疊期間的記憶體峰值和執行延遲。

有效負載大小

大型 JSON 物件、文件和二進位資料會增加記憶體壓力。與許多輕量級 API 自動化相比，一些資料密集型執行可能需要更多的 RAM。

CPU-重節點

程式碼、轉換和其他計算量大的步驟可能會產生持續的 CPU 壓力。當實際執行競爭計算時，更多核心會有所幫助。

配套服務

作業系統、PostgreSQL、反向代理、監控和 Docker 也需要資源。調整整個堆疊的大小，而不僅僅是 n8n 流程。

升級前測量

如何判斷 n8n 是否需要更多 RAM、CPU 或磁碟

運行最大的預期工作流程和實際的重疊突發，然後檢查伺服器和 n8n 執行日誌。編輯器中儲存的工作流程數量本身並不是有用的容量基準。

記憶體/OOM

檢查 docker stats --no-stream 和 free -h。如果記憶體耗盡，請先減少 JSON 或二進位有效負載，批次匯入大量內容並避免佔用大量記憶體的程式碼步驟。 JavaScript 堆錯誤不一定可以透過加入 vCPU 來修復。

CPU / 並發

衡量 CPU 在轉換期間是否保持忙碌，或作業是否僅等待外部 API。在常規模式下，在擴展到工作人員之前請考慮支援的生產並發限制。增加 CPU 不會加速外部速率限制 API。

儲存/資料庫

檢查 df -h、資料庫大小和保留的執行歷史記錄。觀察磁碟增長和緩慢的資料庫操作。在購買更大的磁碟之前有意設置保留；將恢復副本保留在伺服器之外。

使用 n8n 的並發指南和官方基準測試解釋。在不知道其有效負載和 API 延遲的情況下宣傳的任何數量的並發工作流程都只是一個估計。

数据库与存储

SQLite、PostgreSQL 和持久性數據

SQLite

SQLite 可以適合小型單一執行個體部署和測試。隨著生產使用和並發性的成長，資料庫選擇成為操作約束而不是安裝細節。

PostgreSQL

對於以生產為導向的 VPS 堆疊，PostgreSQL 提供了更強大的資料庫基礎。為資料庫本身製定預算 RAM、CPU 和磁碟並監控其成長。

持久 .n8n 數據

不要將 PostgreSQL 視為唯一的持久資產。保留 n8n 資料目錄並保護恢復加密憑證所需的加密金鑰。

磁盘增长

執行歷史記錄、二進位資料、資料庫檔案和日誌會隨著時間的推移而擴展。保留設定和伺服器外備份直接影響所需的容量。

磁盘容量

訂購前估計 n8n 執行歷史存儲

開始於 每天儲存的執行次數 × 每次執行的平均儲存位元組數 × 保留天數。例如，每天 500 保存的執行 × 200 KB 每 × 14 天 = 1.4 GB 資料庫開銷之前的範例執行資料。 200 KB 假設是說明性的，而不是 n8n 基準。

也為作業系統、Docker 映像層、資料庫索引、二進位檔案、應用程式日誌、升級和臨時檔案指派磁碟。離線備份需要自己的容量。 10 GB 磁碟可用於精實堆疊，但用於保留文件的空間比 40 或 80 GB 磁碟少得多。

n8n 記錄了按期限（336 小時/14 天）或計數（10,000 執行）進行的預設執行修剪，但有例外。檢查您的實際設定並在更改之前驗證保留的內容。 SQLite 可以重複使用釋放的空間，而不是自動縮小其文件。

來源：n8n：管理執行資料和修剪。磁碟要求取決於觀察到的保存的有效負載大小，而不僅僅是節點的數量。

系統需求

Docker 和生產費用

Linux VPS

使用經過維護的 Linux 發行版，除了應用程式堆疊之外，還為作業系統和安全更新提供足夠的資源。

Docker & 撰写

容器部署簡化了可重複性，但並沒有消除資源開銷。將 n8n 和資料庫資料保留在一次性容器之外。

HTTPS & 反向代理

公共 Webhook 需要穩定的主機名稱和正確配置的 HTTPS。在生產設計中包括反向代理和 TLS 層。

監控和備份

追蹤 RAM、CPU、磁碟和資料庫成長。將可恢復的備份保留在第 VPS 之外並測試恢復，而不是假設快照就足夠了。

並發性

當更大的 VPS 不再是完整的答案時

當一個實例可以乾淨地處理工作負載時，垂直擴展是合適的。當持續的並行需求造成爭用時，請評估佇列模式和工作執行緒。隊列模式引入 Redis、PostgreSQL 和一個或多個工作進程；每個組件的預算 RAM 和 CPU，而不僅僅是 n8n。 n8n 還記錄了佇列模式下檔案系統二進位資料儲存的限制，因此在切換之前驗證相容的資料儲存設計。

閱讀佇列模式和工作人員指南

保持單一實例當 CPU、RAM 和執行延遲在峰值重疊下保持舒適時。
垂直縮放當持續的 CPU 或記憶體壓力是限制因素且架構仍然簡單時。
考虑队列模式當測量並行需求時，Redis 和單獨的工人是合理的。
重新檢查儲存狀況當執行歷史記錄、二進位或 PostgreSQL 成長成為主要約束。

入門級和存儲 I/O

如何使用 1 GB 條目 VPS

1 GB RAM

這是一個真正的工作 VPS 層，而不是一個僅供測試的產品。當您將記憶體、磁碟使用和並發作業保持在測量限制內時，它適用於小型始終在線的自動化和大多數順序 API 工作。它在同一台伺服器上提供給 PostgreSQL 的空間很小，但有效負載很大或平行執行量很大。

2 GB RAM

當您需要為作業系統、Docker 和小突發提供更多空間而不立即轉移到生產規模的堆疊時，請使用 2 GB 作為更安全的輕量級執行個體基準。

SSD 與 NVMe

Standard SSD 對於輕型自動化來說足夠了。當 PostgreSQL 和執行歷史記錄導致頻繁讀寫或在測量的工作流程效能中出現磁碟延遲時，NVMe 變得更加有用。

升級前測量

使用 CPU、內存、磁碟增長和峰值重疊下的執行持續時間來確定瓶頸是計算、內存還是存儲，而不是假設更大的 VPS 可以解決每次減速問題。

常見問題

n8n VPS 要求：常見問題

n8n 需要多少 RAM？

沒有通用的數字。 RAM 需求隨並發性、有效負載大小、執行行為和 VPS 上的支援服務而變化。 4 GB 伺服器是實用的小批量生產入門級伺服器，並非每個工作負載的保證要求。

我應該使用多少個 CPU 核心？

輕量工作負載可以從較小的 CPU 分配開始。當監控顯示持續的 CPU 壓力或併發下執行速度較慢時添加核心，而不是僅根據工作流程計數來調整大小。

n8n 需要 PostgreSQL 嗎？

小型部署可以使用 SQLite，但隨著操作要求和並發性的增加，PostgreSQL 是更強大的生產導向的選擇。

什麼時候需要 Redis？

Redis 與隊列模式相關。正常的單一實例部署不需要 Redis，僅僅因為它運行在 VPS 上。

我應該保留多少磁碟空間？

磁碟需求取決於 PostgreSQL 的成長、保留的執行歷史記錄、二進位資料、日誌、容器層和備份。監控成長並留出空間，而不是依賴固定的通用數字。

我可以在 1 GB VPS 上連續運行 n8n 嗎？

是的，當實際工作量適合時。 1 GB VPS 是一個真正的工作伺服器，可以支援小型、大多數順序自動化，但記憶體空間有限。避免假設同一伺服器 PostgreSQL 堆疊、二進位密集型作業或多個大型並發執行將適合。根據觀察到的資源壓力監控消耗和升級。

對於製作 n8n VPS 來說，2 GB 還是 4 GB RAM 比較好？

兩 GB 比精簡的 1 GB 實例提供了更多空間，而 4 GB 是評估 n8n 以及 PostgreSQL 和 HTTPS 的實用起始類別。不存在通用的保證生產最低限度：工作負載複雜度、尖峰重疊、容器配置和保留資料決定了實際需求。

n8n 人工智慧工作流程需要 GPU 嗎？

當 n8n 僅調用外部模型 API 時則不然：模型提供者處理推理，而 VPS 處理編排、有效負載和並發性。在本地運行推理模型是一項單獨的硬體決策，可能需要更多的 RAM 和適當的 GPU 資源。

是什麼導致 n8n 記憶體不足錯誤？

大型 JSON 或二進位有效負載、佔用大量記憶體的程式碼操作和重疊執行是常見原因。檢查運行時日誌和峰值記憶體使用情況，然後根據測量的問題減少一次執行中保存的資料或分配更多 RAM。
