碼頭安裝

在 VPS 上安裝 n8n

使用 Docker Compose 和 PostgreSQL 在 VPS 上安裝 n8n。生產部署還需要持久的應用程式和資料庫資料、穩定的 N8N_ENCRYPTION_KEY、公用主機名稱、HTTPS 和正確的 Webhook 設定。在啟動生產工作流程之前驗證這些部分。

在開始 n8n 之前準備好 VPS

Linux VPS

使用大小為 n8n、PostgreSQL、Docker 的維護的 Linux 伺服器和反向代理。

DNS

在頒發 TLS 憑證和發布 Webhook URL 之前，將網域或子網域指向 VPS。

Docker Compose

使用作業系統支援的軟體包安裝 Docker 引擎和Compose外掛程式。

防火牆

僅公開所需的管理和 Web 連接埠。保持 PostgreSQL 和內部應用程式服務的私密性。

在已託管網站的 VPS 上安裝？ 當 CPU、RAM 和儲存允許時，您可以將 n8n 新增至您控制的伺服器。但是，如果 Nginx、Apache、Caddy 或其他反向代理已擁有連接埠 80/443，則執行 不 啟動下面的範例 Caddy 容器，保持不變：連接埠將發生衝突。相反，請使用適當的專用網路透過現有反向代理路由新的 n8n 子域，或使用乾淨的 VPS 作為確切的 Compose 範例。保留其他站點及其 TLS 設定；此範例假設連接埠 80/443 可用。

複製並調整安裝

使用 Docker Compose 在 VPS 上安裝 n8n

使用此範例建立一個 n8n 部署在 自我管理 Linux VPS。您自行安裝和維護 n8n；透過我們的合作夥伴選擇的伺服器不包括預先安裝的 n8n 執行個體。此範例在專用 Compose 網路中結合了 n8n、PostgreSQL、外部任務運作程序和 Caddy HTTPS。它是一個設定範本， 並非現場測試部署的聲明.

想要最快的全新安裝嗎？ n8n 也提供官方單行 Docker 設定。您可以下載並查看其腳本 curl -fsSL https://get.n8n.io -o get-n8n.sh 執行前 sh get-n8n.sh。該選項在本地 URL 處啟動帶有 SQLite 的初始執行個體，並包括 n8n 助理沙箱服務；這是 不一樣 作為此公開 HTTPS、PostgreSQL 支援的 VPS 部署。官方完整沙盒堆疊比精簡的 n8n 安裝需要更多的 RAM 和 CPU（其 Compose 指南指定至少 4 GB RAM / 2 vCPU）。對於面向網際網路的生產 VPS，請繼續使用下面的手動設定堆疊。

1。準備 Docker、DNS 並訪問

透過 sudo 存取連接 SSH 並指向 DNS A 記錄 n8n.example.com 到您的 VPS IPv4 位址。上一個 新鮮的 Ubuntu 22.04、24.04 或 26.04 VPS，以下命令安裝 Docker 引擎和現代 docker compose 來自 Docker 官方簽署的插件 apt 儲存庫：

# Fresh official Ubuntu 22.04 / 24.04 / 26.04 installation
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Register Docker's signed apt repository
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

這是官方 Docker Ubuntu 安裝指南中以生產為導向的儲存庫方法。 不要在已有執行中容器或其他網站的 VPS 上，未經檢查就重新安裝或移除 Docker;首先檢查現有的安裝和可能的套件衝突。對於 Debian 或其他發行版，請使用相應的官方作業系統特定指令而不是 Ubuntu 命令。

現在驗證 Docker 本身、Compose 外掛程式、DNS 和工作目錄：

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

如果 getent hosts 未交回地址或地址錯誤，請在開始 Caddy 之前更正您的 DNS；替換 n8n.example.com 在本指南中使用您的真實主機名稱。 Docker 通常需要 root 權限：如果您的 SSH 使用者無法執行後者 docker compose 直接命令，前綴為 sudo。將用戶加入到 docker 群組授予 root 等效存取權限，不應在共享伺服器上隨意執行。

在啟用防火牆之前，請確保您的實際 SSH 管理連接埠可存取。允許入站 HTTP (80) 和 HTTPS (443) 進行證書頒發和編輯。 Docker-發布的容器連接埠可以繞過某些 UFW 規則，因此請查看 Docker 的防火牆指南並僅發布預期的 Caddy 連接埠。這個 Compose 範例刻意不將 PostgreSQL (5432)、n8n (5678) 或 task-runner broker (5679) 暴露到公用網際網路。

2。建立環境值並儲存密鑰

從專案目錄中，產生三個 不同的 隨機十六進位值：

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

建立一個名為 .env 使用下面的模板，替換每個 REPLACE_WITH_RANDOM_HEX 使用不同的產生值，並變更主機名稱和時區。所示的 2.42.5 標籤是 穩定版本於 10 月 8 2026 上市，此處用作過時的設定範例， 不能保證即時測試過的部署或未來的安全性。在安裝之前，請檢查目前的官方 n8n 版本，然後將 n8n 及其task runner 映像保留在同一經過驗證的版本上。

# .env — replace the three example secrets
# Pin a maintained n8n release; keep n8n and runner equal.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

絕不要將 .env 提交到公開儲存庫。將加密金鑰和復原指令安全地儲存在 VPS 之外。在容器重新建立或遷移後，金鑰必須保持不變。

3。為全新安裝編寫 compose.yaml

在同一目錄下建立 compose.yaml。此範例使用官方的 n8n 環境變數約定和 PostgreSQL 18 PGDATA n8n hosting 專案文件所記載的路徑：

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

這四個服務有不同的角色：PostgreSQL 儲存資料庫狀態，n8n 運行工作流程， n8n-runner 使用匹配版本和共享身分驗證令牌執行運行器任務，Caddy 處理公開 HTTPS。一個外部 任務執行者 不是 Redis 佇列模式。僅 Caddy 發布主機連接埠。此精實插圖使用單一資料庫角色進行設定；要加強 PostgreSQL 權限的分離，請參閱官方 n8n PostgreSQL 部署範例。

4。建立 HTTPS Caddyfile

建立文件 Caddyfile （大寫 C，無副檔名）旁邊 compose.yaml。將範例主機名稱替換為您自己的 DNS 名稱：

n8n.example.com {
    reverse_proxy n8n:5678
}

當網域正確解析且外部流量可以到達連接埠 80/443 時，Caddy 請求並續訂公共 TLS 憑證。不要將 DNS 指向 localhost。如果將 Caddy 替換為另一個反向代理，則轉送原始主機、協定和用戶端位址標頭並調整 N8N_PROXY_HOPS 為可信代理躍點的實際數量。

5。啟動容器並從外部進行測試

儲存後從專案目錄執行這些命令 .env, compose.yaml 和 Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

最後一個命令會檢查 公開 HTTPS 健康檢查端點。如果證書頒發仍在等待中，請在得出 n8n 已損壞的結論之前檢查 Caddy 日誌和 DNS/連接埠。打開 https://n8n.example.com，立即建立第一個所有者帳戶並啟用適當的登入保護。確認執行個體實際執行工作流程，而不僅僅是編輯器載入：

  1. 在編輯器中，建立一個工作流程 Webhook 觸發。套裝 HTTP 方法 到 GET，選擇 Path vps-check，並設定 回應 到 立即。儲存工作流程。
  2. 點選 監聽測試事件，複製完整的 測試網址 由 n8n 顯示，並從另一台裝置運行 curl -i 'PASTE_TEST_URL_HERE' 與複製的 URL。預計 HTTP 成功回應和傳入事件將出現在 n8n 編輯器中。測試 URL 僅在 n8n 偵聽事件時有效。
  3. 發布 工作流程，將節點切換到其 生產網址，複製並運行 curl -i 'PASTE_PRODUCTION_URL_HERE' 再次。確認工作流程下的執行 處決 選項卡。生產 Webhook 請求需要發布工作流程，並且不會在編輯器的測試視圖中顯示其負載。

這是一個故意簡單的、未經身分驗證的冒煙測試：永遠不要向它發送秘密。測試後取消發布/刪除它，或在使用公開端點獲取真實資料之前設定 Webhook 身分驗證/IP 限制。請參閱官方 Webhook 測試/生產文件。

6。在更改固定版本之前進行備份

保存可恢復的 PostgreSQL 轉儲 和 持久的 n8n 資料量， .env/加密金鑰和需要儲存在該伺服器外部的外部檔案。使用以下命令驗證恢復 備份和復原指南 在更新生產之前。命令範例：

# Back up the database, encryption key, instance data,
# and files before changing the pinned versions.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# After securing the backup outside this VPS:
docker compose pull
docker compose up -d
docker compose ps

變更固定的 N8N_VERSION 僅在閱讀發行說明後才變更固定版本；n8n 與 task runner 映像必須同步升級。 不要執行 docker compose down -v 在日常維護期間，因為這會刪除命名資料磁碟區。 PostgreSQL 主要版本變更需要資料庫升級或轉儲/復原計畫；以不同的主要標籤取代 Postgres 18 映像並不是自動遷移。

權威參考：n8n Docker Compose 指南、n8n 反向代理/Webhook 設定以及官方 PostgreSQL 部署說明。不假定任何基礎設施基準或特定於供應商的預先安裝功能。

加密金鑰

在儲存生產憑證之前設定並保留強大的 n8n 加密金鑰。恢復後需要相同的密鑰。

PostgreSQL 憑證

使用專用資料庫憑證並將密碼置於公共原始碼控制之外。

公用主機名

常見故障

為什麼 n8n Docker 安裝在本地運行但在生產中失敗

Webhook URL 錯誤

回呼指向 localhost、HTTP 或內部主機名，而非公開 HTTPS 來源。

缺少堅持

重新建立容器時，應用程式或資料庫狀態會消失。

遺失加密金鑰

重建後，已儲存的憑證將變得不可用，因為新執行個體使用不同的金鑰。

公共資料庫連接埠

PostgreSQL 被不必要地暴露，儘管只有 n8n 需要到達它。

部署後驗證

連接真實工作流程之前驗證運行狀況

檢查容器狀態

運行 docker compose ps 並確認應用程式和資料庫服務按預期運行，然後再將部署視為正常。

檢查 n8n 健康端點

對於上面的 Compose 範例，連接埠 5678 未在主機上發布。檢查公開端點 curl -fsS https://n8n.example.com/healthz 更改主機名稱後，然後使用 docker compose ps 如果 HTTPS 或資料庫尚未就緒，請一併檢查服務日誌。

固定應用程式版本

請勿將未經審查的浮動映像更新視為維護策略。記錄您正在執行的 n8n 版本，請閱讀發行說明並在變更之前進行備份。

不要將 PostgreSQL 主要版本更改到位

僅更改 Postgres 主映像標籤可能會使現有資料目錄不相容。備份並遵循資料庫升級流程，而不是假設容器重新建立執行主要版本遷移。

常見問題

將 n8n 與 Docker 一起安裝：常見問題

使用 Docker 時 n8n 是否需要 PostgreSQL？

Docker 不需要 PostgreSQL，小型部署可以使用 SQLite。對於以生產為導向的 VPS 部署，PostgreSQL 提供了更強大的資料庫基礎並支援以後的佇列模式擴展。

如果 PostgreSQL 儲存資料，為什麼還要保留持久的 n8n 磁碟區？

持久性 n8n 目錄可以包含重要的執行個體狀態和設定。根據部署設計保留它，而不是假設資料庫是唯一的復原資產。

為什麼我的 webhook 顯示 localhost？

內部容器位址與公開來源不同。設定外部主機名稱、協定和 Webhook URL，並確保反向代理傳遞所需的標頭。

連接埠 5678 應該是公開的嗎？

對於反向代理後面的正常生產部署，請在代理處公開 HTTPS，並將 n8n 應用程式連接埠保留在內部，除非有特定的操作原因不這樣做。

我需要 Redis 嗎？

不適用於標準單一執行個體 Docker 部署。當您有意轉向隊列模式和工作人員時，Redis 變得相關。

外部 n8n task runner 與佇列模式工作程序相同嗎？

不會。外部 task runner 獨立於 n8n 主程序執行支援的任務代碼，並使用共享身分驗證令牌。 Redis 佇列模式分佈工作流程執行並有其自己的基礎設施要求。此範例顯示外部 task runner，而不是 Redis 佇列模式。請讓 task runner 映像版本與 n8n 版本保持一致。
