क्षमता वाढवणे

n8n Queue Mode

रांग मोड वर्कफ्लो अंमलबजावणीला मुख्य n8n प्रक्रियेपासून वेगळे करतो. मुख्य उदाहरण ट्रिगर प्राप्त करते आणि अंमलबजावणी तयार करते, Redis रांगेत समन्वय साधते, कामगार कार्ये कार्यान्वित करतात आणि PostgreSQL सामायिक कार्यप्रवाह आणि अंमलबजावणी डेटा संचयित करते.

झटपट निर्णय

तुम्हाला खरोखर Queue Mode ची गरज आहे का?

नियमित मोड कधी वापरावा?

एकच उदाहरण पीक एक्झिक्यूशन आरामात हाताळते आणि CPU, RAM आणि एक्झिक्यूशन लेटन्सी स्थिर राहते. रांग मोड आपल्याला अद्याप आवश्यक नसलेले घटक जोडतो.

Queue Mode कधी विचारात घ्यावा?

सातत्यपूर्ण समांतर अंमलबजावणीमुळे वाद निर्माण होतात, अंमलबजावणीची लेटन्सी लोडखाली वाढते किंवा तुम्हाला एकाधिक कामगार चालवून अंमलबजावणी क्षमता जोडण्याची आवश्यकता असते.

सर्वप्रथम VPS ची क्षमता कधी वाढवावी?

अडथळे फक्त अपुरे आहेत CPU किंवा RAM आणि एक मोठे उदाहरण अद्याप कामाचा भार स्वच्छपणे पूर्ण करू शकते.

आर्किटेक्चर बदलण्यापूर्वी मोजमाप करा

हालचालीचे समर्थन करण्यासाठी पीक कॉन्करन्सी, CPU, RAM, अंमलबजावणी कालावधी, रांगेची खोली आणि डेटाबेस दाब वापरा.

प्रणालीची रचना

n8n Queue Mode कसा कार्य करतो?

1 · मुख्यटाइमर, वेबहुक आणि वर्कफ्लो विनंत्या प्राप्त करते आणि उत्पादन अंमलबजावणी स्वतः करण्याऐवजी एक अंमलबजावणी तयार करते.
2 · Redisसंदेश दलाल म्हणून काम करते. त्यामध्ये प्रलंबित अंमलबजावणी संदेश आहेत जेणेकरून पुढील उपलब्ध कामगार नोकरीसाठी दावा करू शकेल.
3 · कामगारएक्झिक्युशन आयडी प्राप्त करतो, शेअर केलेल्या डेटाबेसमधून वर्कफ्लो डेटा लोड करतो, वर्कफ्लो चालवतो आणि निकाल परत लिहितो.
4 · PostgreSQLसामायिक सतत कार्यप्रवाह आणि अंमलबजावणी डेटा प्रदान करते. वितरित रांग मोड SQLite वर समर्थित नाही.

मूलभूत आवश्यकता

Queue Mode डिप्लॉयमेंटसाठी आवश्यक घटक

Redis

सर्व मुख्य आणि कामगार प्रक्रियांना रांग समन्वयासाठी वापरल्या जाणाऱ्या Redis सेवेसाठी विश्वसनीय प्रवेश आवश्यक आहे.

PostgreSQL

मुख्य आणि कामगारांनी डेटाबेस सामायिक करणे आवश्यक आहे. रांग मोड एक वितरित आर्किटेक्चर आहे आणि SQLite च्या आसपास डिझाइन केलेले नसावे.

जुळणारे n8n कॉन्फिगरेशन

मुख्य आणि कामगारांनी रांग मोड चालवणे आवश्यक आहे आणि Redis, PostgreSQL आणि एनक्रिप्टेड क्रेडेन्शियल्समध्ये प्रवेश करण्यासाठी आवश्यक कॉन्फिगरेशन सामायिक करणे आवश्यक आहे.

वर्कर्सची क्षमता

कामगारांना ते कार्यान्वित करत असलेल्या वर्कफ्लोसाठी पुरेसे CPU आणि RAM आवश्यक आहे. प्रक्रिया जोडल्याने प्रत्येक अंमलबजावणीची संसाधन किंमत काढली जात नाही.

विद्यमान स्व-होस्ट केलेल्या स्टॅकवर रांग मोड सक्षम करा. प्रथम खात्री करा की n8n मुख्य सेवा आणि प्रत्येक कामगार खाजगी नेटवर्कवर समान PostgreSQL डेटाबेस आणि Redis पर्यंत पोहोचू शकतात. सेट करा EXECUTIONS_MODE=queue मुख्य आणि कामगार आणि पुरवठा दोन्हीवर QUEUE_BULL_REDIS_HOST=redis आणि QUEUE_BULL_REDIS_PORT=6379 जेव्हा redis तुमचे वास्तविक रचना सेवा नाव आहे. वापरा DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres आणि जुळणारे DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER आणि DB_POSTGRESDB_PASSWORD प्रत्येक प्रक्रियेवर; उदाहरण सेवा नावे तुमच्या नावाने बदला. अचूक विद्यमान प्रदान करा N8N_ENCRYPTION_KEY त्या सर्वांना. Redis किंवा PostgreSQL होस्ट पोर्ट फक्त त्याच कंपोझ नेटवर्कवर कंटेनर कनेक्ट करण्यासाठी कधीही प्रकाशित करू नका.

एक एक्झिक्यूटर लाँच करा, दुसरा संपादक नाही. समान पिन केलेली n8n प्रतिमा आवृत्ती आणि मुख्य म्हणून सामायिक केलेली सेटिंग्ज वापरून n8n कार्यकर्ता सेवा जोडा, परंतु ती यासह चालवा worker आज्ञा जर तुम्ही त्या सेवेला नाव दिले n8n-worker, ते सुरू करा docker compose up -d n8n-worker. एका कामगारावर प्रत्यक्ष अंमलबजावणीची पुष्टी केल्यानंतर, तुम्ही वापरू शकता docker compose up -d --scale n8n-worker=2 त्या सेवेतून दुसरा कामगार सुरू करण्यासाठी. हे ॲडिशन्स आहेत विद्यमान योग्यरित्या कॉन्फिगर केले आहे स्टॅक तयार करा, एक स्वतंत्र स्थापना फाइल नाही; तुमचे विद्यमान सक्तीचे खंड, HTTPS प्रॉक्सी, रहस्ये आणि बॅकअप ठेवा.

विद्यमान स्टॅकसाठी रांग-मोड तयार करा. खालील उदाहरण तुमच्या वर्तमान मध्ये विलीन करा compose.yaml; आहे नाही संपूर्ण स्टँड-अलोन तैनाती. हे गृहीत धरते की तुमच्याकडे आधीपासूनच कायम, खाजगी आहे postgres आणि n8n सेवा, विद्यमान N8N_VERSION आपल्या वातावरणात पिन करा आणि आपले स्वतःचे संरक्षित करा POSTGRES_PASSWORD आणि मूळ N8N_ENCRYPTION_KEY. त्याची नावे, खंड, डेटाबेस आणि n8n आवृत्ती विद्यमान प्रकल्पाशी जुळवा. रांग-मोड Redis सेटिंग्ज जोडा आणि EXECUTIONS_MODE=queue वर वर्णन केल्याप्रमाणे विद्यमान मुख्य सेवेसाठी देखील.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Redis किंवा या खंडातील कामगारासाठी कोणतेही होस्ट पोर्ट प्रकाशित केलेले नाही. Redis केवळ-जोडणे हा एक अतिरिक्त पुनर्प्राप्ती स्तर आहे, नाही ऑफ-सर्व्हर बॅकअपसाठी पर्याय. विद्यमान HTTPS आणि प्रमाणीकरण कॉन्फिगरेशन अपरिवर्तित ठेवा. बाह्य टास्क रनर्सची आवश्यकता असलेल्या कोड नोड्ससाठी, तुमच्या कामगार तैनातीसाठी रनर प्रक्रिया स्वतंत्रपणे कॉन्फिगर करा; रांग मोड स्वतः टास्क रनर बदलत नाही.

विद्यमान SQLite उदाहरण रूपांतरित करत आहात? फक्त बदलू नका DB_TYPE आणि रिक्त PostgreSQL डेटाबेसपासून प्रारंभ करा: असे केल्याने जुने वर्कफ्लो आणि क्रेडेन्शियल्स स्थलांतरित होत नाहीत. कोणत्याही कटओव्हरपूर्वी, स्त्रोत डेटाबेसचा बॅकअप घ्या, पर्सिस्टंट .n8n निर्देशिका आणि मूळ एनक्रिप्शन की; समर्थित n8n निर्यात/आयात किंवा स्थलांतर प्रक्रिया वापरा, नंतर वेगळ्या लक्ष्यावर वर्कफ्लो आणि एनक्रिप्टेड क्रेडेन्शियल सत्यापित करा. मूळ फाइल्स रोलबॅकसाठी ठेवा आणि पुनर्प्राप्तीच्या तयारीसाठी खाली लिंक केलेल्या बॅकअप आणि पुनर्संचयित मार्गदर्शकाचा वापर करा. कधीही हटवू नका database.sqlite शॉर्टकट म्हणून.

वर्कर्सची समांतर क्षमता

वर्कर्सची संख्या आणि प्रत्येक वर्करची समांतर कामे दोन्ही महत्त्वाची

प्रत्येक कामगार एकाच वेळी अनेक नोकऱ्यांवर प्रक्रिया करू शकतो. n8n ची वर्तमान डीफॉल्ट वर्कर कॉन्करन्सी 10 आहे आणि त्याचे दस्तऐवज 5 किंवा त्याहून अधिक समानतेची शिफारस करते. बऱ्याच कामगारांसह एकत्रितपणे खूप कमी संयोग अनावश्यक डेटाबेस कनेक्शन तयार करू शकतात आणि डेटाबेस कनेक्शन पूल संपुष्टात आणू शकतात.

समांतर कामांची मर्यादा कधी वाढवावी?

कामगाराकडे अतिरिक्त CPU आणि RAM असतात आणि वर्कफ्लो बहुतेक कॉम्प्युट किंवा मेमरी संतृप्त करण्याऐवजी बाह्य सेवांवर थांबतात.

अधिक वर्कर्स कधी जोडावेत?

एक कामगार प्रक्रिया अडथळे बनते आणि डेटाबेस, Redis आणि पायाभूत सुविधांमध्ये अधिक समांतर अंमलबजावणीची क्षमता असते.

समांतर कामांची मर्यादा कधी कमी करावी?

वैयक्तिक वर्कफ्लो मेमरी-हेवी किंवा CPU-जड असतात आणि समांतर नोकऱ्यांमुळे विवाद, OOM दबाव किंवा अस्थिर अंमलबजावणी वेळा होतात.

PostgreSQL वर लक्ष ठेवा

अधिक कामगार आणि अधिक संगम डेटाबेस क्रियाकलाप वाढवते. डेटाबेस क्षमतेशिवाय स्केलिंग अंमलबजावणी क्षमता अडथळे दूर करण्याऐवजी हलवू शकते.

कोणती समवर्ती मर्यादा प्रत्यक्षात लागू होते ते जाणून घ्या. एक कार्यकर्ता वापरून सुरू केले जाऊ शकते n8n worker --concurrency=5, किंवा तुमच्या कंपोझ सेवेमधील समतुल्य वर्कर कमांड. जर N8N_CONCURRENCY_PRODUCTION_LIMIT पेक्षा इतर मूल्यावर स्पष्टपणे सेट केले आहे -1, ती सेटिंग रांग मोडमध्ये प्राधान्य घेते; अन्यथा n8n कामगारांचा वापर करते --concurrency मूल्य किंवा त्याचे डीफॉल्ट 10. कामगारांची संख्या नाममात्र डीफॉल्टने गुणाकार करू नका आणि त्याला गॅरंटीड थ्रूपुट म्हणू नका: वास्तविक क्षमता कामाचा कालावधी, CPU, मेमरी, बाह्य API आणि PostgreSQL कनेक्शनवर अवलंबून असते.

वेबहुक

Queue Mode मुळे काम हस्तांतरित करताना विलंब वाढू शकतो

मुख्य किंवा वेबहुक प्रक्रियेस HTTP विनंती प्राप्त होते, परंतु कार्यकर्ता वर्कफ्लो अंमलबजावणी करतो. Redis द्वारे ते हँडऑफ काही ओव्हरहेड जोडते. विलंब-संवेदनशील वेबहुकसाठी, अधिक कामगार प्रत्येक विनंती आपोआप जलद करतात असे गृहित धरण्यापेक्षा एंड-टू-एंड प्रतिसाद वेळ मोजा.

प्राप्त करामुख्य/वेबहुक प्रक्रिया विनंती स्वीकारते.
रांगअंमलबजावणी Redis ला दिली जाते.
अंमलात आणाउपलब्ध कार्यकर्ता कार्यप्रवाह चालवतो.
प्रतिसाद द्याजेव्हा आवश्यक असेल तेव्हा परिणाम रांगेच्या मार्गाने परत पाठविला जातो.

वेबहुक ट्रॅफिकला योग्य प्रक्रियेकडे जा. समर्पित सह n8n webhook रिव्हर्स प्रॉक्सी किंवा लोड बॅलन्सरच्या मागे प्रोसेसर, रूट उत्पादन मार्ग /webhook/* आणि /webhook-waiting/* वेबहुक प्रोसेसरसाठी; ठेवा /webhook-test/*, मुख्य वर संपादक आणि API विनंत्या. उत्पादन वेबहुक लोड-बॅलेंसिंग पूलमध्ये मुख्य टाकू नका जोपर्यंत तुम्ही मुद्दामहून अतिरिक्त कामाचा भार स्वीकारत नाही. ए Webhook ला प्रतिसाद द्या वर्कफ्लो क्लायंटला कार्यकर्ता पूर्ण होईपर्यंत आणि त्याचा प्रतिसाद परत येईपर्यंत प्रतीक्षा करू शकतो, म्हणून रांग मोड हे त्वरित HTTP प्रतिसाद किंवा शून्य कालबाह्यतेचे वचन नाही. रहदारी स्विच करण्यापूर्वी वास्तविक बाह्य कॉलबॅक आणि प्रतिसाद वर्तन तपासा.

मोठी वेबहुक प्रतिसाद सीमा. वर्तमान n8n दस्तऐवजीकरण देते N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX चे डीफॉल्ट 64 MiB रांगेतून परत पाठवलेल्या कामगाराच्या प्रतिसादासाठी. केवळ हिरव्या कंटेनरवरच नव्हे तर कामगारावरील अंमलबजावणीची पडताळणी करा. योग्यरित्या कॉन्फिगर केलेल्या कंपोझ स्टॅकसह, तपासा docker compose ps आणि docker compose logs --tail=100 n8n-worker (वेगळे असल्यास सेवेचे नाव बदला). एक निरुपद्रवी चालवा प्रकाशित उत्पादन शेड्यूल्ड ट्रिगर किंवा टेस्ट वेबहुक वापरून वर्कफ्लो, नंतर n8n च्या एक्झिक्यूशन व्ह्यूमधील त्याची अंमलबजावणी वर्कर लॉगमधील वास्तविक कामगार प्रक्रियेशी जुळवा. एक संपादक जो यशस्वीरित्या उघडतो, एक चालू असलेला Redis कंटेनर किंवा रांगेत अंमलात आणला जातो नाही कार्यकर्त्याने काम केले आहे हे सिद्ध करा.

अवलंबित्व आणि तयारी तपासा. डीफॉल्ट उदाहरण सेवा नावांसह, docker compose exec -T redis redis-cli ping प्राप्त केले पाहिजे PONG जेव्हा Redis प्रमाणीकरण परवानगी देते, आणि docker compose exec -T postgres pg_isready -U n8n -d n8n PostgreSQL तत्परता तपासते (क्रेडेन्शियल्स आणि सेवा नावे जुळवून घेतात). सक्षम करा QUEUE_HEALTH_CHECK_ACTIVE=true जेव्हा तुम्हाला त्याची खाजगी गरज असते तेव्हा कामगारावर /healthz आणि /healthz/readiness अंतिम बिंदू; रेडिनेस एंडपॉइंट Redis/डेटाबेस कनेक्टिव्हिटी तपासते. केवळ त्यांचे निरीक्षण करण्यासाठी ते कामगार अंत्यबिंदू सार्वजनिकपणे उघड करू नका.
