क्षमता वाढवणे

n8n Queue Mode

रांग पद्धती कार्यप्रवाह अंमलबजावणीला मुख्य n8n प्रक्रियेपासून वेगळे करते. मुख्य उदाहरण ट्रिगर्स प्राप्त करते आणि अंमलबजावणी तयार करते, Redis रांगेत समन्वय साधते, कामगार नोकऱ्या अंमलात आणतात आणि PostgreSQL सामायिक कार्यप्रवाह आणि अंमलबजावणी डेटा संचयित करते.

झटपट निर्णय

तुम्हाला खरोखरच रांग मोडची गरज आहे का?

जेव्हा नियमित स्थितीत राहा

एकच उदाहरण सर्वोच्च अंमलबजावणी आरामात हाताळते आणि CPU, RAM आणि अंमलबजावणी विलंबता स्थिर राहते. रांग मोडमध्ये तुम्हाला अद्याप आवश्यक नसलेले घटक जोडले जातात.

जेव्हा रांग पद्धतीचा विचार करा

सातत्यपूर्ण समांतर फाशीमुळे वाद निर्माण होतो, अंमलबजावणीची विलंबता भाराखाली वाढते किंवा तुम्हाला अनेक कामगार चालवून अंमलबजावणीची क्षमता जोडण्याची आवश्यकता असते.

जेव्हा प्रथम अनुलंबपणे स्केल करा

अडथळा फक्त CPU किंवा RAM अपुरा आहे आणि एक मोठे उदाहरण अजूनही कामाचे ओझे स्वच्छपणे पूर्ण करू शकते.

वास्तुकला बदलण्यापूर्वी मोजमाप करा

या हालचालीचे समर्थन करण्यासाठी शिखर समवर्ती, CPU, RAM, अंमलबजावणीचा कालावधी, रांगेत खोली आणि डेटाबेस दाब वापरा.

प्रणालीची रचना

n8n क्यू मोड कसा कार्य करतो

1 मुख्यटाइमर, वेबहूक आणि वर्कफ्लो विनंत्या प्राप्त करते आणि निर्मितीची अंमलबजावणी स्वतःच करण्याऐवजी अंमलबजावणी तयार करते.
2§ · Redisसंदेश दलाल म्हणून काम करते. त्यात अंमलबजावणी संदेश प्रलंबित असतात जेणेकरून पुढील उपलब्ध कामगार नोकरीचा दावा करू शकेल.
3 कामगारएक्झिक्युशन आयडी प्राप्त करतो, सामायिक केलेल्या डेटाबेसमधून वर्कफ्लो डेटा लोड करतो, वर्कफ्लो चालवतो आणि निकाल परत लिहितो.
4§ · PostgreSQLसामायिक सातत्यपूर्ण कार्यप्रवाह आणि अंमलबजावणीची माहिती प्रदान करते. वितरित रांग पद्धतीला SQLite वर समर्थन नाही.

मूलभूत आवश्यकता

प्रत्येक रांग-मोड उपयोजनासाठी काय आवश्यक आहे

Redis

सर्व मुख्य आणि कामगार प्रक्रियांना रांग समन्वयासाठी वापरल्या जाणार्या Redis सेवेमध्ये विश्वासार्ह प्रवेश आवश्यक आहे.

PostgreSQL

मुख्य आणि कामगारांनी डेटाबेस सामायिक करणे आवश्यक आहे. रांग पद्धती ही एक वितरित रचना आहे आणि ती SQLite च्या आसपास तयार केली जाऊ नये.

n8n संरचना जुळत आहे

मुख्य आणि कामगारांनी रांग मोड चालवणे आवश्यक आहे आणि Redis, PostgreSQL आणि एन्क्रिप्टेड ओळखपत्रांमध्ये प्रवेश करण्यासाठी आवश्यक संरचना सामायिक करणे आवश्यक आहे.

कामगार क्षमता

कामगारांना त्यांनी अंमलात आणलेल्या कार्यप्रवाहासाठी पुरेशा CPU आणि RAM ची आवश्यकता असते. प्रक्रिया जोडल्याने प्रत्येक अंमलात आणण्याचा संसाधन खर्च कमी होत नाही.

विद्यमान सेल्फ-होस्टेड स्टॅकवर कतार मोड सक्षम करा. प्रथम याची पुष्टी करा की n8n मुख्य सेवा आणि प्रत्येक कामगार त्याच PostgreSQL डेटाबेस आणि Redis पर्यंत खाजगी नेटवर्कद्वारे पोहोचू शकतो. EXECUTIONS_MODE=queue मुख्य आणि कामगार आणि पुरवठा या दोन्हींवर QUEUE_BULL_REDIS_HOST=redis आणि QUEUE_BULL_REDIS_PORT=6379 केव्हा? redis तुमचे खरे'कंपोज'सेवा नाव आहे. वापरा DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres आणि जुळणी DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER आणि DB_POSTGRESDB_PASSWORD प्रत्येक प्रक्रियेवर, सेवा नावांचे उदाहरण बदलून तुमची नावे घ्या. अस्तित्वात असलेली अचूक नावे द्या. N8N_ENCRYPTION_KEY त्या सर्वांसाठी. केवळ एकाच कंपोज नेटवर्कवरील कंटेनर जोडण्यासाठी Redis किंवा PostgreSQL होस्ट पोर्ट कधीही प्रकाशित करू नका.

दुसरा संपादक नव्हे, तर कार्यकारी सुरू करा. समान पिन केलेली n8n प्रतिमा आवृत्ती आणि सामायिक सेटिंग्ज मुख्य म्हणून वापरून n8n कामगार सेवा जोडा, परंतु ती चालवा worker आदेश. जर तुम्ही त्या सेवेचे नाव दिले n8n-worker, यापासून सुरुवात करा docker compose up -d n8n-workerएका कामगारावर प्रत्यक्ष अंमलबजावणीची पुष्टी केल्यानंतर, तुम्ही त्याचा वापर करू शकता. docker compose up -d --scale n8n-worker=2 त्या सेवेतून दुसरा कामगार सुरू करण्यासाठी. ह्या एका सेवेमध्ये भर घातलेल्या आहेत. योग्यरित्या संरचित केलेले विद्यमान स्टॅक तयार करा, स्वतंत्र इंस्टॉलेशन फाइल नाही; तुमचे विद्यमान स्थिर खंड, HTTPS प्रॉक्सी, रहस्ये आणि बॅकअप ठेवा.

विद्यमान स्टॅकसाठी क्यू-मोड तुकडा तयार करा. खालील उदाहरण तुमच्या वर्तमानात मिसळा. compose.yaml; असे आहे नाही. एक संपूर्ण स्वतंत्र उपयोजन. असे गृहीत धरले जाते की तुमच्याकडे आधीच सातत्यपूर्ण, खाजगी आहे postgres आणि n8n विद्यमान सेवा N8N_VERSION तुमच्या वातावरणात पिन करा आणि तुमचे स्वतःचे संरक्षित करा POSTGRES_PASSWORD आणि मूळ N8N_ENCRYPTION_KEYत्याची नावे, खंड, डेटाबेस आणि n8n आवृत्ती सध्याच्या प्रकल्पाशी जुळवून घ्या. रांग-मोड Redis सेटिंग्ज जोडा आणि EXECUTIONS_MODE=queue वर वर्णन केल्याप्रमाणे विद्यमान मुख्य सेवेसाठी देखील.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Redis साठी किंवा या तुकड्यातील कामगारासाठी कोणतेही यजमान बंदर प्रकाशित केले जात नाही. Redis केवळ-परिशिष्ट सातत्य हा एक अतिरिक्त पुनर्प्राप्ती थर आहे, नाही. ऑफ-सर्व्हर बॅकअपसाठी एक पर्याय. विद्यमान HTTPS आणि प्रमाणीकरण संरचना अपरिवर्तित ठेवा. बाह्य कार्य चालकांची आवश्यकता असलेल्या कोड नोड्ससाठी, तुमच्या कामगार नियोजनासाठी धावपटू प्रक्रिया स्वतंत्रपणे संरचित करा; रांग मोड स्वतःच कार्य चालकांची जागा घेत नाही.

विद्यमान SQLite उदाहरण रूपांतरित करत आहात? फक्त बदलू नका DB_TYPE आणि रिकाम्या PostgreSQL डेटाबेसपासून सुरुवात कराः असे केल्याने जुन्या वर्कफ्लो आणि क्रेडेन्शियल्स स्थलांतरित होत नाहीत. कोणत्याही कटओव्हरपूर्वी, स्रोत डेटाबेसचा बॅकअप घ्या, सतत .n8n डिरेक्टरी आणि मूळ एन्क्रिप्शन की; समर्थित n8n एक्सपोर्ट/इम्पोर्ट किंवा मायग्रेशन प्रक्रिया वापरा, नंतर वेगळ्या लक्ष्यावर वर्कफ्लो आणि एन्क्रिप्टेड क्रेडेन्शियल्सची पडताळणी करा. मूळ फाइल्स रोलबॅकसाठी ठेवा आणि पुनर्प्राप्तीच्या तयारीसाठी खाली लिंक केलेले बॅकअप आणि रिस्टोर मार्गदर्शक वापरा. कधीही हटवू नका database.sqlite एक शॉर्टकट म्हणून.

वर्कर्सची समांतर क्षमता

प्रत्येक कामगाराला मोजणी आणि नोकऱ्या या दोन्हींच्या आधारे कामगार मोजमाप करतात.

प्रत्येक कामगार एकाच वेळी अनेक कामांवर प्रक्रिया करू शकतो. कलम n8n चे सध्याचे पूर्वनिर्धारित कामगार समवर्ती कलम 10 आहे आणि त्याचे दस्तऐवजीकरण कलम 5 किंवा त्याहून अधिक समवर्ती असण्याची शिफारस करते. अनेक कामगारांसह खूप कमी समवर्ती अनावश्यक डेटाबेस जोडणी तयार करू शकते आणि डेटाबेस जोडणी पूल संपवू शकते.

जेव्हा समवर्ती चलन वाढवा

कामगाराकडे अतिरिक्त CPU आणि RAM असतात आणि कामाचा प्रवाह बहुतेक वेळा गणना किंवा स्मृती संतृप्त करण्याऐवजी बाह्य सेवांवर प्रतीक्षा करत असतो.

जेव्हा कामगारांचा समावेश करा

एक कामगार प्रक्रिया एक अडथळा बनते आणि डेटाबेस, Redis आणि पायाभूत सुविधांमध्ये अधिक समांतर अंमलबजावणीची क्षमता असते.

जेव्हा समवर्ती चलन कमी करा

वैयक्तिक कार्यप्रवाह हे स्मृती-भारी किंवा CPU-भारी आणि समांतर कामे आहेत ज्यामुळे वाद निर्माण होतात, OOM दबाव किंवा अस्थिर अंमलबजावणी वेळा.

PostgreSQL पहा

अधिक कामगार आणि अधिक समवर्ती व्यवहार डेटाबेस क्रियाकलाप वाढवतात. डेटाबेस क्षमतेशिवाय अंमलबजावणी क्षमता मोजणे हे अडथळे दूर करण्याऐवजी हलवू शकते.

कोणती समवर्ती मर्यादा प्रत्यक्षात लागू होते हे जाणून घ्या. कामगार त्याचा वापर सुरू करू शकतो. n8n worker --concurrency=5, किंवा तुमच्या रचना सेवेतील समतुल्य कामगार आदेश. जर N8N_CONCURRENCY_PRODUCTION_LIMIT त्याखेरीज इतर मूल्यांवर स्पष्टपणे सेट केलेले आहे -1, त्या सेटिंगला कतार मोडमध्ये प्राधान्य दिले जाते; अन्यथा n8n कामगारांचा वापर करते --concurrency मूल्य किंवा त्याचे 10 चे पूर्वनिर्धारित मूल्य. कामगारांच्या मोजणीला नाममात्र पूर्वनिर्धारित पद्धतीने गुणाकार करू नका आणि त्याला गॅरंटीड थ्रूपुट म्हणू नकाः वास्तविक क्षमता नोकरीचा कालावधी, CPU, मेमरी, बाह्य API आणि PostgreSQL जोडणीवर अवलंबून असते.

वेबहुक

रांग मोड अंमलबजावणी हस्तांतराची विलंबता जोडू शकतो

मुख्य किंवा वेबहूक प्रक्रियेला HTTP ची विनंती प्राप्त होते, परंतु कामगार वर्कफ्लोची अंमलबजावणी करतो. Redis द्वारे हस्तांतरीत केल्याने काही ओव्हरहेड जोडले जाते. विलंब-संवेदनशील वेबहूकसाठी, अधिक कामगार प्रत्येक विनंती स्वयंचलितपणे जलद करतात असे गृहीत धरण्याऐवजी एंड-टू-एंड प्रतिसाद वेळ मोजा.

मिळवा.मुख्य/वेबहूक प्रक्रिया विनंती स्वीकारते.
रांगRedis ला फाशी दिली जाते.
अंमलात आणाएक उपलब्ध कामगार वर्कफ्लो चालवतो.
