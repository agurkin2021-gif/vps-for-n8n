उत्पादनासाठी सुरक्षा

VPS वरील n8n सुरक्षित करा

VPS वर n8n सुरक्षित करण्यासाठी, n8n (5678), PostgreSQL (5432) आणि पर्यायी Redis (6379) सार्वजनिक इंटरनेट बंद ठेवा; HTTPS रिव्हर्स प्रॉक्सी, SSH की आणि MFA वापरा, तुमची एनक्रिप्शन की जतन करा, वेबहुक प्रमाणित करा, धोकादायक वर्कफ्लो क्षमता मर्यादित करा आणि तैनात केलेल्या उदाहरणाचे ऑडिट करा. सार्वजनिक वेबहुक मार्गांपासून संपादकाचे वेगळे संरक्षण करा. HTTPS केवळ कनेक्ट केलेल्या सेवा सुरक्षित करत नाही.

n8n साठी VPS निवडा

भागीदार दुवा: आम्ही खरेदीतून कमिशन मिळवू शकतो.

झटपट तपासणी यादी

इंटरनेटवर उपलब्ध करण्यापूर्वी आवश्यक किमान सुरक्षा

तुमच्या पोहोचण्यायोग्य पोर्ट, HTTPS, सत्यापित प्रशासकीय प्रवेश, MFA आणि जतन केलेल्या क्रेडेन्शियल्सच्या संरक्षणासह प्रारंभ करा. प्रत्येक येणाऱ्या वेबहुकने संवेदनशील कार्य ट्रिगर करण्यापूर्वी प्रमाणीकृत करा. प्रवेश नियंत्रणे बदलल्यानंतर, इच्छित संपादक आणि बाह्य एकत्रीकरण अद्याप कार्य करत असल्याचे सत्यापित करा, नंतर n8n सुरक्षा ऑडिट चालवा.

फक्त HTTPS

योग्यरित्या कॉन्फिगर केलेल्या TLS रिव्हर्स प्रॉक्सीच्या मागे n8n ठेवा आणि संपादक आणि वेबहुकसाठी सातत्याने सार्वजनिक HTTPS URL वापरा.

फक्त आवश्यक पोर्ट उघडे ठेवा

सार्वजनिक वाहतुकीसाठी आवश्यक असलेली बंदरे उघडा. PostgreSQL, Redis आणि अंतर्गत अनुप्रयोग पोर्ट सार्वजनिक इंटरनेटपासून दूर ठेवा.

SSH सुरक्षा मजबूत करा

की-आधारित प्रशासन वापरा, कोण लॉग इन करू शकते हे प्रतिबंधित करा आणि ऑपरेटिंग सिस्टम पॅच ठेवा.

क्रेडेन्शियल संरक्षित करा

n8n एन्क्रिप्शन की स्थिर आणि गुप्त ठेवा. पर्यावरण फाइल्स, डेटाबेस ऍक्सेस आणि बॅकअप प्रतींना संवेदनशील मालमत्ता म्हणून हाताळा.

नेटवर्कची सीमा

रिव्हर्स प्रॉक्सी, HTTPS आणि विश्वसनीय HTTP हेडर्स

TLS टर्मिनेशन

HTTPS समाप्त करण्यासाठी Nginx, Caddy किंवा Traefik सारखी रिव्हर्स प्रॉक्सी वापरा. प्लेन HTTP पुनर्निर्देशित करा आणि जेव्हा प्रॉक्सी इच्छित प्रवेश बिंदू असेल तेव्हा थेट n8n अनुप्रयोग पोर्ट उघड करणे टाळा.

प्रॉक्सी कॉन्फिगरेशन

जेव्हा n8n रिव्हर्स प्रॉक्सीच्या मागे धावते, तेव्हा प्रॉक्सी हॉप संख्या योग्यरित्या कॉन्फिगर करा आणि फॉरवर्ड केलेले शीर्षलेख पास करा n8n मूळ क्लायंट विनंतीची पुनर्रचना करणे आवश्यक आहे.

सुरक्षित कुकीज

HTTPS पेक्षा जास्त संपादकाला सेवा द्या जेणेकरून प्रमाणीकरण कुकीज सुरक्षित राहू शकतील. कुकी सुरक्षा कमकुवत करून तुटलेल्या TLS सेटअपच्या आसपास काम करू नका.

वेबहुक URL

सार्वजनिक वेबहुक URL बाह्यरित्या पोहोचण्यायोग्य HTTPS होस्टनावावर सेट करा जेणेकरून व्युत्पन्न केलेले वेबहुक एंडपॉइंट्स अंतर्गत कंटेनर किंवा HTTP पत्त्याकडे निर्देशित करत नाहीत.

वेबहुक न तोडता संपादक खाजगी ठेवा. जेव्हा व्यावहारिक असेल तेव्हा VPN, विश्वसनीय-IP धोरण किंवा प्रमाणीकृत प्रॉक्सी वापरून व्यवस्थापन प्रवेश प्रतिबंधित करा. सार्वजनिक वेबहुक रिसीव्हर्स आणि OAuth कॉलबॅक मार्गांना पोहोचण्यायोग्य राहण्याची आवश्यकता असू शकते; प्रॉक्सी नियम लागू करण्यापूर्वी विश्वसनीय संपादक साइन-इन आणि वास्तविक बाह्य कॉलबॅक दोन्हीची चाचणी घ्या. क्लायंट-पत्ता शीर्षलेख केवळ विश्वसनीय प्रॉक्सींकडून फॉरवर्ड करा, अनियंत्रित विनंती शीर्षलेख नाही.

वेबहुक कॉलर ऑथेंटिकेट करा: वेबहुक नोडमध्ये प्रेषकाने सपोर्ट केल्यावर None ऐवजी बेसिक, हेडर किंवा JWT ऑथेंटिकेशन निवडा. त्याचा वापर करा IP(ची) अनुमती यादी जेथे योग्य असेल तेथे पर्याय, आणि जेथे एकीकरण स्वाक्षरी केलेल्या विनंत्यांना समर्थन देते तेथे प्रदात्याच्या स्वाक्षऱ्या सत्यापित करा. अंदाज लावायला अवघड URL पुरेसे प्रमाणीकरण नाही. जेव्हा योग्य असेल तेव्हा प्रॉक्सीवर दर मर्यादा लागू करा आणि वैध स्फोट अवरोधित नसल्याची पुष्टी करा. अधिकृत वेबहुक प्रमाणीकरण पर्याय.

VPS अधिक सुरक्षित करा

सर्व्हरवरील हल्ल्याची शक्यता कमी करा

फायरवॉल

अवांछित इनबाउंड रहदारी डीफॉल्ट-नकार द्या आणि फक्त त्या सेवांना परवानगी द्या ज्या पोहोचण्यायोग्य असणे आवश्यक आहे. डेटाबेस आणि Redis पोर्ट सामान्यतः खाजगी/स्थानिक नेटवर्कशी संबंधित असतात.

SSH

संकेतशब्दांपेक्षा SSH की ला प्राधान्य द्या, अनावश्यक लॉगिन मार्ग अक्षम करा आणि प्रशासकीय प्रवेश मर्यादित करा. रूट-समतुल्य प्रवेश घट्टपणे नियंत्रित केला पाहिजे.

OS अद्यतने

Linux होस्ट आणि कंटेनर रनटाइम पॅच करा. ऍप्लिकेशन हार्डनिंग उघड किंवा अप्रचलित ऑपरेटिंग सिस्टमची भरपाई करू शकत नाही.

कंटेनर एक्सपोजर

फक्त तेच पोर्ट प्रकाशित करा ज्यांना होस्ट ऍक्सेसची आवश्यकता आहे. अंतर्गत सेवांनी सार्वजनिक इंटरफेस ऐवजी खाजगी Docker नेटवर्कवर संवाद साधला पाहिजे.

फायरवॉल किंवा SSH सेटिंग्ज बदलण्यापूर्वी तपासणी करा: सह ऐकण्याचे पोर्ट तपासा sudo ss -lntp, Docker सह प्रकाशन docker compose ps प्रोजेक्ट डिरेक्टरीमधून, आणि होस्ट फायरवॉल पॉलिसीसह sudo ufw status verbose UFW वापरले असल्यास. पासवर्ड ऍक्सेस अक्षम करण्यापूर्वी एका वेगळ्या सत्रात तुमचा वास्तविक SSH पोर्ट आणि यशस्वी की लॉगिन तपासा. प्रकाशित Docker पोर्ट UFW नियमांना बायपास करू शकतात; केवळ फायरवॉल स्थिती पृष्ठ हे पोर्ट 5678 खाजगी असल्याचे सिद्ध करत नाही. वास्तविक बाह्य पोहोचता तपासा. Docker/UFW चेतावणी.

स्वयंचलित Ubuntu सुरक्षा अद्यतने कार्य करतात असे मानण्याऐवजी तपासा: तपासणी apt-config dump APT::Periodic::Unattended-Upgrade आणि लॉग /var/log/unattended-upgrades/unattended-upgrades.log. अप्राप्य सुरक्षा अपग्रेड अक्षम केले असल्यास, sudo dpkg-reconfigure unattended-upgrades सपोर्टेड कॉन्फिगरेशन डायलॉग पुरवतो. कार्यरत VPS वर सक्षम करण्यापूर्वी रीबूट आणि सेवा-रीस्टार्ट वर्तनाचे पुनरावलोकन करा. Ubuntu APT अद्यतने करतात नाही n8n Docker प्रतिमा किंवा प्रत्येक तृतीय-पक्ष सॉफ्टवेअर रेपॉजिटरी स्वयंचलितपणे अद्यतनित करा. Ubuntu स्वयंचलित-अपडेट दस्तऐवजीकरण.

पर्यायी SSH ब्रूट-फोर्स मॉनिटरिंग: Fail2Ban वारंवार अयशस्वी SSH लॉगिन शोधू शकतो. SSH साठी स्थापित आणि कॉन्फिगर केले असल्यास, यासह जेलची पडताळणी करा sudo fail2ban-client status sshd आणि पुष्टी करा की ते तुमचे वास्तविक SSH प्रमाणीकरण लॉग किंवा जर्नल वाचते आणि कॉन्फिगर केलेल्या पोर्टशी जुळते. हे SSH की आणि नेटवर्क निर्बंधांना पूरक आहे; ते त्यांना बदलत नाही. प्रथम विद्यमान प्रवेश तपासल्याशिवाय निश्चित SSH पोर्ट किंवा प्रतिबंध नियम कॉपी करू नका. Ubuntu SSH कठोर मार्गदर्शन.

डेटाबेस आणि Redis

बॅकएंड सेवा खाजगी ठेवा

ठराविक Docker कंपोझ सेटअपमध्ये, PostgreSQL आणि रांग-मोड Redis खाजगी नेटवर्किंगद्वारे संबंधित कंटेनरद्वारे पोहोचण्यायोग्य असावे, होस्ट-प्रकाशित पोर्ट्सद्वारे नाही. सह सत्यापित करा docker compose ps 5432 आणि 6379 सार्वजनिकरित्या प्रकाशित केलेले नाहीत; स्वतंत्रपणे VPS/क्लाउड फायरवॉल एक्सपोजरचे पुनरावलोकन करा. नेटवर्क पॉलिसी किमान-विशेषाधिकार डेटाबेस क्रेडेन्शियल्सला पर्याय देत नाहीत.

PostgreSQLरिमोट ऍक्सेस स्पष्टपणे आवश्यक आणि स्वतंत्रपणे सुरक्षित केल्याशिवाय ते खाजगी इंटरफेस किंवा कंटेनर नेटवर्कशी बांधा.
Redisरांग-मोड Redis पायाभूत सुविधा आहे, सार्वजनिक अंत्यबिंदू नाही. आवश्यक असलेल्या n8n घटकांसाठी नेटवर्क प्रवेश प्रतिबंधित करा.
ओळखपत्रेअनुप्रयोगास आवश्यक असलेल्या परवानग्यांसह समर्पित डेटाबेस क्रेडेन्शियल्स वापरा आणि त्यांना स्त्रोत नियंत्रणाबाहेर संरक्षित करा.
वाहतूकजेव्हा डेटाबेस ट्रॅफिक अविश्वासू नेटवर्क्स ओलांडते, तेव्हा ऍप्लिकेशन-स्तरीय क्रेडेंशियल एन्क्रिप्शनवर अवलंबून न राहता योग्य एनक्रिप्टेड वाहतूक वापरा.

n8n च्या गुप्त की

एन्क्रिप्शन की आणि क्रेडेन्शियल सीमा संरक्षित करा

एनक्रिप्शन की

n8n त्याची एन्क्रिप्शन की वापरून संचयित क्रेडेन्शियल एन्क्रिप्ट करते. रीस्टार्ट आणि कामगारांमध्ये समान की जतन करा आणि सामान्य अनुप्रयोग सामग्रीपासून वेगळे संरक्षित करा.

एन्व्हायर्नमेंटमधील गुप्त मूल्ये

सार्वजनिक भांडारासाठी पासवर्ड, टोकन किंवा एनक्रिप्शन की कमिट करू नका. पर्यावरण फाइल्स आणि उपयोजन रहस्ये प्रवेश प्रतिबंधित करा.

वापरकर्ता प्रवेश

फक्त विश्वसनीय वापरकर्त्यांना संपादक प्रवेश द्या. वर्कफ्लो संवेदनशील प्रणालींशी कनेक्ट होऊ शकतात आणि गुपितांवर प्रक्रिया करू शकतात किंवा शक्तिशाली नोड्स कार्यान्वित करू शकतात.

क्रेडेन्शियल स्कोप

जेथे शक्य असेल तेथे अल्प प्रमाणात सेवा खाती आणि API टोकन वापरा. तडजोड केलेल्या वर्कफ्लोला आपोआप असंबंधित सिस्टीमवर व्यापक प्रवेश मिळू नये.

पुनरावलोकन करण्यासाठी n8n कॉन्फिगरेशन: N8N_BLOCK_ENV_ACCESS_IN_NODE=true पर्यावरण मूल्यांमध्ये कोड-नोड आणि अभिव्यक्ती प्रवेश प्रतिबंधित करते; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true सेटिंग्ज फाइलवर फक्त-मालक परवानगीची विनंती करते. ठेवा N8N_ENCRYPTION_KEY पर्सिस्टंट आणि सुरक्षितपणे बॅकअप: n8n पहिल्या स्टार्टअपवर एक यादृच्छिक की तयार करू शकते, परंतु ती गमावल्यास विद्यमान एनक्रिप्टेड क्रेडेन्शियल्स निरुपयोगी होऊ शकतात. प्रोडक्शन एनक्रिप्शन की आकस्मिकपणे बदलू नका; अधिकृतपणे समर्थित रोटेशन प्रक्रिया वापरा. पर्यावरण प्रवेश अवरोधित केल्याने विद्यमान एकीकरण खंडित होऊ शकते, म्हणून उत्पादन बदलण्यापूर्वी चाचणी करा. n8n सुरक्षा व्हेरिएबल व्याख्या.

वर्कफ्लोचे धोके
