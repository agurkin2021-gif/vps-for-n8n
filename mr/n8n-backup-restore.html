n8n बॅकअप आणि पुनर्संचयन

सेल्फ-होस्टेड n8n चा बॅकअप आणि पुनर्संचयित करण्यासाठी, तुमचा SQLite डेटाबेस किंवा सातत्यपूर्ण PostgreSQL डंप, पर्सिस्टंट .n8n फोल्डर आणि मूळ एन्क्रिप्शन की, डिप्लॉयमेंट कॉन्फिगरेशन आणि प्रत्येक बाह्य बायनरी किंवा माउंटेड-फाइल अवलंबित्व संरक्षित करा. VPS वरून एनक्रिप्टेड प्रत ठेवा आणि वेगळ्या उदाहरणावर पुनर्प्राप्तीची चाचणी करा. निवडक पुनर्प्राप्तीसाठी CLI कार्यप्रवाह आणि क्रेडेन्शियल निर्यात वापरा; JSON केवळ निर्यात पूर्ण सर्व्हर बॅकअप नाही.

डेटाबेस

उदाहरणाद्वारे वापरलेल्या PostgreSQL डेटाबेस किंवा SQLite डेटाबेस फाइलचा बॅकअप घ्या. डेटाबेसमध्ये मुख्य n8n स्थिती असते जसे की वर्कफ्लो, क्रेडेन्शियल्स आणि एक्झिक्यूशन डेटा.

एनक्रिप्शन की

अचूक n8n एन्क्रिप्शन की स्वतंत्रपणे आणि सुरक्षितपणे जतन करा. पुनर्संचयित एनक्रिप्टेड क्रेडेन्शियल समान की वर अवलंबून असतात.

पर्सिस्टंट फाइल्स

पर्सिस्टंट n8n डेटा डिरेक्टरी आणि कोणत्याही माउंट केलेल्या फाइल्स, बायनरी-डेटा स्टोरेज किंवा वर्कफ्लो मालमत्ता समाविष्ट करा ज्यावर तुमची तैनाती अवलंबून आहे.

डिप्लॉयमेंट कॉन्फिगरेशन

कम्पोज/कॉन्फिगरेशन फाइल्स आणि स्टॅक पुन्हा तयार करण्यासाठी आवश्यक नसलेले कॉन्फिगरेशन ठेवा. योग्य प्रवेश नियंत्रणांसह रहस्ये संरक्षित करा.

बॅकअपचे दोन स्तर

डेटा एक्स्पोर्ट विरुद्ध संपूर्ण आपत्तीनंतरची पुनर्प्राप्ती

वर्कफ्लो आणि क्रेडेन्शियल्स एक्स्पोर्ट

n8n CLI निर्यात स्थलांतर, आवृत्तीत वर्कफ्लो प्रती आणि निवडक पुनर्संचयनासाठी उपयुक्त आहेत. क्रेडेन्शियल्स एन्क्रिप्टेड स्वरूपात निर्यात केले जाऊ शकतात आणि जुळणाऱ्या एनक्रिप्शन कीसह नंतर आयात केले जाऊ शकतात. फक्त एक वर्कफ्लो पुनर्प्राप्त करण्यासाठी, त्याचे JSON डाउनलोड करण्यासाठी वर्कफ्लो एडिटरचा थ्री-डॉट मेनू वापरा, नंतर नवीन पुनरावलोकन वर्कफ्लो किंवा वेगळ्या उदाहरणामध्ये फाइलमधून आयात करा. थेट वर्कफ्लो बदलण्यापूर्वी क्रेडेन्शियल, वर्कफ्लो आयडी आणि नोड पॅरामीटर्स तपासा: वर्कफ्लो JSON पुनर्संचयित केल्याने संपूर्ण सर्व्हर पुनर्संचयित होत नाही.

एंटिटी एक्स्पोर्ट

CLI समर्थित डेटाबेस प्रकारांमध्ये डेटा हलविण्यासाठी डेटाबेस घटक निर्यात करू शकते. अंमलबजावणी-इतिहास सारण्या पर्यायी आहेत कारण ते खूप मोठे असू शकतात.

संपूर्ण n8n इन्स्टन्सची पुनर्प्राप्ती

डेड-सर्व्हर परिस्थितीसाठी, वास्तविक डेटाबेस, एनक्रिप्शन की, पर्सिस्टंट डेटा आणि डिप्लॉयमेंट अवलंबित्व संरक्षित करा. वर्कफ्लो JSON निर्यात संपूर्ण उदाहरणाची पुनर्रचना करते असे गृहीत धरू नका.

प्रदात्याचे स्नॅपशॉट

एक VPS स्नॅपशॉट अतिरिक्त पुनर्प्राप्ती स्तर म्हणून उपयुक्त आहे, परंतु ती एकमेव प्रत नसावी आणि स्वतंत्रपणे सत्यापित अनुप्रयोग/डेटाबेस बॅकअप बदलू नये.

डेटाबेस

डेटाबेसचा सुसंगत बॅकअप घ्या

PostgreSQL

एक सुसंगत PostgreSQL बॅकअप पद्धत वापरा आणि परिणामी बॅकअप VPS पासून दूर ठेवा. त्याच अयशस्वी डिस्कवरील डेटाबेस प्रत म्हणजे आपत्ती पुनर्प्राप्ती नाही.

SQLite

डिप्लॉयमेंट SQLite वापरत असल्यास, डेटाबेस फाइलला पर्सिस्टंट n8n डेटा डिरेक्ट्रीपासून संरक्षित करा. डेटाबेस सक्रियपणे बदलत असताना असुरक्षित स्थितीत कॉपी करणे टाळा.

अंमलबजावणीचा इतिहास

ऐतिहासिक अंमलबजावणी डेटा तुमच्या पुनर्प्राप्ती उद्दिष्टाचा भाग आहे की नाही ते ठरवा. हे बॅकअप मोठ्या प्रमाणात वाढवू शकते, म्हणून धारणा आणि अनुपालन आवश्यकतांनी निवड चालविली पाहिजे.

डेटाबेस आवृत्ती

स्त्रोत उपयोजनाद्वारे वापरलेले डेटाबेस इंजिन आणि आवृत्ती रेकॉर्ड करा जेणेकरून पुनर्प्राप्ती वातावरण सुसंगतपणे तयार केले जाऊ शकते.

PostgreSQL एक Docker कंपोझ VPS वर. PostgreSQL सेवेचे नाव असल्यास postgres आणि त्याचा डेटाबेस/वापरकर्ता दोन्ही आहेत n8n, खालील आदेश होस्टवर एक सुसंगत PostgreSQL सानुकूल-स्वरूप डंप तयार करते. चालवण्यापूर्वी तुमची वास्तविक रचना फाइल तपासा आणि डेटाबेस क्रेडेन्शियल आणि सेवा नावे समायोजित करा. pg_dump PostgreSQL चालू असताना तार्किकदृष्ट्या सुसंगत स्नॅपशॉट तयार करू शकतो; ते करते नाही वेगळे बॅक अप घ्या .n8n वापरकर्ता फोल्डर किंवा बाह्य बायनरी डेटा.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

संग्रह-सूची तपासणी स्पष्ट स्वरूप समस्या पकडते परंतु डेटा पुनर्संचयित केला जाऊ शकतो हे सिद्ध करत नाही. एक एन्क्रिप्टेड कॉपी ऑफ-सर्व्हर संचयित करा आणि पुनर्संचयित करा. डेटाबेस-विशिष्ट पर्यायांसाठी अधिकृत PostgreSQL pg_dump दस्तऐवजीकरण वापरा.

Docker वर SQLite. डीफॉल्ट SQLite तैनातीसाठी, database.sqlite आणि व्युत्पन्न केलेले एनक्रिप्शन-की कॉन्फिगरेशन पर्सिस्टंटमध्ये राहतात .n8n फोल्डर (सामान्यपणे येथे आरोहित /home/node/.n8n). SQLite ची साधी थेट प्रत कधीही सुसंगत मानू नका. फोल्डर कॉपी करण्यापूर्वी n8n आणि इतर डेटाबेस लेखकांना थांबवा किंवा व्यत्यय आणणे अशक्य असताना SQLite ची समर्थित ऑनलाइन बॅकअप यंत्रणा वापरा:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

या सेवा आणि दाखवलेल्या मार्गासाठी उदाहरणात्मक आदेश आहेत, सार्वत्रिक व्हॉल्यूम लेआउट नाही. कॉपी केलेले फोल्डर सुरुवातीला त्याच VPS वर आहे; ते ऑफ-सर्व्हर हस्तांतरण आणि संरक्षित करा. जेव्हा रांगेतील कामगार किंवा इतर लेखक अस्तित्वात असतात, तेव्हा त्यांनाही शांत करा आणि त्यांच्या वास्तविक उपयोजन डिझाइनचे अनुसरण करा. n8n चे वर्तमान पूर्ण-बॅकअप मार्गदर्शन दस्तऐवज SQLite सातत्य आवश्यकता.

डीफॉल्ट SQLite फोल्डर स्वच्छ लक्ष्यावर पुनर्संचयित करणे: प्रथम n8n सेवा आणि सर्व डेटाबेस लेखक थांबवा. एकदा सुसंगत n8n सेवा कंटेनर आणि त्याचे गंतव्य व्हॉल्यूम अस्तित्वात आल्यावर, बॅक-अप कॉपी करा .n8n सामग्री परत समान पर्सिस्टंट डिरेक्टरीमध्ये. हे लक्ष्य फायली ओव्हरराइट करते, म्हणून तुम्हाला ठेवण्यासाठी आवश्यक असलेल्या डेटासह ती चालवू नका:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker थांबलेल्या कंटेनरवर कॉपी करू शकते, परंतु गंतव्यस्थानाची मालकी मूळपेक्षा वेगळी असू शकते; पुनर्संचयित कॉन्फिगरेशन आणि डेटाबेस फाइल सुरू करण्यापूर्वी n8n प्रक्रियेद्वारे वाचनीय आणि लिहिण्यायोग्य असल्याची खात्री करा. तुमचे खरे कंपोझ कॉन्फिगरेशन वेगळे पथ किंवा बाइंड माउंट वापरत असल्यास, त्यानुसार कॉपी जुळवून घ्या. Docker कॉपी संदर्भ तयार करा. एक n8n फोल्डर पुनर्संचयित करणे स्वतंत्र PostgreSQL डेटाबेस वापरणाऱ्या उपयोजनांसाठी पुरेसे नाही.

अत्यावश्यक गुप्त की

एन्क्रिप्शन की पुनर्प्राप्तीचा भाग आहे

n8n इन्स्टन्स एन्क्रिप्शन की सह संचयित क्रेडेन्शियल्स एन्क्रिप्ट करते. जुळणाऱ्या की शिवाय डेटाबेस किंवा एन्क्रिप्टेड क्रेडेन्शियल एक्सपोर्ट केल्याने पुनर्संचयित वर्कफ्लो त्यांचे जतन केलेले क्रेडेन्शियल वापरण्यात अक्षम राहू शकतात.

आपण N8N_ENCRYPTION_KEY सेट केल्यास, ते अचूक रहस्य पुनर्संचयित करा. अन्यथा व्युत्पन्न केलेली की पर्सिस्टंट .n8n/कॉन्फिग फाइलमध्ये साठवली जाते: बॅकअप घेताना किंवा पुनर्बांधणी करताना त्या कॉन्फिगचे संरक्षण करा. पुनर्प्राप्ती की VPS च्या बाहेर सुरक्षितपणे साठवा. रांग मोडमध्ये, सर्व मुख्य आणि कार्यकर्ता प्रक्रियांनी समान की वापरणे आवश्यक आहे.

कराउत्पादनाद्वारे वापरलेल्या अचूक कीची संरक्षित प्रत ठेवा.
कराक्रेडेन्शियल्सची चाचणी करण्यापूर्वी पुनर्प्राप्ती वातावरण ती की वापरते याची पडताळणी करा.
करू नकासर्व्हरची पुनर्बांधणी केल्यानंतर नव्याने व्युत्पन्न केलेल्या कीवर अवलंबून रहा.
करू नकासार्वजनिक भांडाराची किल्ली द्या किंवा ती असुरक्षित बॅकअपच्या बाजूला ठेवा.

फाईल्स आणि बायनरी डेटा

डेटाबेस बॅकअप प्रत्येक वर्कफ्लो अवलंबित्व कव्हर करू शकत नाही

पर्सिस्टंट .n8n डेटा

केवळ कंटेनर प्रतिमाच नव्हे तर वास्तविक .n8n वापरकर्ता फोल्डर शोधा आणि जतन करा. ठराविक Docker तैनातीमध्ये ते /home/node/.n8n वर माउंट केले जाते; Docker बाहेर डीफॉल्ट ~/.n8n आहे. जर N8N_USER_FOLDER कॉन्फिगर केले असेल, तर n8n त्या निर्दिष्ट केलेल्या मूळ निर्देशिकेत .n8n तयार करते. तुमची स्थापना वापरत असलेली कॉन्फिगरेशन की आणि कोणताही स्थानिक SQLite, बायनरी किंवा फाइल सिस्टम एक्झिक्यूशन डेटा समाविष्ट करा.

माउंट केलेल्या वर्कफ्लो फाइल्स

जर वर्कफ्लोने होस्ट-माउंट केलेल्या डिरेक्टरी वाचल्या किंवा लिहिल्या, तर त्या डिरेक्टरीजचा स्वतंत्रपणे बॅकअप घ्या. त्यांच्याशिवाय n8n पुनर्संचयित केल्याने अन्यथा वैध कार्यप्रवाह खंडित होऊ शकतो.

बायनरी डेटा
