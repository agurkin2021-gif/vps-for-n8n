n8n 队列模式

队列模式将工作流执行与主 n8n 流程分开。主实例接收触发器并创建执行，Redis 协调队列，工作人员执行作业，PostgreSQL 存储共享工作流和执行数据。

快速决策

你真的需要队列模式吗？

保持常规模式时

单个实例可以轻松处理峰值执行，并且 CPU、RAM 和执行延迟保持稳定。队列模式添加了您还不需要的组件。

当以下情况时考虑队列模式

持续的并行执行会产生争用，负载下执行延迟会增加，或者您需要通过运行多个工作线程来增加执行能力。

首先垂直缩放

瓶颈只是不够 CPU 或 RAM，一个更大的实例仍然可以干净地满足工作负载。

更改架构之前进行测量

使用峰值并发性、CPU、RAM、执行持续时间、队列深度和数据库压力来证明移动的合理性。

建筑

n8n 队列模式如何工作

1· 主要接收计时器、Webhook 和工作流请求并创建执行，而不是自行执行生产执行。
2·Redis充当消息代理。它保存待处理的执行消息，以便下一个可用的工作人员可以领取工作。
3·工人接收执行 ID，从共享数据库加载工作流数据，运行工作流并将结果写回。
4·PostgreSQL提供共享的持久工作流程和执行数据。 SQLite 不支持分布式队列模式。

核心要求

每个队列模式部署需要什么

Redis

所有主进程和工作进程都需要可靠地访问用于队列协调的 Redis 服务。

PostgreSQL

Main 和worker 必须共享数据库。队列模式是分布式架构，不应该围绕 SQLite 来设计。

匹配 n8n 配置

Main 和 Worker 必须运行队列模式并共享访问 Redis、PostgreSQL 和加密凭据所需的配置。

工人容量

工作人员需要足够的 CPU 和 RAM 来执行他们执行的工作流程。添加进程并不会消除每次执行的资源成本。

在现有自承载堆栈上启用队列模式。 首先确认 n8n 主要服务和每个工作人员都可以通过专用网络访问相同的 PostgreSQL 数据库和 Redis。套装 EXECUTIONS_MODE=queue 主要和工人，以及供应 QUEUE_BULL_REDIS_HOST=redis 和 QUEUE_BULL_REDIS_PORT=6379 当 redis 是您实际的 Compose 服务名称。使用 DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres 和匹配 DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER 和 DB_POSTGRESDB_PASSWORD 在每个过程中；将示例服务名称替换为您的服务名称。提供准确的现有信息 N8N_ENCRYPTION_KEY 对他们所有人。切勿仅仅为了连接同一 Compose 网络上的容器而发布 Redis 或 PostgreSQL 主机端口。

启动一个执行器，而不是第二个编辑器。 使用与主要相同的固定 n8n 映像版本和共享设置添加 n8n 辅助服务，但使用 worker 命令。如果您将该服务命名为 n8n-worker, 开始于 docker compose up -d n8n-worker。确认一个worker的实际执行后，您可以使用 docker compose up -d --scale n8n-worker=2 从该服务启动第二个工作人员。这些是对 现有的正确配置 撰写堆栈，而不是独立的安装文件；保留现有的持久卷、HTTPS 代理、机密和备份。

队列模式为现有堆栈编写片段。 将下面的示例合并到您当前的示例中 compose.yaml;是的 不 完整的独立部署。它假设你已经拥有持久的、私有的 postgres 和 n8n 服务，现有的 N8N_VERSION 固定在您的环境和您自己的受保护的环境中 POSTGRES_PASSWORD 和原创的 N8N_ENCRYPTION_KEY。将其名称、卷、数据库和 n8n 版本与现有项目相匹配。添加队列模式 Redis 设置并 EXECUTIONS_MODE=queue 如上所述，也适用于现有的主要服务。

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

没有为 Redis 或此片段中的工作程序发布主机端口。 Redis 仅附加持久性是一个额外的恢复层， 不 离线备份的替代品。保持现有 HTTPS 和身份验证配置不变。对于需要外部任务运行程序的代码节点，请单独为您的工作部署配置运行程序进程；队列模式本身并不能取代任务运行器。

转换现有的 SQLite 实例？ 不要简单地改变 DB_TYPE 并从空的 PostgreSQL 数据库开始：这样做不会迁移旧的工作流程和凭据。在任何切换之前，备份源数据库，持久化 .n8n 目录和原始加密密钥；使用受支持的 n8n 导出/导入或迁移程序，然后在单独的目标上验证工作流程和加密凭据。保留原始文件以进行回滚，并使用下面链接的备份和恢复指南进行恢复准备。绝不删除 database.sqlite 作为捷径。

工人并发

工人按数量和每个工人的工作量进行扩展

每个工人可以同时处理多个作业。 n8n 当前的默认工作线程并发度为 10，其文档建议并发度为 5 或更高。非常低的并发性与许多工作线程相结合可能会创建不必要的数据库连接并耗尽数据库连接池。

当以下情况时增加并发性：

工作人员有空闲的 CPU 和 RAM，并且工作流程主要等待外部服务，而不是使计算或内存饱和。

添加工人时

一个工作进程成为瓶颈，数据库、Redis 和基础设施有能力进行更多并行执行。

当以下情况时减少并发

各个工作流程内存繁重或 CPU 重，并行作业会导致争用、OOM 压力或不稳定的执行时间。

观看 PostgreSQL

更多的工作人员和更多的并发性会增加数据库活动。在没有数据库容量的情况下扩展执行容量可以移动而不是消除瓶颈。

了解实际适用的并发限制。 一个worker可以开始使用 n8n worker --concurrency=5，或 Compose 服务中的等效工作命令。如果 N8N_CONCURRENCY_PRODUCTION_LIMIT 显式设置为除 -1，该设置在队列模式下优先；否则 n8n 使用工人的 --concurrency 值或其默认值 10。不要将工作线程数乘以名义默认值，并将其称为保证吞吐量：实际容量取决于作业持续时间、CPU、内存、外部 API 和 PostgreSQL 连接。

网络钩子

队列模式会增加执行切换延迟

主进程或 Webhook 进程接收 HTTP 请求，但工作人员执行工作流执行。通过 Redis 的切换增加了一些开销。对于延迟敏感的 Webhook，测量端到端响应时间，而不是假设更多工作人员自动使每个请求更快。

接收Main/webhook 进程接受请求。
队列执行交给 Redis。
执行可用的工作人员运行工作流程。
回应当需要时，结果通过队列路径转发回来。

将 Webhook 流量路由到正确的进程。 配有专用 n8n webhook 反向代理或负载均衡器后面的处理器，路由生产路径 /webhook/* 和 /webhook-waiting/* 到 webhook 处理器；保留 /webhook-test/*、编辑器和 API 对 main 的请求。不要将 main 放入生产 Webhook 负载平衡池中，除非您故意接受增加的工作负载。一个 响应 Webhook 工作流可能会让客户端等待，直到工作程序完成并返回其响应，因此队列模式并不能保证即时 HTTP 响应或零超时。在切换流量之前测试实际的外部回调和响应行为。

二进制数据

不要忽视共享存储

文件系统限制

队列模式不支持文件系统二进制数据存储作为分布式工作人员的共享持久性模型。

外部二进制存储

当工作流必须跨分布式工作人员保存二进制数据时，请使用每个所需实例都可以访问的存储设计，例如支持的外部对象存储。

大型 Webhook 响应

来自工作人员的 Webhook 响应返回到接收进程。大型响应主体会增加 Redis 内存压力，并且需要精心设计的响应存储配置。

分配工人之前做好计划

在工作人员跨机器分布之前，必须重新设计严重依赖于本地文件的工作负载以实现共享持久性。

大型 Webhook 响应边界。 当前的 n8n 文档给出了 N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX 默认为 64 MiB 通过队列发回工作人员的响应。 Redis 可以在运行中保存多个副本，因此每个并发大型响应的预算大约是 Redis 内存中响应大小的 1.5 倍。如果没有卸载，过大的响应就会失败，而不是通过添加工作人员来神奇地变得更快。

版本和许可证限制。 从 n8n 2.34.0，工人可以使用 N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true 将过大的 Webhook 响应主体卸载到可读的共享二进制存储，但首先升级 每个主处理器和 Webhook 处理器 到 2.34.0 或更高版本。所选择的 N8N_DEFAULT_BINARY_DATA_MODE 必须实际存储数据并且可由每个参与进程读取。外部 S3 和 Azure 二进制存储需要有效的自托管 商业或企业 许可证；不要假设社区版可以启用它们。的 database 二进制模式可以卸载超大响应，无需付费外部存储，但主实例将整个存储体加载到内存中，并且数据库存储有自己的文件大小限制。对于 专门卸载响应主体，n8n 还描述了一个共享的 filesystem 当每个实例安装同一磁盘时的选项，但明确不建议这种安排。不要将此特殊的卸载路径误认为是在分布式队列模式部署中支持基于文件系统的持久二进制数据。在启用卸载之前，请检查您的版本、版本和存储配置。

监控

了解队列是否有帮助

队列深度

队列的增长速度快于工作人员的消耗速度，表明执行能力不足或存在下游瓶颈。

工人 CPU 和 RAM

测量每个工作人员的饱和度和内存峰值。队列不断增加的闲置工人指出了另一个限制。

执行延迟

跟踪创建执行和实际启动之间的延迟，而不仅仅是工作流运行时本身。

健康检查

工作线程运行状况端点可以报告工作线程是否处于活动状态以及其数据库和 Redis 连接是否准备就绪。

验证工作线程的执行情况，而不仅仅是绿色容器。 使用正确配置的 Compose 堆栈，检查 docker compose ps 和 docker compose logs --tail=100 n8n-worker （如果不同，请替换服务名称）。运行无害 出版作品 使用计划触发器或测试 Webhook 运行工作流，然后将 n8n 的执行视图中的执行与工作日志中的实际工作处理进行匹配。成功打开的编辑器、正在运行的 Redis 容器或单独的排队执行 不 证明工人已经完成了该工作。

检查依赖性和准备情况。 使用默认示例服务名称， docker compose exec -T redis redis-cli ping 应该收到 PONG 当 Redis 身份验证允许时，并且 docker compose exec -T postgres pg_isready -U n8n -d n8n 检查 PostgreSQL 准备情况（调整凭证和服务名称）。启用 QUEUE_HEALTH_CHECK_ACTIVE=true 当你需要它的私有时，在工人身上 /healthz 和 /healthz/readiness 终点；就绪端点检查 Redis/数据库连接。不要仅仅为了监视而公开这些工作端点。

手动运行是一种不同的测试。 默认情况下 OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false，因此即使正确配置了队列模式，在编辑器中手动运行工作流也可以在 main 上执行。将其设置为 true 仅当您打算向工作人员发送手动执行并已在暂存环境中检查更改时。队列模式工作线程也不同于 n8n 外部任务运行程序，后者对代码节点执行有单独的配置要求。

扩展路径

一次扩展一个瓶颈

阶段 1带有 PostgreSQL 的单个 n8n 实例；测量峰值 CPU、RAM 和并发性。
阶段 2当垂直扩展仍然可以干净地解决测量的瓶颈时，增加 VPS 资源。
阶段 3当持续的并行需求证明分布式执行合理时，引入 Redis 和工作人员。
阶段 4添加工作线程或调整工作线程并发性，同时观察 PostgreSQL、Redis 和执行延迟。
阶段 5仅当容量、可用性或操作要求证明增加的复杂性合理时，才在服务器之间分离组件。

高可用性边界

队列模式可扩展执行，但它不会自动使主进程具有高可用性

共享加密密钥

每个工人必须使用相同的 N8N_ENCRYPTION_KEY 作为主实例，以便工作人员可以解密工作流程执行所需的凭据。

保持版本一致

主进程、Webhook 进程和工作进程应运行相同的 n8n 版本。混合版本可能会在滚动更改期间产生不兼容的行为。

Webhook 处理器是一个单独的扩展层

当传入的 Webhook 量成为瓶颈时，专用的 Webhook 处理器可以位于负载均衡器后面，同时工作线程处理执行。除非测量的请求量证明其合理，否则不要添加此层。

多主是一个不同的功能

运行多个主进程以获得高可用性与普通队列模式不同。 n8n 目前将多主网记录为自托管企业功能，并具有额外的负载均衡器和会话要求。

常见问题

n8n 队列模式：常见问题

n8n 队列模式是否需要 Redis？

是的。 Redis 是协调主实例和工作线程之间待处理执行的消息代理。

队列模式可以使用 SQLite 吗？

对于分布式队列模式架构来说不是。 Main 和 Workers 需要共享数据库访问权限，并且 n8n 文档 PostgreSQL 作为此设置的数据库。

我应该运行多少个工人？

没有通用的计数。从测量的并发性和工作人员利用率开始，然后在监控 PostgreSQL、Redis、CPU、RAM 和队列深度的同时添加容量。

什么是 n8n 工人并发？

它是一个工人可以并行处理的作业数量。当前默认值为 10，n8n 建议工作线程并发度为 5 或更高，而不是创建许多低并发工作线程。

我应该在小 VPS 上启用队列模式吗？

仅当工作量证明合理时。作为一个实例轻松运行的小型部署通常更容易操作，无需 Redis 和单独的工作人员。
