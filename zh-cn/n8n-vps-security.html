生产环境安全

在 VPS 上保护 n8n

为了确保 VPS 上的 n8n 的安全，请将 n8n (5678)、PostgreSQL (5432) 和可选的 Redis (6379) 远离公网；使用 HTTPS 反向代理、SSH 密钥和 MFA，保留您的加密密钥、验证 Webhook、限制有风险的工作流程功能并审核已部署的实例。将编辑器与公网 Webhook 路由分开保护。 HTTPS 本身并不能保证连接服务的安全。

快速清单

公开曝光前的最低安全基线

从可访问的端口开始，HTTPS，经过验证的管理访问，MFA 以及对已保存凭据的保护。在每个传入的 Webhook 触发敏感工作之前对其进行身份验证。更改访问控制后，验证预期的编辑器和外部集成是否仍然有效，然后执行 n8n 安全审计。

仅 HTTPS

将 n8n 放在正确配置的 TLS 反向代理后面，并为编辑器和Webhook一致使用公网 HTTPS URL。

最少开放端口

仅开放公网流量所需的端口。保持 PostgreSQL、Redis 和内部应用程序端口远离公网。

加固 SSH

使用基于密钥的管理，限制可以登录的人员并保持操作系统修补。

保护凭证

保持 n8n 加密密钥稳定且保密。将环境文件、数据库访问和备份副本视为敏感资产。

网络边缘

反向代理、HTTPS 和可信标头

TLS 终止

使用反向代理（例如 Nginx、Caddy 或 Traefik）来终止 HTTPS。当代理是预期入口点时，重定向普通 HTTP 并避免直接暴露 n8n 应用程序端口。

代理设置

当 n8n 在反向代理后面运行时，正确设置代理跳数并传递转发的标头 n8n 需要重建原始客户端请求。

安全 cookie

通过 HTTPS 提供编辑器访问，以便身份验证 cookie 保持安全。不要通过削弱 cookie 安全性来解决损坏的 TLS 设置。

Webhook URL

将公网 Webhook URL 设置为外部可访问的 HTTPS 主机名，以便生成的 Webhook 端点不会指向内部容器或 HTTP 地址。

在不影响 Webhook 的情况下限制编辑器访问。 在可行的情况下，使用 VPN、可信 IP 策略或经过身份验证的代理来限制管理访问。公网 Webhook 接收端点和 OAuth 回调路由可能需要保持可访问；在执行代理规则之前测试受信任的编辑器登录和真实的外部回调。仅转发来自受信任代理的客户端地址标头，而不是任意请求标头。

对 Webhook 调用者进行身份验证： 在 Webhook 节点中，如果发件人支持，请选择基本、标头或 JWT 身份验证，而不是“无”。使用其 IP 许可名单 选项（在适当的情况下），并在集成支持签名请求的情况下验证提供商签名。难以猜测的 URL 不足以进行身份​​验证。适当时在代理上应用速率限制，并确认有效的突发未被阻止。官方 Webhook 身份验证说明。

VPS 加固

减少服务器攻击面

防火墙

默认拒绝未经请求的入站流量，仅允许必须可达的服务。数据库和 Redis 端口通常属于专用/本地网络。

SSH

优先使用 SSH 密钥而不是密码，禁用不必要的登录路径并限制管理访问。应严格控制等同 root 的权限。

操作系统更新

修补 Linux 主机和容器运行时。应用程序强化无法弥补暴露或过时的操作系统。

容器暴露

仅发布需要主机访问的端口。内部服务应在专用 Docker 网络上进行通信，而不是通过公网接口进行通信。

更改防火墙或 SSH 设置之前检查： 检查监听端口 sudo ss -lntp, Docker 端口发布 docker compose ps 从项目目录，并主机防火墙策略 sudo ufw status verbose 如果使用UFW。在禁用密码访问之前，请在单独的会话中验证您的实际 SSH 端口和成功的密钥登录。已发布的 Docker 端口可以绕过UFW规则；仅防火墙状态页面并不能证明端口 5678 是私有的。检查真实的外部可达性。 Docker/UFW 注意事项。

检查自动 Ubuntu 安全更新，而不是假设它们有效： 检查 apt-config dump APT::Periodic::Unattended-Upgrade 和日志 /var/log/unattended-upgrades/unattended-upgrades.log。如果禁用无人值守安全升级， sudo dpkg-reconfigure unattended-upgrades 提供支持的配置对话框。在工作 VPS 上启用之前，请检查重新启动和服务重新启动行为。 Ubuntu APT 更新可以 不 自动更新 n8n Docker 映像或每个第三方软件存储库。 Ubuntu 自动更新文档。

可选的 SSH 暴力破解监控： Fail2Ban 可以检测重复失败的 SSH 登录。如果已安装并配置为 SSH，请使用以下命令验证jail sudo fail2ban-client status sshd 并确认它读取您实际的 SSH 身份验证日志或日志并匹配配置的端口。这补充了 SSH 密钥和网络限制；它不会取代它们。在未首先检查现有访问权限的情况下，请勿复制固定的 SSH 端口或禁止规则。 Ubuntu SSH 强化指导。

数据库和Redis

保持后端服务的私密性

在典型的 Docker Compose 设置中，相关容器应可通过专用网络（而不是主机发布的端口）访问 PostgreSQL 和队列模式 Redis。验证与 docker compose ps 5432 和 6379 未公开发布；单独审查 VPS/云防火墙暴露。网络策略不能替代最低权限的数据库凭据。

PostgreSQL将其绑定到私有接口或容器网络，除非明确需要远程访问并独立保护。
Redis队列模式 Redis 是基础设施，而不是公网端点。限制对需要它的 n8n 组件的网络访问。
凭证仅使用具有应用程序所需权限的专用数据库凭据，并在源代码控制之外保护它们。
传输当数据库流量穿过不受信任的网络时，请使用适当的加密传输，而不是依赖应用程序级凭据加密。

N8N 的秘密

保护加密密钥和凭证边界

加密密钥

n8n 使用其加密密钥对存储的凭据进行加密。在重新启动和工作期间保留相同的密钥，并将其与普通应用程序内容分开保护。

环境秘密

不要将密码、令牌或加密密钥提交到公共代码仓库。限制对环境文件和部署机密的访问。

用户访问

仅向受信任的用户授予编辑器访问权限。工作流可以连接到敏感系统，并可以处理秘密或执行强大的节点。

凭证范围

尽可能使用范围狭窄的服务帐户和 API 令牌。受损的工作流程不应自动继承对不相关系统的广泛访问权限。

n8n 要审查的配置： N8N_BLOCK_ENV_ACCESS_IN_NODE=true 防止代码节点和表达式访问环境值； N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true 请求对设置文件的仅所有者权限。保留 N8N_ENCRYPTION_KEY 持久且安全备份：n8n 可以在首次启动时创建随机密钥，但丢失它可能会使现有的加密凭据无法使用。不要随意更换生产密钥；使用官方支持的轮换程序。阻止环境访问可能会破坏现有集成，因此在生产更改之前进行测试。 n8n 安全变量定义。

工作流程风险

节点可以扩展安全边界

自托管为工作流程提供了强大的功能。代码执行、shell 访问、任意 HTTP 请求和第三方社区节点都会增加风险。禁用不需要的功能，并在运行不受信任的工作流导入之前对其进行检查。

使用精确支持的控件： 配置 NODES_EXCLUDE 具有要禁用的 JSON 节点数组，例如 n8n-nodes-base.executeCommand 和 n8n-nodes-base.readWriteFile，如果未使用。一些高风险节点在新版本中已经默认被屏蔽；在更改之前查看实际列表。官方节点排除。

从 n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true 启用对内部、环回和元数据地址范围的出站 HTTP 请求的检查。合法的内部 API 工作流程可能会停止工作；如有必要，仅将您控制的目的地列入允许范围。将网络分段作为主要防御措施。对于代码节点隔离，请查看外部task runner。 SSRF 保护 · task runner隔离。

社区节点仅安装您信任的软件包；它们在您的 n8n 环境中执行。
风险节点当部署不需要的节点的功能超出预期的工作流边界时，请排除这些节点。
SSRF在工作流不应到达内部或元数据端点的情况下，使用 n8n 的 SSRF 保护和网络控制。
工作流程导入激活前检查导入的工作流程、凭据、表达式和可执行步骤。

审计和更新

安全是一项持续的运维工作

执行 n8n 安全审计

官方的 CLI 命令是 n8n audit。如果您的 Docker Compose 服务已命名 n8n，请在该部署目录中运行 docker compose exec -T n8n n8n audit。查看五个类别：未使用的凭据、有风险的 SQL 查询模式、文件系统访问、有风险/社区节点以及实例风险（包括不受保护的 Webhook 和过时的版本）。修复相关发现并重新运行。这不是渗透测试。官方审计指南。

有计划地更新

保持 n8n 足够最新以接收安全修复。查看发行说明并测试重要的升级，而不是让面向互联网的实例永久陈旧。

监控身份验证

观察意外的访问模式、工作流程变化和故障。当您的运维模式不需要广泛的公网可访问性时，进一步限制编辑器 UI。

准备回滚与恢复

在重大升级之前进行可用于恢复的备份。详细的备份范围和恢复流程请参阅单独的恢复指南。

最小化敏感执行历史记录： 成功运行可以保留客户数据和令牌。适当时设置 EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, 保留 EXECUTIONS_DATA_PRUNE=true，并选择一个 EXECUTIONS_DATA_MAX_AGE 以小时为单位，例如 168 （七天）。这些是可配置的示例，而不是法律保留规则。更少的历史记录意味着更少的调试与取证数据；正在运行、正在等待或带注释的执行可能不会以相同的方式进行修剪。官方执行数据保留说明。

疑似遭入侵： 在不破坏证据的情况下限制恶意访问，检查代理、主机和 n8n 活动并更改工作流程，撤销或轮换可能暴露的上游凭据，修补原因，并在需要时仅从经过测试的可恢复备份进行恢复。检查受影响的 webhook URL、编辑器帐户和连接的服务；不要假设 HTTPS、快照或 VPS 购买提供事件响应服务。

帐户和平台控制

同时保护编辑器和 VPS

需要更强的登录保护

当您的版本支持集中策略实施时，为编辑者帐户启用双因素身份验证并实施 MFA 至 n8n 安全策略。

限制谁可以编辑工作流程

编辑者访问权限是特权访问权限：工作流程可以读取凭据、调用内部系统并执行强大的节点。缩小用户访问范围并删除不再需要的帐户。

禁用您不使用的功能

通过在不必要时禁用公开 API 并阻止您的运维模式不需要的高风险节点或功能来减少应用程序攻击面。

合理使用 SSRF 防护和密钥控制

对于可以发出任意 HTTP 请求的工作流程，评估 n8n 的 SSRF 保护，并在工作流程代码、公共代码仓库和广泛可读的环境文件中保密。

限制未使用的管理端点： N8N_PUBLIC_API_DISABLED=true 禁用 n8n 公共 REST API，并且 N8N_PUBLIC_API_SWAGGERUI_DISABLED=true 单独禁用其 API 调试界面。仅当您的集成不需要这些功能时才执行此操作。禁用 REST API 不会验证工作流 Webhook URL。对编辑器用户使用 MFA，仅在您的 n8n 版本支持的情况下使用集中策略。

常见问题

n8n VPS 安全：常见问题

n8n 端口是否应该直接暴露？

当反向代理是公共入口点时，公开代理并将应用程序端口保留在其后面，而不是广泛发布不必要的服务。

PostgreSQL 或 Redis 应该公开吗？

通常不会。它们应该只能由需要它们的系统访问。暴露到公网会增加攻击面，但不会帮助正常的 n8n 操作。

为什么 n8n 加密密钥很重要？

它保护 n8n 存储的凭据，并且必须在整个部署中保持一致。丢失它可能会阻止恢复的数据产生可用的加密凭据。

社区节点安全吗？

它们用第三方代码扩展了 n8n，因此它们应该被视为具有自己的供应链和特权风险的软件依赖项。仅安装您信任和需要的内容。

HTTPS 是否使自托管 n8n 实例安全？

HTTPS 只能保护传输链路。生产环境安全还需要主机强化、访问控制、私有后端服务、秘密保护、安全工作流程能力、监控和更新。

当生产 webhook 仍然运行时，n8n 编辑器可以是私有的吗？

是的。受信任的反向代理或 VPN 可以独立于公共生产 Webhook 和 OAuth 回调路径来限制编辑者/管理员访问。每次访问规则更改后测试可信登录和外部 Webhook 传送，以避免意外阻止您的集成。

如何验证传入的 n8n webhook？

当发送者支持时，在 Webhook 节点中配置基本、标头或 JWT 身份验证。您还可以使用 IP 白名单并检查提供商签名（如果可用）。不要仅依赖看似秘密的路径，并在请求触发敏感的 API 操作之前对其进行验证。
