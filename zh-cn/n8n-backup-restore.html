备份与恢复

n8n 备份和恢复

要备份和恢复自托管 n8n，请保护您的 SQLite 数据库或一致的 PostgreSQL 转储、持久性.n8n 文件夹和原始加密密钥、部署配置以及每个外部二进制或已安装文件依赖项。将加密副本保留在 VPS 之外，并在单独的实例上测试恢复。使用 CLI 工作流程和凭证导出进行选择性恢复； JSON 单独导出并不是完整的服务器备份。

快速清单

n8n 备份应保护什么

数据库

备份实例使用的 PostgreSQL 数据库或 SQLite 数据库文件。该数据库包含核心 n8n 状态，例如工作流程、凭证和执行数据。

加密密钥

单独并安全地保存准确的 n8n 加密密钥。恢复的加密凭据依赖于相同的密钥。

持久文件

包括持久性 n8n 数据目录以及您的部署所依赖的任何已安装文件、二进制数据存储或工作流资产。

部署配置

保留重建堆栈所需的 Compose/配置文件和非秘密配置。通过适当的访问控制来保护秘密。

两个备份级别

逻辑导出与完整灾难恢复

工作流程和凭证导出

n8n CLI 导出对于迁移、版本化工作流程副本和选择性恢复非常有用。凭证可以以加密形式导出，并在稍后使用匹配的加密密钥导入。要仅恢复一个工作流程，请使用工作流程编辑器的三点菜单下载其 JSON，然后从文件导入到新的审阅工作流程或隔离实例中。在替换实时工作流之前检查凭证、工作流 ID 和节点参数：恢复工作流 JSON 不会恢复整个服务器。

实体导出

CLI 可以导出数据库实体，以便在支持的数据库类型之间移动数据。执行历史表是可选的，因为它们可能非常大。

完整实例恢复

对于死服务器场景，保护实际数据库、加密密钥、持久数据和部署依赖项。不要假设工作流程 JSON 导出会重建整个实例。

提供商快照

VPS 快照可用作附加恢复层，但它不应该是唯一的副本，也不应该取代独立验证的应用程序/数据库备份。

数据库

一致地备份数据库

PostgreSQL

使用一致的 PostgreSQL 备份方法并将生成的备份存储在远离 VPS 的地方。同一故障磁盘上的数据库副本不是灾难恢复。

SQLite

如果部署使用 SQLite，请保护数据库文件免受持久性 n8n 数据目录的影响。避免在主动修改数据库时复制处于不安全状态的数据库。

执行历史

确定历史执行数据是否是您的恢复目标的一部分。它可以使备份变得更大，因此保留和合规性要求应该推动选择。

数据库版本

记录源部署使用的数据库引擎和版本，以便可以准备兼容的恢复环境。

PostgreSQL 在 Docker 撰写 VPS 上。 如果 PostgreSQL 服务被命名 postgres 它的数据库/用户都是 n8n，以下命令在主机上创建一致的 PostgreSQL 自定义格式转储。在运行之前检查实际的 Compose 文件，并调整数据库凭据和服务名称。 pg_dump PostgreSQL 运行时可以生成逻辑上一致的快照；确实如此 不 备份单独的 .n8n 用户文件夹或外部二进制数据。

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

存档列表检查可以捕获明显的格式问题，但不能证明数据可以恢复。在服务器外存储加密副本并演练恢复。使用官方 PostgreSQL pg_dump 文档了解特定于数据库的选项。

SQLite 关于 Docker。 对于默认的 SQLite 部署， database.sqlite 并且生成的加密密钥配置存在于持久性文件中 .n8n 文件夹（通常安装在 /home/node/.n8n）。切勿将 SQLite 的简单实时副本视为一致。在复制文件夹之前停止 n8n 和其他数据库编写器，或者在不可能中断时使用 SQLite 支持的在线备份机制：

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

这些是所示服务和路径的说明性命令，而不是通用卷布局。复制的文件夹最初仍在同一个 VPS 上；在服务器外传输并保护它。当队列工作人员或其他写入程序存在时，也将其停顿并遵循其实际部署设计。 n8n 当前的完整备份指南记录了 SQLite 一致性要求。

将默认的 SQLite 文件夹恢复到干净的目标： 首先停止 n8n 服务和所有数据库编写器。一旦存在兼容的 n8n 服务容器及其目标卷，复制备份的 .n8n 内容 回来 到同一个持久目录。这会覆盖目标文件，因此不要在包含需要保留数据的实例上运行它：

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker 可以复制到已停止的容器，但目的地所有权可能与原始容器不同；在启动之前，确保 n8n 进程可以读取和写入恢复的配置和数据库文件。如果您的真实 Compose 配置使用不同的路径或绑定安装，请相应地调整副本。 Docker 撰写副本参考。对于使用单独的 PostgreSQL 数据库的部署来说，单独恢复 n8n 文件夹是不够的。

关键秘密

加密密钥是恢复的一部分

n8n 使用实例加密密钥对存储的凭据进行加密。没有匹配密钥的数据库或加密凭据导出可能会使恢复的工作流程无法使用其保存的凭据。

如果您设置 N8N_ENCRYPTION_KEY，则恢复该确切的秘密。否则，生成的密钥将存储在持久的 .n8n/config 文件中：在备份或重建时保护该配置。将恢复密钥安全地存储在 VPS 之外。在队列模式下，所有主进程和工作进程必须使用相同的密钥。

做保留生产所使用的确切密钥的受保护副本。
做在测试凭据之前验证恢复环境是否使用该密钥。
不重建服务器后依赖新生成的密钥。
不将密钥提交到公共存储库或将其存储在不受保护的备份旁边。

文件和二进制数据

数据库备份可能无法涵盖每个工作流依赖项

持久 .n8n 数据

找到并保留实际的 .n8n 用户文件夹，而不仅仅是容器映像。在典型的 Docker 部署中，它安装在/home/node/.n8n；在 Docker 之外，默认值为 ~/.n8n。如果配置了 N8N_USER_FOLDER，则 n8n 会在指定的父目录内创建.n8n。包括其配置密钥以及您的安装使用的任何本地 SQLite、二进制或文件系统执行数据。

已安装的工作流程文件

如果工作流读取或写入主机安装的目录，请单独备份这些目录。在没有它们的情况下恢复 n8n 可能会导致其他有效的工作流程被破坏。

二进制数据

识别存储模式并恢复每个外部依赖项。基于文件系统的二进制或执行数据可能位于.n8n 或自定义目录中； S3/Azure Blob 或其他配置的外部存储需要其自己的可恢复副本和访问设置。仅数据库转储无法替换这些文件。

社区节点

记录社区包和版本，并备份通过 N8N_CUSTOM_EXTENSIONS 配置的任何其他自定义节点目录。这些目录可以位于 .n8n; 之外仅恢复数据库和用户文件夹可能仍会使自定义节点工作流程无法使用。

离线策略

同一 VPS 上的备份只是本地副本

本地副本对于快速回滚很有用，但容易受到服务器丢失、磁盘故障和破坏性错误的影响。
离线副本在存储中至少保留一份独立于生产的备份 VPS。
版本控制副本保留多个恢复点，以便损坏或错误更改不会覆盖唯一可用的备份。
访问控制备份可以包含凭据、工作流逻辑和敏感业务数据。适当地加密和限制它们。
监控当计划的备份失败或停止生成新的恢复点时发出警报。

使时间表可衡量。 记录每个成功备份的时间戳、传输完成、文件大小、源数据库版本、加密密钥恢复位置以及最近成功的恢复测试。文件丢失、失败或意外为空时发出警报。在将备份存档发送出去之前对其进行加密 VPS 并限制对恢复机密的访问。多个过时的恢复点可以防止仅在最新副本覆盖最后一个正常副本后才发现损坏。

例如，如果您最多可以容忍六个小时的更改丢失，那么成功的六小时备份计划只是一个起点，而不是保证：失败的作业和延迟的服务器外复制可能会增加实际损失。根据您自己的 RPO/RTO 和数据要求设置保留和恢复节奏，而不是采用通用的 7 天或 30 天政策。

恢复秩序

按受控顺序恢复

1·准备提供兼容的服务器、数据库和容器/运行时环境。
2·恢复秘密安全地配置原始 n8n 加密密钥和所需的部署机密。
3·恢复数据库恢复 PostgreSQL 或 SQLite 并验证 n8n 可以连接到预期数据。
4·恢复文件恢复持久目录、二进制数据和已安装的工作流资产。
5·开始 n8n使用预期的主机名、数据库和环境配置启动应用程序。
6·验证确认用户、工作流程和凭据加载，然后执行代表性工作流程和 Webhook 路径。

PostgreSQL 灾难恢复示例： 在一个 独立、干净的恢复目标 已经具有正确的数据库角色和空的 n8n 数据库，启动 仅 PostgreSQL. 等到它健康后再导入： docker compose up -d 当 PostgreSQL 仍在初始化时，单独可以返回，因此以下 pg_restore 可能会失败。该示例使用 --wait 现代 Compose 安装并独立检查 pg_isready。配置适当的 PostgreSQL 运行状况检查以实现可靠的等待，或在继续之前明确确认准备情况。不要将此命令指向已填充的生产数据库或在数据库及其匹配之前启动 n8n .n8n 密钥/数据已恢复。

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

目标必须具有兼容的 PostgreSQL 版本、角色权限、扩展和原始 n8n 配置。恢复 .n8n 到其正确的持久卷或使用备份机制绑定安装，保留所有权和权限。恢复外部二进制文件、自定义扩展、Compose 和机密配置，然后在兼容版本上启动 n8n 并检查其日志。单独恢复数据库并不能恢复密钥：PostgreSQL 部署将密钥保留在 .n8n/config 除非你明确配置 N8N_ENCRYPTION_KEY。 pg_restore 参考·n8n 全实例恢复序列。

恢复测试

在恢复成功之前备份无法得到验证

在干净的环境下进行测试

真正的演习应该证明备份可以重建实例，而不依赖于生产服务器上留下的未声明的文件。

检查凭据

打开工作流程还不够。确认恢复的加密凭据确实成功解密和身份验证。

运行代表性工作流程

测试依赖于 webhook、外部 API、已安装文件和社区节点的工作流程，而不是仅验证简单的自动化。

测量恢复时间

记录恢复需要多长时间以及剩余的手动步骤。这将假定的备份转换为可操作的恢复过程。

已验证的恢复练习：SQLite 和 PostgreSQL

测试环境： n8n 2.42.5 使用合成的两节点工作流程，在一次性 GitHub 操作运行器上的隔离 Docker 容器中。这些检查持续进行 8 十月 2026，不在客户或生产 n8n 服务器上。

SQLite：通过导入测试工作流程，导出它，停止所有编写器，存档 SQLite 支持的持久性 .n8n 文件夹及其生成的加密密钥，恢复到干净的卷中，开始 n8n，然后重新导出并执行恢复的工作流程。
PostgreSQL：通过导入相同的测试工作流程，创建并检查自定义格式 pg_dump，使用恢复它 pg_restore 到一个新的空 PostgreSQL 数据库中，恢复单独的 .n8n 文件夹，然后重新导出并执行恢复的工作流程。
PASS 建立了什么测试的备份路径保留了该工作流程、其两个节点及其连接，并允许在恢复后执行。这些是可重复的功能冒烟测试，而不是工作负载基准。
什么没有测试过真实凭证、生产 Webhooks、队列模式工作线程和 Redis、S3/Azure 二进制存储、自定义节点、用户/项目访问或实时生产实例的恢复的解密和身份验证。为您实际使用的每个依赖项运行单独的演练。

如何重现： 使用一次性 n8n 安装，创建无害的两节点工作流程，执行适用的数据库和持久文件夹备份，恢复到干净的卷或数据库，然后验证恢复的工作流程的节点、连接和实际执行。在宣布灾难恢复经过验证之前，在生产系统上还要检查加密凭证、网络钩子和外部文件。

恢复钻探验收清单： 使用隔离的域/环境；检查用户和工作流程是否存在，现有的加密凭证无需重新输入即可进行身份验证，生产 Webhook 调用预期恢复的工作流程，已安装的文件和二进制附件保持可读，以及与所需社区节点加载的集成。确认备份期限、测量的停机时间和服务器外可访问性。如果任何重要检查失败，请标记该恢复点 未经验证 而不是报告备份已完成。

CLI 备份限制

准确了解哪些工作流程和凭证导出不会恢复

CLI 导出不是完整实例备份

工作流和凭证备份导出不包括用户和角色、执行历史记录和日志、变量或实例设置（例如加密密钥）。

全新实例恢复需要所有者

在干净的实例上，在导入凭据之前完成所有者设置。多用户或项目恢复可能还需要正确的用户或项目分配。

导入的 ID 可以覆盖现有项目

工作流和凭证导出保留其原始 ID。导入到已包含相同 ID 的实例中可以替换那些现有项目。

有意发布导入的工作流程

CLI 导入通常会使工作流程处于非活动状态。在 n8n 2.x 上，检查每个导入的工作流程的发布状态并仅发布您想要运行的工作流程；自托管服务器 CLI 还支持 n8n 发布：工作流--id=YOUR_WORKFLOW_ID。当 n8n 运行时，服务器 CLI 发布/取消发布状态更改仅在重新启动 n8n 后生效。在验证计划的触发器和生产 Webhook 或切换流量之前重新启动。

Docker Compose 的批量导出示例： 如果您的 n8n 服务已命名 n8n，您可以运行下面的官方 CLI 备份。输出路径故意位于其安装的持久性内部 .n8n 目录，因为容器内的任意目录在重新创建时可能会消失。确认该目录可由 n8n 容器用户写入。保留工作流程和凭证 JSON 单独的目录—n8n 记录了两种共享目录时的导入问题。

n8n 2.x 草稿与已发布的备份： 一个正常的 --backup 工作流程导出捕获当前草稿；这些可能与生产中发布的版本不同。要保留特定工作流程的实际发布版本，请使用以下命令单独导出它 docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json，在确保输出文件夹存在并且可写之后。 CLI 还可以使用导出历史版本 --version=VERSION_ID。将这些捕获与完整备份一起保存在服务器外；不要假设草稿 JSON 记录了实时发布的状态。

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

复制的 ~/n8n-recovery/cli 目录仍位于 VPS 上，直到您将其移动到安全、独立的备份位置。凭证导出默认加密，导入时需要匹配的加密密钥。避免使用 --decrypted 除了严格控制的迁移：它以明文形式写入秘密。切勿将包含敏感工作流程逻辑或凭据的导出提交到公共 GitHub 存储库。一些第三方 GitHub 凭证备份模板故意导出解密的秘密；私有存储库是一种访问限制，而不是加密。检查每个模板的实际导出设置和存储权限，在服务器外传输之前加密机密，并轮换通过意外的纯文本上传暴露的任何凭据。

批量导入示例： 在干净的目标上，完成所有者设置，提供原始加密密钥并确保保存的备份文件在该恢复中可用 VPS。以下创建目标文件夹并复制 workflows/ 和 credentials/ 从主机到 n8n 容器的子文件夹；如果您的 Docker 卷布局不同，请调整路径：

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

检查 n8n 容器用户的文件所有权和访问权限。请勿在未经过验证回滚的情况下导入已填充的生产实例：工作流和凭证 ID 可能会覆盖现有条目。然后运行：

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

常见问题

n8n 备份和恢复：常见问题

导出工作流程是否足以备份 n8n？

不会。工作流程导出是有用的逻辑副本，但完整恢复还可能需要凭据、匹配的加密密钥、数据库状态、持久文件和二进制数据存储。

如果我有数据库，我是否需要 n8n 加密密钥？

如果您需要存储在该数据库中的加密凭据保持可用，则可以。妥善保存原始密钥。

我应该备份 PostgreSQL 还是导出工作流程和凭据？

为了进行灾难恢复，请保护数据库和加密密钥。逻辑导出作为额外的迁移和选择性恢复层很有价值，而不是替代实例的每个部分。

VPS 快照可以作为我唯一的备份吗？

最好将其视为一层恢复层。保留独立的服务器外备份，以便提供商、帐户、服务器或快照故障不会立即删除每个恢复点。

我如何知道我的备份有效？

将其恢复到干净的测试环境中，验证凭据解密并运行代表性工作流程。仅成功的备份作业并不能证明可恢复性。

GitHub 或 Google Drive 工作流程备份是否包含已保存的凭据机密？

仅工作流 JSON 备份不包括由 n8n 的凭证存储或实例加密密钥管理的秘密值。但是，导出的 JSON 可以公开直接输入到节点参数（例如身份验证标头）中的凭证名称、ID 和秘密。在上传或共享之前检查并保护导出的 JSON。要完全恢复，请备份数据库和原始密钥，或使用受支持的加密凭据 CLI 导出以及经过测试的恢复。仅限工作流程的 GitHub 或 Google 云端硬盘模板不是完整的灾难恢复。

恢复目标

在事件发生之前定义 RPO 和 RTO

恢复点目标 是最近变化的最大可容忍损失。从最新可用的、独立存储的恢复点开始测量；如果导出或传输失败，计划的六小时作业不会建立六小时 RPO。 RTO 是最大可容忍中断。通过干净的恢复练习来衡量它，包括检索机密、恢复外部文件、重新检查凭据和发布恢复的工作流程，而不仅仅是启动容器。

恢复密钥

重建前找到原始加密密钥

如果生产集 N8N_ENCRYPTION_KEY，保留确切的环境秘密。如果没有，请将生成的密钥保留在原始持久性 .n8n/config 中。在导入加密凭据之前检查恢复的实例实际使用哪个源；新生成的密钥无法解密旧数据库中的凭据。
