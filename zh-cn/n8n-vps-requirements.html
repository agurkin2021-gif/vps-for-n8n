n8n VPS 要求

对于 n8n VPS 要求，请从您的工作负载开始，而不是从通用硬件最低限度开始。精心设计的 1 vCPU / 1 GB VPS 可以运行小型始终在线的自动化，而 2 vCPU / 4 GB RAM 是 n8n、PostgreSQL 和 HTTPS 的实用起始类。大有效负载、同时运行和本地数据处理需要更多的空间；选择前先衡量实际使用情况。

最小容量与实际容量

n8n 是否有一个官方的最低 VPS 配置？

不适用于所有工作负载。 n8n 的官方先决条件示例描述了示例性 OEM 部署，并明确警告要求因工作负载而异。该文档并不能普遍保证任何特定的 CPU、RAM 或磁盘分配将支持生产自动化。

n8n 指出，空闲实例可能使用相对较少的内存，但代码节点、大型二进制负载或同时执行可能会急剧增加内存需求。分别为操作系统、Docker、PostgreSQL 和备份/监控工具制定预算。

RAM 和 CPU

实际消耗服务器资源的是什么

并发执行

同时运行的多个工作流程可能比 n8n 中存储的工作流程总数更重要。观察重叠期间的内存峰值和执行延迟。

有效负载大小

大型 JSON 对象、文件和二进制数据会增加内存压力。与许多轻量级 API 自动化相比，一些数据密集型执行可能需要更多的 RAM。

CPU 密集型节点

代码、转换和其他计算量大的步骤可能会产生持续的 CPU 压力。当实际执行竞争计算时，更多核心会有所帮助。

辅助服务

操作系统、PostgreSQL、反向代理、监控和 Docker 也需要资源。调整整个堆栈的大小，而不仅仅是 n8n 流程。

升级前测量

如何判断 n8n 是否需要更多 RAM、CPU 或磁盘

运行最大的预期工作流程和实际的重叠突发，然后检查服务器和 n8n 执行日志。编辑器中保存的工作流程数量本身并不是有用的容量基准。

内存/OOM

检查 docker stats --no-stream 和 free -h。如果内存耗尽，请首先减少 JSON 或二进制有效负载，批量导入大量内容并避免占用大量内存的代码步骤。 JavaScript 堆错误不一定可以通过添加 vCPU 来修复。

CPU / 并发

衡量 CPU 在转换过程中是否保持忙碌，或者作业是否仅等待外部 API。在常规模式下，在扩展到worker之前请考虑支持的生产并发限制。增加 CPU 不会加速外部速率限制 API。

存储/数据库

检查 df -h、数据库大小和保留的执行历史记录。观察磁盘增长和缓慢的数据库操作。在购买更大的磁盘之前有意设置保留；将恢复副本保留在服务器之外。

使用 n8n 的并发指南和官方基准测试解释。在不知道其有效负载和 API 延迟的情况下宣传的任何数量的并发工作流程都只是一个估计。

数据库与存储

SQLite、PostgreSQL 和持久数据

SQLite

SQLite 可以适合小型单实例部署和测试。随着生产使用和并发性的增长，数据库选择成为操作约束而不是安装细节。

PostgreSQL

对于面向生产的 VPS 堆栈，PostgreSQL 提供了更强大的数据库基础。为数据库本身制定预算 RAM、CPU 和磁盘并监控其增长。

持久 .n8n 数据

不要将 PostgreSQL 视为唯一的持久资产。保留 n8n 数据目录并保护恢复加密凭据所需的加密密钥。

磁盘增长

执行历史记录、二进制数据、数据库文件和日志会随着时间的推移而扩展。保留设置和服务器外备份直接影响所需的容量。

磁盘容量

订购前估计 n8n 执行历史存储

开始于 每天保存的执行次数 × 每次执行的平均存储字节数 × 保留天数。例如，每天 500 保存的执行 × 200 KB 每 × 14 天 = 1.4 GB 数据库开销之前的示例执行数据。 200 KB 假设是说明性的，而不是 n8n 基准。

还为操作系统、Docker 映像层、数据库索引、二进制文件、应用程序日志、升级和临时文件分配磁盘。离线备份需要自己的容量。 10 GB 磁盘可用于精简堆栈，但用于保留文件的空间比 40 或 80 GB 磁盘少得多。

n8n 记录了按期限（336 小时/14 天）或计数（10,000 执行）进行的默认执行修剪，但有例外。检查您的实际设置并在更改之前验证保留的内容。 SQLite 可以重用释放的空间，而不是自动缩小其文件。

来源：n8n：管理执行数据和修剪。磁盘要求取决于观察到的保存的有效负载大小，而不仅仅是节点的数量。

系统要求

Docker 和生产费用

Linux VPS

使用经过维护的 Linux 发行版，除了应用程序堆栈之外，还为操作系统和安全更新提供足够的资源。

Docker Compose

容器部署简化了可重复性，但并没有消除资源开销。将 n8n 和数据库数据保留在一次性容器之外。

HTTPS & 反向代理

公共 webhook 需要稳定的主机名和正确配置的 HTTPS。在生产设计中包括反向代理和 TLS 层。

监控和备份

跟踪 RAM、CPU、磁盘和数据库增长。将可恢复的备份保留在第 VPS 之外并测试恢复，而不是假设快照就足够了。

并发性

当更大的 VPS 不再是完整的答案时

当一个实例可以干净地处理工作负载时，垂直扩展是合适的。当持续的并行需求造成争用时，请评估队列模式和worker。队列模式引入 Redis、PostgreSQL 和一个或多个工作进程；每个组件的预算 RAM 和 CPU，而不仅仅是 n8n。 n8n 还记录了队列模式下文件系统二进制数据存储的限制，因此在切换之前验证兼容的数据存储设计。

阅读队列模式和worker指南

保持单实例当 CPU、RAM 和执行延迟在峰值重叠下保持舒适时。
垂直缩放当持续的 CPU 或内存压力是限制因素并且架构仍然简单时。
考虑队列模式当测量并行需求时，Redis 和单独的worker是合理的。
重新检查存储情况当执行历史记录、二进制文件或 PostgreSQL 增长成为主要约束时。

入门级和存储 I/O

如何使用 1 GB 入门级 VPS

1 GB RAM

这是一个真正的工作 VPS 层，而不是一个仅供测试的产品。当您将内存、磁盘使用和并发作业保持在测量限制内时，它适用于小型始终在线的自动化和大多数顺序 API 工作。它在同一服务器上为 PostgreSQL 提供的空间很小，但有效负载很大或并行执行量很大。

2 GB RAM

当您需要为操作系统、Docker 和小突发提供更多空间而不立即转移到生产规模的堆栈时，请使用 2 GB 作为更安全的轻量级实例基线。

SSD 与 NVMe

Standard SSD 对于轻型自动化来说足够了。当 PostgreSQL 和执行历史记录导致频繁读写或在测量的工作流程性能中出现磁盘延迟时，NVMe 变得更加有用。

升级前测量

使用 CPU、内存、磁盘增长和峰值重叠下的执行持续时间来确定瓶颈是计算、内存还是存储，而不是假设更大的 VPS 可以解决每次减速问题。

常见问题

n8n VPS 要求：常见问题

n8n 需要多少 RAM？

没有通用的数字。 RAM 需求随并发性、有效负载大小、执行行为和 VPS 上的支持服务而变化。 4 GB 服务器是实用的小生产起始级别，并不是每个工作负载的保证要求。

我应该使用多少个 CPU 核心？

轻量工作负载可以从较小的 CPU 分配开始。当监控显示持续的 CPU 压力或并发下执行速度较慢时添加核心，而不是仅根据工作流计数来调整大小。

n8n 需要 PostgreSQL 吗？

小型部署可以使用 SQLite，但随着操作要求和并发性的增加，PostgreSQL 是更强大的面向生产的选择。

什么时候需要 Redis？

Redis 与队列模式相关。正常的单实例部署不需要 Redis，仅仅因为它运行在 VPS 上。

我应该保留多少磁盘空间？

磁盘需求取决于 PostgreSQL 增长、保留的执行历史记录、二进制数据、日志、容器层和备份。监控增长并留出空间，而不是依赖固定的通用数字。

我可以在 1 GB VPS 上连续运行 n8n 吗？

是的，当实际工作量适合时。 1 GB VPS 是一个真正的工作服务器，可以支持小型、大多数顺序自动化，但内存空间有限。避免假设同一服务器 PostgreSQL 堆栈、二进制密集型作业或多个大型并发执行将适合。根据观察到的资源压力监控消耗和升级。

对于生产环境的 n8n VPS 来说，2 GB 还是 4 GB RAM 更好？

两 GB 比精简的 1 GB 实例提供了更多空间，而 4 GB 是评估 n8n 以及 PostgreSQL 和 HTTPS 的实用起始类。不存在通用的保证生产最低限度：工作负载复杂性、峰值重叠、容器配置和保留数据决定了实际需求。

n8n 人工智能工作流程需要 GPU 吗？

当 n8n 仅调用外部模型 API 时则不然：模型提供者处理推理，而 VPS 处理编排、有效负载和并发性。在本地运行推理模型是一项单独的硬件决策，可能需要更多的 RAM 和适当的 GPU 资源。

是什么导致 n8n 内存不足错误？

大型 JSON 或二进制有效负载、占用大量内存的代码操作和重叠执行是常见原因。检查运行时日志和峰值内存使用情况，然后根据测量的问题减少一次执行中保存的数据或分配更多 RAM。
