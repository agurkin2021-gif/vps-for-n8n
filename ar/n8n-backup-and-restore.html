n8n النسخ الاحتياطي والاستعادة

لعمل نسخة احتياطية من n8n واستعادتها، وحماية قاعدة بيانات SQLite الخاصة بك أو تفريغ PostgreSQL المتسق، ومجلد .n8n المستمر ومفتاح التشفير الأصلي، وتكوين النشر، وكل تبعية خارجية ثنائية أو ملف مثبت. احتفظ بنسخة مشفرة من VPS واختبر الاسترداد في نسخة منفصلة. استخدم CLI سير العمل وتصدير بيانات الاعتماد للاسترداد الانتقائي؛ JSON الصادرات وحدها ليست نسخة احتياطية كاملة للخادم.

قائمة مرجعية سريعة

ما الذي يجب أن تحميه النسخة الاحتياطية n8n

قاعدة البيانات

قم بعمل نسخة احتياطية من قاعدة بيانات PostgreSQL أو ملف قاعدة بيانات SQLite الذي يستخدمه المثيل. تحتوي قاعدة البيانات على حالة n8n الأساسية مثل سير العمل وبيانات الاعتماد وبيانات التنفيذ.

مفتاح التشفير

احتفظ بمفتاح التشفير n8n الدقيق بشكل منفصل وآمن. تعتمد بيانات الاعتماد المشفرة المستعادة على نفس المفتاح.

الملفات الدائمة

قم بتضمين دليل بيانات n8n المستمر وأي ملفات مثبتة أو تخزين بيانات ثنائية أو أصول سير العمل التي يعتمد عليها النشر.

تكوين النشر

احتفظ بملفات الإنشاء/التكوين والتكوين غير السري اللازم لإعادة بناء المكدس. حماية الأسرار باستخدام ضوابط الوصول المناسبة.

مستويين احتياطيين

التصدير المنطقي مقابل التعافي الكامل من الكوارث

سير العمل وتصدير بيانات الاعتماد

n8n CLI تعتبر الصادرات مفيدة للترحيل ونسخ سير العمل ذات الإصدارات والاستعادة الانتقائية. يمكن تصدير بيانات الاعتماد في شكل مشفر واستيرادها لاحقًا باستخدام مفتاح التشفير المطابق. لاستعادة سير عمل واحد فقط، استخدم القائمة ثلاثية النقاط لمحرر سير العمل لتنزيل JSON، ثم الاستيراد من ملف إلى سير عمل مراجعة جديد أو مثيل معزول. تحقق من بيانات الاعتماد ومعرفات سير العمل ومعلمات العقدة قبل استبدال سير العمل المباشر: استعادة سير العمل JSON لا تؤدي إلى استعادة الخادم بالكامل.

تصدير الكيان

يمكن لـ CLI تصدير كيانات قاعدة البيانات لنقل البيانات بين أنواع قواعد البيانات المدعومة. تعد جداول سجل التنفيذ اختيارية لأنها يمكن أن تكون كبيرة جدًا.

استرداد المثيل الكامل

بالنسبة لسيناريو الخادم الميت، قم بحماية قاعدة البيانات الفعلية ومفتاح التشفير والبيانات المستمرة وتبعيات النشر. لا تفترض أن تصدير سير العمل JSON يعيد بناء المثيل بأكمله.

لقطة من المزود

تعد لقطة VPS مفيدة كطبقة استرداد إضافية، ولكن لا ينبغي أن تكون النسخة الوحيدة ويجب ألا تحل محل النسخة الاحتياطية للتطبيق/قاعدة البيانات التي تم التحقق منها بشكل مستقل.

قاعدة البيانات

عمل نسخة احتياطية من قاعدة البيانات باستمرار

PostgreSQL

استخدم طريقة نسخ احتياطي PostgreSQL متسقة وقم بتخزين النسخة الاحتياطية الناتجة بعيدًا عن VPS. لا تعد نسخة قاعدة البيانات الموجودة على نفس القرص الفاشل بمثابة استرداد بعد عطل فادح.

SQLite

إذا كان النشر يستخدم SQLite، قم بحماية ملف قاعدة البيانات من دليل بيانات n8n المستمر. تجنب نسخ قاعدة بيانات في حالة غير آمنة أثناء تعديلها بشكل فعال.

تاريخ التنفيذ

قرر ما إذا كانت بيانات التنفيذ التاريخية جزءًا من هدف الاسترداد الخاص بك. يمكن أن يجعل النسخ الاحتياطية أكبر بكثير، لذا يجب أن تكون متطلبات الاحتفاظ والامتثال هي الدافع وراء الاختيار.

نسخة قاعدة البيانات

قم بتسجيل محرك قاعدة البيانات والإصدار المستخدم بواسطة النشر المصدر حتى يمكن إعداد بيئة الاسترداد بشكل متوافق.

PostgreSQL على Docker يؤلف VPS. إذا تم تسمية خدمة PostgreSQL postgres وقاعدة البيانات/المستخدم كلاهما n8n، ينشئ الأمر التالي تفريغًا متسقًا للتنسيق المخصص PostgreSQL على المضيف. تحقق من ملف الإنشاء الفعلي قبل تشغيله، واضبط بيانات اعتماد قاعدة البيانات وأسماء الخدمات. pg_dump يمكن أن تنتج لقطة متسقة منطقيا أثناء تشغيل PostgreSQL؛ إنه كذلك لا عمل نسخة احتياطية منفصلة .n8n مجلد المستخدم أو البيانات الثنائية الخارجية.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

يكتشف فحص قائمة الأرشيف مشاكل التنسيق الواضحة ولكنه لا يثبت إمكانية استعادة البيانات. قم بتخزين نسخة مشفرة خارج الخادم وتدرب على الاستعادة. استخدم وثائق PostgreSQL pg_dump الرسمية للخيارات الخاصة بقاعدة البيانات.

SQLite على Docker. بالنسبة للنشر الافتراضي SQLite، database.sqlite ويعيش تكوين مفتاح التشفير الذي تم إنشاؤه داخل الملف المستمر .n8n مجلد (يتم تثبيته عادةً على /home/node/.n8n). لا تعامل أبدًا نسخة حية بسيطة من SQLite على أنها متسقة. قم بإيقاف n8n وكتاب قاعدة البيانات الآخرين قبل نسخ المجلد، أو استخدم آلية النسخ الاحتياطي عبر الإنترنت المدعومة من SQLite عندما يكون الانقطاع مستحيلاً:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

هذه أوامر توضيحية للخدمة والمسار الموضح، وليست تخطيطًا عامًا لوحدة التخزين. المجلد المنسوخ لا يزال في البداية على نفس VPS؛ نقله وحمايته خارج الخادم. عند وجود عمال قائمة الانتظار أو كتاب آخرين، قم بإخمادهم أيضًا واتبع تصميم النشر الفعلي الخاص بهم. n8n توثق إرشادات النسخ الاحتياطي الكامل الحالية متطلبات الاتساق SQLite.

استعادة المجلد SQLite الافتراضي إلى هدف نظيف: قم أولاً بإيقاف خدمة n8n وجميع كتاب قاعدة البيانات. بمجرد وجود حاوية خدمة n8n متوافقة وحجم الوجهة الخاص بها، قم بنسخ النسخة الاحتياطية .n8n محتويات العودة إلى نفس الدليل المستمر. يؤدي هذا إلى استبدال الملفات المستهدفة، لذا لا تقم بتشغيلها على مثيل يحتوي على البيانات التي تحتاج إلى الاحتفاظ بها:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker يمكن النسخ إلى الحاويات المتوقفة، لكن ملكية الوجهة قد تختلف عن الأصل؛ تأكد من أن التكوين المستعاد وملف قاعدة البيانات قابلان للقراءة والكتابة من خلال عملية n8n قبل البدء بها. إذا كان تكوين Compose الحقيقي الخاص بك يستخدم مسارًا مختلفًا أو رابط ربط، فقم بتعديل النسخة وفقًا لذلك. Docker إنشاء مرجع النسخة. استعادة مجلد n8n وحده لا يكفي لعمليات النشر التي تستخدم قاعدة بيانات PostgreSQL منفصلة.

سر بالغ الأهمية

يعد مفتاح التشفير جزءًا من عملية الاسترداد

n8n يقوم بتشفير بيانات الاعتماد المخزنة باستخدام مفتاح تشفير المثيل. يمكن لقاعدة البيانات أو تصدير بيانات الاعتماد المشفرة بدون المفتاح المطابق أن يترك سير العمل المستعاد غير قادر على استخدام بيانات الاعتماد المحفوظة الخاصة به.

إذا قمت بتعيين N8N_ENCRYPTION_KEY، قم باستعادة هذا السر بالضبط. وإلا فسيتم تخزين المفتاح الذي تم إنشاؤه في ملف .n8n/config المستمر: قم بحماية هذا التكوين عند النسخ الاحتياطي أو إعادة البناء. قم بتخزين مفاتيح الاسترداد بشكل آمن خارج VPS. في وضع قائمة الانتظار، يجب أن تستخدم جميع العمليات الرئيسية والعاملة نفس المفتاح.

افعلاحتفظ بنسخة محمية من المفتاح الدقيق الذي يستخدمه الإنتاج.
افعلتحقق من أن بيئة الاسترداد تستخدم هذا المفتاح قبل اختبار بيانات الاعتماد.
لا تفعل ذلكاعتمد على المفتاح الذي تم إنشاؤه حديثًا بعد إعادة بناء الخادم.
لا تفعل ذلكقم بإيداع المفتاح في مستودع عام أو قم بتخزينه بجانب نسخة احتياطية غير محمية.

الملفات والبيانات الثنائية

قد لا يغطي النسخ الاحتياطي لقاعدة البيانات كل تبعيات سير العمل

بيانات .n8n المستمرة

حدد موقع مجلد المستخدم الفعلي .n8n واحتفظ به، وليس صورة الحاوية فقط. في نشر Docker النموذجي، يتم تثبيته على /home/node/.n8n؛ خارج Docker الافتراضي هو ~/.n8n. إذا تم تكوين N8N_USER_FOLDER، فسيقوم n8n بإنشاء .n8n داخل الدليل الأصلي المحدد. قم بتضمين مفتاح التكوين الخاص به وأي بيانات تنفيذ SQLite محلية أو ثنائية أو نظام ملفات يستخدمها التثبيت الخاص بك.

ملفات سير العمل المثبتة

إذا كانت مهام سير العمل تقرأ أو تكتب أدلة مثبتة على المضيف، فقم بعمل نسخة احتياطية من هذه الدلائل بشكل منفصل. يمكن أن تؤدي استعادة n8n بدونها إلى تعطيل سير العمل الصالح.

البيانات الثنائية

تحديد وضع التخزين واستعادة كل التبعية الخارجية. قد تكون البيانات الثنائية أو بيانات التنفيذ المستندة إلى نظام الملفات موجودة في .n8n أو في دليل مخصص؛ يحتاج S3/Azure Blob أو أي وحدة تخزين خارجية أخرى تم تكوينها إلى إعدادات النسخ والوصول الخاصة بها القابلة للاسترداد. لا يمكن لتفريغ قاعدة البيانات وحده استبدال تلك الملفات.

عقد المجتمع

قم بتسجيل حزم وإصدارات المجتمع، وقم بعمل نسخة احتياطية لأي أدلة عقدة مخصصة إضافية تم تكوينها من خلال N8N_CUSTOM_EXTENSIONS. يمكن أن تجلس هذه الدلائل خارج .n8n; قد تظل قاعدة البيانات واستعادة مجلد المستخدم بمفردهما تترك سير عمل العقدة المخصصة غير قابل للاستخدام.

استراتيجية خارج الخادم

النسخة الاحتياطية على نفس VPS ليست سوى نسخة محلية

نسخة محليةمفيد للتراجع السريع، ولكنه عرضة لفقد الخادم وفشل القرص والأخطاء المدمرة.
نسخة خارج الخادماحتفظ بنسخة احتياطية واحدة على الأقل في وحدة التخزين بشكل مستقل عن VPS الإنتاج.
نسخ محدثةاحتفظ بنقاط استرداد متعددة حتى لا يؤدي الفساد أو التغيير السيئ إلى استبدال النسخة الاحتياطية الوحيدة القابلة للاستخدام.
التحكم في الوصوليمكن أن تحتوي النسخ الاحتياطية على بيانات الاعتماد ومنطق سير العمل وبيانات العمل الحساسة. تشفيرها وتقييدها بشكل مناسب.
المراقبةالتنبيه عند فشل النسخ الاحتياطية المجدولة أو توقفها عن إنتاج نقاط استرداد جديدة.

اجعل الجدول الزمني قابلاً للقياس. قم بتسجيل الطابع الزمني لكل نسخة احتياطية ناجحة، وإكمال النقل، وحجم الملف، وإصدار قاعدة البيانات المصدر، وموقع استرداد مفتاح التشفير، وآخر اختبار استعادة ناجح. تنبيه بشأن الملفات المفقودة أو الفاشلة أو الفارغة بشكل غير متوقع. قم بتشفير أرشيفات النسخ الاحتياطي قبل إرسالها إلى VPS وتقييد الوصول إلى أسرار الاسترداد. تعمل نقاط الاسترداد المتعددة المؤرخة على الحماية من اكتشاف الفساد فقط بعد أن تحل أحدث نسخة محل آخر نسخة سليمة.

على سبيل المثال، إذا كان بإمكانك تحمل ست ساعات من التغييرات المفقودة على الأكثر، فإن جدول النسخ الاحتياطي الناجح لمدة ست ساعات هو نقطة بداية، وليس ضمانًا: يمكن أن تؤدي المهام الفاشلة وتأخر النسخ المتماثل خارج الخادم إلى زيادة الخسارة الفعلية. قم بتعيين الاحتفاظ واستعادة الإيقاع إلى RPO/RTO ومتطلبات البيانات الخاصة بك، بدلاً من افتراض سياسة 7-day أو 30-day العالمية.

استعادة النظام

التعافي في تسلسل متحكم فيه

1 · الاستعدادتوفير خادم متوافق وقاعدة بيانات وبيئة حاوية/وقت تشغيل.
2 · استعادة الأسرارقم بتكوين مفتاح التشفير n8n الأصلي وأسرار النشر المطلوبة بشكل آمن.
3 · استعادة قاعدة البياناتقم باسترداد PostgreSQL أو SQLite وتحقق من إمكانية اتصال n8n بالبيانات المتوقعة.
4 · استعادة الملفاتيمكنك استعادة الدلائل المستمرة والبيانات الثنائية وأصول سير العمل المثبتة.
5 · ابدأ n8nأظهر التطبيق باسم المضيف وقاعدة البيانات وتكوين البيئة المتوقع.
6 · التحقق من صحةتأكد من تحميل المستخدمين ومهام سير العمل وبيانات الاعتماد، ثم قم بتنفيذ مهام سير العمل التمثيلية ومسارات خطاف الويب.

PostgreSQL مثال على التعافي من الكوارث: على أ هدف استعادة منفصل ونظيف الذي لديه بالفعل دور قاعدة البيانات الصحيح وفارغ n8n قاعدة البيانات، ابدأ فقط PostgreSQL. انتظر حتى يصبح صحيًا قبل الاستيراد: docker compose up -d بمفرده يمكنه العودة بينما لا يزال PostgreSQL قيد التهيئة، لذا فإن ما يلي pg_restore يمكن أن تفشل. يستخدم المثال --wait على تثبيت Compose حديث والتحقق بشكل مستقل pg_isready. قم بتكوين فحص صحي مناسب PostgreSQL للانتظار الموثوق به، أو قم بتأكيد الاستعداد بشكل صريح قبل المضي قدمًا. لا تقم بتوجيه هذا الأمر إلى قاعدة بيانات إنتاج مملوءة أو بدء n8n قبل قاعدة البيانات ومطابقتها .n8n تتم استعادة المفتاح/البيانات.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

يجب أن تحتوي الوجهة على إصدار PostgreSQL متوافق، وامتيازات الدور، والملحقات، وتكوين n8n الأصلي. استعادة .n8n إلى حجمه الثابت الصحيح أو ربطه باستخدام آلية النسخ الاحتياطي، مع الحفاظ على الملكية والأذونات. قم باستعادة الملفات الثنائية الخارجية، والامتدادات المخصصة، وتكوين الإنشاء والأسرار، ثم ابدأ تشغيل n8n بإصدار متوافق وتحقق من سجلاته. استعادة قاعدة البيانات وحدها لا تؤدي إلى استرداد المفتاح: يؤدي نشر PostgreSQL إلى الاحتفاظ بالمفتاح .n8n/config إلا إذا قمت بتكوينها بشكل صريح N8N_ENCRYPTION_KEY. مرجع pg_restore · n8n تسلسل استعادة المثيل الكامل.

استعادة الاختبار

لم يتم إثبات النسخ الاحتياطي حتى تنجح عملية الاستعادة

اختبار على بيئة نظيفة

يجب أن يثبت التدريب الحقيقي أن النسخة الاحتياطية يمكنها إعادة بناء مثيل دون الاعتماد على الملفات غير المعلنة المتبقية على خادم الإنتاج.

التحقق من بيانات الاعتماد

فتح سير العمل لا يكفي. تأكد من أن بيانات الاعتماد المشفرة التي تمت استعادتها قد تم فك تشفيرها والمصادقة عليها بنجاح.

تشغيل سير العمل التمثيلي

اختبار سير العمل الذي يعتمد على خطافات الويب وواجهات برمجة التطبيقات الخارجية والملفات المثبتة وعقد المجتمع بدلاً من التحقق من صحة التشغيل الآلي البسيط فقط.

قياس وقت الاسترداد

سجل المدة التي تستغرقها عملية الاستعادة والخطوات اليدوية المتبقية. يؤدي هذا إلى تحويل النسخة الاحتياطية المفترضة إلى إجراء استرداد تشغيلي.

تدريبات الاستعادة التي تم التحقق منها: SQLite و PostgreSQL

بيئة الاختبار: n8n 2.42.5 في حاويات Docker المعزولة على مشغل الإجراءات GitHub القابل للتصرف، باستخدام سير عمل اصطناعي ثنائي العقدة. استمرت هذه الشيكات 8 أكتوبر 2026، وليس على خادم n8n الخاص بالعميل أو الإنتاج.

SQLite: تمريرتم استيراد سير عمل اختباري، وتصديره، وإيقاف جميع الكتاب، وأرشفة الثابت المدعوم من SQLite .n8n المجلد ومفتاح التشفير الذي تم إنشاؤه، واستعادتهما إلى مجلد نظيف، وبدء تشغيل n8n، ثم إعادة تصدير وتنفيذ سير العمل المسترد.
PostgreSQL: تمريرتم استيراد نفس سير العمل الاختباري، وإنشاء تنسيق مخصص وفحصه pg_dump، واستعادته باستخدام pg_restore في قاعدة بيانات PostgreSQL فارغة جديدة، تم استعادة الملف المنفصل .n8n المجلد، ثم إعادة تصديره وتنفيذ سير العمل المسترد.
ما يؤسس PASSحافظت مسارات النسخ الاحتياطي التي تم اختبارها على سير العمل وعقدتيه واتصالاتهما وسمحت بالتنفيذ بعد الاسترداد. هذه هي اختبارات الدخان الوظيفية القابلة للتكرار، وليست معايير عبء العمل.
ما لم يتم اختبارهفك تشفير بيانات الاعتماد الحقيقية والمصادقة عليها، وخطافات الويب الخاصة بالإنتاج، والعاملين في وضع قائمة الانتظار، و Redis، والتخزين الثنائي S3/Azure، والعقد المخصصة، والوصول إلى المستخدم/المشروع أو استعادة مثيل الإنتاج المباشر. قم بإجراء تمرين منفصل لكل تبعية تستخدمها بالفعل.

كيفية التكاثر: استخدم تثبيت n8n القابل للتصرف، وقم بإنشاء سير عمل ثنائي العقدة غير ضار، وقم بتنفيذ قاعدة البيانات القابلة للتطبيق بالإضافة إلى النسخ الاحتياطي للمجلد المستمر، والاستعادة إلى وحدة تخزين أو قاعدة بيانات نظيفة، ثم تحقق من عقد سير العمل المستعاد والاتصالات والتنفيذ الفعلي. في نظام الإنتاج، تحقق أيضًا من بيانات الاعتماد المشفرة وخطافات الويب والملفات الخارجية قبل الإعلان عن إثبات التعافي من الكوارث.

استعادة قائمة التحقق من قبول التدريب: استخدام مجال/بيئة معزولة؛ تحقق من وجود المستخدمين ومهام سير العمل، ومصادقة بيانات الاعتماد المشفرة الموجودة دون إعادة الإدخال، واستدعاء خطاف الويب الخاص بالإنتاج سير العمل المستعاد المقصود، وبقاء الملفات المحملة والمرفقات الثنائية قابلة للقراءة، وتحميل عمليات التكامل مع عقد المجتمع المطلوبة. قم بتأكيد عمر النسخ الاحتياطي ووقت التوقف المقاس وإمكانية الوصول خارج الخادم. في حالة فشل أي فحص أساسي، قم بوضع علامة على نقطة الاسترداد هذه لم يتم التحقق منها بدلاً من الإبلاغ عن النسخة الاحتياطية على أنها كاملة.

CLI حدود النسخ الاحتياطي

تعرف بالضبط على سير العمل وصادرات بيانات الاعتماد التي لا يمكن استعادتها

CLI الصادرات ليست نسخة احتياطية كاملة للمثيل

لا تتضمن عمليات تصدير النسخ الاحتياطي لسير العمل وبيانات الاعتماد المستخدمين والأدوار، أو محفوظات وسجلات التنفيذ، أو المتغيرات، أو إعدادات المثيل مثل مفتاح التشفير.

استعادة المثيل الجديد تحتاج إلى مالك

في المثيل النظيف، أكمل إعداد المالك قبل استيراد بيانات الاعتماد. قد تحتاج عمليات استعادة المستخدمين المتعددين أو عمليات استعادة المشروع أيضًا إلى تعيين المستخدم أو المشروع الصحيح.

يمكن للمعرفات المستوردة استبدال العناصر الموجودة

تحتفظ عمليات تصدير سير العمل وبيانات الاعتماد بمعرفاتها الأصلية. يمكن أن يؤدي الاستيراد إلى مثيل يحتوي بالفعل على نفس المعرفات إلى استبدال تلك العناصر الموجودة.

نشر مسارات العمل المستوردة عمدا

CLI الواردات عادة ما تترك سير العمل غير نشط. في n8n 2.x، تحقق من الحالة المنشورة لكل سير عمل مستورد وانشر فقط مسارات العمل التي تنوي تشغيلها؛ يدعم الخادم المستضاف ذاتيًا CLI أيضًا n8n نشر: سير العمل --id=YOUR_WORKFLOW_ID. عند تشغيل n8n، تصبح تغييرات حالة النشر/إلغاء النشر الخاصة بالخادم CLI سارية المفعول فقط بعد إعادة تشغيل n8n. أعد التشغيل قبل التحقق من المشغلات المجدولة وخطافات الويب الخاصة بالإنتاج أو تبديل حركة المرور.

مثال التصدير المجمع لـ Docker التأليف: إذا تم تسمية خدمة n8n الخاصة بك n8n، يمكنك تشغيل النسخ الاحتياطية الرسمية CLI أدناه. مسار الإخراج موجود بشكل متعمد داخل مساره المثبت .n8n الدليل، لأن الدلائل العشوائية الموجودة داخل الحاوية قد تختفي عند إعادة إنشائها. تأكد من أن الدليل قابل للكتابة بواسطة مستخدم حاوية n8n. احتفظ بسير العمل وبيانات الاعتماد JSON في أدلة منفصلة—n8n يوثق مشكلة الاستيراد عندما يشترك كلا النوعين في الدليل.

n8n 2.x المسودة مقابل النسخة الاحتياطية المنشورة: عادي --backup تصدير سير العمل يلتقط المسودات الحالية؛ يمكن أن تختلف هذه عن الإصدارات المنشورة في الإنتاج. للاحتفاظ بالإصدار الفعلي المنشور لسير عمل معين، قم بتصديره بشكل منفصل باستخدام docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json، بعد التأكد من وجود مجلد الإخراج وقابل للكتابة. يمكن لـ CLI أيضًا تصدير نسخة تاريخية باستخدام --version=VERSION_ID. احتفظ بهذه اللقطات خارج الخادم إلى جانب النسخة الاحتياطية الكاملة؛ لا تفترض أن المسودة JSON تسجل حالة النشر المباشر.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

المنسوخ ~/n8n-recovery/cli لا يزال الدليل موجودًا في VPS حتى تقوم بنقله إلى موقع نسخ احتياطي آمن ومستقل. يتم تشفير تصدير بيانات الاعتماد بشكل افتراضي ويحتاج إلى مفتاح التشفير المطابق عند الاستيراد. تجنب استخدام --decrypted باستثناء الهجرة الخاضعة لرقابة صارمة: فهي تكتب الأسرار بنص عادي. لا تقم مطلقًا بتنفيذ عمليات تصدير تحتوي على منطق سير عمل حساس أو بيانات اعتماد إلى مستودع GitHub عام. تقوم بعض قوالب النسخ الاحتياطي لبيانات الاعتماد GitHub التابعة لجهات خارجية بتصدير الأسرار التي تم فك تشفيرها عمدًا؛ المستودع الخاص هو تقييد الوصول، وليس التشفير. افحص إعدادات التصدير الفعلية لكل قالب وأذونات التخزين، وقم بتشفير الأسرار قبل النقل خارج الخادم، وقم بتدوير أي بيانات اعتماد مكشوفة من خلال تحميل نص عادي غير مقصود.

مثال على الاستيراد بالجملة: على هدف نظيف، أكمل إعداد المالك، وقم بتوفير مفتاح التشفير الأصلي وتأكد من توفر ملفات النسخ الاحتياطي المحفوظة على هذا الاسترداد VPS. ما يلي يقوم بإنشاء المجلد الوجهة ونسخ الملف workflows/ و credentials/ المجلدات الفرعية من المضيف إلى حاوية n8n؛ قم بتعديل المسارات إذا كان تخطيط وحدة التخزين Docker مختلفًا:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

تحقق من ملكية الملف والوصول إليه لمستخدم حاوية n8n. لا تقم بالاستيراد عبر مثيل إنتاج مملوء دون الرجوع إلى الحالة السابقة التي تم التحقق منها: يمكن لسير العمل ومعرفات الاعتماد أن تحل محل الإدخالات الموجودة. ثم قم بتشغيل:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

يمكن أن تحل المعرفات المستوردة محل مهام سير العمل أو بيانات الاعتماد الحالية؛ استخدم نسخة اختبار معزولة لعمليات التشغيل الجافة وتحقق من بيانات الاعتماد وحالات التنشيط/النشر بعد ذلك. في n8n 2.x، لا تثبت استعادة مسودة JSON بحد ذاتها أنه تم نشر سير العمل ويمكن تشغيل المشغلات المجدولة. سلامة الاستيراد: في مثيل n8n غير متعدد العناصر الرئيسية، يمكن أن تستمر مشغلات cron النشطة مسبقًا في التشغيل بعد استيراد CLI حتى تتم إعادة تشغيل المثيل. إيقاف مشغلات الإنتاج أو عزلها وإعادة تشغيل n8n قبل تمكين الوظائف المستعادة؛ تحقق من عدم وجود تنفيذ مكرر. CLI الصادرات تفعل لا تحتوي على المستخدمين الأصليين أو سجلات التنفيذ أو متغيرات الحالة أو مفتاح التشفير. --backup مجموعات --all --pretty --separate، وليس "المثيل الكامل". المصادر: دليل النسخ الاحتياطي/الاستعادة الرسمي الحالي n8n ومرجع الأمر n8n CLI.

استعادة مجمعة من GitHub أو قوالب Google Drive: يعد هذا بديلاً لسير العمل JSON فقط، وليس لقاعدة بيانات المثيلات أو المستخدمين أو قيم بيانات الاعتماد المشفرة أو مفتاح التشفير. قبل تشغيل قالب يستند إلى API، تحقق من n8n API وأذونات التخزين، وإصدار النسخ الاحتياطي المحدد والمثيل المستهدف، وما إذا كان يقوم بتحديث المعرفات المطابقة ويعيد إنشاء مسارات العمل المحذوفة، وما يفعله بنشر سير العمل. لا تقوم كافة القوالب بإعادة إنشاء معرف مفقود من الهدف؛ اختبر هذا السيناريو بشكل منفصل قبل الاعتماد على الاستعادة التلقائية.

الأسئلة الشائعة

n8n النسخ الاحتياطي والاستعادة: الأسئلة الشائعة

هل تصدير سير العمل كافٍ لعمل نسخة احتياطية من n8n؟

لا، تعد عمليات تصدير سير العمل نسخًا منطقية مفيدة، ولكن الاسترداد الكامل قد يتطلب أيضًا بيانات اعتماد ومفتاح التشفير المطابق وحالة قاعدة البيانات والملفات الدائمة وتخزين البيانات الثنائية.

هل أحتاج إلى مفتاح التشفير n8n إذا كان لدي قاعدة البيانات؟

نعم إذا كنت تريد أن تظل بيانات الاعتماد المشفرة المخزنة في قاعدة البيانات هذه قابلة للاستخدام. الحفاظ على المفتاح الأصلي بشكل آمن.

هل يجب أن أقوم بعمل نسخة احتياطية من PostgreSQL أو تصدير سير العمل وبيانات الاعتماد؟

للتعافي من الكوارث، قم بحماية قاعدة البيانات ومفتاح التشفير. تعتبر الصادرات المنطقية ذات قيمة باعتبارها طبقة ترحيل إضافية واسترداد انتقائي بدلاً من كونها بديلاً لكل جزء من المثيل.

هل يمكن أن تكون لقطة VPS هي النسخة الاحتياطية الوحيدة لدي؟

من الأفضل معاملتها كطبقة استرداد واحدة. احتفظ بنسخة احتياطية مستقلة خارج الخادم حتى لا يؤدي فشل الموفر أو الحساب أو الخادم أو اللقطة إلى إزالة كل نقطة استرداد مرة واحدة.

كيف أعرف أن النسخة الاحتياطية تعمل؟

قم باستعادته إلى بيئة اختبار نظيفة، وتحقق من فك تشفير بيانات الاعتماد، وقم بتشغيل مسارات العمل التمثيلية. لا تثبت مهمة النسخ الاحتياطي الناجحة وحدها إمكانية الاسترداد.

هل تتضمن GitHub أو النسخ الاحتياطية لسير عمل Google Drive أسرار بيانات الاعتماد المحفوظة؟

لا تتضمن النسخ الاحتياطية لسير العمل JSON فقط القيم السرية التي تتم إدارتها بواسطة مخزن بيانات الاعتماد الخاص بـ n8n أو مفتاح تشفير المثيل. ومع ذلك، يمكن أن يعرض JSON المُصدَّر أسماء بيانات الاعتماد والمعرفات والأسرار المكتوبة مباشرةً في معلمات العقدة، مثل رؤوس المصادقة. فحص وحماية JSON المصدرة قبل تحميلها أو مشاركتها. للحصول على الاسترداد الكامل، قم بعمل نسخة احتياطية من قاعدة البيانات والمفتاح الأصلي، أو استخدم تصدير بيانات الاعتماد المشفرة المدعومة CLI مع استعادة تم اختبارها. لا يعد قالب GitHub أو قالب Google Drive المخصص لسير العمل فقط بمثابة استرداد كامل للكوارث.

أهداف التعافي

تحديد RPO وRTO قبل وقوع الحادث

RPO هو الحد الأقصى للخسارة المسموح بها للتغييرات الأخيرة. قم بقياسه من أحدث نقطة استرداد قابلة للاستخدام ومخزنة بشكل مستقل؛ لا تؤدي المهمة المجدولة لمدة ست ساعات إلى إنشاء RPO لمدة ست ساعات في حالة فشل عمليات التصدير أو النقل. RTO هو الحد الأقصى للانقطاع المسموح به. قم بقياس ذلك من خلال تدريبات استعادة نظيفة، بما في ذلك استرداد الأسرار واستعادة الملفات الخارجية وإعادة فحص بيانات الاعتماد ونشر مسارات العمل المستردة، وليس مجرد بدء حاوية.

مفتاح الاسترداد

ابحث عن مفتاح التشفير الأصلي قبل إعادة البناء

إذا تم تعيين الإنتاج N8N_ENCRYPTION_KEY، حافظ على سر البيئة الدقيق هذا. إذا لم يحدث ذلك، فاحتفظ بالمفتاح الذي تم إنشاؤه في الملف الثابت الأصلي .n8n/config. تحقق من المصدر الذي يستخدمه المثيل المسترد بالفعل قبل استيراد بيانات الاعتماد المشفرة؛ لا يمكن للمفتاح الذي تم إنشاؤه حديثًا فك تشفير بيانات الاعتماد من قاعدة البيانات القديمة.
