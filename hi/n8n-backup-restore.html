BACKUP & RECOVERY

n8n Backup और Restore

Self-hosted n8n का backup और restore करने के लिए SQLite database या consistent PostgreSQL dump, persistent .n8n folder और original encryption key, deployment configuration तथा सभी external binary या mounted-file dependencies सुरक्षित रखें। VPS के बाहर encrypted copy रखें और अलग instance पर recovery test करें। Selective recovery के लिए CLI workflow और credential exports उपयोग करें; केवल JSON exports full server backup नहीं हैं।

QUICK CHECKLIST

n8n backup में क्या सुरक्षित होना चाहिए

Database

PostgreSQL database या instance द्वारा उपयोग की जाने वाली SQLite database file का backup लें। Database में workflows, credentials और execution data जैसे core n8n state होते हैं।

Encryption key

ठीक वही n8n encryption key अलग और सुरक्षित रखें। Restored encrypted credentials उसी key पर निर्भर करते हैं।

Persistent files

Persistent n8n data directory और वे सभी mounted files, binary-data storage या workflow assets शामिल करें जिन पर deployment निर्भर है।

Deployment configuration

Stack rebuild करने के लिए जरूरी Compose/configuration files और non-secret configuration सुरक्षित रखें। Secrets को उचित access controls से protect करें।

दो BACKUP LEVELS

Logical export बनाम complete disaster recovery

Workflow & credential export

n8n CLI exports migration, versioned workflow copies और selective restoration के लिए उपयोगी हैं। Credentials encrypted form में export करके बाद में matching encryption key के साथ import किए जा सकते हैं। केवल एक workflow recover करने के लिए workflow editor के three-dot menu से JSON Download करें, फिर नए review workflow या isolated instance में Import from File करें। Live workflow replace करने से पहले credentials, workflow IDs और node parameters जाँचें: workflow JSON restore करने से पूरा server restore नहीं होता।

Entity export

CLI supported database types के बीच data move करने के लिए database entities export कर सकती है। Execution-history tables optional हैं क्योंकि वे बहुत बड़े हो सकते हैं।

Full instance recovery

Dead-server scenario के लिए actual database, encryption key, persistent data और deployment dependencies सुरक्षित रखें। Workflow JSON export से पूरी instance reconstruct हो जाएगी, ऐसा न मानें।

Provider snapshot

VPS snapshot अतिरिक्त recovery layer के रूप में उपयोगी है, लेकिन यह एकमात्र copy नहीं होना चाहिए और independently verified application/database backup की जगह नहीं लेना चाहिए।

DATABASE

Database का consistent backup लें

PostgreSQL

Consistent PostgreSQL backup method उपयोग करें और backup को VPS से बाहर रखें। उसी failed disk पर database copy disaster recovery नहीं है।

SQLite

यदि deployment SQLite उपयोग करता है, तो persistent n8n data directory की database file सुरक्षित रखें। Database actively modify हो रही हो तो unsafe state में copy न करें।

Execution history

तय करें कि historical execution data recovery objective का हिस्सा है या नहीं। इससे backups काफी बड़े हो सकते हैं, इसलिए retention और compliance requirements के आधार पर निर्णय लें।

Database version

Source deployment में उपयोग database engine और version record करें ताकि compatible recovery environment तैयार किया जा सके।

Docker Compose VPS पर PostgreSQL। यदि PostgreSQL service का नाम postgres और database/user दोनों n8n, तो नीचे का command host पर consistent PostgreSQL custom-format dump बनाता है। चलाने से पहले actual Compose file देखें और database credentials तथा service names adjust करें। pg_dump PostgreSQL चलने के दौरान logically consistent snapshot बना सकता है; यह नहीं अलग .n8n user folder या external binary data का backup नहीं लेता।

# Docker Compose project में service, DB और user names adapt करें
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# जाँचें कि archive की object list readable है
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Archive-list check स्पष्ट format problems पकड़ती है, लेकिन यह साबित नहीं करती कि data restore हो सकता है। Encrypted copy off-server रखें और restore rehearsal करें। Database-specific options के लिए official PostgreSQL pg_dump documentation देखें।

Docker पर SQLite। Default SQLite deployment में database.sqlite और generated encryption-key config persistent .n8n folder के अंदर रहते हैं (आम तौर पर mount होता है /home/node/.n8n )। SQLite की simple live copy को consistent न मानें। Folder copy करने से पहले n8n और अन्य database writers रोकें, या interruption संभव न हो तो SQLite का supported online backup mechanism उपयोग करें:

# केवल SQLite और default /home/node/.n8n mount के लिए
# SQLite database copy करने से पहले n8n और अन्य writers रोकें
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

ये दिखाए गए service और path के illustrative commands हैं, universal volume layout नहीं। Copied folder शुरू में उसी VPS पर रहता है; उसे off-server transfer और protect करें। Queue workers या अन्य writers हों तो उन्हें भी रोकें और actual deployment design follow करें। n8n की current full-backup guidance SQLite consistency requirement document करती है।

Default SQLite folder को clean target पर restore करना: पहले n8n service और सभी database writers रोकें। Compatible n8n service container और destination volume बनने के बाद backed-up .n8n contents वापस उसी persistent directory में copy करें। इससे target files overwrite होंगी, इसलिए ऐसी instance पर न चलाएँ जिसका data रखना है:

# केवल intended CLEAN recovery instance पर चलाएँ
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# अगले command से पहले n8n container user के ownership और permissions verify करें
# Restored files n8n द्वारा readable/writable होने के बाद ही start करें
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker stopped containers में copy कर सकता है, लेकिन destination ownership original से अलग हो सकती है; start करने से पहले सुनिश्चित करें कि restored configuration और database file n8n process द्वारा readable/writable हों। यदि actual Compose configuration अलग path या bind mount उपयोग करती है, copy को उसके अनुसार adapt करें। Docker Compose copy reference। Separate PostgreSQL database वाले deployments में केवल n8n folder restore करना पर्याप्त नहीं है।

CRITICAL SECRET

Encryption key recovery का हिस्सा है

n8n stored credentials को instance encryption key से encrypt करता है। Matching key के बिना database या encrypted credential export restore होने पर workflows saved credentials उपयोग नहीं कर पाएँगे।

यदि N8N_ENCRYPTION_KEY set किया है, ठीक वही secret restore करें। अन्यथा generated key persistent .n8n/config file में होता है; backup या rebuild के समय उस config को protect करें। Recovery keys VPS के बाहर सुरक्षित रखें। Queue mode में सभी main और worker processes को वही key उपयोग करनी चाहिए।

करेंProduction में उपयोग हुई exact key की protected copy रखें।
करेंCredentials test करने से पहले verify करें कि recovery environment वही key उपयोग करता है।
न करेंServer rebuild के बाद newly generated key पर निर्भर न रहें।
न करेंKey को public repository में commit न करें और unprotected backup के साथ न रखें।

FILES & BINARY DATA

Database backup हर workflow dependency cover नहीं कर सकता

Persistent .n8n data

Actual .n8n user folder locate और preserve करें, केवल container image नहीं। Typical Docker deployment में यह /home/node/.n8n पर mounted होता है; Docker के बाहर default ~/.n8n है। यदि N8N_USER_FOLDER configured है, n8n दिए गए parent directory के अंदर .n8n बनाता है। इसकी config key और installation द्वारा उपयोग local SQLite, binary या filesystem execution data शामिल करें।

Mounted workflow files

यदि workflows host-mounted directories read/write करते हैं, उन directories का अलग backup लें। उनके बिना n8n restore करने पर valid workflows भी टूट सकते हैं।

Binary data

Storage mode identify करें और हर external dependency restore करें। Filesystem-based binary या execution data .n8n या custom directory में हो सकता है; S3/Azure Blob या अन्य configured external storage के लिए अपनी recoverable copy और access settings चाहिए। केवल database dump उन files की जगह नहीं ले सकता।

Community nodes

Community packages और versions record करें और N8N_CUSTOM_EXTENSIONS से configured additional custom node directories का backup लें। ये directories .n8n के बाहर हो सकती हैं; केवल database और user-folder restore करने पर custom-node workflows unusable रह सकते हैं।

OFF-SERVER STRATEGY

उसी VPS पर backup केवल local copy है

Local copyQuick rollback के लिए उपयोगी, लेकिन server loss, disk failure और destructive mistakes से vulnerable।
Off-server copyकम से कम एक backup production VPS से independent storage में रखें।
Versioned copiesMultiple recovery points retain करें ताकि corruption या खराब change अकेले usable backup को overwrite न कर दे।
Access controlBackups में credentials, workflow logic और sensitive business data हो सकते हैं। उन्हें उचित रूप से encrypt और restrict करें।
MonitoringScheduled backups fail हों या नए recovery points बनना बंद हों तो alert करें।

Schedule को measurable बनाएँ। हर successful backup का timestamp, transfer completion, file size, source database version, encryption-key recovery location और latest successful restore test record करें। Missing, failed या unexpectedly empty files पर alert करें। Backup archives को VPS से बाहर भेजने से पहले encrypt करें और recovery secrets का access restrict करें। Multiple dated recovery points उस स्थिति से बचाते हैं जब corruption का पता newest copy द्वारा last healthy copy overwrite करने के बाद चले।

उदाहरण के लिए यदि आप अधिकतम छह घंटे के changes खोना tolerate कर सकते हैं, तो successful six-hour backup schedule सिर्फ starting point है, guarantee नहीं: failed jobs और delayed off-server replication actual loss बढ़ा सकते हैं। Universal 7-day या 30-day policy मानने के बजाय retention और restore cadence अपने RPO/RTO और data requirements के अनुसार तय करें।

RESTORE ORDER

Controlled sequence में recover करें

1 · तैयार करेंCompatible server, database और container/runtime environment provision करें।
2 · Secrets restore करेंOriginal n8n encryption key और required deployment secrets सुरक्षित रूप से configure करें।
3 · Database restore करेंPostgreSQL या SQLite recover करें और verify करें कि n8n expected data से connect कर सकता है।
4 · Files restore करेंPersistent directories, binary data और mounted workflow assets recover करें।
5 · n8n start करेंExpected hostname, database और environment configuration के साथ application start करें।
6 · Validate करेंConfirm करें कि users, workflows और credentials load होते हैं, फिर representative workflows और webhook paths execute करें।

PostgreSQL disaster-recovery example: एक अलग, clean restore target जिसमें पहले से सही database role और खाली n8n database हो, पहले start करें सिर्फ PostgreSQL। Import से पहले healthy होने तक wait करें: docker compose up -d अकेला return कर सकता है जबकि PostgreSQL अभी initialize हो रहा हो, इसलिए अगला pg_restore fail हो सकता है। Example उपयोग करता है --wait modern Compose installation पर और separately check करता है pg_isready. Reliable wait के लिए appropriate PostgreSQL healthcheck configure करें या आगे बढ़ने से पहले readiness explicitly confirm करें। इस command को populated production database पर न चलाएँ और database तथा matching .n8n key/data restore होने से पहले n8n start न करें।

# केवल FRESH, EMPTY TARGET DATABASE में RESTORE करें
# Postgres Compose service, database और user names adapt करें
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Destination में compatible PostgreSQL version, role privileges, extensions और original n8n configuration होना चाहिए। Restore करें .n8n backup mechanism से सही persistent volume या bind mount पर, ownership और permissions preserve करते हुए। External binary files, custom extensions, Compose और secrets configuration restore करें, फिर compatible version पर n8n start करके logs जाँचें। केवल database restore करने से key recover नहीं होती: PostgreSQL deployment key को .n8n/config में रखता है, जब तक आपने explicitly configure न किया हो N8N_ENCRYPTION_KEY. pg_restore reference · n8n full-instance restore sequence.

CLI BACKUP LIMITS

जानें workflow और credential exports क्या restore नहीं करते

CLI exports full instance backup नहीं हैं

Workflow और credential backup exports में users/roles, execution history/logs, variables या encryption key जैसी instance settings शामिल नहीं होतीं।

Fresh-instance restore में owner चाहिए

Clean instance पर credentials import करने से पहले owner setup पूरा करें। Multi-user या project restores में सही user/project assignment भी चाहिए हो सकता है।

Imported IDs existing items overwrite कर सकते हैं

Workflow और credential exports original IDs preserve करते हैं। Same IDs वाली instance में import करने पर existing items replace हो सकते हैं।

Imported workflows को सोच-समझकर publish करें

CLI imports सामान्यतः workflows inactive छोड़ती हैं। n8n 2.x में हर imported workflow की published state जाँचें और केवल intended workflows publish करें; self-hosted Server CLI n8n publish:workflow --id=YOUR_WORKFLOW_ID भी support करती है। n8n चल रहा हो तो Server CLI publish/unpublish changes restart के बाद लागू होते हैं। Scheduled triggers/production webhooks verify या traffic switch करने से पहले restart करें।

Docker Compose के लिए bulk export example: यदि n8n service का नाम n8n, तो नीचे official CLI backups चला सकते हैं। Output path जानबूझकर mounted persistent .n8n directory के अंदर है क्योंकि container recreate होने पर arbitrary directories गायब हो सकती हैं। Confirm करें कि directory n8n container user द्वारा writable है। Workflow और credential JSON को अलग directoriesमें रखें—दोनों types एक directory share करें तो n8n import problem document करता है।

n8n 2.x draft बनाम published backup: सामान्य --backup workflow export current drafts capture करता है; ये production में published versions से अलग हो सकते हैं। किसी workflow का actual published version preserve करने के लिए इसे separately export करें docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, यह सुनिश्चित करने के बाद कि output folder मौजूद और writable है। CLI historical version भी export कर सकती है --version=VERSION_ID. इन captures को full backup के साथ off-server रखें; draft JSON को live published state का record न मानें।

# Docker Compose project से execute करें; n8n service मौजूद होनी चाहिए
# Workflow और credential backups अलग folders में रखें
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Saved export directories को container से बाहर host पर copy करें
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Copied ~/n8n-recovery/cli directory तब तक VPS पर है जब तक उसे secured independent backup location पर move नहीं करते। Credential export default रूप से encrypted है और import पर matching encryption key चाहिए। उपयोग न करें --decrypted सिवाय strictly controlled migration के: यह secrets plaintext में लिखता है। Sensitive workflow logic या credentials वाले exports को public GitHub repository में कभी commit न करें। कुछ third-party GitHub credential-backup templates जानबूझकर decrypted secrets export करते हैं; private repository access restriction है, encryption नहीं। हर template की actual export settings/storage permissions inspect करें, off-server transfer से पहले secrets encrypt करें और unintended plaintext upload से exposed credentials rotate करें।

Bulk import example: clean target पर owner setup पूरा करें, original encryption key दें और सुनिश्चित करें saved backup files recovery VPS पर उपलब्ध हों। नीचे destination folder बनता है और workflows/ और credentials/ subfolders host से n8n container में copy होते हैं; Docker volume layout अलग हो तो paths adapt करें:

# केवल intended CLEAN recovery instance पर चलाएँ
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups

FAQ

n8n backup और restore: आम सवाल

क्या workflows export करना n8n backup के लिए पर्याप्त है?

नहीं। Workflow exports useful logical copies हैं, लेकिन complete recovery में credentials, matching encryption key, database state, persistent files और binary-data storage भी चाहिए हो सकते हैं।

Database होने पर भी n8n encryption key चाहिए?

हाँ, यदि database में stored encrypted credentials usable रखने हैं। Original key सुरक्षित रखें।

PostgreSQL backup लें या workflows और credentials export करें?

Disaster recovery के लिए database और encryption key protect करें। Logical exports अतिरिक्त migration/selective-recovery layer के रूप में उपयोगी हैं, instance के हर हिस्से का substitute नहीं।

क्या VPS snapshot ही एकमात्र backup हो सकता है?

इसे एक recovery layer मानना बेहतर है। Independent off-server backup रखें ताकि provider, account, server या snapshot failure सभी recovery points एक साथ न हटाए।

कैसे पता चले backup काम करता है?

इसे clean test environment में restore करें, credentials decrypt होते हैं यह verify करें और representative workflows चलाएँ। केवल successful backup job recoverability साबित नहीं करती।

क्या GitHub या Google Drive workflow backups में saved credential secrets शामिल होते हैं?

Workflow-only JSON backups में n8n credential store द्वारा managed secret values या instance encryption key शामिल नहीं होते। लेकिन exported JSON credential names/IDs और node parameters में सीधे लिखे secrets, जैसे authentication headers, expose कर सकता है। Upload/share से पहले exported JSON inspect और protect करें। Full recovery के लिए database और original key का backup लें या tested restore के साथ supported encrypted credential CLI exports उपयोग करें। Workflow-only GitHub/Google Drive template full disaster recovery नहीं है।
