PRODUCTION सुरक्षा

VPS पर n8n को सुरक्षित करें

VPS पर n8n को सुरक्षित करने के लिए n8n (5678), PostgreSQL (5432) और optional Redis (6379) को public internet से बाहर रखें; HTTPS reverse proxy, SSH keys और MFA उपयोग करें, encryption key सुरक्षित रखें, webhooks authenticate करें, risky workflow capabilities सीमित करें और deployed instance का audit करें। Editor को public webhook routes से अलग protect करें। केवल HTTPS connected services को सुरक्षित नहीं करता।

QUICK CHECKLIST

Public exposure से पहले minimum security baseline

Reachable ports, HTTPS, verified administrative access, MFA और saved credentials की protection से शुरू करें। हर incoming webhook को sensitive work trigger करने से पहले authenticate करें। Access controls बदलने के बाद verify करें कि intended editors और external integrations काम करते हैं, फिर n8n security audit चलाएँ।

केवल HTTPS

n8n को correctly configured TLS reverse proxy के पीछे रखें और editor तथा webhooks के लिए public HTTPS URL consistently उपयोग करें।

Minimum open ports

केवल public traffic के लिए जरूरी ports expose करें। PostgreSQL, Redis और internal application ports को public internet से बाहर रखें।

SSH harden करें

Key-based administration उपयोग करें, login access restrict करें और operating system patched रखें।

Credentials protect करें

n8n encryption key को stable और secret रखें। Environment files, database access और backup copies को sensitive assets मानें।

NETWORK EDGE

Reverse proxy, HTTPS और trusted headers

TLS termination

HTTPS terminate करने के लिए Nginx, Caddy या Traefik जैसे reverse proxy का उपयोग करें। Plain HTTP redirect करें और जब proxy intended entry point हो तो n8n application port सीधे expose न करें।

Proxy configuration

जब n8n reverse proxy के पीछे चलता है, proxy hop count सही configure करें और वे forwarded headers pass करें जिनसे n8n original client request reconstruct करता है।

Secure cookies

Editor को HTTPS पर serve करें ताकि authentication cookies secure रहें। Broken TLS setup को cookie security कमजोर करके workaround न करें।

Webhook URL

Public webhook URL को externally reachable HTTPS hostname पर set करें ताकि generated webhook endpoints internal container या HTTP address पर point न करें।

Webhooks को तोड़े बिना editor private रखें। जहाँ practical हो management access को VPN, trusted-IP policy या authenticated proxy से restrict करें। Public webhook receivers और OAuth callback routes reachable रह सकते हैं; proxy rule लागू करने से पहले trusted editor sign-in और real external callback दोनों test करें। Client-address headers केवल trusted proxies से forward करें, arbitrary request headers से नहीं।

Webhook callers authenticate करें: Webhook node में sender support करे तो None के बजाय Basic, Header या JWT authentication चुनें। इसकी IP(s) Allowlist option उचित जगह उपयोग करें और जहाँ integration signed requests support करे वहाँ provider signatures verify करें। Difficult-to-guess URL पर्याप्त authentication नहीं है। जरूरत पर proxy में rate limits लागू करें और confirm करें valid bursts block न हों। Official Webhook authentication options।

VPS HARDENING

Server attack surface कम करें

Firewall

Unsolicited inbound traffic default-deny करें और केवल जरूरी reachable services allow करें। Database और Redis ports सामान्यतः private/local networks पर रहने चाहिए।

SSH

Passwords के बजाय SSH keys prefer करें, unnecessary login paths disable करें और administrative access सीमित रखें। Root-equivalent access कड़ाई से control करें।

OS updates

Linux host और container runtime patch करें। Application hardening exposed या obsolete operating system की भरपाई नहीं कर सकता।

Container exposure

केवल वे ports publish करें जिन्हें host access चाहिए। Internal services public interfaces के बजाय private Docker networks पर communicate करें।

Firewall या SSH settings बदलने से पहले inspect करें: check listening ports with sudo ss -lntp, Docker publishing with docker compose ps from the project directory, and host firewall policy with sudo ufw status verbose if UFW is used. Verify your actual SSH port and successful key login in a separate session before disabling password access. Published Docker ports can bypass UFW rules; a firewall status page alone does not prove port 5678 is private. Check real external reachability. Docker/UFW caveat.

Automatic Ubuntu security updates काम करते हैं ऐसा मानने के बजाय check करें: inspect apt-config dump APT::Periodic::Unattended-Upgrade and the log /var/log/unattended-upgrades/unattended-upgrades.log. If unattended security upgrades are disabled, sudo dpkg-reconfigure unattended-upgrades provides a supported configuration dialog. Review reboot and service-restart behavior before enabling it on a working VPS. Ubuntu APT updates do नहीं n8n Docker image या हर third-party software repository को automatically update नहीं करते। Ubuntu automatic-update documentation।

Optional SSH brute-force monitoring: Fail2Ban can detect repeated failed SSH logins. If installed and configured for SSH, verify the jail with sudo fail2ban-client status sshd and confirm it reads your actual SSH authentication log or journal and matches the configured port. This complements SSH keys and network restrictions; it does not replace them. Do not copy a fixed SSH port or ban rule without checking existing access first. Ubuntu SSH hardening guidance.

DATABASE & REDIS

Backend services private रखें

In a typical Docker Compose setup, PostgreSQL and queue-mode Redis should be reachable by the relevant containers through private networking, not host-published ports. Verify with docker compose ps that 5432 and 6379 are not publicly published; separately review VPS/cloud firewall exposure. Network policies do not substitute for least-privilege database credentials.

PostgreSQLइसे private interface या container network से bind करें, जब तक remote access explicitly required और independently secured न हो।
RedisQueue-mode Redis infrastructure है, public endpoint नहीं। Network access केवल उन n8n components तक restrict करें जिन्हें इसकी जरूरत है।
CredentialsDedicated database credentials केवल application की जरूरी permissions के साथ उपयोग करें और source control से बाहर protect करें।
TransportDatabase traffic untrusted networks cross करे तो केवल application-level credential encryption पर निर्भर रहने के बजाय उचित encrypted transport उपयोग करें।

N8N SECRETS

Encryption key और credential boundary protect करें

Encryption key

n8n stored credentials को encryption key से encrypt करता है। Restarts और workers में वही key preserve करें और ordinary application content से अलग protect करें।

Environment secrets

Passwords, tokens या encryption key को public repository में commit न करें। Environment files और deployment secrets का access restrict करें।

User access

Editor access केवल trusted users को दें। Workflows sensitive systems से connect कर सकते हैं और secrets process या powerful nodes execute कर सकते हैं।

Credential scope

जहाँ संभव हो narrowly scoped service accounts और API tokens उपयोग करें। Compromised workflow को unrelated systems का broad access automatically inherit नहीं होना चाहिए।

Review करने वाली n8n configuration: N8N_BLOCK_ENV_ACCESS_IN_NODE=true prevents Code-node and expression access to environment values; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true requests owner-only permissions on the settings file. Keep N8N_ENCRYPTION_KEY persistent and backed up securely: n8n can create a random key at first startup, but losing it may make existing encrypted credentials unusable. Do not replace a production encryption key casually; use an officially supported rotation procedure. Blocking environment access can break existing integrations, so test before production changes. n8n security variable definitions.

WORKFLOW RISK

Nodes security boundary बढ़ा सकते हैं

Self-hosting workflows को काफी power देता है। Code execution, shell access, arbitrary HTTP requests और third-party community nodes risk बढ़ा सकते हैं। Unneeded functionality disable करें और untrusted workflow imports run करने से पहले review करें।

Exact supported controls उपयोग करें: configure NODES_EXCLUDE with a JSON array of nodes to disable, such as n8n-nodes-base.executeCommand and n8n-nodes-base.readWriteFile, if unused. Some high-risk nodes are already blocked by default in newer versions; review the actual list before changing it. Official node exclusions.

n8n से 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true enables checks for outbound HTTP requests to internal, loopback and metadata-address ranges. Legitimate internal API workflows may stop working; if necessary, narrowly allowlist only destinations you control. Keep network segmentation as the primary defense. For Code-node isolation, review external task runners. SSRF protection · Task-runner isolation.

Community nodesकेवल trusted packages install करें; वे आपके n8n environment में execute करते हैं।
Risky nodesउन nodes को exclude करें जिनकी capabilities intended workflow boundary से अधिक हैं और deployment को उनकी जरूरत नहीं।
SSRFजहाँ workflows को internal या metadata endpoints तक नहीं पहुँचना चाहिए वहाँ n8n SSRF protection और network controls उपयोग करें।
Workflow importsActivation से पहले imported workflows, credentials, expressions और executable steps review करें।

AUDIT & अपडेट्स

Security एक ongoing operating process है

n8n security audit चलाएँ

The official CLI command is n8n audit. If your Docker Compose service is named n8n, run docker compose exec -T n8n n8n audit in that deployment directory. Review the five categories: unused credentials, risky SQL-query patterns, file-system access, risky/community nodes, and instance risks including unprotected webhooks and outdated releases. Fix relevant findings and rerun. This is not a penetration test. Official audit guide.

Updates सोच-समझकर करें

Security fixes पाने के लिए n8n को पर्याप्त current रखें। Internet-facing instance को permanently stale छोड़ने के बजाय release notes review करें और important upgrades test करें।

Authentication monitor करें

Unexpected access patterns, workflow changes और failures देखें। जब operating model को broad public reachability की जरूरत न हो तो editor UI को और restrict करें।

Rollback और recovery तैयार करें

Significant upgrades से पहले recoverable backups लें। Detailed backup scope और restoration अलग recovery guide में हैं।

Sensitive execution history कम रखें: successful runs can persist customer data and tokens. When appropriate set EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, keep EXECUTIONS_DATA_PRUNE=true, and choose an EXECUTIONS_DATA_MAX_AGE in hours, such as 168 (seven days). These are configurable examples, not legal retention rules. Less history means less debugging and forensic data; running, waiting or annotated executions may not be pruned in the same way. Official execution retention.

Compromise का संदेह: Evidence नष्ट किए बिना malicious access restrict करें, proxy/host/n8n activity और changed workflows inspect करें, possibly exposed upstream credentials revoke या rotate करें, cause patch करें और जरूरत पर केवल tested recoverable backups से restore करें। Affected webhook URLs, editor accounts और connected services review करें; HTTPS, snapshots या VPS purchase में incident-response services included हैं ऐसा न मानें।

ACCOUNT & PLATFORM CONTROLS

Editor और VPS दोनों protect करें

मजबूत login protection जरूरी करें

Editor accounts के लिए two-factor authentication enable करें और edition centralized policy enforcement support करे तो n8n security policies से MFA enforce करें।

Workflow edit access सीमित करें

Editor access privileged access है: workflows credentials पढ़ सकते हैं, internal systems call कर सकते हैं और powerful nodes execute कर सकते हैं। User access narrow रखें और unnecessary accounts हटाएँ।

Unused capabilities disable करें

Public API unnecessary हो तो disable करके और high-risk nodes/features block करके application attack surface कम करें।

SSRF और secret controls सोच-समझकर उपयोग करें

Arbitrary HTTP requests करने वाले workflows के लिए n8n SSRF protection evaluate करें और secrets को workflow code, public repositories तथा broadly readable environment files से बाहर रखें।

Unused management endpoints restrict करें: N8N_PUBLIC_API_DISABLED=true disables the n8n public REST API, and N8N_PUBLIC_API_SWAGGERUI_DISABLED=true disables its API playground separately. Do this only when your integrations do not require those features. Disabling the REST API does not authenticate workflow webhook URLs. Use MFA for editor users, and centralized policies only where your n8n edition supports them.

FAQ

n8n VPS security: आम सवाल

क्या n8n port सीधे expose होना चाहिए?

जब reverse proxy public entry point हो, proxy expose करें और application port उसके पीछे रखें, unnecessary services broadly publish न करें।

क्या PostgreSQL या Redis public होने चाहिए?

सामान्यतः नहीं। वे केवल उन systems के लिए reachable हों जिन्हें उनकी जरूरत है। Public exposure normal n8n operation में मदद किए बिना attack surface बढ़ाता है।

n8n encryption key महत्वपूर्ण क्यों है?

यह n8n में stored credentials protect करती है और पूरे deployment में consistent रहनी चाहिए। इसे खोने पर recovered data से usable encrypted credentials नहीं मिल सकतीं।

क्या community nodes सुरक्षित हैं?

वे n8n में third-party code जोड़ते हैं, इसलिए उन्हें अपनी supply-chain और privilege risks वाली software dependencies मानें। केवल वही install करें जिस पर भरोसा हो और जरूरत हो।

क्या HTTPS self-hosted n8n instance को सुरक्षित बना देता है?

नहीं। HTTPS transport protect करता है। Production security को host hardening, access control, private backend services, secret protection, safe workflow capabilities, monitoring और updates भी चाहिए।

क्या n8n editor private रह सकता है जबकि production webhooks चलते रहें?

हाँ। Trusted reverse proxy या VPN editor/admin access को public production webhook और OAuth callback paths से अलग restrict कर सकता है। हर access-rule change के बाद trusted sign-in और external webhook delivery test करें ताकि integrations accidentally block न हों।

Incoming n8n webhooks authenticate कैसे करें?

Sender support करे तो Webhook node में Basic, Header या JWT authentication configure करें। IP(s) Allowlist भी उपयोग कर सकते हैं और available होने पर provider signatures check करें। केवल secret-looking path पर निर्भर न रहें; sensitive API actions trigger होने से पहले requests validate करें।
