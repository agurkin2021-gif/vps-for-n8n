PRODUCTION SECURITY

Secure n8n on a VPS

To secure n8n on a VPS, keep n8n (5678), PostgreSQL (5432) and optional Redis (6379) off the public internet; use an HTTPS reverse proxy, SSH keys and MFA, preserve your encryption key, authenticate webhooks, limit risky workflow capabilities and audit the deployed instance. Protect the editor separately from the public webhook routes. HTTPS alone does not secure the connected services.

QUICK CHECKLIST

Minimum security baseline before public exposure

Start with your reachable ports, HTTPS, verified administrative access, MFA and protection of saved credentials. Authenticate each incoming webhook before it can trigger sensitive work. After changing access controls, verify that intended editors and external integrations still work, then run the n8n security audit.

HTTPS only

Put n8n behind a correctly configured TLS reverse proxy and use the public HTTPS URL consistently for the editor and webhooks.

Minimal open ports

Expose only the ports required for public traffic. Keep PostgreSQL, Redis and internal application ports off the public internet.

Harden SSH

Use key-based administration, restrict who can log in and keep the operating system patched.

Protect credentials

Keep the n8n encryption key stable and secret. Treat environment files, database access and backup copies as sensitive assets.

NETWORK EDGE

Reverse proxy, HTTPS and trusted headers

TLS termination

Use a reverse proxy such as Nginx, Caddy or Traefik to terminate HTTPS. Redirect plain HTTP and avoid exposing the n8n application port directly when the proxy is the intended entry point.

Proxy configuration

When n8n runs behind a reverse proxy, configure the proxy hop count correctly and pass the forwarded headers n8n needs to reconstruct the original client request.

Secure cookies

Serve the editor over HTTPS so authentication cookies can remain secure. Do not work around a broken TLS setup by weakening cookie security.

Webhook URL

Set the public webhook URL to the externally reachable HTTPS hostname so generated webhook endpoints do not point at an internal container or HTTP address.

Keep the editor private without breaking webhooks. Restrict management access using a VPN, trusted-IP policy or an authenticated proxy when practical. Public webhook receivers and OAuth callback routes may need to remain reachable; test both a trusted editor sign-in and a real external callback before enforcing a proxy rule. Forward client-address headers only from trusted proxies, not arbitrary request headers.

Authenticate webhook callers: in the Webhook node choose Basic, Header or JWT authentication instead of None when supported by the sender. Use its IP(s) Allowlist option where appropriate, and verify provider signatures where the integration supports signed requests. A difficult-to-guess URL is not sufficient authentication. Apply rate limits at the proxy when appropriate and confirm valid bursts are not blocked. Official Webhook authentication options.

VPS HARDENING

Reduce the server attack surface

Firewall

Default-deny unsolicited inbound traffic and permit only services that must be reachable. Database and Redis ports normally belong on private/local networks.

SSH

Prefer SSH keys over passwords, disable unnecessary login paths and limit administrative access. Root-equivalent access should be tightly controlled.

OS updates

Patch the Linux host and container runtime. Application hardening cannot compensate for an exposed or obsolete operating system.

Container exposure

Publish only the ports that need host access. Internal services should communicate on private Docker networks rather than through public interfaces.

Inspect before changing firewall or SSH settings: check listening ports with sudo ss -lntp, Docker publishing with docker compose ps from the project directory, and host firewall policy with sudo ufw status verbose if UFW is used. Verify your actual SSH port and successful key login in a separate session before disabling password access. Published Docker ports can bypass UFW rules; a firewall status page alone does not prove port 5678 is private. Check real external reachability. Docker/UFW caveat.

Check automatic Ubuntu security updates instead of assuming they work: inspect apt-config dump APT::Periodic::Unattended-Upgrade and the log /var/log/unattended-upgrades/unattended-upgrades.log. If unattended security upgrades are disabled, sudo dpkg-reconfigure unattended-upgrades provides a supported configuration dialog. Review reboot and service-restart behavior before enabling it on a working VPS. Ubuntu APT updates do not automatically update the n8n Docker image or every third-party software repository. Ubuntu automatic-update documentation.

Optional SSH brute-force monitoring: Fail2Ban can detect repeated failed SSH logins. If installed and configured for SSH, verify the jail with sudo fail2ban-client status sshd and confirm it reads your actual SSH authentication log or journal and matches the configured port. This complements SSH keys and network restrictions; it does not replace them. Do not copy a fixed SSH port or ban rule without checking existing access first. Ubuntu SSH hardening guidance.

DATABASE & REDIS

Keep backend services private

In a typical Docker Compose setup, PostgreSQL and queue-mode Redis should be reachable by the relevant containers through private networking, not host-published ports. Verify with docker compose ps that 5432 and 6379 are not publicly published; separately review VPS/cloud firewall exposure. Network policies do not substitute for least-privilege database credentials.

PostgreSQLBind it to a private interface or container network unless remote access is explicitly required and independently secured.
RedisQueue-mode Redis is infrastructure, not a public endpoint. Restrict network access to the n8n components that require it.
CredentialsUse dedicated database credentials with only the permissions the application needs and protect them outside source control.
TransportWhen database traffic crosses untrusted networks, use appropriate encrypted transport rather than relying on application-level credential encryption.

N8N SECRETS

Protect the encryption key and credential boundary

Encryption key

n8n encrypts stored credentials using its encryption key. Preserve the same key across restarts and workers and protect it separately from ordinary application content.

Environment secrets

Do not commit passwords, tokens or the encryption key to a public repository. Restrict access to environment files and deployment secrets.

User access

Give editor access only to trusted users. Workflows can connect to sensitive systems and may process secrets or execute powerful nodes.

Credential scope

Use narrowly scoped service accounts and API tokens where possible. A compromised workflow should not automatically inherit broad access to unrelated systems.

n8n configuration to review: N8N_BLOCK_ENV_ACCESS_IN_NODE=true prevents Code-node and expression access to environment values; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true requests owner-only permissions on the settings file. Keep N8N_ENCRYPTION_KEY persistent and backed up securely: n8n can create a random key at first startup, but losing it may make existing encrypted credentials unusable. Do not replace a production encryption key casually; use an officially supported rotation procedure. Blocking environment access can break existing integrations, so test before production changes. n8n security variable definitions.

WORKFLOW RISK

Nodes can expand the security boundary

Self-hosting gives workflows substantial power. Code execution, shell access, arbitrary HTTP requests and third-party community nodes can increase risk. Disable functionality you do not need and review untrusted workflow imports before running them.

Use exact supported controls: configure NODES_EXCLUDE with a JSON array of nodes to disable, such as n8n-nodes-base.executeCommand and n8n-nodes-base.readWriteFile, if unused. Some high-risk nodes are already blocked by default in newer versions; review the actual list before changing it. Official node exclusions.

From n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true enables checks for outbound HTTP requests to internal, loopback and metadata-address ranges. Legitimate internal API workflows may stop working; if necessary, narrowly allowlist only destinations you control. Keep network segmentation as the primary defense. For Code-node isolation, review external task runners. SSRF protection · Task-runner isolation.

Community nodesInstall only packages you trust; they execute inside your n8n environment.
Risky nodesExclude nodes that your deployment does not need when their capabilities exceed the intended workflow boundary.
SSRFUse n8n's SSRF protection and network controls where workflows should not be able to reach internal or metadata endpoints.

AUDIT & UPDATES

Security is an operating process

Run n8n security audit

The official CLI command is n8n audit. If your Docker Compose service is named n8n, run docker compose exec -T n8n n8n audit in that deployment directory. Review the five categories: unused credentials, risky SQL-query patterns, file-system access, risky/community nodes, and instance risks including unprotected webhooks and outdated releases. Fix relevant findings and rerun. This is not a penetration test. Official audit guide.

Update deliberately

Keep n8n current enough to receive security fixes. Review release notes and test important upgrades rather than leaving an internet-facing instance permanently stale.

Monitor authentication

Watch unexpected access patterns, workflow changes and failures. Restrict the editor UI further when your operating model does not require broad public reachability.

Prepare rollback and recovery

Take recoverable backups before significant upgrades. Detailed backup scope and restoration belong to the separate recovery guide.

Minimize sensitive execution history: successful runs can persist customer data and tokens. When appropriate set EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, keep EXECUTIONS_DATA_PRUNE=true, and choose an EXECUTIONS_DATA_MAX_AGE in hours, such as 168 (seven days). These are configurable examples, not legal retention rules. Less history means less debugging and forensic data; running, waiting or annotated executions may not be pruned in the same way. Official execution retention.

Suspected compromise: restrict malicious access without destroying evidence, inspect proxy, host and n8n activity and changed workflows, revoke or rotate possibly exposed upstream credentials, patch the cause, and restore only from tested recoverable backups when needed. Review affected webhook URLs, editor accounts and connected services; do not assume HTTPS, snapshots or a VPS purchase provide incident-response services.

ACCOUNT & PLATFORM CONTROLS

Protect the editor as well as the VPS

Require stronger login protection

Enable two-factor authentication for editor accounts and enforce MFA through n8n security policies when your edition supports centralized policy enforcement.

Limit who can edit workflows

Editor access is privileged access: workflows can read credentials, call internal systems and execute powerful nodes. Keep user access narrow and remove accounts that no longer need it.

Disable capabilities you do not use

Reduce application attack surface by disabling the public API when it is unnecessary and blocking high-risk nodes or features that your operating model does not need.

Use SSRF and secret controls deliberately

For workflows that can make arbitrary HTTP requests, evaluate n8n's SSRF protection and keep secrets out of workflow code, public repositories and broadly readable environment files.

Restrict unused management endpoints: N8N_PUBLIC_API_DISABLED=true disables the n8n public REST API, and N8N_PUBLIC_API_SWAGGERUI_DISABLED=true disables its API playground separately. Do this only when your integrations do not require those features. Disabling the REST API does not authenticate workflow webhook URLs. Use MFA for editor users, and centralized policies only where your n8n edition supports them.

FAQ

n8n VPS security: common questions

Should the n8n port be exposed directly?

When a reverse proxy is the public entry point, expose the proxy and keep the application port behind it rather than publishing unnecessary services broadly.

Should PostgreSQL or Redis be public?

Normally no. They should be reachable only by the systems that require them. Public exposure increases attack surface without helping normal n8n operation.

Why is the n8n encryption key important?

It protects credentials stored by n8n and must remain consistent across the deployment. Losing it can prevent recovered data from yielding usable encrypted credentials.

Are community nodes safe?

They extend n8n with third-party code, so they should be treated as software dependencies with their own supply-chain and privilege risks. Install only what you trust and need.

Does HTTPS make a self-hosted n8n instance secure?

No. HTTPS protects transport. Production security also requires host hardening, access control, private backend services, secret protection, safe workflow capabilities, monitoring and updates.

Can the n8n editor be private while production webhooks still run?

Yes. A trusted reverse proxy or VPN can restrict editor/admin access separately from public production webhook and OAuth callback paths. Test trusted sign-in and external webhook delivery after every access-rule change to avoid accidentally blocking your integrations.

How do I authenticate incoming n8n webhooks?

Configure Basic, Header or JWT authentication in the Webhook node when the sender supports it. You can also use IP(s) Allowlist and check provider signatures where available. Do not rely only on a secret-looking path, and validate requests before they trigger sensitive API actions.
