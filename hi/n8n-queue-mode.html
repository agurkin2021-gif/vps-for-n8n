स्केलिंग

n8n Queue Mode

Queue mode workflow execution को main n8n process से अलग करता है। Main instance triggers receive करके executions बनाती है, Redis queue coordinate करता है, workers jobs execute करते हैं और PostgreSQL shared workflow तथा execution data store करता है।

त्वरित निर्णय

क्या आपको वास्तव में queue mode चाहिए?

Regular mode में रहें जब

एक instance peak executions आराम से संभालती हो और CPU, RAM तथा execution latency stable रहें। Queue mode ऐसे components जोड़ता है जिनकी अभी जरूरत नहीं।

Queue mode consider करें जब

Sustained parallel executions contention बनाएँ, load में execution latency बढ़े या multiple workers चलाकर execution capacity बढ़ानी हो।

पहले vertically scale करें जब

Bottleneck सिर्फ insufficient CPU या RAM हो और एक बड़ी instance workload को साफ़ तरीके से संभाल सके।

Architecture बदलने से पहले measure करें

Move justify करने के लिए peak concurrency, CPU, RAM, execution duration, queue depth और database pressure देखें।

ARCHITECTURE

n8n queue mode कैसे काम करता है

1 · MainTimers, webhooks और workflow requests receive करके production execution खुद करने के बजाय execution बनाता है।
2 · RedisMessage broker की तरह काम करता है। Pending execution messages रखता है ताकि अगला available worker job claim कर सके।
3 · WorkerExecution ID receive करता है, shared database से workflow data load करता है, workflow चलाता है और result वापस लिखता है।
4 · PostgreSQLShared persistent workflow और execution data देता है। Distributed queue mode SQLite पर supported नहीं है।

मुख्य आवश्यकताएँ

हर queue-mode deployment को क्या चाहिए

Redis

सभी main और worker processes को queue coordination के लिए उपयोग Redis service का reliable access चाहिए।

PostgreSQL

Main और workers को database share करना चाहिए। Queue mode distributed architecture है और SQLite के आसपास design नहीं होना चाहिए।

Matching n8n configuration

Main और workers queue mode में चलें और Redis, PostgreSQL तथा encrypted credentials access करने वाली configuration share करें।

Worker capacity

Workers को execute किए जाने वाले workflows के लिए पर्याप्त CPU और RAM चाहिए। Processes जोड़ने से हर execution की resource cost खत्म नहीं होती।

Existing self-hosted stack पर queue mode enable करें। First confirm that the n8n main service and every worker can reach the same PostgreSQL database and Redis over a private network. Set EXECUTIONS_MODE=queue on both main and workers, and supply QUEUE_BULL_REDIS_HOST=redis and QUEUE_BULL_REDIS_PORT=6379 when redis is your actual Compose service name. Use DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres and matching DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER and DB_POSTGRESDB_PASSWORD on every process; replace the example service names with yours. Provide the exact existing N8N_ENCRYPTION_KEY to all of them. Never publish Redis or PostgreSQL host ports merely to connect containers on the same Compose network.

Executor launch करें, दूसरा editor नहीं। Add an n8n worker service using the same pinned n8n image version and shared settings as main, but run it with the worker command. If you named that service n8n-worker, start it with docker compose up -d n8n-worker. After confirming actual execution on one worker, you can use docker compose up -d --scale n8n-worker=2 to start a second worker from that service. These are additions to an existing correctly configured Compose stack में, standalone installation file नहीं; existing persistent volumes, HTTPS proxy, secrets और backups रखें।

Existing stack के लिए queue-mode Compose fragment। Merge the example below into your current compose.yaml; it is not a complete stand-alone deployment. It assumes you already have persistent, private postgres and n8n services, an existing N8N_VERSION pin in your environment and your own protected POSTGRES_PASSWORD and original N8N_ENCRYPTION_KEY. Match its names, volumes, database and n8n version to the existing project. Add the queue-mode Redis settings and EXECUTIONS_MODE=queue to the existing main service too, as described above.

# Existing services के साथ merge करें; पूरी Compose file replace न करें।
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

इस fragment में Redis या worker के लिए host port publish नहीं है। Redis append-only persistence extra recovery layer है, not off-server backups का substitute नहीं। Existing HTTPS और authentication configuration unchanged रखें। External task runners चाहने वाले Code nodes के लिए runner processes worker deployment में अलग configure करें; queue mode task runners replace नहीं करता।

Existing SQLite instance convert कर रहे हैं? Do not simply change DB_TYPE and start against an empty PostgreSQL database: doing so does not migrate the old workflows and credentials. Before any cutover, back up the source database, persistent .n8n directory and original encryption key; use a supported n8n export/import or migration procedure, then verify workflows and encrypted credentials on a separate target. Keep the original files for rollback and use the Backup & Restore guide linked below for recovery preparation. Never delete database.sqlite as a shortcut.

WORKER CONCURRENCY

Workers count और jobs per worker दोनों से scale होते हैं

हर worker multiple jobs concurrently process कर सकता है। n8n का current default worker concurrency 10 है और documentation 5 या अधिक recommend करती है। बहुत low concurrency और कई workers unnecessary database connections बना सकते हैं और connection pool exhaust कर सकते हैं।

Concurrency बढ़ाएँ जब

Worker में spare CPU/RAM हो और workflows compute या memory saturate करने के बजाय mostly external services का wait कर रही हों।

Workers जोड़ें जब

एक worker process bottleneck बन जाए और database, Redis तथा infrastructure में अधिक parallel execution की capacity हो।

Concurrency घटाएँ जब

Individual workflows memory-heavy या CPU-heavy हों और parallel jobs contention, OOM pressure या unstable execution times पैदा करें।

PostgreSQL monitor करें

अधिक workers और concurrency database activity बढ़ाते हैं। Database capacity के बिना execution capacity scale करने से bottleneck हटने के बजाय shift हो सकता है।

जानें कौन-सी concurrency limit वास्तव में लागू होती है। A worker can be started using n8n worker --concurrency=5, or the equivalent worker command in your Compose service. If N8N_CONCURRENCY_PRODUCTION_LIMIT is explicitly set to a value other than -1, that setting takes precedence in queue mode; otherwise n8n uses the worker's --concurrency value or its default of 10. Do not multiply worker count by a nominal default and call it guaranteed throughput: actual capacity depends on job duration, CPU, memory, external APIs and PostgreSQL connections.

WEBHOOKS

Queue mode execution handoff latency जोड़ सकता है

Main या webhook process HTTP request receive करता है, लेकिन workflow execution worker करता है। Redis से handoff कुछ overhead जोड़ता है। Latency-sensitive webhooks के लिए end-to-end response time measure करें; अधिक workers हर request automatically तेज करेंगे ऐसा न मानें।

ReceiveMain/webhook process request accept करता है।
QueueExecution Redis को handoff होती है।
ExecuteAvailable worker workflow चलाता है।
Respondजरूरत पर result queue path से वापस relay होता है।

Webhook traffic सही process पर route करें। With dedicated n8n webhook processors behind a reverse proxy or load balancer, route production paths /webhook/* and /webhook-waiting/* to the webhook processors; keep /webhook-test/*, editor and API requests on main. Do not put main into the production webhook load-balancing pool unless you deliberately accept that added workload. A Respond to Webhook workflow client को तब तक wait करा सकता है जब तक worker finish होकर response लौटाए; इसलिए queue mode instant HTTP responses या zero timeouts की guarantee नहीं। Traffic switch से पहले actual external callback और response behavior test करें।

BINARY DATA

Shared storage को नज़रअंदाज़ न करें

Filesystem limitation

Queue mode distributed workers के shared persistence model के रूप में filesystem binary-data storage support नहीं करता।

External binary storage

जब workflows को distributed workers के बीच binary data persist करना हो, ऐसा storage design उपयोग करें जिसे हर required instance access कर सके, जैसे supported external object storage।

बड़े webhook responses

Workers से webhook responses receiving process की ओर वापस जाते हैं। बड़े response bodies Redis memory pressure बढ़ा सकते हैं और deliberate response-storage configuration की जरूरत हो सकती है।

Workers distribute करने से पहले plan करें

Local files पर heavily dependent workload को workers machines में spread करने से पहले shared persistence के लिए redesign करना चाहिए।

बड़े webhook response की सीमा। Current n8n documentation gives N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX a default of 64 MiB worker response के लिए जो queue से वापस भेजा जाता है। Redis कई copies in flight रख सकता है, इसलिए हर concurrent large response के लिए Redis memory में response size का लगभग 1.5 गुना budget करें। Offloading के बिना oversized response fail होगा; workers जोड़ने से वह magically faster नहीं होगा।

Version और license limits। n8n से 2.34.0, workers can use N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true to offload oversized webhook response bodies to readable shared binary storage, but first upgrade हर main और webhook processor to 2.34.0 or later. The selected N8N_DEFAULT_BINARY_DATA_MODE must actually store data and be readable by every participating process. External S3 and Azure binary storage require a valid self-hosted Business या Enterprise license; do not assume Community Edition can enable them. The database binary mode can offload an oversized response without paid external storage, but the main instance loads the whole stored body into memory and database storage has its own file-size limit. For विशेष रूप से response-body offload के लिए, n8n also describes a shared filesystem option when every instance mounts the same disk, but explicitly does not recommend that arrangement. Do not mistake this special offload path for support of filesystem-based persistent binary data in a distributed queue-mode deployment. Check your edition, version and storage configuration before enabling offload.

MONITORING

जानें queue वास्तव में मदद कर रही है या नहीं

Queue depth

Queue workers के drain करने से तेज बढ़े तो यह insufficient execution capacity या downstream bottleneck दिखाता है।

Worker CPU & RAM

हर worker की saturation और memory peaks measure करें। Growing queue के साथ idle workers किसी दूसरी constraint की ओर इशारा करते हैं।

Execution latency

Execution create होने और वास्तव में start होने के बीच delay track करें, केवल workflow runtime नहीं।

Health checks

Worker health endpoints बता सकते हैं कि worker alive है और database तथा Redis connections ready हैं या नहीं।

Execution worker पर verify करें, सिर्फ green container पर नहीं। With a correctly configured Compose stack, check docker compose ps and docker compose logs --tail=100 n8n-worker (replace the service name if different). Run a harmless published production workflow scheduled trigger या test webhook से चलाएँ, फिर n8n Executions view की execution को worker logs की actual processing से match करें। Editor का खुलना, running Redis container या queued execution अकेले not यह prove नहीं करता कि worker ने job perform की।

Dependencies और readiness check करें। With default example service names, docker compose exec -T redis redis-cli ping should receive PONG when Redis authentication permits it, and docker compose exec -T postgres pg_isready -U n8n -d n8n checks PostgreSQL readiness (adapt credentials and service names). Enable QUEUE_HEALTH_CHECK_ACTIVE=true on a worker when you need its private /healthz and /healthz/readiness endpoints; the readiness endpoint checks Redis/database connectivity. Do not expose those worker endpoints publicly just to monitor them.

Manual runs अलग test हैं। By default OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, so manually running a workflow in the editor can execute on main even when queue mode is correctly configured. Set it to true only if you intend to send manual executions to workers and have checked the change in a staging environment. Queue-mode workers are also distinct from n8n external task runners, which have separate configuration requirements for Code-node execution.

SCALING PATH

एक bottleneck को एक बार में scale करें

Stage 1PostgreSQL के साथ single n8n instance; peak CPU, RAM और concurrency measure करें।
Stage 2VPS resources तब बढ़ाएँ जब vertical scaling measured bottleneck को अभी भी साफ़ तरीके से solve करे।
Stage 3Redis और workers तब introduce करें जब sustained parallel demand distributed execution justify करे।
Stage 4PostgreSQL, Redis और execution latency देखते हुए workers जोड़ें या worker concurrency tune करें।
Stage 5Components को servers में केवल तब अलग करें जब capacity, availability या operational requirements extra complexity justify करें।

HIGH AVAILABILITY सीमा

Queue mode executions scale करता है, लेकिन main process को automatically highly available नहीं बनाता

Encryption key share करें

Every worker must use the same N8N_ENCRYPTION_KEY as the main instance so workers can decrypt credentials required by workflow executions.

Versions aligned रखें

Main, webhook और worker processes को same n8n version चलानी चाहिए। Mixed versions rolling changes के दौरान incompatible behavior पैदा कर सकती हैं।

Webhook processors अलग scaling layer हैं

जब incoming webhook volume bottleneck बन जाए, dedicated webhook processors load balancer के पीछे रह सकते हैं और workers execution संभालते हैं। Measured request volume justify न करे तो यह layer न जोड़ें।

Multi-main अलग feature है

High availability के लिए multiple main processes चलाना ordinary queue mode जैसा नहीं है। n8n currently multi-main को self-hosted Enterprise feature के रूप में document करता है जिसमें additional load-balancer और session requirements हैं।

FAQ

n8n queue mode: आम सवाल

क्या n8n queue mode को Redis चाहिए?

हाँ। Redis message broker है जो main instance और workers के बीच pending executions coordinate करता है।

क्या queue mode SQLite उपयोग कर सकता है?

Distributed queue-mode architecture के लिए नहीं। Main और workers को shared database access चाहिए और n8n इस setup के लिए PostgreSQL document करता है।

कितने workers चलाने चाहिए?

Universal count नहीं है। Measured concurrency और worker utilization से शुरू करें, फिर PostgreSQL, Redis, CPU, RAM और queue depth monitor करते हुए capacity जोड़ें।

n8n worker concurrency क्या है?

यह jobs की संख्या है जो worker parallel process कर सकता है। Current default 10 है और n8n कई low-concurrency workers बनाने के बजाय worker concurrency 5 या अधिक recommend करता है।

क्या छोटे VPS पर queue mode enable करना चाहिए?

केवल जब workload justify करे। छोटा deployment जो एक instance के रूप में आराम से चलता है, सामान्यतः Redis और separate workers के बिना operate करना सरल है।
