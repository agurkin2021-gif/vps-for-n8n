PENSKALAAN

n8n Baris gilir Mode

Baris gilir Mode memisahkan pelaksanaan aliran kerja daripada proses utama n8n. Instans utama menerima pencetus dan mencipta pelaksanaan, Redis menyelaras baris gilir, worker menjalankan tugas, dan PostgreSQL menyimpan data aliran kerja serta pelaksanaan yang dikongsi.

KEPUTUSAN PANTAS

Adakah anda benar-benar memerlukan Baris gilir Mode?

Kekal dengan mod biasa apabila

Satu instans mengendalikan pelaksanaan puncak dengan selesa dan CPU, RAM serta latensi pelaksanaan kekal stabil. Baris gilir Mode menambah komponen yang belum anda perlukan.

Pertimbangkan Baris gilir Mode apabila

Pelaksanaan selari yang berterusan menyebabkan perebutan sumber, latensi pelaksanaan meningkat di bawah beban, atau anda perlu menambah kapasiti pelaksanaan dengan menjalankan beberapa worker.

Skalakan secara menegak dahulu apabila

Jika kekangannya hanyalah CPU atau RAM yang tidak mencukupi dan satu instans lebih besar masih boleh memenuhi beban kerja dengan baik.

Ukur sebelum mengubah seni bina

Gunakan keserentakan puncak, CPU, RAM, tempoh pelaksanaan, kedalaman baris gilir dan tekanan pangkalan data untuk menentukan sama ada perubahan seni bina memang diperlukan.

SENI BINA

Cara Baris gilir Mode n8n berfungsi

1 · UtamaMenerima timer, webhook dan permintaan aliran kerja, kemudian mencipta pelaksanaan tanpa menjalankan pelaksanaan produksi itu sendiri.
2 · RedisBertindak sebagai message broker. Redis menyimpan mesej pelaksanaan tertunda supaya worker tersedia seterusnya boleh mengambil tugas.
3 · WorkerMenerima ID pelaksanaan, memuatkan data aliran kerja daripada pangkalan data dikongsi, menjalankan aliran kerja dan menulis semula hasilnya.
4 · PostgreSQLMenyediakan data aliran kerja dan pelaksanaan persisten yang dikongsi. Baris gilir Mode teragih tidak disokong dengan SQLite.

KEPERLUAN TERAS

Komponen yang diperlukan oleh setiap pelaksanaan Baris gilir Mode

Redis

Semua proses utama dan worker memerlukan akses yang boleh dipercayai kepada perkhidmatan Redis yang digunakan untuk menyelaras baris gilir.

PostgreSQL

Proses utama dan worker mesti berkongsi pangkalan data. Baris gilir Mode ialah seni bina teragih dan tidak patut dibina berasaskan SQLite.

konfigurasi n8n yang sepadan

Proses utama dan worker mesti menjalankan Baris gilir Mode dan berkongsi konfigurasi yang diperlukan untuk mengakses Redis, PostgreSQL dan bukti kelayakan disulitkan.

Kapasiti worker

Worker memerlukan CPU dan RAM yang mencukupi bagi aliran kerja yang dijalankan. menambah proses tidak menghapuskan kos sumber bagi setiap pelaksanaan.

Aktifkan Baris gilir Mode pada tindanan yang dihos sendiri. Pertama konfirmasikan bahwa layanan utama n8n dan setiap worker boleh menjangkau pangkalan data PostgreSQL dan Redis yang sama melalui rangkaian persendirian. Tetapkan EXECUTIONS_MODE=queue pada utama dan worker, dan pasokan QUEUE_BULL_REDIS_HOST=redis dan QUEUE_BULL_REDIS_PORT=6379 kapan redis adalah nama layanan Compose anda yang sebenar. Gunakan DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres dan mencocokkan DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER dan DB_POSTGRESDB_PASSWORD pada setiap proses; ganti contoh nama layanan dengan milik anda. Berikan yang sebenar ada N8N_ENCRYPTION_KEY kepada mereka semua. Jangan pernah memublikasikan port hos Redis atau PostgreSQL hanya untuk menghubungkan kontena di rangkaian Compose yang sama.

Jalankan executor, bukan editor kedua. Tambahkan layanan worker n8n menggunakan versi gambar n8n yang disematkan dan tetapan bersama sebagai yang utama, tetapi jalankan dengan worker perintah. Jika anda menamai layanan itu n8n-worker, mulailah dengan docker compose up -d n8n-worker. selepas mengesahkan pelaksanaan aktual pada satu worker, anda boleh menggunakannya docker compose up -d --scale n8n-worker=2 untuk memulakan worker kedua dari layanan itu. Ini adalah tambahan pada yang ada dikonfigurasi dengan benar Buat stack, bukan fail instalasi mandiri; simpan volume persisten, HTTPS proxy, rahsia, dan sandaran anda yang ada.

Fragmen Baris gilir Mode Compose untuk tindanan sedia ada. Gabungkan contoh di bawah ini ke dalam contoh anda apabila ini compose.yaml; itu tidak penyebaran yang berdiri sendiri secara lengkap. Ini mengasumsikan anda sudah memiliki persendirian yang persisten postgres dan n8n layanan, yang sudah ada N8N_VERSION sematkan di lingkungan anda dan perlindungan anda sendiri POSTGRES_PASSWORD dan asli N8N_ENCRYPTION_KEY. Cocokkan nama, volume, pangkalan data, dan versi n8n dengan proyek yang ada. Tambahkan tetapan Baris gilir Mode Redis dan EXECUTIONS_MODE=queue ke layanan utama yang ada juga, seperti dijelaskan di atas.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Tidak ada port hos yang dipublikasikan untuk Redis atau worker dalam fragmen ini. Redis persistensi tambahan saja adalah lapisan pemulihan tambahan, tidak pengganti sandaran di luar pelayan. Pertahankan HTTPS dan konfigurasi autentikasi yang ada tidak berubah. Untuk node Kode yang memerlukan runner tugas luaran, konfigurasikan proses runner untuk pelaksanaan worker anda secara terpisah; Baris gilir Mode itu sendiri tidak menggantikan pelari tugas.

Menukar instans SQLite sedia ada? Jangan sekadar berubah DB_TYPE dan memulakan dengan pangkalan data PostgreSQL yang kosong: hal ini tidak akan memigrasikan aliran kerja dan bukti kelayakan lama. Sebelum peralihan apa pun, buat sandaran pangkalan data sumber, tetap ada .n8n direktori dan kunci penyulitan asli; gunakan prosedur n8n ekspor/impor atau migrasi yang disokong, lalu sahkan aliran kerja dan bukti kelayakan terenkripsi pada target terpisah. Simpan fail asli untuk rollback dan gunakan panduan sandaran & Pemulihan yang ditautkan di bawah untuk persiapan pemulihan. Jangan pernah menghapus database.sqlite sebagai jalan pintas.

KESERENTAKAN WORKER

Skalakan worker berdasarkan bilangan dan keserentakan setiap worker

Setiap worker boleh memproses beberapa tugas secara serentak. Keserentakan worker lalai n8n pada masa ini ialah 10 dan dokumentasinya mengesyorkan keserentakan 5 atau lebih tinggi. Keserentakan terlalu rendah bersama banyak worker boleh menghasilkan sambungan pangkalan data yang tidak perlu dan menghabiskan connection pool pangkalan data.

Naikkan keserentakan apabila

Worker masih mempunyai lebihan CPU dan RAM, dan kebanyakan aliran kerja menunggu perkhidmatan luaran berbanding menggunakan penuh CPU atau memori.

Tambah worker apabila

Satu proses worker menjadi kekangan dan pangkalan data, Redis serta infrastruktur masih mempunyai kapasiti untuk pelaksanaan selari tambahan.

Kurangkan keserentakan apabila

Aliran kerja individu menggunakan banyak memori atau CPU dan tugas selari menyebabkan perebutan sumber, tekanan OOM atau tempoh pelaksanaan tidak stabil.

Pantau PostgreSQL

Lebih banyak worker dan keserentakan meningkatkan aktiviti pangkalan data. Menskalakan kapasiti pelaksanaan tanpa kapasiti pangkalan data yang sepadan hanya memindahkan kekangan, bukan menghapuskannya.

Ketahui had keserentakan yang benar-benar berkuat kuasa. Seorang worker boleh mulai menggunakan n8n worker --concurrency=5, atau perintah worker yang setara di layanan Compose anda. Jika N8N_CONCURRENCY_PRODUCTION_LIMIT secara eksplisit disetel ke nilai selain -1, tetapan tersebut diutamakan dalam Baris gilir Mode; jika tidak, n8n menggunakan milik worker --concurrency nilai atau defaultnya 10. Jangan mengalikan jumlah worker dengan nominal lalai dan menyebutnya throughput terjamin: kapasiti aktual bergantung pada durasi tugas, CPU, memori, API luaran, dan koneksi PostgreSQL.

WEBHOOK

Baris gilir Mode boleh menambah latensi penyerahan pelaksanaan

Proses utama atau webhook menerima permintaan HTTP, tetapi worker menjalankan aliran kerja. Penyerahan melalui Redis menambah sedikit overhead. Untuk webhook sensitif latensi, ukur masa respons hujung-ke-hujung dan jangan anggap lebih banyak worker secara automatik menjadikan setiap permintaan lebih pantas.

TerimaProses utama/webhook menerima permintaan.
Baris gilirPelaksanaan diserahkan kepada Redis.
JalankanWorker tersedia menjalankan aliran kerja.
BalasHasil dihantar semula melalui laluan baris gilir apabila diperlukan.

Halakan trafik webhook kepada proses yang betul. Dengan berdedikasi n8n webhook prosesor di belakang proxy terbalik atau penyeimbang beban, merutekan jalur produksi /webhook/* dan /webhook-waiting/* ke pemroses webhook; simpan /webhook-test/*, editor dan permintaan API di main. Jangan memasukkan main ke dalam kumpulan penyeimbang beban webhook produksi kecuali anda dengan sengaja menerima beban kerja tambahan tersebut. SEBUAH Balas Webhook aliran kerja mungkin membuat klien menunggu hingga worker selesai dan mengembalikan responsnya, jadi Baris gilir Mode bukanlah janji respons instan HTTP atau waktu tunggu nol. Uji perilaku panggilan balik dan respons luaran yang sebenar sebelum mengalihkan traffic.

DATA BINARI

Jangan abaikan storan dikongsi

Had sistem fail

Baris gilir Mode tidak menyokong storan data binari berasaskan sistem fail sebagai model persistensi dikongsi bagi worker teragih.

Storan binari luaran

Apabila aliran kerja perlu mengekalkan data binari merentas worker teragih, gunakan reka bentuk storan yang boleh dicapai oleh setiap instans diperlukan, seperti storan objek luaran yang disokong.

Respons webhook besar

Respons webhook daripada worker kembali kepada proses penerima. Badan respons besar boleh meningkatkan tekanan memori Redis dan memerlukan konfigurasi storan respons secara sengaja.

Rancang sebelum mengagihkan worker

Beban kerja yang banyak bergantung pada fail setempat perlu direka semula untuk persistensi dikongsi sebelum worker diagihkan merentas mesin.

Had respons webhook besar. Dokumentasi n8n apabila ini memberi N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX lalai dari 64 MiB untuk respons worker dikirim kembali melalui baris gilir. Redis boleh menampung beberapa salinan dalam penerbangan, sehingga anggaran kira-kira 1.5 kali saiz respons dalam memori Redis per respons besar secara bersamaan. Tanpa pembongkaran, respons yang terlalu besar akan gagal dan bukannya menjadi lebih cepat secara ajaib dengan menambah worker.

Had versi dan lesen. Dari n8n 2.34.0, worker boleh menggunakan N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true untuk memindahkan badan respons webhook yang berukuran besar ke storan binari bersama yang boleh dibaca, tetapi tingkatkan terlebih dahulu setiap prosesor utama dan webhook hingga 2.34.0 atau lebih baru. Yang dipilih N8N_DEFAULT_BINARY_DATA_MODE mesti benar-benar menyimpan data dan boleh dibaca oleh setiap proses yang berpartisipasi. storan binari S3 dan Azure luaran memerlukan self-hos yang valid Bisnis atau Enterprise lesen; jangan berasumsi Edisi Komunitas boleh mengaktifkannya. Itu database mode binari boleh memindahkan respons berukuran besar tanpa storan luaran berbayar, namun instans utama memuatkan seluruh isi yang disimpan ke dalam memori dan storan pangkalan data memiliki batas saiz filenya sendiri. Untuk pembongkaran badan respons secara khusus, n8n juga menjelaskan yang dibagikan filesystem pilihan apabila setiap instans memasang disk yang sama, namun secara eksplisit tidak merekomendasikan tetapan itu. Jangan salah mengartikan jalur offload khusus ini sebagai sokongan terhadap data binari persisten berbasis sistem fail dalam pelaksanaan Baris gilir Mode teragih. Periksa edisi, versi, dan konfigurasi storan anda sebelum mengaktifkan offload.

pemantauan

Ukur sama ada Baris gilir Mode benar-benar membantu

Kedalaman baris gilir

Baris gilir yang bertambah lebih cepat daripada kadar worker mengosongkannya menunjukkan kapasiti pelaksanaan tidak mencukupi atau terdapat kekangan di hiliran.

CPU & RAM worker

Ukur ketepuan dan puncak memori setiap worker. Worker melahu apabila baris gilir terus bertambah menunjukkan terdapat kekangan lain.

Latensi pelaksanaan

Jejaki kelewatan antara pelaksanaan dicipta dan benar-benar bermula, bukan hanya masa pemprosesan aliran kerja.

Pemeriksaan kesihatan

Health endpoint worker boleh melaporkan sama ada worker masih hidup dan sama ada sambungan pangkalan data serta Redis sudah sedia.

Sahkan pelaksanaan pada worker, bukan sekadar kontena hijau. Dengan stack Compose yang dikonfigurasi dengan benar, periksa docker compose ps dan docker compose logs --tail=100 n8n-worker (ganti nama layanan jika berbeda). Jalankan yang tidak berbahaya produksi yang diterbitkan aliran kerja menggunakan pemicu terjadwal atau webhook pengujian, lalu cocokkan eksekusinya dalam tampilan pelaksanaan n8n dengan pemrosesan worker sebenar di log worker. Editor yang berhasil dibuka, kontena Redis yang sedang berjalan, atau pelaksanaan yang diantri saja boleh melakukannya tidak membuktikan bahwa seorang worker telah melakukan pekerjaannya.

Semak kebergantungan dan kesediaan. Dengan contoh nama layanan lalai, docker compose exec -T redis redis-cli ping mesti menerima PONG apabila Redis otentikasi mengizinkannya, dan docker compose exec -T postgres pg_isready -U n8n -d n8n memeriksa kesiapan PostgreSQL (melaraskan bukti kelayakan dan nama layanan). Aktifkan QUEUE_HEALTH_CHECK_ACTIVE=true pada seorang worker apabila anda memerlukan pribadinya /healthz dan /healthz/readiness endpoint; endpoint kesiapan memeriksa konektivitas Redis/pangkalan data. Jangan mengekspos endpoint worker tersebut secara awam hanya untuk memantaunya.

Pelaksanaan manual ialah ujian yang berbeza. Secara lalai OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, jadi menjalankan aliran kerja secara manual di editor boleh dijalankan di main bahkan apabila Baris gilir Mode dikonfigurasi dengan benar. Setel ke true hanya jika anda bermaksud mengirimkan pelaksanaan manual ke worker dan telah memeriksa perubahan dalam lingkungan pementasan. Worker Baris gilir Mode juga berbeda dari pelari tugas luaran n8n, yang memiliki keperluan konfigurasi terpisah untuk pelaksanaan node kode.

SEMPADAN ketersediaan TINGGI

Baris gilir Mode menskalakan pelaksanaan, tetapi tidak secara automatik menjadikan proses utama highly available

Kongsi kunci penyulitan

Setiap worker mesti menggunakan hal yang sama N8N_ENCRYPTION_KEY sebagai instans utama sehingga worker boleh mendekripsi bukti kelayakan yang diperlukan oleh pelaksanaan aliran kerja.

Kekalkan versi yang sepadan

Proses utama, webhook, dan worker mesti menjalankan versi n8n yang sama. versi campuran boleh menimbulkan perilaku yang tidak kompatibel selama perubahan berterusan.

Webhook processor ialah lapisan penskalaan berasingan

apabila volume webhook yang masuk menjadi penghambat, pemroses webhook khusus boleh berada di belakang penyeimbang beban sementara worker menangani pelaksanaan. Jangan tambahkan lapisan ini kecuali volume permintaan yang diukur membenarkannya.

Multi-main ialah ciri berbeza

Menjalankan beberapa proses utama untuk ketersediaan tinggi tidak sama dengan Baris gilir Mode biasa. n8n apabila ini mendokumentasikan multi-utama sebagai fitur Enterprise yang self-hosted dengan penyeimbang beban tambahan dan keperluan sesi.

FAQ

n8n Baris gilir Mode: soalan lazim

Adakah n8n Baris gilir Mode memerlukan Redis?

Ya. Redis ialah message broker yang menyelaras pelaksanaan tertunda antara instans utama dan worker.

Bolehkah Baris gilir Mode menggunakan SQLite?

Tidak untuk seni bina Baris gilir Mode teragih. Proses utama dan worker memerlukan akses kepada pangkalan data dikongsi, dan n8n mendokumenkan PostgreSQL sebagai pangkalan data bagi persediaan ini.

Berapa banyak worker yang patut saya jalankan?

Tiada bilangan universal. Mulakan dengan saiz keserentakan dan penggunaan worker, kemudian tambah kapasiti sambil memantau PostgreSQL, Redis, CPU, RAM dan kedalaman baris gilir.

Apakah keserentakan worker n8n?

Ini ialah bilangan tugas yang boleh diproses worker secara selari. Nilai lalai semasa ialah 10, dan n8n mengesyorkan keserentakan worker 5 atau lebih tinggi berbanding mencipta banyak worker dengan keserentakan rendah.

Patutkah saya mengaktifkan Baris gilir Mode pada VPS kecil?

Hanya jika beban kerja membenarkannya. Pelaksanaan kecil yang berjalan selesa sebagai satu instans biasanya lebih mudah dikendalikan tanpa Redis dan worker berasingan.
