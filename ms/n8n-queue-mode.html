PENSKALAAN

n8n Queue Mode

Queue Mode memisahkan pelaksanaan aliran kerja daripada proses utama n8n. Instans utama menerima pencetus dan mencipta pelaksanaan, Redis menyelaras baris gilir, worker menjalankan tugas, dan PostgreSQL menyimpan data aliran kerja serta pelaksanaan yang dikongsi.

KEPUTUSAN PANTAS

Adakah anda benar-benar memerlukan Queue Mode?

Kekal dengan mod biasa apabila

Satu instans mengendalikan pelaksanaan puncak dengan selesa dan CPU, RAM serta latensi pelaksanaan kekal stabil. Queue Mode menambah komponen yang belum anda perlukan.

Pertimbangkan Queue Mode apabila

Pelaksanaan selari yang berterusan menyebabkan perebutan sumber, latensi pelaksanaan meningkat di bawah beban, atau anda perlu menambah kapasiti pelaksanaan dengan menjalankan beberapa worker.

Skalakan secara menegak dahulu apabila

Jika kekangannya hanyalah CPU atau RAM yang tidak mencukupi dan satu instans lebih besar masih boleh memenuhi beban kerja dengan baik.

Ukur sebelum mengubah seni bina

Gunakan keserentakan puncak, CPU, RAM, tempoh pelaksanaan, kedalaman baris gilir dan tekanan pangkalan data untuk menentukan sama ada perubahan seni bina memang diperlukan.

SENI BINA

Cara Queue Mode n8n berfungsi

1 · UtamaMenerima timer, webhook dan permintaan aliran kerja, kemudian mencipta pelaksanaan tanpa menjalankan pelaksanaan produksi itu sendiri.
2 · RedisBertindak sebagai message broker. Redis menyimpan mesej pelaksanaan tertunda supaya worker tersedia seterusnya boleh mengambil tugas.
3 · WorkerMenerima ID pelaksanaan, memuatkan data aliran kerja daripada pangkalan data dikongsi, menjalankan aliran kerja dan menulis semula hasilnya.
4 · PostgreSQLMenyediakan data aliran kerja dan pelaksanaan persisten yang dikongsi. Queue Mode teragih tidak disokong dengan SQLite.

KEPERLUAN TERAS

Komponen yang diperlukan oleh setiap pelaksanaan Queue Mode

Redis

Semua proses utama dan worker memerlukan akses yang boleh dipercayai kepada perkhidmatan Redis yang digunakan untuk menyelaras baris gilir.

PostgreSQL

Proses utama dan worker mesti berkongsi pangkalan data. Queue Mode ialah seni bina teragih dan tidak patut dibina berasaskan SQLite.

Konfigurasi n8n yang sepadan

Proses utama dan worker mesti menjalankan Queue Mode dan berkongsi konfigurasi yang diperlukan untuk mengakses Redis, PostgreSQL dan bukti kelayakan disulitkan.

Kapasiti worker

Worker memerlukan CPU dan RAM yang mencukupi bagi aliran kerja yang dijalankan. Menambah proses tidak menghapuskan kos sumber bagi setiap pelaksanaan.

Aktifkan Queue Mode pada tindanan yang dihos sendiri. Mula-mula sahkan bahawa perkhidmatan utama n8n dan setiap worker boleh mencapai pangkalan data PostgreSQL serta Redis yang sama melalui rangkaian persendirian. Tetapkan EXECUTIONS_MODE=queue pada proses utama dan semua worker, serta gunakan QUEUE_BULL_REDIS_HOST=redis dan QUEUE_BULL_REDIS_PORT=6379 apabila redis ialah nama sebenar perkhidmatan Compose anda. Gunakan DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres dan nilai sepadan untuk DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER serta DB_POSTGRESDB_PASSWORD pada setiap proses; gantikan nama perkhidmatan contoh dengan nama anda sendiri. Berikan N8N_ENCRYPTION_KEY sedia ada yang tepat kepada semua proses. Jangan terbitkan port hos Redis atau PostgreSQL hanya untuk menghubungkan kontena dalam rangkaian Compose yang sama.

Jalankan executor, bukan editor kedua. Tambah perkhidmatan worker n8n menggunakan versi imej n8n yang sama seperti proses utama dan tetapan dikongsi yang sama, tetapi jalankannya dengan arahan worker. Jika perkhidmatan itu dinamakan n8n-worker, mulakan dengan docker compose up -d n8n-worker. Selepas mengesahkan pelaksanaan sebenar pada satu worker, gunakan docker compose up -d --scale n8n-worker=2 untuk memulakan worker kedua daripada perkhidmatan tersebut. Ini ialah tambahan kepada tindanan Compose sedia ada yang telah dikonfigurasi dengan betul, bukan fail pemasangan kendiri; kekalkan volum persisten, proxy HTTPS, rahsia dan sandaran sedia ada.

Fragmen Compose Queue Mode untuk tindanan sedia ada. Gabungkan contoh di bawah ke dalam compose.yaml semasa anda; ia bukan pelaksanaan kendiri yang lengkap. Contoh ini menganggap anda sudah mempunyai perkhidmatan postgres dan n8n yang persisten dan persendirian, nilai N8N_VERSION yang telah dipin dalam persekitaran, serta POSTGRES_PASSWORD terlindung dan N8N_ENCRYPTION_KEY asal anda. Padankan nama, volum, pangkalan data dan versi n8n dengan projek sedia ada. Tambah tetapan Redis untuk Queue Mode dan EXECUTIONS_MODE=queue kepada perkhidmatan utama sedia ada seperti diterangkan di atas.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

Tiada port hos diterbitkan untuk Redis atau worker dalam fragmen ini. Persistensi append-only Redis hanyalah lapisan pemulihan tambahan, bukan pengganti sandaran di luar pelayan. Kekalkan konfigurasi HTTPS dan pengesahan sedia ada tanpa perubahan. Untuk Code node yang memerlukan task runner luaran, konfigurasikan proses runner secara berasingan bagi pelaksanaan worker anda; Queue Mode sendiri tidak menggantikan task runner.

Menukar instans SQLite sedia ada? Jangan hanya menukar DB_TYPE dan memulakan n8n dengan pangkalan data PostgreSQL kosong kerana tindakan itu tidak memigrasikan aliran kerja dan bukti kelayakan lama. Sebelum peralihan, sandarkan pangkalan data sumber, direktori .n8n persisten dan kunci penyulitan asal; gunakan prosedur eksport/import atau migrasi n8n yang disokong, kemudian sahkan aliran kerja dan bukti kelayakan disulitkan pada sasaran berasingan. Simpan fail asal untuk rollback dan gunakan panduan Sandaran & Pemulihan di bawah untuk persediaan pemulihan. Jangan padam database.sqlite sebagai jalan pintas.

KESERENTAKAN WORKER

Worker diskalakan melalui bilangan worker dan tugas setiap worker

Setiap worker boleh memproses beberapa tugas secara serentak. Keserentakan worker lalai n8n pada masa ini ialah 10 dan dokumentasinya mengesyorkan keserentakan 5 atau lebih tinggi. Keserentakan terlalu rendah bersama banyak worker boleh menghasilkan sambungan pangkalan data yang tidak perlu dan menghabiskan connection pool pangkalan data.

Naikkan keserentakan apabila

Worker masih mempunyai lebihan CPU dan RAM, dan kebanyakan aliran kerja lebih banyak menunggu perkhidmatan luaran berbanding memenuhi CPU atau memori.

Tambah worker apabila

Satu proses worker menjadi kekangan dan pangkalan data, Redis serta infrastruktur masih mempunyai kapasiti untuk lebih banyak pelaksanaan selari.

Kurangkan keserentakan apabila

Aliran kerja individu menggunakan banyak memori atau CPU dan tugas selari menyebabkan perebutan sumber, tekanan OOM atau tempoh pelaksanaan tidak stabil.

Pantau PostgreSQL

Lebih banyak worker dan keserentakan meningkatkan aktiviti pangkalan data. Menskalakan kapasiti pelaksanaan tanpa kapasiti pangkalan data yang sepadan hanya memindahkan kekangan, bukan menghapuskannya.

Ketahui had keserentakan yang benar-benar berkuat kuasa. Worker boleh dimulakan dengan n8n worker --concurrency=5, atau arahan worker yang setara dalam perkhidmatan Compose anda. Jika N8N_CONCURRENCY_PRODUCTION_LIMIT ditetapkan secara jelas kepada nilai selain -1, tetapan itu mengambil keutamaan dalam Queue Mode; jika tidak, n8n menggunakan nilai --concurrency worker atau nilai lalai 10. Jangan darab bilangan worker dengan nilai lalai nominal lalu menganggapnya throughput terjamin: kapasiti sebenar bergantung pada tempoh tugas, CPU, memori, API luaran dan sambungan PostgreSQL.

WEBHOOK

Queue Mode boleh menambah latensi penyerahan pelaksanaan

Proses utama atau webhook menerima permintaan HTTP, tetapi worker menjalankan aliran kerja. Penyerahan melalui Redis menambah sedikit overhead. Untuk webhook sensitif latensi, ukur masa respons hujung-ke-hujung dan jangan anggap lebih banyak worker secara automatik menjadikan setiap permintaan lebih pantas.

TerimaProses utama/webhook menerima permintaan.
Baris gilirPelaksanaan diserahkan kepada Redis.
JalankanWorker tersedia menjalankan aliran kerja.
BalasHasil dihantar semula melalui laluan baris gilir apabila diperlukan.

Halakan trafik webhook kepada proses yang betul. Jika anda menggunakan pemproses n8n webhook khusus di belakang reverse proxy atau load balancer, halakan laluan produksi /webhook/* dan /webhook-waiting/* kepada pemproses webhook; kekalkan /webhook-test/*, editor dan permintaan API pada proses utama. Jangan masukkan proses utama ke dalam kumpulan load balancing webhook produksi melainkan anda memang mahu menerima beban tambahan itu. Aliran kerja Respond to Webhook mungkin menyebabkan klien menunggu sehingga worker selesai dan memulangkan respons, jadi Queue Mode bukan jaminan respons HTTP serta-merta atau timeout sifar. Uji callback luaran dan tingkah laku respons sebenar sebelum mengalihkan trafik.

DATA BINARI

Jangan abaikan storan dikongsi

Had sistem fail

Queue Mode tidak menyokong storan data binari berasaskan sistem fail sebagai model persistensi dikongsi bagi worker teragih.

Storan binari luaran

Apabila aliran kerja perlu mengekalkan data binari merentas worker teragih, gunakan reka bentuk storan yang boleh dicapai oleh setiap instans diperlukan, seperti storan objek luaran yang disokong.

Respons webhook besar

Respons webhook daripada worker kembali kepada proses penerima. Badan respons besar boleh meningkatkan tekanan memori Redis dan memerlukan konfigurasi storan respons secara sengaja.

Rancang sebelum mengagihkan worker

Beban kerja yang banyak bergantung pada fail setempat perlu direka semula untuk persistensi dikongsi sebelum worker diagihkan merentas mesin.

Had respons webhook besar. Dokumentasi n8n semasa menetapkan nilai lalai N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX sebanyak 64 MiB bagi respons worker yang dihantar semula melalui baris gilir. Redis boleh menyimpan beberapa salinan dalam penerbangan, jadi anggarkan kira-kira 1.5 kali saiz respons dalam memori Redis bagi setiap respons besar serentak. Tanpa offload, respons terlalu besar akan gagal; menambah worker tidak menjadikannya lebih pantas secara automatik.

Had versi dan lesen. Bermula dengan n8n 2.34.0, worker boleh menggunakan N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true untuk memindahkan badan respons webhook terlalu besar ke storan binari dikongsi yang boleh dibaca, tetapi naik taraf dahulu semua proses utama dan pemproses webhook kepada 2.34.0 atau lebih baharu. Nilai N8N_DEFAULT_BINARY_DATA_MODE yang dipilih mesti benar-benar menyimpan data dan boleh dibaca oleh semua proses yang terlibat. Storan binari luaran S3 dan Azure memerlukan lesen Business atau Enterprise yang sah bagi n8n dihos sendiri; jangan anggap Community Edition boleh mengaktifkannya. Mod binari database boleh offload respons besar tanpa storan luaran berbayar, tetapi instans utama memuatkan keseluruhan badan respons ke memori dan storan pangkalan data mempunyai had saiz fail sendiri. Khusus untuk offload badan respons, n8n turut menerangkan pilihan filesystem dikongsi apabila semua instans memasang cakera yang sama, tetapi secara jelas tidak mengesyorkan susunan itu. Jangan anggap laluan offload khusus ini sebagai sokongan umum untuk data binari persisten berasaskan sistem fail dalam pelaksanaan Queue Mode teragih. Semak edisi, versi dan konfigurasi storan sebelum mengaktifkan offload.

PEMANTAUAN

Ukur sama ada Queue Mode benar-benar membantu

Kedalaman baris gilir

Baris gilir yang bertambah lebih cepat daripada kadar worker mengosongkannya menunjukkan kapasiti pelaksanaan tidak mencukupi atau terdapat kekangan di hiliran.

CPU & RAM worker

Ukur ketepuan dan puncak memori setiap worker. Worker melahu ketika baris gilir terus bertambah menunjukkan terdapat kekangan lain.

Latensi pelaksanaan

Jejaki kelewatan antara pelaksanaan dicipta dan benar-benar bermula, bukan hanya masa pemprosesan aliran kerja itu sendiri.

Pemeriksaan kesihatan

Health endpoint worker boleh melaporkan sama ada worker masih hidup dan sama ada sambungan pangkalan data serta Redis sudah sedia.

Sahkan pelaksanaan pada worker, bukan sekadar kontena hijau. Dengan tindanan Compose yang dikonfigurasi dengan betul, semak docker compose ps dan docker compose logs --tail=100 n8n-worker (gantikan nama perkhidmatan jika berbeza). Jalankan aliran kerja produksi yang diterbitkan dan tidak berbahaya menggunakan pencetus berjadual atau webhook ujian, kemudian padankan pelaksanaannya dalam paparan Executions n8n dengan pemprosesan sebenar dalam log worker. Editor yang berjaya dibuka, kontena Redis yang sedang berjalan atau pelaksanaan yang hanya berada dalam baris gilir tidak membuktikan worker telah menjalankan tugas.

Semak kebergantungan dan kesediaan. Dengan nama perkhidmatan contoh lalai, docker compose exec -T redis redis-cli ping sepatutnya menerima PONG apabila pengesahan Redis membenarkannya, dan docker compose exec -T postgres pg_isready -U n8n -d n8n memeriksa kesediaan PostgreSQL (laraskan bukti kelayakan dan nama perkhidmatan). Aktifkan QUEUE_HEALTH_CHECK_ACTIVE=true pada worker apabila anda memerlukan endpoint persendirian /healthz dan /healthz/readiness; endpoint readiness memeriksa sambungan Redis/pangkalan data. Jangan dedahkan endpoint worker ini kepada umum hanya untuk tujuan pemantauan.

Pelaksanaan manual ialah ujian yang berbeza. Secara lalai OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, jadi aliran kerja yang dijalankan secara manual dalam editor boleh berjalan pada proses utama walaupun Queue Mode dikonfigurasi dengan betul. Tetapkan kepada true hanya jika anda memang mahu menghantar pelaksanaan manual kepada worker dan telah menguji perubahan tersebut dalam persekitaran staging. Worker Queue Mode juga berbeza daripada task runner luaran n8n, yang mempunyai keperluan konfigurasi berasingan bagi pelaksanaan Code node.

SEMPADAN KETERSEDIAAN TINGGI

Queue Mode menskalakan pelaksanaan, tetapi tidak secara automatik menjadikan proses utama highly available

Kongsi kunci penyulitan

Setiap worker mesti menggunakan N8N_ENCRYPTION_KEY yang sama seperti instans utama supaya worker boleh menyahsulit bukti kelayakan yang diperlukan oleh pelaksanaan aliran kerja.

Kekalkan versi yang sepadan

Proses utama, webhook dan worker patut menjalankan versi n8n yang sama. Versi bercampur boleh menghasilkan tingkah laku tidak serasi semasa perubahan rolling.

Webhook processor ialah lapisan penskalaan berasingan

Apabila volum webhook masuk menjadi kekangan, webhook processor khusus boleh berada di belakang load balancer sementara worker mengendalikan pelaksanaan. Jangan tambah lapisan ini melainkan volum permintaan yang diukur benar-benar membenarkannya.

Multi-main ialah ciri berbeza

Menjalankan beberapa proses utama untuk high availability tidak sama dengan Queue Mode biasa. n8n pada masa ini mendokumenkan multi-main sebagai ciri Enterprise dihos sendiri dengan keperluan tambahan untuk load balancer dan sesi.

FAQ

n8n Queue Mode: soalan lazim

Adakah n8n Queue Mode memerlukan Redis?

Ya. Redis ialah message broker yang menyelaras pelaksanaan tertunda antara instans utama dan worker.

Bolehkah Queue Mode menggunakan SQLite?

Tidak bagi seni bina Queue Mode teragih. Proses utama dan worker memerlukan akses kepada pangkalan data dikongsi, dan n8n mendokumenkan PostgreSQL sebagai pangkalan data bagi persediaan ini.

Berapa banyak worker yang patut saya jalankan?

Tiada bilangan universal. Mulakan dengan keserentakan yang diukur dan penggunaan worker, kemudian tambah kapasiti sambil memantau PostgreSQL, Redis, CPU, RAM dan kedalaman baris gilir.

Apakah keserentakan worker n8n?

Ia ialah bilangan tugas yang boleh diproses oleh seorang worker secara selari. Nilai lalai semasa ialah 10, dan n8n mengesyorkan keserentakan worker 5 atau lebih tinggi berbanding mencipta banyak worker dengan keserentakan rendah.

Patutkah saya mengaktifkan Queue Mode pada VPS kecil?

Hanya jika beban kerja membenarkannya. Pelaksanaan kecil yang berjalan selesa sebagai satu instans biasanya lebih mudah dikendalikan tanpa Redis dan worker berasingan.
