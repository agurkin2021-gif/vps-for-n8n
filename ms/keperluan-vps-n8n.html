KEPERLUAN PELAYAN

Keperluan VPS n8n

Untuk menentukan keperluan VPS n8n, mulakan dengan beban kerja anda, bukan angka minimum universal. VPS 1 vCPU / 1 GB boleh menjalankan automasi kecil yang sentiasa aktif, manakala 2 vCPU / 4 GB RAM ialah kelas permulaan yang praktikal untuk n8n bersama PostgreSQL dan HTTPS. Payload besar, pelaksanaan serentak dan pemprosesan data setempat memerlukan lebih banyak ruang; ukur penggunaan sebenar sebelum memilih.

KEPERLUAN PANTAS

Minimum, produksi praktikal dan beban kerja lebih berat

Ringan, sentiasa aktif

1 vCPU · 1–2 GB RAM

VPS 1 GB sebenar boleh menjalankan aliran kerja n8n yang terhad dan ringan jika penggunaan memori serta ruang cakera dipantau dengan teliti. Kelas 2 GB memberikan lebih banyak ruang untuk Docker, lonjakan kecil dan perkhidmatan lain. Tiada satu angka yang menjamin jumlah aliran kerja tertentu.

Produksi kecil yang praktikal

2 vCPU · 4 GB RAM

Kelas permulaan yang seimbang apabila n8n berkongsi VPS dengan PostgreSQL, Docker dan reverse proxy. Kekalkan ruang kapasiti untuk pelaksanaan bertindih dan penyelenggaraan.

Berat atau intensif data

4+ vCPU · 8 GB+ RAM

JSON besar, fail binari, Code node, kerja pelayar dan banyak pelaksanaan bertindih boleh memerlukan lebih banyak CPU serta memori.

Storan

SSD / NVMe dengan ruang untuk pertumbuhan

Kapasiti bergantung pada pertumbuhan PostgreSQL, pengekalan pelaksanaan, data binari, log, lapisan Docker dan strategi sandaran, bukan n8n sahaja.

KAPASITI MINIMUM VS PRAKTIKAL

Adakah n8n mempunyai satu saiz minimum rasmi VPS?

Tidak untuk setiap beban kerja. Contoh prasyarat rasmi n8n menerangkan pelaksanaan OEM sebagai ilustrasi dan menyatakan dengan jelas bahawa keperluan berbeza mengikut beban kerja. Dokumentasi itu bukan jaminan universal bahawa CPU, RAM atau peruntukan cakera tertentu akan menyokong automasi produksi.

n8n menyatakan bahawa instans melahu mungkin menggunakan memori yang agak sedikit, tetapi Code node, payload binari besar atau pelaksanaan serentak boleh meningkatkan keperluan memori dengan mendadak. Peruntukkan sumber secara berasingan untuk sistem operasi, Docker, PostgreSQL serta alat sandaran/pemantauan.

Sumber teknikal: prasyarat ilustratif n8n dan panduan memori rasmi. Empat baris di atas ialah set sumber sebenar yang boleh dibeli, bukan keperluan rasmi n8n yang tetap.

RAM & CPU

Perkara yang sebenar menggunakan sumber pelayan

Pelaksanaan serentak

Beberapa aliran kerja yang berjalan serentak boleh lebih penting daripada jumlah keseluruhan aliran kerja yang disimpan dalam n8n. Pantau puncak memori dan latensi pelaksanaan apabila tugas bertindih.

Saiz payload

Objek JSON besar, fail dan data binari meningkatkan tekanan memori. Beberapa pelaksanaan intensif data boleh memerlukan lebih banyak RAM berbanding banyak automasi API yang ringan.

Node intensif CPU

Code node, transformasi dan langkah pengkomputeran berat lain boleh menghasilkan tekanan CPU berterusan. Lebih banyak teras membantu apabila pelaksanaan sebenar bersaing untuk kuasa pengkomputeran.

Perkhidmatan sokongan

Sistem operasi, PostgreSQL, reverse proxy, pemantauan dan Docker turut memerlukan sumber. Ukur keseluruhan tindanan, bukan proses n8n sahaja.

UKUR SEBELUM MENAIK TARAF

Cara mengetahui sama ada n8n memerlukan lebih banyak RAM, CPU atau cakera

Jalankan aliran kerja terbesar yang dijangka serta lonjakan pertindihan yang realistik, kemudian semak pelayan dan log pelaksanaan n8n. Jumlah aliran kerja yang disimpan dalam editor bukan ukuran kapasiti yang berguna.

Memori / OOM

Semak docker stats --no-stream dan free -h. Jika memori habis, kurangkan dahulu JSON atau payload binari, proses import besar secara kelompok dan elakkan Code node yang menggunakan banyak memori. Ralat stack JavaScript tidak semestinya diselesaikan dengan menambah vCPU.

CPU / keserentakan

Ukur sama ada CPU kekal sibuk semasa transformasi atau tugas hanya menunggu API luaran. Dalam mod biasa, pertimbangkan had keserentakan produksi yang disokong sebelum beralih kepada worker. Menambah CPU tidak mempercepat API yang dibatasi oleh rate limit luaran.

Storan / pangkalan data

Semak df -h, saiz pangkalan data dan sejarah pelaksanaan yang disimpan. Pantau pertumbuhan cakera serta operasi pangkalan data yang perlahan. Tetapkan pengekalan secara sengaja sebelum membayar untuk cakera lebih besar; simpan salinan pemulihan di luar pelayan.

Gunakan panduan keserentakan n8n dan penerangan penanda aras rasmi. Angka aliran kerja serentak yang diiklankan tanpa mengetahui payload dan latensi API hanyalah anggaran.

PANGKALAN DATA & STORAN

SQLite, PostgreSQL dan data persisten

SQLite

SQLite boleh menyokong pelaksanaan dan ujian satu instans bersaiz kecil. Apabila penggunaan produksi dan keserentakan meningkat, pilihan pangkalan data menjadi kekangan operasi, bukan sekadar butiran pemasangan.

PostgreSQL

Untuk tindanan VPS berorientasikan produksi, PostgreSQL menyediakan asas pangkalan data yang lebih kukuh. Peruntukkan RAM, CPU dan cakera untuk pangkalan data itu sendiri serta pantau pertumbuhannya.

Data .n8n persisten

Jangan anggap PostgreSQL sebagai satu-satunya aset persisten. Kekalkan direktori data n8n dan lindungi kunci penyulitan yang diperlukan untuk memulihkan bukti kelayakan disulitkan.

Pertumbuhan cakera

Sejarah pelaksanaan, data binari, fail pangkalan data dan log boleh berkembang dari semasa ke semasa. Tetapan pengekalan dan sandaran di luar pelayan mempengaruhi kapasiti yang diperlukan secara langsung.

KAPASITI CAKERA

Anggarkan storan sejarah pelaksanaan n8n sebelum membuat pesanan

Mulakan dengan pelaksanaan tersimpan sehari × purata bait tersimpan bagi setiap pelaksanaan × hari pengekalan. Contohnya, 500 pelaksanaan tersimpan sehari × 200 KB setiap satu × 14 hari = 1.4 GB data pelaksanaan contoh sebelum overhead pangkalan data. Angka 200 KB itu hanyalah ilustrasi, bukan penanda aras n8n.

Peruntukkan juga ruang cakera untuk OS, lapisan imej Docker, indeks pangkalan data, fail binari, log aplikasi, naik taraf dan fail sementara. Sandaran di luar pelayan memerlukan kapasiti tersendiri. Cakera 10 GB boleh mencukupi untuk tindanan yang ringkas tetapi memberikan ruang yang lebih terhad untuk fail tersimpan berbanding cakera 40 atau 80 GB.

n8n mendokumenkan pemangkasan pelaksanaan lalai berdasarkan umur (336 jam / 14 hari) atau bilangan (10,000 pelaksanaan), dengan beberapa pengecualian. Semak tetapan sebenar anda dan sahkan data yang dikekalkan sebelum mengubahnya. SQLite boleh menggunakan semula ruang kosong tanpa mengecilkan failnya secara automatik.

Sumber: n8n — pengurusan data pelaksanaan dan pemangkasan. Keperluan cakera bergantung pada saiz payload tersimpan yang diperhatikan, bukan jumlah node sahaja.

KEPERLUAN SISTEM

Docker dan overhead produksi

Linux VPS

Gunakan distribusi Linux yang masih diselenggara dengan sumber mencukupi untuk sistem operasi dan kemas kini keselamatan selain tindanan aplikasi.

Docker & Compose

Pelaksanaan berasaskan kontena memudahkan pengulangan tetapi tidak menghapuskan overhead sumber. Kekalkan data n8n dan pangkalan data di luar kontena yang boleh dicipta semula.

HTTPS & reverse proxy

Webhook awam memerlukan nama hos stabil dan HTTPS yang dikonfigurasi dengan betul. Sertakan reverse proxy dan lapisan TLS dalam reka bentuk produksi.

Pemantauan & sandaran

Pantau pertumbuhan RAM, CPU, cakera dan pangkalan data. Simpan sandaran boleh pulih di luar VPS dan uji proses pemulihan, bukannya menganggap snapshot sahaja sudah mencukupi.

KESERENTAKAN

Apabila VPS lebih besar bukan lagi jawapan keseluruhan

Penskalaan menegak sesuai jika satu instans masih boleh mengendalikan beban kerja dengan baik. Apabila permintaan selari yang berterusan mula menyebabkan perebutan sumber, nilai Queue Mode dan worker. Queue Mode menambah Redis, PostgreSQL dan satu atau lebih proses worker; peruntukkan RAM dan CPU untuk setiap komponen, bukan n8n sahaja. n8n turut mendokumenkan had bagi storan data binari berasaskan sistem fail dalam Queue Mode, jadi sahkan reka bentuk storan yang serasi sebelum beralih.

TAHAP PERMULAAN & I/O STORAN

Cara menggunakan pilihan VPS 1 GB

1 GB RAM

Ini ialah kelas VPS yang benar-benar boleh digunakan, bukan sekadar produk percubaan. Ia sesuai untuk automasi kecil yang sentiasa aktif dan kebanyakan tugas API berurutan apabila penggunaan memori, cakera dan tugas serentak kekal dalam had yang diukur. Ruang tambahannya kecil jika PostgreSQL berkongsi pelayan, payload besar diproses atau beberapa pelaksanaan berat berjalan serentak.

2 GB RAM

Gunakan 2 GB sebagai asas yang lebih selamat untuk instans ringan apabila anda mahukan lebih banyak ruang bagi sistem operasi, Docker dan lonjakan kecil tanpa terus beralih ke tindanan bersaiz produksi.

SSD vs NVMe

SSD Standard mencukupi untuk automasi ringan. NVMe menjadi lebih berguna apabila PostgreSQL dan sejarah pelaksanaan menghasilkan operasi baca/tulis yang kerap atau apabila latensi cakera kelihatan dalam prestasi aliran kerja yang diukur.

Ukur sebelum menaik taraf

Gunakan CPU, memori, pertumbuhan cakera dan tempoh pelaksanaan semasa puncak pertindihan untuk menentukan sama ada kekangannya ialah pengkomputeran, memori atau storan, bukannya menganggap VPS lebih besar akan menyelesaikan setiap masalah prestasi.

FAQ

Keperluan VPS n8n: soalan lazim

Berapa banyak RAM yang diperlukan oleh n8n?

Tiada angka universal. Keperluan RAM berubah mengikut keserentakan, saiz payload, corak pelaksanaan dan perkhidmatan sokongan pada VPS. Pelayan 4 GB ialah kelas permulaan praktikal untuk produksi kecil, bukan jaminan minimum bagi setiap beban kerja.

Berapa banyak teras CPU yang patut saya gunakan?

Beban kerja ringan boleh bermula dengan peruntukan CPU kecil. Tambah teras apabila pemantauan menunjukkan tekanan CPU berterusan atau pelaksanaan menjadi lebih perlahan ketika tugas berjalan serentak; jangan tentukan saiz berdasarkan jumlah aliran kerja sahaja.

Adakah n8n memerlukan PostgreSQL?

Pelaksanaan kecil boleh menggunakan SQLite, tetapi PostgreSQL ialah pilihan berorientasikan produksi yang lebih kukuh apabila keperluan operasi dan keserentakan meningkat.

Bilakah Redis diperlukan?

Redis berkaitan dengan Queue Mode. Pelaksanaan satu instans biasa tidak memerlukan Redis hanya kerana ia dijalankan pada VPS.

Berapa banyak ruang cakera yang patut saya pilih?

Keperluan cakera bergantung pada pertumbuhan PostgreSQL, sejarah pelaksanaan yang dikekalkan, data binari, log, lapisan kontena dan sandaran. Pantau pertumbuhan dan sediakan ruang tambahan, bukannya bergantung pada satu angka universal.

Bolehkah saya menjalankan n8n secara berterusan pada VPS 1 GB?

Ya, jika beban kerja sebenar sesuai. VPS 1 GB ialah pelayan yang boleh digunakan dan boleh menyokong automasi kecil yang kebanyakannya berurutan, tetapi ruang memorinya terhad. Jangan anggap PostgreSQL pada pelayan yang sama, tugas intensif binari atau beberapa pelaksanaan besar serentak akan sesuai. Pantau penggunaan dan naik taraf berdasarkan tekanan sumber yang benar-benar diukur.

Adakah 2 GB atau 4 GB RAM lebih sesuai untuk produksi n8n pada VPS?

2 GB memberikan lebih banyak ruang berbanding konfigurasi 1 GB yang ringkas, manakala 4 GB ialah kelas permulaan praktikal untuk menilai n8n bersama PostgreSQL dan HTTPS. Tiada jaminan minimum produksi yang universal: kerumitan beban kerja, pertindihan puncak, konfigurasi kontena dan data tersimpan menentukan keperluan sebenar.

Adakah aliran kerja AI n8n memerlukan GPU?

Tidak jika n8n hanya memanggil API model luaran: penyedia model mengendalikan inferens, manakala VPS mengendalikan orkestrasi, payload dan keserentakan. Menjalankan model inferens secara setempat ialah keputusan perkakasan berasingan yang mungkin memerlukan lebih banyak RAM dan GPU yang sesuai.

Apakah yang menyebabkan ralat kehabisan memori n8n?

Payload JSON atau binari besar, Code node yang menggunakan banyak memori dan pelaksanaan bertindih ialah punca lazim. Semak log runtime dan penggunaan memori puncak, kemudian kurangkan data yang disimpan dalam satu pelaksanaan atau peruntukkan lebih banyak RAM berdasarkan masalah yang telah diukur.
