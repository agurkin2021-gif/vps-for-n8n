SANDARAN & PEMULIHAN

Sandaran dan Pemulihan n8n

Untuk membuat sandaran dan memulihkan n8n yang dihos sendiri, lindungi pangkalan data SQLite atau dump PostgreSQL yang konsisten, folder .n8n persisten dan kunci penyulitan asal, konfigurasi pelaksanaan serta setiap kebergantungan data binari atau fail luaran yang dipasang. Simpan salinan yang disulitkan di luar VPS dan uji pemulihan pada instans berasingan. Gunakan eksport aliran kerja dan bukti kelayakan melalui CLI untuk pemulihan terpilih; eksport JSON sahaja bukan sandaran pelayan yang lengkap.

Pilih VPS untuk n8n

SENARAI SEMAK PANTAS

Perkara yang perlu dilindungi oleh sandaran n8n

Pangkalan data

Sandarkan pangkalan data PostgreSQL atau fail pangkalan data SQLite yang digunakan oleh instans. Pangkalan data mengandungi keadaan teras n8n seperti aliran kerja, bukti kelayakan dan data pelaksanaan.

Kunci penyulitan

Simpan kunci penyulitan n8n yang asal secara berasingan dan selamat. Bukti kelayakan disulitkan yang dipulihkan memerlukan kunci yang sama.

fail persisten

Sertakan direktori data n8n persisten serta semua fail yang dipasang, storan data binari dan aset aliran kerja yang diperlukan oleh pelaksanaan anda.

Konfigurasi pelaksanaan

Simpan fail Compose/konfigurasi dan tetapan bukan rahsia yang diperlukan untuk membina semula tindanan. Lindungi rahsia dengan kawalan akses yang sesuai.

DUA TAHAP SANDARAN

Eksport logik berbanding pemulihan bencana penuh

Eksport aliran kerja & bukti kelayakan

Eksport melalui n8n CLI berguna untuk migrasi, salinan aliran kerja berversi dan pemulihan terpilih. Bukti kelayakan boleh dieksport dalam bentuk disulitkan dan diimport kemudian menggunakan kunci penyulitan yang sepadan. Untuk memulihkan satu aliran kerja sahaja, gunakan menu tiga titik dalam editor aliran kerja untuk memuat turun JSON, kemudian Import daripada Fail ke aliran kerja semakan baharu atau instans terpencil. Semak bukti kelayakan, ID aliran kerja dan parameter node sebelum menggantikan aliran kerja aktif: memulihkan JSON aliran kerja tidak memulihkan keseluruhan pelayan.

Eksport entiti

CLI boleh mengeksport entiti pangkalan data untuk memindahkan data antara jenis pangkalan data yang disokong. Jadual sejarah pelaksanaan adalah pilihan kerana saiznya boleh menjadi sangat besar.

Pemulihan instans penuh

Untuk senario pelayan gagal, lindungi pangkalan data sebenar, kunci penyulitan, data persisten dan kebergantungan pelaksanaan. Jangan anggap eksport JSON aliran kerja boleh membina semula keseluruhan instans.

Snapshot penyedia

Snapshot VPS berguna sebagai lapisan pemulihan tambahan, tetapi tidak sepatutnya menjadi satu-satunya salinan atau menggantikan sandaran aplikasi/pangkalan data yang telah disahkan secara bebas.

PANGKALAN DATA

Sandarkan pangkalan data secara konsisten

PostgreSQL

Gunakan kaedah sandaran PostgreSQL yang konsisten dan simpan sandaran yang terhasil di luar VPS. Salinan pangkalan data pada cakera yang sama tidak memberikan pemulihan bencana jika cakera itu gagal.

SQLite

Jika pelaksanaan menggunakan SQLite, lindungi fail pangkalan data dalam direktori data n8n persisten. Elakkan menyalin pangkalan data ketika ia sedang diubah secara aktif tanpa kaedah yang menjamin konsistensi.

Sejarah pelaksanaan

Tentukan sama ada data sejarah pelaksanaan termasuk dalam objektif pemulihan anda. Data ini boleh membesarkan sandaran dengan ketara, jadi keperluan pengekalan dan pematuhan perlu menentukan pilihan.

Versi pangkalan data

Catat enjin dan versi pangkalan data yang digunakan oleh pelaksanaan asal supaya persekitaran pemulihan boleh disediakan secara serasi.

PostgreSQL pada VPS Docker Compose. Jika perkhidmatan PostgreSQL bernama postgres dan nama pangkalan data serta penggunanya kedua-duanya n8n, arahan berikut menghasilkan dump PostgreSQL format tersuai yang konsisten pada hos. Semak fail Compose sebenar anda sebelum menjalankannya dan laraskan bukti kelayakan pangkalan data serta nama perkhidmatan. pg_dump boleh menghasilkan snapshot yang konsisten secara logik ketika PostgreSQL sedang berjalan; ia tidak menyandarkan folder pengguna .n8n yang berasingan atau data binari luaran.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Semakan senarai arkib boleh mengesan masalah format yang jelas, tetapi tidak membuktikan bahawa data boleh dipulihkan. Simpan salinan yang disulitkan di luar pelayan dan jalankan latihan pemulihan. Gunakan dokumentasi rasmi PostgreSQL pg_dump untuk pilihan khusus pangkalan data.

SQLite pada Docker. Bagi pelaksanaan SQLite lalai, database.sqlite dan konfigurasi kunci penyulitan yang dijana berada dalam folder .n8n persisten, yang biasanya dipasang pada /home/node/.n8n. Jangan anggap salinan langsung SQLite semasa ia aktif sebagai konsisten. Hentikan n8n dan semua proses lain yang menulis ke pangkalan data sebelum menyalin folder, atau gunakan mekanisme sandaran dalam talian yang disokong oleh SQLite apabila gangguan perkhidmatan tidak boleh dilakukan:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

Arahan ini ialah contoh untuk perkhidmatan dan laluan yang ditunjukkan, bukan susun atur volum yang universal. Folder yang disalin pada mulanya masih berada pada VPS yang sama; pindahkan dan lindunginya di luar pelayan. Jika terdapat worker Queue Mode atau proses penulis lain, hentikan proses tersebut juga dan ikut reka bentuk pelaksanaan sebenar anda. Panduan sandaran penuh n8n semasa menerangkan keperluan konsistensi SQLite.

Memulihkan folder SQLite lalai ke sasaran yang bersih: hentikan dahulu perkhidmatan n8n dan semua proses yang menulis ke pangkalan data. Selepas kontena perkhidmatan n8n yang serasi dan volum sasaran tersedia, salin semula kandungan .n8n daripada sandaran ke direktori persisten yang sama. Langkah ini menimpa fail sasaran, jadi jangan jalankannya pada instans yang mengandungi data yang perlu dikekalkan:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker boleh menyalin fail ke kontena yang dihentikan, tetapi pemilikan pada sasaran mungkin berbeza daripada asal. Pastikan konfigurasi yang dipulihkan dan fail pangkalan data boleh dibaca serta ditulis oleh proses n8n sebelum memulakannya. Jika konfigurasi Compose sebenar anda menggunakan laluan atau bind mount yang berbeza, laraskan proses penyalinan dengan sewajarnya. Rujuk dokumentasi Docker Compose untuk arahan copy. Memulihkan folder n8n sahaja tidak mencukupi bagi pelaksanaan yang menggunakan pangkalan data PostgreSQL berasingan.

RAHSIA KRITIKAL

Kunci penyulitan ialah sebahagian daripada pemulihan

n8n menyulitkan bukti kelayakan yang disimpan menggunakan kunci penyulitan instans. Eksport pangkalan data atau bukti kelayakan disulitkan tanpa kunci yang sepadan boleh menyebabkan aliran kerja yang dipulihkan tidak dapat menggunakan bukti kelayakan tersimpan.

Jika anda menetapkan N8N_ENCRYPTION_KEY, pulihkan rahsia yang sama tepat. Jika tidak, kunci yang dijana disimpan dalam fail .n8n/config persisten; lindungi konfigurasi itu ketika membuat sandaran atau membina semula pelayan. Simpan kunci pemulihan dengan selamat di luar VPS. Dalam Queue Mode, semua proses utama dan worker mesti menggunakan kunci yang sama.

LakukanSimpan salinan terlindung bagi kunci tepat yang digunakan dalam produksi.
LakukanSahkan bahawa persekitaran pemulihan menggunakan kunci tersebut sebelum menguji bukti kelayakan.
JanganJangan bergantung pada kunci baharu yang dijana selepas pelayan dibina semula.
JanganJangan commit kunci ke repositori awam atau menyimpannya bersama sandaran yang tidak dilindungi.

FAIL & DATA BINARI

Sandaran pangkalan data mungkin tidak merangkumi setiap kebergantungan aliran kerja

Data .n8n persisten

Cari dan simpan folder pengguna .n8n sebenar, bukan hanya imej kontena. Dalam pelaksanaan Docker lazim, folder ini dipasang pada /home/node/.n8n; di luar Docker, lalai ialah ~/.n8n. Jika N8N_USER_FOLDER dikonfigurasi, n8n mencipta .n8n di dalam direktori induk yang ditetapkan. Sertakan kunci konfigurasinya serta sebarang data pelaksanaan SQLite, binari atau sistem fail setempat yang digunakan oleh pemasangan anda.

Fail aliran kerja yang dipasang

Jika aliran kerja membaca atau menulis direktori yang dipasang pada hos, sandarkan direktori tersebut secara berasingan. Memulihkan n8n tanpanya boleh menyebabkan aliran kerja yang sebaliknya sah gagal berfungsi.

Data binari

Kenal pasti mod storan dan pulihkan setiap kebergantungan luaran. Data binari atau data pelaksanaan berasaskan sistem fail mungkin berada dalam .n8n atau direktori tersuai; S3/Azure Blob atau storan luaran lain yang dikonfigurasi memerlukan salinan boleh pulih dan tetapan aksesnya sendiri. Dump pangkalan data sahaja tidak boleh menggantikan fail tersebut.

Node komuniti

Catat pakej komuniti dan versinya, serta sandarkan sebarang direktori node tersuai tambahan yang dikonfigurasi melalui N8N_CUSTOM_EXTENSIONS. Direktori itu boleh berada di luar .n8n; memulihkan pangkalan data dan folder pengguna sahaja masih boleh menyebabkan aliran kerja yang menggunakan node tersuai tidak berfungsi.

STRATEGI LUAR PELAYAN

Sandaran pada VPS yang sama hanyalah salinan setempat

Salinan setempatBerguna untuk rollback pantas, tetapi terdedah kepada kehilangan pelayan, kegagalan cakera dan kesilapan yang merosakkan data.
Salinan di luar pelayanSimpan sekurang-kurangnya satu sandaran dalam storan yang bebas daripada VPS produksi.
Salinan berversiKekalkan beberapa titik pemulihan supaya kerosakan data atau perubahan yang salah tidak menimpa satu-satunya sandaran yang boleh digunakan.
Kawalan aksesSandaran boleh mengandungi bukti kelayakan, logik aliran kerja dan data perniagaan sensitif. Sulitkan sandaran dan hadkan akses dengan sewajarnya.
PemantauanHantar amaran apabila sandaran berjadual gagal atau berhenti menghasilkan titik pemulihan baharu.

Jadikan jadual sandaran boleh diukur. Catat cap masa setiap sandaran yang berjaya, masa pemindahan selesai, saiz fail, versi pangkalan data sumber, lokasi kunci penyulitan untuk pemulihan dan ujian pemulihan berjaya yang paling terkini. Hantar amaran jika fail hilang, sandaran gagal atau fail kosong secara luar biasa. Sulitkan arkib sandaran sebelum menghantarnya keluar dari VPS dan hadkan akses kepada rahsia pemulihan. Beberapa titik pemulihan bertarikh melindungi anda jika kerosakan data hanya ditemui selepas salinan terbaharu telah menimpa salinan sihat sebelumnya.

Contohnya, jika anda boleh menerima kehilangan perubahan maksimum enam jam, jadual sandaran setiap enam jam yang berjaya hanyalah titik permulaan, bukan jaminan. Tugas yang gagal dan kelewatan replikasi ke luar pelayan boleh meningkatkan kehilangan sebenar. Tetapkan tempoh pengekalan dan kekerapan ujian pemulihan mengikut RPO/RTO serta keperluan data anda, bukan berdasarkan dasar universal 7 hari atau 30 hari.

URUTAN PEMULIHAN

Pulihkan mengikut urutan yang terkawal

1 · SediakanSediakan pelayan, pangkalan data dan persekitaran kontena/runtime yang serasi.
2 · Pulihkan rahsiaKonfigurasikan kunci penyulitan n8n asal dan rahsia pelaksanaan yang diperlukan dengan selamat.
3 · Pulihkan pangkalan dataPulihkan PostgreSQL atau SQLite dan sahkan bahawa n8n boleh bersambung kepada data yang sepatutnya.
4 · Pulihkan failPulihkan direktori persisten, data binari dan aset aliran kerja yang dipasang.
5 · Mulakan n8nMulakan aplikasi dengan nama hos, pangkalan data dan konfigurasi persekitaran yang sepatutnya.
6 · SahkanSahkan bahawa pengguna, aliran kerja dan bukti kelayakan dimuatkan, kemudian jalankan aliran kerja yang mewakili penggunaan sebenar serta laluan webhook.

Contoh pemulihan bencana PostgreSQL: pada sasaran pemulihan yang berasingan dan bersih yang sudah mempunyai peranan pangkalan data yang betul serta pangkalan data n8n yang kosong, mulakan PostgreSQL sahaja. Tunggu sehingga PostgreSQL sedia menerima sambungan sebelum mengimport: arahan docker compose up -d boleh selesai ketika PostgreSQL masih dalam proses permulaan, jadi arahan pg_restore selepasnya boleh gagal. Contoh ini menggunakan --wait pada pemasangan Compose moden dan menyemak pg_isready secara berasingan. Konfigurasikan healthcheck PostgreSQL yang sesuai untuk penantian yang boleh dipercayai, atau sahkan kesediaan secara jelas sebelum meneruskan. Jangan halakan arahan ini kepada pangkalan data produksi yang sudah mengandungi data dan jangan mulakan n8n sebelum pangkalan data serta kunci/data .n8n yang sepadan dipulihkan.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Sasaran mesti mempunyai versi PostgreSQL yang serasi, keistimewaan peranan, extension yang diperlukan dan konfigurasi n8n asal. Pulihkan .n8n ke volum persisten atau bind mount yang betul menggunakan mekanisme sandaran anda sambil mengekalkan pemilikan dan kebenaran. Pulihkan fail binari luaran, extension tersuai, konfigurasi Compose dan rahsia, kemudian mulakan n8n pada versi yang serasi dan semak lognya. Memulihkan pangkalan data sahaja tidak memulihkan kunci: pelaksanaan PostgreSQL menyimpan kunci dalam .n8n/config melainkan anda menetapkan N8N_ENCRYPTION_KEY secara jelas. Rujuk dokumentasi pg_restore dan urutan pemulihan instans penuh n8n.

UJIAN PEMULIHAN

Sandaran belum terbukti sehingga pemulihan berjaya

Uji dalam persekitaran yang bersih

Latihan sebenar perlu membuktikan bahawa sandaran boleh membina semula instans tanpa bergantung pada fail yang tidak dinyatakan tetapi masih tertinggal pada pelayan produksi.

Semak bukti kelayakan

Membuka aliran kerja sahaja tidak mencukupi. Sahkan bahawa bukti kelayakan disulitkan yang dipulihkan benar-benar boleh dinyahsulit dan digunakan untuk pengesahan.

Jalankan aliran kerja yang mewakili penggunaan sebenar

Uji aliran kerja yang bergantung pada webhook, API luaran, fail yang dipasang dan node komuniti, bukan sekadar mengesahkan automasi ringkas.

Ukur masa pemulihan

Catat tempoh yang diperlukan untuk pemulihan dan langkah manual yang masih perlu dilakukan. Ini menukar sandaran yang hanya diandaikan berfungsi menjadi prosedur pemulihan operasi yang boleh diuji.

Latihan pemulihan yang disahkan: SQLite dan PostgreSQL

Persekitaran ujian: n8n 2.42.5 dalam kontena Docker terpencil pada runner GitHub Actions sementara, menggunakan aliran kerja sintetik dua node. Ujian ini dijalankan pada 8 Oktober 2026, bukan pada pelayan n8n pelanggan atau pelayan produksi.

SQLite: LULUSAliran kerja ujian diimport dan dieksport, semua proses penulis dihentikan, folder .n8n persisten berasaskan SQLite serta kunci penyulitan yang dijana diarkibkan, kemudian dipulihkan ke volum bersih. Selepas n8n dimulakan, aliran kerja yang dipulihkan dieksport semula dan dijalankan.
PostgreSQL: LULUSAliran kerja ujian yang sama diimport, dump pg_dump format tersuai dibuat dan diperiksa, kemudian dipulihkan dengan pg_restore ke pangkalan data PostgreSQL baharu yang kosong. Folder .n8n yang berasingan turut dipulihkan sebelum aliran kerja dieksport semula dan dijalankan.
Perkara yang dibuktikan oleh status LULUSLaluan sandaran yang diuji mengekalkan aliran kerja ini, dua nodenya dan sambungan antara node, serta membolehkan aliran kerja dijalankan selepas pemulihan. Ini ialah ujian fungsi asas yang boleh dihasilkan semula, bukan penanda aras beban kerja.
Perkara yang tidak diujiPenyahsulitan dan pengesahan bukti kelayakan sebenar, webhook produksi, worker Queue Mode dan Redis, storan binari S3/Azure, node tersuai, akses pengguna/projek atau pemulihan instans produksi yang sedang digunakan. Jalankan latihan berasingan bagi setiap kebergantungan yang benar-benar anda gunakan.

Cara menghasilkan semula ujian: gunakan pemasangan n8n sementara, cipta aliran kerja dua node yang tidak berbahaya, buat sandaran pangkalan data yang berkaitan bersama folder persisten, pulihkan ke volum atau pangkalan data yang bersih, kemudian sahkan node, sambungan dan pelaksanaan sebenar aliran kerja yang dipulihkan. Pada sistem produksi, semak juga bukti kelayakan disulitkan, webhook dan fail luaran sebelum menganggap pemulihan bencana telah terbukti.

Senarai semak penerimaan latihan pemulihan: gunakan domain/persekitaran terpencil; semak bahawa pengguna dan aliran kerja tersedia, sekurang-kurangnya satu bukti kelayakan disulitkan sedia ada boleh mengesahkan identiti tanpa dimasukkan semula, webhook produksi memanggil aliran kerja dipulihkan yang betul, fail yang dipasang dan lampiran binari masih boleh dibaca, serta integrasi dengan node komuniti yang diperlukan dapat dimuatkan. Sahkan umur sandaran, masa henti yang diukur dan kebolehcapaian salinan di luar pelayan. Jika mana-mana semakan penting gagal, tandakan titik pemulihan itu sebagai belum disahkan dan jangan laporkan sandaran sebagai lengkap.

HAD SANDARAN CLI

Ketahui dengan tepat perkara yang tidak dipulihkan oleh eksport aliran kerja dan bukti kelayakan

Eksport CLI bukan sandaran instans penuh

eksport sandaran aliran kerja dan bukti kelayakan tidak mencakup pengguna dan peran, sejarah pelaksanaan dan log, variabel, atau tetapan instans seperti kunci penyulitan.

Pemulihan instans baharu memerlukan pemilik

Pada contoh yang bersih, selesaikan persediaan pemilik sebelum mengimpor bukti kelayakan. Pemulihan multi-pengguna atau proyek mungkin juga memerlukan penetapan pengguna atau proyek yang benar.

ID yang diimport boleh menimpa item sedia ada

aliran kerja dan eksport bukti kelayakan mempertahankan ID aslinya. Mengimpor ke instance yang sudah berisi ID yang sama boleh menggantikan item yang sudah ada.

Terbitkan aliran kerja yang diimport secara terkawal

CLI import biasanya membuat aliran kerja tidak aktif. Pada n8n 2.x, semak status penerbitan setiap aliran kerja yang diimpor dan publikasikan hanya aliran kerja yang ingin anda jalankan; pelayan yang dihos sendiri CLI juga mendukung n8n terbitkan: aliran kerja --id=YOUR_WORKFLOW_ID. Ketika n8n berjalan, perubahan status publikasi/batalkan pelayan CLI hanya berlaku selepas memulai ulang n8n. Mulai ulang sebelum memverifikasi pemicu terjadwal dan webhook produksi atau mengalihkan traffic.

Contoh eksport pukal untuk Docker Compose: jika perkhidmatan n8n anda diberi nama n8n, anda boleh menjalankan sandaran resmi CLI di bawah. Jalur keluaran sengaja berada di dalam persisten yang dipasang .n8n direktori, kerana direktori sembarang di dalam kontena mungkin hilang saat dibuat ulang. sahkan bahwa direktori boleh ditulis oleh pengguna kontena n8n. Pertahankan aliran kerja dan bukti kelayakan JSON tetap masuk direktori berasingan—n8n mendokumentasikan masalah import ketika kedua jenis berbagi direktori.

n8n 2.x: draf berbanding sandaran versi diterbitkan: normal --backup eksport aliran kerja menangkap draf semasa; ini mungkin berbeda dari versi yang diterbitkan dalam produksi. Untuk mempertahankan versi aktual aliran kerja tertentu yang dipublikasikan, eksport secara berasingan menggunakan docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, selepas memastikan bahwa folder keluaran ada dan boleh ditulis. CLI juga boleh mengekspor versi historis menggunakan --version=VERSION_ID. Simpan salinan ini di luar pelayan bersama dengan sandaran penuh; jangan menganggap draf JSON mencatat status diterbitkan dalam produksi.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Yang disalin ~/n8n-recovery/cli direktori masih di VPS sampai anda memindahkannya ke lokasi sandaran yang aman dan independen. eksport bukti kelayakan dienkripsi secara lalai dan memerlukan kunci penyulitan yang cocok saat mengimpor. Hindari menggunakan --decrypted kecuali untuk migrasi yang dikontrol ketat: ia menulis secret dalam teks biasa. Jangan pernah commit eksport yang berisi logika atau bukti kelayakan aliran kerja sensitif ke repositori GitHub awam. Beberapa templat sandaran bukti kelayakan GitHub pihak ketiga dengan sengaja mengekspor secret yang didekripsi; repositori pribadi adalah pembatasan akses, bukan penyulitan. semak tetapan eksport aktual dan izin storan setiap templat, penyulitan secret sebelum transfer ke luar pelayan, dan putar ganti bukti kelayakan apa pun yang terekspos melalui unggahan teks biasa yang tidak diinginkan.

Contoh import pukal: pada target yang bersih, selesaikan tetapan pemilik, berikan kunci penyulitan asli dan pastikan fail sandaran yang disimpan tersedia pada VPS pemulihan tersebut. Berikut ini membuat folder tujuan dan menyalinnya workflows/ dan credentials/ subfolder dari hos ke dalam kontena n8n; sesuaikan jalur jika tata letak volume Docker anda berbeda:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

semak kepemilikan dan akses fail untuk pengguna kontena n8n. Jangan mengimpor instans produksi yang terisi tanpa rollback disahkan: aliran kerja dan ID bukti kelayakan boleh menimpa entri yang sudah ada. Kemudian jalankan:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

ID yang diimpor boleh menggantikan aliran kerja atau bukti kelayakan yang ada; gunakan instance ujian terisolasi untuk ujian kering dan semak bukti kelayakan serta status aktivasi/penerbitan setelahnya. Di n8n 2.x, memulihkan draf JSON tidak dengan sendirinya membuktikan aliran kerja telah dipublikasikan dan boleh menjalankan pemicu terjadwal. Keselamatan import: pada instance n8n non-multi-main, pemicu cron yang sebelumnya aktif boleh terus berjalan selepas import CLI hingga instance dimulai ulang. Hentikan atau isolasi pemicu produksi dan mulai ulang n8n sebelum mengaktifkan tugas yang dipulihkan; verifikasi tidak ada pelaksanaan duplikat. CLI eksport boleh tidak berisi pengguna asli, log pelaksanaan, variabel instan, atau kunci penyulitan. --backup set --all --pretty --separate, bukan 'instans penuh'. Sumber: panduan sandaran/pemulihan n8n resmi terkini dan rujukan arahan n8n CLI.

Pemulihan pukal daripada templat GitHub atau Google Drive: ini merupakan alternatif untuk aliran kerja JSON saja, bukan untuk pangkalan data instans, pengguna, nilai bukti kelayakan disulitkan, atau kunci penyulitan. Sebelum menjalankan templat berbasis API, verifikasi n8n API dan izin penyimpanannya, versi sandaran yang dipilih dan instans target, apakah templat tersebut memperbarui ID yang cocok dan membuat ulang aliran kerja yang dihapus, dan apa fungsinya dengan penerbitan aliran kerja. Tidak semua template membuat ulang ID yang hilang dari target; uji senario tersebut secara berasingan sebelum bergantung pada pemulihan automatik.

FAQ

Sandaran dan pemulihan n8n: soalan lazim

Adakah mengeksport aliran kerja sahaja mencukupi untuk menyandarkan n8n?

Tidak. eksport aliran kerja adalah salinan logis yang berguna, namun pemulihan lengkap juga memerlukan bukti kelayakan, kunci penyulitan yang cocok, status pangkalan data, fail persisten, dan storan data binari.

Adakah saya memerlukan kunci penyulitan n8n jika saya mempunyai pangkalan data?

Ya, jika anda memerlukan bukti kelayakan disulitkan yang disimpan dalam pangkalan data tersebut agar tetap boleh digunakan. Simpan kunci asli dengan aman.

Patutkah saya menyandarkan PostgreSQL atau mengeksport aliran kerja dan bukti kelayakan?

Untuk pemulihan bencana, lindungi pangkalan data dan kunci penyulitan. eksport logis lebih berharga sebagai lapisan migrasi tambahan dan pemulihan selektif, bukan sebagai pengganti setiap bagian dari proses tersebut.

Bolehkah snapshot VPS menjadi satu-satunya sandaran saya?

Lebih baik diperlakukan sebagai satu lapisan pemulihan. Simpan sandaran di luar pelayan yang independen sehingga kegagalan penyedia, akun, pelayan, atau snapshot tidak menghapus setiap titik pemulihan sekaligus.

Bagaimanakah saya tahu sandaran saya berfungsi?

Pulihkan ke lingkungan ujian yang bersih, verifikasi dekripsi bukti kelayakan, dan jalankan aliran kerja yang mewakili penggunaan sebenar. tugas sandaran yang berhasil saja tidak membuktikan kebolehpulihan.

Adakah sandaran aliran kerja GitHub atau Google Drive merangkumi rahsia bukti kelayakan yang disimpan?

sandaran JSON khusus aliran kerja tidak menyertakan nilai secret yang dikelola oleh storan bukti kelayakan n8n atau kunci penyulitan instans. Namun, JSON yang diekspor boleh mengekspos nama bukti kelayakan dan ID serta secret yang diketik langsung ke dalam parameter node, seperti header autentikasi. semak dan lindungi JSON yang diekspor sebelum mengunggah atau membagikannya. Untuk pemulihan penuh, buat sandaran pangkalan data dan kunci asli, atau gunakan eksport bukti kelayakan disulitkan yang didukung CLI dengan pemulihan yang diuji. Templat GitHub atau Google Drive khusus aliran kerja bukanlah pemulihan bencana sepenuhnya.

OBJEKTIF PEMULIHAN

Tetapkan RPO dan RTO sebelum insiden

RPO adalah kehilangan maksimum yang boleh ditoleransi dari perubahan terkini. Ukur dari titik pemulihan terbaharu yang boleh digunakan dan disimpan secara independen; tugas enam jam yang dijadwalkan tidak menghasilkan RPO enam jam jika eksport atau transfer gagal. RTO adalah tempoh henti maksimum yang boleh ditoleransi. Ukur hal ini dalam latihan pemulihan yang bersih, termasuk mengambil secret, memulihkan fail eksternal, memeriksa ulang bukti kelayakan, dan menerbitkan aliran kerja yang dipulihkan—bukan hanya memulai sebuah kontena.

KUNCI PEMULIHAN

Cari kunci penyulitan asal sebelum membina semula

Jika produksi ditetapkan N8N_ENCRYPTION_KEY, jaga environment secret tersebut. Jika tidak, pertahankan kunci yang dihasilkan dalam .n8n/config asli. semak sumber mana sebenar digunakan oleh instance yang dipulihkan sebelum mengimpor bukti kelayakan disulitkan; kunci baru yang dihasilkan tidak boleh menyahsulit bukti kelayakan dari pangkalan data lama.
