SANDARAN & PEMULIHAN

Sandaran dan Pemulihan n8n

Untuk membuat sandaran dan memulihkan n8n yang dihos sendiri, lindungi pangkalan data SQLite atau dump PostgreSQL yang konsisten, folder .n8n persisten dan kunci penyulitan asal, konfigurasi pelaksanaan serta setiap kebergantungan data binari atau fail luaran yang dipasang. Simpan salinan yang disulitkan di luar VPS dan uji pemulihan pada instans berasingan. Gunakan eksport aliran kerja dan bukti kelayakan melalui CLI untuk pemulihan terpilih; eksport JSON sahaja bukan sandaran pelayan yang lengkap.

SENARAI SEMAK PANTAS

Perkara yang perlu dilindungi oleh sandaran n8n

Pangkalan data

Sandarkan pangkalan data PostgreSQL atau fail pangkalan data SQLite yang digunakan oleh instans. Pangkalan data mengandungi keadaan teras n8n seperti aliran kerja, bukti kelayakan dan data pelaksanaan.

Kunci penyulitan

Simpan kunci penyulitan n8n yang asal secara berasingan dan selamat. Bukti kelayakan disulitkan yang dipulihkan memerlukan kunci yang sama.

fail persisten

Sertakan direktori data n8n persisten serta semua fail yang dipasang, storan data binari dan aset aliran kerja yang diperlukan oleh pelaksanaan anda.

Konfigurasi pelaksanaan

Simpan fail Compose/konfigurasi dan tetapan bukan rahsia yang diperlukan untuk membina semula tindanan. Lindungi rahsia dengan kawalan akses yang sesuai.

DUA TAHAP SANDARAN

Eksport logik berbanding pemulihan bencana penuh

Eksport aliran kerja & bukti kelayakan

Eksport melalui n8n CLI berguna untuk migrasi, salinan aliran kerja berversi dan pemulihan terpilih. Bukti kelayakan boleh dieksport dalam bentuk disulitkan dan diimport kemudian menggunakan kunci penyulitan yang sepadan. Untuk memulihkan satu aliran kerja sahaja, gunakan menu tiga titik dalam editor aliran kerja untuk memuat turun JSON, kemudian Import daripada Fail ke aliran kerja semakan baharu atau instans terpencil. Semak bukti kelayakan, ID aliran kerja dan parameter node sebelum menggantikan aliran kerja aktif: memulihkan JSON aliran kerja tidak memulihkan keseluruhan pelayan.

Eksport entiti

CLI boleh mengeksport entiti pangkalan data untuk memindahkan data antara jenis pangkalan data yang disokong. Jadual sejarah pelaksanaan adalah pilihan kerana saiznya boleh menjadi sangat besar.

Pemulihan instans penuh

Untuk senario pelayan gagal, lindungi pangkalan data sebenar, kunci penyulitan, data persisten dan kebergantungan pelaksanaan. Jangan anggap eksport JSON aliran kerja boleh membina semula keseluruhan instans.

Snapshot penyedia

Snapshot VPS berguna sebagai lapisan pemulihan tambahan, tetapi tidak sepatutnya menjadi satu-satunya salinan atau menggantikan sandaran aplikasi/pangkalan data yang telah disahkan secara bebas.

pangkalan data

Sandarkan pangkalan data secara konsisten

PostgreSQL

Gunakan kaedah sandaran PostgreSQL yang konsisten dan simpan sandaran yang terhasil di luar VPS. Salinan pangkalan data pada cakera yang sama tidak memberikan pemulihan bencana jika cakera tersebut gagal.

SQLite

Jika pelaksanaan menggunakan SQLite, lindungi fail pangkalan data dalam direktori data n8n persisten. Elakkan menyalin pangkalan data dalam keadaan tidak konsisten ketika ia sedang diubah secara aktif.

Sejarah pelaksanaan

Tentukan sama ada data sejarah pelaksanaan merupakan sebahagian daripada objektif pemulihan anda. Data ini boleh membesarkan saiz sandaran dengan ketara, jadi keperluan pengekalan dan pematuhan perlu menentukan pilihan.

Versi pangkalan data

Catat enjin dan versi pangkalan data yang digunakan oleh pelaksanaan asal supaya persekitaran pemulihan boleh disediakan secara serasi.

PostgreSQL pada VPS Docker Compose. Jika perkhidmatan PostgreSQL diberi nama postgres dan pangkalan data/penggunanya keduanya n8n, arahan berikut membuat dump format khusus PostgreSQL yang konsisten pada hos. semak fail Compose anda sebenar sebelum menjalankannya, dan sesuaikan bukti kelayakan pangkalan data dan nama perkhidmatan. pg_dump boleh menghasilkan snapshot yang konsisten secara logis saat PostgreSQL sedang berjalan; memang demikian tidak sandaran yang berasingan .n8n folder pengguna atau data binari eksternal.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Semakan senarai arkib boleh mengesan masalah format yang jelas tetapi tidak membuktikan bahawa data boleh dipulihkan. Simpan salinan disulitkan di luar pelayan dan jalankan latihan pemulihan. Gunakan dokumentasi rasmi PostgreSQL pg_dump untuk pilihan khusus pangkalan data.

SQLite pada Docker. Untuk pelaksanaan SQLite lalai, pangkalan data.sqlite dan konfigurasi kunci penyulitan yang dihasilkan berada di dalam persisten .n8n folder (biasanya dipasang di /home/node/.n8n). Jangan pernah memperlakukan salinan terus SQLite sebagai sesuatu yang konsisten. Hentikan n8n dan proses penulis pangkalan data lainnya sebelum menyalin folder, atau gunakan mekanisme sandaran online yang didukung SQLite apabila gangguan tidak boleh dilakukan:

# Only for SQLite and the lalai /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite pangkalan data
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-sandaran
docker compose start n8n

Ini adalah arahan ilustratif untuk perkhidmatan dan jalur yang ditampilkan, bukan tata letak volume universal. Folder yang disalin awalnya masih di VPS yang sama; pindahkan dan melindunginya di luar pelayan. Jika ada worker queue atau penulis lain, hentikan juga dan ikuti desain pelaksanaan sebenarnya. Panduan sandaran penuh n8n saat ini mendokumentasikan keperluan konsistensi SQLite.

Memulihkan folder SQLite lalai ke target yang bersih: pertama-tama hentikan perkhidmatan n8n dan semua proses penulis pangkalan data. selepas kontena perkhidmatan n8n yang kompatibel dan volume tujuannya ada, salin sandarannya .n8n isinya kembali ke direktori persisten yang sama. Ini akan menimpa fail target, jadi jangan jalankan pada instance dengan data yang perlu anda simpan:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-sandaran/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n kontena user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and aliran kerja triggers

Docker boleh disalin ke kontena yang dihentikan, tetapi kepemilikan tujuan mungkin berbeda dari aslinya; pastikan konfigurasi yang dipulihkan dan fail pangkalan data boleh dibaca dan ditulis oleh proses n8n sebelum memulainya. Jika konfigurasi Compose anda sebenar menggunakan jalur atau bind mount yang berbeda, sesuaikan salinannya. Docker Compose rujukan salinan. Memulihkan folder n8n saja tidak cukup untuk pelaksanaan yang menggunakan pangkalan data PostgreSQL berasingan.

RAHSIA KRITIKAL

Kunci penyulitan ialah sebahagian daripada pemulihan

n8n menyulitkan bukti kelayakan yang disimpan menggunakan kunci penyulitan instans. Eksport pangkalan data atau bukti kelayakan disulitkan tanpa kunci yang sepadan boleh menyebabkan aliran kerja yang dipulihkan tidak boleh menggunakan bukti kelayakan tersimpan.

Jika anda menyetel N8N_ENCRYPTION_KEY, pulihkan secret persisnya. Jika tidak, kunci yang dihasilkan disimpan dalam fail .n8n/config yang persisten: lindungi konfigurasi tersebut saat membuat sandaran atau membangun kembali. Simpan kunci pemulihan dengan aman di luar VPS. Dalam Queue Mode, semua proses utama dan worker perlu menggunakan kunci yang sama.

LakukanSimpan salinan terlindung bagi kunci tepat yang digunakan dalam produksi.
LakukanSahkan bahawa persekitaran pemulihan menggunakan kunci tersebut sebelum menguji bukti kelayakan.
JanganJangan bergantung pada kunci baharu yang dijana selepas pelayan dibina semula.
JanganJangan commit kunci ke repositori awam atau menyimpannya bersama sandaran yang tidak dilindungi.

FAIL & DATA BINARI

Sandaran pangkalan data mungkin tidak merangkumi setiap kebergantungan aliran kerja

Data .n8n persisten

Temukan dan pertahankan folder pengguna .n8n sebenar, bukan hanya imej kontena. Dalam pelaksanaan Docker tipikal, ini dipasang di /home/node/.n8n; di luar Docker defaultnya adalah ~/.n8n. Jika N8N_USER_FOLDER dikonfigurasi, n8n membuat .n8n di dalam direktori induk yang ditentukan. Sertakan kunci konfigurasinya dan data pelaksanaan SQLite, binari, atau sistem fail setempat apa pun yang digunakan instalasi anda.

Fail aliran kerja yang dipasang

Jika aliran kerja membaca atau menulis direktori yang dipasang pada hos, buat sandaran direktori tersebut secara berasingan. Memulihkan n8n tanpanya boleh menyebabkan aliran kerja yang valid menjadi rosak.

Data binari

Identifikasi mode storan dan pulihkan setiap ketergantungan eksternal. Data binari atau pelaksanaan berbasis sistem fail mungkin berada di .n8n atau direktori khusus; S3/Azure Blob atau storan eksternal terkonfigurasi lainnya memerlukan tetapan salinan dan aksesnya sendiri yang boleh dipulihkan. Dump pangkalan data saja tidak boleh menggantikan fail-fail tersebut.

Node komuniti

Catat paket dan versi komunitas, dan buat sandaran direktori node khusus tambahan yang dikonfigurasi melalui N8N_CUSTOM_EXTENSIONS. Direktori tersebut boleh berada di luar .n8n; pemulihan pangkalan data dan folder pengguna saja mungkin masih membuat aliran kerja node tersuai tidak boleh digunakan.

Sandaran pada VPS yang sama hanyalah salinan setempat

Salinan berversiKekalkan beberapa titik pemulihan supaya kerosakan data atau perubahan yang salah tidak menimpa satu-satunya sandaran yang boleh digunakan.
Kawalan aksesSandaran boleh mengandungi bukti kelayakan, logik aliran kerja dan data perniagaan sensitif. Sulitkan dan hadkan akses dengan sewajarnya.

Jadikan jadual sandaran boleh diukur. Catat stempel masa setiap sandaran yang berhasil, pemindahan selesai, saiz fail, versi pangkalan data sumber, lokasi kunci penyulitan untuk pemulihan, dan ujian pemulihan terbaharu yang berhasil. amaran tentang fail yang hilang, gagal, atau tiba-tiba kosong. penyulitan arkib sandaran sebelum mengirimnya keluar dari VPS dan batasi akses ke secret pemulihan. Beberapa titik pemulihan bertanggal melindungi terhadap penemuan korupsi hanya selepas salinan terbaharu menimpa salinan terakhir yang sehat.

Contohnya, jika anda boleh mentolerir perubahan yang hilang paling lama enam jam, jadual sandaran enam jam yang berhasil adalah titik awal, bukan jaminan: tugas yang gagal dan kelewatan replikasi di luar pelayan boleh meningkatkan kehilangan sebenarnya. Tetapkan pengekalan dan pemulihan kekerapan sesuai RPO/RTO dan keperluan data anda, daripada menerapkan kebijakan universal 7-hari atau 30-hari.

URUTAN PEMULIHAN

Pulihkan mengikut urutan yang terkawal

1 · SediakanSediakan pelayan, pangkalan data dan persekitaran kontena/runtime yang serasi.
2 · Pulihkan rahsiaKonfigurasikan kunci penyulitan n8n asal dan rahsia pelaksanaan yang diperlukan dengan selamat.
3 · Pulihkan pangkalan dataPulihkan PostgreSQL atau SQLite dan sahkan bahawa n8n boleh bersambung kepada data yang sepatutnya.
4 · Pulihkan failPulihkan direktori persisten, data binari dan aset aliran kerja yang dipasang.
5 · Mulakan n8nMulakan aplikasi dengan nama hos, pangkalan data dan konfigurasi persekitaran yang sepatutnya.
6 · SahkanSahkan bahawa pengguna, aliran kerja dan bukti kelayakan dimuatkan, kemudian jalankan aliran kerja yang mewakili penggunaan sebenar serta laluan webhook.

PostgreSQL contoh pemulihan bencana: pada target pemulihan yang berasingan dan bersih yang sudah memiliki peran pangkalan data yang benar dan kosong n8n pangkalan data, mulai saja PostgreSQL. Tunggu sehingga PostgreSQL sedia menerima sambungan sebelum mengimpor: docker compose up -d sendiri boleh kembali saat PostgreSQL masih dimulakan, jadi berikut ini pg_restore boleh gagal. Contohnya menggunakan --wait pada instalasi Compose modern dan memeriksa secara independen pg_isready. Konfigurasikan healthcheck PostgreSQL yang sesuai untuk penantian yang andal, atau sahkan kesiapan secara jelas sebelum melanjutkan. Jangan arahkan arahan ini ke pangkalan data produksi yang terisi atau mulai n8n sebelum pangkalan data dan pencocokannya .n8n kunci/data dipulihkan.

# RESTORE ONLY TO A FRESH, EMPTY TARGET pangkalan data
# Adapt Postgres Compose service, pangkalan data and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Tujuan perlu memiliki versi PostgreSQL yang kompatibel, keistimewaan peranan, ekstensi, dan konfigurasi n8n asli. Pulihkan .n8n ke volume persisten yang benar atau bind mount menggunakan mekanisme sandaran anda, menjaga kepemilikan dan izin. Pulihkan fail binari eksternal, ekstensi khusus, konfigurasi Tulis dan secret, lalu mulai n8n pada versi yang kompatibel dan semak lognya. Memulihkan pangkalan data saja tidak akan memulihkan kunci: pelaksanaan PostgreSQL akan mempertahankan kunci tersebut .n8n/config kecuali anda mengkonfigurasi secara jelas N8N_ENCRYPTION_KEY. rujukan pg_restore · n8n urutan pemulihan instance penuh.

UJIAN PEMULIHAN

Sandaran belum terbukti sehingga pemulihan berjaya

Uji dalam persekitaran yang bersih

Latihan sebenar perlu membuktikan bahawa sandaran boleh membina semula instans tanpa bergantung pada fail yang tidak dinyatakan tetapi masih tertinggal pada pelayan produksi.

Semak bukti kelayakan

Membuka aliran kerja sahaja tidak mencukupi. Sahkan bahawa bukti kelayakan disulitkan yang dipulihkan benar-benar boleh dinyahsulit dan digunakan untuk pengesahan.

Jalankan aliran kerja yang mewakili penggunaan sebenar

Uji aliran kerja yang bergantung pada webhook, API eksternal, fail terpasang, dan node komunitas, bukan hanya memvalidasi otomatisasi ringkas.

Ukur masa pemulihan

Catat berapa lama masa yang dibutuhkan untuk pemulihan dan langkah manual apa yang tersisa. Ini mengubah sandaran yang diasumsikan menjadi prosedur pemulihan operasional.

Latihan pemulihan yang disahkan: SQLite dan PostgreSQL

Persekitaran ujian: n8n 2.42.5 dalam kontena Docker terisolasi pada runner GitHub Actions sekali pakai, menggunakan aliran kerja dua node sintetis. Ujian ini dijalankan pada 8 Oktober 2026, bukan di pelayan n8n pelanggan atau produksi.

SQLite: LULUSMengimpor aliran kerja ujian, mengekspornya, menghentikan semua penulis, mengarsipkan persisten yang didukung SQLite .n8n folder dan kunci penyulitan yang dihasilkannya, dipulihkan ke volume bersih, dimulai n8n, lalu diekspor kembali dan menjalankan aliran kerja yang dipulihkan.
PostgreSQL: LULUSMengimpor aliran kerja ujian yang sama, membuat dan memeriksa format khusus pg_dump, memulihkannya menggunakan pg_restore ke dalam pangkalan data PostgreSQL baru yang kosong, pulihkan yang berasingan .n8n folder, lalu mengekspor ulang dan menjalankan aliran kerja yang dipulihkan.
Perkara yang dibuktikan oleh status LULUSJalur sandaran yang diuji mempertahankan aliran kerja ini, kedua nodenya, serta koneksinya dan memungkinkan pelaksanaan selepas pemulihan. Ini adalah ujian asap fungsional yang boleh direproduksi, bukan tolok ukur beban kerja.
Perkara yang tidak diujiDekripsi dan autentikasi bukti kelayakan nyata, webhook produksi, worker Queue Mode dan Redis, storan binari S3/Azure, node tersuai, akses pengguna/proyek, atau pemulihan instans produksi langsung. Jalankan latihan berasingan untuk setiap ketergantungan sebenar anda gunakan.

Cara menghasilkan semula ujian: gunakan instalasi n8n sekali pakai, buat aliran kerja dua node yang tidak berbahaya, jalankan pangkalan data yang berlaku ditambah sandaran folder persisten, pulihkan ke volume atau pangkalan data yang bersih, lalu verifikasi node, koneksi, dan pelaksanaan aktual aliran kerja yang dipulihkan. Pada sistem produksi juga memeriksa bukti kelayakan disulitkan, webhook, dan fail eksternal sebelum menyatakan pemulihan bencana terbukti.

Senarai semak penerimaan latihan pemulihan: menggunakan domain/lingkungan yang terisolasi; memeriksa apakah pengguna dan aliran kerja ada, satu bukti kelayakan disulitkan yang ada mengesahkan identiti tanpa memasukkan semula, webhook produksi memanggil aliran kerja yang dipulihkan, fail yang dipasang dan lampiran binari tetap boleh dibaca, dan integrasi dengan node komunitas yang diperlukan dimuat. sahkan umur sandaran, masa henti terukur, dan kebolehcapaian di luar pelayan. Jika ada pemeriksaan penting yang gagal, tandai titik pemulihan tersebut belum disahkan daripada melaporkan sandaran sebagai selesai.

HAD SANDARAN CLI

Ketahui dengan tepat perkara yang tidak dipulihkan oleh eksport aliran kerja dan bukti kelayakan

Eksport CLI bukan sandaran instans penuh

eksport sandaran aliran kerja dan bukti kelayakan tidak mencakup pengguna dan peran, sejarah pelaksanaan dan log, variabel, atau tetapan instans seperti kunci penyulitan.

Pemulihan instans baharu memerlukan pemilik

Pada contoh yang bersih, selesaikan persediaan pemilik sebelum mengimpor bukti kelayakan. Pemulihan multi-pengguna atau proyek mungkin juga memerlukan penetapan pengguna atau proyek yang benar.

ID yang diimport boleh menimpa item sedia ada

aliran kerja dan eksport bukti kelayakan mempertahankan ID aslinya. Mengimpor ke instance yang sudah berisi ID yang sama boleh menggantikan item yang sudah ada.

Terbitkan aliran kerja yang diimport secara terkawal

CLI import biasanya membuat aliran kerja tidak aktif. Pada n8n 2.x, semak status penerbitan setiap aliran kerja yang diimpor dan publikasikan hanya aliran kerja yang ingin anda jalankan; pelayan yang dihos sendiri CLI juga mendukung n8n terbitkan: aliran kerja --id=YOUR_WORKFLOW_ID. Ketika n8n berjalan, perubahan status publikasi/batalkan pelayan CLI hanya berlaku selepas memulai ulang n8n. Mulai ulang sebelum memverifikasi pemicu terjadwal dan webhook produksi atau mengalihkan traffic.

Contoh eksport pukal untuk Docker Compose: jika perkhidmatan n8n anda diberi nama n8n, anda boleh menjalankan sandaran resmi CLI di bawah. Jalur keluaran sengaja berada di dalam persisten yang dipasang .n8n direktori, kerana direktori sembarang di dalam kontena mungkin hilang saat dibuat ulang. sahkan bahwa direktori boleh ditulis oleh pengguna kontena n8n. Pertahankan aliran kerja dan bukti kelayakan JSON tetap masuk direktori berasingan—n8n mendokumentasikan masalah import ketika kedua jenis berbagi direktori.

n8n 2.x: draf berbanding sandaran versi diterbitkan: normal --sandaran eksport aliran kerja menangkap draf semasa; ini mungkin berbeda dari versi yang diterbitkan dalam produksi. Untuk mempertahankan versi aktual aliran kerja tertentu yang dipublikasikan, eksport secara berasingan menggunakan docker compose exec -T n8n n8n export:aliran kerja --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-aliran kerja.json, selepas memastikan bahwa folder keluaran ada dan boleh ditulis. CLI juga boleh mengekspor versi historis menggunakan --version=VERSION_ID. Simpan salinan ini di luar pelayan bersama dengan sandaran penuh; jangan menganggap draf JSON mencatat status diterbitkan dalam produksi.

# Execute from your Docker Compose project; the n8n service must exist
# Keep aliran kerja and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:aliran kerja --sandaran --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --sandaran --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the kontena to the hos
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Yang disalin ~/n8n-recovery/cli direktori masih di VPS sampai anda memindahkannya ke lokasi sandaran yang aman dan independen. eksport bukti kelayakan dienkripsi secara lalai dan memerlukan kunci penyulitan yang cocok saat mengimpor. Hindari menggunakan --decrypted kecuali untuk migrasi yang dikontrol ketat: ia menulis secret dalam teks biasa. Jangan pernah commit eksport yang berisi logika atau bukti kelayakan aliran kerja sensitif ke repositori GitHub awam. Beberapa templat sandaran bukti kelayakan GitHub pihak ketiga dengan sengaja mengekspor secret yang didekripsi; repositori pribadi adalah pembatasan akses, bukan penyulitan. semak tetapan eksport aktual dan izin storan setiap templat, penyulitan secret sebelum transfer ke luar pelayan, dan putar ganti bukti kelayakan apa pun yang terekspos melalui unggahan teks biasa yang tidak diinginkan.

Contoh import pukal: pada target yang bersih, selesaikan tetapan pemilik, berikan kunci penyulitan asli dan pastikan fail sandaran yang disimpan tersedia pada VPS pemulihan tersebut. Berikut ini membuat folder tujuan dan menyalinnya workflows/ dan credentials/ subfolder dari hos ke dalam kontena n8n; sesuaikan jalur jika tata letak volume Docker anda berbeda:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

semak kepemilikan dan akses fail untuk pengguna kontena n8n. Jangan mengimpor instans produksi yang terisi tanpa rollback disahkan: aliran kerja dan ID bukti kelayakan boleh menimpa entri yang sudah ada. Kemudian jalankan:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:aliran kerja --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

ID yang diimpor boleh menggantikan aliran kerja atau bukti kelayakan yang ada; gunakan instance ujian terisolasi untuk ujian kering dan semak bukti kelayakan serta status aktivasi/penerbitan setelahnya. Di n8n 2.x, memulihkan draf JSON tidak dengan sendirinya membuktikan aliran kerja telah dipublikasikan dan boleh menjalankan pemicu terjadwal. Keselamatan import: pada instance n8n non-multi-main, pemicu cron yang sebelumnya aktif boleh terus berjalan selepas import CLI hingga instance dimulai ulang. Hentikan atau isolasi pemicu produksi dan mulai ulang n8n sebelum mengaktifkan tugas yang dipulihkan; verifikasi tidak ada pelaksanaan duplikat. CLI eksport boleh tidak berisi pengguna asli, log pelaksanaan, variabel instan, atau kunci penyulitan. --sandaran set --all --pretty --separate, bukan 'instans penuh'. Sumber: panduan sandaran/pemulihan n8n resmi terkini dan rujukan arahan n8n CLI.

Pemulihan pukal daripada templat GitHub atau Google Drive: ini merupakan alternatif untuk aliran kerja JSON saja, bukan untuk pangkalan data instans, pengguna, nilai bukti kelayakan disulitkan, atau kunci penyulitan. Sebelum menjalankan templat berbasis API, verifikasi n8n API dan izin penyimpanannya, versi sandaran yang dipilih dan instans target, apakah templat tersebut memperbarui ID yang cocok dan membuat ulang aliran kerja yang dihapus, dan apa fungsinya dengan penerbitan aliran kerja. Tidak semua template membuat ulang ID yang hilang dari target; uji senario tersebut secara berasingan sebelum bergantung pada pemulihan automatik.

FAQ

Sandaran dan pemulihan n8n: soalan lazim

Adakah mengeksport aliran kerja sahaja mencukupi untuk menyandarkan n8n?

Tidak. eksport aliran kerja adalah salinan logis yang berguna, namun pemulihan lengkap juga memerlukan bukti kelayakan, kunci penyulitan yang cocok, status pangkalan data, fail persisten, dan storan data binari.

Adakah saya memerlukan kunci penyulitan n8n jika saya mempunyai pangkalan data?

Ya, jika anda memerlukan bukti kelayakan disulitkan yang disimpan dalam pangkalan data tersebut agar tetap boleh digunakan. Simpan kunci asli dengan aman.

Patutkah saya menyandarkan PostgreSQL atau mengeksport aliran kerja dan bukti kelayakan?

Untuk pemulihan bencana, lindungi pangkalan data dan kunci penyulitan. eksport logis lebih berharga sebagai lapisan migrasi tambahan dan pemulihan selektif, bukan sebagai pengganti setiap bagian dari proses tersebut.

Bolehkah snapshot VPS menjadi satu-satunya sandaran saya?

Lebih baik diperlakukan sebagai satu lapisan pemulihan. Simpan sandaran di luar pelayan yang independen sehingga kegagalan penyedia, akun, pelayan, atau snapshot tidak menghapus setiap titik pemulihan sekaligus.

Bagaimanakah saya tahu sandaran saya berfungsi?

Pulihkan ke lingkungan ujian yang bersih, verifikasi dekripsi bukti kelayakan, dan jalankan aliran kerja yang mewakili penggunaan sebenar. tugas sandaran yang berhasil saja tidak membuktikan kebolehpulihan.

Adakah sandaran aliran kerja GitHub atau Google Drive merangkumi rahsia bukti kelayakan yang disimpan?

sandaran JSON khusus aliran kerja tidak menyertakan nilai secret yang dikelola oleh storan bukti kelayakan n8n atau kunci penyulitan instans. Namun, JSON yang diekspor boleh mengekspos nama bukti kelayakan dan ID serta secret yang diketik langsung ke dalam parameter node, seperti header autentikasi. semak dan lindungi JSON yang diekspor sebelum mengunggah atau membagikannya. Untuk pemulihan penuh, buat sandaran pangkalan data dan kunci asli, atau gunakan eksport bukti kelayakan disulitkan yang didukung CLI dengan pemulihan yang diuji. Templat GitHub atau Google Drive khusus aliran kerja bukanlah pemulihan bencana sepenuhnya.

OBJEKTIF PEMULIHAN

Tetapkan RPO dan RTO sebelum insiden

RPO adalah kehilangan maksimum yang boleh ditoleransi dari perubahan terkini. Ukur dari titik pemulihan terbaharu yang boleh digunakan dan disimpan secara independen; tugas enam jam yang dijadwalkan tidak menghasilkan RPO enam jam jika eksport atau transfer gagal. RTO adalah tempoh henti maksimum yang boleh ditoleransi. Ukur hal ini dalam latihan pemulihan yang bersih, termasuk mengambil secret, memulihkan fail eksternal, memeriksa ulang bukti kelayakan, dan menerbitkan aliran kerja yang dipulihkan—bukan hanya memulai sebuah kontena.

KUNCI PEMULIHAN

Cari kunci penyulitan asal sebelum membina semula

Jika produksi ditetapkan N8N_ENCRYPTION_KEY, jaga environment secret tersebut. Jika tidak, pertahankan kunci yang dihasilkan dalam .n8n/config asli. semak sumber mana sebenar digunakan oleh instance yang dipulihkan sebelum mengimpor bukti kelayakan disulitkan; kunci baru yang dihasilkan tidak boleh menyahsulit bukti kelayakan dari pangkalan data lama.
