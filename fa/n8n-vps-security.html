امنیت تولید

امن‌سازی n8n روی VPS

برای ایمن کردن n8n در VPS، n8n (5678)، PostgreSQL (5432) و Redis (6379) اختیاری را از اینترنت عمومی خارج کنید. از یک Reverse Proxy HTTPS، کلیدهای SSH و MFA استفاده کنید، کلید رمزگذاری خود را حفظ کنید، قلاب‌های وب را احراز هویت کنید، قابلیت‌های گردش‌کار خطرناک را محدود کنید و نمونه مستقر شده را بررسی کنید. از ویرایشگر به‌طور جداگانه از مسیرهای وب‌هوک عمومی محافظت کنید. HTTPS به تنهایی خدمات متصل را ایمن نمی‌کند.

چک‌لیست سریع

حداقل خط مبنای امنیتی پیش از دسترسی عمومی

با پورت های قابل دسترسی، HTTPS، دسترسی مدیریت تایید شده، MFA و حفاظت از اعتبارنامه های ذخیره شده شروع کنید. هر وب‌هوک ورودی را قبل از شروع کار حساس تأیید کنید. پس از تغییر کنترل های دسترسی، بررسی کنید که ویرایشگرهای مورد نظر و ادغام‌های خارجی هنوز کار می کنند، سپس ممیزی امنیتی n8n را اجرا کنید.

HTTPS فقط

n8n را در پشت یک پراکسی معکوس TLS که به درستی پیکربندی شده است قرار دهید و از URL عمومی HTTPS به‌طور مداوم برای ویرایشگر و هوک ها استفاده کنید.

حداقل پورت های باز

فقط پورت های مورد نیاز برای ترافیک عمومی را در معرض دید قرار دهید. PostgreSQL، Redis و درگاه های برنامه داخلی را از اینترنت عمومی خارج کنید.

سخت شدن SSH

از مدیریت مبتنی بر کلید استفاده کنید، افرادی که می توانند وارد سیستم شوند را محدود کنید و سیستم عامل را وصله نگه دارید.

از اعتبارنامه ها محافظت کنید

کلید رمزگذاری n8n را ثابت و مخفی نگه دارید. فایل های محیطی، دسترسی به پایگاه‌داده و نسخه های پشتیبان را به عنوان دارایی های حساس در نظر بگیرید.

NETWORK EDGE

Reverse Proxy، HTTPS و سرصفحه های قابل اعتماد

TLS خاتمه

از یک Reverse Proxy مانند Nginx، Caddy یا Traefik برای خاتمه دادن به HTTPS استفاده کنید. HTTP ساده را هدایت کنید و از افشای مستقیم پورت برنامه n8n در زمانی که پراکسی نقطه ورودی مورد نظر است، خودداری کنید.

پیکربندی پروکسی

هنگامی که n8n در پشت یک پراکسی معکوس اجرا می‌شود، تعداد پراکسی هاپ را به درستی پیکربندی کنید و هدرهای ارسال شده را ارسال کنید. n8n برای بازسازی درخواست مشتری اصلی نیاز است.

کوکی ها را ایمن کنید

ویرایشگر را روی HTTPS ارائه کنید تا کوکی‌های احراز هویت امن باقی بمانند. با تضعیف امنیت کوکی ها، راه‌اندازی TLS شکسته را حل نکنید.

آدرس وب‌هوک

URL عمومی وب‌هوک را روی نام میزبان HTTPS قابل دسترسی خارجی تنظیم کنید تا نقاط پایانی وبک هوک ایجاد شده به یک ظرف داخلی یا آدرس HTTP اشاره نکنند.

ویرایشگر را بدون شکستن وب‌هوک‌ها خصوصی نگه دارید. دسترسی مدیریت را با استفاده از VPN، خط مشی IP قابل اعتماد یا یک پروکسی تأیید شده در صورت عملی محدود کنید. گیرنده های وب‌هوک عمومی و مسیرهای برگشت به تماس OAuth ممکن است نیاز به دسترسی داشته باشند. قبل از اجرای یک قانون پروکسی، هم یک ورود به سیستم ویرایشگر قابل اعتماد و هم یک تماس خارجی واقعی را آزمایش کنید. هدرهای آدرس کلاینت را فقط از پروکسی های قابل اعتماد منتقل کنید، نه سرصفحه های درخواست دلخواه.

احراز هویت تماس گیرندگان وب‌هوک: در گره Webhook احراز هویت پایه، سربرگ یا JWT را به جای None در صورت پشتیبانی توسط فرستنده انتخاب کنید. از آن استفاده کنید IP(ها) لیست مجاز در صورت لزوم گزینه را انتخاب کنید و امضاهای ارائه‌دهنده را در جایی که ادغام از درخواست های امضا شده پشتیبانی می‌کند تأیید کنید. یک URL که حدس زدن آن دشوار است، احراز هویت کافی نیست. در صورت لزوم محدودیت‌های نرخ را در پروکسی اعمال کنید و تأیید کنید که انفجارهای معتبر مسدود نشده‌اند. گزینه های رسمی احراز هویت Webhook.

VPS سخت شدن

سطح حمله سرور را کاهش دهید

فایروال

ترافیک ورودی ناخواسته را به‌طور پیش‌فرض رد کنید و فقط به خدماتی اجازه دهید که باید قابل دسترسی باشند. پورت های پایگاه‌داده و Redis معمولاً به شبکه های خصوصی/محلی تعلق دارند.

SSH

کلیدهای SSH را به رمز عبور ترجیح دهید، مسیرهای ورود غیر ضروری را غیرفعال کنید و دسترسی مدیریت را محدود کنید. دسترسی معادل ریشه باید به شدت کنترل شود.

به‌روزرسانی سیستم عامل

Linux میزبان و زمان اجرا کانتینر را وصله کنید. سخت شدن برنامه نمی‌تواند سیستم عامل در معرض یا منسوخ را جبران کند.

قرار گرفتن در معرض کانتینر

فقط پورت هایی را که نیاز به دسترسی میزبان دارند منتشر کنید. سرویس های داخلی باید در شبکه های خصوصی Docker به جای از طریق رابط های عمومی ارتباط برقرار کنند.

قبل از تغییر تنظیمات فایروال یا SSH بازرسی کنید: پورت های گوش دادن را با sudo ss -lntp، Docker انتشار با docker compose ps از دایرکتوری پروژه و خط مشی فایروال میزبان با sudo ufw status verbose اگر از UFW استفاده شود. قبل از غیرفعال کردن دسترسی به رمز عبور، پورت SSH واقعی و ورود موفقیت آمیز کلید خود را در یک جلسه جداگانه تأیید کنید. پورت های Docker منتشر شده می توانند قوانین UFW را دور بزنند. صفحه وضعیت فایروال به تنهایی ثابت نمی‌کند که پورت 5678 خصوصی است. دسترسی خارجی واقعی را بررسی کنید. Docker/اخطار UFW.

به‌جای اینکه فرض کنید کار می‌کنند، به‌روزرسانی‌های امنیتی خودکار Ubuntu را بررسی کنید: بازرسی apt-config dump APT::Periodic::Unattended-Upgrade و ورود به سیستم /var/log/unattended-upgrades/unattended-upgrades.log. اگر ارتقاء امنیتی بدون نظارت غیرفعال باشد، sudo dpkg-reconfigure unattended-upgrades یک گفتگوی پیکربندی پشتیبانی شده را ارائه می‌دهد. رفتار راه‌اندازی مجدد و راه‌اندازی مجدد سرویس را قبل از فعال کردن آن بر روی یک VPS فعال بررسی کنید. Ubuntu به‌روزرسانی APT انجام می‌شود نه تصویر n8n Docker یا هر مخزن نرم افزار شخص ثالث را به‌طور خودکار به روز کنید. Ubuntu به‌روزرسانی خودکار اسناد.

اختیاری SSH نظارت بر brute-force: Fail2Ban می‌تواند ورودهای ناموفق مکرر SSH را شناسایی کند. اگر برای SSH نصب و پیکربندی شده است، زندان را با آن تأیید کنید sudo fail2ban-client status sshd و تأیید کنید که گزارش یا ژورنال احراز هویت SSH واقعی شما را می خواند و با پورت پیکربندی شده مطابقت دارد. این کلیدهای SSH و محدودیت های شبکه را تکمیل می‌کند. جایگزین آن‌ها نمی‌شود. یک پورت SSH ثابت یا قانون ممنوعیت را بدون بررسی دسترسی موجود کپی نکنید. Ubuntu SSH هدایت سخت شدن.

پایگاه‌داده و REDIS

سرویس‌های backend را خصوصی نگه دارید

در یک تنظیم معمولی Docker Compose، PostgreSQL و حالت صف Redis باید توسط کانتینرهای مربوطه از طریق شبکه خصوصی قابل دسترسی باشد، نه پورت های منتشر شده توسط میزبان. تأیید با docker compose ps که 5432 و 6379 به صورت عمومی منتشر نشده اند. به‌طور جداگانه VPS/ قرار گرفتن در معرض فایروال ابری را بررسی کنید. خط‌مشی‌های شبکه جایگزین اعتبارنامه‌های پایگاه‌داده با حداقل امتیاز نمی‌شوند.

PostgreSQLآن را به یک رابط خصوصی یا شبکه کانتینری متصل کنید، مگر اینکه دسترسی از راه دور به صراحت مورد نیاز باشد و به‌طور مستقل ایمن شود.
Redisحالت صف Redis زیرساخت است، نه یک نقطه پایانی عمومی. دسترسی شبکه را به اجزای n8n که به آن نیاز دارند محدود کنید.
اعتبارنامهاز اعتبارات پایگاه‌داده اختصاصی تنها با مجوزهایی که برنامه نیاز دارد استفاده کنید و از کنترل منبع خارج از آن‌ها محافظت کنید.
حمل و نقلهنگامی که ترافیک پایگاه‌داده از شبکه های نامعتبر عبور می‌کند، به جای اتکا به رمزگذاری اعتبار در سطح برنامه، از حمل و نقل رمزگذاری شده مناسب استفاده کنید.

اسرار N8N

از کلید رمزگذاری و مرز اعتبارنامه‌ها محافظت کنید

کلید رمزگذاری

n8n اعتبارنامه های ذخیره شده را با استفاده از کلید رمزگذاری خود رمزگذاری می‌کند. کلید یکسان را در راه‌اندازی مجدد و Workerها حفظ کنید و آن را جدا از محتوای برنامه های معمولی محافظت کنید.

اسرار محیطی

گذرواژه‌ها، نشانه‌ها یا کلید رمزگذاری را به یک مخزن عمومی تحویل ندهید. دسترسی به فایل های محیطی و اسرار استقرار را محدود کنید.

دسترسی کاربر

اجازه دسترسی ویرایشگر را فقط به کاربران قابل اعتماد بدهید. گردش‌کار می‌تواند به سیستم های حساس متصل شود و ممکن است اسرار را پردازش کند یا گره های قدرتمندی را اجرا کند.

محدوده اعتبار

در صورت امکان از حساب‌های سرویس با محدوده محدود و نشانه‌های API استفاده کنید. یک گردش‌کار به خطر افتاده نباید به‌طور خودکار دسترسی گسترده به سیستم های نامرتبط را به ارث ببرد.

n8n پیکربندی برای بازبینی: N8N_BLOCK_ENV_ACCESS_IN_NODE=true از دسترسی Code-node و عبارت به مقادیر محیط جلوگیری می‌کند. N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true فقط مجوزهای مالک را در فایل تنظیمات درخواست می‌کند. نگه دارید N8N_ENCRYPTION_KEY پایدار و پشتیبان‌گیری ایمن: n8n می‌تواند در اولین راه‌اندازی یک کلید تصادفی ایجاد کند، اما از دست دادن آن ممکن است اعتبار رمزگذاری‌شده موجود را غیرقابل استفاده کند. کلید رمزگذاری تولیدی را به صورت تصادفی جایگزین نکنید. از یک روال چرخش پشتیبانی رسمی استفاده کنید. مسدود کردن دسترسی به محیط می‌تواند ادغام‌های موجود را از بین ببرد، بنابراین قبل از تغییرات تولید، آزمایش کنید. n8n تعاریف متغیر امنیتی.

ریسک جریان کار

Nodeها می‌توانند دامنه امنیتی را گسترش دهند

میزبانی شخصی به گردش‌کار قدرت قابل توجهی می‌دهد. اجرای کد، دسترسی به پوسته، درخواست های دلخواه HTTP و گره های جامعه شخص ثالث می‌تواند خطر را افزایش دهد. عملکردی را که به آن نیاز ندارید غیرفعال کنید و قبل از اجرای آن‌ها، وارد کردن گردش‌کار نامعتبر را بررسی کنید.

از کنترل های دقیق پشتیبانی شده استفاده کنید: پیکربندی کنید NODES_EXCLUDE با یک آرایه JSON از گره ها برای غیرفعال کردن، مانند n8n-nodes-base.executeCommand و n8n-nodes-base.readWriteFile، در صورت عدم استفاده برخی از گره‌های پرخطر قبلاً در نسخه‌های جدیدتر به‌طور پیش‌فرض مسدود شده‌اند. لیست واقعی را قبل از تغییر آن مرور کنید. حذف های رسمی گره

از n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true بررسی درخواست‌های HTTP خروجی در محدوده‌های داخلی، حلقه‌ای و آدرس فراداده را فعال می‌کند. گردش‌کارها API داخلی قانونی ممکن است کار را متوقف کنند. در صورت لزوم، فقط مقصدهایی را که کنترل می کنید به صورت محدود فهرست کنید. تقسیم بندی شبکه را به عنوان دفاع اصلی نگه دارید. برای جداسازی گره کد، اجراکننده های وظیفه خارجی را بررسی کنید. حفاظت SSRF · جداسازی Task-runner.

گره های جامعهفقط بسته هایی را که به آن‌ها اعتماد دارید نصب کنید. آن‌ها در محیط n8n شما اجرا می‌شوند.
گره های مخاطره آمیزگره هایی را که استقرار شما نیازی به آن‌ها ندارد، زمانی که قابلیت های آن‌ها از مرز گردش‌کار مورد نظر فراتر می رود، حذف کنید.
SSRFاز حفاظت SSRF و کنترل‌های شبکه n8n در جایی که جریان‌های کاری نباید به نقاط پایانی داخلی یا فراداده دسترسی پیدا کنند، استفاده کنید.
Import گردش‌کارقبل از فعال‌سازی، گردش‌های کاری، اعتبارنامه‌ها، عبارات و مراحل اجرایی وارد شده را بررسی کنید.

حسابرسی و به‌روزرسانی

امنیت یک فرایند عملیاتی مستمر است

n8n ممیزی امنیتی را اجرا کنید

دستور رسمی CLI است n8n audit. اگر سرویس Docker نوشتن نام شما نامگذاری شده است n8n، اجرا کنید docker compose exec -T n8n n8n audit در آن دایرکتوری استقرار پنج دسته را مرور کنید: اعتبارنامه‌های استفاده نشده، الگوهای پرخطر SQL-query، دسترسی به سیستم فایل، گره‌های مخاطره‌آمیز/جامعه، و خطرات نمونه از جمله وبک‌قلک‌های محافظت‌نشده و نسخه‌های قدیمی. یافته های مربوطه را برطرف کنید و دوباره اجرا کنید. این یک تست نفوذ نیست. راهنمای حسابرسی رسمی

به‌روزرسانی عمدی

n8n را به اندازه کافی جاری نگه دارید تا رفع‌های امنیتی دریافت کنید. یادداشت‌های انتشار را مرور کنید و به‌روزرسانی‌های مهم را آزمایش کنید، به‌جای اینکه یک نمونه اینترنتی را برای همیشه کهنه کنید.

نظارت بر احراز هویت

الگوهای دسترسی غیرمنتظره، تغییرات گردش‌کار و شکست را تماشا کنید. زمانی که مدل عملیاتی شما به دسترسی عمومی گسترده ای نیاز ندارد، رابط کاربری ویرایشگر را بیشتر محدود کنید.

بازگشت و بازیابی را آماده کنید

قبل از ارتقاء قابل توجه، بک آپ های قابل بازیابی بگیرید. دامنه پشتیبان‌گیری دقیق و بازیابی به راهنمای بازیابی جداگانه تعلق دارد.

به حداقل رساندن سابقه اجرای حساس: اجراهای موفق می توانند داده ها و نشانه های مشتری را حفظ کنند. در صورت تنظیم مناسب EXECUTIONS_DATA_SAVE_ON_SUCCESS=none، نگه دارید EXECUTIONS_DATA_PRUNE=true، و یک را انتخاب کنید EXECUTIONS_DATA_MAX_AGE در ساعت، مانند 168 (هفت روز). این موارد نمونه های قابل تنظیم هستند، نه قوانین حفظ قانونی. تاریخچه کمتر به معنای اشکال زدایی کمتر و داده‌های پزشکی قانونی است. اجراهای در حال اجرا، انتظار یا حاشیه نویسی ممکن است به یک شکل هرس نشوند. حفظ اعدام رسمی

محدود کردن افرادی که می توانند گردش‌کار را ویرایش کنند

دسترسی ویرایشگر یک دسترسی ممتاز است: گردش‌های کاری می‌توانند اعتبارنامه‌ها را بخوانند، سیستم‌های داخلی را فراخوانی کنند و گره‌های قدرتمند را اجرا کنند. دسترسی کاربر را محدود نگه دارید و حساب هایی را که دیگر به آن نیاز ندارند حذف کنید.

قابلیت هایی را که استفاده نمی کنید غیرفعال کنید

سطح حمله برنامه را با غیرفعال کردن API عمومی در مواقع غیرضروری و مسدود کردن گره‌ها یا ویژگی‌های پرخطری که مدل عامل شما به آن نیاز ندارد، کاهش دهید.

از SSRF و کنترل های مخفی عمدا استفاده کنید

برای جریان‌های کاری که می‌توانند درخواست‌های دلخواه HTTP را ارائه کنند، حفاظت SSRF n8n را ارزیابی کنید و اسرار را از کد گردش‌کار، مخازن عمومی و فایل‌های محیطی قابل خواندن دور نگه دارید.

محدود کردن نقاط پایانی مدیریت استفاده نشده: N8N_PUBLIC_API_DISABLED=true n8n REST عمومی API را غیرفعال می‌کند و N8N_PUBLIC_API_SWAGGERUI_DISABLED=true زمین بازی API خود را به‌طور جداگانه غیرفعال می‌کند. این کار را فقط زمانی انجام دهید که ادغام‌های شما به آن ویژگی ها نیاز نداشته باشند. غیرفعال کردن REST API، آدرس‌های وب‌هوک گردش‌کار را تأیید اعتبار نمی‌کند. از MFA برای کاربران ویرایشگر استفاده کنید و از خط مشی های متمرکز فقط در جایی استفاده کنید که نسخه n8n شما از آن‌ها پشتیبانی می‌کند.

امنیت n8n روی VPS: سؤالات متداول

آیا باید پورت n8n مستقیماً در معرض دید قرار گیرد؟

هنگامی که یک پراکسی معکوس نقطه ورود عمومی است، به جای انتشار گسترده خدمات غیر ضروری، پروکسی را در معرض دید قرار دهید و پورت برنامه را پشت آن نگه دارید.

آیا PostgreSQL یا Redis باید عمومی باشد؟

به‌طور معمول خیر. آن‌ها باید فقط توسط سیستم هایی که به آن‌ها نیاز دارند قابل دسترسی باشند. قرار گرفتن در معرض عمومی سطح حمله را بدون کمک به عملکرد عادی n8n افزایش می‌دهد.

چرا کلید رمزگذاری n8n مهم است؟

از اعتبارنامه های ذخیره شده توسط n8n محافظت می‌کند و باید در سراسر استقرار ثابت بماند. از دست دادن آن می‌تواند از ایجاد اطلاعات رمزگذاری شده قابل استفاده از اطلاعات بازیابی جلوگیری کند.

آیا گره های جامعه ایمن هستند؟

آن‌ها n8n را با کد شخص ثالث گسترش می دهند، بنابراین باید به عنوان وابستگی های نرم افزاری با خطرات زنجیره تامین و امتیاز خود در نظر گرفته شوند. فقط آنچه را که به آن اعتماد دارید و نیاز دارید نصب کنید.

آیا HTTPS یک نمونه n8n خودمیزبان را ایمن می‌کند؟

شماره HTTPS از حمل و نقل محافظت می‌کند. امنیت تولید همچنین مستلزم سخت‌سازی میزبان، کنترل دسترسی، خدمات پشتیبان خصوصی، حفاظت مخفی، قابلیت‌های گردش‌کار ایمن، نظارت و به‌روزرسانی است.

آیا ویرایشگر n8n می‌تواند خصوصی باشد در حالی که وبکهک های تولید هنوز اجرا می‌شوند؟

بله. یک Reverse Proxy قابل اعتماد یا VPN می‌تواند دسترسی ویرایشگر/مدیر را جدا از مسیرهای وب‌قلاب تولید عمومی و پاسخ به تماس OAuth محدود کند. برای جلوگیری از مسدود شدن تصادفی ادغام‌هایتان، ورود به سیستم مورداعتماد و تحویل وب‌هوک خارجی را پس از هر تغییر قانون دسترسی آزمایش کنید.

چگونه می توانم وب‌هوک‌های دریافتی n8n را احراز هویت کنم؟

هنگامی که فرستنده از آن پشتیبانی می‌کند، احراز هویت پایه، سربرگ یا JWT را در گره Webhook پیکربندی کنید. همچنین می‌توانید از IP(های) Allowlist استفاده کنید و امضاهای ارائه‌دهنده را در صورت وجود بررسی کنید. فقط به یک مسیر مخفی تکیه نکنید و درخواست ها را قبل از اینکه اقدامات حساس API را آغاز کنند اعتبار سنجی کنید.
