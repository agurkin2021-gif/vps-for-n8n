n8n پشتیبان گیری و بازیابی

برای تهیه نسخه پشتیبان و بازیابی از n8n خود میزبانی شده، از پایگاه داده SQLite یا یک روکش PostgreSQL ثابت، پوشه n8n دائمی و کلید رمزگذاری اصلی، پیکربندی استقرار و هر وابستگی باینری یا فایل نصب شده خارجی محافظت کنید. یک کپی رمزگذاری شده را از VPS نگه دارید و بازیابی را در یک نمونه جداگانه آزمایش کنید. از CLI گردش کار و صادرات اعتبار برای بازیابی انتخابی استفاده کنید. JSON صادرات به تنهایی یک نسخه پشتیبان کامل از سرور نیست.

پیوند شریک: ممکن است از خرید کمیسیون دریافت کنیم.

چک لیست سریع

پشتیبان n8n باید از چه چیزی محافظت کند

پایگاه داده

از پایگاه داده PostgreSQL یا فایل پایگاه داده SQLite استفاده شده توسط نمونه پشتیبان تهیه کنید. پایگاه داده شامل وضعیت n8n اصلی مانند گردش کار، اعتبارنامه ها و داده های اجرایی است.

کلید رمزگذاری

کلید رمزگذاری دقیق n8n را جداگانه و ایمن حفظ کنید. اعتبارنامه های رمزگذاری شده بازیابی شده به همان کلید بستگی دارد.

فایل های ماندگار

فهرست n8n دائمی داده ها و هر فایل نصب شده، ذخیره سازی داده های باینری یا دارایی های گردش کار را که استقرار شما به آنها متکی است، اضافه کنید.

پیکربندی استقرار

فایل های Compose/configuration و پیکربندی غیرمخفی مورد نیاز برای بازسازی پشته را نگه دارید. از اسرار با کنترل های دسترسی مناسب محافظت کنید.

دو سطح پشتیبان

صادرات منطقی در مقابل بازیابی کامل بلایا

گردش کار و صدور اعتبار

صادرات n8n CLI برای مهاجرت، نسخه های گردش کار نسخه شده و بازیابی انتخابی مفید است. اعتبارنامه ها را می توان به صورت رمزگذاری شده صادر کرد و بعداً با کلید رمزگذاری منطبق وارد کرد. برای بازیابی تنها یک گردش کار، از منوی سه نقطه ویرایشگر گردش کار برای دانلود JSON آن استفاده کنید، سپس از فایل به یک گردش کار بررسی جدید یا نمونه ایزوله وارد کنید. اعتبارنامه، شناسه‌های گردش کار و پارامترهای گره را قبل از جایگزینی جریان کار زنده بررسی کنید: بازیابی گردش کار JSON کل سرور را بازیابی نمی‌کند.

صادرات نهاد

CLI می تواند موجودیت های پایگاه داده را برای انتقال داده ها بین انواع پایگاه داده پشتیبانی شده صادر کند. جداول تاریخچه اجرا اختیاری هستند زیرا می توانند بسیار بزرگ باشند.

بازیابی کامل نمونه

برای یک سناریوی سرور مرده، از پایگاه داده واقعی، کلید رمزگذاری، داده های پایدار و وابستگی های استقرار محافظت کنید. فرض نکنید که یک گردش کار JSON صادرات کل نمونه را بازسازی می کند.

عکس فوری ارائه دهنده

یک عکس فوری VPS به عنوان یک لایه بازیابی اضافی مفید است، اما نباید تنها کپی باشد و نباید جایگزین نسخه پشتیبان برنامه/پایگاه داده تایید شده مستقل شود.

پایگاه داده

به طور مداوم از پایگاه داده پشتیبان تهیه کنید

PostgreSQL

از یک روش پشتیبان گیری ثابت PostgreSQL استفاده کنید و نسخه پشتیبان به دست آمده را دور از VPS ذخیره کنید. کپی پایگاه داده روی همان دیسک شکست خورده بازیابی فاجعه نیست.

SQLite

اگر استقرار از SQLite استفاده می کند، از فایل پایگاه داده در برابر دایرکتوری داده n8n پایدار محافظت کنید. از کپی کردن پایگاه داده در حالت ناامن در زمانی که به طور فعال در حال تغییر است خودداری کنید.

سابقه اعدام

تصمیم بگیرید که آیا داده‌های اجرای تاریخی بخشی از هدف بازیابی شما است یا خیر. می‌تواند پشتیبان‌گیری‌ها را به میزان قابل‌توجهی بزرگ‌تر کند، بنابراین حفظ و رعایت الزامات باید انتخاب را هدایت کند.

نسخه پایگاه داده

موتور پایگاه داده و نسخه مورد استفاده توسط استقرار منبع را ضبط کنید تا بتوان یک محیط بازیابی را به طور سازگار آماده کرد.

PostgreSQL در Docker VPS را بنویسید. اگر سرویس PostgreSQL نامگذاری شده باشد postgres و پایگاه داده/کاربر آن هر دو هستند n8n، دستور زیر یک Dump با فرمت سفارشی PostgreSQL سازگار در هاست ایجاد می کند. فایل Compose واقعی خود را قبل از اجرای آن بررسی کنید و اعتبار پایگاه داده و نام سرویس را تنظیم کنید. pg_dump می تواند در حین اجرای PostgreSQL یک عکس فوری منطقی یکسان تولید کند. انجام می دهد نه از جدا بک آپ بگیرید .n8n پوشه کاربر یا داده های باینری خارجی.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

بررسی فهرست بایگانی مشکلات فرمت آشکار را پیدا می کند اما ثابت نمی کند که داده ها قابل بازیابی هستند. یک کپی رمزگذاری شده را خارج از سرور ذخیره کنید و یک بازیابی را تمرین کنید. از اسناد رسمی PostgreSQL pg_dump برای گزینه های خاص پایگاه داده استفاده کنید.

SQLite در Docker. برای استقرار پیش فرض SQLite، database.sqlite و پیکربندی کلید رمزگذاری ایجاد شده در داخل پایدار وجود دارد .n8n پوشه (به طور معمول در /home/node/.n8n). هرگز با یک کپی زنده ساده از SQLite به عنوان یکنواخت برخورد نکنید. قبل از کپی کردن پوشه، n8n و سایر نویسندگان پایگاه داده را متوقف کنید، یا زمانی که وقفه غیرممکن است از مکانیسم پشتیبان گیری آنلاین پشتیبانی شده SQLite استفاده کنید:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

اینها دستورات گویا برای سرویس و مسیر نشان داده شده هستند، نه طرح بندی حجم جهانی. پوشه کپی شده در ابتدا همچنان روی همان VPS است. انتقال و محافظت از آن خارج از سرور هنگامی که کارگران صف یا سایر نویسندگان وجود دارند، آنها را نیز ساکت کنید و طرح استقرار واقعی آنها را دنبال کنید. راهنمای فعلی n8n پشتیبان گیری کامل، الزامات سازگاری SQLite را مستند می کند.

بازیابی پوشه پیش فرض SQLite به یک هدف تمیز: ابتدا سرویس n8n و همه نویسندگان پایگاه داده را متوقف کنید. هنگامی که یک ظرف سرویس سازگار n8n و حجم مقصد آن وجود داشت، نسخه پشتیبان تهیه شده را کپی کنید .n8n مطالب برگشت به همان دایرکتوری مداوم این فایل‌های هدف را بازنویسی می‌کند، بنابراین آن را روی نمونه‌ای با داده‌هایی که باید نگه دارید اجرا نکنید:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker می تواند در کانتینرهای متوقف شده کپی شود، اما مالکیت مقصد ممکن است با اصلی متفاوت باشد. قبل از شروع، اطمینان حاصل کنید که پیکربندی بازیابی شده و فایل پایگاه داده قابل خواندن و نوشتن با فرآیند n8n هستند. اگر پیکربندی Compose واقعی شما از مسیر دیگری یا اتصال اتصال استفاده می‌کند، کپی را مطابق با آن تطبیق دهید. Docker نوشتن مرجع کپی. بازیابی یک پوشه n8n به تنهایی برای استقرارهایی که از پایگاه داده PostgreSQL جداگانه استفاده می کنند کافی نیست.

راز بحرانی

کلید رمزگذاری بخشی از بازیابی است

n8n اعتبارنامه های ذخیره شده را با یک کلید رمزگذاری نمونه رمزگذاری می کند. یک پایگاه داده یا صادر کردن اعتبار رمزگذاری شده بدون کلید منطبق می‌تواند باعث شود که گردش‌های کاری بازیابی شده نتوانند از اعتبار ذخیره‌شده خود استفاده کنند.

اگر N8N_ENCRYPTION_KEY را تنظیم کردید، آن راز دقیق را بازیابی کنید. در غیر این صورت، کلید تولید شده در فایل n8n/config دائمی ذخیره می شود: هنگام پشتیبان گیری یا بازسازی از آن پیکربندی محافظت کنید. کلیدهای بازیابی را به طور ایمن در خارج از VPS ذخیره کنید. در حالت صف، تمام فرآیندهای اصلی و کارگر باید از یک کلید استفاده کنند.

انجام دهیدیک کپی محافظت شده از کلید دقیق استفاده شده توسط تولید را نگه دارید.
انجام دهیدبررسی کنید که محیط بازیابی از آن کلید قبل از آزمایش اعتبار استفاده می کند.
نکنپس از بازسازی سرور به کلیدی که به تازگی تولید شده است تکیه کنید.
نکنکلید را به یک مخزن عمومی اختصاص دهید یا آن را در کنار یک نسخه پشتیبان محافظت نشده ذخیره کنید.

فایل ها و داده های باینری

پشتیبان گیری از پایگاه داده ممکن است تمام وابستگی های گردش کار را پوشش ندهد

داده n8n پایدار

پوشه کاربر n8n واقعی، نه تنها تصویر ظرف را پیدا کرده و حفظ کنید. در یک استقرار Docker معمولی در /home/node/.n8n نصب می شود. خارج از Docker پیش فرض ~/.n8n است. اگر N8N_USER_FOLDER پیکربندی شده باشد، n8n n8n را در داخل دایرکتوری والد مشخص شده ایجاد می کند. کلید پیکربندی آن و هر داده SQLite محلی، باینری یا فایل سیستمی را که نصب شما استفاده می‌کند، اضافه کنید.

فایل های گردش کار نصب شده

اگر جریان های کاری دایرکتوری های نصب شده روی میزبان را می خوانند یا می نویسند، آن دایرکتوری ها را جداگانه پشتیبان گیری کنید. بازیابی n8n بدون آنها می تواند جریان های کاری معتبر را از بین ببرد.

داده های باینری

حالت ذخیره سازی را شناسایی کنید و هر وابستگی خارجی را بازیابی کنید. داده‌های باینری یا اجرایی مبتنی بر سیستم فایل ممکن است در n8n. یا یک فهرست سفارشی زندگی کنند. S3/Azure Blob یا سایر حافظه های خارجی پیکربندی شده نیاز به کپی و تنظیمات دسترسی قابل بازیابی خود دارند. یک پایگاه داده به تنهایی نمی تواند جایگزین آن فایل ها شود.

گره های جامعه

بسته ها و نسخه های جامعه را ضبط کنید و از هر دایرکتوری گره سفارشی اضافی که از طریق N8N_CUSTOM_EXTENSIONS پیکربندی شده اند نسخه پشتیبان تهیه کنید. آن دایرکتوری ها می توانند خارج از .n8n; بازیابی پایگاه داده و پوشه کاربر به تنهایی ممکن است همچنان گردش کار گره سفارشی را غیرقابل استفاده بگذارد.

استراتژی خارج از سرور

یک نسخه پشتیبان در همان VPS فقط یک کپی محلی است

کپی محلیمفید برای بازگشت سریع، اما در برابر از دست دادن سرور، خرابی دیسک و اشتباهات مخرب آسیب پذیر است.
کپی خارج از سرورحداقل یک نسخه پشتیبان را مستقل از VPS تولید در فضای ذخیره سازی نگه دارید.
نسخه های نسخه شدهچندین نقطه بازیابی را حفظ کنید تا خرابی یا تغییر بد تنها نسخه پشتیبان قابل استفاده را بازنویسی نکند.
کنترل دسترسیپشتیبان‌گیری می‌تواند شامل اعتبار، منطق گردش کار و داده‌های تجاری حساس باشد. آنها را به طور مناسب رمزگذاری و محدود کنید.
نظارتهنگامی که پشتیبان‌گیری‌های برنامه‌ریزی‌شده با شکست مواجه می‌شوند یا تولید نقاط بازیابی جدید متوقف می‌شوند، هشدار دهید.

برنامه را قابل اندازه گیری کنید. مُهر زمانی هر پشتیبان‌گیری موفقیت‌آمیز، تکمیل انتقال، اندازه فایل، نسخه پایگاه داده منبع، مکان بازیابی کلید رمزگذاری و آخرین آزمایش بازیابی موفق را ثبت کنید. هشدار در مورد فایل های مفقود، ناموفق یا خالی غیرمنتظره. آرشیوهای پشتیبان را قبل از ارسال VPS رمزگذاری کنید و دسترسی به اسرار بازیابی را محدود کنید. چندین نقطه بازیابی با تاریخ از کشف فساد فقط پس از بازنویسی آخرین نسخه سالم توسط جدیدترین نسخه محافظت می کند.

به عنوان مثال، اگر می توانید حداکثر شش ساعت تغییرات از دست رفته را تحمل کنید، یک برنامه پشتیبان گیری موفق شش ساعته یک نقطه شروع است، نه تضمین: کارهای ناموفق و تکرار تاخیر در خارج از سرور می تواند ضرر واقعی را افزایش دهد. به جای اینکه یک خط مشی جهانی 7-day یا 30-day را در نظر بگیرید، حفظ و بازیابی آهنگ را بر اساس نیازهای RPO/RTO و داده های خود تنظیم کنید.

بازیابی سفارش

در یک توالی کنترل شده ریکاوری کنید

1 · آماده کنیدارائه یک سرور سازگار، پایگاه داده و محیط کانتینر/زمان اجرا.
2 · بازیابی اسرارکلید رمزگذاری اصلی n8n و اسرار استقرار مورد نیاز را به صورت ایمن پیکربندی کنید.
3 · بازیابی پایگاه دادهPostgreSQL یا SQLite را بازیابی کنید و بررسی کنید که n8n می تواند به داده های مورد انتظار متصل شود.
4 · بازیابی فایل هادایرکتوری های پایدار، داده های باینری و دارایی های گردش کار نصب شده را بازیابی کنید.
5 · شروع n8nبرنامه را با نام میزبان، پایگاه داده و پیکربندی محیط مورد انتظار بیاورید.
6 · اعتبارسنجیبارگیری کاربران، گردش‌های کاری و اعتبارنامه‌ها را تأیید کنید، سپس گردش‌های کاری نماینده و مسیرهای webhook را اجرا کنید.

PostgreSQL مثال بازیابی فاجعه: روی یک هدف بازیابی تمیز و جدا که قبلاً نقش پایگاه داده صحیح و خالی است n8n پایگاه داده، شروع کنید فقط PostgreSQL. قبل از وارد کردن، صبر کنید تا سالم باشد: docker compose up -d در حالی که PostgreSQL هنوز در حال مقداردهی اولیه است، به تنهایی می تواند برگردد، بنابراین موارد زیر را دنبال کنید pg_restore می تواند شکست بخورد. مثال استفاده می کند --wait در نصب Compose مدرن و به طور مستقل بررسی می کند pg_isready. یک بررسی سلامت PostgreSQL مناسب برای انتظار قابل اعتماد پیکربندی کنید، یا قبل از حرکت به طور صریح آمادگی را تأیید کنید. این دستور را به یک پایگاه داده تولید پر شده نشان ندهید یا n8n را قبل از پایگاه داده و تطبیق آن شروع نکنید .n8n کلید/داده ها بازیابی می شوند.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

مقصد باید دارای یک نسخه PostgreSQL، امتیازات نقش، برنامه های افزودنی و پیکربندی اصلی n8n باشد. بازیابی کنید .n8n با استفاده از مکانیسم پشتیبان خود، با حفظ مالکیت و مجوزها، به ولوم دائمی صحیح آن یا باند متصل کنید. فایل‌های باینری خارجی، پسوندهای سفارشی، پیکربندی Compose و Secrets را بازیابی کنید، سپس n8n را در یک نسخه سازگار شروع کنید و گزارش‌های آن را بررسی کنید. بازیابی پایگاه داده به تنهایی کلید را بازیابی نمی کند: استقرار PostgreSQL کلید را در داخل نگه می دارد .n8n/config مگر اینکه به صراحت پیکربندی کرده باشید N8N_ENCRYPTION_KEY. مرجع pg_restore · n8n دنباله بازیابی نمونه کامل.

دریل بازیابی تایید شده: SQLite و PostgreSQL

محیط تست: n8n 2.42.5 در ظروف Docker ایزوله روی یک GitHub یک بار مصرف Actions runner، با استفاده از یک گردش کار مصنوعی دو گره. این چک ها ادامه یافت 8 اکتبر 2026، روی سرور n8n مشتری یا تولیدی نیست.

SQLite: گذریک گردش کار آزمایشی را وارد کرد، آن را صادر کرد، همه نویسندگان را متوقف کرد، ماندگاری با پشتیبانی SQLite را بایگانی کرد .n8n پوشه و کلید رمزگذاری تولید شده آن، به یک حجم تمیز بازیابی شد، n8n را شروع کرد، سپس دوباره صادر شد و گردش کار بازیابی شده را اجرا کرد.
PostgreSQL: گذرهمان گردش کار آزمایشی را وارد کرد، یک قالب سفارشی ایجاد و بازرسی کرد pg_dump، آن را با استفاده از آن بازیابی کرد pg_restore در پایگاه داده PostgreSQL خالی جدید، جداگانه را بازیابی کرد .n8n پوشه، سپس دوباره صادر و گردش کار بازیابی شده را اجرا کرد.
آنچه PASS ایجاد می کندمسیرهای پشتیبان آزمایش شده این گردش کار، دو گره و اتصالات آن را حفظ کرده و پس از بازیابی اجازه اجرا را می دهند. اینها تست های دود عملکردی قابل تکرار هستند، نه معیارهای بار کاری.
چیزی که آزمایش نشدرمزگشایی و احراز هویت اعتبارنامه های واقعی، وبکهک های تولید، کارگران حالت صف و Redis، ذخیره سازی باینری S3/Azure، گره های سفارشی، دسترسی کاربر/پروژه یا بازیابی یک نمونه تولید زنده. برای هر وابستگی که واقعاً استفاده می کنید یک مته جداگانه اجرا کنید.

نحوه تکثیر: از یک نصب n8n یکبار مصرف استفاده کنید، یک گردش کار دو گره بی ضرر ایجاد کنید، پایگاه داده قابل اجرا به همراه پشتیبان گیری پوشه دائمی را انجام دهید، به حجم یا پایگاه داده تمیز بازگردانید، سپس گره ها، اتصالات و اجرای واقعی گردش کار بازیابی شده را تأیید کنید. در سیستم تولید، قبل از اینکه بازیابی فاجعه را اثبات شده اعلام کنید، اعتبار رمزگذاری شده، وب هوک ها و فایل های خارجی را نیز بررسی کنید.

بازیابی چک لیست پذیرش مته: استفاده از یک دامنه/محیط ایزوله؛ بررسی کنید که کاربران و جریان‌های کاری موجود باشند، یکی از اعتبارنامه‌های رمزگذاری‌شده موجود بدون ورود مجدد احراز هویت می‌شود، یک وب هوک تولیدی، گردش کار بازیابی شده مورد نظر را فراخوانی می‌کند، فایل‌های نصب‌شده و پیوست‌های باینری قابل خواندن باقی می‌مانند، و ادغام‌ها با گره‌های جامعه مورد نیاز بارگیری می‌شوند. سن پشتیبان‌گیری، زمان خرابی اندازه‌گیری شده و دسترسی خارج از سرور را تأیید کنید. اگر هر بررسی ضروری ناموفق بود، آن نقطه بازیابی را علامت بزنید تایید نشده به جای گزارش نسخه پشتیبان به عنوان کامل.

CLI محدودیت های پشتیبان گیری

دقیقا بدانید که چه جریان کاری و صادرات اعتباری را بازیابی نمی کند

CLI صادرات یک نسخه پشتیبان کامل نیست

گردش کار و صدور پشتیبان اعتبارنامه شامل کاربران و نقش‌ها، سابقه اجرا و گزارش‌ها، متغیرها یا تنظیمات نمونه مانند کلید رمزگذاری نمی‌شود.

بازیابی نمونه تازه نیاز به مالک دارد

در یک نمونه تمیز، قبل از وارد کردن اعتبارنامه، تنظیمات مالک را کامل کنید. بازیابی های چند کاربره یا پروژه نیز ممکن است به تخصیص صحیح کاربر یا پروژه نیاز داشته باشند.

شناسه های وارد شده می توانند موارد موجود را بازنویسی کنند

گردش کار و صادرات اعتبار شناسه اصلی خود را حفظ می کند. وارد کردن به نمونه‌ای که قبلاً دارای شناسه‌های مشابه است می‌تواند جایگزین آن موارد موجود شود.

گردش‌های کاری وارداتی را عمداً منتشر کنید

CLI واردات معمولاً گردش کار را غیرفعال می کند. در n8n 2.x، وضعیت منتشر شده هر گردش کار وارد شده را بررسی کنید و فقط گردش‌های کاری را که می‌خواهید اجرا کنید منتشر کنید. سرور خود میزبان CLI همچنین از n8n publish:workflow --id=YOUR_WORKFLOW_ID پشتیبانی می کند. هنگامی که n8n در حال اجرا است، تغییرات وضعیت انتشار/لغو انتشار سرور CLI تنها پس از راه اندازی مجدد n8n اعمال می شود. قبل از تأیید راه‌اندازهای برنامه‌ریزی‌شده و وبک‌قلک‌های تولید یا تغییر ترافیک، راه‌اندازی مجدد کنید.

نمونه صادرات انبوه برای Docker نوشتن: اگر سرویس n8n شما نامگذاری شده باشد n8n، می توانید پشتیبان گیری های رسمی CLI را در زیر اجرا کنید. مسیر خروجی عمدا در داخل ثابت نصب شده آن است .n8n دایرکتوری، زیرا دایرکتوری های دلخواه درون یک کانتینر ممکن است هنگام ایجاد مجدد محو شوند. تأیید کنید که دایرکتوری توسط کاربر ظرف n8n قابل نوشتن است. گردش کار و اعتبار JSON را حفظ کنید دایرکتوری های جداگانه—n8n یک مشکل واردات را هنگامی که هر دو نوع دایرکتوری مشترک دارند، مستند می کند.

n8n 2.x پیش نویس در مقابل نسخه پشتیبان منتشر شده: یک عادی --backup صادرات گردش کار پیش نویس های جاری را ثبت می کند. اینها می توانند با نسخه های منتشر شده در تولید متفاوت باشند. برای حفظ نسخه منتشر شده واقعی یک گردش کار خاص، آن را به طور جداگانه با استفاده از آن صادر کنید docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json، پس از اطمینان از وجود پوشه خروجی و قابل نوشتن بودن آن. CLI همچنین می تواند یک نسخه تاریخی را با استفاده از آن صادر کند --version=VERSION_ID. این عکس‌ها را در کنار نسخه پشتیبان کامل، خارج از سرور نگه دارید. فرض نکنید پیش نویس JSON وضعیت منتشر شده زنده را ثبت می کند.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

کپی شده ~/n8n-recovery/cli دایرکتوری هنوز در VPS است تا زمانی که آن را به یک مکان پشتیبان امن و مستقل منتقل کنید. صدور اعتبارنامه به طور پیش فرض رمزگذاری شده است و در هنگام واردات به کلید رمزگذاری منطبق نیاز دارد. از مصرف خودداری کنید --decrypted به جز یک مهاجرت کاملاً کنترل شده: اسرار را در متن ساده می نویسد. هرگز صادراتی حاوی منطق گردش کار حساس یا اعتبار را به یک مخزن GitHub عمومی انجام ندهید. برخی از قالب‌های GitHub شخص ثالث برای پشتیبان‌گیری اعتبار، اسرار رمزگشایی شده را عمدا صادر می‌کنند. یک مخزن خصوصی یک محدودیت دسترسی است نه رمزگذاری. تنظیمات واقعی صادرات و مجوزهای ذخیره سازی هر الگو را بررسی کنید، اسرار را قبل از انتقال خارج از سرور رمزگذاری کنید، و هر اعتباری را که از طریق یک آپلود متن ساده ناخواسته در معرض دید قرار گرفته است بچرخانید.

نمونه واردات انبوه: در یک هدف تمیز، نصب مالک را به پایان برسانید، کلید رمزگذاری اصلی را ارائه دهید و اطمینان حاصل کنید که فایل های پشتیبان ذخیره شده در آن بازیابی VPS موجود هستند. زیر پوشه مقصد را ایجاد می کند و آن را کپی می کند workflows/ و credentials/ پوشه های فرعی از میزبان به ظرف n8n. اگر طرح‌بندی حجم Docker شما متفاوت است، مسیرها را تطبیق دهید:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

مالکیت فایل و دسترسی کاربر ظرف n8n را بررسی کنید. از یک نمونه تولید پرجمعیت بدون بازگشت تأیید شده وارد نکنید: گردش کار و شناسه های اعتبار می توانند ورودی های موجود را بازنویسی کنند. سپس اجرا کنید:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

شناسه‌های وارد شده می‌توانند جایگزین گردش‌های کاری یا اعتبارنامه‌های موجود شوند. از یک نمونه آزمایشی ایزوله برای اجراهای خشک استفاده کنید و اعتبارنامه ها و وضعیت های فعال سازی/انتشار را بررسی کنید. در n8n 2.x، بازیابی پیش‌نویس JSON به خودی خود ثابت نمی‌کند که گردش کار منتشر شده است و می‌تواند محرک‌های زمان‌بندی شده را اجرا کند. ایمنی واردات: در یک نمونه n8n غیر چند اصلی، تریگرهای cron قبلا فعال می توانند پس از وارد کردن CLI تا زمانی که نمونه راه اندازی مجدد شود، به کار خود ادامه دهند. محرک های تولید را متوقف یا جدا کنید و قبل از فعال کردن کارهای بازیابی شده، n8n را مجدداً راه اندازی کنید. بررسی کنید که اجرای تکراری وجود ندارد. CLI صادرات انجام دهد نه شامل کاربران اصلی، گزارش‌های اجرایی، متغیرهای نمونه یا کلید رمزگذاری باشد. --backup مجموعه ها --all --pretty --separate، نه "نمونه کامل". منابع: راهنمای رسمی نسخه پشتیبان/بازیابی n8n و مرجع فرمان n8n CLI.

بازیابی انبوه از GitHub یا الگوهای Google Drive: این یک جایگزین فقط برای گردش کار JSON است، نه برای نمونه پایگاه داده، کاربران، مقادیر اعتبار رمزگذاری شده یا کلید رمزگذاری. قبل از اجرای یک الگوی مبتنی بر API، n8n API و مجوزهای ذخیره سازی، نسخه پشتیبان انتخاب شده و نمونه هدف، اینکه آیا شناسه های منطبق را به روز می کند و جریان های کاری حذف شده را دوباره ایجاد می کند و اینکه با انتشار گردش کار چه می کند، بررسی کنید. همه الگوها شناسه گم شده از هدف را دوباره ایجاد نمی کنند. قبل از تکیه بر بازیابی خودکار، آن سناریو را به صورت مجزا آزمایش کنید.

سؤالات متداول

n8n پشتیبان گیری و بازیابی: سوالات رایج

آیا صادرات گردش کار برای پشتیبان گیری از n8n کافی است؟

خیر. صادرات گردش کار کپی‌های منطقی مفیدی هستند، اما بازیابی کامل می‌تواند به اعتبار، کلید رمزگذاری منطبق، وضعیت پایگاه داده، فایل‌های پایدار و ذخیره‌سازی داده‌های باینری نیز نیاز داشته باشد.

آیا در صورت داشتن پایگاه داده به کلید رمزگذاری n8n نیاز دارم؟

بله، اگر به اعتبارنامه های رمزگذاری شده ذخیره شده در آن پایگاه داده نیاز دارید تا قابل استفاده باقی بمانند. کلید اصلی را ایمن نگه دارید.

آیا باید از PostgreSQL نسخه پشتیبان تهیه کنم یا گردش کار و اعتبارنامه را صادر کنم؟

برای بازیابی فاجعه، از پایگاه داده و کلید رمزگذاری محافظت کنید. صادرات منطقی به عنوان یک لایه مهاجرت اضافی و بازیابی انتخابی به جای جایگزینی برای هر بخش از نمونه ارزشمند است.

آیا یک عکس فوری VPS می تواند تنها پشتیبان من باشد؟

بهتر است به عنوان یک لایه بازیابی رفتار شود. یک پشتیبان مستقل خارج از سرور داشته باشید تا خرابی ارائه دهنده، حساب، سرور یا عکس فوری همه نقاط بازیابی را به یکباره حذف نکند.

چگونه بفهمم پشتیبان من کار می کند؟

آن را در یک محیط آزمایشی تمیز بازیابی کنید، اعتبارنامه‌ها را رمزگشایی کنید و گردش‌های کاری نماینده را اجرا کنید. یک کار پشتیبان موفق به تنهایی قابلیت بازیابی را ثابت نمی کند.

آیا GitHub یا پشتیبان‌گیری از گردش کار Google Drive شامل اسرار اطلاعات کاربری ذخیره شده است؟

پشتیبان‌گیری‌های JSON فقط در جریان کار شامل مقادیر مخفی مدیریت شده توسط فروشگاه اعتبار n8n یا کلید رمزگذاری نمونه نمی‌شوند. با این حال، JSON صادر شده می‌تواند نام‌های اعتبار و شناسه‌ها و اسرار تایپ شده مستقیماً در پارامترهای گره، مانند سرصفحه‌های احراز هویت را آشکار کند. قبل از آپلود یا اشتراک گذاری، JSON صادر شده را بازرسی و محافظت کنید. برای بازیابی کامل، از پایگاه داده و کلید اصلی نسخه پشتیبان تهیه کنید یا از صادرات CLI اعتبار رمزگذاری شده پشتیبانی شده با بازیابی آزمایش شده استفاده کنید. یک الگوی GitHub یا Google Drive فقط برای گردش کار، بازیابی کامل بلایا نیست.

اهداف بازیابی

RPO و RTO را قبل از حادثه تعریف کنید

RPO حداکثر ضرر قابل تحمل تغییرات اخیر است. آن را از جدیدترین نقطه بازیابی قابل استفاده و ذخیره شده مستقل اندازه گیری کنید. یک کار شش ساعته برنامه ریزی شده در صورت عدم موفقیت صادرات یا انتقال، RPO شش ساعته ایجاد نمی کند. RTO حداکثر خاموشی قابل تحمل است. آن را در یک تمرین بازیابی تمیز اندازه‌گیری کنید، از جمله بازیابی اسرار، بازیابی فایل‌های خارجی، بررسی مجدد اعتبارنامه‌ها و انتشار گردش‌های کاری بازیابی شده – نه فقط راه‌اندازی یک ظرف.

کلید بازیابی

قبل از بازسازی، کلید رمزگذاری اصلی را پیدا کنید

اگر مجموعه تولید N8N_ENCRYPTION_KEY، آن راز دقیق محیط را حفظ کنید. اگر اینطور نبود، کلید تولید شده را در n8n/config ثابت اصلی حفظ کنید. قبل از وارد کردن اعتبارنامه های رمزگذاری شده، بررسی کنید که نمونه بازیابی شده واقعاً از کدام منبع استفاده می کند. یک کلید تازه تولید شده نمی تواند اعتبارنامه ها را از پایگاه داده قدیمی رمزگشایی کند.
