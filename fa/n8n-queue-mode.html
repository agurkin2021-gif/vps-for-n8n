مقیاس‌پذیری

Queue Mode در n8n

حالت صف اجرای گردش‌کار را از فرآیند n8n اصلی جدا می‌کند. نمونه اصلی محرک‌ها را دریافت می‌کند و اجراها را ایجاد می‌کند، Redis صف را هماهنگ می‌کند، Workerها کارها را اجرا می‌کنند، و PostgreSQL گردش‌کار مشترک و داده‌های اجرا را ذخیره می‌کند.

تصمیم سریع

آیا واقعاً به Queue Mode نیاز دارید؟

زمانی که در حالت عادی بمانید

یک نمونه واحد به راحتی اجرای اوج را انجام می دهد و CPU، RAM و تأخیر اجرا ثابت می مانند. حالت صف اجزایی را اضافه می‌کند که شما هنوز به آن نیاز ندارید.

حالت صف را در نظر بگیرید

اجرای موازی پایدار باعث ایجاد مشاجره می‌شود، تأخیر اجرا تحت بار افزایش می یابد، یا باید ظرفیت اجرا را با اجرای چندین Worker اضافه کنید.

ابتدا مقیاس عمودی زمانی که

گلوگاه به سادگی CPU یا RAM ناکافی است و یک نمونه بزرگتر هنوز هم می‌تواند حجم کار را به خوبی برآورده کند.

قبل از تغییر معماری اندازه گیری کنید

از حداکثر همزمانی، CPU، RAM، مدت زمان اجرا، عمق صف و فشار پایگاه‌داده برای توجیه حرکت استفاده کنید.

معماری

Queue Mode در n8n چگونه کار می‌کند

1 · اصلیتایمرها، وب‌هوک‌ها و درخواست های گردش‌کار را دریافت می‌کند و به جای اینکه خود اجرای تولید را انجام دهد، یک اجرا ایجاد می‌کند.
2 · Redisبه عنوان واسطه پیام عمل می‌کند. پیام‌های اجرایی در انتظار را نگه می‌دارد تا Worker بعدی بتواند شغلی را درخواست کند.
3 · Workerشناسه اجرا را دریافت می‌کند، داده‌های گردش‌کار را از پایگاه‌داده مشترک بارگیری می‌کند، گردش‌کار را اجرا می‌کند و نتیجه را باز می نویسد.
4 · PostgreSQLگردش‌کار مداوم و داده‌های اجرایی مشترک را ارائه می دهد. حالت صف توزیع شده بیش از SQLite پشتیبانی نمی‌شود.

الزامات اصلی

هر استقرار Queue Mode به چه چیزهایی نیاز دارد

Redis

تمام فرآیندهای اصلی و Worker نیاز به دسترسی قابل اعتماد به سرویس Redis مورد استفاده برای هماهنگی صف دارند.

PostgreSQL

اصلی و Workerها باید پایگاه‌داده را به اشتراک بگذارند. حالت صف یک معماری توزیع شده است و نباید حول SQLite طراحی شود.

مطابق با پیکربندی n8n

Main و Workerها باید حالت صف را اجرا کنند و پیکربندی مورد نیاز برای دسترسی به Redis، PostgreSQL و اعتبارنامه های رمزگذاری شده را به اشتراک بگذارند.

ظرفیت Workerی

Workerها برای گردش‌کاری که اجرا می کنند به CPU و RAM کافی نیاز دارند. افزودن فرآیندها هزینه منابع هر اجرا را حذف نمی‌کند.

حالت صف را در یک پشته خودمیزبانی شده موجود فعال کنید. ابتدا تأیید کنید که سرویس اصلی n8n و هر Worker می‌تواند به پایگاه‌داده PostgreSQL و Redis از طریق یک شبکه خصوصی دسترسی پیدا کند. تنظیم کنید EXECUTIONS_MODE=queue هم روی اصلی و هم Workerها و هم عرضه QUEUE_BULL_REDIS_HOST=redis و QUEUE_BULL_REDIS_PORT=6379 چه زمانی redis نام سرویس Compose واقعی شما است. استفاده کنید DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres و تطبیق DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER و DB_POSTGRESDB_PASSWORD در هر فرآیند؛ نام خدمات نمونه را با نام خود جایگزین کنید. دقیق موجود را ارائه دهید N8N_ENCRYPTION_KEY به همه آن‌ها هرگز پورت های میزبان Redis یا PostgreSQL را صرفاً برای اتصال کانتینرها در یک شبکه Compose منتشر نکنید.

یک اجرا کننده راه اندازی کنید، نه ویرایشگر دوم. با استفاده از همان نسخه تصویر n8n پین شده و تنظیمات مشترک به عنوان اصلی، یک سرویس Worker n8n اضافه کنید، اما آن را با worker فرمان اگر نام آن سرویس را گذاشتید n8n-worker، آن را با آن شروع کنید docker compose up -d n8n-worker. پس از تایید اجرای واقعی روی یک Worker، می توانید استفاده کنید docker compose up -d --scale n8n-worker=2 برای راه اندازی Worker دوم از آن سرویس. اینها اضافاتی به یک هستند موجود به درستی پیکربندی شده است نوشتن پشته، نه یک فایل نصبی مستقل. حجم های موجود، پروکسی HTTPS، اسرار و نسخه های پشتیبان خود را نگه دارید.

حالت صف نوشتن قطعه برای یک پشته موجود. مثال زیر را با فعلی خود ادغام کنید compose.yaml; آن است نه استقرار کامل مستقل این فرض را بر این می‌گذارد که شما قبلاً خصوصی و مداوم دارید postgres و n8n خدمات، موجود N8N_VERSION پین در محیط خود و خود محافظت می‌شود POSTGRES_PASSWORD و اصلی N8N_ENCRYPTION_KEY. نام، جلد، پایگاه‌داده و نسخه n8n آن را با پروژه موجود مطابقت دهید. تنظیمات Redis حالت صف را اضافه کنید و EXECUTIONS_MODE=queue به سرویس اصلی موجود نیز همانطور که در بالا توضیح داده شد.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

هیچ پورت میزبان برای Redis یا Worker در این قطعه منتشر نشده است. Redis ماندگاری فقط پیوست یک لایه بازیابی اضافی است، نه جایگزینی برای پشتیبان‌گیری خارج از سرور. HTTPS موجود و پیکربندی احراز هویت را بدون تغییر نگه دارید. برای گره‌های کدی که به اجراکننده‌های وظیفه خارجی نیاز دارند، فرآیندهای runner را برای استقرار Worker خود به‌طور جداگانه پیکربندی کنید. حالت صف به خودی خود جایگزین task runner ها نمی‌شود.

تبدیل یک نمونه SQLite موجود؟ به سادگی تغییر ندهید DB_TYPE و در مقابل یک پایگاه‌داده خالی PostgreSQL شروع کنید: انجام این کار گردش‌کارها و اعتبارنامه های قدیمی را منتقل نمی‌کند. قبل از هر برش، از پایگاه‌داده منبع، پشتیبان تهیه کنید، مداوم .n8n دایرکتوری و کلید رمزگذاری اصلی؛ از یک روش صادرات/واردات یا مهاجرت n8n پشتیبانی شده استفاده کنید، سپس گردش‌کار و اعتبارنامه های رمزگذاری شده را در یک هدف جداگانه تأیید کنید. فایل‌های اصلی را برای بازگردانی نگه دارید و از راهنمای پشتیبان‌گیری و بازیابی لینک زیر برای آماده‌سازی بازیابی استفاده کنید. هرگز حذف نکنید database.sqlite به عنوان میانبر

کنکور Workerی

Workerها هم بر اساس تعداد و هم بر اساس تعداد اجرای هم‌زمان در هر Worker مقیاس می‌شوند

هر Worker می‌تواند چندین کار را به‌طور همزمان پردازش کند. همزمانی Worker پیش فرض فعلی n8n 10 است و مستندات آن همزمانی 5 یا بالاتر را توصیه می‌کند. همزمانی بسیار کم همراه با بسیاری از Workerها می‌تواند اتصالات پایگاه‌داده غیر ضروری ایجاد کند و استخر اتصال پایگاه‌داده را خسته کند.

افزایش همزمانی زمانی که

یک Worker CPU و RAM اضافی دارد و گردش‌کار بیشتر در انتظار خدمات خارجی است تا محاسبات یا حافظه اشباع.

وقتی Workerها را اضافه کنید

یک فرآیند Worker تبدیل به یک گلوگاه می‌شود و پایگاه‌داده، Redis و زیرساخت ظرفیت اجرای موازی بیشتری دارند.

زمانی که همزمانی را کاهش دهید

گردش‌های کاری فردی دارای حافظه سنگین یا CPU سنگین هستند و کارهای موازی باعث مشاجره، فشار OOM یا زمان اجرای ناپایدار می‌شوند.

تماشا PostgreSQL

Workerها بیشتر و همزمانی بیشتر فعالیت پایگاه‌داده را افزایش می دهد. مقیاس‌پذیری ظرفیت اجرای بدون ظرفیت پایگاه‌داده می‌تواند گلوگاه را به جای حذف آن حرکت دهد.

بدانید کدام محدودیت همزمانی واقعا اعمال می‌شود. یک Worker می‌تواند شروع به استفاده کند n8n worker --concurrency=5، یا دستور worker معادل در سرویس Compose شما. اگر N8N_CONCURRENCY_PRODUCTION_LIMIT به صراحت روی مقداری غیر از -1، این تنظیم در حالت صف اولویت دارد. در غیر این صورت n8n از Worker استفاده می‌کند --concurrency مقدار یا پیش فرض آن 10. تعداد Workerها را در یک پیش فرض اسمی ضرب نکنید و آن را توان عملیاتی تضمین شده بنامید: ظرفیت واقعی به مدت زمان کار، CPU، حافظه، API های خارجی و اتصالات PostgreSQL بستگی دارد.

WEBHOOKS

Queue Mode می‌تواند کمی تأخیر در انتقال اجرای کار اضافه کند

فرآیند main یا webhook درخواست HTTP را دریافت می‌کند، اما یک Worker اجرای گردش‌کار را انجام می دهد. آن انتقال از طریق Redis مقداری سربار اضافه می‌کند. برای وب‌قلاب‌های حساس به تأخیر، به جای اینکه فرض کنید تعداد بیشتری از Workerها به‌طور خودکار هر درخواست را سریع‌تر انجام می‌دهند، زمان پاسخ‌دهی سرتاسر را اندازه‌گیری کنید.

دریافت کنیدفرآیند اصلی/وب‌هوک درخواست را می پذیرد.
صفاجرا به Redis داده می‌شود.
اجرا کنیدیک Worker در دسترس گردش‌کار را اجرا می‌کند.
پاسخ دهیدنتیجه در صورت لزوم از طریق مسیر صف ارسال می‌شود.

ترافیک وب‌هوک را به فرآیند درست هدایت کنید. با اختصاص n8n webhook پردازنده های پشت پراکسی معکوس یا متعادل کننده بار، مسیرهای تولید را مسیر می دهند /webhook/* و /webhook-waiting/* به پردازنده های وب‌هوک؛ نگه دارید /webhook-test/*، ویرایشگر و درخواست های API در اصلی. اصل را در استخر تولید توازن بار webhook قرار ندهید مگر اینکه عمداً آن حجم کار اضافه شده را بپذیرید. الف به وب‌هوک پاسخ دهید گردش‌کار ممکن است مشتری را منتظر بماند تا Worker تمام شود و پاسخ خود را برگرداند، بنابراین حالت صف وعده پاسخ‌های فوری HTTP یا مهلت زمانی صفر نیست. قبل از تغییر ترافیک، رفتار پاسخ به تماس و پاسخ خارجی واقعی را آزمایش کنید.

داده‌های باینری

ذخیره‌سازی مشترک را نادیده نگیرید

محدودیت سیستم فایل

حالت صف از ذخیره‌سازی داده‌های باینری سیستم فایل به عنوان مدل پایداری مشترک برای Workerها توزیع شده پشتیبانی نمی‌کند.

ذخیره‌سازی باینری خارجی

هنگامی که جریان کار باید داده‌های باینری را در بین Workerها توزیع شده حفظ کند، از یک طرح ذخیره‌سازی استفاده کنید که هر نمونه مورد نیاز بتواند به آن دسترسی داشته باشد، مانند ذخیره‌سازی اشیاء خارجی پشتیبانی شده.

پاسخ های وب‌هوک بزرگ

پاسخ های وب‌هوک از سوی Workerها به سمت فرآیند دریافت باز می گردد. بدنه های پاسخ بزرگ می توانند فشار حافظه Redis را افزایش دهند و به پیکربندی ذخیره‌سازی پاسخ عمدی نیاز دارند.

قبل از توزیع Workerها برنامه ریزی کنید

حجم کاری که به شدت به فایل های محلی بستگی دارد باید برای پایداری مشترک دوباره طراحی شود قبل از اینکه Workerها در ماشین ها پخش شوند.

مرز پاسخ وب‌هوک بزرگ. اسناد n8n فعلی می دهد N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX پیش فرض از 64 MiB برای پاسخ یک Worker از طریق صف ارسال می‌شود. Redis می‌تواند چندین نسخه را در پرواز نگه دارد، بنابراین بودجه تقریباً 1.5 برابر اندازه پاسخ در حافظه Redis در هر پاسخ همزمان بزرگ است. بدون بارگذاری، یک پاسخ بزرگ به جای اینکه با اضافه کردن Workerها به‌طور جادویی سریعتر شود، شکست می خورد.

محدودیت نسخه و مجوز از n8n 2.34.0، Workerها می توانند استفاده کنند N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true برای بارگذاری بدنه‌های پاسخ‌دهی بزرگ وب‌هوک به حافظه باینری مشترک قابل خواندن، اما ابتدا ارتقا دهید هر پردازنده اصلی و وب‌هوک به 2.34.0 یا بالاتر. انتخاب شده N8N_DEFAULT_BINARY_DATA_MODE باید در واقع داده ها را ذخیره کند و توسط هر فرآیند شرکت کننده قابل خواندن باشد. S3 خارجی و ذخیره‌سازی باینری Azure به یک میزبان معتبر خود نیاز دارند کسب و کار یا شرکت مجوز؛ فرض نکنید که نسخه انجمن می‌تواند آن‌ها را فعال کند. را database حالت باینری می‌تواند یک پاسخ بزرگ را بدون حافظه خارجی پولی بارگیری کند، اما نمونه اصلی کل بدنه ذخیره‌شده را در حافظه بارگیری می‌کند و ذخیره‌سازی پایگاه‌داده محدودیت اندازه فایل خاص خود را دارد. برای تخلیه پاسخ بدن به‌طور خاص، n8n همچنین یک اشتراک گذاری شده را توصیف می‌کند filesystem گزینه زمانی که هر نمونه یک دیسک را نصب می‌کند، اما به صراحت آن ترتیب را توصیه نمی‌کند. این مسیر تخلیه ویژه را با پشتیبانی از داده‌های باینری پایدار مبتنی بر سیستم فایل در استقرار حالت صف توزیع شده اشتباه نگیرید. قبل از فعال کردن بارگذاری، نسخه، نسخه و پیکربندی فضای ذخیره‌سازی خود را بررسی کنید.

مانیتورینگ

تشخیص دهید Queue Mode واقعاً به شما کمک می‌کند یا نه

عمق صف

صفی که سریعتر از تخلیه Workerها رشد می‌کند نشان دهنده ظرفیت اجرای ناکافی یا تنگنای پایین دست است.

Worker CPU و RAM

اندازه گیری اشباع و حداکثر حافظه به ازای هر Worker. Workerها بیکار با صف رو به رشد به محدودیت دیگری اشاره می کنند.

تأخیر اجرا

نه تنها زمان اجرا گردش‌کار، تأخیر بین اجرا و شروع واقعی آن را پیگیری کنید.

بررسی های سلامت

نقاط پایانی سلامت Workerها می توانند گزارش دهند که آیا Worker زنده است و آیا پایگاه‌داده و اتصالات Redis آن آماده است یا خیر.

بررسی اجرا بر روی یک Worker، نه فقط یک ظرف سبز. با یک پشته Compose که به درستی پیکربندی شده است، بررسی کنید docker compose ps و docker compose logs --tail=100 n8n-worker (در صورت متفاوت بودن نام سرویس را جایگزین کنید). اجرا بی ضرر تولید منتشر شده گردش‌کار با استفاده از یک راه‌انداز برنامه‌ریزی‌شده یا یک وبکهک آزمایشی، سپس اجرای آن را در نمای اجرای n8n با پردازش واقعی Worker در گزارش‌های Worker مطابقت دهید. یک ویرایشگر که با موفقیت باز می‌شود، یک ظرف Redis در حال اجرا یا یک اجرای در صف به تنهایی این کار را انجام می دهد. نه ثابت کند که یک Worker کار را انجام داده است.

وابستگی ها و آمادگی را بررسی کنید. با نام‌های نمونه سرویس پیش‌فرض، docker compose exec -T redis redis-cli ping باید دریافت کند PONG هنگامی که احراز هویت Redis آن را اجازه می دهد، و docker compose exec -T postgres pg_isready -U n8n -d n8n آمادگی PostgreSQL را بررسی می‌کند (مطابق اعتبارنامه و نام خدمات). فعال کردن QUEUE_HEALTH_CHECK_ACTIVE=true روی یک Worker زمانی که به خصوصی آن نیاز دارید /healthz و /healthz/readiness نقاط پایانی؛ نقطه پایانی آمادگی Redis/اتصال پایگاه‌داده را بررسی می‌کند. آن نقاط پایانی Worker را فقط برای نظارت بر آن‌ها در معرض عموم قرار ندهید.

اجرای دستی آزمایش متفاوتی است. به‌طور پیش فرض OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false، بنابراین اجرای دستی یک گردش‌کار در ویرایشگر می‌تواند در حالت اصلی اجرا شود حتی زمانی که حالت صف به درستی پیکربندی شده باشد. آن را تنظیم کنید true فقط در صورتی که قصد دارید اعدام های دستی را برای Workerها ارسال کنید و تغییرات را در یک محیط صحنه سازی بررسی کرده باشید. Workerها حالت صف نیز از اجراکننده‌های وظیفه خارجی n8n متمایز هستند که الزامات پیکربندی جداگانه‌ای برای اجرای گره کد دارند.

مرز در دسترس بودن بالا

Queue Mode اجرای کارها را مقیاس‌پذیر می‌کند، اما فرایند اصلی را به‌طور خودکار High Availability نمی‌کند

کلید رمزگذاری را به اشتراک بگذارید

هر Workerی باید از همان استفاده کند N8N_ENCRYPTION_KEY به عنوان نمونه اصلی تا Workerها بتوانند اعتبارنامه های مورد نیاز اجرای گردش‌کار را رمزگشایی کنند.

نسخه ها را تراز نگه دارید

فرآیندهای اصلی، webhook و worker باید همان نسخه n8n را اجرا کنند. نسخه‌های ترکیبی می‌توانند رفتار ناسازگاری را در طول تغییرات نورد ایجاد کنند.

پردازنده های Webhook یک لایه مقیاس پذیر جداگانه هستند

وقتی حجم وب‌هوک ورودی به گلوگاه تبدیل می‌شود، پردازنده‌های اختصاصی وب‌هوک می‌توانند پشت یک متعادل‌کننده بار بنشینند در حالی که Workerها عملیات اجرا را انجام می‌دهند. این لایه را اضافه نکنید مگر اینکه حجم درخواست اندازه گیری شده آن را توجیه کند.

چند اصلی یک ویژگی متفاوت است

اجرای چندین فرآیند اصلی برای دسترسی بالا مانند حالت صف معمولی نیست. n8n در حال حاضر چند اصلی را به عنوان یک ویژگی Enterprise خودمیزبان با بار اضافی و الزامات جلسه مستند می‌کند.

سؤالات متداول

Queue Mode در n8n: سؤالات متداول

آیا حالت صف n8n به Redis نیاز دارد؟

بله. Redis دلال پیامی است که اعدام های معلق بین نمونه اصلی و Workerها را هماهنگ می‌کند.

آیا حالت صف می‌تواند از SQLite استفاده کند؟

نه برای معماری حالت صف توزیع شده. اصلی و Workerها به دسترسی به پایگاه‌داده مشترک و اسناد n8n PostgreSQL به عنوان پایگاه‌داده برای این تنظیم نیاز دارند.

چند Worker باید اجرا کنم؟

هیچ شمارش جهانی وجود ندارد. از همزمانی اندازه گیری شده و استفاده Worker شروع کنید، سپس ظرفیت را در حین نظارت بر PostgreSQL، Redis، CPU، RAM و عمق صف اضافه کنید.

n8n همزمانی Worker چیست؟

تعداد کارهای است که یک Worker ممکن است به‌طور موازی پردازش کند. پیش‌فرض فعلی 10 است، و n8n به جای ایجاد بسیاری از Workerها با همزمانی کم، همزمانی Workerی 5 یا بالاتر را توصیه می‌کند.

آیا باید حالت صف را روی یک VPS کوچک فعال کنم؟

فقط زمانی که حجم کار آن را توجیه کند. یک استقرار کوچک که به راحتی به عنوان یک نمونه اجرا می‌شود، معمولاً بدون Redis و Workerها مجزا، ساده تر است.
