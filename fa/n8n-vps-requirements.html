آیا n8n حداقل اندازه رسمی برای VPS دارد؟

نه برای هر حجم کاری. نمونه‌های پیش‌نیاز رسمی n8n یک استقرار OEM را توضیح می‌دهند و به صراحت هشدار می‌دهند که الزامات بر اساس حجم کار متفاوت است. این مستندات تضمینی جهانی برای اینکه هر CPU، RAM یا تخصیص دیسک خاص از اتوماسیون‌های تولید پشتیبانی کند نیست.

n8n اشاره می‌کند که یک نمونه غیرفعال ممکن است از حافظه نسبتا کمی استفاده کند، اما یک گره کد، بار باینری بزرگ یا اجرای همزمان می‌تواند تقاضای حافظه را به شدت افزایش دهد. بودجه به‌طور جداگانه برای سیستم عامل، Docker، PostgreSQL و ابزارهای پشتیبان / نظارت.

منابع فنی: پیش نیازهای تصویری n8n و راهنمای رسمی حافظه. چهار سطح بالا بسته‌های منابع واقعی قابل خرید هستند، الزامات رسمی n8n تجویز نشده‌اند.

قبل از ارتقا، اندازه گیری کنید

چگونه تشخیص دهیم که n8n به RAM، CPU یا دیسک بیشتری نیاز دارد

بزرگترین گردش‌کار مورد انتظار خود و یک انفجار همپوشانی واقعی را اجرا کنید، سپس سرور و گزارش های اجرای n8n را بررسی کنید. تعداد گردش های کاری ذخیره شده در ویرایشگر به تنهایی یک معیار ظرفیت مفید نیست.

حافظه / OOM

بررسی کنید docker stats --no-stream و free -h. اگر حافظه تمام شده است، ابتدا JSON یا محموله های باینری را کاهش دهید، مقدار زیادی وارد کنید و از مراحل کد سنگین حافظه خودداری کنید. یک خطای پشته جاوا اسکریپت لزوماً با افزودن vCPU برطرف نمی‌شود.

CPU / همزمانی

اندازه‌گیری کنید که آیا CPU در طول تبدیل‌ها مشغول می‌ماند یا کارها فقط منتظر APIهای خارجی هستند. در حالت معمولی، قبل از مقیاس‌بندی برای Workerها، یک حد تولید همزمان پشتیبانی شده را در نظر بگیرید. افزایش CPU، سرعت API با نرخ خارجی محدود را افزایش نمی‌دهد.

ذخیره‌سازی / پایگاه‌داده

بررسی کنید df -h، اندازه پایگاه‌داده و سابقه اجرای حفظ شده. رشد دیسک و کندی عملیات پایگاه‌داده را تماشا کنید. قبل از پرداخت برای یک دیسک بزرگتر، ذخیره را عمدا تنظیم کنید. کپی های بازیابی را خارج از سرور نگه دارید.

از راهنمای همزمانی n8n و توضیح معیارهای رسمی استفاده کنید. هر تعداد گردش‌کار همزمان که بدون اطلاع از میزان بارگذاری آن‌ها و تأخیر API تبلیغ می‌شود، تنها یک تخمین است.

پایگاه‌داده و ذخیره‌سازی

SQLite، PostgreSQL و داده‌های پایدار

SQLite

SQLite می‌تواند برای استقرار و آزمایش های تک نمونه کوچک مناسب باشد. همانطور که استفاده از تولید و همزمانی رشد می‌کند، انتخاب پایگاه‌داده به جای یک جزئیات نصب به یک محدودیت عملیاتی تبدیل می‌شود.

PostgreSQL

برای یک پشته VPS تولید محور، PostgreSQL پایه پایگاه‌داده قوی تری را فراهم می‌کند. بودجه RAM، CPU و دیسک برای خود پایگاه‌داده و نظارت بر رشد آن.

داده n8n پایدار

با PostgreSQL به عنوان تنها دارایی پایدار رفتار نکنید. دایرکتوری داده n8n را حفظ کنید و از کلید رمزگذاری مورد نیاز برای بازیابی اطلاعات رمزگذاری شده محافظت کنید.

رشد دیسک

تاریخچه اجرا، داده‌های باینری، فایل های پایگاه‌داده و گزارش ها می توانند در طول زمان گسترش یابند. تنظیمات حفظ و پشتیبان‌گیری خارج از سرور مستقیماً بر ظرفیت مورد نیاز تأثیر می گذارد.

ظرفیت دیسک

پیش از سفارش، فضای لازم برای تاریخچه اجرای n8n را برآورد کنید

شروع کنید با اجراهای ذخیره شده در روز × میانگین بایت های ذخیره شده در هر اجرا × روزهای نگهداری. به عنوان مثال، 500 اعدام ها در هر روز × 200 KB هر × 14 روز = 1.4 GB به عنوان مثال داده‌های اجرایی قبل از سربار پایگاه‌داده. این فرض 200 KB گویا است، نه یک معیار n8n.

همچنین دیسک را برای سیستم عامل، لایه های تصویر Docker، فهرست های پایگاه‌داده، فایل های باینری، گزارش های برنامه، ارتقاء و فایل های موقت اختصاص دهید. پشتیبان‌گیری خارج از سرور به ظرفیت خود نیاز دارد. دیسک 10 GB می‌تواند برای یک پشته ناب کار کند اما فضای کمتری برای فایل های حفظ شده نسبت به دیسک 40 یا 80 GB دارد.

n8n هرس اجرای پیش‌فرض را براساس سن (336 ساعت / 14 روز) یا شمارش (10,000 اعدام)، با استثناء مستند می‌کند. تنظیمات واقعی خود را بررسی کنید و قبل از تغییر آن موارد را بررسی کنید. SQLite ممکن است از فضای آزاد شده مجدداً به جای کوچک کردن خودکار فایل آن استفاده کند.

منبع: n8n: مدیریت داده‌های اجرا و هرس. الزامات دیسک به اندازه بار ذخیره شده مشاهده شده بستگی دارد، نه تعداد گره ها به تنهایی.

RAM، CPU، دیسک و رشد پایگاه‌داده را ردیابی کنید. نسخه‌های پشتیبان قابل بازیابی را خارج از VPS نگه دارید و به جای اینکه یک عکس فوری را کافی فرض کنید، بازیابی را آزمایش کنید.
