BACKUP & RECOVERY

n8n Backup and Restore

A workflow export is useful, but it is not automatically a complete disaster-recovery backup. A recoverable self-hosted n8n deployment must preserve the application data, the matching encryption key and every external file or storage dependency required by your workflows.

QUICK CHECKLIST

What an n8n backup should protect

Database

Back up the PostgreSQL database or the SQLite database file used by the instance. The database contains core n8n state such as workflows, credentials and execution data.

Encryption key

Preserve the exact n8n encryption key separately and securely. Restored encrypted credentials depend on the same key.

Persistent files

Include the persistent n8n data directory and any mounted files, binary-data storage or workflow assets your deployment relies on.

Deployment configuration

Keep the Compose/configuration files and the non-secret configuration needed to rebuild the stack. Protect secrets with appropriate access controls.

TWO BACKUP LEVELS

Logical export vs complete disaster recovery

Workflow & credential export

n8n CLI exports are useful for migration, versioned workflow copies and selective restoration. Credentials can be exported in encrypted form and imported later with the matching encryption key.

Entity export

The CLI can export database entities for moving data between supported database types. Execution-history tables are optional because they can be very large.

Full instance recovery

For a dead-server scenario, protect the actual database, encryption key, persistent data and deployment dependencies. Do not assume a workflow JSON export reconstructs the entire instance.

Provider snapshot

A VPS snapshot is useful as an additional recovery layer, but it should not be the only copy and should not replace an independently verified application/database backup.

DATABASE

Back up the database consistently

PostgreSQL

Use a consistent PostgreSQL backup method and store the resulting backup away from the VPS. A database copy on the same failed disk is not disaster recovery.

SQLite

If the deployment uses SQLite, protect the database file from the persistent n8n data directory. Avoid copying a database in an unsafe state while it is actively being modified.

Execution history

Decide whether historical execution data is part of your recovery objective. It can make backups substantially larger, so retention and compliance requirements should drive the choice.

Database version

Record the database engine and version used by the source deployment so a recovery environment can be prepared compatibly.

CRITICAL SECRET

The encryption key is part of recovery

n8n encrypts stored credentials with an instance encryption key. A database or encrypted credential export without the matching key can leave the restored workflows unable to use their saved credentials.

Store the key in a secure location independent of the VPS. In queue mode, all main and worker processes must use the same key.

DoKeep a protected copy of the exact key used by production.
DoVerify the recovery environment uses that key before testing credentials.
Do notRely on a newly generated key after rebuilding the server.
Do notCommit the key to a public repository or store it beside an unprotected backup.

FILES & BINARY DATA

Database backup may not cover every workflow dependency

Persistent .n8n data

Preserve the n8n persistent directory according to your deployment design. It can contain configuration and instance data needed outside the database.

Mounted workflow files

If workflows read or write host-mounted directories, back those directories up separately. Restoring n8n without them can leave otherwise valid workflows broken.

Binary data

Back up the binary-data store appropriate to your configuration. Filesystem or external object storage must be included in the recovery plan when workflow data depends on it.

Community nodes

Record required community packages and versions so a rebuilt instance can reproduce workflows that depend on non-core nodes.

OFF-SERVER STRATEGY

A backup on the same VPS is only a local copy

Local copyUseful for quick rollback, but vulnerable to server loss, disk failure and destructive mistakes.
Off-server copyKeep at least one backup in storage independent of the production VPS.
Versioned copiesRetain multiple recovery points so corruption or a bad change does not overwrite the only usable backup.
Access controlBackups can contain credentials, workflow logic and sensitive business data. Encrypt and restrict them appropriately.
MonitoringAlert when scheduled backups fail or stop producing new recovery points.

RESTORE TEST

A backup is not proven until restoration succeeds

Test on a clean environment

A real drill should prove that the backup can rebuild an instance without relying on undeclared files left on the production server.

Check credentials

Opening a workflow is not enough. Confirm restored encrypted credentials actually decrypt and authenticate successfully.

Run representative workflows

Test workflows that depend on webhooks, external APIs, mounted files and community nodes rather than validating only a trivial automation.

Measure recovery time

Record how long the restore takes and what manual steps remain. This converts an assumed backup into an operational recovery procedure.

CLI BACKUP LIMITS

Know exactly what workflow and credential exports do not restore

CLI exports are not a full instance backup

Workflow and credential backup exports do not include users and roles, execution history and logs, variables, or instance settings such as the encryption key.

Fresh-instance restore needs an owner

On a clean instance, complete owner setup before importing credentials. Multi-user or project restores may also need the correct user or project assignment.

Imported IDs can overwrite existing items

Workflow and credential exports preserve their original IDs. Importing into an instance that already contains the same IDs can replace those existing items.

Imported workflows may be inactive

Do not assume restored workflows immediately resume production. Verify activation state, credentials and webhook behavior after import before switching traffic back.

FAQ

n8n backup and restore: common questions

Is exporting workflows enough to back up n8n?

No. Workflow exports are useful logical copies, but complete recovery can also require credentials, the matching encryption key, database state, persistent files and binary-data storage.

Do I need the n8n encryption key if I have the database?

Yes if you need the encrypted credentials stored in that database to remain usable. Preserve the original key securely.

Should I back up PostgreSQL or export workflows and credentials?

For disaster recovery, protect the database and the encryption key. Logical exports are valuable as an additional migration and selective-recovery layer rather than a substitute for every part of the instance.

Can a VPS snapshot be my only backup?

It is better treated as one recovery layer. Keep an independent off-server backup so a provider, account, server or snapshot failure does not remove every recovery point at once.

How do I know my backup works?

Restore it into a clean test environment, verify credentials decrypt, and run representative workflows. A successful backup job alone does not prove recoverability.

RECOVERY OBJECTIVES

Define RPO and RTO before an incident

RPO defines how much recent data loss is acceptable and therefore how often backups must run. RTO defines how quickly n8n must be restored and therefore how automated and rehearsed the recovery path needs to be.

RECOVERY KEY

Preserve N8N_ENCRYPTION_KEY

The exact N8N_ENCRYPTION_KEY used by production is part of recovery. Restoring the database with a different key can leave stored credentials unusable.
