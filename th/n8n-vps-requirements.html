RAM & CPU

สิ่งที่ใช้ทรัพยากรเซิร์ฟเวอร์จริงๆ

การประหารชีวิตพร้อมกัน

เวิร์กโฟลว์หลายรายการที่ทำงานพร้อมกันอาจมีความสำคัญมากกว่าจำนวนเวิร์กโฟลว์ทั้งหมดที่จัดเก็บไว้ใน n8n ดูหน่วยความจำสูงสุดและเวลาแฝงในการดำเนินการระหว่างการทับซ้อนกัน

ขนาดเพย์โหลด

ออบเจ็กต์ JSON ขนาดใหญ่ ไฟล์ และข้อมูลไบนารีเพิ่มแรงกดดันให้กับหน่วยความจำ การดำเนินการที่มีข้อมูลจำนวนมากบางรายการอาจต้องใช้ RAM มากกว่าการทำงานอัตโนมัติแบบ lighty API หลายๆ รายการ

CPU-โหนดหนัก

โค้ด การแปลง และขั้นตอนอื่นๆ ที่ต้องใช้การประมวลผลอย่างหนักสามารถสร้างแรงกดดัน CPU ที่ยั่งยืนได้ แกนประมวลผลที่มากขึ้นจะช่วยได้เมื่อการประมวลผลจริงแข่งขันกันเพื่อการประมวลผล

บริการสนับสนุน

ระบบปฏิบัติการ PostgreSQL, reverse proxy, การตรวจสอบ และ Docker ก็ต้องการทรัพยากรเช่นกัน ปรับขนาดสแต็กให้สมบูรณ์ ไม่ใช่แค่กระบวนการ n8n เท่านั้น

วัดผลก่อนอัปเกรด

จะทราบได้อย่างไรว่า n8n ต้องการ RAM, CPU หรือดิสก์เพิ่มเติม

เรียกใช้เวิร์กโฟลว์ที่ใหญ่ที่สุดที่คุณคาดหวังและการระเบิดต่อเนื่องที่ทับซ้อนกันสมจริง จากนั้นตรวจสอบเซิร์ฟเวอร์และบันทึกการดำเนินการ n8n จำนวนเวิร์กโฟลว์ที่บันทึกไว้ในตัวแก้ไขไม่ใช่เกณฑ์มาตรฐานความสามารถที่มีประโยชน์ในตัวมันเอง

หน่วยความจำ / OOM

ตรวจสอบ docker stats --no-stream และ free -h. หากหน่วยความจำหมด ขั้นแรกให้ลด JSON หรือเพย์โหลดไบนารี จัดกลุ่มการนำเข้าจำนวนมาก และหลีกเลี่ยงขั้นตอนโค้ดที่มีหน่วยความจำจำนวนมาก ข้อผิดพลาดฮีป JavaScript ไม่จำเป็นต้องแก้ไขโดยการเพิ่ม vCPU

CPU / เห็นพ้องกัน

วัดว่า CPU ยังคงยุ่งระหว่างการเปลี่ยนแปลงหรืองานรอเพียง API ภายนอกเท่านั้น ในโหมดปกติ ให้พิจารณาขีดจำกัดการทำงานพร้อมกันในการผลิตที่รองรับก่อนที่จะปรับขนาดให้กับworker การเพิ่ม CPU ไม่ได้เร่งการจำกัดอัตราภายนอก API

พื้นที่จัดเก็บ/ฐานข้อมูล

ตรวจสอบ df -hขนาดฐานข้อมูลและประวัติการดำเนินการที่เก็บไว้ ดูการเติบโตของดิสก์และการทำงานของฐานข้อมูลที่ช้า ตั้งค่าการเก็บรักษาอย่างจงใจก่อนชำระค่าดิสก์ที่ใหญ่กว่า เก็บสำเนาการกู้คืนไว้นอกเซิร์ฟเวอร์

ใช้คำแนะนำเกี่ยวกับการทำงานพร้อมกันของ n8n และคำอธิบายการเปรียบเทียบอย่างเป็นทางการ จำนวนขั้นตอนการทำงานที่เกิดขึ้นพร้อมกันที่โฆษณาโดยไม่ทราบเพย์โหลดและเวลาแฝง API เป็นเพียงการประมาณการเท่านั้น

ฐานข้อมูลและการจัดเก็บ

SQLite, PostgreSQL และข้อมูลถาวร

SQLite

SQLite สามารถรองรับการใช้งานและการทดสอบอินสแตนซ์เดี่ยวขนาดเล็กได้ เมื่อการใช้งานจริงและการทำงานพร้อมกันเพิ่มขึ้น ตัวเลือกฐานข้อมูลจะกลายเป็นข้อจำกัดในการปฏิบัติงานแทนที่จะเป็นรายละเอียดการติดตั้ง

PostgreSQL

สำหรับสแต็ก VPS ที่มุ่งเน้นการผลิต PostgreSQL มอบรากฐานฐานข้อมูลที่แข็งแกร่งยิ่งขึ้น งบประมาณ RAM, CPU และดิสก์สำหรับฐานข้อมูลและติดตามการเติบโตของฐานข้อมูล

ข้อมูล .n8n แบบถาวร

อย่าถือว่า PostgreSQL เป็นทรัพย์สินถาวรเพียงอย่างเดียว เก็บรักษาไดเร็กทอรีข้อมูล n8n และปกป้องคีย์การเข้ารหัสที่จำเป็นในการกู้คืนข้อมูลรับรองที่เข้ารหัส

การเติบโตของดิสก์

ประวัติการดำเนินการ ข้อมูลไบนารี ไฟล์ฐานข้อมูล และบันทึกสามารถขยายได้เมื่อเวลาผ่านไป การตั้งค่าการเก็บรักษาและbackupนอกเซิร์ฟเวอร์ส่งผลโดยตรงต่อความจุที่ต้องการ

ความจุของดิสก์

ประมาณการ n8n ที่เก็บข้อมูลประวัติการดำเนินการก่อนสั่งซื้อ

เริ่มต้นด้วย การดำเนินการที่บันทึกไว้ต่อวัน × จำนวนไบต์ที่จัดเก็บโดยเฉลี่ยต่อการดำเนินการ × จำนวนวันที่เก็บรักษา. ตัวอย่างเช่น 500 การดำเนินการที่บันทึกไว้ต่อวัน × 200 KB แต่ละรายการ × 14 วัน = 1.4 GB ตัวอย่างข้อมูลการดำเนินการก่อนค่าใช้จ่ายฐานข้อมูล สมมติฐาน 200 KB นั้นเป็นเพียงตัวอย่าง ไม่ใช่เกณฑ์มาตรฐาน n8n

นอกจากนี้ จัดสรรดิสก์สำหรับ OS, Docker เลเยอร์รูปภาพ, ดัชนีฐานข้อมูล, ไฟล์ไบนารี, บันทึกแอปพลิเคชัน, การอัพเกรด และไฟล์ชั่วคราว backupนอกเซิร์ฟเวอร์จำเป็นต้องมีความจุของตัวเอง ดิสก์ 10 GB สามารถทำงานกับลีนสแต็กได้ แต่มีพื้นที่สำหรับเก็บไฟล์น้อยกว่าดิสก์ 40 หรือ 80 GB มาก

n8n การดำเนินการตามค่าเริ่มต้นของเอกสารจะตัดตามอายุ (336 ชั่วโมง / 14 วัน) หรือจำนวน (10,000 การดำเนินการ) โดยมีข้อยกเว้น ตรวจสอบการตั้งค่าจริงของคุณและตรวจสอบสิ่งที่ยังคงอยู่ก่อนที่จะทำการเปลี่ยนแปลง SQLite อาจนำพื้นที่ว่างมาใช้ซ้ำ แทนที่จะย่อขนาดไฟล์โดยอัตโนมัติ

พร้อมกัน

เมื่อ VPS ที่ใหญ่กว่านั้นหยุดเป็นคำตอบทั้งหมด

การปรับขนาดแนวตั้งมีความเหมาะสมในขณะที่อินสแตนซ์หนึ่งสามารถจัดการปริมาณงานได้อย่างหมดจด เมื่อความต้องการแบบขนานที่ยั่งยืนทำให้เกิดความขัดแย้ง ให้ประเมินQueue Modeและworker Queue Modeแนะนำ Redis, PostgreSQL และกระบวนการของworkerตั้งแต่หนึ่งกระบวนการขึ้นไป งบประมาณ RAM และ CPU สำหรับทุกองค์ประกอบ ไม่ใช่แค่ n8n n8n ยังจัดทำเอกสารข้อจำกัดเกี่ยวกับการจัดเก็บข้อมูลไบนารี่ของระบบไฟล์ในQueue Mode ดังนั้นควรตรวจสอบการออกแบบการจัดเก็บข้อมูลที่เข้ากันได้ก่อนที่จะเปลี่ยน

อ่านQueue Modeและคู่มือworker

พักอินสแตนซ์เดียวเมื่อ CPU, RAM และเวลาแฝงในการดำเนินการยังคงสบายภายใต้การทับซ้อนสูงสุด
ปรับขนาดในแนวตั้งเมื่อการคง CPU หรือแรงกดดันด้านหน่วยความจำเป็นปัจจัยจำกัด และสถาปัตยกรรมยังคงเรียบง่าย
พิจารณาQueue Modeเมื่อวัดความต้องการแบบคู่ขนาน Redis จะเหมาะสมและแยกworkerออกจากกัน
ตรวจสอบพื้นที่เก็บข้อมูลอีกครั้งเมื่อประวัติการดำเนินการ ไบนารีหรือการเติบโต PostgreSQL กลายเป็นข้อจำกัดหลัก

งานทับซ้อนกันขนาดไหน?

แชร์เซิร์ฟเวอร์อะไร?

รวม PostgreSQL พร็อกซี การตรวจสอบ และคอนเทนเนอร์อื่นๆ ไว้ในงบประมาณทรัพยากร

ข้อมูลจะเติบโตเร็วแค่ไหน?

ประมาณการการเก็บรักษาการดำเนินการ การเติบโตของฐานข้อมูล และพื้นที่จัดเก็บbackupก่อนที่จะเลือกความจุของดิสก์

วิธีใช้รายการ 1 GB VPS

1 GB RAM

นี่คือระดับ VPS ที่ใช้งานได้จริง ไม่ใช่ผลิตภัณฑ์สำหรับทดสอบเท่านั้น เหมาะสำหรับการทำงานอัตโนมัติที่เปิดตลอดเวลาเล็กๆ น้อยๆ และการทำงานแบบต่อเนื่อง API เป็นส่วนใหญ่ เมื่อคุณเก็บหน่วยความจำ การใช้ดิสก์ และงานที่เกิดขึ้นพร้อมกันภายในขีดจำกัดที่วัดได้ มันมีพื้นที่เหลือเพียงเล็กน้อยสำหรับ PostgreSQL บนเซิร์ฟเวอร์เดียวกัน เพย์โหลดขนาดใหญ่ หรือการประมวลผลแบบขนานจำนวนมาก

2 GB RAM

ใช้ 2 GB เป็นพื้นฐานอินสแตนซ์แสงที่ปลอดภัยยิ่งขึ้น เมื่อคุณต้องการพื้นที่เพิ่มขึ้นสำหรับระบบปฏิบัติการ Docker และการระเบิดเล็กๆ น้อยๆ โดยไม่ต้องย้ายไปยังสแต็กขนาดที่ใช้งานจริงในทันที

SSD กับ NVMe

Standard SSD เพียงพอสำหรับระบบอัตโนมัติของแสง NVMe จะมีประโยชน์มากขึ้นเมื่อ PostgreSQL และประวัติการดำเนินการสร้างการอ่านและเขียนบ่อยครั้ง หรือเมื่อเวลาแฝงของดิสก์ปรากฏขึ้นในประสิทธิภาพเวิร์กโฟลว์ที่วัดได้

วัดขนาดก่อนอัพเกรด

ใช้ CPU หน่วยความจำ การเติบโตของดิสก์ และระยะเวลาการดำเนินการภายใต้การทับซ้อนสูงสุด เพื่อตัดสินใจว่าคอขวดคือการประมวลผล หน่วยความจำ หรือการจัดเก็บข้อมูล แทนที่จะคิดว่า VPS ที่ใหญ่กว่าจะแก้ไขทุกการชะลอตัว

คำถามที่พบบ่อย

ข้อกำหนด n8n VPS: คำถามทั่วไป

n8n ต้องการ RAM เท่าใด

ไม่มีรูปสากล RAM เรียกร้องการเปลี่ยนแปลงพร้อมๆ กัน ขนาดเพย์โหลด พฤติกรรมการดำเนินการ และบริการสนับสนุนใน VPS เซิร์ฟเวอร์ 4 GB เป็นคลาสเริ่มต้นสำหรับการผลิตขนาดเล็กที่ใช้งานได้จริง ไม่ใช่ข้อกำหนดที่รับประกันสำหรับทุกปริมาณงาน

ฉันควรใช้คอร์ CPU จำนวนเท่าใด

ปริมาณงานไม่มากสามารถเริ่มต้นด้วยการจัดสรร CPU เพียงเล็กน้อย เพิ่มคอร์เมื่อการตรวจสอบแสดงแรงกดดัน CPU ที่ยั่งยืนหรือการดำเนินการที่ช้าลงภายใต้การทำงานพร้อมกัน แทนที่จะปรับขนาดจากจำนวนเวิร์กโฟลว์เพียงอย่างเดียว

n8n ต้องใช้ PostgreSQL หรือไม่

การใช้งานขนาดเล็กสามารถใช้ SQLite ได้ แต่ PostgreSQL เป็นตัวเลือกที่มุ่งเน้นการผลิตที่แข็งแกร่งกว่า เนื่องจากข้อกำหนดในการปฏิบัติงานและการทำงานพร้อมกันเพิ่มขึ้น

เมื่อใดที่ต้องใช้ Redis?

Redis เกี่ยวข้องกับQueue Mode deploymentอินสแตนซ์เดี่ยวแบบปกติไม่จำเป็นต้องใช้ Redis เพียงเพราะมันทำงานบน VPS

ฉันควรจองพื้นที่ดิสก์เท่าใด

ความต้องการดิสก์ขึ้นอยู่กับการเติบโต PostgreSQL ประวัติการดำเนินการที่เก็บไว้ ข้อมูลไบนารี บันทึก เลเยอร์คอนเทนเนอร์ และbackup ติดตามการเติบโตและออกจากช่องว่างแทนการพึ่งพาจำนวนสากลคงที่

ฉันสามารถเรียกใช้ n8n อย่างต่อเนื่องบน 1 GB VPS ได้หรือไม่

ใช่ เมื่อปริมาณงานจริงเหมาะสม A 1 GB VPS เป็นเซิร์ฟเวอร์ที่ใช้งานได้จริง และสามารถรองรับการทำงานอัตโนมัติขนาดเล็กซึ่งส่วนใหญ่เป็นลำดับได้ แต่พื้นที่ว่างของหน่วยความจำมีจำกัด หลีกเลี่ยงการสันนิษฐานว่าสแต็ก PostgreSQL ของเซิร์ฟเวอร์เดียวกัน งานไบนารีหนัก หรือการดำเนินการขนาดใหญ่หลายรายการพร้อมกันจะพอดี ตรวจสอบปริมาณการใช้และการอัปเกรดตามแรงกดดันด้านทรัพยากรที่สังเกตได้

2 GB หรือ 4 GB RAM ดีกว่าสำหรับการผลิต n8n VPS หรือไม่

สองกิกะไบต์ให้พื้นที่มากกว่าอินสแตนซ์ 1 GB แบบลีน ในขณะที่ 4 GB เป็นคลาสเริ่มต้นที่ใช้งานได้จริงในการประเมิน n8n ร่วมกับ PostgreSQL และ HTTPS ไม่มีการรับประกันการผลิตขั้นต่ำที่เป็นสากล: ความซับซ้อนของปริมาณงาน การทับซ้อนสูงสุด การกำหนดค่าคอนเทนเนอร์ และข้อมูลที่เก็บจะกำหนดความต้องการที่แท้จริง

n8n เวิร์กโฟลว์ AI จำเป็นต้องมี GPU หรือไม่

ไม่ใช่เมื่อ n8n เรียกเฉพาะโมเดลภายนอก API: ผู้ให้บริการโมเดลจะจัดการการอนุมาน ในขณะที่ VPS จัดการการเรียบเรียง เพย์โหลด และการทำงานพร้อมกัน การรันโมเดลการอนุมานภายในเครื่องเป็นการตัดสินใจด้านฮาร์ดแวร์แยกต่างหากซึ่งอาจต้องใช้ทรัพยากร RAM และทรัพยากร GPU ที่เหมาะสมมากขึ้น

อะไรทำให้เกิดข้อผิดพลาดหน่วยความจำไม่เพียงพอ n8n

JSON หรือเพย์โหลดไบนารีขนาดใหญ่ การทำงานของโค้ดที่มีหน่วยความจำหนัก และการดำเนินการที่ทับซ้อนกันเป็นสาเหตุที่พบบ่อย ตรวจสอบบันทึกรันไทม์และการใช้หน่วยความจำสูงสุด จากนั้นลดข้อมูลที่เก็บไว้ในการดำเนินการครั้งเดียวหรือจัดสรร RAM เพิ่มเติมตามปัญหาที่วัดได้
