การสำรองข้อมูลและการกู้คืน

การสำรองและกู้คืน n8n

หากต้องการสำรองและกู้คืน n8n ที่โฮสต์เอง ให้ปกป้องฐานข้อมูล SQLite ของคุณหรือดัมพ์ PostgreSQL ที่สอดคล้องกัน โฟลเดอร์ .n8n ถาวรและคีย์การเข้ารหัสดั้งเดิม การกำหนดค่าการปรับใช้ และการอ้างอิงไบนารีภายนอกหรือไฟล์ที่เมาท์ทุกรายการ เก็บสำเนาที่เข้ารหัสไว้นอก VPS และทดสอบการกู้คืนในอินสแตนซ์ที่แยกต่างหาก ใช้เวิร์กโฟลว์ CLI และการส่งออกข้อมูลประจำตัวสำหรับการกู้คืนแบบเลือก JSON การส่งออกเพียงอย่างเดียวไม่ใช่การสำรองข้อมูลเซิร์ฟเวอร์เต็มรูปแบบ

รายการตรวจสอบด่วน

การสำรองข้อมูล n8n ควรครอบคลุมอะไรบ้าง

ฐานข้อมูล

สำรองฐานข้อมูล PostgreSQL หรือไฟล์ฐานข้อมูล SQLite ที่ใช้โดยอินสแตนซ์ ฐานข้อมูลประกอบด้วยสถานะหลัก n8n เช่น เวิร์กโฟลว์ ข้อมูลรับรอง และข้อมูลการดำเนินการ

คีย์การเข้ารหัส

เก็บคีย์การเข้ารหัส n8n ที่ถูกต้องแยกกันและปลอดภัย ข้อมูลรับรองที่เข้ารหัสที่กู้คืนจะขึ้นอยู่กับคีย์เดียวกัน

ไฟล์ถาวร

รวมไดเร็กทอรีข้อมูล n8n แบบถาวร และไฟล์ที่เมาท์ พื้นที่จัดเก็บข้อมูลไบนารี หรือสินทรัพย์เวิร์กโฟลว์ที่ปรับใช้ของคุณ

การกำหนดค่าการปรับใช้

เก็บไฟล์เขียน/การกำหนดค่าและการกำหนดค่าที่ไม่เป็นความลับซึ่งจำเป็นในการสร้างสแต็กใหม่ ปกป้องความลับด้วยการควบคุมการเข้าถึงที่เหมาะสม

การสำรองข้อมูลสองระดับ

การส่งออกเชิงตรรกะเทียบกับการกู้คืนระบบเต็มรูปแบบ

ขั้นตอนการทำงานและการส่งออกข้อมูลประจำตัว

n8n CLI การส่งออกมีประโยชน์สำหรับการย้ายข้อมูล สำเนาเวิร์กโฟลว์ที่มีเวอร์ชัน และการกู้คืนแบบเลือก ข้อมูลรับรองสามารถส่งออกในรูปแบบที่เข้ารหัสและนำเข้าในภายหลังด้วยคีย์เข้ารหัสที่ตรงกัน หากต้องการกู้คืนเวิร์กโฟลว์เพียงรายการเดียว ให้ใช้เมนูสามจุดของตัวแก้ไขเวิร์กโฟลว์เพื่อดาวน์โหลด JSON จากนั้นนำเข้าจากไฟล์ไปยังเวิร์กโฟลว์การตรวจสอบใหม่หรืออินสแตนซ์ที่แยกออกมา ตรวจสอบข้อมูลประจำตัว รหัสเวิร์กโฟลว์ และพารามิเตอร์โหนดก่อนที่จะแทนที่เวิร์กโฟลว์ที่ใช้งานจริง: การคืนค่าเวิร์กโฟลว์ JSON จะไม่กู้คืนทั้งเซิร์ฟเวอร์

การส่งออกเอนทิตี

CLI สามารถส่งออกเอนทิตีฐานข้อมูลสำหรับการย้ายข้อมูลระหว่างประเภทฐานข้อมูลที่รองรับ ตารางประวัติการดำเนินการเป็นทางเลือก เนื่องจากอาจมีขนาดใหญ่มาก

การกู้คืนอินสแตนซ์แบบเต็ม

สำหรับสถานการณ์เซิร์ฟเวอร์ที่ไม่ทำงาน ให้ปกป้องฐานข้อมูลจริง คีย์การเข้ารหัส ข้อมูลถาวร และการพึ่งพาการปรับใช้ อย่าถือว่าเวิร์กโฟลว์ JSON การส่งออกจะสร้างอินสแตนซ์ทั้งหมดใหม่

ภาพรวมของผู้ให้บริการ

สแน็ปช็อต VPS มีประโยชน์เป็นเลเยอร์การกู้คืนเพิ่มเติม แต่ไม่ควรเป็นเพียงสำเนาเดียว และไม่ควรแทนที่การสำรองข้อมูลแอปพลิเคชัน/ฐานข้อมูลที่ได้รับการตรวจสอบโดยอิสระ

ฐานข้อมูล

สำรองฐานข้อมูลแบบสอดคล้องกัน

PostgreSQL

ใช้วิธีการสำรองข้อมูล PostgreSQL ที่สอดคล้องกัน และจัดเก็บข้อมูลสำรองที่เป็นผลลัพธ์ให้ห่างจาก VPS สำเนาฐานข้อมูลบนดิสก์ที่ล้มเหลวเดียวกันไม่ใช่การกู้คืนระบบ

SQLite

หากการปรับใช้ใช้ SQLite ให้ป้องกันไฟล์ฐานข้อมูลจากไดเร็กทอรีข้อมูล n8n ที่คงอยู่ หลีกเลี่ยงการคัดลอกฐานข้อมูลในสถานะที่ไม่ปลอดภัยในขณะที่กำลังแก้ไข

ประวัติการดำเนินการ

ตัดสินใจว่าข้อมูลการดำเนินการในอดีตเป็นส่วนหนึ่งของวัตถุประสงค์การกู้คืนของคุณหรือไม่ สามารถทำให้การสำรองข้อมูลมีขนาดใหญ่ขึ้นอย่างมาก ดังนั้นข้อกำหนดในการเก็บรักษาและการปฏิบัติตามข้อกำหนดจึงควรเป็นตัวขับเคลื่อนทางเลือก

เวอร์ชันฐานข้อมูล

บันทึกกลไกฐานข้อมูลและเวอร์ชันที่ใช้โดยการปรับใช้ต้นทาง เพื่อให้สามารถเตรียมสภาพแวดล้อมการกู้คืนที่เข้ากันได้

PostgreSQL ใน Docker Compose VPS หากมีการตั้งชื่อบริการ PostgreSQL postgres และฐานข้อมูล/ผู้ใช้เป็นทั้งคู่ n8nคำสั่งต่อไปนี้จะสร้างดัมพ์รูปแบบที่กำหนดเอง PostgreSQL ที่สอดคล้องกันบนโฮสต์ ตรวจสอบไฟล์ Compose จริงของคุณก่อนที่จะรัน และปรับข้อมูลรับรองฐานข้อมูลและชื่อบริการ pg_dump สามารถสร้างสแนปชอตที่สอดคล้องกันในเชิงตรรกะในขณะที่ PostgreSQL กำลังทำงานอยู่ มันทำ ไม่ สำรองข้อมูลแยกต่างหาก .n8n โฟลเดอร์ผู้ใช้หรือข้อมูลไบนารีภายนอก

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

การตรวจสอบรายการเก็บถาวรจะพบปัญหาเกี่ยวกับรูปแบบที่ชัดเจน แต่ไม่ได้พิสูจน์ว่าสามารถกู้คืนข้อมูลได้ จัดเก็บสำเนาที่เข้ารหัสไว้นอกเซิร์ฟเวอร์และซ้อมการกู้คืน ใช้เอกสาร PostgreSQL pg_dump อย่างเป็นทางการสำหรับตัวเลือกเฉพาะฐานข้อมูล

SQLite บน Docker สำหรับการปรับใช้ SQLite เริ่มต้น database.sqlite และการกำหนดค่าคีย์เข้ารหัสที่สร้างขึ้นนั้นอยู่ภายในไฟล์ถาวร .n8n โฟลเดอร์ (ปกติจะติดตั้งที่ /home/node/.n8n). อย่าถือว่าสำเนาสดธรรมดาของ SQLite มีความสอดคล้องกัน หยุด n8n และผู้เขียนฐานข้อมูลอื่นๆ ก่อนที่จะคัดลอกโฟลเดอร์ หรือใช้กลไกการสำรองข้อมูลออนไลน์ที่รองรับของ SQLite เมื่อไม่สามารถหยุดชะงักได้:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

นี่เป็นคำสั่งที่แสดงให้เห็นอย่างชัดเจนสำหรับบริการและเส้นทางที่แสดง ไม่ใช่โครงร่างวอลุ่มสากล โฟลเดอร์ที่คัดลอกจะยังคงอยู่ใน VPS เดิม ถ่ายโอนและป้องกันนอกเซิร์ฟเวอร์ เมื่อมี worker คิวหรือผู้เขียนอื่นๆ อยู่ ให้หยุดสิ่งเหล่านั้นด้วยและปฏิบัติตามการออกแบบการใช้งานจริงของ worker คำแนะนำการสำรองข้อมูลเต็มรูปแบบในปัจจุบันของ n8n บันทึกข้อกำหนดความสอดคล้องของ SQLite

การคืนค่าโฟลเดอร์ SQLite เริ่มต้นเป็นเป้าหมายที่สะอาด: ขั้นแรกให้หยุดบริการ n8n และผู้เขียนฐานข้อมูลทั้งหมด เมื่อมีคอนเทนเนอร์บริการ n8n ที่เข้ากันได้และโวลุ่มปลายทางแล้ว ให้คัดลอกข้อมูลที่สำรองไว้ .n8n เนื้อหา กลับ ไปยังไดเร็กทอรีถาวรเดียวกัน การดำเนินการนี้จะเขียนทับไฟล์เป้าหมาย ดังนั้นอย่ารันบนอินสแตนซ์ที่มีข้อมูลที่คุณต้องการเก็บไว้:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker สามารถคัดลอกไปยังคอนเทนเนอร์ที่ถูกหยุดได้ แต่การเป็นเจ้าของปลายทางอาจแตกต่างจากต้นฉบับ ตรวจสอบให้แน่ใจว่าการกำหนดค่าที่กู้คืนและไฟล์ฐานข้อมูลสามารถอ่านและเขียนได้โดยกระบวนการ n8n ก่อนที่จะเริ่มต้น หากการกำหนดค่าการเขียนจริงของคุณใช้พาธอื่นหรือการเชื่อมต่อแบบผูก ให้ปรับสำเนาตามนั้น Docker Composeสำเนาอ้างอิง การกู้คืนโฟลเดอร์ n8n เพียงอย่างเดียวไม่เพียงพอสำหรับการปรับใช้ที่ใช้ฐานข้อมูล PostgreSQL แยกต่างหาก

ความลับที่สำคัญ

คีย์เข้ารหัสเป็นส่วนหนึ่งของการกู้คืน

n8n เข้ารหัสข้อมูลรับรองที่เก็บไว้ด้วยคีย์การเข้ารหัสอินสแตนซ์ ฐานข้อมูลหรือการส่งออกข้อมูลประจำตัวที่เข้ารหัสโดยไม่มีคีย์ที่ตรงกันอาจทำให้เวิร์กโฟลว์ที่กู้คืนไม่สามารถใช้ข้อมูลประจำตัวที่บันทึกไว้ได้

หากคุณตั้งค่า N8N_ENCRYPTION_KEY ให้กู้คืนข้อมูลลับที่แน่นอนนั้น มิฉะนั้น คีย์ที่สร้างขึ้นจะถูกจัดเก็บไว้ในไฟล์ .n8n/config ถาวร: ป้องกันการกำหนดค่านั้นเมื่อสำรองข้อมูลหรือสร้างใหม่ จัดเก็บคีย์การกู้คืนไว้อย่างปลอดภัยภายนอก VPS ใน Queue Mode กระบวนการหลักและกระบวนการของ worker ทั้งหมดต้องใช้คีย์เดียวกัน

ทำเก็บสำเนาที่ได้รับการป้องกันของคีย์ที่ใช้ในการผลิต
ทำตรวจสอบสภาพแวดล้อมการกู้คืนใช้คีย์นั้นก่อนทดสอบข้อมูลรับรอง
อย่าใช้คีย์ที่สร้างขึ้นใหม่หลังจากสร้างเซิร์ฟเวอร์ใหม่
อย่ามอบคีย์ให้กับพื้นที่เก็บข้อมูลสาธารณะหรือเก็บไว้ข้างการสำรองข้อมูลที่ไม่มีการป้องกัน

ไฟล์และข้อมูลไบนารี

การสำรองฐานข้อมูลอาจไม่ครอบคลุมทุกขั้นตอนการทำงาน

ข้อมูล .n8n แบบถาวร

ค้นหาและรักษาโฟลเดอร์ผู้ใช้ .n8n ที่แท้จริง ไม่ใช่เฉพาะคอนเทนเนอร์อิมเมจเท่านั้น ในการปรับใช้ Docker โดยทั่วไป จะมีการติดตั้งที่ /home/node/.n8n; ภายนอก Docker ค่าเริ่มต้นคือ ~/.n8n หากมีการกำหนดค่า N8N_USER_FOLDER n8n จะสร้าง .n8n ภายในไดเรกทอรีหลักที่ระบุ รวมคีย์การกำหนดค่าและข้อมูลการดำเนินการ SQLite ไบนารี หรือระบบไฟล์ในเครื่องที่การติดตั้งของคุณใช้

ไฟล์เวิร์กโฟลว์ที่เมาท์

หากเวิร์กโฟลว์อ่านหรือเขียนไดเร็กทอรีที่เชื่อมต่อกับโฮสต์ ให้สำรองข้อมูลไดเร็กทอรีเหล่านั้นแยกกัน การกู้คืน n8n โดยไม่มีสิ่งเหล่านี้อาจทำให้เวิร์กโฟลว์ที่ถูกต้องเสียหายได้

ข้อมูลไบนารี

ระบุโหมดการจัดเก็บข้อมูลและกู้คืนการขึ้นต่อกันภายนอกทั้งหมด ข้อมูลไบนารีหรือการดำเนินการตามระบบไฟล์อาจอยู่ใน .n8n หรือไดเร็กทอรีที่กำหนดเอง S3/Azure Blob หรือที่จัดเก็บข้อมูลภายนอกที่กำหนดค่าไว้อื่นๆ จำเป็นต้องมีการตั้งค่าสำเนาและการเข้าถึงที่สามารถกู้คืนได้ของตัวเอง ดัมพ์ฐานข้อมูลเพียงอย่างเดียวไม่สามารถแทนที่ไฟล์เหล่านั้นได้

บันทึกแพ็คเกจและเวอร์ชันของชุมชน และสำรองข้อมูลไดเร็กทอรีโหนดที่กำหนดเองเพิ่มเติมที่กำหนดค่าผ่าน N8N_CUSTOM_EXTENSIONS ไดเร็กทอรีเหล่านั้นสามารถอยู่ข้างนอก .n8n; การกู้คืนฐานข้อมูลและโฟลเดอร์ผู้ใช้เพียงอย่างเดียวอาจทำให้เวิร์กโฟลว์โหนดแบบกำหนดเองไม่สามารถใช้งานได้

กลยุทธ์นอกเซิร์ฟเวอร์

การสำรองข้อมูลไว้บน VPS เครื่องเดียวกันเป็นเพียงสำเนาภายในเครื่อง

สำเนาท้องถิ่นมีประโยชน์สำหรับการย้อนกลับอย่างรวดเร็ว แต่เสี่ยงต่อการสูญเสียเซิร์ฟเวอร์ ดิสก์ล้มเหลว และข้อผิดพลาดในการทำลายล้าง
สำเนานอกเซิร์ฟเวอร์เก็บข้อมูลสำรองอย่างน้อยหนึ่งรายการไว้ในที่เก็บข้อมูลโดยไม่ขึ้นอยู่กับการผลิต VPS
สำเนาเวอร์ชันเก็บจุดการกู้คืนไว้หลายจุด ดังนั้นความเสียหายหรือการเปลี่ยนแปลงที่ไม่ถูกต้องจะไม่เขียนทับข้อมูลสำรองที่ใช้งานได้เพียงอย่างเดียว
การควบคุมการเข้าถึงการสำรองข้อมูลอาจมีข้อมูลประจำตัว ตรรกะเวิร์กโฟลว์ และข้อมูลธุรกิจที่ละเอียดอ่อน เข้ารหัสและจำกัดอย่างเหมาะสม
การตรวจสอบแจ้งเตือนเมื่อการสำรองข้อมูลตามกำหนดเวลาล้มเหลวหรือหยุดสร้างจุดกู้คืนใหม่

ทำให้ตารางเวลาสามารถวัดผลได้ บันทึกการประทับเวลาของการสำรองข้อมูลที่สำเร็จแต่ละครั้ง การถ่ายโอนเสร็จสมบูรณ์ ขนาดไฟล์ เวอร์ชันฐานข้อมูลต้นทาง ตำแหน่งการกู้คืนคีย์การเข้ารหัส และการทดสอบการคืนค่าที่สำเร็จล่าสุด แจ้งเตือนเมื่อไฟล์สูญหาย ล้มเหลว หรือว่างเปล่าโดยไม่คาดคิด เข้ารหัสข้อมูลสำรองก่อนที่จะส่งออกจาก VPS และจำกัดการเข้าถึงความลับในการกู้คืน จุดกู้คืนที่ลงวันที่หลายจุดจะช่วยป้องกันการค้นพบความเสียหายเฉพาะหลังจากที่สำเนาใหม่ล่าสุดได้เขียนทับสำเนาล่าสุดที่สมบูรณ์แล้วเท่านั้น

ตัวอย่างเช่น หากคุณสามารถทนต่อการเปลี่ยนแปลงที่สูญหายได้สูงสุดหกชั่วโมง ตารางการสำรองข้อมูลหกชั่วโมงที่ประสบความสำเร็จคือจุดเริ่มต้น ไม่ใช่การรับประกัน: งานที่ล้มเหลวและการจำลองแบบนอกเซิร์ฟเวอร์ที่ล่าช้าสามารถเพิ่มการสูญเสียที่แท้จริงได้ ตั้งค่าการรักษาและคืนจังหวะให้กับ RPO/RTO และข้อกำหนดข้อมูลของคุณเอง แทนที่จะใช้นโยบายสากล 7 วันหรือ 30 วัน

เรียกคืนคำสั่งซื้อ

กู้คืนตามลำดับที่ควบคุมได้

1 · เตรียมพร้อมจัดเตรียมเซิร์ฟเวอร์ ฐานข้อมูล และสภาพแวดล้อมคอนเทนเนอร์/รันไทม์ที่เข้ากันได้
2 · เรียกคืนความลับกำหนดค่าคีย์การเข้ารหัส n8n ดั้งเดิมและความลับในการปรับใช้ที่จำเป็นอย่างปลอดภัย
3 · กู้คืนฐานข้อมูลกู้คืน PostgreSQL หรือ SQLite และตรวจสอบว่า n8n สามารถเชื่อมต่อกับข้อมูลที่คาดหวังได้
4 · กู้คืนไฟล์กู้คืนไดเร็กทอรีถาวร ข้อมูลไบนารี และสินทรัพย์เวิร์กโฟลว์ที่ติดตั้ง
5 · เริ่ม n8nเรียกใช้แอปพลิเคชันด้วยชื่อโฮสต์ ฐานข้อมูล และการกำหนดค่าสภาพแวดล้อมที่ต้องการ
6 · ตรวจสอบยืนยันการโหลดผู้ใช้ เวิร์กโฟลว์ และข้อมูลรับรอง จากนั้นดำเนินการเวิร์กโฟลว์ตัวแทนและเส้นทาง webhook

PostgreSQL ตัวอย่างการกู้คืนความเสียหาย: บน แยกเป้าหมายการคืนค่าที่สะอาด ที่มีบทบาทฐานข้อมูลที่ถูกต้องและว่างเปล่าอยู่แล้ว n8n ฐานข้อมูลเริ่มต้น เท่านั้น PostgreSQL รอจนกว่าจะแข็งแรงก่อนนำเข้า: docker compose up -d เพียงอย่างเดียวสามารถกลับมาได้ในขณะที่ PostgreSQL ยังคงเริ่มต้นอยู่ ดังนั้นต่อไปนี้ pg_restore สามารถล้มเหลวได้ ตัวอย่างการใช้งาน --wait ในการติดตั้ง Compose ที่ทันสมัย และตรวจสอบอย่างอิสระ pg_isready. กำหนดค่าการตรวจสุขภาพ PostgreSQL ที่เหมาะสมเพื่อการรอที่เชื่อถือได้ หรือยืนยันความพร้อมอย่างชัดเจนก่อนที่จะดำเนินการต่อ อย่าชี้คำสั่งนี้ไปที่ฐานข้อมูลการผลิตที่มีประชากรหรือเริ่ม n8n ก่อนฐานข้อมูลและการจับคู่ .n8n คีย์/ข้อมูลถูกเรียกคืน

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

ปลายทางจะต้องมีเวอร์ชัน PostgreSQL สิทธิ์ของบทบาท ส่วนขยาย และการกำหนดค่า n8n ดั้งเดิมที่เข้ากันได้ คืนค่า .n8n ไปยังวอลุ่มถาวรที่ถูกต้องหรือการเมานต์การผูกโดยใช้กลไกการสำรองข้อมูลของคุณ โดยรักษาความเป็นเจ้าของและการอนุญาต กู้คืนไฟล์ไบนารีภายนอก ส่วนขยายที่กำหนดเอง การกำหนดค่าการเขียนและความลับ จากนั้นเริ่ม n8n ในเวอร์ชันที่เข้ากันได้ และตรวจสอบบันทึก การกู้คืนฐานข้อมูลเพียงอย่างเดียวไม่สามารถกู้คืนคีย์ได้: การปรับใช้ PostgreSQL จะเก็บคีย์ไว้ .n8n/config เว้นแต่คุณจะกำหนดค่าไว้อย่างชัดเจน N8N_ENCRYPTION_KEY. การอ้างอิง pg_restore · n8n ลำดับการกู้คืนอินสแตนซ์แบบเต็ม

เลือกการกู้คืน VPS หากคุณต้องการเซิร์ฟเวอร์ที่ปลอดภัย

ลิงค์พันธมิตร: เราอาจได้รับค่าคอมมิชชั่นจากการซื้อ

คืนค่าการทดสอบ

การสำรองข้อมูลยังไม่ถือว่าใช้ได้จริงจนกว่าจะกู้คืนสำเร็จ

ทดสอบในสภาพแวดล้อมที่สะอาด

การเจาะลึกจริงควรพิสูจน์ว่าการสำรองข้อมูลสามารถสร้างอินสแตนซ์ใหม่ได้โดยไม่ต้องอาศัยไฟล์ที่ไม่ได้ประกาศที่เหลืออยู่บนเซิร์ฟเวอร์ที่ใช้งานจริง

ตรวจสอบข้อมูลรับรอง

การเปิดเวิร์กโฟลว์ไม่เพียงพอ ยืนยันข้อมูลประจำตัวที่เข้ารหัสที่กู้คืนแล้ว ถอดรหัสและตรวจสอบสิทธิ์ได้สำเร็จ

เรียกใช้เวิร์กโฟลว์ตัวแทน

ทดสอบเวิร์กโฟลว์ที่ขึ้นอยู่กับ webhooks, API ภายนอก, ไฟล์ที่เมาท์ และโหนดชุมชน แทนที่จะตรวจสอบความถูกต้องเพียงการทำงานอัตโนมัติเล็กๆ น้อยๆ

วัดระยะเวลาการฟื้นตัว

บันทึกระยะเวลาการคืนค่าและขั้นตอนที่ต้องดำเนินการด้วยตนเองที่เหลืออยู่ ซึ่งจะแปลงการสำรองข้อมูลที่สมมติให้เป็นขั้นตอนการกู้คืนการปฏิบัติงาน

การเจาะลึกการคืนค่าที่ตรวจสอบแล้ว: SQLite และ PostgreSQL

สภาพแวดล้อมการทดสอบ: n8n 2.42.5 ในคอนเทนเนอร์ Docker แบบแยกบนตัวรันการดำเนินการ GitHub แบบใช้แล้วทิ้ง โดยใช้เวิร์กโฟลว์แบบสองโหนดสังเคราะห์ การตรวจสอบเหล่านี้ดำเนินต่อไป 8 ตุลาคม 2026ไม่ใช่บนเซิร์ฟเวอร์ n8n ของลูกค้าหรือการผลิต

SQLite: ผ่านนำเข้าเวิร์กโฟลว์ทดสอบ ส่งออก หยุดผู้เขียนทั้งหมด เก็บถาวรที่สนับสนุน SQLite .n8n โฟลเดอร์และคีย์การเข้ารหัสที่สร้างขึ้น กู้คืนเป็นวอลลุมใหม่ เริ่มต้น n8n จากนั้นส่งออกอีกครั้งและดำเนินการเวิร์กโฟลว์ที่กู้คืน
PostgreSQL: ผ่านนำเข้าเวิร์กโฟลว์ทดสอบเดียวกัน สร้างและตรวจสอบรูปแบบที่กำหนดเอง pg_dumpคืนค่าโดยใช้ pg_restore ลงในฐานข้อมูล PostgreSQL ว่างเปล่าใหม่ กู้คืนข้อมูลแยกต่างหาก .n8n จากนั้นส่งออกอีกครั้งและดำเนินการเวิร์กโฟลว์ที่กู้คืน
สิ่งที่ PASS กำหนดไว้เส้นทางการสำรองข้อมูลที่ผ่านการทดสอบจะรักษาเวิร์กโฟลว์นี้ โหนดทั้งสองและการเชื่อมต่อไว้ และอนุญาตให้ดำเนินการได้หลังจากการกู้คืน การทดสอบเหล่านี้เป็นการทดสอบควันการทำงานที่สามารถทำซ้ำได้ ไม่ใช่การวัดประสิทธิภาพด้านปริมาณงาน
สิ่งที่ไม่ได้ทดสอบการถอดรหัสและการรับรองความถูกต้องของข้อมูลประจำตัวจริง webhooks ที่ใช้งานจริง worker ใน Queue Mode และ Redis พื้นที่เก็บข้อมูลไบนารี S3/Azure โหนดที่กำหนดเอง การเข้าถึงผู้ใช้/โครงการ หรือการกู้คืนอินสแตนซ์ที่ใช้งานจริง เรียกใช้การเจาะลึกแยกต่างหากสำหรับการขึ้นต่อกันแต่ละรายการที่คุณใช้จริง

วิธีการสืบพันธุ์: ใช้การติดตั้ง n8n แบบใช้แล้วทิ้ง สร้างเวิร์กโฟลว์แบบสองโหนดที่ไม่เป็นอันตราย ดำเนินการฐานข้อมูลที่เกี่ยวข้องพร้อมการสำรองข้อมูลโฟลเดอร์ถาวร คืนค่าเป็นคลีนวอลุ่มหรือฐานข้อมูล จากนั้นตรวจสอบโหนดของเวิร์กโฟลว์ที่กู้คืน การเชื่อมต่อ และการดำเนินการจริง ในระบบที่ใช้งานจริง ให้ตรวจสอบข้อมูลรับรองที่เข้ารหัส webhook และไฟล์ภายนอก ก่อนที่จะประกาศการกู้คืนระบบที่พิสูจน์แล้ว

เรียกคืนรายการตรวจสอบการยอมรับการเจาะ: ใช้โดเมน/สภาพแวดล้อมที่แยกออกจากกัน ตรวจสอบว่ามีผู้ใช้และเวิร์กโฟลว์อยู่ มีข้อมูลรับรองความถูกต้องที่เข้ารหัสไว้หนึ่งรายการตรวจสอบสิทธิ์โดยไม่ต้องกลับเข้าไปใหม่ webhook ที่ใช้งานจริงเรียกใช้เวิร์กโฟลว์ที่ได้รับการกู้คืนตามที่ตั้งใจไว้ ไฟล์ที่เมาท์และไฟล์แนบแบบไบนารียังคงสามารถอ่านได้ และการผสานรวมกับโหลดโหนดชุมชนที่ต้องการ ยืนยันอายุการสำรองข้อมูล วัดเวลาหยุดทำงาน และการเข้าถึงนอกเซิร์ฟเวอร์ หากการตรวจสอบที่จำเป็นล้มเหลว ให้ทำเครื่องหมายจุดการกู้คืนนั้น ไม่ได้รับการยืนยัน แทนที่จะรายงานการสำรองข้อมูลว่าเสร็จสมบูรณ์

เวิร์กโฟลว์และการส่งออกข้อมูลสำรองจะไม่รวมผู้ใช้และบทบาท ประวัติการดำเนินการและบันทึก ตัวแปร หรือการตั้งค่าอินสแตนซ์ เช่น คีย์การเข้ารหัส

การกู้คืนอินสแตนซ์ Fresh จำเป็นต้องมีเจ้าของ

ในอินสแตนซ์ที่ปลอดภัย ให้ตั้งค่าเจ้าของให้เสร็จสิ้นก่อนที่จะนำเข้าข้อมูลรับรอง การกู้คืนแบบหลายผู้ใช้หรือโปรเจ็กต์อาจต้องมีการกำหนดผู้ใช้หรือโปรเจ็กต์ที่ถูกต้องด้วย

รหัสที่นำเข้าสามารถเขียนทับรายการที่มีอยู่ได้

เวิร์กโฟลว์และการส่งออกข้อมูลรับรองจะรักษารหัสเดิมไว้ การนำเข้าไปยังอินสแตนซ์ที่มี ID เดียวกันอยู่แล้วสามารถแทนที่รายการที่มีอยู่เหล่านั้นได้

เผยแพร่เวิร์กโฟลว์ที่นำเข้าอย่างจงใจ

CLI การนำเข้าโดยปกติจะปล่อยให้เวิร์กโฟลว์ไม่ทำงาน ใน n8n 2.x ให้ตรวจสอบสถานะการเผยแพร่ของเวิร์กโฟลว์ที่นำเข้าแต่ละสถานะ และเผยแพร่เฉพาะเวิร์กโฟลว์ที่คุณตั้งใจจะเรียกใช้เท่านั้น เซิร์ฟเวอร์ที่โฮสต์เอง CLI ยังรองรับ n8n publish:workflow --id=YOUR_WORKFLOW_ID เมื่อ n8n ทำงานอยู่ เซิร์ฟเวอร์ CLI การเผยแพร่/ยกเลิกการเผยแพร่ การเปลี่ยนแปลงสถานะจะมีผลหลังจากรีสตาร์ท n8n เท่านั้น รีสตาร์ทก่อนที่จะตรวจสอบทริกเกอร์ที่กำหนดเวลาไว้และ webhook ที่ใช้งานจริงหรือเปลี่ยนการรับส่งข้อมูล

ตัวอย่างการส่งออกจำนวนมากสำหรับ Docker Compose: หากมีการตั้งชื่อบริการ n8n ของคุณ n8nคุณสามารถเรียกใช้การสำรองข้อมูล CLI อย่างเป็นทางการด้านล่าง เส้นทางเอาต์พุตถูกจงใจอยู่ภายในที่เมาท์แบบถาวร .n8n ไดเร็กทอรี เนื่องจากไดเร็กทอรีที่กำหนดเองภายในคอนเทนเนอร์อาจหายไปเมื่อสร้างขึ้นใหม่ ยืนยันว่าไดเร็กทอรีสามารถเขียนได้โดยผู้ใช้คอนเทนเนอร์ n8n เก็บขั้นตอนการทำงานและข้อมูลรับรอง JSON ไว้ ไดเรกทอรีแยกต่างหาก—n8n บันทึกปัญหาการนำเข้าเมื่อทั้งสองประเภทแชร์ไดเร็กทอรี

n8n 2.x ฉบับร่างกับข้อมูลสำรองที่เผยแพร่: ปกติ --backup การส่งออกเวิร์กโฟลว์จับร่างปัจจุบัน สิ่งเหล่านี้อาจแตกต่างจากเวอร์ชันที่เผยแพร่ในการผลิต หากต้องการรักษาเวิร์กโฟลว์เวอร์ชันที่เผยแพร่จริงไว้ ให้ส่งออกเวิร์กโฟลว์แยกต่างหากโดยใช้ docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.jsonหลังจากตรวจสอบให้แน่ใจว่ามีโฟลเดอร์เอาต์พุตอยู่และสามารถเขียนได้ CLI ยังสามารถส่งออกเวอร์ชันในอดีตได้โดยใช้ --version=VERSION_ID. เก็บการจับภาพเหล่านี้นอกเซิร์ฟเวอร์ควบคู่ไปกับการสำรองข้อมูลทั้งหมด อย่าถือว่าร่าง JSON บันทึกสถานะการเผยแพร่สด

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

ที่ถูกคัดลอก ~/n8n-recovery/cli ไดเรกทอรีจะยังคงอยู่ใน VPS จนกว่าคุณจะย้ายไปยังตำแหน่งสำรองข้อมูลที่ปลอดภัยและเป็นอิสระ การส่งออกข้อมูลรับรองจะได้รับการเข้ารหัสตามค่าเริ่มต้น และต้องใช้คีย์เข้ารหัสที่ตรงกันในการนำเข้า หลีกเลี่ยงการใช้ --decrypted ยกเว้นการย้ายข้อมูลที่มีการควบคุมอย่างเข้มงวด โดยจะเขียนความลับเป็นข้อความธรรมดา ห้ามทำการส่งออกที่มีตรรกะขั้นตอนการทำงานที่ละเอียดอ่อนหรือข้อมูลรับรองไปยังพื้นที่เก็บข้อมูล GitHub สาธารณะ เทมเพลตการสำรองข้อมูลรับรอง GitHub ของบุคคลที่สามบางรายการจงใจส่งออกความลับที่ถอดรหัสแล้ว พื้นที่เก็บข้อมูลส่วนตัวเป็นการจำกัดการเข้าถึง ไม่ใช่การเข้ารหัส ตรวจสอบการตั้งค่าการส่งออกและการอนุญาตพื้นที่เก็บข้อมูลจริงของเทมเพลตทุกรายการ เข้ารหัสความลับก่อนถ่ายโอนนอกเซิร์ฟเวอร์ และหมุนเวียนข้อมูลประจำตัวใด ๆ ที่เปิดเผยผ่านการอัปโหลดข้อความธรรมดาโดยไม่ได้ตั้งใจ

ตัวอย่างการนำเข้าจำนวนมาก: บนเป้าหมายที่ปลอดภัย ตั้งค่าเจ้าของให้เสร็จสิ้น จัดเตรียมคีย์เข้ารหัสดั้งเดิม และตรวจสอบให้แน่ใจว่าไฟล์สำรองข้อมูลที่บันทึกไว้นั้นพร้อมใช้งานในการกู้คืน VPS ต่อไปนี้จะสร้างโฟลเดอร์ปลายทางและคัดลอกไฟล์ workflows/ และ credentials/ โฟลเดอร์ย่อยจากโฮสต์ไปยังคอนเทนเนอร์n8n ปรับเส้นทางหากเค้าโครงโวลุ่ม Docker ของคุณแตกต่าง:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

ตรวจสอบความเป็นเจ้าของไฟล์และการเข้าถึงสำหรับผู้ใช้คอนเทนเนอร์ n8n อย่านำเข้าผ่านอินสแตนซ์การใช้งานจริงที่มีประชากรโดยไม่มีการย้อนกลับที่ได้รับการยืนยัน: เวิร์กโฟลว์และรหัสประจำตัวสามารถเขียนทับรายการที่มีอยู่ได้ จากนั้นเรียกใช้:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

รหัสที่นำเข้าสามารถแทนที่เวิร์กโฟลว์หรือข้อมูลประจำตัวที่มีอยู่ได้ ใช้อินสแตนซ์การทดสอบแบบแยกสำหรับการทดลองเรียกใช้ และตรวจสอบข้อมูลรับรองและสถานะการเปิดใช้งาน/การเผยแพร่ในภายหลัง ใน n8n 2.x การกู้คืนร่าง JSON ไม่ได้พิสูจน์ด้วยตัวเองว่าเวิร์กโฟลว์ได้รับการเผยแพร่แล้ว และสามารถเรียกใช้ทริกเกอร์ที่กำหนดเวลาไว้ได้ ความปลอดภัยในการนำเข้า: บนอินสแตนซ์ n8n ที่ไม่ใช่หลายหลัก ทริกเกอร์ cron ที่ใช้งานอยู่ก่อนหน้านี้สามารถทำงานต่อไปได้หลังจากการนำเข้า CLI จนกว่าอินสแตนซ์จะรีสตาร์ท หยุดหรือแยกทริกเกอร์การผลิตและรีสตาร์ท n8n ก่อนที่จะเปิดใช้งานงานที่กู้คืน ตรวจสอบว่าไม่มีการดำเนินการซ้ำกัน CLI การส่งออกทำ ไม่ ประกอบด้วยผู้ใช้ดั้งเดิม บันทึกการดำเนินการ ตัวแปรอินสแตนซ์ หรือคีย์การเข้ารหัส --backup ชุด --all --pretty --separateไม่ใช่ 'ตัวอย่างทั้งหมด' แหล่งที่มา: คู่มือการสำรองข้อมูล/กู้คืน n8n อย่างเป็นทางการในปัจจุบัน และการอ้างอิงคำสั่ง n8n CLI

การกู้คืนจำนวนมากจาก GitHub หรือเทมเพลต Google Drive: นี่เป็นทางเลือกสำหรับเวิร์กโฟลว์ JSON เท่านั้น ไม่ใช่สำหรับฐานข้อมูลอินสแตนซ์ ผู้ใช้ ค่าข้อมูลรับรองที่เข้ารหัส หรือคีย์การเข้ารหัส ก่อนที่จะเรียกใช้เทมเพลตที่ใช้ API ให้ตรวจสอบสิทธิ์ n8n API และการอนุญาตพื้นที่เก็บข้อมูล เวอร์ชันสำรองที่เลือกและอินสแตนซ์เป้าหมาย ไม่ว่าจะอัปเดต ID ที่ตรงกันและสร้างเวิร์กโฟลว์ที่ถูกลบขึ้นมาใหม่ หรือไม่ และสิ่งที่ทำกับการเผยแพร่เวิร์กโฟลว์ ไม่ใช่ทุกเทมเพลตที่สร้าง ID ที่หายไปจากเป้าหมายขึ้นมาใหม่ ทดสอบสถานการณ์นั้นแยกกันก่อนที่จะใช้การกู้คืนอัตโนมัติ

คำถามที่พบบ่อย

การสำรองและกู้คืน n8n: คำถามที่พบบ่อย

การส่งออกเวิร์กโฟลว์เพียงพอที่จะสำรองข้อมูล n8n หรือไม่

ไม่ การส่งออกเวิร์กโฟลว์เป็นสำเนาเชิงตรรกะที่มีประโยชน์ แต่การกู้คืนที่สมบูรณ์อาจต้องใช้ข้อมูลประจำตัว คีย์การเข้ารหัสที่ตรงกัน สถานะฐานข้อมูล ไฟล์ถาวร และพื้นที่จัดเก็บข้อมูลไบนารี

ฉันจำเป็นต้องมีคีย์เข้ารหัส n8n หรือไม่หากฉันมีฐานข้อมูล

ใช่ หากคุณต้องการข้อมูลประจำตัวที่เข้ารหัสซึ่งจัดเก็บไว้ในฐานข้อมูลนั้นเพื่อให้ยังคงใช้งานได้ รักษากุญแจเดิมไว้อย่างปลอดภัย

ฉันควรสำรองข้อมูล PostgreSQL หรือส่งออกเวิร์กโฟลว์และข้อมูลรับรองหรือไม่

สำหรับการกู้คืนระบบ ให้ปกป้องฐานข้อมูลและคีย์การเข้ารหัส การส่งออกแบบลอจิคัลมีคุณค่าในฐานะการโยกย้ายเพิ่มเติมและเลเยอร์การกู้คืนแบบเลือก แทนที่จะทดแทนทุกส่วนของอินสแตนซ์

สแน็ปช็อต VPS สามารถเป็นข้อมูลสำรองเดียวของฉันได้หรือไม่

จะถือว่าเป็นชั้นการกู้คืนชั้นเดียวที่ดีกว่า เก็บสำรองข้อมูลนอกเซิร์ฟเวอร์ที่เป็นอิสระ เพื่อให้ผู้ให้บริการ บัญชี เซิร์ฟเวอร์ หรือสแน็ปช็อตล้มเหลวไม่สามารถลบจุดการกู้คืนทุกจุดในคราวเดียว

ฉันจะรู้ได้อย่างไรว่าการสำรองข้อมูลของฉันใช้งานได้?

คืนค่าในสภาพแวดล้อมการทดสอบที่ปลอดภัย ตรวจสอบการถอดรหัสข้อมูลรับรอง และเรียกใช้เวิร์กโฟลว์ตัวแทน งานสำรองข้อมูลที่ประสบความสำเร็จเพียงอย่างเดียวไม่สามารถพิสูจน์ความสามารถในการกู้คืนได้

GitHub หรือการสำรองข้อมูลเวิร์กโฟลว์ของ Google Drive มีข้อมูลลับของข้อมูลรับรองที่บันทึกไว้หรือไม่

การสำรองข้อมูล JSON เฉพาะเวิร์กโฟลว์ไม่รวมค่าลับที่จัดการโดยที่เก็บข้อมูลรับรองของ n8n หรือคีย์การเข้ารหัสอินสแตนซ์ อย่างไรก็ตาม JSON ที่ส่งออกสามารถเปิดเผยชื่อข้อมูลประจำตัวและ ID และข้อมูลลับที่พิมพ์ลงในพารามิเตอร์โหนดโดยตรง เช่น ส่วนหัวการตรวจสอบสิทธิ์ ตรวจสอบและปกป้องการส่งออก JSON ก่อนที่จะอัปโหลดหรือแชร์ สำหรับการกู้คืนแบบเต็ม ให้สำรองฐานข้อมูลและคีย์ต้นฉบับ หรือใช้การส่งออกข้อมูลรับรองที่เข้ารหัส CLI ที่รองรับด้วยการกู้คืนที่ทดสอบแล้ว เทมเพลต GitHub หรือเทมเพลต Google ไดรฟ์เฉพาะเวิร์กโฟลว์ไม่ใช่การกู้คืนความเสียหายเต็มรูปแบบ

วัตถุประสงค์การกู้คืน

กำหนด RPO และ RTO ก่อนเกิดเหตุการณ์

อาร์พีโอ คือการสูญเสียสูงสุดที่ยอมรับได้ของการเปลี่ยนแปลงล่าสุด วัดจากจุดการกู้คืนที่ใช้งานได้ใหม่ล่าสุดและจัดเก็บอย่างอิสระ งานหกชั่วโมงตามกำหนดการจะไม่สร้าง RPO หกชั่วโมงหากการส่งออกหรือการถ่ายโอนล้มเหลว อาร์ทีโอ คือค่าไฟดับสูงสุดที่ยอมรับได้ วัดผลในการเจาะลึกการคืนค่าใหม่ทั้งหมด ซึ่งรวมถึงการเรียกข้อมูลลับ การกู้คืนไฟล์ภายนอก การตรวจสอบข้อมูลประจำตัวอีกครั้ง และการเผยแพร่เวิร์กโฟลว์ที่กู้คืน ไม่ใช่แค่การเริ่มต้นคอนเทนเนอร์

ค้นหาคีย์เข้ารหัสดั้งเดิมก่อนสร้างระบบใหม่

หากกำหนดการผลิต N8N_ENCRYPTION_KEYรักษาความลับของสภาพแวดล้อมนั้นไว้ หากไม่เป็นเช่นนั้น ให้เก็บคีย์ที่สร้างขึ้นไว้ในไฟล์ .n8n/config ดั้งเดิม ตรวจสอบแหล่งที่มาที่อินสแตนซ์ที่กู้คืนใช้จริงก่อนที่จะนำเข้าข้อมูลรับรองที่เข้ารหัส คีย์ที่สร้างขึ้นใหม่ไม่สามารถถอดรหัสข้อมูลรับรองจากฐานข้อมูลเก่าได้

กำลังเปรียบเทียบผู้ให้บริการอยู่หรือไม่?

สำหรับตัวเลือกของผู้ให้บริการ การตั้งค่าเพียงคลิกเดียว ขอบเขตการสนับสนุน การสำรองข้อมูล การโยกย้าย ภูมิภาค และการปรับขนาด ให้ใช้ ดีที่สุด VPS สำหรับการเปรียบเทียบ n8n. สำหรับการกำหนดขนาดทรัพยากร ให้กลับไปที่ หลัก VPS สำหรับคำแนะนำ n8n.

n8nVPSคู่มือโครงสร้างพื้นฐานอิสระสำหรับโฮสต์เอง n8n
