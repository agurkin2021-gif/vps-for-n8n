การปรับขนาด

n8n Queue Mode

Queue Modeแยกการดำเนินการเวิร์กโฟลว์ออกจากกระบวนการ n8n หลัก อินสแตนซ์หลักรับทริกเกอร์และสร้างการดำเนินการ Redis ประสานงานคิว workerดำเนินงาน และ PostgreSQL เก็บเวิร์กโฟลว์ที่ใช้ร่วมกันและข้อมูลการดำเนินการ

การตัดสินใจที่รวดเร็ว

คุณต้องการQueue Modeจริงหรือ?

อยู่ในโหมดปกติเมื่อ

อินสแตนซ์เดียวจัดการการประมวลผลสูงสุดได้อย่างสะดวกสบาย และ CPU, RAM และเวลาในการตอบสนองของการดำเนินการยังคงมีเสถียรภาพ Queue Modeจะเพิ่มส่วนประกอบที่คุณไม่ต้องการ

พิจารณาQueue Modeเมื่อใด

การดำเนินการแบบขนานที่ยั่งยืนจะสร้างความขัดแย้ง เวลาแฝงในการดำเนินการจะเพิ่มขึ้นภายใต้ภาระงาน หรือคุณต้องเพิ่มความสามารถในการดำเนินการโดยการเรียกใช้workerหลายคน

ปรับขนาดในแนวตั้งก่อนเมื่อไร

คอขวดนั้นไม่เพียงพอ CPU หรือ RAM และอินสแตนซ์ที่ใหญ่กว่าอีกอินสแตนซ์หนึ่งยังคงสามารถตอบสนองปริมาณงานได้อย่างหมดจด

วัดผลก่อนเปลี่ยนสถาปัตยกรรม

ใช้การทำงานพร้อมกันสูงสุด CPU, RAM ระยะเวลาการดำเนินการ ความลึกของคิว และความกดดันของฐานข้อมูลเพื่อพิสูจน์การย้าย

สถาปัตยกรรม

n8n Queue Mode ทำงานอย่างไร

1 · หลักรับตัวจับเวลา webhook และคำขอเวิร์กโฟลว์ และสร้างการดำเนินการแทนการดำเนินการจริงด้วยตนเอง
2 · Redisทำหน้าที่เป็นนายหน้าข้อความ มีข้อความการดำเนินการที่รอดำเนินการเพื่อให้workerคนถัดไปสามารถอ้างสิทธิ์งานได้
3 · workerรับ ID การดำเนินการ โหลดข้อมูลเวิร์กโฟลว์จากฐานข้อมูลที่ใช้ร่วมกัน รันเวิร์กโฟลว์ และเขียนผลลัพธ์กลับ
4 · PostgreSQLจัดเตรียมเวิร์กโฟลว์ถาวรและข้อมูลการดำเนินการที่ใช้ร่วมกัน ไม่รองรับQueue Modeแบบกระจายบน SQLite

ข้อกำหนดหลัก

สิ่งที่ทุกความต้องการใช้งานในQueue Mode

Redis

กระบวนการหลักและกระบวนการของworkerทั้งหมดจำเป็นต้องเข้าถึงบริการ Redis ที่เชื่อถือได้ซึ่งใช้สำหรับการประสานงานคิว

PostgreSQL

หลักและพนักงานต้องแชร์ฐานข้อมูล Queue Modeเป็นสถาปัตยกรรมแบบกระจาย และไม่ควรได้รับการออกแบบประมาณ SQLite

การจับคู่การกำหนดค่า n8n

หลักและworkerต้องเรียกใช้Queue Modeและแบ่งปันการกำหนดค่าที่จำเป็นในการเข้าถึง Redis, PostgreSQL และข้อมูลรับรองที่เข้ารหัส

ความจุของworker

workerจำเป็นต้องมี CPU และ RAM เพียงพอสำหรับขั้นตอนการทำงานที่พวกเขาดำเนินการ การเพิ่มกระบวนการไม่ได้ลบต้นทุนทรัพยากรของการดำเนินการแต่ละครั้ง

เปิดใช้งานQueue Modeบนสแต็กที่self-hostedที่มีอยู่ ขั้นแรกให้ยืนยันว่าบริการหลัก n8n และพนักงานทุกคนสามารถเข้าถึงฐานข้อมูล PostgreSQL และ Redis เดียวกันผ่านเครือข่ายส่วนตัว ชุด EXECUTIONS_MODE=queue ทั้งหลักและworkerและอุปทาน QUEUE_BULL_REDIS_HOST=redis และ QUEUE_BULL_REDIS_PORT=6379 เมื่อ redis คือชื่อบริการการเขียนที่แท้จริงของคุณ ใช้ DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres และการจับคู่ DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER และ DB_POSTGRESDB_PASSWORD ในทุกกระบวนการ แทนที่ชื่อบริการตัวอย่างด้วยชื่อของคุณ ระบุสิ่งที่มีอยู่จริง N8N_ENCRYPTION_KEY ถึงพวกเขาทั้งหมด ห้ามเผยแพร่พอร์ตโฮสต์ Redis หรือ PostgreSQL เพียงเพื่อเชื่อมต่อคอนเทนเนอร์บนเครือข่าย Compose เดียวกัน

เรียกใช้ตัวดำเนินการ ไม่ใช่ตัวแก้ไขตัวที่สอง เพิ่มบริการworker n8n โดยใช้เวอร์ชันรูปภาพ n8n ที่ปักหมุดไว้และการตั้งค่าที่ใช้ร่วมกันเป็นหลัก แต่เรียกใช้ด้วย worker คำสั่ง หากคุณตั้งชื่อบริการนั้น n8n-worker, เริ่มต้นด้วย docker compose up -d n8n-worker. หลังจากยืนยันการดำเนินการจริงกับworkerหนึ่งรายแล้ว คุณสามารถใช้ได้ docker compose up -d --scale n8n-worker=2 เพื่อเริ่มต้นพนักงานคนที่สองจากบริการนั้น สิ่งเหล่านี้เป็นส่วนเพิ่มเติมของ มีการกำหนดค่าอย่างถูกต้องแล้ว เขียนสแต็ก ไม่ใช่ไฟล์การติดตั้งแบบสแตนด์อโลน เก็บวอลุ่มถาวรที่มีอยู่ของคุณ, HTTPS พร็อกซี, secret และbackup

ส่วนการเขียนในQueue Modeสำหรับสแต็กที่มีอยู่ รวมตัวอย่างด้านล่างเข้ากับปัจจุบันของคุณ compose.yaml; มันคือ ไม่ การใช้งานแบบสแตนด์อโลนที่สมบูรณ์ จะถือว่าคุณมีความต่อเนื่องและเป็นส่วนตัวอยู่แล้ว postgres และ n8n บริการที่มีอยู่ N8N_VERSION ปักหมุดในสภาพแวดล้อมของคุณและป้องกันตัวคุณเอง POSTGRES_PASSWORD และเป็นต้นฉบับ N8N_ENCRYPTION_KEY. จับคู่ชื่อ วอลุ่ม ฐานข้อมูล และเวอร์ชัน n8n กับโปรเจ็กต์ที่มีอยู่ เพิ่มการตั้งค่าQueue Mode Redis และ EXECUTIONS_MODE=queue ไปยังบริการหลักที่มีอยู่ตามที่อธิบายไว้ข้างต้น

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

ไม่มีการเผยแพร่พอร์ตโฮสต์สำหรับ Redis หรือworkerในส่วนนี้ Redis การคงอยู่ต่อท้ายเท่านั้นเป็นชั้นการกู้คืนเพิ่มเติม ไม่ ทดแทนbackupนอกเซิร์ฟเวอร์ คงไว้ซึ่ง HTTPS และการกำหนดค่าการรับรองความถูกต้องที่มีอยู่ไม่เปลี่ยนแปลง สำหรับโหนดโค้ดที่ต้องการตัวรันงานภายนอก ให้กำหนดค่ากระบวนการรันเนอร์สำหรับdeploymentworkerของคุณแยกกัน Queue Modeนั้นไม่ได้แทนที่ตัวรันงาน

กำลังแปลงอินสแตนซ์ SQLite ที่มีอยู่หรือไม่ อย่าเพิ่งเปลี่ยน DB_TYPE และเริ่มต้นด้วยฐานข้อมูล PostgreSQL ที่ว่างเปล่า: การทำเช่นนี้จะไม่ย้ายเวิร์กโฟลว์และข้อมูลรับรองเก่า ก่อนที่จะตัดทอนใดๆ ให้สำรองฐานข้อมูลต้นทางอย่างต่อเนื่อง .n8n ไดเร็กทอรีและคีย์เข้ารหัสดั้งเดิม ใช้ขั้นตอนการส่งออก/นำเข้าหรือการย้ายข้อมูล n8n ที่ได้รับการสนับสนุน จากนั้นตรวจสอบขั้นตอนการทำงานและข้อมูลรับรองที่เข้ารหัสบนเป้าหมายที่แยกต่างหาก เก็บไฟล์ต้นฉบับไว้สำหรับการย้อนกลับ และใช้คำแนะนำbackupและการคืนค่าตามลิงก์ด้านล่างเพื่อเตรียมการกู้คืน ไม่เคยลบ database.sqlite เป็นทางลัด

ความเห็นพ้องต้องกันของworker

workerปรับขนาดทั้งตามการนับและตามงานต่อworker

workerแต่ละคนสามารถประมวลผลงานหลายงานพร้อมกันได้ การทำงานพร้อมกันของworkerเริ่มต้นในปัจจุบันของ n8n คือ 10 และเอกสารประกอบแนะนำการทำงานพร้อมกันของ 5 หรือสูงกว่า การทำงานพร้อมกันที่ต่ำมากเมื่อรวมกับworkerจำนวนมากสามารถสร้างการเชื่อมต่อฐานข้อมูลที่ไม่จำเป็น และทำให้พูลการเชื่อมต่อฐานข้อมูลหมดลง

เพิ่มการทำงานพร้อมกันเมื่อ

workerมีอะไหล่ CPU และ RAM และเวิร์กโฟลว์ส่วนใหญ่กำลังรอบริการภายนอก แทนที่จะทำให้คอมพิวเตอร์หรือหน่วยความจำอิ่มตัว

เพิ่มworkerเมื่อ

กระบวนการของworkerคนหนึ่งกลายเป็นคอขวดและฐานข้อมูล Redis และโครงสร้างพื้นฐานมีความสามารถในการดำเนินการแบบขนานมากขึ้น

ลดภาวะพร้อมกันเมื่อ

เวิร์กโฟลว์ส่วนบุคคลมีหน่วยความจำหนักหรืองาน CPU หนักและงานคู่ขนานทำให้เกิดความขัดแย้ง OOM ความกดดัน หรือเวลาดำเนินการไม่เสถียร

ดู PostgreSQL

workerมากขึ้นและการทำงานพร้อมกันมากขึ้นทำให้กิจกรรมฐานข้อมูลเพิ่มขึ้น การปรับขนาดความสามารถในการดำเนินการโดยไม่มีความจุของฐานข้อมูลสามารถย้ายปัญหาคอขวดแทนที่จะลบออก

รู้ว่าขีดจำกัดการทำงานพร้อมกันแบบใดที่นำไปใช้จริง workerสามารถเริ่มใช้งานได้ n8n worker --concurrency=5หรือคำสั่งของworkerที่เทียบเท่าในบริการเขียนของคุณ ถ้า N8N_CONCURRENCY_PRODUCTION_LIMIT ถูกตั้งค่าอย่างชัดเจนเป็นค่าอื่นที่ไม่ใช่ -1การตั้งค่านั้นจะมีความสำคัญเหนือกว่าในQueue Mode มิฉะนั้น n8n จะใช้ของworker --concurrency ค่าหรือค่าเริ่มต้นของ 10 อย่าคูณจำนวนworkerด้วยค่าเริ่มต้นที่ระบุ และเรียกมันว่าปริมาณงานที่รับประกัน: ความจุจริงขึ้นอยู่กับระยะเวลางาน, CPU, หน่วยความจำ, API ภายนอก และการเชื่อมต่อ PostgreSQL

webhook

Queue Modeสามารถเพิ่มเวลาแฝงในการดำเนินการแฮนด์ออฟได้

กระบวนการหลักหรือกระบวนการwebhookได้รับคำขอ HTTP แต่workerดำเนินการตามเวิร์กโฟลว์ การส่งมอบผ่าน Redis นั้นเพิ่มค่าใช้จ่ายบางส่วน สำหรับwebhookที่ไวต่อเวลาในการตอบสนอง ให้วัดเวลาตอบสนองตั้งแต่ต้นทางถึงปลายทาง แทนที่จะคิดว่าworkerจำนวนมากขึ้นจะทำให้ทุกคำขอเร็วขึ้นโดยอัตโนมัติ

รับกระบวนการหลัก/webhookยอมรับคำขอ
คิวการดำเนินการถูกส่งไปยัง Redis
ดำเนินการworkerที่พร้อมใช้งานดำเนินการเวิร์กโฟลว์
ตอบกลับผลลัพธ์จะถูกส่งกลับผ่านเส้นทางคิวเมื่อจำเป็น

กำหนดเส้นทางการรับส่งข้อมูลwebhookไปยังกระบวนการที่ถูกต้อง ด้วยความทุ่มเท n8n webhook โปรเซสเซอร์ที่อยู่ด้านหลังreverse proxyหรือโหลดบาลานเซอร์ จะกำหนดเส้นทางเส้นทางการผลิต /webhook/* และ /webhook-waiting/* ไปยังโปรเซสเซอร์ webhook; เก็บ /webhook-test/*บรรณาธิการและคำร้องขอ API บนหน้าหลัก อย่าใส่ main ลงในพูลการปรับสมดุลโหลดของ webhook ที่ใช้งานจริง เว้นแต่คุณจะยอมรับภาระงานที่เพิ่มเข้ามานั้นโดยเจตนา ก ตอบกลับ Webhook เวิร์กโฟลว์อาจทำให้ไคลเอนต์รอจนกว่าworkerจะเสร็จสิ้นและส่งกลับการตอบกลับ ดังนั้นQueue Modeจึงไม่ใช่การรับประกันว่าจะมีการตอบกลับ HTTP ทันทีหรือการหมดเวลาเป็นศูนย์ ทดสอบพฤติกรรมการโทรกลับและการตอบสนองภายนอกจริงก่อนที่จะเปลี่ยนการรับส่งข้อมูล

ข้อมูลไบนารี

อย่ามองข้ามที่เก็บข้อมูลที่ใช้ร่วมกัน

ข้อจำกัดของระบบไฟล์

Queue Modeไม่รองรับการจัดเก็บข้อมูลไบนารีของระบบไฟล์เป็นรูปแบบการคงอยู่ที่ใช้ร่วมกันสำหรับworkerแบบกระจาย

ที่เก็บข้อมูลไบนารีภายนอก

เมื่อเวิร์กโฟลว์ต้องคงข้อมูลไบนารีไว้กับworkerแบบกระจาย ให้ใช้การออกแบบพื้นที่จัดเก็บข้อมูลที่ทุกอินสแตนซ์ที่จำเป็นสามารถเข้าถึงได้ เช่น พื้นที่จัดเก็บออบเจ็กต์ภายนอกที่รองรับ

การตอบกลับwebhookขนาดใหญ่

การตอบกลับของ Webhook จากworkerจะเดินทางกลับไปยังกระบวนการรับ เนื้อหาการตอบสนองขนาดใหญ่สามารถเพิ่มแรงกดดันของหน่วยความจำ Redis และต้องมีการกำหนดค่าการจัดเก็บการตอบสนองโดยเจตนา

วางแผนก่อนกระจายworker

เวิร์กโหลดที่ขึ้นอยู่กับไฟล์ในเครื่องอย่างมากจะต้องได้รับการออกแบบใหม่เพื่อการคงอยู่ร่วมกันก่อนที่workerจะกระจายไปตามเครื่อง

ขอบเขตการตอบกลับwebhookขนาดใหญ่ เอกสาร n8n ปัจจุบันให้ไว้ N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX ค่าเริ่มต้นของ 64 MiB สำหรับการตอบกลับของพนักงานที่ส่งกลับทางคิว Redis สามารถเก็บสำเนาได้หลายชุด ดังนั้นงบประมาณประมาณ 1.5 คูณด้วยขนาดการตอบสนองในหน่วยความจำ Redis ต่อการตอบกลับจำนวนมากพร้อมกัน หากไม่มีการถ่ายข้อมูล การตอบสนองขนาดใหญ่จะล้มเหลว แทนที่จะเร็วขึ้นอย่างน่าอัศจรรย์ด้วยการเพิ่มworker

เวอร์ชันและขีดจำกัดใบอนุญาต จาก n8n 2.34.0,workerก็ใช้ได้ N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true เพื่อถ่ายโอนเนื้อหาการตอบสนองของ webhook ขนาดใหญ่ไปยังพื้นที่เก็บข้อมูลไบนารีที่ใช้ร่วมกันที่อ่านได้ แต่ต้องอัปเกรดก่อน โปรเซสเซอร์หลักและwebhookทุกตัว ถึง 2.34.0 หรือใหม่กว่า ที่เลือก N8N_DEFAULT_BINARY_DATA_MODE จะต้องเก็บข้อมูลจริงและสามารถอ่านได้ทุกกระบวนการที่เข้าร่วม ที่เก็บข้อมูลไบนารี S3 และ Azure ภายนอกจำเป็นต้องมีการself-hostedที่ถูกต้อง ธุรกิจหรือองค์กร ใบอนุญาต; อย่าถือว่า Community Edition สามารถเปิดใช้งานได้ ที่ database โหมดไบนารี่สามารถถ่ายการตอบสนองที่มากเกินไปโดยไม่ต้องใช้พื้นที่จัดเก็บข้อมูลภายนอกแบบชำระเงิน แต่อินสแตนซ์หลักจะโหลดเนื้อหาที่จัดเก็บไว้ทั้งหมดลงในหน่วยความจำ และพื้นที่จัดเก็บฐานข้อมูลก็มีขีดจำกัดขนาดไฟล์ของตัวเอง สำหรับ การลดภาระการตอบสนองของร่างกายโดยเฉพาะ, n8n ยังอธิบายถึงการแบ่งปัน filesystem ตัวเลือกเมื่อทุกอินสแตนซ์เมานต์ดิสก์เดียวกัน แต่ไม่แนะนำการจัดเรียงดังกล่าวอย่างชัดเจน อย่าเข้าใจผิดว่าพาธออฟโหลดพิเศษนี้เพื่อรองรับข้อมูลไบนารีถาวรที่ใช้ระบบไฟล์ในdeploymentQueue Modeแบบกระจาย ตรวจสอบรุ่น เวอร์ชัน และการกำหนดค่าพื้นที่เก็บข้อมูลของคุณก่อนเปิดใช้งานออฟโหลด

การตรวจสอบ

รู้ว่าคิวช่วยหรือไม่

ความลึกของคิว

คิวที่เติบโตเร็วกว่าที่พนักงานระบายออกไป บ่งชี้ว่ามีความสามารถในการดำเนินการไม่เพียงพอหรือเกิดปัญหาคอขวดในดาวน์สตรีม

worker CPU & RAM

วัดความอิ่มตัวและจุดสูงสุดของหน่วยความจำต่อพนักงาน workerที่ไม่ได้ใช้งานซึ่งมีคิวเพิ่มขึ้นเรื่อยๆ ชี้ไปที่ข้อจำกัดอื่น

เวลาแฝงในการดำเนินการ

ติดตามความล่าช้าระหว่างการดำเนินการที่กำลังสร้างและการเริ่มต้นจริง ไม่ใช่แค่รันไทม์ของเวิร์กโฟลว์เท่านั้น

การตรวจสุขภาพ

endpointด้านสุขภาพของworkerสามารถรายงานว่าworkerยังมีชีวิตอยู่หรือไม่ และฐานข้อมูลและการเชื่อมต่อ Redis พร้อมหรือไม่

ตรวจสอบการดำเนินการกับworker ไม่ใช่แค่คอนเทนเนอร์สีเขียว ตรวจสอบด้วย Stack Compose ที่กำหนดค่าอย่างถูกต้อง docker compose ps และ docker compose logs --tail=100 n8n-worker (เปลี่ยนชื่อบริการหากแตกต่าง) วิ่งแบบไม่เป็นอันตราย การผลิตที่ตีพิมพ์ เวิร์กโฟลว์ที่ใช้ทริกเกอร์ตามกำหนดการหรือทดสอบ webhook จากนั้นจับคู่การดำเนินการในมุมมองการดำเนินการของ n8n กับการประมวลผลของworkerจริงในบันทึกของworker ตัวแก้ไขที่เปิดได้สำเร็จ คอนเทนเนอร์ Redis ที่ทำงานอยู่หรือการดำเนินการในคิวเพียงอย่างเดียวก็ทำได้ ไม่ พิสูจน์ว่าworkerได้ปฏิบัติงานแล้ว

ตรวจสอบการพึ่งพาและความพร้อม ด้วยชื่อบริการตัวอย่างเริ่มต้น docker compose exec -T redis redis-cli ping ควรได้รับ PONG เมื่อ Redis การรับรองความถูกต้องอนุญาต และ docker compose exec -T postgres pg_isready -U n8n -d n8n ตรวจสอบความพร้อม PostgreSQL (ปรับข้อมูลรับรองและชื่อบริการ) เปิดใช้งาน QUEUE_HEALTH_CHECK_ACTIVE=true กับworkerเมื่อคุณต้องการความเป็นส่วนตัว /healthz และ /healthz/readiness endpoint; endpointความพร้อมจะตรวจสอบ Redis/การเชื่อมต่อฐานข้อมูล อย่าเปิดเผยendpointของworkerเหล่านั้นต่อสาธารณะเพียงเพื่อตรวจสอบเท่านั้น

การวิ่งด้วยตนเองเป็นการทดสอบที่แตกต่างออกไป ตามค่าเริ่มต้น OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=falseดังนั้นการรันเวิร์กโฟลว์ในเอดิเตอร์ด้วยตนเองจึงสามารถดำเนินการบน main ได้ แม้ว่าQueue Modeจะได้รับการกำหนดค่าอย่างถูกต้องก็ตาม ตั้งเป็น true เฉพาะในกรณีที่คุณต้องการส่งการดำเนินการด้วยตนเองไปยังworkerและได้ตรวจสอบการเปลี่ยนแปลงในสภาพแวดล้อมชั่วคราวแล้วเท่านั้น workerในQueue Modeยังแตกต่างจาก n8n ตัวดำเนินการงานภายนอก ซึ่งมีข้อกำหนดการกำหนดค่าแยกต่างหากสำหรับการดำเนินการโหนดโค้ด

เส้นทางการปรับขนาด

ปรับขนาดคอขวดทีละรายการ

ด่าน 1อินสแตนซ์ n8n เดี่ยวที่มี PostgreSQL; วัดจุดสูงสุด CPU, RAM และการทำงานพร้อมกัน
ด่าน 2เพิ่มทรัพยากร VPS เมื่อมาตราส่วนแนวตั้งยังคงแก้ปัญหาคอขวดที่วัดได้หมดจด
ด่าน 3แนะนำ Redis และworkerเมื่อความต้องการแบบขนานที่ยั่งยืนแสดงให้เห็นถึงการดำเนินการแบบกระจาย
ด่าน 4เพิ่มworkerหรือปรับแต่งการทำงานพร้อมกันของworkerขณะรับชม PostgreSQL, Redis และเวลาแฝงในการดำเนินการ
ด่าน 5แยกส่วนประกอบระหว่างเซิร์ฟเวอร์เฉพาะเมื่อความจุ ความพร้อมใช้งาน หรือข้อกำหนดในการดำเนินงานแสดงให้เห็นถึงความซับซ้อนที่เพิ่มเข้ามา
เลือกความจุ VPS เพิ่มเติมเมื่อจำเป็นต้องปรับขนาด

ลิงค์พันธมิตร: เราอาจได้รับค่าคอมมิชชั่นจากการซื้อ

ขอบเขตความพร้อมใช้งานสูง

Queue Modeจะปรับขนาดการดำเนินการ แต่ไม่ได้ทำให้กระบวนการหลักมีความพร้อมใช้งานสูงโดยอัตโนมัติ

แบ่งปันคีย์การเข้ารหัส

workerทุกคนต้องใช้เหมือนกัน N8N_ENCRYPTION_KEY เป็นอินสแตนซ์หลักเพื่อให้workerสามารถถอดรหัสข้อมูลรับรองที่จำเป็นสำหรับการดำเนินการเวิร์กโฟลว์

ให้เวอร์ชันต่างๆ สอดคล้องกัน

กระบวนการหลัก webhook และกระบวนการของworkerควรใช้เวอร์ชัน n8n เดียวกัน เวอร์ชันผสมสามารถสร้างลักษณะการทำงานที่เข้ากันไม่ได้ระหว่างการเปลี่ยนแปลงแบบต่อเนื่อง

โปรเซสเซอร์ Webhook เป็นเลเยอร์สเกลที่แยกจากกัน

เมื่อวอลลุม Webhook ขาเข้ากลายเป็นปัญหาคอขวด ตัวประมวลผล Webhook เฉพาะด้านสามารถอยู่ข้างหลังโหลดบาลานเซอร์ในขณะที่workerจัดการการดำเนินการ อย่าเพิ่มเลเยอร์นี้ เว้นแต่ปริมาณคำขอที่วัดได้จะทำให้เลเยอร์นี้สมเหตุสมผล

Multi-main เป็นคุณสมบัติที่แตกต่าง

การรันกระบวนการหลักหลายกระบวนการเพื่อความพร้อมใช้งานสูงนั้นไม่เหมือนกับQueue Modeทั่วไป n8n ปัจจุบันจัดทำเอกสารหลายหลักเป็นคุณลักษณะองค์กรที่self-hosted พร้อมด้วยตัวโหลดบาลานซ์และข้อกำหนดเซสชันเพิ่มเติม

สถาปัตยกรรมและการกำหนดค่าQueue Modeอย่างเป็นทางการ

คำถามที่พบบ่อย

n8n Queue Mode: คำถามทั่วไป

n8n Queue Mode ต้องใช้ Redis หรือไม่

ใช่ Redis คือนายหน้าข้อความที่ประสานการดำเนินการที่รอดำเนินการระหว่างอินสแตนซ์หลักและworker

Queue Modeสามารถใช้ SQLite ได้หรือไม่

ไม่ใช่สำหรับสถาปัตยกรรมQueue Modeแบบกระจาย หลักและworkerจำเป็นต้องเข้าถึงฐานข้อมูลที่ใช้ร่วมกัน และ n8n เอกสาร PostgreSQL เป็นฐานข้อมูลสำหรับการตั้งค่านี้

ฉันควรมีworkerกี่คน?

ไม่มีการนับสากล เริ่มต้นจากการทำงานพร้อมกันที่วัดได้และการใช้งานของworker จากนั้นเพิ่มความจุในขณะที่ตรวจสอบ PostgreSQL, Redis, CPU, RAM และความลึกของคิว

n8n การทำงานพร้อมกันของworkerคืออะไร

เป็นจำนวนงานที่พนักงานอาจดำเนินการควบคู่กันไป ค่าเริ่มต้นปัจจุบันคือ 10 และ n8n แนะนำการทำงานพร้อมกันของworkerที่ 5 หรือสูงกว่า แทนที่จะสร้างworkerที่ทำงานพร้อมกันต่ำจำนวนมาก

ฉันควรเปิดใช้งานQueue Modeใน VPS ขนาดเล็กหรือไม่

เฉพาะเมื่อปริมาณงานเหมาะสมเท่านั้น deploymentขนาดเล็กที่ทำงานอย่างสะดวกสบายด้วยอินสแตนซ์เดียวมักจะดำเนินการได้ง่ายกว่าโดยไม่ต้องใช้ Redis และแยกworker

เปรียบเทียบผู้ให้บริการ?

สำหรับตัวเลือกของผู้ให้บริการ การตั้งค่าเพียงคลิกเดียว ขอบเขตการสนับสนุน backup การโยกย้าย ภูมิภาค และการปรับขนาด ให้ใช้ ดีที่สุด VPS สำหรับการเปรียบเทียบ n8n. สำหรับการกำหนดขนาดทรัพยากร ให้กลับไปที่ หลัก VPS สำหรับคำแนะนำ n8n.
