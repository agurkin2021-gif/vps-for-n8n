ปลอดภัย n8n บน VPS

เพื่อความปลอดภัยของ n8n บน VPS ให้เก็บ n8n (5678), PostgreSQL (5432) และตัวเลือก Redis (6379) ออกจากอินเทอร์เน็ตสาธารณะ ใช้ HTTPS Reverse Proxy, คีย์ SSH และ MFA, รักษาคีย์การเข้ารหัสของคุณ, ตรวจสอบความถูกต้องของ Webhooks, จำกัดความสามารถด้านเวิร์กโฟลว์ที่มีความเสี่ยง และตรวจสอบอินสแตนซ์ที่ปรับใช้ ปกป้องตัวแก้ไขแยกจากเส้นทางwebhookสาธารณะ HTTPS เพียงอย่างเดียวไม่สามารถรักษาความปลอดภัยของบริการที่เชื่อมต่อได้

เลือก VPS สำหรับ n8n

ลิงค์พันธมิตร: เราอาจได้รับค่าคอมมิชชั่นจากการซื้อ

รายการตรวจสอบด่วน

พื้นฐานความปลอดภัยขั้นต่ำก่อนการเปิดเผยสู่สาธารณะ

เริ่มต้นด้วยพอร์ตที่เข้าถึงได้ของคุณ HTTPS การเข้าถึงระดับผู้ดูแลระบบที่ได้รับการตรวจสอบ MFA และการปกป้องข้อมูลรับรองที่บันทึกไว้ ตรวจสอบสิทธิ์webhookขาเข้าแต่ละรายการก่อนที่จะทริกเกอร์การทำงานที่มีความละเอียดอ่อน หลังจากเปลี่ยนการควบคุมการเข้าถึง ให้ตรวจสอบว่าผู้แก้ไขที่ต้องการและการผสานการทำงานภายนอกยังคงใช้งานได้ จากนั้นจึงเรียกใช้การตรวจสอบความปลอดภัย n8n

HTTPS เท่านั้น

วาง n8n ไว้ด้านหลังreverse proxy TLS ที่กำหนดค่าอย่างถูกต้อง และใช้ URL HTTPS สาธารณะอย่างสม่ำเสมอสำหรับตัวแก้ไขและ webhooks

พอร์ตเปิดน้อยที่สุด

เปิดเผยเฉพาะพอร์ตที่จำเป็นสำหรับการรับส่งข้อมูลสาธารณะ เก็บ PostgreSQL, Redis และพอร์ตแอปพลิเคชันภายในออกจากอินเทอร์เน็ตสาธารณะ

ฮาร์เดน SSH

ใช้การดูแลระบบตามคีย์ จำกัดผู้ที่สามารถเข้าสู่ระบบและรักษาระบบปฏิบัติการให้ได้รับการแก้ไข

ปกป้องข้อมูลรับรอง

รักษาคีย์การเข้ารหัส n8n ให้เสถียรและเป็นsecret ถือว่าไฟล์สภาพแวดล้อม การเข้าถึงฐานข้อมูล และสำเนาสำรองเป็นสินทรัพย์ที่ละเอียดอ่อน

ขอบเครือข่าย

Reverse proxy, HTTPS และส่วนหัวที่เชื่อถือได้

TLS การสิ้นสุด

ใช้reverse proxy เช่น Nginx, Caddy หรือ Traefik เพื่อยุติ HTTPS เปลี่ยนเส้นทางธรรมดา HTTP และหลีกเลี่ยงการเปิดเผยพอร์ตแอปพลิเคชัน n8n โดยตรงเมื่อพร็อกซีเป็นจุดเข้าที่ต้องการ

การกำหนดค่าพร็อกซี

เมื่อ n8n ทำงานอยู่หลังreverse proxy ให้กำหนดค่าจำนวนพร็อกซีฮอปอย่างถูกต้อง และส่งส่วนหัวที่ส่งต่อ n8n จำเป็นต้องสร้างคำขอไคลเอ็นต์ดั้งเดิมขึ้นมาใหม่

คุกกี้ที่ปลอดภัย

ใช้งานตัวแก้ไขบน HTTPS เพื่อให้คุกกี้การตรวจสอบความถูกต้องยังคงปลอดภัย อย่าแก้ไขการตั้งค่า TLS ที่เสียหายโดยการลดความปลอดภัยของคุกกี้

URL ของwebhook

ตั้งค่า URL ของwebhookสาธารณะเป็นชื่อโฮสต์ HTTPS ที่เข้าถึงได้จากภายนอก เพื่อให้endpointของwebhookที่สร้างขึ้นไม่ชี้ไปที่คอนเทนเนอร์ภายในหรือที่อยู่ HTTP

รักษาความเป็นส่วนตัวของตัวแก้ไขโดยไม่ทำให้webhookเสียหาย จำกัดการเข้าถึงการจัดการโดยใช้ VPN, นโยบาย IP ที่เชื่อถือได้ หรือพร็อกซีที่ได้รับการรับรองความถูกต้องเมื่อใช้งานได้จริง ตัวรับwebhookสาธารณะและเส้นทางการเรียกกลับ OAuth อาจต้องยังคงเข้าถึงได้ ทดสอบทั้งการลงชื่อเข้าใช้ตัวแก้ไขที่เชื่อถือได้และการโทรกลับภายนอกจริงก่อนที่จะบังคับใช้กฎพร็อกซี ส่งต่อส่วนหัวที่อยู่ไคลเอ็นต์จากพร็อกซีที่เชื่อถือได้เท่านั้น ไม่ใช่ส่วนหัวคำขอที่กำหนดเอง

ตรวจสอบสิทธิ์ผู้โทรผ่าน webhook: ในโหนด Webhook ให้เลือกการตรวจสอบสิทธิ์ Basic, Header หรือ JWT แทน None เมื่อผู้ส่งรองรับ ใช้มัน รายการที่อนุญาตของ IP ตัวเลือกตามความเหมาะสม และตรวจสอบลายเซ็นของผู้ให้บริการในกรณีที่การบูรณาการรองรับคำขอที่ลงนาม URL ที่คาดเดายากไม่เพียงพอในการตรวจสอบสิทธิ์ ใช้การจำกัดอัตราที่พร็อกซีตามความเหมาะสม และยืนยันว่าไม่มีการบล็อกการระเบิดที่ถูกต้อง ตัวเลือกการตรวจสอบสิทธิ์ Webhook อย่างเป็นทางการ

VPS การแข็งตัว

ลดพื้นผิวการโจมตีเซิร์ฟเวอร์

ไฟร์วอลล์

ปฏิเสธการรับส่งข้อมูลขาเข้าที่ไม่พึงประสงค์โดยค่าเริ่มต้น และอนุญาตเฉพาะบริการที่ต้องสามารถเข้าถึงได้เท่านั้น โดยปกติแล้วพอร์ตฐานข้อมูลและ Redis จะอยู่ในเครือข่ายส่วนตัว/ท้องถิ่น

SSH

ต้องการใช้คีย์ SSH มากกว่ารหัสผ่าน ปิดการใช้งานเส้นทางการเข้าสู่ระบบที่ไม่จำเป็น และจำกัดการเข้าถึงของผู้ดูแลระบบ การเข้าถึงที่เทียบเท่ากับรูทควรได้รับการควบคุมอย่างเข้มงวด

การอัปเดตระบบปฏิบัติการ

แก้ไขโฮสต์ Linux และรันไทม์คอนเทนเนอร์ การทำให้แอปพลิเคชันแข็งแกร่งขึ้นไม่สามารถชดเชยระบบปฏิบัติการที่เปิดเผยหรือล้าสมัยได้

การสัมผัสภาชนะ

เผยแพร่เฉพาะพอร์ตที่ต้องการการเข้าถึงโฮสต์ บริการภายในควรสื่อสารบนเครือข่าย Docker ส่วนตัว แทนที่จะสื่อสารผ่านอินเทอร์เฟซสาธารณะ

ตรวจสอบก่อนเปลี่ยนไฟร์วอลล์หรือการตั้งค่า SSH: ตรวจสอบพอร์ตการฟังด้วย sudo ss -lntp, Docker การเผยแพร่ด้วย docker compose ps จากไดเร็กทอรีโครงการและนโยบายไฟร์วอลล์โฮสต์ด้วย sudo ufw status verbose ถ้าใช้ UFW ตรวจสอบพอร์ต SSH จริงของคุณและการเข้าสู่ระบบด้วยรหัสที่สำเร็จในเซสชันแยกต่างหากก่อนที่จะปิดใช้งานการเข้าถึงด้วยรหัสผ่าน พอร์ต Docker ที่เผยแพร่สามารถข้ามกฎ UFW ได้ หน้าสถานะไฟร์วอลล์เพียงอย่างเดียวไม่ได้พิสูจน์ว่าพอร์ต 5678 เป็นแบบส่วนตัว ตรวจสอบความสามารถในการเข้าถึงภายนอกที่แท้จริง Docker/คำเตือน UFW

ตรวจสอบการอัปเดตความปลอดภัย Ubuntu อัตโนมัติแทนที่จะคิดว่าใช้งานได้: ตรวจสอบ apt-config dump APT::Periodic::Unattended-Upgrade และบันทึก /var/log/unattended-upgrades/unattended-upgrades.log. หากปิดใช้งานการอัพเกรดความปลอดภัยแบบอัตโนมัติ sudo dpkg-reconfigure unattended-upgrades จัดเตรียมกล่องโต้ตอบการกำหนดค่าที่รองรับ ตรวจสอบพฤติกรรมการรีบูตและการรีสตาร์ทบริการก่อนเปิดใช้งานใน VPS ที่ใช้งานได้ Ubuntu การอัปเดต APT ทำ ไม่ อัปเดตอิมเมจ n8n Docker หรือคลังซอฟต์แวร์บุคคลที่สามทุกรายการโดยอัตโนมัติ Ubuntu เอกสารการอัปเดตอัตโนมัติ

ตัวเลือก SSH การตรวจสอบกำลังดุร้าย: Fail2Ban สามารถตรวจจับการเข้าสู่ระบบ SSH ที่ล้มเหลวซ้ำแล้วซ้ำอีก หากติดตั้งและกำหนดค่าสำหรับ SSH ให้ตรวจสอบคุกด้วย sudo fail2ban-client status sshd และยืนยันว่าได้อ่านบันทึกการรับรองความถูกต้อง SSH หรือบันทึกประจำวันของคุณ และตรงกับพอร์ตที่กำหนดค่าไว้ สิ่งนี้เป็นส่วนเสริมคีย์ SSH และข้อจำกัดของเครือข่าย มันไม่ได้แทนที่พวกเขา อย่าคัดลอกพอร์ต SSH หรือกฎการแบนคงที่โดยไม่ตรวจสอบการเข้าถึงที่มีอยู่ก่อน Ubuntu SSH คำแนะนำในการทำให้แข็งตัว

ฐานข้อมูลและ REDIS

รักษาบริการแบ็กเอนด์ให้เป็นส่วนตัว

ในการตั้งค่า Docker Composeทั่วไป PostgreSQL และQueue Mode Redis ควรสามารถเข้าถึงได้โดยคอนเทนเนอร์ที่เกี่ยวข้องผ่านเครือข่ายส่วนตัว ไม่ใช่พอร์ตที่เผยแพร่โดยโฮสต์ ยืนยันด้วย docker compose ps 5432 และ 6379 ไม่ได้ถูกเผยแพร่สู่สาธารณะ ตรวจสอบ VPS/การเปิดเผยไฟร์วอลล์คลาวด์แยกต่างหาก นโยบายเครือข่ายไม่สามารถทดแทนข้อมูลรับรองฐานข้อมูลที่มีสิทธิ์น้อยที่สุด

PostgreSQLเชื่อมโยงกับอินเทอร์เฟซส่วนตัวหรือเครือข่ายคอนเทนเนอร์ เว้นแต่จำเป็นต้องมีการเข้าถึงระยะไกลอย่างชัดเจนและมีความปลอดภัยโดยอิสระ
RedisQueue Mode Redis เป็นโครงสร้างพื้นฐาน ไม่ใช่endpointสาธารณะ จำกัดการเข้าถึงเครือข่ายสำหรับส่วนประกอบ n8n ที่ต้องการ
ข้อมูลรับรองใช้ข้อมูลรับรองฐานข้อมูลเฉพาะโดยมีสิทธิ์ที่แอปพลิเคชันต้องการเท่านั้น และปกป้องสิทธิ์เหล่านั้นภายนอกการควบคุมแหล่งที่มา
ขนส่งเมื่อการรับส่งข้อมูลฐานข้อมูลข้ามเครือข่ายที่ไม่น่าเชื่อถือ ให้ใช้การขนส่งที่เข้ารหัสที่เหมาะสม แทนที่จะอาศัยการเข้ารหัสข้อมูลรับรองระดับแอปพลิเคชัน

คีย์การเข้ารหัส

n8n เข้ารหัสข้อมูลประจำตัวที่เก็บไว้โดยใช้คีย์การเข้ารหัส รักษาคีย์เดียวกันในการรีสตาร์ทและworker และปกป้องคีย์นั้นแยกต่างหากจากเนื้อหาแอปพลิเคชันทั่วไป

secretด้านสิ่งแวดล้อม

อย่าส่งรหัสผ่าน โทเค็น หรือคีย์การเข้ารหัสไปยังพื้นที่เก็บข้อมูลสาธารณะ จำกัดการเข้าถึงไฟล์สภาพแวดล้อมและsecretในdeployment

การเข้าถึงของผู้ใช้

ให้สิทธิ์การเข้าถึงแก่ผู้แก้ไขเฉพาะผู้ใช้ที่เชื่อถือได้เท่านั้น เวิร์กโฟลว์สามารถเชื่อมต่อกับระบบที่มีความละเอียดอ่อน และอาจประมวลผลsecretหรือดำเนินการโหนดที่ทรงพลัง

ขอบเขตข้อมูลรับรอง

ใช้บัญชีบริการที่มีขอบเขตจำกัดและโทเค็น API หากเป็นไปได้ เวิร์กโฟลว์ที่ถูกบุกรุกไม่ควรสืบทอดการเข้าถึงระบบที่ไม่เกี่ยวข้องในวงกว้างโดยอัตโนมัติ

n8n การกำหนดค่าที่ต้องตรวจสอบ: N8N_BLOCK_ENV_ACCESS_IN_NODE=true ป้องกันการเข้าถึงโค้ดโหนดและนิพจน์ไปยังค่าสภาพแวดล้อม N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true ขอสิทธิ์เฉพาะเจ้าของไฟล์การตั้งค่า เก็บ N8N_ENCRYPTION_KEY ถาวรและสำรองข้อมูลอย่างปลอดภัย: n8n สามารถสร้างคีย์สุ่มได้เมื่อเริ่มต้นระบบครั้งแรก แต่การสูญเสียคีย์อาจทำให้ข้อมูลรับรองที่เข้ารหัสที่มีอยู่ใช้งานไม่ได้ อย่าเปลี่ยนคีย์การเข้ารหัสที่ใช้งานจริงโดยไม่ตั้งใจ ใช้ขั้นตอนการหมุนเวียนที่ได้รับการสนับสนุนอย่างเป็นทางการ การบล็อกการเข้าถึงสภาพแวดล้อมอาจทำให้การบูรณาการที่มีอยู่เสียหายได้ ดังนั้นให้ทดสอบก่อนการเปลี่ยนแปลงการใช้งานจริง n8n คำจำกัดความของตัวแปรความปลอดภัย

การself-hostedทำให้เวิร์กโฟลว์มีประสิทธิภาพอย่างมาก การเรียกใช้โค้ด การเข้าถึงเชลล์ คำขอ HTTP โดยพลการ และโหนดชุมชนบุคคลที่สามสามารถเพิ่มความเสี่ยงได้ ปิดใช้งานฟังก์ชันที่คุณไม่ต้องการ และตรวจสอบการนำเข้าเวิร์กโฟลว์ที่ไม่น่าเชื่อถือก่อนที่จะเรียกใช้

ใช้การควบคุมที่รองรับทุกประการ: กำหนดค่า NODES_EXCLUDE ด้วยอาร์เรย์ JSON ของโหนดที่จะปิดใช้งาน เช่น n8n-nodes-base.executeCommand และ n8n-nodes-base.readWriteFileหากไม่ได้ใช้ โหนดที่มีความเสี่ยงสูงบางโหนดถูกบล็อกโดยค่าเริ่มต้นในเวอร์ชันที่ใหม่กว่า ตรวจสอบรายการจริงก่อนที่จะเปลี่ยนแปลง การยกเว้นโหนดอย่างเป็นทางการ

จาก n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true เปิดใช้งานการตรวจสอบคำขอ HTTP ขาออกไปยังช่วงภายใน ลูปแบ็ค และช่วงที่อยู่เมตาดาต้า เวิร์กโฟลว์ภายใน API ที่ถูกต้องตามกฎหมายอาจหยุดทำงาน หากจำเป็น ให้อนุญาตเฉพาะจุดหมายปลายทางที่คุณควบคุมเท่านั้น ให้การแบ่งส่วนเครือข่ายเป็นการป้องกันหลัก สำหรับการแยกโหนดโค้ด ให้ตรวจสอบตัวดำเนินการงานภายนอก การป้องกัน SSRF · การแยก Task-runner

โหนดชุมชนติดตั้งเฉพาะแพ็คเกจที่คุณเชื่อถือ พวกเขาดำเนินการภายในสภาพแวดล้อม n8n ของคุณ
โหนดที่มีความเสี่ยงยกเว้นโหนดที่deploymentของคุณไม่จำเป็นต้องใช้เมื่อความสามารถเกินขอบเขตเวิร์กโฟลว์ที่ต้องการ
สสสใช้การป้องกัน SSRF และการควบคุมเครือข่ายของ n8n โดยที่เวิร์กโฟลว์ไม่ควรเข้าถึงปลายทางภายในหรือข้อมูลเมตา
การนำเข้าเวิร์กโฟลว์ตรวจสอบเวิร์กโฟลว์ ข้อมูลประจำตัว นิพจน์ และขั้นตอนปฏิบัติการที่นำเข้าก่อนเปิดใช้งาน

การตรวจสอบและการอัปเดต

การรักษาความปลอดภัยเป็นกระบวนการปฏิบัติงาน

เรียกใช้การตรวจสอบความปลอดภัย n8n

คำสั่ง CLI อย่างเป็นทางการคือ n8n audit. ถ้าบริการ Docker Composeของคุณมีชื่อว่า n8nวิ่ง docker compose exec -T n8n n8n audit ในไดเร็กทอรีdeploymentนั้น ตรวจสอบห้าหมวดหมู่: ข้อมูลประจำตัวที่ไม่ได้ใช้ รูปแบบการสืบค้น SQL ที่มีความเสี่ยง การเข้าถึงระบบไฟล์ โหนดที่มีความเสี่ยง/ชุมชน และความเสี่ยงของอินสแตนซ์ รวมถึง webhooks ที่ไม่ได้รับการปกป้องและการเผยแพร่ที่ล้าสมัย แก้ไขข้อค้นพบที่เกี่ยวข้องและเรียกใช้ใหม่ นี่ไม่ใช่การทดสอบการเจาะ คู่มือการตรวจสอบอย่างเป็นทางการ

ปรับปรุงอย่างตั้งใจ

ทำให้ n8n เป็นปัจจุบันเพียงพอที่จะรับการแก้ไขด้านความปลอดภัย ตรวจสอบบันทึกประจำรุ่นและทดสอบการอัปเกรดที่สำคัญ แทนที่จะปล่อยให้อินสแตนซ์ที่เชื่อมต่อกับอินเทอร์เน็ตค้างถาวร

ตรวจสอบการรับรองความถูกต้อง

ดูรูปแบบการเข้าถึงที่ไม่คาดคิด การเปลี่ยนแปลงขั้นตอนการทำงาน และความล้มเหลว จำกัด UI ตัวแก้ไขเพิ่มเติมเมื่อโมเดลการดำเนินงานของคุณไม่ต้องการการเข้าถึงสาธารณะในวงกว้าง

เตรียมการย้อนกลับและการกู้คืน

ทำbackupที่สามารถกู้คืนได้ก่อนการอัพเกรดที่สำคัญ ขอบเขตbackupโดยละเอียดและการคืนค่าเป็นของคู่มือการกู้คืนแยกต่างหาก

ลดประวัติการดำเนินการที่ละเอียดอ่อนให้เหลือน้อยที่สุด: การรันที่ประสบความสำเร็จสามารถคงข้อมูลลูกค้าและโทเค็นไว้ได้ เมื่อเหมาะสมแล้ว EXECUTIONS_DATA_SAVE_ON_SUCCESS=noneเก็บไว้ EXECUTIONS_DATA_PRUNE=trueและเลือก EXECUTIONS_DATA_MAX_AGE ภายในไม่กี่ชั่วโมง เช่น 168 (เจ็ดวัน) นี่เป็นตัวอย่างที่กำหนดค่าได้ ไม่ใช่กฎการเก็บรักษาทางกฎหมาย ประวัติที่น้อยลงหมายถึงการดีบักและข้อมูลทางนิติวิทยาศาสตร์น้อยลง การรัน การรอ หรือการดำเนินการที่มีคำอธิบายประกอบอาจไม่ถูกตัดออกในลักษณะเดียวกัน การเก็บรักษาการดำเนินการอย่างเป็นทางการ

การประนีประนอมที่น่าสงสัย: จำกัดการเข้าถึงที่เป็นอันตรายโดยไม่ทำลายหลักฐาน ตรวจสอบกิจกรรมพร็อกซี โฮสต์และ n8n และเปลี่ยนเวิร์กโฟลว์ เพิกถอนหรือหมุนเวียนข้อมูลประจำตัวอัปสตรีมที่อาจเปิดเผย แก้ไขสาเหตุ และกู้คืนจากbackupที่กู้คืนได้ที่ได้รับการทดสอบแล้วเท่านั้น เมื่อจำเป็น ตรวจสอบ URL ของwebhook บัญชีตัวแก้ไข และบริการที่เชื่อมต่อที่ได้รับผลกระทบ อย่าถือว่า HTTPS สแนปชอต หรือการซื้อ VPS ให้บริการตอบสนองต่อเหตุการณ์

คำสั่งปรับใช้

รักษาความปลอดภัยสแต็กก่อนเปิดใช้งานเวิร์กโฟลว์การผลิต

1แพทช์ VPS สร้างการควบคุมการเข้าถึงของผู้ดูแลระบบ และกำหนดค่าไฟร์วอลล์
2ปรับใช้ n8n และ PostgreSQL บนขอบเขตคอนเทนเนอร์/เครือข่ายส่วนตัว
3กำหนดค่าคีย์เข้ารหัสและsecretในdeploymentก่อนที่จะจัดเก็บข้อมูลประจำตัว
4เพิ่มreverse proxy HTTPS ชื่อโฮสต์สาธารณะ ส่วนหัวที่ส่งต่อ และ URL ของwebhook
5จำกัดผู้ใช้ โหนด และการเข้าถึงเครือข่ายให้ตรงกับเวิร์กโฟลว์ที่ต้องการจริงๆ
6ดำเนินการตรวจสอบความปลอดภัย ตรวจสอบbackup จากนั้นเปิดเผยขั้นตอนการทำงานจริง

การควบคุมบัญชีและแพลตฟอร์ม

ปกป้องบรรณาธิการตลอดจน VPS

ต้องการการป้องกันการเข้าสู่ระบบที่แข็งแกร่งยิ่งขึ้น

เปิดใช้งานการตรวจสอบสิทธิ์แบบสองปัจจัยสำหรับบัญชีผู้แก้ไขและบังคับใช้นโยบายความปลอดภัย MFA ถึง n8n เมื่อรุ่นของคุณรองรับการบังคับใช้นโยบายแบบรวมศูนย์

จำกัดผู้ที่สามารถแก้ไขเวิร์กโฟลว์ได้

การเข้าถึงแบบแก้ไขเป็นการเข้าถึงแบบมีสิทธิพิเศษ: เวิร์กโฟลว์สามารถอ่านข้อมูลประจำตัว เรียกระบบภายใน และดำเนินการโหนดที่มีประสิทธิภาพ ทำให้การเข้าถึงของผู้ใช้แคบลงและลบบัญชีที่ไม่ต้องการอีกต่อไป

ปิดการใช้งานความสามารถที่คุณไม่ได้ใช้

ลดพื้นผิวการโจมตีแอปพลิเคชันโดยการปิดการใช้งานสาธารณะ API เมื่อไม่จำเป็น และบล็อกโหนดหรือคุณสมบัติที่มีความเสี่ยงสูงที่โมเดลปฏิบัติการของคุณไม่ต้องการ

ใช้ SSRF และการควบคุมที่เป็นsecretโดยเจตนา

สำหรับเวิร์กโฟลว์ที่สามารถส่งคำขอ HTTP ได้ตามใจชอบ ให้ประเมินการป้องกัน SSRF ของ n8n และเก็บsecretไว้ในโค้ดเวิร์กโฟลว์ พื้นที่เก็บข้อมูลสาธารณะ และไฟล์สภาพแวดล้อมที่อ่านได้ในวงกว้าง

จำกัดปลายทางการจัดการที่ไม่ได้ใช้: N8N_PUBLIC_API_DISABLED=true ปิดการใช้งาน n8n REST สาธารณะ API และ N8N_PUBLIC_API_SWAGGERUI_DISABLED=true ปิดการใช้งานสนามเด็กเล่น API แยกกัน ทำสิ่งนี้เฉพาะเมื่อการรวมระบบของคุณไม่ต้องการคุณสมบัติเหล่านั้น การปิดใช้งาน REST API จะไม่ตรวจสอบสิทธิ์ URL ของwebhookเวิร์กโฟลว์ ใช้ MFA สำหรับผู้ใช้ตัวแก้ไข และใช้นโยบายแบบรวมศูนย์เฉพาะในกรณีที่รุ่น n8n ของคุณรองรับเท่านั้น

เอกสารอย่างเป็นทางการ: ปิดการใช้งานสาธารณะ API · ตัวแปรนโยบายความปลอดภัย · คำสั่งการตรวจสอบ

คำถามที่พบบ่อย

n8n VPS ความปลอดภัย: คำถามทั่วไป

พอร์ต n8n ควรถูกเปิดเผยโดยตรงหรือไม่

เมื่อreverse proxyเป็นจุดเข้าสาธารณะ ให้เปิดเผยพร็อกซีและเก็บพอร์ตแอปพลิเคชันไว้ด้านหลัง แทนที่จะเผยแพร่บริการที่ไม่จำเป็นในวงกว้าง

PostgreSQL หรือ Redis ควรเปิดเผยต่อสาธารณะหรือไม่

ปกติไม่มี. ควรสามารถเข้าถึงได้โดยระบบที่ต้องการเท่านั้น การเปิดเผยต่อสาธารณะจะเพิ่มพื้นผิวการโจมตีโดยไม่ช่วยการทำงาน n8n ปกติ

เหตุใดคีย์การเข้ารหัส n8n จึงมีความสำคัญ

โดยจะปกป้องข้อมูลรับรองที่จัดเก็บโดย n8n และต้องคงความสอดคล้องตลอดdeployment การสูญเสียข้อมูลดังกล่าวสามารถป้องกันไม่ให้ข้อมูลที่กู้คืนได้รับข้อมูลรับรองที่เข้ารหัสที่ใช้งานได้

โหนดชุมชนปลอดภัยหรือไม่

พวกเขาขยาย n8n ด้วยโค้ดของบุคคลที่สาม ดังนั้นจึงควรถือเป็นการพึ่งพาซอฟต์แวร์โดยมีความเสี่ยงในห่วงโซ่อุปทานและสิทธิพิเศษของตัวเอง ติดตั้งเฉพาะสิ่งที่คุณเชื่อถือและต้องการเท่านั้น

HTTPS ทำให้อินสแตนซ์ n8n ที่self-hostedมีความปลอดภัยหรือไม่

หมายเลข HTTPS คุ้มครองการขนส่ง การรักษาความปลอดภัยในการผลิตยังต้องมีการเสริมความแข็งแกร่งของโฮสต์ การควบคุมการเข้าถึง บริการแบ็กเอนด์ส่วนตัว การป้องกันsecret ความสามารถในการเวิร์กโฟลว์ที่ปลอดภัย การตรวจสอบและการอัปเดต

ตัวแก้ไข n8n สามารถเป็นแบบส่วนตัวในขณะที่ webhooks ที่ใช้งานจริงยังคงทำงานอยู่ได้หรือไม่

ใช่ Reverse proxy หรือ VPN ที่เชื่อถือได้สามารถจำกัดการเข้าถึงของผู้แก้ไข/ผู้ดูแลระบบแยกจาก webhook ที่ใช้งานจริงแบบสาธารณะและเส้นทางเรียกกลับ OAuth ทดสอบการลงชื่อเข้าใช้ที่เชื่อถือได้และการส่งwebhookภายนอกหลังจากการเปลี่ยนแปลงกฎการเข้าถึงทุกครั้ง เพื่อหลีกเลี่ยงการบล็อกการผสานรวมของคุณโดยไม่ตั้งใจ

ฉันจะตรวจสอบสิทธิ์ n8n webhooks ขาเข้าได้อย่างไร

กำหนดค่าการตรวจสอบสิทธิ์ขั้นพื้นฐาน ส่วนหัว หรือ JWT ในโหนด Webhook เมื่อผู้ส่งรองรับ คุณยังใช้รายการที่อนุญาตของ IP และตรวจสอบลายเซ็นของผู้ให้บริการได้หากมี อย่าพึ่งพาเฉพาะเส้นทางที่ดูเป็นsecret และตรวจสอบความถูกต้องของคำขอก่อนที่จะทริกเกอร์การดำเนินการที่ละเอียดอ่อน API
