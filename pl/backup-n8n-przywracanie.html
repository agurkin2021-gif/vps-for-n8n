BACKUP I ODZYSKIWANIE

Backup i przywracanie n8n

Aby wykonać backup i przywrócić self-hosted n8n, zabezpiecz bazę SQLite albo spójny dump PostgreSQL, trwały folder .n8n i oryginalny klucz szyfrowania, konfigurację wdrożenia oraz każdą zewnętrzną zależność danych binarnych lub zamontowanych plików. Przechowuj zaszyfrowaną kopię poza VPS i testuj odzyskiwanie na osobnej instancji. Eksporty workflow i credentials z CLI wykorzystuj do selektywnego odzyskiwania; same eksporty JSON nie są pełnym backupem serwera.

SZYBKA LISTA KONTROLNA

Co powinien chronić backup n8n

Baza danych

Wykonuj backup bazy PostgreSQL albo pliku bazy SQLite używanego przez instancję. Baza zawiera kluczowy stan n8n, w tym workflow, credentials i dane wykonań.

Klucz szyfrowania

Zachowaj dokładnie ten sam klucz szyfrowania n8n, oddzielnie i bezpiecznie. Przywrócone zaszyfrowane credentials wymagają tego samego klucza.

Trwałe pliki

Uwzględnij trwały katalog danych n8n oraz wszystkie zamontowane pliki, magazyn danych binarnych i zasoby workflow, od których zależy wdrożenie.

Konfiguracja wdrożenia

Zachowaj pliki Compose/konfiguracyjne oraz niesekretną konfigurację potrzebną do odtworzenia stosu. Sekrety chroń odpowiednimi mechanizmami kontroli dostępu.

DWA POZIOMY BACKUPU

Eksport logiczny a pełne odzyskiwanie po awarii

Eksport workflow i credentials

Eksporty z n8n CLI są przydatne do migracji, wersjonowanych kopii workflow i selektywnego przywracania. Credentials można wyeksportować w formie zaszyfrowanej i później zaimportować z pasującym kluczem szyfrowania. Aby odzyskać tylko jeden workflow, użyj menu z trzema kropkami w edytorze workflow, pobierz jego JSON, a następnie użyj Import from File w nowym workflow do weryfikacji albo na odizolowanej instancji. Przed zastąpieniem działającego workflow sprawdź credentials, identyfikatory workflow i parametry node'ów: przywrócenie JSON workflow nie odtwarza całego serwera.

Eksport encji

CLI może eksportować encje bazy danych do przenoszenia danych między obsługiwanymi typami baz. Tabele historii wykonań są opcjonalne, ponieważ mogą być bardzo duże.

Pełne odzyskiwanie instancji

Na wypadek całkowitej awarii serwera zabezpiecz właściwą bazę danych, klucz szyfrowania, trwałe dane i zależności wdrożenia. Nie zakładaj, że eksport JSON workflow odtworzy całą instancję.

Snapshot dostawcy

Snapshot VPS jest przydatny jako dodatkowa warstwa odzyskiwania, ale nie powinien być jedyną kopią ani zastępować niezależnie zweryfikowanego backupu aplikacji/bazy danych.

BAZA DANYCH

Wykonuj spójny backup bazy danych

PostgreSQL

Używaj spójnej metody backupu PostgreSQL i przechowuj wynikową kopię poza VPS. Kopia bazy na tym samym uszkodzonym dysku nie jest odzyskiwaniem po awarii.

SQLite

Jeśli wdrożenie używa SQLite, zabezpiecz plik bazy z trwałego katalogu danych n8n. Nie kopiuj bazy w niebezpiecznym stanie, gdy jest aktywnie modyfikowana.

Historia wykonań

Zdecyduj, czy historyczne dane wykonań są częścią celu odzyskiwania. Mogą znacznie powiększać backup, dlatego decyzję powinny wyznaczać wymagania retencji i zgodności.

Wersja bazy danych

Zapisz silnik i wersję bazy używane przez wdrożenie źródłowe, aby środowisko odzyskiwania można było przygotować zgodnie z nimi.

PostgreSQL na VPS z Docker Compose. Jeśli usługa PostgreSQL nazywa się postgres a baza/użytkownik to n8n, poniższe polecenie tworzy na hoście spójny dump PostgreSQL w formacie custom. Przed uruchomieniem sprawdź rzeczywisty plik Compose i dostosuj dane uwierzytelniające bazy oraz nazwy usług. pg_dump może utworzyć logicznie spójny snapshot podczas działania PostgreSQL; nie tworzy jednak backupu nie oddzielnego .n8n folderu użytkownika ani zewnętrznych danych binarnych.

# W projekcie Docker Compose; dostosuj nazwy usługi, bazy i użytkownika
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Sprawdź, czy archiwum ma czytelną listę obiektów
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

Sprawdzenie listy archiwum wykrywa oczywiste problemy z formatem, ale nie dowodzi, że dane da się odtworzyć. Przechowuj zaszyfrowaną kopię poza serwerem i przećwicz przywracanie. Dla opcji zależnych od bazy korzystaj z oficjalnej dokumentacji PostgreSQL pg_dump.

SQLite w Dockerze. Dla domyślnego wdrożenia SQLite database.sqlite oraz konfiguracja wygenerowanego klucza szyfrowania znajdują się w trwałym folderze .n8n (zwykle montowanym w /home/node/.n8n). Nigdy nie traktuj zwykłej kopii działającej bazy SQLite jako spójnej. Zatrzymaj n8n i inne procesy zapisujące do bazy przed kopiowaniem folderu albo użyj obsługiwanego mechanizmu backupu online SQLite, gdy przerwa jest niemożliwa:

# Tylko dla SQLite i domyślnego montowania /home/node/.n8n
# Zatrzymaj n8n (i inne procesy zapisujące) przed kopiowaniem bazy SQLite
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

To przykładowe polecenia dla pokazanej usługi i ścieżki, a nie uniwersalny układ wolumenów. Skopiowany folder początkowo nadal znajduje się na tym samym VPS; przenieś go i zabezpiecz poza serwerem. Jeśli istnieją workery kolejki lub inne procesy zapisujące, również je wycisz i postępuj zgodnie z faktycznym projektem wdrożenia. Aktualne wytyczne n8n dotyczące pełnego backupu opisują wymóg spójności SQLite.

Przywracanie domyślnego folderu SQLite na czysty cel: najpierw zatrzymaj usługę n8n i wszystkie procesy zapisujące do bazy. Gdy istnieje zgodny kontener usługi n8n i jego wolumen docelowy, skopiuj zapisane .n8n dane z powrotem do tego samego trwałego katalogu. Operacja nadpisuje pliki docelowe, więc nie uruchamiaj jej na instancji z danymi, które musisz zachować:

# Uruchamiaj tylko na przeznaczonej do tego CZYSTEJ instancji odzyskiwania
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# PRZED kolejnym poleceniem sprawdź właściciela i uprawnienia dla użytkownika kontenera n8n
# Uruchom dopiero, gdy przywrócone pliki są czytelne i zapisywalne przez n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker może kopiować do zatrzymanych kontenerów, ale właściciel plików w miejscu docelowym może różnić się od oryginału; przed uruchomieniem upewnij się, że przywrócona konfiguracja i plik bazy są czytelne i zapisywalne przez proces n8n. Jeśli rzeczywista konfiguracja Compose używa innej ścieżki lub bind mount, dostosuj kopiowanie. Dokumentacja kopiowania Docker Compose. Samo przywrócenie folderu n8n nie wystarcza w wdrożeniach korzystających z oddzielnej bazy PostgreSQL.

KRYTYCZNY SEKRET

Klucz szyfrowania jest częścią odzyskiwania

n8n szyfruje zapisane credentials kluczem szyfrowania instancji. Baza danych lub eksport zaszyfrowanych credentials bez pasującego klucza może sprawić, że przywrócone workflow nie będą mogły używać zapisanych danych uwierzytelniających.

Jeśli ustawiono N8N_ENCRYPTION_KEY, przywróć dokładnie ten sam sekret. W przeciwnym razie wygenerowany klucz jest przechowywany w trwałym pliku .n8n/config: zabezpiecz tę konfigurację podczas backupu lub odbudowy. Klucze odzyskiwania przechowuj bezpiecznie poza VPS. W trybie kolejkowym wszystkie procesy główne i workery muszą używać tego samego klucza.

RóbPrzechowuj zabezpieczoną kopię dokładnego klucza używanego w produkcji.
RóbPrzed testowaniem credentials sprawdź, czy środowisko odzyskiwania używa tego klucza.
Nie róbNie polegaj na nowo wygenerowanym kluczu po odbudowie serwera.
Nie róbNie zapisuj klucza w publicznym repozytorium ani obok niezabezpieczonego backupu.

PLIKI I DANE BINARNE

Backup bazy może nie obejmować każdej zależności workflow

Trwałe dane .n8n

Znajdź i zachowaj rzeczywisty folder użytkownika .n8n, a nie tylko obraz kontenera. W typowym wdrożeniu Docker jest montowany w /home/node/.n8n; poza Dockerem domyślna ścieżka to ~/.n8n. Jeśli skonfigurowano N8N_USER_FOLDER, n8n tworzy .n8n we wskazanym katalogu nadrzędnym. Uwzględnij jego klucz konfiguracyjny oraz lokalne dane SQLite, binarne lub dane wykonań w systemie plików używane przez instalację.

Zamontowane pliki workflow

Jeśli workflow odczytują lub zapisują katalogi zamontowane z hosta, wykonuj ich backup oddzielnie. Przywrócenie n8n bez nich może pozostawić poprawne workflow niedziałające.

Dane binarne

Zidentyfikuj tryb przechowywania i przywróć każdą zewnętrzną zależność. Dane binarne lub dane wykonań oparte na systemie plików mogą znajdować się w .n8n albo własnym katalogu; S3/Azure Blob lub inny skonfigurowany magazyn zewnętrzny wymaga własnej odtwarzalnej kopii i ustawień dostępu. Sam dump bazy nie zastąpi tych plików.

Community nodes

Zapisz pakiety community i ich wersje oraz wykonaj backup dodatkowych katalogów custom node skonfigurowanych przez N8N_CUSTOM_EXTENSIONS. Te katalogi mogą znajdować się poza .n8n; samo przywrócenie bazy i folderu użytkownika może nadal pozostawić workflow z custom node niedziałające.

STRATEGIA POZA SERWEREM

Backup na tym samym VPS to tylko kopia lokalna

Kopia lokalnaPrzydatna do szybkiego rollbacku, ale podatna na utratę serwera, awarię dysku i destrukcyjne błędy.
Kopia poza serweremPrzechowuj co najmniej jeden backup w magazynie niezależnym od produkcyjnego VPS.
Kopie wersjonowaneZachowuj wiele punktów odzyskiwania, aby uszkodzenie lub zła zmiana nie nadpisały jedynego użytecznego backupu.
Kontrola dostępuBackupy mogą zawierać credentials, logikę workflow i wrażliwe dane biznesowe. Szyfruj je i odpowiednio ograniczaj dostęp.
MonitoringAlarmuj, gdy zaplanowane backupy zawodzą lub przestają tworzyć nowe punkty odzyskiwania.

Uczyń harmonogram mierzalnym. Zapisuj znacznik czasu każdego udanego backupu, zakończenie transferu, rozmiar pliku, wersję źródłowej bazy danych, lokalizację klucza odzyskiwania oraz ostatni udany test odtworzenia. Alarmuj o brakujących, nieudanych lub niespodziewanie pustych plikach. Szyfruj archiwa backupów przed wysłaniem poza VPS i ograniczaj dostęp do sekretów odzyskiwania. Wiele datowanych punktów odzyskiwania chroni przed sytuacją, w której uszkodzenie zostanie odkryte dopiero po nadpisaniu ostatniej zdrowej kopii przez najnowszą.

Na przykład jeśli możesz tolerować najwyżej sześć godzin utraconych zmian, skuteczny harmonogram backupu co sześć godzin jest punktem wyjścia, a nie gwarancją: nieudane zadania i opóźniona replikacja poza serwer mogą zwiększyć rzeczywistą utratę. Ustal retencję i częstotliwość odtwarzania według własnych RPO/RTO i wymagań danych zamiast przyjmować uniwersalną politykę 7- lub 30-dniową.

KOLEJNOŚĆ ODTWARZANIA

Odzyskuj w kontrolowanej kolejności

1 · PrzygotujPrzygotuj zgodny serwer, bazę danych i środowisko kontenerowe/runtime.
2 · Przywróć sekretyBezpiecznie skonfiguruj oryginalny klucz szyfrowania n8n i wymagane sekrety wdrożenia.
3 · Przywróć bazę danychPrzywróć PostgreSQL lub SQLite i sprawdź, czy n8n może połączyć się z oczekiwanymi danymi.
4 · Przywróć plikiPrzywróć trwałe katalogi, dane binarne i zamontowane zasoby workflow.
5 · Uruchom n8nUruchom aplikację z oczekiwaną nazwą hosta, bazą danych i konfiguracją środowiska.
6 · ZweryfikujPotwierdź, że użytkownicy, workflow i credentials się wczytują, a następnie wykonaj reprezentatywne workflow i ścieżki webhooków.

Przykład odzyskiwania PostgreSQL po awarii: na oddzielnym, czystym środowisku odtwarzania które ma już poprawną rolę bazy i pustą n8n bazę, uruchom tylko PostgreSQL. Przed importem poczekaj, aż będzie gotowe: docker compose up -d może zakończyć się, gdy PostgreSQL nadal się inicjalizuje, przez co kolejne pg_restore może się nie udać. Przykład używa --wait w nowoczesnej instalacji Compose i niezależnie sprawdza pg_isready. Skonfiguruj odpowiedni healthcheck PostgreSQL dla niezawodnego oczekiwania albo jawnie potwierdź gotowość przed przejściem dalej. Nie kieruj tego polecenia na zapełnioną bazę produkcyjną i nie uruchamiaj n8n przed przywróceniem bazy oraz pasującego .n8n klucza/danych.

# PRZYWRACAJ TYLKO DO ŚWIEŻEJ, PUSTEJ BAZY DOCELOWEJ
# Dostosuj nazwy usługi Postgres Compose, bazy i użytkownika
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

Miejsce docelowe musi mieć zgodną wersję PostgreSQL, uprawnienia ról, rozszerzenia i oryginalną konfigurację n8n. Przywróć .n8n do właściwego trwałego wolumenu lub bind mount przy użyciu mechanizmu backupu, zachowując właściciela i uprawnienia. Przywróć zewnętrzne pliki binarne, własne rozszerzenia, Compose i konfigurację sekretów, następnie uruchom zgodną wersję n8n i sprawdź logi. Samo przywrócenie bazy nie odzyskuje klucza: wdrożenie PostgreSQL przechowuje klucz w .n8n/config chyba że jawnie skonfigurowano N8N_ENCRYPTION_KEY. Dokumentacja pg_restore · sekwencja pełnego odtwarzania instancji n8n.

TEST ODTWARZANIA

Backup nie jest potwierdzony, dopóki odtwarzanie się nie powiedzie

Testuj w czystym środowisku

Prawdziwy test powinien dowieść, że backup potrafi odtworzyć instancję bez polegania na nieudokumentowanych plikach pozostałych na serwerze produkcyjnym.

Sprawdź credentials

Samo otwarcie workflow nie wystarcza. Potwierdź, że przywrócone zaszyfrowane credentials rzeczywiście się odszyfrowują i poprawnie uwierzytelniają.

Uruchom reprezentatywne workflow

Testuj workflow zależne od webhooków, zewnętrznych API, zamontowanych plików i community nodes zamiast sprawdzać tylko trywialną automatyzację.

Zmierz czas odzyskiwania

Zapisz, ile trwa odtwarzanie i jakie ręczne kroki pozostają. To zamienia domniemany backup w operacyjną procedurę odzyskiwania.

Zweryfikowany test odtwarzania: SQLite i PostgreSQL

Środowisko testowe: n8n 2.42.5 w odizolowanych kontenerach Docker na jednorazowym runnerze GitHub Actions, z syntetycznym workflow z dwoma node'ami. Testy wykonano 8 October 2026, a nie na serwerze klienta ani produkcyjnym serwerze n8n.

SQLite: PASSZaimportowano testowy workflow, wyeksportowano go, zatrzymano wszystkie procesy zapisujące, zarchiwizowano trwały folder SQLite .n8n oraz wygenerowany klucz szyfrowania, przywrócono je do czystego wolumenu, uruchomiono n8n, a następnie ponownie wyeksportowano i wykonano odzyskany workflow.
PostgreSQL: PASSZaimportowano ten sam testowy workflow, utworzono i sprawdzono dump w formacie custom pg_dump, przywrócono go przy użyciu pg_restore do nowej pustej bazy PostgreSQL, przywrócono oddzielny .n8n folder, a następnie ponownie wyeksportowano i wykonano odzyskany workflow.
Co potwierdza PASSPrzetestowane ścieżki backupu zachowały ten workflow, jego dwa node'y i ich połączenia oraz umożliwiły wykonanie po odzyskaniu. To powtarzalne funkcjonalne smoke testy, a nie benchmarki obciążenia.
Czego nie testowanoNie testowano odszyfrowywania i uwierzytelniania prawdziwych credentials, produkcyjnych webhooków, workerów trybu kolejkowego i Redis, magazynu binarnego S3/Azure, custom nodes, dostępu użytkowników/projektów ani odzyskiwania działającej instancji produkcyjnej. Wykonaj oddzielny test dla każdej zależności, której rzeczywiście używasz.

Jak odtworzyć test: użyj jednorazowej instalacji n8n, utwórz nieszkodliwy workflow z dwoma node'ami, wykonaj odpowiedni backup bazy i trwałego folderu, przywróć do czystego wolumenu lub bazy, a następnie sprawdź node'y, połączenia i rzeczywiste wykonanie przywróconego workflow. W systemie produkcyjnym sprawdź również zaszyfrowane credentials, webhooki i pliki zewnętrzne, zanim uznasz odzyskiwanie po awarii za potwierdzone.

Lista akceptacyjna testu odtwarzania: użyj odizolowanej domeny/środowiska; sprawdź obecność użytkowników i workflow, czy co najmniej jedno istniejące zaszyfrowane credential uwierzytelnia bez ponownego wpisywania, czy produkcyjny webhook uruchamia właściwy przywrócony workflow, czy zamontowane pliki i załączniki binarne pozostają czytelne oraz czy integracje z wymaganymi community nodes się ładują. Potwierdź wiek backupu, zmierzony downtime i dostępność poza serwerem. Jeśli którykolwiek kluczowy test zawiedzie, oznacz punkt odzyskiwania jako niezweryfikowany zamiast zgłaszać backup jako kompletny.

OGRANICZENIA BACKUPU CLI

Wiedz dokładnie, czego eksporty workflow i credentials nie przywracają

Eksporty CLI nie są pełnym backupem instancji

Eksporty backupu workflow i credentials nie obejmują użytkowników i ról, historii wykonań i logów, zmiennych ani ustawień instancji, takich jak klucz szyfrowania.

Przywracanie na świeżej instancji wymaga ownera

Na czystej instancji zakończ konfigurację ownera przed importem credentials. Odtwarzanie wieloużytkownikowe lub projektowe może również wymagać poprawnego przypisania użytkownika lub projektu.

Importowane ID mogą nadpisać istniejące elementy

Eksporty workflow i credentials zachowują oryginalne ID. Import do instancji, która już zawiera te same ID, może zastąpić istniejące elementy.

Publikuj importowane workflow świadomie

Importy CLI zwykle pozostawiają workflow nieaktywne. W n8n 2.x sprawdź stan publikacji każdego zaimportowanego workflow i publikuj tylko te, które mają działać; self-hosted Server CLI obsługuje też n8n publish:workflow --id=YOUR_WORKFLOW_ID. Gdy n8n działa, zmiany stanu publish/unpublish wykonane przez Server CLI zaczynają obowiązywać dopiero po restarcie n8n. Zrestartuj przed weryfikacją zaplanowanych triggerów i produkcyjnych webhooków lub przełączeniem ruchu.

Przykład eksportu zbiorczego dla Docker Compose: jeśli usługa n8n nazywa się n8nmożesz uruchomić poniższe oficjalne backupy CLI. Ścieżka wyjściowa celowo znajduje się wewnątrz zamontowanego trwałego .n8n katalogu, ponieważ dowolne katalogi wewnątrz kontenera mogą zniknąć przy jego odtworzeniu. Potwierdź, że katalog jest zapisywalny przez użytkownika kontenera n8n. Trzymaj JSON workflow i credentials w oddzielnych katalogach— n8n dokumentuje problem z importem, gdy oba typy znajdują się w jednym katalogu.

n8n 2.x: backup wersji roboczej a opublikowanej: zwykły --backup eksport workflow zapisuje aktualne wersje robocze; mogą różnić się od wersji opublikowanych w produkcji. Aby zachować rzeczywiście opublikowaną wersję konkretnego workflow, wyeksportuj ją oddzielnie za pomocą docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, po upewnieniu się, że folder wyjściowy istnieje i jest zapisywalny. CLI może również wyeksportować wersję historyczną przy użyciu --version=VERSION_ID. Przechowuj te kopie poza serwerem razem z pełnym backupem; nie zakładaj, że JSON wersji roboczej odzwierciedla opublikowany stan produkcyjny.

# Uruchom z projektu Docker Compose; usługa n8n musi istnieć
# Przechowuj backupy workflow i credentials w ODDZIELNYCH folderach
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Skopiuj zapisane katalogi eksportu Z kontenera na hosta
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

Skopiowany ~/n8n-recovery/cli katalog nadal znajduje się na VPS, dopóki nie przeniesiesz go do zabezpieczonej, niezależnej lokalizacji backupu. Eksport credentials jest domyślnie szyfrowany i przy imporcie wymaga pasującego klucza szyfrowania. Unikaj używania --decrypted poza ściśle kontrolowaną migracją: zapisuje sekrety jako plaintext. Nigdy nie commituj eksportów zawierających wrażliwą logikę workflow lub credentials do publicznego repozytorium GitHub. Niektóre zewnętrzne szablony backupu credentials do GitHub celowo eksportują odszyfrowane sekrety; prywatne repozytorium ogranicza dostęp, ale nie szyfruje. Sprawdź rzeczywiste ustawienia eksportu i uprawnienia magazynu każdego szablonu, szyfruj sekrety przed transferem poza serwer i rotuj credentials ujawnione przez niezamierzone przesłanie plaintextu.

Przykład importu zbiorczego: na czystym celu zakończ konfigurację ownera, podaj oryginalny klucz szyfrowania i upewnij się, że zapisane pliki backupu są dostępne na tym VPS do odzyskiwania. Poniższe polecenia tworzą folder docelowy i kopiują workflows/ oraz credentials/ podfoldery z hosta do kontenera n8n; dostosuj ścieżki, jeśli układ wolumenów Docker jest inny:

# Uruchamiaj tylko na przeznaczonej do tego CZYSTEJ instancji odzyskiwania
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

Sprawdź właściciela plików i dostęp użytkownika kontenera n8n. Nie importuj na zapełnioną instancję produkcyjną bez zweryfikowanego rollbacku: ID workflow i credentials mogą nadpisać istniejące wpisy. Następnie uruchom:

# Po skonfigurowaniu ownera świeżej instancji ORAZ podaniu poprawnego klucza
# Skopiuj zapisane dane cli/ z powrotem do .n8n/backups/ docelowej usługi n8n
docker compose exec -T n8n n8n import:workflow --separate --input=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n import:credentials --separate --input=/home/node/.n8n/backups/credentials/

Importowane ID mogą zastąpić istniejące workflow lub credentials; do prób używaj odizolowanej instancji testowej, a potem sprawdź credentials i stany aktywacji/publikacji. W n8n 2.x samo przywrócenie roboczego JSON nie dowodzi, że workflow został opublikowany i może uruchamiać zaplanowane triggery. Bezpieczeństwo importu: na instancji n8n bez multi-main wcześniej aktywne triggery cron mogą nadal działać po imporcie CLI aż do restartu instancji. Zatrzymaj lub odizoluj produkcyjne triggery i zrestartuj n8n przed włączeniem przywróconych zadań; sprawdź, czy nie ma podwójnych wykonań. Eksporty CLI nie nie zawierają oryginalnych użytkowników, logów wykonań, zmiennych instancji ani klucza szyfrowania. --backup sets --all --pretty --separate, a nie „pełna instancja”. Źródła: aktualny oficjalny przewodnik n8n po backupie/odtwarzaniu oraz dokumentacja poleceń n8n CLI.

Zbiorcze odtwarzanie z szablonów GitHub lub Google Drive: to alternatywa wyłącznie dla JSON workflow, nie dla bazy instancji, użytkowników, zaszyfrowanych wartości credentials ani klucza szyfrowania. Przed uruchomieniem szablonu opartego na API sprawdź jego uprawnienia do n8n API i magazynu, wybraną wersję backupu i instancję docelową, czy aktualizuje pasujące ID i odtwarza usunięte workflow oraz jak obsługuje publikację workflow. Nie wszystkie szablony odtwarzają ID brakujące w celu; przetestuj ten scenariusz w izolacji, zanim polegniesz na automatycznym przywracaniu.

FAQ

Backup i przywracanie n8n: najczęstsze pytania

Czy eksport workflow wystarczy jako backup n8n?

Nie. Eksporty workflow są użytecznymi kopiami logicznymi, ale pełne odzyskiwanie może wymagać także credentials, pasującego klucza szyfrowania, stanu bazy, trwałych plików i magazynu danych binarnych.

Czy potrzebuję klucza szyfrowania n8n, jeśli mam bazę danych?

Tak, jeśli zaszyfrowane credentials zapisane w bazie mają pozostać użyteczne. Bezpiecznie zachowaj oryginalny klucz.

Czy robić backup PostgreSQL, czy eksportować workflow i credentials?

Dla odzyskiwania po awarii zabezpiecz bazę danych i klucz szyfrowania. Eksporty logiczne są cenną dodatkową warstwą migracji i selektywnego odzyskiwania, a nie zamiennikiem wszystkich elementów instancji.

Czy snapshot VPS może być jedynym backupem?

Lepiej traktować go jako jedną warstwę odzyskiwania. Przechowuj niezależny backup poza serwerem, aby awaria dostawcy, konta, serwera lub snapshotu nie usunęła wszystkich punktów odzyskiwania naraz.

Skąd wiadomo, że backup działa?

Przywróć go do czystego środowiska testowego, sprawdź odszyfrowywanie credentials i uruchom reprezentatywne workflow. Sam udany job backupu nie dowodzi możliwości odzyskania.

Czy backupy workflow w GitHub lub Google Drive zawierają zapisane sekrety credentials?

Backupy JSON obejmujące wyłącznie workflow nie zawierają tajnych wartości zarządzanych przez magazyn credentials n8n ani klucza szyfrowania instancji. Eksportowany JSON może jednak ujawniać nazwy i ID credentials oraz sekrety wpisane bezpośrednio w parametrach node'ów, np. nagłówki uwierzytelniające. Przed przesłaniem lub udostępnieniem sprawdź i zabezpiecz eksportowany JSON. Dla pełnego odzyskiwania wykonuj backup bazy i oryginalnego klucza albo używaj obsługiwanych zaszyfrowanych eksportów credentials z CLI z przetestowanym odtwarzaniem. Szablon GitHub lub Google Drive obejmujący tylko workflow nie jest pełnym odzyskiwaniem po awarii.

CELE ODZYSKIWANIA

Zdefiniuj RPO i RTO przed incydentem

RPO to maksymalna tolerowana utrata ostatnich zmian. Mierz ją od najnowszego użytecznego, niezależnie przechowywanego punktu odzyskiwania; zaplanowane zadanie co sześć godzin nie zapewnia sześciogodzinnego RPO, jeśli eksporty lub transfery zawiodły. RTO to maksymalny tolerowany czas niedostępności. Mierz go w czystym teście odtwarzania, uwzględniając pobranie sekretów, odtworzenie plików zewnętrznych, ponowne sprawdzenie credentials i publikację odzyskanych workflow — nie tylko uruchomienie kontenera.

KLUCZ ODZYSKIWANIA

Znajdź oryginalny klucz szyfrowania przed odbudową

Jeśli produkcja ustawiła N8N_ENCRYPTION_KEY, zachowaj dokładnie ten sekret środowiskowy. Jeśli nie, zachowaj wygenerowany klucz z oryginalnego trwałego .n8n/config. Przed importem zaszyfrowanych credentials sprawdź, którego źródła faktycznie używa odzyskana instancja; nowo wygenerowany klucz nie odszyfruje credentials ze starej bazy.
