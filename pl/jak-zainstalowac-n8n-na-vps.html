INSTALACJA: SKOPIUJ I DOSTOSUJ

Zainstaluj n8n na VPS przy użyciu Docker Compose

Użyj tego przykładu, aby zbudować wdrożenie n8n na samodzielnie zarządzanym VPS z Linuxem. n8n instalujesz i utrzymujesz samodzielnie; wybór serwera przez naszego partnera nie obejmuje preinstalowanej instancji n8n. Przykład łączy n8n, PostgreSQL, zewnętrzny task runner i Caddy HTTPS w prywatnej sieci Compose. Jest to szablon konfiguracji, a nie twierdzenie o wdrożeniu przetestowanym na żywo.

Wolisz najszybszą świeżą instalację? n8n udostępnia również oficjalną jednoliniową konfigurację Docker. Możesz pobrać i sprawdzić jej skrypt poleceniem curl -fsSL https://get.n8n.io -o get-n8n.sh przed uruchomieniem sh get-n8n.sh. Ta opcja uruchamia początkową instancję z SQLite pod lokalnym URL i zawiera usługi sandbox n8n Assistant; to nie jest tym samym co to wdrożenie VPS z publicznym HTTPS i PostgreSQL. Oficjalny pełny stos sandbox wymaga więcej RAM i CPU niż lekka instalacja n8n (przewodnik Compose podaje co najmniej 4 GB RAM / 2 vCPU). Dla produkcyjnego VPS dostępnego z Internetu kontynuuj z ręcznie konfigurowanym stosem poniżej.

1. Przygotuj Docker, DNS i dostęp

Połącz się przez SSH z dostępem sudo i skieruj rekord DNS A dla n8n.example.com na adres IPv4 VPS. Na świeżym Ubuntu 22.04, 24.04 lub 26.04 VPS poniższe polecenia instalują Docker Engine i nowoczesny plugin docker compose z oficjalnego podpisanego apt repozytorium Docker:

# Świeża oficjalna instalacja Ubuntu 22.04 / 24.04 / 26.04
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Zarejestruj podpisane repozytorium apt Docker
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

To metoda oparta na repozytorium, przeznaczona do produkcji i opisana w oficjalnym przewodniku instalacji Docker na Ubuntu. Nie reinstaluj ani nie usuwaj Docker bez sprawdzenia na VPS, który już uruchamia kontenery lub inne strony; najpierw sprawdź istniejącą instalację i możliwe konflikty pakietów. Dla Debian lub innej dystrybucji użyj odpowiednich oficjalnych instrukcji dla danego systemu zamiast poleceń Ubuntu.

Teraz sprawdź sam Docker, plugin Compose, DNS i katalog roboczy:

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

Jeśli getent hosts nie zwraca adresu albo zwraca zły adres, popraw DNS przed uruchomieniem Caddy; zastąp n8n.example.com w całym przewodniku własną rzeczywistą nazwą hosta. Docker zwykle wymaga uprawnień root: jeśli użytkownik SSH nie może uruchamiać późniejszych docker compose poleceń bezpośrednio, poprzedź je sudoDodanie użytkownika do grupy docker daje dostęp równoważny root i nie powinno być wykonywane bez namysłu na współdzielonym serwerze.

Przed włączeniem firewalla zachowaj dostęp do faktycznego portu administracyjnego SSH. Zezwól na przychodzący HTTP (80) i HTTPS (443) do wydawania certyfikatów i dostępu do edytora. Porty kontenerów publikowane przez Docker mogą omijać niektóre reguły UFW, dlatego sprawdź wytyczne Docker dotyczące firewalla i publikuj tylko zamierzone porty Caddy. Ten przykład Compose celowo nie nie publikuje PostgreSQL (5432), n8n (5678) ani brokera task runnera (5679) do publicznego Internetu.

2. Utwórz wartości środowiskowe i zachowaj klucz

W katalogu projektu wygeneruj trzy różne losowe wartości szesnastkowe poleceniem:

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

Utwórz plik o nazwie .env na podstawie poniższego szablonu, zastąp każdy REPLACE_WITH_RANDOM_HEX inną wygenerowaną wartością oraz zmień nazwę hosta i strefę czasową. Pokazany 2.42.5 tag to stabilne wydanie wymienione 8 października 2026, użyte tutaj jako datowany przykład konfiguracji, a nie gwarancja wdrożenia przetestowanego na żywo ani przyszłego bezpieczeństwa. Przed instalacją sprawdź aktualne oficjalne wydania n8n, a następnie utrzymuj n8n i obraz task runnera na tej samej zweryfikowanej wersji.

# .env — zastąp trzy przykładowe sekrety
# Przypnij wspieraną wersję n8n; utrzymuj tę samą wersję n8n i runnera.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

Nigdy nie commituj .env do publicznego repozytorium. Klucz szyfrowania i instrukcje odzyskiwania przechowuj bezpiecznie poza VPS. Klucz musi pozostać taki sam po odtworzeniu kontenera lub migracji.

3. Utwórz compose.yaml dla świeżej instalacji

W tym samym katalogu utwórz compose.yamlPrzykład używa oficjalnych konwencji zmiennych środowiskowych n8n i ścieżki PostgreSQL 18 PGDATA udokumentowanej przez projekt hostingowy n8n:

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

Cztery usługi mają różne role: PostgreSQL przechowuje stan bazy, n8n uruchamia workflow, n8n-runner wykonuje zadania runnera z pasującą wersją i współdzielonym tokenem uwierzytelniającym, a Caddy obsługuje publiczny HTTPS. Zewnętrzny task runner nie jest trybem kolejkowym Redis. Tylko Caddy publikuje porty hosta. Ten lekki przykład używa jednej roli bazy do konfiguracji; dla silniejszego rozdzielenia uprawnień PostgreSQL sprawdź oficjalny przykład wdrożenia n8n z PostgreSQL.

4. Utwórz Caddyfile dla HTTPS

Utwórz plik Caddyfile (duże C, bez rozszerzenia) obok compose.yaml. Wszędzie zastąp przykładową nazwę hosta własną nazwą DNS:

n8n.example.com {
    reverse_proxy n8n:5678
}

Caddy pobiera i odnawia publiczne certyfikaty TLS, gdy domena rozwiązuje się poprawnie, a ruch zewnętrzny może dotrzeć do portów 80/443. Nie kieruj DNS na localhost. Jeśli zastąpisz Caddy innym reverse proxy, przekazuj oryginalny host, protokół i nagłówki adresu klienta oraz dostosuj N8N_PROXY_HOPS do faktycznej liczby zaufanych hopów proxy.

5. Uruchom kontenery i przetestuj z zewnątrz

Uruchom te polecenia z katalogu projektu po zapisaniu .env, compose.yaml oraz Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

Ostatnie polecenie sprawdza publiczny HTTPS endpoint health. Jeśli wydawanie certyfikatu nadal trwa, sprawdź logi Caddy oraz DNS/porty, zanim uznasz, że n8n jest uszkodzone. Otwórz https://n8n.example.com, od razu utwórz pierwsze konto ownera i włącz odpowiednie zabezpieczenia logowania. Potwierdź, że instancja faktycznie wykonuje workflow, a nie tylko ładuje edytor:

  1. W edytorze utwórz workflow z triggerem Webhook Ustaw HTTP Method na GET, wybierz Path vps-check, i ustaw Respond na Immediately. Zapisz workflow.
  2. Kliknij Listen for Test Eventskopiuj pełny Test URL pokazany przez n8n, a z innego urządzenia uruchom curl -i 'PASTE_TEST_URL_HERE' z wklejonym URL. Oczekuj poprawnej odpowiedzi HTTP i pojawienia się przychodzącego zdarzenia w edytorze n8n. Testowe URL działają tylko wtedy, gdy n8n nasłuchuje zdarzenia.
  3. Opublikuj workflow, przełącz node na jego Production URL, skopiuj go i uruchom curl -i 'PASTE_PRODUCTION_URL_HERE' ponownie. Potwierdź wykonanie na karcie Executions workflow. Żądania produkcyjnych webhooków wymagają opublikowanego workflow i nie pokazują payloadu w widoku testowym edytora.

To celowo prosty, nieuwierzytelniony smoke test: nigdy nie wysyłaj do niego sekretów. Po teście cofnij publikację/usuń go albo skonfiguruj uwierzytelnianie Webhook i ograniczenia IP przed użyciem publicznego endpointu z prawdziwymi danymi. Zobacz oficjalną dokumentację testowych/produkcyjnych webhooków.

6. Wykonaj backup przed zmianą przypiętych wersji

Zapisz możliwy do odtworzenia dump PostgreSQL oraz trwały wolumen danych n8n, .env/klucz szyfrowania i wymagane pliki zewnętrzne w magazynie poza tym serwerem. Zweryfikuj odtwarzanie przy użyciu przewodnika backupu i odzyskiwania przed aktualizacją produkcji. Przykładowe polecenia:

# Wykonaj backup bazy, klucza szyfrowania i danych instancji,
# oraz plików przed zmianą przypiętych wersji.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# Po zabezpieczeniu backupu poza tym VPS:
docker compose pull
docker compose up -d
docker compose ps

Zmieniaj przypiętą N8N_VERSION dopiero po przeczytaniu release notes; obrazy n8n i runnera muszą być aktualizowane razem. Nie uruchamiaj docker compose down -v podczas rutynowego utrzymania, ponieważ usuwa to nazwane wolumeny danych. Zmiana głównej wersji PostgreSQL wymaga aktualizacji bazy lub planu dump/restore; zastąpienie obrazu Postgres 18 innym głównym tagiem nie jest automatyczną migracją.

Źródła autorytatywne: przewodnik n8n Docker Compose, konfiguracja reverse proxy/webhooków n8n i oficjalne uwagi dotyczące wdrożenia PostgreSQL. Nie zakładamy żadnego benchmarku infrastruktury ani preinstalowanej funkcji konkretnego dostawcy.

Zmiana wyłącznie głównego tagu obrazu Postgres może uczynić istniejący katalog danych niekompatybilnym. Wykonaj backup i zastosuj procedurę aktualizacji bazy zamiast zakładać, że odtworzenie kontenera wykonuje migrację głównej wersji.

FAQ

Instalacja n8n z Docker: najczęstsze pytania

Czy n8n potrzebuje PostgreSQL przy użyciu Docker?

Docker nie wymaga PostgreSQL, a małe wdrożenia mogą używać SQLite. Dla wdrożenia VPS nastawionego na produkcję PostgreSQL daje solidniejszą bazę danych i wspiera późniejsze skalowanie w trybie kolejkowym.

Po co trwały wolumen n8n, skoro PostgreSQL przechowuje dane?

Trwały katalog n8n może zawierać ważny stan instancji i konfigurację. Zachowuj go zgodnie z projektem wdrożenia zamiast zakładać, że baza jest jedynym zasobem do odzyskiwania.

Dlaczego webhook pokazuje localhost?

Wewnętrzny adres kontenera różni się od publicznego origin. Skonfiguruj zewnętrzną nazwę hosta, protokół i URL webhooka oraz upewnij się, że reverse proxy przekazuje wymagane nagłówki.

Czy port 5678 powinien być publiczny?

Dla normalnego wdrożenia produkcyjnego za reverse proxy wystaw HTTPS na proxy, a port aplikacji n8n pozostaw wewnętrzny, chyba że istnieje konkretny powód operacyjny, by zrobić inaczej.

Czy potrzebuję Redis?

Nie przy standardowym wdrożeniu Docker z jedną instancją. Redis staje się istotny, gdy świadomie przechodzisz do trybu kolejkowego i workerów.

Czy zewnętrzne task runnery n8n to to samo co workery trybu kolejkowego?

Nie. Zewnętrzne task runnery wykonują obsługiwany kod zadań oddzielnie od głównego procesu n8n i używają współdzielonego tokenu uwierzytelniającego. Tryb kolejkowy Redis rozdziela wykonania workflow i ma własne wymagania infrastrukturalne. Ten przykład pokazuje zewnętrzny task runner, a nie tryb kolejkowy Redis.
