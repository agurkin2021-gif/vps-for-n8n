INSTALACJA N8N NA VPS

Jak zainstalować n8n na VPS

Przygotuj serwer Linux, skonfiguruj Docker Compose, PostgreSQL i HTTPS, a następnie sprawdź webhooki oraz trwałość danych przed uruchomieniem ważnych automatyzacji.

Zobacz VPS

Najważniejsza odpowiedź

Do samodzielnego uruchomienia n8n na VPS potrzebujesz serwera Linux z Docker, stałego klucza szyfrowania, trwałych wolumenów i poprawnej konfiguracji HTTPS. Najpierw przygotuj DNS i sekrety, potem uruchom kontenery oraz testowe workflow. Nie wystawiaj bazy PostgreSQL publicznie.

Przygotowanie serwera i DNS

Wybierz Linux VPS, zaloguj się bezpiecznie po SSH i zaktualizuj system. Ustal domenę lub subdomenę (np. n8n.example.com) i skieruj rekord DNS A/AAAA na właściwy adres serwera. Ogranicz porty sieciowe: zwykle wystarczą 80/443 do obsługi HTTPS oraz SSH zarządzane odpowiednimi regułami zapory.

Przed uruchomieniem sprawdź, czy operator pozwala na samodzielne zarządzanie systemem i instalację Docker. Mały VPS może być testowym punktem startu, ale bazę i proxy trzeba uwzględnić w bilansie RAM. Zobacz wymagania n8n.

1. Instalacja Docker i sprawdzenie Compose

Instalację silnika Docker wykonaj zgodnie z instrukcją odpowiednią dla używanego wydania Linux. Po instalacji zweryfikuj dostępność narzędzi; nie zakładaj, że pakiety istnieją na każdym obrazie systemu:

docker --version
docker compose version
sudo systemctl status docker --no-pager

Uruchamiaj polecenia wdrożeniowe jako uprawniony administrator. Najpierw sprawdź wersję systemu i bieżące wymagania Docker.

2. Zapisz zmienne środowiskowe i klucz szyfrowania

W katalogu projektu przechowuj plik .env z bezpiecznym hasłem PostgreSQL, docelową domeną i trwałym, losowo wygenerowanym kluczem N8N_ENCRYPTION_KEY. Klucza nie zmieniaj po pierwszym uruchomieniu, inaczej zapisane credentials mogą przestać działać.

# PRZYKŁADOWE NAZWY ZMIENNYCH, BEZ PRAWDZIWYCH SEKRETÓW
N8N_HOST=n8n.example.com
N8N_PROTOCOL=https
WEBHOOK_URL=https://n8n.example.com/
POSTGRES_PASSWORD=TU_WSTAW_SILNE_HASLO
N8N_ENCRYPTION_KEY=TU_WSTAW_STALY_LOSOWY_KLUCZ

Nie publikuj .env w repozytorium ani nie wysyłaj go do nieszyfrowanych raportów. Własny oryginalny klucz musi być częścią planu odzyskiwania.

3. Docker Compose dla nowej instalacji

Przygotuj compose.yaml z osobną usługą PostgreSQL, n8n i trwałymi wolumenami. Poniżej jest schemat dla nowej instalacji — uzupełnij bezpieczne sekrety, skonfiguruj zewnętrzny reverse proxy i przypnij sprawdzoną wersję obrazu n8n przed użyciem na serwerze produkcyjnym.

services:
  postgres:
    image: postgres:16
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
    volumes:
      - postgres_data:/var/lib/postgresql/data
  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      WEBHOOK_URL: ${WEBHOOK_URL}
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      - postgres
volumes:
  postgres_data:
  n8n_data:

Ten fragment nie publikuje żadnych portów — wymaga poprawnej konfiguracji reverse proxy we wspólnej sieci Docker. W pliku .env zdefiniuj również N8N_VERSION. Nie uruchamiaj fragmentu bez dołożenia dostępu HTTP/HTTPS i odpowiednich zabezpieczeń.

4. Skonfiguruj HTTPS i reverse proxy

Publiczny ruch do edytora n8n powinien przechodzić przez serwer proxy obsługujący TLS i poprawne przekazywanie nagłówków. W Caddy możesz użyć konfiguracji dopasowanej do rzeczywistej sieci Compose, np.:

n8n.example.com {
    reverse_proxy n8n:5678
}

Utwórz usługę Caddy lub inny proxy w tym samym projekcie sieciowym, opublikuj tylko porty 80 i 443, dodaj trwałe wolumeny dla certyfikatów. Wskaż zaufany proxy zgodnie z dokumentacją n8n; skonfiguruj N8N_PROXY_HOPS zgodnie z rzeczywistą liczbą pośredników.

5. Uruchom i przetestuj usługi

docker compose config
# Po uzupełnieniu usług i proxy:
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n

Sprawdź w przeglądarce HTTPS, proces rejestracji właściciela instancji, dostęp do edytora i testowe wykonanie workflow. Opublikuj testowy webhook i wywołaj go z zewnętrznej sieci, aby zweryfikować publiczną domenę i reverse proxy.

Uruchom ponownie usługę i sprawdź, czy workflow nadal istnieje. Jeśli dane zniknęły, najpierw napraw wolumeny.

Prawidłowe adresy i credentials

N8N_HOST, N8N_PROTOCOL i WEBHOOK_URL muszą odpowiadać rzeczywistemu publicznemu adresowi. W przeciwnym razie część callbacków nie dotrze do aplikacji. Klucz szyfrowania musi pozostać identyczny w kolejnym uruchomieniu. Sekrety PostgreSQL przechowuj poza publiczną wersją repozytorium, a port bazy pozostaw prywatny.

Aktualizacja bez utraty danych

  1. Przeczytaj informacje o wersji i wymagania dotyczące migracji.
  2. Wykonaj spójną kopię PostgreSQL, wolumenu n8n i oryginalnego klucza.
  3. Zmień przypiętą wersję obrazu n8n w sposób kontrolowany.
  4. Odtwórz lub uruchom usługę zgodnie z planem zmiany.
  5. Sprawdź edytor, credentials, webhooki, harmonogramy i logi.

Nie aktualizuj jednocześnie głównej wersji PostgreSQL bez osobnej procedury migracji. Zobacz odzyskiwanie n8n.

Dlaczego działa lokalnie, ale nie produkcyjnie?

Najczęstsze błędy to: nieprawidłowy publiczny URL webhooków, brak przekazywania nagłówków HTTPS, niezapisane wolumeny, utracony klucz szyfrowania, niedostępny serwer bazy lub przypadkowo otwarte porty. Sprawdź logi i połączenia wewnętrznej sieci Docker. Weryfikacja z samego hosta nie zastępuje wywołania HTTPS z Internetu.

Bezpieczeństwo po wdrożeniu

Wymuszaj HTTPS, używaj kluczy SSH i aktualizacji bezpieczeństwa, nie wystawiaj PostgreSQL publicznie i ogranicz dostęp do edytora. Uruchom audit n8n oraz monitoring kontenerów. Nie włączaj nieznanych community nodes bez oceny ryzyka. Pełna lista zabezpieczeń.

Najczęstsze pytania

Czy muszę używać PostgreSQL?

Do prostego środowiska można rozważać SQLite, ale PostgreSQL jest praktyczniejszą bazą do rozwoju i skalowania.

Dlaczego nie działają webhooki?

Sprawdź DNS, HTTPS, reverse proxy i publiczny WEBHOOK_URL; przetestuj także wywołanie z zewnątrz.

Co dzieje się z danymi po usunięciu kontenera?

Przy poprawnych wolumenach dane zostają na trwałym storage. Bez nich odtworzenie kontenera może utracić aplikacyjne pliki.

Czy mam zmieniać klucz szyfrowania przy każdym wdrożeniu?

Nie. Oryginalny klucz musi pozostać stabilny, aby odszyfrować zapisane credentials.
