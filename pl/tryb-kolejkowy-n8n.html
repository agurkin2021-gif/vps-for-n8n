Tryb kolejkowy n8n

Tryb kolejkowy oddziela przyjmowanie i koordynację wykonań od ich realizacji przez workery. Pomaga przy wielu jednoczesnych workflow, ale wymaga Redis, wspólnej bazy PostgreSQL i świadomego monitoringu.

Odpowiedź w skrócie

Queue Mode n8n polega na tym, że instancja main przekazuje zadania do Redis, a workery wykonują workflow, korzystając ze wspólnego PostgreSQL. Warto go rozważyć przy potwierdzonym problemie z równoległymi wykonaniami, nie zaś dlatego, że na serwerze jest dużo zapisanych workflow.

Kiedy warto włączyć tryb kolejkowy?

Zostań przy regularMasz niewiele jednoczesnych workflow i jeden serwer nie osiąga granic zasobów.
Zwiększ VPSJeśli problemem jest przede wszystkim mała ilość RAM albo CPU, najpierw rozważ skalowanie pionowe.
Rozważ queueWiele jednoczesnych uruchomień obciąża proces main i wydłuża oczekiwanie na wykonanie.
Zmierz obciążenieMonitoruj czas trwania, peak RAM, CPU, liczbę oczekujących zadań i limity zewnętrznych API.

Jak działa architektura main – Redis – workers?

Main obsługuje interfejs i część ruchu wejściowego, tworząc wykonania. Redis koordynuje kolejkę, a workery pobierają i uruchamiają zadania. PostgreSQL jest wspólną bazą dla wszystkich procesów. Workery nie są samodzielnymi, niezależnymi kopiami całej instalacji.

Każdy worker musi używać kompatybilnej wersji n8n i tego samego N8N_ENCRYPTION_KEY. Problem z bazą danych lub kluczem może uniemożliwić wykonanie workflow, mimo że Redis działa.

Wymagane komponenty i sieć

Przygotuj stabilną bazę PostgreSQL oraz Redis dostępny po prywatnej sieci. Skonfiguruj main i wszystkie workery z identycznymi danymi połączenia do bazy, Redis i tym samym kluczem szyfrowania. Nie otwieraj portów Redis i PostgreSQL na cały Internet.

Podstawowe zmienne obejmują EXECUTIONS_MODE=queue, QUEUE_BULL_REDIS_HOST, QUEUE_BULL_REDIS_PORT, DB_TYPE=postgresdb i DB_POSTGRESDB_*. Dokładne wartości zależą od rzeczywistych nazw usług Docker.

Jak uruchomić worker na istniejącym VPS?

Dodaj usługę worker do już działającego stosu Docker Compose. Użyj tej samej przypiętej wersji n8n, co w main, skonfiguruj bazę, Redis i klucz szyfrowania, a worker uruchom poleceniem worker z odpowiednim limitem współbieżności.

# W istniejącym poprawnie skonfigurowanym projekcie:
docker compose up -d n8n-worker
docker compose logs --tail=100 n8n-worker
# Po przetestowaniu jednego workera:
docker compose up -d --scale n8n-worker=2

Przykładowa nazwa usługi n8n-worker musi odpowiadać Twojemu plikowi Compose. To nie jest kompletna instalacja n8n od zera; taką procedurę opisuje poradnik Docker.

Bezpieczne przejście z SQLite do PostgreSQL

Nie zmieniaj samego DB_TYPE z SQLite na PostgreSQL w nadziei, że n8n przeniesie rekordy. Takie przełączenie uruchamia połączenie z inną bazą i nie zapewnia migracji workflow ani credentials. Najpierw zrób pełną kopię obecnej bazy, katalogu .n8n, konfiguracji i oryginalnego klucza.

Następnie użyj obsługiwanej procedury eksportu/importu lub migracji, sprawdź dane w środowisku testowym i dopiero po weryfikacji wykonaj cutover. Nie usuwaj starego database.sqlite jako skrótu.

Współbieżność: liczba workerów a liczba zadań

Możesz zwiększać liczbę workerów lub liczbę wykonywanych zadań na worker, np. n8n worker --concurrency=5. Gdy N8N_CONCURRENCY_PRODUCTION_LIMIT ustawiono na wartość inną niż -1, może ona mieć pierwszeństwo przed parametrem współbieżności uruchomienia. W przeciwnym razie znaczenie ma ustawienie workera lub wartość domyślna.

Nie zakładaj, że podwojenie workerów zawsze podwaja wydajność. Ograniczać mogą połączenia do PostgreSQL, RAM, CPU, API i czas pojedynczego workflow.

Webhooks i właściwe przekierowanie ruchu

Jeśli korzystasz z osobnych procesorów webhooków, proxy powinien kierować produkcyjne ścieżki /webhook/* oraz /webhook-waiting/* do właściwych procesorów, a edytor, API i testowe /webhook-test/* do main. Przetestuj odpowiedzi z rzeczywistego zewnętrznego klienta.

Workflow z Respond to Webhook nadal może czekać na wykonanie po stronie workera. Queue Mode może dodać opóźnienie przekazania zadania i nie gwarantuje natychmiastowej odpowiedzi HTTP.

Pliki binarne i ograniczenia dużych odpowiedzi

W wielu procesach pliki muszą być dostępne dla właściwego workera. Zwykły filesystem nie jest uniwersalnym współdzielonym systemem przechowywania binariów w architekturze queue. Dla dużych odpowiedzi webhooków istnieją osobne mechanizmy przekazywania lub offload; ich dostępność zależy od wersji n8n, sposobu storage i licencji.

Domyślny limit N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX wynosi według dokumentacji 64 MiB. Od n8n 2.34.0 można rozważać N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true po odpowiednim przygotowaniu procesów i storage. Zewnętrzny S3/Azure storage wymaga właściwej licencji self-hosted Business lub Enterprise; nie zakładaj, że funkcje te istnieją w Community Edition.

Offload przez wspólny system plików jest opisywany dla szczególnego scenariusza odpowiedzi, ale nie jest rekomendowaną ogólną architekturą trwałych binariów.

Jak udowodnić, że workflow naprawdę wykonał worker?

Sam zielony status Redis i kontenera n8n-worker nie jest wystarczający. Uruchom bezpieczny, opublikowany workflow wyzwalany webhookiem lub harmonogramem, sprawdź wykonanie w widoku Executions i skoreluj zdarzenie z logiem workera.

docker compose ps
docker compose logs --tail=100 n8n-worker
# Przy odpowiedniej konfiguracji Redis:
docker compose exec -T redis redis-cli ping

PONG potwierdza odpowiedź Redis, ale nie wykonanie workflow. Gdy używasz mechanizmu health check, można włączyć QUEUE_HEALTH_CHECK_ACTIVE=true i sprawdzać prywatnie /healthz oraz /healthz/readiness.

Ręczne wykonania i task runners

Przy domyślnym OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false ręczne uruchomienie workflow z edytora może nadal wykonać się na main. Do weryfikacji kolejkowania użyj prawidłowo opublikowanego, produkcyjnego wyzwalacza. Zewnętrzne task runners dla Code nodes to osobny komponent, a nie alternatywna nazwa workerów queue.

Skalowanie nie oznacza wysokiej dostępności main

Dodanie kilku workerów zwiększa zdolność obsługi pracy, lecz nie zapewnia automatycznej redundancji interfejsu i instancji main. Opcje multi-main i dedykowane procesory webhooków mają osobne wymagania. Nie utożsamiaj wzrostu liczby procesów ze zweryfikowaną odpornością na awarię.

Planuj backup, monitoring PostgreSQL i Redis, wymianę wersji i plan awaryjnego wycofania zmiany. Backup n8n.

Najczęstsze pytania

Czy queue mode wymaga PostgreSQL?

Tak, opisany model kolejkowy korzysta ze wspólnej bazy PostgreSQL i Redis.

Czy workery zwiększą szybkość jednego workflow?

Nie zawsze. Ich zaletą jest równoległa obsługa wielu wykonań, nie automatyczne przyspieszenie pojedynczego wywołania API.

Czy ręczny test workflow pokaże pracę workera?

Niekoniecznie. Przy domyślnych ustawieniach ręczne uruchomienie może działać na main.

Czy queue mode zastępuje kopie zapasowe?

Nie. Jest rozwiązaniem do rozdzielenia wykonań, a nie do odzyskiwania danych po awarii.
