SKALOWANIE

Tryb kolejkowy n8n

Tryb kolejkowy oddziela wykonywanie workflow od głównego procesu n8n. Główna instancja odbiera triggery i tworzy wykonania, Redis koordynuje kolejkę, workery wykonują zadania, a PostgreSQL przechowuje współdzielone dane workflow i wykonań.

SZYBKA DECYZJA

Czy rzeczywiście potrzebujesz trybu kolejkowego?

Pozostań w trybie zwykłym, gdy

Jedna instancja swobodnie obsługuje szczytowe wykonania, a CPU, RAM i opóźnienia wykonywania pozostają stabilne. Tryb kolejkowy dodaje komponenty, których jeszcze nie potrzebujesz.

Rozważ tryb kolejkowy, gdy

Trwałe równoległe wykonania powodują konkurencję o zasoby, opóźnienia wykonywania rosną pod obciążeniem albo potrzebujesz zwiększyć wydajność, uruchamiając wiele workerów.

Najpierw skaluj pionowo, gdy

Wąskim gardłem jest po prostu niewystarczające CPU lub RAM, a jedna większa instancja nadal może sprawnie obsłużyć obciążenie.

Mierz przed zmianą architektury

Użyj szczytowej współbieżności, CPU, RAM, czasu wykonania, głębokości kolejki i obciążenia bazy, aby uzasadnić zmianę.

ARCHITEKTURA

Jak działa tryb kolejkowy n8n

1 · MainOdbiera timery, webhooki i żądania workflow oraz tworzy wykonanie zamiast samodzielnie realizować wykonanie produkcyjne.
2 · RedisDziała jako broker wiadomości. Przechowuje oczekujące komunikaty wykonań, aby następny dostępny worker mógł przejąć zadanie.
3 · WorkerOdbiera ID wykonania, ładuje dane workflow ze współdzielonej bazy, uruchamia workflow i zapisuje wynik z powrotem.
4 · PostgreSQLZapewnia współdzielone trwałe dane workflow i wykonań. Rozproszony tryb kolejkowy nie jest obsługiwany z SQLite.

PODSTAWOWE WYMAGANIA

Czego wymaga każde wdrożenie trybu kolejkowego

Redis

Wszystkie procesy main i workerów potrzebują niezawodnego dostępu do usługi Redis używanej do koordynacji kolejki.

PostgreSQL

Main i workery muszą współdzielić bazę. Tryb kolejkowy jest architekturą rozproszoną i nie powinien być projektowany wokół SQLite.

Spójna konfiguracja n8n

Main i workery muszą działać w trybie kolejkowym i współdzielić konfigurację potrzebną do dostępu do Redis, PostgreSQL i zaszyfrowanych credentials.

Zasoby workerów

Workery potrzebują wystarczającego CPU i RAM dla wykonywanych workflow. Dodanie procesów nie usuwa kosztu zasobów każdego wykonania.

Włącz tryb kolejkowy w istniejącym stosie self-hosted. Najpierw potwierdź, że główna usługa n8n i każdy worker mogą przez sieć prywatną połączyć się z tą samą bazą PostgreSQL i Redis. Ustaw EXECUTIONS_MODE=queue zarówno na main, jak i workerach, oraz podaj QUEUE_BULL_REDIS_HOST=redis oraz QUEUE_BULL_REDIS_PORT=6379 gdy redis jest faktyczną nazwą usługi Compose. Użyj DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres oraz pasujących DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER oraz DB_POSTGRESDB_PASSWORD na każdym procesie; zastąp przykładowe nazwy usług własnymi. Podaj dokładnie istniejący N8N_ENCRYPTION_KEY we wszystkich procesach. Nigdy nie publikuj portów hosta Redis ani PostgreSQL tylko po to, aby połączyć kontenery w tej samej sieci Compose.

Uruchom wykonawcę, nie drugi edytor. Dodaj usługę workera n8n używając tej samej przypiętej wersji obrazu n8n i współdzielonych ustawień co main, ale uruchom ją poleceniem worker Jeśli nazwałeś tę usługę n8n-worker, uruchom ją poleceniem docker compose up -d n8n-worker. Po potwierdzeniu rzeczywistego wykonania na jednym workerze możesz użyć docker compose up -d --scale n8n-worker=2 aby uruchomić drugi worker z tej usługi. Są to dodatki do istniejącego poprawnie skonfigurowanego stosu Compose, a nie samodzielny plik instalacyjny; zachowaj istniejące trwałe wolumeny, proxy HTTPS, sekrety i backupy.

Fragment Compose trybu kolejkowego dla istniejącego stosu. Scal poniższy przykład z bieżącym compose.yaml; to nie jest pełnym samodzielnym wdrożeniem. Zakłada, że masz już trwałe, prywatne postgres oraz n8n usługi, istniejącą N8N_VERSION przypiętą wersję w środowisku oraz własne chronione POSTGRES_PASSWORD i oryginalny N8N_ENCRYPTION_KEY. Dopasuj nazwy, wolumeny, bazę i wersję n8n do istniejącego projektu. Dodaj ustawienia Redis trybu kolejkowego i EXECUTIONS_MODE=queue również do istniejącej usługi main, jak opisano wyżej.

# Scal z istniejącymi usługami; nie zastępuj całego pliku Compose.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

W tym fragmencie żaden port hosta nie jest publikowany dla Redis ani workera. Trwałość append-only Redis jest dodatkową warstwą odzyskiwania, nie jest a nie zamiennikiem backupów poza serwerem. Pozostaw istniejącą konfigurację HTTPS i uwierzytelniania bez zmian. Dla node'ów Code wymagających zewnętrznych task runnerów skonfiguruj procesy runnerów dla wdrożenia workerów oddzielnie; sam tryb kolejkowy nie zastępuje task runnerów.

Konwertujesz istniejącą instancję SQLite? Nie zmieniaj po prostu DB_TYPE i nie uruchamiaj z pustą bazą PostgreSQL: to nie migruje starych workflow i credentials. Przed przełączeniem wykonaj backup źródłowej bazy, trwałego .n8n katalogu i oryginalnego klucza szyfrowania; użyj obsługiwanej procedury eksportu/importu lub migracji n8n, a następnie zweryfikuj workflow i zaszyfrowane credentials na oddzielnym celu. Zachowaj oryginalne pliki do rollbacku i użyj podlinkowanego niżej przewodnika Backup i odtwarzanie do przygotowania odzyskiwania. Nigdy nie usuwaj database.sqlite jako skrótu.

WSPÓŁBIEŻNOŚĆ WORKERÓW

Workery skalują się zarówno liczbą procesów, jak i liczbą zadań na worker

Każdy worker może przetwarzać wiele zadań równolegle. Obecna domyślna współbieżność workera w n8n wynosi 10, a dokumentacja zaleca współbieżność 5 lub większą. Bardzo niska współbieżność połączona z wieloma workerami może tworzyć zbędne połączenia z bazą i wyczerpać pulę połączeń.

Zwiększ współbieżność, gdy

Worker ma wolne CPU i RAM, a workflow głównie czekają na usługi zewnętrzne zamiast nasycać moc obliczeniową lub pamięć.

Dodaj workery, gdy

Jeden proces workera staje się wąskim gardłem, a baza, Redis i infrastruktura mają zapas na większą równoległość.

Zmniejsz współbieżność, gdy

Pojedyncze workflow mocno obciążają pamięć lub CPU, a równoległe zadania powodują konkurencję o zasoby, presję OOM lub niestabilny czas wykonania.

Obserwuj PostgreSQL

Więcej workerów i większa współbieżność zwiększają aktywność bazy. Skalowanie wydajności wykonawczej bez skalowania bazy może tylko przenieść wąskie gardło zamiast je usunąć.

Wiedz, który limit współbieżności faktycznie obowiązuje. Worker może zostać uruchomiony poleceniem n8n worker --concurrency=5, lub równoważnym poleceniem workera w usłudze Compose. Jeśli N8N_CONCURRENCY_PRODUCTION_LIMIT jest jawnie ustawione na wartość inną niż -1, to ustawienie ma pierwszeństwo w trybie kolejkowym; w przeciwnym razie n8n używa wartości workera --concurrency lub domyślnej wartości 10. Nie mnoż liczby workerów przez nominalną wartość domyślną i nie nazywaj tego gwarantowaną przepustowością: rzeczywista wydajność zależy od czasu zadań, CPU, pamięci, zewnętrznych API i połączeń PostgreSQL.

WEBHOOKI

Tryb kolejkowy może dodać opóźnienie przekazania wykonania

Proces main lub webhook odbiera żądanie HTTP, ale wykonanie workflow realizuje worker. Przekazanie przez Redis dodaje pewien narzut. Dla webhooków wrażliwych na opóźnienia mierz czas odpowiedzi end-to-end zamiast zakładać, że większa liczba workerów automatycznie przyspiesza każde żądanie.

OdbiórProces main/webhook przyjmuje żądanie.
KolejkaWykonanie jest przekazywane do Redis.
WykonanieDostępny worker uruchamia workflow.
OdpowiedźW razie potrzeby wynik wraca ścieżką kolejki.

Kieruj ruch webhooków do właściwego procesu. Przy dedykowanych n8n webhook procesach za reverse proxy lub load balancerem kieruj produkcyjne ścieżki /webhook/* oraz /webhook-waiting/* do procesów webhook; pozostaw /webhook-test/*, żądania edytora i API na main. Nie dodawaj main do puli load balancingu produkcyjnych webhooków, chyba że świadomie akceptujesz dodatkowe obciążenie. Workflow Respond to Webhook może utrzymywać klienta w oczekiwaniu, aż worker zakończy i zwróci odpowiedź, więc tryb kolejkowy nie gwarantuje natychmiastowych odpowiedzi HTTP ani braku timeoutów. Przed przełączeniem ruchu przetestuj rzeczywisty zewnętrzny callback i zachowanie odpowiedzi.

DANE BINARNE

Nie pomijaj współdzielonej przestrzeni

Ograniczenie systemu plików

Tryb kolejkowy nie obsługuje magazynu danych binarnych opartego na systemie plików jako współdzielonego modelu trwałości dla rozproszonych workerów.

Zewnętrzny magazyn danych binarnych

Gdy workflow muszą przechowywać dane binarne między rozproszonymi workerami, użyj magazynu dostępnego dla każdej wymaganej instancji, np. obsługiwanego zewnętrznego object storage.

Duże odpowiedzi webhooków

Odpowiedzi webhooków z workerów wracają do procesu odbierającego. Duże body odpowiedzi mogą zwiększać presję na pamięć Redis i wymagać świadomej konfiguracji magazynu odpowiedzi.

Planuj przed rozproszeniem workerów

Obciążenie silnie zależne od lokalnych plików musi zostać przeprojektowane pod współdzieloną trwałość, zanim workery zostaną rozproszone między maszynami.

Granica dużych odpowiedzi webhooków. Aktualna dokumentacja n8n podaje dla N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX domyślną wartość 64 MiB dla odpowiedzi workera przesyłanej z powrotem przez kolejkę. Redis może utrzymywać kilka kopii jednocześnie, dlatego zaplanuj około 1.5-krotności rozmiaru odpowiedzi w pamięci Redis na każdą równoległą dużą odpowiedź. Bez offloadingu zbyt duża odpowiedź zakończy się błędem zamiast magicznie przyspieszyć po dodaniu workerów.

Ograniczenia wersji i licencji. Od n8n 2.34.0, workery mogą używać N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true do offloadingu zbyt dużych body odpowiedzi webhooków do czytelnego współdzielonego magazynu binarnego, ale najpierw zaktualizuj każdy proces main i webhook do 2.34.0 lub nowszej. Wybrany N8N_DEFAULT_BINARY_DATA_MODE musi faktycznie przechowywać dane i być czytelny dla każdego uczestniczącego procesu. Zewnętrzny magazyn binarny S3 i Azure wymaga ważnej self-hosted licencji Business lub Enterprise ; nie zakładaj, że Community Edition może je włączyć. Tryb database danych binarnych może offloadować zbyt dużą odpowiedź bez płatnego magazynu zewnętrznego, ale instancja main ładuje całe zapisane body do pamięci, a magazyn bazy ma własny limit rozmiaru pliku. Dla konkretnie offloadingu body odpowiedzi, n8n opisuje również współdzieloną opcję systemu plików gdy każda instancja montuje ten sam dysk, ale wyraźnie nie rekomenduje takiej konfiguracji. Nie myl tej specjalnej ścieżki offloadingu z obsługą trwałych danych binarnych opartych na systemie plików w rozproszonym wdrożeniu trybu kolejkowego. Przed włączeniem offloadingu sprawdź edycję, wersję i konfigurację magazynu.

MONITORING

Sprawdź, czy kolejka rzeczywiście pomaga

Głębokość kolejki

Kolejka rosnąca szybciej, niż workery ją opróżniają, wskazuje na niewystarczającą wydajność wykonywania albo wąskie gardło dalej w systemie.

CPU i RAM workerów

Mierz nasycenie i szczyty pamięci dla każdego workera. Bezczynne workery przy rosnącej kolejce wskazują na inne ograniczenie.

Opóźnienie wykonania

Śledź opóźnienie między utworzeniem wykonania a jego faktycznym startem, a nie tylko sam czas działania workflow.

Health checks

Endpointy health workera mogą informować, czy worker działa oraz czy jego połączenia z bazą i Redis są gotowe.

Zweryfikuj wykonanie na workerze, a nie tylko zielony status kontenera. Przy poprawnie skonfigurowanym stosie Compose sprawdź docker compose ps oraz docker compose logs --tail=100 n8n-worker (zastąp nazwę usługi, jeśli jest inna). Uruchom nieszkodliwy opublikowany produkcyjny workflow przy użyciu zaplanowanego triggera lub testowego webhooka, następnie dopasuj jego wykonanie w widoku Executions n8n do faktycznego przetwarzania przez workera w logach. Sam poprawnie otwierający się edytor, działający kontener Redis lub oczekujące wykonanie nie jest nie dowodzi, że worker wykonał zadanie.

Sprawdź zależności i gotowość. Przy domyślnych przykładowych nazwach usług docker compose exec -T redis redis-cli ping powinno otrzymać PONG gdy uwierzytelnianie Redis na to pozwala, a docker compose exec -T postgres pg_isready -U n8n -d n8n sprawdza gotowość PostgreSQL (dostosuj credentials i nazwy usług). Włącz QUEUE_HEALTH_CHECK_ACTIVE=true na workerze, gdy potrzebujesz jego prywatnych /healthz oraz /healthz/readiness endpointów; endpoint readiness sprawdza łączność z Redis/bazą. Nie wystawiaj tych endpointów workera publicznie tylko po to, aby je monitorować.

Ręczne uruchomienia to inny test. Domyślnie OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, więc ręczne uruchomienie workflow w edytorze może wykonać się na main nawet przy poprawnie skonfigurowanym trybie kolejkowym. Ustaw na true tylko jeśli zamierzasz wysyłać ręczne wykonania do workerów i sprawdziłeś zmianę w środowisku staging. Workery trybu kolejkowego różnią się także od zewnętrznych task runnerów n8n, które mają osobne wymagania konfiguracyjne dla wykonywania node'ów Code.

GRANICA WYSOKIEJ DOSTĘPNOŚCI

Tryb kolejkowy skaluje wykonania, ale nie zapewnia automatycznie wysokiej dostępności procesu main

Współdziel klucz szyfrowania

Każdy worker musi używać tego samego N8N_ENCRYPTION_KEY co instancja main, aby workery mogły odszyfrować credentials wymagane przez wykonania workflow.

Utrzymuj zgodne wersje

Procesy main, webhook i worker powinny działać na tej samej wersji n8n. Mieszane wersje mogą powodować niezgodne zachowanie podczas zmian rolling.

Procesy webhook są oddzielną warstwą skalowania

Gdy wolumen przychodzących webhooków staje się wąskim gardłem, dedykowane procesy webhook mogą działać za load balancerem, podczas gdy workery obsługują wykonania. Nie dodawaj tej warstwy, jeśli zmierzony wolumen żądań jej nie uzasadnia.

Multi-main to inna funkcja

Uruchamianie wielu procesów main dla wysokiej dostępności nie jest tym samym co zwykły tryb kolejkowy. n8n obecnie dokumentuje multi-main jako funkcję self-hosted Enterprise z dodatkowymi wymaganiami dotyczącymi load balancera i sesji.

FAQ

Tryb kolejkowy n8n: najczęstsze pytania

Czy tryb kolejkowy n8n wymaga Redis?

Tak. Redis jest brokerem wiadomości koordynującym oczekujące wykonania między instancją main a workerami.

Czy tryb kolejkowy może używać SQLite?

Nie w rozproszonej architekturze trybu kolejkowego. Main i workery potrzebują współdzielonego dostępu do bazy, a n8n dokumentuje PostgreSQL jako bazę dla tej konfiguracji.

Ile workerów uruchomić?

Nie ma uniwersalnej liczby. Zacznij od zmierzonej współbieżności i wykorzystania workerów, a następnie dodawaj wydajność, monitorując PostgreSQL, Redis, CPU, RAM i głębokość kolejki.

Czym jest współbieżność workera n8n?

To liczba zadań, które worker może przetwarzać równolegle. Obecna wartość domyślna to 10, a n8n zaleca współbieżność workera 5 lub większą zamiast tworzenia wielu workerów o niskiej współbieżności.

Czy włączać tryb kolejkowy na małym VPS?

Tylko gdy obciążenie to uzasadnia. Małe wdrożenie, które swobodnie działa jako jedna instancja, zwykle łatwiej obsługiwać bez Redis i oddzielnych workerów.
