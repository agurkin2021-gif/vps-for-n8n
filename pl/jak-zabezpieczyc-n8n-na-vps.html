BEZPIECZEŃSTWO PRODUKCYJNE

Jak zabezpieczyć n8n na VPS

Aby zabezpieczyć n8n na VPS, nie wystawiaj n8n (5678), PostgreSQL (5432) ani opcjonalnego Redis (6379) do publicznego Internetu; używaj reverse proxy HTTPS, kluczy SSH i MFA, zachowaj klucz szyfrowania, uwierzytelniaj webhooki, ogranicz ryzykowne możliwości workflow i audytuj wdrożoną instancję. Zabezpiecz edytor oddzielnie od publicznych tras webhooków. Sam HTTPS nie zabezpiecza połączonych usług.

SZYBKA LISTA KONTROLNA

Minimalny poziom bezpieczeństwa przed publicznym udostępnieniem

Zacznij od sprawdzenia dostępnych portów, HTTPS, zweryfikowanego dostępu administracyjnego, MFA i ochrony zapisanych credentials. Uwierzytelniaj każdy przychodzący webhook, zanim będzie mógł uruchomić wrażliwe działania. Po zmianie kontroli dostępu sprawdź, czy uprawnieni edytorzy i integracje zewnętrzne nadal działają, a następnie uruchom audyt bezpieczeństwa n8n.

Tylko HTTPS

Umieść n8n za poprawnie skonfigurowanym reverse proxy TLS i konsekwentnie używaj publicznego URL HTTPS dla edytora i webhooków.

Minimalna liczba otwartych portów

Wystawiaj tylko porty wymagane dla ruchu publicznego. PostgreSQL, Redis i wewnętrzne porty aplikacji pozostaw poza publicznym Internetem.

Utwardź SSH

Administruj za pomocą kluczy, ogranicz osoby mogące się logować i regularnie aktualizuj system operacyjny.

Chroń credentials

Utrzymuj stały i tajny klucz szyfrowania n8n. Pliki środowiskowe, dostęp do bazy i kopie backupów traktuj jako wrażliwe zasoby.

BRZEG SIECI

Reverse proxy, HTTPS i zaufane nagłówki

Terminacja TLS

Użyj reverse proxy, takiego jak Nginx, Caddy lub Traefik, do terminacji HTTPS. Przekieruj zwykły HTTP i nie wystawiaj bezpośrednio portu aplikacji n8n, gdy zamierzonym punktem wejścia jest proxy.

Konfiguracja proxy

Gdy n8n działa za reverse proxy, poprawnie skonfiguruj liczbę hopów proxy i przekazuj nagłówki forwarded potrzebne n8n do odtworzenia pierwotnego żądania klienta.

Bezpieczne cookies

Udostępniaj edytor przez HTTPS, aby cookies uwierzytelniające mogły pozostać bezpieczne. Nie obchodź błędnej konfiguracji TLS przez osłabianie bezpieczeństwa cookies.

URL webhooka

Ustaw publiczny URL webhooka na zewnętrznie dostępnej nazwie hosta HTTPS, aby generowane endpointy webhooków nie wskazywały wewnętrznego kontenera ani adresu HTTP.

Utrzymaj edytor prywatny bez psucia webhooków. Jeśli to praktyczne, ogranicz dostęp administracyjny za pomocą VPN, polityki zaufanych IP lub uwierzytelnionego proxy. Publiczne odbiorniki webhooków i trasy callback OAuth mogą wymagać dalszej dostępności; przed wymuszeniem reguły proxy przetestuj zarówno logowanie zaufanego edytora, jak i rzeczywisty zewnętrzny callback. Nagłówki adresu klienta przekazuj tylko z zaufanych proxy, nie z dowolnych nagłówków żądania.

Uwierzytelniaj wywołujących webhooki: w node Webhook wybierz uwierzytelnianie Basic, Header lub JWT zamiast None, gdy nadawca je obsługuje. Użyj opcji IP(s) Allowlist tam, gdzie jest to właściwe, i weryfikuj podpisy dostawcy, jeśli integracja obsługuje podpisane żądania. Trudny do odgadnięcia URL nie jest wystarczającym uwierzytelnieniem. W razie potrzeby stosuj limity zapytań na proxy i potwierdź, że prawidłowe skoki ruchu nie są blokowane. Oficjalne opcje uwierzytelniania Webhook.

UTWARDZANIE VPS

Zmniejsz powierzchnię ataku serwera

Firewall

Domyślnie odrzucaj niezamówiony ruch przychodzący i zezwalaj tylko na usługi, które muszą być dostępne. Porty bazy danych i Redis zwykle powinny znajdować się w sieciach prywatnych/lokalnych.

SSH

Preferuj klucze SSH zamiast haseł, wyłącz zbędne ścieżki logowania i ogranicz dostęp administracyjny. Dostęp równoważny root powinien być ściśle kontrolowany.

Aktualizacje systemu

Aktualizuj host Linux i runtime kontenerów. Utwardzenie aplikacji nie zrekompensuje wystawionego lub przestarzałego systemu operacyjnego.

Ekspozycja kontenerów

Publikuj tylko porty wymagające dostępu z hosta. Usługi wewnętrzne powinny komunikować się przez prywatne sieci Docker, a nie przez interfejsy publiczne.

Sprawdź przed zmianą ustawień firewalla lub SSH: sprawdź nasłuchujące porty poleceniem sudo ss -lntp, publikację Docker poleceniem docker compose ps z katalogu projektu oraz politykę firewalla hosta poleceniem sudo ufw status verbose jeśli używany jest UFW. Przed wyłączeniem logowania hasłem sprawdź faktyczny port SSH i udane logowanie kluczem w osobnej sesji. Porty publikowane przez Docker mogą omijać reguły UFW; sam status firewalla nie dowodzi, że port 5678 jest prywatny. Sprawdź rzeczywistą dostępność z zewnątrz. Ograniczenie Docker/UFW.

Sprawdź automatyczne aktualizacje bezpieczeństwa Ubuntu zamiast zakładać, że działają: sprawdź apt-config dump APT::Periodic::Unattended-Upgrade oraz log /var/log/unattended-upgrades/unattended-upgrades.log. Jeśli automatyczne aktualizacje bezpieczeństwa są wyłączone, sudo dpkg-reconfigure unattended-upgrades udostępnia obsługiwane okno konfiguracji. Przed włączeniem na działającym VPS sprawdź zachowanie restartów systemu i usług. Aktualizacje Ubuntu APT nie aktualizują automatycznie obrazu Docker n8n ani każdego zewnętrznego repozytorium oprogramowania. Dokumentacja automatycznych aktualizacji Ubuntu.

Opcjonalny monitoring brute-force SSH: Fail2Ban może wykrywać powtarzające się nieudane logowania SSH. Jeśli jest zainstalowany i skonfigurowany dla SSH, sprawdź jail poleceniem sudo fail2ban-client status sshd i potwierdź, że czyta właściwy log uwierzytelniania SSH lub journal oraz pasuje do skonfigurowanego portu. To uzupełnia klucze SSH i ograniczenia sieciowe; nie zastępuje ich. Nie kopiuj stałego portu SSH ani reguły banowania bez wcześniejszego sprawdzenia istniejącego dostępu. Wytyczne Ubuntu dotyczące utwardzania SSH.

BAZA DANYCH I REDIS

Utrzymuj usługi backendowe prywatne

W typowej konfiguracji Docker Compose PostgreSQL i Redis trybu kolejkowego powinny być dostępne dla odpowiednich kontenerów przez sieć prywatną, a nie porty publikowane na hoście. Sprawdź poleceniem docker compose ps że 5432 i 6379 nie są publikowane publicznie; osobno sprawdź ekspozycję firewalla VPS/cloud. Polityki sieciowe nie zastępują danych uwierzytelniających bazy zgodnych z zasadą najmniejszych uprawnień.

RedisRedis w trybie kolejkowym to infrastruktura, a nie publiczny endpoint. Ogranicz dostęp sieciowy do komponentów n8n, które go wymagają.
CredentialsUżywaj dedykowanych credentials bazy wyłącznie z uprawnieniami potrzebnymi aplikacji i chroń je poza kontrolą wersji.

SEKRETY N8N

Chroń klucz szyfrowania i granicę credentials

Klucz szyfrowania

n8n szyfruje zapisane credentials przy użyciu klucza szyfrowania. Zachowuj ten sam klucz między restartami i workerami oraz chroń go oddzielnie od zwykłej zawartości aplikacji.

Sekrety środowiska

Nie commituj haseł, tokenów ani klucza szyfrowania do publicznego repozytorium. Ogranicz dostęp do plików środowiskowych i sekretów wdrożenia.

Dostęp użytkowników

Dostęp do edytora dawaj tylko zaufanym użytkownikom. Workflow mogą łączyć się z wrażliwymi systemami, przetwarzać sekrety lub uruchamiać potężne node'y.

Zakres credentials

Tam, gdzie to możliwe, używaj kont usługowych i tokenów API o wąskim zakresie. Przejęty workflow nie powinien automatycznie dziedziczyć szerokiego dostępu do niezwiązanych systemów.

Konfiguracja n8n do sprawdzenia: N8N_BLOCK_ENV_ACCESS_IN_NODE=true blokuje dostęp node'a Code i wyrażeń do wartości środowiskowych; N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true wymusza uprawnienia tylko dla właściciela pliku ustawień. Utrzymuj N8N_ENCRYPTION_KEY jako trwały i bezpiecznie zbackupowany: n8n może utworzyć losowy klucz przy pierwszym uruchomieniu, ale jego utrata może sprawić, że istniejące zaszyfrowane credentials staną się bezużyteczne. Nie zastępuj lekkomyślnie produkcyjnego klucza szyfrowania; używaj oficjalnie obsługiwanej procedury rotacji. Zablokowanie dostępu do środowiska może zepsuć istniejące integracje, dlatego testuj przed zmianami produkcyjnymi. Definicje zmiennych bezpieczeństwa n8n.

RYZYKO WORKFLOW

Node'y mogą rozszerzać granicę bezpieczeństwa

Self-hosting daje workflow znaczne możliwości. Wykonywanie kodu, dostęp do shell, dowolne żądania HTTP i zewnętrzne community nodes mogą zwiększać ryzyko. Wyłącz funkcje, których nie potrzebujesz, i sprawdzaj niezaufane importy workflow przed uruchomieniem.

Używaj dokładnie obsługiwanych mechanizmów: skonfiguruj NODES_EXCLUDE jako tablicę JSON node'ów do wyłączenia, takich jak n8n-nodes-base.executeCommand oraz n8n-nodes-base.readWriteFile, jeśli nie są używane. Niektóre node'y wysokiego ryzyka są już domyślnie blokowane w nowszych wersjach; przed zmianą sprawdź faktyczną listę. Oficjalne wykluczenia node'ów.

W n8n 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true włącza kontrole wychodzących żądań HTTP do zakresów adresów wewnętrznych, loopback i metadata. Prawidłowe workflow korzystające z wewnętrznych API mogą przestać działać; jeśli to konieczne, dodawaj do allowlisty wyłącznie konkretne cele, które kontrolujesz. Segmentację sieci zachowaj jako podstawową ochronę. Dla izolacji node'a Code sprawdź zewnętrzne task runnery. Ochrona SSRF · Izolacja task runnera.

Community nodesInstaluj tylko pakiety, którym ufasz; wykonują się wewnątrz środowiska n8n.
Ryzykowne node'yWyklucz node'y, których wdrożenie nie potrzebuje, gdy ich możliwości wykraczają poza zamierzoną granicę workflow.
SSRFUżywaj ochrony SSRF n8n i kontroli sieciowej tam, gdzie workflow nie powinny mieć dostępu do endpointów wewnętrznych lub metadata.
Importy workflowPrzed aktywacją sprawdzaj importowane workflow, credentials, wyrażenia i kroki wykonywalne.

AUDYT I AKTUALIZACJE

Bezpieczeństwo jest procesem operacyjnym

Uruchom audyt bezpieczeństwa n8n

Oficjalne polecenie CLI to n8n audit. Jeśli usługa Docker Compose nazywa się n8n, uruchom docker compose exec -T n8n n8n audit w katalogu tego wdrożenia. Sprawdź pięć kategorii: nieużywane credentials, ryzykowne wzorce zapytań SQL, dostęp do systemu plików, ryzykowne/community nodes oraz ryzyka instancji, w tym niezabezpieczone webhooki i przestarzałe wydania. Napraw istotne problemy i uruchom audyt ponownie. To nie jest test penetracyjny. Oficjalny przewodnik audytu.

Aktualizuj świadomie

Utrzymuj n8n na wersji wystarczająco aktualnej, aby otrzymywać poprawki bezpieczeństwa. Czytaj release notes i testuj ważne aktualizacje zamiast pozostawiać publicznie dostępną instancję stale przestarzałą.

Monitoruj uwierzytelnianie

Obserwuj nietypowe wzorce dostępu, zmiany workflow i awarie. Dodatkowo ogranicz interfejs edytora, jeśli model operacyjny nie wymaga szerokiej dostępności publicznej.

Przygotuj rollback i odzyskiwanie

Przed istotnymi aktualizacjami wykonuj możliwe do odtworzenia backupy. Szczegółowy zakres backupu i odtwarzania opisuje oddzielny przewodnik odzyskiwania.

Ograniczaj wrażliwą historię wykonań: udane wykonania mogą utrwalać dane klientów i tokeny. Gdy to właściwe, ustaw EXECUTIONS_DATA_SAVE_ON_SUCCESS=none, zachowaj EXECUTIONS_DATA_PRUNE=true, i wybierz EXECUTIONS_DATA_MAX_AGE w godzinach, na przykład 168 (siedem dni). To konfigurowalne przykłady, a nie prawne zasady retencji. Mniej historii oznacza mniej danych do debugowania i analizy incydentów; wykonania działające, oczekujące lub opatrzone adnotacjami mogą nie być usuwane w ten sam sposób. Oficjalna retencja wykonań.

Podejrzenie przejęcia: ogranicz złośliwy dostęp bez niszczenia dowodów, sprawdź aktywność proxy, hosta i n8n oraz zmienione workflow, unieważnij lub zrotuj potencjalnie ujawnione credentials usług zewnętrznych, usuń przyczynę i w razie potrzeby odtwarzaj wyłącznie z przetestowanych backupów. Sprawdź dotknięte URL webhooków, konta edytora i połączone usługi; nie zakładaj, że HTTPS, snapshoty lub zakup VPS zapewniają usługę reagowania na incydenty.

KONTROLA KONTA I PLATFORMY

Chroń edytor tak samo jak VPS

Wymagaj silniejszej ochrony logowania

Włącz uwierzytelnianie dwuskładnikowe dla kont edytora i wymuszaj MFA przez polityki bezpieczeństwa n8n, jeśli Twoja edycja obsługuje centralne egzekwowanie zasad.

Ogranicz osoby mogące edytować workflow

Dostęp do edytora jest dostępem uprzywilejowanym: workflow mogą odczytywać credentials, wywoływać systemy wewnętrzne i uruchamiać potężne node'y. Ograniczaj dostęp użytkowników i usuwaj konta, które nie są już potrzebne.

Wyłącz możliwości, których nie używasz

Zmniejsz powierzchnię ataku aplikacji, wyłączając publiczne API, gdy nie jest potrzebne, oraz blokując node'y lub funkcje wysokiego ryzyka, których nie wymaga Twój model operacyjny.

Świadomie używaj kontroli SSRF i sekretów

Dla workflow mogących wykonywać dowolne żądania HTTP oceń ochronę SSRF n8n i trzymaj sekrety poza kodem workflow, publicznymi repozytoriami i szeroko czytelnymi plikami środowiskowymi.

Ogranicz nieużywane endpointy zarządzania: N8N_PUBLIC_API_DISABLED=true wyłącza publiczne REST API n8n, a N8N_PUBLIC_API_SWAGGERUI_DISABLED=true oddzielnie wyłącza jego API playground. Rób to tylko wtedy, gdy integracje nie wymagają tych funkcji. Wyłączenie REST API nie uwierzytelnia URL webhooków workflow. Używaj MFA dla użytkowników edytora, a scentralizowanych polityk tylko tam, gdzie obsługuje je Twoja edycja n8n.

Oficjalna dokumentacja: wyłączenie publicznego API · zmienne polityki bezpieczeństwa · polecenia audytu.

FAQ

Bezpieczeństwo VPS z n8n: najczęstsze pytania

Czy port n8n powinien być wystawiony bezpośrednio?

Gdy reverse proxy jest publicznym punktem wejścia, wystaw proxy, a port aplikacji pozostaw za nim zamiast szeroko publikować zbędne usługi.

Czy PostgreSQL lub Redis powinny być publiczne?

Zwykle nie. Powinny być dostępne wyłącznie dla systemów, które ich wymagają. Publiczna ekspozycja zwiększa powierzchnię ataku bez korzyści dla normalnego działania n8n.

Dlaczego klucz szyfrowania n8n jest ważny?

Chroni credentials przechowywane przez n8n i musi pozostać spójny w całym wdrożeniu. Jego utrata może sprawić, że odzyskane dane nie pozwolą uzyskać użytecznych zaszyfrowanych credentials.

Czy community nodes są bezpieczne?

Rozszerzają n8n o kod stron trzecich, dlatego należy traktować je jako zależności oprogramowania z własnym ryzykiem łańcucha dostaw i uprawnień. Instaluj tylko to, czemu ufasz i czego potrzebujesz.

Czy HTTPS sprawia, że self-hosted n8n jest bezpieczne?

Nie. HTTPS chroni transport. Bezpieczeństwo produkcyjne wymaga również utwardzenia hosta, kontroli dostępu, prywatnych usług backendowych, ochrony sekretów, bezpiecznych możliwości workflow, monitoringu i aktualizacji.

Czy edytor n8n może być prywatny, gdy produkcyjne webhooki nadal działają?

Tak. Zaufane reverse proxy lub VPN może ograniczać dostęp edytora/administratora oddzielnie od publicznych tras produkcyjnych webhooków i callback OAuth. Po każdej zmianie reguł dostępu przetestuj zaufane logowanie i dostarczenie zewnętrznego webhooka, aby przypadkowo nie zablokować integracji.

Jak uwierzytelniać przychodzące webhooki n8n?

Skonfiguruj uwierzytelnianie Basic, Header lub JWT w node Webhook, gdy nadawca je obsługuje. Możesz również użyć IP(s) Allowlist i sprawdzać podpisy dostawcy, jeśli są dostępne. Nie polegaj wyłącznie na pozornie tajnej ścieżce i weryfikuj żądania, zanim uruchomią wrażliwe działania API.
