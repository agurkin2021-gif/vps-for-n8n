スケーリング

n8nキューモード

キュー モードは、ワークフローの実行をメインの n8n プロセスから分離します。メイン インスタンスはトリガーを受信して​​実行を作成し、Redis がキューを調整し、ワーカーがジョブを実行し、PostgreSQL が共有ワークフローと実行データを保存します。

まず判断する

本当にキューモードが必要なのでしょうか？

次の場合は通常モードのままにしてください

単一のインスタンスでピーク時の実行を快適に処理し、CPU、RAM、実行レイテンシは安定したままになります。キュー モードでは、まだ必要のないコンポーネントが追加されます。

次の場合はキュー モードを検討してください。

並列実行を継続すると競合が発生したり、負荷がかかると実行レイテンシーが増加したり、複数のワーカーを実行して実行能力を追加したりする必要があります。

次の場合に最初に垂直方向にスケーリングします。

ボトルネックは単純に CPU または RAM が不足しているため、1 つの大きなインスタンスでもワークロードを適切に満たすことができます。

アーキテクチャを変更する前に測定する

ピーク時の同時実行性、CPU、RAM、実行時間、キューの深さ、データベースの負荷を考慮して、移行を正当化します。

構成と仕組み

n8n キュー モードの仕組み

1 · メインタイマー、Webhook、およびワークフロー リクエストを受信し、本番実行自体を行う代わりに実行を作成します。
2 · レディスメッセージブローカーとして機能します。保留中の実行メッセージが保持されるので、次に利用可能なワーカーがジョブを要求できるようになります。
3 · 労働者実行 ID を受け取り、共有データベースからワークフロー データをロードし、ワークフローを実行して結果を書き込みます。
4 · PostgreSQL共有された永続的なワークフローと実行データを提供します。分散キュー モードは SQLite ではサポートされていません。

必須要件

すべてのキューモード展開に必要なもの

レディス

すべてのメイン プロセスとワーカー プロセスは、キュー調整に使用される Redis サービスへの信頼できるアクセスを必要とします。

PostgreSQL

メインとワーカーはデータベースを共有する必要があります。キュー モードは分散アーキテクチャであるため、SQLite を中心に設計すべきではありません。

一致する n8n 構成

メインとワーカーはキュー モードを実行し、Redis、PostgreSQL、および暗号化された認証情報にアクセスするために必要な構成を共有する必要があります。

労働者の能力

ワーカーは、実行するワークフローに十分な CPU と RAM を必要とします。プロセスを追加しても、各実行のリソース コストは削除されません。

既存のセルフホスト型スタックでキュー モードを有効にします。 まず、n8n メイン サービスとすべてのワーカーがプライベート ネットワーク経由で同じ PostgreSQL データベースと Redis にアクセスできることを確認します。セット EXECUTIONS_MODE=queue メインとワーカー、およびサプライの両方で QUEUE_BULL_REDIS_HOST=redis そして QUEUE_BULL_REDIS_PORT=6379 いつ redis 実際の Compose サービス名です。使用する DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres そしてマッチング DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER そして DB_POSTGRESDB_PASSWORD あらゆるプロセスにおいて。サンプルのサービス名を実際のサービス名に置き換えます。正確な既存のものを提供します N8N_ENCRYPTION_KEY 彼ら全員に。同じ Compose ネットワーク上のコンテナに接続するためだけに Redis または PostgreSQL のホスト ポートを公開しないでください。

2 番目のエディタではなく、エグゼキュータを起動します。 メインと同じ固定された n8n イメージ バージョンと共有設定を使用して n8n ワーカー サービスを追加しますが、 worker コマンド。そのサービスに名前を付けた場合 n8n-worker、で始めてください docker compose up -d n8n-worker。 1 つのワーカーで実際の実行を確認した後、次を使用できます。 docker compose up -d --scale n8n-worker=2 そのサービスから 2 番目のワーカーを開始します。これらは、 正しく構成された既存の スタンドアロンのインストール ファイルではなく、スタックを作成します。既存の永続ボリューム、HTTPS プロキシ、シークレット、バックアップを保持します。

キューモード 既存のスタックのフラグメントを作成します。 以下の例を現在のものにマージします。 compose.yaml;それはです そうではない 完全なスタンドアロン展開。すでに永続的なプライベートを持っていることを前提としています postgres そして n8n サービス、既存の N8N_VERSION あなたの環境とあなた自身の保護にピンを留めます POSTGRES_PASSWORD そしてオリジナルの N8N_ENCRYPTION_KEY。名前、ボリューム、データベース、n8n バージョンを既存のプロジェクトと一致させます。キューモード Redis 設定を追加し、 EXECUTIONS_MODE=queue 前述のように、既存のメイン サービスにも適用されます。

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

このフラグメント内の Redis またはワーカーに対してホスト ポートは公開されていません。 Redis の追加専用永続性は追加の回復レイヤーです。 そうではない オフサーバーバックアップの代替手段。既存の HTTPS と認証構成を変更しないでください。外部タスク ランナーを必要とするコード ノードの場合は、ワーカー デプロイメントのランナー プロセスを個別に構成します。キュー モード自体はタスク ランナーを置き換えるものではありません。

既存の SQLite インスタンスを変換しますか? 単純に変えるのではなく DB_TYPE そして、空の PostgreSQL データベースに対して開始します。これを行っても、古いワークフローと資格情報は移行されません。カットオーバーの前に、ソース データベースを永続的にバックアップします。 .n8n ディレクトリと元の暗号化キー。サポートされている n8n エクスポート/インポートまたは移行手順を使用して、別のターゲットでワークフローと暗号化された資格情報を検証します。ロールバック用に元のファイルを保存し、以下にリンクされているバックアップと復元ガイドを使用して回復の準備をします。決して削除しないでください database.sqlite ショートカットとして。

ワーカーの同時実行数

ワーカーは数とワーカーごとのジョブの両方でスケールします

各ワーカーは複数のジョブを同時に処理できます。 n8n の現在のデフォルトのワーカー同時実行数は 10 であり、ドキュメントでは 5 以上の同時実行性を推奨しています。非常に低い同時実行性と多数のワーカーが組み合わされると、不要なデータベース接続が作成され、データベース接続プールが枯渇する可能性があります。

次の場合に同時実行性を高めます。

ワーカーには予備の CPU と RAM があり、ワークフローはほとんどの場合、コンピューティングやメモリを飽和させることなく、外部サービスを待機します。

ワーカーを追加する場合

1 つのワーカー プロセスがボトルネックになり、データベース、Redis、インフラストラクチャにはより多くの並列実行の容量が確保されます。

次の場合に同時実行性を減らします。

個々のワークフローはメモリまたは CPU を大量に使用し、並列ジョブは競合、OOM プレッシャー、または不安定な実行時間を引き起こします。

PostgreSQLを見る

ワーカーと同時実行性が増加すると、データベースのアクティビティが増加します。データベース容量を使用せずに実行容量を拡張すると、ボトルネックが解消されるのではなく、移動する可能性があります。

実際に適用される同時実行制限を確認します。 ワーカーは次を使用して開始できます n8n worker --concurrency=5、または Compose サービスの同等のワーカー コマンド。もし N8N_CONCURRENCY_PRODUCTION_LIMIT 以外の値が明示的に設定されている -1、その設定はキュー モードで優先されます。それ以外の場合、n8n はワーカーの --concurrency 値またはそのデフォルトの 10。ワーカー数に名目上のデフォルトを掛けて、それを保証スループットと呼ぶことはしないでください。実際の容量は、ジョブの期間、CPU、メモリ、外部 API、PostgreSQL 接続によって異なります。

Webhook

キュー モードでは実行ハンドオフ レイテンシが追加される可能性があります

メインまたは Webhook プロセスは HTTP リクエストを受信しますが、ワーカーがワークフローの実行を実行します。 Redis を介したハンドオフにより、オーバーヘッドが追加されます。レイテンシの影響を受けやすい Webhook の場合は、より多くのワーカーが自動的にすべてのリクエストを高速化すると仮定するのではなく、エンドツーエンドの応答時間を測定します。

受信メイン/Webhook プロセスがリクエストを受け入れます。
キュー実行は Redis に渡されます。
実行する利用可能なワーカーがワークフローを実行します。
応答する結果は、必要に応じてキュー パスを通じて中継されます。

Webhook トラフィックを適切なプロセスにルーティングします。 専用の n8n webhook リバース プロキシまたはロード バランサの背後にあるプロセッサ、本番パスのルート /webhook/* そして /webhook-waiting/* Webhookプロセッサへ。保つ /webhook-test/*、メインのエディターと API リクエスト。追加されたワークロードを意図的に受け入れる場合を除き、main を運用 Webhook 負荷分散プールに入れないでください。あ Webhook に応答する ワークフローでは、ワーカーが終了して応答を返すまでクライアントを待たせる可能性があるため、キュー モードは即時の HTTP 応答やタイムアウトゼロを保証するものではありません。トラフィックを切り替える前に、実際の外部コールバックと応答の動作をテストします。

バイナリデータ

共有ストレージを見逃さないでください

ファイルシステムの制限

キュー モードは、分散ワーカーの共有永続モデルとしてファイル システムのバイナリ データ ストレージをサポートしません。

外部バイナリストレージ

ワークフローが分散ワーカー間でバイナリ データを保持する必要がある場合は、サポートされている外部オブジェクト ストレージなど、必要なすべてのインスタンスがアクセスできるストレージ設計を使用します。

大規模な Webhook 応答

ワーカーからの Webhook 応答は、受信プロセスに戻ります。応答本体が大きいと、Redis のメモリ負荷が増大する可能性があり、意図的な応答ストレージ構成が必要になります。

従業員を配置する前に計画を立てる

ローカル ファイルに大きく依存するワークロードは、ワーカーが複数のマシンに分散される前に、共有永続性を実現するように再設計する必要があります。

Webhook 応答境界が大きい。 現在の n8n ドキュメントでは、 N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX デフォルトの 64 MiB ワーカーの応答がキューを通じて返送された場合。 Redis は実行中に複数のコピーを保持できるため、同時大規模応答ごとに Redis メモリ内の応答サイズのおよそ 1.5 倍の予算を割り当てます。オフロードを行わないと、ワーカーを追加して魔法のように高速になる代わりに、サイズが大きすぎる応答が失敗します。

バージョンとライセンスの制限。 n8nから 2.34.0、労働者が使用できる N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true サイズが大きすぎる Webhook 応答本文を読み取り可能な共有バイナリ ストレージにオフロードしますが、最初にアップグレードします すべてのメインおよび Webhook プロセッサ 2.34.0以降に。選択された N8N_DEFAULT_BINARY_DATA_MODE 実際にデータを保存し、参加しているすべてのプロセスから読み取れる必要があります。外部 S3 および Azure バイナリ ストレージには有効なセルフホスト型ストレージが必要です ビジネスまたはエンタープライズ ライセンス。 Community Edition でこれらを有効にできるとは想定しないでください。の database バイナリ モードでは、有料の外部ストレージを使用せずにサイズ超過の応答をオフロードできますが、メイン インスタンスは保存された本体全体をメモリにロードし、データベース ストレージには独自のファイル サイズ制限があります。のために レスポンスボディの具体的なオフロード、n8n は共有についても説明します。 filesystem すべてのインスタンスが同じディスクをマウントする場合のオプションですが、その配置は明示的に推奨されません。この特別なオフロード パスを、分散キュー モード展開におけるファイル システム ベースの永続バイナリ データのサポートと間違えないでください。オフロードを有効にする前に、エディション、バージョン、ストレージ構成を確認してください。

監視

キューが役に立っているかどうかを知る

キューの深さ

ワーカーが排出するよりも早くキューが増加する場合は、実行能力が不十分であるか、下流のボトルネックが発生していることを示しています。

ワーカーの CPU と RAM

ワーカーごとの飽和とメモリのピークを測定します。キューが増大しているアイドル状態のワーカーは、別の制約を示しています。

実行レイテンシ

ワークフロー ランタイム自体だけでなく、実行の作成と実際の開始との間の遅延を追跡します。

健康診断

ワーカーの正常性エンドポイントは、ワーカーが生存しているかどうか、およびそのデータベースと Redis 接続の準備ができているかどうかを報告できます。

緑色のコンテナだけでなく、ワーカーでの実行を確認します。 Compose スタックが正しく構成されている場合は、次のことを確認します。 docker compose ps そして docker compose logs --tail=100 n8n-worker (サービス名が異なる場合は置き換えてください)。無害な実行 出版された作品 スケジュールされたトリガーまたはテスト Webhook を使用してワークフローを実行し、n8n の実行ビューでその実行をワーカー ログ内の実際のワーカー処理と照合します。エディターが正常に開くか、実行中の Redis コンテナーまたはキューに入れられた実行のみが実行されます。 そうではない 労働者が仕事を遂行したことを証明する。

依存関係と準備状況を確認します。 デフォルトのサービス名の例では、 docker compose exec -T redis redis-cli ping 受け取るべきです PONG Redis 認証で許可されている場合、および docker compose exec -T postgres pg_isready -U n8n -d n8n PostgreSQL の準備状況をチェックします (資格情報とサービス名を適合させます)。有効にする QUEUE_HEALTH_CHECK_ACTIVE=true プライベートが必要な場合にワーカー上で /healthz そして /healthz/readiness エンドポイント; readiness エンドポイントは Redis/データベース接続をチェックします。これらのワーカー エンドポイントを監視するためだけに公開しないでください。

手動実行は別のテストです。 デフォルトでは OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=falseしたがって、エディターでワークフローを手動で実行すると、キュー モードが正しく構成されている場合でもメインで実行できます。に設定します true 手動実行をワーカーに送信する予定があり、ステージング環境で変更を確認した場合のみ。キュー モード ワーカーは、コード ノードの実行に別の構成要件がある n8n 外部タスク ランナーとも異なります。

高可用性に関する制約

キュー モードは実行を拡張しますが、メイン プロセスの可用性が自動的に高くなるわけではありません。

暗号化キーを共有する

すべての労働者は同じものを使用する必要があります N8N_ENCRYPTION_KEY メイン インスタンスとして使用されるため、ワーカーはワークフローの実行に必要な認証情報を復号化できます。

バージョンを揃える

メイン、Webhook、およびワーカー プロセスは同じ n8n バージョンを実行する必要があります。バージョンが混在すると、ローリング変更中に互換性のない動作が発生する可能性があります。

Webhook プロセッサは別個のスケーリング レイヤーです

受信 Webhook ボリュームがボトルネックになると、ワーカーが実行を処理している間、専用 Webhook プロセッサがロード バランサの背後に配置されます。測定されたリクエスト量が正当である場合を除き、このレイヤーを追加しないでください。

マルチメインは別の機能です

高可用性を実現するために複数のメインプロセスを実行することは、通常のキューモードと同じではありません。 n8n では現在、追加のロードバランサーとセッション要件を備えたセルフホスト型エンタープライズ機能としてマルチメインを文書化しています。

公式のキューモードのアーキテクチャと構成

よくある質問

n8n キュー モード: よくある質問

n8n キュー モードには Redis が必要ですか?

はい。 Redis は、メイン インスタンスとワーカーの間で保留中の実行を調整するメッセージ ブローカーです。

キューモードでは SQLite を使用できますか?

分散キューモード アーキテクチャの場合は「いいえ」です。メインとワーカーは共有データベース アクセスを必要とし、n8n ではこのセットアップ用のデータベースとして PostgreSQL を文書化しています。

何人のワーカーを実行すればよいですか?

普遍的なカウントはありません。同時実行性とワーカー使用率の測定から開始し、PostgreSQL、Redis、CPU、RAM、キューの深さを監視しながら容量を追加します。

n8n ワーカーの同時実行性とは何ですか?

これは、ワーカーが並行して処理できるジョブの数です。現在のデフォルトは 10 で、n8n は同時実行性の低いワーカーを多数作成するのではなく、5 以上のワーカー同時実行性を推奨します。

小規模な VPS ではキュー モードを有効にする必要がありますか?

ワークロードがそれを正当化する場合のみ。 1 つのインスタンスとして快適に実行される小規模なデプロイメントは、通常、Redis や個別のワーカーを使用しない方が簡単に操作できます。
