バックアップと復旧

n8nのバックアップと復元

セルフホスト型 n8n をバックアップおよび復元するには、SQLite データベースまたは一貫性のある PostgreSQL ダンプ、永続的な .n8n フォルダーと元の暗号化キー、展開構成、およびすべての外部バイナリまたはマウント ファイルの依存関係を保護します。暗号化されたコピーを VPS から離れた場所に保管し、別のインスタンスでリカバリをテストします。選択的リカバリには CLI ワークフローと認証情報のエクスポートを使用します。 JSON エクスポートだけでは、サーバーの完全なバックアップにはなりません。

簡易チェックリスト

n8n バックアップで保護すべきもの

データベース

インスタンスが使用する PostgreSQL データベースまたは SQLite データベース ファイルをバックアップします。データベースには、ワークフロー、認証情報、実行データなどのコア n8n 状態が含まれています。

暗号化キー

正確な n8n 暗号化キーを個別に安全に保存します。復元された暗号化された資格情報は同じキーに依存します。

永続ファイル

永続的な n8n データ ディレクトリと、展開が依存するマウントされたファイル、バイナリ データ ストレージ、またはワークフロー アセットを含めます。

導入構成

スタックの再構築に必要な構成/構成ファイルと非機密構成を保持します。適切なアクセス制御で秘密を保護します。

2段階のバックアップ

論理エクスポートと完全な災害復旧

ワークフローと認証情報のエクスポート

n8n CLI エクスポートは、移行、バージョン管理されたワークフローのコピー、および選択的な復元に役立ちます。資格情報は暗号化された形式でエクスポートし、後で一致する暗号化キーを使用してインポートできます。ワークフローを 1 つだけ復元するには、ワークフロー エディターの 3 点メニューを使用して JSON をダウンロードし、ファイルから新しいレビュー ワークフローまたは分離されたインスタンスにインポートします。ライブ ワークフローを置き換える前に、資格情報、ワークフロー ID、およびノー​​ド パラメーターを確認してください。ワークフロー JSON を復元しても、サーバー全体は復元されません。

エンティティのエクスポート

CLI は、サポートされているデータベース タイプ間でデータを移動するためにデータベース エンティティをエクスポートできます。実行履歴テーブルは非常に大きくなる可能性があるため、オプションです。

インスタンス全体のリカバリ

サーバーが停止した場合のシナリオでは、実際のデータベース、暗号化キー、永続データ、および展開の依存関係を保護します。ワークフロー JSON エクスポートによってインスタンス全体が再構築されると想定しないでください。

プロバイダーのスナップショット

VPS スナップショットは追加の回復レイヤーとして役立ちますが、それが唯一のコピーであってはならず、個別に検証されたアプリケーション/データベースのバックアップを置き換えるべきではありません。

データベース

データベースを一貫してバックアップする

PostgreSQL

一貫した PostgreSQL バックアップ方法を使用し、結果のバックアップを VPS から離れた場所に保存します。障害が発生した同じディスク上のデータベース コピーはディザスタ リカバリではありません。

SQLite

デプロイメントで SQLite を使用する場合は、データベース ファイルを永続的な n8n データ ディレクトリから保護します。データベースがアクティブに変更されている間は、安全でない状態でデータベースをコピーすることは避けてください。

実行履歴

過去の実行データが回復目標の一部であるかどうかを決定します。バックアップのサイズが大幅に大きくなる可能性があるため、保存とコンプライアンスの要件を考慮して選択する必要があります。

データベースのバージョン

回復環境を互換性を持って準備できるように、ソース展開で使用されているデータベース エンジンとバージョンを記録します。

Docker Compose VPS 上の PostgreSQL。 PostgreSQL サービスの名前が指定されている場合 postgres とそのデータベース/ユーザーは両方とも n8nの場合、次のコマンドはホスト上に一貫した PostgreSQL カスタム形式のダンプを作成します。実際の Compose ファイルを実行する前に確認し、データベースの資格情報とサービス名を調整してください。 pg_dump PostgreSQL の実行中に論理的に一貫したスナップショットを作成できます。それはあります そうではない 個別にバックアップする .n8n ユーザーフォルダーまたは外部バイナリデータ。

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

アーカイブ リスト チェックでは、明らかな形式の問題は検出されますが、データが復元できることは証明されません。暗号化されたコピーをサーバー外に保存し、復元のリハーサルを行います。データベース固有のオプションについては、PostgreSQL の pg_dump の公式ドキュメントを使用してください。

Docker 上の SQLite。 デフォルトの SQLite デプロイメントの場合、 database.sqlite 生成された暗号化キー設定は永続的なファイル内に存在します。 .n8n フォルダー (通常は次の場所にマウントされます) /home/node/.n8n）。 SQLite の単純なライブ コピーを一貫したものとして扱わないでください。フォルダーをコピーする前に n8n およびその他のデータベース ライターを停止するか、中断できない場合は SQLite でサポートされているオンライン バックアップ メカニズムを使用します。

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

これらは、示されているサービスとパスのコマンド例であり、普遍的なボリューム レイアウトではありません。コピーされたフォルダーは、最初はまだ同じ VPS 上にあります。オフサーバーに転送して保護します。キュー ワーカーまたは他のライターが存在する場合は、それらも静止し、実際のデプロイメント設計に従います。 n8n の現在の完全バックアップ ガイダンスには、SQLite の整合性要件が文書化されています。

デフォルトの SQLite フォルダーをクリーンなターゲットに復元します。 まず、n8n サービスとすべてのデータベース ライターを停止します。互換性のある n8n サービス コンテナとその宛先ボリュームが存在したら、バックアップされたボリュームをコピーします。 .n8n 内容 戻る 同じ永続ディレクトリにコピーします。これによりターゲット ファイルが上書きされるため、保持する必要があるデータを含むインスタンスでは実行しないでください。

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker は停止したコンテナにコピーできますが、宛先の所有権が元のコンテナと異なる場合があります。 n8n プロセスを開始する前に、復元された構成とデータベース ファイルが n8n プロセスによって読み書き可能であることを確認してください。実際の Compose 構成で別のパスまたはバインド マウントが使用されている場合は、それに応じてコピーを調整します。 Docker Compose コピーのリファレンス。別の PostgreSQL データベースを使用する展開では、n8n フォルダーだけを復元するだけでは十分ではありません。

重要な機密情報

暗号化キーはリカバリの一部です

n8n は、保存された認証情報をインスタンス暗号化キーを使用して暗号化します。一致するキーを使用せずにデータベースまたは暗号化された資格情報をエクスポートすると、復元されたワークフローが保存された資格情報を使用できなくなる可能性があります。

N8N_ENCRYPTION_KEY を設定した場合は、その正確なシークレットを復元します。それ以外の場合、生成されたキーは永続的な .n8n/config ファイルに保存されます。バックアップまたは再構築するときにその構成を保護してください。回復キーは VPS の外部に安全に保管します。キュー モードでは、すべてのメイン プロセスとワーカー プロセスが同じキーを使用する必要があります。

する本番環境で使用される正確なキーの保護されたコピーを保管してください。
する資格情報をテストする前に、回復環境でそのキーが使用されていることを確認してください。
しないでくださいサーバーを再構築した後は、新しく生成されたキーを使用します。
しないでくださいキーをパブリック リポジトリにコミットするか、保護されていないバックアップの横に保存します。

ファイルとバイナリデータ

データベースのバックアップでは、すべてのワークフローの依存関係がカバーされない可能性があります

永続的な .n8n データ

コンテナー イメージだけでなく、実際の .n8n ユーザー フォルダーを見つけて保存します。一般的な Docker デプロイメントでは、/home/node/.n8n にマウントされます。 Docker の外部では、デフォルトは ~/.n8n です。 N8N_USER_FOLDER が設定されている場合、n8n は指定された親ディレクトリ内に .n8n を作成します。構成キーと、インストールで使用されるローカル SQLite、バイナリ、またはファイルシステムの実行データを含めます。

マウントされたワークフロー ファイル

ワークフローがホストにマウントされたディレクトリを読み書きする場合は、それらのディレクトリを個別にバックアップしてください。これらを使用せずに n8n を復元すると、有効なワークフローが壊れたままになる可能性があります。

バイナリデータ

ストレージ モードを特定し、すべての外部依存関係を復元します。ファイルシステムベースのバイナリまたは実行データは、.n8n またはカスタム ディレクトリに存在する場合があります。 S3/Azure Blob またはその他の構成された外部ストレージには、独自の回復可能なコピーとアクセス設定が必要です。データベース ダンプだけではこれらのファイルを置き換えることはできません。

コミュニティノード

コミュニティ パッケージとバージョンを記録し、N8N_CUSTOM_EXTENSIONS で構成された追加のカスタム ノード ディレクトリをバックアップします。これらのディレクトリは .n8n の外側に置くことができます。データベースとユーザー フォルダーの復元だけでは、カスタム ノードのワークフローが使用できないままになる可能性があります。

サーバー外での保管方針

同じ VPS 上のバックアップはローカル コピーのみです

ローカルコピー迅速なロールバックには便利ですが、サーバーの損失、ディスク障害、破壊的なミスに対して脆弱です。
オフサーバーコピー実稼働 VPS から独立したストレージに少なくとも 1 つのバックアップを保持します。
バージョン管理されたコピー破損や不適切な変更によって唯一使用可能なバックアップが上書きされないように、複数の復旧ポイントを保持します。
アクセス制御バックアップには、資格情報、ワークフロー ロジック、機密ビジネス データが含まれる場合があります。適切に暗号化して制限します。
モニタリングスケジュールされたバックアップが失敗した場合、または新しい回復ポイントの作成が停止した場合に警告します。

スケジュールを測定可能なものにします。 成功した各バックアップのタイムスタンプ、転送の完了、ファイル サイズ、ソース データベースのバージョン、暗号化キーの回復場所、および最後に成功した復元テストを記録します。欠落しているファイル、失敗したファイル、または予期せず空のファイルを警告します。バックアップ アーカイブを VPS から送信する前に暗号化し、回復シークレットへのアクセスを制限します。複数の日付の付いた回復ポイントは、最新のコピーが最後の正常なコピーを上書きした後にのみ破損が発見されることを防ぎます。

たとえば、最大 6 時間の変更の損失を許容できる場合、6 時間のバックアップ スケジュールの成功は保証ではなく出発点です。失敗したジョブや遅延したオフサーバー レプリケーションにより、実際の損失が増加する可能性があります。普遍的な 7 日または 30 日ポリシーを前提とするのではなく、独自の RPO/RTO およびデータ要件に合わせて保存と復元の頻度を設定します。

復旧の手順

制御されたシーケンスで回復する

1 · 準備する互換性のあるサーバー、データベース、コンテナ/ランタイム環境をプロビジョニングします。
2 · シークレットを復元する元の n8n 暗号化キーと必要な展開シークレットを安全に構成します。
3 · データベースの復元PostgreSQL または SQLite を回復し、n8n が予期したデータに接続できることを確認します。
4 · ファイルを復元する永続ディレクトリ、バイナリ データ、マウントされたワークフロー アセットを回復します。
5 · n8n を開始する予想されるホスト名、データベース、環境構成を使用してアプリケーションを起動します。
6 · 検証するユーザー、ワークフロー、認証情報の読み込みを確認し、代表的なワークフローと Webhook パスを実行します。

PostgreSQL の災害復旧の例: に 個別のクリーンな復元ターゲット すでに正しいデータベース ロールと空のデータベース ロールを持っています。 n8n データベース、開始 だけ ポストグレSQL。 インポートする前に、正常になるまで待ちます。 docker compose up -d PostgreSQL の初期化中に単独で返すことができるため、次のようになります。 pg_restore 失敗する可能性があります。例では、 --wait 最新の Compose インストールで独自にチェックする pg_isready。確実に待機できるように適切な PostgreSQL ヘルスチェックを構成するか、次に進む前に準備が整っていることを明示的に確認します。このコマンドを、データが設定された運用データベースに指定したり、データベースとその一致の前に n8n を起動したりしないでください。 .n8n キー/データが復元されます。

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

宛先には、互換性のある PostgreSQL バージョン、ロール権限、拡張機能、および元の n8n 構成が必要です。復元 .n8n 正しい永続ボリュームにコピーするか、バックアップ メカニズムを使用してバインド マウントし、所有権とアクセス許可を保持します。外部バイナリ ファイル、カスタム拡張機能、Compose およびシークレットの構成を復元し、互換性のあるバージョンで n8n を起動し、ログを確認します。データベースだけを復元してもキーは回復されません。PostgreSQL デプロイメントではキーが保持されます。 .n8n/config 明示的に設定していない限り、 N8N_ENCRYPTION_KEY。 pg_restore リファレンス · n8n フルインスタンス復元シーケンス。

復旧テスト

復元が成功するまでバックアップは証明されません

クリーンな環境でのテスト

実際のドリルでは、運用サーバーに残された未宣言のファイルに依存せずに、バックアップによってインスタンスを再構築できることが証明されるはずです。

資格情報を確認する

ワークフローを開くだけでは十分ではありません。復元された暗号化された資格情報が実際に復号化され、正常に認証されることを確認します。

代表的なワークフローを実行する

簡単な自動化だけを検証するのではなく、Webhook、外部 API、マウントされたファイル、コミュニティ ノードに依存するワークフローをテストします。

回復時間を測定する

復元にかかる時間と残っている手動手順を記録します。これにより、想定されたバックアップが運用上のリカバリ手順に変換されます。

テスト環境: n8n 2.42.5 合成 2 ノード ワークフローを使用して、使い捨ての GitHub Actions ランナー上の分離された Docker コンテナーで実行します。これらのチェックは次のように実行されました 8 10月 2026、顧客または本番の n8n サーバー上ではありません。

PostgreSQL: 合格同じテスト ワークフローをインポートし、カスタム形式を作成して検査しました pg_dumpを使用して復元しました pg_restore 新しい空の PostgreSQL データベースに、別の .n8n フォルダーに保存し、復元されたワークフローを再エクスポートして実行します。
PASSが定めるものテストされたバックアップ パスでは、このワークフロー、その 2 つのノードとその接続が保存され、回復後の実行が可能になりました。これらは再現可能な機能的なスモーク テストであり、ワークロードのベンチマークではありません。

再現方法: 使い捨ての n8n インストールを使用し、無害な 2 ノード ワークフローを作成し、該当するデータベースと永続フォルダーのバックアップを実行し、クリーンなボリュームまたはデータベースに復元してから、復元されたワークフローのノード、接続、および実際の実行を確認します。本番システムでは、災害復旧が証明されたことを宣言する前に、暗号化された資格情報、Webhook、および外部ファイルもチェックします。

CLIバックアップの限界

どのワークフローと認証情報のエクスポートで復元されないのかを正確に把握する

CLI エクスポートは完全なインスタンスのバックアップではありません

ワークフローおよび認証情報のバックアップのエクスポートには、ユーザーとロール、実行履歴とログ、変数、または暗号化キーなどのインスタンス設定は含まれません。

新しいインスタンスの復元には所有者が必要です

クリーンなインスタンスでは、資格情報をインポートする前に所有者のセットアップを完了します。マルチユーザーまたはプロジェクトの復元には、正しいユーザーまたはプロジェクトの割り当ても必要な場合があります。

インポートされた ID は既存のアイテムを上書きする可能性があります

ワークフローと資格情報のエクスポートでは、元の ID が保持されます。すでに同じ ID が含まれているインスタンスにインポートすると、それらの既存の項目が置き換えられる可能性があります。

インポートしたワークフローを意図的に公開する

CLI インポートでは、通常、ワークフローが非アクティブなままになります。 n8n 2.x では、インポートされた各ワークフローの公開状態を確認し、実行する予定のワークフローのみを公開します。セルフホステッド サーバー CLI は、n8n public:workflow --id=YOUR_WORKFLOW_ID もサポートします。 n8n が実行されている場合、サーバー CLI の公開/非公開状態の変更は、n8n を再起動した後にのみ有効になります。スケジュールされたトリガーと運用 Webhook を検証する前、またはトラフィックを切り替える前に再起動してください。

Docker Compose の一括エクスポートの例: n8n サービスに名前が付けられている場合 n8n、以下の公式 CLI バックアップを実行できます。出力パスは意図的にマウントされた永続的なパスの内部にあります。 .n8n ディレクトリを再作成すると、コンテナ内の任意のディレクトリが消える可能性があるためです。ディレクトリが n8n コンテナ ユーザーによって書き込み可能であることを確認します。ワークフローと認証情報の JSON を保持する 別々のディレクトリ—n8n は、両方の種類がディレクトリを共有する場合のインポートの問題を文書化しています。

n8n 2.x のドラフトと公開されたバックアップ: 普通の --backup ワークフローのエクスポートは現在のドラフトをキャプチャします。これらは実稼働環境で公開されているバージョンとは異なる場合があります。特定のワークフローの実際に公開されたバージョンを保存するには、次を使用して個別にエクスポートします。 docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json出力フォルダーが存在し、書き込み可能であることを確認した後。 CLI は、次を使用して履歴バージョンをエクスポートすることもできます。 --version=VERSION_ID。これらのキャプチャは完全バックアップとともにオフサーバーに保管してください。ドラフト JSON が公開されたライブ状態を記録するとは想定しないでください。

よくある質問

n8n のバックアップと復元: よくある質問

n8n をバックアップするには、ワークフローをエクスポートするだけで十分ですか?

いいえ。ワークフローのエクスポートは便利な論理コピーですが、完全なリカバリには資格情報、一致する暗号化キー、データベースの状態、永続ファイル、およびバイナリ データ ストレージも必要になる場合があります。

データベースを持っている場合、n8n 暗号化キーは必要ですか?

データベースに保存されている暗号化された資格情報を引き続き使用できるようにする必要がある場合は、はい。元のキーは安全に保管してください。

PostgreSQL をバックアップするか、ワークフローと認証情報をエクスポートする必要がありますか?

災害復旧のために、データベースと暗号化キーを保護します。論理エクスポートは、インスタンスのすべての部分の代替としてではなく、追加の移行および選択的リカバリ層として価値があります。

VPS スナップショットを唯一のバックアップにすることはできますか?

1 つの回復層として扱う方が適切です。プロバイダー、アカウント、サーバー、またはスナップショットの障害によってすべての復旧ポイントが一度に削除されないように、独立したオフサーバー バックアップを保持してください。

バックアップが機能していることを確認するにはどうすればよいですか?

これをクリーンなテスト環境に復元し、資格情報が復号化されていることを確認し、代表的なワークフローを実行します。バックアップ ジョブが成功しただけでは、回復可能であることは証明されません。

GitHub または Google Drive ワークフローのバックアップには、保存された認証情報のシークレットが含まれますか?

ワークフローのみの JSON バックアップには、n8n の資格情報ストアによって管理されるシークレット値やインスタンス暗号化キーは含まれません。ただし、エクスポートされた JSON は、認証ヘッダーなどのノード パラメーターに直接入力された認証情報の名前、ID、およびシークレットを公開する可能性があります。エクスポートまたは共有する前に、エクスポートされた JSON を検査して保護します。完全なリカバリの場合は、データベースと元のキーをバックアップするか、テスト済みの復元でサポートされている暗号化された資格情報 CLI エクスポートを使用します。ワークフロー専用の GitHub または Google Drive テンプレートは、完全な災害復旧ではありません。

復旧目標

インシデントの前に RPO と RTO を定義する

RPO 最近の変更による許容可能な最大損失です。使用可能な、独立して保存された最新の復旧ポイントから測定します。エクスポートまたは転送が失敗した場合、スケジュールされた 6 時間のジョブでは 6 時間の RPO は確立されません。 RTO 許容可能な最大の停止です。コンテナーを開始するだけでなく、シークレットの取得、外部ファイルの復元、資格情報の再チェック、復元されたワークフローの公開など、クリーンな復元ドリルで測定します。

復旧に必要な鍵

再構築する前に元の暗号化キーを見つける

本番セットの場合 N8N_ENCRYPTION_KEY、その正確な環境秘密を保持します。そうでない場合は、生成されたキーを元の永続的な .n8n/config に保存します。暗号化された認証情報をインポートする前に、復元されたインスタンスが実際に使用するソースを確認してください。新しく生成されたキーでは、古いデータベースから資格情報を復号化できません。
