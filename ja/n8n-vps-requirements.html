n8nのVPS必要スペック

n8n VPS 要件については、ユニバーサル ハードウェアの最小要件ではなく、ワークロードから始めます。慎重にサイジングされた1 vCPU / 1 GB VPS は小規模な常時オンのオートメーションを実行できますが、2 vCPU / 4 GB RAM は PostgreSQL および HTTPS を使用する n8n の実用的な開始クラスです。大きなペイロード、同時実行、およびローカル データ処理には、より多くのヘッドルームが必要です。選択する前に実際の使用量を測定してください。

必要スペックの概要

最小限の実用的な生産とより重いワークロード

軽量の常時稼働インスタンス

1 vCPU · 1–2 GB RAM

実際の1 GB VPS は、メモリとディスクのヘッドルームが検証されていれば、慎重に制限された軽量の連続 n8n ワークフローを実行できます。 2 GB クラスには、Docker、小規模バースト、その他のサービスのための余地がさらに残されています。どちらの数字も、特定のワークフロー数を保証するものではありません。

実用的な少量生産

2 vCPU · 4 GB RAM

n8n が VPS を PostgreSQL、Docker、リバース プロキシと共有する場合のバランスのとれた開始クラス。重複する実行とメンテナンスに備えて余裕を保ちます。

重い、またはデータ集約型

4+ vCPU · 8 GB+ RAM

大規模な JSON、バイナリ ファイル、コード ノード、ブラウザーの作業、および多数の重複した実行により、CPU とメモリが大幅に増加する可能性があります。

ストレージ

成長に余裕のある SSD / NVMe

容量は、n8n 単独ではなく、PostgreSQL の成長、実行保持、バイナリ データ、ログ、Docker レイヤー、バックアップ戦略によって決まります。

最小構成と実用的な構成

n8n には公式の最小 VPS サイズが 1 つありますか?

すべてのワークロードに適しているわけではありません。 n8n の公式前提条件の例では、OEM 導入の実例を説明し、要件がワークロードによって異なることを明示的に警告しています。このドキュメントは、特定の CPU、RAM、またはディスク割り当てが運用自動化をサポートすることを普遍的に保証するものではありません。

n8n は、アイドル状態のインスタンスは比較的少量のメモリしか使用しない可能性があるが、コード ノード、大きなバイナリ ペイロード、または同時実行によりメモリ需要が急激に増加する可能性があると指摘しています。オペレーティング システム、Docker、PostgreSQL、バックアップ/監視ツールについては個別に予算を立てます。

技術情報源: n8n の前提条件の説明と公式メモリ ガイド。上の 4 行は実際に購入可能なリソース バンドルであり、公式の n8n 要件が規定されているものではありません。

RAMとCPU

実際にサーバーリソースを消費するもの

同時実行

同時に実行される複数のワークフローは、n8n に保存されているワークフローの総数よりも重要な場合があります。オーバーラップ中のメモリのピークと実行レイテンシを監視します。

ペイロードサイズ

大きな JSON オブジェクト、ファイル、バイナリ データにより、メモリ負荷が増大します。いくつかのデータ量の多い実行では、多くの軽量 API オートメーションよりも多くの RAM が必要になる場合があります。

CPU 負荷の高いノード

コード、変換、その他の計算量の多いステップにより、持続的な CPU 負荷が発生する可能性があります。実際の実行がコンピューティングをめぐって競合する場合、より多くのコアが役立ちます。

サポートサービス

オペレーティング システム、PostgreSQL、リバース プロキシ、モニタリング、Docker にもリソースが必要です。 n8n プロセスだけでなく、スタック全体のサイズを決定します。

増強の前に実測する

n8n にさらに多くの RAM、CPU、またはディスクが必要かどうかを判断する方法

予想される最大のワークフローと現実的なオーバーラップバーストを実行し、サーバーと n8n の実行ログを検査します。エディターに保存されたワークフローの数は、それ自体では有用な容量ベンチマークにはなりません。

メモリ/OOM

チェックする docker stats --no-stream そして free -h。メモリが不足している場合は、まず JSON またはバイナリ ペイロードを減らし、大規模なインポートをバッチ処理して、メモリを大量に使用するコード ステップを避けます。 JavaScript ヒープ エラーは、vCPU を追加しても必ずしも修正されるわけではありません。

CPU / 同時実行性

変換中に CPU がビジー状態のままかどうか、またはジョブが外部 API を待機するだけかどうかを測定します。通常モードでは、ワーカーに拡張する前に、サポートされている運用同時実行数の制限を考慮してください。 CPU を増やしても、レート制限のある外部 API は高速化されません。

ストレージ/データベース

チェックする df -h、データベースのサイズと保持される実行履歴。ディスクの増大とデータベース操作の遅延に注意してください。より大きなディスクの料金を支払う前に、保持期間を意図的に設定してください。リカバリ コピーをサーバー外に保管します。

n8n の同時実行性ガイダンスと公式ベンチマークの説明を使用してください。ペイロードと API レイテンシーが不明な場合にアドバタイズされる同時ワークフローの数は、単なる推定値にすぎません。

データベースとストレージ

SQLite、PostgreSQL、永続データ

SQLite

SQLite は、小規模な単一インスタンスのデプロイメントとテストに適合します。運用環境の使用量と同時実行性が増大するにつれて、データベースの選択はインストールの詳細ではなく運用上の制約になります。

PostgreSQL

実稼働指向の VPS スタックの場合、PostgreSQL はより強力なデータベース基盤を提供します。データベース自体に RAM、CPU、ディスクを割り当て、その増加を監視します。

永続的な .n8n データ

PostgreSQL を唯一の永続的な資産として扱わないでください。 n8n データ ディレクトリを保存し、暗号化された認証情報を回復するために必要な暗号化キーを保護します。

ディスクの増加

実行履歴、バイナリ データ、データベース ファイル、ログは時間の経過とともに拡大する可能性があります。保持設定とオフサーバー バックアップは、必要な容量に直接影響します。

ディスク容量

注文前に n8n 実行履歴ストレージを見積もる

から始める 1 日あたりの保存された実行数 × 実行ごとの平均保存バイト数 × 保持日数。たとえば、1 日あたりの 500 保存された実行数 × 200 KB ごと × 14 日 = 1.4 GB データベースのオーバーヘッド前の実行データの例。 200 KB の仮定は例示的なものであり、n8n ベンチマークではありません。

また、OS、Docker イメージ レイヤー、データベース インデックス、バイナリ ファイル、アプリケーション ログ、アップグレード、一時ファイル用にディスクを割り当てます。オフサーバーバックアップには独自の容量が必要です。 10 GB ディスクはリーン スタックとして機能しますが、40 または 80 GB ディスクよりもファイルを保持する余地がはるかに少なくなります。

n8n は、例外を除き、経過時間 (336 時間 / 14 日) またはカウント (10,000 実行) によるデフォルトの実行プルーニングを文書化しています。実際の設定を確認し、変更する前に何が保持されているかを確認してください。 SQLite は、ファイルを自動的に圧縮するのではなく、解放された領域を再利用することがあります。

出典: n8n: 実行データとプルーニングを管理します。ディスク要件は、ノード数だけではなく、観測された保存ペイロード サイズによって決まります。

システム要件

Docker と本番環境のオーバーヘッド

Linux VPS

アプリケーション スタックに加えて、オペレーティング システムとセキュリティの更新に十分なリソースを備えた、保守された Linux ディストリビューションを使用します。

ドッカーと構成

コンテナーのデプロイメントにより再現性が簡素化されますが、リソースのオーバーヘッドは排除されません。 n8n とデータベースのデータを使い捨てコンテナの外に保持します。

HTTPS & リバースプロキシ

パブリック Webhook には、安定したホスト名と正しく構成された HTTPS が必要です。リバース プロキシと TLS レイヤーを実稼働設計に含めます。

監視とバックアップ

RAM、CPU、ディスク、データベースの増加を追跡します。スナップショットだけで十分だと考えるのではなく、回復可能なバックアップを VPS の外部に保持し、復元をテストします。

同時実行

大規模な VPS がすべての解決策ではなくなるとき

1 つのインスタンスがワークロードを適切に処理できる間は、垂直スケーリングが適切です。持続的な並列需要によって競合が発生する場合は、キュー モードとワーカーを評価します。キュー モードでは、Redis、PostgreSQL、および 1 つ以上のワーカー プロセスが導入されます。 n8n だけでなく、すべてのコンポーネントに RAM と CPU を割り当てます。 n8n には、キュー モードでのファイル システムのバイナリ データ ストレージに関する制限も文書化されているため、切り替える前に互換性のあるデータ ストレージ設計を検証してください。

キューモードとワーカーガイドを読む

単一インスタンスに留まるCPU、RAM、実行レイテンシーがピークオーバーラップ下でも快適な状態を維持している場合。
垂直方向に拡大縮小する持続的な CPU またはメモリの負荷が制限要因であり、アーキテクチャがまだ単純な場合。
キューモードを検討する並列需要を測定すると、Redis と個別のワーカーが正当化されます。
ストレージを再確認する実行履歴、バイナリ、または PostgreSQL の増加が主要な制約となる場合。

1 GBエントリーVPSの使い方

1 GB RAM

これはテスト専用の製品ではなく、実際に動作する VPS 層です。メモリ、ディスク使用量、同時ジョブを測定された制限内に維持する場合、小規模な常時稼働の自動化や、主に順次的な API 作業に適しています。同じサーバー上の PostgreSQL、大きなペイロード、または大量の並列実行に対しては、余裕がほとんどありません。

2 GB RAM

運用サイズのスタックにすぐに移行せずに、オペレーティング システム、Docker、および小規模バースト用にさらにスペースが必要な場合は、より安全なライト インスタンス ベースラインとして 2 GB を使用します。

SSDとNVMeの比較

標準の SSD は、軽度のオートメーションには十分です。 NVMe は、PostgreSQL と実行履歴によって頻繁な読み取りと書き込みが発生する場合、またはディスク遅延がワークフローのパフォーマンスの測定値に現れる場合に、さらに役立ちます。

アップグレード前に測定する

より大きな VPS がすべての速度低下を解決すると仮定するのではなく、CPU、メモリ、ディスクの増加、およびピークの重複下での実行時間を使用して、ボトルネックがコンピューティング、メモリ、ストレージのいずれであるかを判断します。

よくある質問

n8n VPS 要件: よくある質問

n8n にはどれくらいの RAM が必要ですか?

普遍的な数字はありません。 RAM の需要は、同時実行性、ペイロード サイズ、実行動作、および VPS 上のサポート サービスによって変化します。 4 GB サーバーは、実用的な小規模運用の開始クラスであり、すべてのワークロードに対して保証された要件ではありません。

CPU コアはいくつ使用すればよいですか?

軽いワークロードは、小さな CPU 割り当てから開始できます。ワークフロー数だけからサイジングするのではなく、監視によって持続的な CPU プレッシャーや同時実行時の実行速度の低下が示された場合は、コアを追加します。

n8n には PostgreSQL が必要ですか?

小規模なデプロイメントでは SQLite を使用できますが、運用要件と同時実行性が増加するため、PostgreSQL は実稼働指向の選択肢としてより強力です。

Redis が必要になるのはどのような場合ですか?

Redis はキュー モードに関連付けられています。通常の単一インスタンスのデプロイメントでは、VPS 上で実行されるため、Redis は必要ありません。

どれくらいのディスク容量を確保すればよいでしょうか?

ディスクの需要は、PostgreSQL の成長、保持される実行履歴、バイナリ データ、ログ、コンテナ レイヤー、バックアップによって異なります。固定のユニバーサルナンバーに依存するのではなく、成長を監視し、余裕を残してください。

1 GB VPS で n8n を継続的に実行できますか?

はい、実際のワークロードが適合する場合には可能です。 1 GB VPS は実際に動作するサーバーであり、小規模でほとんどが順次自動化をサポートできますが、メモリ ヘッドルームは限られています。同じサーバーの PostgreSQL スタック、バイナリの多いジョブ、または複数の大規模な同時実行が適合すると想定することは避けてください。消費を監視し、観察されたリソースのプレッシャーに基づいてアップグレードします。

本番の n8n VPS には2 GB または4 GB RAM のどちらが適していますか?

2 ギガバイトでは、無駄のない 1 GB インスタンスよりも多くの余地が得られますが、4 GB は、PostgreSQL および HTTPS とともに n8n を評価するための実用的な開始クラスです。普遍的に保証される最低生産量はありません。ワークロードの複雑さ、ピークの重複、コンテナの構成、および保持されるデータが実際の需要を決定します。

n8n AI ワークフローには GPU が必要ですか?

n8n が外部モデル API のみを呼び出す場合は異なります。モデル プロバイダーが推論を処理し、VPS がオーケストレーション、ペイロード、同時実行性を処理します。推論モデルをローカルで実行するには、ハードウェアが個別に決定され、より多くの RAM と適切な GPU リソースが必要になる場合があります。

n8n のメモリ不足エラーの原因は何ですか?

大規模な JSON またはバイナリ ペイロード、メモリを大量に使用するコード操作、および重複した実行が一般的な原因です。実行時ログとピーク時のメモリ使用量を確認し、測定された問題に基づいて 1 回の実行で保持されるデータを減らすか、より多くの RAM を割り当てます。
