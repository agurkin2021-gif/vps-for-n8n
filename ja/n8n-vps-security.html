VPS上のn8nを安全に運用する

VPS 上で n8n を保護するには、n8n (5678)、PostgreSQL (5432)、およびオプションの Redis (6379) を公共のインターネットから遠ざけてください。 HTTPS リバース プロキシ、SSH キー、MFA を使用し、暗号化キーを保存し、Webhook を認証し、リスクのあるワークフロー機能を制限し、デプロイされたインスタンスを監査します。エディターをパブリック Webhook ルートとは別に保護します。 HTTPS だけでは、接続されたサービスは保護されません。

ネットワークの入口

リバース プロキシ、HTTPS、および信頼できるヘッダー

TLS終端

HTTPS を終了するには、Nginx、Caddy、Traefik などのリバース プロキシを使用します。プロキシが目的のエントリ ポイントである場合は、プレーン HTTP をリダイレクトし、n8n アプリケーション ポートを直接公開しないようにします。

プロキシ設定

n8n がリバース プロキシの背後で実行されている場合は、プロキシ ホップ カウントを正しく設定し、n8n が元のクライアント リクエストを再構築するために必要な転送ヘッダーを渡します。

安全なクッキー

認証 Cookie が安全な状態を維持できるように、HTTPS 上でエディタを提供します。 Cookie のセキュリティを弱めて、TLS セットアップの破損を回避しないでください。

Webhook URL

パブリック Webhook URL を外部からアクセス可能な HTTPS ホスト名に設定し、生成された Webhook エンドポイントが内部コンテナーまたは HTTP アドレスを指さないようにします。

Webhook を中断せずにエディターを非公開にします。 可能であれば、VPN、信頼できる IP ポリシー、または認証されたプロキシを使用して管理アクセスを制限します。パブリック Webhook レシーバーと OAuth コールバック ルートは、到達可能な状態を維持する必要がある場合があります。プロキシ ルールを適用する前に、信頼できる編集者のサインインと実際の外部コールバックの両方をテストします。任意のリクエスト ヘッダーではなく、信頼できるプロキシからのみクライアント アドレス ヘッダーを転送します。

Webhook 呼び出し元を認証します。 Webhook ノードで、送信者によってサポートされている場合は、「なし」の代わりに「基本」、「ヘッダー」、または「JWT」認証を選択します。それを使用してください IP 許可リスト 必要に応じてオプションを使用し、統合が署名付きリクエストをサポートしている場合はプロバイダーの署名を確認します。推測しにくい URL は認証として不十分です。必要に応じてプロキシでレート制限を適用し、有効なバーストがブロックされていないことを確認します。公式の Webhook 認証オプション。

n8nの機密情報

暗号化キーと資格情報の境界を保護する

暗号化キー

n8n は、暗号化キーを使用して保存された資格情報を暗号化します。再起動とワーカー間で同じキーを保持し、通常のアプリケーション コンテンツとは別に保護します。

環境の秘密

パスワード、トークン、または暗号化キーをパブリック リポジトリにコミットしないでください。環境ファイルと展開シークレットへのアクセスを制限します。

ユーザーアクセス

信頼できるユーザーにのみ編集者アクセスを許可します。ワークフローは機密システムに接続することができ、機密情報を処理したり、強力なノードを実行したりする可能性があります。

資格情報の範囲

可能な場合は、範囲が狭いサービス アカウントと API トークンを使用してください。侵害されたワークフローによって、無関係なシステムへの広範なアクセスが自動的に継承されるべきではありません。

確認する n8n 構成: N8N_BLOCK_ENV_ACCESS_IN_NODE=true コードノードおよび式による環境値へのアクセスを防止します。 N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true 設定ファイルに対する所有者のみのアクセス許可を要求します。キープする N8N_ENCRYPTION_KEY 永続的で安全にバックアップされる: n8n は最初の起動時にランダムなキーを作成できますが、それを失うと、既存の暗号化された認証情報が使用できなくなる可能性があります。実稼働暗号化キーをむやみに置き換えないでください。公式にサポートされているローテーション手順を使用してください。環境へのアクセスをブロックすると、既存の統合が中断される可能性があるため、運用環境を変更する前にテストしてください。 n8n セキュリティ変数の定義。

監査とアップデート

n8n セキュリティ監査を実行する

公式の CLI コマンドは次のとおりです。 n8n audit。 Docker Compose サービスに次の名前が付けられている場合 n8n、走る docker compose exec -T n8n n8n audit その展開ディレクトリ内にあります。未使用の認証情報、危険な SQL クエリ パターン、ファイル システム アクセス、危険なノード/コミュニティ ノード、および保護されていない Webhook や古いリリースを含むインスタンスのリスクの 5 つのカテゴリを確認します。関連する調査結果を修正して再実行します。これは侵入テストではありません。公式監査ガイド。

意図的に更新する

セキュリティ修正を受信できるように、n8n を最新の状態に保ちます。インターネットに接続されたインスタンスを永久に古いままにするのではなく、リリース ノートを確認し、重要なアップグレードをテストしてください。

モニター認証

予期しないアクセス パターン、ワークフローの変更、障害を監視します。オペレーティング モデルが広範なパブリック アクセスを必要としない場合は、エディター UI をさらに制限します。

ロールバックとリカバリの準備

重要なアップグレードの前に、回復可能なバックアップを作成します。詳細なバックアップ範囲と復元については、別のリカバリ ガイドに記載されています。

機密性の高い実行履歴を最小限に抑えます。 実行が成功すると、顧客データとトークンが永続化されます。適切な場合に設定 EXECUTIONS_DATA_SAVE_ON_SUCCESS=none、保管してください EXECUTIONS_DATA_PRUNE=trueを選択し、 EXECUTIONS_DATA_MAX_AGE 時間単位など 168 (7日間)。これらは構成可能な例であり、法的な保持ルールではありません。履歴が少ないということは、デバッグ データやフォレンジック データが少ないことを意味します。実行中、待機中、または注釈付きの実行は、同じ方法でプルーニングできない場合があります。正式な執行保留。

侵害の疑い: 証拠を破壊することなく悪意のあるアクセスを制限し、プロキシ、ホスト、n8n のアクティビティと変更されたワークフローを検査し、公開された可能性のある上流の資格情報を取り消しまたはローテーションし、原因をパッチし、必要な場合にテスト済みの回復可能なバックアップからのみ復元します。影響を受ける Webhook URL、編集者アカウント、接続されているサービスを確認します。 HTTPS、スナップショットまたは VPS の購入によってインシデント対応サービスが提供されるとは想定しないでください。

アカウントとプラットフォームの保護

エディターと VPS を保護する

より強力なログイン保護が必要

編集者アカウントの 2 要素認証を有効にし、お使いのエディションが一元的なポリシーの適用をサポートしている場合は、n8n セキュリティ ポリシーを通じて MFA を適用します。

ワークフローを編集できる人を制限する

編集者アクセスは特権アクセスです。ワークフローは資格情報を読み取り、内部システムを呼び出し、強力なノードを実行できます。ユーザーのアクセスを制限し、不要になったアカウントを削除します。

使用しない機能を無効にする

不要な場合はパブリック API を無効にし、オペレーティング モデルに必要のない高リスクのノードや機能をブロックすることで、アプリケーションの攻撃対象領域を減らします。

SSRF とシークレット コントロールを意図的に使用する

任意の HTTP リクエストを行う可能性のあるワークフローの場合は、n8n の SSRF 保護を評価し、ワークフロー コード、パブリック リポジトリ、および広く読み取り可能な環境ファイルに機密情報が含まれないようにします。

未使用の管理エンドポイントを制限します。 N8N_PUBLIC_API_DISABLED=true n8n パブリック REST API を無効にし、 N8N_PUBLIC_API_SWAGGERUI_DISABLED=true API プレイグラウンドを個別に無効にします。これは、統合でこれらの機能が必要ない場合にのみ実行してください。 REST API を無効にすると、ワークフロー Webhook URL は認証されません。エディタ ユーザーには MFA を使用し、n8n エディションでサポートされている場合にのみ集中ポリシーを使用します。

公式ドキュメント: パブリック API · セキュリティ ポリシー変数 · 監査コマンドを無効にします。

よくある質問

n8n VPS セキュリティ: よくある質問

n8n ポートを直接公開する必要がありますか?

リバース プロキシがパブリック エントリ ポイントである場合は、不要なサービスを広く公開するのではなく、プロキシを公開し、アプリケーション ポートをその背後に保持します。

PostgreSQL または Redis はパブリックにすべきでしょうか?

通常はいいえ。これらは、それらを必要とするシステムによってのみ到達可能である必要があります。一般に公開すると、n8n の通常の動作に影響を与えることなく、攻撃対象領域が増加します。

n8n 暗号化キーが重要なのはなぜですか?

n8n によって保存された認証情報を保護し、展開全体で一貫性を保つ必要があります。これを紛失すると、復元されたデータから使用可能な暗号化された資格情報が得られなくなる可能性があります。

コミュニティノードは安全ですか?

これらはサードパーティのコードを使用して n8n を拡張するため、独自のサプライ チェーンと特権のリスクを伴うソフトウェアの依存関係として扱う必要があります。信頼でき必要なものだけをインストールしてください。

HTTPS はセルフホスト型の n8n インスタンスを安全にしますか?

いいえ、HTTPS は輸送を保護します。本番環境のセキュリティには、ホストの強化、アクセス制御、プライベート バックエンド サービス、機密保護、安全なワークフロー機能、監視と更新も必要です。

運用 Webhook が実行されている間、n8n エディターをプライベートにすることはできますか?

はい。信頼されたリバース プロキシまたは VPN は、公開実稼働 Webhook および OAuth コールバック パスとは別に、編集者/管理者のアクセスを制限できます。統合を誤ってブロックしないように、アクセス ルールを変更するたびに信頼されたサインインと外部 Webhook 配信をテストします。

受信した n8n Webhook を認証するにはどうすればよいですか?

送信者がサポートしている場合は、Webhook ノードで基本認証、ヘッダー認証、または JWT 認証を構成します。 IP ホワイトリストを使用し、利用可能な場合はプロバイダーの署名を確認することもできます。秘密に見えるパスだけに依存せず、機密性の高い API アクションをトリガーする前にリクエストを検証してください。
