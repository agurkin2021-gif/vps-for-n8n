Dockerによるインストール

VPSにn8nをインストールする

Docker Compose と PostgreSQL を使用して n8n を VPS にインストールします。運用環境のデプロイメントには、永続的なアプリケーションとデータベースのデータ、安定したデータも必要です。 N8N_ENCRYPTION_KEY、パブリック ホスト名、HTTPS、および正しい Webhook 構成。実稼働ワークフローをアクティブ化する前に、これらの部分を確認してください。

n8n、PostgreSQL、Docker、およびリバース プロキシ向けにサイズを維持した Linux サーバーを使用します。

TLS 証明書を発行して Webhook URL を公開する前に、VPS でドメインまたはサブドメインを指定します。

オペレーティング システムでサポートされているパッケージを使用して、Docker エンジンと Compose プラグインをインストールします。

CPU、RAM、ストレージが許可する場合は、制御するサーバーに n8n を追加できます。ただし、Nginx、Apache、Caddy、または別のリバース プロキシがすでにポート 80/443 を所有している場合は、次のようにします。 そうではない 以下のサンプル Caddy コンテナを変更せずに開始します。ポートが競合します。代わりに、適切なプライベート ネットワークを使用して既存のリバース プロキシ経由で新しい n8n サブドメインをルーティングするか、Compose の正確な例にクリーンな VPS を使用します。他のサイトとその TLS 構成を保持します。この例では、ポート 80/443 が使用可能であることを前提としています。

Docker Compose を使用して VPS に n8n をインストールする

この例を使用して、n8n デプロイメントを構築します。 自己管理型 Linux VPS。 n8n のインストールと保守は自分で行います。当社のパートナーを通じてサーバーを選択した場合、プリインストールされた n8n インスタンスは含まれません。この例では、n8n、PostgreSQL、外部タスク ランナー、および Caddy HTTPS をプライベート Compose ネットワークで組み合わせています。設定テンプレートですので、 ライブテストされた展開を主張するものではありません.

代わりに最速の新規インストールをご希望ですか? n8n は、公式の 1 行の Docker セットアップも提供します。スクリプトをダウンロードして確認できます。 curl -fsSL https://get.n8n.io -o get-n8n.sh 走る前に sh get-n8n.sh。このオプションは、ローカル URL で SQLite を使用して初期インスタンスを起動し、n8n Assistant サンドボックス サービスを含みます。それはです 同じではない この public-HTTPS の PostgreSQL ベースの VPS デプロイメントとして。公式の完全なサンドボックス スタックには、リーン n8n インストールよりも多くの RAM と CPU が必要です (Compose ガイドでは、少なくとも 4 GB RAM / 2 vCPU と指定されています)。インターネットに接続された実稼働 VPS の場合は、以下の手動で構成されたスタックを続行します。

1。 Docker、DNS、アクセスの準備

sudo アクセスで SSH 経由で接続し、DNS A レコードをポイントします。 n8n.example.com VPS IPv4 アドレスに送信します。で 新しい Ubuntu 22.04、24.04、または 26.04 VPS の場合、次のコマンドで Docker Engine と最新の docker compose Docker の公式署名済みプラグイン apt リポジトリ:

# Fresh official Ubuntu 22.04 / 24.04 / 26.04 installation
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Register Docker's signed apt repository
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

これは、公式の Docker Ubuntu インストール ガイドに記載されている運用指向のリポジトリ方法です。 すでにコンテナーや他の Web サイトを実行している VPS 上で Docker をやみくもに再インストールまたは削除しないでください。;まず、既存のインストールと考えられるパッケージの競合を検査します。 Debian または別のディストリビューションの場合は、Ubuntu コマンドの代わりに、対応する公式 OS 固有の手順を使用してください。

次に、Docker 自体、Compose プラグイン、DNS、作業ディレクトリを確認します。

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

もし getent hosts アドレスが返されないか、間違ったアドレスが返されます。Caddy を開始する前に DNS を修正してください。交換する n8n.example.com このガイドでは実際のホスト名を使用します。通常、Docker には root 権限が必要です。SSH ユーザーが後者の権限を実行できない場合は、 docker compose コマンドを直接使用する場合は、接頭辞を付けます sudo。ユーザーを追加する docker group は root と同等のアクセスを許可するため、共有サーバー上で気軽に実行しないでください。

ファイアウォールを有効にする前に、実際の SSH 管理ポートにアクセスできるようにしてください。証明書の発行とエディターにインバウンド HTTP (80) および HTTPS (443) を許可します。 Docker が公開するコンテナ ポートは一部の UFW ルールをバイパスする可能性があるため、Docker のファイアウォール ガイダンスを確認し、目的の Caddy ポートのみを公開してください。この Compose 例では、意図的に次のことを行っています。 そうではない PostgreSQL (5432)、n8n (5678)、またはタスクランナー ブローカー (5679) を公共のインターネットに公開します。

2。環境値を作成し、キーを保存する

プロジェクト ディレクトリから、次の 3 つを生成します。 違う ランダムな 16 進値:

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

という名前のファイルを作成します .env 以下のテンプレートを使用して、すべてを置き換えます REPLACE_WITH_RANDOM_HEX 生成された別の値を使用して、ホスト名とタイムゾーンを変更します。示されている 2.42.5 タグは 安定版リリースは 8 10 月 2026 にリストされています、ここでは古い構成例として使用されています。 ライブテストされた展開や将来のセキュリティを保証するものではありません。インストールする前に、現在の公式 n8n リリースを確認し、n8n とそのタスク ランナー イメージを同じ検証済みバージョンに保持してください。

# .env — replace the three example secrets
# Pin a maintained n8n release; keep n8n and runner equal.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

決してコミットしないでください .env パブリックリポジトリに。暗号化キーと回復手順を VPS から安全に保管します。キーは、コンテナーの再作成または移行後も同じままである必要があります。

3。新規インストール用に compose.yaml を作成する

同じディレクトリに、 compose.yaml。この例では、公式の n8n 環境変数規則と PostgreSQL 18 を使用しています。 PGDATA n8n ホスティング プロジェクトによって文書化されたパス:

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

4 つのサービスには異なる役割があります。PostgreSQL はデータベースの状態を保存し、n8n はワークフローを実行します。 n8n-runner 一致するバージョンと共有認証トークンを使用してランナー タスクを実行し、Caddy がパブリック HTTPS を処理します。外部 タスクランナー Redis キュー モードではありません。 Caddy のみがホスト ポートを公開します。この無駄のない図では、セットアップに単一のデータベース ロールを使用します。 PostgreSQL 権限をより強力に分離するには、公式の n8n PostgreSQL 導入例を参照してください。

4。 HTTPS キャディファイルを作成する

ファイルを作成する Caddyfile (大文字の C、拡張子なし) 横に compose.yaml。サンプルのホスト名をすべて独自の DNS 名に置き換えます。

n8n.example.com {
    reverse_proxy n8n:5678
}

ドメインが正しく解決され、外部トラフィックがポート 80/443 に到達できる場合、Caddy はパブリック TLS 証明書を要求して更新します。 DNS を指定しないでください localhost。 Caddy を別のリバース プロキシに置き換える場合は、元のホスト、プロトコル、およびクライアント アドレス ヘッダーを転送して調整します。 N8N_PROXY_HOPS 信頼できるプロキシ ホップの実際の数。

6。固定バージョンを変更する前にバックアップする

回復可能な PostgreSQL ダンプを保存する そして 永続的な n8n データ ボリューム、 .env/encryption キーと必要な外部ファイルをこのサーバーの外部のストレージに保存します。を使用して復元を確認します。 バックアップとリカバリのガイド 生産を更新する前に。コマンドの例:

# and files before changing the pinned versions.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# After securing the backup outside this VPS:
docker compose pull
docker compose up -d
docker compose ps

固定されたものを変更する N8N_VERSION リリースノートを読んだ後にのみ。 n8n イメージとランナー イメージは両方とも一緒に進む必要があります。 走らないでください docker compose down -v 定期メンテナンス中に名前付きデータ ボリュームが削除されるためです。 PostgreSQL のメジャー バージョンの変更には、データベースのアップグレードまたはダンプ/復元計画が必要です。 Postgres 18 イメージを別のメジャー タグに置き換えることは、自動移行ではありません。

バックアップと復元ガイド

よくある問題

n8n Docker インストールがローカルでは機能するのに本番環境では失敗する理由

間違った Webhook URL

コールバックは、パブリック HTTPS オリジンではなく、ローカルホスト、HTTP、または内部ホスト名を指します。

持続性が欠けている

コンテナーが再作成されると、アプリケーションまたはデータベースの状態が失われます。

新しいインスタンスでは別のキーが使用されるため、保存された認証情報は再構築後に使用できなくなります。

パブリックデータベースポート

PostgreSQL は、n8n のみが到達する必要があるにもかかわらず、不必要に公開されます。

未レビューのフローティング イメージの更新をメンテナンス戦略として扱わないでください。実行している n8n バージョンを記録し、リリース ノートを読み、変更する前にバックアップしてください。

PostgreSQL のメジャー バージョンを適切な場所に追加しないでください

Postgres のメジャー イメージ タグのみを変更すると、既存のデータ ディレクトリと互換性がなくなる可能性があります。コンテナーの再作成によってメジャー バージョンの移行が実行されると想定するのではなく、バックアップしてデータベースのアップグレード手順に従います。

Docker を使用した n8n のインストール: よくある質問

Docker を使用する場合、n8n には PostgreSQL が必要ですか?

Docker は PostgreSQL を必要とせず、小規模なデプロイメントでは SQLite を使用できます。実稼働指向の VPS 導入の場合、PostgreSQL はより強力なデータベース基盤を提供し、その後のキューモード スケーリングをサポートします。

PostgreSQL にデータが保存されている場合、なぜ永続的な n8n ボリュームを保持するのでしょうか?

永続的な n8n ディレクトリには、重要なインスタンスの状態と構成が含まれる場合があります。データベースが唯一の回復資産であると想定するのではなく、展開設計に従って保存してください。

Webhook に localhost が表示されるのはなぜですか?

内部コンテナのアドレスはパブリック オリジンとは異なります。外部ホスト名、プロトコル、Webhook URL を構成し、リバース プロキシが必要なヘッダーを確実に渡すようにします。

ポート 5678 はパブリックにする必要がありますか?

リバース プロキシの背後にある通常の運用環境の場合、特別な運用上の理由がない限り、プロキシで HTTPS を公開し、n8n アプリケーション ポートを内部に保持します。

Redis は必要ですか?

標準の単一インスタンスの Docker デプロイメント用ではありません。 Redis は、意図的にキュー モードとワーカーに移行する場合に関連します。

外部 n8n タスク ランナーはキュー モード ワーカーと同じですか?

いいえ。外部タスク ランナーは、サポートされているタスク コードを n8n メイン プロセスとは別に実行し、共有認証トークンを使用します。 Redis キュー モードはワークフローの実行を分散し、独自のインフラストラクチャ要件があります。この例は、Redis キュー モードではなく、外部タスク ランナーを示しています。ランナー イメージのバージョンを n8n のバージョンと一致させます。
