n8n-ის დაყენება VPS-ზე

დააყენეთ n8n VPS-ზე Docker Compose-ით და PostgreSQL-ით. პროდუქტიულ განთავსებას ასევე სჭირდება აპლიკაციისა და მონაცემთა ბაზის მუდმივი მონაცემები და სტაბილური N8N_ENCRYPTION_KEY, საჯარო hostname, HTTPS და სწორი webhook კონფიგურაცია. პროდუქტიული სამუშაო პროცესების გააქტიურებამდე ეს ელემენტები გადაამოწმეთ.

Docker Compose

დააყენეთ Docker Engine და Compose plugin ოპერაციული სისტემისთვის მხარდაჭერილი პაკეტებით.

Firewall

ღია დატოვეთ მხოლოდ საჭირო ადმინისტრაციული და ვებ-პორტები. PostgreSQL და შიდა აპლიკაციის სერვისები საჯაროდ არ გამოიტანოთ.

აყენებთ VPS-ზე, სადაც უკვე განთავსებულია ვებსაიტები? შეგიძლიათ n8n დაამატოთ თქვენს სერვერზე, თუ CPU, RAM და საცავი ამის საშუალებას იძლევა. თუმცა, თუ Nginx, Apache, Caddy ან სხვა reverse proxy უკვე იყენებს 80/443 პორტებს, არ ქვემოთ მოცემული Caddy კონტეინერი უცვლელად არ გაუშვათ: პორტები კონფლიქტში შევა. ამის ნაცვლად ახალი n8n ქვედომენი გაატარეთ არსებულ უკუ პროქსიზე შესაბამისი კერძო ქსელით, ან ზუსტად ამ Compose მაგალითისთვის გამოიყენეთ სუფთა VPS. შეინარჩუნეთ სხვა საიტები და მათი TLS კონფიგურაცია; მაგალითი ვარაუდობს, რომ 80/443 პორტები თავისუფალია.

კონფიგურირებადი კომპონენტები

Reverse proxyიღებს საჯარო HTTPS ტრაფიკს და გადაამისამართებს n8n-ზე.
n8nუშვებს რედაქტორს, ტრიგერებსა და სამუშაო პროცესებს აპლიკაციის მუდმივი მონაცემებით.
PostgreSQLინახავს სამუშაო პროცესების, ავტორიზაციის მონაცემებისა და შესრულებების მდგომარეობას პროდუქტიული განთავსებისთვის.
მუდმივი volumesაპლიკაციისა და მონაცემთა ბაზის მდგომარეობა ერთჯერადი კონტეინერების გარეთ შეინახეთ.
საჯარო DNSრედაქტორისა და webhook პროვაიდერების მიერ გამოყენებულ hostname-ს VPS-ზე აკავშირებს.

დააკოპირეთ და მოარგეთ

დააყენეთ n8n თქვენს VPS-ზე Docker Compose-ით

გამოიყენეთ ეს მაგალითი n8n-ის განთავსების ასაწყობად თვითმართვად Linux VPS-ზე. n8n-ს თავად აყენებთ და მართავთ; ჩვენი პარტნიორის მეშვეობით სერვერის არჩევა წინასწარ დაყენებულ n8n ინსტანციას არ გულისხმობს. მაგალითი აერთიანებს n8n-ს, PostgreSQL-ს, გარე task runner-სა და Caddy HTTPS-ს კერძო Compose ქსელში. ეს არის კონფიგურაციის შაბლონი, და არა განცხადება ცოცხალ გარემოში სრულად გამოცდილი განთავსების შესახებ.

გსურთ ახალი ინსტალაციის ყველაზე სწრაფი გზა? n8n ასევე გთავაზობთ ოფიციალურ ერთსტრიქონიან Docker დაყენებას. მისი სკრიპტის ჩამოტვირთვა და გადახედვა შეგიძლიათ ბრძანებით curl -fsSL https://get.n8n.io -o get-n8n.sh before running sh get-n8n.sh. ეს ვარიანტი უშვებს საწყის ინსტანციას SQLite-ით ლოკალურ URL-ზე და მოიცავს n8n Assistant sდაbox სერვისებს; ის იგივე არ არის როგორც ეს საჯარო HTTPS-ითა და PostgreSQL-ით გამაგრებული VPS განთავსება. ოფიციალურ სრულ sდაbox სტეკს მეტი RAM და CPU სჭირდება, ვიდრე მსუბუქ n8n ინსტალაციას; Compose გზამკვლევი მინიმუმ 4 GB RAM / 2 vCPU-ს უთითებს. ინტერნეტიდან ხელმისაწვდომ პროდუქტიულ VPS-ზე ქვემოთ მოცემული ხელით კონფიგურირებული სტეკი გამოიყენეთ.

1. მოამზადეთ Docker, DNS და წვდომა

დაუკავშირდით SSH-ით sudo წვდომით და DNS A ჩანაწერი n8n.example.com to your VPS IPv4 address. On a Ubuntu 22.04, 24.04 ან 26.04 VPS-ზე შემდეგი ბრძანებები აყენებს Docker Engine-სა და თანამედროვე docker compose plugin from Docker's official signed apt repository:

# Fresh official Ubuntu 22.04 / 24.04 / 26.04 installation
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Register Docker's signed apt repository
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

ეს არის პროდუქტიულ გარემოზე ორიენტირებული repository მეთოდი Docker-ის ოფიციალურ Ubuntu ინსტალაციის გზამკვლევში. არ გადააყენოთ ან წაშალოთ Docker დაუფიქრებლად VPS-ზე, სადაც უკვე მუშაობს კონტეინერები ან სხვა ვებსაიტები; ჯერ შეამოწმეთ არსებული ინსტალაცია და შესაძლო package conflict-ები. Debian-ის ან სხვა დისტრიბუტივისთვის Ubuntu ბრძანებების ნაცვლად შესაბამისი ოფიციალური OS-სპეციფიკური ინსტრუქციები გამოიყენეთ.

ახლა გადაამოწმეთ Docker, Compose plugin, DNS და სამუშაო დირექტორია:

sudo docker --version
sudo docker compose version
sudo docker run --rm hello-world
getent hosts n8n.example.com
mkdir -p ~/n8n && cd ~/n8n

If getent hosts თუ მისამართს არ აბრუნებს ან არასწორ მისამართს აბრუნებს, Caddy-ის გაშვებამდე DNS გაასწორეთ; n8n.example.com ამ გზამკვლევში ყველგან ჩაანაცვლეთ თქვენი რეალური hostname-ით. Docker ჩვეულებრივ root უფლებებს მოითხოვს: თუ თქვენი SSH მომხმარებელი შემდგომ docker compose ბრძანებებს პირდაპირ ვერ უშვებს, წინ დაუმატეთ sudo. მომხმარებლის docker ჯგუფში დამატება root-ის ეკვივალენტურ წვდომას იძლევა და გაზიარებულ სერვერზე დაუფიქრებლად არ უნდა გაკეთდეს.

Firewall-ის ჩართვამდე თქვენი რეალური SSH ადმინისტრირების პორტი ხელმისაწვდომად დატოვეთ. სერტიფიკატის გაცემისა და რედაქტორისთვის დაუშვით შემომავალი HTTP (80) და HTTPS (443). Docker-ის მიერ გამოქვეყნებულ კონტეინერის პორტებს ზოგი UFW წესი შეიძლება გვერდი აუაროს, ამიტომ გადახედეთ Docker-ის firewall ინსტრუქციას და გამოაქვეყნეთ მხოლოდ განკუთვნილი Caddy პორტები. ეს Compose მაგალითი განზრახ არ არ აქვეყნებს PostgreSQL (5432), n8n (5678) ან task-runner broker (5679) პორტებს საჯარო ინტერნეტში.

2. შექმენით გარემოს მნიშვნელობები და შეინახეთ გასაღები

პროექტის დირექტორიიდან შექმენით სამი განსხვავებული შემთხვევითი თექვსმეტობითი მნიშვნელობა ბრძანებით:

openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 32

Create a file named .env ქვემოთ მოცემული შაბლონით, ყველა REPLACE_WITH_RANDOM_HEX ჩაანაცვლეთ სხვადასხვა გენერირებული მნიშვნელობით და შეცვალეთ hostname და timezone. ნაჩვენები 2.42.5 tag არის სტაბილური რელიზი, რომელიც 2026 წლის 8 ოქტომბერს იყო მითითებული, used here as a dated configuration example, და არა ცოცხალ გარემოში გამოცდილი განთავსების ან მომავალი უსაფრთხოების გარანტია. დაყენებამდე გადაამოწმეთ n8n-ის მიმდინარე ოფიციალური რელიზი და n8n-ისა და task-runner image-ის ერთი და იგივე შემოწმებული ვერსია გამოიყენეთ.

# .env — replace the three example secrets
# Pin a maintained n8n release; keep n8n and runner equal.
N8N_VERSION=2.42.5
N8N_HOST=n8n.example.com
GENERIC_TIMEZONE=Etc/UTC
POSTGRES_PASSWORD=REPLACE_WITH_RANDOM_HEX
N8N_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_HEX
RUNNERS_AUTH_TOKEN=REPLACE_WITH_RANDOM_HEX

Never commit .env საჯარო რეპოზიტორიაში. დაშიფვრის გასაღები და აღდგენის ინსტრუქცია VPS-ის გარეთ უსაფრთხოდ შეინახეთ. კონტეინერის თავიდან შექმნის ან მიგრაციის შემდეგ გასაღები იგივე უნდა დარჩეს.

3. დაწერეთ compose.yaml ახალი ინსტალაციისთვის

იმავე დირექტორიაში შექმენით compose.yaml. მაგალითი იყენებს n8n-ის ოფიციალურ environment-variable წესებს და PostgreSQL 18-ის PGDATA ბილიკს, რომელიც n8n hosting პროექტშია დოკუმენტირებული:

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
      PGDATA: /var/lib/postgresql/data
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    restart: unless-stopped
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: "5432"
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      N8N_EDITOR_BASE_URL: https://${N8N_HOST}/
      N8N_WEBHOOK_URL: https://${N8N_HOST}/
      N8N_PROXY_HOPS: "1"
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      GENERIC_TIMEZONE: ${GENERIC_TIMEZONE}
      TZ: ${GENERIC_TIMEZONE}
      N8N_RUNNERS_MODE: external
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_BROKER_LISTEN_ADDRESS: 0.0.0.0
    volumes:
      - n8n_data:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

  n8n-runner:
    image: n8nio/runners:${N8N_VERSION}
    restart: unless-stopped
    environment:
      N8N_RUNNERS_AUTH_TOKEN: ${RUNNERS_AUTH_TOKEN}
      N8N_RUNNERS_TASK_BROKER_URI: http://n8n:5679
    depends_on:
      - n8n

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - n8n

volumes:
  postgres_data:
  n8n_data:
  caddy_data:
  caddy_config:

ოთხ სერვისს განსხვავებული როლი აქვს: PostgreSQL ინახავს მონაცემთა ბაზის მდგომარეობას, n8n უშვებს სამუშაო პროცესებს, n8n-runner ასრულებს runner დავალებებს შესაბამისი ვერსიითა და shared authentication token-ით, ხოლო Caddy ამუშავებს საჯარო HTTPS-ს. გარე task runner ეს არ არის Redis-ის queue mode. ჰოსტის პორტებს მხოლოდ Caddy აქვეყნებს. ეს მსუბუქი მაგალითი დაყენებისთვის მონაცემთა ბაზის ერთ როლს იყენებს; PostgreSQL პრივილეგიების უფრო მკაფიო გამიჯვნისთვის იხილეთ n8n PostgreSQL-ის ოფიციალური განთავსების მაგალითი.

4. შექმენით HTTPS Caddyfile

შექმენით ფაილი Caddyfile (capital C, no extension) alongside compose.yaml. მაგალითში hostname ყველგან თქვენი DNS სახელით ჩაანაცვლეთ:

n8n.example.com {
    reverse_proxy n8n:5678
}

Caddy ითხოვს და აახლებს საჯარო TLS სერტიფიკატებს, როდესაც დომენი სწორად resolve-დება და გარე ტრაფიკი აღწევს 80/443 პორტებს. DNS არ მიმართოთ localhost. თუ Caddy-ს სხვა reverse proxy-ით შეცვლით, გადააგზავნეთ ორიგინალი host, protocol და client-address headers და მოარგეთ N8N_PROXY_HOPS რეალურად ნდობით აღჭურვილი proxy hops-ის რაოდენობას.

5. გაუშვით კონტეინერები და გარედან შეამოწმეთ

ეს ბრძანებები პროექტის დირექტორიიდან გაუშვით მას შემდეგ, რაც შეინახავთ .env, compose.yaml და Caddyfile:

chmod 600 .env
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=100 n8n n8n-runner postgres caddy
curl -fsS https://n8n.example.com/healthz

ბოლო ბრძანება ამოწმებს საჯარო HTTPS health endpoint. If certificate issuance is still pending, inspect Caddy logs და DNS/ports before concluding n8n is broken. Open https://n8n.example.com, დაუყოვნებლივ შექმენით პირველი owner ანგარიში და ჩართეთ შესაბამისი sign-in დაცვა. დაადასტურეთ, რომ ინსტანცია რეალურად ასრულებს სამუშაო პროცესს და არა მხოლოდ რედაქტორს ხსნის:

  1. რედაქტორში შექმენით სამუშაო პროცესი Webhook trigger. Set HTTP Method to GET, აირჩიეთ Path vps-check, და Respond დააყენეთ Immediately მნიშვნელობაზე. შეინახეთ სამუშაო პროცესი.
  2. დააწკაპუნეთ სატესტო მოვლენის მოსმენა, დააკოპირეთ n8n-ის მიერ ნაჩვენები სრული სატესტო URL და სხვა მოწყობილობიდან გაუშვით curl -i 'PASTE_TEST_URL_HERE' დაკოპირებული URL-ით. მოსალოდნელია წარმატებული HTTP პასუხი და შემომავალი მოვლენის გამოჩენა n8n რედაქტორში. სატესტო URL-ები მუშაობს მხოლოდ მაშინ, როცა n8n მოვლენას უსმენს.
  3. გამოაქვეყნეთ სამუშაო პროცესი, node გადართეთ მის პროდუქტიული URL, დააკოპირეთ და გაუშვით curl -i 'PASTE_PRODUCTION_URL_HERE' კიდევ ერთხელ. დაადასტურეთ შესრულება სამუშაო პროცესის Executions ჩანართში. პროდუქტიული webhook მოთხოვნებისთვის სამუშაო პროცესი გამოქვეყნებული უნდა იყოს და მათი payload რედაქტორის სატესტო ხედში არ გამოჩნდება.

ეს განზრახ მარტივი, ავტორიზაციის გარეშე ფუნქციური ტესტია: არასდროს გაუგზავნოთ საიდუმლო მონაცემები. ტესტის შემდეგ გააუქმეთ გამოქვეყნება ან წაშალეთ, ან რეალური მონაცემებისთვის საჯარო endpoint-ის გამოყენებამდე დააკონფიგურირეთ Webhook-ის ავტორიზაცია/IP შეზღუდვები. იხილეთ Webhook-ის სატესტო და პროდუქტიული რეჟიმების ოფიციალური დოკუმენტაცია.

6. pinned ვერსიების შეცვლამდე შექმენით სარეზერვო ასლი

Save a recoverable PostgreSQL dump და მუდმივი n8n data volume, .env/დაშიფვრის გასაღები და საჭირო გარე ფაილები ამ სერვერის გარეთ საცავში. აღდგენა გადაამოწმეთ სარეზერვო და აღდგენის გზამკვლევით პროდუქტიული გარემოს განახლებამდე. ბრძანებების მაგალითი:

# Back up the database, encryption key, instance data,
# and files before changing the pinned versions.
docker compose exec -T postgres \
  pg_dump -U n8n -d n8n > n8n-db.sql
# After securing the backup outside this VPS:
docker compose pull
docker compose up -d
docker compose ps

დააფიქსირებული N8N_VERSION შეცვალეთ მხოლოდ release notes-ის წაკითხვის შემდეგ; n8n-ისა და runner-ის images ერთად უნდა განახლდეს. არ გაუშვათ docker compose down -v რუტინული მოვლისას, რადგან ეს სახელდებულ მონაცემთა ტომებს წაშლის. PostgreSQL-ის მთავარი ვერსიის ცვლილება საჭიროებს მონაცემთა ბაზის განახლების ან dump/restore გეგმას; Postgres 18 image-ის სხვა მთავარი ვერსიის tag-ით ჩანაცვლება ავტომატური მიგრაცია არ არის.

ავტორიტეტული წყაროები: n8n Docker Compose გზამკვლევი, n8n უკუ-პროქსი/webhook კონფიგურაცია და PostgreSQL-ის ოფიციალური განთავსების შენიშვნები. ინფრასტრუქტურული წარმადობის შედარებითი ტესტი ან კონკრეტული პროვაიდერის წინასწარ დაყენებული ფუნქცია ნაგულისხმევი არ არის.

კონფიგურაცია

საიდუმლოებები და საჯარო URL-ები გააზრებულად დააყენეთ

დაშიფვრის გასაღები

პროდუქტიული ავტორიზაციის მონაცემების შენახვამდე დააყენეთ და შეინახეთ ძლიერი n8n დაშიფვრის გასაღები. აღდგენის შემდეგ იგივე გასაღებია საჭირო.

PostgreSQL ავტორიზაციის მონაცემები

გამოიყენეთ ცალკე მონაცემთა ბაზის ავტორიზაციის მონაცემები და პაროლები საჯარო source control-ის გარეთ შეინახეთ.

საჯარო hostname

შიდა კონტეინერის მისამართის ნაცვლად რეალური გარე hostname და HTTPS origin დააკონფიგურირეთ.

Webhook URL

Set N8N_WEBHOOK_URL საჯაროდ ხელმისაწვდომ HTTPS საბაზო URL-ზე დააყენეთ და N8N_PROXY_HOPS=1 როდესაც ერთი trusted reverse proxy არის. WEBHOOK_URL is a deprecated alias in n8n 2.35.0 და later; avoid copying it from older tutorials.

მუდმივი მონაცემები

n8n და PostgreSQL ცალ-ცალკე შეინარჩუნეთ

n8n მონაცემები

n8n მონაცემების დირექტორიისთვის მუდმივი საცავი დაამაუნტეთ, რათა კრიტიკული ინსტანციის მდგომარეობა კონტეინერის თავიდან შექმნის შემდეგაც დარჩეს.

PostgreSQL მონაცემები

მონაცემთა ბაზის დირექტორია PostgreSQL კონტეინერისგან დამოუკიდებლად შეინარჩუნეთ.

ფაილის permissions

mounted ბილიკები განკუთვნილი კონტეინერის მომხმარებლისთვის ჩაწერადი გახადეთ ისე, რომ ჰოსტის საცავი ზედმეტად ღია არ გახდეს.

სამუშაო პროცესის ფაილები

შეინარჩუნეთ ყველა mounted ფაილი ან ბინარული მონაცემების საცავი, რომელზეც პროდუქტიული სამუშაო პროცესებია დამოკიდებული.

POSTGRESQL

დააკავშირეთ n8n კერძო მონაცემთა ბაზის სერვისს

მონაცემთა ბაზის ტიპიდააკონფიგურირეთ n8n PostgreSQL-ზე, რათა შემთხვევით SQLite-ზე არ გადავიდეს.
Hostგამოიყენეთ PostgreSQL სერვისის სახელი კერძო Docker ქსელში.
ავტორიზაციის მონაცემებიშეუსაბამეთ განკუთვნილ მონაცემთა ბაზას, აპლიკაციის მომხმარებელსა და პაროლს.
მზადყოფნაn8n-ის წარმატებულ ინიციალიზაციამდე PostgreSQL-ს მზადყოფნის დრო მიეცით.
ქსელიკონტეინერებს შორის მონაცემთა ბაზის წვდომას საჯარო PostgreSQL პორტი არ სჭირდება.

HTTPS და PROXY

საჯარო n8n URL HTTPS-ის უკან მოათავსეთ

Reverse proxy

საჯარო შესვლის წერტილად გამოიყენეთ Nginx, Caddy ან Traefik და ტრაფიკი კერძო n8n სერვისზე გადაამისამართეთ.

TLS

საჯარო hostname-ისთვის გასცეთ ვალიდური სერტიფიკატი და HTTP ტრაფიკი HTTPS-ზე გადაამისამართეთ.

Forwarded headers

გადააწოდეთ host, protocol და client information, რომელიც n8n-ს სჭირდება, და დააკონფიგურირეთ მოსალოდნელი proxy hop count.

Webhook-ის შემოწმება

VPS-ის გარედან გამოიძახეთ webhook და დაადასტურეთ, რომ n8n ქმნის გარედან ხელმისაწვდომ HTTPS URL-ს.

პროდუქტიული უსაფრთხოების სრული საკონტროლო სია

პირველი გაშვება

პროდუქტიულ გამოყენებამდე persistence გადაამოწმეთ

კონტეინერებიდაადასტურეთ, რომ n8n, PostgreSQL და proxy გაშვებისა და restart-ის შემდეგაც გამართულად მუშაობს.
რედაქტორიგახსენით საჯარო HTTPS hostname და დაადასტურეთ, რომ authentication სწორად მუშაობს.
მონაცემთა ბაზაშექმენით სატესტო მდგომარეობა, თავიდან შექმენით კონტეინერები და გადაამოწმეთ, რომ მდგომარეობა შენარჩუნდა.
Webhookგაუშვით გარე webhook ტესტი DNS-ის, TLS-ის, proxying-ისა და საჯარო callback URL-ის შესამოწმებლად.
ავტორიზაციის მონაცემებიგადაამოწმეთ, რომ დაშიფრული ავტორიზაციის მონაცემები n8n restart-ის შემდეგაც გამოყენებადია.

FAQ

n8n-ის Docker-ით დაყენება: გავრცელებული კითხვები

სჭირდება n8n-ს PostgreSQL Docker-ის გამოყენებისას?

Docker PostgreSQL-ს არ მოითხოვს და მცირე განთავსებებს SQLite-ის გამოყენება შეუძლია. პროდუქტიულ VPS განთავსებაში PostgreSQL უფრო ძლიერი მონაცემთა ბაზის საფუძველია და შემდგომ queue mode-ზე მასშტაბირებას უჭერს მხარს.

რატომ შევინარჩუნოთ მუდმივი n8n volume, თუ მონაცემებს PostgreSQL ინახავს?

მუდმივი n8n დირექტორია შეიძლება შეიცავდეს ინსტანციის მნიშვნელოვან მდგომარეობასა და კონფიგურაციას. შეინარჩუნეთ იგი განთავსების დიზაინის მიხედვით და ნუ ჩათვლით, რომ აღდგენის ერთადერთი რესურსი მონაცემთა ბაზაა.

რატომ აჩვენებს ჩემი webhook localhost-ს?

შიდა კონტეინერის მისამართი საჯარო origin-ისგან განსხვავდება. დააკონფიგურირეთ გარე hostname, protocol და webhook URL და დარწმუნდით, რომ reverse proxy საჭირო headers-ს გადასცემს.

უნდა იყოს 5678 პორტი საჯარო?

ჩვეულებრივ პროდუქტიულ განთავსებაში reverse proxy-ის უკან HTTPS proxy-ზე გამოაქვეყნეთ, ხოლო n8n აპლიკაციის პორტი შიდა დატოვეთ, თუ მისი საჯაროდ გახსნის კონკრეტული საოპერაციო მიზეზი არ არსებობს.

მჭირდება Redis?

სტანდარტული ერთინსტანციანი Docker განთავსებისთვის არა. Redis საჭირო ხდება, როდესაც განზრახ გადადიხართ queue mode-სა და worker-ებზე.

External n8n task runner-ები იგივეა, რაც queue mode worker-ები?

არა. External task runner-ები მხარდაჭერილ task code-ს n8n main process-ისგან ცალკე ასრულებს და shared authentication token-ს იყენებს. Redis queue mode სამუშაო პროცესების შესრულებებს ანაწილებს და საკუთარი ინფრასტრუქტურული მოთხოვნები აქვს. ეს მაგალითი external task runner-ს აჩვენებს და არა Redis queue mode-ს. runner image-ის ვერსია n8n-ის ვერსიას შეუსაბამეთ.

პროვაიდერებს ადარებთ?
