n8n Backup და Restore

თვითჰოსტირებული n8n-ის სარეზერვო ასლისა და აღდგენისთვის დაიცავით SQLite მონაცემთა ბაზა ან თანმიმდევრული PostgreSQL dump, მუდმივი .n8n საქაღალდე და საწყისი დაშიფვრის გასაღები, განთავსების კონფიგურაცია და ყველა გარე ბინარული ან mounted-file დამოკიდებულება. დაშიფრული ასლი VPS-ის გარეთ შეინახეთ და აღდგენა ცალკე ინსტანციაზე გამოცადეთ. შერჩევითი აღდგენისთვის გამოიყენეთ CLI-ით სამუშაო პროცესებისა და ავტორიზაციის მონაცემების ექსპორტი; მხოლოდ JSON ექსპორტები სრულ სერვერულ სარეზერვო ასლს არ წარმოადგენს.

სწრაფი საკონტროლო სია

რას უნდა იცავდეს n8n-ის სარეზერვო ასლი

მონაცემთა ბაზა

შექმენით იმ PostgreSQL მონაცემთა ბაზის ან SQLite ფაილის სარეზერვო ასლი, რომელსაც ინსტანცია იყენებს. მონაცემთა ბაზა შეიცავს n8n-ის ძირითად მდგომარეობას, მათ შორის სამუშაო პროცესებს, ავტორიზაციის მონაცემებსა და შესრულების მონაცემებს.

დაშიფვრის გასაღები

ზუსტად ის n8n დაშიფვრის გასაღები ცალკე და უსაფრთხოდ შეინახეთ. აღდგენილი დაშიფრული ავტორიზაციის მონაცემები იმავე გასაღებზეა დამოკიდებული.

მუდმივი ფაილები

ჩართეთ n8n-ის მუდმივი მონაცემების დირექტორია და ყველა mounted ფაილი, ბინარული მონაცემების საცავი ან სამუშაო პროცესის რესურსი, რომელზეც თქვენი განთავსებაა დამოკიდებული.

განთავსების კონფიგურაცია

შეინახეთ Compose/კონფიგურაციის ფაილები და არაკონფიდენციალური პარამეტრები, რომლებიც სტეკის თავიდან ასაწყობად არის საჭირო. საიდუმლო მონაცემები შესაბამისი წვდომის კონტროლით დაიცავით.

სარეზერვო ასლის ორი დონე

ლოგიკური ექსპორტი და სრული ავარიული აღდგენა

სამუშაო პროცესებისა და ავტორიზაციის მონაცემების ექსპორტი

n8n CLI ექსპორტები სასარგებლოა მიგრაციისთვის, სამუშაო პროცესების ვერსირებული ასლებისთვის და შერჩევითი აღდგენისთვის. ავტორიზაციის მონაცემები შეიძლება დაშიფრული ფორმით გაიტანოთ და მოგვიანებით შესაბამისი დაშიფვრის გასაღებით შემოიტანოთ. მხოლოდ ერთი სამუშაო პროცესის აღსადგენად რედაქტორის სამწერტილიანი მენიუდან ჩამოტვირთეთ მისი JSON, შემდეგ Import from File-ით შემოიტანეთ ახალ სატესტო სამუშაო პროცესში ან იზოლირებულ ინსტანციაში. მოქმედი სამუშაო პროცესის ჩანაცვლებამდე შეამოწმეთ ავტორიზაციის მონაცემები, workflow ID-ები და node პარამეტრები: workflow JSON-ის აღდგენა მთელ სერვერს არ აღადგენს.

ობიექტების ექსპორტი

CLI-ს შეუძლია მონაცემთა ბაზის ობიექტების ექსპორტი მხარდაჭერილ მონაცემთა ბაზის ტიპებს შორის გადასატანად. შესრულებების ისტორიის ცხრილები არჩევითია, რადგან შეიძლება ძალიან დიდი იყოს.

სრული ინსტანციის აღდგენა

სერვერის სრული დაკარგვის სცენარისთვის დაიცავით რეალური მონაცემთა ბაზა, დაშიფვრის გასაღები, მუდმივი მონაცემები და განთავსების დამოკიდებულებები. ნუ ჩათვლით, რომ workflow JSON ექსპორტი მთელ ინსტანციას აღადგენს.

პროვაიდერის snapshot

VPS snapshot სასარგებლოა როგორც დამატებითი აღდგენის ფენა, მაგრამ ის არ უნდა იყოს ერთადერთი ასლი და არ უნდა ჩაანაცვლოს დამოუკიდებლად შემოწმებული აპლიკაციის/მონაცემთა ბაზის სარეზერვო ასლი.

მონაცემთა ბაზა

შექმენით მონაცემთა ბაზის თანმიმდევრული სარეზერვო ასლი

PostgreSQL

გამოიყენეთ PostgreSQL-ის თანმიმდევრული სარეზერვო მეთოდი და მიღებული ასლი VPS-ის გარეთ შეინახეთ. იმავე დაზიანებულ დისკზე არსებული მონაცემთა ბაზის ასლი ავარიული აღდგენა არ არის.

SQLite

თუ განთავსება SQLite-ს იყენებს, დაიცავით მონაცემთა ბაზის ფაილი n8n-ის მუდმივი მონაცემების დირექტორიიდან. მოერიდეთ მონაცემთა ბაზის კოპირებას არასაიმედო მდგომარეობაში, როდესაც მასში აქტიურად იწერება.

შესრულებების ისტორია

განსაზღვრეთ, შედის თუ არა შესრულებების ისტორიული მონაცემები თქვენს აღდგენის მიზანში. მათ შეუძლიათ სარეზერვო ასლის მოცულობა მნიშვნელოვნად გაზარდონ, ამიტომ არჩევანი შენახვისა და შესაბამისობის მოთხოვნებმა უნდა განსაზღვროს.

მონაცემთა ბაზა version

ჩაიწერეთ საწყისი განთავსების მონაცემთა ბაზის ძრავა და ვერსია, რათა აღდგენის გარემო თავსებადად მოამზადოთ.

PostgreSQL გააკეთეთcker Compose VPS-ზე. თუ PostgreSQL სერვისის სახელია postgres და მონაცემთა ბაზისა და მომხმარებლის სახელია n8n, შემდეგი ბრძანება ჰოსტზე ქმნის PostgreSQL-ის თანმიმდევრულ custom-format dump-ს. გაშვებამდე შეამოწმეთ თქვენი რეალური Compose ფაილი და საჭიროებისამებრ შეცვალეთ მონაცემთა ბაზის ავტორიზაციის მონაცემები და სერვისის სახელები. pg_dump PostgreSQL-ის მუშაობისას შეუძლია ლოგიკურად თანმიმდევრული snapshot-ის შექმნა; ის არ ქმნის ცალკე .n8n მომხმარებლის საქაღალდის ან გარე ბინარული მონაცემების სარეზერვო ასლს.

# In the გააკეთეთcker Compose project; adapt service, DB და user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

The archive-list check catches obvious format problems but does არ prove the data can be restored. Store an encrypted copy off-server და rehearse a restore. Use the official PostgreSQL pg_dump documentation for database-specific options.

SQLite გააკეთეთcker-ზე. ნაგულისხმევი SQLite განთავსებისთვის database.sqlite და გენერირებული დაშიფვრის გასაღების კონფიგურაცია მუდმივ .n8n საქაღალდეშია (ჩვეულებრივ mounted მისამართზე /home/node/.n8n). SQLite-ის უბრალო ცოცხალი ასლი თანმიმდევრულად არ ჩათვალოთ. საქაღალდის კოპირებამდე გააჩერეთ n8n და მონაცემთა ბაზაში მწერი სხვა პროცესები, ან როცა გაჩერება შეუძლებელია, გამოიყენეთ SQLite-ის მხარდაჭერილი online უკანup მექანიზმი:

# Only for SQLite და the default /home/node/.n8n mount
# Stop n8n (და any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-უკანup
docker compose start n8n

These are illustrative commდაs for the service და path shown, არ a universal volume layout. დაკოპირებული folder is initially still on the same VPS; transfer და protect it off-server. When queue workers or other writers exist, quiesce those too და follow their actual deployment design. n8n's current full-უკანup guidance documents the SQLite consistency requirement.

ნაგულისხმევი SQLite საქაღალდის სუფთა სამიზნეზე აღდგენა: ჯერ გააჩერეთ n8n სერვისი და მონაცემთა ბაზაში ყველა მწერი პროცესი. როდესაც თავსებადი n8n სერვისის კონტეინერი და მისი სამიზნე volume უკვე არსებობს, დააკოპირეთ სარეზერვოდ შენახული .n8n შიგთავსი უკან to the same persistent directory. This overwrites target files, so do არ run it n instance with data you need to keep:

# Run მხოლოდ on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-უკანup/. n8n:/home/node/.n8n/
# Verify ownership და permissions for the n8n container user BEFORE the next commდა
# Start მხოლოდ after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials და workflow triggers

გააკეთეთcker can copy to stopped containers, but destination ownership may differ from the original; ensure the restored configuratind database file are readable და writable by the n8n process before starting it. If your real Compose configuration uses a different path or bind mount, adapt the copy accordingly. გააკეთეთcker Compose copy reference. Restoring an n8n folder alone is არ enough for deployments that use a separate PostgreSQL database.

კრიტიკული საიდუმლო

დაშიფვრის გასაღები აღდგენის ნაწილია

n8n შენახულ ავტორიზაციის მონაცემებს ინსტანციის დაშიფვრის გასაღებით შიფრავს. მონაცემთა ბაზის ან დაშიფრული ავტორიზაციის მონაცემების ექსპორტი შესაბამისი გასაღების გარეშე შეიძლება აღდგენილ სამუშაო პროცესებს შენახული ავტორიზაციის მონაცემების გამოყენების შესაძლებლობა დაუკარგოს.

If you set N8N_ENCRYPTION_KEY, restore that exact secret. Otherwise the generated key is stored in the persistent .n8n/config file: protect that config when უკანing up or rebuilding. Store recovery keys securely outside the VPS. In queue mode, all main და worker processes must use the same key.

გააკეთეთშეინახეთ პროდუქტიულ გარემოში გამოყენებული ზუსტი გასაღების დაცული ასლი.
გააკეთეთავტორიზაციის მონაცემების ტესტირებამდე გადაამოწმეთ, რომ აღდგენის გარემო სწორედ ამ გასაღებს იყენებს.
გააკეთეთ არსერვერის თავიდან აწყობის შემდეგ ახალ გენერირებულ გასაღებს ნუ დაეყრდნობით.
გააკეთეთ არCommit the key to a public repository or store it beside an unprotected უკანup.

ფაილები და ბინარული მონაცემები

მონაცემთა ბაზა უკანup may არ cover every workflow dependency

მუდმივი .n8n მონაცემები

Locate და preserve the actual .n8n user folder, არ მხოლოდ the container image. In a typical გააკეთეთcker deployment it is mounted at /home/node/.n8n; outside გააკეთეთcker the default is ~/.n8n. If N8N_USER_FOLDER is configured, n8n creates .n8n inside that specified parent directory. Include its config key და any local SQLite, binary or filesystem execution data your installation uses.

Mounted workflow ფაილები

If workflows read or write host-mounted directories, უკან those directories up separately. Restoring n8n without them can leave otherwise valid workflows broken.

ბინარული მონაცემები

Identify the storage mode და restore every external dependency. Filesystem-based binary or execution data may live in .n8n or a custom directory; S3/Azure Blob or other configured external storage needs its own recoverable copy და access settings. A database dump alone canარ replace those files.

Community node-ები

Record community packages და versions, და უკან up any additional custom node directories configured through N8N_CUSTOM_EXTENSIONS. Those directories can sit outside .n8n; a database და user-folder restore alone may still leave custom-node workflows unusable.

სერვერისგარე სტრატეგია

A უკანup on the same VPS is მხოლოდ a local copy

ლოკალური ასლიUseful for quick rollუკან, but vulnerable to server loss, disk failure და destructive mistakes.
სერვერისგარე ასლიKeep at least one უკანup in storage independent of the production VPS.
ვერსირებული ასლებიRetain multiple recovery points so corruption or a bad change does არ overwrite the მხოლოდ usable უკანup.
წვდომის კონტროლისარეზერვო ასლები შეიძლება შეიცავდეს ავტორიზაციის მონაცემებს, workflow ლოგიკას და სენსიტიურ ბიზნეს-მონაცემებს. შესაბამისად დაშიფრეთ და შეზღუდეთ წვდომა.

FAQ

n8n უკანup და restore: common questions

Is exporting workflows enough to უკან up n8n?

No. Workflow exports are useful logical copies, but complete recovery can also require credentials, the matching encryption key, database state, persistent files და binary-data storage.

გააკეთეთ I need the n8n encryption key if I have the database?

დიახ, თუ გსურთ მონაცემთა ბაზაში შენახული დაშიფრული credentials კვლავ გამოყენებადი იყოს. საწყისი გასაღები უსაფრთხოდ შეინახეთ.

Should I უკან up PostgreSQL or export workflows და credentials?

For disaster recovery, protect the database და the encryption key. Logical exports are valuable as an additional migratind selective-recovery layer rather than a substitute for every part of the instance.

Can a VPS snapshot be my მხოლოდ უკანup?

It is better treated as one recovery layer. Keep an independent off-server უკანup so a provider, account, server or snapshot failure does არ remove every recovery point at once.

How do I know my უკანup works?

Restore it into a clean test environment, verify credentials decrypt, და run representative workflows. A successful უკანup job alone does არ prove recoverability.

გააკეთეთ GitHub or Google Drive workflow უკანups include saved credential secrets?

Workflow-მხოლოდ JSON უკანups do არ include the secret values managed by n8n's credential store or the instance encryption key. However, exported JSON can expose credential names და IDs და secrets typed directly into node parameters, such as authentication headers. Inspect და protect exported JSON before uploading or sharing it. For full recovery, უკან up the database და original key, or use supported encrypted credential CLI exports with a tested restore. A workflow-მხოლოდ GitHub or Google Drive template is არ full disaster recovery.
