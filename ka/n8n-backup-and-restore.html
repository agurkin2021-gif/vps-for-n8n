n8n-ის სარეზერვო ასლი და აღდგენა

თვითჰოსტირებული n8n-ის სარეზერვო ასლისა და აღდგენისთვის დაიცავით SQLite მონაცემთა ბაზა ან თანმიმდევრული PostgreSQL dump, მუდმივი .n8n საქაღალდე და საწყისი დაშიფვრის გასაღები, განთავსების კონფიგურაცია და ყველა გარე ბინარული ან mounted-file დამოკიდებულება. დაშიფრული ასლი VPS-ის გარეთ შეინახეთ და აღდგენა ცალკე ინსტანციაზე გამოცადეთ. შერჩევითი აღდგენისთვის გამოიყენეთ CLI-ით სამუშაო პროცესებისა და ავტორიზაციის მონაცემების ექსპორტი; მხოლოდ JSON ექსპორტები სრულ სერვერულ სარეზერვო ასლს არ წარმოადგენს.

აირჩიეთ VPS n8n-ისთვის

პარტნიორული ბმული: შეძენიდან შესაძლოა მივიღოთ საკომისიო.

სწრაფი საკონტროლო სია

რას უნდა იცავდეს n8n-ის სარეზერვო ასლი

მონაცემთა ბაზა

შექმენით იმ PostgreSQL მონაცემთა ბაზის ან SQLite ფაილის სარეზერვო ასლი, რომელსაც ინსტანცია იყენებს. მონაცემთა ბაზა შეიცავს n8n-ის ძირითად მდგომარეობას, მათ შორის სამუშაო პროცესებს, ავტორიზაციის მონაცემებსა და შესრულების მონაცემებს.

დაშიფვრის გასაღები

ზუსტად ის n8n დაშიფვრის გასაღები ცალკე და უსაფრთხოდ შეინახეთ. აღდგენილი დაშიფრული ავტორიზაციის მონაცემები იმავე გასაღებზეა დამოკიდებული.

მუდმივი ფაილები

ჩართეთ n8n-ის მუდმივი მონაცემების დირექტორია და ყველა mounted ფაილი, ბინარული მონაცემების საცავი ან სამუშაო პროცესის რესურსი, რომელზეც თქვენი განთავსებაა დამოკიდებული.

განთავსების კონფიგურაცია

შეინახეთ Compose/კონფიგურაციის ფაილები და არაკონფიდენციალური პარამეტრები, რომლებიც სტეკის თავიდან ასაწყობად არის საჭირო. საიდუმლო მონაცემები შესაბამისი წვდომის კონტროლით დაიცავით.

სარეზერვო ასლის ორი დონე

ლოგიკური ექსპორტი და სრული ავარიული აღდგენა

სამუშაო პროცესებისა და ავტორიზაციის მონაცემების ექსპორტი

n8n CLI ექსპორტები სასარგებლოა მიგრაციისთვის, სამუშაო პროცესების ვერსირებული ასლებისთვის და შერჩევითი აღდგენისთვის. ავტორიზაციის მონაცემები შეიძლება დაშიფრული ფორმით გაიტანოთ და მოგვიანებით შესაბამისი დაშიფვრის გასაღებით შემოიტანოთ. მხოლოდ ერთი სამუშაო პროცესის აღსადგენად რედაქტორის სამწერტილიანი მენიუდან ჩამოტვირთეთ მისი JSON, შემდეგ „ფაილიდან იმპორტით“ შემოიტანეთ ახალ სატესტო სამუშაო პროცესში ან იზოლირებულ ინსტანციაში. მოქმედი სამუშაო პროცესის ჩანაცვლებამდე შეამოწმეთ ავტორიზაციის მონაცემები, სამუშაო პროცესის ID-ები და node პარამეტრები: სამუშაო პროცესის JSON-ის აღდგენა მთელ სერვერს არ აღადგენს.

ობიექტების ექსპორტი

CLI-ს შეუძლია მონაცემთა ბაზის ობიექტების ექსპორტი მხარდაჭერილ მონაცემთა ბაზის ტიპებს შორის გადასატანად. შესრულებების ისტორიის ცხრილები არჩევითია, რადგან შეიძლება ძალიან დიდი იყოს.

სრული ინსტანციის აღდგენა

სერვერის სრული დაკარგვის სცენარისთვის დაიცავით რეალური მონაცემთა ბაზა, დაშიფვრის გასაღები, მუდმივი მონაცემები და განთავსების დამოკიდებულებები. ნუ ჩათვლით, რომ სამუშაო პროცესის JSON ექსპორტი მთელ ინსტანციას აღადგენს.

პროვაიდერის snapshot

VPS snapshot სასარგებლოა როგორც დამატებითი აღდგენის ფენა, მაგრამ ის არ უნდა იყოს ერთადერთი ასლი და არ უნდა ჩაანაცვლოს დამოუკიდებლად შემოწმებული აპლიკაციის/მონაცემთა ბაზის სარეზერვო ასლი.

მონაცემთა ბაზა

შექმენით მონაცემთა ბაზის თანმიმდევრული სარეზერვო ასლი

PostgreSQL

გამოიყენეთ PostgreSQL-ის თანმიმდევრული სარეზერვო მეთოდი და მიღებული ასლი VPS-ის გარეთ შეინახეთ. იმავე დაზიანებულ დისკზე არსებული მონაცემთა ბაზის ასლი ავარიული აღდგენა არ არის.

SQLite

თუ განთავსება SQLite-ს იყენებს, დაიცავით მონაცემთა ბაზის ფაილი n8n-ის მუდმივი მონაცემების დირექტორიიდან. მოერიდეთ მონაცემთა ბაზის კოპირებას არასაიმედო მდგომარეობაში, როდესაც მასში აქტიურად იწერება.

შესრულებების ისტორია

განსაზღვრეთ, შედის თუ არა შესრულებების ისტორიული მონაცემები თქვენს აღდგენის მიზანში. მათ შეუძლიათ სარეზერვო ასლის მოცულობა მნიშვნელოვნად გაზარდონ, ამიტომ არჩევანი შენახვისა და შესაბამისობის მოთხოვნებმა უნდა განსაზღვროს.

მონაცემთა ბაზა version

ჩაიწერეთ საწყისი განთავსების მონაცემთა ბაზის ძრავა და ვერსია, რათა აღდგენის გარემო თავსებადად მოამზადოთ.

PostgreSQL გააკეთეთcker Compose VPS-ზე. თუ PostgreSQL სერვისის სახელია postgres და მონაცემთა ბაზისა და მომხმარებლის სახელია n8n, შემდეგი ბრძანება ჰოსტზე ქმნის PostgreSQL-ის თანმიმდევრულ custom-format dump-ს. გაშვებამდე შეამოწმეთ თქვენი რეალური Compose ფაილი და საჭიროებისამებრ შეცვალეთ მონაცემთა ბაზის ავტორიზაციის მონაცემები და სერვისის სახელები. pg_dump PostgreSQL-ის მუშაობისას შეუძლია ლოგიკურად თანმიმდევრული snapshot-ის შექმნა; ის არ ქმნის ცალკე .n8n მომხმარებლის საქაღალდის ან გარე ბინარული მონაცემების სარეზერვო ასლს.

# In the Docker Compose project; adapt service, DB and user names
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc > n8n-postgres.dump
test -s n8n-postgres.dump
# Check that the archive has a readable object list
docker compose exec -T postgres pg_restore --list < n8n-postgres.dump

არქივის სიის შემოწმება ფორმატის აშკარა პრობლემებს ავლენს, მაგრამ არ ამტკიცებს, რომ მონაცემები აღდგება. დაშიფრული ასლი სერვერის გარეთ შეინახეთ და აღდგენა პრაქტიკაში გამოცადეთ. მონაცემთა ბაზისთვის სპეციფიკური პარამეტრებისთვის გამოიყენეთ PostgreSQL pg_dump-ის ოფიციალური დოკუმენტაცია.

SQLite გააკეთეთcker-ზე. ნაგულისხმევი SQLite განთავსებისთვის database.sqlite და გენერირებული დაშიფვრის გასაღების კონფიგურაცია მუდმივ .n8n საქაღალდეშია (ჩვეულებრივ mounted მისამართზე /home/node/.n8n). SQLite-ის უბრალო ცოცხალი ასლი თანმიმდევრულად არ ჩათვალოთ. საქაღალდის კოპირებამდე გააჩერეთ n8n და მონაცემთა ბაზაში მწერი სხვა პროცესები, ან როცა გაჩერება შეუძლებელია, გამოიყენეთ SQLite-ის მხარდაჭერილი online უკანup მექანიზმი:

# Only for SQLite and the default /home/node/.n8n mount
# Stop n8n (and any other writers) before copying an SQLite database
docker compose stop n8n
docker compose cp n8n:/home/node/.n8n ./n8n-user-folder-backup
docker compose start n8n

ეს ბრძანებები მხოლოდ ნაჩვენები სერვისისა და ბილიკის მაგალითებია და არა უნივერსალური volume განლაგება. დაკოპირებული საქაღალდე თავდაპირველად ისევ იმავე VPS-ზეა; გადაიტანეთ და დაიცავით სერვერის გარეთ. თუ queue worker-ები ან სხვა მწერი პროცესებია, ისინიც გააჩერეთ და მიჰყევით რეალურ განთავსების დიზაინს. n8n-ის მიმდინარე სრული სარეზერვო ინსტრუქცია SQLite-ის თანმიმდევრულობის მოთხოვნას აღწერს.

ნაგულისხმევი SQLite საქაღალდის სუფთა სამიზნეზე აღდგენა: ჯერ გააჩერეთ n8n სერვისი და მონაცემთა ბაზაში ყველა მწერი პროცესი. როდესაც თავსებადი n8n სერვისის კონტეინერი და მისი სამიზნე volume უკვე არსებობს, დააკოპირეთ სარეზერვოდ შენახული .n8n შიგთავსი უკან იმავე მუდმივ დირექტორიაში. ეს სამიზნე ფაილებს გადაწერს, ამიტომ არ გაუშვათ ინსტანციაზე, სადაც შესანარჩუნებელი მონაცემებია:

# Run only on the intended CLEAN recovery instance
docker compose stop n8n
docker compose cp ./n8n-user-folder-backup/. n8n:/home/node/.n8n/
# Verify ownership and permissions for the n8n container user BEFORE the next command
# Start only after restored files are readable/writable by n8n
docker compose start n8n
# Check logs, restored credentials and workflow triggers

Docker-ს შეუძლია გაჩერებულ კონტეინერებში კოპირება, მაგრამ სამიზნის მფლობელობა შეიძლება ორიგინალისგან განსხვავდებოდეს; გაშვებამდე დარწმუნდით, რომ აღდგენილი კონფიგურაცია და მონაცემთა ბაზის ფაილი n8n პროცესისთვის წაკითხვადი და ჩაწერადია. თუ თქვენი რეალური Compose კონფიგურაცია სხვა ბილიკს ან bind mount-ს იყენებს, კოპირება შესაბამისად მოარგეთ. იხილეთ Docker Compose-ის კოპირების დოკუმენტაცია. მხოლოდ n8n საქაღალდის აღდგენა საკმარისი არ არის იმ განთავსებებისთვის, რომლებიც ცალკე PostgreSQL მონაცემთა ბაზას იყენებს.

კრიტიკული საიდუმლო

დაშიფვრის გასაღები აღდგენის ნაწილია

n8n შენახულ ავტორიზაციის მონაცემებს ინსტანციის დაშიფვრის გასაღებით შიფრავს. მონაცემთა ბაზის ან დაშიფრული ავტორიზაციის მონაცემების ექსპორტი შესაბამისი გასაღების გარეშე შეიძლება აღდგენილ სამუშაო პროცესებს შენახული ავტორიზაციის მონაცემების გამოყენების შესაძლებლობა დაუკარგოს.

თუ N8N_ENCRYPTION_KEY გაქვთ დაყენებული, აღადგინეთ ზუსტად ის საიდუმლო. წინააღმდეგ შემთხვევაში გენერირებული გასაღები ინახება მუდმივ .n8n/config ფაილში: სარეზერვო ასლის შექმნის ან თავიდან აწყობისას ეს კონფიგურაციაც დაიცავით. აღდგენის გასაღებები VPS-ის გარეთ უსაფრთხოდ შეინახეთ. queue mode-ში ყველა main და worker პროცესმა იგივე გასაღები უნდა გამოიყენოს.

გააკეთეთშეინახეთ პროდუქტიულ გარემოში გამოყენებული ზუსტი გასაღების დაცული ასლი.
გააკეთეთავტორიზაციის მონაცემების ტესტირებამდე გადაამოწმეთ, რომ აღდგენის გარემო სწორედ ამ გასაღებს იყენებს.
გააკეთეთ არსერვერის თავიდან აწყობის შემდეგ ახალ გენერირებულ გასაღებს ნუ დაეყრდნობით.
გააკეთეთ არგასაღები საჯარო რეპოზიტორიაში არ ატვირთოთ და დაუცველი სარეზერვო ასლის გვერდით არ შეინახოთ.

ფაილები და ბინარული მონაცემები

მონაცემთა ბაზის სარეზერვო ასლმა შეიძლება სამუშაო პროცესის ყველა დამოკიდებულება არ მოიცვას

მუდმივი .n8n მონაცემები

იპოვეთ და შეინახეთ რეალური .n8n მომხმარებლის საქაღალდე და არა მხოლოდ კონტეინერის იმიჯი. ტიპურ Docker განთავსებაში ის mounted არის /home/node/.n8n-ზე; Docker-ის გარეთ ნაგულისხმევია ~/.n8n. თუ N8N_USER_FOLDER კონფიგურირებულია, n8n .n8n საქაღალდეს მითითებული მშობელი დირექტორიის შიგნით ქმნის. ჩართეთ მისი config key და ყველა ლოკალური SQLite, ბინარული ან ფაილურ სისტემაში შენახული შესრულების მონაცემი, რომელსაც თქვენი ინსტალაცია იყენებს.

Mounted სამუშაო პროცესის ფაილები

If workflows read or write host-mounted directories, უკან those directories up separately. Restoring n8n without them can leave otherwise valid workflows broken.

ბინარული მონაცემები

განსაზღვრეთ საცავის რეჟიმი და აღადგინეთ ყველა გარე დამოკიდებულება. ფაილურ სისტემაზე დაფუძნებული ბინარული ან შესრულების მონაცემები შეიძლება .n8n-ში ან custom დირექტორიაში იყოს; S3/Azure Blob-ს ან სხვა კონფიგურირებულ გარე საცავს საკუთარი აღდგენადი ასლი და წვდომის პარამეტრები სჭირდება. მხოლოდ მონაცემთა ბაზის dump ამ ფაილებს ვერ ჩაანაცვლებს.

Community node-ები

ჩაიწერეთ community პაკეტები და ვერსიები და შექმენით N8N_CUSTOM_EXTENSIONS-ით კონფიგურირებული დამატებითი custom node დირექტორიების სარეზერვო ასლები. ეს დირექტორიები შეიძლება .n8n-ის გარეთ იყოს; მხოლოდ მონაცემთა ბაზისა და მომხმარებლის საქაღალდის აღდგენის შემდეგ custom-node სამუშაო პროცესები შესაძლოა მაინც არ მუშაობდეს.

სერვერისგარე სტრატეგია

იმავე VPS-ზე სარეზერვო ასლი მხოლოდ ლოკალური ასლია

ლოკალური ასლისასარგებლოა სწრაფი rollback-ისთვის, მაგრამ დაუცველია სერვერის დაკარგვის, დისკის დაზიანებისა და დამანგრეველი შეცდომების მიმართ.
სერვერისგარე ასლიმინიმუმ ერთი სარეზერვო ასლი პროდუქტიული VPS-ისგან დამოუკიდებელ საცავში შეინახეთ.
ვერსირებული ასლებიშეინახეთ რამდენიმე აღდგენის წერტილი, რათა დაზიანებამ ან ცუდმა ცვლილებამ ერთადერთი გამოსადეგი სარეზერვო ასლი არ გადაწეროს.
წვდომის კონტროლისარეზერვო ასლები შეიძლება შეიცავდეს ავტორიზაციის მონაცემებს, სამუშაო პროცესის ლოგიკას და სენსიტიურ ბიზნეს-მონაცემებს. შესაბამისად დაშიფრეთ და შეზღუდეთ წვდომა.
მონიტორინგიშეტყობინება მიიღეთ, როდესაც დაგეგმილი სარეზერვო პროცესი ვერ სრულდება ან ახალი აღდგენის წერტილების შექმნას წყვეტს.

გრაფიკი გაზომვადი გახადეთ. ჩაიწერეთ თითოეული წარმატებული სარეზერვო ასლის დრო, გადატანის დასრულება, ფაილის ზომა, საწყისი მონაცემთა ბაზის ვერსია, დაშიფვრის გასაღების აღდგენის მდებარეობა და ბოლო წარმატებული აღდგენის ტესტი. მიიღეთ შეტყობინება დაკარგულ, ჩავარდნილ ან მოულოდნელად ცარიელ ფაილებზე. VPS-ის გარეთ გაგზავნამდე სარეზერვო არქივები დაშიფრეთ და აღდგენის საიდუმლოებზე წვდომა შეზღუდეთ. სხვადასხვა თარიღის აღდგენის წერტილები გიცავთ იმისგან, რომ დაზიანება მხოლოდ მას შემდეგ აღმოაჩინოთ, რაც უახლესმა ასლმა ბოლო ჯანმრთელი ასლი გადაწერა.

მაგალითად, თუ ცვლილებების მაქსიმუმ ექვსსაათიანი დაკარგვა მისაღებია, წარმატებული ექვსსაათიანი სარეზერვო გრაფიკი მხოლოდ საწყისი წერტილია და არა გარანტია: ჩავარდნილმა დავალებებმა და სერვერისგარე რეპლიკაციის დაგვიანებამ რეალური დანაკარგი შეიძლება გაზარდოს. შენახვისა და აღდგენის სიხშირე თქვენს RPO/RTO-სა და მონაცემთა მოთხოვნებს მოარგეთ და არა უნივერსალურ 7- ან 30-დღიან პოლიტიკას.

აღდგენის თანმიმდევრობა

აღადგინეთ კონტროლირებადი თანმიმდევრობით

1 · მომზადებამოამზადეთ თავსებადი სერვერი, მონაცემთა ბაზა და container/runtime გარემო.
2 · საიდუმლოებების აღდგენაუსაფრთხოდ დააკონფიგურირეთ საწყისი n8n დაშიფვრის გასაღები და საჭირო განთავსების საიდუმლოებები.
3 · მონაცემთა ბაზის აღდგენააღადგინეთ PostgreSQL ან SQLite და გადაამოწმეთ, რომ n8n მოსალოდნელ მონაცემებს უკავშირდება.
4 · ფაილების აღდგენააღადგინეთ მუდმივი დირექტორიები, ბინარული მონაცემები და mounted სამუშაო პროცესის რესურსები.
5 · n8n-ის გაშვებაგაუშვით აპლიკაცია მოსალოდნელი hostname-ით, მონაცემთა ბაზითა და გარემოს კონფიგურაციით.
6 · შემოწმებადაადასტურეთ, რომ მომხმარებლები, სამუშაო პროცესები და ავტორიზაციის მონაცემები იტვირთება, შემდეგ გაუშვით წარმომადგენლობითი სამუშაო პროცესები და webhook მარშრუტები.

PostgreSQL ავარიული აღდგენის მაგალითი: ცალკე, სუფთა აღდგენის სამიზნეზე რომელსაც უკვე აქვს მონაცემთა ბაზის სწორი role და ცარიელი n8n მონაცემთა ბაზა, გაუშვით მხოლოდ PostgreSQL. იმპორტამდე დაელოდეთ, სანამ მზად იქნება: `docker compose up -d` შეიძლება დასრულდეს მაშინ, როცა PostgreSQL ჯერ კიდევ ინიციალიზდება, ამიტომ შემდგომი `pg_restore` შეიძლება ჩავარდეს. მაგალითი თანამედროვე Compose ინსტალაციაზე იყენებს `--wait`-ს და დამოუკიდებლად ამოწმებს `pg_isready`-ს. საიმედო ლოდინისთვის დააკონფიგურირეთ შესაბამისი PostgreSQL healthcheck ან გაგრძელებამდე აშკარად დაადასტურეთ მზადყოფნა. ეს ბრძანება შევსებულ პროდუქტიულ მონაცემთა ბაზაზე არ გაუშვათ და n8n არ ჩართოთ მანამ, სანამ მონაცემთა ბაზა და შესაბამისი `.n8n` გასაღები/მონაცემები არ აღდგება.

# RESTORE ONLY TO A FRESH, EMPTY TARGET DATABASE
# Adapt Postgres Compose service, database and user names
docker compose up -d --wait postgres
docker compose exec -T postgres pg_isready -U n8n -d n8n
docker compose exec -T postgres pg_restore --exit-on-error --no-owner --no-acl -U n8n -d n8n < n8n-postgres.dump

სამიზნეს უნდა ჰქონდეს თავსებადი PostgreSQL ვერსია, role პრივილეგიები, გაფართოებები და საწყისი n8n კონფიგურაცია. აღადგინეთ .n8n სწორ persistent volume-ში ან bind mount-ში თქვენი სარეზერვო მექანიზმით, მფლობელობისა და permissions-ის შენარჩუნებით. აღადგინეთ გარე ბინარული ფაილები, custom extensions, Compose და secrets კონფიგურაცია, შემდეგ გაუშვით n8n თავსებად ვერსიაზე და შეამოწმეთ logs. მხოლოდ მონაცემთა ბაზის აღდგენა გასაღებს არ აღადგენს: PostgreSQL განთავსება გასაღებს .n8n/config-ში ინახავს, თუ პირდაპირ არ გაქვთ კონფიგურირებული N8N_ENCRYPTION_KEY. იხილეთ pg_restore reference და n8n-ის სრული ინსტანციის აღდგენის თანმიმდევრობა.

ჩაიწერეთ, რამდენ ხანს გრძელდება აღდგენა და რომელი ხელით შესასრულებელი ნაბიჯები რჩება. ასე სავარაუდო სარეზერვო ასლი რეალურ საოპერაციო აღდგენის პროცედურად იქცევა.

შემოწმებული აღდგენის ტესტი: SQLite და PostgreSQL

ტესტის გარემო: n8n 2.42.5 იზოლირებულ Docker კონტეინერებში, დროებით GitHub Actions runner-ზე, სინთეზური ორნოდიანი სამუშაო პროცესის გამოყენებით. ეს შემოწმებები ჩატარდა 2026 წლის 8 ოქტომბერს, და არა მომხმარებლის ან პროდუქტიულ n8n სერვერზე.

SQLite: PASSშემოვიტანეთ სატესტო სამუშაო პროცესი, გავიტანეთ, გავაჩერეთ ყველა მწერი პროცესი, დავაარქივეთ SQLite-ზე დაფუძნებული persistent .n8n საქაღალდე და მისი გენერირებული დაშიფვრის გასაღები, აღვადგინეთ სუფთა volume-ში, გავუშვით n8n, შემდეგ ხელახლა გავიტანეთ და შევასრულეთ აღდგენილი სამუშაო პროცესი.
PostgreSQL: PASSშემოვიტანეთ იგივე სატესტო სამუშაო პროცესი, შევქმენით და შევამოწმეთ custom-format pg_dump, აღვადგინეთ pg_restore-ის გამოყენებით ახალ ცარიელ PostgreSQL მონაცემთა ბაზაში, აღვადგინეთ ცალკე .n8n საქაღალდე, შემდეგ ხელახლა გავიტანეთ და შევასრულეთ აღდგენილი სამუშაო პროცესი.
რას ადასტურებს PASSგამოცდილმა სარეზერვო გზებმა შეინარჩუნა ეს სამუშაო პროცესი, მისი ორი node და მათი კავშირები და აღდგენის შემდეგ შესრულების საშუალება მისცა. ეს გამეორებადი ფუნქციური სატესტო შემოწმებებია და არა დატვირთვის benchmark-ები.
What was არ testedრეალური ავტორიზაციის მონაცემების გაშიფვრა და ავტორიზაცია, პროდუქტიული webhooks, queue-mode worker-ები და Redis, S3/Azure ბინარული საცავი, custom node-ები, მომხმარებლის/პროექტის წვდომა ან ცოცხალი პროდუქტიული ინსტანციის აღდგენა. თითოეული რეალურად გამოყენებული დამოკიდებულებისთვის ცალკე ტესტი ჩაატარეთ.

როგორ გაიმეოროთ: გამოიყენეთ დროებითი n8n ინსტალაცია, შექმენით უსაფრთხო ორნოდიანი სამუშაო პროცესი, გააკეთეთ შესაბამისი მონაცემთა ბაზისა და მუდმივი საქაღალდის სარეზერვო ასლი, აღადგინეთ სუფთა volume-ში ან მონაცემთა ბაზაში და შემდეგ გადაამოწმეთ აღდგენილი სამუშაო პროცესის node-ები, კავშირები და რეალური შესრულება. პროდუქტიულ სისტემაზე ავარიული აღდგენის დადასტურებამდე ასევე შეამოწმეთ დაშიფრული ავტორიზაციის მონაცემები, webhooks და გარე ფაილები.

აღდგენის ტესტის მიღების საკონტროლო სია: გამოიყენეთ იზოლირებული დომენი/გარემო; შეამოწმეთ, რომ მომხმარებლები და სამუშაო პროცესები არსებობს, ერთი არსებული დაშიფრული ავტორიზაციის მონაცემი ხელახალი შეყვანის გარეშე ავტორიზდება, პროდუქტიული webhook იძახებს საჭირო აღდგენილ სამუშაო პროცესს, mounted ფაილები და ბინარული დანართები კვლავ იკითხება და საჭირო community node-ებთან ინტეგრაციები იტვირთება. დაადასტურეთ სარეზერვო ასლის ასაკი, გაზომილი downtime და სერვერისგარე ხელმისაწვდომობა. თუ რომელიმე აუცილებელი შემოწმება ვერ გაივლის, ეს აღდგენის წერტილი მონიშნეთ როგორც დაუდასტურებელი ნაცვლად იმისა, რომ სარეზერვო ასლი სრულად დადასტურებულად ჩათვალოთ.

CLI სარეზერვო ასლის შეზღუდვები

ზუსტად იცოდეთ, რას არ აღადგენს სამუშაო პროცესებისა და ავტორიზაციის მონაცემების ექსპორტები

CLI ექსპორტები სრული ინსტანციის სარეზერვო ასლი არ არის

სამუშაო პროცესებისა და ავტორიზაციის მონაცემების სარეზერვო ექსპორტები არ შეიცავს მომხმარებლებსა და როლებს, შესრულების ისტორიასა და logs-ს, ცვლადებს ან ინსტანციის პარამეტრებს, მაგალითად დაშიფვრის გასაღებს.

სუფთა ინსტანციის აღდგენას owner სჭირდება

სუფთა ინსტანციაზე ავტორიზაციის მონაცემების იმპორტამდე დაასრულეთ owner-ის საწყისი დაყენება. მრავალმომხმარებლიან ან პროექტის აღდგენას შეიძლება სწორი მომხმარებლის ან პროექტის მინიჭებაც დასჭირდეს.

იმპორტირებულ ID-ებს არსებული ობიექტების გადაწერა შეუძლია

სამუშაო პროცესებისა და ავტორიზაციის მონაცემების ექსპორტები ინარჩუნებს საწყის ID-ებს. იმ ინსტანციაში იმპორტმა, სადაც იგივე ID-ები უკვე არსებობს, არსებული ობიექტები შეიძლება ჩაანაცვლოს.

იმპორტირებული workflows გააზრებულად გამოაქვეყნეთ

CLI იმპორტი ჩვეულებრივ სამუშაო პროცესებს არააქტიურს ტოვებს. n8n 2.x-ზე შეამოწმეთ თითოეული იმპორტირებული სამუშაო პროცესის გამოქვეყნების მდგომარეობა და გამოაქვეყნეთ მხოლოდ ისინი, რომელთა გაშვებაც გსურთ; თვითჰოსტირებული Server CLI ასევე მხარს უჭერს `n8n publish:workflow --id=YOUR_WORKFLOW_ID` ბრძანებას. როდესაც n8n მუშაობს, Server CLI-ის გამოქვეყნება/გამოუქვეყნებლობის მდგომარეობის ცვლილებები ძალაში მხოლოდ n8n-ის გადატვირთვის შემდეგ შედის. დაგეგმილი ტრიგერებისა და პროდუქტიული ვებჰუკების შემოწმებამდე ან ტრაფიკის გადართვამდე გადატვირთეთ.

მასობრივი ექსპორტის მაგალითი Docker Compose-ისთვის: თუ თქვენი n8n სერვისის სახელია n8n, შეგიძლიათ ქვემოთ მოცემული ოფიციალური CLI სარეზერვო ბრძანებები გაუშვათ. output ბილიკი განზრახ არის მის mounted persistent .n8n დირექტორიაში, რადგან კონტეინერის შიგნით შემთხვევითი დირექტორიები მისი ხელახლა შექმნისას შეიძლება გაქრეს. დაადასტურეთ, რომ დირექტორია n8n container user-ისთვის ჩაწერადია. სამუშაო პროცესისა და ავტორიზაციის მონაცემების JSON შეინახეთ ცალკე დირექტორიებში—n8n აღწერს იმპორტის პრობლემას, როდესაც ორივე ტიპი ერთ დირექტორიაშია.

n8n 2.x: draft და გამოქვეყნებული სარეზერვო ასლები: ჩვეულებრივი --backup workflow ექსპორტი მიმდინარე draft-ებს ინახავს; ისინი შეიძლება პროდუქტიულ გარემოში გამოქვეყნებული ვერსიებისგან განსხვავდებოდეს. კონკრეტული workflow-ის რეალურად გამოქვეყნებული ვერსიის შესანარჩუნებლად ცალკე გაიტანეთ შემდეგის გამოყენებით docker compose exec -T n8n n8n export:workflow --id=WORKFLOW_ID --published --output=/home/node/.n8n/backups/published-workflow.json, მას შემდეგ, რაც დარწმუნდებით, რომ output საქაღალდე არსებობს და ჩაწერადია. CLI-ს შეუძლია ისტორიული ვერსიის ექსპორტიც შემდეგის გამოყენებით --version=VERSION_ID. ეს ასლები სრული სარეზერვო ასლის გვერდით სერვერის გარეთ შეინახეთ; ნუ ჩათვლით, რომ draft JSON ცოცხალ published მდგომარეობას ასახავს.

# Execute from your Docker Compose project; the n8n service must exist
# Keep workflow and credential backups in DIFFERENT folders
docker compose exec -T n8n n8n export:workflow --backup --output=/home/node/.n8n/backups/workflows/
docker compose exec -T n8n n8n export:credentials --backup --output=/home/node/.n8n/backups/credentials/
# Copy the saved export directories OUT of the container to the host
mkdir -p ~/n8n-recovery
docker compose cp n8n:/home/node/.n8n/backups ~/n8n-recovery/cli

დაკოპირებული ~/n8n-recovery/cli დირექტორია კვლავ VPS-ზეა, სანამ დაცულ, დამოუკიდებელ სარეზერვო საცავში არ გადაიტანთ. ავტორიზაციის მონაცემების ექსპორტი ნაგულისხმევად დაშიფრულია და იმპორტისას შესაბამისი დაშიფვრის გასაღები სჭირდება. `--decrypted` გამოიყენეთ მხოლოდ მკაცრად კონტროლირებული მიგრაციისას, რადგან ის საიდუმლოებებს plaintext-ში წერს. სენსიტიური სამუშაო პროცესის ლოგიკის ან ავტორიზაციის მონაცემების შემცველი ექსპორტები საჯარო GitHub რეპოზიტორიაში არასდროს ატვირთოთ. ზოგი მესამე მხარის GitHub credential-backup შაბლონი განზრახ ექსპორტავს გაშიფრულ საიდუმლოებებს; private repository მხოლოდ წვდომის შეზღუდვაა და არა დაშიფვრა. შეამოწმეთ თითოეული შაბლონის რეალური export პარამეტრები და storage permissions, სერვერის გარეთ გადატანამდე საიდუმლოებები დაშიფრეთ და შეცვალეთ ნებისმიერი credential, რომელიც უნებლიე plaintext ატვირთვით გამჟღავნდა.

მასობრივი იმპორტის მაგალითი: სუფთა სამიზნეზე დაასრულეთ owner-ის დაყენება, მიუთითეთ საწყისი დაშიფვრის გასაღები და დარწმუნდით, რომ შენახული სარეზერვო ფაილები აღდგენის VPS-ზე ხელმისაწვდომია. შემდეგი ბრძანება ქმნის სამიზნე საქაღალდეს და აკოპირებს `workflows/` და `credentials/` ქვესაქაღალდეებს ჰოსტიდან n8n კონტეინერში; თუ თქვენი Docker volume განლაგება განსხვავდება, ბილიკები მოარგეთ:

# Run only on the intended CLEAN recovery instance
docker compose exec -T n8n mkdir -p /home/node/.n8n/backups
docker compose cp ~/n8n-recovery/cli/. n8n:/home/node/.n8n/backups/

შეამოწმეთ ფაილების ownership და წვდომა n8n container user-ისთვის. შევსებულ პროდუქტიულ ინსტანციაზე ვერიფიცირებული rollback-ის გარეშე იმპორტი არ გააკეთოთ: სამუშაო პროცესისა და ავტორიზაციის მონაცემების ID-ებს არსებული ჩანაწერების გადაწერა შეუძლია. შემდეგ გაუშვით:

# After fresh-instance owner setup AND providing the correct key
# Copy saved cli/ contents back under the target n8n service's .n8n/backups/

იმპორტირებულ ID-ებს არსებული სამუშაო პროცესების ან ავტორიზაციის მონაცემების ჩანაცვლება შეუძლია; dry run-ებისთვის გამოიყენეთ იზოლირებული სატესტო ინსტანცია და შემდეგ გადაამოწმეთ ავტორიზაციის მონაცემები და activation/publishing მდგომარეობა. n8n 2.x-ში JSON draft-ის აღდგენა თავისთავად არ ამტკიცებს, რომ სამუშაო პროცესი გამოქვეყნებულია და დაგეგმილი triggers-ის გაშვება შეუძლია. იმპორტის უსაფრთხოება: non-multi-main n8n ინსტანციაზე ადრე აქტიურმა cron triggers-მა CLI იმპორტის შემდეგ შეიძლება მუშაობა გააგრძელოს ინსტანციის გადატვირთვამდე. აღდგენილი jobs-ის ჩართვამდე პროდუქტიული triggers გააჩერეთ ან იზოლირება გაუკეთეთ და n8n გადატვირთეთ; გადაამოწმეთ, რომ დუბლირებული შესრულება არ ხდება. CLI ექსპორტები არ არ შეიცავს საწყის მომხმარებლებს, შესრულების ჟურნალებს, ინსტანციის ცვლადებს ან დაშიფვრის გასაღებს. `--backup` იყენებს `--all --pretty --separate` პარამეტრებს და არა „სრულ ინსტანციას“. წყაროები: n8n-ის მიმდინარე ოფიციალური სარეზერვო/აღდგენის გზამკვლევი და n8n CLI ბრძანებების დოკუმენტაცია.

მასობრივი აღდგენა GitHub ან Google Drive შაბლონებიდან: ეს ალტერნატივაა მხოლოდ სამუშაო პროცესის JSON-ისთვის და არა ინსტანციის მონაცემთა ბაზისთვის, მომხმარებლებისთვის, დაშიფრული ავტორიზაციის მონაცემების მნიშვნელობებისთვის ან დაშიფვრის გასაღებისთვის. API-ზე დაფუძნებული შაბლონის გაშვებამდე გადაამოწმეთ მისი n8n API და საცავის წვდომის უფლებები, არჩეული სარეზერვო ვერსია და სამიზნე ინსტანცია, აახლებს თუ არა შესაბამის ID-ებს და აღადგენს თუ არა წაშლილ სამუშაო პროცესებს, ასევე რას აკეთებს სამუშაო პროცესის გამოქვეყნებასთან. ყველა შაბლონი არ აღადგენს სამიზნეში დაკარგულ ID-ს; ავტომატურ აღდგენაზე დაყრდნობამდე ეს სცენარი იზოლირებულად გამოცადეთ.

FAQ

n8n-ის სარეზერვო ასლი და აღდგენა: გავრცელებული კითხვები

Is exporting workflows enough to უკან up n8n?

არა. სამუშაო პროცესების ექსპორტები სასარგებლო ლოგიკური ასლებია, მაგრამ სრულ აღდგენას ასევე შეიძლება დასჭირდეს ავტორიზაციის მონაცემები, შესაბამისი დაშიფვრის გასაღები, მონაცემთა ბაზის მდგომარეობა, მუდმივი ფაილები და ბინარული მონაცემების საცავი.

მჭირდება n8n დაშიფვრის გასაღები, თუ მონაცემთა ბაზა მაქვს?

დიახ, თუ გსურთ მონაცემთა ბაზაში შენახული დაშიფრული ავტორიზაციის მონაცემები კვლავ გამოყენებადი იყოს. საწყისი გასაღები უსაფრთხოდ შეინახეთ.

PostgreSQL-ის სარეზერვო ასლი შევქმნა თუ სამუშაო პროცესები და ავტორიზაციის მონაცემები გავიტანო?

ავარიული აღდგენისთვის დაიცავით მონაცემთა ბაზა და დაშიფვრის გასაღები. ლოგიკური ექსპორტები სასარგებლოა როგორც მიგრაციისა და შერჩევითი აღდგენის დამატებითი ფენა და არა ინსტანციის ყველა ნაწილის შემცვლელი.

Can a VPS snapshot be my მხოლოდ უკანup?

უმჯობესია ის ერთ-ერთ აღდგენის ფენად განიხილოთ. დამოუკიდებელი სერვერისგარე სარეზერვო ასლი შეინახეთ, რათა პროვაიდერის, ანგარიშის, სერვერის ან snapshot-ის პრობლემამ ყველა აღდგენის წერტილი ერთდროულად არ გააქროს.

How do I know my უკანup works?

აღადგინეთ სუფთა სატესტო გარემოში, გადაამოწმეთ ავტორიზაციის მონაცემების გაშიფვრა და გაუშვით წარმომადგენლობითი სამუშაო პროცესები. მხოლოდ წარმატებული სარეზერვო დავალება აღდგენადობას არ ამტკიცებს.

შეიცავს GitHub ან Google Drive სამუშაო პროცესის სარეზერვო ასლები შენახულ ავტორიზაციის საიდუმლოებებს?

მხოლოდ სამუშაო პროცესის JSON სარეზერვო ასლები არ შეიცავს n8n credential store-ში მართულ საიდუმლო მნიშვნელობებს ან ინსტანციის დაშიფვრის გასაღებს. თუმცა ექსპორტირებულ JSON-ში შეიძლება გამოჩნდეს ავტორიზაციის მონაცემების სახელები და ID-ები და node პარამეტრებში პირდაპირ შეყვანილი საიდუმლოებები, მაგალითად authentication headers. ატვირთვამდე ან გაზიარებამდე შეამოწმეთ და დაიცავით ექსპორტირებული JSON. სრული აღდგენისთვის შექმენით მონაცემთა ბაზისა და საწყისი გასაღების სარეზერვო ასლი ან გამოიყენეთ მხარდაჭერილი დაშიფრული credential CLI ექსპორტები გამოცდილი აღდგენით. მხოლოდ სამუშაო პროცესზე დაფუძნებული GitHub ან Google Drive შაბლონი სრული ავარიული აღდგენა არ არის.

RTO არის მაქსიმალურად დასაშვები გათიშვის დრო. გაზომეთ იგი სუფთა აღდგენის ტესტში, საიდუმლოებების მიღების, გარე ფაილების აღდგენის, ავტორიზაციის მონაცემების ხელახლა შემოწმებისა და აღდგენილი სამუშაო პროცესების გამოქვეყნების ჩათვლით და არა მხოლოდ კონტეინერის გაშვებით.
