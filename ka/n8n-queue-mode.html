მასშტაბირება

n8n Queue Mode

Queue mode სამუშაო პროცესის შესრულებას n8n-ის მთავარი პროცესისგან აცალკევებს. მთავარი ინსტანცია იღებს triggers-ს და ქმნის შესრულებებს, Redis რიგს კოორდინირებს, worker-ები ასრულებს jobs-ს, ხოლო PostgreSQL ინახავს საერთო workflow და execution მონაცემებს.

სწრაფი გადაწყვეტილება

რეალურად გჭირდებათ queue mode?

დარჩით ჩვეულებრივ რეჟიმში, როდესაც

ერთი ინსტანცია პიკურ შესრულებებს კომფორტულად უმკლავდება და CPU, RAM და execution latency სტაბილურია. Queue mode ამატებს კომპონენტებს, რომლებიც ჯერ არ გჭირდებათ.

განიხილეთ queue mode, როდესაც

მუდმივი პარალელური შესრულებები კონკურენციას ქმნის, დატვირთვისას execution latency იზრდება ან რამდენიმე worker-ის გაშვებით შესრულების სიმძლავრის დამატება გჭირდებათ.

ჯერ ვერტიკალურად გაზარდეთ, როდესაც

bottleneck უბრალოდ არასაკმარისი CPU ან RAM-ია და ერთი უფრო დიდი ინსტანცია დატვირთვას ჯერ კიდევ გამართულად უმკლავდება.

არქიტექტურის შეცვლამდე გაზომეთ

გადასვლის დასასაბუთებლად გამოიყენეთ პიკური concurrency, CPU, RAM, execution duration, queue depth და მონაცემთა ბაზის დატვირთვა.

არქიტექტურა

როგორ მუშაობს n8n queue mode

1 · Mainიღებს timers-ს, webhooks-სა და workflow requests-ს და თვითონ პროდუქტიული შესრულების ნაცვლად execution-ს ქმნის.
2 · Redisმუშაობს message broker-ად. ინახავს მოლოდინში მყოფ execution messages-ს, რათა შემდეგმა თავისუფალმა worker-მა job აიღოს.
3 · Workerიღებს execution ID-ს, საერთო მონაცემთა ბაზიდან ტვირთავს workflow მონაცემებს, ასრულებს workflow-ს და შედეგს უკან წერს.
4 · PostgreSQLუზრუნველყოფს საერთო მუდმივ workflow და execution მონაცემებს. განაწილებული queue mode SQLite-ზე მხარდაჭერილი არ არის.

ძირითადი მოთხოვნები

რა სჭირდება ყველა queue-mode deployment-ს

Redis

ყველა main და worker პროცესს სჭირდება საიმედო წვდომა Redis სერვისზე, რომელიც რიგის კოორდინაციისთვის გამოიყენება.

PostgreSQL

Main და worker-ებმა მონაცემთა ბაზა უნდა გაიზიაროს. Queue mode განაწილებული არქიტექტურაა და SQLite-ზე არ უნდა აიგოს.

შესაბამისი n8n კონფიგურაცია

Main და worker-ებმა queue mode უნდა გამოიყენოს და გაიზიაროს Redis-ზე, PostgreSQL-ზე და დაშიფრულ credentials-ზე წვდომისთვის საჭირო კონფიგურაცია.

Worker-ის სიმძლავრე

Worker-ებს საკმარისი CPU და RAM სჭირდება იმ workflows-ისთვის, რომლებსაც ასრულებს. პროცესების დამატება თითოეული execution-ის რესურსის ღირებულებას არ აუქმებს.

ჩართეთ queue mode არსებულ თვითჰოსტირებულ სტეკზე. First confirm that the n8n main service and every worker can reach the same PostgreSQL database and Redis over a private network. Set EXECUTIONS_MODE=queue on both main and workers, and supply QUEUE_BULL_REDIS_HOST=redis and QUEUE_BULL_REDIS_PORT=6379 when redis is your actual Compose service name. Use DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres and matching DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER and DB_POSTGRESDB_PASSWORD on every process; replace the example service names with yours. Provide the exact existing N8N_ENCRYPTION_KEY to all of them. Never publish Redis or PostgreSQL host ports merely to connect containers on the same Compose network.

გაუშვით executor და არა მეორე editor. Add an n8n worker service using the same pinned n8n image version and shared settings as main, but run it with the worker command. If you named that service n8n-worker, start it with docker compose up -d n8n-worker. After confirming actual execution on one worker, you can use docker compose up -d --scale n8n-worker=2 to start a second worker from that service. These are additions to an არსებულ სწორად კონფიგურირებულ Compose stack, not a standalone installation file; keep your existing persistent volumes, HTTPS proxy, secrets and backups.

Queue-mode Compose fragment არსებული სტეკისთვის. Merge the example below into your current compose.yaml; it is არ არის a complete stand-alone deployment. It assumes you already have persistent, private postgres and n8n services, an existing N8N_VERSION pin in your environment and your own protected POSTGRES_PASSWORD and original N8N_ENCRYPTION_KEY. Match its names, volumes, database and n8n version to the existing project. Add the queue-mode Redis settings and EXECUTIONS_MODE=queue to the existing main service too, as described above.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

No host port is published for Redis or the worker in this fragment. Redis append-only persistence is an extra recovery layer, არ არის a substitute for off-server backups. Keep the existing HTTPS and authentication configuration unchanged. For Code nodes requiring external task runners, configure the runner processes for your worker deployment separately; queue mode itself does not replace task runners.

არსებულ SQLite ინსტანციას გარდაქმნით? Do not simply change DB_TYPE and start against an empty PostgreSQL database: doing so does not migrate the old workflows and credentials. Before any cutover, back up the source database, persistent .n8n directory and original encryption key; use a supported n8n export/import or migration procedure, then verify workflows and encrypted credentials on a separate target. Keep the original files for rollback and use the Backup & Restore guide linked below for recovery preparation. Never delete database.sqlite as a shortcut.

WORKER პარალელურობა

Worker-ები მასშტაბირდება როგორც რაოდენობით, ისე თითო worker-ზე jobs-ის რაოდენობით

თითო worker-ს შეუძლია რამდენიმე job პარალელურად დაამუშაოს. n8n-ის მიმდინარე default worker concurrency არის 10 და დოკუმენტაცია 5 ან მეტ concurrency-ს ურჩევს. ძალიან დაბალმა concurrency-მ ბევრ worker-თან ერთად შეიძლება ზედმეტი database connections შექმნას და database connection pool ამოწუროს.

გაზარდეთ concurrency, როდესაც

worker-ს თავისუფალი CPU და RAM აქვს და workflows ძირითადად გარე სერვისებს ელოდება, ნაცვლად compute ან memory-ის გაჯერებისა.

დაამატეთ worker-ები, როდესაც

ერთი worker process bottleneck ხდება და database, Redis და infrastructure-ს მეტი parallel execution-ის რესურსი აქვს.

შეამცირეთ concurrency, როდესაც

ცალკეული workflows memory-heavy ან CPU-heavy არის და parallel jobs ქმნის contention-ს, OOM pressure-ს ან არასტაბილურ execution times-ს.

დააკვირდით PostgreSQL-ს

მეტი worker და მეტი concurrency ზრდის database activity-ს. execution capacity-ის გაზრდამ database capacity-ის გარეშე bottleneck შეიძლება უბრალოდ სხვა ადგილას გადაიტანოს.

იცოდეთ, რეალურად რომელი concurrency limit მოქმედებს. A worker can be started using n8n worker --concurrency=5, or the equivalent worker command in your Compose service. If N8N_CONCURRENCY_PRODUCTION_LIMIT is explicitly set to a value other than -1, that setting takes precedence in queue mode; otherwise n8n uses the worker's --concurrency value or its default of 10. Do not multiply worker count by a nominal default and call it guaranteed throughput: actual capacity depends on job duration, CPU, memory, external APIs and PostgreSQL connections.

WEBHOOKS

Queue mode-ს შეუძლია execution handoff latency დაამატოს

Main ან webhook process იღებს HTTP request-ს, მაგრამ workflow execution-ს worker ასრულებს. Redis-ის გავლით ეს handoff გარკვეულ overhead-ს ამატებს. latency-sensitive webhooks-ისთვის end-to-end response time გაზომეთ და ნუ ჩათვლით, რომ მეტი worker ყველა request-ს ავტომატურად აჩქარებს.

მიღებაMain/webhook process იღებს request-ს.
რიგიExecution გადაეცემა Redis-ს.
შესრულებათავისუფალი worker ასრულებს workflow-ს.
პასუხისაჭიროებისას შედეგი queue path-ით უკან ბრუნდება.

Webhook traffic სწორ process-ზე მიმართეთ. With dedicated n8n webhook processors behind a reverse proxy or load balancer, route production paths /webhook/* and /webhook-waiting/* to the webhook processors; keep /webhook-test/*, editor and API requests on main. Do not put main into the production webhook load-balancing pool unless you deliberately accept that added workload. A Respond to Webhook workflow may keep the client waiting until the worker finishes and returns its response, so queue mode is not a promise of instant HTTP responses or zero timeouts. Test the actual external callback and response behavior before switching traffic.

ბინარული მონაცემები

Shared storage არ გამოგრჩეთ

Filesystem შეზღუდვა

Queue mode არ უჭერს მხარს filesystem binary-data storage-ს როგორც shared persistence model-ს distributed workers-ისთვის.

გარე ბინარული საცავი

როდესაც workflows-მა binary data distributed workers-ს შორის უნდა შეინარჩუნოს, გამოიყენეთ storage design, რომელზეც ყველა საჭირო instance-ს წვდომა აქვს, მაგალითად მხარდაჭერილი external object storage.

დიდი webhook responses

Worker-ებიდან webhook responses receiving process-ისკენ უკან მიდის. დიდ response bodies-ს შეუძლია Redis memory pressure გაზარდოს და გააზრებული response-storage configuration მოითხოვოს.

Worker-ების განაწილებამდე დაგეგმეთ

Workload, რომელიც ძლიერაა დამოკიდებული local files-ზე, shared persistence-ისთვის თავიდან უნდა დაიგეგმოს worker-ების სხვადასხვა machines-ზე განაწილებამდე.

დიდი webhook response-ის ზღვარი. Current n8n documentation gives N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX a default of 64 MiB for a worker's response sent back through the queue. Redis can hold several copies in flight, so budget roughly 1.5 times the response size in Redis memory per concurrent large response. Without offloading, an oversized response fails instead of becoming magically faster by adding workers.

ვერსიისა და ლიცენზიის ლიმიტები. From n8n 2.34.0, workers can use N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true to offload oversized webhook response bodies to readable shared binary storage, but first upgrade ყველა main და webhook processor to 2.34.0 or later. The selected N8N_DEFAULT_BINARY_DATA_MODE must actually store data and be readable by every participating process. External S3 and Azure binary storage require a valid self-hosted Business or Enterprise license; do not assume Community Edition can enable them. The database binary mode can offload an oversized response without paid external storage, but the main instance loads the whole stored body into memory and database storage has its own file-size limit. For response-body offload specifically, n8n also describes a shared filesystem option when every instance mounts the same disk, but explicitly does not recommend that arrangement. Do not mistake this special offload path for support of filesystem-based persistent binary data in a distributed queue-mode deployment. Check your edition, version and storage configuration before enabling offload.

მონიტორინგი

გაიგეთ, ეხმარება თუ არა რიგი

Queue depth

რიგი, რომელიც worker-ების დამუშავებაზე სწრაფად იზრდება, მიუთითებს არასაკმარის execution capacity-ზე ან downstream bottleneck-ზე.

Worker CPU და RAM

გაზომეთ saturation და memory peaks თითო worker-ზე. Idle worker-ები მზარდ რიგთან ერთად სხვა constraint-ზე მიუთითებს.

Execution latency

აკონტროლეთ execution-ის შექმნასა და რეალურ დაწყებას შორის delay და არა მხოლოდ workflow runtime.

Health checks

Worker health endpoints-ს შეუძლია აჩვენოს, worker მუშაობს თუ არა და მზადაა თუ არა database და Redis connections.

Execution worker-ზე გადაამოწმეთ და არა მხოლოდ green container-ზე. With a correctly configured Compose stack, check docker compose ps and docker compose logs --tail=100 n8n-worker (replace the service name if different). Run a harmless გამოქვეყნებული პროდუქტიული workflow using a scheduled trigger or test webhook, then match its execution in n8n's Executions view to actual worker processing in the worker logs. An editor that opens successfully, a running Redis container or a queued execution alone does არ არის prove a worker has performed the job.

შეამოწმეთ dependencies და readiness. With default example service names, docker compose exec -T redis redis-cli ping should receive PONG when Redis authentication permits it, and docker compose exec -T postgres pg_isready -U n8n -d n8n checks PostgreSQL readiness (adapt credentials and service names). Enable QUEUE_HEALTH_CHECK_ACTIVE=true on a worker when you need its private /healthz and /healthz/readiness endpoints; the readiness endpoint checks Redis/database connectivity. Do not expose those worker endpoints publicly just to monitor them.

Manual runs სხვა ტესტია. By default OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, so manually running a workflow in the editor can execute on main even when queue mode is correctly configured. Set it to true only if you intend to send manual executions to workers and have checked the change in a staging environment. Queue-mode workers are also distinct from n8n external task runners, which have separate configuration requirements for Code-node execution.

ერთ ჯერზე ერთი bottleneck გაზარდეთ

ეტაპი 1ერთი n8n ინსტანცია PostgreSQL-ით; გაზომეთ peak CPU, RAM და concurrency.
ეტაპი 2გაზარდეთ VPS რესურსები, როდესაც vertical scaling ჯერ კიდევ გამართულად აგვარებს გაზომილ bottleneck-ს.
ეტაპი 3დაამატეთ Redis და worker-ები, როდესაც მუდმივი parallel demand distributed execution-ს ამართლებს.
ეტაპი 4დაამატეთ worker-ები ან მოარგეთ worker concurrency PostgreSQL-ის, Redis-ისა და execution latency-ის მონიტორინგით.
ეტაპი 5კომპონენტები სხვადასხვა servers-ზე მხოლოდ მაშინ გაყავით, როცა capacity, availability ან operational requirements დამატებით complexity-ს ამართლებს.
აირჩიეთ მეტი VPS სიმძლავრე, როდესაც scaling ამას მოითხოვს

პარტნიორული ბმული: შეძენიდან შესაძლოა მივიღოთ საკომისიო.

HIGH AVAILABILITY-ის საზღვარი

Queue mode executions-ს მასშტაბირებს, მაგრამ main process-ს ავტომატურად highly available არ ხდის

გააზიარეთ encryption key

Every worker must use the same N8N_ENCRYPTION_KEY as the main instance so workers can decrypt credentials required by workflow executions.

ვერსიები შესაბამისობაში შეინახეთ

Main, webhook და worker processes ერთსა და იმავე n8n version-ზე უნდა მუშაობდეს. Mixed versions rolling changes-ისას incompatible behavior-ს ქმნის.

Webhook processors ცალკე scaling layer-ია

როდესაც შემომავალი webhook volume bottleneck ხდება, dedicated webhook processors შეიძლება load balancer-ის უკან განთავსდეს, ხოლო worker-ებმა execution დაამუშაოს. ეს layer არ დაამატოთ, თუ გაზომილი request volume ამას არ ამართლებს.

Multi-main სხვა ფუნქციაა

High availability-ისთვის რამდენიმე main process-ის გაშვება ჩვეულებრივი queue mode-ის იგივე არ არის. n8n ამჟამად multi-main-ს self-hosted Enterprise feature-ად აღწერს დამატებითი load-balancer და session requirements-ით.

Queue-mode არქიტექტურისა და კონფიგურაციის ოფიციალური დოკუმენტაცია

FAQ

n8n queue mode: გავრცელებული კითხვები

სჭირდება n8n queue mode-ს Redis?

დიახ. Redis არის message broker, რომელიც main instance-სა და worker-ებს შორის pending executions-ს კოორდინირებს.

შეუძლია queue mode-ს SQLite-ის გამოყენება?

არა, distributed queue-mode architecture-ისთვის. Main და worker-ებს shared database access სჭირდება და n8n ამ setup-ის მონაცემთა ბაზად PostgreSQL-ს აღწერს.

რამდენი worker გავუშვა?

უნივერსალური რაოდენობა არ არსებობს. დაიწყეთ გაზომილი concurrency-ითა და worker utilization-ით, შემდეგ capacity დაამატეთ PostgreSQL-ის, Redis-ის, CPU-ს, RAM-ისა და queue depth-ის მონიტორინგით.

რა არის n8n worker concurrency?

ეს არის jobs-ის რაოდენობა, რომელსაც worker პარალელურად ამუშავებს. მიმდინარე default არის 10 და n8n ურჩევს worker concurrency 5 ან მეტს, ნაცვლად ბევრი low-concurrency worker-ის შექმნისა.

უნდა ჩავრთო queue mode მცირე VPS-ზე?

მხოლოდ მაშინ, როცა workload ამას ამართლებს. მცირე deployment, რომელიც ერთ ინსტანციად კომფორტულად მუშაობს, ჩვეულებრივ უფრო მარტივია Redis-ისა და ცალკე worker-ების გარეშე.
