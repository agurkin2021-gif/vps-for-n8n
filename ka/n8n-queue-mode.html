მასშტაბირება

n8n Queue Mode

Queue mode სამუშაო პროცესის შესრულებას n8n-ის მთავარი პროცესისგან აცალკევებს. მთავარი ინსტანცია იღებს triggers-ს და ქმნის შესრულებებს, Redis რიგს კოორდინირებს, worker-ები ასრულებს jobs-ს, ხოლო PostgreSQL ინახავს საერთო workflow და execution მონაცემებს.

სწრაფი გადაწყვეტილება

რეალურად გჭირდებათ queue mode?

დარჩით ჩვეულებრივ რეჟიმში, როდესაც

ერთი ინსტანცია პიკურ შესრულებებს კომფორტულად უმკლავდება და CPU, RAM და execution latency სტაბილურია. Queue mode ამატებს კომპონენტებს, რომლებიც ჯერ არ გჭირდებათ.

განიხილეთ queue mode, როდესაც

მუდმივი პარალელური შესრულებები კონკურენციას ქმნის, დატვირთვისას execution latency იზრდება ან რამდენიმე worker-ის გაშვებით შესრულების სიმძლავრის დამატება გჭირდებათ.

ჯერ ვერტიკალურად გაზარდეთ, როდესაც

bottleneck უბრალოდ არასაკმარისი CPU ან RAM-ია და ერთი უფრო დიდი ინსტანცია დატვირთვას ჯერ კიდევ გამართულად უმკლავდება.

არქიტექტურის შეცვლამდე გაზომეთ

გადასვლის დასასაბუთებლად გამოიყენეთ პიკური concurrency, CPU, RAM, execution duration, queue depth და მონაცემთა ბაზის დატვირთვა.

არქიტექტურა

როგორ მუშაობს n8n queue mode

1 · Mainიღებს timers-ს, webhooks-სა და workflow requests-ს და თვითონ პროდუქტიული შესრულების ნაცვლად execution-ს ქმნის.
2 · Redisმუშაობს message broker-ად. ინახავს მოლოდინში მყოფ execution messages-ს, რათა შემდეგმა თავისუფალმა worker-მა job აიღოს.
3 · Workerიღებს execution ID-ს, საერთო მონაცემთა ბაზიდან ტვირთავს workflow მონაცემებს, ასრულებს workflow-ს და შედეგს უკან წერს.
4 · PostgreSQLუზრუნველყოფს საერთო მუდმივ workflow და execution მონაცემებს. განაწილებული queue mode SQLite-ზე მხარდაჭერილი არ არის.

ძირითადი მოთხოვნები

რა სჭირდება ყველა queue-mode deployment-ს

Redis

ყველა main და worker პროცესს სჭირდება საიმედო წვდომა Redis სერვისზე, რომელიც რიგის კოორდინაციისთვის გამოიყენება.

PostgreSQL

Main და worker-ებმა მონაცემთა ბაზა უნდა გაიზიაროს. Queue mode განაწილებული არქიტექტურაა და SQLite-ზე არ უნდა აიგოს.

შესაბამისი n8n კონფიგურაცია

Main და worker-ებმა queue mode უნდა გამოიყენოს და გაიზიაროს Redis-ზე, PostgreSQL-ზე და დაშიფრულ credentials-ზე წვდომისთვის საჭირო კონფიგურაცია.

Worker-ის სიმძლავრე

Worker-ებს საკმარისი CPU და RAM სჭირდება იმ workflows-ისთვის, რომლებსაც ასრულებს. პროცესების დამატება თითოეული execution-ის რესურსის ღირებულებას არ აუქმებს.

ჩართეთ queue mode არსებულ თვითჰოსტირებულ სტეკზე. ჯერ დაადასტურეთ, რომ n8n main service-ს და ყველა worker-ს ერთსა და იმავე PostgreSQL მონაცემთა ბაზასა და Redis-ზე კერძო ქსელით წვდომა აქვს. EXECUTIONS_MODE=queue დააყენეთ როგორც main-ზე, ისე worker-ებზე და მიუთითეთ QUEUE_BULL_REDIS_HOST=redis და QUEUE_BULL_REDIS_PORT=6379, როცა redis თქვენი რეალური Compose service name-ია. ყველა პროცესზე გამოიყენეთ DB_TYPE=postgresdb, DB_POSTGRESDB_HOST=postgres და შესაბამისი DB_POSTGRESDB_DATABASE, DB_POSTGRESDB_USER და DB_POSTGRESDB_PASSWORD; მაგალითის service names თქვენი სახელებით ჩაანაცვლეთ. ყველა მათგანს ზუსტად არსებული N8N_ENCRYPTION_KEY მიაწოდეთ. Redis-ის ან PostgreSQL-ის host ports არასდროს გამოაქვეყნოთ მხოლოდ იმისთვის, რომ იმავე Compose ქსელში კონტეინერები დააკავშიროთ.

გაუშვით executor და არა მეორე editor. დაამატეთ n8n worker service იგივე pinned n8n image version-ითა და main-ის საერთო settings-ით, მაგრამ გაუშვით worker ბრძანებით. თუ სერვისს n8n-worker დაარქვით, გაუშვით docker compose up -d n8n-worker. ერთ worker-ზე რეალური execution-ის დადასტურების შემდეგ შეგიძლიათ გამოიყენოთ docker compose up -d --scale n8n-worker=2, რათა ამ სერვისიდან მეორე worker გაუშვათ. ეს არის დამატება არსებულ სწორად კონფიგურირებულ Compose stack-ზე და არა დამოუკიდებელ ინსტალაციის ფაილად; შეინარჩუნეთ არსებული მუდმივი volumes, HTTPS proxy, საიდუმლოებები და სარეზერვო ასლები.

Queue-mode Compose fragment არსებული სტეკისთვის. ქვემოთ მოცემული მაგალითი ჩასვით თქვენს მიმდინარე compose.yaml-ში; ეს არ არის სრული დამოუკიდებელი deployment. ვარაუდობს, რომ უკვე გაქვთ persistent, private postgres და n8n services, environment-ში არსებული N8N_VERSION pin, საკუთარი დაცული POSTGRES_PASSWORD და საწყისი N8N_ENCRYPTION_KEY. მისი სახელები, volumes, database და n8n version არსებულ პროექტს შეუსაბამეთ. Queue-mode Redis settings და EXECUTIONS_MODE=queue არსებულ main service-საც დაამატეთ, როგორც ზემოთაა აღწერილი.

# Merge with the existing services; do not replace your full Compose file.
services:
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    restart: unless-stopped
    volumes:
      - redis_data:/data
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:${N8N_VERSION}
    command: worker --concurrency=5
    restart: unless-stopped
    environment:
      EXECUTIONS_MODE: queue
      QUEUE_BULL_REDIS_HOST: redis
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    depends_on:
      - redis
      - postgres
volumes:
  redis_data:

ამ fragment-ში Redis-ის ან worker-ის host port გამოქვეყნებული არ არის. Redis append-only persistence აღდგენის დამატებითი ფენაა და არ არის off-server backups-ის შემცვლელი. არსებული HTTPS და authentication configuration უცვლელი დატოვეთ. Code node-ებისთვის, რომლებსაც external task runners სჭირდება, runner processes worker deployment-ისთვის ცალკე დააკონფიგურირეთ; queue mode თავად task runners-ს არ ანაცვლებს.

არსებულ SQLite ინსტანციას გარდაქმნით? უბრალოდ DB_TYPE არ შეცვალოთ და ცარიელ PostgreSQL მონაცემთა ბაზაზე არ გაუშვათ: ეს ძველ workflows-სა და credentials-ს არ გადაიტანს. ნებისმიერ cutover-მდე შექმენით source database-ის, persistent .n8n დირექტორიისა და საწყისი encryption key-ის backup; გამოიყენეთ მხარდაჭერილი n8n export/import ან migration procedure, შემდეგ ცალკე target-ზე გადაამოწმეთ workflows და encrypted credentials. ორიგინალი files rollback-ისთვის შეინახეთ და recovery preparation-ისთვის ქვემოთ მიბმული Backup & Restore guide გამოიყენეთ. database.sqlite shortcut-ის სახით არასდროს წაშალოთ.

WORKER პარალელურობა

Worker-ები მასშტაბირდება როგორც რაოდენობით, ისე თითო worker-ზე jobs-ის რაოდენობით

თითო worker-ს შეუძლია რამდენიმე job პარალელურად დაამუშაოს. n8n-ის მიმდინარე default worker concurrency არის 10 და დოკუმენტაცია 5 ან მეტ concurrency-ს ურჩევს. ძალიან დაბალმა concurrency-მ ბევრ worker-თან ერთად შეიძლება ზედმეტი database connections შექმნას და database connection pool ამოწუროს.

გაზარდეთ concurrency, როდესაც

worker-ს თავისუფალი CPU და RAM აქვს და workflows ძირითადად გარე სერვისებს ელოდება, ნაცვლად compute ან memory-ის გაჯერებისა.

დაამატეთ worker-ები, როდესაც

ერთი worker process bottleneck ხდება და მონაცემთა ბაზას, Redis-სა და ინფრასტრუქტურას მეტი პარალელური execution-ის რესურსი აქვს.

შეამცირეთ concurrency, როდესაც

ცალკეული workflows მეხსიერებაზე ან CPU-ზე მძიმეა და parallel jobs ქმნის contention-ს, OOM pressure-ს ან არასტაბილურ execution times-ს.

დააკვირდით PostgreSQL-ს

მეტი worker და მეტი concurrency ზრდის database activity-ს. execution capacity-ის გაზრდამ database capacity-ის გარეშე bottleneck შეიძლება უბრალოდ სხვა ადგილას გადაიტანოს.

იცოდეთ, რეალურად რომელი concurrency limit მოქმედებს. Worker-ის გაშვება შეიძლება n8n worker --concurrency=5-ით ან შესაბამისი worker command-ით თქვენს Compose service-ში. თუ N8N_CONCURRENCY_PRODUCTION_LIMIT პირდაპირ დაყენებულია -1-ისგან განსხვავებულ მნიშვნელობაზე, ეს setting queue mode-ში პრიორიტეტულია; წინააღმდეგ შემთხვევაში n8n იყენებს worker-ის --concurrency მნიშვნელობას ან default 10-ს. Worker count ნუ გაამრავლებთ nominal default-ზე და guaranteed throughput-ს ნუ უწოდებთ: რეალური capacity დამოკიდებულია job duration-ზე, CPU-ზე, memory-ზე, external APIs-ზე და PostgreSQL connections-ზე.

WEBHOOKS

Queue mode-ს შეუძლია execution handoff-ის დაყოვნება დაამატოს

Main ან webhook process იღებს HTTP request-ს, მაგრამ workflow execution-ს worker ასრულებს. Redis-ის გავლით ეს handoff გარკვეულ overhead-ს ამატებს. latency-sensitive webhooks-ისთვის end-to-end response time გაზომეთ და ნუ ჩათვლით, რომ მეტი worker ყველა request-ს ავტომატურად აჩქარებს.

მიღებაMain/webhook process იღებს მოთხოვნას.
რიგიშესრულება გადაეცემა Redis-ს.
შესრულებათავისუფალი worker ასრულებს workflow-ს.
პასუხისაჭიროებისას შედეგი queue path-ით უკან ბრუნდება.

Webhook ტრაფიკი სწორ პროცესზე მიმართეთ. ცალკე n8n webhook პროცესორები reverse proxy-ის ან load balancer-ის უკან მოათავსეთ და პროდუქტიული მარშრუტები /webhook/* და /webhook-waiting/* webhook პროცესორებზე მიმართეთ; /webhook-test/*, editor და API მოთხოვნები მთავარ პროცესზე დატოვეთ. მთავარი პროცესი პროდუქტიული webhook load-balancing pool-ში არ ჩასვათ, თუ დამატებით დატვირთვას გააზრებულად არ იღებთ. Respond to Webhook workflow შეიძლება კლიენტს ალოდინოს, სანამ worker დასრულდება და პასუხს დააბრუნებს, ამიტომ queue mode მყისიერი HTTP პასუხების ან ნულოვანი timeout-ების დაპირება არ არის. ტრაფიკის გადართვამდე გამოცადეთ რეალური გარე callback და პასუხის ქცევა.

ბინარული მონაცემები

Shared storage არ გამოგრჩეთ

Filesystem შეზღუდვა

Queue mode არ უჭერს მხარს filesystem binary-data storage-ს, როგორც განაწილებული worker-ების საერთო შენახვის მოდელს.

გარე ბინარული საცავი

როდესაც workflows-მა binary data distributed workers-ს შორის უნდა შეინარჩუნოს, გამოიყენეთ storage design, რომელზეც ყველა საჭირო instance-ს წვდომა აქვს, მაგალითად მხარდაჭერილი external object storage.

დიდი webhook responses

Worker-ებიდან webhook responses მიმღები process-ისკენ უკან მიდის. დიდ response bodies-ს შეუძლია Redis memory pressure გაზარდოს და გააზრებული response-storage configuration მოითხოვოს.

Worker-ების განაწილებამდე დაგეგმეთ

Workload, რომელიც ძლიერაა დამოკიდებული local files-ზე, shared persistence-ისთვის თავიდან უნდა დაიგეგმოს worker-ების სხვადასხვა machines-ზე განაწილებამდე.

დიდი webhook response-ის ზღვარი. n8n-ის მიმდინარე დოკუმენტაციაში N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX-ის default მნიშვნელობაა 64 MiB worker-ის response-ისთვის, რომელიც queue-ით უკან იგზავნება. Redis-ს შეუძლია რამდენიმე copy ერთდროულად შეინახოს, ამიტომ თითო concurrent large response-ზე Redis memory-ში დაახლოებით response size-ის 1.5-ჯერ მეტი დაგეგმეთ. Offloading-ის გარეშე oversized response ჩავარდება და მეტი worker-ის დამატებით ავტომატურად არ აჩქარდება.

ვერსიისა და ლიცენზიის ლიმიტები. n8n 2.34.0-იდან worker-ებს შეუძლია გამოიყენოს N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED=true, რათა ზედმეტად დიდი webhook პასუხის body საერთო წაკითხვად ბინარულ საცავში გადაიტანოს, მაგრამ ჯერ ყველა მთავარი და webhook პროცესორი 2.34.0 ან ახალ ვერსიაზე განაახლეთ. არჩეულმა N8N_DEFAULT_BINARY_DATA_MODE-მა რეალურად უნდა შეინახოს მონაცემები და ყველა მონაწილე პროცესისთვის წაკითხვადი იყოს. გარე S3 და Azure ბინარული საცავი მოქმედ self-hosted Business or Enterprise ლიცენზიას მოითხოვს; ნუ ჩათვლით, რომ Community Edition-ს შეუძლია მათი ჩართვა. database binary mode-ს შეუძლია ზედმეტად დიდი პასუხის paid external storage-ის გარეშე offload, მაგრამ მთავარი ინსტანცია მთელ შენახულ body-ს მეხსიერებაში ტვირთავს და database storage-ს საკუთარი file-size limit აქვს. კონკრეტულად response-body offload-ისთვის n8n ასევე აღწერს საერთო filesystem ვარიანტს, როდესაც ყველა instance ერთსა და იმავე disk-ს mount-ავს, თუმცა ამ arrangement-ს პირდაპირ არ ურჩევს. ეს სპეციალური offload path არ აურიოთ filesystem-based persistent binary data-ის მხარდაჭერაში distributed queue-mode deployment-ზე. Offload-ის ჩართვამდე გადაამოწმეთ edition, version და storage configuration.

მონიტორინგი

გაიგეთ, ეხმარება თუ არა რიგი

Queue depth

რიგი, რომელიც worker-ების დამუშავებაზე სწრაფად იზრდება, მიუთითებს არასაკმარის execution capacity-ზე ან downstream bottleneck-ზე.

Worker CPU და RAM

გაზომეთ saturation და memory peaks თითო worker-ზე. Idle worker-ები მზარდ რიგთან ერთად სხვა constraint-ზე მიუთითებს.

Execution latency

აკონტროლეთ execution-ის შექმნასა და რეალურ დაწყებას შორის delay და არა მხოლოდ workflow runtime.

Health checks

Worker health endpoints-ს შეუძლია აჩვენოს, worker მუშაობს თუ არა და მზადაა თუ არა database და Redis connections.

შესრულება worker-ზე გადაამოწმეთ და არა მხოლოდ მწვანე სტატუსის მქონე კონტეინერზე. სწორად კონფიგურირებულ Compose stack-ზე შეამოწმეთ docker compose ps და docker compose logs --tail=100 n8n-worker (თუ service name განსხვავდება, ჩაანაცვლეთ). გაუშვით უსაფრთხო გამოქვეყნებული პროდუქტიული workflow დაგეგმილი trigger-ის ან test webhook-ის გამოყენებით, შემდეგ n8n-ის Executions view-ში მისი შესრულება შეუსაბამეთ worker logs-ში რეალურ worker processing-ს. მხოლოდ წარმატებით გახსნილი editor, მოქმედი Redis container ან რიგში ჩასმული execution არ ამტკიცებს, რომ worker-მა job შეასრულა.

შეამოწმეთ დამოკიდებულებები და მზადყოფნა. მაგალითის default service names-ით docker compose exec -T redis redis-cli ping-მა უნდა მიიღოს PONG, როცა Redis authentication ამის საშუალებას იძლევა, ხოლო docker compose exec -T postgres pg_isready -U n8n -d n8n ამოწმებს PostgreSQL readiness-ს (credentials და service names მოარგეთ). Worker-ზე ჩართეთ QUEUE_HEALTH_CHECK_ACTIVE=true, როცა მისი private /healthz და /healthz/readiness endpoints გჭირდებათ; readiness endpoint ამოწმებს Redis/database connectivity-ს. მხოლოდ მონიტორინგისთვის worker endpoints საჯაროდ არ გახსნათ.

Manual runs სხვა ტესტია. ნაგულისხმევად OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS=false, ამიტომ workflow-ის manual გაშვება editor-ში შეიძლება main-ზე შესრულდეს მაშინაც, როცა queue mode სწორადაა კონფიგურირებული. true მხოლოდ მაშინ დააყენეთ, თუ manual executions worker-ებზე გაგზავნა გსურთ და ცვლილება staging environment-ში გადაამოწმეთ. Queue-mode worker-ები ასევე განსხვავდება n8n external task runners-ისგან, რომლებსაც Code-node execution-ისთვის ცალკე configuration requirements აქვს.

მასშტაბირების გზა

ერთ ჯერზე ერთი bottleneck გაზარდეთ

ეტაპი 1ერთი n8n ინსტანცია PostgreSQL-ით; გაზომეთ peak CPU, RAM და concurrency.
ეტაპი 2გაზარდეთ VPS რესურსები, როდესაც vertical scaling ჯერ კიდევ გამართულად აგვარებს გაზომილ bottleneck-ს.
ეტაპი 3დაამატეთ Redis და worker-ები, როდესაც მუდმივი parallel demand distributed execution-ს ამართლებს.
ეტაპი 4დაამატეთ worker-ები ან მოარგეთ worker concurrency PostgreSQL-ის, Redis-ისა და execution latency-ის მონიტორინგით.
ეტაპი 5კომპონენტები სხვადასხვა servers-ზე მხოლოდ მაშინ გაყავით, როცა capacity, availability ან operational requirements დამატებით complexity-ს ამართლებს.
აირჩიეთ მეტი VPS სიმძლავრე, როდესაც scaling ამას მოითხოვს

პარტნიორული ბმული: შეძენიდან შესაძლოა მივიღოთ საკომისიო.

მაღალი ხელმისაწვდომობის საზღვარი

Queue mode executions-ს მასშტაბირებს, მაგრამ main process-ს ავტომატურად highly available არ ხდის

გააზიარეთ დაშიფვრის გასაღები

ყველა worker-მა უნდა გამოიყენოს იგივე N8N_ENCRYPTION_KEY, რასაც main instance იყენებს, რათა worker-ებმა workflow executions-ისთვის საჭირო credentials გაშიფროს.

ვერსიები შესაბამისობაში შეინახეთ

Main, webhook და worker processes ერთსა და იმავე n8n version-ზე უნდა მუშაობდეს. შერეულმა ვერსიებმა rolling changes-ისას შეუთავსებელი ქცევა შეიძლება შექმნას.

Webhook processors ცალკე მასშტაბირების ფენაა

როდესაც შემომავალი webhook volume bottleneck ხდება, dedicated webhook processors შეიძლება load balancer-ის უკან განთავსდეს, ხოლო worker-ებმა execution დაამუშაოს. ეს layer არ დაამატოთ, თუ გაზომილი request volume ამას არ ამართლებს.

Multi-main სხვა ფუნქციაა

High availability-ისთვის რამდენიმე main process-ის გაშვება ჩვეულებრივი queue mode-ის იგივე არ არის. n8n ამჟამად multi-main-ს self-hosted Enterprise feature-ად აღწერს დამატებითი load-balancer და session requirements-ით.

Queue-mode არქიტექტურისა და კონფიგურაციის ოფიციალური დოკუმენტაცია

FAQ

n8n queue mode: გავრცელებული კითხვები

სჭირდება n8n-ის queue mode-ს Redis?

დიახ. Redis არის message broker, რომელიც main instance-სა და worker-ებს შორის pending executions-ს კოორდინირებს.

შეუძლია queue mode-ს SQLite-ის გამოყენება?

არა, distributed queue-mode architecture-ისთვის. Main და worker-ებს საერთო მონაცემთა ბაზაზე წვდომა სჭირდება და n8n ამ setup-ის მონაცემთა ბაზად PostgreSQL-ს აღწერს.

რამდენი worker გავუშვა?

უნივერსალური რაოდენობა არ არსებობს. დაიწყეთ გაზომილი concurrency-ითა და worker utilization-ით, შემდეგ capacity დაამატეთ PostgreSQL-ის, Redis-ის, CPU-ს, RAM-ისა და queue depth-ის მონიტორინგით.

რა არის n8n worker-ის პარალელურობა?

ეს არის jobs-ის რაოდენობა, რომელსაც worker პარალელურად ამუშავებს. მიმდინარე default არის 10 და n8n ურჩევს worker concurrency 5 ან მეტს, ნაცვლად ბევრი low-concurrency worker-ის შექმნისა.

უნდა ჩავრთო queue mode მცირე VPS-ზე?

მხოლოდ მაშინ, როცა workload ამას ამართლებს. მცირე deployment, რომელიც ერთ ინსტანციად კომფორტულად მუშაობს, ჩვეულებრივ უფრო მარტივია Redis-ისა და ცალკე worker-ების გარეშე.
