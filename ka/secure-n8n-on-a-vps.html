Secure n8n on a VPS

n8n-ის VPS-ზე დასაცავად n8n (5678), PostgreSQL (5432) და სურვილისამებრ Redis (6379) საჯარო ინტერნეტიდან დახურული დატოვეთ; გამოიყენეთ HTTPS reverse proxy, SSH გასაღებები და MFA, შეინახეთ დაშიფვრის გასაღები, webhooks-ზე ჩართეთ ავტორიზაცია, შეზღუდეთ სარისკო workflow შესაძლებლობები და ჩაატარეთ განთავსებული ინსტანციის აუდიტი. რედაქტორი საჯარო webhook მარშრუტებისგან ცალკე დაიცავით. მხოლოდ HTTPS დაკავშირებულ სერვისებს სრულად არ იცავს.

აირჩიეთ VPS n8n-ისთვის

პარტნიორული ბმული: შეძენიდან შესაძლოა მივიღოთ საკომისიო.

სწრაფი საკონტროლო სია

უსაფრთხოების მინიმალური დონე საჯაროდ გახსნამდე

დაიწყეთ ხელმისაწვდომი პორტების, HTTPS-ის, შემოწმებული ადმინისტრაციული წვდომის, MFA-სა და შენახული ავტორიზაციის მონაცემების დაცვით. თითოეული შემომავალი webhook ავთენტიფიცირეთ მანამდე, სანამ ის სენსიტიურ სამუშაოს გაუშვებს. წვდომის კონტროლის შეცვლის შემდეგ გადაამოწმეთ, რომ საჭირო რედაქტორები და გარე ინტეგრაციები კვლავ მუშაობს, შემდეგ გაუშვით n8n-ის უსაფრთხოების აუდიტი.

მხოლოდ HTTPS

n8n მოათავსეთ სწორად კონფიგურირებული TLS reverse proxy-ის უკან და რედაქტორისა და webhooks-ისთვის მუდმივად გამოიყენეთ საჯარო HTTPS URL.

მინიმალური ღია პორტები

გახსენით მხოლოდ საჯარო ტრაფიკისთვის საჭირო პორტები. PostgreSQL, Redis და აპლიკაციის შიდა პორტები საჯარო ინტერნეტიდან დახურული დატოვეთ.

გაამაგრეთ SSH

გამოიყენეთ გასაღებებზე დაფუძნებული ადმინისტრირება, შეზღუდეთ შესვლის უფლება და ოპერაციული სისტემა განახლებულ მდგომარეობაში შეინახეთ.

დაიცავით ავტორიზაციის მონაცემები

n8n-ის დაშიფვრის გასაღები უცვლელი და საიდუმლო შეინახეთ. გარემოს ფაილები, მონაცემთა ბაზაზე წვდომა და სარეზერვო ასლები სენსიტიურ რესურსებად განიხილეთ.

ქსელის საზღვარი

Reverse proxy, HTTPS და სანდო სათაურები

TLS termination

HTTPS-ის termination-ისთვის გამოიყენეთ reverse proxy, მაგალითად Nginx, Caddy ან Traefik. ჩვეულებრივი HTTP გადაამისამართეთ და n8n აპლიკაციის პორტი პირდაპირ არ გამოიტანოთ, როდესაც შესვლის წერტილად proxy გამოიყენება.

Proxy-ის კონფიგურაცია

როდესაც n8n reverse proxy-ის უკან მუშაობს, სწორად დააკონფიგურირეთ proxy hop count და გადასცით forwarded headers, რომლებიც n8n-ს საწყისი კლიენტის მოთხოვნის აღსადგენად სჭირდება.

უსაფრთხო cookies

რედაქტორი HTTPS-ით მიაწოდეთ, რათა ავტორიზაციის cookies უსაფრთხო დარჩეს. დაზიანებული TLS კონფიგურაციის გამო cookie უსაფრთხოება არ შეასუსტოთ.

Webhook URL

საჯარო webhook URL დააყენეთ გარედან ხელმისაწვდომ HTTPS hostname-ზე, რათა გენერირებული webhook endpoints შიდა კონტეინერზე ან HTTP მისამართზე არ მიუთითებდეს.

რედაქტორი კერძო დატოვეთ webhooks-ის დარღვევის გარეშე. შესაძლებლობის შემთხვევაში მართვის წვდომა შეზღუდეთ VPN-ით, სანდო IP პოლიტიკით ან ავტორიზებული proxy-ით. საჯარო webhook მიმღებები და OAuth callback მარშრუტები შეიძლება ხელმისაწვდომი უნდა დარჩეს; proxy წესის მკაცრად ამოქმედებამდე გამოცადეთ როგორც სანდო რედაქტორის შესვლა, ისე რეალური გარე callback. კლიენტის მისამართის headers მიიღეთ მხოლოდ სანდო proxy-ებიდან და არა თვითნებური მოთხოვნის headers-იდან.

Webhook გამომძახებლების ავთენტიფიკაცია: Webhook node-ში აირჩიეთ Basic, Header ან JWT authentication ნაცვლად None-ისა, თუ გამომგზავნი ამას მხარს უჭერს. გამოიყენეთ მისი IP(s) Allowlist პარამეტრი შესაბამის შემთხვევებში და გადაამოწმეთ პროვაიდერის ხელმოწერები, სადაც ინტეგრაცია signed requests-ს მხარს უჭერს. რთულად გამოსაცნობი URL საკმარისი ავტორიზაცია არ არის. საჭიროებისას proxy-ზე rate limit-ები გამოიყენეთ და დარწმუნდით, რომ ვალიდური პიკური ტრაფიკი არ იბლოკება. Webhook ავტორიზაციის ოფიციალური ვარიანტები.

VPS-ის გამაგრება

შეამცირეთ სერვერის attack surface

Firewall

ნაგულისხმევად აკრძალეთ არასასურველი შემომავალი ტრაფიკი და დაუშვით მხოლოდ აუცილებელი სერვისები. მონაცემთა ბაზისა და Redis-ის პორტები ჩვეულებრივ კერძო/ლოკალურ ქსელებში უნდა დარჩეს.

SSH

პაროლების ნაცვლად უპირატესობა SSH გასაღებებს მიანიჭეთ, გამორთეთ არასაჭირო შესვლის გზები და შეზღუდეთ ადმინისტრაციული წვდომა. Root-ის ეკვივალენტური წვდომა მკაცრად უნდა კონტროლდებოდეს.

OS განახლებები

განაახლეთ Linux host და container runtime. აპლიკაციის გამაგრება ღია ან მოძველებულ ოპერაციულ სისტემას ვერ ანაცვლებს.

კონტეინერების ხელმისაწვდომობა

გამოაქვეყნეთ მხოლოდ ის პორტები, რომლებსაც host-ზე წვდომა სჭირდება. შიდა სერვისებმა საჯარო interfaces-ის ნაცვლად private Docker ქსელებით უნდა იკომუნიკაციოს.

Firewall ან SSH პარამეტრების შეცვლამდე შეამოწმეთ: მოსმენილ პორტებს შეამოწმეთ sudo ss -lntp, Docker publishing — docker compose ps პროექტის დირექტორიიდან, ხოლო host firewall policy — sudo ufw status verbose თუ UFW გამოიყენება. პაროლით წვდომის გამორთვამდე ცალკე სესიაში გადაამოწმეთ რეალური SSH პორტი და გასაღებით წარმატებული შესვლა. Docker-ის გამოქვეყნებულ პორტებს UFW წესების გვერდის ავლა შეუძლია; მხოლოდ firewall status არ ამტკიცებს, რომ 5678 პორტი კერძოა. შეამოწმეთ რეალური გარე ხელმისაწვდომობა. Docker/UFW თავისებურება.

Ubuntu-ს ავტომატური უსაფრთხოების განახლებები გადაამოწმეთ და ნუ ჩათვლით, რომ თავისით მუშაობს: შეამოწმეთ apt-config dump APT::Periodic::Unattended-Upgrade და log /var/log/unattended-upgrades/unattended-upgrades.log. თუ unattended security upgrades გამორთულია, sudo dpkg-reდააკონფიგურირეთ unattended-upgrades გთავაზობთ მხარდაჭერილ კონფიგურაციის დიალოგს. სამუშაო VPS-ზე ჩართვამდე შეაფასეთ reboot-ისა და service restart-ის ქცევა. Ubuntu APT განახლებები არ აახლებს ავტომატურად n8n Docker image-ს ან ყველა მესამე მხარის პროგრამულ რეპოზიტორიას. Ubuntu-ს ავტომატური განახლებების დოკუმენტაცია.

სურვილისამებრ SSH brute-force მონიტორინგი: Fail2Ban-ს შეუძლია განმეორებადი წარუმატებელი SSH შესვლების აღმოჩენა. თუ SSH-სთვის დაყენებული და კონფიგურირებულია, jail გადაამოწმეთ და დარწმუნდით, რომ ის რეალურ SSH ავტორიზაციის log-ს ან journal-ს კითხულობს და კონფიგურირებულ პორტს ემთხვევა. ეს SSH გასაღებებსა და ქსელის შეზღუდვებს ავსებს და არ ანაცვლებს. არსებული წვდომის შემოწმების გარეშე ფიქსირებული SSH პორტი ან ban rule არ გადაიტანოთ. იხილეთ Ubuntu SSH hardening გზამკვლევი.

მონაცემთა ბაზა და REDIS

Backend სერვისები კერძო დატოვეთ

ტიპურ Docker Compose კონფიგურაციაში PostgreSQL და queue-mode Redis შესაბამისი კონტეინერებისთვის კერძო ქსელით უნდა იყოს ხელმისაწვდომი და არა host-published პორტებით. გადაამოწმეთ, რომ 5432 და 6379 საჯაროდ არ არის გამოქვეყნებული; ცალკე შეამოწმეთ VPS/cloud firewall exposure. ქსელის პოლიტიკა least-privilege მონაცემთა ბაზის ავტორიზაციის მონაცემებს არ ანაცვლებს.

PostgreSQLდააკავშირეთ private interface-ზე ან container network-ზე, თუ დისტანციური წვდომა პირდაპირ არ არის საჭირო და დამოუკიდებლად დაცული.
RedisQueue-mode Redis ინფრასტრუქტურაა და არა საჯარო endpoint. ქსელის წვდომა მხოლოდ იმ n8n კომპონენტებით შეზღუდეთ, რომლებსაც ის სჭირდება.
ავტორიზაციის მონაცემებიგამოიყენეთ ცალკე მონაცემთა ბაზის ავტორიზაციის მონაცემები მხოლოდ საჭირო უფლებებით და source control-ის გარეთ დაიცავით.
ტრანსპორტიროდესაც მონაცემთა ბაზის ტრაფიკი არასანდო ქსელებს კვეთს, გამოიყენეთ შესაბამისი დაშიფრული ტრანსპორტი და ნუ დაეყრდნობით მხოლოდ აპლიკაციის დონეზე ავტორიზაციის მონაცემების დაშიფვრას.

N8N საიდუმლოებები

დაიცავით დაშიფვრის გასაღები და ავტორიზაციის საზღვარი

დაშიფვრის გასაღები

n8n შენახულ ავტორიზაციის მონაცემებს საკუთარი დაშიფვრის გასაღებით შიფრავს. იგივე გასაღები შეინარჩუნეთ restart-ებსა და worker-ებზე და ჩვეულებრივი აპლიკაციის კონტენტისგან ცალკე დაიცავით.

გარემოს საიდუმლოებები

პაროლები, tokens ან დაშიფვრის გასაღები საჯარო რეპოზიტორიაში არ ატვირთოთ. შეზღუდეთ წვდომა environment files-სა და deployment secrets-ზე.

მომხმარებლის წვდომა

რედაქტორზე წვდომა მხოლოდ სანდო მომხმარებლებს მიეცით. Workflows-ს შეუძლია სენსიტიურ სისტემებთან დაკავშირება, საიდუმლოებების დამუშავება ან ძლიერი node-ების შესრულება.

ავტორიზაციის მონაცემების ფარგლები

შესაძლებლობის შემთხვევაში გამოიყენეთ ვიწრო უფლებების service accounts და API tokens. კომპრომეტირებულ workflow-ს ავტომატურად ფართო წვდომა არ უნდა გადაეცეს დაუკავშირებელ სისტემებზე.

გადასამოწმებელი n8n კონფიგურაცია: N8N_BLOCK_ENV_ACCESS_IN_NODE=true კრძალავს Code-node-ისა და expression-ის წვდომას გარემოს მნიშვნელობებზე; settings ფაილზე მხოლოდ owner-ის უფლებებს ითხოვს. გასაღები მუდმივად შეინარჩუნეთ და უსაფრთხო სარეზერვო ასლი შექმენით: n8n-ს შეუძლია პირველი გაშვებისას შემთხვევითი გასაღების შექმნა, მაგრამ მისი დაკარგვა არსებულ დაშიფრულ ავტორიზაციის მონაცემებს გამოუსადეგარს გახდის. პროდუქტიული დაშიფვრის გასაღები დაუფიქრებლად არ შეცვალოთ; გამოიყენეთ ოფიციალურად მხარდაჭერილი rotation პროცედურა. გარემოზე წვდომის დაბლოკვამ არსებული ინტეგრაციები შეიძლება დააზიანოს, ამიტომ პროდუქტიულ ცვლილებამდე გამოცადეთ. იხილეთ n8n უსაფრთხოების ცვლადების განმარტებები.

WORKFLOW რისკი

Node-ებს შეუძლიათ უსაფრთხოების საზღვრის გაფართოება

თვითჰოსტინგი workflows-ს მნიშვნელოვან შესაძლებლობებს აძლევს. Code execution, shell access, თვითნებური HTTP requests და მესამე მხარის community nodes რისკს ზრდის. გამორთეთ არასაჭირო ფუნქციები და გაშვებამდე გადაამოწმეთ არასანდო workflow imports.

გამოიყენეთ ზუსტი მხარდაჭერილი კონტროლები: დააკონფიგურირეთ NODES_EXCLUDE გასათიში node-ების JSON array-ით, მაგალითად n8n-nodes-base.executeCommand and n8n-nodes-base.readWriteFile, თუ არ იყენებთ. ზოგი მაღალი რისკის node ახალ ვერსიებში ნაგულისხმევად უკვე დაბლოკილია; ცვლილებამდე გადაამოწმეთ რეალური სია. Node exclusions-ის ოფიციალური დოკუმენტაცია.

n8n-იდან 2.12.0, N8N_SSRF_PROTECTION_ENABLED=true რთავს outbound HTTP requests-ის შემოწმებას შიდა, loopback და metadata მისამართების დიაპაზონებზე. ლეგიტიმურმა შიდა API workflows-მა შეიძლება მუშაობა შეწყვიტოს; საჭიროებისას ვიწროდ allowlist-ში ჩასვით მხოლოდ თქვენ მიერ კონტროლირებადი destinations. ქსელის სეგმენტაცია მთავარ დაცვად შეინარჩუნეთ. Code-node isolation-ისთვის გადაამოწმეთ external task runners. SSRF protection · Task-runner isolation.

Community node-ებიდააყენეთ მხოლოდ სანდო პაკეტები; ისინი თქვენს n8n გარემოში სრულდება.
სარისკო node-ებიგამორიცხეთ node-ები, რომლებიც თქვენს deployment-ს არ სჭირდება, როდესაც მათი შესაძლებლობები workflow-ის განკუთვნილ საზღვრებს სცდება.
SSRFგამოიყენეთ n8n-ის SSRF protection და ქსელის კონტროლები იქ, სადაც workflows-ს შიდა ან metadata endpoints-ზე წვდომა არ უნდა შეეძლოს.
Workflow importsაქტივაციამდე გადაამოწმეთ იმპორტირებული workflows, ავტორიზაციის მონაცემები, expressions და შესრულებადი ნაბიჯები.

აუდიტი და განახლებები

უსაფრთხოება საოპერაციო პროცესია

გაუშვით n8n უსაფრთხოების აუდიტი

ოფიციალური CLI ბრძანებაა `n8n audit`. თუ თქვენი Docker Compose სერვისის სახელია `n8n`, გაუშვით `docker compose exec -T n8n n8n audit` იმ deployment დირექტორიაში. გადაამოწმეთ ხუთი კატეგორია: გამოუყენებელი ავტორიზაციის მონაცემები, სარისკო SQL-query patterns, file-system access, სარისკო/community nodes და instance risks, მათ შორის დაუცველი webhooks და მოძველებული releases. გაასწორეთ შესაბამისი findings და ხელახლა გაუშვით. ეს penetration test არ არის. იხილეთ აუდიტის ოფიციალური გზამკვლევი.

განაახლეთ გააზრებულად

n8n საკმარისად განახლებულ მდგომარეობაში შეინახეთ უსაფრთხოების fixes-ის მისაღებად. ინტერნეტიდან ხელმისაწვდომი ინსტანცია მუდმივად მოძველებულად არ დატოვოთ; გადახედეთ release notes-ს და მნიშვნელოვანი upgrades გამოცადეთ.

აკონტროლეთ ავტორიზაცია

დააკვირდით მოულოდნელ access patterns-ს, workflow ცვლილებებსა და failures-ს. რედაქტორის UI დამატებით შეზღუდეთ, თუ თქვენი საოპერაციო მოდელი ფართო საჯარო ხელმისაწვდომობას არ მოითხოვს.

მოამზადეთ rollback და აღდგენა

მნიშვნელოვან upgrades-მდე შექმენით აღდგენადი სარეზერვო ასლები. Backup scope-ისა და restoration-ის დეტალები ცალკე recovery გზამკვლევს ეკუთვნის.

შეამცირეთ სენსიტიური შესრულებების ისტორია: წარმატებულმა გაშვებებმა შეიძლება მომხმარებლის მონაცემები და tokens შეინახოს. საჭიროებისას დააყენეთ `EXECUTIONS_DATA_SAVE_ON_SUCCESS=none`, შეინარჩუნეთ `EXECUTIONS_DATA_PRUNE=true` და `EXECUTIONS_DATA_MAX_AGE` აირჩიეთ საათებში, მაგალითად 168 (შვიდი დღე). ეს კონფიგურირებადი მაგალითებია და არა იურიდიული retention წესები. ნაკლები ისტორია ნიშნავს ნაკლებ debugging და forensic მონაცემს; running, waiting ან annotated შესრულებები შეიძლება იგივე წესით არ წაიშალოს. იხილეთ შესრულებების retention-ის ოფიციალური დოკუმენტაცია.

სავარაუდო კომპრომეტაცია: შეზღუდეთ მავნე წვდომა მტკიცებულებების განადგურების გარეშე, შეამოწმეთ proxy, host და n8n აქტივობა და შეცვლილი workflows, გააუქმეთ ან შეცვალეთ შესაძლოა გამჟღავნებული upstream credentials, გაასწორეთ მიზეზი და საჭიროებისას აღადგინეთ მხოლოდ გამოცდილი აღდგენადი backups-იდან. გადაამოწმეთ დაზიანებული webhook URLs, editor accounts და connected services; ნუ ჩათვლით, რომ HTTPS, snapshots ან VPS-ის შეძენა incident-response სერვისებს მოიცავს.

შეზღუდეთ, ვის შეუძლია workflows-ის რედაქტირება

რედაქტორზე წვდომა პრივილეგირებული წვდომაა: workflows-ს შეუძლია credentials-ის წაკითხვა, შიდა სისტემების გამოძახება და ძლიერი node-ების შესრულება. მომხმარებლის წვდომა ვიწროდ შეინარჩუნეთ და წაშალეთ ანგარიშები, რომლებსაც აღარ სჭირდება.

გამორთეთ შესაძლებლობები, რომლებსაც არ იყენებთ

შეამცირეთ აპლიკაციის attack surface არასაჭირო public API-ის გამორთვით და მაღალი რისკის node-ების ან ფუნქციების დაბლოკვით, რომლებიც თქვენს საოპერაციო მოდელს არ სჭირდება.

SSRF და secret controls გააზრებულად გამოიყენეთ

workflows-ისთვის, რომლებსაც თვითნებური HTTP requests შეუძლია, შეაფასეთ n8n-ის SSRF protection და საიდუმლოებები workflow code-იდან, საჯარო repositories-იდან და ფართოდ წაკითხვადი environment files-იდან მოაშორეთ.

შეზღუდეთ გამოუყენებელი management endpoints: N8N_PUBLIC_API_DISABLED=true თიშავს n8n public REST API-ს, ხოლო `N8N_PUBLIC_API_SWAGGERUI_DISABLED=true` ცალკე თიშავს მის API playground-ს. ეს მხოლოდ მაშინ გააკეთეთ, როცა ინტეგრაციებს ეს ფუნქციები არ სჭირდება. REST API-ის გამორთვა workflow webhook URLs-ს არ ავთენტიფიცირებს. რედაქტორის მომხმარებლებისთვის გამოიყენეთ MFA, ხოლო ცენტრალიზებული policies მხოლოდ იქ, სადაც თქვენი n8n გამოცემა მხარს უჭერს.

ოფიციალური დოკუმენტაცია: Public API-ის გამორთვა · უსაფრთხოების policy variables · აუდიტის ბრძანებები.

FAQ

n8n VPS უსაფრთხოება: გავრცელებული კითხვები

უნდა იყოს n8n პორტი პირდაპირ გახსნილი?

როდესაც reverse proxy საჯარო შესვლის წერტილია, გამოაქვეყნეთ proxy და აპლიკაციის პორტი მის უკან დატოვეთ, ზედმეტი სერვისების ფართოდ გამოქვეყნების ნაცვლად.

უნდა იყოს PostgreSQL ან Redis საჯარო?

ჩვეულებრივ არა. ისინი ხელმისაწვდომი უნდა იყოს მხოლოდ იმ სისტემებისთვის, რომლებსაც სჭირდება. საჯარო exposure ზრდის attack surface-ს და n8n-ის ჩვეულებრივ მუშაობას არ ეხმარება.

რატომ არის n8n დაშიფვრის გასაღები მნიშვნელოვანი?

ის იცავს n8n-ში შენახულ ავტორიზაციის მონაცემებს და deployment-ის მასშტაბით უცვლელი უნდა დარჩეს. მისი დაკარგვა შეიძლება აღდგენილ მონაცემებში შენახული დაშიფრული ავტორიზაციის მონაცემების გამოყენებას შეუძლებელს ხდიდეს.

უსაფრთხოა community node-ები?

ისინი n8n-ს მესამე მხარის code-ით აფართოებს, ამიტომ მათ software dependencies-ად უნდა შეხედოთ საკუთარი supply-chain და privilege რისკებით. დააყენეთ მხოლოდ ის, რასაც ენდობით და გჭირდებათ.

ხდის HTTPS თვითჰოსტირებულ n8n ინსტანციას უსაფრთხოს?
